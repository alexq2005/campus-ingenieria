Módulo 10 — Data Fetching con TanStack Query

Hacer fetch a mano con useEffect funciona para hello world. En producción no escala: no hay cache, no hay deduplicación, no hay retry, no hay refetch al volver al tab. TanStack Query resuelve TODO esto.

1. El problema de useEffect + fetch

Si codeás todo el data fetching con useEffect manualmente:
  • 3 componentes piden los mismos datos → 3 fetches al backend.
  • Cliente vuelve al tab tras 5 min → datos viejos.
  • Network blip → fallo sin retry.
  • Sin loading/error/success states consistentes.
  • Cache manual = bug factory.

2. ¿Qué es TanStack Query?

Librería para manejar "server state" (datos del backend) en React. Maneja cache, deduplicación, retry, refetch, mutations — todo con una API declarativa.

Antes se llamaba "React Query". En 2026 se llama TanStack Query y soporta Vue, Solid, Svelte también.

3. Instalación y setup

npm install @tanstack/react-query
npm install @tanstack/react-query-devtools  # opcional pero recomendado
// src/main.jsx
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';
import { ReactQueryDevtools } from '@tanstack/react-query-devtools';

const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 1000 * 60,        // 1 minuto antes de marcar como "stale"
      refetchOnWindowFocus: false, // opcional: desactivar si molesta
    },
  },
});

ReactDOM.createRoot(document.getElementById('root')).render(
  <QueryClientProvider client={queryClient}>
    <App />
    <ReactQueryDevtools />
  </QueryClientProvider>
);

4. Tu primer useQuery

import { useQuery } from '@tanstack/react-query';

function Posts() {
  const { data, isLoading, error } = useQuery({
    queryKey: ['posts'],
    queryFn: async () => {
      const res = await fetch('/api/posts');
      if (!res.ok) throw new Error('Falló');
      return res.json();
    },
  });

  if (isLoading) return <p>Cargando...</p>;
  if (error) return <p>Error: {error.message}</p>;

  return (
    <ul>
      {data.map(p => <li key={p.id}>{p.title}</li>)}
    </ul>
  );
}
Qué hace TanStack Query automáticamente:
  • Llama queryFn al montar.
  • Cachea el resultado bajo queryKey (['posts']).
  • Si otro componente hace useQuery({ queryKey: ['posts'] }), REUTILIZA el cache — no hace 2 fetches.
  • Si los datos se vuelven "stale" (pasó staleTime), refetch en background al refocus, al reconectar, al remount.
  • Retry automático en errores transitorios.

5. Query keys con argumentos

function Post({ id }) {
  const { data, isLoading } = useQuery({
    queryKey: ['post', id],
    queryFn: () => fetch(`/api/posts/${id}`).then(r => r.json()),
  });

  if (isLoading) return <p>...</p>;
  return <h1>{data.title}</h1>;
}
Las queryKeys son arrays. Cada combinación distinta es una entrada de cache diferente. ['post', 1] y ['post', 2] se cachean por separado.

7. Mutations (POST/PUT/DELETE)

import { useMutation, useQueryClient } from '@tanstack/react-query';

function CreatePost() {
  const queryClient = useQueryClient();

  const mutation = useMutation({
    mutationFn: async (newPost) => {
      const res = await fetch('/api/posts', {
        method: 'POST',
        body: JSON.stringify(newPost),
      });
      return res.json();
    },
    onSuccess: () => {
      // Invalida la lista de posts → refetch automático
      queryClient.invalidateQueries({ queryKey: ['posts'] });
    },
  });

  function handleSubmit(e) {
    e.preventDefault();
    const title = e.target.title.value;
    mutation.mutate({ title });
  }

  return (
    <form onSubmit={handleSubmit}>
      <input name="title" />
      <button disabled={mutation.isPending}>
        {mutation.isPending ? 'Creando...' : 'Crear'}
      </button>
      {mutation.isError && <p>Error: {mutation.error.message}</p>}
    </form>
  );
}

8. Optimistic updates

Cambiá la UI ANTES de que el servidor confirme. Si falla, rollback:

const mutation = useMutation({
  mutationFn: deletePost,
  onMutate: async (postId) => {
    // Cancela queries en curso
    await queryClient.cancelQueries({ queryKey: ['posts'] });

    // Snapshot del estado previo
    const previous = queryClient.getQueryData(['posts']);

    // Optimistic update
    queryClient.setQueryData(['posts'], (old) =>
      old.filter(p => p.id !== postId)
    );

    // Return context para rollback
    return { previous };
  },
  onError: (err, postId, context) => {
    queryClient.setQueryData(['posts'], context.previous);
  },
  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: ['posts'] });
  },
});

9. Cómo afecta el cache la UX

Estado del cacheQué hace TanStack Query
Sin datosFetch + muestra isLoading
Datos fresh (< staleTime)Devuelve cache, NO fetch
Datos stale (> staleTime)Devuelve cache + fetch en background (UI no parpadea)
Datos stale + window refocusRefetch automático
Componente desmontadoDatos siguen en cache (cacheTime default 5 min) → próxima vez es instant

10. Pagination e Infinite Queries

// Pagination simple
const { data } = useQuery({
  queryKey: ['posts', page],
  queryFn: () => fetchPosts(page),
  placeholderData: (prev) => prev,  // mantener data anterior mientras carga nueva (no flicker)
});

// Infinite scroll
import { useInfiniteQuery } from '@tanstack/react-query';

const { data, fetchNextPage, hasNextPage } = useInfiniteQuery({
  queryKey: ['posts-infinite'],
  queryFn: ({ pageParam = 0 }) => fetchPosts(pageParam),
  initialPageParam: 0,
  getNextPageParam: (lastPage, allPages) => lastPage.nextCursor,
});

  const posts = await fetch('/api/posts').then(r => r.json());  // ⭐ await directo

No necesitás TanStack Query del lado server. PERO si tu componente es Client, sí. Lo profundizamos en M13.

13. Errores típicos

QueryKeys inconsistentes: ['post', 1] en un componente y ['posts', 1] (plural) en otro. Cache no se comparte porque las keys son distintas.
QueryFn que no tira error en !res.ok: si fetch devuelve 404, response.ok es false PERO no tira. TanStack Query no sabe que falló. Hay que tirar manualmente throw new Error.
No invalidar queries tras mutation: hacés POST exitoso pero la lista no se actualiza. Llamá queryClient.invalidateQueries en onSuccess.
useEffect + fetch en proyectos serios: 90% de los problemas que vas a tener (cache stale, refetch, loading) ya están resueltos. No reinventes la rueda.
Usar TanStack Query para client-only state: TanStack Query es para SERVER state (datos del backend). Para estado UI local (modal abierto, theme), useState o Zustand.

✅ Checkpoint

1. ¿Qué problemas resuelve TanStack Query que useEffect+fetch no?

Cache compartido entre componentes, deduplicación de requests, retry automático, refetch al window focus / reconnect, loading/error/success states consistentes, devtools, optimistic updates. TODO el "boilerplate" de server state se elimina.

2. ¿Qué es el queryKey y por qué importa?

Es el identificador de la entrada de cache. Si 2 componentes usan la MISMA queryKey, comparten cache (no doble fetch). Si cambia un elemento del array, se trata como query nueva (útil para params: ['post', id]).

3. ¿Diferencia entre isLoading y isFetching?

isLoading es true SOLO el primer fetch (no hay data aún). isFetching es true CUALQUIER fetch (primero o refetch en background). Para spinner inicial: isLoading. Para indicador discreto de "actualizando": isFetching.

4. ¿Qué hace invalidateQueries?

Marca queries como stale → TanStack Query las refetch al próximo render que las use. Patrón común: tras una mutación POST exitosa, invalidás la lista para que se refetch.

5. ¿Qué es un optimistic update?

Actualizar la UI ANTES de que el servidor confirme. Si falla, rollback. UX percibida como instantánea. Se implementa con onMutate (snapshot + cambio), onError (rollback), onSettled (invalidate).

6. ¿Cuándo usar Zustand en lugar de TanStack Query?

Para client state (UI local): modal abierto, theme, items seleccionados, formularios complejos. TanStack Query es ESPECÍFICAMENTE para server state (datos que vienen del backend y tienen que mantenerse sincronizados).

Respondé sin mirar arriba. Cada pregunta te explica el porqué.

1. Tres componentes hacen useQuery con la misma queryKey: ['posts']. ¿Qué pasa?

La queryKey ES el identificador del cache. Justamente por eso las keys tienen que ser consistentes: ['post', 1] en un componente y ['posts', 1] en otro son dos entradas distintas y el cache no se comparte.

2. ¿Qué diferencia hay entre isLoading e isFetching?

Spinner grande de pantalla vacía → isLoading. Indicador discreto de "actualizando" sin tapar los datos que ya se ven → isFetching. Confundirlos hace que la UI parpadee en cada refetch.

3. Tu queryFn hace fetch y el servidor responde 404. ¿Qué hace falta para que TanStack Query lo tome como error?

fetch solo rechaza la promesa por fallas de red: un 404 o un 500 llegan como respuesta "exitosa" con res.ok en false. Si no tirás vos el error, la query queda en success y cachea el cuerpo del error.

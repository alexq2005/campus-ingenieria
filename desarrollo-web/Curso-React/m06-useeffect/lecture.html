Módulo 06 — useEffect y Efectos Secundarios

useEffect es el hook más mal usado de React. La mayoría de problemas con efectos vienen de usarlo cuando NO hace falta. Este módulo te enseña cuándo usarlo y cuándo evitarlo.

1. ¿Qué es un "efecto secundario"?

Un side effect es algo que pasa FUERA del flujo puro de render. Ejemplos: hacer fetch, suscribirse a un WebSocket, agregar un event listener al window, manipular el DOM directamente, setear localStorage, llamar a librerías externas (Stripe, mapas, charts).
Render = describir UI a partir de estado. Efecto = sincronizar React con algún sistema externo (red, DOM, browser API).

2. La regla #1 de useEffect: a veces NO lo necesitás

React docs (2024) lo dicen explícitamente: "You might not need an Effect". Antes de escribir uno, preguntate si podés:
  • Derivar el valor en cada render (no guardar en estado).
  • Calcular durante el render sin esperar.
  • Ponerlo en un event handler que YA respondía al evento que dispara el efecto.

Ejemplo: NO usar useEffect para esto

// ❌ MAL — usar useEffect para derivar estado
function FullName({ first, last }) {
  const [full, setFull] = useState('');

  useEffect(() => {
    setFull(first + ' ' + last);
  }, [first, last]);

  return <p>{full}</p>;
}

// ✅ BIEN — derivar en cada render
function FullName({ first, last }) {
  const full = first + ' ' + last;
  return <p>{full}</p>;
}

3. Cuándo SÍ usar useEffect

Caso de usoPor qué necesita Effect

Suscribirse a WebSocket / EventSourceSide effect: abrir/cerrar conexión
Agregar listener a window/documentSide effect: tocar API global
setInterval / setTimeoutSide effect: timer del browser
Sincronizar con librería externa (Chart.js, Leaflet)Side effect: instanciar / destruir

4. Anatomía de useEffect

import { useEffect } from 'react';

function Componente() {
  useEffect(() => {
    // Código del efecto: corre DESPUÉS del render
    console.log('Efecto ejecutado');

    return () => {
      // Cleanup: corre ANTES del próximo efecto o al desmontar
      console.log('Cleanup');
    };
  }, [/* dependencias */]);
}
Las 3 partes:
  1. Función del efecto: lo que hace.
  2. Cleanup (opcional, vía return): cómo deshacer/limpiar.
  3. Array de dependencias: cuándo re-ejecutar.

5. El array de dependencias — 3 formas

FormaCuándo corre el efecto
useEffect(fn)Después de CADA render (raro, casi nunca)
useEffect(fn, [])Solo después del primer mount
useEffect(fn, [a, b])Después del mount + cuando a o b cambian

6. Ejemplo: fetch al montar

function Posts() {
  const [posts, setPosts] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    let cancelled = false;

    async function load() {
      try {
        const res = await fetch('/api/posts');
        const data = await res.json();
        if (!cancelled) setPosts(data);
      } catch (err) {
        if (!cancelled) setError(err);
      } finally {
        if (!cancelled) setLoading(false);
      }
    }

    load();

    return () => { cancelled = true; };  // race condition prevention
  }, []);

  if (loading) return <p>Cargando...</p>;
  if (error) return <p>Error: {error.message}</p>;
  return <ul>{posts.map(p => <li key={p.id}>{p.title}</li>)}</ul>;
}
El patrón cancelled es para race conditions: si el componente se desmonta o se vuelve a montar antes de que llegue la response, NO setear estado. Sin esto, podés tener "memory leak" warnings o estado inconsistente.
En 2026, para data fetching real usá TanStack Query (M10). useEffect+fetch funciona pero falta cache, retry, deduplicación, etc. Lo escribimos así para entender el primitivo.

7. Cleanup: el alma de useEffect

La función que devuelve el effect se ejecuta:

  • Antes del próximo efecto (cuando una dependencia cambia).
  • Al desmontar el componente.

Caso: suscripción a evento

function MousePosition() {
  const [pos, setPos] = useState({ x: 0, y: 0 });

  useEffect(() => {
    function handler(e) {
      setPos({ x: e.clientX, y: e.clientY });
    }

    window.addEventListener('mousemove', handler);

    return () => {
      window.removeEventListener('mousemove', handler);  // ⭐ cleanup
    };
  }, []);

  return <p>{pos.x}, {pos.y}</p>;
}
Sin cleanup, cada mount agrega OTRO listener. En SPAs con navegación, terminás con cientos de listeners zombies = memory leak.

Caso: timer

function Clock() {
  const [time, setTime] = useState(new Date());

  useEffect(() => {
    const id = setInterval(() => setTime(new Date()), 1000);
    return () => clearInterval(id);  // ⭐ obligatorio
  }, []);

  return <p>{time.toLocaleTimeString()}</p>;
}

8. Dependencias: tienen que estar TODAS

Si tu efecto usa una variable que viene de props, estado o función, tiene que estar en el array de deps.

// ❌ MAL — userId NO está en deps; el efecto usa el viejo
useEffect(() => {
  fetch(`/api/users/${userId}`);
}, []);

// ✅ BIEN
useEffect(() => {
  fetch(`/api/users/${userId}`);
}, [userId]);
El ESLint plugin react-hooks/exhaustive-deps te avisa de estas omisiones. Tomá la advertencia en serio — el 95% de las veces hay bug real.

9. Efectos en serie por dependencias

function UserProfile({ userId }) {
  const [user, setUser] = useState(null);

  // Re-ejecuta cuando cambia userId (por ej, navegás a otro usuario)
  useEffect(() => {
    let cancelled = false;
    fetch(`/api/users/${userId}`)
      .then(r => r.json())
      .then(u => { if (!cancelled) setUser(u); });
    return () => { cancelled = true; };
  }, [userId]);

  if (!user) return <p>Cargando...</p>;
  return <h2>{user.nombre}</h2>;
}

10. StrictMode y double-mount en dev

En modo dev, React 18+ monta tus componentes 2 veces para que detectes efectos no-idempotentes. Si tu efecto loguea "Hola" 2 veces en dev, ES EL COMPORTAMIENTO ESPERADO. En producción solo corre 1 vez. Si te molesta, es porque tu efecto necesita cleanup correcto.

11. Anti-patrón: usar effect para reaccionar a evento

// ❌ MAL — el efecto sigue al estado
function Form() {
  const [submitted, setSubmitted] = useState(false);

  useEffect(() => {
    if (submitted) {
      analytics.track('form_submit');
      router.push('/thanks');
    }
  }, [submitted]);

  return <button onClick={() => setSubmitted(true)}>Submit</button>;
}

// ✅ BIEN — el handler hace las dos cosas
function Form() {
  function handleSubmit() {
    analytics.track('form_submit');
    router.push('/thanks');
  }

  return <button onClick={handleSubmit}>Submit</button>;
}
Si la acción es respuesta a un EVENTO de usuario (click, submit, change), ponela en el HANDLER. useEffect es para sincronizar con sistemas externos, no para encadenar acciones tras eventos.

12. useEffect vs useLayoutEffect

HookCuándo correCuándo usar
useEffectDespués de pintar (browser ya mostró frame)99% de casos — fetch, listeners, timers
useLayoutEffectDespués del render, antes del paint (sincrónico)Medir DOM, evitar flicker visual
Si dudás, usá useEffect. useLayoutEffect solo cuando ves "salto" visual al medir un elemento del DOM y aplicar el resultado.

13. Casos reales útiles

Cambiar el título de la página

useEffect(() => {
  document.title = `Posts (${unread})`;
  return () => { document.title = 'App'; };
}, [unread]);

Atajos de teclado

useEffect(() => {
  function onKey(e) {
    if (e.key === 'Escape') onClose();
  }
  window.addEventListener('keydown', onKey);
  return () => window.removeEventListener('keydown', onKey);
}, [onClose]);

Sincronizar con localStorage

useEffect(() => {
  localStorage.setItem('theme', theme);
}, [theme]);

14. Errores comunes con useEffect

Dependencias incompletas: el efecto usa una variable que no está en deps. ESLint te avisa. Resolver: agregarla o refactorizar para que no dependa.
Loop infinito: efecto que cambia un estado del cual depende. useEffect(() => setX(x+1), [x]) renderiza para siempre.
Sin cleanup en listeners/timers: cada mount agrega más listeners. Memory leak garantizado.
Usar useEffect para derivar estado: 90% del tiempo no hace falta. Calculá en cada render o derivá.
Async function como callback de useEffect: useEffect(async () => ...) es error — useEffect espera función que devuelve cleanup, no Promise. Definí async ADENTRO y llamala.
Setear estado en cada render: si tu efecto siempre llama setX sin condición, va a haber un re-render extra inútil. Solo setear cuando hay cambio real.

✅ Checkpoint

1. ¿Para qué sirve useEffect?

Sincronizar React con sistemas EXTERNOS (red, DOM, browser APIs, librerías). NO es para encadenar lógica React-interna — eso va en handlers o cálculos derivados.

2. ¿Qué hace el cleanup?

Se ejecuta antes del próximo efecto (cuando cambia una dependencia) y al desmontar el componente. Sirve para "deshacer" lo del efecto: remover listeners, cancelar timers, abortar fetches, cerrar WebSockets.

3. ¿Por qué el array de dependencias debe ser completo?

Porque si una variable usada dentro del efecto cambia y NO está en deps, el efecto NO se re-ejecuta — usa el valor viejo (stale closure). Causa bugs sutiles de sincronización. ESLint te avisa.

4. ¿Por qué los efectos corren 2 veces en dev (React 18)?

StrictMode monta tus componentes 2 veces a propósito para detectar efectos no-idempotentes (los que rompen si se ejecutan 2 veces). En producción solo corre 1 vez. La solución es asegurar cleanup correcto, no "evitar el comportamiento".

5. ¿Cuándo NO usar useEffect?

Para derivar estado (calculá durante el render), para responder a eventos de usuario (poné en handler), para transformar props (calculá en el render), para datos del backend en producción (usá TanStack Query / SWR).

6. ¿Diferencia entre useEffect y useLayoutEffect?

useEffect corre DESPUÉS del paint (el browser ya pintó el frame). useLayoutEffect corre antes del paint, sincrónico al render. Solo usar useLayoutEffect si necesitás medir el DOM y aplicar cambios sin flicker visual.

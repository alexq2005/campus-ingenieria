Parte 1 — TypeScript con React

1. ¿Por qué TypeScript?

TS te avisa de bugs ANTES de runtime: usás una prop que no existe, le pasás un string a un componente que espera number, llamás un método inexistente. Más confianza al refactorizar grandes apps.
En 2026 NO es opcional para apps profesionales. Las ofertas de trabajo casi todas requieren TS. Aprenderlo es no-negociable.

7. Tipar custom hooks

function useLocalStorage<T>(key: string, initial: T): [T, (v: T) => void] {
  const [value, setValue] = useState<T>(() => {
    const stored = localStorage.getItem(key);
    return stored ? JSON.parse(stored) : initial;
  });

  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);

  return [value, setValue];
}

// Uso — T se infiere
const [theme, setTheme] = useLocalStorage('theme', 'light');         // T = string
const [count, setCount] = useLocalStorage('count', 0);               // T = number
const [user, setUser] = useLocalStorage<User | null>('user', null);  // T explícito

11. Server Components — el cambio fundamental

Por DEFAULT, los componentes en App Router corren EN EL SERVIDOR. Pueden hacer DB queries directamente, leer archivos, usar secrets:

// app/posts/page.tsx — Server Component (no 'use client')
import { db } from '@/lib/db';

export default async function PostsPage() {
  const posts = await db.posts.findMany();   // ⭐ query directa a la DB

  return (
    <ul>
      {posts.map(p => <li key={p.id}>{p.title}</li>)}
    </ul>
  );
}
El JS de Server Components NUNCA llega al browser. Cero hidration cost para ese componente. La response es HTML directo.

12. Client Components — cuando necesitás interactividad

// app/components/Counter.tsx
'use client';   // ⭐ directiva al inicio del archivo

import { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}
¿Cuándo Client vs Server?
  • Usás useState, useEffect, eventos onClick → Client.
  • Solo renderizás HTML estático con data del backend → Server.
  • Por default, mantené Server. Marcá Client solo donde hace falta.

13. Server Actions

Funciones marcadas 'use server' que corren en el servidor pero se llaman desde el cliente:

// app/actions.ts
'use server';

import { db } from '@/lib/db';
import { revalidatePath } from 'next/cache';

export async function createPost(formData: FormData) {
  const title = formData.get('title') as string;
  await db.posts.create({ data: { title } });
  revalidatePath('/posts');  // invalida cache de esta ruta
}

// app/posts/new/page.tsx
import { createPost } from '@/app/actions';

export default function NewPostPage() {
  return (
    <form action={createPost}>
      <input name="title" />
      <button>Crear</button>
    </form>
  );
}
El form se envía sin escribir fetch ni endpoint. La función createPost corre en el servidor. Es como un RPC pero más simple.

19. Errores típicos

Usar hooks en Server Components: error. Hooks solo en Client. Si necesitás useState, marca el archivo con 'use client'.
Importar Client en Server sin marcar: si Server Component renderiza Client Component, marcá el Client con 'use client' arriba.
Cliente "use client" arriba pero usa fetch del server: si pasaste a Client, ya no podés hacer DB queries directas. Usás fetch a una API route.
Tipos any regados: derrota el propósito de TS. Si TS se queja, RESOLVÉ el tipo, no escapes con any.
tsconfig sin strict: true: TS sin strict atrapa la mitad de bugs. Activá siempre.
Bundle con todo en Client: si todo es 'use client', perdés la ventaja de RSC (bundle chico, no hidration). Default Server, Client solo donde hace falta.

✅ Checkpoint

1. ¿Por qué TypeScript en React?

Atrapa bugs en compile-time (props mal pasadas, métodos inexistentes, refactors rotos). Mejora autocomplete del IDE. En 2026, requisito casi universal en ofertas profesionales.

2. ¿Diferencia entre Server y Client Components en Next.js 15?

Server (default): corren solo en servidor, pueden hacer DB queries directo, NO usan hooks. Su JS no llega al browser. Client (marcado con 'use client'): corren en browser, usan hooks, manejan interactividad.

3. ¿Cómo funciona Server Actions?

Función marcada con 'use server' que corre en el servidor. Se llama desde el cliente vía form action o programáticamente. Sin necesidad de escribir API route ni fetch. Next.js hace el RPC por vos.

4. ¿Cuándo Next.js vs Vite + React Router?

Next.js: cuando necesitás SEO (SSR/SSG), fullstack con DB, o vas a deployar en Vercel. Vite + RR: SPA pura sin SSR, extensión, Electron, o cuando querés más control.

5. ¿Qué hace revalidatePath?

Invalida la cache de Next.js para una ruta específica. Después de una mutation (Server Action), llamás revalidatePath para que la próxima visita reflje el nuevo dato sin esperar TTL.

6. ¿Cuál es la regla de oro de Server vs Client?

Por default mantené Server. Pasá a Client SOLO cuando necesitás useState/useEffect/eventos. Marcá Client en componentes hoja, no en el padre. Así maximizás los beneficios de RSC (menos JS, menos hidration).

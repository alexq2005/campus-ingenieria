RS2 — Concurrent React: transiciones, Suspense y streaming

RS2.0 Por qué este módulo: "concurrente" no significa multihilo

En RS1 viste que React construye un árbol de fibers y que el render está partido en dos fases: render (calcular qué cambió, sin tocar el DOM) y commit (aplicar los cambios). Ese diseño no existe por elegancia arquitectónica. Existe para habilitar exactamente una cosa: que la fase de render pueda pausarse a la mitad, tirarse a la basura y volver a empezar.

💡 La tesis del módulo. React sigue corriendo en un solo hilo, el del navegador. "Concurrente" acá significa que React trocea el trabajo de render y le devuelve el control al browser cada pocos milisegundos, para que pueda pintar, responder a un click o procesar una tecla. La consecuencia profunda no es de rendimiento: es semántica. Tu función componente puede ejecutarse para un render que después se descarta. Todo lo que asumía "esto corre una vez y termina" deja de ser cierto.

Mucha gente aprende Concurrent React como una lista de hooks nuevos: useTransition, useDeferredValue, use. Así aprendido, se convierte en cargo cult: se envuelve todo en startTransition "por las dudas" y la app queda peor. La forma útil de entenderlo es al revés: primero el modelo de ejecución, y los hooks después, como la API que te deja participar de ese modelo.

La analogía que sí sirve. Un scheduler de sistema operativo con un solo núcleo. No hay paralelismo: hay quantum. React se toma ~5 ms de CPU, mira si el navegador tiene algo urgente (shouldYield()), y si lo hay, guarda el puntero al fiber donde iba y devuelve el control. Después retoma. Si mientras tanto llegó una actualización más urgente, abandona el trabajo hecho y arranca de nuevo desde arriba con el estado nuevo. Ese "abandona el trabajo hecho" es la fuente de todos los bugs sutiles de este módulo.

Y hay un detalle que casi nadie tiene claro, que va a ser el hilo conductor del worked example:

📌 La fase de render se puede interrumpir. La fase de commit, no. Cuando React termina de calcular el árbol nuevo, aplica todas las mutaciones al DOM de corrido, sincrónicamente, sin ceder el control. Insertar 5.000 nodos es una tarea larga que ningún scheduler puede partir. Por eso las transiciones mejoran la respuesta al input y no arreglan el frame en el que aparece la lista.

RS2.1 El modelo de prioridades: urgente vs transición

Internamente React clasifica cada actualización en un lane (un bit dentro de un bitmask de 31 posiciones). No necesitás manejar lanes a mano, pero sí necesitás saber que existen cuatro grandes categorías, porque son las que explican por qué dos setState escritos uno al lado del otro se comportan distinto:

PrioridadQué la disparaComportamiento
Discreta / sincrónicaclick, keydown, input, submitSe procesa antes del próximo paint. No se interrumpe.
Continuamousemove, scroll, dragUrgente, pero se puede colapsar: si llegan diez, importa la última.
DefaultsetState desde un useEffect, una promesa, un timerSe procesa apenas se pueda, interrumpible.
TransiciónstartTransition, useDeferredValueExplícitamente no urgente. Interrumpible y descartable.

El caso canónico donde esto importa es una única interacción que dispara dos actualizaciones con urgencias distintas. Tipear en un buscador es exactamente eso:

function Buscador() {
  const [texto, setTexto] = useState("");      // (A) lo que ve el usuario en el input
  const [query, setQuery] = useState("");      // (B) lo que filtra 5.000 resultados

  function onChange(e) {
    setTexto(e.target.value);                  // urgente: la letra tiene que aparecer YA
    startTransition(() => setQuery(e.target.value)); // puede esperar: los resultados
  }

  return (
    <>
      <input value={texto} onChange={onChange} />
      <Resultados query={query} />
    </>
  );
}

Sin la transición, ambas actualizaciones viajan en el mismo lane sincrónico: React tiene que terminar de renderizar los 5.000 resultados antes de poder pintar la letra. Con la transición, React hace un commit chiquito con la letra, pinta, y después arranca el render caro — que además puede abandonar en cuanto la persona toque otra tecla.

Qué siente el usuario, concretamente. Sin transición: tipeás rápido y las letras aparecen a los tirones, en bloque, con 200–400 ms de retraso. Con transición: las letras aparecen instantáneas y los resultados llegan un poquito después, quizás con un estado de "actualizando". La cantidad total de trabajo de CPU no bajó — en general subió. Lo que cambió es en qué orden se hace y cuándo se pinta. Esta distinción entre latencia percibida y trabajo total es todo el módulo en una frase.

RS2.2 useTransition y startTransition

Hay dos formas de marcar una actualización como transición y no son intercambiables:

import { startTransition, useTransition } from "react";

// 1) La función suelta: marca la actualización, no te da estado pendiente.
//    Sirve fuera de componentes (un store, un handler de router, un módulo).
startTransition(() => setTab("perfil"));

// 2) El hook: además te devuelve isPending para renderizar feedback.
const [isPending, startTransition] = useTransition();

El hook es el que vas a usar el 90% del tiempo, porque el problema real de diferir algo es que el usuario no sabe si su acción se registró:

function Tabs() {
  const [tab, setTab] = useState("inicio");
  const [isPending, startTransition] = useTransition();

  function seleccionar(siguiente) {
    startTransition(() => setTab(siguiente));
  }

  return (
    <>
      <nav>
        {["inicio", "posts", "config"].map((t) => (
          <button
            key={t}
            onClick={() => seleccionar(t)}
            aria-current={t === tab ? "page" : undefined}
          >
            {t}
          </button>
        ))}
      </nav>

      {/* La pestaña vieja sigue visible e interactiva mientras se prepara la nueva */}
      <div style={{ opacity: isPending ? 0.6 : 1, transition: "opacity .15s" }}>
        <Panel tab={tab} />
      </div>
    </>
  );
}
Fijate en el detalle del opacity: la pestaña vieja no se reemplaza por un spinner. Ese es el punto de las transiciones. Un spinner destruye contexto (la persona pierde de vista dónde estaba) y provoca layout shift. Atenuar lo viejo mantiene el layout y comunica "estoy trabajando" sin borrar nada.

El error más común: meter el fetch en vez del cambio de estado

Este es el malentendido número uno. Alguien tiene una búsqueda lenta y escribe esto:

// ❌ Confusión de origen: la lentitud es de red, no de render
function Buscador() {
  const [isPending, startTransition] = useTransition();
  const [datos, setDatos] = useState([]);

  function buscar(q) {
    startTransition(async () => {
      const r = await fetch(`/api/buscar?q=${q}`);
      setDatos(await r.json());
    });
  }
  // "sigue lento" — obvio: startTransition no acelera la red
}
Una transición no hace nada más rápido. No cachea, no cancela requests, no baja la latencia del servidor. Lo único que hace es decirle al scheduler de React "esta actualización puede esperar y podés abandonarla". Si tu problema es que el endpoint tarda 800 ms, la transición te da un isPending lindo y cero milisegundos de mejora. El diagnóstico previo —¿es render caro o es red lenta?— no es opcional.

Ahora bien, ese código no está mal escrito: en React 19 las transiciones asíncronas son oficialmente soportadas y se llaman Actions. La función que pasás puede ser async, y las actualizaciones que hagas después del await siguen marcadas como transición, con isPending en true durante todo el proceso. Esto en React 18 estaba roto: el estado se perdía cruzando el await.

// ✅ Action correcta (React 19+): isPending cubre red + render
function GuardarPerfil({ id }) {
  const [isPending, startTransition] = useTransition();
  const [error, setError] = useState(null);

  function onSubmit(formData) {
    startTransition(async () => {
      const res = await actualizarPerfil(id, formData);  // el await va ADENTRO
      if (res.error) { setError(res.error); return; }     // este setState sigue en la transición
      setError(null);
    });
  }

  return (
    <form action={onSubmit}>
      <input name="nombre" />
      <button disabled={isPending}>{isPending ? "Guardando…" : "Guardar"}</button>
      {error && <p role="alert">{error}</p>}
    </form>
  );
}
El await tiene que estar adentro del callback. Si escribís const r = await fetch(...); startTransition(() => setDatos(r)), solo el setState queda en la transición: isPending nunca cubre la espera de red y tu botón no se deshabilita mientras el request viaja. Es la diferencia entre "la transición envuelve la operación" y "la transición envuelve el último paso".

El otro error: meter el input controlado adentro

// ❌ El input se siente PEOR que antes
function Mal() {
  const [texto, setTexto] = useState("");
  const [isPending, startTransition] = useTransition();

  return (
    <input
      value={texto}
      onChange={(e) => startTransition(() => setTexto(e.target.value))}
    />
  );
}

Un input controlado necesita que su value se actualice de forma urgente y garantizada. Al ponerlo en una transición, esa actualización pasa a ser interrumpible y descartable: si el usuario tipea rápido, React puede abandonar renders intermedios y el cursor salta, se comen letras o el valor "rebota". React incluso te lo advierte en la documentación como pitfall explícito.

📌 La regla de oro de las transiciones. Lo que la persona acaba de escribir o tocar va urgente. Lo que se deriva de eso y es caro va en la transición. Nunca al revés. Si te encontrás queriendo diferir el valor de un input, lo que necesitás es useDeferredValue sobre la parte cara, no useTransition sobre el input.

RS2.3 useDeferredValue: cuando no controlás el setState

useDeferredValue ataca el mismo problema desde el otro lado. En vez de marcar la actualización como no urgente, marca un valor como "puede ir atrasado":

function Buscador() {
  const [texto, setTexto] = useState("");
  const textoDiferido = useDeferredValue(texto);

  return (
    <>
      <input value={texto} onChange={(e) => setTexto(e.target.value)} />
      <Resultados query={textoDiferido} />
    </>
  );
}

Lo que pasa por dentro es un render doble: cuando texto cambia, React renderiza primero con textoDiferido viejo (rapidísimo, porque nada caro cambió) y commitea eso para que la letra aparezca. Después agenda en segundo plano un render con el valor nuevo, interrumpible. Si llega otra tecla antes de terminarlo, lo descarta y arranca de nuevo.

⚠️ El detalle que hace que funcione o que sea inútil: la memoización. Si <Resultados> no está envuelto en memo, el render "rápido" con el valor viejo también re-renderiza los 5.000 resultados. Resultado: hacés dos renders caros por tecla en vez de uno, y la app queda medible y notoriamente peor. useDeferredValue sin memoización es un anti-patrón, no una optimización. 
// ✅ La forma correcta: el hijo caro salta el render cuando la prop no cambió
const Resultados = memo(function Resultados({ query }) {
  const items = useMemo(() => filtrar(TODOS, query), [query]);
  return (
    <ul>
      {items.map((it) => <li key={it.id}>{it.nombre}</li>)}
    </ul>
  );
});
Con el React Compiler (RS3) esta memoización deja de ser manual: el compilador la inserta por vos. Pero el requisito no desaparece — sigue siendo necesario que el subárbol caro pueda saltarse el render intermedio. Cambia quién escribe el memo, no la física del asunto.

React 19 agregó un segundo argumento, initialValue, que resuelve el caso del primer render: en vez de renderizar de una con el valor real (caro) o con undefined (feo), arrancás con un valor liviano y React agenda el real en segundo plano.

function Listado({ query }) {
  // Primer render: usa "" (barato). Después va al valor real en background.
  const diferido = useDeferredValue(query, "");
  const desactualizado = diferido !== query;

  return (
    <div aria-busy={desactualizado}>
      {desactualizado && <span className="hint">actualizando…</span>}
      <Resultados query={diferido} />
    </div>
  );
}
Ese diferido !== query es el equivalente casero de isPending. useDeferredValue no te devuelve un booleano, pero comparar el valor diferido contra el actual te dice exactamente lo mismo: hay un render en vuelo. Sumale aria-busy y el estado también existe para lectores de pantalla, no solo para los ojos.

Usá useTransition. ¿El valor te llega ya hecho —como prop, desde un contexto, desde una librería de estado— y no tenés dónde meter el startTransition? Usá useDeferredValue. Escribir librerías genéricas cae casi siempre del lado de useDeferredValue.

RS2.4 Suspense a fondo: qué suspende de verdad

<Suspense> es un límite que dice "si algo acá abajo todavía no está listo, mostrá este fallback". La confusión clásica es creer que capta cualquier estado de carga. No: capta un mecanismo muy específico.

// ✅ Estas tres cosas SÍ suspenden
const Panel = lazy(() => import("./Panel"));       // 1) código: React.lazy

function Perfil({ promesaUsuario }) {
  const usuario = use(promesaUsuario);              // 2) datos: use(promise)
  return <h1>{usuario.nombre}</h1>;
}

// 3) Server Components en streaming, y librerías integradas
//    (useSuspenseQuery de TanStack Query, Relay, el router de tu framework)
// ❌ Esto NO suspende. Jamás. El fallback nunca se muestra.
function Perfil({ id }) {
  const [usuario, setUsuario] = useState(null);
  useEffect(() => {
    fetch(`/api/u/${id}`).then((r) => r.json()).then(setUsuario);
  }, [id]);

  if (!usuario) return <Spinner />;   // el loading lo manejás vos, a mano
  return <h1>{usuario.nombre}</h1>;
}
Envolver un componente con useEffect + useState en un <Suspense> no hace nada. El componente renderiza inmediato devolviendo null o su propio spinner; nunca "lanza" nada que el límite pueda interceptar. Es un error frecuentísimo en migraciones: se agregan boundaries por todos lados y no cambia absolutamente nada, porque la capa de datos nunca se integró con Suspense.

La interacción clave: Suspense dentro de una transición

Acá es donde Suspense y las transiciones se cruzan, y es el comportamiento que más gente desconoce:

function App() {
  const [pagina, setPagina] = useState("home");
  const [isPending, startTransition] = useTransition();

  return (
    <>
      <button onClick={() => startTransition(() => setPagina("perfil"))}>
        Ir al perfil
      </button>
      <Suspense fallback={<Skeleton />}>
        <Pagina nombre={pagina} />
      </Suspense>
    </>
  );
}
💡 El comportamiento. Si el cambio de página suspende y la actualización no está en una transición, React esconde el contenido actual y muestra el <Skeleton />: la pantalla parpadea de contenido bueno a esqueleto y de vuelta. Si sí está en una transición, React mantiene la página vieja en pantalla, no muestra el fallback, y pone isPending en true hasta que la nueva esté lista. El fallback queda reservado para la primera carga, cuando todavía no hay nada bueno que preservar.

Esto convierte a startTransition en la herramienta de navegación por defecto: es lo que hace que cambiar de ruta no sea un flash blanco. Todos los routers modernos de React envuelven las navegaciones en transiciones por esta razón.

Dónde poner los límites

El error de principiante es un boundary gigante:

// ❌ Un solo límite: si cualquier cosa tarda, TODA la pantalla es un esqueleto
<Suspense fallback={<PantallaCompletaCargando />}>
  <Header />
  <Sidebar />
  <Feed />         {/* el lento es este */}
  <Footer />
</Suspense>
// ✅ Límites por unidad significativa: lo rápido se ve rápido
<>
  <Header />                        {/* datos que ya están: sin boundary */}
  <div className="layout">
    <Suspense fallback={<SidebarSkeleton />}>
      <Sidebar />
    </Suspense>
    <Suspense fallback={<FeedSkeleton filas={5} />}>
      <Feed />
    </Suspense>
  </div>
  <Footer />
</>

Pero el extremo opuesto también es malo: un boundary por cada tarjeta produce el efecto popcorn — quince pedacitos que aparecen en momentos distintos, cada uno empujando el layout. La heurística es:

1. Un límite envuelve cosas que tiene sentido que aparezcan juntas. Si la persona no puede usar la mitad de un widget sin la otra mitad, van adentro del mismo límite.
2. El fallback tiene que ocupar el mismo espacio que el contenido real. Un skeleton con la altura correcta convierte una carga en algo invisible; un <p>Cargando…</p> de 20 px que después se reemplaza por 600 px de contenido es CLS puro y te destroza Core Web Vitals.
3. Lo que está por encima del pliegue y no depende de datos, va fuera de todo límite. Eso es el shell, y en streaming es literalmente lo primero que se manda (RS2.5).
// El skeleton correcto: misma estructura, mismas dimensiones, sin texto que salte
function FeedSkeleton({ filas = 5 }) {
  return (
    <ul aria-hidden="true" className="skeleton">
      {Array.from({ length: filas }, (_, i) => (
        <li key={i} style={{ height: 96, marginBottom: 12 }} />
      ))}
    </ul>
  );
}
Cuidado con las key. Cambiar la key de un <Suspense> lo resetea: se vuelve a montar y sí muestra el fallback, incluso dentro de una transición. Es útil a propósito (querés el esqueleto al cambiar de usuario) y es una fuente de parpadeos accidentales cuando la key incluye algo que cambia más seguido de lo que pensabas.

RS2.5 Streaming SSR y el batching de reveals de React 19.2

El SSR clásico era renderToString: bloqueante, todo o nada. El servidor esperaba a tener el HTML completo y recién ahí mandaba el primer byte. Una consulta lenta arruinaba el TTFB de toda la página. El streaming rompe esa atadura:

// Node.js
import { renderToPipeableStream } from "react-dom/server";

app.get("/*", (req, res) => {
  const { pipe, abort } = renderToPipeableStream(<App url={req.url} />, {
    bootstrapScripts: ["/client.js"],

    onShellReady() {
      // El "shell" es todo lo que está FUERA de límites de Suspense.
      // Apenas está listo, empezamos a mandar bytes: TTFB bajo y estable.
      res.statusCode = 200;
      res.setHeader("Content-Type", "text/html");
      pipe(res);
    },

    onShellError(error) {
      // Falló lo esencial: no hay página. Acá sí devolvés 500.
      res.statusCode = 500;
      res.send("<h1>Error</h1>");
    },

    onAllReady() {
      // Todo resuelto. Es el hook para crawlers o generación estática.
    },

    onError(error) {
      // Falló algo DENTRO de un boundary: la página igual se sirve,
      // ese pedazo se recupera en el cliente. Loguealo, no lo tragues.
      logger.error(error);
    },
  });

  setTimeout(abort, 10_000); // presupuesto de tiempo duro
});
// Runtimes con Web Streams (edge, Deno, Bun, Cloudflare Workers)
import { renderToReadableStream } from "react-dom/server";

const stream = await renderToReadableStream(<App />, {
  bootstrapScripts: ["/client.js"],
  onError(error) { logger.error(error); },
});

// allReady permite decidir: streaming para humanos, HTML completo para bots
if (esCrawler(request)) await stream.allReady;

return new Response(stream, {
  headers: { "content-type": "text/html" },
});

El mecanismo de transporte es más ingenioso de lo que parece. Para cada boundary pendiente, el servidor manda primero el HTML del fallback. Cuando los datos llegan, manda el HTML real dentro de un <div hidden> al final del documento, más un <script> minúsculo que mueve esos nodos a su lugar y borra el fallback. No hace falta que el bundle de React haya cargado: funciona con HTML y unas líneas de JS inline.

La mejora de React 19.2: los reveals se batchean

💡 El problema visual que resuelve. Hasta 19.1, durante el streaming cada boundary se revelaba apenas llegaba su HTML, uno por uno. Una página con ocho boundaries que resolvían en 300, 310, 340, 350, 380 ms producía cinco reflows separados en 80 ms: contenido saltando, texto corriéndose, el botón que ibas a tocar moviéndose de lugar. En el cliente esto no pasaba, porque React ya aplicaba un throttle a los reveals para agruparlos. El servidor y el cliente se comportaban distinto ante la misma página.

React 19.2 alineó los dos: ahora los límites de Suspense batchean sus reveals durante el streaming, con la misma cadencia con la que lo hace el cliente. Los boundaries que terminan cerca en el tiempo se revelan juntos, en menos pasos y más grandes.

AspectoAntes (≤ 19.1)React 19.2
Cadencia de revealsUno por uno, apenas llega cada unoAgrupados con throttle, como en el cliente
Reflows percibidosUno por boundaryUno por grupo
Consistencia servidor/clienteDistinta: la misma página se veía distinta según de dónde vinieraIgual en los dos caminos
Trabajo total—Igual: es scheduling de reveals, no menos bytes
Es la misma lección de useDeferredValue en otra capa: no se hizo menos trabajo, se ordenó mejor. Un contenido que aparece 40 ms más tarde pero sin arrastrar el layout se percibe más rápido que uno que aparece antes y hace saltar la página. Si venís de 19.0/19.1 y tu página tenía muchos boundaries chicos, actualizar te da esta mejora sin tocar una línea de código.

Hidratación selectiva

La otra mitad del streaming pasa en el cliente. hydrateRoot no espera a tener todo el HTML: hidrata el shell primero y después cada boundary a medida que su contenido llega. Y hay un detalle brillante:

📌 Si el usuario hace click en una parte que todavía no se hidrató, React prioriza hidratar esa parte primero y después reproduce el evento. La interacción no se pierde. Es la razón concreta por la que muchos boundaries bien puestos mejoran la interactividad real, no solo la métrica: la página se vuelve usable por pedazos, empezando por el pedazo que a la persona le importa. 
import { hydrateRoot } from "react-dom/client";

hydrateRoot(document.getElementById("root"), <App />, {
  // Se dispara cuando React se recupera de un error o de un mismatch.
  // NO es fatal, pero es exactamente lo que querés en tu telemetría:
  // un pico acá suele ser un bug de hidratación en producción.
  onRecoverableError(error, errorInfo) {
    telemetria.enviar("hydration-recoverable", {
      mensaje: error.message,
      componentStack: errorInfo.componentStack,
    });
  },
});
React 19.2 sumó además pre-renderizado parcial: prerender genera el shell estático (cacheable en un CDN) y resume completa el resto en el request, retomando el stream desde donde quedó. Es la combinación de "estático rápido" con "datos frescos" sin duplicar el árbol. El detalle fino corresponde a RS4, cuando entren Server Components.

RS2.6 Hidratación: qué es, por qué es cara y cómo se depuran los mismatch

Hidratar no es "activar el HTML". React ejecuta todo el árbol de componentes igual que en un render normal —construye fibers, corre hooks, calcula el resultado— pero en vez de crear nodos DOM, va comparando contra los que ya existen y les adosa listeners y refs.

Es como recibir una casa construida y tener que recorrerla habitación por habitación con los planos en la mano, verificando que cada pared esté donde dice el plano y conectando la electricidad. Recibir la casa hecha te ahorró la obra gruesa (crear el DOM, el primer layout, el primer paint), pero el recorrido completo lo hacés igual. Por eso el HTML aparece rápido y la página tarda un rato más en responder: ese hueco entre "se ve" y "funciona" es la hidratación, y es lo que mide el INP de la primera interacción.

Los mismatch y su origen real

Un mismatch es que el HTML que produjo el cliente no coincide con el que mandó el servidor. Casi siempre viene de una de estas cinco causas:

Cómo se depuran de verdad

1. Leé el diff. React 19 unificó los errores de hidratación en un único mensaje que muestra el árbol con + y - marcando qué renderizó el servidor y qué el cliente. Antes eran tres warnings crípticos; ahora el mensaje suele nombrar el componente exacto. Empezá siempre por ahí, no por adivinar.
2. Descartá extensiones. Ventana de incógnito sin extensiones. Si el mismatch desaparece, no era tu código y te ahorraste medio día. Este paso va segundo porque es el más barato.
3. Comparativa de HTML crudo. curl de la URL contra el innerHTML del cliente antes de hidratar. Un diff de texto plano encuentra el anidamiento inválido en segundos, que es la causa que más cuesta ver leyendo JSX.
4. Bisección por boundary. Si el diff no alcanza, comentá mitades del árbol. Con boundaries bien puestos la bisección es casi gratis: cada uno es una unidad aislable.
5. Dejalo instrumentado. onRecoverableError en telemetría. Los mismatch que solo aparecen con datos reales o zonas horarias específicas no se reproducen en tu máquina — se detectan con una métrica.

RS2.7 use(): leer una promesa o un contexto durante el render

use es la API que integra promesas con Suspense. Es la primera cosa en React que se parece a un hook pero no lo es: se puede llamar condicionalmente y dentro de loops, porque no guarda estado en el slot de hooks del fiber.

import { use, Suspense } from "react";

function Perfil({ promesaUsuario }) {
  const usuario = use(promesaUsuario);   // suspende hasta que resuelva
  return <h1>{usuario.nombre}</h1>;
}

function Pantalla({ promesaUsuario }) {
  return (
    <ErrorBoundary fallback={<p>No se pudo cargar</p>}>
      <Suspense fallback={<Skeleton />}>
        <Perfil promesaUsuario={promesaUsuario} />
      </Suspense>
    </ErrorBoundary>
  );
}
// use(context): legal condicionalmente. useContext no lo es.
function Item({ destacado }) {
  if (destacado) {
    const tema = use(TemaContext);       // ✅ dentro de un if
    return <li className={tema.clase}>…</li>;
  }
  return <li>…</li>;
}
⚠️ El anti-patrón que rompe todo: crear la promesa en el render. Un componente cliente que hace use(fetch(url)) crea una promesa nueva en cada render. React suspende, la promesa resuelve, React re-renderiza, se crea otra promesa nueva, suspende de nuevo… loop infinito con requests infinitos. La promesa tiene que ser estable: creada en un Server Component y bajada como prop, guardada en un caché, o entregada por una librería que hace la deduplicación por vos. 
// ❌ Loop infinito
function Malo({ id }) {
  const u = use(fetch(`/api/u/${id}`).then((r) => r.json()));
  return <h1>{u.nombre}</h1>;
}

// ✅ Caché a nivel módulo: misma clave, misma instancia de promesa
const cache = new Map();
function getUsuario(id) {
  if (!cache.has(id)) {
    cache.set(id, fetch(`/api/u/${id}`).then((r) => r.json()));
  }
  return cache.get(id);
}

function Bueno({ id }) {
  const u = use(getUsuario(id));   // estable entre renders
  return <h1>{u.nombre}</h1>;
}

RS2.8 useSyncExternalStore: el hook que existe por el tearing

Este hook casi nunca lo escribís en código de producto, y sin embargo es el que mejor explica por qué el render concurrente cambió las reglas.

💡 Qué es el tearing. Un render se puede interrumpir a la mitad. Supongamos que React renderizó diez componentes que leen store.precio y valía 100. Cede el control al browser. Durante esa pausa llega un WebSocket y el precio pasa a 105. React retoma y renderiza los diez restantes, que ahora leen 105. Commitea. En pantalla quedan veinte componentes mostrando dos valores distintos del mismo dato, en el mismo frame. Eso es tearing — "desgarro" — y antes del render concurrente era imposible, porque el render era una sola pasada sincrónica.

useState y useReducer son inmunes: React guarda el valor en el fiber y todo el render ve la misma foto. El problema es exclusivo de las fuentes externas y mutables: un Redux/Zustand escrito a mano, un singleton, navigator.onLine, window.matchMedia, document.cookie.

import { useSyncExternalStore } from "react";

type Oyente = () => void;

function crearStore<T>(inicial: T) {
  let estado = inicial;
  const oyentes = new Set<Oyente>();

  return {
    // 1) subscribe: recibe un callback y devuelve la función de limpieza.
    //    Tiene que ser ESTABLE entre renders (definida fuera del componente).
    subscribe(fn: Oyente) {
      oyentes.add(fn);
      return () => { oyentes.delete(fn); };
    },
    // 2) getSnapshot: devuelve el valor actual. React lo llama muchas veces
    //    y compara con Object.is. Tiene que ser referencialmente estable.
    getSnapshot() {
      return estado;
    },
    // 3) getServerSnapshot: el valor durante SSR e hidratación.
    getServerSnapshot() {
      return inicial;
    },
    set(siguiente: T) {
      estado = siguiente;
      oyentes.forEach((fn) => fn());
    },
  };
}

const storePrecio = crearStore(100);

function Precio() {
  const precio = useSyncExternalStore(
    storePrecio.subscribe,
    storePrecio.getSnapshot,
    storePrecio.getServerSnapshot,
  );
  return <span>{precio}</span>;
}

Lo que hace React con esto: antes de commitear, vuelve a llamar a getSnapshot y verifica que el valor no haya cambiado durante el render. Si cambió, descarta el render y lo rehace sincrónicamente con el valor nuevo. Sacrifica la interrumpibilidad para garantizar consistencia. Ese es todo el truco: las suscripciones externas se degradan a render sincrónico a cambio de no mostrar datos desgarrados.

⚠️ El error universal: devolver un objeto nuevo desde getSnapshot. React compara snapshots con Object.is. Si devolvés un objeto o array construido en el momento, nunca son iguales, React cree que el store cambió en cada chequeo y entrás en un loop de renders infinito. El warning literal es "The result of getSnapshot should be cached to avoid an infinite loop". 
// ❌ Objeto nuevo en cada llamada → loop infinito
useSyncExternalStore(subscribe, () => ({ a: store.a, b: store.b }));

// ❌ Filtrado en cada llamada → array nuevo → loop infinito
useSyncExternalStore(subscribe, () => store.items.filter((i) => i.activo));

// ✅ Valor primitivo: comparable por identidad
useSyncExternalStore(subscribe, () => store.a);

// ✅ Referencia estable, cacheada dentro del store (recalculada solo al mutar)
useSyncExternalStore(subscribe, () => store.itemsActivosMemo);
// Caso real y legítimo en código de producto: una API del navegador
const suscribirseAOnline = (cb) => {
  window.addEventListener("online", cb);
  window.addEventListener("offline", cb);
  return () => {
    window.removeEventListener("online", cb);
    window.removeEventListener("offline", cb);
  };
};

export function useEstaOnline() {
  return useSyncExternalStore(
    suscribirseAOnline,               // definida FUERA: referencia estable
    () => navigator.onLine,           // primitivo
    () => true,                       // en el servidor asumimos online
  );
}
📌 Cuándo lo necesitás. Si escribís una librería de estado, un adaptador a una API del navegador, o cualquier cosa que exponga un hook para leer datos mutables de afuera de React: sí, es obligatorio. Si tu estado vive en useState, useReducer o context: no, y usarlo solo agrega ceremonia. Zustand, Redux Toolkit, Jotai y compañía ya lo usan por dentro — parte de por qué conviene usar una librería en vez de un singleton casero.

RS2.9 Qué se rompe en modo concurrente

Todo lo anterior tiene una contracara. Estas son las tres familias de bugs que aparecen cuando el render deja de ser una sola pasada.

1. Efectos que asumían correr una sola vez

// ❌ Se rompe con doble montaje, con Activity, y con cualquier remount
function Chat({ salaId }) {
  useEffect(() => {
    const conn = conectar(salaId);
    conn.abrir();
    // sin cleanup: cada montaje deja una conexión colgada
  }, [salaId]);
}

// ✅ Simétrico: todo lo que abrís, lo cerrás
function Chat({ salaId }) {
  useEffect(() => {
    const conn = conectar(salaId);
    conn.abrir();
    return () => conn.cerrar();
  }, [salaId]);
}
// ❌ Race condition: una respuesta vieja pisa a una nueva
useEffect(() => {
  fetch(`/api/buscar?q=${q}`).then((r) => r.json()).then(setDatos);
}, [q]);

// ✅ Ignorar respuestas obsoletas + abortar el request
useEffect(() => {
  const ctrl = new AbortController();
  let vigente = true;

  fetch(`/api/buscar?q=${q}`, { signal: ctrl.signal })
    .then((r) => r.json())
    .then((d) => { if (vigente) setDatos(d); })
    .catch((e) => { if (e.name !== "AbortError") setError(e); });

  return () => { vigente = false; ctrl.abort(); };
}, [q]);
React 19.2 sumó useEffectEvent para el caso hermano: leer el valor más reciente de una prop o estado dentro de un efecto sin ponerla en el array de dependencias. Es la solución oficial al patrón de la ref mutable que se usaba para no re-suscribirse cada vez que cambia un callback.

2. Refs mutadas durante el render

La regla de pureza no es un consejo de estilo: es un requisito del scheduler. Un render se puede ejecutar dos veces (StrictMode), abandonarse a la mitad (transición interrumpida) o descartarse entero. Un efecto secundario durante el render sobrevive a un render que nunca se commiteó.

// ❌ Contador que miente: cuenta renders abandonados y renders dobles
function Malo() {
  const veces = useRef(0);
  veces.current++;                      // mutación durante el render
  return <p>Renders: {veces.current}</p>;
}

// ✅ Los efectos secundarios van al commit
function Bueno() {
  const veces = useRef(0);
  useEffect(() => { veces.current++; });
  return <p>Commits: {veces.current}</p>;
}
// ❌ Mutar props/estado durante el render
function Lista({ items }) {
  items.sort((a, b) => a.n - b.n);      // muta el array del padre
  return <ul>{items.map(/* … */)}</ul>;
}

// ✅ Copia local; el input queda intacto
function Lista({ items }) {
  const ordenados = useMemo(() => [...items].sort((a, b) => a.n - b.n), [items]);
  return <ul>{ordenados.map(/* … */)}</ul>;
}
La única mutación de ref aceptada durante el render es la inicialización perezosa, y solo porque es idempotente: if (ref.current === null) ref.current = crearAlgoCaro();. Se puede correr veinte veces y el resultado observable es el mismo. Ese es el criterio real — no "¿es una ref?" sino "¿es idempotente y no observable desde afuera?".

// ❌ Lee una fuente mutable directo en el render: tearing asegurado

  return <p>{window.innerWidth}</p>;   // además, rompe SSR

// ❌ Se suscribe en el render en vez de en un efecto

RS2.10 Cuándo NO usar transiciones

1. Cuando el trabajo es rápido. Si el render tarda 4 ms, envolverlo en startTransition agrega overhead de scheduling, una posible pasada extra y un estado pendiente que nunca se ve. Estás pagando complejidad por nada.
2. Cuando el cuello de botella es la red. Una transición no acelera un endpoint. Ahí lo que servís es caché, prefetch, paginación o un endpoint más rápido.
3. En inputs controlados y controles directos. Checkbox, toggle, abrir un menú, el value de un input: son feedback directo y tienen que ser inmediatos. Diferirlos rompe la sensación de causalidad.
4. Cuando el problema es la cantidad de nodos. Si el commit tiene que insertar miles de elementos, ninguna prioridad ayuda: el commit no se interrumpe. La respuesta es virtualizar o paginar.
5. En animaciones frame a frame. Lo que tiene que correr a 60 fps no va por el scheduler de React: va por CSS, Web Animations API o una librería de animación. Una transición justamente puede retrasarlo.
6. "Por las dudas", en todos lados. Si todo es baja prioridad, nada lo es. Además convertís cada interacción en potencialmente reversible y llenás la UI de estados pendientes que compiten entre sí.

Paso 4 — Por qué el scroll sigue trabando

Acá es donde se separa entender el modelo de repetir la receta. El render de fondo son 305 ms, pero es interrumpible: React cede cada ~5 ms y el scroll fluye durante esa etapa. El problema es el commit: 95 ms de inserciones de DOM, layout y paint, sincrónicos y sin ceder el control. Ninguna prioridad de React puede partir eso. Es un long task de 95 ms cada vez que la lista se materializa, y el scroll se congela ahí.

📌 useDeferredValue compró percepción. Para bajar el trabajo hay que renderizar menos cosas. Ninguna cantidad de scheduling reduce el costo de meter 60.000 nodos DOM en la página. Lo que lo reduce es no meterlos.

Checkpoint — ¿lo tenés claro?

Envolviste el setState de un input controlado en startTransition y el input quedó peor. ¿Por qué exactamente?

Porque un input controlado necesita que su value se actualice de forma urgente y garantizada, y una transición hace lo contrario: la marca como interrumpible y descartable. Si la persona tipea rápido, React puede abandonar renders intermedios, con lo que el value que muestra el DOM se atrasa respecto de lo que el usuario tecleó: el cursor salta, se comen letras, el texto rebota. La corrección no es sacar el diferimiento sino moverlo de lugar: q se actualiza urgente y lo derivado —el filtro, la lista— pasa por useDeferredValue. Regla general: lo que la persona acaba de escribir va urgente; lo que se deriva de eso, difiérelo.

Aplicaste useDeferredValue, el INP bajó 10×, y el scroll sigue trabando cuando aparece la lista. ¿Qué está pasando y qué hacés?

Estás viendo la frontera entre las dos fases. El render es interrumpible: React cede el control cada ~5 ms y por eso el input responde. El commit no lo es: aplicar miles de mutaciones al DOM, más el layout y el paint que provoca, es una tarea sincrónica que ningún scheduler puede partir. Ese long task de decenas de milisegundos es el que congela el scroll. Cambiar prioridades no lo toca, porque el trabajo sigue siendo el mismo. La solución es reducir el trabajo: virtualizar para montar solo las filas visibles, o paginar. useDeferredValue compra percepción; virtualizar compra trabajo, y no son sustitutos.

Tu librería de estado expone un hook que lee un objeto mutable. ¿Por qué no alcanza con useState + un useEffect que se suscribe, y qué te da useSyncExternalStore?

Porque el render se puede interrumpir. Con useEffect, los componentes leen el valor mutable en distintos momentos del render; si el store cambia durante una pausa, la mitad del árbol muestra el valor viejo y la otra mitad el nuevo, en el mismo frame: eso es tearing. Además el efecto corre después del paint, así que hay una ventana donde la UI ya se pintó con un valor desactualizado. useSyncExternalStore vuelve a llamar a getSnapshot antes de commitear y, si el valor cambió, descarta el render y lo rehace sincrónicamente: sacrifica interrumpibilidad para garantizar consistencia. También resuelve el SSR con getServerSnapshot. Condiciones: subscribe estable y getSnapshot devolviendo un valor cacheado —si devolvés un objeto nuevo cada vez, entrás en un loop infinito de renders.

Resumen ejecutivo

  • Concurrente no es multihilo. Es un solo hilo con render troceado que cede al navegador cada ~5 ms, y que puede abandonar y rehacer trabajo. La consecuencia importante es semántica, no de rendimiento: tu componente puede correr para un render que se descarta.
  • La fase de render se interrumpe; la de commit, no. Todo lo que se puede y no se puede arreglar con prioridades se deduce de esa frase.
  • useTransition marca actualizaciones cuando sos dueño del setState, te da isPending y en React 19 soporta funciones async (Actions), siempre que el await esté adentro del callback. Nunca envuelvas el valor de un input controlado.
  • useDeferredValue marca un valor cuando el setState no es tuyo. Exige memoizar el subárbol caro: sin eso hacés dos renders caros por cambio y empeorás todo.
  • Suspense solo intercepta lazy, use(promesa), RSC y librerías integradas — nunca useEffect + useState. Dentro de una transición no muestra el fallback: preserva el contenido viejo. Límites por unidad significativa, con fallbacks de la misma altura.
  • Streaming SSR: manda el shell en onShellReady, el resto por el stream, y el cliente hidrata selectivamente priorizando lo que el usuario toca. React 19.2 batchea los reveals de los boundaries durante el streaming, con la misma cadencia del cliente: menos reflows, misma cantidad de bytes, y es gratis con solo actualizar.
  • Hidratación: es un render completo sobre HTML existente, y es cara. Los mismatch vienen de no determinismo, ramas por entorno, locale/TZ, HTML inválido y extensiones. Se depuran leyendo el diff de React 19, descartando extensiones y comparando HTML crudo — no con suppressHydrationWarning.
  • use() lee promesas y contextos durante el render, se puede llamar condicionalmente, y exige promesas estables: crearlas en el render es un loop infinito. Los errores van a un error boundary, no a un try/catch.
  • useSyncExternalStore existe por el tearing. Lo necesitás si escribís librerías de estado o adaptás APIs del navegador; getSnapshot tiene que devolver valores cacheados.
  • Lo que se rompe: efectos sin cleanup, refs mutadas en el render, suscripciones mal hechas. StrictMode es el detector, no la causa — y con <Activity> estable en 19.2 esos escenarios ya ocurren en producción.
  • Orden de ataque: renderizar menos → trabajar menos → reordenar con prioridades. Empezar por el último es el error más común.

🧠 Autoevaluación

1. Tenés un input controlado que filtra una lista pesada. Envolvés el setQuery del input en startTransition y el input se siente peor que antes. ¿Cuál es la explicación?

Un input controlado necesita que su value se actualice de forma urgente y garantizada. Una transición dice exactamente lo contrario: "esto puede esperar y lo podés abandonar". Con tecleo rápido, React descarta renders intermedios y el DOM se atrasa respecto de lo tecleado: cursor que salta, letras comidas, valor que rebota. La documentación de React lo marca como pitfall explícito. El arreglo es mover el diferimiento del input al valor derivado.

2. ¿Por qué existe useSyncExternalStore?

Con render concurrente, React puede pausar a la mitad del árbol. Si una fuente externa mutable cambia durante esa pausa, los componentes renderizados antes y después ven valores distintos y la pantalla queda "desgarrada". useState es inmune porque React congela el valor por render; las fuentes externas no. useSyncExternalStore revalida getSnapshot antes del commit y, si cambió, rehace el render sincrónicamente: cambia interrumpibilidad por consistencia. Requisitos: subscribe estable y getSnapshot con valor cacheado, o entrás en un loop infinito.

3. Aplicaste useDeferredValue con memo: el INP bajó de 480 ms a 45 ms, pero el scroll sigue trabándose cuando la lista se actualiza. ¿Qué lo explica?

React trocea y cede el control durante la fase de render, que es por qué el input responde al instante. El commit —mutaciones de DOM, layout y paint— es sincrónico y no cede: son decenas de milisegundos de tarea larga cada vez que la lista se materializa, y ahí se congela el scroll. Ninguna prioridad reduce ese trabajo porque el trabajo sigue siendo el mismo. Virtualizar baja de 5.000 filas a ~20 y el commit se desploma. Es la diferencia entre reordenar el trabajo y reducirlo.

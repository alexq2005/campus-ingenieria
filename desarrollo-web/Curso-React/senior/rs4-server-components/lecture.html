RS4 — Server Components a fondo

RS4.0 Por qué este módulo

Casi todo el material que vas a encontrar sobre React Server Components arranca mal. Dice algo como "es SSR pero mejor", o "es una forma de renderizar en el servidor". Las dos frases son falsas, y creerlas te lleva a escribir código que técnicamente compila pero que no aprovecha nada de lo que RSC ofrece — o peor, que arrastra medio árbol al cliente sin que te des cuenta.

💡 La tesis del módulo. SSR y RSC responden preguntas distintas. SSR pregunta "¿dónde genero el primer HTML?" — y la respuesta no cambia el hecho de que ese componente después se hidrata y vive en el cliente. RSC pregunta "¿qué componentes tienen que existir en el cliente?" — y para muchos la respuesta es ninguno, nunca. Un Server Component no se hidrata porque no está allá: lo que viaja es su resultado.

Esa diferencia es la que produce el número que todo el mundo cita. Migrar una app del directorio pages/ al directorio app/ con Server Components da, típicamente, alrededor de un 40% menos de JavaScript en el bundle. No porque el compilador sea más listo, sino porque una parte del código que antes tenía que llegar al navegador ahora simplemente no llega: la librería de markdown, el cliente del ORM, el formateador de fechas con sus tres locales, el SDK del CMS. Todo eso corre una vez, en el servidor, y lo que cruza la red es texto ya resuelto.

A septiembre de 2026 esto ya no es material experimental. RSC y Server Functions son estables en React 19, y la versión estable de la librería es React 19.2. Dejó de ser una apuesta de framework para ser parte del modelo del lenguaje: cambia dónde vive tu código, no solo cómo lo empaquetás.

Advertencia de expectativas. RSC no hace tu app más rápida por decreto. Hace posible otra arquitectura, y en esa arquitectura hay trampas nuevas: cascadas de fetch invisibles, props que no serializan, cachés que devuelven contenido viejo y funciones de servidor que son endpoints públicos sin que nadie lo escriba. Este módulo es tanto sobre lo que ganás como sobre lo que se rompe.

RS4.1 El modelo mental: tres cosas distintas que suenan iguales

Antes de escribir una línea, hay que separar tres conceptos que la industria mezcla todo el tiempo. La confusión no es tuya: los tres involucran "un servidor" y "React".

SSR clásicoServer ComponentClient Component
Dónde corre el códigoServidor y cliente (dos veces)Solo servidor (una vez)Servidor (opcional) y cliente
Qué viaja por el cableHTML + el bundle JS del componenteUn payload RSC serializadoSu bundle JS + props serializadas

La fila que importa es la última de costos. En SSR clásico, el servidor renderiza tu componente a HTML y además te manda el código del componente para que el cliente lo vuelva a ejecutar y "adopte" ese HTML. Pagás el trabajo dos veces y pagás el transporte del código. Es el precio de tener interactividad.

La analogía. SSR es mandar una torta ya horneada junto con la receta y los ingredientes, porque el que la recibe va a necesitar decorarla en vivo. RSC es preguntarse cuáles partes del pedido realmente hay que decorar: la base va horneada y punto, y solo mandás receta e ingredientes para el glaseado. La caja pesa menos porque decidiste qué necesitaba llegar crudo.

En código, un Server Component es simplemente un componente que puede ser async y hablar con recursos del servidor sin ceremonia:

// app/productos/[slug]/page.tsx  — Server Component por defecto
import { db } from "@/lib/db";
import { marked } from "marked";          // ~40 KB que NUNCA llegan al cliente

export default async function PaginaProducto({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  const producto = await db.producto.findUnique({ where: { slug } });

  if (!producto) return <p>No existe.</p>;

  return (
    <article>
      <h1>{producto.nombre}</h1>
      {/* marked corre acá, en el server. El cliente recibe HTML resuelto. */}
      <div dangerouslySetInnerHTML={{ __html: marked(producto.descripcionMd) }} />
    </article>
  );
}
📌 En una app RSC, todo componente es Server Component salvo que digas lo contrario. Es el default invertido respecto de lo que venías haciendo. No hay directiva "use server" para marcar un componente de servidor — esa directiva significa otra cosa (RS4.5). El servidor es el piso; "use client" es la puerta de salida.

Y sí: SSR y RSC conviven. En una app moderna con el App Router, un Server Component produce el payload RSC, los Client Components dentro de ese árbol se renderizan a HTML en el servidor (eso es SSR) y después se hidratan en el navegador. No son alternativas: son dos capas del mismo pipeline.

// Lo que pasa en una sola request, en orden:
//
// 1. El servidor ejecuta los Server Components  → produce el payload RSC
// 2. Con ese payload, el servidor renderiza HTML → eso es SSR (incluye los Client Components)
// 3. El navegador pinta el HTML                  → hay contenido visible
// 4. Llega el bundle de los Client Components    → React hidrata SOLO esos
// 5. El payload RSC queda disponible para las navegaciones siguientes

RS4.2 El RSC payload: qué viaja realmente por el cable

Acá es donde la mayoría de la gente deja de entender, porque el payload RSC no es HTML ni es JSON común. Es un formato de streaming, línea por línea, donde cada línea es una fila numerada que el cliente va incorporando a medida que llega. Se lo suele llamar Flight.

Podés verlo con tus propios ojos. En una app con App Router, pedile a una ruta el payload en vez del HTML:

curl -s 'http://localhost:3000/productos/teclado?_rsc=1' \
     -H 'RSC: 1' | head -40

Lo que sale se parece a esto (simplificado y con nombres en español para que se lea):

0:I["(app-pages-browser)/./components/Galeria.tsx",["static/chunks/galeria.js"],"default"]
1:["$","article",null,{"children":[
     ["$","h1",null,{"children":"Teclado mecánico"}],
     ["$","$L0",null,{"imagenes":["/a.webp","/b.webp"],"alt":"Teclado"}],
     "$L2"
   ]}]
2:["$","section",null,{"children":[["$","h2",null,{"children":"Reseñas"}], "…"]}]

Leelo con calma, porque cada pieza explica una propiedad del sistema:

  • Fila 0:I[...] — una referencia a componente cliente. No es el componente: es una tarjeta que dice "esto está en el chunk galeria.js, exportado como default". El cliente sabe qué bajar y cuándo.
  • Fila 1 — el árbol de elementos ya renderizado. ["$","h1",null,{...}] es la forma serializada de un elemento React: tipo, key, props. El h1 viene resuelto porque es un Server Component; no hay código para él.
  • "$L0" — "acá va lo que definió la fila 0". Así se referencia al Client Component dentro del árbol, con sus props ya serializadas al lado.
  • "$L2" — un hueco: "esto llega después". La conexión sigue abierta y la fila 2 aparece cuando el servidor termina de resolver esa parte. Eso es el streaming.
💡 Por qué el formato tiene que ser este y no HTML. Con HTML, el cliente recibe pintura: no puede saber qué parte del árbol cambió sin volver a parsear todo y adivinar. Con el payload RSC, el cliente recibe la descripción del árbol de React, así que puede hacer un reconcile real contra el árbol que ya tiene. Por eso una navegación o una revalidación puede actualizar una rama sin tirar el estado del cliente que está al lado: el input donde estabas escribiendo sigue con su texto, el acordeón sigue abierto.

Esa es la propiedad de la que sale casi todo el resto del módulo:

📌 El payload RSC permite actualizaciones parciales que preservan el estado del cliente. Un router.refresh() o una revalidación después de una Server Function vuelve a pedir el payload del servidor y React lo mezcla con lo que ya hay. No es una recarga: es un re-render con datos frescos donde solo cambia lo que cambió.

Y también sale de ahí la primera restricción dura. Si todo lo que cruza tiene que expresarse como filas de ese formato, entonces todo lo que cruza tiene que ser serializable. Ese es el tema de la sección siguiente, y es el error número uno de todo el ecosistema.

RS4.3 El límite: "use client" y la serialización

La directiva "use client" no significa "este componente corre solo en el cliente". Significa algo más preciso y más importante:

💡 Qué hace realmente "use client". Marca un punto de entrada al bundle del cliente. El archivo que la lleva, y todo lo que ese archivo importa, y todo lo que esos archivos importan, entra al grafo de módulos del navegador. No es una anotación sobre un componente: es una raíz de dependencias.

Se pone una sola vez, arriba del archivo, y se hereda hacia abajo por importación:

"use client";                    // ← primera línea del archivo, antes de los imports

import { useState } from "react";
import { formatearFecha } from "@/lib/fechas";   // esto también entra al bundle

export function Acordeon({ titulo, children }: {
  titulo: string;
  children: React.ReactNode;
}) {
  const [abierto, setAbierto] = useState(false);
  return (
    <section>
      <button onClick={() => setAbierto(v => !v)}>{titulo}</button>
      {abierto && children}
    </section>
  );
}
El error más caro y más silencioso: poner "use client" en un archivo barril (components/index.ts) que reexporta cuarenta componentes. Con una línea acabás de mandar cuarenta componentes y sus dependencias al navegador, incluidos los que nadie usa en esa página. El bundle crece, nadie ve un error, y el número que mirás en el dashboard empeora sin causa aparente. Nunca pongas la directiva en un barril.

Props serializables: la regla que rompe a todo el mundo

Cuando un Server Component le pasa props a un Client Component, esas props tienen que viajar dentro del payload. Y no todo se puede escribir en un payload.

// ✅ Cruzan el límite sin problema
<Widget
  texto="hola"                        // string
  cantidad={42}                       // number, bigint
  activo={true}                       // boolean
  nada={null}                         // null / undefined
  lista={[1, 2, 3]}                   // Array
  objeto={{ a: 1, b: { c: 2 } }}      // objeto plano
  fecha={new Date()}                  // Date
  conjunto={new Set([1, 2])}          // Set, Map, TypedArray, ArrayBuffer
  formulario={formData}               // FormData
  promesa={promesaDeDatos}            // ¡Promise! (se resuelve en el cliente)
  hijos={<p>JSX ya resuelto</p>}      // elementos React
  onGuardar={guardarEnDB}             // función marcada con "use server"
/>
// ❌ NO cruzan: rompen en tiempo de render
<Widget
  onClick={() => console.log("hola")}   // función común → error
  formatear={(n) => n.toFixed(2)}       // idem
  usuario={usuarioDeLaClaseUsuario}     // instancia de clase → se pierde el prototipo
  simbolo={Symbol("id")}                // Symbol no registrado
  cliente={prismaClient}                // objetos con métodos y estado interno
/>

El mensaje que ves cuando lo hacés mal es este, y ahora ya sabés exactamente qué significa:

Error: Functions cannot be passed directly to Client Components
unless you explicitly expose it by marking it with "use server".
  <... onClick={function onClick}>
                ^^^^^^^^^^^^^^^^^
Por qué una función no puede cruzar. Una función es código más su closure: las variables que capturó del ámbito donde se creó. Serializar eso significaría mandar el código y el entorno, es decir, mandar el servidor al cliente. El sistema no lo intenta. Te ofrece la única alternativa honesta: si querés que el cliente invoque algo del servidor, exponelo explícitamente como Server Function — y ahí lo que viaja no es la función sino un identificador que el cliente usa para llamarla por red.

Los dos arreglos correctos

Cuando chocás con el límite, hay exactamente dos salidas legítimas. La primera: mover el handler adentro del Client Component, que es donde pertenece.

// ❌ Server Component intentando pasar un handler
export default async function Pagina() {
  const items = await db.items.findMany();
  return <Lista items={items} onSeleccionar={(id) => console.log(id)} />;
}

// ✅ El handler nace donde se usa
"use client";
export function Lista({ items }: { items: Item[] }) {
  return (
    <ul>
      {items.map((it) => (
        <li key={it.id} onClick={() => console.log(it.id)}>{it.nombre}</li>
      ))}
    </ul>
  );
}

La segunda: pasar datos, no comportamiento. Si el Client Component necesita formatear, mandale el valor ya formateado o el dato crudo, nunca el formateador.

// ❌ pasás la función de formateo
<Precio valor={p.centavos} formatear={fmt} />

// ✅ formateás en el servidor y pasás el resultado
<Precio texto={fmt(p.centavos)} />

// ✅ o pasás el dato y el cliente trae su propio formateador
<Precio centavos={p.centavos} moneda="ARS" />
Ojo con el "todo serializado" como excusa para mandar de más. Un objeto de Prisma con 40 columnas serializa perfecto y por eso nadie te avisa que estás mandando el costo_proveedor y el margen al navegador. El payload RSC es público: cualquiera lo lee en la pestaña Network. Seleccioná los campos antes de cruzar el límite, siempre. 
// ❌ el registro entero viaja al navegador, con todo lo que no debería salir
const producto = await db.producto.findUnique({ where: { slug } });
return <Ficha producto={producto} />;

// ✅ solo lo que la UI necesita
const producto = await db.producto.findUnique({
  where: { slug },
  select: { id: true, nombre: true, precio: true, imagenes: true },
});
return <Ficha producto={producto} />;

RS4.4 Composición: pasar Server Components como children

Este patrón es la mitad del módulo. Si te llevás una sola técnica de RS4, que sea esta.

El problema aparece apenas necesitás algo interactivo cerca de la raíz: un layout con tema oscuro, un tab bar, un panel colapsable, un provider de contexto. La reacción natural es marcar ese componente con "use client"… y ahí explotó todo, porque todo lo que un Client Component importa se vuelve cliente.

// ❌ El anti-patrón. Panel es cliente → importa Feed → Feed se vuelve cliente
"use client";

import { useState } from "react";
import { Feed } from "./Feed";          // Feed usaba la DB y marked… ya no puede

export function Panel() {
  const [tab, setTab] = useState("todo");
  return (
    <div>
      <nav>{/* botones que cambian tab */}</nav>
      <Feed filtro={tab} />             {/* ← arrastrado al bundle */}
    </div>
  );
}

El resultado es una bola de nieve: Feed ya no puede ser async, ya no puede tocar la base, y sus dependencias (el ORM, el parser de markdown) o bien viajan al navegador o bien te obligan a reescribir todo con useEffect. Un solo "use client" mal puesto convierte media app en cliente.

📌 La regla que lo resuelve: importar arrastra, recibir no. Un Client Component no puede import un Server Component, pero sí puede recibirlo como children o como cualquier prop de tipo ReactNode. Cuando lo recibe, ya viene renderizado desde el servidor: el cliente solo lo coloca en un hueco del árbol. Nada de ese subárbol entra al bundle.

La versión correcta separa el "envase" interactivo del "contenido" de servidor:

// components/Panel.tsx  — SOLO el envase es cliente
"use client";

import { useState, type ReactNode } from "react";

export function Panel({
  tabs,
  contenido,
}: {
  tabs: string[];
  contenido: Record<string, ReactNode>;   // ← huecos, no importaciones
}) {
  const [tab, setTab] = useState(tabs[0]);
  return (
    <div>
      <nav>
        {tabs.map((t) => (
          <button key={t} onClick={() => setTab(t)} aria-current={t === tab}>
            {t}
          </button>
        ))}
      </nav>
      <div>{contenido[tab]}</div>
    </div>
  );
}
// app/page.tsx — Server Component: acá se arma el contenido
import { Panel } from "@/components/Panel";
import { Feed } from "@/components/Feed";           // sigue siendo de servidor
import { Estadisticas } from "@/components/Estadisticas";

export default function Pagina() {
  return (
    <Panel
      tabs={["Feed", "Estadísticas"]}
      contenido={{
        Feed: <Feed filtro="todo" />,               {/* ← ya renderizado en server */}
        "Estadísticas": <Estadisticas />,
      }}
    />
  );
}

El caso más común de todos es el provider de contexto, y se resuelve igual:

// components/Proveedores.tsx
"use client";
import { ThemeProvider } from "@/lib/tema";

export function Proveedores({ children }: { children: React.ReactNode }) {
  return <ThemeProvider>{children}</ThemeProvider>;
}

// app/layout.tsx  — sigue siendo Server Component
export default function Layout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="es">
      <body>
        <Proveedores>{children}</Proveedores>
      </body>
    </html>
  );
}
Cómo pensarlo. El Client Component no "contiene" al Server Component: le reserva un agujero. En el payload, ese agujero es un children que ya viene con el árbol resuelto adentro. Por eso el orden mental correcto es: empujá el "use client" lo más abajo y lo más a las hojas que puedas, y donde necesites envolver, envolvé por composición.

RS4.5 Server Functions: potentes y peligrosas

Una Server Function es una función que se define en el servidor y que el cliente puede invocar como si fuera local. La directiva es "use server" — que, insisto, no marca componentes de servidor sino funciones expuestas al cliente.

// app/acciones.ts
"use server";                      // todo lo exportado de acá es invocable por red

import { db } from "@/lib/db";
import { revalidatePath } from "next/cache";

export async function agregarReseña(slug: string, texto: string) {
  await db.reseña.create({ data: { productoSlug: slug, texto } });
  revalidatePath(`/productos/${slug}`);
}
// components/FormReseña.tsx
"use client";
import { agregarReseña } from "@/app/acciones";

export function FormReseña({ slug }: { slug: string }) {
  return (
    <form action={async (fd: FormData) => {
      await agregarReseña(slug, String(fd.get("texto")));
    }}>
      <textarea name="texto" required />
      <button type="submit">Publicar</button>
    </form>
  );
}

Se lee como una llamada a función. No lo es. Lo que el cliente importa no es el cuerpo de agregarReseña: es un identificador opaco. Al invocarla, el runtime hace un POST al servidor con ese identificador y los argumentos serializados. Miralo vos mismo en la pestaña Network:

POST /productos/teclado
Next-Action: 7f3a1c9e0b2d4a6f8c1e5b7d9a0f2c4e6b8d1a3f
Content-Type: text/plain;charset=UTF-8

["teclado","muy buen producto"]
🔒 Una Server Function es un endpoint HTTP público. No hay ninguna diferencia de seguridad entre esa función y una ruta de API que hubieras escrito a mano. El identificador es adivinable/observable, cualquiera puede reproducir ese POST con curl, y los argumentos vienen del cliente, así que son datos hostiles hasta que los valides. El hecho de que el formulario esté escondido detrás de un if (esAdmin) en la UI no protege absolutamente nada: la UI es sugerencia, no control de acceso.

La consecuencia práctica es que la autorización va adentro de la función, en su primera línea, sin excepciones:

"use server";

import { z } from "zod";
import { db } from "@/lib/db";
import { getSesion } from "@/lib/auth";
import { revalidateTag } from "next/cache";

const Entrada = z.object({
  slug: z.string().min(1).max(120),
  texto: z.string().min(10).max(2000),
  puntaje: z.number().int().min(1).max(5),
});

export async function agregarReseña(datosCrudos: unknown) {
  // 1. AUTENTICACIÓN — ¿quién sos?
  const sesion = await getSesion();
  if (!sesion) throw new Error("No autenticado");

  // 2. VALIDACIÓN — los argumentos vienen del cliente, son hostiles
  const datos = Entrada.parse(datosCrudos);

  // 3. AUTORIZACIÓN — ¿podés hacer ESTO, sobre ESTE recurso?
  const compro = await db.pedido.findFirst({
    where: { usuarioId: sesion.userId, items: { some: { slug: datos.slug } } },
  });
  if (!compro) throw new Error("Solo compradores verificados pueden reseñar");

  // 4. Recién ahora, el efecto
  await db.reseña.create({
    data: { ...datos, autorId: sesion.userId },   // el autor sale de la SESIÓN
  });
  revalidateTag(`reseñas:${datos.slug}`);
}
El bug clásico: aceptar autorId como argumento. Si la función recibe quién sos en vez de deducirlo de la sesión, cualquiera publica reseñas —o transfiere plata— en nombre de otro con un curl. La identidad nunca viene del cliente. Sale de la sesión, del token verificado, del contexto del servidor. Los argumentos solo llevan qué hacer, jamás quién lo hace.

Los cuatro pasos de arriba (autenticar → validar → autorizar → actuar) son el mismo orden que ya viste fuera de React. Si te quedan dudas sobre el diseño de la capa de permisos —modelos RBAC vs ABAC, el problema del IDOR, dónde poner el chequeo de propiedad del recurso— este módulo asume esos temas y no los repite:

  • Track Senior · Módulo 04 — Seguridad y autenticación: sesiones, tokens, y por qué el chequeo de frontend no es un chequeo.
  • Ciberseguridad · M03 — Autorización: modelos de permisos, autorización a nivel de objeto y las fallas de control de acceso roto.

Estado de la acción en la UI

Del lado del cliente, React 19 trae los hooks para manejar el ciclo de vida de una acción sin escribir un reducer a mano:

"use client";
import { useActionState } from "react";
import { useFormStatus } from "react-dom";
import { agregarReseña } from "@/app/acciones";

function Boton() {
  const { pending } = useFormStatus();        // lee el <form> padre
  return <button disabled={pending}>{pending ? "Enviando…" : "Publicar"}</button>;
}

export function FormReseña({ slug }: { slug: string }) {
  const [estado, accion] = useActionState(
    async (_previo: string | null, fd: FormData) => {
      try {
        await agregarReseña({
          slug,
          texto: String(fd.get("texto")),
          puntaje: Number(fd.get("puntaje")),
        });
        return null;
      } catch (e) {
        return e instanceof Error ? e.message : "Error";
      }
    },
    null
  );

  return (
    <form action={accion}>
      <textarea name="texto" required />
      <input name="puntaje" type="number" min="1" max="5" required />
      <Boton />
      {estado && <p role="alert">{estado}</p>}
    </form>
  );
}
Devolvé errores, no los tires al vacío. Una excepción sin capturar dentro de una Server Function llega al cliente con el mensaje ofuscado en producción (React lo reemplaza por un digest). Está bien para errores inesperados, pero pésimo para errores de negocio esperables: capturalos y devolvelos como valor, como en el ejemplo. Y cuidado con lo contrario — nunca devuelvas el mensaje crudo de una excepción de base de datos: filtra nombres de tablas y estructura.

RS4.6 Cascadas de datos: el problema clásico de RSC

Los Server Components son async, y eso los vuelve trivialmente fáciles de escribir… y trivialmente fáciles de encadenar mal. La cascada (waterfall) es el modo de falla característico de RSC.

// ❌ Tres viajes SECUENCIALES. El total es la suma, no el máximo.
export default async function Pagina({ params }) {
  const { slug } = await params;
  const producto = await db.producto.findUnique({ where: { slug } });  // 120 ms
  const reseñas  = await db.reseña.findMany({ where: { slug } });      // 180 ms
  const stock    = await inventario.consultar(slug);                   // 200 ms
  //                                                          total ≈ 500 ms
  return <Ficha producto={producto} reseñas={reseñas} stock={stock} />;
}

Las tres consultas no dependen entre sí: solo dependen de slug. Se pueden disparar juntas.

// ✅ Tres viajes EN PARALELO. El total es el más lento.
export default async function Pagina({ params }) {
  const { slug } = await params;
  const [producto, reseñas, stock] = await Promise.all([
    db.producto.findUnique({ where: { slug } }),
    db.reseña.findMany({ where: { slug } }),
    inventario.consultar(slug),
  ]);
  //                                                          total ≈ 200 ms
  return <Ficha producto={producto} reseñas={reseñas} stock={stock} />;
}

Pero Promise.all tiene un límite: iguala a todos al más lento. Si las reseñas tardan 800 ms y el producto 100 ms, el usuario espera 800 ms para ver el título. La herramienta correcta ahí es Suspense: mostrás lo rápido de entrada y dejás que lo lento llegue por streaming.

import { Suspense } from "react";

export default async function Pagina({ params }) {
  const { slug } = await params;
  const producto = await db.producto.findUnique({ where: { slug } });  // rápido: se espera

  return (
    <>
      <Ficha producto={producto} />

      {/* lento: NO se espera. Se pinta el fallback y el contenido llega después */}
      <Suspense fallback={<EsqueletoReseñas />}>
        <Reseñas slug={slug} />
      </Suspense>
    </>
  );
}

async function Reseñas({ slug }: { slug: string }) {
  const reseñas = await db.reseña.findMany({ where: { slug } });   // 800 ms
  return <ul>{reseñas.map((r) => <li key={r.id}>{r.texto}</li>)}</ul>;
}
📌 La técnica avanzada: iniciar la promesa sin esperarla. Si un dato lento se necesita abajo en el árbol, disparalo arriba y pasá la promesa hacia abajo sin await. El pedido arranca ya; el await ocurre recién donde hace falta. Es la forma de tener paralelismo real sin aplanar la composición. 
export default async function Pagina({ params }) {
  const { slug } = await params;

  const pReseñas = db.reseña.findMany({ where: { slug } });   // ← SIN await: ya arrancó
  const producto = await db.producto.findUnique({ where: { slug } });

  return (
    <>
      <Ficha producto={producto} />
      <Suspense fallback={<EsqueletoReseñas />}>
        <Reseñas promesa={pReseñas} />
      </Suspense>
    </>
  );
}

async function Reseñas({ promesa }: { promesa: Promise<Reseña[]> }) {
  const reseñas = await promesa;      // el viaje ya venía en camino
  return <ul>{reseñas.map((r) => <li key={r.id}>{r.texto}</li>)}</ul>;
}
Una promesa también puede cruzar el límite hacia un Client Component y desenvolverse ahí con el hook use(). Sirve cuando querés que el fallback y la interactividad vivan en el cliente pero el fetch arranque en el servidor. Es potente y conviene usarlo con moderación: complica el razonamiento sobre dónde falla qué.
La cascada oculta: componentes anidados donde cada uno hace su propio await. <Layout> pide el usuario, <Sidebar> pide sus proyectos, <Lista> pide sus tareas. Cada nivel espera al anterior porque React renderiza de arriba hacia abajo, y como cada archivo se lee lindo por separado, nadie ve la cascada. Se detecta con trazas, no leyendo código. Instrumentá con OpenTelemetry o mirá el waterfall de la request en las devtools del framework.

RS4.7 Caché y revalidación: por qué esto confunde a todo el mundo

Si hay una parte de RSC que genera issues de GitHub, es el caching. Y la razón es que no hay un caché: hay varias capas que se pisan, con dueños distintos y tiempos de vida distintos.

CapaDónde viveQué guardaCómo se invalida
Memoización de requestServidor, durante una requestEl mismo fetch/función repetidoSola, al terminar la request
Caché de datosServidor, persistenteResultados de fetch con tags/TTLrevalidateTag, revalidatePath, TTL
Caché de ruta llenaServidor, en build/ISRHTML + payload RSC de rutas estáticasrevalidatePath, redeploy, TTL
Caché de routerCliente, en memoriaPayloads RSC ya visitadosrouter.refresh(), navegación, tiempo
💡 El origen de la confusión. Cuando alguien dice "cambié el dato y la página sigue mostrando lo viejo", la pregunta correcta no es "¿cómo apago el caché?" sino "¿cuál de las cuatro capas me está devolviendo esto?". Un revalidatePath impecable en el servidor no arregla nada si lo que estás viendo salió del caché de router del navegador. Y al revés: un router.refresh() vuelve a pedir al servidor, que te devuelve el mismo dato viejo si la caché de datos no se invalidó.

La forma de resolverlo es etiquetar lo que se cachea, para poder invalidarlo con precisión quirúrgica en vez de tirar todo abajo:

// lib/datos.ts — lecturas etiquetadas
export async function traerReseñas(slug: string) {
  const res = await fetch(`${API}/productos/${slug}/reseñas`, {
    next: { tags: [`reseñas:${slug}`, "reseñas"], revalidate: 3600 },
  });
  return res.json();
}

export async function traerProducto(slug: string) {
  const res = await fetch(`${API}/productos/${slug}`, {
    next: { tags: [`producto:${slug}`], revalidate: 86400 },  // cambia poco
  });
  return res.json();
}
"use server";
import { revalidateTag, revalidatePath } from "next/cache";

export async function agregarReseña(datos: Entrada) {
  // … auth + validación + escritura …

  revalidateTag(`reseñas:${datos.slug}`);   // ✅ solo las reseñas de ESE producto
  // revalidateTag("reseñas");              // 😬 todas las reseñas del sitio
  // revalidatePath("/", "layout");         // 🚨 la bomba nuclear: TODO el sitio
}
📌 revalidateTag vs revalidatePath. revalidateTag invalida datos: cualquier ruta que haya leído ese tag se regenera. revalidatePath invalida una ruta concreta. Preferí tags: un dato suele aparecer en varias páginas (el detalle, el listado, el sitemap) y con tags las alcanzás todas sin enumerarlas. Usá revalidatePath cuando lo que cambió es la forma de la página, no un dato.

Cuando un dato no debe cachearse nunca —un carrito, un saldo, un panel con datos de la sesión— hay que decirlo explícitamente:

// Nivel fetch: este pedido nunca se cachea
const res = await fetch(url, { cache: "no-store" });

// Nivel ruta: esta ruta siempre se renderiza dinámica
export const dynamic = "force-dynamic";

// Nivel ruta: revalidar como máximo cada 60 s (ISR)
export const revalidate = 60;
Leer cookies o headers vuelve la ruta dinámica. En cuanto un Server Component hace await cookies() o await headers(), el framework no puede prerenderizar esa ruta: depende de la request. Es correcto y deseable, pero es la causa número uno de "¿por qué mi página dejó de ser estática?" — y suele estar escondida tres niveles abajo, dentro de un helper de sesión. Aislá esas lecturas en el componente más chico posible y envolvelo en Suspense para que el resto de la página siga siendo estático. 
// ❌ toda la página se vuelve dinámica por el saludo
export default async function Pagina() {
  const sesion = await getSesion();      // lee cookies acá arriba
  return (
    <>
      <p>Hola {sesion?.nombre}</p>
      <CatalogoEstatico />               {/* ya no se puede prerenderizar */}
    </>
  );
}

// ✅ solo el saludo es dinámico; el catálogo sigue estático
export default function Pagina() {
  return (
    <>
      <Suspense fallback={<span>…</span>}>
        <Saludo />                       {/* acá adentro se leen las cookies */}
      </Suspense>
      <CatalogoEstatico />
    </>
  );
}

RS4.8 Qué NO podés hacer en un Server Component

La lista es corta y se deduce de una sola premisa: el componente corre una vez, en un proceso de servidor, y después deja de existir. No hay "después" para él.

No podésPor quéQué hacés en su lugar
useState, useReducerNo hay re-render local: el componente ya terminóClient Component en la hoja que necesita el estado
useEffect, useLayoutEffectLos efectos corren después del montaje, y no hay montajeEl trabajo va directo en el cuerpo async, o en un Client Component
onClick, onChange…No hay listener que registrar: no hay DOM ahíClient Component, o <form action={serverFn}>
useContextNo hay árbol vivo con providersPasar props, o leer el contexto en un Client Component
window, document, localStorageNo existen en NodeClient Component (y useEffect si necesitás el DOM montado)
Custom hooks con estadoHeredan la restricción de los hooks que usanConvertirlos en función pura, o moverlos al cliente
Lo que sí podés y no es obvio: usar async/await directo en el componente, leer variables de entorno privadas sin miedo a filtrarlas, importar librerías pesadas sin costo de bundle, hacer consultas SQL, leer del sistema de archivos, y usar cache() de React para deduplicar una función cara dentro de la misma request. Un Server Component se parece más a un template de servidor que a un componente de React clásico — y eso es exactamente lo que es.

RS4.9 Cuándo RSC no conviene

La parte que casi nadie escribe. RSC es una arquitectura, y como toda arquitectura tiene un dominio de aplicabilidad fuera del cual estorba.

Situación¿RSC?Por qué
E-commerce, blog, docs, marketing, dashboards con mucha lectura✅ IdealMucho contenido, poca interactividad por pantalla, SEO importa
Editor colaborativo, canvas, DAW, juego, IDE web❌ EstorbaCasi todo es estado del cliente; el servidor no aporta y el límite molesta
App interna detrás de login, sin SEO, con datos en vivo⚠️ DependeGanás poco: casi todo es dinámico y ya autenticado. Medí antes de migrar
SPA servida como estáticos (S3, GitHub Pages, CDN sola)❌ ImposibleRSC necesita un runtime de servidor que ejecute los componentes
Móvil con React Native❌ Fuera de alcanceEl modelo apunta a la web; el ecosistema no está ahí
Equipo chico sin experiencia de backend ni infra⚠️ CuidadoSumás un servidor que hay que operar, monitorear, escalar y pagar
App existente grande con mucho useEffect de fetch⚠️ IncrementalMigrá ruta por ruta. Un big bang acá termina mal
El costo que nunca sale en los benchmarks. RSC te devuelve un servidor a mantener. Antes tenías archivos estáticos en un CDN y un backend con el que hablabas por HTTP; ahora tenés un proceso que renderiza React, con su memoria, su latencia p99, su cold start, sus timeouts y su factura por invocación. Si el equipo no tiene con qué operar eso —observabilidad, alertas, un plan de rollback— el ahorro de 40% de bundle se lo come el primer incidente de producción.
📌 El criterio en una línea. Preguntate qué fracción de esta pantalla necesita estado del cliente. Si es baja (una ficha de producto, un artículo, un listado), RSC gana claramente. Si es alta (un editor, un tablero drag-and-drop), estás pagando complejidad arquitectónica para mover al servidor un 5% del árbol.

🧑‍🎓 Worked Example — página de producto con reseñas

Una página de producto tarde 2,8 s hasta el primer contenido y manda 340 KB de JS. Es la ruta con más tráfico del sitio y la que más convierte. Objetivo: bajar las dos cosas sin perder ninguna funcionalidad.

Paso 1 — La versión que hay (todo cliente)

"use client";
import { useState, useEffect } from "react";
import { marked } from "marked";              // 42 KB
import { format } from "date-fns";            // 18 KB + locale
import { es } from "date-fns/locale";

export default function PaginaProducto({ slug }: { slug: string }) {
  const [producto, setProducto] = useState(null);
  const [reseñas, setReseñas]   = useState([]);
  const [stock, setStock]       = useState(null);

  useEffect(() => {
    fetch(`/api/productos/${slug}`).then(r => r.json()).then(setProducto);
  }, [slug]);

  useEffect(() => {
    if (!producto) return;                    // ← espera al producto
    fetch(`/api/productos/${producto.id}/reseñas`).then(r => r.json()).then(setReseñas);
    fetch(`/api/stock/${producto.id}`).then(r => r.json()).then(setStock);
  }, [producto]);

  if (!producto) return <Esqueleto />;

  return (
    <article>
      <h1>{producto.nombre}</h1>
      <div dangerouslySetInnerHTML={{ __html: marked(producto.descripcionMd) }} />
      <Galeria imagenes={producto.imagenes} />
      <p>{stock?.disponible ? "En stock" : "Sin stock"}</p>
      <ul>
        {reseñas.map(r => (
          <li key={r.id}>
            {r.texto} — {format(new Date(r.fecha), "d 'de' MMMM", { locale: es })}
          </li>
        ))}
      </ul>
      <FormReseña productoId={producto.id} />
    </article>
  );
}

Diagnóstico, con números y no con opinión:

  1. Cascada de red de tres saltos. HTML vacío → bundle JS → /api/productos → /api/reseñas. Nada se ve hasta que terminan los tres. Y como /api/stock depende de producto.id, también espera, aunque el slug alcanzaba.
  2. 60 KB de librerías que el usuario no necesita. marked parsea un markdown que ya está escrito y no cambia. date-fns con locale formatea fechas del pasado. Ese trabajo no tiene por qué ocurrir en el dispositivo del usuario.
  3. SEO nulo. El HTML inicial es un esqueleto. Lo que indexa el buscador depende de que ejecute el JS.

Paso 2 — Dibujar el árbol antes de tocar código

PaginaProducto ................... server   (async, lee la DB)
├── Titulo + descripción ......... server   (marked corre acá, 0 KB al cliente)
├── Galeria ...................... CLIENTE  (zoom, swipe, teclado)
├── Stock ........................ server   (Suspense: es el más lento)
├── Reseñas ...................... server   (Suspense: 800 ms)
│   └── FechaRelativa ............ server   (format corre acá, 0 KB)
└── FormReseña ................... CLIENTE  (useActionState + validación en vivo)
    └── agregarReseña() .......... SERVER FUNCTION (con auth adentro)

Dos componentes de cliente en toda la página. Todo lo demás es servidor. Ese dibujo es la decisión de arquitectura completa; lo que sigue es transcribirlo.

Paso 3 — La página, con datos en paralelo y streaming

// app/productos/[slug]/page.tsx — Server Component
import { Suspense } from "react";
import { marked } from "marked";
import { traerProducto, traerReseñas, traerStock } from "@/lib/datos";
import { Galeria } from "@/components/Galeria";        // "use client" adentro
import { FormReseña } from "@/components/FormReseña";  // "use client" adentro

export default async function PaginaProducto({
  params,
}: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;

  // Arrancan YA, sin await: los tres viajes van en paralelo desde el primer ms
  const pReseñas = traerReseñas(slug);
  const pStock   = traerStock(slug);
  const producto = await traerProducto(slug);          // el rápido sí se espera

  return (
    <article>
      <h1>{producto.nombre}</h1>

        <Reseñas promesa={pReseñas} />

// Server Components auxiliares: no cuestan un byte de bundle

async function Reseñas({ promesa }: { promesa: Promise<Reseña[]> }) {
  const reseñas = await promesa;
  const fmt = new Intl.DateTimeFormat("es-AR", { dateStyle: "long" });
  return (
    <ul>

Detalle que vale 18 KB: date-fns desapareció y en su lugar hay Intl.DateTimeFormat, que viene con la plataforma. Al mover el formateo al servidor, la pregunta "¿qué librería uso?" cambió de respuesta — en Node la API nativa alcanza y sobra. Muchas dependencias del frontend existen solo porque el navegador viejo no las tenía.

Paso 4 — La Server Function, con su autorización adentro

// app/productos/acciones.ts
"use server";

import { z } from "zod";
import { revalidateTag } from "next/cache";
import { db } from "@/lib/db";
import { getSesion } from "@/lib/auth";

const NuevaReseña = z.object({
  slug: z.string().min(1).max(120),
  texto: z.string().trim().min(10).max(2000),
  puntaje: z.coerce.number().int().min(1).max(5),
});

export async function agregarReseña(_previo: unknown, fd: FormData) {
  // 1. ¿Quién sos? — de la sesión, NUNCA de los argumentos
  const sesion = await getSesion();
  if (!sesion) return { error: "Iniciá sesión para reseñar" };

  // 2. ¿Los datos son válidos? — vienen del cliente: hostiles por defecto
  const parseo = NuevaReseña.safeParse(Object.fromEntries(fd));
  if (!parseo.success) return { error: "Revisá los campos" };
  const datos = parseo.data;

  // 3. ¿Podés hacer ESTO sobre ESTE recurso? — autorización a nivel de objeto
  const compro = await db.pedido.findFirst({
    where: { usuarioId: sesion.userId, items: { some: { slug: datos.slug } } },
    select: { id: true },
  });
  if (!compro) return { error: "Solo compradores verificados pueden reseñar" };

  const yaReseñó = await db.reseña.findFirst({
    where: { autorId: sesion.userId, productoSlug: datos.slug },
    select: { id: true },
  });
  if (yaReseñó) return { error: "Ya publicaste una reseña de este producto" };

  // 4. Recién ahora, el efecto
  await db.reseña.create({
    data: {
      productoSlug: datos.slug,
      texto: datos.texto,
      puntaje: datos.puntaje,
      autorId: sesion.userId,            // ← de la sesión, no del formulario
    },
  });

  revalidateTag(`reseñas:${datos.slug}`);
  return { ok: true };
}
Reproducí el ataque antes de dar esto por bueno. Con la función publicada, cualquiera puede mandar el POST a mano sin pasar por tu formulario. Probalo con curl: sin cookie de sesión tiene que fallar en el paso 1; con una sesión de alguien que no compró el producto, en el paso 3. Si pasa alguno de los dos, tu control de acceso vive en el frontend y no existe. El detalle de estos modelos está en S-04 (Seguridad y autenticación) y M03 de Ciberseguridad (Autorización).

📌 La lección del ejercicio no es "usá RSC". Es que la ganancia salió de tres decisiones separadas y conviene saber cuál aportó qué: (a) mover el trabajo que no necesita el usuario al servidor bajó el bundle; (b) disparar los fetch en paralelo eliminó la cascada; (c) Suspense sacó lo lento del camino crítico. Checkpoint — ¿lo tenés claro?

¿Por qué un Client Component no puede importar un Server Component, pero sí recibirlo como children?

Porque son dos mecanismos distintos. Importar es una relación en el grafo de módulos que resuelve el bundler: si un archivo cliente importa otro, ese otro tiene que existir en el bundle del navegador, y un Server Component no puede existir ahí (usa la DB, secretos, APIs de Node). Recibir como children es una relación en el árbol de React en tiempo de render: quien construye ese elemento es el Server Component padre, en el servidor, y lo que el Client Component recibe es un subárbol ya renderizado — en el payload es un valor, no una referencia a código. Por eso la regla práctica es empujar el "use client" hacia las hojas y envolver por composición: el envase es cliente, el contenido sigue siendo servidor.

Publicás una Server Function que borra un comentario y el botón solo se muestra a los moderadores. ¿Alcanza?

No, y no alcanza por un margen enorme. Esa función es un endpoint HTTP público: al buildear queda expuesta con un identificador que cualquiera puede leer en el payload o en la pestaña Network, y reproducir con curl sin pasar jamás por tu UI. Esconder el botón cambia lo que se ve, no lo que se puede invocar. El chequeo tiene que estar adentro de la función, en este orden: autenticar (¿hay sesión válida?), validar los argumentos (vienen del cliente, son hostiles), autorizar contra el recurso concreto (¿este usuario puede borrar este comentario?) y recién ahí ejecutar. Y la identidad del que actúa sale siempre de la sesión, nunca de un argumento.

Tu página hace tres await seguidos y tarda 600 ms. ¿Cuándo Promise.all es la respuesta correcta y cuándo no?

Promise.all sirve cuando los tres pedidos son independientes (dependen solo de datos que ya tenés, como el slug): pasás de 600 ms a lo que tarde el más lento. No sirve en dos casos. Uno: si hay dependencia real —necesitás el id del producto para pedir el stock— ahí no hay paralelismo posible sin cambiar la API. Dos: si uno de los tres es mucho más lento que los otros, Promise.all iguala a todos para abajo y el usuario espera 800 ms para ver un título que estaba listo en 100 ms. En ese caso la respuesta es Suspense: esperás lo rápido, envolvés lo lento y lo dejás llegar por streaming. La variante fina es iniciar la promesa arriba sin await y pasarla hacia abajo, para que el viaje arranque temprano y el await ocurra donde el dato se usa.

Resumen ejecutivo

  • RSC no es SSR mejorado. SSR decide dónde se genera el primer HTML; RSC decide qué componentes existen en el cliente. Un Server Component no se hidrata porque no está allá.
  • Lo que viaja es el payload RSC: filas numeradas con el árbol serializado, referencias a chunks de cliente ($L0) y huecos que llegan después. De ese formato salen el streaming y las actualizaciones parciales que preservan el estado del cliente.
  • "use client" marca un punto de entrada al bundle, no un componente. Todo lo que ese archivo importa entra al navegador — por eso nunca va en un barril.
  • Las props que cruzan el límite tienen que ser serializables. Una función común no cruza porque es código más closure; la única forma legítima es exponerla como Server Function.
  • Importar arrastra, recibir no. Pasá Server Components como children o props ReactNode para no llevarte el árbol entero al cliente. Es el patrón que más bundle ahorra.
  • Una Server Function es un endpoint público: autenticar → validar → autorizar sobre el recurso → actuar. La identidad sale de la sesión, jamás de los argumentos.
  • La cascada es el modo de falla propio de RSC. Se rompe con Promise.all cuando los pedidos son independientes, y con Suspense cuando uno es mucho más lento.
  • Hay cuatro cachés, no uno. Antes de pelear con el caching, identificá cuál te está devolviendo lo viejo. Etiquetá con tags e invalidá con revalidateTag.
  • RSC brilla en contenido con poca interactividad; estorba en editores, canvas y SPAs sin servidor. Y te devuelve un servidor para operar — ese costo no aparece en ningún benchmark.

🧠 Autoevaluación

1. Un Client Component necesita mostrar adentro un componente que lee la base de datos. ¿Cuál es la solución correcta?

Importar lo arrastra al bundle del cliente, donde no puede existir; convertirlo a cliente te devuelve la cascada de useEffect y manda el ORM al navegador. La salida es la composición: el Client Component reserva un hueco (children) y el Server Component padre lo llena con un subárbol ya renderizado. En el payload eso es un valor, no una referencia a código — cero bytes de bundle.

2. Exponés una Server Function que cambia el rol de un usuario, y el botón solo aparece si sesion.rol === "admin". ¿Qué falta?

La Server Function se compila a un endpoint HTTP con un identificador visible en el payload y en la pestaña Network. Cualquiera lo reproduce sin tocar tu UI. Esconder el botón cambia lo que se ve, no lo que se puede invocar. El chequeo va adentro y en orden: autenticar, validar los argumentos, autorizar contra el recurso concreto, y recién entonces actuar — con la identidad tomada de la sesión, nunca de un argumento. Ver M03 de Ciberseguridad.

3. Tu página hace await del producto (100 ms) y después await de las reseñas (800 ms). Ambos dependen solo del slug. ¿Cuál es la mejor mejora para el primer contenido visible?

Promise.all arregla la cascada pero iguala a todos al más lento: el usuario espera 800 ms para ver un título que estaba listo en 100 ms. Iniciar la promesa lenta sin await hace que el viaje arranque en el primer milisegundo, el título se pinta a los ~100 ms, y las reseñas llegan por streaming al hueco del Suspense. Mover todo a useEffect es volver al problema original: reintroduce la cascada de red y suma bundle.

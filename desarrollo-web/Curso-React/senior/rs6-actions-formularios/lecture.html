RS6 — Actions, formularios y mutaciones

RS6.0 Por qué este módulo

Durante diez años React no tuvo opinión sobre los formularios. Te daba onSubmit, value y onChange, y el resto era problema tuyo. Como el problema era real y recurrente, cada equipo escribió su propia solución — y todas las soluciones caseras terminaron pareciéndose entre sí, incluidos los bugs.

Si trabajaste en una base de código React de cierto tamaño, ya viste este componente. Probablemente lo escribiste vos:

const [email, setEmail] = useState("");
const [cargando, setCargando] = useState(false);
const [error, setError] = useState(null);
const [exito, setExito] = useState(false);
const [errores, setErrores] = useState({});

Cinco useState para un formulario. Y con los cinco puestos, el componente todavía tiene: doble submit si el usuario hace clic dos veces rápido, pérdida de lo tipeado cuando el servidor devuelve un error, una condición de carrera si el usuario envía dos veces y la primera respuesta llega última, y cero accesibilidad — el error aparece en pantalla y ningún lector de pantalla lo anuncia.

💡 La tesis del módulo. Enviar datos al servidor y esperar la respuesta es una máquina de estados, no cinco variables sueltas. Tiene estados (inactivo, enviando, error, éxito), transiciones legales e ilegales, y una regla de concurrencia. Antes de React 19 esa máquina la escribías vos, mal, una vez por formulario. Las Actions son esa máquina, hecha por React, integrada con transiciones, Suspense, error boundaries y —el detalle que nadie esperaba— con el <form> de HTML de 1995.

A septiembre de 2026 esto ya no es material de vanguardia: React 19.2 es la versión estable, y tanto las Actions como las Server Functions son API estables, no experimentales. Lo que sigue siendo experimental es el conocimiento del equipo promedio sobre ellas.

Lo que este módulo no es. No es "dejá de usar react-hook-form". Hay formularios donde la librería sigue ganando por goleada y en RS6.9 los vamos a nombrar con precisión. Lo que sí es: entender qué resuelve React de fábrica, para que la decisión de agregar una dependencia sea una decisión y no un reflejo.

RS6.1 Qué es una Action, exactamente

El término "Action" se usa con tres significados en la documentación y en las charlas, y conviene separarlos ya:

TérminoQué esDónde corre
Action (convención)Una función async pasada a action, formAction o startTransitionCliente
Server FunctionUna función marcada con "use server", invocable desde el clienteServidor
Server ActionNombre viejo de lo anterior. Sobrevive en blogs y en el ecosistemaServidor
📌 Una Action no es un tipo especial de función. Es una función async común que React ejecuta dentro de una transición. Eso es todo el truco: al estar en una transición, React sabe cuándo empezó y cuándo terminó, y de ahí saca el pending, el orden de las respuestas y la reversión de lo optimista. No hay magia; hay contabilidad que antes hacías vos.

La forma más simple es pasar la función directo al <form>. React la llama con el FormData y previene el submit nativo por vos:

function Suscribirse() {
  async function suscribir(formData) {
    await fetch("/api/newsletter", {
      method: "POST",
      body: JSON.stringify({ email: formData.get("email") }),
      headers: { "Content-Type": "application/json" },
    });
  }

  return (
    <form action={suscribir}>
      <input name="email" type="email" required />
      <button>Suscribirme</button>
    </form>
  );
}

Comparalo con lo que había que escribir antes para lo mismo, y contá cuántas líneas son lógica de negocio y cuántas son plomería:

// La versión pre-19
function Suscribirse() {
  const [email, setEmail] = useState("");
  const [enviando, setEnviando] = useState(false);

  async function onSubmit(e) {
    e.preventDefault();          // se olvida constantemente
    setEnviando(true);           // y hay que acordarse del finally
    try {
      await fetch("/api/newsletter", { /* … */ });
    } finally {
      setEnviando(false);
    }
  }

  return (
    <form onSubmit={onSubmit}>
      <input value={email} onChange={(e) => setEmail(e.target.value)} />
      <button disabled={enviando}>Suscribirme</button>
    </form>
  );
}

Dos comportamientos que hay que saber de entrada

El <form action> de React tiene dos conductas propias que sorprenden la primera vez:

  1. React resetea el formulario cuando la acción termina, si los campos son no controlados. Es lo correcto para el caso feliz (enviaste un comentario, el textarea queda limpio) y es exactamente lo que te arruina el día cuando el servidor devuelve un error de validación: el usuario ve el error y el formulario vacío.
  2. La acción corre en una transición. Eso significa que la UI queda interactiva mientras se envía, y que React puede priorizar otras actualizaciones por encima del render que dispare la respuesta.
import { requestFormReset } from "react-dom";

// Si necesitás controlar el reseteo vos mismo —por ejemplo, resetear
// SOLO cuando la respuesta fue exitosa— usás la API explícita.
async function enviar(formData) {
  const r = await guardar(formData);
  if (r.ok) requestFormReset(document.forms.comentario);
}
En la práctica casi nunca vas a llamar requestFormReset a mano: la solución idiomática al problema "se me borró lo que había tipeado" es devolver los valores enviados en el estado de la acción y usarlos como defaultValue. Lo vemos con código en RS6.2 y lo aplicamos completo en el Worked Example.

RS6.2 useActionState: la firma completa

El <form action> pelado no te devuelve nada: no sabés si falló, ni por qué. useActionState es la pieza que convierte una acción en una máquina de estados con resultado.

const [estado, accion, pendiente] = useActionState(
  fn,            // (estadoPrevio, formData) => nuevoEstado
  estadoInicial, // el valor de `estado` antes del primer envío
  permalink?     // URL de fallback para progressive enhancement
);

Tres cosas de esa firma importan y suelen pasarse por alto:

1. La función recibe el estado previo como primer argumento

No es decorativo. Habilita acumular información entre envíos: contar intentos fallidos, mantener un historial, aplicar un backoff, o —el caso más común— conservar lo que el usuario ya había tipeado.

type Estado = {
  errores?: Record<string, string>;
  valores?: Record<string, string>;
  intentos: number;
  ok?: boolean;
};

const [estado, accion, pendiente] = useActionState<Estado, FormData>(
  async (previo, formData) => {
    const valores = Object.fromEntries(formData) as Record<string, string>;
    const r = await registrar(valores);

    if (!r.ok) {
      return {
        errores: r.errores,
        valores,                       // ← lo tipeado vuelve al formulario
        intentos: previo.intentos + 1, // ← el estado previo, usado de verdad
      };
    }
    return { ok: true, intentos: previo.intentos };
  },
  { intentos: 0 }
);

Con ese estado en la mano, el formulario se reconstruye sin perder nada:

<form action={accion}>
  <input
    name="email"
    defaultValue={estado.valores?.email ?? ""}
    aria-invalid={!!estado.errores?.email}
  />
  {estado.errores?.email && <p>{estado.errores.email}</p>}

  {estado.intentos >= 3 && (
    <p>¿Necesitás ayuda? <a href="/soporte">Escribinos</a></p>
  )}
</form>
El error que ve todo el mundo la primera vez: escribir async (formData) => … y encontrarse con que formData.get no existe. La firma es (estadoPrevio, formData), en ese orden. Si no vas a usar el previo, el idioma es async (_previo, formData) => …, no borrarlo.

2. El tercer valor de retorno es pending

Existe desde React 19 y evita el useState de cargando por completo. Sirve para el componente que renderiza el <form>. Para el botón de adentro hay una herramienta mejor, y es el tema de RS6.3.

3. permalink: el argumento que casi nadie usa (y debería)

Es el eslabón de progressive enhancement. Si el formulario se envía antes de que el JavaScript haya hidratado y la acción es una Server Function, React no puede ejecutar la lógica del cliente — entonces el navegador hace el POST nativo y el servidor redirige a la URL del permalink, que renderiza la misma página con el estado ya aplicado.

const [estado, accion] = useActionState(
  actualizarPerfil,        // Server Function, con "use server"
  { errores: null },
  "/perfil/editar"         // ← a dónde ir si todavía no hidrató
);
Cuándo importa esto de verdad. No es un caso de laboratorio: la ventana entre "el HTML está pintado" y "el bundle terminó de hidratar" son cientos de milisegundos en un celular de gama media con red 3G. Un usuario que llega, ve el formulario y aprieta rápido cae justo ahí. Sin permalink, ese envío se pierde o se comporta distinto; con él, degrada a una navegación normal.

RS6.3 useFormStatus: el botón que sabe sin que le digan

Este hook parece redundante — useActionState ya devuelve pending. La razón de su existencia es de arquitectura de componentes, no de conveniencia.

Pensá en un design system. Tenés un <BotonEnviar> que se usa en cuarenta formularios distintos. Sin useFormStatus, cada uno de esos cuarenta formularios tiene que pasarle una prop pending, y si el botón está tres niveles abajo, la prop viaja tres niveles. El componente compartido depende de que cada consumidor se acuerde de cablear el estado.

"use client";
import { useFormStatus } from "react-dom";

// Este componente NO recibe ninguna prop de estado.
// Lee el <form> ancestro más cercano.
export function BotonEnviar({ children }: { children: React.ReactNode }) {
  const { pending } = useFormStatus();
  return (
    <button type="submit" disabled={pending} aria-busy={pending}>
      {pending ? "Enviando…" : children}
    </button>
  );
}

Y ahora cualquier formulario lo usa sin cablear nada:

<form action={accion}>
  <input name="email" />
  <BotonEnviar>Crear cuenta</BotonEnviar>
</form>
📌 La regla que hace fallar a todos: useFormStatus lee el <form> ancestro. Un componente que renderiza el <form> y llama al hook en el mismo cuerpo va a leer pending: false para siempre. El hook tiene que estar en un componente que sea hijo del <form>, no en el que lo crea. 
// ❌ Siempre pending: false. El hook está en el MISMO componente
//    que renderiza el form, no adentro de él.
function Formulario() {
  const { pending } = useFormStatus();
  return (
    <form action={accion}>
      <button disabled={pending}>Enviar</button>
    </form>
  );
}

// ✅ El hook vive en un componente hijo.
function Formulario() {
  return (
    <form action={accion}>
      <BotonEnviar>Enviar</BotonEnviar>
    </form>
  );
}

El hook devuelve más que pending. El objeto completo es útil para UIs que muestran lo que se está enviando mientras se envía:

const { pending, data, method, action } = useFormStatus();

// `data` es el FormData en vuelo — sirve para previsualizar
if (pending && data) {
  return <p>Publicando “{String(data.get("titulo"))}”…</p>;
}
useFormStatus se importa de react-dom, no de react. Es un detalle que cuesta media hora de depuración la primera vez, y tiene su lógica: el hook depende del DOM (existe un <form> real), mientras que useActionState es agnóstico del renderer.

RS6.4 useOptimistic: mostrar el futuro y poder retractarse

La UI optimista es simple de describir y difícil de hacer bien: mostrás el resultado antes de que el servidor confirme, y si falla, lo deshacés. La parte difícil es el "si falla, lo deshacés" — sobre todo cuando hay varias operaciones en vuelo.

Así se hacía a mano, y así fallaba:

// ❌ La versión artesanal. Funciona hasta que no.
async function enviar(texto) {
  const provisorio = { id: `temp-${Date.now()}`, texto };
  setMensajes((m) => [...m, provisorio]);        // optimista

  try {
    const real = await enviarAlServidor(texto);
    setMensajes((m) =>
      m.map((x) => (x.id === provisorio.id ? real : x))
    );
  } catch {
    // rollback manual: hay que acordarse, y hay que filtrar bien
    setMensajes((m) => m.filter((x) => x.id !== provisorio.id));
  }
}

Los problemas de esa versión no son de estilo:

  • El rollback es tuyo. Si te olvidás de un catch, el mensaje fantasma se queda en pantalla para siempre.
  • Con dos envíos concurrentes se rompe. Si el segundo responde antes que el primero, el map por id todavía anda, pero cualquier reemplazo de lista completa pisa el otro optimista.
  • Los ids temporales se filtran a la UI. Un key que cambia de temp-123 a 987 desmonta y remonta el nodo: se pierden animaciones, foco y estado local.

useOptimistic ataca la raíz: el valor optimista no es estado que vos administrás, es una proyección que React descarta sola cuando la transición termina — con éxito o con error.

"use client";
import { useOptimistic, useRef } from "react";

type Mensaje = { id: string; texto: string; enviando?: boolean };

export function Chat({ mensajes, enviar }: {
  mensajes: Mensaje[];
  enviar: (fd: FormData) => Promise<void>;
}) {
  const form = useRef<HTMLFormElement>(null);

  const [vista, agregarOptimista] = useOptimistic(
    mensajes,
    (actual: Mensaje[], texto: string) => [
      ...actual,
      { id: `opt-${actual.length}`, texto, enviando: true },
    ]
  );

  return (
    <>
      <ul>
        {vista.map((m) => (
          <li key={m.id} style={{ opacity: m.enviando ? 0.5 : 1 }}>
            {m.texto} {m.enviando && <span aria-label="enviando">⏳</span>}
          </li>
        ))}
      </ul>

      <form
        ref={form}
        action={async (fd) => {
          agregarOptimista(String(fd.get("texto")));  // dentro de la acción
          form.current?.reset();
          await enviar(fd);
        }}
      >
        <input name="texto" required />
        <button>Enviar</button>
      </form>
    </>
  );
}
💡 El modelo mental correcto. useOptimistic no guarda nada. Toma el estado real (el primer argumento) y le aplica una función de proyección mientras hay una transición en curso. Cuando la transición termina, la proyección desaparece y volvés a ver el estado real — que para entonces ya incluye el mensaje si salió bien, o no lo incluye si falló. El rollback no es una acción: es la ausencia de la proyección. Por eso no puede olvidarse.
La llamada tiene que ocurrir dentro de una acción o transición. Si llamás a agregarOptimista desde un onClick común, fuera de startTransition y fuera de un action, React descarta la actualización de inmediato y no vas a ver nada. No es un bug: es la definición.

Y una advertencia de producto que los tutoriales omiten: la UI optimista es una promesa que hacés en nombre del servidor. Está bien para operaciones que fallan poco y cuyo fracaso es barato (un like, un ítem de una lista, marcar como leído). Está mal para cualquier cosa con consecuencias: no muestres "pago aprobado" de manera optimista. La regla es la reversibilidad percibida, no la técnica.

RS6.5 Formularios sin JavaScript: por qué esto importa

Cuando pasás una Server Function a action, React emite un <form> con method="post" y un action apuntando a un endpoint. Si el JavaScript nunca llega, el navegador hace lo que hace desde 1995: postea el formulario. El servidor ejecuta la función, responde, y la página se re-renderiza.

// app/acciones.ts
"use server";

export async function crearTarea(formData: FormData) {
  const titulo = String(formData.get("titulo") ?? "").trim();
  if (!titulo) return;
  await db.tarea.create({ data: { titulo, usuarioId: await usuarioActual() } });
  revalidatePath("/tareas");
}
// app/tareas/page.tsx — Server Component. Ni una línea de "use client".
import { crearTarea } from "../acciones";

export default async function Tareas() {
  const tareas = await db.tarea.findMany();
  return (
    <>
      <form action={crearTarea}>
        <input name="titulo" required />
        <button>Agregar</button>
      </form>
      <ul>{tareas.map((t) => <li key={t.id}>{t.titulo}</li>)}</ul>
    </>
  );
}

Ese formulario funciona con JavaScript deshabilitado. No "más o menos": funciona.

"Nadie deshabilita JavaScript"

Es la objeción estándar, y es una respuesta a la pregunta equivocada. Casi nadie lo deshabilita a propósito; lo que pasa todo el tiempo es que el JavaScript no está disponible:

  • El bundle todavía no terminó de descargar y el usuario ya está tocando la pantalla.
  • Un chunk falló: la CDN tuvo un hipo, el túnel del subte cortó la conexión, un proxy corporativo lo bloqueó.
  • Una extensión del navegador rompió el árbol y el error de hidratación tiró abajo la isla interactiva.
  • El dispositivo se quedó sin memoria y el navegador descartó el contexto de la pestaña.
  • Un bug tuyo en un componente ajeno reventó el error boundary de arriba.
📌 El progressive enhancement no es un gesto de caridad hacia usuarios raros: es tolerancia a fallas. Es la diferencia entre "la app se degradó y el checkout todavía funciona" y "la app se rompió y no se puede comprar". El mismo argumento por el que ponés un timeout y un reintento en una llamada de red aplica acá.
Dónde se pierde el beneficio sin darse cuenta. En el momento en que envolvés la acción en una función de cliente —para agregar un console.log, para mostrar un toast, para leer algo de un store— dejás de tener un <form> que postea solo, porque la lógica ahora vive en el bundle. Si el progressive enhancement te importa, la acción del <form> tiene que ser la Server Function en sí, o un useActionState con permalink sobre una Server Function. Todo lo demás degrada a "no pasa nada al apretar el botón".

RS6.6 Validación: la del cliente es UX, la del servidor es la que cuenta

Hay tres capas de validación y cada una tiene un trabajo distinto. Confundirlas produce, en un extremo, formularios molestos, y en el otro, agujeros de seguridad.

CapaPara qué sirveSe puede saltear
HTML nativo (required, type, pattern)Feedback instantáneo, cero JS, gratisSí — con devtools o curl
JS de cliente (Zod, react-hook-form)Mensajes claros, validación cruzada entre camposSí — es código del atacante
ServidorLa verdad. Integridad de datos y seguridadNo
Todo lo que llega del cliente es hostil. No "puede ser hostil": es. Los campos de un formulario son texto arbitrario que alguien te manda por HTTP; el <input type="number" max="5"> no es una restricción, es una sugerencia dibujada. Esto no es paranoia de módulo de seguridad, es el A03: Inyección y el A04: Diseño inseguro del OWASP Top 10. Si querés el tratamiento completo —inyección, validación de entrada, control de acceso roto— está en M04 de Ciberseguridad.

Un esquema, dos usos

La forma limpia de no duplicar reglas es definir el esquema una sola vez y usarlo en las dos puntas. El de cliente da inmediatez; el de servidor decide.

// lib/esquemas.ts — compartido
import { z } from "zod";

export const Checkout = z.object({
  email: z.email("Email inválido"),
  nombre: z.string().min(2, "Mínimo 2 caracteres"),
  cantidad: z.coerce.number().int().min(1).max(10),
  cupon: z.string().optional(),
});
// Lado servidor: la validación que cuenta
"use server";
import { Checkout } from "@/lib/esquemas";

export async function comprar(_previo: unknown, formData: FormData) {
  const parsed = Checkout.safeParse(Object.fromEntries(formData));

  if (!parsed.success) {
    const errores: Record<string, string> = {};
    for (const issue of parsed.error.issues) {
      const campo = String(issue.path[0]);
      errores[campo] ??= issue.message;     // el primero por campo
    }
    return { errores, valores: Object.fromEntries(formData) };
  }

  // parsed.data está tipado y es seguro de acá para abajo
  await procesarPago(parsed.data);
  return { ok: true };
}
En Zod 4 hay atajos para eso: z.flattenError(parsed.error) te da { formErrors, fieldErrors } listo para pintar. El bucle de arriba lo escribí a mano a propósito, porque deja ver la forma de issues — y porque cuando quieras un mensaje por campo en vez de un array, ya sabés dónde tocar.
Nunca devuelvas el error crudo de la capa de datos. Un mensaje de excepción de la base filtra nombres de tablas, columnas y a veces fragmentos de la consulta — información gratis para quien esté sondeando. Traducí a mensajes de negocio y logueá el original del lado del servidor con un identificador de correlación.

La validación de servidor no es solo de forma

Es la trampa sutil: un esquema Zod valida forma (es un string, mide más de 2, es un número entre 1 y 10). No valida reglas de negocio ni permisos. Un checkout puede pasar el esquema perfectamente y aun así ser inválido:

  • El cupón existe pero venció, o ya se usó, o no aplica a esa categoría.
  • Hay 3 unidades en stock y el FormData pide 10.
  • El precio que mandó el cliente no es el precio real. Nunca confíes en un precio que viene del formulario — leelo de tu base por el id del producto.
  • El usuario no tiene permiso sobre ese recurso.

RS6.7 Server Functions como mutación: el endpoint que no parece uno

En RS4 estableciste la regla central y acá se aplica en su contexto natural, que es el de las mutaciones:

Una Server Function es un endpoint HTTP público. Al buildear queda expuesta con un identificador que cualquiera puede leer en el payload o en la pestaña Network, y reproducir con curl sin pasar jamás por tu interfaz. Que el botón esté escondido, que el formulario no se renderice, que la ruta esté detrás de un guard — nada de eso protege la función. El chequeo va adentro.

El orden importa y es siempre el mismo: autenticar → validar → autorizar sobre el recurso concreto → actuar.

"use server";

export async function borrarComentario(_previo: unknown, formData: FormData) {
  // 1. Autenticar: ¿hay sesión válida?
  const sesion = await getSesion();
  if (!sesion) return { error: "No autenticado" };

  // 2. Validar: los argumentos vienen del cliente, son hostiles
  const parsed = z.object({ id: z.uuid() })
    .safeParse(Object.fromEntries(formData));
  if (!parsed.success) return { error: "Solicitud inválida" };

  // 3. Autorizar sobre ESTE recurso, no sobre un rol genérico
  const comentario = await db.comentario.findUnique({
    where: { id: parsed.data.id },
  });
  if (!comentario) return { error: "No encontrado" };

  const esDueño   = comentario.autorId === sesion.usuarioId;
  const esModerador = sesion.roles.includes("moderador");
  if (!esDueño && !esModerador) return { error: "Sin permisos" };

  // 4. Recién ahora, actuar
  await db.comentario.delete({ where: { id: parsed.data.id } });
  revalidatePath(`/post/${comentario.postId}`);
  return { ok: true };
}
El bug que se repite: aceptar usuarioId como campo del formulario. Si la función recibe quién sos en vez de deducirlo de la sesión, cualquiera actúa en nombre de otro con un curl de una línea. La identidad sale siempre de la sesión. Los argumentos llevan qué hacer, nunca quién lo hace. Fijate en el ejemplo: sesion.usuarioId no aparece jamás en el FormData.

Dos detalles operativos que muerden en producción:

  • Los ids de las Server Functions cambian entre builds. Si un usuario tiene la pestaña abierta desde antes de un deploy, su próximo envío puede apuntar a un id que ya no existe. Manejá ese error como "recargá la página", no como un fallo genérico.
  • No hay rate limiting gratis. Un endpoint público sin límite es un endpoint que se puede martillar. Poné el límite del lado del servidor, por usuario y por IP, en las mutaciones que valgan algo.

RS6.8 Actions + caché: mutar es la mitad del trabajo

Una mutación que anda pero deja la pantalla mostrando lo viejo es, para el usuario, una mutación que no anda. Acá se enganchan las Actions con todo lo que viste en RS5: la acción cambia el dato, y algo tiene que decirle a la caché que lo que tenía ya no sirve.

"use server";
import { revalidateTag } from "next/cache";

Cuando la mutación convive con caché de cliente

Si tenés TanStack Query, las Actions no lo reemplazan: se combinan. La Action hace la mutación, el onSuccess invalida.

"use client";
import { useQueryClient } from "@tanstack/react-query";
import { useActionState } from "react";

export function FormNota() {
  const qc = useQueryClient();

  const [estado, accion] = useActionState(async (_p, fd) => {
    const r = await crearNota(fd);            // Server Function
    if (r.ok) await qc.invalidateQueries({ queryKey: ["notas"] });
    return r;
  }, {});

  return <form action={accion}>{/* … */}</form>;
}
El orden importa. Si invalidás antes de que la escritura haya commiteado en la base —o si tu base tiene réplicas de lectura con lag— vas a refetchear el valor viejo y a pintar exactamente lo que querías evitar. Invalidá después del await de la escritura, y si hay réplicas, leé de la primaria inmediatamente después de mutar.

Cuándo cada uno sigue ganando

Actions nativas. Formularios de envío: login, alta, checkout, comentario, contacto, filtros. Todo lo que sea "junto datos, los mando, muestro el resultado". Si además es una app con servidor, el progressive enhancement viene de regalo y no lo pagás.
react-hook-form. Sigue ganando —y por bastante— en formularios muy dinámicos: wizards de varios pasos con estado compartido, arrays de campos que el usuario agrega y borra (ítems de una factura, pasajeros de un vuelo), validación cruzada en vivo ("la fecha de fin tiene que ser posterior a la de inicio", evaluado en cada tecla), campos condicionales que aparecen según respuestas anteriores, y todo lo que integre componentes controlados de una librería de UI. Ahí FormData se te queda corto y armar el equivalente a mano es reescribir la librería peor.
Formik. Solo por inercia. Está en modo mantenimiento y su modelo controlado re-renderiza el árbol del formulario en cada tecla, cosa que se nota en formularios grandes. Si tenés uno andando y estable, dejalo; no arranques nada nuevo con él.
Manual. Un campo de búsqueda con debounce, un toggle que persiste, un input que no es realmente un formulario. Meter una máquina de estados de submit ahí es sobrediseño.
El híbrido existe y es legítimo. react-hook-form para la experiencia de tipeo en el cliente, y la Action para el envío y los errores del servidor: handleSubmit valida, y si pasa, llama a la Server Function. No tenés que elegir un bando; tenés que saber qué te da cada pieza.

RS6.10 Accesibilidad: un formulario inaccesible está roto

No "es mejorable": está roto, del mismo modo que lo está uno que pierde los datos. Un formulario existe para que alguien complete una tarea, y si una parte de tus usuarios no puede completarla, no cumple su función. Además, en la mayoría de las jurisdicciones donde vende software una empresa mediana, es un requisito legal.

Son cinco cosas concretas.

1. Etiquetas de verdad

// ❌ El placeholder desaparece al tipear y no lo lee el lector de pantalla
<input name="email" placeholder="Tu email" />

// ✅ Label asociado, y el placeholder como ejemplo, no como etiqueta
<label htmlFor="email">Email</label>
<input id="email" name="email" type="email" autoComplete="email" />
El atributo autoComplete no es solo comodidad. Para usuarios con dificultades motrices o cognitivas, el autocompletado del navegador es la diferencia entre completar un checkout y abandonarlo. Es, literalmente, un criterio de la WCAG (1.3.5, Identify Input Purpose).

2. Errores vinculados al campo

<label htmlFor="email">Email</label>
<input
  id="email"
  name="email"
  type="email"
  defaultValue={estado.valores?.email}
  aria-invalid={estado.errores?.email ? true : undefined}
  aria-describedby={estado.errores?.email ? "email-error" : undefined}
/>
{estado.errores?.email && (
  <p id="email-error" className="error">{estado.errores.email}</p>
)}
📌 aria-invalid dice que está mal; aria-describedby dice qué está mal. Hacen falta los dos. Sin el primero, el lector de pantalla no marca el campo como erróneo al navegarlo. Sin el segundo, dice "inválido" y el usuario tiene que adivinar por qué. Y ponelos condicionalmente: un aria-invalid="false" permanente es ruido, y un aria-describedby que apunta a un id inexistente es peor que no ponerlo.

3. Anuncio del resumen de errores

Cuando el envío falla, alguien que usa lector de pantalla no ve el error aparecer. Hay que anunciarlo, y el detalle importa:

{/* La región vive SIEMPRE en el DOM, aunque esté vacía */}
<div role="alert" aria-live="assertive" ref={resumen} tabIndex={-1}>
  {estado.errores && (
    <>
      <h2>No pudimos procesar el formulario</h2>
      <ul>
        {Object.entries(estado.errores).map(([campo, msg]) => (
          <li key={campo}><a href={`#${campo}`}>{msg}</a></li>
        ))}
      </ul>
    </>
  )}
</div>
La trampa fina: si montás el contenedor role="alert" junto con su contenido, varios lectores de pantalla no anuncian nada — el nodo aparece ya "lleno" y la mutación no dispara el anuncio. La región tiene que existir vacía desde el primer render, y lo que cambia es su contenido. Es el bug de accesibilidad más común en formularios de React, y es invisible en cualquier auditoría automática.

4. Foco al primer error

const resumen = useRef<HTMLDivElement>(null);

useEffect(() => {
  if (estado.errores) resumen.current?.focus();  // el div tiene tabIndex={-1}
}, [estado]);

Sin esto, el usuario que envió con el teclado queda con el foco en el botón, al final del formulario, sin ninguna pista de que arriba pasó algo. Mover el foco al resumen —y que cada ítem del resumen sea un link al campo— resuelve el recorrido completo.

Depender de [estado] y no de [estado.errores] es intencional: si el usuario reenvía y vuelve a fallar con el mismo error, la referencia del objeto de estado cambia igual y el foco se mueve otra vez. Con la dependencia más fina, el segundo intento fallido no anuncia nada y parece que el botón no hace nada.

5. No dependas solo del color

Un borde rojo no es un mensaje. Necesitás texto, y un ícono o un cambio de forma que sobreviva a un daltonismo. Es el criterio 1.4.1 de la WCAG y es trivial de cumplir si el error ya está escrito.

RS6.11 Los errores clásicos

Doble submit

El usuario hace clic dos veces rápido, o aprieta Enter dos veces, y se crean dos pedidos. Con useFormStatus el botón se deshabilita solo apenas arranca la transición, y eso tapa el 95% de los casos. El 5% restante —red lenta, doble tap, un reintento del navegador— se tapa del lado del servidor:

"use server";

export async function crearPedido(_previo: unknown, fd: FormData) {
  const clave = String(fd.get("idempotencyKey"));   // generada al renderizar

  const existente = await db.pedido.findUnique({ where: { clave } });
  if (existente) return { ok: true, id: existente.id };  // ya pasó: no dupliques

  const pedido = await db.pedido.create({ data: { clave, /* … */ } });
  return { ok: true, id: pedido.id };
}
📌 Deshabilitar el botón es UX; la clave de idempotencia es corrección. Lo primero evita que el usuario lo intente; lo segundo garantiza que aunque lo intente —o aunque el navegador reintente el POST solo— no le cobres dos veces. En cualquier mutación con consecuencias (cobros, envío de mails, creación de recursos), la clave no es opcional.

Se pierde lo tipeado

Ya está diagnosticado en RS6.1: React resetea el formulario no controlado cuando la acción termina, incluso si terminó devolviendo un error. La cura es devolver los valores en el estado y usarlos como defaultValue. Es dos líneas, y es la diferencia entre un usuario que corrige un campo y uno que abandona el checkout.

El spinner que no aparece

// ❌ pending SIEMPRE false: el hook está en el componente que crea el form
function Checkout() {
  const { pending } = useFormStatus();
  return <form action={pagar}><button disabled={pending}>Pagar</button></form>;
}

// ✅ Opción A: el tercer valor de useActionState, en este mismo componente

  const [estado, accion, pendiente] = useActionState(pagar, {});
  return <form action={accion}><button disabled={pendiente}>Pagar</button></form>;
}

// ✅ Opción B: useFormStatus en un hijo, reutilizable en todo el sistema

}

Estados imposibles que la UI muestra igual

Con cinco booleanos hay 32 combinaciones y solo 4 son válidas. cargando && error, exito && error, cargando && exito — todos representables, todos bugs. Un único estado con forma de unión discriminada los vuelve imposibles de escribir:

type Estado =
  | { fase: "inicial" }
  | { fase: "error"; errores: Record<string, string>; valores: Valores }
  | { fase: "ok"; pedidoId: string };

// Ya no existe manera de estar en "error" y en "ok" a la vez.

Tragarse el error

Una excepción sin capturar dentro de una Server Function llega al cliente ofuscada en producción: React la reemplaza por un digest. Está bien para lo inesperado y es pésimo para lo esperable. Los errores de negocio se capturan y se devuelven como valor; los inesperados se dejan subir al error boundary, con su digest, y se correlacionan en el log del servidor.

Confiar en el precio del formulario

Merece su propia línea porque cuesta plata. Si tu Action lee fd.get("precio") y cobra eso, ya te robaron: cualquiera edita el value del input oculto. Del formulario viene el id del producto y la cantidad; el precio se lee de tu base, siempre, sin excepciones.

🧑‍🎓 Worked Example — checkout con validación de servidor

Un formulario de checkout: email, nombre, cantidad y cupón. El servidor valida forma, stock y cupón. Vamos a escribir la versión que hay en la mayoría de las bases de código, listar sus bugs con precisión, y reescribirla.

Paso 1 — La versión que hay

function Checkout({ producto }) {
  const [email, setEmail] = useState("");
  const [nombre, setNombre] = useState("");
  const [cantidad, setCantidad] = useState(1);
  const [cargando, setCargando] = useState(false);
  const [error, setError] = useState(null);

  async function onSubmit(e) {
    e.preventDefault();
    setCargando(true);
    setError(null);

    try {
      const r = await fetch("/api/checkout", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({
          email, nombre, cantidad,
          precio: producto.precio,       // ← el cliente manda el precio
        }),
      });
      if (!r.ok) throw new Error(await r.text());
      window.location.href = "/gracias";
    } catch (err) {
      setError(err.message);             // ← mensaje crudo del servidor
    } finally {
      setCargando(false);
    }
  }

  return (
    <form onSubmit={onSubmit}>
      <input value={email} onChange={(e) => setEmail(e.target.value)}
             placeholder="Email" />
      <input value={nombre} onChange={(e) => setNombre(e.target.value)}
             placeholder="Nombre" />
      <input type="number" value={cantidad}
             onChange={(e) => setCantidad(+e.target.value)} />
      {error && <p style={{ color: "red" }}>{error}</p>}
      <button disabled={cargando}>
        {cargando ? "Procesando…" : "Comprar"}
      </button>
    </form>
  );
}

Paso 3 — La Server Function

// app/checkout/acciones.ts
"use server";

import { z } from "zod";
import { redirect } from "next/navigation";
import { revalidateTag } from "next/cache";

const Esquema = z.object({
  email: z.email("Ingresá un email válido"),
  nombre: z.string().min(2, "El nombre es muy corto"),
  cantidad: z.coerce.number().int().min(1, "Mínimo 1").max(10, "Máximo 10"),
  cupon: z.string().trim().optional(),
  productoId: z.uuid(),
  clave: z.uuid(),                       // idempotencia
});

export type EstadoCheckout = {
  errores?: Record<string, string>;
  valores?: Record<string, string>;
  ok?: boolean;
};

export async function comprar(
  _previo: EstadoCheckout,
  fd: FormData
): Promise<EstadoCheckout> {
  const crudo = Object.fromEntries(fd) as Record<string, string>;

  // 1. Autenticar
  const sesion = await getSesion();
  if (!sesion) return { errores: { _: "Iniciá sesión para comprar" }, valores: crudo };

  // 2. Validar forma
  const parsed = Esquema.safeParse(crudo);
  if (!parsed.success) {
    const errores: Record<string, string> = {};
    for (const i of parsed.error.issues) {
      const campo = String(i.path[0]);
      errores[campo] ??= i.message;
    }
    return { errores, valores: crudo };     // ← devolvemos lo tipeado
  }

  const { productoId, cantidad, cupon, clave } = parsed.data;

  // 3. Idempotencia: si esta clave ya se procesó, no cobres de nuevo
  const previoPedido = await db.pedido.findUnique({ where: { clave } });
  if (previoPedido) redirect(`/gracias/${previoPedido.id}`);

  // 4. Reglas de negocio (el esquema NO las valida)
  const producto = await db.producto.findUnique({ where: { id: productoId } });
  if (!producto) return { errores: { _: "El producto ya no está disponible" }, valores: crudo };
  if (producto.stock < cantidad) {
    return {
      errores: { cantidad: `Solo quedan ${producto.stock} unidades` },
      valores: crudo,
    };
  }

  let descuento = 0;
  if (cupon) {
    const c = await db.cupon.findUnique({ where: { codigo: cupon } });
    if (!c || c.venceEl < new Date() || c.usos >= c.maxUsos) {
      return { errores: { cupon: "Cupón inválido o vencido" }, valores: crudo };
    }
    descuento = c.porcentaje;
  }

  // 5. Actuar. El PRECIO sale de la base, jamás del formulario.
  const total = producto.precio * cantidad * (1 - descuento / 100);

  try {
    const pedido = await db.pedido.create({
      data: { clave, productoId, cantidad, total, usuarioId: sesion.usuarioId },
    });
    revalidateTag("carrito");
    redirect(`/gracias/${pedido.id}`);
  } catch (e) {
    logger.error({ err: e, usuarioId: sesion.usuarioId }, "checkout falló");
    return { errores: { _: "No pudimos procesar tu compra. Probá de nuevo." }, valores: crudo };
  }
}
Ojo con redirect() dentro de un try. En Next.js, redirect() funciona lanzando una excepción especial. Un catch genérico alrededor se la come y el redirect nunca ocurre: el usuario ve el formulario otra vez y cree que no compró. Sacá el redirect del try, o re-lanzá lo que no sepas manejar. Es un bug real, silencioso y carísimo.

Paso 4 — El formulario

"use client";

import { useActionState, useEffect, useRef } from "react";
import { useFormStatus } from "react-dom";
import { comprar, type EstadoCheckout } from "./acciones";

function BotonComprar() {
  const { pending } = useFormStatus();
  return (
    <button type="submit" disabled={pending} aria-busy={pending}>
      {pending ? "Procesando…" : "Confirmar compra"}
    </button>

export function Checkout({
  producto,
  clave,                       // uuid generado en el servidor al renderizar

  producto: { id: string; nombre: string; precio: number };
  clave: string;

noValidate apaga los globos nativos del navegador para que todos los errores se vean con el mismo diseño y el mismo comportamiento de anuncio. Los atributos type="email", min y max quedan igual: siguen dando teclado apropiado en móvil y siguen siendo la primera línea de validación cuando no hay JS. Apagás la UI nativa, no la semántica.

Paso 5 — Verificar, que es lo único que cuenta

Declarar que funciona no es haberlo verificado. Cinco pruebas concretas:

  1. Sin JavaScript. DevTools → Settings → Debugger → Disable JavaScript, recargá y comprá. Tiene que funcionar: se pierden el spinner y los mensajes en vivo, pero la compra se hace y el error de validación se muestra en la página recargada.
  2. Doble submit. Network throttling en Slow 3G, doble clic. Un solo pedido en la base. Después probá el caso duro: mandá el mismo curl dos veces con la misma clave. Sigue siendo uno.
  3. Precio. Mandá un curl con un campo precio falso. El total cobrado tiene que ser el de la base, y el campo extra tiene que ser ignorado.
  4. Teclado y lector. Completá y enviá solo con teclado. Al fallar, el foco tiene que saltar al resumen, cada error tiene que ser un link a su campo, y NVDA o VoiceOver tienen que leer el resumen sin que navegues hasta él.
  5. Datos preservados. Llená los cuatro campos, provocá un error de cupón, y confirmá que email, nombre y cantidad siguen ahí.
📌 La prueba 1 es la que nadie hace y la que más dice. Si el checkout anda sin JavaScript, sabés que el servidor es la autoridad, que la validación real está del lado correcto, y que el día que un chunk falle vas a seguir vendiendo. Si no anda, tenés una app cuya facturación depende de que ningún archivo se pierda en el camino.

Checkpoint — ¿lo tenés claro?

Ponés useFormStatus en tu componente de checkout y pending nunca cambia. ¿Por qué, y cuáles son las dos salidas?

Porque useFormStatus lee el <form> ancestro, y el componente que llama al hook es el que renderiza el form — no está adentro de él, está afuera creándolo. React no tiene forma de asociarlos. Hay dos salidas y son distintas, no intercambiables. (a) Usar el tercer valor de useActionState, pending, que sí está disponible en el componente que crea el form: es lo correcto cuando el indicador vive en ese mismo nivel. (b) Extraer el botón a un componente hijo que llame al hook: es lo correcto cuando el botón es compartido por muchos formularios, porque el hijo no necesita recibir ninguna prop de estado y funciona en cualquier form del sistema. La opción (b) es la razón de existir del hook: si useActionState alcanzara siempre, useFormStatus no haría falta.

Tu Action valida con Zod, corre en el servidor y el esquema pasa. ¿Alcanza para procesar la compra?

No. Zod valida forma: que cantidad sea un entero entre 1 y 10, que el email tenga estructura de email. No sabe nada del mundo. Faltan tres capas. Autorización: ¿hay sesión?, ¿este usuario puede comprar esto? — y la identidad sale de la sesión, nunca de un campo del formulario. Reglas de negocio: ¿hay stock para esa cantidad?, ¿el cupón existe, no venció y no se agotó?, ¿el producto sigue publicado? Todo eso pasa el esquema y aun así es inválido. Integridad de valores: el precio se lee de la base por el id del producto; si lo tomás del FormData, cualquiera edita el input oculto y compra a un peso. Regla corta: el esquema decide si los datos tienen la forma correcta; el servidor decide si la operación es correcta.

Tu formulario muestra el error en pantalla, con borde rojo y texto claro. ¿Por qué puede seguir estando roto?

Porque "mostrar" es una operación visual y una parte de tus usuarios no está mirando. Faltan cuatro cosas. Anuncio: el mensaje tiene que estar en una región role="alert" / aria-live que exista en el DOM desde el primer render — si montás el contenedor junto con su contenido, varios lectores de pantalla no anuncian nada, y es el bug más común y más invisible. Vínculo: el campo necesita aria-invalid (que algo está mal) y aria-describedby apuntando al id del mensaje (qué está mal); con uno solo, el usuario oye "inválido" y adivina. Foco: tras un envío fallido el foco queda en el botón, al final; hay que moverlo al resumen de errores, con cada ítem como link a su campo. Color: el borde rojo no es información — el texto sí. Un formulario que una parte de tus usuarios no puede completar no cumple su función; no es un detalle de pulido.

Resumen ejecutivo

  • Una Action es una función async que React corre dentro de una transición. De ahí salen gratis el pending, el orden de las respuestas y la reversión de lo optimista. No hay magia: hay contabilidad que antes hacías vos con cinco useState.
  • useActionState(fn, inicial, permalink?) devuelve [estado, accion, pendiente], y fn recibe (estadoPrevio, formData) en ese orden. El estado previo no es decorativo: es lo que te deja acumular intentos y devolver lo tipeado para no perderlo.
  • React resetea el formulario no controlado cuando la acción termina, también cuando terminó con error. La cura es devolver valores en el estado y usarlos como defaultValue.
  • useFormStatus se importa de react-dom y lee el <form> ancestro. En el componente que renderiza el form devuelve pending: false para siempre. Existe para que un botón de design system sepa que su formulario está enviando sin recibir props.
  • useOptimistic proyecta sobre el estado real mientras dura la transición. El rollback no es una acción: es la ausencia de la proyección, y por eso no puede olvidarse. Usalo solo en operaciones baratas de deshacer — jamás en un pago.
  • Un <form action={serverFunction}> funciona sin JavaScript. No es caridad: es tolerancia a fallas, para el bundle que no cargó, el chunk que se perdió y el usuario que apretó antes de hidratar. permalink cubre esa ventana.
  • La validación de cliente es UX; la de servidor es la que cuenta. Y la de servidor no termina en el esquema: falta autorización, reglas de negocio y leer los valores sensibles —el precio— de tu base. Ver M04 de Ciberseguridad.
  • Una Server Function es un endpoint público: autenticar → validar → autorizar sobre el recurso → actuar. La identidad sale de la sesión, nunca de un argumento. Ver RS4.
  • Mutar es la mitad del trabajo: hay que invalidar. Etiquetá por dato (revalidateTag), no por pantalla — el contador del header vive en otro lado que la página. Se enlaza con RS5.
  • react-hook-form sigue ganando en formularios muy dinámicos: wizards, useFieldArray, validación cruzada por tecla, campos condicionales. Formik está en mantenimiento. Y el híbrido —librería para tipear, Action para enviar— es legítimo.
  • Accesibilidad, cinco cosas: <label> real y autoComplete, aria-invalid + aria-describedby, región role="alert" que exista vacía desde el primer render, foco al resumen tras fallar, y nunca solo color.
  • Deshabilitar el botón es UX; la clave de idempotencia es corrección. En cualquier mutación con consecuencias, la clave no es opcional.

🧠 Autoevaluación

1. Tu componente de checkout llama a useFormStatus() y renderiza el <form>. El pending nunca se pone en true. ¿Cuál es la causa?

useFormStatus lee el <form> ancestro más cercano. Un componente que renderiza el form está afuera de él, así que React no tiene con qué asociarlo y devuelve pending: false para siempre. Las dos salidas: usar el tercer valor de useActionState (correcto cuando el indicador vive en ese mismo componente), o extraer el botón a un hijo que llame al hook (correcto cuando el botón es compartido, porque así no necesita recibir ninguna prop de estado — que es exactamente la razón de existir del hook). El import es de react-dom, sí, pero un import mal no da false: da un error.

2. Tu Action valida con Zod en el servidor, el esquema pasa y procesás la compra leyendo fd.get("precio"). ¿Qué está mal?

Zod confirma que precio es un número, no que sea el precio. Cualquiera edita el input oculto o manda un curl y compra a un peso: el precio se lee de tu base por el id del producto, siempre. Y falta más de lo mismo: autorización (¿hay sesión?, ¿este usuario puede?, con la identidad sacada de la sesión y nunca de un campo) y reglas de negocio que el esquema no conoce (stock disponible, cupón vigente y no agotado, producto todavía publicado). Validar también en el cliente mejora la UX pero no agrega ninguna garantía: es código que corre en la máquina del atacante.

3. Un usuario llena tu formulario, el servidor devuelve un error de validación y todos los campos aparecen vacíos. ¿Por qué pasa y cómo se arregla?

React resetea los campos no controlados cuando la acción termina — también cuando terminó devolviendo un error, que es justo cuando no querés. La cura idiomática son dos líneas: la Action devuelve valores: Object.fromEntries(fd) junto con los errores, y cada input lee defaultValue={estado.valores?.campo}. El FormData no se "consume" al leerlo. Y volver a componentes controlados es tirar todo el modelo por la borda para arreglar algo que ya tiene solución; si querés control fino del reseteo existe requestFormReset de react-dom.

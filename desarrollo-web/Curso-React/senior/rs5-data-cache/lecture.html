RS5 — Data fetching y caché a escala

RS5.0 Por qué este módulo

Hay una frase que separa a quien pelea con los datos de quien los tiene bajo control: el estado de servidor no es estado de tu aplicación. Es una copia de algo que vive en otro lado, que otro proceso puede modificar mientras vos mirás la pantalla, y sobre lo que no tenés autoridad.

Casi todo el mundo lo trata igual que a un useState. Y ahí empieza todo: el usuario edita un perfil, vuelve a la lista y ve el nombre viejo. Dos pestañas muestran saldos distintos. Un dashboard tarda cuatro segundos porque hizo seis pedidos en fila cuando podía hacerlos juntos. Un botón de "me gusta" que se siente lento. Nada de eso es un bug de React: son consecuencias de haber modelado datos remotos como si fueran locales.

💡 La tesis del módulo. El estado de servidor tiene tres propiedades que el estado de cliente no tiene: (1) no sos el dueño —alguien más lo puede cambiar sin avisarte—, (2) tu copia empieza a envejecer en el instante en que llega, y (3) muchas partes de la UI quieren el mismo dato al mismo tiempo. Una librería de queries no es "fetch con azúcar": es una caché con identidad, deduplicación y política de frescura. Si no la usás, vas a escribir una peor.

Este módulo no discute estilos de API —REST contra GraphQL contra tRPC, quién orquesta qué— porque esa conversación es sobre el contrato y vive en otro lado. Acá el tema es lo que pasa después de que la respuesta entra al navegador: dónde se guarda, cuánto vale, quién la mira, cuándo se vuelve a pedir y qué ve el usuario mientras tanto.

Vamos a usar TanStack Query v5 como referencia concreta, con React 19.2. Pero el objetivo no es que aprendas una API: es que entiendas el mecanismo, porque el mecanismo es el mismo en SWR, en RTK Query, en Apollo y en la caché que termines escribiendo vos si trabajás en una app con restricciones raras.

Advertencia de expectativas. Agregar una librería de queries no arregla una arquitectura de datos mala. Si tus claves de caché están mal diseñadas vas a invalidar de más o de menos; si copiás el resultado a un useState volvés al problema original con más pasos; y si ponés staleTime: 0 en todo, cada foco de ventana dispara una tormenta de pedidos. La librería te da las herramientas — las decisiones siguen siendo tuyas.

📌 La regla operativa. Si el dato se obtiene con una petición de red, no lo pongas en un store de cliente. Ni en Redux, ni en Zustand, ni en un contexto, ni en un useState. En el momento en que lo copiás a estado propio creás una segunda fuente de verdad que nadie sincroniza, y ese es exactamente el bug que estás tratando de evitar.

El error más frecuente de todos —y el más silencioso— es copiar el resultado a estado local para poder editarlo:

// ❌ El anti-patrón que parece razonable
function PerfilEditable({ id }: { id: string }) {
  const { data } = useQuery({ queryKey: ["usuario", id], queryFn: () => getUsuario(id) });
  const [nombre, setNombre] = useState(data?.nombre ?? "");
  // A partir de acá hay DOS verdades: la caché y `nombre`.
  // Si la query refetchea en foco, `nombre` no se entera. Si el usuario
  // editó, un refetch pisaría su trabajo. No hay respuesta buena:
  // el problema es la copia, no la sincronización.
}
// ✅ El dato remoto es el valor inicial de un formulario, no su estado
function PerfilEditable({ id }: { id: string }) {
  const { data, isPending } = useQuery({
    queryKey: ["usuario", id],
    queryFn: () => getUsuario(id),
    staleTime: Infinity, // mientras se edita, no quiero que cambie bajo los pies
  });

  if (isPending) return <Skeleton />;

  // `key` remonta el formulario si cambia el usuario: el estado local
  // arranca limpio y la caché nunca compite con lo que el usuario escribe.
  return <FormularioPerfil key={data.id} inicial={data} />;
}
La analogía útil. El estado de servidor es una fotocopia del original que está en otra oficina. Podés leerla, podés trabajar con ella, pero no podés tacharla y decir que el original cambió. Para cambiar el original mandás un pedido (una mutación) y después pedís una fotocopia nueva. Todo el diseño de una caché de queries sale de tomarse en serio esa metáfora.

RS5.2 Por qué useEffect + fetch es un anti-patrón

Este es el código que todos escribimos alguna vez. Tiene ocho problemas, y no es una exageración retórica: son ocho, contables.

// ❌ El clásico
function Usuario({ id }: { id: string }) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    setLoading(true);
    fetch(`/api/usuarios/${id}`)
      .then((r) => r.json())
      .then(setData)
      .catch(setError)
      .finally(() => setLoading(false));

  if (loading) return <Spinner />;
  if (error) return <Error />;

La race condition, reproducible

Esta no es teórica y no es rara. Es la que hace que un buscador muestre resultados de una consulta anterior. Reproducila así:

// Endpoint de prueba: cuanto más corta la consulta, más tarda.
// (Un backend real hace exactamente esto: "a" busca en todo el índice.)
async function buscar(q: string) {
  const demora = q.length === 1 ? 1500 : 100;
  await new Promise((r) => setTimeout(r, demora));
  return { q, resultados: [`resultado para "${q}"`] };
}

function Buscador() {
  const [q, setQ] = useState("");
  const [data, setData] = useState(null);

  useEffect(() => {
    if (!q) return;
    buscar(q).then(setData); // ❌ sin protección
  }, [q]);

  return (
    <>
      <input value={q} onChange={(e) => setQ(e.target.value)} />
      <pre>{JSON.stringify(data)}</pre>
    </>
  );
}

Escribí "a" y enseguida "ab". Lo que ocurre, en orden real:

t=0ms     tecleás "a"    → arranca buscar("a"),  volverá en 1500ms
t=120ms   tecleás "ab"   → arranca buscar("ab"), volverá en  220ms
t=220ms   llega "ab"     → setData({q:"ab"})   ✅ pantalla correcta
t=1500ms  llega "a"      → setData({q:"a"})    ❌ pisa lo nuevo con lo viejo

Estado final: el input dice "ab", la pantalla muestra resultados de "a".
Por qué esto es peor que un bug visual. No hay error en consola, no hay excepción, no hay nada en el monitoreo. En desarrollo, con localhost a 3 ms, es invisible. Aparece en producción, en un celular con red mala, de forma intermitente, y el reporte que te llega dice "a veces muestra cualquier cosa". Es la clase de bug que se cierra como "no reproducible" tres veces antes de que alguien entienda qué pasa.

Los dos arreglos, y por qué hacen falta los dos

// Arreglo 1 — la bandera de ignorar. Corrige la UI.
useEffect(() => {
  if (!q) return;
  let cancelado = false;

  buscar(q).then((r) => {
    if (!cancelado) setData(r); // la respuesta vieja llega y se descarta
  });

  return () => { cancelado = true; }; // cleanup al cambiar `q` o desmontar
}, [q]);

Esto arregla lo que el usuario ve, pero la petición vieja igual viajó, igual consumió una de las seis conexiones que el navegador te da por dominio, e igual le costó CPU al backend. Para eso está la segunda mitad:

// Arreglo 2 — AbortController. Corrige la red.
useEffect(() => {
  if (!q) return;
  const ctrl = new AbortController();

  fetch(`/api/buscar?q=${encodeURIComponent(q)}`, { signal: ctrl.signal })
    .then((r) => r.json())
    .then(setData)
    .catch((e) => {
      if (e.name === "AbortError") return; // ⚠️ obligatorio: abortar RECHAZA
      setError(e);
    });

  return () => ctrl.abort();
}, [q]);
El error que sigue al arreglo. Al abortar, la promesa de fetch se rechaza con un AbortError. Si tu .catch no lo filtra, cada tecla que el usuario escribe pinta un cartel de error rojo por un instante. Y si además tenés un .finally(() => setLoading(false)), el aborto apaga el spinner de la petición que sí está en curso. Cancelar bien es más sutil de lo que parece.

El doble fetch en StrictMode no es el bug: es el detector

En desarrollo con <StrictMode>, React monta el componente, lo desmonta y lo vuelve a montar. Los efectos corren dos veces. Todo el mundo lo vive como una molestia y lo primero que busca en Google es cómo apagarlo.

📌 No lo apagues. Ese doble montaje es una prueba de resistencia. Está simulando algo que React ya hace en producción: desmontar y remontar preservando estado —al volver atrás en la navegación, al restaurar una vista suspendida—. Si tu efecto se rompe cuando corre dos veces, tu efecto está mal escrito. El fetch duplicado es el síntoma visible de que te falta el cleanup, no una imposición de la herramienta.

Y acá está el punto que cierra la sección: con una caché de queries, el doble montaje no produce dos peticiones. No porque la librería detecte StrictMode, sino porque la deduplicación es una propiedad natural del diseño: dos observadores de la misma clave con una petición en vuelo comparten la misma promesa. El problema desaparece como efecto secundario de tener el mecanismo correcto.

RS5.3 Cómo funciona una caché de queries por dentro

Para no usar la librería como una caja negra, construyámosla. La versión mínima entra en unas setenta líneas y contiene las cuatro ideas que importan: identidad, almacén, deduplicación y observadores.

1. La queryKey es identidad, no una etiqueta

La clave no es un nombre bonito: es el hash con el que se indexa la entrada. Dos claves que hashean igual son el mismo dato para la caché, aunque tu intención fuera otra.

// Aproximación a lo que hace TanStack Query (packages/query-core/src/utils.ts)
function hashKey(key: unknown): string {
  return JSON.stringify(key, (_, val) =>
    esObjetoPlano(val)
      ? Object.keys(val)                 // ⬅ las claves de objeto se ORDENAN
          .sort()                        //    para que {a,b} y {b,a} hasheen igual
          .reduce((acc, k) => { acc[k] = val[k]; return acc; }, {} as any)
      : val
  );
}

hashKey(["todos", { estado: "abierto", pagina: 1 }]);
// '["todos",{"estado":"abierto","pagina":1}]'
hashKey(["todos", { pagina: 1, estado: "abierto" }]);
// '["todos",{"estado":"abierto","pagina":1}]'   ← idéntico, y está bien

El orden de las claves de un objeto no importa. El orden de los elementos del array sí, y el tipo también:

hashKey(["todo", 1]);    // '["todo",1]'
hashKey(["todo", "1"]);  // '["todo","1"]'   ← OTRA entrada de caché

// El bug clásico: el id viene de useParams() como string en una ruta
// y como number del payload de una mutación. Dos entradas para la
// misma fila de la base de datos, que se desincronizan sin ruido.
Normalizá el tipo en la fábrica de claves, no en cada llamada. Si el id es un string en la URL y un número en la base, elegí uno y convertí siempre en el mismo lugar. Una fábrica de claves centralizada (RS5.6) hace esto imposible de olvidar.

2, 3 y 4: el almacén, la deduplicación y los observadores

type Estado<T> = {
  data?: T;
  error?: unknown;
  status: "pending" | "success" | "error";
  fetching: boolean;
  actualizadoEn: number;
};

class MiniQueryCache {
  private entradas = new Map<string, {
    estado: Estado<any>;
    promesa?: Promise<any>;              // ⬅ deduplicación
    observadores: Set<() => void>;       // ⬅ suscriptores
    temporizadorGc?: ReturnType<typeof setTimeout>;
  }>();

  private obtener(hash: string) {
    let e = this.entradas.get(hash);
    if (!e) {
      e = {
        estado: { status: "pending", fetching: false, actualizadoEn: 0 },
        observadores: new Set(),
      };
      this.entradas.set(hash, e);
    }
    return e;
  }

  // El corazón: si ya hay una petición en vuelo, devolvemos ESA promesa.
  // Diez componentes montándose a la vez producen UNA petición.
  fetch<T>(hash: string, fn: () => Promise<T>, staleTime: number): Promise<T> {
    const e = this.obtener(hash);

    if (e.promesa) return e.promesa;                          // dedupe
    const fresco = Date.now() - e.estado.actualizadoEn < staleTime;
    if (e.estado.status === "success" && fresco) {
      return Promise.resolve(e.estado.data);                  // caché fresca
    }

    this.setEstado(hash, { fetching: true });
    e.promesa = fn()
      .then((data) => {
        this.setEstado(hash, {
          data, status: "success", fetching: false, actualizadoEn: Date.now(),
        });
        return data;
      })
      .catch((error) => {
        this.setEstado(hash, { error, status: "error", fetching: false });
        throw error;
      })
      .finally(() => { e.promesa = undefined; });

    return e.promesa;
  }

  private setEstado(hash: string, parcial: Partial<Estado<any>>) {
    const e = this.obtener(hash);
    e.estado = { ...e.estado, ...parcial };   // objeto NUEVO: useSyncExternalStore lo detecta
    e.observadores.forEach((notificar) => notificar());
  }

  leer(hash: string) { return this.obtener(hash).estado; }

  suscribir(hash: string, notificar: () => void, gcTime: number) {
    const e = this.obtener(hash);
    clearTimeout(e.temporizadorGc);          // volvió a haber interesados
    e.observadores.add(notificar);

    return () => {
      e.observadores.delete(notificar);
      if (e.observadores.size === 0) {       // ⬅ nadie mira: arranca el reloj de GC
        e.temporizadorGc = setTimeout(() => this.entradas.delete(hash), gcTime);
      }
    };
  }
}

Y el hook que lo consume, con useSyncExternalStore —la API que React expone justamente para leer de un store externo sin romper el renderizado concurrente que viste en RS2:

const cache = new MiniQueryCache();

function useMiniQuery<T>(key: unknown[], fn: () => Promise<T>, opts = {
  staleTime: 0, gcTime: 5 * 60_000,
}) {
  const hash = hashKey(key);

  const estado = useSyncExternalStore(
    (notificar) => cache.suscribir(hash, notificar, opts.gcTime),
    () => cache.leer(hash),          // snapshot en cliente
    () => cache.leer(hash),          // snapshot en servidor
  );

  useEffect(() => {
    cache.fetch(hash, fn, opts.staleTime).catch(() => {});
  }, [hash]);                        // ⬅ el hash, NO el array (que es nuevo en cada render)

  return estado;
}

El error de manual. "Quiero que los datos se refresquen cada 5 minutos" → alguien pone gcTime: 5 * 60_000. No hace nada de eso. gcTime no fuerza ningún refetch: solo decide cuándo se tira la entrada que nadie está mirando. Mientras el componente esté montado, gcTime es completamente irrelevante. Lo que buscabas era staleTime, o refetchInterval si querés que pida sola sin que nadie la toque.
gcTime más chico que staleTime es casi siempre un error. Estás diciendo "considerá esto fresco por diez minutos, pero borralo de memoria a los treinta segundos". Resultado: cada vuelta a la ruta arranca de cero con spinner y una petición, exactamente lo que el staleTime largo intentaba evitar. Como piso, gcTime >= staleTime.

Los cuatro disparadores de refetch, y qué los frena

useQuery({
  queryKey: ["pedidos"],
  queryFn: getPedidos,
  staleTime: 30_000,

  refetchOnMount: true,        // al montar un observador nuevo
  refetchOnWindowFocus: true,  // al volver a la pestaña
  refetchOnReconnect: true,    // al recuperar conexión
  refetchInterval: false,      // polling (este NO mira staleTime)
});
📌 Los tres primeros son condicionales: solo disparan si la query está stale. Por eso staleTime es la única perilla que necesitás tocar el 90% de las veces: sube el staleTime y los tres se calman juntos. Apagar refetchOnWindowFocus porque "pide demasiado" es tratar el síntoma; el diagnóstico real es que dejaste el staleTime en 0. La excepción es refetchInterval, que ignora la frescura y pide igual — es polling, no revalidación.

RS5.6 Invalidación: por clave, por prefijo, o a mano

Invalidar es decir "esto que tengo ya no sirve". El diseño de las claves es lo que hace que invalidar sea una línea o una pesadilla.

El prefijo es la característica que justifica los arrays

Las claves son arrays porque se comparan por prefijo, de izquierda a derecha. Eso te da jerarquía gratis:

// Entradas existentes en la caché:
["pedidos"]
["pedidos", "lista", { estado: "abierto" }]
["pedidos", "lista", { estado: "cerrado" }]
["pedidos", "detalle", 42]
["usuarios", "detalle", 7]

// Invalidar TODO lo relacionado con pedidos:

//   ✅ alcanza a las cuatro primeras · ❌ no toca usuarios

// Solo las listas, sin tocar los detalles ya cargados:
queryClient.invalidateQueries({ queryKey: ["pedidos", "lista"] });

// Solo esa entrada exacta:
queryClient.invalidateQueries({ queryKey: ["pedidos", "detalle", 42], exact: true });

// Lo que el prefijo no puede expresar → predicado:
queryClient.invalidateQueries({
  predicate: (q) => q.queryKey[0] === "pedidos" && (q.queryKey[2] as any)?.estado === "abierto",
});
📌 Ordená las claves de lo general a lo específico, como una ruta de archivos: [entidad, tipoDeVista, parámetros]. Si ponés el id primero ([42, "pedido"]) perdés la invalidación por prefijo para siempre y te quedan predicados por todos lados. Es una decisión de cinco segundos que se paga o se cobra durante toda la vida del proyecto.

Escribir arrays a mano en cada archivo garantiza que algún día alguien ponga ["pedido"] en singular y pase dos semanas buscando por qué la lista no se actualiza. La fábrica lo vuelve imposible:

RS5.7 Optimistic updates y el rollback correcto

Un "me gusta" que tarda 300 ms en aparecer se siente roto. La actualización optimista pinta el resultado antes de que el servidor conteste y lo revierte si falla. El patrón tiene cuatro pasos y ninguno es opcional:

const { mutate } = useMutation({
  mutationFn: toggleFavorito,

  // 1️⃣ Antes de salir a la red
  onMutate: async (postId: string) => {
    // (a) CANCELAR peticiones en vuelo de esa clave.
    //     Si no, un GET que salió hace 200ms puede llegar DESPUÉS de tu
    //     escritura optimista y pisarla con el valor viejo del servidor.
    await queryClient.cancelQueries({ queryKey: claves.detalle(postId) });

    // (b) SNAPSHOT: la única forma de poder volver atrás.
    const previo = queryClient.getQueryData<Post>(claves.detalle(postId));

    // (c) Escritura optimista.
    queryClient.setQueryData<Post>(claves.detalle(postId), (p) =>
      p ? { ...p, favorito: !p.favorito, favs: p.favs + (p.favorito ? -1 : 1) } : p
    );

    // (d) Lo que devolvés acá llega como `context` a onError y onSettled.
    return { previo };
  },

  // 2️⃣ Falló: restaurar exactamente lo que había
  onError: (_err, postId, context) => {
    if (context?.previo) {
      queryClient.setQueryData(claves.detalle(postId), context.previo);
    }
  },

  // 3️⃣ Pase lo que pase: que el servidor tenga la última palabra
  onSettled: (_data, _err, postId) => {
    return queryClient.invalidateQueries({ queryKey: claves.detalle(postId) });
  },
});
Los tres errores que rompen el rollback. (1) No cancelar: una respuesta en vuelo aterriza sobre tu escritura optimista y el corazoncito vuelve a apagarse solo, medio segundo después. (2) No snapshotear: en el onError se "revierte" recalculando el toggle al revés, lo cual es correcto solo si nada más tocó ese dato mientras tanto — y con dos clics rápidos deja de serlo. Guardá el objeto previo, no la operación inversa. (3) Invalidar solo en onSuccess: si falló y no invalidás, la caché queda con el valor restaurado a mano y nunca se confronta con el servidor. Por eso el paso 3 va en onSettled.

La variante que evita el rollback entero

Si la mutación afecta a una sola pantalla, hay una alternativa mucho más barata: no tocar la caché y renderizar el estado optimista desde las variables de la mutación. Cuando la mutación termina, el estado desaparece solo y la caché ya trae la verdad.

function AgregarTarea() {
  const { mutate, variables, isPending } = useMutation({
    mutationFn: crearTarea,
    onSettled: () => queryClient.invalidateQueries({ queryKey: claves.listas() }),
  });
  const { data: tareas } = useQuery({ queryKey: claves.listas(), queryFn: getTareas });

  return (
    <ul>
      {tareas?.map((t) => <li key={t.id}>{t.titulo}</li>)}
      {/* la fila fantasma vive solo mientras dura la mutación */}
      {isPending && <li style={{ opacity: 0.5 }}>{variables.titulo}</li>}
    </ul>
  );
}
Elegí por alcance. ¿El cambio tiene que verse en varias pantallas a la vez (el corazón en la lista, en el detalle y en el contador del header)? Escritura optimista en la caché. ¿Se ve en un solo lugar? Variables de la mutación: cero snapshots, cero rollback, cero posibilidad de dejar la caché en un estado inconsistente.
Cuándo NO ser optimista. Cuando revertir le miente al usuario sobre algo que importa: transferencias de dinero, confirmar un pedido, borrar definitivamente, publicar. Mostrar "listo" y después "en realidad no" es peor que 400 ms de spinner. La actualización optimista es para acciones reversibles y de bajo impacto, donde la probabilidad de fallo es baja y el costo de equivocarse es cosmético.

RS5.8 Paginación e infinite scroll

Por qué el offset se rompe (y no es un caso raro)

?page=2&per_page=20 asume que la lista no cambia entre pedidos. En cualquier lista ordenada por fecha con inserciones —un feed, una bandeja, un log— esa suposición es falsa cada pocos segundos:

Lista ordenada por fecha descendente. El usuario pide la página 1 (LIMIT 3 OFFSET 0):

  [ E, D, C ]   ← ve estos tres
    resto: B, A

Mientras lee, se inserta F arriba. Ahora pide la página 2 (LIMIT 3 OFFSET 3):

  servidor:  F, E, D, C, B, A
  OFFSET 3 → [ C, B, A ]
                ^
                C YA lo había visto → aparece DUPLICADO

Y si en vez de insertarse se hubiera borrado un elemento de arriba,
el corrimiento va para el otro lado y un elemento se SALTEA sin que
nadie lo note nunca — el usuario simplemente no lo ve.

Sin keepPreviousData, cada cambio de página devuelve la query a pending: la tabla desaparece, el layout colapsa, la página salta y vuelve. Con él, la página anterior queda visible hasta que llega la nueva. Es una línea y cambia por completo la sensación de la tabla.

El deshabilitado que falta. Si no deshabilitás "Siguiente" mientras isPlaceholderData es cierto, dos clics rápidos saltan de la 1 a la 3 mostrando datos de la 1. La caché está perfecta; la UI mintió porque el botón permitía adelantarse a los datos.

Scroll infinito con cursores

Una infinite query es UNA sola entrada de caché, no una por página. Cuando se invalida o refetchea, la librería vuelve a pedir todas las páginas cargadas, en secuencia, para mantener la coherencia de los cursores. Si el usuario scrolleó 40 páginas, un refocus de ventana dispara 40 peticiones encadenadas. Por eso existe maxPages: acota la ventana en memoria y descarta las de los extremos. Sin él, el scroll infinito es una bomba de tiempo que solo explota con usuarios que scrollean mucho — o sea, los que más te importan.
undefined y null no son lo mismo acá. getNextPageParam tiene que devolver undefined para que hasNextPage pase a false. Si tu API devuelve null cuando se acabaron los resultados y lo pasás tal cual, hasNextPage sigue en true y el observador de scroll pide la misma página para siempre. Es un ?? undefined de diferencia.

En RS4 viste que un Server Component puede leer datos directamente, sin ningún hook. La pregunta natural es: si el servidor ya trae los datos, ¿para qué quiero una caché en el cliente?

El patrón que combina las dos: prefetch en el servidor, hidratar en el cliente

// app/pedidos/page.tsx — Server Component
import { dehydrate, HydrationBoundary, QueryClient } from "@tanstack/react-query";

export default async function Page() {
  const qc = new QueryClient();

  // Se pide en el servidor: sin cascada, sin spinner, sin salto de red extra.
  await qc.prefetchQuery({
    queryKey: ["pedidos", "lista"],
    queryFn: () => db.pedidos.findMany(),   // acceso directo, no pasa por HTTP
  });

  return (
    <HydrationBoundary state={dehydrate(qc)}>
      <ListaPedidos />   {/* Client Component */}
    </HydrationBoundary>
  );
}
"use client";

export function ListaPedidos() {
  // Misma clave → la caché ya viene poblada desde el HTML.
  // No hay petición al montar: el dato está antes del primer píxel.
  const { data } = useQuery({
    queryKey: ["pedidos", "lista"],
    queryFn: getPedidos,        // se usará solo en refetches posteriores
  });
  return <Tabla filas={data} />;
}
El bug que arruina este patrón: staleTime: 0. Con el default, el dato deshidratado llega marcado como viejo y refetchOnMount dispara una petición inmediata al hidratar. Resultado: hiciste todo el trabajo de prefetch en el servidor y el navegador pide lo mismo de nuevo, medio segundo después. Se ve como una petición fantasma en Network que nadie explica. Poné un staleTime de al menos algunos segundos en los defaults del QueryClient del servidor y del cliente — es el arreglo de una línea más rentable de toda la integración.
Y en el servidor, un QueryClient por request. Si creás el QueryClient como módulo de nivel superior, todos los usuarios comparten la misma caché en el proceso de Node: el pedido de uno puede terminar renderizado en el HTML de otro. Es una fuga de datos entre usuarios, no un problema de performance. En el servidor se instancia adentro del componente o con cache() de React 19; en el cliente, una sola vez con useState(() => new QueryClient()).

Cuándo ya no necesitás la librería

Con RSC estable, hay una franja real de aplicaciones donde agregarla es sumar peso y conceptos sin ganar nada:

  • Los datos se leen en el servidor y se muestran; el cliente no los pide nunca.
  • Las escrituras van por Server Actions y la revalidación la hace revalidatePath / revalidateTag.
  • No hay polling, ni scroll infinito con estado, ni datos compartidos entre componentes cliente lejanos.
  • Lo optimista, cuando hace falta, se resuelve con useOptimistic dentro del formulario que lo necesita.
📌 El síntoma de que sí la necesitás: aparece el primer router.refresh() puesto para "que se vea el cambio", el primer useEffect con fetch en un Client Component, o el primer dato que dos componentes cliente distintos piden por separado. Ahí ya estás escribiendo una caché de queries — peor, y sin devtools.

RS5.11 Errores, reintentos y el error boundary de datos

Reintentar lo que tiene sentido reintentar

// Default de la librería: 3 reintentos, backoff exponencial hasta 30s.
// Razonable para GETs; peligroso si lo dejás igual para todo.
{
  retry: (fallos, error: any) => {
    if (error?.status >= 400 && error?.status < 500) return false;
    // 4xx: el pedido está mal. Reintentar 30 veces no lo va a arreglar.
    // Excepción típica: 408 y 429, que sí se reintentan (con Retry-After).
    return fallos < 3;
  },
  retryDelay: (intento) =>
    Math.min(1000 * 2 ** intento, 30_000) + Math.random() * 300,
    //                                      ⬆ jitter, no es opcional
}
📌 Por qué el jitter importa. Si el backend se cae 30 segundos, mil clientes fallan casi al mismo tiempo. Sin jitter, los mil reintentan a los 1000 ms, después a los 2000, después a los 4000 — sincronizados, en oleadas. El servicio que estaba por recuperarse recibe mil peticiones simultáneas y se vuelve a caer. Es el thundering herd, y se previene con una línea de ruido aleatorio.
Las mutaciones NO se reintentan por default, y está bien. Reintentar un POST puede crear dos pedidos, cobrar dos veces o mandar dos mails. Si necesitás reintentar una escritura, el requisito previo es que sea idempotente: el cliente genera una clave única por intento, el servidor la guarda y, si ve la misma clave dos veces, devuelve el resultado original en vez de ejecutar de nuevo. Sin eso del lado del servidor, retry en una mutación es una decisión de negocio disfrazada de configuración.

El error boundary de datos

Manejar isError en cada componente termina en veinte copias del mismo bloque. Con throwOnError, el error viaja al boundary más cercano y se maneja una vez:

Checkpoint — ¿lo tenés claro?

Tu lista de pedidos se refetchea cada vez que el usuario vuelve a la pestaña, y el equipo pide "apagar eso". ¿Qué hacés?

Apagar refetchOnWindowFocus es tratar el síntoma. El refetch en foco solo se dispara si la query está stale, así que el diagnóstico real es que el staleTime está en su default de 0: la data nace vieja en el instante en que llega. La pregunta correcta no es técnica sino de producto: ¿cuántos segundos de retraso tolera quien mira esta lista? Si son treinta, staleTime: 30_000 elimina el 95% de los refetch y conserva el comportamiento valioso —volvés después de almorzar y ves datos frescos—. Apagar el foco te deja con datos de hace dos horas y sin ninguna señal de que están viejos, que es peor que el problema original. La única razón legítima para apagarlo es que el endpoint sea carísimo y el dato casi inmutable, y en ese caso staleTime: Infinity lo expresa mejor: dice "esto no envejece", en vez de "no mires si envejeció".

Después de una mutación exitosa, ¿cuándo setQueryData y cuándo invalidateQueries?

setQueryData cuando la respuesta del servidor es la entidad completa y final, y vos podés reproducir exactamente lo que la caché debería tener: ahorrás un round-trip y la UI se actualiza en el mismo frame. invalidateQueries cuando el efecto de la mutación excede lo que ves: la lista puede reordenarse, hay contadores y agregados, la fila puede entrar o salir de un filtro activo, el servidor calcula campos derivados (totales, estados, permisos) que tu escritura a mano no puede inventar. La combinación habitual es hacer las dos cosas: setQueryData sobre el detalle —que sí conocés— e invalidateQueries sobre las listas —que no—. Y devolvé la promesa de invalidateQueries desde onSuccess: así isPending de la mutación sigue en true hasta que el refetch termine, y el botón no se re-habilita mostrando todavía datos viejos. El criterio de fondo: escribí a mano solo lo que podés reconstruir con certeza; para todo lo demás, que hable el servidor.

Tu dashboard hace seis peticiones en cascada. ¿Alcanza con envolver todo en un <Suspense>?

No, y probablemente lo empeore. Suspense administra qué se muestra mientras se espera; no cambia cuándo arrancan las peticiones. Peor: si los seis widgets usan useSuspenseQuery como hermanos bajo una misma frontera, el primero suspende y React nunca llega a renderizar a los otros cinco, así que sus queries ni siquiera se registran — convertís seis peticiones paralelas en seis secuenciales. Y con una sola frontera, el usuario no ve nada hasta que el más lento termine: el tiempo hasta el primer contenido empeora aunque el total sea igual. Los arreglos van en este orden: (1) eliminar la dependencia falsa que causa la cascada —muchas veces el parámetro que "hacía falta" no hacía falta—, (2) disparar en paralelo con useQueries / useSuspenseQueries o prefetch en el padre, y (3) recién ahí usar Suspense, con una frontera por widget, para que cada uno aparezca cuando esté listo. Suspense es la presentación; el paralelismo es la arquitectura.

Resumen ejecutivo

  • El estado de servidor no es estado de la app: es una copia que envejece sola y que no controlás. Copiarlo a useState o a un store crea una segunda fuente de verdad que nadie sincroniza.
  • useEffect + fetch falla en ocho puntos. El más grave es la race condition: invisible en desarrollo, intermitente en producción, sin ningún error en consola. Se arregla con bandera de cancelación (la UI) y AbortController (la red).
  • El doble fetch de StrictMode no es el bug: es el detector de que falta el cleanup. Con una caché desaparece solo, por deduplicación.
  • Una caché de queries son cuatro piezas: hash de la clave, Map, promesa compartida y set de observadores. Todo el comportamiento "mágico" sale de ahí.
  • staleTime es frescura (¿pido de nuevo?); gcTime es memoria (¿lo borro?). El reloj de gcTime ni siquiera arranca mientras haya un componente montado. gcTime < staleTime es casi siempre un error.
  • isLoading === isPending && isFetching. Usá isPending para decidir el esqueleto e isFetching solo para un indicador sutil: confundirlos es la pantalla que parpadea sola.
  • Las claves se comparan por prefijo: ordenalas de lo general a lo específico y centralizalas en una fábrica. Ese diseño es lo que hace que invalidar sea una línea.
  • Lo optimista necesita cancelar, snapshotear, escribir y reconciliar en onSettled. Y no va en operaciones irreversibles: mostrar "listo" y desdecirse es peor que esperar.
  • Offset se rompe con datos que cambian —duplica y saltea—. Para feeds, cursores. Y acotá el scroll infinito con maxPages, porque una infinite query refetchea todas sus páginas.
  • Con RSC, hacé prefetchQuery en el servidor e hidratá — pero con staleTime > 0, o el cliente vuelve a pedir todo al montar. Y un QueryClient por request: compartirlo filtra datos entre usuarios.
  • Si leés en el servidor, escribís con Server Actions y no hay polling ni datos compartidos entre componentes cliente, puede que no necesites la librería. El primer router.refresh() puesto "para que se vea" es la señal de que sí.

🧠 Autoevaluación

1. Querés que una lista se refresque cada 5 minutos. ¿Qué configurás?

gcTime no fuerza ningún refetch: solo decide cuándo se borra de memoria una entrada que ya no mira nadie, y su reloj ni siquiera arranca mientras haya un componente montado. Lo que buscás es staleTime: pasados los 5 minutos la query queda stale y el próximo disparador —montaje, foco de ventana, reconexión— la refresca. Si además querés que se refresque sin que nadie interactúe, eso es refetchInterval, que es la única opción que ignora la frescura.

2. Tu pantalla se llena de esqueletos cada vez que el usuario vuelve a la pestaña, aunque los datos ya estaban cargados. ¿Cuál es la causa?

isFetching es cierto durante cualquier petición, incluidos los refetch de fondo en los que ya tenés datos perfectamente mostrables. isPending significa "no tengo datos", que es la única condición que justifica un esqueleto de pantalla completa. La regla exacta: isLoading === isPending && isFetching — o sea, primera carga. Para el refetch de fondo va un indicador sutil que no cambie el layout; borrar la pantalla comunica un problema que no existe.

3. En una actualización optimista, ¿por qué hay que llamar a cancelQueries en onMutate?

Es una carrera contra una petición que ya salió. Si un GET de esa clave estaba viajando cuando el usuario hizo clic, va a llegar unos milisegundos después de tu escritura optimista y va a sobrescribir la caché con el estado anterior del servidor — que todavía no conoce la mutación. El usuario ve el corazón encenderse y apagarse solo. cancelQueries descarta esas respuestas en vuelo para esa clave. Junto con el snapshot para el rollback y el invalidateQueries en onSettled, son los tres pasos que hacen que lo optimista sea confiable en vez de una fuente nueva de inconsistencias.

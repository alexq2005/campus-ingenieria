RS1 — El reconciliador por dentro: fiber, render y commit

RS1.0 Por qué este módulo

"React re-renderiza de más" es la frase que más se repite en las revisiones de código de cualquier equipo de React, y casi siempre está mal planteada. Un re-render no es un bug ni es caro por definición: llamar a una función que devuelve objetos es de las cosas más baratas que hace un navegador. Podés renderizar un componente cien veces por segundo y no pasar de un milisegundo.

El problema es que "re-render" es un síntoma que la gente usa como si fuera un diagnóstico. Cuando alguien dice "esto re-renderiza de más" en realidad está describiendo alguna de estas cosas, que son distintas entre sí y se arreglan de maneras distintas: el navegador tarda 200 ms en responder a una tecla; un input pierde el foco solo; el texto que escribiste aparece en la fila equivocada; una animación se corta; un efecto se dispara dos veces. Todas esas son consecuencias observables de cómo funciona el reconciliador, y ninguna se resuelve espolvoreando React.memo hasta que el síntoma desaparece.

💡 La tesis del módulo. Casi todo lo raro que hace React se explica con tres hechos: (1) cuando escribís JSX no tocás el DOM, construís una descripción; (2) React compara esa descripción contra una estructura de datos propia —el árbol de fibers— que puede pausar, descartar y rehacer; (3) el DOM se toca en un único momento sincrónico al final, el commit. Render ≠ commit ≠ pintado del navegador. Entendé esos tres momentos y el resto se deduce.

Este módulo no es una lista de trucos de optimización — eso es RS7. Es el mapa mental que te permite mirar un perfil de rendimiento y decir qué está pasando y por qué, en vez de probar cosas hasta que el número baje.

Nada de lo que sigue es API pública. Los nombres de los campos internos cambian entre versiones de React sin aviso ni changelog. Estamos parados en React 19.2 (línea de parches 19.2.x). Lo que no cambia —hace ya casi una década— es el modelo: dos árboles, dos fases, un heurístico de identidad. Aprendé el modelo, no los nombres de las variables.

RS1.1 De VDOM a Fiber: el problema que había que resolver

Hasta React 15, el reconciliador era recursivo. Cuando llegaba una actualización, React llamaba a tu componente raíz, que devolvía elementos, que hacían que React llamara a los hijos, y así hasta abajo. Todo eso pasaba en una sola llamada de función, dentro del stack del motor de JavaScript.

Esa arquitectura tiene una propiedad fatal: una vez que empezaste, no podés parar. El stack de JavaScript no se pausa. Si el árbol tenía cinco mil nodos y recorrerlo tardaba 300 ms, el hilo principal quedaba ocupado 300 ms: sin responder clicks, sin procesar teclas, sin pintar. A 60 fps tenés unos 16,7 ms por cuadro. Trescientos milisegundos son dieciocho cuadros perdidos, y eso el usuario lo ve como una app trabada.

🔗 La analogía. La recursión es leer un libro sin poder poner un marcapáginas: si te interrumpen, o seguís hasta terminar o perdés el lugar. Fiber es reescribir la lectura como "estoy en la página 84, la próxima es la 85": el estado del recorrido está guardado en un objeto, no en el stack. Ahora sí podés cerrar el libro, atender el timbre y volver exactamente donde estabas. O tirar el marcapáginas y empezar de nuevo con otro libro, si mientras tanto cambió lo que había que leer.

React 16 (2017) reimplementó el reconciliador con esa idea. El recorrido recursivo pasó a ser un bucle sobre una lista enlazada, y el "stack de llamadas" pasó a vivir en el heap, como datos:

// react-reconciler/src/ReactFiberWorkLoop.js — la idea, muy simplificada
let workInProgress = null;   // el fiber que estamos procesando AHORA

function workLoopConcurrent() {
  while (workInProgress !== null && !shouldYield()) {
    workInProgress = performUnitOfWork(workInProgress);
  }
  // Si salimos por shouldYield(), NO terminamos el árbol.
  // workInProgress queda apuntando al próximo nodo: devolvemos el control
  // al navegador y retomamos en el siguiente hueco libre.
}

Ese while es toda la revolución. shouldYield() pregunta si se acabó la porción de tiempo asignada —en la práctica, unos 5 ms— y si se acabó, el bucle corta. React devuelve el control al navegador, que pinta, procesa el click pendiente y respira, y después React retoma el recorrido desde workInProgress.

No todas las actualizaciones se trocean. Que la arquitectura pueda interrumpirse no significa que siempre lo haga. Una actualización urgente (escribir en un input, un click) se renderiza de un tirón, porque trocearla la haría llegar más tarde. El troceo se usa para trabajo de baja prioridad: transiciones, contenido diferido. Ese sistema de prioridades se llama lanes y es el tema completo de RS2. Para RS1 alcanza con una consecuencia: la fase de render puede descartarse y rehacerse.

RS1.2 Anatomía de un fiber

Un fiber es un objeto plano de JavaScript que representa una unidad de trabajo: un componente, un nodo del DOM, un fragmento, un límite de Suspense. Hay uno por cada cosa que React tiene que procesar. Sacando campos experimentales y de desarrollo, se parece bastante a esto:

// react-reconciler/src/ReactInternalTypes.js — recortado y comentado
type Fiber = {
  // ── IDENTIDAD: con esto React decide si te reutiliza o te destruye ──
  tag: WorkTag,          // 0 = FunctionComponent, 1 = ClassComponent,
                         // 3 = HostRoot, 5 = HostComponent (<div>), 6 = HostText…
  key: null | string,    // la key que le pusiste en el JSX
  elementType: any,      // el tipo tal cual lo escribiste (Foo, 'div', memo(Foo)…)
  type: any,             // el tipo resuelto (lo que React realmente invoca)

  // ── POSICIÓN: el árbol es una lista enlazada, no un array de hijos ──
  return: Fiber | null,  // el padre (se llama "return" porque es a dónde volver)
  child: Fiber | null,   // SOLO el primer hijo
  sibling: Fiber | null, // el próximo hermano
  index: number,         // posición entre hermanos

  // ── ESTADO ──
  stateNode: any,          // el nodo real del DOM, o la instancia de la clase
  pendingProps: any,       // las props de ESTE render
  memoizedProps: any,      // las props del render ANTERIOR (ya commiteadas)
  memoizedState: any,      // clases: this.state · funciones: la lista de hooks
  updateQueue: mixed,      // cola de setState pendientes
  dependencies: Dependencies | null,  // contextos que este fiber consume

  // ── TRABAJO PENDIENTE ──
  flags: Flags,            // qué hay que hacerle en el commit: Placement,
                           // Update, Deletion, Ref, Passive…
  subtreeFlags: Flags,     // el OR de los flags de todo el subárbol
  deletions: Array<Fiber> | null,
  lanes: Lanes,            // prioridad del trabajo agendado EN este fiber
  childLanes: Lanes,       // prioridad del trabajo agendado más ABAJO

  // ── EL OTRO ÁRBOL ──
  alternate: Fiber | null, // el mismo nodo, en el árbol opuesto
};

Fijate en child y sibling: un fiber no tiene un array de hijos. Tiene un puntero al primer hijo, y ese hijo tiene un puntero al próximo hermano. Es una lista enlazada, porque una lista enlazada se recorre con un bucle y un puntero — que es exactamente lo que necesitás para poder pausar.

Lo que escribís en JSX:

    <App>
      <Header />
      <Lista>
        <Fila a />
        <Fila b />
      </Lista>
    </App>

Lo que React guarda:

                    App
                     │ child
                     ▼
                  Header ──── sibling ────►  Lista
                     │                          │ child
              return │                          ▼
                     └───────────►  App      Fila a ──sibling──► Fila b
                                                 │                  │
                                          return │           return │
                                                 └──► Lista ◄───────┘

Recorrido (profundidad primero): App → Header → Lista → Fila a → Fila b
Cuando un nodo no tiene child, se va por sibling.
Cuando no tiene sibling, sube por return y prueba el sibling del padre.
Todo el recorrido cabe en una variable: workInProgress.
📌 Un fiber es la unidad de trabajo y también la unidad de identidad. El estado local de tu componente no vive "en el componente": vive en memoizedState de ese fiber. Si React decide que el fiber de esta posición ya no corresponde al mismo componente, el fiber se descarta — y tu estado se va con él. Todo el resto del módulo es, en el fondo, la respuesta a "¿cuándo decide eso?".

Por qué los hooks no pueden ser condicionales

Acá hay un pago inmediato por saber internals. memoizedState, en un componente de función, es la cabeza de una lista enlazada de hooks. No hay nombres, no hay claves: solo orden.

// Lo que React guarda para: useState(0); useState(''); useEffect(fn, [x])
fiber.memoizedState = {
  memoizedState: 0,              // ← el useState(0)
  queue: { /* … */ },
  next: {
    memoizedState: '',           // ← el useState('')
    queue: { /* … */ },
    next: {
      memoizedState: { /* efecto: create, destroy, deps */ },
      next: null,
    },
  },
};

En cada render, React recorre esa lista en el mismo orden en que vos llamás a los hooks. El primer useState agarra el primer nodo, el segundo agarra el segundo. No hay ninguna otra forma de emparejarlos.

function Perfil({ usuario }) {
  if (usuario) {
    const [nombre, setNombre] = useState(usuario.nombre); // ⛔ a veces sí, a veces no
  }
  const [tema, setTema] = useState('oscuro');
  // Si `usuario` es null, `useState('oscuro')` agarra el PRIMER nodo de la lista,
  // que es el que guardaba el nombre. React te devuelve el string equivocado
  // y, si hay efectos, se desincronizan las dependencias.
}
Por eso la regla "los hooks se llaman siempre, en el mismo orden, en el nivel superior" no es una convención de estilo ni una manía del linter: es la única forma de que una lista enlazada sin claves se pueda emparejar entre renders. Y por eso el error que te tira React es "Rendered fewer hooks than expected": literalmente contó.

RS1.3 Los dos árboles: current, work in progress y alternate

React mantiene dos árboles de fibers a la vez. Es la misma técnica que usan los motores gráficos con el double buffering: dibujás en un búfer mientras se muestra el otro, y al final los intercambiás.

   FiberRoot
   ├─ current ──────────────┐
   │                        ▼
   │   ÁRBOL CURRENT                    ÁRBOL WORK IN PROGRESS
   │   (lo que está en pantalla)        (el que se está construyendo)
   │   ─────────────────────────        ────────────────────────────
   │        HostRoot  ◄──── alternate ────►  HostRoot'
   │           │ child                          │ child
   │           ▼                                ▼
   │          App     ◄──── alternate ────►    App'
   │           │                                │
   │           ▼                                ▼
   │        Header    ◄──── alternate ────►  (no se tocó:
   │                                           se clonó o se
   │                                           saltó entero)
   │
   └─ Al terminar el commit:  root.current = workInProgressTree
      El árbol viejo pasa a ser el "alternate" y se recicla en el próximo render.

Cuando llega una actualización, React empieza a construir el árbol work in progress clonando nodos del current sobre la marcha:

// react-reconciler/src/ReactFiber.js — createWorkInProgress, simplificado
function createWorkInProgress(current, pendingProps) {
  let wip = current.alternate;

  if (wip === null) {
    // Primera vez: creamos el gemelo y los enlazamos para siempre
    wip = createFiber(current.tag, pendingProps, current.key, current.mode);
    wip.stateNode = current.stateNode;   // el nodo del DOM se COMPARTE
    wip.alternate = current;
    current.alternate = wip;
  } else {
    // Ya existe: lo reciclamos en vez de alocar un objeto nuevo
    wip.pendingProps = pendingProps;
    wip.flags = NoFlags;                 // se limpian los efectos del render anterior
    wip.deletions = null;
  }

  wip.child = current.child;             // se copian los punteros
  wip.memoizedProps = current.memoizedProps;
  wip.memoizedState = current.memoizedState;
  wip.updateQueue = current.updateQueue;
  return wip;
}

Dos consecuencias que importan de verdad:

1. Mientras React renderiza, la pantalla sigue mostrando lo viejo. El árbol current describe exactamente lo que hay en el DOM en este instante. Por eso React puede tirar a la basura un work in progress a medio construir sin que el usuario vea absolutamente nada — no hubo ninguna mutación del DOM.
2. Solo hay dos fibers vivos por nodo, no uno por render. Se reciclan. Un componente que renderizó ochocientas veces no dejó ochocientos objetos: dejó dos, que se van pasando la pelota. Eso es lo que hace que renderizar sea barato.
El error que se deduce de acá: leer el DOM durante el render y esperar ver lo nuevo. En la fase de render el DOM todavía es el del árbol current; tu ref.current.offsetHeight te devuelve la medida vieja. Medir el DOM es trabajo de commit — y para eso está useLayoutEffect (RS1.11).

Qué NO podés hacer en la fase de render

let contadorDeVisitas = 0;                    // ⛔ estado fuera de React
const yaAvisados = new Set();

function Tarjeta({ item, onVisto }) {
  contadorDeVisitas++;                        // ⛔ 1. mutás una variable de módulo
  item.visitas = (item.visitas ?? 0) + 1;     // ⛔ 2. mutás una prop
  if (!yaAvisados.has(item.id)) {
    yaAvisados.add(item.id);
    fetch('/api/visto', { method: 'POST' });  // ⛔ 3. efecto de red en el render
  }
  const alto = document.getElementById('caja')?.offsetHeight;  // ⛔ 4. leés el DOM
  onVisto(item.id);                           // ⛔ 5. avisás al padre (setState ajeno)

  return <div className="caja">{item.titulo}</div>;
}

Nada de eso es "mala práctica" en abstracto: es incompatible con la arquitectura. React puede llamar a Tarjeta tres veces y quedarse con el resultado de la tercera. Puede llamarla, abandonar el render a mitad porque llegó algo más urgente, y volver a llamarla desde cero. Tu contador va a contar renders descartados. Tu fetch va a disparar peticiones por renders que nunca llegaron a la pantalla. Tu Set va a impedir que el segundo intento —el bueno— haga lo suyo.

// La versión pura: mismas props → mismo resultado, cero efectos
function Tarjeta({ item }) {
  return <div className="caja">{item.titulo}</div>;
}

// Y el efecto donde corresponde: en el commit, con limpieza
function TarjetaConTelemetria({ item }) {
  useEffect(() => {
    const ac = new AbortController();
    fetch('/api/visto', {
      method: 'POST',
      body: JSON.stringify({ id: item.id }),
      signal: ac.signal,
    }).catch(() => {});
    return () => ac.abort();   // ⬅️ si el efecto se rehace, se cancela lo anterior
  }, [item.id]);

}
📌 La pureza no es una preferencia estética: es un requisito. "Mismas props y mismo estado producen el mismo JSX, y no pasa nada más" es el contrato que le permite a React descartar un render sin consecuencias. El día que lo rompés, el precio no lo pagás ese día: lo pagás cuando activás una transición, o Suspense, o simplemente cuando alguien mueve tu componente adentro de otro que renderiza más seguido.

El commit por dentro

El commit no es un solo bloque: son tres sub-fases sincrónicas, en este orden exacto. Saberlo es lo que te permite explicar por qué tu tooltip parpadea o por qué el ref vale null.

// react-reconciler/src/ReactFiberCommitWork.js — el orden, muy simplificado
function commitRoot(root, finishedWork) {

  // ── 1. BEFORE MUTATION ─────────────────────────────────────────
  //     El DOM todavía es el VIEJO. Última chance de medirlo.
  //     Acá corre getSnapshotBeforeUpdate (clases).
  //     Acá se AGENDAN (no se ejecutan) los efectos pasivos: useEffect.
  commitBeforeMutationEffects(root, finishedWork);

  // ── 2. MUTATION ────────────────────────────────────────────────
  //     Se toca el DOM: insertar, actualizar atributos, borrar nodos.
  //     Antes de cada mutación corre la LIMPIEZA de useLayoutEffect
  //     y se desenganchan los refs (pasan a null).
  //     También corre useInsertionEffect, antes que nada de esto.
  commitMutationEffects(root, finishedWork);

  // ── AQUÍ SE INTERCAMBIAN LOS ÁRBOLES ───────────────────────────
  root.current = finishedWork;

  // ── 3. LAYOUT ──────────────────────────────────────────────────
  //     El DOM ya es el NUEVO, pero el navegador TODAVÍA NO PINTÓ.
  //     Se enganchan los refs y corre useLayoutEffect / componentDidMount.
  //     Si acá hacés setState, React re-renderiza ANTES de pintar.
  commitLayoutEffects(finishedWork, root);

  // ── El navegador pinta ─────────────────────────────────────────
  // ── Después, asincrónicamente: los efectos pasivos (useEffect) ──
}
⚠️ El commit no se puede interrumpir, y eso es a propósito. Si React pudiera pausar a mitad de aplicar mutaciones, el usuario vería un DOM inconsistente: media lista actualizada, media vieja. Por eso todo el commit es sincrónico. Y por eso el trabajo caro que metas en useLayoutEffect bloquea el pintado: estás dentro de la parte no interrumpible.

RS1.5 StrictMode: por qué tu código corre dos veces

Si la fase de render tiene que ser pura, hace falta una forma de detectar cuándo no lo es. <StrictMode> es esa forma: en desarrollo, invoca dos veces todo lo que debería ser puro, y remonta los efectos, para que las impurezas se rompan ruidosamente en tu máquina y no en silencio en producción.

import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>
);

function Sala({ salaId }) {
  useEffect(() => {
    const conexion = crearConexion(salaId);
    conexion.conectar();

  }, [salaId]);

// Con StrictMode: monta (conecta) → desmonta (NO desconecta) → monta (conecta)
// Resultado observable: DOS conexiones abiertas, y en la consola dos "conectado a…".
// Sin StrictMode el bug existe igual, pero recién lo ves en producción cuando
// el usuario navega diez veces y tenés diez sockets colgados.

function SalaCorrecta({ salaId }) {
  useEffect(() => {
    const conexion = crearConexion(salaId);
    conexion.conectar();
    return () => conexion.desconectar();   // ✅ simétrico
  }, [salaId]);
}
Si tu app se rompe con StrictMode, el bug es tuyo, no de StrictMode. "Lo apagué porque me duplicaba las peticiones" es la decisión que te garantiza que el mismo problema va a reaparecer en producción, disfrazado de otra cosa, seis meses después. La duplicación de peticiones se arregla con una limpieza que aborte, o con una librería de datos que deduplique (RS5).
StrictMode no hace nada en el build de producción: no duplica, no remonta, no cuesta un milisegundo. Y ojo con esto al perfilar: si medís tiempos en desarrollo con StrictMode activo, estás midiendo dos renders por cada uno real.

RS1.6 Qué dispara un re-render de verdad

Un componente de función se vuelve a ejecutar por exactamente tres razones. No hay una cuarta.

1. Su propio estado cambió. Un setState, un dispatch, o una store externa que notificó vía useSyncExternalStore.
2. Su padre se re-renderizó. Por defecto, si el padre corre, los hijos corren. Sin importar si sus props cambiaron.
3. Un contexto que consume cambió de valor. Y esto atraviesa cualquier memo que haya en el medio.

Repasemos las trampas de cada uno.

Estado que "cambia" sin cambiar

const [n, setN] = useState(0);

setN(0);        // n ya era 0 → React compara con Object.is → no agenda trabajo
setN(n);        // idem

const [user, setUser] = useState({ nombre: 'Ada' });
user.nombre = 'Grace';       // ⛔ mutaste: MISMA referencia
setUser(user);               // Object.is(user, user) === true → no pasa nada
setUser({ ...user, nombre: 'Grace' });   // ✅ objeto nuevo → re-render
React compara con Object.is, no con igualdad profunda. Y hay un detalle honesto de la implementación: al llamar a setN(0), React puede llegar a ejecutar tu componente una vez más antes de decidir que no hay nada que hacer (el eager state solo se calcula si la cola está vacía). No debería afectar a tu código — si te afecta, tu componente no es puro.

El padre re-renderizó

function Padre() {
  const [n, setN] = useState(0);
  return (
    <>
      <button onClick={() => setN(n + 1)}>{n}</button>
      <Hijo texto="constante" />   {/* la prop NUNCA cambia… */}
    </>
  );
}

function Hijo({ texto }) {
  console.log('Hijo renderizó');   // …y sin embargo esto se imprime en CADA click
  return <p>{texto}</p>;
}

La razón, en términos de fibers: cada vez que Padre corre, el JSX crea un elemento nuevo para <Hijo />, con un objeto de props nuevo. Cuando React llega al fiber de Hijo, compara current.memoizedProps con workInProgress.pendingProps y son objetos distintos —aunque tengan el mismo contenido— así que no puede saltear nada y llama a la función. La comparación es por referencia, y sale barata justamente porque es por referencia.

El contexto

function App() {
  const [usuario, setUsuario] = useState(null);
  const [tema, setTema] = useState('oscuro');

  // ⛔ objeto literal: referencia nueva en CADA render de App
  return (
    <SesionContext value={{ usuario, setUsuario, tema }}>
      <TodoElArbol />
    </SesionContext>
  );
}

Cambiar el tema hace que App renderice, que se cree un objeto value nuevo, y que todos los consumidores del contexto se re-rendericen — incluidos los que solo leen usuario, que no cambió. Y no los salva ningún memo intermedio: la propagación de contexto recorre los fibers marcando a los consumidores directamente, saltándose los bailouts.

📌 Los tres arreglos del contexto, en orden de preferencia: (1) partir el contexto en varios más chicos y estables (uno de datos, uno de acciones); (2) poner el contexto lo más abajo posible en el árbol; (3) recién ahí, estabilizar el value. La arquitectura de estado en serio es RS6.

Y la aclaración más importante de todo el módulo

💡 Que un componente re-renderice NO significa que el DOM cambie. "Renderizar" es llamar a tu función y obtener elementos. React compara esos elementos contra el fiber actual; si las props del nodo host son iguales, no marca ningún flag, y en el commit ese nodo recibe cero trabajo. Cero mutaciones, cero recálculo de layout, cero repintado. El navegador ni se entera. 
function Reloj() {
  const [, forzar] = useState(0);
  useEffect(() => {
    const id = setInterval(() => forzar(n => n + 1), 16);  // ~60 renders/s
    return () => clearInterval(id);
  }, []);

  // Este JSX es idéntico en cada render.
  // React lo va a comparar 60 veces por segundo y no va a tocar el DOM ni una vez.
  return <p className="titulo">Hola</p>;
}

Comprobalo vos: activá Paint flashing en Chrome DevTools (Rendering) y no vas a ver ni un parpadeo. El costo de esos 60 renders por segundo es real pero minúsculo: llamar una función y comparar dos objetos.

🔗 Es la diferencia entre recalcular una planilla y reimprimirla. Recalcular ochocientas celdas cuesta microsegundos. Reimprimir la hoja cuesta papel, tinta y tiempo. React recalcula seguido justamente para poder imprimir poco.

De acá sale la regla práctica que ordena el 90% de las discusiones de rendimiento en React: el problema casi nunca es "renderiza mucho", es "cada render hace algo caro". Un .filter().sort() sobre 50.000 items, un JSON.parse, un cálculo de fechas por fila, o un árbol de 5.000 nodos que se recorre entero. Eso es lo que hay que buscar en el perfil.

RS1.7 Reconciliación: el heurístico del tipo

Comparar dos árboles cualesquiera es un problema de complejidad O(n³). React lo resuelve en O(n) haciendo dos suposiciones que en interfaces reales se cumplen casi siempre:

Suposición 1. Dos elementos de tipo distinto en la misma posición producen árboles distintos. No se comparan: se destruye lo viejo y se construye lo nuevo.
Suposición 2. El desarrollador puede indicar, con una key, qué hijos se mantienen estables entre renders aunque cambien de posición.

La segunda es RS1.8. Vamos con la primera, que es la que produce los bugs más desconcertantes.

Render anterior          Render nuevo            Qué hace React
──────────────────       ─────────────────       ─────────────────────────────
<div><Input/></div>      <div><Input/></div>     mismo tipo → reutiliza el nodo,
                                                 actualiza solo lo que cambió,
                                                 CONSERVA el estado

<div><Input/></div>      <span><Input/></span>   tipo distinto → DESMONTA todo
                                                 el subárbol y lo vuelve a montar:
                                                 estado PERDIDO

<Perfil user="a" />      <Perfil user="b" />     mismo tipo → conserva el estado
                                                 aunque el usuario sea otro (!)
⚠️ "Desmontar el subárbol" es más caro y más destructivo de lo que suena. Se pierde el estado local de todos los descendientes; los refs se ponen en null; corren todas las limpiezas de efectos; los nodos del DOM se destruyen y se crean de nuevo, y con ellos se va el foco, la selección de texto, la posición del scroll, el estado de un <video> que estaba reproduciendo y cualquier animación CSS en curso. Un cambio de tipo en el nodo equivocado es un bug de UX, no de performance.

El caso 1: el condicional que cambia la forma del árbol

function Campo({ editando }) {
  return (
    <>
      {editando
        ? <div className="marco"><input /></div>   {/* posición 0: div  */}
        : <input />                                {/* posición 0: input */}
      }
    </>

}
// Al pasar editando de false a true, en la posición 0 había un `input`
// y ahora hay un `div`. React desmonta el input y monta uno nuevo adentro
// del div: lo que el usuario había escrito desaparece.
// ✅ Misma estructura en las dos ramas: el input nunca cambia de posición ni de tipo
function Campo({ editando }) {
  return (
    <div className={editando ? 'marco' : 'marco--plano'}>
      <input />
    </div>
  );
}

El caso 2: el componente definido adentro de otro

Este es el bug que separa a quien entendió el reconciliador de quien no. Se ve así:

function Formulario() {
  const [nombre, setNombre] = useState('');

  // ⛔ Se define en CADA render: cada vez es una FUNCIÓN DISTINTA
  function CampoNombre() {
    return <input value={nombre} onChange={e => setNombre(e.target.value)} />;
  }

  return <CampoNombre />;
}

Síntoma: el input pierde el foco después de cada tecla. Causa, en términos de fibers: el type del elemento es la referencia a la función CampoNombre. Como la función se crea de nuevo en cada render, tipoViejo !== tipoNuevo, y React aplica la suposición 1: desmonta el subárbol entero y monta uno nuevo. El nodo <input> del DOM se destruye y se crea otro — y un nodo recién creado no tiene el foco.

// ✅ Opción A: sacarlo afuera (la función es la misma para siempre)
function CampoNombre({ valor, onChange }) {
  return <input value={valor} onChange={onChange} />;
}

function Formulario() {
  const [nombre, setNombre] = useState('');
  return <CampoNombre valor={nombre} onChange={e => setNombre(e.target.value)} />;
}

// ✅ Opción B: si de verdad necesitás componer al vuelo, pasá ELEMENTOS, no componentes
function Formulario() {
  const [nombre, setNombre] = useState('');
  return <Marco contenido={<input value={nombre} onChange={/* … */} />} />;

La misma trampa, disfrazada: React.lazy(() => import('./X')) llamado dentro del cuerpo de un componente, o un styled.div`…` creado adentro del render, o cualquier HOC aplicado en línea (withAuth(MiComponente) dentro del JSX). Todos producen un tipo nuevo por render y todos desmontan el subárbol en cada tecla. La regla general: los tipos de componente se definen a nivel de módulo.

El corolario útil: el estado vive en la posición

📌 El estado se identifica por la terna (posición en el árbol, tipo, key). No por "el componente". Si esa terna se mantiene, el estado sobrevive; si cambia cualquiera de los tres, el estado se destruye.

Y eso se puede usar a propósito, que es una de las técnicas más limpias y menos usadas de React:

// ⛔ El patrón que se ve por todos lados: "sincronizar" estado con un efecto
function Perfil({ userId }) {
  const [borrador, setBorrador] = useState('');
  useEffect(() => { setBorrador(''); }, [userId]);   // render de más + flash visual
  // …
}

// ✅ Cambiar la key remonta el subárbol: el estado se reinicia solo,
//    sin efecto, sin render extra, sin nada que mantener sincronizado.
function Pagina({ userId }) {
  return <Perfil key={userId} userId={userId} />;
}

RS1.8 Keys: la identidad de un elemento

Dentro de un mismo padre, la key le dice a React qué hijo del render anterior corresponde a qué hijo del render nuevo. Nada más, y nada menos. Sin keys, React empareja por posición: el primero con el primero, el segundo con el segundo.

El algoritmo de listas hace una pasada en orden mientras las keys coinciden; en cuanto dejan de coincidir, arma un Map con los hijos viejos restantes indexados por key y busca ahí. Lo que encuentra, lo mueve; lo que no aparece en el nuevo, lo borra; lo nuevo que no estaba, lo inserta.

Anterior:  [a] [b] [c]          Nuevo:  [c] [a] [b]

Con keys estables ("a","b","c"):
   c → ya existía: MOVER (el nodo del DOM y su estado se conservan)
   a → ya existía: MOVER
   b → ya existía: MOVER
   Resultado: 3 movimientos, 0 destrucciones. El estado viaja con el item.

Sin keys (empareja por posición 0,1,2):
   pos 0: era "a", ahora "c" → actualizar props del nodo 0
   pos 1: era "b", ahora "a" → actualizar props del nodo 1
   pos 2: era "c", ahora "b" → actualizar props del nodo 2
   Resultado: 3 actualizaciones. El DOM queda bien…
   …pero el ESTADO LOCAL de cada fila se quedó en su posición vieja.

El caso reproducible: el índice como key

Escribí esto y probalo, porque leerlo no alcanza:

function ListaRota() {

function Fila({ item, onBorrar }) {
  const [nota, setNota] = useState('');    // ⬅️ estado LOCAL, vive en el fiber
  return (

Por qué. Antes había keys 0, 1, 2. Después de borrar quedan 0, 1. React ve que la key 0 existía y sigue existiendo, así que reutiliza ese fiber: le cambia las props (ahora el item es "Llamar al banco") pero le deja el memoizedState — que es el estado local de la fila que antes estaba en la posición 0. Lo mismo con la 1. La fila que se destruye es la última, la key 2, que no tiene nada que ver con la que vos borraste.

💡 Dicho de otra forma: con key={i} le estás diciendo a React "la identidad de esta fila es su posición". Entonces, cuando borrás un elemento del medio, para React no se borró ese elemento: se borró el último, y todos los demás cambiaron de contenido. Las props viajan; el estado, los refs, el foco y el DOM se quedan. 
// ✅ La corrección: la identidad es del DATO, no de la posición
{items.map(item => (
  <Fila key={item.id} item={item} onBorrar={/* … */} />
))}
// Ahora borrar "a" borra el fiber de "a". Los otros dos se mueven con su estado intacto.

Y el peor de todos: key={Math.random()} o key={crypto.randomUUID()} generado en el render. Es peor que no poner key. Como la key cambia en cada render, ninguna coincide con la anterior: React destruye y vuelve a crear la lista entera, siempre. Pierde el estado, pierde el foco, pierde el scroll y hace el máximo trabajo posible en el DOM. Si no tenés un id estable, generalo cuando creás el dato, no cuando lo renderizás.
Dos precisiones que se preguntan mucho: las keys tienen que ser únicas entre hermanos, no en toda la app — dos listas distintas pueden usar las mismas keys sin problema. Y key no llega como prop: si el hijo necesita el id, pasáselo también como id={item.id}.

RS1.9 Bailing out: cuándo React corta la rama

Ya vimos que por defecto un padre que renderiza arrastra a sus hijos. "Por defecto" quiere decir: salvo que React pueda hacer un bailout. Acá está la lógica, que es sorprendentemente corta:

// react-reconciler/src/ReactFiberBeginWork.js — muy simplificado
function beginWork(current, workInProgress, renderLanes) {
  if (current !== null) {
    const oldProps = current.memoizedProps;
    const newProps = workInProgress.pendingProps;

    // ¿Las props son EL MISMO OBJETO? (comparación por referencia, no por contenido)
    if (oldProps === newProps && !hasContextChanged()) {
      // ¿Hay algún setState agendado en ESTE fiber?
      if (!includesSomeLane(renderLanes, workInProgress.lanes)) {
        return bailoutOnAlreadyFinishedWork(current, workInProgress, renderLanes);
      }
    }
  }
  // Si no hubo bailout: acá se llama de verdad a TU función componente.
}

function bailoutOnAlreadyFinishedWork(current, workInProgress, renderLanes) {
  // ¿Hay trabajo agendado en algún lugar MÁS ABAJO del subárbol?
  if (!includesSomeLane(renderLanes, workInProgress.childLanes)) {
    return null;                    // ⬅️ se corta la rama ENTERA: ni se clonan los hijos
  }
  cloneChildFibers(current, workInProgress);
  return workInProgress.child;      // hay trabajo abajo: bajamos, pero sin renderizar acá
}

Hay dos niveles de ahorro, y conviene distinguirlos:

NivelCondiciónQué ahorra
Bailout del nodoMismas props por referencia y sin trabajo propioNo se llama a tu función. Se clonan los hijos y se sigue bajando
Corte de la ramaLo anterior y childLanes vacíoNo se toca nada del subárbol: ni un fiber, ni una comparación

La clave está en oldProps === newProps. Cuando el padre re-renderiza, el JSX crea un objeto de props nuevo, así que esa condición es falsa y no hay bailout. Salvo que el elemento sea literalmente el mismo objeto — y eso pasa cuando el elemento se creó más arriba y baja como children:

// ✅ El bailout "gratis" por composición
function Pagina() {
  return (
    <Contador>
      <ArbolCarisimo />   {/* este elemento se crea acá, en Pagina */}
    </Contador>
  );
}

function Contador({ children }) {
  const [n, setN] = useState(0);
  return (
    <div>
      <button onClick={() => setN(n + 1)}>{n}</button>
      {children}   {/* ⬅️ el MISMO objeto elemento que en el render anterior */}
    </div>
  );
}
// Al hacer click, Pagina no renderiza (su estado no cambió), así que el elemento
// <ArbolCarisimo /> es exactamente el mismo objeto. React compara por referencia,
// da igual, y corta la rama. Sin memo, sin useMemo, sin arrays de dependencias.

Por qué React.memo a veces no sirve para nada

React.memo agrega un paso más: si el bailout por referencia no aplica, compara las props superficialmente (clave por clave, con Object.is) y, si son iguales, hace el bailout igual. Muy útil… cuando se dan las condiciones. Estas son las cinco razones por las que no se dan:

const Lista = React.memo(function Lista({ items, filtros, onSeleccion }) {

});

  return (
    <>
      <button onClick={() => setN(n + 1)}>{n}</button>

      {/* ⛔ 1. objeto literal: referencia nueva en cada render */}
      {/* ⛔ 2. array derivado: idem */}
      {/* ⛔ 3. función inline: idem */}
      <Lista
        filtros={{ activos: true }}
        items={datos.filter(d => d.activo)}
        onSeleccion={(id) => console.log(id)}

// ⛔ 4. children como JSX: SIEMPRE es un objeto elemento nuevo,
//       así que la comparación superficial de props nunca da igual

// ⛔ 5. el componente consume un contexto que cambió:
//       la propagación de contexto marca a los consumidores directamente
//       y se saltea cualquier memo que haya en el camino

Y la sexta razón, la más común: no hacía falta. memo no es gratis: cuesta una comparación de props por render, memoria para retener el resultado anterior, y —el costo real— obliga a mantener estables todas las props río arriba, lo que contamina el código de padres y abuelos con useMemo y useCallback. Si el componente rinde 0,3 ms, acabás de pagar complejidad permanente por nada.
📌 En 2026 la memoización manual no es la respuesta por defecto. El React Compiler memoiza automáticamente a partir del análisis del código, sin arrays de dependencias que se desincronicen. Cómo funciona, qué garantiza y cómo se adopta en un proyecto que ya existe es todo RS3. La regla para hoy: primero arreglá dónde vive el estado y la forma del árbol; memo es el último recurso, no el primero.

RS1.10 Batching automático

React agrupa varios setState en un solo render. Hasta React 17 eso solo pasaba dentro de manejadores de eventos de React; en cualquier otro lado —una promesa, un setTimeout, un evento nativo— cada setState provocaba su propio render. Desde React 18 el agrupamiento es automático en todos lados.

function Formulario() {
  const [cargando, setCargando] = useState(false);
  const [datos, setDatos] = useState(null);
  const [error, setError] = useState(null);

  async function enviar() {
    setCargando(true);              // ── dentro de un handler: 1 render (igual en 17 y 18)
    try {
      const r = await fetch('/api/guardar');
      const json = await r.json();

      // ── DESPUÉS del await: acá está la diferencia
      setDatos(json);
      setError(null);
      setCargando(false);
      // React 17: TRES renders, y dos de ellos con estado inconsistente
      //           (datos cargados pero cargando todavía en true)
      // React 18+: UN render, con los tres valores ya coherentes
    } catch (e) {
      setError(e);
      setCargando(false);           // React 18+: un solo render
    }
  }
}

El mecanismo: React no re-renderiza en el momento del setState. Encola la actualización y agenda un microtask para vaciar la cola. Todo lo que se encole en el mismo tick termina en el mismo render. De ahí sale el malentendido más frecuente de todos:

const [n, setN] = useState(0);

function alClickear() {
  setN(n + 1);
  setN(n + 1);
  setN(n + 1);
  console.log(n);   // 0 — `n` es una CONSTANTE de este render, no cambia nunca
}
// Resultado: n pasa a 1, no a 3. Las tres llamadas calcularon 0 + 1.

function alClickearBien() {
  setN(prev => prev + 1);
  setN(prev => prev + 1);
  setN(prev => prev + 1);
}
// Resultado: 3. Las funciones actualizadoras se aplican en orden sobre la cola.

La salida de emergencia: flushSync

import { flushSync } from 'react-dom';

function agregarYBajar(texto) {
  flushSync(() => {
    setMensajes(ms => [...ms, texto]);
  });
  // Al salir de flushSync, React YA renderizó y commiteó: el DOM tiene el mensaje.
  listaRef.current.scrollTop = listaRef.current.scrollHeight;
}
⚠️ Cuándo NO usar flushSync. Fuerza un render y un commit sincrónicos, tirando abajo el agrupamiento y el sistema de prioridades: es exactamente lo contrario de lo que React quiere hacer. Usarlo en un onChange de un input, o dentro de un loop, es la forma más rápida de convertir una app fluida en una app trabada. Se justifica en tres casos: medir el DOM inmediatamente después de un cambio, integrarte con una librería no-React que exige el DOM actualizado ya, y algún caso de impresión o exportación. Si lo estás usando para "arreglar" un estado que llega tarde, el problema es otro.

El caso legítimo de useLayoutEffect

Hay uno solo, en el fondo: necesitás medir el DOM y ajustarlo antes de que el usuario lo vea.

function Tooltip({ anclaRef, children }) {
  const tooltipRef = useRef(null);
  const [arriba, setArriba] = useState(true);

  useLayoutEffect(() => {
    const t = tooltipRef.current.getBoundingClientRect();
    const a = anclaRef.current.getBoundingClientRect();
    // ¿Entra arriba del ancla, o hay que darlo vuelta?
    setArriba(a.top - t.height >= 0);
    // Con useLayoutEffect: el usuario nunca ve la posición equivocada.
    // Con useEffect: se pinta mal, y en el cuadro siguiente salta. Eso es el "flash".
  }, [anclaRef, children]);

  return <div ref={tooltipRef} className={arriba ? 'arriba' : 'abajo'}>{children}</div>;
}
Cuándo NO usar useLayoutEffect: para pedir datos, para suscribirte a algo, para loguear, para sincronizar con una store, o "porque parece más rápido". Corre dentro del bloque sincrónico que bloquea el pintado: cada milisegundo que le metas es un milisegundo de pantalla congelada, y si adentro hacés setState, React tiene que renderizar y commitear otra vez antes de dejar pintar. Además no corre en el servidor (React te avisa con un warning en SSR), así que un componente que depende de él para posicionarse va a hidratar distinto — eso es RS4.
useInsertionEffect existe casi exclusivamente para librerías de CSS-in-JS: es el único lugar donde se pueden inyectar reglas <style> antes de que alguien mida el layout. No tenés refs disponibles y no deberías tocar el estado. Si no estás escribiendo una librería de estilos, no es para vos.
React 19.2 sumó useEffectEvent, que separa lo que un efecto lee de lo que lo dispara, y elimina buena parte de los arrays de dependencias con valores que no querías como disparadores. No cambia nada de los tiempos de esta tabla; se cubre junto con los patrones de efectos en RS7.

RS1.12 Cómo verlo con tus propios ojos

Todo lo anterior es verificable en tu propia app, en cinco minutos. La herramienta es React DevTools, y hay tres cosas que la mayoría de la gente nunca activa.

1. Highlight updates. En la pestaña Components, engranaje → General → "Highlight updates when components render". Cada componente que renderiza se dibuja con un borde de color; el color va de azul (poco frecuente) a rojo (muy frecuente). Es la forma más rápida de ver que al tipear en un input se enciende media pantalla. Ojo con la interpretación: el borde dice "renderizó", no dice "cambió el DOM" (RS1.6).
2. Why did this render? En la pestaña Profiler, engranaje → Profiler → "Record why each component rendered while profiling". Después de grabar, al seleccionar un componente te dice el motivo: "Props changed: (items)", "Hook 1 changed", "Context changed" o "The parent component rendered". Ese último mensaje es el diagnóstico completo del 80% de los problemas de este módulo.
3. Los commits, no los componentes. La barra de arriba del Profiler muestra una barra por commit, con su duración. Antes de mirar el flamegraph, mirá esa barra: ¿hay un commit caro, o hay ochenta commits baratos? Son dos problemas distintos. Uno se arregla haciendo menos trabajo por render; el otro, renderizando menos veces (o agrupando).
// Medición programática: el mismo dato que ves en el Profiler, pero en tu código
import { Profiler } from 'react';

function alRenderizar(id, fase, duracionReal, duracionBase, inicio, commit) {
  // fase: 'mount' | 'update' | 'nested-update'
  // duracionReal: cuánto tardó ESTE render (con los bailouts ya aplicados)
  // duracionBase: cuánto tardaría SIN ningún bailout ni memoización
  if (duracionReal > 16) {
    console.warn(`[perf] ${id} · ${fase} · ${duracionReal.toFixed(1)}ms ` +
                 `(base ${duracionBase.toFixed(1)}ms)`);
  }
}

<Profiler id="TablaProductos" onRender={alRenderizar}>
  <TablaProductos items={items} />
</Profiler>
La relación entre duracionReal y duracionBase es la métrica que casi nadie mira, y es la buena. Si son parecidas, tus bailouts no están sirviendo: React está haciendo todo el trabajo posible. Si duracionReal es mucho menor, la composición está funcionando. Es la forma de responder con un número a "¿este memo hace algo?".

Además, React 19.2 agregó performance tracks propias al panel Performance de Chrome: pistas dedicadas que muestran el planificador y los componentes junto al resto de la línea de tiempo del navegador. Sirve para lo que el Profiler de React no puede mostrarte: cómo se intercala el trabajo de React con el layout, el pintado, la red y el resto del JavaScript de la página.

Los números de desarrollo son mentira, pero son mentira útil. El build de desarrollo es entre 2 y 5 veces más lento, y con StrictMode cada render se cuenta dos veces. Sirven perfectamente para comparar antes y después de un cambio, o para ver qué renderiza. No sirven para prometerle a nadie un número absoluto: eso se mide en un build de producción, con datos reales y en un dispositivo parecido al del usuario.

RS1.13 Cuándo esto importa (y cuándo no)

Saber internals no es para escribir React más raro. Es para tomar bien tres o cuatro decisiones que después salen caras de revertir:

1. Dónde vive cada pedazo de estado. Es la decisión más barata de tomar, la más cara de cambiar después, y la que más determina el rendimiento. Un estado que se actualiza en cada tecla y vive tres niveles más arriba de lo necesario arrastra medio árbol con él. Esto es el 90% de los problemas reales.
2. La forma del árbol. Composición con children vs. props que bajan tres niveles. La primera te da bailouts gratis y componentes que se leen solos; la segunda te da prop drilling y renders en cascada.
3. Qué tiene identidad estable. Keys derivadas del dato, tipos de componente definidos a nivel de módulo, y key usada a propósito cuando querés reiniciar un subárbol. Esto no es rendimiento: es corrección.
4. Cuándo no hacer absolutamente nada. Si un commit tarda 3 ms, cualquier memo que agregues es deuda técnica con interés: complejidad permanente a cambio de cero milisegundos.
⚠️ El antipatrón senior más caro es memoizar preventivamente. "Por las dudas" se paga con memoria retenida, con arrays de dependencias que se desincronizan del cuerpo de la función, con bugs de valores viejos que aparecen una vez cada mil renders, y con revisiones de código donde nadie se anima a tocar nada. Y con el React Compiler (RS3), buena parte de ese trabajo manual queda directamente obsoleto. Medí, encontrá el commit caro, arreglá ese.

Checkpoint — ¿lo tenés claro?

¿Por qué la fase de render tiene que ser pura, en términos de la arquitectura y no de "buenas prácticas"?

Porque React construye el árbol work in progress en paralelo al que está en pantalla, y se reserva el derecho de descartarlo y rehacerlo: si llega una actualización más urgente, si una transición queda obsoleta, o si el trabajo se troceó y algo cambió en el medio. Descartar un árbol es seguro únicamente si construirlo no dejó rastros fuera de React. En el momento en que tu componente incrementa un contador de módulo, dispara un fetch, muta una prop o llama al setState de otro componente, ese render dejó de ser descartable: el rastro queda aunque el resultado se tire. StrictMode duplica el render en desarrollo justamente para que eso se rompa en tu máquina y no en producción.

Un componente aparece marcado 40 veces por segundo con "Highlight updates". ¿Es un problema?

Todavía no se sabe: renderizar no es cambiar el DOM. Ese borde de color dice que React llamó a la función y comparó elementos, no que haya emitido una sola mutación. Si el JSX resultante es igual, el commit para ese nodo es cero trabajo. Lo que hay que mirar es la duración del commit en el Profiler y qué hace el componente durante el render: un filter().sort() sobre miles de items, un JSON.parse, un cálculo por fila. Si el commit tarda 0,4 ms, 40 renders por segundo son 16 ms por segundo: irrelevante. Si tarda 90 ms, el problema no es la cantidad de renders sino lo que cada uno hace.

Tenés una lista donde se pueden borrar filas y cada fila tiene un input. ¿Por qué key={index} hace que el texto termine en la fila equivocada?

Porque la key es la identidad con la que React empareja los fibers entre renders, y el estado local vive en el fiber. Con el índice como key, la identidad de una fila es su posición. Al borrar la primera de tres, antes había keys 0, 1, 2 y ahora hay 0, 1: para React no desapareció la primera, desapareció la última, y las otras dos "cambiaron de contenido". Entonces reutiliza los fibers 0 y 1 —con su memoizedState, es decir con el texto que vos escribiste— y les cambia solo las props. Las props viajan con el dato; el estado, los refs, el foco y el nodo del DOM se quedan en la posición. Con key={item.id} React borra el fiber que corresponde y mueve los otros con su estado intacto.

Resumen ejecutivo

  • Fiber convirtió la recursión del reconciliador en un bucle sobre una lista enlazada (child, sibling, return). Eso es lo que permite pausar, retomar, descartar y priorizar el trabajo.
  • Hay dos árboles unidos por alternate: el current, que describe la pantalla, y el work in progress, que se está construyendo. Se intercambian en un solo instante, dentro del commit.
  • La fase de render es pura, interrumpible y descartable. La de commit es sincrónica e imposible de interrumpir. Toda la disciplina de React sale de ahí, y StrictMode existe para que las violaciones aparezcan en desarrollo.
  • Un componente re-renderiza por tres razones: su estado, su padre, o un contexto que consume. Y re-renderizar no es cambiar el DOM: el costo real está en lo que hace cada render, no en cuántos hay.
  • La reconciliación es O(n) gracias a dos heurísticos: tipo distinto en la misma posición ⇒ se desmonta el subárbol entero (estado, refs, foco, scroll y nodos incluidos), y las keys para la identidad entre hermanos.
  • El estado vive en la terna (posición, tipo, key), no "en el componente". De ahí salen el bug del componente definido adentro de otro, el del índice como key, y la técnica de cambiar la key a propósito para reiniciar un subárbol.
  • El bailout se apoya en identidad por referencia: mismas props (mismo objeto) y sin trabajo agendado ⇒ no se llama a tu función; si además childLanes está vacío, se corta la rama entera. Componer con children te da ese bailout gratis; React.memo te lo da pagando comparaciones y estabilidad río arriba, y no te protege de los contextos.
  • Desde React 18 el batching es automático en todos lados; flushSync es la salida de emergencia y hay que justificarla.
  • Orden de los efectos: useInsertionEffect → mutación del DOM → refs → useLayoutEffect → pintado → useEffect. useLayoutEffect bloquea el pintado: solo para medir y ajustar antes de que se vea.
  • Se diagnostica con el Profiler ("why did this render", duración real vs. base) y con las performance tracks de React 19.2 en Chrome. Primero se mira cuántos commits y cuán caros; recién después, el flamegraph.
  • La memoización manual no es la respuesta por defecto en 2026: primero el lugar del estado, después la forma del árbol, y el React Compiler (RS3) para el resto.

🧠 Autoevaluación

1. Tenés {editando ? <div className="marco"><input /></div> : <input />}. El usuario escribe algo y recién ahí pasás editando de false a true. ¿Qué pasa con lo que escribió?

La identidad de un nodo es la terna (posición, tipo, key). En la posición 0 antes había un input y ahora hay un div: React aplica el heurístico del tipo, destruye el subárbol viejo —con su estado, sus refs y sus nodos del DOM— y monta uno nuevo. El input resultante es un nodo recién creado: vacío y sin foco. Poner una key no cambia nada, porque el tipo sigue siendo distinto. El arreglo es mantener la estructura estable en las dos ramas y cambiar solo el className.

2. Envolviste una lista pesada en React.memo y sigue re-renderizando con cada tecla que se escribe en un input del padre. ¿Cuál es la causa más probable?

memo compara las props clave por clave con Object.is. Un {...}, un .filter() o una arrow function escritos en el JSX del padre producen una referencia nueva en cada render, y con eso la comparación falla siempre: memo paga el costo de comparar y no ahorra nada. Los otros dos sospechosos habituales son children como JSX (siempre es un objeto elemento nuevo) y un contexto que cambió, que se salta cualquier memo intermedio. Antes de estabilizar props a mano, preguntate si el estado no debería vivir más abajo — y acordate de que el React Compiler (RS3) existe justamente para no hacer esto a mano.

3. Necesitás medir el ancho de un tooltip recién montado y darlo vuelta si no entra, sin que el usuario vea el salto. ¿Dónde va esa medición?

useLayoutEffect corre en la sub-fase de layout del commit: el DOM ya tiene los nodos nuevos, pero el navegador todavía no pintó. Si hacés setState ahí, React vuelve a renderizar y commitear antes de dejar pintar, así que el usuario nunca ve la posición equivocada. Con useEffect la medición ocurre después del pintado: se ve un cuadro con el tooltip mal ubicado y al siguiente salta — el clásico "flash". Y en el cuerpo del componente no sirve: durante el render el DOM todavía es el del árbol current, así que medirías el nodo viejo (o ninguno).

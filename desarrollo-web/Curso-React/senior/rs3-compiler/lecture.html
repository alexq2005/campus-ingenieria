RS3 — React Compiler: el fin de la memoización manual

RS3.0 Por qué este módulo

Durante casi una década, "saber React avanzado" significó, en buena medida, saber dónde poner useMemo, useCallback y memo. Era conocimiento real: había que entender identidad referencial, entender que un objeto literal creado en el render es un objeto nuevo cada vez, entender que pasar una función inline a un hijo memoizado anula el memo. Ese conocimiento separaba al que hacía que la app fuera fluida del que la dejaba trabada.

También era, mirado con honestidad, trabajo mecánico. La decisión de memoizar casi nunca requería creatividad: requería aplicar reglas. Y las reglas que un humano aplica a mano las aplica mal, tarde y de a ratos: memoiza de más "por las dudas", se olvida de la dependencia que importa, deja un useCallback que envuelve una función que igual se recrea porque su closure cambió.

💡 La tesis del módulo. El React Compiler convirtió ese trabajo mecánico en trabajo de la herramienta. No te vuelve innecesario: te cambia el trabajo. En vez de decidir dónde memoizar, tu trabajo pasa a ser garantizar que tu código cumpla las Reglas de React —que es lo único que el compilador necesita para optimizarte— y verificar que efectivamente lo hizo, porque cuando no puede, se saltea el componente en silencio.

Y hay una razón de coyuntura para estudiarlo ahora. El compilador dejó de ser un experimento: llegó a 1.0 el 7 de octubre de 2025, y sobre React 19.2 —la versión estable actual— es una herramienta de producción. Meta ya lo usa en producción en features de Instagram, que es la validación a escala que a este tipo de herramientas siempre les falta. Los números que publica el equipo: entre 25% y 40% menos re-renders innecesarios, sin ningún esfuerzo del desarrollador.

Ojo con esa cifra. "25–40% menos re-renders" no es "25–40% más rápido". Un re-render que no se ve, no se mide y no bloquea nada no cuesta nada perceptible. La ganancia real depende por completo de cuáles re-renders elimina en tu app. Por eso la mitad de este módulo es sobre medir, no sobre activar.

RS3.1 Qué hace exactamente: no es magia, es análisis estático

El React Compiler es un plugin de build —vive como plugin de Babel, y a través de él lo consumen Vite, Next.js, Remix, Expo, etc.— que corre antes de que tu código llegue al navegador. Toma cada función que reconoce como componente o como hook, la analiza, y reescribe su código agregando memoización automática.

Lo que hace, paso a paso:

1. Identifica componentes y hooks. Por convención: funciones con nombre en PascalCase que devuelven JSX, y funciones cuyo nombre empieza con use. Si tu componente se llama miWidget en minúscula, para el compilador no es un componente y ni lo mira.
2. Construye una representación intermedia (HIR). Convierte el cuerpo de la función a una forma de bajo nivel con control de flujo explícito, similar a lo que hace un compilador de verdad. Sobre esa forma puede razonar.
3. Hace análisis de dependencias y de mutación. Determina, para cada valor que tu componente calcula, de qué otros valores depende y quién lo muta. Este es el corazón del asunto: si no puede probar que un valor no se muta después de crearse, no puede cachearlo.
4. Corta el cuerpo en "scopes reactivos". Agrupa las instrucciones en bloques que comparten dependencias, y le asigna a cada bloque un slot en una caché.
5. Emite el código memoizado. Reescribe la función para que, en cada render, compare las dependencias de cada bloque con las del render anterior y reutilice el resultado guardado si no cambiaron.
📌 La granularidad es más fina que la tuya. Vos memoizás un valor con useMemo. El compilador memoiza cada scope reactivo del componente por separado, incluyendo los elementos JSX que devolvés. Eso último es lo que un humano casi nunca hace a mano y es de donde sale buena parte de la ganancia: si el <Sidebar /> que devolvés no depende de nada que cambió, el compilador devuelve el mismo objeto elemento y React ni siquiera baja a reconciliar ese subárbol.

Eso último conecta directo con RS1: React compara los elementos del árbol nuevo contra los del viejo. Si un elemento es referencialmente idéntico al del render anterior, React puede saltearse esa rama entera. Memoizar JSX es memoizar reconciliación, no solo cálculo.

RS3.2 Cómo se ve el output (esto es lo que hace que se entienda)

Nada explica el compilador tan bien como mirar lo que emite. Partimos de un componente absolutamente común, sin ninguna memoización:

function ListaDeTareas({ tareas, filtro, onToggle }) {
  const visibles = tareas.filter((t) => t.estado === filtro);
  const resumen = `${visibles.length} de ${tareas.length}`;

  return (
    <section>
      <Encabezado texto={resumen} />
      <ul>
        {visibles.map((t) => (
          <Tarea key={t.id} tarea={t} onToggle={onToggle} />
        ))}
      </ul>
    </section>
  );
}

Sin compilador, cada render de este componente vuelve a filtrar el array, vuelve a construir el string, y vuelve a crear todos los elementos JSX —incluido <Encabezado />, aunque resumen no haya cambiado.

Con el compilador activado, el output es —simplificado y con nombres legibles— algo muy parecido a esto:

import { c as _c } from "react/compiler-runtime";

function ListaDeTareas(props) {
  const $ = _c(9);                 // 9 slots de caché para este componente
  const { tareas, filtro, onToggle } = props;

  // --- scope 1: visibles depende de (tareas, filtro) ---
  let visibles;
  if ($[0] !== tareas || $[1] !== filtro) {
    visibles = tareas.filter((t) => t.estado === filtro);
    $[0] = tareas;
    $[1] = filtro;
    $[2] = visibles;
  } else {
    visibles = $[2];
  }

  // --- scope 2: resumen depende de (visibles.length, tareas.length) ---
  let resumen;
  if ($[3] !== visibles || $[4] !== tareas) {
    resumen = `${visibles.length} de ${tareas.length}`;
    $[3] = visibles;
    $[4] = tareas;
    $[5] = resumen;
  } else {
    resumen = $[5];
  }

  // --- scope 3: el ELEMENTO <Encabezado /> depende solo de resumen ---
  let encabezado;
  if ($[6] !== resumen) {
    encabezado = <Encabezado texto={resumen} />;
    $[6] = resumen;
    $[7] = encabezado;
  } else {
    encabezado = $[7];
  }

  // ... y así con el resto del árbol
  return $[8] !== encabezado ? ($[8] = encabezado, armarSeccion(...)) : /* cacheado */;
}
El $ es un array que vive en un hook interno del componente (por eso _c(9) reserva 9 posiciones). En el primer render todas las posiciones arrancan con un centinela —Symbol.for("react.memo_cache_sentinel")— que garantiza que ninguna comparación acierte y todo se calcule. En los siguientes, cada if es una comparación por identidad (!==), exactamente la misma semántica que las dependencias de useMemo.

Tres observaciones que cambian cómo pensás el tema:

Es literalmente lo que vos escribirías a mano. No hay ninguna técnica exótica. Es useMemo aplicado sistemáticamente, con dependencias correctas, sobre cada valor intermedio. Un humano no escribe esto porque es ilegible; una herramienta sí, porque nadie lo lee.
Memoiza el JSX, no solo los datos. El scope 3 del ejemplo no cachea un cálculo caro: cachea un objeto elemento. Ese es el caso que a mano casi nadie cubre y que, en árboles grandes, es el que más rinde.
El costo también es visible. Ese array de 9 slots existe por cada instancia montada del componente, y esas comparaciones se ejecutan en cada render. No es gratis. Volvemos sobre esto en RS3.9.

Podés ver el output real de tu propio código sin adivinar. El playground oficial del compilador muestra el HIR y el JavaScript emitido lado a lado, y para un archivo local alcanza con pedirle a Babel que imprima el resultado:

npx babel src/componentes/ListaDeTareas.jsx \
  --plugins babel-plugin-react-compiler \
  --presets @babel/preset-react
Hacé esto una vez, con un componente tuyo real, antes de seguir leyendo el módulo. La diferencia entre "entiendo el concepto" y "vi el código que genera" es enorme, y no se recupera leyendo más prosa.

RS3.3 Las Reglas de React son el contrato

Todo el análisis de RS3.1 se apoya en una suposición: que tu componente es una función pura del estado y las props. Si lo es, el compilador puede probar cosas sobre él y optimizarlo. Si no lo es, cualquier caché que ponga puede cambiar el comportamiento del programa — y ahí el compilador hace lo correcto: no lo optimiza.

Las reglas relevantes, y qué rompe cada una:

ReglaQué significa en la prácticaSi la violás
Los componentes son purosCon las mismas props y estado, mismo output. Sin efectos secundarios durante el render.El compilador no puede reordenar ni saltear el cálculo: se abstiene
No mutar props ni estadoTratar props, estado y todo lo que viene de un hook como inmutableEs la causa #1 de componentes salteados
No mutar valores después de usarlos en JSXUn objeto que ya pasaste a un hijo no se toca másLa caché devolvería el objeto ya mutado
Hooks en el tope, sin condicionalesMismo orden de hooks en todos los rendersError de compilación, no solo skip
No leer ni escribir refs durante el renderref.current solo en efectos y handlersEl render deja de ser puro
No llamar setState durante el renderSalvo el patrón oficial de estado derivadoRender con efectos: no memoizable

El caso más frecuente, de lejos, es la mutación de props. Casi siempre entra por la puerta de atrás, disfrazada de conveniencia:

// ❌ Muta una prop. El compilador NO va a optimizar este componente.
function TablaUsuarios({ usuarios, columnas }) {
  // .sort() ordena EL ARRAY ORIGINAL, in place
  usuarios.sort((a, b) => a.apellido.localeCompare(b.apellido));

  // y esto muta el objeto que nos pasaron
  columnas.forEach((col) => {
    col.ancho = col.ancho ?? 120;
  });

  return <Tabla filas={usuarios} cols={columnas} />;
}

Esto probablemente "funcione" hoy. Nunca fue correcto: el padre le pasó un array y vos se lo reordenaste sin avisar, y le pusiste campos a sus objetos. Con Strict Mode y doble render en desarrollo ya podía dar sorpresas. Lo que cambia con el compilador es que ahora esa incorrección tiene un costo visible: el componente queda afuera de la optimización.

// ✅ Copiar antes de transformar. Ahora es puro y memoizable.
function TablaUsuarios({ usuarios, columnas }) {
  const ordenados = [...usuarios].sort((a, b) =>
    a.apellido.localeCompare(b.apellido)
  );

  const conAncho = columnas.map((col) => ({
    ...col,
    ancho: col.ancho ?? 120,
  }));

  return <Tabla filas={ordenados} cols={conAncho} />;
}
La trampa mental. "Pero copiar el array en cada render es más lento". Sin compilador, tal vez. Con compilador, ese [...usuarios].sort(...) queda dentro de un scope reactivo que depende de usuarios: si la prop no cambió, la copia no se vuelve a hacer. Escribir código puro es lo que habilita la optimización, no lo que la impide.

El segundo caso frecuente es leer un ref durante el render, que suele aparecer como un intento de "acordarse" de algo entre renders:

// ❌ Lee y escribe ref.current en pleno render
function Grafico({ datos }) {
  const anterior = useRef(datos);
  const crecio = datos.total > anterior.current.total;   // lectura en render
  anterior.current = datos;                              // escritura en render

  return <Barra valor={datos.total} subiendo={crecio} />;
}
// ✅ El "valor anterior" es estado derivado, y tiene un patrón oficial
function Grafico({ datos }) {
  const [anterior, setAnterior] = useState(datos);
  const [crecio, setCrecio] = useState(false);

  if (anterior !== datos) {           // patrón soportado: ajustar estado en render
    setAnterior(datos);
    setCrecio(datos.total > anterior.total);
  }

  return <Barra valor={datos.total} subiendo={crecio} />;
}
Lo importante del contrato: el incumplimiento es silencioso. Cuando el compilador detecta que no puede probar la pureza de un componente, lo deja tal cual y sigue de largo. No tira un error, no rompe el build, no aparece nada en la consola del navegador. Tu app funciona exactamente igual que antes — simplemente ese componente no recibió ninguna optimización. Por eso lo que viene ahora es la parte operativa del módulo.

RS3.4 El linter: la herramienta que te dice qué quedó afuera

Si el skip es silencioso, necesitás una fuente de verdad sobre qué se optimizó y qué no. Esa fuente es el linter del compilador, que desde eslint-plugin-react-hooks v6 viene integrado en el mismo plugin de siempre: ya no es un paquete aparte.

npm install --save-dev eslint-plugin-react-hooks@latest
npm install --save-dev babel-plugin-react-compiler@latest

La configuración en flat config es de dos líneas:

// eslint.config.js
import reactHooks from "eslint-plugin-react-hooks";

export default [
  // Incluye las reglas clásicas de hooks MÁS los diagnósticos del compilador
  reactHooks.configs.recommended,

  {
    rules: {
      // Subir a error los que te importa que bloqueen el CI
      "react-hooks/immutability": "error",
      "react-hooks/purity": "error",
      "react-hooks/set-state-in-render": "error",
      "react-hooks/refs": "warn",
      "react-hooks/preserve-manual-memoization": "warn",
    },
  },
];
Los nombres exactos de las reglas dependen de la versión del plugin — verificalos con npx eslint --print-config src/App.jsx. El conjunto cubre, a grandes rasgos: pureza del render (purity), mutación de props y estado (immutability), setState en render, uso de refs, globals, componentes definidos dentro de otros componentes (static-components), y respeto de la memoización manual que ya escribiste (preserve-manual-memoization).

Corriéndolo, la salida deja de ser una intuición y pasa a ser una lista:

npx eslint src --format stylish

# src/componentes/TablaUsuarios.jsx
#   12:3  error  This mutates `usuarios`, a value received as a prop.
#                Props are immutable  react-hooks/immutability
#
# src/componentes/Grafico.jsx
#   8:19  warn   Ref values (`anterior.current`) may not be read during
#                render  react-hooks/refs
#
# ✖ 2 problems (1 error, 1 warning)

Cada diagnóstico acá es, literalmente, un componente que no se está optimizando y por qué. Esa es la lista de trabajo del módulo: no "activar el compilador", sino vaciar esa lista.

Además del linter, existe una herramienta de diagnóstico que te da el panorama de todo el proyecto antes de tocar nada:

npx react-compiler-healthcheck@latest
# Salida típica
Successfully compiled 184 out of 203 components.
StrictMode usage not found.
Found no usage of incompatible libraries.
📌 Ese "184 de 203" es tu métrica de adopción. Anotalo antes de empezar y volvé a correrlo después de cada tanda de arreglos. Es el número que hace que "estamos migrando al compilador" deje de ser una sensación y pase a ser un porcentaje que sube. Los 19 que faltan son deuda técnica concreta, con archivo y línea.

El healthcheck también avisa dos cosas que importan mucho: si no tenés StrictMode activo (sin él, muchas impurezas nunca se manifiestan en desarrollo) y si usás librerías incompatibles — típicamente librerías que dependen de que React re-renderice de más, o que mutan valores que les pasás.

RS3.5 Adopción incremental: por directorio y con escape hatch

Nadie activa el compilador en un monorepo de 2.000 componentes en un solo commit. La estrategia sensata tiene tres velocidades.

Velocidad 1 — Modo anotación: solo lo que marcás

El compilador puede arrancar en modo opt-in: no toca nada salvo las funciones que llevan la directiva "use memo".

// vite.config.js
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [
    react({
      babel: {
        plugins: [
          ["babel-plugin-react-compiler", { compilationMode: "annotation" }],
        ],
      },
    }),
  ],
});
function PanelDeMetricas({ series }) {
  "use memo";           // ← solo este componente entra al compilador
  const totales = series.map(agregar);
  return <Grilla datos={totales} />;
}

Velocidad 2 — Por directorio

Más útil en la práctica: activar el compilador para todo, pero acotando el alcance a las carpetas donde ya limpiaste el linter.

// vite.config.js — adopción por rutas
const reactCompilerConfig = {
  sources: (filename) => {
    return (
      filename.includes("/src/features/checkout/") ||
      filename.includes("/src/componentes/ui/")
    );
  },
};

En Next.js el interruptor es de más alto nivel y la configuración del plugin va por debajo:

// next.config.js  (Next.js 15.x — verificá el nombre del flag en tu versión)
module.exports = {
  experimental: {
    reactCompiler: {
      compilationMode: "annotation",   // o true, para todo el proyecto
    },
  },
};

Velocidad 3 — Todo activado, con "use no memo" como válvula

El estado final es el compilador aplicado a todo el proyecto. Para los componentes que todavía no se pueden arreglar, existe la directiva inversa:

function VisorLegacy({ config }) {
  "use no memo";        // ← el compilador ignora este componente
  // TODO(2026-Q4): depende de mutar config.filtros desde un plugin externo.
  // Issue #4471. Sacar esta directiva cuando migremos el plugin.
  config.filtros.push(filtroPorDefecto);
  return <Visor {...config} />;
}
"use no memo" es una deuda, no una solución. Es la contraparte exacta de un // eslint-disable-next-line: legítima como medida temporal, tóxica como costumbre. Tratala igual — siempre con un comentario que diga por qué está y qué la va a sacar. Si tenés 40 en el repo y ninguna tiene fecha, no adoptaste el compilador: lo apagaste de a poco.

Compatibilidad de versiones

El compilador emite llamadas a react/compiler-runtime, que existe nativamente en React 19. Para proyectos en React 17 o 18 hay un runtime de compatibilidad que hay que instalar y declarar:

npm install react-compiler-runtime@latest
// Para React 17 / 18
const reactCompilerConfig = {
  target: "18",        // "17", "18" o "19"
};

RS3.6 Medir en vez de suponer

Activar el compilador y declarar "quedó más rápido" es exactamente el tipo de afirmación que un senior no hace sin datos. Hay tres instrumentos, y conviene usar los tres porque miden cosas distintas.

1. React DevTools: quién se optimizó

Con el compilador activo, los componentes optimizados aparecen en el árbol de DevTools con una insignia "Memo ✨". Es la verificación visual más rápida que existe: abrís el panel, mirás el árbol, y los que no tienen la insignia son los que quedaron afuera. Cruzá esa lista con la salida del linter — deberían coincidir.

2. El Profiler: cuánto se renderiza y cuánto cuesta

El Profiler de React DevTools es la medición que importa. El procedimiento correcto es siempre el mismo, y el orden no es negociable:

1. Elegí una interacción concreta y repetible: "escribir 10 caracteres en el buscador", "tildar tres filas de la tabla". No "usar la app".
2. Grabá esa interacción con el compilador apagado. Anotá: cantidad de commits, duración del commit más lento, y qué componentes aparecen re-renderizando en el flamegraph.
3. Activá el compilador. Repetí exactamente la misma interacción. Anotá los mismos tres números.
4. Compará commits y duración, no sensaciones. Si los commits bajaron pero la duración no, ganaste poco: estabas renderizando de más, pero barato.
Error clásico de medición: perfilar en build de desarrollo y sacar conclusiones de producción. El build de desarrollo tiene checks extra, y con StrictMode los componentes se renderizan dos veces a propósito. Los números absolutos no son comparables con producción. Para comparar A/B está bien (ambos lados tienen el mismo overhead), pero nunca reportes "el render tarda 34 ms" tomado en desarrollo.

3. <Profiler> programático: la medición que no depende de vos

Los números del panel se pierden cuando cerrás la pestaña. Para dejar la medición escrita —y poder detectar regresiones dentro de seis meses— React expone el componente <Profiler>:

import { Profiler } from "react";

function registrar(id, fase, duracionReal, duracionBase) {
  // fase: "mount" | "update" | "nested-update"
  // duracionReal: lo que tardó ESTE commit
  // duracionBase: lo que tardaría sin ninguna memoización
  if (fase === "update" && duracionReal > 16) {
    telemetria.track("render_lento", { id, duracionReal, duracionBase });
  }
}

<Profiler id="ListaDeTareas" onRender={registrar}>
  <ListaDeTareas tareas={tareas} filtro={filtro} onToggle={toggle} />
</Profiler>
La relación entre duracionReal y duracionBase es la métrica más honesta que tenés sobre la memoización: duracionBase es el costo sin ninguna caché. Si después de activar el compilador duracionReal sigue casi igual a duracionBase, la memoización no está evitando trabajo — algo no se está optimizando, o el trabajo estaba en otro lado.

Y para no depender de que alguien mire un dashboard, la medición se puede convertir en un test que falla solo:

import { render, screen, fireEvent } from "@testing-library/react";

let renders = 0;
function TareaEspiada(props: TareaProps) {
  renders++;
  return <Tarea {...props} />;
}

test("cambiar el filtro no re-renderiza las tareas visibles", () => {
  render(<ListaDeTareas tareas={FIXTURE} Item={TareaEspiada} />);
  renders = 0;

  fireEvent.click(screen.getByRole("button", { name: /pendientes/i }));

  // Antes del compilador este número era 40. Si vuelve a subir,
  // alguien rompió la pureza de un componente del camino.
  expect(renders).toBeLessThanOrEqual(12);
});

RS3.7 Qué NO hace el compilador

Esta sección existe porque la expectativa desmedida es la principal causa de decepción con la herramienta. El compilador resuelve una clase de problema: el trabajo repetido de un componente cuyo input no cambió. Todo lo demás sigue siendo tuyo.

Problema¿Lo arregla el compilador?Qué lo arregla
Fetch en cascada (hijo que pide datos recién cuando el padre terminó)❌ No, ni de casualidadLevantar el fetch, prefetch, Suspense con promesas iniciadas arriba (RS4/RS5)
Estado mal ubicado (un input controlado en la raíz del árbol)⚠️ Mitiga el síntoma, no la causaBajar el estado, o colocation (RS6)
Lista de 10.000 filas en el DOM❌ NoVirtualización — el problema es el DOM, no el render de React
Bundle de 3 MB❌ No, lo agranda un pocoCode splitting, tree shaking, revisar dependencias
Un cálculo O(n²) sobre 50.000 items⚠️ Lo hace una sola vez en vez de en cada renderCambiar el algoritmo, o sacarlo a un worker
Layout thrashing (leer offsetHeight en un loop)❌ No, eso es del navegadorBatchear lecturas y escrituras del DOM
Context que dispara todo el árbol⚠️ Parcial: los consumidores puros pueden salteárseloPartir el context, o selector-based state (RS6)
Re-render por props que cambian de verdad❌ No — y hace bienNada: si el input cambió, hay que renderizar
📌 El compilador no reemplaza a RS1. Sigue haciendo falta entender el reconciliador: por qué una key mal elegida remonta un subárbol entero, por qué mover un componente en el árbol destruye su estado, cuándo React puede reutilizar una instancia. El compilador optimiza dentro de las reglas del reconciliador; no las cambia. Si tu problema es que las keys son índices y la lista se reordena, el compilador no te va a salvar de nada.

Y hay un caso donde el compilador es directamente irrelevante: cuando el input sí cambió. Si en cada tecla del buscador el array filtrado es distinto, ninguna caché puede reutilizar nada — el trabajo hay que hacerlo. Ahí la solución es de RS2: useDeferredValue, startTransition, marcar ese trabajo como interrumpible para que el input no se trabe. El compilador evita trabajo innecesario; la concurrencia prioriza el trabajo necesario. Son ejes distintos y se combinan.

RS3.8 ¿Hay que borrar los useMemo que ya tenés?

Es la pregunta que aparece siempre, y la respuesta honesta no es un sí ni un no. Empecemos por el hecho técnico que la mayoría ignora:

💡 El compilador NO elimina tu memoización manual: la respeta. Si escribiste un useMemo, el compilador lo trata como parte del contrato del código y se asegura de preservar esa garantía. Existe una regla del linter dedicada a eso (preserve-manual-memoization) que te avisa cuando tu memo manual está escrito de una forma que el compilador no puede preservar. Es decir: dejar los memos no rompe nada, y no genera doble memoización del mismo valor.

Entonces la pregunta no es "¿es peligroso dejarlos?" sino "¿me conviene sacarlos?". Y ahí la respuesta depende de para qué estaba puesto cada uno:

Para qué estaba el memo¿Borrarlo?Por qué
Evitar que un hijo con memo se re-renderice✅ SíEs exactamente lo que el compilador hace, mejor y con más granularidad
Estabilizar un objeto de props que se pasa hacia abajo✅ SíÍdem: es memoización de identidad, el trabajo del compilador
useCallback de un handler pasado a un hijo✅ SíÍdem
Evitar un cálculo genuinamente caro (parsear, ordenar 50k, comprimir)🟡 Podés, pero no ganás nadaEl compilador lo cubre. Dejarlo documenta la intención: "esto es caro"
Dar identidad referencial a una dependencia de useEffect❌ NoAcá el memo es corrección, no performance. Sacarlo puede disparar el efecto de más
Estabilizar el value de un Context.Provider❌ No, todavía noEs semántica observable por todos los consumidores; verificalo antes de tocarlo
Estabilizar algo que entra a una librería externa (deps de React Query, etc.)❌ NoEl contrato es con la librería, no con React. El compilador no lo conoce

La línea que separa las dos mitades de la tabla es una sola pregunta: ¿este memo existe por velocidad o por corrección?

// ✅ SE PUEDE BORRAR: existía solo para que <Fila /> no se re-renderizara.
function Tabla({ filas, orden }) {
  const ordenadas = useMemo(
    () => [...filas].sort(comparadores[orden]),
    [filas, orden]
  );
  const alClic = useCallback((id) => seleccionar(id), []);

  return ordenadas.map((f) => <Fila key={f.id} fila={f} onClick={alClic} />);
}
// ❌ NO BORRAR: acá el memo es CORRECCIÓN, no performance.
function Buscador({ termino, filtros }) {
  // Si `query` cambia de identidad, el efecto vuelve a pedir al servidor.
  // Sin memo, cada render dispararía un fetch nuevo. Eso es un bug, no lentitud.
  const query = useMemo(
    () => ({ q: termino, ...filtros }),
    [termino, filtros]
  );

  useEffect(() => {
    const ctrl = new AbortController();
    buscar(query, ctrl.signal).then(setResultados);
    return () => ctrl.abort();
  }, [query]);                    // ← la dependencia que el memo protege

  return <Resultados datos={resultados} />;
}
¿Y el compilador no memoiza query igual? En general sí, y muchas veces sacar el useMemo de ese ejemplo funciona perfecto. Pero funciona perfecto no es lo mismo que está garantizado: la memoización del compilador es una optimización, y una optimización puede cambiar entre versiones. Nunca apoyes la corrección de tu programa en una optimización. Si el efecto tiene que dispararse una sola vez, eso se escribe explícito.

La estrategia recomendada

1. No hagas una limpieza masiva. Un PR de "saco 300 useMemo" es imposible de revisar y de bisectar si algo se rompe. Es el peor riesgo/beneficio disponible.
2. Borralos oportunísticamente. Cuando tocás un archivo por otra razón y ves un memo defensivo obvio, sacalo en ese mismo PR. Cero costo marginal.
3. Cuando dudes, dejalo. Un useMemo redundante cuesta unos bytes y una comparación. Un useMemo borrado que garantizaba una identidad cuesta un bug de producción raro de reproducir. La asimetría es enorme.
4. Documentá los que se quedan. Un comentario de una línea —// identidad requerida por el efecto de abajo— evita que el próximo lo borre en su limpieza.

RS3.9 El costo: build, bundle y cuándo empeora

Ninguna herramienta es gratis, y el senior es el que sabe qué está pagando.

Tiempo de build

El compilador agrega una pasada de análisis por archivo. En proyectos medianos el impacto suele ser modesto; en monorepos grandes es real y se nota en CI. Es medible en dos comandos:

# Sin compilador
time npm run build

# Con compilador activado
time npm run build

# Y si querés saber quién se lleva el tiempo dentro del build:
npx vite build --profile
Si el build se vuelve el cuello de botella, acotá sources a los directorios donde la optimización rinde —las pantallas críticas, no los formularios de configuración que se abren dos veces por mes—. La ganancia de perf del compilador no está distribuida uniformemente por el código, así que el costo de build tampoco tiene por qué estarlo.

Tamaño del bundle

El código emitido es más grande que el que escribiste: cada scope reactivo agrega comparaciones y asignaciones. En la práctica el crecimiento reportado ronda un pequeño porcentaje del bundle de la app, y suele quedar bien compensado por la ganancia en runtime — pero si estás peleando por kilobytes en una landing, es un dato que tenés que medir vos:

npx vite-bundle-visualizer
# o, más simple, comparar el output crudo:
ls -la dist/assets/*.js

Memoria en runtime

Cada instancia montada de un componente compilado tiene su array $. En un componente con 12 slots montado 5.000 veces (una tabla virtualizada grande), eso son 60.000 referencias vivas más. Es raro que importe, pero deja de ser raro en listas enormes con componentes complejos.

Cuándo el compilador puede empeorar las cosas

Componentes triviales que se renderizan muchísimo. Si un componente devuelve <span>{texto}</span> y se renderiza 10.000 veces, el costo de las comparaciones de caché puede superar al costo de simplemente ejecutarlo. La memoización nunca es gratis: siempre cambia cálculo por comparación más memoria. Cuando el cálculo es más barato que la comparación, perdés.
Props que cambian de identidad en cada render igual. Si un componente recibe un objeto nuevo siempre —porque el padre no está compilado, o porque el dato viene de una librería que lo recrea— la caché nunca acierta. Pagás todas las comparaciones y no ahorrás ningún cálculo. Es el peor caso posible, y es la razón por la que "use no memo" existe.
Fugas de memoria por retener valores grandes. Si un componente calcula un objeto de varios megabytes y el compilador lo cachea, ese objeto queda vivo mientras el componente esté montado, aunque ya no se use. Sin caché, el GC lo levantaba enseguida.

Los tres casos tienen el mismo antídoto: medir el componente concreto con el Profiler y, si efectivamente empeoró, sacarlo con "use no memo" y dejar el comentario que explique por qué. Es una decisión perfectamente legítima, siempre que esté respaldada por un número.

RS3.10 Cuándo memo manual todavía tiene sentido

El compilador memoiza dentro de un componente y memoiza los elementos JSX que ese componente crea. Pero hay una frontera que no puede cruzar: lo que le llega desde afuera de su alcance.

// El padre NO está compilado (código de terceros, o carpeta excluida
// de `sources`, o un render prop de una librería). Cada render crea
// un objeto `config` nuevo, con identidad nueva.

function VisorCaro({ config, datos }) {
  // El compilador memoiza los cálculos internos... pero todos dependen
  // de `config`, que cambia SIEMPRE. Ninguna caché acierta nunca.
  const escala = calcularEscala(config, datos);
  return <Canvas escala={escala} />;
}

// ✅ memo con comparador propio: acá SÍ agrega algo que el compilador no puede
export default memo(VisorCaro, (prev, next) =>
  prev.datos === next.datos &&
  prev.config.zoom === next.config.zoom &&
  prev.config.tema === next.config.tema
);

Los casos donde memo manual sigue siendo la herramienta correcta:

CasoPor qué el compilador no alcanza
El padre no está compilado (librería, código legacy, carpeta excluida)El compilador optimiza el componente, no a quien lo llama
Necesitás una comparación semántica, no por identidadEl compilador siempre compara con !==; no sabe que dos objetos distintos son "iguales para vos"
Un límite duro del árbol: un subárbol carísimo que querés aislar sí o síEl memo es un contrato explícito y legible; la memoización del compilador es implícita
El componente es la raíz de una isla de terceros (mapa, editor, canvas)Querés control explícito sobre cuándo esa isla se toca
📌 La regla de convivencia. Dejá que el compilador se ocupe de todo lo interno —cálculos, handlers, elementos JSX— y reservá memo manual para fronteras: el punto donde tu código compilado se toca con código que no controlás. Ahí memo deja de ser un parche de performance y pasa a ser documentación ejecutable de un límite arquitectónico.

// ❌ TablaPedidos.jsx — el original
function TablaPedidos({ pedidos, orden, onSeleccionar }) {
  // Muta la prop: .sort() y .reverse() son in place
  pedidos.sort((a, b) => a[orden.campo] > b[orden.campo] ? 1 : -1);
  if (orden.desc) pedidos.reverse();

  // Y encima le agrega un campo calculado a cada objeto del padre
  pedidos.forEach((p) => {
    p.etiqueta = `${p.numero} · ${p.cliente}`;
  });

  const filas = useMemo(
    () => pedidos.map((p) => <Fila key={p.id} pedido={p} />),
    [pedidos, orden]        // ← dependencia mentirosa: `pedidos` es la MISMA
  );                        //    referencia siempre, porque se muta in place

  const seleccionar = useCallback(
    (id) => onSeleccionar(id),
    [onSeleccionar]
  );

  return <tbody onClick={seleccionar}>{filas}</tbody>;
}
El useMemo de este componente estaba roto desde el día uno. Como pedidos se ordena in place, la referencia del array nunca cambia — así que la dependencia [pedidos, orden] no detecta el reordenamiento y filas queda cacheada con el orden viejo. Nadie lo notó porque orden también está en las dependencias y cambia junto. Este es el patrón: el linter del compilador encuentra bugs latentes de correctitud, no solo oportunidades de optimización. 
// ✅ TablaPedidos.jsx — puro, sin memos, listo para el compilador
function TablaPedidos({ pedidos, orden, onSeleccionar }) {
  const ordenados = [...pedidos]
    .sort((a, b) => (a[orden.campo] > b[orden.campo] ? 1 : -1))
    .map((p) => ({ ...p, etiqueta: `${p.numero} · ${p.cliente}` }));

  const finales = orden.desc ? ordenados.reverse() : ordenados;
  //  ↑ .reverse() acá es seguro: `ordenados` es una copia nuestra

  return (
    <tbody>
      {finales.map((p) => (
        <Fila key={p.id} pedido={p} onSeleccionar={onSeleccionar} />
      ))}
    </tbody>
  );
}

Fijate lo que pasó: el componente quedó más corto y más claro, sin useMemo ni useCallback, y ahora sí es memoizable. El compilador va a cachear la copia, el sort, el map y los elementos <Fila /> — con dependencias correctas, cosa que el memo manual no tenía.

El segundo caso, ResumenEstado, es la misma clase de bug con otro disfraz:

// ❌ Muta el objeto que devuelve un hook — igual de prohibido que mutar props
function ResumenEstado({ pedidos }) {
  const resumen = useResumenDePedidos(pedidos);
  resumen.total = resumen.pendientes + resumen.enviados;   // ⛔
  return <Tarjetas datos={resumen} />;
}

// ✅ Derivar sin mutar
function ResumenEstado({ pedidos }) {
  const resumen = useResumenDePedidos(pedidos);
  const total = resumen.pendientes + resumen.enviados;
  return <Tarjetas datos={resumen} total={total} />;
}

Checkpoint — ¿lo tenés claro?

Activaste el compilador, el build pasa sin errores y la app funciona igual que antes. ¿Podés concluir que todo se está optimizando?

No, y es exactamente el error que este módulo intenta evitar. Cuando el compilador no puede probar que un componente cumple las Reglas de React, lo deja sin tocar y sigue de largo, sin emitir ningún error. Un build verde es compatible con que la mitad de tus componentes hayan quedado afuera. Las tres verificaciones que sí sirven: npx react-compiler-healthcheck te da el conteo "N de M compilados", el linter (eslint-plugin-react-hooks v6) te dice archivo y línea de cada motivo, y React DevTools te muestra la insignia Memo ✨ componente por componente. Las tres deberían contar la misma historia; si no coinciden, lo más probable es que el plugin no esté corriendo sobre esos archivos.

Tenés un useMemo que estabiliza un objeto usado como dependencia de un useEffect. ¿Lo borrás?

No. Ese memo no está por performance: está por corrección. Si el objeto cambia de identidad en cada render, el efecto vuelve a ejecutarse en cada render — y si el efecto hace un fetch, abre un socket o dispara un evento de analytics, el resultado no es "un poco más lento": es un bug. En la práctica el compilador probablemente memoice ese objeto igual y todo siga funcionando, pero la memoización del compilador es una optimización, y las optimizaciones no son garantías semánticas: pueden cambiar entre versiones o desactivarse si alguien rompe la pureza del componente. La regla general es nunca apoyar la correctitud de un programa sobre una optimización. Dejalo, y dejale un comentario de una línea diciendo por qué está, para que el próximo no lo borre.

Un componente compilado se sigue renderizando en cada tecla del buscador. ¿Está fallando el compilador?

Casi seguro que no. Hay que separar dos cosas: el compilador evita el trabajo cuyo input no cambió. Si el componente depende del texto del buscador y ese texto cambia con cada tecla, el input sí cambió — hay que renderizar, y ninguna caché puede ni debe evitarlo. Las causas posibles a revisar, en orden: (1) el componente depende de un valor que cambia de verdad, y entonces el problema no es de memoización sino de prioridad, que se resuelve con useDeferredValue o startTransition (RS2); (2) recibe un objeto o función que el padre recrea porque el padre no está compilado — ahí memo manual en la frontera es la respuesta; (3) consume un Context cuyo value cambia de identidad en cada render del provider. El compilador y la concurrencia atacan ejes distintos: uno elimina trabajo innecesario, el otro prioriza el necesario.

Resumen ejecutivo

  • El React Compiler llegó a 1.0 el 7 de octubre de 2025. Sobre React 19.2 es una herramienta de producción: Meta lo usa en features de Instagram y reporta entre 25% y 40% menos re-renders innecesarios sin esfuerzo del desarrollador.
  • No es magia: es análisis estático en build time. Reescribe cada componente insertando una caché por scope reactivo — el equivalente a un useMemo por valor intermedio, con dependencias correctas, incluyendo los elementos JSX, que es donde más rinde.
  • Solo puede optimizar código que cumple las Reglas de React. Cuando no puede probarlas, se saltea el componente en silencio: sin error, sin warning, sin nada.
  • Por eso lo operativo del módulo es la verificación: react-compiler-healthcheck para la métrica "N de M", eslint-plugin-react-hooks v6 para el motivo con archivo y línea, y la insignia Memo ✨ de DevTools para el chequeo visual.
  • La adopción es incremental: modo annotation con "use memo", después por directorio con sources, y finalmente todo con "use no memo" como válvula temporal — siempre con comentario que explique por qué está.
  • No arregla fetch en cascada, estado mal ubicado, listas sin virtualizar, bundles gordos ni algoritmos malos. Y no reemplaza entender el reconciliador (RS1).
  • Sobre los useMemo existentes: el compilador los respeta, no los borra. Sacá los que solo evitaban re-renders; conservá los que garantizan identidad referencial para un efecto, para un Context o para una librería externa. La pregunta es siempre: ¿este memo está por velocidad o por corrección?
  • El costo es real: build más lento, bundle levemente más grande, un array de caché por instancia montada. Puede empeorar componentes triviales renderizados muchísimo, o los que reciben props que cambian de identidad siempre.
  • memo manual sigue teniendo lugar en las fronteras: donde tu código compilado toca código que no controlás, o donde necesitás comparación semántica en vez de por identidad.
  • La conclusión del Worked Example vale más que la herramienta: la mayor parte de la memoización manual acumulada no hacía nada. El compilador funciona tanto como acelerador como auditor.

🧠 Autoevaluación

1. Activaste el React Compiler, el build pasa limpio y no hay warnings en consola. ¿Qué podés afirmar sobre tus componentes?

El skip es silencioso por diseño: si el compilador no puede probar que un componente cumple las Reglas de React, lo deja intacto y sigue. No hay error ni warning, y la app funciona idéntica — simplemente sin optimizar. Las tres fuentes de verdad son npx react-compiler-healthcheck (te da "N de M compilados"), eslint-plugin-react-hooks v6 (te da archivo, línea y motivo) y la insignia Memo ✨ en React DevTools. Un build verde no dice absolutamente nada sobre la cobertura.

2. Tenés un useMemo que estabiliza un objeto query usado como dependencia de un useEffect que hace un fetch. Con el compilador activo, ¿lo borrás?

La pregunta que decide siempre es: ¿este memo está por velocidad o por corrección? Acá el memo garantiza la identidad referencial de la dependencia del efecto. Sin él, si el objeto cambia de identidad en cada render, el efecto vuelve a correr en cada render — y eso no es lentitud, es un fetch de más, un socket reabierto, un evento duplicado. En la práctica el compilador probablemente lo memoice igual, pero eso es una optimización, no una garantía semántica: puede cambiar entre versiones o desactivarse si alguien rompe la pureza del componente. Nunca apoyes la correctitud de un programa sobre una optimización.

3. Un componente compilado tiene un .sort() sobre una prop. ¿Cuál es la consecuencia más importante?

Dos problemas por el precio de uno. .sort() ordena in place: muta el array que te pasó el padre, lo que viola las Reglas de React y hace que el compilador saltee el componente entero. Y como la referencia del array no cambia al mutarlo, cualquier useMemo con [pedidos] en las dependencias nunca detecta el reordenamiento y devuelve el resultado viejo — un bug de correctitud que venía escondido desde antes del compilador. El arreglo es una línea ([...pedidos].sort(...)) y, contra la intuición, no es más lento: la copia queda dentro de un scope reactivo y solo se rehace cuando la prop cambia de verdad.

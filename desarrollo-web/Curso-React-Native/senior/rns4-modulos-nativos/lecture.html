RNS4 — Módulos nativos propios: TurboModules y Codegen

RNS4.0 Por qué este módulo

Arranco con la parte incómoda: el 95% de las veces que creés que necesitás un módulo nativo, no lo necesitás. Hay una librería. Está en npm, la mantiene alguien, resuelve tu problema, y lo resuelve mejor de lo que lo vas a resolver vos en tres días peleándote con Gradle y con un podspec.

Entonces, ¿por qué dedicarle un módulo entero? Por dos razones, y la segunda es la que de verdad te va a pagar el sueldo:

  1. Existe el 5% restante. Un SDK que el proveedor publica solo como binario nativo. Un sensor que ninguna librería expone. Una librería que sí existe pero que quedó en la arquitectura vieja y ya no compila. Un algoritmo cuyo costo en JS es prohibitivo y lo medís, no lo suponés.
  2. Vas a usar módulos nativos de terceros todos los días, y se rompen. El día que una librería crashea solo en release de Android, la diferencia entre un dev mid y uno senior es que el senior abre el .kt, lee, encuentra la línea, y escribe el patch o el PR. No espera seis semanas a que el mantenedor conteste.
💡 La tesis del módulo. Escribir un TurboModule y leer el TurboModule de otra persona son la misma habilidad. Aprendés a escribir uno no porque vayas a escribir muchos, sino porque después de escribir uno dejás de ver node_modules/<lo-que-sea>/android/ como una caja negra. Eso es lo que cambia tu techo como desarrollador de React Native.

Y hay una razón de coyuntura para estudiarlo ahora: el terreno se movió y buena parte de lo que vas a encontrar googleando ya es arqueología. React Native 0.82 eliminó el Bridge y los NativeModules viejos. No están deprecados: no están. Todo tutorial que hable de RCTBridgeModule, de RCT_EXPORT_METHOD sobre el bridge, o de leer NativeModules.MiModulo describe un sistema que ya no existe. Lo que hay hoy es TurboModules + Codegen, y desde 0.86 la Strict TypeScript API. Expo SDK 52 en adelante viene con la Nueva Arquitectura por defecto.

RNS4.1 Cuándo bajar a nativo, y cuándo definitivamente no

Esta es la tabla que deberías tener a mano antes de abrir Android Studio. Es honesta: la mayoría de las filas dicen que no.

Situación¿Nativo?Razón
Una API del sistema operativo sin ningún wrapper mantenidoSíEs la única puerta. No hay alternativa en JS.
Un SDK de un tercero que solo se distribuye como .aar / .xcframeworkSíPagos, biometría de un fabricante, lectores de tarjetas, telemetría de un OEM.
Trabajo CPU-bound imposible en JS, medidoSíProcesar cada frame de la cámara, criptografía pesada, decodificar un formato propietario.
Necesitás un hilo con garantías que JS no tiene (audio en tiempo real)SíEl hilo de JS no da latencia determinista. No es cuestión de optimizar.

Existe la librería pero "no me gusta su API"NoEnvolvela en un módulo de JS de 30 líneas con la API que te gusta.
"Nativo va a ser más rápido", sin haber perfiladoNoCasi siempre el cuello está en el render, en la lista o en la red. Ver RNS2.

El costo real de un módulo nativo no es escribirlo: es mantenerlo. Cada versión de React Native puede romperte la compilación. Cada nueva versión de Android puede cambiar el comportamiento de un permiso. Cada release de Xcode puede pedirte otra cosa. Un módulo nativo propio es un compromiso de años, en dos lenguajes, con dos toolchains, y con dos flotas de dispositivos donde probarlo. Escribilo cuando tengas que hacerlo, no cuando quieras.
📌 Regla de decisión. Antes de la primera línea de Kotlin, escribí en el PR o en el issue: (a) qué API o SDK necesitás exactamente; (b) qué librerías evaluaste y por qué ninguna sirve —con nombre y versión, no "no encontré nada"—; (c) si el motivo es rendimiento, el número medido y el número objetivo; (d) quién lo mantiene cuando vos no estés. Si no podés completar las cuatro, todavía no estás listo para escribirlo.

RNS4.2 Codegen: la especificación en TypeScript manda

Este es el cambio conceptual respecto de la arquitectura vieja, y conviene decirlo con todas las letras.

Antes: escribías el código nativo, lo marcabas con macros para exportarlo, y del lado de JS lo llamabas "a ciegas" a través de un objeto sin tipos. Si le pasabas un string donde esperaba un número, te enterabas en runtime, en un dispositivo, con un mensaje horrible.

Ahora: escribís un contrato en TypeScript, y Codegen —una herramienta que corre en tiempo de build— genera a partir de ese contrato las clases base nativas de ambas plataformas. Vos no escribís la clase: implementás la que se generó. Si tu implementación no coincide con el contrato, no compila.

La analogía. La spec de Codegen es a un módulo nativo lo que un archivo .proto es a gRPC, o lo que un esquema OpenAPI es a un cliente generado. La fuente de la verdad es un archivo de tipos, y las dos puntas se derivan de ahí. La dirección del flujo importa: del TypeScript hacia lo nativo, nunca al revés.

Una spec real

Este es el archivo entero. Es todo lo que hay que escribir para definir el contrato:

// src/NativeProximity.ts
import type { TurboModule } from 'react-native';
import { TurboModuleRegistry } from 'react-native';
import type { EventEmitter } from 'react-native/Libraries/Types/CodegenTypes';

export type ProximityEvent = {
  near: boolean;
  distanceCm: number | null;   // null en iOS: el SO no lo expone
  timestamp: number;
};

export interface Spec extends TurboModule {
  /** ¿El dispositivo tiene sensor de proximidad usable? Barato, cacheado. */
  isAvailable(): boolean;

  /** Enciende el sensor y resuelve con la primera lectura. Toca hardware. */
  start(): Promise<ProximityEvent>;

  /** Apaga el sensor. */
  stop(): void;

  /** Última muestra en memoria. NO toca hardware: por eso puede ser síncrona. */
  getLastSample(): ProximityEvent | null;

  /** Evento tipado: Codegen genera el emisor nativo. */
  readonly onProximityChange: EventEmitter<ProximityEvent>;
}

export default TurboModuleRegistry.getEnforcing<Spec>('NativeProximity');
📌 Las reglas del archivo de spec, que no son negociables.
  • El nombre del archivo tiene que empezar con Native (para TurboModules) o terminar en NativeComponent (para vistas Fabric). Codegen los descubre por el nombre del archivo, no por su contenido.
  • Tiene que exportar una interfaz llamada exactamente Spec que extienda TurboModule.
  • El export default tiene que ser la llamada a TurboModuleRegistry.
  • No pongas lógica en este archivo. Es un contrato, no un módulo. La API "linda" para tus usuarios va en otro archivo que importa a este.

getEnforcing lanza un error claro si el módulo nativo no está registrado. Existe también TurboModuleRegistry.get(), que devuelve null en ese caso: usalo solo cuando el módulo es genuinamente opcional y tenés un camino alternativo escrito, no para "que no explote".

Prender Codegen

Codegen no adivina: se configura en el package.json de tu librería o de tu app.

{
  "name": "react-native-proximity",
  "version": "1.0.0",
  "codegenConfig": {
    "name": "RNProximitySpec",
    "type": "modules",
    "jsSrcsDir": "src",
    "android": {
      "javaPackageName": "com.rnproximity"
    },
    "ios": {
      "componentProvider": {}
    }
  }
}
  • name: el nombre de la librería generada (Android) y del pod de specs (iOS). Por convención termina en Spec.
  • type: "modules" (TurboModules), "components" (vistas Fabric) o "all".
  • jsSrcsDir: la carpeta que Codegen escanea buscando archivos Native*.ts.
  • javaPackageName: el paquete Java/Kotlin donde va a quedar la clase abstracta generada. Tu implementación tiene que vivir en ese mismo paquete o importarla explícitamente.

Corre solo durante el build, pero podés dispararlo a mano para ver qué produce —y deberías, al menos una vez en la vida:

# Genera el código nativo sin compilar la app entera
npx react-native codegen

# Android: queda acá
ls android/app/build/generated/source/codegen/java/com/rnproximity/

# iOS: queda acá (después de pod install)
ls ios/build/generated/ios/

Del lado de Android, lo que sale es una clase abstracta como esta (recortada). Fijate que ya tiene los tipos: no hay un ReadableMap genérico donde debería haber un booleano.

// GENERADO — no lo edites
package com.rnproximity

abstract class NativeProximitySpec(reactContext: ReactApplicationContext) :
    ReactContextBaseJavaModule(reactContext), TurboModule {

  abstract fun isAvailable(): Boolean
  abstract fun start(promise: Promise)
  abstract fun stop()
  abstract fun getLastSample(): WritableMap?

  // el emisor del evento también viene generado
  fun emitOnProximityChange(value: WritableMap) { /* ... */ }
}
Novedad de RN 0.86: la Strict TypeScript API. Hasta ahora Codegen leía un subconjunto acotado de TypeScript con reglas propias, y era fácil escribir tipos válidos para tsc que Codegen no entendía. Con la Strict TypeScript API, los tipos nativos se generan directamente desde el código fuente con la misma semántica de tipos que usa TypeScript, lo que reduce mucho la clase de errores "compila en TS pero Codegen no lo soporta". Si arrancás un módulo hoy, arrancalo sobre esta API.

Android: implementar la clase generada

package com.rnproximity

import android.content.Context
import android.hardware.Sensor
import android.hardware.SensorEvent
import android.hardware.SensorEventListener
import android.hardware.SensorManager
import com.facebook.react.bridge.Arguments
import com.facebook.react.bridge.Promise
import com.facebook.react.bridge.ReactApplicationContext
import com.facebook.react.bridge.WritableMap
import com.facebook.react.module.annotations.ReactModule

@ReactModule(name = ProximityModule.NAME)
class ProximityModule(reactContext: ReactApplicationContext) :
    NativeProximitySpec(reactContext), SensorEventListener {

  companion object {
    // TIENE que coincidir con el string de getEnforcing() en la spec
    const val NAME = "NativeProximity"
  }

  private val sensorManager =
      reactContext.getSystemService(Context.SENSOR_SERVICE) as SensorManager
  private val sensor: Sensor? =
      sensorManager.getDefaultSensor(Sensor.TYPE_PROXIMITY)

  private var lastSample: WritableMap? = null
  private var pendingStart: Promise? = null

  override fun getName() = NAME

  override fun isAvailable(): Boolean = sensor != null

  override fun start(promise: Promise) {
    val s = sensor ?: return promise.reject(
        "E_NO_SENSOR", "Este dispositivo no tiene sensor de proximidad")
    pendingStart = promise
    sensorManager.registerListener(this, s, SensorManager.SENSOR_DELAY_NORMAL)
  }

  override fun stop() {
    sensorManager.unregisterListener(this)
    pendingStart = null
  }

  override fun getLastSample(): WritableMap? = lastSample?.copy()

  override fun onSensorChanged(event: SensorEvent) {
    val cm = event.values[0].toDouble()
    val max = sensor?.maximumRange?.toDouble() ?: cm
    val map = Arguments.createMap().apply {
      putBoolean("near", cm < max)
      putDouble("distanceCm", cm)
      putDouble("timestamp", System.currentTimeMillis().toDouble())
    }
    lastSample = map
    pendingStart?.resolve(map.copy()); pendingStart = null
    emitOnProximityChange(map.copy())   // método generado por Codegen
  }

  override fun onAccuracyChanged(sensor: Sensor?, accuracy: Int) { /* no aplica */ }

  override fun invalidate() {   // se llama cuando muere el contexto de React
    stop()
    super.invalidate()
  }
}
El error de novato #1 en Android: registrar un listener del sistema y no desregistrarlo nunca. Un SensorEventListener, un BroadcastReceiver o un LocationListener vivo mantiene una referencia a tu módulo, que mantiene una referencia al ReactApplicationContext, que mantiene la Activity. Resultado: fuga de memoria que sobrevive a recargas de Fast Refresh y a rotaciones de pantalla. Siempre sobreescribí invalidate() y limpiá ahí.

Falta registrarlo. En la Nueva Arquitectura se hace con un BaseReactPackage, que a diferencia del viejo ReactPackage crea los módulos a demanda —esa es una de las ganancias de arranque de TurboModules: el módulo no se instancia hasta que JS lo pide por primera vez.

package com.rnproximity

import com.facebook.react.BaseReactPackage
import com.facebook.react.bridge.NativeModule
import com.facebook.react.bridge.ReactApplicationContext
import com.facebook.react.module.model.ReactModuleInfo
import com.facebook.react.module.model.ReactModuleInfoProvider

class ProximityPackage : BaseReactPackage() {

  override fun getModule(name: String, ctx: ReactApplicationContext): NativeModule? =
      if (name == ProximityModule.NAME) ProximityModule(ctx) else null

  override fun getReactModuleInfoProvider() = ReactModuleInfoProvider {
    mapOf(
      ProximityModule.NAME to ReactModuleInfo(
        ProximityModule.NAME,          // name
        ProximityModule.NAME,          // className
        false,                         // canOverrideExistingModule
        false,                         // needsEagerInit
        false,                         // isCxxModule
        true                           // isTurboModule
      )
    )
  }
}

iOS: Swift para la lógica, ObjC++ para el puente

Acá viene el detalle que ningún tutorial corto te cuenta: la clase base que genera Codegen para iOS es un protocolo de Objective-C acompañado de una clase C++ (NativeProximitySpecJSI). Swift no puede conformar directamente a esa mezcla. El patrón real, el que usan las librerías serias, es de dos archivos: la lógica en Swift, y un .mm (Objective-C++) finito que hace de puente.

// ios/ProximityCore.swift — toda la lógica vive acá, en Swift limpio
import Foundation
import UIKit

@objc public class ProximityCore: NSObject {

  @objc public static let shared = ProximityCore()

  @objc public var onChange: (([String: Any]) -> Void)?
  private(set) var lastSample: [String: Any]?

  @objc public func isAvailable() -> Bool {
    // iOS no expone el sensor crudo: se prende el monitoreo y se pregunta.
    let device = UIDevice.current
    device.isProximityMonitoringEnabled = true
    let ok = device.isProximityMonitoringEnabled
    device.isProximityMonitoringEnabled = false
    return ok
  }

  @objc public func start() {
    UIDevice.current.isProximityMonitoringEnabled = true
    NotificationCenter.default.addObserver(
      self,
      selector: #selector(proximityChanged),
      name: UIDevice.proximityStateDidChangeNotification,
      object: nil)
    proximityChanged()   // primera muestra inmediata
  }

  @objc public func stop() {
    NotificationCenter.default.removeObserver(self)
    UIDevice.current.isProximityMonitoringEnabled = false
  }

  @objc public func getLastSample() -> [String: Any]? { lastSample }

  @objc private func proximityChanged() {
    let sample: [String: Any] = [
      "near": UIDevice.current.proximityState,
      "distanceCm": NSNull(),          // iOS NO da la distancia. Y está bien.
      "timestamp": Date().timeIntervalSince1970 * 1000
    ]
    lastSample = sample
    onChange?(sample)
  }
}

Y el puente. Es corto a propósito: cuanto más finito el .mm, menos código incómodo tenés que mantener.

// ios/Proximity.mm — Objective-C++, solo pegamento
#import "Proximity.h"
#import "react_native_proximity-Swift.h"   // header generado desde Swift

@implementation Proximity

RCT_EXPORT_MODULE(NativeProximity)

- (NSNumber *)isAvailable {
  return @([ProximityCore.shared isAvailable]);
}

- (void)start:(RCTPromiseResolveBlock)resolve
       reject:(RCTPromiseRejectBlock)reject {
  ProximityCore.shared.onChange = ^(NSDictionary *sample) {
    [self emitOnProximityChange:sample];
  };
  [ProximityCore.shared start];
  resolve([ProximityCore.shared getLastSample]);
}

- (void)stop { [ProximityCore.shared stop]; }

- (NSDictionary *)getLastSample { return [ProximityCore.shared getLastSample]; }

// Esto es lo que conecta la clase con el JSI generado por Codegen
- (std::shared_ptr<facebook::react::TurboModule>)getTurboModule:
    (const facebook::react::ObjCTurboModule::InitParams &)params {
  return std::make_shared<facebook::react::NativeProximitySpecJSI>(params);
}

@end
Este puente de ObjC++ es exactamente el dolor que la Expo Modules API elimina (RNS4.7). Si tu módulo no necesita control fino sobre el JSI, ese es un argumento fuerte para no escribir un TurboModule puro.

Registro y autolinking

En Android hay que sumar el ProximityPackage. Si es una librería publicada, el autolinking lo hace por vos leyendo el package.json: no toques MainApplication.kt. En iOS, RCT_EXPORT_MODULE(NativeProximity) registra el módulo con ese nombre y CocoaPods hace el resto.

# Después de tocar la spec o el codegenConfig, SIEMPRE:
cd ios && bundle exec pod install && cd ..

# Y en Android, cuando el generado quedó viejo:
cd android && ./gradlew clean && cd ..

# Verificar que el módulo quedó registrado, desde la app:
# console.log(require('./src/NativeProximity').default.isAvailable())
"Cambié la spec y no pasa nada". El 90% de las veces es que Codegen no volvió a correr. La spec es una entrada de build, no un archivo que Metro recargue: Fast Refresh no la mira. Después de tocar un archivo Native*.ts o el codegenConfig, hay que recompilar la app nativa, y en iOS correr pod install otra vez.

RNS4.4 Tipos soportados: qué cruza el borde y qué no

JSI eliminó el bridge JSON asíncrono, pero no eliminó la conversión. Cuando pasás un objeto de JS a Kotlin, alguien construye un ReadableMap; cuando volvés, alguien construye un objeto de JS. Eso cuesta, y cuesta proporcional al tamaño del dato. La frase "con JSI ya no hay serialización" es marketing: lo que desapareció es el batching asíncrono, no la traducción.

TypeScriptKotlinSwift / ObjCNota
booleanBooleanNSNumber / Bool—
numberDoubleNSNumber / DoubleSiempre double. No hay enteros.
stringStringNSString—
objeto tipadoReadableMap / WritableMapNSDictionaryDefinilo con un type, no con Object.
Array<T>ReadableArrayNSArrayHomogéneo. Nada de tuplas mixtas.
Promise<T>Promiseresolve / reject blocksEl método pasa a ser asíncrono.
() => voidCallbackRCTResponseSenderBlockSe puede llamar una sola vez.
T | nulltipo ? nullableopcional / NSNullModelá el vacío explícitamente.
EventEmitter<T>emitOnX(...)[self emitOnX:...]Codegen genera el emisor tipado.

Y lo que no cruza, por más que TypeScript te deje escribirlo:

  • Date — pasá milisegundos como number o un ISO-8601 como string.
  • Map, Set, bigint, symbol, unknown.
  • Uniones arbitrarias (string | number). Las uniones de literales de string tienen soporte parcial; si dudás, usá string y validá.
  • Funciones dentro de objetos, instancias de clases, tipos recursivos.
  • undefined como valor distinto de null. Del otro lado hay un solo vacío.
  • any — Codegen lo acepta y te destruye exactamente el beneficio por el que existe. Si ves un any en una spec, es una revisión de código fallida.
La trampa de los números que muerde en producción. Un number de JS es un double IEEE-754: los enteros exactos llegan hasta 253. Si tu SDK nativo devuelve un ID de 64 bits (un Long de Kotlin, un Int64 de Swift), vas a perder precisión en silencio y dos registros distintos van a terminar con el mismo ID. No hay excepción, no hay warning. Los identificadores de 64 bits se pasan como string. Siempre. 
// MAL: el ID se corrompe al cruzar
map.putDouble("transactionId", tx.id.toDouble())     // 9007199254740993 -> 9007199254740992

// BIEN: el borde es texto, la precisión se conserva
map.putString("transactionId", tx.id.toString())

La otra decisión de diseño en el borde es el tamaño. Si tu módulo produce datos grandes —imágenes, audio, un buffer de sensores a 200 Hz— pasarlos como Array<number> es un desastre: se construye un array de JS elemento por elemento. Las tres salidas sanas:

// 1) Ruta de archivo: el nativo escribe, JS solo recibe un string
processVideo(inputPath: string): Promise<string>;

// 2) Handle opaco: el dato queda en memoria nativa, JS maneja un identificador
openSession(): Promise<string>;
readChunk(sessionId: string, n: number): Promise<string>;  // base64 acotado
closeSession(sessionId: string): void;

// 3) Agregar del lado nativo: no mandes 10.000 muestras, mandá la estadística
getWindowStats(ms: number): Promise<{ min: number; max: number; avg: number }>;
📌 Diseñá la spec para minimizar el tráfico, no para ser cómoda. Un buen módulo nativo tiene pocas llamadas que hacen mucho. Un módulo que expone getX(), getY(), getZ() por separado y que la app llama en un loop es un módulo mal diseñado, por más que cada llamada individual sea rápida.

RNS4.5 Síncrono vs asíncrono: el arma cargada de JSI

Con el Bridge viejo, todo era asíncrono: no había forma de que JS esperara una respuesta nativa. JSI cambió eso: ahora una llamada nativa puede ser síncrona, y devolver el valor en la misma expresión.

La regla que lo decide es simple y está en la spec: si el método devuelve Promise<T>, Codegen lo genera asíncrono; si devuelve T directamente, lo genera síncrono.

export interface Spec extends TurboModule {
  getDeviceModel(): string;                  // SÍNCRONO
  readFile(path: string): Promise<string>;   // ASÍNCRONO
}

Que se pueda no significa que convenga. Una llamada síncrona bloquea el hilo de JS mientras el código nativo corre. Si el hilo de JS está bloqueado, no procesa eventos, no corre efectos, no responde a toques y —si estás animando desde JS— perdés frames. Con un presupuesto de 16,6 ms por frame, un método síncrono de 40 ms te come dos frames y medio, todos los que se llame.

El anti-patrón concreto. "Es un archivo chiquito, lo leo síncrono así el código queda más lindo": 
// MAL — es I/O de disco en el hilo de JS
const config = NativeConfig.readConfigSync();  // 8 ms en un iPhone nuevo,
                                               // 60 ms en un Android de gama baja
El "archivo chiquito" en el dispositivo del percentil 95 de tus usuarios está en un almacenamiento eMMC lento, con la app compitiendo con otras cinco. Medí en ese dispositivo, no en el tuyo.
Usá SÍNCRONO cuando…Usá ASÍNCRONO cuando…
El valor ya está en memoria (una constante, un flag, la última muestra cacheada)Hay I/O: disco, red, base de datos
El costo medido es de microsegundos, no de milisegundosSe enciende o se despierta hardware (cámara, sensor, GPS, NFC)
Lo necesitás durante el primer render y no querés un estado "cargando"Hay que saltar de hilo (muchas APIs nativas exigen el main thread)
Es configuración leída una sola vez en el arranqueEl costo depende del tamaño de la entrada
El fallo es imposible (no hay nada que rechazar)Puede fallar y querés un reject con código de error
📌 El criterio de una línea. Síncrono es aceptable cuando la respuesta a "¿puede tardar más de un milisegundo en el peor teléfono que soporto?" es no, con certeza. Ante la duda, Promise. Convertir un método síncrono en asíncrono después es un cambio breaking para todos tus usuarios; al revés no molesta a nadie.

Y una aclaración que se malinterpreta seguido: una llamada síncrona no es "más rápida". El trabajo nativo tarda lo mismo. Lo único que cambia es quién espera: en la asíncrona espera la promesa y el hilo de JS sigue trabajando; en la síncrona espera el hilo de JS entero. Elegís dónde poner el costo, no lo eliminás.

RNS4.6 Fabric Components vs TurboModules

Son dos mecanismos distintos y la gente los mezcla todo el tiempo. La regla es corta: si dibuja píxeles, es Fabric; si es un servicio, es TurboModule.

La spec de un componente Fabric se ve así. Notá que los tipos numéricos se declaran con precisión, cosa que en TurboModules no hace falta:

RNS4.7 Expo Modules API: el 80% del resultado con el 20% del código

La Expo Modules API es una capa por encima de la Nueva Arquitectura que te deja escribir el módulo en Swift y Kotlin puros, con un DSL declarativo, sin spec de Codegen, sin codegenConfig y —esto es lo grande— sin una sola línea de Objective-C++.

No hace falta usar el "managed workflow" de Expo. La Expo Modules API funciona en cualquier proyecto de React Native que tenga instalado el paquete expo. Es una confusión muy repetida y hace que equipos se coman semanas de ObjC++ sin necesidad.

El mismo módulo de proximidad, entero, en Kotlin:

// android/src/main/java/expo/modules/proximity/ProximityModule.kt
package expo.modules.proximity

import expo.modules.kotlin.modules.Module
import expo.modules.kotlin.modules.ModuleDefinition

class ProximityModule : Module() {
  private val core by lazy { ProximityCore(appContext.reactContext!!) }

  override fun definition() = ModuleDefinition {
    Name("Proximity")

    Events("onProximityChange")

    Function("isAvailable") { core.isAvailable() }          // síncrona

    AsyncFunction("start") {                                 // asíncrona
      core.start { sample -> sendEvent("onProximityChange", sample) }
      core.lastSample()
    }

    Function("stop") { core.stop() }

    Function("getLastSample") { core.lastSample() }

    OnDestroy { core.stop() }
  }
}

Y en Swift:

// ios/ProximityModule.swift
import ExpoModulesCore

public class ProximityModule: Module {
  private let core = ProximityCore()

  public func definition() -> ModuleDefinition {
    Name("Proximity")
    Events("onProximityChange")

    Function("isAvailable") { core.isAvailable() }

    AsyncFunction("start") { () -> [String: Any]? in
      core.onChange = { [weak self] sample in
        self?.sendEvent("onProximityChange", sample)
      }
      core.start()
      return core.lastSample
    }

    Function("stop") { core.stop() }
    Function("getLastSample") { core.lastSample }

    OnDestroy { core.stop() }
  }
}

RNS4.8 Testear un módulo nativo (y mockearlo desde JS)

Un módulo nativo tiene tres superficies de prueba, y son independientes. Confundirlas es la razón por la que hay librerías con el badge de 100% de cobertura que crashean en el primer dispositivo real.

La condición previa para poder testear: mantené la clase que hereda del spec generado finita y poné la lógica en una clase común sin dependencias de React Native. Esa clase sí se testea sin emulador.

// ProximityCoreTest.kt — JUnit puro, sin React Native, corre en milisegundos

  @Test
  fun `near es false cuando la lectura iguala al rango maximo`() {

  }
}

RNS4.9 Distribución: publicar, versionar y sobrevivir a los upgrades de RN

No armes el esqueleto a mano. El generador oficial te deja el codegenConfig, el podspec, el build.gradle, la app de ejemplo y la configuración de react-native-builder-bob ya resueltos:

# elegí: "Turbo module" (Kotlin/Swift) o "Expo module"

Las tres cosas que hay que entender del empaquetado:

1. El codegenConfig viaja en el paquete publicado

Codegen corre en el proyecto del consumidor, no en el tuyo. Por eso el codegenConfig y la carpeta src/ con los archivos Native*.ts tienen que estar en el tarball de npm. Si tu files del package.json los excluye, la librería instala bien y falla al compilar con un error críptico sobre una clase que no existe.

{
  "files": ["src", "lib", "android", "ios", "*.podspec", "!**/__tests__"],
  "peerDependencies": {
    "react": "*",
    "react-native": "*"
  }
}
react-native va en peerDependencies, nunca en dependencies. Si lo ponés como dependencia normal, el consumidor termina con dos copias de React Native en su árbol y obtiene errores imposibles de diagnosticar ("Invalid hook call", dos instancias del registro de módulos). Lo mismo vale para react y para expo-modules-core.

2. Alineá las versiones del toolchain con las del host

# android/build.gradle — tomá la versión de Kotlin del proyecto que te consume,
# con un default por si no la define. NUNCA la fijes a la tuya.

      : "2.0.21"
}

android {
  compileSdkVersion safeExtGet("compileSdkVersion", 35)
  defaultConfig { minSdkVersion safeExtGet("minSdkVersion", 24) }
}

Y en iOS, el podspec tiene una sola línea imprescindible: la que engancha las dependencias de la Nueva Arquitectura sin que las escribas a mano.

RNS4.10 Depurar el módulo nativo de otro

Esta es, con diferencia, la habilidad de este módulo que más veces vas a usar. El escenario típico: una librería anda perfecto en debug y crashea en el build de release de Android. La app la usan 40.000 personas. El issue de GitHub tiene 6 meses.

El método, en orden, sin saltear pasos:

RNS4.11 Worked example: un sensor que ninguna librería te da

El caso: una app de telemedicina necesita apagar la pantalla cuando el usuario se lleva el teléfono a la oreja durante una consulta, y además registrar los eventos de proximidad para detectar llamadas interrumpidas. Necesitamos el sensor de proximidad.

Paso 0 — Verificar que hace falta (el paso que todos saltean)

Antes de escribir nada, la búsqueda:

  • expo-sensors expone acelerómetro, giroscopio, magnetómetro, barómetro, podómetro. Proximidad no.
  • react-native-proximity existe: última publicación de hace años, escrito sobre RCTBridgeModule. En RN 0.82+ no compila, porque el Bridge ya no está.
  • Hay dos forks; ninguno migrado, ninguno con commits en los últimos doce meses.
📌 Este es el escenario más común de 2026, y hay que nombrarlo: la librería existe, pero pertenece a la arquitectura muerta. La decisión no es "escribo un módulo nativo desde cero" contra "uso la librería": es "migro el fork" contra "escribo uno chico y correcto". Acá el módulo son ~150 líneas, la librería vieja arrastra código de compatibilidad que ya no aplica, y el fork tendría que pasar por mi revisión igual. Escribo uno propio, y lo documento en el PR con estas tres viñetas.

Paso 1 — Diseñar el contrato antes que el código

Acá está la decisión de diseño de verdad, y es de modelado, no de programación. Las dos plataformas no dan lo mismo:

AndroidiOS
APISensorManager + TYPE_PROXIMITYUIDevice.proximityState
Qué devuelveCentímetros (aunque la mayoría de los teléfonos son binarios)Solo un booleano
Rango máximoSe consulta con maximumRangeNo existe el concepto
DisponibilidadEl sensor puede no existirDepende del modelo; se detecta probando

Tres opciones y sus consecuencias:

  1. Exponer solo el mínimo común (near: boolean). API limpia, pero tirás información que Android sí tiene y algún día alguien la va a necesitar.
  2. Exponer todo y que el consumidor lo resuelva con Platform.OS. Traslada la complejidad a cada punto de uso: el peor lugar posible.
  3. Exponer el común como no nullable y lo específico como nullable. near: boolean siempre; distanceCm: number | null, con null en iOS.
📌 Elegimos la 3, y esa es la lección transferible. El tipo number | null hace que la diferencia de plataformas sea visible en el sistema de tipos: TypeScript obliga a manejar el caso null en el punto de uso, y nadie puede olvidarse. La spec es el lugar donde decidís cuánta diferencia de plataforma se filtra hacia arriba. Un as number ahí es una decisión de arquitectura tomada con un casteo.

Paso 2 — La spec

Es exactamente la de RNS4.2, y ahora se entiende cada línea:

// src/NativeProximity.ts
import type { TurboModule } from 'react-native';
import { TurboModuleRegistry } from 'react-native';
import type { EventEmitter } from 'react-native/Libraries/Types/CodegenTypes';

export type ProximityEvent = {
  near: boolean;              // común a las dos plataformas
  distanceCm: number | null;  // null en iOS: la diferencia es explícita
  timestamp: number;          // ms desde epoch, NO un Date
};

export interface Spec extends TurboModule {
  isAvailable(): boolean;                 // síncrono: valor cacheado
  start(): Promise<ProximityEvent>;       // async: despierta hardware
  stop(): void;                            // síncrono: no espera nada
  getLastSample(): ProximityEvent | null;  // síncrono: memoria
  readonly onProximityChange: EventEmitter<ProximityEvent>;
}

export default TurboModuleRegistry.getEnforcing<Spec>('NativeProximity');

Paso 3 — La decisión síncrono / asíncrono, con el argumento

Este es el punto que en una entrevista senior distingue una respuesta memorizada de una razonada. Método por método:

MétodoDecisiónArgumento
isAvailable()SíncronoEn Android es un getDefaultSensor() que devuelve un objeto ya cargado por el sistema: nanosegundos. Además se llama durante el primer render para decidir si mostrar la feature, y una promesa ahí obligaría a un estado "cargando" para algo que no carga nada.
start()AsíncronoRegistra un listener y espera la primera muestra del hardware. Ese tiempo lo decide el sensor: en gama baja se midieron hasta 300 ms. Síncrono acá serían ~18 frames perdidos. Además puede fallar (sin sensor) y necesitamos un reject con código.
stop()Síncrono, y devuelve voidDesregistrar un listener no espera nada. Y es importante que sea síncrono: se llama en el cleanup de un useEffect, que no puede esperar promesas. Un stop() asíncrono es una fuga esperando a pasar.
getLastSample()SíncronoDevuelve un objeto que ya está en memoria nativa. El único costo es construir el mapa: microsegundos. Ni siquiera toca el sensor.
EventosPushEl hardware decide cuándo hay novedad. Hacer polling desde JS a 60 Hz para leer un valor que cambia dos veces por minuto es desperdiciar batería y hilo de JS.
💡 La heurística detrás de toda la tabla. Síncrono es para leer estado que ya existe. Asíncrono es para provocar que algo pase. Si el método hace que el mundo cambie —enciende, escribe, pide, conecta— devolvé una promesa. Si solo cuenta cómo está el mundo ahora mismo, puede ser síncrono.

Paso 4 — Android en Kotlin

La implementación completa está en RNS4.3. Lo que importa acá es la separación: la clase ProximityModule es puro pegamento con React Native, y la lógica de decidir near vive en una clase que se testea sin emulador.

// ProximityCore.kt — sin dependencias de React Native: testeable con JUnit
class ProximityCore(private val maxRangeCm: Double) {
  private var last: Sample? = null
  var onChange: ((Sample) -> Unit)? = null

  data class Sample(val near: Boolean, val distanceCm: Double?, val timestamp: Long)

  fun onRawValue(cm: Double) {
    val s = Sample(
      near = cm < maxRangeCm,     // la regla: "cerca" es cualquier cosa bajo el rango
      distanceCm = cm,
      timestamp = System.currentTimeMillis())
    last = s
    onChange?.invoke(s)
  }

  fun lastSample(): Sample? = last
  fun stop() { last = null; onChange = null }   // no servir datos viejos
}

Paso 5 — iOS en Swift

Mismo criterio: ProximityCore.swift (RNS4.3) tiene la lógica y el .mm es un puente de veinte líneas. Y fijate el detalle de modelado: distanceCm se llena con NSNull(), no con 0.

El bug sutil que casi se cuela. La tentación era poner "distanceCm": 0 en iOS "para que el tipo sea siempre número". Habría sido un dato falso: cero centímetros significa "el objeto está tocando el sensor", que es exactamente lo contrario de "no sé". Cualquier consumidor que hiciera if (distanceCm < 1) tendría un falso positivo permanente en todos los iPhone. La ausencia de dato se modela como ausencia, nunca como un valor por defecto plausible.

Paso 6 — La API que consume la app

La spec no es la API pública. Encima va un hook que resuelve el ciclo de vida, que es donde están los bugs reales:

// src/useProximity.ts
import { useEffect, useState } from 'react';
import NativeProximity, { type ProximityEvent } from './NativeProximity';

export function useProximity(enabled: boolean = true) {
  const [sample, setSample] = useState<ProximityEvent | null>(null);
  const [error, setError] = useState<Error | null>(null);

  useEffect(() => {
    if (!enabled || !NativeProximity.isAvailable()) return;

    let cancelado = false;
    const sub = NativeProximity.onProximityChange((e) => {
      if (!cancelado) setSample(e);
    });

    NativeProximity.start()
      .then((first) => { if (!cancelado) setSample(first); })
      .catch((e) => { if (!cancelado) setError(e as Error); });

    return () => {
      cancelado = true;      // evita el setState sobre un componente desmontado
      sub.remove();          // primero el listener
      NativeProximity.stop();// después el hardware: síncrono, corre siempre
    };
  }, [enabled]);

  return {
    near: sample?.near ?? false,
    distanceCm: sample?.distanceCm ?? null,   // null en iOS, y el tipo lo dice
    available: NativeProximity.isAvailable(),
    error,
  };
}
📌 El orden del cleanup no es cosmético. Primero sub.remove(), después stop(). Al revés, hay una ventana en la que el sensor todavía puede emitir un último evento hacia un listener vivo cuyo componente ya no existe. En Android eso es un warning; en iOS, con un self mal capturado, es un crash.

Checkpoint — ¿lo tenés claro?

¿Por qué la spec de TypeScript es la fuente de la verdad y no la implementación nativa?

Porque el contrato entre JS y nativo tiene que existir en un solo lugar, y ese lugar es el que las dos puntas pueden verificar. Codegen genera desde la spec las clases base de Android e iOS: si tu Kotlin no implementa un método declarado, o lo implementa con otra firma, el build falla. En la arquitectura vieja el contrato era implícito —vivía en la cabeza de quien escribió el módulo— y las discrepancias aparecían en runtime, en un dispositivo, como un error incomprensible. Además de la seguridad de tipos, tener la spec como fuente única te da una segunda cosa: leer src/Native*.ts de cualquier librería te dice en treinta segundos exactamente qué expone y con qué tipos, sin abrir código nativo.

Tu módulo tiene un método síncrono que anda perfecto en tu iPhone y produce jank en Android de gama baja. ¿Qué revisás y qué cambiás?

Primero medís lo que tarda el método en ese dispositivo, no en el tuyo: un log con timestamps a cada lado de la llamada nativa alcanza. Si supera el orden del milisegundo, el diagnóstico es el del módulo: una llamada síncrona bloquea el hilo de JS, y con 16,6 ms de presupuesto por frame cualquier cosa que tarde decenas de milisegundos te hace perder frames cada vez que se llama. La corrección es cambiar la firma de la spec a Promise<T>, lo que hace que Codegen lo genere asíncrono. Ojo: eso es un cambio breaking —major en semver—, y esa es justamente la razón para elegir asíncrono cuando dudás: pasar de asíncrono a síncrono después no le molesta a nadie, al revés rompe a todos tus usuarios. Alternativa sin romper la API si el valor lo permite: calcularlo de forma anticipada en el arranque y que el método síncrono solo lea la caché.

Una librería de terceros anda en debug y crashea en release de Android. Antes de abrir un issue, ¿qué hacés?

Uno: consigo el stack trace nativo con adb logcat, porque el error rojo de React Native es el síntoma, no la causa. Dos: si dice ClassNotFoundException o NoSuchMethodError, la hipótesis principal es R8/ProGuard —que no corre en debug, y por eso el bug aparece recién en release— borrando u ofuscando una clase que la librería resuelve por reflexión; se confirma agregando una regla -keep para el paquete de la librería y recompilando. Tres: leo el código en node_modules/<lib>/android/, que está en mi disco y no es una caja negra, empezando por la spec en src/Native*.ts. Cuatro: intento reproducirlo en la app de ejemplo de la librería; si ahí no falla, el problema es la interacción con mi proyecto. Recién con todo eso abro un issue —que ahora incluye stack trace, causa probable y reproducción— o directamente el PR. Mientras tanto me destrabo con patch-package.

Resumen ejecutivo

  • El 95% de las veces no necesitás un módulo nativo: hay librería. Este módulo es para el 5% restante y, sobre todo, para saber leer y arreglar los módulos de terceros que ya usás.
  • El Bridge y los NativeModules viejos no existen desde RN 0.82. Todo lo que encuentres sobre RCTBridgeModule es arqueología.
  • Codegen invierte la dirección: escribís la spec en TypeScript y se generan las clases base nativas de ambas plataformas. Si tu implementación no coincide, no compila. RN 0.86 suma la Strict TypeScript API.
  • El archivo de spec tiene reglas rígidas: nombre que empieza con Native, interfaz Spec, y codegenConfig en el package.json —que además tiene que viajar en el paquete publicado.
  • Un TurboModule son cinco piezas: spec, clase generada, Kotlin, Swift + puente ObjC++, y registro. En iOS Swift no puede conformar al spec generado: siempre hay un .mm en el medio.
  • JSI no eliminó la serialización, eliminó el batching asíncrono. Los datos grandes se pasan por ruta de archivo, handle opaco o agregación nativa; los IDs de 64 bits, como string, siempre.
  • Síncrono para leer estado que ya existe; asíncrono para provocar que algo pase. Una llamada síncrona bloquea el hilo de JS y no acelera nada: solo mueve quién espera. Ante la duda, Promise: pasar a síncrono después no rompe a nadie, al revés sí.
  • Fabric Components son vistas en el árbol de React con layout de Yoga; TurboModules son servicios. Si dibuja píxeles, Fabric.
  • La Expo Modules API resuelve el caso común con ~40% menos código y cero ObjC++, y funciona en proyectos de RN sin managed workflow. Cede control fino del JSI y suma un acoplamiento de versiones. Para envolver un SDK o una API del sistema, suele ser la respuesta correcta.
  • Testeá en tres capas: lógica nativa con JUnit/XCTest, API de JS con Jest sobre un mock del archivo de la spec, e integración en dispositivo real. Jest en verde no dice nada del código nativo. Si publicás una librería, publicá su mock.
  • Depurar módulos de terceros es una habilidad concreta: logcat primero, código en node_modules después —está en tu disco—, reproducir en la app de ejemplo, patch-package para destrabarte y PR upstream. R8 no corre en debug: probá el release antes de publicar.

🧠 Autoevaluación

1. Tu módulo tiene dos métodos: uno devuelve la última muestra ya cacheada en memoria nativa, y otro enciende el sensor y espera la primera lectura (~200 ms en gama baja). ¿Cómo los declarás en la spec?

Síncrono es para leer estado que ya existe; asíncrono para provocar que algo pase. El cacheado son microsegundos y encima suele necesitarse durante el primer render. El que espera al hardware, síncrono, bloquearía el hilo de JS ~200 ms: con 16,6 ms por frame son unos 12 frames perdidos cada vez. Y además puede fallar, así que necesitás un reject con código de error. Una llamada síncrona no es "más rápida": el trabajo nativo tarda lo mismo, solo cambia quién espera.

2. Una librería nativa de terceros funciona perfecto en debug y crashea con ClassNotFoundException solo en el build de release de Android. ¿Cuál es la primera hipótesis?

La pista decisiva es "solo en release": R8 no corre en builds de debug. Si la spec estuviera mal, no compilaría en ninguno de los dos modos; si faltara un permiso, fallaría igual en debug. R8 elimina y renombra clases que "nadie usa" según el análisis estático, y las que se resuelven por reflexión —muy comunes en el registro de módulos nativos— son invisibles para ese análisis. Se confirma en dos minutos agregando -keep class com.lib.** { *; } y recompilando. De ahí la regla: probá el build de release antes de publicar.

3. En la Nueva Arquitectura, ¿cuál es la fuente de la verdad del contrato entre JS y el código nativo?

La dirección importa: del TypeScript hacia lo nativo. Codegen lee los archivos Native*.ts declarados en codegenConfig y produce una clase abstracta en Android y un protocolo ObjC más glue C++ en iOS. Tu implementación hereda de lo generado, así que una discrepancia de firma rompe el build en vez de aparecer en runtime en un dispositivo. Ese es el cambio conceptual respecto de la arquitectura vieja, donde el contrato era implícito. Como efecto secundario práctico: leer el src/Native*.ts de cualquier librería te dice en treinta segundos qué expone y con qué tipos.

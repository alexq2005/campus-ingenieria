RNS3 — Animaciones y gestos a 60fps

RNS3.0 Por qué este módulo

Una animación a 45fps no se ve "un poco más lenta". Se ve rota. El ojo humano no cuenta cuadros, pero detecta con una precisión brutal la irregularidad: si de cada tres cuadros uno tarda el doble, no percibís "menos fluidez", percibís un tirón. Y un tirón en el momento en que el usuario tiene el dedo apoyado en la pantalla es de las cosas que más rápido hacen que una app se sienta barata.

Lo desconcertante es que la animación funciona. No hay error, no hay warning, no hay excepción. El código es correcto. Simplemente se ejecuta en el lugar equivocado.

💡 La tesis del módulo. La calidad de una animación en React Native casi nunca depende de la animación. Depende de qué hilo la ejecuta. Si depende del hilo de JavaScript, hereda todo lo que ese hilo tenga que hacer: tu render, tu deserialización de JSON, tu reduce sobre 4.000 elementos. Si corre en el hilo de UI, es indiferente a todo eso. Todo el resto del módulo —worklets, shared values, Gesture Handler— son herramientas para lograr ese traslado.

Empecemos por el número. A 60fps tenés 16,67 milisegundos por cuadro para hacer todo: procesar el toque, calcular la posición nueva, aplicarla a la vista y componer la pantalla. A 120fps —y prácticamente todo gama media/alta desde 2023 tiene panel de 120 Hz— tenés 8,33 ms.

// El presupuesto por cuadro, sin misterio
const presupuesto = (hz: number) => 1000 / hz;

presupuesto(60);   // 16.67 ms
presupuesto(90);   // 11.11 ms
presupuesto(120);  //  8.33 ms

// Si un frame tarda 20 ms en una pantalla de 60 Hz, no perdés 3,33 ms:
// perdés el cuadro entero. El sistema muestra el anterior otra vez
// y el próximo llega a los 33 ms. Un salto visible de 2 cuadros.
📌 Los cuadros no se pierden "un poco". El compositor del sistema operativo tiene una cita fija con la pantalla (el vsync). Si tu contenido no está listo cuando llega esa cita, no se muestra tarde: no se muestra. Por eso el costo de pasarse 1 ms del presupuesto es idéntico al de pasarse 15 ms. No hay degradación gradual, hay un umbral.

RNS3.1 El problema de fondo: quién ejecuta tu animación

Acá hace falta una aclaración de época, porque la explicación que vas a encontrar en la mitad de los blogs describe una arquitectura que ya no existe. Durante años la respuesta canónica era "la animación pasa por el puente y el puente es lento". Con la Nueva Arquitectura —que viste en RNS1 y es el default desde RN 0.76, con el modo legacy ya eliminado en RN 0.82— el puente no existe. JSI permite que JavaScript llame funciones nativas de forma sincrónica, sin serializar nada a JSON.

Y sin embargo el problema sigue ahí. Porque nunca fue realmente el puente: era, y es, que el hilo de JavaScript es uno solo y hace muchas cosas. Eliminar la serialización bajó el costo de cada cruce, pero no multiplicó el hilo. Si tu animación necesita que JS calcule una posición 60 veces por segundo, y JS está ocupado 120 ms haciendo otra cosa, tu animación se congela 120 ms. Con puente o sin puente.

Los hilos que te importan hoy son estos:

HiloQué haceQuién lo bloquea
JSTu código React: render, efectos, handlers, fetch, parseoVos. Un map caro, un JSON grande, un render en cascada
UI (main)Dibuja las vistas nativas, procesa los toques, corre el compositorMedición de layout costosa, imágenes gigantes, vistas nativas pesadas
UI runtime (Reanimated)Ejecuta worklets: un segundo runtime de JS montado sobre el hilo de UIUn worklet lento — y ahí sí bloqueás el dibujo
Shadow / backgroundCalcula layout con Yoga, arma el árbol de sombraÁrboles muy profundos, cambios de layout por cuadro

El experimento que resuelve la discusión en diez segundos es este: bloquear el hilo de JS a propósito y mirar qué le pasa a la animación.

// Ponelo detrás de un botón, en desarrollo, y tocalo mientras algo se anima.
function bloquearJS(ms = 800) {
  const fin = Date.now() + ms;
  while (Date.now() < fin) {
    // ocupación deliberada del hilo de JS
  }
}

// Resultado esperado:
//  · Animación en el hilo de JS  → se CONGELA 800 ms y después salta al final.
//  · Animación en el hilo de UI  → sigue perfecta. Ni se entera.
// Esta es la prueba definitiva. No hay opinión posible después de correrla.
La analogía útil. El hilo de JS es el director de orquesta y el hilo de UI son los músicos. Una animación "en JS" es un director que le marca cada nota a cada músico, uno por uno, sesenta veces por segundo: si el director se distrae atendiendo el teléfono, la música se detiene. Una animación "en UI" es entregarles la partitura y dejarlos tocar. El director puede irse a atender el teléfono, contestar tres mails y volver: la música siguió.

RNS3.2 Animated y useNativeDriver: el techo de la API incluida

React Native trae su propia API de animaciones, Animated, y trae también la primera solución histórica al problema de los hilos: useNativeDriver: true. Lo que hace es declarar la animación por adelantado —origen, destino, duración, curva— y entregársela al lado nativo para que la ejecute sin volver a consultar a JS.

import { Animated, Easing } from 'react-native';
import { useRef, useEffect } from 'react';

export function Aparecer({ children }: { children: React.ReactNode }) {
  const opacidad = useRef(new Animated.Value(0)).current;

  useEffect(() => {
    Animated.timing(opacidad, {
      toValue: 1,
      duration: 300,
      easing: Easing.out(Easing.cubic),
      useNativeDriver: true,     // ← sin esto, cada frame vuelve a JS
    }).start();
  }, [opacidad]);

  return <Animated.View style={{ opacity: opacidad }}>{children}</Animated.View>;
}

Con useNativeDriver: true, JS dice una vez "llevá esta opacidad de 0 a 1 en 300 ms con esta curva" y se desentiende. Es una animación en el hilo de UI, y es genuinamente buena para lo que cubre. El problema es qué cubre.

Qué propiedades acepta el driver nativo (y por qué)

Propiedad¿Driver nativo?Por qué
opacity✅ SíEs una propiedad de composición. La GPU la aplica sin recalcular nada
transform: translateX/Y, scale, rotate, skew, perspective✅ SíEs una matriz aplicada a una capa ya dibujada. No cambia el layout
width, height❌ NoCambian el tamaño de la caja → hay que recalcular el layout del árbol
top, left, right, bottom❌ NoÍdem: son propiedades de layout, no de composición
margin*, padding*, flex, gap❌ NoÍdem, y encima afectan a los hermanos
backgroundColor, borderColor⚠️ DependeAlgunas versiones lo soportan; no lo des por hecho sin probarlo en tu versión
💡 La regla detrás de la tabla. El corte no es arbitrario ni es una limitación de React Native: es la misma frontera que existe en la web entre propiedades que disparan layout y propiedades que solo disparan composite. transform y opacity se aplican sobre una capa ya renderizada — la GPU la mueve, la escala o le baja el alfa sin preguntar nada. width obliga a preguntar de nuevo cuánto mide todo lo demás: Yoga tiene que recorrer el árbol, recolocar hermanos, quizá reflowear texto. Eso no es una operación de GPU, es trabajo de CPU sobre una estructura de datos, y no se puede empaquetar y mandar al hilo de UI de forma trivial.

Si te olvidás la bandera y animás una propiedad de layout, el fallo es explícito:

Animated.timing(altura, {
  toValue: 200,
  duration: 300,
  useNativeDriver: true,     // 💥 explota en runtime
}).start();

// Error: Style property 'height' is not supported by native animated module

// El "arreglo" que hace todo el mundo — y que es el bug:
useNativeDriver: false      // ← ahora sí anda... a 30fps y bloqueándose
                            //    cada vez que el hilo de JS esté ocupado
El antipatrón más común de todos. Poner useNativeDriver: false para silenciar el error. No silenciaste nada: aceptaste que cada cuadro vuelva al hilo de JS a preguntar el valor siguiente. La solución correcta casi siempre es reformular la animación en términos de transform — scaleY en vez de height, translateX en vez de left— o, si de verdad necesitás animar layout, usar Reanimated, que puede hacerlo comprometiendo el árbol de sombra desde el hilo de UI. Sigue costando más que un transform, pero al menos no depende de que JS esté libre.

Animated.event permite además atar un gesto o un scroll directamente a un valor animado, también sin pasar por JS:

const scrollY = useRef(new Animated.Value(0)).current;

const onScroll = Animated.event(
  [{ nativeEvent: { contentOffset: { y: scrollY } } }],
  { useNativeDriver: true },
);

// <Animated.ScrollView onScroll={onScroll} scrollEventThrottle={16} />
Entonces, ¿Animated sirve o no sirve? Sirve, y no requiere ninguna dependencia. Para animaciones declarativas simples y disparadas por estado —un fade in, un modal que entra, un botón que hace scale al presionarse— es perfectamente adecuada y una dependencia menos. Su techo aparece cuando la animación tiene que seguir a un gesto de forma continua, cuando necesitás lógica condicional por cuadro, o cuando tenés que combinar varios valores derivados entre sí. Ahí empieza Reanimated.

RNS3.3 Worklets: el concepto central de Reanimated

Reanimated resuelve el problema de raíz con una idea más ambiciosa que "declarar la animación por adelantado": crear un segundo runtime de JavaScript que viva en el hilo de UI. No un truco, no un intérprete de expresiones limitado: un runtime de Hermes completo, con su propio heap y su propio contexto global, corriendo sobre el hilo que dibuja.

Un worklet es una función marcada para ejecutarse en ese runtime.

function calcularEscala(distancia: number) {
  'worklet';                      // ← la marca. El plugin de Babel la ve
  const k = 1 - Math.abs(distancia) / 600;
  return Math.max(0.85, Math.min(1, k));
}

La directiva 'worklet' no es una convención decorativa: el plugin de Babel de Reanimated la detecta en tiempo de compilación y reescribe la función para que su código y las variables que captura puedan copiarse al otro runtime. Por eso el plugin tiene que ir último en la lista de plugins de Babel — es un requisito, no una recomendación.

// babel.config.js
module.exports = {
  presets: ['babel-preset-expo'],
  plugins: [
    // ...otros plugins...
    'react-native-worklets/plugin',   // ← SIEMPRE el último
  ],
};

// Si ves "Reanimated: worklet is not a function" o valores que no
// se actualizan nunca, revisá esto antes que cualquier otra cosa.
// En Reanimated 3.x el plugin se llamaba 'react-native-reanimated/plugin'.
Versiones, 2026. Reanimated 3.5.1+ y Gesture Handler 2.16.2+ son los pisos de compatibilidad con la Nueva Arquitectura. Reanimated 4 ya exige Nueva Arquitectura —no corre en la legacy— y movió el motor de worklets a un paquete aparte, react-native-worklets, que se instala junto. La API que ves en este módulo (useSharedValue, useAnimatedStyle, withTiming) es la misma en ambas mayores; lo que cambia es el nombre del plugin de Babel y algunas funciones periféricas. Fijá versiones exactas y leé el changelog de la mayor antes de subir.

La mayoría de los worklets no los escribís explícitamente: los hooks de Reanimated convierten en worklet la función que les pasás. Podés verificar dónde está corriendo tu código con la variable global _WORKLET:

const estilo = useAnimatedStyle(() => {
  console.log('¿corro en el UI runtime?', global._WORKLET);  // true
  return { transform: [{ translateX: x.value }] };
});

// En un handler normal de React → undefined (estás en el runtime de JS).
// Es la forma más barata de comprobar una sospecha.

La consecuencia que hay que entender: dos memorias separadas

El worklet no referencia las variables de tu componente. Las copia al otro runtime en el momento en que se crea. Son dos heaps distintos: no hay memoria compartida entre el runtime de JS y el runtime de UI, salvo por un mecanismo explícito que vemos en la sección siguiente.

function Roto() {
  let contador = 0;                        // variable JS común

  const tap = Gesture.Tap().onEnd(() => {
    'worklet';
    contador += 1;                         // ← incrementa la COPIA del UI runtime
    console.log(contador);                 // sube: 1, 2, 3...
  });

  // ...pero acá, en el runtime de JS, `contador` sigue valiendo 0 para siempre.
  // Y si el componente re-renderiza, se crea un worklet NUEVO con una copia
  // nueva desde 0. No hay error, no hay warning: simplemente miente.
}
📌 Todo estado que cruza la frontera de hilos tiene que ser un shared value. Una variable común capturada por un worklet es una foto congelada, no un enlace. Este es el origen de la clase entera de bugs "el valor no se actualiza" en Reanimated, y es la razón por la que existe useSharedValue.

RNS3.4 Shared values: el estado que viven los dos hilos

Un shared value es una caja que ambos runtimes pueden leer y escribir. Se crea con useSharedValue y se accede siempre por .value.

import Animated, {
  useSharedValue, useAnimatedStyle, withTiming, useDerivedValue,
} from 'react-native-reanimated';

function Panel() {
  const abierto  = useSharedValue(0);   // 0 = cerrado, 1 = abierto

  const estilo = useAnimatedStyle(() => ({
    opacity: abierto.value,
    transform: [{ translateY: (1 - abierto.value) * 24 }],
  }));

  return (
    <>
      <Pressable onPress={() => { abierto.value = withTiming(1, { duration: 220 }); }}>
        <Text>Abrir</Text>
      </Pressable>
      <Animated.View style={estilo} />
    </>
  );
}

Lo importante de este código es lo que no tiene: no hay useState, no hay re-render. Escribir abierto.value no dispara ningún ciclo de React. El useAnimatedStyle queda suscrito a los shared values que lee, y cuando alguno cambia, el estilo se recalcula en el hilo de UI y se aplica directamente a la vista nativa.

💡 Reanimated no anima React: lo esquiva. El árbol de React se renderiza una vez y queda quieto. Los valores que cambian sesenta veces por segundo viven fuera de React, en un canal paralelo que va directo a la vista nativa. Por eso una animación de Reanimated puede correr sobre una pantalla con doscientos componentes montados sin costo adicional: React ni se entera de que está pasando.

useDerivedValue: valores que dependen de otros valores

Cuando necesitás un valor calculado a partir de otros, y ese cálculo lo consume más de un lugar, useDerivedValue lo memoriza en el UI runtime:

const x = useSharedValue(0);

// Se recalcula solo cuando x cambia, una vez por cuadro, no por consumidor.
const progreso = useDerivedValue(() => {
  'worklet';
  return Math.min(1, Math.abs(x.value) / ANCHO_PANTALLA);
});

const sombra  = useAnimatedStyle(() => ({ opacity: progreso.value * 0.4 }));
const escala  = useAnimatedStyle(() => ({ transform: [{ scale: 1 - progreso.value * 0.1 }] }));
Cuándo NO usar useDerivedValue. Si el cálculo lo consume un solo useAnimatedStyle, ponelo adentro y listo: un derived value de más es un nodo de más en el grafo de dependencias. La regla práctica es la misma que con useMemo en React — se justifica cuando hay varios consumidores o cuando el cálculo es realmente caro, no "por prolijidad".

Leer un shared value desde React

Tarde o temprano necesitás mostrar en la UI algo que vive en el UI runtime: el índice actual de un carrusel, por ejemplo. La forma correcta es useAnimatedReaction, que observa un valor y reacciona solo cuando realmente cambia lo que te interesa:

const [indice, setIndice] = useState(0);

useAnimatedReaction(
  () => Math.round(-x.value / ANCHO),        // qué observo (worklet)
  (actual, anterior) => {                    // qué hago cuando cambia (worklet)
    if (actual !== anterior) {
      runOnJS(setIndice)(actual);            // ← 1 vez por cambio de tarjeta,
    }                                        //   no 60 veces por segundo
  },
);

RNS3.5 Cruzar la frontera: runOnJS y runOnUI

Los dos runtimes están aislados, así que llamar de uno al otro necesita un cruce explícito. Hay dos direcciones:

FunciónDirecciónUso típico
runOnJS(fn)(args)UI → JSNavegar, setState, disparar un fetch, feedback háptico
runOnUI(fn)()JS → UIArrancar una animación imperativa desde un handler común

Ambos son asincrónicos: encolan el trabajo en el otro hilo y vuelven. No devuelven el resultado de la función y no podés esperarlos. Y cada cruce tiene un costo: hay que copiar los argumentos entre heaps y despertar al otro hilo.

// ❌ El error clásico: setState desde un worklet, en cada cuadro
const pan = Gesture.Pan().onUpdate((e) => {
  'worklet';
  x.value = e.translationX;
  runOnJS(setPosicion)(e.translationX);   // 💥 60 renders de React por segundo
});

Ese runOnJS convierte una animación que corría perfecta en el hilo de UI en una animación que además martilla al hilo de JS con sesenta ciclos de render por segundo. Y como el hilo de JS se satura, todo lo demás de la app —incluidos los toques que React tiene que procesar— empieza a llegar tarde. La animación en sí sigue fluida (vive en UI), pero la app se siente trabada. Es el peor de los diagnósticos: el síntoma aparece lejos de la causa.

// ✅ Correcto: cruzar en los bordes del gesto, no en el medio
const pan = Gesture.Pan()
  .onStart(() => {
    'worklet';
    inicio.value = x.value;
  })
  .onUpdate((e) => {
    'worklet';
    x.value = inicio.value + e.translationX;   // solo UI. Cero cruces.
  })
  .onEnd((e) => {
    'worklet';
    x.value = withDecay({ velocity: e.velocityX, clamp: [MIN, MAX] });
    runOnJS(registrarSwipe)(e.velocityX);      // 1 cruce por gesto completo
  });
📌 Regla de los bordes. Los cruces de hilo van en onStart y onEnd — nunca en onUpdate. Un gesto de dos segundos son ~120 onUpdate y exactamente 2 bordes. Si necesitás avisarle a React de algo intermedio, hacelo con useAnimatedReaction sobre una condición discreta (cambió de página, cruzó un umbral), que dispara una vez por transición y no una vez por cuadro.

En la dirección contraria, runOnUI te deja empujar trabajo al UI runtime desde un handler normal:

function sacudir() {
  runOnUI(() => {
    'worklet';
    offset.value = withSequence(
      withTiming(-8, { duration: 50 }),
      withRepeat(withTiming(8, { duration: 100 }), 3, true),
      withTiming(0,  { duration: 50 }),
    );
  })();                                   // ← ojo: se invoca dos veces
}
En la práctica casi nunca necesitás runOnUI: asignar directamente offset.value = withTiming(...) desde el hilo de JS ya funciona, porque Reanimated se encarga del traslado. runOnUI se justifica cuando querés que varias operaciones ocurran juntas en el mismo cuadro del UI runtime, sin quedar partidas entre dos cuadros distintos.

RNS3.6 withTiming, withSpring, withDecay: elegir, no copiar

Reanimated tiene tres motores de animación, y la diferencia entre ellos no es estética: cada uno modela un fenómeno físico distinto y por eso "se siente" bien en contextos distintos.

MotorModeloSe siente natural para
withTimingDuración fija + curva de easingCambios de estado sin gesto: fade, expandir, aparecer un modal
withSpringMasa, resorte y amortiguación realesTodo lo que responde a un dedo: soltar una tarjeta, snap a una posición
withDecayFricción sobre una velocidad inicialInercia: soltar con impulso y dejar que frene solo

withTiming: cuando vos decidís cuánto dura

import { withTiming, Easing } from 'react-native-reanimated';

opacidad.value = withTiming(1, {
  duration: 250,
  easing: Easing.bezier(0.25, 0.1, 0.25, 1),   // ease estándar
});

// Curvas y para qué sirven:
// Easing.out(Easing.cubic)   → entra rápido y frena. Para cosas que APARECEN.
// Easing.in(Easing.cubic)    → arranca lento y acelera. Para cosas que SE VAN.
// Easing.inOut(Easing.cubic) → simétrica. Para cosas que se MUEVEN de A a B.
// Easing.linear              → mecánico. Solo para rotaciones infinitas.
Duraciones que funcionan. 150–200 ms para micro-interacciones (un botón que responde), 250–300 ms para transiciones de elementos dentro de la pantalla, 300–400 ms para entradas y salidas de pantalla completa. Arriba de 500 ms la animación deja de ser retroalimentación y pasa a ser espera: el usuario ya sabe lo que va a pasar y tu app le está haciendo mirar cómo pasa.

withSpring: la física que sí conviene entender

La razón por la que casi todo el mundo copia y pega parámetros de spring es que parecen arbitrarios. No lo son: son los tres coeficientes de la ecuación del oscilador armónico amortiguado, y con una sola fórmula podés predecir cómo se va a ver la animación antes de correrla.

x.value = withSpring(destino, {
  mass: 1,          // inercia: cuánto "pesa" el objeto
  stiffness: 100,   // rigidez del resorte: cuánto tira hacia el destino
  damping: 10,      // amortiguación: cuánto se opone al movimiento (el freno)

  overshootClamping: false,        // true = prohibido pasarse del destino
  restDisplacementThreshold: 0.01, // qué tan cerca es "llegó"
  restSpeedThreshold: 2,           // qué tan lento es "se detuvo"
});

El único número que importa de verdad es el factor de amortiguación, ζ (zeta), que combina los tres:

// ζ = damping / (2 · √(stiffness · mass))
const zeta = (damping: number, stiffness: number, mass = 1) =>
  damping / (2 * Math.sqrt(stiffness * mass));

zeta(10, 100);   // 0.50 → los valores por defecto de Reanimated: rebota bastante
zeta(15, 100);   // 0.75 → un rebote apenas perceptible. El más usado en producto
zeta(20, 100);   // 1.00 → crítico: llega lo más rápido posible SIN pasarse
zeta(30, 100);   // 1.50 → sobreamortiguado: llega lento, se siente pesado
ζRégimenCómo se percibeDónde usarlo
< 0,4Muy subamortiguadoRebota varias veces, "de juguete"Juegos, celebraciones, onboarding lúdico
0,5 – 0,8SubamortiguadoUn rebote sutil: se siente vivoSoltar una tarjeta, snap de carrusel, bottom sheet
≈ 1,0CríticoDirecto y firme, sin oscilaciónCerrar un modal, volver a posición, cosas serias
> 1,2SobreamortiguadoPesado, casi lánguidoElementos grandes, paneles de mucha superficie

Y la otra intuición: stiffness gobierna la velocidad y mass la inercia. Si subís stiffness tenés que subir damping proporcionalmente a la raíz para conservar la misma sensación — por eso "acelerar" un spring cambiando un solo número casi siempre lo arruina.

// La API moderna te deja saltear la aritmética por completo:
x.value = withSpring(destino, { duration: 500, dampingRatio: 0.7 });

// Y el detalle que separa un swipe bueno de uno mediocre:
// pasarle la velocidad REAL del dedo al soltar.
.onEnd((e) => {
  'worklet';
  x.value = withSpring(destinoSnap, {
    velocity: e.velocityX,        // ← el resorte CONTINÚA el movimiento del dedo
    damping: 18, stiffness: 140,
  });
})

// Sin `velocity`, la tarjeta se detiene en seco al levantar el dedo y
// después arranca de nuevo. Se percibe como un corte, aunque no sepas por qué.

withDecay: inercia pura

.onEnd((e) => {
  'worklet';
  x.value = withDecay({
    velocity: e.velocityX,
    deceleration: 0.997,        // 0.998 ≈ scroll de iOS; más bajo = frena antes
    clamp: [-anchoMaximo, 0],   // límites duros
    rubberBandEffect: true,     // resistencia elástica al pasarse del límite
    rubberBandFactor: 0.6,
  });
});
La combinación que se siente cara: withDecay para el impulso libre y withSpring para el snap a una posición concreta. Un carrusel con páginas usa spring (querés que caiga en una página); una lista con desplazamiento libre usa decay (querés que frene donde el impulso la deje). Elegir mal acá es la diferencia entre "se siente nativo" y "se siente web".

RNS3.7 Gesture Handler: por qué PanResponder no alcanza

React Native trae PanResponder, y tiene un defecto que ninguna cantidad de código propio arregla: los eventos de toque llegan al hilo de JS. Cada movimiento del dedo se convierte en una llamada a tu handler de JS, con lo cual el gesto entero hereda la salud de ese hilo. Si JS está ocupado, el gesto se atrasa.

Peor: la decisión de quién se queda con el gesto —el scroll de la lista o tu componente arrastrable— también se toma en JS, un cuadro tarde, cuando el sistema nativo de reconocimiento ya tomó su decisión. Ahí nacen los conflictos irresolubles.

📌 Gesture Handler no es "un PanResponder mejor". Es un binding al sistema nativo de reconocimiento de gestos de cada plataforma — UIGestureRecognizer en iOS, el sistema de touch de Android. Los gestos se reconocen, compiten entre sí y se resuelven en el hilo nativo, con las mismas reglas que usan las apps nativas. Y sus callbacks son worklets, así que corren en el UI runtime. El toque nunca toca el hilo de JS. 
// El setup obligatorio: la raíz de la app tiene que ser GestureHandlerRootView
import { GestureHandlerRootView } from 'react-native-gesture-handler';

export default function App() {
  return (
    <GestureHandlerRootView style={{ flex: 1 }}>
      <Navegacion />
    </GestureHandlerRootView>
  );
}

// Si te olvidás: en Android los gestos simplemente NO responden, sin error.
// Es el primer lugar donde mirar cuando "funciona en iOS pero no en Android".
import { Gesture, GestureDetector } from 'react-native-gesture-handler';
import Animated, { useSharedValue, useAnimatedStyle, withSpring } from 'react-native-reanimated';

function Arrastrable() {
  const x = useSharedValue(0);
  const y = useSharedValue(0);
  const ini = useSharedValue({ x: 0, y: 0 });

  const pan = Gesture.Pan()
    .onStart(() => { ini.value = { x: x.value, y: y.value }; })
    .onUpdate((e) => {
      x.value = ini.value.x + e.translationX;
      y.value = ini.value.y + e.translationY;
    })
    .onEnd(() => {
      x.value = withSpring(0);
      y.value = withSpring(0);
    });

  const estilo = useAnimatedStyle(() => ({
    transform: [{ translateX: x.value }, { translateY: y.value }],
  }));

  return (
    <GestureDetector gesture={pan}>
      <Animated.View style={[styles.caja, estilo]} />
    </GestureDetector>
  );
}
El envoltorio directo de GestureDetector debe ser una vista. Si adentro ponés un fragmento, un componente que devuelve null en algún caso, o un componente que no reenvía la ref, el gesto no se adjunta a nada. En iOS puede parecer que funciona por herencia de toques; en Android no.

Composición: Race, Simultaneous, Exclusive

Un componente real casi nunca tiene un solo gesto. Gesture Handler te deja combinarlos declarativamente, y las tres formas de combinar responden a tres preguntas distintas:

ComposiciónSemánticaEjemplo canónico
Gesture.Race(a, b)Compiten; el primero que se activa cancela al otroArrastrar o hacer scroll: uno de los dos, nunca los dos
Gesture.Simultaneous(a, b)Corren a la vez, ambos reciben eventosPinch + rotate + pan en un visor de imágenes
Gesture.Exclusive(a, b)Prioridad fija: b solo se activa si a fallaDoble tap tiene prioridad sobre tap simple
 
// Visor de imágenes: zoom, rotación y desplazamiento simultáneos
const pinch = Gesture.Pinch().onUpdate((e) => { escala.value = base.value * e.scale; });
const rot   = Gesture.Rotation().onUpdate((e) => { angulo.value = baseAng.value + e.rotation; });
const arr   = Gesture.Pan().onUpdate((e) => { x.value = iniX.value + e.translationX; });

const combinado = Gesture.Simultaneous(pinch, rot, arr);

// Doble tap para zoom, tap simple para abrir: Exclusive resuelve la ambigüedad
const doble  = Gesture.Tap().numberOfTaps(2).onEnd(() => { escala.value = withSpring(2); });
const simple = Gesture.Tap().onEnd(() => { runOnJS(abrirDetalle)(); });

const taps = Gesture.Exclusive(doble, simple);
// Sin Exclusive, el tap simple se dispararía SIEMPRE, y además dos veces
// al hacer doble tap. Con Exclusive, el simple espera a que el doble falle
// (~200 ms) antes de activarse.
Ese "~200 ms de espera" no es gratis: el tap simple se siente levemente perezoso. Por eso las apps buenas usan Exclusive solo donde el doble tap existe de verdad. Si en esa zona no hay doble tap, no pongas la espera — la latencia percibida en un tap es de las cosas que más rápido se notan.

El conflicto clásico: gesto vs. scroll

Una tarjeta arrastrable horizontalmente dentro de una lista que scrollea verticalmente. Es el caso que rompe todas las implementaciones caseras, y en Gesture Handler se resuelve declarando desde qué umbral tu gesto se considera intencional:

const swipe = Gesture.Pan()
  // Solo me activo si el dedo se movió 10 px en horizontal.
  .activeOffsetX([-10, 10])
  // Y me RINDO si antes se movió 12 px en vertical: eso era scroll.
  .failOffsetY([-12, 12]);

// El orden importa conceptualmente:
//   activeOffsetX = "esto sí es lo mío"
//   failOffsetY   = "esto claramente no es lo mío, dejalo pasar"
// Sin failOffsetY, un swipe diagonal secuestra el scroll y la lista
// se traba a mitad de camino. Es EXACTAMENTE el bug que hace que una
// app se sienta rota sin que nadie sepa explicar por qué.
// Cuando necesitás que tu gesto y un componente nativo scrollable
// convivan, referenciás el gesto nativo explícitamente:
const scrollRef = useAnimatedRef<Animated.ScrollView>();

const pan = Gesture.Pan()
  .simultaneousWithExternalGesture(scrollRef)   // conviven
  // .blocksExternalGesture(scrollRef)          // el mío gana y bloquea al scroll
  // .requireExternalGestureToFail(scrollRef)   // el mío espera a que el scroll falle
  .onUpdate((e) => { x.value = e.translationX; });
Lo que NO hay que hacer. Resolver el conflicto midiendo ángulos a mano en onUpdate y decidiendo con ifs si "esto era scroll". Llegás tarde por diseño: cuando tu primer onUpdate se ejecuta, el reconocedor nativo del scroll ya tomó su decisión. activeOffsetX / failOffsetY se evalúan dentro del sistema de reconocimiento, antes de que ninguno de los dos gane. Es la diferencia entre participar de la negociación y quejarse después.

RNS3.8 Interpolación y efectos ligados al scroll

interpolate mapea un rango de entrada a un rango de salida. Es la herramienta que convierte "cuánto se movió el dedo" o "cuánto scrolleó" en cualquier propiedad visual.

import { interpolate, Extrapolation } from 'react-native-reanimated';

const estilo = useAnimatedStyle(() => {
  const opacidad = interpolate(
    x.value,                    // valor de entrada
    [0, 100, 200],              // puntos de entrada
    [1, 0.5, 0],                // puntos de salida (mismo largo)
    Extrapolation.CLAMP,        // qué pasa FUERA del rango
  );
  return { opacity: opacidad };
});

// Extrapolation.CLAMP    → se queda en el borde. El default seguro.
// Extrapolation.EXTEND   → sigue la recta al infinito (opacidad de -3: bug visual)
// Extrapolation.IDENTITY → devuelve la entrada sin transformar
No poner CLAMP es un bug esperando su momento. Con EXTEND (el comportamiento por defecto), un scroll que llega a 900 px cuando tu rango llegaba a 200 produce escalas negativas, opacidades mayores a 1 y rotaciones absurdas. Suele descubrirse en producción, en el dispositivo de alguien que scrolleó más rápido que vos durante las pruebas.

Para atar animaciones al scroll, useAnimatedScrollHandler hace lo mismo que un gesto: recibe los eventos en el UI runtime.

import Animated, { useAnimatedScrollHandler, useSharedValue } from 'react-native-reanimated';

function ListaConHeader() {
  const scrollY = useSharedValue(0);

  const onScroll = useAnimatedScrollHandler({
    onScroll: (e) => { scrollY.value = e.contentOffset.y; },
    onBeginDrag: () => { arrastrando.value = 1; },
    onMomentumEnd: () => { arrastrando.value = 0; },
  });

  const header = useAnimatedStyle(() => ({
    height: interpolate(scrollY.value, [0, 120], [200, 64], Extrapolation.CLAMP),
    opacity: interpolate(scrollY.value, [0, 90], [1, 0], Extrapolation.CLAMP),
  }));

  return (
    <>
      <Animated.View style={[styles.header, header]} />
      <Animated.FlatList onScroll={onScroll} scrollEventThrottle={16} data={datos} /* ... */ />
    </>
  );
}
Ese height del header es una decisión, no un descuido. Animar height obliga a recalcular layout en cada cuadro — Reanimated puede hacerlo desde el UI runtime, pero cuesta bastante más que un transform. Si el header es simple, translateY + scaleY logran el mismo efecto visual sin tocar el layout. Si adentro hay texto que tiene que reacomodarse de verdad, entonces sí necesitás height: solo asegurate de que sea una elección consciente y de medirla en un dispositivo de gama media.

RNS3.9 Layout animations y transiciones entre pantallas

Hay una categoría de animación que no podés escribir a mano razonablemente: la que ocurre cuando un elemento se monta, se desmonta o cambia de posición porque cambió la lista. Reanimated la resuelve declarativamente.

import Animated, {
  FadeIn, FadeOut, SlideInRight, LinearTransition,
} from 'react-native-reanimated';

{tareas.map((t) => (
  <Animated.View
    key={t.id}
    entering={SlideInRight.duration(220).springify()}
    exiting={FadeOut.duration(150)}
    layout={LinearTransition.springify().damping(18)}
  >
    <Tarea {...t} />
  </Animated.View>
))}

// entering → cuando el elemento se monta
// exiting  → cuando se desmonta (Reanimated retrasa la baja hasta terminar)
// layout   → cuando cambia de posición porque otro entró o salió

layout es el que hace el trabajo invisible: si borrás el tercer ítem de una lista, los de abajo se deslizan hacia arriba en vez de saltar. Es una línea de código y cambia por completo la percepción de calidad.

// Animaciones de entrada a medida, con Keyframe
import { Keyframe } from 'react-native-reanimated';

const entrada = new Keyframe({
  0:   { opacity: 0, transform: [{ scale: 0.8 }, { translateY: 20 }] },
  60:  { opacity: 1, transform: [{ scale: 1.03 }, { translateY: 0 }] },
  100: { opacity: 1, transform: [{ scale: 1 }, { translateY: 0 }] },
}).duration(320);

// <Animated.View entering={entrada}> ... </Animated.View>
// Ese pico en 60 —pasarse apenas y volver— es el truco que hace que
// una entrada se sienta física en vez de mecánica.
Transiciones compartidas entre pantallas: cuidado. La API sharedTransitionTag de Reanimated 3 fue siempre experimental y quedó fuera de Reanimated 4 a la espera de un rediseño. Para transiciones entre pantallas en producción, apoyate en lo que ofrezca tu librería de navegación (React Navigation con react-native-screens y las transiciones nativas del stack) y reservá el efecto "elemento compartido" para casos donde puedas absorber el riesgo. Es exactamente el tipo de dependencia que no querés en el camino crítico de tu app.

RNS3.10 Los errores clásicos

1. Animar width/height cuando querías transform

// ❌ Recalcula layout de todo el subárbol, 60 veces por segundo
const malo = useAnimatedStyle(() => ({
  width:  ancho.value,
  height: alto.value,
}));

// ✅ Mismo efecto visual, cero layout: solo composición en GPU
const bueno = useAnimatedStyle(() => ({
  transform: [{ scaleX: ancho.value / ANCHO_BASE },
              { scaleY: alto.value  / ALTO_BASE  }],
}));
La advertencia honesta: scale escala todo, incluido el texto y los bordes. Si el contenido tiene que quedar del mismo tamaño mientras la caja crece, scale no sirve y necesitás height. El truco intermedio es escalar solo el fondo (una View absoluta detrás) y dejar el contenido quieto: conseguís el efecto sin pagar el layout.

2. Worklets que capturan valores obsoletos

function Roto({ limite }: { limite: number }) {
  const pan = Gesture.Pan().onUpdate((e) => {
    'worklet';
    x.value = Math.min(limite, e.translationX);   // ⚠️ `limite` es una COPIA
  });
  // El worklet se creó con el `limite` del primer render. Si el prop cambia,
  // el worklet sigue usando el viejo hasta que se vuelva a crear.
}

// ✅ Estado que cambia y cruza hilos → shared value
function Bien({ limite }: { limite: number }) {
  const limiteSV = useSharedValue(limite);
  useEffect(() => { limiteSV.value = limite; }, [limite, limiteSV]);

  const pan = useMemo(() =>
    Gesture.Pan().onUpdate((e) => {
      'worklet';
      x.value = Math.min(limiteSV.value, e.translationX);   // siempre actual
    }), []);
}
📌 Envolvé la definición del gesto en useMemo. Sin memorizar, cada render construye un objeto de gesto nuevo, GestureDetector lo reconfigura, y en el peor caso un gesto en curso se cancela a mitad de camino. El síntoma es "el arrastre se corta solo a veces" — de los bugs más difíciles de reproducir, porque depende de que algo dispare un render justo mientras el dedo está apoyado.

3. Animaciones que no se cancelan al desmontar

import { cancelAnimation } from 'react-native-reanimated';

useEffect(() => {
  rotacion.value = withRepeat(withTiming(360, { duration: 1200 }), -1);
  return () => { cancelAnimation(rotacion); };    // ← obligatorio
}, [rotacion]);

// Sin cancelar, un `withRepeat(-1)` sigue corriendo en el UI runtime
// después de que el componente se fue. Multiplicalo por cada vez que
// el usuario entra y sale de la pantalla: son animaciones acumulándose
// sobre vistas que ya no existen. Consumo de CPU permanente y silencioso.
// La variante venenosa: un callback que toca React después del desmontaje
opacidad.value = withTiming(0, { duration: 300 }, (terminada) => {
  'worklet';
  if (terminada) runOnJS(cerrarModal)();   // 💥 si ya se desmontó, actualizás
});                                        //    estado de un componente muerto

// ✅ Guardá un flag vivo/muerto en un shared value
const vivo = useSharedValue(1);
useEffect(() => () => { vivo.value = 0; }, [vivo]);

opacidad.value = withTiming(0, { duration: 300 }, (terminada) => {
  'worklet';
  if (terminada && vivo.value) runOnJS(cerrarModal)();
});

4. Animar dentro de una lista virtualizada sin pensarlo

// Cada fila con su propio useSharedValue + useAnimatedStyle es un nodo
// en el grafo del UI runtime. Con 8 filas visibles no pasa nada.
// Con 60 filas montadas por un windowSize alto (ver RNS2), el UI runtime
// evalúa 60 estilos por cuadro y ahí sí bloqueás el hilo de dibujo.
//
// Estrategia: UN shared value en el contenedor (el scroll) y filas que
// derivan su estilo de ese único valor, en vez de 60 valores independientes.
El worklet lento es el peligro que nadie ve venir. Todo este módulo trata de mover trabajo al hilo de UI, pero ese hilo también es el que dibuja. Un worklet que hace un filter sobre 5.000 elementos en cada onUpdate no "corre en paralelo": bloquea el dibujo, exactamente igual que un handler pesado bloquea JS. Los worklets tienen que ser aritmética barata. Si necesitás una decisión costosa, calculala una vez en JS y pasá el resultado por un shared value.

RNS3.11 Accesibilidad: reduce motion no es opcional

Para una parte real de tus usuarios —trastornos vestibulares, migraña vestibular, sensibilidad al movimiento— una animación de paralaje agresiva no es "un detalle lindo": produce mareo, náusea o dolor de cabeza. Y esas personas ya te lo dijeron: activaron Reducir movimiento en la configuración del sistema operativo. Ignorar esa preferencia es ignorar una instrucción explícita del usuario.

import { useReducedMotion } from 'react-native-reanimated';

function Tarjeta() {
  const reducir = useReducedMotion();

  const estilo = useAnimatedStyle(() => ({
    transform: [{
      // Sin movimiento reducido: paralaje completo.
      // Con movimiento reducido: sin desplazamiento, solo el fade.
      translateY: reducir ? 0 : desplazamiento.value * 0.4,
    }],
    opacity: opacidad.value,
  }));

  return <Animated.View style={estilo} />;
}
// A nivel de app, Reanimated respeta la preferencia del sistema por defecto
// en las layout animations. Podés forzar el comportamiento explícitamente:
import { ReducedMotionConfig, ReduceMotion } from 'react-native-reanimated';

<ReducedMotionConfig mode={ReduceMotion.System} />
//  ReduceMotion.System  → seguir la configuración del SO (lo correcto)
//  ReduceMotion.Always  → todo reducido (útil para probar)
//  ReduceMotion.Never   → ignorar la preferencia (evitalo)

// Y la API cruda, si necesitás la preferencia fuera de Reanimated:
import { AccessibilityInfo } from 'react-native';
const reducido = await AccessibilityInfo.isReduceMotionEnabled();
📌 "Reducir movimiento" no significa "sacar toda la animación". Significa sacar el desplazamiento espacial grande — paralaje, zoom, deslizamientos de pantalla completa, rotación. Un fade o un cambio de color no producen mareo y siguen comunicando el cambio de estado. Eliminar toda la animación deja una interfaz donde las cosas aparecen y desaparecen sin explicación, y eso es peor para todos, incluida la persona que activó la preferencia.
Probalo ahora, tarda un minuto. iOS: Ajustes → Accesibilidad → Movimiento → Reducir movimiento. Android: Configuración → Accesibilidad → Eliminar animaciones. Recorré tu app entera con eso activado. Si algo se rompe visualmente, si una transición desaparece y te deja sin saber qué pasó, o si el paralaje sigue moviéndose, tenés un bug de accesibilidad — con la misma severidad que cualquier otro bug.

RNS3.12 Medir: confirmar en qué hilo corre, con evidencia

Todo lo anterior es teoría hasta que lo verificás en un dispositivo. Y "se ve fluido en mi iPhone en modo desarrollo" no es una medición: es una anécdota tomada en las peores condiciones posibles para sacar conclusiones.

Cómo medir en serio.
1. Release build, no dev. El modo desarrollo agrega verificaciones, no optimiza el bundle y no representa nada.
2. Dispositivo físico de gama media, no el simulador ni tu teléfono nuevo. El simulador usa la CPU de tu computadora y miente por exceso.
3. Dos números, no uno: FPS del hilo de UI y FPS del hilo de JS. La combinación es el diagnóstico completo. 
# Android: Perf Monitor del menú de desarrollo (agitar / adb shell input keyevent 82)
#   UI 60 · JS 60  → todo bien
#   UI 60 · JS 18  → la animación está en UI, pero algo satura JS (¿setState por frame?)
#   UI 32 · JS 60  → el hilo de UI está saturado: worklet caro, layout por frame,
#                    imágenes gigantes o demasiadas vistas animadas

# Medición externa, sin instrumentar la app y sobre un build de release:
npx flashlight test --bundleId com.tuapp --testCommand "..."

// La prueba binaria, que no requiere ninguna herramienta y no admite discusión:

El complemento de RNS2. Un hilo de JS saturado también degrada la respuesta al toque, aunque la animación esté en UI: el onPress tarda en ejecutarse porque la cola de JS está llena. Por eso las dos disciplinas van juntas — mover la animación al UI runtime resuelve la fluidez, pero no te exime de mantener el hilo de JS liviano.

🧑‍🎓 Worked Example — el carrusel con paralaje que va a 40fps

Un carrusel de tarjetas: se arrastra horizontalmente, cada tarjeta se escala según su distancia al centro y la imagen de fondo se mueve a otra velocidad (paralaje). En el iPhone del desarrollador se ve bien. En un Android de gama media va a 38–45fps y el arrastre "se siente pegajoso". El reporte de QA dice, literalmente: "anda pero se siente mal".

Paso 1 — El código que existe

// ❌ ANTES
function Carrusel({ items }: { items: Item[] }) {
  const [x, setX] = useState(0);                     // ⚠️ posición en estado de React
  const pan = useRef(new Animated.Value(0)).current;

  const responder = useRef(
    PanResponder.create({
      onMoveShouldSetPanResponder: () => true,
      onPanResponderMove: (_, g) => {
        setX(g.dx);                                  // ⚠️ un render POR CUADRO
        pan.setValue(g.dx);                          // ⚠️ sin driver nativo
      },
      onPanResponderRelease: (_, g) => {
        const destino = Math.round(-g.dx / ANCHO) * ANCHO;
        Animated.spring(pan, { toValue: destino, useNativeDriver: false }).start();
        setX(destino);
      },
    }),
  ).current;

  return (
    <View {...responder.panHandlers} style={styles.pista}>
      {items.map((it, i) => {
        const d = x - i * ANCHO;                     // ⚠️ recalculado en JS, por tarjeta
        return (
          <Tarjeta
            key={it.id}
            item={it}
            paralaje={d * 0.35}
            escala={1 - Math.min(0.15, Math.abs(d) / (ANCHO * 6))}
          />
        );
      })}
    </View>
  );
}

MétricaAntesLectura

La cadena causal completa: onPanResponderMove llega al hilo de JS → llama a setX → React re-renderiza el carrusel → recalcula paralaje y escala de cada tarjeta → reconcilia y comitea cinco subárboles. Todo eso tiene que caber en 16,67 ms, sesenta veces por segundo, mientras el hilo de JS además atiende los eventos de toque siguientes. No cabe. Se pierden cuadros, y como se pierden de forma irregular, se percibe como pegajosidad y no como lentitud.

📌 El bug no es PanResponder ni es useNativeDriver: false. El bug es usar estado de React como posición de un gesto. Los otros dos son consecuencias de esa decisión. Por eso la corrección no es cambiar una bandera: es cambiar dónde vive la posición.

Paso 3 — Reescritura: la posición vive en el UI runtime

// ✅ DESPUÉS — el contenedor
import { Gesture, GestureDetector } from 'react-native-gesture-handler';
import Animated, {
  useSharedValue, useAnimatedReaction, runOnJS, withSpring,
} from 'react-native-reanimated';

function Carrusel({ items, onCambioPagina }: Props) {
  const x     = useSharedValue(0);   // posición: fuera de React
  const ini   = useSharedValue(0);
  const vivo  = useSharedValue(1);
  useEffect(() => () => { vivo.value = 0; }, [vivo]);

  const maxX = -(items.length - 1) * ANCHO;

  const pan = useMemo(() =>
    Gesture.Pan()
      .activeOffsetX([-10, 10])       // solo me activo si el movimiento es horizontal
      .failOffsetY([-14, 14])         // y me rindo si era scroll vertical
      .onStart(() => {
        'worklet';
        ini.value = x.value;
      })
      .onUpdate((e) => {
        'worklet';
        x.value = ini.value + e.translationX;   // ← 0 cruces de hilo. 0 renders.
      })
      .onEnd((e) => {
        'worklet';
        // La proyección con velocidad: el snap sigue el impulso del dedo,
        // no la posición donde el dedo quedó. Esto es lo que se siente "nativo".
        const proyectada = x.value + e.velocityX * 0.15;
        const pagina = Math.round(-proyectada / ANCHO);
        const destino = Math.max(maxX, Math.min(0, -pagina * ANCHO));

        x.value = withSpring(destino, {
          velocity: e.velocityX,       // el resorte CONTINÚA el gesto
          damping: 18, stiffness: 140, // ζ ≈ 0,76 → un rebote apenas perceptible
        });
      }),
  [items.length]);

  // Avisarle a React solo cuando cambia la PÁGINA: ~1 vez por gesto, no 60/s
  useAnimatedReaction(
    () => Math.round(-x.value / ANCHO),
    (actual, anterior) => {
      'worklet';
      if (actual !== anterior && vivo.value) runOnJS(onCambioPagina)(actual);
    },
  );

  return (
    <GestureDetector gesture={pan}>
      <View style={styles.pista}>
        {items.map((it, i) => (
          <Tarjeta key={it.id} item={it} indice={i} x={x} />
        ))}
      </View>
    </GestureDetector>
  );
}
// ✅ DESPUÉS — la tarjeta. Recibe el shared value y deriva TODO de él.
import Animated, {
  useAnimatedStyle, interpolate, Extrapolation, useReducedMotion,
} from 'react-native-reanimated';

const Tarjeta = React.memo(function Tarjeta({ item, indice, x }: TarjetaProps) {
  const reducir = useReducedMotion();
  const centro = indice * ANCHO;

  const cuerpo = useAnimatedStyle(() => {
    const d = -x.value - centro;                       // distancia al centro
    return {
      transform: [
        { translateX: x.value },
        { scale: interpolate(d, [-ANCHO, 0, ANCHO], [0.88, 1, 0.88], Extrapolation.CLAMP) },
      ],
      opacity: interpolate(d, [-ANCHO, 0, ANCHO], [0.55, 1, 0.55], Extrapolation.CLAMP),
    };
  });

  const fondo = useAnimatedStyle(() => {
    const d = -x.value - centro;
    return {
      // Respeta reduce motion: sin paralaje, la tarjeta sigue funcionando.
      transform: [{ translateX: reducir ? 0 : d * 0.35 }],
    };
  });

  return (
    <Animated.View style={[styles.tarjeta, cuerpo]}>
      <Animated.Image source={item.img} style={[styles.fondo, fondo]} />
      <Texto item={item} />
    </Animated.View>
  );
});

Esa última fila es la que importa, y conviene entender exactamente por qué cambió. En la versión nueva, el hilo de JS ya no participa del gesto. El toque lo reconoce el sistema nativo, el onUpdate corre como worklet en el UI runtime, x.value se escribe en memoria compartida y los useAnimatedStyle se reevalúan en el mismo hilo que va a dibujar el cuadro. En ningún punto de esa cadena hay una cola de JS.

💡 Lo que esto habilita de verdad. Ahora el hilo de JS puede estar ocupado sin que se note: podés precargar la pantalla siguiente, deserializar la respuesta de la API o hidratar la caché mientras el usuario arrastra el carrusel, y la animación no pierde un solo cuadro. Antes, cualquiera de esas tareas convertía el arrastre en un tirón. El beneficio no es solo "la animación va a 60fps": es que desacoplaste dos cosas que nunca debieron estar acopladas, y eso te devuelve el hilo de JS para hacer trabajo útil en el momento exacto en que antes tenías que quedarte quieto.
Y el error que sigue acechando. Si mañana alguien agrega un runOnJS(setProgreso)(x.value) dentro del onUpdate "para mostrar un indicador", la regresión completa vuelve en una línea, sin romper ningún test y sin generar ningún warning. Por eso conviene dejar la prueba de bloqueo de JS en el menú de debug y un comentario explícito arriba del onUpdate: la decisión de arquitectura tiene que ser visible en el lugar donde se puede deshacer.

Checkpoint — ¿lo tenés claro?

Si el puente ya no existe en RN 0.82+, ¿por qué sigue importando en qué hilo corre la animación?

Porque el puente nunca fue el único problema — era un síntoma caro de uno más profundo: el hilo de JavaScript es uno solo. JSI eliminó la serialización, así que cada cruce entre JS y nativo hoy es mucho más barato; pero si tu animación necesita que JS calcule una posición sesenta veces por segundo, sigue dependiendo de que ese hilo esté libre sesenta veces por segundo. Y ese hilo también corre tu render, tus efectos, tu parseo de JSON y tus handlers. La solución nunca fue "hacer el cruce más rápido": es no cruzar. Que el gesto se reconozca en nativo, que el valor viva en memoria compartida y que el estilo se calcule en el UI runtime. Cero participación de JS durante el gesto.

Tu animación de Reanimated corre en el UI runtime y aun así la app se siente trabada durante el gesto. ¿Qué revisás?

Dos hipótesis, en este orden. (1) Un runOnJS dentro de onUpdate: la animación va fluida —vive en UI— pero estás martillando al hilo de JS con 60 llamadas por segundo, típicamente un setState. La app se siente trabada porque todo lo demás (toques, navegación, otros componentes) se atrasa. Se arregla moviendo el cruce a onEnd o usando useAnimatedReaction sobre una condición discreta. (2) Un worklet caro: el UI runtime corre sobre el hilo que dibuja, así que un cálculo pesado dentro de un useAnimatedStyle —un filter sobre miles de elementos, una operación con strings— bloquea el dibujo igual que un handler pesado bloquea JS. Se distinguen con Perf Monitor: en el caso (1) ves UI 60 / JS 20; en el (2), UI 30 / JS 60.

¿Por qué useNativeDriver no soporta width y height, y qué hacés cuando de verdad necesitás animarlas?

Porque son propiedades de layout, no de composición. transform y opacity se aplican sobre una capa ya renderizada: la GPU la mueve o le cambia el alfa sin preguntar nada. Cambiar width obliga a recalcular el layout del árbol con Yoga —recolocar hermanos, quizá reflowear texto—, que es trabajo de CPU sobre una estructura de datos y no se puede delegar como una animación declarativa simple. Cuando de verdad necesitás animar tamaño, tenés tres caminos, de menor a mayor costo: (a) reformularlo como scaleX/scaleY, si escalar el contenido junto con la caja es aceptable; (b) escalar solo un fondo absoluto y dejar el contenido quieto, que da el efecto sin tocar el layout; (c) usar Reanimated, que sí puede animar propiedades de layout comprometiendo el árbol de sombra desde el UI runtime — cuesta más que un transform, pero al menos no depende de que el hilo de JS esté libre. Lo que nunca es la respuesta es useNativeDriver: false.

Resumen ejecutivo

  • A 60fps tenés 16,67 ms por cuadro; a 120fps, 8,33. Pasarse por poco cuesta lo mismo que pasarse por mucho: el cuadro se pierde entero.
  • El puente ya no existe (RN 0.82+), pero el hilo de JS sigue siendo uno solo. Ese, y no la serialización, es el problema de hoy.
  • useNativeDriver: true resuelve bien las animaciones declarativas de transform y opacity. No soporta layout porque layout implica recalcular el árbol, no componer una capa. Poner false para callar el error es el antipatrón.
  • Un worklet es una función que corre en un segundo runtime de JS montado sobre el hilo de UI. Captura las variables por copia: todo lo que cambia y cruza hilos tiene que ser un useSharedValue.
  • Los cruces (runOnJS, runOnUI) van en los bordes del gesto, jamás en onUpdate. Para avisos intermedios, useAnimatedReaction sobre una condición discreta.
  • Elegí el motor por el fenómeno: withTiming para cambios de estado, withSpring para respuestas a un dedo (y pasale la velocity real), withDecay para inercia. El factor ζ = damping/(2√(stiffness·mass)) predice cómo se va a sentir antes de correrlo.
  • Gesture Handler reconoce los gestos en el sistema nativo, no en JS. activeOffsetX + failOffsetY resuelven el conflicto con el scroll dentro de la negociación; los ifs en onUpdate llegan siempre tarde.
  • Cancelá las animaciones al desmontar (cancelAnimation) y protegé los callbacks con un flag de vida. Un withRepeat(-1) huérfano consume CPU en silencio para siempre.
  • Respetá reduce motion. Reducir movimiento es quitar el desplazamiento espacial grande, no toda la animación. Una animación que marea es un bug con la misma severidad que cualquier otro.
  • Medí en release, en un dispositivo de gama media, mirando los dos FPS. La prueba definitiva: bloqueá el hilo de JS un segundo. Si la animación no se inmuta, está donde tiene que estar.

🧠 Autoevaluación

1. Tu animación de Reanimated se ve perfecta, pero la app se siente trabada mientras el usuario arrastra. Perf Monitor muestra UI 60 / JS 20. ¿Cuál es la primera hipótesis?

La firma del diagnóstico está en los dos números: UI en 60 significa que el hilo de dibujo está sano, así que la animación efectivamente vive en el UI runtime; JS en 20 significa que algo lo está saturando 60 veces por segundo, y el sospechoso número uno es un cruce de hilo en onUpdate. La animación no se rompe (no depende de JS), pero todo lo demás —toques, navegación, otros componentes— se atrasa. Si fuera un worklet caro verías lo inverso: UI 30 / JS 60. Y useNativeDriver no existe en Reanimated: es de la API Animated.

2. Un worklet lee una variable común de tu componente (const limite = props.limite) y usa ese valor en onUpdate. El prop cambia, pero el gesto sigue usando el valor viejo. ¿Por qué?

El runtime de UI tiene su propio heap. Cuando el plugin de Babel convierte la función en worklet, serializa el código y las variables que captura para copiarlas al otro lado. Esa copia es una foto del momento en que se creó el worklet: no es un enlace vivo. Por eso el valor queda congelado, sin error ni warning — es la clase entera de bugs "el valor no se actualiza". La solución es un useSharedValue, que es la única memoria que los dos runtimes leen y escriben de verdad; y conviene además memorizar la definición del gesto con useMemo, porque reconstruirlo en cada render puede cancelar un gesto en curso.

3. Una tarjeta arrastrable horizontalmente vive dentro de una FlatList vertical. Al hacer un swipe diagonal, el scroll se traba a mitad de camino. ¿Cuál es la corrección?

La decisión de quién se queda con el toque la toma el sistema nativo de reconocimiento, y la toma antes de que tu primer onUpdate se ejecute. Medir ángulos ahí adentro es participar de una negociación que ya terminó — por eso el bug persiste por más ifs que agregues. activeOffsetX declara desde qué umbral el movimiento cuenta como tuyo y failOffsetY declara cuándo te rendís explícitamente; ambos se evalúan dentro del reconocedor, mientras los gestos todavía compiten. La opción del setState es peor aún: agrega un render de React en medio de un gesto y llega un cuadro tarde.

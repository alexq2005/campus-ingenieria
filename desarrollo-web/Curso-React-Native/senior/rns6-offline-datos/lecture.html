RNS6 — Offline-first: datos, sincronización y conflictos

RNS6.0 Por qué este módulo

En la web escribís código asumiendo que hay red. Es una suposición razonable: el navegador vive en una máquina que casi siempre está enchufada a algo. En móvil esa suposición es falsa por diseño. El dispositivo se mueve, entra al subte, sube en un ascensor, cruza un túnel, se queda sin datos a mitad de mes, se conecta al wifi del bar que pide login, y se va al campo donde no hay antena.

💡 La tesis del módulo. En móvil la red no es una excepción: es un estado intermitente normal. Una app que trata la desconexión como error de borde se rompe en el uso cotidiano. Y una app que trata la desconexión como algo que "se arregla con un caché" pierde datos en silencio. El trabajo senior no es "agregar soporte offline": es elegir conscientemente cuánto offline soporta tu producto, y pagar el costo de ese nivel entero, no la mitad.

En el M07 del curso base viste AsyncStorage y un caché de lectura: mostrar lo último que se vio mientras se refresca de la red. Eso resuelve el 60% de los casos y está muy bien. Este módulo empieza justo donde ese patrón se rompe: cuando el usuario tiene que poder escribir sin conexión. Ahí aparecen la cola de operaciones, la idempotencia, el versionado, y el problema que nadie quiere mirar de frente: dos versiones distintas de la misma cosa, y alguien tiene que decidir cuál sobrevive.

📌 La frase que hay que grabarse. Leer offline es un problema de caché. Escribir offline es un problema de sistemas distribuidos. Son dos disciplinas distintas y cuestan órdenes de magnitud diferentes. Confundirlas es el origen de casi todos los desastres de sincronización.

RNS6.1 El espectro offline: cuánto necesitás de verdad

"Offline-first" se usa como si fuera un interruptor, y no lo es. Es una escala con cuatro escalones bien distintos, cada uno con un costo de construcción y de mantenimiento muy diferente. Antes de escribir una línea, ubicá tu app en la escala a propósito.

⚠️ La mayoría de las apps NO necesitan el nivel 3. Decilo en voz alta antes de arrancar. El nivel 3 no es "el nivel 2 pero mejor": es otro producto. Te obliga a diseñar el backend distinto (versionado, tombstones, cursores de sync), a mantener migraciones de esquema en dispositivos que no controlás, y a construir UI para conflictos que en el 99% de los usos no aparecen — y en el 1% restante deciden si el usuario confía en tu app o la borra. Si el caso de uso real es "a veces el ascensor", el nivel 1 o 2 es la respuesta correcta y madura.

El error más caro no es elegir un nivel bajo. Es elegir el nivel 3 sin darse cuenta: alguien agrega "guardar aunque no haya internet" a una app de nivel 1, sin cola, sin versiones, sin ids de cliente. Funciona en la demo. Seis meses después, los usuarios reportan notas que desaparecen y no hay forma de reconstruir qué pasó porque nunca hubo un registro de las operaciones.

El síntoma clásico del nivel 3 accidental: tickets de soporte que dicen "se me borró lo que había escrito" y que no podés reproducir. No podés reproducirlos porque el bug depende del orden de dos escrituras en dos dispositivos, y tu sistema no guardó ese orden en ningún lado. Si no podés reconstruir la historia, no tenés un bug: tenés un diseño.

AsyncStorage: por qué sigue existiendo y por qué no alcanza

Es la API que aprendiste en M07 y está bien para lo que fue diseñada. El problema empieza cuando se usa como base de datos:

import AsyncStorage from '@react-native-async-storage/async-storage';

// 🔴 El antipatrón más común de offline en RN
async function guardarNotas(notas: Nota[]) {
  await AsyncStorage.setItem('notas', JSON.stringify(notas));
}

async function agregarNota(nueva: Nota) {
  const crudo = await AsyncStorage.getItem('notas');
  const notas = crudo ? JSON.parse(crudo) : [];
  notas.push(nueva);
  await AsyncStorage.setItem('notas', JSON.stringify(notas));  // reescribe TODO
}

Ese código tiene tres defectos que no se ven con 20 notas y son fatales con 2.000:

1. Reescribe todo el dataset por cada cambio. Agregar una nota de 200 bytes serializa y escribe el megabyte entero. El costo crece con el total, no con el cambio.
2. No hay atomicidad. Si dos partes de la app hacen ese read-modify-write al mismo tiempo, una pisa a la otra. No hay transacción, no hay bloqueo, no hay error: simplemente falta una nota.
3. Hay un límite duro. En Android, AsyncStorage se apoya en SQLite con un tope por defecto de ~6 MB. Cuando lo cruzás, el setItem falla — y si no estás mirando ese error, la app sigue como si nada con datos viejos.

MMKV: la mejora de una línea

MMKV es clave-valor igual que AsyncStorage, pero está construido sobre JSI (el mecanismo que viste en RNS1): el código JS llama a C++ directamente, sin puente y sin serializar a JSON. Eso lo vuelve síncrono, que es la característica que más cambia el código:

import { MMKV } from 'react-native-mmkv';

export const almacen = new MMKV({
  id: 'app-notas',
  encryptionKey: undefined,   // ver RNS6.3: la clave NO se hardcodea acá
});

// Síncrono: se puede leer durante el primer render, sin useEffect ni spinner
const temaGuardado = almacen.getString('tema') ?? 'sistema';

export function usarTema() {
  const [tema, setTema] = useState(temaGuardado);   // ya tiene el valor real
  const cambiar = (nuevo: string) => {
    almacen.set('tema', nuevo);   // sin await
    setTema(nuevo);
  };
  return { tema, cambiar };
}
Ese detalle —poder leer en el primer render— elimina toda una categoría de bugs visuales: el flash de tema claro antes de aplicar el oscuro, el idioma que parpadea, la pantalla de login que aparece medio segundo aunque haya sesión. Con AsyncStorage necesitás un estado "cargando" para eso. Con MMKV, no existe el problema.

Lo que MMKV no resuelve: sigue siendo clave-valor. No podés preguntar "las notas del último mes con etiqueta trabajo ordenadas por fecha". Para eso hace falta SQL.

SQLite: la opción por defecto para datos reales

import { open } from '@op-engineering/op-sqlite';

const db = open({ name: 'notas.db' });

db.execute(`
  CREATE TABLE IF NOT EXISTS notas (
    id            TEXT PRIMARY KEY,
    titulo        TEXT NOT NULL,
    cuerpo        TEXT NOT NULL DEFAULT '',
    etiqueta      TEXT,
    version       INTEGER NOT NULL DEFAULT 0,
    actualizado   INTEGER NOT NULL,
    borrado       INTEGER NOT NULL DEFAULT 0
  );
`);
db.execute(`CREATE INDEX IF NOT EXISTS idx_notas_etiqueta ON notas(etiqueta, actualizado DESC);`);

// Una consulta real, resuelta por el motor y no por JavaScript
const { rows } = db.execute(
  `SELECT id, titulo, actualizado FROM notas
   WHERE borrado = 0 AND etiqueta = ?
   ORDER BY actualizado DESC LIMIT 50`,
  ['trabajo'],
);
📌 La diferencia que importa no es "SQL vs JSON": es dónde corre el filtro. Con AsyncStorage tenés que traer todo a memoria, parsear el JSON completo y filtrar en JS — en el hilo que también dibuja la pantalla. Con SQLite, el motor usa un índice, toca las páginas necesarias y te devuelve 50 filas. Con 10.000 registros la diferencia es entre una lista instantánea y una app que se congela dos segundos al abrir.

WatermelonDB: SQLite con reactividad y sync incorporado

WatermelonDB pone una capa reactiva encima de SQLite: los componentes se suscriben a consultas y se vuelven a renderizar solos cuando esos datos cambian. Además —y esto es lo que lo vuelve relevante en este módulo— trae un protocolo de sincronización ya diseñado con pullChanges / pushChanges, que es exactamente el par que vamos a construir a mano en RNS6.6.

import { synchronize } from '@nozbe/watermelondb/sync';

await synchronize({
  database,
  pullChanges: async ({ lastPulledAt }) => {
    const r = await fetch(`${API}/sync?desde=${lastPulledAt ?? 0}`);
    const { changes, timestamp } = await r.json();
    return { changes, timestamp };     // created / updated / deleted por tabla
  },
  pushChanges: async ({ changes, lastPulledAt }) => {
    await fetch(`${API}/sync`, {
      method: 'POST',
      body: JSON.stringify({ changes, lastPulledAt }),
    });
  },
});
Adoptar una librería de sync te ahorra el mecanismo (cursores, lotes, tombstones), pero no te ahorra las decisiones: seguís teniendo que definir qué pasa cuando dos dispositivos cambiaron el mismo campo. Por eso este módulo enseña primero el problema y después las herramientas. Si no entendés el conflicto, ninguna librería lo va a resolver bien por vos: va a elegir un default, y ese default va a ser "el último gana".

RNS6.3 Cifrado en reposo y qué NO guardar en el dispositivo

Todo lo que guardás localmente vive en un aparato que se pierde, se roba, se presta y a veces está rooteado. El sistema operativo ayuda —iOS cifra el sandbox con Data Protection si hay código de acceso, Android usa cifrado basado en archivos— pero esas garantías se caen con un dispositivo comprometido, con un backup a la nube mal configurado, o con un usuario que no puso PIN.

⚠️ Lo primero es no guardar. El dato más seguro es el que no está en el teléfono. Antes de preguntarte cómo cifrar algo, preguntate si el flujo necesita que ese algo exista offline. Números completos de tarjeta, documentos de identidad, historia clínica que solo se consulta con red, tokens de larga duración sin rotación: si no lo necesitás offline, no lo persistas.

Para lo que sí tiene que quedarse, hay dos niveles y no son intercambiables:

import * as SecureStore from 'expo-secure-store';
import { MMKV } from 'react-native-mmkv';
import * as Crypto from 'expo-crypto';

const CLAVE_DB = 'clave-cifrado-notas';

// La clave se genera UNA vez en el dispositivo y vive en Keychain/Keystore.
// Nunca se hardcodea, nunca viaja al server, nunca se guarda en AsyncStorage.
async function obtenerClave(): Promise<string> {
  let clave = await SecureStore.getItemAsync(CLAVE_DB);
  if (!clave) {
    const bytes = await Crypto.getRandomBytesAsync(32);
    clave = Array.from(bytes, (b) => b.toString(16).padStart(2, '0')).join('');
    await SecureStore.setItemAsync(CLAVE_DB, clave, {
      keychainAccessible: SecureStore.WHEN_UNLOCKED_THIS_DEVICE_ONLY,
    });
  }
  return clave;
}

export async function abrirAlmacenCifrado() {
  return new MMKV({ id: 'notas-privadas', encryptionKey: await obtenerClave() });
}
El error que anula todo el cifrado: generar la clave en el código (encryptionKey: 'mi-clave-secreta-123') o guardarla junto a los datos. Una clave que está en el bundle JavaScript la extrae cualquiera con un descompilador en cinco minutos — y tu bundle viaja en cada instalación y en cada actualización OTA (RNS7). Cifrar con una clave pública es teatro, no seguridad.

El otro detalle que se pasa por alto son los backups automáticos. Por defecto, iOS puede subir el contenedor de la app a iCloud y Android puede respaldarla en Google Drive. Si tu base local tiene datos sensibles, esa copia sale del dispositivo y del modelo de amenazas que pensaste. Se excluye explícitamente: android:allowBackup="false" (o reglas de dataExtractionRules) y, en iOS, marcando el archivo con NSURLIsExcludedFromBackupKey o guardándolo en un directorio que no se respalda.

📚 Profundizá. Qué significa "cifrado en reposo", por qué una clave derivada de una contraseña no es lo mismo que una clave aleatoria, y por qué el hardware seguro importa: Curso de Ciberseguridad — M01: Criptografía. Este módulo asume esos conceptos y se concentra en dónde ponerlos en una app RN.

RNS6.4 Migraciones de esquema en un dispositivo que no controlás

En el servidor, una migración es un procedimiento con red de contención: la corrés en staging, tenés backup, y si sale mal restaurás y revertís el deploy. En un teléfono no tenés nada de eso.

📌 Por qué una migración fallida en móvil es peor que en el servidor. (1) No podés hacer rollback del dispositivo: la app 2.0 ya se instaló y la base ya se transformó. (2) No tenés backup de los datos del usuario — a menos que el servidor tenga todo, y si lo tuviera no necesitarías offline-first. (3) Las versiones conviven durante meses: siempre hay gente en 1.8, en 1.9 y en 2.0 al mismo tiempo, y a veces la misma persona en dos dispositivos. (4) Si la app crashea al arrancar por una migración rota, el usuario no puede ni abrirla para que le mandes el fix.

El mecanismo básico en SQLite es PRAGMA user_version: un entero que la base guarda por vos y que usás como número de esquema.

-- Leer la versión actual del esquema en el dispositivo
PRAGMA user_version;

-- Migración 1 -> 2: SOLO agregar. Nada destructivo.
ALTER TABLE notas ADD COLUMN etiqueta TEXT;
CREATE INDEX IF NOT EXISTS idx_notas_etiqueta ON notas(etiqueta, actualizado DESC);
PRAGMA user_version = 2;
type Migracion = { version: number; sql: string[] };

const MIGRACIONES: Migracion[] = [
  { version: 1, sql: [`CREATE TABLE notas (id TEXT PRIMARY KEY, titulo TEXT NOT NULL,
                       cuerpo TEXT NOT NULL DEFAULT '', version INTEGER NOT NULL DEFAULT 0,
                       actualizado INTEGER NOT NULL, borrado INTEGER NOT NULL DEFAULT 0)`] },
  { version: 2, sql: [`ALTER TABLE notas ADD COLUMN etiqueta TEXT`] },
  { version: 3, sql: [`CREATE TABLE outbox (id TEXT PRIMARY KEY, entidad TEXT NOT NULL,
                       entidad_id TEXT NOT NULL, op TEXT NOT NULL, payload TEXT NOT NULL,
                       base_version INTEGER, creado INTEGER NOT NULL,
                       intentos INTEGER NOT NULL DEFAULT 0, proximo_intento INTEGER NOT NULL DEFAULT 0,
                       estado TEXT NOT NULL DEFAULT 'pendiente')`] },
];

const ESQUEMA_ESPERADO = MIGRACIONES[MIGRACIONES.length - 1].version;

export function migrar(db: DB) {
  const actual = Number(db.execute('PRAGMA user_version').rows[0].user_version);

  // 🔴 El caso que nadie prevé: app VIEJA abriendo datos NUEVOS
  if (actual > ESQUEMA_ESPERADO) {
    throw new EsquemaDelFuturo(actual, ESQUEMA_ESPERADO);
  }

  for (const m of MIGRACIONES.filter((m) => m.version > actual)) {
    db.transaction(() => {                 // una transacción POR migración
      for (const sentencia of m.sql) db.execute(sentencia);
      db.execute(`PRAGMA user_version = ${m.version}`);
    });
  }
}

La app vieja que abre datos nuevos

Este escenario parece imposible hasta que lo ves. Ocurre en tres situaciones muy reales: un rollback de una actualización OTA (RNS7) que devuelve el bundle JS a una versión anterior sobre una base ya migrada; un usuario que restaura un backup de un teléfono nuevo en uno viejo; o dos dispositivos de la misma persona con versiones distintas compartiendo datos sincronizados.

⚠️ Nunca sigas adelante con un esquema del futuro. Una app que no conoce la columna etiqueta va a hacer SELECT *, va a ignorarla, y en el próximo UPDATE la va a dejar en NULL o va a reescribir la fila sin ese dato. Es pérdida silenciosa de información. La respuesta correcta es detenerse y pedir actualizar: una pantalla que dice "estos datos fueron creados por una versión más nueva de la app, actualizá para seguir", con el botón a la tienda. Es feo, y es infinitamente mejor que corromper.

Las cuatro reglas de las migraciones móviles

1. Solo hacia adelante y solo aditivas. Agregar columnas y tablas es seguro. DROP COLUMN y renombrar no lo son: si tenés que retirar un campo, dejalo muerto una o dos versiones y limpialo cuando el 99% de los usuarios ya migró.
2. Cada migración en su propia transacción. Si la 4 falla, la 3 tiene que quedar aplicada y persistida. Meter todas en una transacción gigante convierte cualquier error en "volver a la versión 1 con 200 MB de datos a medio transformar".
3. Probá el camino largo, no solo el último salto. El bug clásico está en el usuario que venía de la versión 1.2 y salta a la 3.0 sin pasar por las intermedias. Tu test de migraciones tiene que arrancar de una base creada por cada versión publicada, no de una base nueva.
4. Definí el plan B antes, no durante el incidente. Si la migración falla, ¿podés borrar la base local y re-sincronizar desde el servidor? Solo si el servidor tiene absolutamente todo. Si hay datos que únicamente existen en el dispositivo, no hay plan B — y eso hay que saberlo el día del diseño, no el día del crash.

RNS6.5 La cola de operaciones: el corazón de la escritura offline

Cuando el usuario escribe sin conexión, la escritura tiene que ir a algún lado. Ese lado es una cola persistente de operaciones —el patrón outbox— que vive en la misma base local, se escribe en la misma transacción que el dato, y se drena cuando hay red.

CREATE TABLE outbox (
  id              TEXT PRIMARY KEY,   -- UUID: ESTE es el id de idempotencia
  entidad         TEXT NOT NULL,      -- 'nota'
  entidad_id      TEXT NOT NULL,      -- id de la nota (generado en el cliente)
  op              TEXT NOT NULL,      -- 'crear' | 'actualizar' | 'borrar'
  payload         TEXT NOT NULL,      -- JSON del cambio
  payload_version INTEGER NOT NULL,   -- formato del payload, ver más abajo
  base_version    INTEGER,            -- versión sobre la que se editó (conflictos)
  creado          INTEGER NOT NULL,
  intentos        INTEGER NOT NULL DEFAULT 0,
  proximo_intento INTEGER NOT NULL DEFAULT 0,
  estado          TEXT NOT NULL DEFAULT 'pendiente',  -- pendiente|enviando|fallo|muerta
  ultimo_error    TEXT
);
CREATE INDEX idx_outbox_listas ON outbox(estado, proximo_intento);

La regla que hace que esto funcione es que el dato y su operación se escriben juntos, en una sola transacción. Si guardás la nota y después encolás en dos pasos separados, un cierre de la app entre ambos deja una nota que nunca se va a sincronizar — o una operación para una nota que no existe.

import { v7 as uuidv7 } from 'uuid';

export function editarNota(db: DB, id: string, cambios: Partial<Nota>) {
  db.transaction(() => {
    const nota = leerNota(db, id);

    db.execute(
      `UPDATE notas SET titulo = ?, cuerpo = ?, actualizado = ? WHERE id = ?`,
      [cambios.titulo ?? nota.titulo, cambios.cuerpo ?? nota.cuerpo, Date.now(), id],
    );

    db.execute(
      `INSERT INTO outbox (id, entidad, entidad_id, op, payload, payload_version,
                           base_version, creado, proximo_intento)
       VALUES (?, 'nota', ?, 'actualizar', ?, 1, ?, ?, 0)`,
      [uuidv7(), id, JSON.stringify(cambios), nota.version, Date.now()],
    );
  });   // ✅ atómico: o quedan las dos cosas, o ninguna
}

Idempotencia: la propiedad no negociable

💡 La misma operación se va a enviar dos veces. Garantizado. No es una posibilidad remota: es lo que pasa cada vez que el servidor procesa el pedido y la respuesta se pierde en el camino. Desde el cliente, "timeout" y "el servidor no lo recibió" son indistinguibles. Si reintentás —y tenés que reintentar— la operación se aplica dos veces. Una operación idempotente es aquella que aplicada N veces deja el mismo resultado que aplicada una vez.

La forma estándar de conseguirlo es un identificador de operación generado por el cliente, que el servidor guarda y usa para deduplicar:

async function enviarOperacion(op: OperacionOutbox) {
  const r = await fetch(`${API}/notas/${op.entidad_id}`, {
    method: op.op === 'crear' ? 'POST' : op.op === 'borrar' ? 'DELETE' : 'PUT',
    headers: {
      'Content-Type': 'application/json',
      'Idempotency-Key': op.id,              // ← el UUID de la fila del outbox
      'If-Match': String(op.base_version),   // ← control de concurrencia (RNS6.6)
    },
    body: op.op === 'borrar' ? undefined : op.payload,
  });
  return r;
}
📌 El contrato del servidor. Al recibir una Idempotency-Key que ya procesó, el servidor no vuelve a aplicar el cambio: devuelve la respuesta que dio la primera vez. Esto es trabajo de backend, y es la mitad del sistema. Si el backend no lo implementa, ninguna cantidad de cuidado en el cliente evita los duplicados: vas a ver la misma nota tres veces y no vas a poder culpar a React Native.

Orden, reintentos y errores permanentes

Tres decisiones que definen si tu cola es sólida o una fuente de bugs:

Orden. Las operaciones sobre la misma entidad tienen que ir en orden estricto (crear antes que editar, editar antes que borrar). Enviar toda la cola en paralelo es la forma más rápida de que el servidor reciba un "editar la nota X" antes de haberla creado. La regla práctica: paralelizá entre entidades distintas, serializá dentro de cada entidad.
Reintentos con backoff exponencial y jitter. Sin backoff, mil dispositivos que recuperan señal al mismo tiempo martillan tu API a la vez. El jitter (una fracción aleatoria) es lo que evita que todos reintenten sincronizados en el mismo segundo.
Retriable vs permanente. Un 500 o un fallo de red se reintentan. Un 400 (payload inválido), un 403 (sin permiso) o un 422 nunca se van a arreglar solos: reintentarlos para siempre es un bucle infinito que gasta batería y datos. Van a un estado muerta, con su error guardado, y se le muestran al usuario.
const MAX_INTENTOS = 8;

function esRetriable(status: number | null) {
  if (status === null) return true;             // error de red: sí
  if (status === 408 || status === 429) return true;
  return status >= 500;                          // 5xx: sí. 4xx: no.
}

function proximoIntento(intentos: number) {
  const base = Math.min(1000 * 2 ** intentos, 5 * 60_000);   // techo de 5 min
  const jitter = Math.random() * base * 0.3;                 // ±30% de dispersión
  return Date.now() + base + jitter;
}

export async function drenarOutbox(db: DB) {
  const pendientes = db.execute(
    `SELECT * FROM outbox
     WHERE estado IN ('pendiente','fallo') AND proximo_intento <= ?
     ORDER BY creado ASC`,
    [Date.now()],
  ).rows;

  // Serializado por entidad, paralelo entre entidades distintas
  for (const grupo of agruparPor(pendientes, (o) => o.entidad_id)) {
    for (const op of grupo) {
      let status: number | null = null;
      try {
        const r = await enviarOperacion(op);
        status = r.status;
        if (r.ok) { confirmar(db, op, await r.json()); continue; }
        if (r.status === 409) { registrarConflicto(db, op, await r.json()); continue; }
      } catch { /* red caída: status queda en null */ }

      const intentos = op.intentos + 1;
      const muerta = !esRetriable(status) || intentos >= MAX_INTENTOS;
      db.execute(
        `UPDATE outbox SET intentos = ?, estado = ?, proximo_intento = ?, ultimo_error = ?
         WHERE id = ?`,
        [intentos, muerta ? 'muerta' : 'fallo', proximoIntento(intentos),
         String(status ?? 'red'), op.id],
      );
      if (muerta) break;   // no sigas con la misma entidad: el orden ya se rompió
    }
  }
}
Ese break vale oro. Si la operación "crear nota X" murió, mandar el "editar nota X" que venía detrás es garantía de error y de datos inconsistentes. Cuando una operación de una entidad falla de forma permanente, toda la cola de esa entidad queda bloqueada hasta que alguien —el usuario o vos— resuelva el problema. Es incómodo y es correcto.

RNS6.6 Sincronización: pull, push y el modelo de consistencia

Un ciclo de sync tiene dos mitades. El push ya lo construimos: es drenar el outbox. El pull es traer lo que cambió en el servidor desde la última vez, y su pieza central es el cursor.

export async function sincronizar(db: DB) {
  await drenarOutbox(db);            // 1. push primero: mandá lo tuyo

  const cursor = leerCursor(db);      // 2. pull: pedí lo que cambió después del cursor
  let siguiente: string | null = cursor;

  do {
    const r = await fetch(`${API}/sync?cursor=${siguiente ?? ''}&limite=500`);
    const { cambios, proximoCursor, hayMas } = await r.json();

    db.transaction(() => {
      for (const c of cambios) {
        if (c.borrado) {
          db.execute(`DELETE FROM notas WHERE id = ? AND version <= ?`, [c.id, c.version]);
        } else {
          db.execute(
            `INSERT INTO notas (id, titulo, cuerpo, etiqueta, version, actualizado, borrado)
             VALUES (?,?,?,?,?,?,0)
             ON CONFLICT(id) DO UPDATE SET
               titulo=excluded.titulo, cuerpo=excluded.cuerpo, etiqueta=excluded.etiqueta,
               version=excluded.version, actualizado=excluded.actualizado
             WHERE notas.version < excluded.version`,   // nunca pises algo más nuevo
            [c.id, c.titulo, c.cuerpo, c.etiqueta, c.version, c.actualizado],
          );
        }
      }
      guardarCursor(db, proximoCursor);   // cursor y datos: misma transacción
    });

    siguiente = hayMas ? proximoCursor : null;
  } while (siguiente);
}
📌 Tres reglas del pull que se aprenden a los golpes. (1) El cursor lo emite el servidor, nunca lo calcula el cliente con su propio reloj. (2) El cursor se guarda en la misma transacción que los datos que trajo; si no, un cierre a destiempo deja el cursor adelantado y esos cambios no llegan nunca. (3) Los borrados necesitan tombstones: si el servidor simplemente deja de mandar una fila, el cliente no tiene forma de distinguir "se borró" de "no cambió".

Merge por campo: el punto dulce

type Campo = keyof Nota;

function fusionarPorCampo(base: Nota, local: Nota, remoto: Nota) {
  const resultado: Nota = { ...remoto };
  const enDisputa: Campo[] = [];

  for (const campo of ['titulo', 'cuerpo', 'etiqueta'] as Campo[]) {
    const cambioLocal  = local[campo]  !== base[campo];
    const cambioRemoto = remoto[campo] !== base[campo];

    if (cambioLocal && !cambioRemoto) resultado[campo] = local[campo];   // solo yo
    else if (!cambioLocal && cambioRemoto) { /* solo el otro: ya está en remoto */ }
    else if (cambioLocal && cambioRemoto && local[campo] !== remoto[campo]) {
      enDisputa.push(campo);   // los dos, y distinto -> conflicto REAL
    }
  }
  return { resultado, enDisputa };
}
Fijate lo que hace esta función: convierte "conflicto en la nota" en "conflicto en el campo cuerpo". En la práctica, la enorme mayoría de los conflictos son falsos —una persona cambió la etiqueta y otra el título— y el merge por campo los resuelve solo. Solo llegás a molestar al usuario cuando dos personas escribieron sobre la misma cosa. Esa reducción de ruido es la diferencia entre una UI de conflictos usable y una que el usuario aprende a ignorar.

CRDT: qué son y cuándo valen la pena

Un CRDT (tipo de dato replicado sin conflictos) es una estructura diseñada para que las operaciones concurrentes se puedan aplicar en cualquier orden y siempre den el mismo resultado. Un contador CRDT no guarda "el valor": guarda "+1 del dispositivo A, +1 del dispositivo B", y sumar es conmutativo, así que ambos llegan a 2 sin ponerse de acuerdo. Para texto, la idea se extiende dando a cada carácter una identidad, de modo que insertar en la posición 5 desde dos lados produce un documento que contiene ambas inserciones.

Los CRDT no eliminan el conflicto: eliminan la divergencia. Garantizan que todos los dispositivos terminen con el mismo documento — no que ese documento sea el que el usuario quería. Si dos personas reescriben el mismo párrafo, el CRDT produce una fusión determinista de ambas versiones, que puede ser una oración sin sentido. Es exactamente lo correcto para escritura colaborativa en vivo (donde ves lo que el otro tipea) y a menudo incorrecto para edición asincrónica de a uno.

El costo real: cambia el formato de almacenamiento (guardás la estructura CRDT, no el string), cambia el protocolo (mandás actualizaciones binarias, no el documento), agrega metadatos que crecen con la historia de edición, y hace que todo el debugging sea más difícil. Es la respuesta correcta a un problema específico, y una complejidad enorme para todos los demás.

Preguntarle al usuario: la opción honesta

📌 No es una derrota del diseño: es una decisión de producto. Cuando dos versiones de algo valioso entran en conflicto, la persona que escribió ese contenido es la única que sabe cuál importa. Ninguna heurística tuya lo sabe. Preguntar tiene dos condiciones: (1) que el conflicto sea infrecuente —si preguntás todos los días, el usuario va a apretar cualquier botón—, y (2) que nunca destruyas la versión perdedora: se guarda como copia, con su fecha y su origen. Un conflicto bien manejado se puede deshacer; uno mal manejado, no.

RNS6.8 Detección de conectividad: "tiene wifi" no es "hay internet"

La pregunta que hace todo el mundo es isConnected, y responde algo que casi nunca es lo que necesitás: que exista una interfaz de red activa. Eso es verdad cuando el teléfono está enganchado al wifi del hotel que todavía no dejaste pasar por el portal de login, cuando la señal es de una barra y el paquete no llega, o cuando tu backend está caído.

import NetInfo from '@react-native-community/netinfo';

⚠️ El portal cautivo es el enemigo clásico. Wifi de aeropuerto, hotel, bar o subte: hay conexión, hay IP, hay DNS, y todas tus peticiones vuelven con un 200 y el HTML de la pantalla de login. Tu fetch no falla: te devuelve una página web donde esperabas JSON. Si tu código hace await r.json() sin verificar nada, explota con un error de parseo que no se parece en nada a "no hay internet", y el usuario recibe un mensaje incomprensible.

La verificación honesta se hace contra tu backend, con un endpoint barato y una respuesta que puedas validar:

const SONDEO_MS = 4000;

export async function hayInternetDeVerdad(): Promise<boolean> {
  const estado = await NetInfo.fetch();
  if (!estado.isConnected) return false;   // descarte rápido, sin gastar red

  const ctrl = new AbortController();
  const t = setTimeout(() => ctrl.abort(), SONDEO_MS);
  try {
    const r = await fetch(`${API}/salud`, {
      method: 'GET',
      cache: 'no-store',
      headers: { Accept: 'application/json' },
      signal: ctrl.signal,
    });
    if (!r.ok) return false;
    const tipo = r.headers.get('content-type') ?? '';
    if (!tipo.includes('application/json')) return false;   // ← portal cautivo
    const cuerpo = await r.json();
    return cuerpo?.ok === true;                             // ← firma propia
  } catch {
    return false;
  } finally {
    clearTimeout(t);
  }
}
📌 La verdad definitiva es el request que hacés. Ningún flag de conectividad es autoritativo: entre que lo leés y que hacés la llamada, el estado puede cambiar. Usá los flags para explicar ("parece que estás sin conexión") y para decidir cuándo intentar (no drenar la cola si isConnected es false, para ahorrar batería). Pero nunca uses el flag para bloquear una acción del usuario: si él quiere reintentar, dejalo. El resultado real del fetch es el único dato confiable.

RNS6.9 UI de estado offline: cómo no mentirle al usuario

La UI optimista —mostrar el cambio al instante y sincronizar después— es lo que hace que una app offline se sienta rápida. También es la forma más elegante de mentir. El pecado no es ser optimista: es ser optimista y después no contar cuando salió mal.

El patrón que rompe la confianza: el usuario escribe una nota en el subte, ve el toast verde de "Guardado ✓", cierra la app tranquilo. Tres días después la nota no está en su computadora. En algún momento la sincronización falló con un 422 y el error se tragó en un catch vacío. El usuario no perdió una nota: perdió la confianza en que tu app guarde algo. Eso no se recupera con un fix.

La solución no es dejar de ser optimista, es tener estados y mostrarlos. Cuatro estados por ítem alcanzan:

  const texto = {

La frase importa más que el ícono. "Guardado en este dispositivo" es honesto, es corto, y le enseña al usuario el modelo mental correcto: existe una copia local y existe una remota. La gente entiende perfectamente esa idea —la usa con las fotos del celular todos los días— siempre que se la digas. El problema nunca fue que el usuario no entienda: es que no le contamos.
Y nunca hagas un rollback visual silencioso. Si el servidor rechazó el cambio y tu UI vuelve al valor anterior sin decir nada, para el usuario eso es la app "borrándole" lo que escribió. Si tenés que revertir, mostralo con una explicación y ofrecé el contenido perdido: "Este cambio fue rechazado por el servidor. Copiá tu texto antes de descartarlo."

RNS6.11 Errores clásicos que se pagan caro

Confiar en el reloj del dispositivo

El reloj del teléfono lo controla el usuario. Puede estar mal por zona horaria, puede estar desincronizado, y puede estar adelantado a propósito (es un truco conocido para saltear temporizadores en juegos). Si tu resolución de conflictos es "gana el timestamp más alto" y ese timestamp lo genera el cliente, un dispositivo con el reloj adelantado gana todos los conflictos para siempre y borra el trabajo de los demás sin que nadie entienda por qué. 
// 🔴 Mal: el orden depende del reloj de cada dispositivo
const nota = { ...datos, actualizado: Date.now() };

// 🟢 Mejor: el reloj local sirve para la UI; el orden lo define el servidor
const nota = {
  ...datos,
  actualizado_local: Date.now(),   // solo para mostrar "hace 5 minutos"
  base_version: versionConocida,   // ESTO es lo que ordena y detecta conflictos
};

// 🟢 Y si necesitás tiempo real, medí el desfase contra el servidor
let desfaseMs = 0;
async function calibrarReloj() {
  const t0 = Date.now();
  const r = await fetch(`${API}/hora`);
  const t1 = Date.now();
  const servidor = Number(r.headers.get('x-server-time'));
  desfaseMs = servidor - (t0 + (t1 - t0) / 2);   // corrige la mitad del viaje
}
export const ahora = () => Date.now() + desfaseMs;

Necesitar el id del servidor antes de tenerlo

El usuario crea una nota offline y le agrega tres adjuntos. Los adjuntos necesitan referenciar la nota. Pero la nota todavía no existe en el servidor, así que no tiene id. El diseño se rompe entero.

📌 La regla: los ids los genera el cliente, siempre. UUID v4 si no te importa el orden, o UUID v7 si querés que además ordenen por tiempo de creación (v7 lleva el timestamp en los bits altos, lo que mantiene los índices de la base ordenados y evita la fragmentación que produce v4). El servidor acepta el id que le manda el cliente; a lo sumo guarda su propio id interno en paralelo. Un sistema offline-first donde el servidor asigna los ids no es offline-first: es online con un caché.

Colas que crecen sin límite

const TOPE_OUTBOX = 5_000;

export function encolar(db: DB, op: NuevaOperacion) {
  // 1. Compactar: dos ediciones seguidas del mismo campo de la misma entidad
  //    que todavía no salieron se colapsan en una sola.
  if (op.op === 'actualizar') {
    const previa = db.execute(
      `SELECT id, payload FROM outbox
       WHERE entidad_id = ? AND op = 'actualizar' AND estado = 'pendiente'
       ORDER BY creado DESC LIMIT 1`,
      [op.entidad_id],
    ).rows[0];
    if (previa) {
      const fusionado = { ...JSON.parse(previa.payload), ...JSON.parse(op.payload) };
      db.execute(`UPDATE outbox SET payload = ?, creado = ? WHERE id = ?`,
                 [JSON.stringify(fusionado), Date.now(), previa.id]);
      return;
    }
  }

  // 2. Tope duro: mejor avisar que degradarse en silencio
  const { total } = db.execute(`SELECT COUNT(*) AS total FROM outbox`).rows[0];
  if (total >= TOPE_OUTBOX) throw new ColaLlena(total);

  db.execute(`INSERT INTO outbox (...) VALUES (...)`, [/* ... */]);
}
El escenario que rompe apps reales: un técnico de campo trabaja tres semanas sin señal. Vuelve con 40.000 operaciones encoladas. Al abrir la app, el drenado intenta mandarlas todas, el dispositivo se queda sin memoria, o el servidor lo bloquea por rate limit y los reintentos con backoff hacen que la sincronización tarde horas. Sin compactación ni tope, ese usuario está atrapado. La compactación no es una micro-optimización: es lo que hace que la cola sea acotada.

No versionar el formato del payload

La cola es persistente: sobrevive a la actualización de la app. Eso significa que la versión 2.0 puede encontrarse con operaciones encoladas por la 1.8, con un JSON de otra forma. Si tu código asume el formato actual, va a fallar al deserializar operaciones viejas y el usuario va a perder todo lo que había escrito antes de actualizar. Por eso el payload_version del esquema de RNS6.5: sin él, cada actualización de la app es una ruleta.

🧑‍🎓 Worked Example — la app de notas que pierde datos

Una app de notas guarda offline y sincroniza al reconectar. Un usuario escribe en el teléfono (en el subte) y en la tablet (en casa sin wifi) sobre la misma nota. Al reconectar los dos, uno de los dos textos desaparece. No hay error, no hay aviso, no hay forma de recuperarlo. Soporte recibe tres tickets por semana y ninguno se puede reproducir.

Paso 1 — Nombrar el bug antes de arreglarlo. Se mira el backend y aparece en una línea:

-- El endpoint PUT /notas/:id, tal como está hoy
UPDATE notas SET titulo = $1, cuerpo = $2, actualizado = now() WHERE id = $3;

No hay condición sobre la versión. El último PUT que llega pisa lo anterior. No es un bug de React Native ni de la cola: es ausencia de control de concurrencia. El cliente hace exactamente lo que el servidor le permite hacer.

Paso 2 — Ubicar el producto en el espectro. Las notas se crean offline, son texto escrito por una persona y no existen en ningún otro lado. Son irreemplazables. Eso pone la app en el nivel 3 de la tabla de RNS6.1, con todo lo que implica. La decisión se documenta: no es "agreguemos versiones", es "asumimos el costo de offline-first completo".

Paso 3 — Ids en el cliente. Se pasa a UUID v7 generado en el dispositivo al crear la nota. Desaparecen los ids temporales, el reemplazo posterior, y las referencias rotas de los adjuntos.

import { v7 as uuidv7 } from 'uuid';

export function crearNota(db: DB, titulo: string) {
  const id = uuidv7();          // el id definitivo, decidido offline

async function confirmarOConflicto(db: DB, op: OperacionOutbox) {
  const r = await enviarOperacion(op);

  if (r.ok) {
    const { version } = await r.json();
    db.transaction(() => {
      db.execute(`UPDATE notas SET version = ?, estado_sync = 'sincronizado' WHERE id = ?`,
                 [version, op.entidad_id]);
      db.execute(`DELETE FROM outbox WHERE id = ?`, [op.id]);
    });
    return;
  }

  if (r.status === 409) {
    const remoto = await r.json();
    const local  = leerNota(db, op.entidad_id);
    const base   = leerSnapshot(db, op.entidad_id, op.base_version);

    const { resultado, enDisputa } = fusionarPorCampo(base, local, remoto);

    db.transaction(() => {
      if (enDisputa.length === 0) {
        // Cambiaron campos distintos: se fusiona solo y se reintenta con la
        // versión nueva. El usuario no se entera de nada, y está bien.
        aplicarNota(db, { ...resultado, version: remoto.version });
        db.execute(`UPDATE outbox SET base_version = ?, payload = ?, estado = 'pendiente'
                    WHERE id = ?`,
                   [remoto.version, JSON.stringify(resultado), op.id]);
      } else {
        // Conflicto real: NO se elige en silencio. Se guardan las dos y se avisa.
        db.execute(
          `INSERT INTO conflictos (id, nota_id, campos, version_local, version_remota,
                                   cuerpo_local, cuerpo_remoto, detectado)
           VALUES (?,?,?,?,?,?,?,?)`,
          [uuidv7(), op.entidad_id, enDisputa.join(','), local.version, remoto.version,
           local.cuerpo, remoto.cuerpo, Date.now()],
        );
        db.execute(`UPDATE notas SET estado_sync = 'conflicto' WHERE id = ?`, [op.entidad_id]);
        db.execute(`UPDATE outbox SET estado = 'muerta' WHERE id = ?`, [op.id]);
      }
    });
  }
}

Checkpoint — ¿lo tenés claro?

¿Por qué "la última escritura gana" es una decisión peligrosa aunque el timestamp lo genere el servidor?

Porque mueve el problema sin resolverlo. Usar el reloj del servidor elimina un riesgo real —el reloj del dispositivo es manipulable y suele estar desfasado— pero no toca el problema de fondo: el servidor no tiene ninguna información para decidir cuál de los dos contenidos es el que el usuario quiere conservar. Descarta uno por el orden de llegada de los paquetes, que es un criterio arbitrario, y lo hace sin dejar rastro. LWW es una elección correcta cuando el dato es reemplazable y de bajo valor (una preferencia, un "leído", la posición de scroll): perder una versión de eso no le cuesta nada a nadie. Sobre contenido que una persona escribió, LWW es pérdida de datos con otro nombre. El criterio práctico: preguntate si podrías explicarle a un usuario, sin vergüenza, por qué su texto no está.

Tu app usa el nivel 2 del espectro (escritura optimista con cola). ¿Qué tres cosas tenés que tener sí o sí, y qué pasa si falta alguna?

(1) Ids generados en el cliente. Sin ellos, no podés referenciar una entidad que todavía no existe en el servidor, y todo lo que dependa de esa entidad —adjuntos, relaciones, ediciones posteriores— se rompe o necesita un remapeo frágil. (2) Idempotencia con una clave de operación que el servidor deduplique. Sin ella, cada timeout de red produce un duplicado, porque desde el cliente "no llegó" y "llegó pero se perdió la respuesta" son el mismo evento. (3) Distinción entre errores retriables y permanentes. Sin ella, un 422 se reintenta para siempre (bucle infinito que gasta batería y datos) o se descarta en silencio (pérdida de datos), y las dos salidas son malas. Falta cualquiera de las tres y no tenés nivel 2: tenés nivel 1 con una capa de optimismo que miente.

¿Por qué una migración de esquema fallida en móvil es peor que en el servidor, y cómo se mitiga?

Por cuatro razones acumuladas. No hay rollback: la app nueva ya se instaló y la base ya se transformó; no podés "volver el deploy". No hay backup de los datos del usuario, a menos que el servidor tenga todo — y si lo tuviera, no necesitarías offline-first. Las versiones conviven meses: siempre hay gente en varias versiones al mismo tiempo, y a veces la misma persona en dos dispositivos distintos. Y si la app crashea al arrancar, el usuario no puede ni abrirla para recibir el arreglo; la única salida es desinstalar, que borra sus datos. Se mitiga con migraciones solo aditivas y hacia adelante, una transacción por migración (para que las anteriores queden firmes), tests que arrancan desde una base creada por cada versión publicada y no solo desde una nueva, un plan B definido de antemano (¿se puede borrar y re-sincronizar? solo si el servidor tiene absolutamente todo), y una verificación explícita del caso "esquema del futuro": si user_version es mayor que la que la app conoce, hay que detenerse y pedir actualizar, nunca seguir leyendo datos que no entendés.

Resumen ejecutivo

  • El espectro tiene cuatro niveles (online-only, caché de lectura, escritura con cola, offline-first completo) y cada uno cuesta un orden de magnitud más que el anterior. Elegí uno a propósito. La mayoría de las apps no necesita el nivel 3, y el error caro es llegar a él sin darse cuenta.
  • Leer offline es caché; escribir offline es un sistema distribuido. Esa frontera es donde aparecen la cola, la idempotencia, el versionado y los conflictos.
  • El almacén se elige por volumen y forma de consulta: AsyncStorage para preferencias, MMKV (síncrono, sobre JSI) como su reemplazo rápido, SQLite como opción por defecto para datos reales, y WatermelonDB cuando querés reactividad y sync incorporado. El componente que más te ata no es la base: es el motor de sincronización.
  • Cifrado: primero no guardes lo que no necesitás offline. Los secretos van a Keychain/Keystore; la base se cifra con una clave generada en el dispositivo que vive ahí — nunca en el código. Excluí la base de los backups automáticos a la nube.
  • Migraciones: solo aditivas y hacia adelante, una transacción por migración, tests desde cada versión publicada, y detenerse ante un esquema del futuro en vez de corromper datos que no entendés.
  • La cola de operaciones se escribe en la misma transacción que el dato. Necesita orden por entidad, backoff exponencial con jitter, distinción entre errores retriables y permanentes, compactación y un tope duro.
  • La idempotencia no es opcional: la misma operación se va a enviar dos veces, siempre. Una clave de operación generada por el cliente y deduplicada por el servidor es la mitad del sistema, y vive en el backend.
  • Versionado > LWW. Un entero por fila y un WHERE version = ? convierten la pérdida silenciosa en un 409 explícito. Detectar no es resolver, pero sin detectar no hay nada que resolver.
  • Cinco estrategias de conflicto: LWW, merge por campo, append-only, CRDT y preguntar al usuario. El merge por campo resuelve solo la mayoría de los conflictos falsos; preguntar es honesto si es infrecuente y nunca destruís la versión perdedora.
  • "Tiene wifi" ≠ "hay internet". El portal cautivo devuelve 200 con HTML. Verificá contra tu propio endpoint validando el content-type y una firma propia. Y recordá que el único dato autoritativo es el resultado del request.
  • La UI optimista sin estados es una mentira. "Guardado en este dispositivo" en vez de "Guardado"; los fallos se muestran y no se pueden ignorar; nunca hagas un rollback visual silencioso.
  • El background sync es un bonus, no un contrato: iOS no garantiza nada y Android lo garantiza "eventualmente" con OEMs que lo rompen. Sincronizá al abrir, al volver del segundo plano, al recuperar conexión y con pull-to-refresh: eso es el 95% del valor.
  • Los tres errores clásicos: confiar en el reloj del dispositivo, necesitar ids del servidor antes de tenerlos (usá UUID v7 en el cliente), y colas que crecen sin límite.

🧠 Autoevaluación

1. Tu app encola escrituras offline y las reenvía al recuperar la conexión. Los usuarios reportan mensajes duplicados. ¿Cuál es la causa más probable?

Es el escenario canónico: desde el cliente, "el servidor no lo recibió" y "lo recibió pero se perdió la respuesta" son indistinguibles — en los dos casos ves un timeout. Como tenés que reintentar, la operación se aplica dos veces. La solución es una Idempotency-Key generada por el cliente (el UUID de la fila del outbox) que el servidor guarda y usa para deduplicar, devolviendo la respuesta original en lugar de volver a aplicar el cambio. Ojo: es trabajo de backend; ningún cuidado del lado del cliente lo compensa.

2. Estás diseñando la resolución de conflictos de una app de notas personales. Los conflictos son poco frecuentes pero el texto es irreemplazable. ¿Cuál es la mejor estrategia?

El merge por campo resuelve solo la mayoría de los casos —una persona cambió el título y otra el cuerpo no es un conflicto real— y reserva la pregunta para cuando dos textos compiten de verdad, que es cuando el usuario es el único que puede decidir. LWW por reloj del servidor arregla el problema equivocado: elimina el riesgo del reloj manipulable pero sigue descartando texto en silencio. Y los CRDT son la respuesta correcta a la edición colaborativa en vivo: acá cambiarías el formato de almacenamiento, el protocolo y todo el debugging por un caso del 0,3%, y encima el resultado del merge automático en prosa puede ser un párrafo que nadie escribió.

3. Tu app depende de sincronizar en segundo plano para que los datos estén frescos cuando el usuario la abre. ¿Qué expectativa es realista?

En iOS, BGAppRefreshTask es oportunista: el sistema decide según tu uso histórico, el Modo de bajo consumo y la preferencia de actualización en segundo plano — un usuario que abre la app una vez por semana puede no recibir ninguna ejecución. Los push silenciosos también están limitados y se pueden descartar por diseño. En Android, WorkManager garantiza ejecución eventual, pero Doze, los App Standby Buckets y varios fabricantes con "optimizaciones de batería" agresivas la rompen. minimumInterval es una sugerencia, no un contrato. Lo que sí controlás: sincronizar al abrir, al volver del segundo plano, al recuperar conexión y con pull-to-refresh — eso cubre el 95% del valor.

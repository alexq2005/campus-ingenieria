RNS1 — La Nueva Arquitectura por dentro: JSI, Fabric y TurboModules

RNS1.0 Por qué este módulo

Buscá hoy "cómo funciona React Native" y vas a encontrar, en la enorme mayoría de los resultados, la misma explicación: "hay un puente asíncrono que serializa mensajes en JSON entre el hilo de JavaScript y el hilo nativo". Artículos de blog, respuestas de Stack Overflow, videos de conferencias, cursos pagos, y —lo más peligroso— asistentes de IA entrenados sobre todo eso.

Ese puente ya no existe. No está desactivado, no está deprecado, no está detrás de un flag: fue eliminado del framework.

💡 La tesis del módulo. React Native reemplazó su capa de comunicación entera. La pieza central es JSI, una API de C++ que le da a JavaScript referencias directas a objetos nativos a los que puede llamar de forma síncrona. Sobre JSI se construyeron TurboModules (los módulos nativos) y Fabric (el renderer). Codegen genera el pegamento tipado entre los dos mundos. Entendé JSI y el resto se deduce.

Y hay una razón de coyuntura muy concreta para estudiarlo ahora:

VersiónQué pasó
0.68La Nueva Arquitectura se puede activar. Experimental, dolorosa, poca gente la usa.
0.76Pasa a ser el default. Dejó de ser experimental.
0.82El Bridge se elimina por completo. Poner newArchEnabled=false ya no hace nada: la propiedad se ignora y no hay camino de vuelta.
0.86 (junio 2026)Todo proyecto nuevo arranca bridgeless por default, con la Strict TypeScript API: los tipos se generan directamente del código fuente vía Codegen.

Del lado de Expo, la Nueva Arquitectura viene activada por default en el managed workflow desde el SDK 52. O sea: si arrancaste un proyecto en los últimos dos años, ya estás corriendo sobre esto, sepas o no cómo funciona.

📌 Lo que separa hoy a un senior de React Native no es saber más componentes. Es poder abrir un stack trace que menciona TurboModuleRegistry, jsi::Runtime o ShadowNode y saber en qué capa está el problema. Este módulo es el mapa de esas capas.

RNS1.1 La arquitectura vieja y su problema

Para entender por qué se rompió todo y se rehízo, hay que entender bien qué se rompió. La arquitectura original de React Native (2015–2024) tenía tres hilos y un cuello de botella entre ellos.

  ARQUITECTURA VIEJA (hasta 0.81)

  ┌──────────────────┐     ┌───────────────┐     ┌──────────────────┐
  │   JS THREAD      │     │    BRIDGE     │     │  NATIVE / UI     │
  │                  │     │               │     │                  │
  │  Tu código React │ ──▶ │  serializa a  │ ──▶ │  UIKit / Android │
  │  JSC o Hermes    │     │     JSON      │     │      Views       │
  │                  │ ◀── │  cola batched │ ◀── │  eventos, touch  │
  └──────────────────┘     │  ASÍNCRONA    │     └──────────────────┘
           │               └───────────────┘              ▲
           │                                              │
           ▼                                              │
  ┌──────────────────┐                                    │
  │  SHADOW THREAD   │  Yoga calcula el layout  ──────────┘
  │  (árbol en C++)  │
  └──────────────────┘

El Bridge era una cola de mensajes. Cada vez que JS quería hacer algo nativo —montar una vista, leer una preferencia, pedir la posición del scroll— el mensaje se serializaba a JSON, se metía en un lote y se entregaba del otro lado en algún momento posterior.

// Lo que realmente viajaba por el Bridge: arrays de números y strings.
// Cada llamada era [moduleId, methodId, args, callbackId], en JSON.
[
  [7],                       // ids de módulos
  [3],                       // ids de métodos
  [["persist", "user_42"]],  // argumentos, YA serializados
  118                        // id del callback que espera del otro lado
]

Podías verlo con tus propios ojos, y todavía vale la pena hacerlo una vez en un proyecto viejo para entender la magnitud:

// Solo en la arquitectura vieja. En bridgeless esto ya no existe.
import MessageQueue from 'react-native/Libraries/BatchedBridge/MessageQueue';

MessageQueue.spy(info => {
  console.log(info.type === 0 ? 'JS→N' : 'N→JS', info.module, info.method);
});

// Al scrollear una FlatList veías CIENTOS de líneas por segundo.
// Cada una: serializar, encolar, esperar el próximo frame, deserializar.

Las tres restricciones que imponía

1. Todo era asíncrono, siempre. No existía forma de que JS le preguntara algo a lo nativo y recibiera la respuesta en la misma línea. Ni siquiera "¿cuánto mide esta vista?". Todo era callback o promesa, incluso lo trivial.
2. Todo pasaba por JSON. Un ArrayBuffer de una imagen, un objeto grande de configuración, una lista de 500 filas: todo se convertía a texto, se copiaba, y se parseaba del otro lado. El costo crecía con el tamaño del dato, no con la complejidad de la operación.
3. Todos los módulos nativos se cargaban al arrancar. Tu app importaba 40 librerías nativas y las 40 se inicializaban en el arranque, aunque el usuario nunca abriera la pantalla de la cámara.
Los síntomas que producía, y que seguramente sufriste:
  • Listas que se "cortan": scrolleás rápido y ves celdas en blanco. El JS no llega a mandar las filas nuevas por el Bridge antes del próximo frame.
  • Gestos con lag: arrastrás un elemento y sigue al dedo con retraso, porque cada evento de touch cruzaba el puente, JS decidía, y la respuesta volvía a cruzarlo.
  • Arranque lento: segundos de splash screen inicializando módulos nativos que quizás nunca ibas a usar.
  • Saltos de layout al medir una vista: como measure() era asíncrono, el primer render se hacía con datos viejos y después corregía.
// El síntoma clásico de la arquitectura vieja: medir para posicionar.
// El componente se pintaba MAL una vez y después se corregía. Flicker.
function Tooltip({ anchorRef }: { anchorRef: React.RefObject<View> }) {
  const [pos, setPos] = useState<{ x: number; y: number } | null>(null);

  useEffect(() => {
    // measure() cruzaba el Bridge: la respuesta llegaba uno o más frames después
    anchorRef.current?.measure((x, y, w, h, pageX, pageY) => {
      setPos({ x: pageX, y: pageY + h });   // ...y recién acá re-renderizabas
    });
  }, []);

  if (!pos) return null;                     // frame 1: nada
  return <View style={{ top: pos.y, left: pos.x }} />;  // frame 2+: aparece
}
Nada de esto era un error de diseño estúpido. En 2015, el Bridge fue una decisión brillante: permitió que un motor de JavaScript cualquiera hablara con dos plataformas nativas distintas sin acoplarse a ninguna. El precio —serialización y asincronía— era aceptable para las apps de esa época. Diez años y varios órdenes de magnitud de expectativa después, dejó de serlo.

RNS1.2 JSI: la pieza que hizo posible todo lo demás

JSI (JavaScript Interface) es una API de C++ ligera que abstrae "un motor de JavaScript". No es un puente: es una interfaz directa. Con JSI, código C++ puede crear valores de JS, leerlos, llamar funciones de JS, y —lo importante— instalar objetos propios dentro del runtime de JS.

🔌 La analogía. El Bridge era un servicio de correo: escribías una carta (JSON), la despachabas, y en algún momento llegaba una respuesta. JSI es un teléfono con línea directa: agarrás el objeto del otro lado y lo llamás. La conversación pasa en el mismo instante, sin sobres ni traducción.

Los tipos fundamentales de JSI son pocos y se entienden rápido:

#include <jsi/jsi.h>
using namespace facebook;

// jsi::Runtime  → el motor de JS en sí (Hermes, JSC, V8: da igual)
// jsi::Value    → un valor de JS visto desde C++ (number, string, object, ...)
// jsi::Object   → un objeto de JS
// jsi::Function → una función de JS que C++ puede LLAMAR
// jsi::String   → un string de JS

void ejemplo(jsi::Runtime &rt) {
  // Crear valores de JS desde C++
  jsi::Value numero = jsi::Value(42);
  jsi::String texto = jsi::String::createFromUtf8(rt, "hola");

  // Leer una propiedad global de JS
  jsi::Value consola = rt.global().getProperty(rt, "console");

  // Llamar a una función de JS desde C++, SIN serializar nada
  jsi::Function log = consola.asObject(rt).getPropertyAsFunction(rt, "log");
  log.call(rt, texto);
}

HostObject: el objeto nativo que JavaScript cree suyo

La pieza que cambia el juego es jsi::HostObject. Es una clase de C++ que se expone al runtime de JS como si fuera un objeto normal. Cuando JS lee una propiedad de ese objeto, se ejecuta tu código C++ en ese mismo instante, en el mismo hilo, sin cola ni serialización.

// Un almacén clave-valor nativo expuesto a JS como un objeto común.
class AlmacenRapido : public jsi::HostObject {
 public:
  // Se llama cuando JS hace: almacen.loQueSea
  jsi::Value get(jsi::Runtime &rt, const jsi::PropNameID &nombre) override {
    auto prop = nombre.utf8(rt);

    if (prop == "leer") {
      return jsi::Function::createFromHostFunction(
        rt, nombre, 1,
        [this](jsi::Runtime &rt, const jsi::Value &, const jsi::Value *args, size_t n)
            -> jsi::Value {
          if (n < 1) return jsi::Value::undefined();
          std::string clave = args[0].asString(rt).utf8(rt);
          std::string valor = db_.get(clave);         // acceso nativo, acá mismo
          return jsi::String::createFromUtf8(rt, valor);  // ← retorno SÍNCRONO
        });
    }
    return jsi::Value::undefined();
  }

 private:
  MiBaseDeDatos db_;
};

Y del lado de JavaScript, se usa así:

// almacen es un HostObject: NO es un proxy, NO hay JSON, NO hay promesa.
declare const almacen: { leer(clave: string): string };

const tema = almacen.leer('tema');   // ← devuelve el valor. Ahora. Acá.
console.log(tema);                   // 'oscuro'

// Con el Bridge esto era, obligatoriamente:
//   const tema = await NativeModules.Almacen.leer('tema');
// y el await costaba, como mínimo, un ciclo del event loop.
📌 El cambio conceptual. Antes, JS enviaba mensajes a lo nativo. Ahora, JS tiene punteros a objetos nativos y los invoca. Esa diferencia es la que habilita MMKV leyendo en microsegundos, Reanimated corriendo animaciones en el hilo de UI, Skia dibujando desde JS, y todo el resto de la Nueva Arquitectura.

Instalar un HostObject en el runtime es una función de una línea que corre al arrancar la app:

// Se llama una vez, cuando el runtime de JS está listo.
void instalar(jsi::Runtime &rt) {
  auto almacen = std::make_shared<AlmacenRapido>();
  rt.global().setProperty(
      rt, "__AlmacenRapido",
      jsi::Object::createFromHostObject(rt, almacen));
}
// A partir de acá, en JS: global.__AlmacenRapido.leer('clave')
Con la línea directa viene la responsabilidad. Una llamada síncrona por JSI bloquea el hilo de JS mientras dura. Si tu HostObject hace una consulta de red o lee 20 MB de disco de forma síncrona, congelaste la app entera. JSI te da la posibilidad de ser síncrono; no te obliga. Lo síncrono es para operaciones de microsegundos: leer una preferencia, consultar un caché en memoria, obtener una medida. Todo lo demás sigue siendo asíncrono, y está bien que lo sea.
JSI es agnóstico del motor. Ese fue el otro gran objetivo: React Native ya no está casado con JavaScriptCore. Hermes es hoy el motor por defecto, pero la app podría correr sobre otro motor y JSI seguiría siendo la misma API. Esa independencia es la que permitió que Hermes evolucionara sin reescribir el framework.

RNS1.3 TurboModules: módulos nativos perezosos y tipados

Un módulo nativo es código Swift/Kotlin/ObjC/Java que exponés a JavaScript: el acceso a la cámara, al almacenamiento seguro, al Bluetooth. Los viejos NativeModules viajaban por el Bridge. Los TurboModules viajan por JSI.

Así se veía un módulo nativo viejo desde JS — sin tipos, todo asíncrono, y con un fallo silencioso si el módulo no estaba:

import { NativeModules } from 'react-native';

// NativeModules es un objeto plano SIN tipos: TypeScript no sabe nada de acá.
const { InfoDispositivo } = NativeModules;

// Si el módulo no está enlazado, InfoDispositivo es undefined y esto
// explota en runtime con "Cannot read property 'obtenerId' of undefined".
const id = await InfoDispositivo.obtenerId();   // any, siempre asíncrono

Un TurboModule empieza por su spec: un archivo de TypeScript que declara el contrato. Este archivo no es documentación — es la fuente de verdad desde la que Codegen genera las interfaces nativas.

// src/specs/NativeInfoDispositivo.ts
// El prefijo "Native" en el nombre del archivo NO es decorativo:
// es cómo Codegen encuentra los specs.
import type { TurboModule } from 'react-native';
import { TurboModuleRegistry } from 'react-native';

export interface Spec extends TurboModule {
  // Síncrono: posible SOLO en la Nueva Arquitectura
  obtenerId(): string;
  obtenerNivelBateria(): number;

  // Asíncrono cuando la operación lo amerita
  obtenerHuellaSegura(): Promise<string>;

  // Los tipos permitidos son un subconjunto: sin uniones arbitrarias,
  // sin genéricos, sin tipos que Codegen no pueda mapear a nativo.
  configurar(opciones: { modo: string; reintentos: number }): void;
}

// getEnforcing lanza un error CLARO al importar si el módulo no está.
// Nada de "undefined" tres pantallas después.
export default TurboModuleRegistry.getEnforcing<Spec>('InfoDispositivo');
// Uso: tipado de punta a punta, y la llamada síncrona es real.
import InfoDispositivo from './src/specs/NativeInfoDispositivo';

const id: string = InfoDispositivo.obtenerId();          // sin await
const bateria: number = InfoDispositivo.obtenerNivelBateria();

// TypeScript te corrige acá, no en un crash del QA:
// InfoDispositivo.obtenerIdd();  // ← Property 'obtenerIdd' does not exist

Carga perezosa: el módulo se inicializa cuando lo tocás

Ésta es la diferencia que más se nota en el arranque. Los NativeModules viejos se registraban todos al iniciar la app. Un TurboModule se instancia la primera vez que JS accede a él.

// Simplificación del registro: nada se construye hasta el primer acceso.
std::shared_ptr<TurboModule> TurboModuleManager::get(const std::string &nombre) {
  auto it = cache_.find(nombre);
  if (it != cache_.end()) return it->second;   // ya instanciado

  auto modulo = crearModulo(nombre);           // ← recién ACÁ se construye
  cache_[nombre] = modulo;
  return modulo;
}
Si tu app importa 40 librerías nativas y el usuario abre la pantalla de inicio, se inicializan las 3 o 4 que esa pantalla usa. Las otras 36 no cuestan nada hasta que hagan falta. Ahí está buena parte del 43% de mejora en arranque en frío que reporta la gente que migró.

El error que más se ve al escribir un spec: usar tipos de TypeScript que Codegen no sabe traducir. Uniones como string | number, genéricos propios, Record<string, unknown>, enums complejos, tipos recursivos. El compilador de TS te deja escribirlos y Codegen falla después, con un mensaje que no siempre apunta al lugar correcto. Regla práctica: si no lo podés expresar en Java y en Objective-C sin pensar, no va en un spec.

RNS1.4 Fabric: el nuevo renderer

Fabric es el sistema de renderizado. Su cambio estructural es que el shadow tree vive en C++ y es compartido por las dos plataformas, en lugar de estar duplicado en Java y Objective-C.

  FABRIC: de tu JSX a píxeles

  React Element Tree      React Shadow Tree        Host View Tree
  (JavaScript)            (C++, inmutable)         (UIView / android.view)
  ┌──────────────┐        ┌──────────────┐         ┌──────────────┐
  │  <View>      │  ───▶  │  ShadowNode  │  ───▶   │   UIView     │
  │   <Text>     │        │  + Yoga      │         │   UILabel    │
  └──────────────┘        └──────────────┘         └──────────────┘
       RENDER                  COMMIT                   MOUNT
   (reconciliación)      (layout + promoción)     (aplicar mutaciones)

El renderizado ocurre en tres fases, y conviene tener los nombres claros porque son los que aparecen en los perfiles y en los errores:

1. Render. React reconcilia y produce un árbol de elementos. Fabric crea el React Shadow Tree correspondiente en C++, donde cada ShadowNode es inmutable: cambiar algo genera un nodo nuevo, no muta el existente.
2. Commit. Se calcula el layout con Yoga sobre el árbol nuevo y se lo promueve a ser el árbol vigente. Como los nodos son inmutables, se puede tener más de un árbol vivo a la vez sin corromper nada.
3. Mount. Se diffean el árbol viejo y el nuevo, se genera una lista de mutaciones (crear vista, actualizar prop, mover, borrar) y se aplican a las vistas nativas reales en el hilo de UI.
// La idea clave: los ShadowNode son inmutables y se clonan.
// Por eso pueden coexistir dos versiones del árbol al mismo tiempo.
class ShadowNode {
 public:
  // "Cambiar" un nodo = crear uno nuevo compartiendo lo que no cambió.
  ShadowNode::Unshared clone(const ShadowNodeFragment &fragment) const;

  const Props::Shared &getProps() const;
  const SharedShadowNodeList &getChildren() const;
  const LayoutMetrics &getLayoutMetrics() const;   // ← lo que calculó Yoga
};

Por qué recién ahora React Native aprovecha React 18/19

Las concurrent features de React —Suspense, startTransition, useDeferredValue— necesitan que React pueda preparar un render en segundo plano, pausarlo, descartarlo o priorizar otro. Con el Bridge eso era imposible: las mutaciones ya habían sido despachadas por una cola asíncrona y no se podían "deshacer". Con el shadow tree inmutable de Fabric, sí.

import { useDeferredValue, useState, useTransition } from 'react';
import { TextInput, FlatList, Text } from 'react-native';

function BuscadorDeProductos({ productos }: { productos: Producto[] }) {
  const [texto, setTexto] = useState('');
  // El input responde con prioridad ALTA; la lista se recalcula con BAJA.
  const textoDiferido = useDeferredValue(texto);
  const [pendiente, startTransition] = useTransition();

  const filtrados = useMemo(
    () => productos.filter(p => p.nombre.includes(textoDiferido)),
    [productos, textoDiferido]
  );

  return (
    <>
      <TextInput value={texto} onChangeText={setTexto} />
      {pendiente && <Text>Buscando…</Text>}
      <FlatList data={filtrados} renderItem={renderProducto} />
    </>
  );
}
// En la arquitectura vieja esto "andaba" pero no priorizaba de verdad:
// el trabajo igual se encolaba en el Bridge y el input se trababa igual.

Medición síncrona de layout

Recordá el Tooltip con flicker de RNS1.1. Con Fabric, el layout de un nodo se puede consultar en el momento, porque el árbol y sus LayoutMetrics están del lado de C++, accesibles vía JSI:

import { useLayoutEffect, useRef, useState } from 'react';
import { View } from 'react-native';

function Tooltip({ anchorRef }: { anchorRef: React.RefObject<View> }) {
  const [pos, setPos] = useState<{ x: number; y: number } | null>(null);

  // Con Fabric, measure resuelve contra el shadow tree en C++.
  // La posición está lista ANTES de que el frame se pinte: sin flicker.
  useLayoutEffect(() => {
    anchorRef.current?.measure((x, y, w, h, pageX, pageY) => {
      setPos({ x: pageX, y: pageY + h });
    });
  }, []);

  if (!pos) return null;
  return <View style={{ position: 'absolute', top: pos.y, left: pos.x }} />;
}
Fabric también trae view flattening: si un <View> existe solo para agrupar y no aporta nada visual (sin fondo, sin borde, sin opacidad, sin manejo de eventos), Fabric no crea la vista nativa. Es una optimización que antes se hacía a mano evitando anidar; ahora la hace el renderer. Por eso una jerarquía profunda hoy cuesta bastante menos que hace tres años.
Cuándo NO te va a salvar Fabric. Concurrent rendering prioriza trabajo de React; no acelera tu código. Si tu renderItem hace un JSON.parse de 2 MB por fila, o recalculás un array de 50.000 elementos en cada render, Fabric va a hacer exactamente el mismo trabajo lento, mejor priorizado. La arquitectura sube el techo; no arregla algoritmos. Eso es RNS2.

RNS1.5 Codegen: el pegamento se genera, no se escribe

Entre TypeScript y C++/Java/ObjC hay un abismo de tipos. Codegen lo cruza automáticamente: lee tus specs y genera las interfaces nativas que la implementación tiene que cumplir.

// package.json de tu librería o app
{
  "name": "mi-libreria-nativa",
  "codegenConfig": {
    "name": "MiLibreriaSpec",
    "type": "all",
    "jsSrcsDir": "src/specs",
    "android": {
      "javaPackageName": "com.milibreria"
    }
  }
}

Ese bloque codegenConfig es, en la práctica, la señal más confiable de que una librería soporta la Nueva Arquitectura. Lo vamos a usar en el worked example.

# Codegen corre solo durante el build, pero se puede invocar a mano
# para ver qué produce (es lo primero que hago cuando algo no cierra):
npx react-native codegen

# Android: el output queda bajo
#   android/app/build/generated/source/codegen/
# iOS: se genera al instalar pods
cd ios && RCT_NEW_ARCH_ENABLED=1 bundle exec pod install

De un spec de TypeScript sale una clase base abstracta en C++ (y sus equivalentes en Java y ObjC) que tu implementación debe heredar:

// GENERADO por Codegen a partir de NativeInfoDispositivo.ts. No se edita.
class JSI_EXPORT NativeInfoDispositivoCxxSpecJSI : public TurboModule {
 public:
  virtual jsi::String obtenerId(jsi::Runtime &rt) = 0;
  virtual double obtenerNivelBateria(jsi::Runtime &rt) = 0;
  virtual jsi::Value obtenerHuellaSegura(jsi::Runtime &rt) = 0;
  virtual void configurar(jsi::Runtime &rt, jsi::Object opciones) = 0;

 protected:
  NativeInfoDispositivoCxxSpecJSI(std::shared_ptr<CallInvoker> jsInvoker);
};
📌 El valor real de Codegen no es ahorrar tipeo: es que el contrato se verifica en tiempo de compilación. Si renombrás un método en el spec y no lo actualizás en Kotlin, la app no compila. En la arquitectura vieja ese mismo error era un undefined is not a function que descubría un usuario en producción tres semanas después.

La Strict TypeScript API (0.86)

Históricamente, los tipos públicos de React Native se mantenían a mano, aparte del código real. El resultado predecible: tipos que decían una cosa y una implementación que hacía otra, props que existían en el código pero no en los tipos, y tipos que sobrevivían a APIs ya eliminadas.

Desde 0.86, la Strict TypeScript API genera los tipos públicos directamente del código fuente, usando la misma maquinaria de Codegen.

// Con la Strict API, los tipos vienen del código real.
// Consecuencia práctica #1: si una prop no es pública, TS ya no te deja usarla.
import { View } from 'react-native';

<View
  style={{ flex: 1 }}
  // @ts-expect-error — props internas que "andaban" ya no tipan
  collapsable={false}
/>;

// Consecuencia práctica #2: importar de rutas internas deja de funcionar.
// ❌ import Foo from 'react-native/Libraries/Components/Foo';
// ✅ import { Foo } from 'react-native';
Al adoptar la Strict API vas a ver errores de TypeScript nuevos en código que "andaba bien". Casi siempre son reales: estabas usando algo interno, algo deprecado, o una prop cuyo tipo estaba mal declarado hace años. Es la clase de migración que duele una tarde y evita bugs durante años. Migrá archivo por archivo, no de golpe.

RNS1.6 Bridgeless: qué significa en la práctica

"Bridgeless" es el estado final: no hay Bridge instanciado en absoluto. No es "el Bridge está ahí pero no lo usamos": el objeto no existe. En 0.82 se eliminó del framework, y desde 0.86 todo proyecto nuevo arranca así por default.

⚠️ Poner newArchEnabled=false en 0.82+ no hace nada. La propiedad se ignora silenciosamente. Es el error más caro de esta migración: un equipo pone el flag, la app compila, asume que volvió al sistema viejo, y pasa dos días depurando por qué el comportamiento no cambia. No hay camino de vuelta. La única decisión disponible es en qué versión te quedás.

Éste es el código que deja de funcionar. Vale la pena grepearlo en tu proyecto hoy:

// ❌ 1. El objeto global del Bridge: no existe
console.log(global.__fbBatchedBridge);           // undefined

// ❌ 2. Espiar la cola de mensajes: no hay cola
import MessageQueue from 'react-native/Libraries/BatchedBridge/MessageQueue';

// ❌ 3. Llamadas síncronas por el hook viejo del Bridge

// ⚠️ 4. NativeModules sigue "andando" gracias a la capa de interop...
import { NativeModules } from 'react-native';
const { MiModuloViejo } = NativeModules;
// ...pero sin carga perezosa, sin tipos, sin llamadas síncronas,
// y es una capa de compatibilidad, no un destino.

// ✅ Lo que corresponde hoy
import MiModulo from './specs/NativeMiModulo';

Del lado nativo, lo que se rompe es todo lo que tocaba RCTBridge directamente:

# Y en JavaScript:

💡 La capa de interop es una rampa, no un puente nuevo. React Native incluye un interop layer que hace que muchos NativeModules y ViewManagers viejos sigan funcionando sobre la Nueva Arquitectura. Sirve para migrar sin parar el mundo. Pero un módulo que corre por interop no obtiene ninguno de los beneficios: no es perezoso, no es síncrono, no está tipado. Si medís la mejora de arranque y no aparece, la primera hipótesis es que tus módulos siguen entrando por la rampa.

RNS1.7 Migración: qué se rompe y cómo detectarlo antes

El ecosistema está hoy en ~90% de compatibilidad. Ese número suena tranquilizador hasta que el 10% restante es justo la librería sobre la que se apoya tu feature principal.

LibreríaVersión mínima compatibleNota
React Navigation7.2+Soporte pleno; revisá también react-native-screens
Reanimated3.5.1+Nació sobre JSI: es de las que mejor se llevan con Fabric
Gesture Handler2.16.2+Va de la mano con la versión de Reanimated
Vision Camera4.0+Frame processors ya usan JSI directamente

Los cuatro modos de fallar, en orden de frecuencia

1. Librería nativa sin mantener. No tiene codegenConfig, no actualizó su podspec, el repo no tiene commits desde hace dos años. Es el caso más común y el más caro.
2. Módulo nativo propio escrito contra RCTBridge. Lo escribiste vos o alguien que ya no está. La buena noticia: lo controlás. La mala: hay que reescribirlo como TurboModule.
3. ViewManagers a mano. Componentes nativos personalizados registrados a la vieja usanza. Necesitan pasar a componentes de Fabric con su propio spec.
4. Suposiciones sobre el orden y el timing. Código que "andaba" porque el Bridge era asíncrono y le daba un frame de gracia. Sin esa latencia accidental, aparecen carreras que siempre estuvieron ahí. Es el más difícil de encontrar porque no rompe la compilación: rompe en producción, a veces.
El error de proceso más caro: actualizar React Native y descubrir los problemas compilando. El inventario de compatibilidad se hace antes de tocar la versión, sobre el package.json que ya tenés. Toma veinte minutos y te dice si la migración es de una tarde o de un mes.

RNS1.9 Cómo verificar en qué arquitectura corre tu app

Nunca lo asumas. Verificalo. Hay tres niveles de verificación, y los tres tienen sentido:

Nivel 1 — Configuración (lo que debería pasar):

# android/gradle.properties
newArchEnabled=true          # ⚠️ en 0.82+ esto se IGNORA: siempre es true

# ios/Podfile.properties.json o variable de entorno
RCT_NEW_ARCH_ENABLED=1

# Versión efectiva de React Native — el dato que manda
npx react-native --version
cat node_modules/react-native/package.json | grep '"version"'

Nivel 2 — Runtime (lo que realmente pasa):

// src/diagnostico/arquitectura.ts
// Estos flags globales son INTERNOS y sin garantía de estabilidad entre
// versiones. Por eso se aíslan acá: si cambian, se toca un solo archivo.
export type Arquitectura = {
  bridgeless: boolean;
  fabric: boolean;
  motor: string;
  version: string;
};

export function inspeccionarArquitectura(): Arquitectura {
  const g = globalThis as Record<string, unknown>;
  return {
    bridgeless: g.RN$Bridgeless === true,
    fabric: g.nativeFabricUIManager != null,
    motor: g.HermesInternal != null ? 'Hermes' : 'otro',
    version: require('react-native/package.json').version,
  };
}

// En el arranque de la app, en builds de desarrollo:
if (__DEV__) console.table(inspeccionarArquitectura());

Nivel 3 — Prueba automatizada (que no se degrade sola):

// __tests__/arquitectura.test.ts
// Lo que no está en CI, se rompe en silencio dentro de seis meses.
import { inspeccionarArquitectura } from '../src/diagnostico/arquitectura';

describe('arquitectura de ejecución', () => {
  it('corre bridgeless con Fabric', () => {
    const a = inspeccionarArquitectura();
    expect(a.bridgeless).toBe(true);
    expect(a.fabric).toBe(true);
  });

  it('usa Hermes', () => {
    expect(inspeccionarArquitectura().motor).toBe('Hermes');
  });
});
Estos tests no corren con el mock de Jest por defecto: en el entorno de Node esos globals no existen. Van en la suite de integración sobre dispositivo/emulador (Detox o similar), donde hay un runtime de React Native de verdad. Un test que pasa contra un mock de sí mismo no verifica nada — y es exactamente el tipo de falso positivo que este módulo intenta enseñarte a detectar.

🧑‍🎓 Worked Example — "actualizamos a 0.82 y la app no arranca"

Una app de logística en producción, React Native 0.79, ~180.000 usuarios. El equipo actualiza a 0.82 para tomar los parches de seguridad. La app compila en Android y crashea al abrir la pantalla de escaneo. En iOS ni siquiera compila. La pantalla de escaneo usa rn-barcode-legacy@2.3.1, una librería sin commits desde hace dos años.

Paso 1 — Leer el error real, no el primero de la pila.

Paso 2 — Inventario: qué módulos nativos hay y cuáles están listos. No preguntes librería por librería en Google. Escaneá el node_modules buscando las señales objetivas de soporte:

// scripts/auditar-arquitectura.mjs
// Heurística: una librería lista para la Nueva Arquitectura declara
// codegenConfig, y/o su podspec usa install_modules_dependencies.
import { readdirSync, readFileSync, existsSync } from 'node:fs';
import { join } from 'node:path';

const RAIZ = 'node_modules';
const paquetes = [];

for (const nombre of readdirSync(RAIZ)) {
  if (nombre.startsWith('.')) continue;
  if (nombre.startsWith('@')) {
    for (const sub of readdirSync(join(RAIZ, nombre))) {
      paquetes.push(join(nombre, sub));
    }
  } else {
    paquetes.push(nombre);
  }
}

const filas = [];

for (const p of paquetes) {
  const dir = join(RAIZ, p);
  const pkgPath = join(dir, 'package.json');
  if (!existsSync(pkgPath)) continue;

  const pkg = JSON.parse(readFileSync(pkgPath, 'utf8'));
  const esNativo =
    existsSync(join(dir, 'android')) ||
    existsSync(join(dir, 'ios')) ||
    readdirSync(dir).some(f => f.endsWith('.podspec'));
  if (!esNativo) continue;

  const tieneCodegen = Boolean(pkg.codegenConfig);
  const podspec = readdirSync(dir).find(f => f.endsWith('.podspec'));
  const podspecNuevo = podspec
    ? readFileSync(join(dir, podspec), 'utf8').includes('install_modules_dependencies')
    : false;

  filas.push({
    paquete: p,
    version: pkg.version,
    codegen: tieneCodegen ? '✅' : '❌',
    podspec: podspecNuevo ? '✅' : '❌',
    veredicto: tieneCodegen || podspecNuevo ? 'OK' : 'REVISAR',
  });
}

filas.sort((a, b) => a.veredicto.localeCompare(b.veredicto));
console.table(filas);
console.log(`\n${filas.filter(f => f.veredicto === 'REVISAR').length} de ${filas.length} requieren revisión manual.`);
node scripts/auditar-arquitectura.mjs

Decisión del equipo:

  • react-native-fs → C. Existe alternativa mantenida y la superficie de uso era chica (leer y escribir archivos). Una semana.
  • rn-barcode-legacy → B. Es el corazón del producto, la librería está muerta, no hay reemplazo con la misma precisión de lectura, y la app usa tres métodos de las cuarenta y pico que expone. Se escribe un TurboModule que envuelve el SDK nativo directamente.

Paso 4 — El shim: spec primero, implementación después.

// src/specs/NativeEscaner.ts
// Superficie MÍNIMA: exactamente los 3 métodos que la app usa.
// Cada método extra acá es código nativo que mantenemos para siempre.
import type { TurboModule } from 'react-native';
import { TurboModuleRegistry } from 'react-native';

export interface Spec extends TurboModule {
  iniciar(config: { formatos: string[]; torch: boolean }): Promise<void>;
  detener(): void;
  estaDisponible(): boolean;   // síncrono: es una consulta de microsegundos
}

export default TurboModuleRegistry.getEnforcing<Spec>('Escaner');
// src/escaner/index.ts
// Fachada: el resto de la app NO importa el TurboModule directamente.
// Si mañana volvemos a una librería de terceros, se toca solo este archivo.
import Native from '../specs/NativeEscaner';

export const escaner = {
  disponible: () => Native.estaDisponible(),
  iniciar: (formatos: string[] = ['QR', 'EAN_13'], torch = false) =>
    Native.iniciar({ formatos, torch }),
  detener: () => Native.detener(),
};
📌 La fachada no es ceremonia. Es lo que hace que la próxima decisión sea barata. Toda la app llama a escaner.iniciar(); ninguna pantalla sabe si abajo hay un TurboModule propio, una librería de terceros o un mock. Cambiar de opción B a opción A el día que aparezca un reemplazo digno cuesta un archivo.

Checkpoint — ¿lo tenés claro?

Si el Bridge ya no existe, ¿por qué NativeModules sigue funcionando en muchas apps?

Por la capa de interop. React Native incluye una capa de compatibilidad que hace que los NativeModules y ViewManagers escritos para la arquitectura vieja sigan siendo invocables sobre la Nueva Arquitectura. Es una rampa de migración deliberada, no un Bridge disfrazado: no hay serialización a JSON ni cola asíncrona por debajo. Pero el módulo que pasa por ahí no obtiene ninguno de los beneficios: se inicializa en el arranque en vez de perezosamente, no puede exponer métodos síncronos, y no tiene contrato verificado por Codegen. Si migraste y no ves la mejora de arranque, la primera hipótesis es que tus módulos siguen entrando por la rampa. Y todo lo que tocaba RCTBridge directamente desde código nativo sí se rompe, sin rampa que valga.

¿Por qué JSI es un requisito para que Fabric y TurboModules existan, y no al revés?

Porque JSI es lo que permite que exista una referencia a un objeto nativo del lado de JS, en vez de un identificador que hay que despachar por una cola. TurboModules son, literalmente, HostObjects instalados en el runtime: sin JSI no hay forma de que InfoDispositivo.obtenerId() devuelva un valor en la misma expresión. Fabric necesita lo mismo para consultar el shadow tree en C++ de forma síncrona (medir layout) y para que React pueda mandar mutaciones sin pasar por una cola que no se puede cancelar. JSI es la capa 0; los otros dos son consumidores de esa capa. Por eso una librería como Reanimated, que ya usaba JSI desde antes, se adaptó a la Nueva Arquitectura mucho mejor que una que hablaba solo el protocolo del Bridge.

Estás en 0.83, ponés newArchEnabled=false, recompilás y el comportamiento no cambia. ¿Qué está pasando?

Exactamente lo esperado: desde 0.82 esa propiedad se ignora. El Bridge fue eliminado del framework, así que no hay un sistema viejo al que volver — el flag quedó como un residuo que no configura nada. Perder tiempo depurando por qué "no toma el flag" es uno de los errores más caros de esta migración, porque es una hipótesis que se siente razonable y consume días. La verificación correcta no es leer gradle.properties (config), sino consultar el runtime: global.RN$Bridgeless y global.nativeFabricUIManager. Config y runtime son cosas distintas, y cuando difieren, la que manda es el runtime. La única decisión real disponible en 0.82+ es en qué versión de React Native te quedás, no qué arquitectura usás.

Resumen ejecutivo

  • El Bridge —cola asíncrona con serialización a JSON— fue eliminado en 0.82. Casi todo el material que vas a encontrar en internet lo explica como si todavía existiera. newArchEnabled=false hoy se ignora: no hay camino de vuelta.
  • JSI es la capa 0: una API de C++ que le da a JS referencias directas a objetos nativos (HostObject) invocables de forma síncrona. Todo lo demás se apoya en eso. Con esa potencia viene la responsabilidad: una llamada síncrona lenta bloquea el hilo de JS.
  • TurboModules = módulos nativos sobre JSI, con carga perezosa (de ahí buena parte del arranque más rápido) y contrato tipado verificado en build. getEnforcing falla claro y temprano; NativeModules fallaba con undefined en producción.
  • Fabric = renderer con el shadow tree inmutable en C++, compartido entre plataformas. Habilita concurrent rendering de verdad, medición síncrona de layout y view flattening. No acelera tu código lento: sube el techo.
  • Codegen genera las interfaces nativas desde los specs de TS/Flow. Un desajuste de contrato rompe la compilación en vez de romper en producción. La Strict TypeScript API de 0.86 extiende la idea a los tipos públicos, generándolos del código fuente.
  • Números de producción reportados: 43% más rápido el arranque en frío, 39% mejor rendimiento de render, 25% menos memoria. Ecosistema ~90% compatible (React Navigation 7.2+, Reanimated 3.5.1+, Gesture Handler 2.16.2+, Vision Camera 4.0+, Detox; Expo SDK 52+ por default).
  • Migrar se planifica con un inventario antes de tocar la versión: escaneá node_modules buscando codegenConfig y podspecs modernos. Tres salidas por paquete roto — actualizar, envolver con un shim, reemplazar — y la cuarta (no hacer nada) se elige sola si no decidís.
  • Lo que NO cambió: seguís escribiendo React. Componentes, hooks, StyleSheet, navegación: idénticos. Esto es infraestructura.
  • Verificá siempre en runtime, no en la config: global.RN$Bridgeless y global.nativeFabricUIManager, aislados en un módulo propio y cubiertos por un test de integración sobre dispositivo.

2. Migraste a la Nueva Arquitectura y el arranque en frío casi no mejoró, aunque los benchmarks públicos hablan de ~43%. ¿Cuál es la primera hipótesis?

Buena parte de la mejora de arranque viene de que los TurboModules se instancian al primer uso en vez de todos al iniciar. Un módulo que corre por la capa de interop sigue registrándose como antes: no es perezoso, no es síncrono y no está tipado. La capa de interop es una rampa de migración, no un destino — verificalo auditando cuáles de tus dependencias nativas declaran codegenConfig.

3. Escribís un TurboModule y exponés leerPerfilCompleto(): string como método síncrono, porque JSI lo permite. Internamente lee un archivo de 8 MB del disco. ¿Cuál es el problema?

JSI te da la posibilidad de ser síncrono, no la obligación. Una llamada síncrona corre en el hilo de JS y lo bloquea hasta terminar: 8 MB de disco son decenas o cientos de milisegundos de app congelada. Lo síncrono es para operaciones de microsegundos —leer una preferencia, consultar un caché en memoria, obtener una medida—; todo lo que involucre disco grande, red o cómputo pesado sigue siendo asíncrono, y está bien que lo sea.

RNS5 — Navegación y arquitectura de app

RNS5.0 Por qué este módulo

En el M04 aprendiste a mover al usuario de una pantalla a otra. Este módulo va por otra cosa: en una app móvil, el árbol de navegación es la arquitectura. No es una capa de presentación que después se ajusta — es la estructura que decide qué componentes se montan, cuáles siguen vivos cuando no se ven, qué estado sobrevive a un cambio de pestaña, qué se pierde cuando el sistema operativo mata el proceso, y qué pasa cuando alguien abre un link a la pantalla 5 sin haber pasado por las cuatro anteriores.

💡 La tesis del módulo. En la web, navegar reemplaza el árbol: cambiás de URL y el componente anterior se desmonta. En móvil, navegar apila: la pantalla anterior sigue montada, viva y ejecutando detrás de la nueva. Casi todos los bugs raros de una app grande —datos viejos al volver, memoria que sube y no baja, sockets duplicados, timers fantasma, pantallas que parpadean al arrancar— salen de asumir el modelo web sobre un runtime que se comporta como el móvil.

Y decidir mal acá es caro de una forma particular: refactorizar un componente lleva una tarde, mover el estado de autenticación de un contexto a otro lleva una semana, pero reorganizar el árbol de navegadores de una app en producción toca todas las pantallas a la vez. Es la decisión menos reversible que vas a tomar en la primera semana del proyecto.

Contexto 2026. La Nueva Arquitectura es el default desde React Native 0.76. React Navigation 7.2+ y Expo SDK 52+ son compatibles con ella. Para apps nuevas sobre Expo, el enfoque recomendado hoy es Expo Router (ruteo basado en archivos), que por debajo es React Navigation — no un competidor, sino una capa de convenciones encima.

RNS5.1 El modelo mental: el árbol de navegadores

Hay cuatro primitivas y todo lo demás es composición de esas cuatro:

📌 La regla del árbol. Las pantallas que se presentan encima de todo (modales globales, cámara, onboarding, paywall) van en el stack raíz, no dentro de una pestaña. Si el modal de búsqueda vive dentro de HomeStack, al abrirlo desde la pestaña "Pedidos" vas a saltar de pestaña sin querer, y la barra de tabs va a quedar visible debajo de un modal que debería taparla.

Con React Navigation 7 el árbol se puede declarar de forma estática, que es la forma nueva y la que mejor tipa:

// navigation/root.tsx — React Navigation 7, API estática
import { createNativeStackNavigator } from '@react-navigation/native-stack';
import { createBottomTabNavigator } from '@react-navigation/bottom-tabs';
import { createStaticNavigation } from '@react-navigation/native';

const AppTabs = createBottomTabNavigator({
  screens: {
    Inicio:  { screen: HomeStack,    options: { title: 'Inicio' } },
    Pedidos: { screen: PedidosStack, options: { title: 'Pedidos' } },
    Perfil:  { screen: PerfilStack,  options: { title: 'Perfil' } },
  },
});

const RootStack = createNativeStackNavigator({
  screens: {
    App:      { screen: AppTabs,  options: { headerShown: false } },
    Buscador: { screen: Buscador, options: { presentation: 'modal' } },
    Camara:   { screen: Camara,   options: { presentation: 'fullScreenModal' } },
  },
});

export const Navigation = createStaticNavigation(RootStack);
// App.tsx:  export default () => <Navigation />
La API estática existe justamente porque el árbol es arquitectura: al declararlo como datos en vez de como JSX condicional, React Navigation puede derivar los tipos, la configuración de deep linking y la lista de rutas sin que vos las escribas tres veces. La API dinámica (<Stack.Screen />) sigue existiendo y sigue siendo válida — la necesitás cuando el árbol depende de datos en tiempo de ejecución.

RNS5.2 El ciclo de vida de una pantalla en móvil

Este es el corazón del módulo. Si te llevás una sola idea, que sea esta:

⚠️ Cuando hacés push, la pantalla anterior NO se desmonta. Se queda montada, con su estado, sus efectos activos, sus timers corriendo, sus suscripciones abiertas y su lista de 500 elementos en memoria. Simplemente dejó de estar visible. Lo mismo pasa al cambiar de pestaña: la pestaña que dejaste sigue viva. En React web, useEffect(() => {...}, []) con cleanup es suficiente porque desmontar es lo normal. Acá, desmontar es la excepción.

Comparado con lo que ya sabés de la web:

Acción del usuarioWeb (SPA con router)React Native
Ir de A a BA se desmonta, B se montaA sigue montada, B se monta encima
Volver de B a AA se vuelve a montar (efectos corren de nuevo)B se desmonta, A recibe foco — sus efectos NO vuelven a correr
Cambiar de pestañaDesmonta y montaAmbas quedan montadas
App a backgroundNada (la pestaña sigue)Todo sigue montado; el SO puede matar el proceso sin aviso
Volver del backgroundNadaO sigue todo igual, o arranca de cero — no hay término medio

La fila que rompe todo es la segunda: volver no re-monta. Por eso el patrón que en web funciona —cargar datos en useEffect con array vacío— acá produce datos viejos para siempre.

Los eventos que sí existen

React Navigation expone el ciclo de vida de navegación, que es distinto del ciclo de vida de React. Instrumentarlo es la primera herramienta de diagnóstico:

// hooks/useLifecycleLogger.ts — pegalo en una pantalla sospechosa
import { useEffect } from 'react';
import { useNavigation, useRoute } from '@react-navigation/native';

export function useLifecycleLogger() {
  const navigation = useNavigation();
  const route = useRoute();
  const tag = `[${route.name}#${route.key.slice(-4)}]`;

  useEffect(() => {
    console.log(tag, 'MOUNT');
    const offFocus = navigation.addListener('focus', () => console.log(tag, 'focus'));
    const offBlur  = navigation.addListener('blur',  () => console.log(tag, 'blur'));
    return () => {
      offFocus(); offBlur();
      console.log(tag, 'UNMOUNT');   // si esto NO aparece, ahí está tu fuga
    };
  }, [navigation, tag]);
}

Navegá Lista → Detalle → atrás → Detalle → atrás y mirá la consola. Vas a ver MOUNT de Lista una sola vez, y pares MOUNT/UNMOUNT de Detalle. El #key te dice que cada push crea una instancia nueva de la pantalla: dos Detalle apilados son dos componentes distintos con estado independiente.

useEffect vs useFocusEffect

import { useCallback, useEffect } from 'react';
import { useFocusEffect } from '@react-navigation/native';   // o desde 'expo-router'

function Pantalla() {
  // ❌ Corre UNA vez, al montar. Si el usuario vuelve acá dentro de una hora,
  //    sigue mostrando lo que se cargó hace una hora.
  useEffect(() => { cargarDatos(); }, []);

  // ✅ Corre cada vez que la pantalla GANA foco, y limpia cuando lo PIERDE.
  useFocusEffect(
    useCallback(() => {
      const sub = suscribirseAUbicacion();
      return () => sub.remove();     // se ejecuta al perder foco, no al desmontar
    }, [])
  );
}
El error #1 con useFocusEffect: pasarle una función inline. useFocusEffect(() => {...}) recibe una callback nueva en cada render, y el hook la interpreta como "cambió el efecto": se limpia y se vuelve a ejecutar en cada render. Un fetch en loop infinito. Siempre envolvela en useCallback con sus dependencias explícitas. Habilitá la regla react-hooks/exhaustive-deps con additionalHooks: "useFocusEffect" para que ESLint te lo marque. 
// .eslintrc.json — que el linter entienda useFocusEffect
{
  "rules": {
    "react-hooks/exhaustive-deps": [
      "warn",
      { "additionalHooks": "(useFocusEffect|useAnimatedStyle)" }
    ]
  }
}

El foco de navegación y el estado de la app son ejes independientes. Si el usuario minimiza la app, la pantalla visible no dispara blur: sigue "enfocada" dentro de su navegador. Una pantalla con un websocket que solo escucha useFocusEffect va a mantener la conexión abierta con la app en background y se va a comer la batería. La combinación correcta es las dos cosas. 
// hooks/useActiveEffect.ts — activo = enfocado Y app en primer plano
import { useCallback, useEffect, useRef } from 'react';
import { AppState } from 'react-native';
import { useFocusEffect } from '@react-navigation/native';

export function useActiveEffect(start: () => () => void) {
  const stop = useRef<null | (() => void)>(null);

  const arrancar = useCallback(() => { if (!stop.current) stop.current = start(); }, [start]);
  const frenar   = useCallback(() => { stop.current?.(); stop.current = null; }, []);

  useFocusEffect(useCallback(() => {
    arrancar();
    const sub = AppState.addEventListener('change', (s) => {
      s === 'active' ? arrancar() : frenar();
    });
    return () => { sub.remove(); frenar(); };
  }, [arrancar, frenar]));
}

Congelar lo que no se ve

react-native-screens permite congelar las pantallas sin foco: dejan de re-renderizar aunque su estado cambie. No se desmontan (no perdés el scroll ni el estado), pero paran de gastar CPU cuando un contexto global se actualiza.

// index.js — antes de registrar el componente raíz
import { enableFreeze } from 'react-native-screens';
enableFreeze(true);

// …o por pantalla, en React Navigation 7:
<Stack.Screen name="Feed" component={Feed} options={{ freezeOnBlur: true }} />
⚠️ Congelar NO arregla fugas. Una pantalla congelada no re-renderiza, pero sus setInterval, sus listeners y su memoria siguen exactamente donde estaban. Si freezeOnBlur "arregló" tu bug de performance, lo que hiciste fue tapar un efecto que nunca debió correr en background. Arreglá el efecto; usá el freeze como optimización encima, no como parche.
En React Navigation 7 la opción unmountOnBlur de tabs y drawer quedó deprecada en favor de popToTopOnBlur (verificá el nombre exacto en la versión que tengas instalada). El cambio tiene una razón de fondo: desmontar al perder foco casi nunca es la solución correcta — es una forma cara de limpiar efectos que deberían limpiarse solos, y encima destruye la posición de scroll y el estado del formulario que el usuario esperaba encontrar.

RNS5.3 Expo Router vs React Navigation puro

Expo Router toma la idea de Next.js —la estructura de carpetas es el árbol de rutas— y la aplica sobre React Navigation. No reemplaza nada: genera la configuración de navegadores a partir del filesystem.

app/
├── _layout.tsx                 → RootStack (envuelve TODO)
├── +not-found.tsx              → ruta 404
├── (auth)/                     → grupo: NO aparece en la URL
│   ├── _layout.tsx             → Stack de auth
│   ├── login.tsx               → /login
│   └── registro.tsx            → /registro
├── (app)/                      → grupo con guard de sesión
│   ├── _layout.tsx             → aquí vive el <Redirect> si no hay sesión
│   └── (tabs)/
│       ├── _layout.tsx         → Tabs
│       ├── index.tsx           → /
│       ├── pedidos/
│       │   ├── index.tsx       → /pedidos
│       │   └── [id].tsx        → /pedidos/42
│       └── perfil.tsx          → /perfil
└── modal.tsx                   → /modal   (presentation: 'modal')

Los _layout.tsx son los navegadores. Los paréntesis marcan grupos: organizan archivos y permiten aplicar un layout compartido sin agregar un segmento a la URL. Los corchetes son segmentos dinámicos.

Recomendación práctica para 2026: app nueva sobre Expo → Expo Router. Vas a escribir menos configuración, el deep linking sale bien por default y el equipo que viene de Next.js arranca en una tarde. App existente con React Navigation funcionando → no migres por moda: la migración toca cada pantalla y el beneficio es de conveniencia, no de capacidad.

Cuándo el imperativo sigue siendo mejor

1. El árbol depende de datos. Una app B2B donde los módulos habilitados vienen del backend por tenant. Con archivos tenés que crear todas las rutas y esconder las que no aplican; con código simplemente no las renderizás.
2. Flujos con estado propio y salida controlada. Un checkout de cinco pasos donde el paso 3 solo existe si el paso 2 devolvió cierta cosa, y donde volver atrás debe recalcular. Un stack armado a mano modela eso mejor que cinco archivos que fingen ser independientes.
3. Brownfield. React Native embebido en una app nativa existente, donde el contenedor de navegación lo maneja iOS o Android y RN solo dibuja algunas pantallas.
4. Rutas que no deberían ser URLs. Un debug menu interno, un flujo de recuperación de cuenta con token de un solo uso: si la ruta es un archivo, la ruta existe y es alcanzable. A veces eso es exactamente lo que no querés.

RNS5.4 Estado de navegación: params, global y contexto por pila

Hay tres lugares donde puede vivir el estado que una pantalla necesita, y elegir mal es la causa silenciosa de la mitad de los bugs de restauración:

DóndeVive mientras…Se serializaPara qué sirve
Params de rutaLa ruta esté en el historial✅ Sí (y debe poder)Identificar qué mira la pantalla: ids, filtros, modo
Estado global (store/caché)Viva el procesoDependeDatos compartidos: sesión, carrito, entidades cacheadas
Contexto por pilaViva ese navegador❌ NoEstado de un flujo: wizard, borrador, selección múltiple
El error clásico: pasar el objeto entero por params. 
// ❌ Mal
navigation.navigate('Detalle', { pedido });   // objeto de 40 KB con Dates y funciones

// ✅ Bien
navigation.navigate('Detalle', { pedidoId: pedido.id });
Los params son el estado de navegación, y el estado de navegación se serializa a JSON para persistirlo y restaurarlo. Un objeto con Date, Map, una función o una referencia circular rompe esa serialización — React Navigation te avisa en desarrollo con "Non-serializable values were found in the navigation state". Además, ese objeto queda congelado: si el pedido cambia mientras el detalle está abierto, seguís mostrando la copia vieja.

La versión correcta: la ruta lleva el id, y los datos salen de la caché compartida. Así, cualquier actualización se propaga a todas las pantallas que muestran esa entidad, sin importar cuántas instancias haya apiladas:

// features/pedidos/screens/DetallePedido.tsx
import { useQuery } from '@tanstack/react-query';

export function DetallePedido({ route }: Props) {
  const { pedidoId } = route.params;                 // solo el id viaja
  const { data, isPending } = useQuery({
    queryKey: ['pedido', pedidoId],
    queryFn: () => api.getPedido(pedidoId),
    staleTime: 30_000,
  });

  if (isPending) return <Skeleton />;
  return <Detalle pedido={data} />;
}
En Expo Router el problema es más estricto: los params son parámetros de URL, así que useLocalSearchParams() devuelve siempre string o string[]. Un id numérico llega como "42", un booleano como "true", y un objeto tenés que serializarlo vos con JSON.stringify (mala idea salvo para payloads mínimos). Convertí y validá en el borde de la pantalla, una sola vez. 
// Validar params en el borde: nunca confíes en que la URL trae lo que esperás
import { z } from 'zod';
import { useLocalSearchParams, Redirect } from 'expo-router';

const Params = z.object({ id: z.coerce.number().int().positive() });

export default function Detalle() {
  const parsed = Params.safeParse(useLocalSearchParams());
  if (!parsed.success) return <Redirect href="/+not-found" />;   // deep link malformado
  const { id } = parsed.data;
  // …
}

Diferencia entre useLocalSearchParams y useGlobalSearchParams

// useLocalSearchParams  → los params de ESTA ruta. NO se actualiza cuando
//                         otra pantalla se apila encima. Es lo que querés casi siempre.
// useGlobalSearchParams → los params de la URL activa, global. Se actualiza en
//                         TODA pantalla montada cuando navegás → re-renders en cascada
//                         de pantallas que ni se ven.
📌 Usá useLocalSearchParams por default. useGlobalSearchParams hace re-renderizar cada pantalla montada de la pila con cada navegación — que, como ya sabés de RNS5.2, son todas. Reservalo para analítica o para un layout que de verdad necesita saber dónde está el usuario.

Contexto por pila: el estado que vive lo que vive el flujo

Un wizard de checkout necesita estado compartido entre pasos, que debe morir cuando el usuario abandona el flujo. Ni params (no se comparte bien entre pasos), ni store global (sobrevive de más y se ensucia entre sesiones). La respuesta es un provider en el layout de esa pila:

// app/(app)/checkout/_layout.tsx
import { Stack } from 'expo-router';
import { CheckoutProvider } from '@/features/checkout/context';

export default function CheckoutLayout() {
  // El provider se monta con la pila y se desmonta al salir del grupo:
  // el borrador del checkout se destruye solo. Sin cleanup manual.
  return (
    <CheckoutProvider>
      <Stack screenOptions={{ gestureEnabled: false }} />
    </CheckoutProvider>
  );
}
Pensalo como scoping léxico. El store global es una variable de módulo: existe siempre y cualquiera la toca. Los params son argumentos de función: viajan con la llamada y tienen que ser valores simples. El contexto por pila es una variable local de un bloque: nace cuando entrás al bloque, muere cuando salís, y nadie de afuera la ve. La mayoría de los bugs de "quedó estado sucio de la vez anterior" son variables globales que debieron ser locales.

📌 El custom scheme no es seguro y no es exclusivo. Cualquier app puede registrar miapp:// y secuestrar tus links. Por eso los tokens de autenticación, los códigos de un solo uso y cualquier dato sensible nunca viajan por un scheme custom: van por universal link con dominio verificado, o no van. El scheme es útil para desarrollo, OAuth con PKCE y navegación interna — no como canal de confianza.

El link que apunta a una pantalla con sesión

Este es el caso que separa una integración de deep links hecha a las apuradas de una hecha bien. Alguien te manda https://miapp.com/pedidos/42. La app abre. No hay sesión. ¿Qué pasa?

La respuesta ingenua —mandarlo al login y después a la home— pierde la intención del usuario y es exactamente lo que hace que la gente abandone. El patrón correcto tiene tres partes: capturar la intención, validarla, y resolverla después del login.

// features/auth/intencionPendiente.ts
import AsyncStorage from '@react-native-async-storage/async-storage';

const CLAVE = 'intencion.pendiente.v1';
const MAX_EDAD_MS = 10 * 60 * 1000;   // 10 minutos: después ya no es "la intención"

// ⚠️ Allowlist: un deep link es entrada del atacante. Nunca redirijas a algo
//    que no esté en esta lista, y NUNCA a una URL absoluta externa.
const RUTAS_PERMITIDAS = [
  /^\/pedidos\/[a-z0-9-]+$/i,
  /^\/publicacion\/[a-z0-9-]+$/i,
  /^\/perfil$/,
];

export async function guardarIntencion(ruta: string) {
  if (!RUTAS_PERMITIDAS.some((re) => re.test(ruta))) return;   // descartada en silencio
  await AsyncStorage.setItem(CLAVE, JSON.stringify({ ruta, ts: Date.now() }));
}

export async function tomarIntencion(): Promise<string | null> {
  const raw = await AsyncStorage.getItem(CLAVE);
  await AsyncStorage.removeItem(CLAVE);        // de un solo uso, siempre
  if (!raw) return null;
  const { ruta, ts } = JSON.parse(raw);
  if (Date.now() - ts > MAX_EDAD_MS) return null;
  return RUTAS_PERMITIDAS.some((re) => re.test(ruta)) ? ruta : null;  // revalidar al leer
}
// app/(app)/_layout.tsx — el guard captura la intención antes de redirigir

}

⚠️ Tres reglas de seguridad no negociables para deep links. (1) Todo path que venga de afuera se valida contra una allowlist antes de usarlo como destino — sin eso tenés un open redirect dentro de tu propia app. (2) Nunca aceptes credenciales, tokens de sesión ni códigos de verificación por params de un scheme custom: quedan en logs del sistema, en el historial del browser y accesibles a cualquier app que registre el mismo scheme. (3) La intención pendiente es de un solo uso y con vencimiento. Si no la borrás al leerla, el usuario va a aterrizar en el pedido 42 cada vez que inicie sesión durante el resto del año.

    let vivo = true;
    (async () => {
      const token = await SecureStore.getItemAsync('token');

      if (!token) return setEstado({ tipo: 'anonimo' });

      } catch {
        if (vivo) setEstado({ tipo: 'anonimo' });     // token vencido = anónimo
      }
    })();
    return () => { vivo = false; };
  }, []);

  return <Ctx.Provider value={estado}>{children}</Ctx.Provider>;
}

RNS5.7 Restauración de estado: la app que el sistema mató

Escenario real, y frecuente: el usuario está llenando un formulario en el paso 3 de un flujo, entra una llamada, abre WhatsApp, contesta un mail, y a los diez minutos vuelve a tu app. En Android con poca RAM (o con "No mantener actividades" activado en opciones de desarrollador), el sistema mató el proceso. En iOS con la app en background y presión de memoria, lo mismo.

💡 Lo que hay que entender. Cuando el SO mata el proceso, todo el contexto de JavaScript desaparece: variables, estado de React, caché en memoria, el árbol de navegación entero. La app arranca de cero. El sistema restaura la tarea (el usuario ve tu app, no el home), pero el bundle se ejecuta desde la primera línea. No hay un "hidratar" automático — todo lo que quieras recuperar lo tenés que haber escrito a disco antes.

⚠️ Un estado de navegación persistido es una bomba de tiempo si no lo versionás. Sale la versión 2.0 de tu app, renombraste una ruta, y el estado guardado por la 1.9 apunta a una pantalla que ya no existe. Restaurar un flujo de pago es un bug, no una feature. Si el usuario estaba en "confirmando pago" cuando el sistema mató el proceso, devolverlo ahí al reabrir es peligroso: no sabés si la transacción se completó del lado del servidor. Lo correcto es llevarlo al estado real —consultar el backend por el pedido— y no reconstruir un paso intermedio a partir de estado local que puede estar desincronizado. RNS5.9 Accesibilidad de la navegación

La navegación es donde la accesibilidad se rompe primero, porque un cambio de pantalla que es obvio visualmente puede ser completamente invisible para un lector de pantalla.

1. El foco tiene que moverse. Al llegar a una pantalla nueva, TalkBack y VoiceOver deben empezar a leer desde arriba. El native-stack lo maneja bien en la mayoría de los casos porque usa contenedores nativos; los stacks en JS y los cambios de contenido dentro de una misma pantalla, no.
// Mover el foco del lector de pantalla al título al ganar foco
import { AccessibilityInfo, findNodeHandle, Text, View } from 'react-native';

function Pantalla({ titulo }: Props) {
  const ref = useRef<View>(null);

  useFocusEffect(useCallback(() => {
    const t = setTimeout(() => {           // esperar a que termine la transición
      const tag = findNodeHandle(ref.current);
      if (tag) AccessibilityInfo.setAccessibilityFocus(tag);
    }, 350);
    return () => clearTimeout(t);
  }, []));

  return (
    <View ref={ref} accessible accessibilityRole="header">
      <Text>{titulo}</Text>
    </View>
  );
}
2. El botón atrás de Android es parte de la navegación, no un extra. Si tu pantalla intercepta gestos, tiene un panel abierto o un formulario a medias, el back físico tiene que hacer lo obvio. Y tiene que hacerlo solo cuando la pantalla está enfocada.
// API moderna: addEventListener devuelve una suscripción con .remove()
import { BackHandler } from 'react-native';

useFocusEffect(useCallback(() => {
  const sub = BackHandler.addEventListener('hardwareBackPress', () => {
    if (panelAbierto) { cerrarPanel(); return true; }   // true = "yo me encargo"
    return false;                                       // false = comportamiento normal
  });
  return () => sub.remove();
}, [panelAbierto]));
Registrar el BackHandler en un useEffect con array vacío es un bug garantizado: como la pantalla nunca se desmonta al apilar otra encima, el handler sigue activo debajo. El usuario está tres pantallas más arriba, aprieta atrás, y se ejecuta la lógica de una pantalla que no está viendo. Va en useFocusEffect, sin excepciones.
3. El gesto de volver es un arma de doble filo. En iOS, deslizar desde el borde vuelve atrás. Si la pantalla tiene un formulario a medio llenar, ese gesto destruye el trabajo del usuario sin preguntar. Desactivarlo del todo también es malo: rompe la expectativa del sistema. Lo correcto es interceptar la salida y preguntar.

Cómo se producen los imports circulares

La cadena es siempre la misma: la pantalla A quiere navegar a B, entonces importa B para tipar la navegación; B tiene un link de vuelta a A y la importa. Módulo A → módulo B → módulo A. En Metro eso no explota con un error claro: te devuelve undefined en el import, y el síntoma es "Element type is invalid: expected a string but got: undefined" — un error que no menciona en ningún lado la palabra "circular".

RNS5.11 Errores clásicos

Anidar navegadores de más. Un stack dentro de un tab dentro de un drawer dentro de otro stack. Cada nivel agrega una capa de headers que hay que apagar, un historial propio que confunde al botón atrás, y una ruta más larga en la config de linking. Regla: si al navegar tenés que escribir navigate('A', { screen: 'B', params: { screen: 'C' } }), tu árbol tiene un nivel de más.
Datos en los params en vez de ids. Ya visto en RNS5.4: rompe la serialización, congela los datos y engorda el estado que persistís.
No limpiar suscripciones al perder foco. El GPS, el websocket y el setInterval siguen corriendo debajo de cinco pantallas. Se nota en la batería antes que en el profiler.
Poner el NavigationContainer en más de un lugar. Solo puede haber uno por árbol. Si necesitás un navegador aislado (por ejemplo dentro de un modal de una librería), React Navigation 7 tiene NavigationIndependentTree — pero antes preguntate si de verdad hace falta.
Usar navigate donde va replace. Después del login, después de completar un onboarding, después de confirmar un pago: el usuario no debe poder volver atrás a esa pantalla. navigate apila; replace reemplaza.
Poner el Provider del store adentro del navegador. Si el QueryClientProvider o el store viven dentro de una pantalla, se desmontan con ella y perdés toda la caché al navegar. Los providers globales van arriba del contenedor de navegación; los de flujo, en el layout de su pila (RNS5.4).
Asumir que goBack() siempre funciona. Si el usuario entró por un deep link, puede no haber nada atrás. Usá navigation.canGoBack() antes, y si no se puede, mandalo a la ruta ancla — o mejor, configurá initialRouteName y que el problema no exista.

function ListaPedidos() {

📌 La lección no es "usá useFocusEffect". Es que el ciclo de vida de una pantalla móvil no es el de un componente web, y que ese único hecho explica los datos viejos, la memoria que sube, la batería que se va y los requests fantasma. Cuando aparezca un bug raro en una app con navegación, la primera pregunta no es "¿qué está mal en esta pantalla?" sino "¿cuántas instancias de esta pantalla hay vivas ahora mismo, y qué están ejecutando?".

Checkpoint — ¿lo tenés claro?

Una pantalla carga datos en useEffect(fn, []). El usuario navega al detalle, edita algo y vuelve. Ve el dato viejo. ¿Por qué, y por qué en React web esto no pasaba?

Porque en móvil volver no re-monta. Al hacer push, la lista quedó montada debajo del detalle; al hacer pop, el detalle se desmonta y la lista simplemente recupera el foco. El componente nunca se desmontó, así que su useEffect con array vacío no vuelve a correr jamás. En React web el router desmonta la ruta anterior, entonces volver es un montaje nuevo y el efecto corre otra vez — el patrón "cargo en useEffect vacío" funciona por accidente del modelo, no porque sea correcto. La corrección tiene dos niveles: useFocusEffect para reaccionar al foco, y —mejor— mover los datos a una caché compartida que la mutación invalida, de modo que la lista se entere del cambio sin depender de cuándo recupere el foco.

Llega un deep link a /pedidos/42, una ruta que requiere sesión, y el usuario no está logueado. Describí el flujo correcto de punta a punta.

El guard del layout protegido detecta que la sesión está en estado anonimo (no cargando: mientras carga, splash y nada más). Antes de redirigir, guarda la intención —el pathname— validada contra una allowlist de rutas internas, con timestamp. Redirige con <Redirect>, no con navigate, para que la ruta protegida no llegue a montarse ni quede en el historial. El usuario se loguea; al terminar, se lee y borra la intención (de un solo uso), se revalida contra la allowlist y se descarta si pasaron más de unos minutos. Se navega con replace, para que el login no quede atrás. Los dos detalles que no son opcionales: la allowlist —sin ella tenés un open redirect dentro de tu app— y el initialRouteName del stack de pedidos, para que el usuario aterrice en el detalle con un "atrás" que lo lleve a la lista y no a un callejón sin salida.

Segundo, contar instancias: un logger de MOUNT/UNMOUNT/focus/blur con la route.key, para ver qué se monta y qué nunca se desmonta. Tercero, buscar en las pantallas que nunca se desmontan los tres sospechosos habituales: timers e intervalos, suscripciones (websocket, GPS, event emitters) y closures que capturan arrays grandes. Cuarto, revisar dónde vive la caché de datos: si cada instancia de pantalla guarda su copia en useState, N pantallas apiladas son N copias. La corrección va siempre en ese orden —efectos por foco, datos en caché compartida— y recién al final, como optimización, freezeOnBlur. Congelar primero solo esconde el problema.

Resumen ejecutivo

  • El árbol de navegadores es la arquitectura de la app, y es la decisión menos reversible que vas a tomar. Lo que se presenta encima de todo va en el stack raíz, no dentro de una pestaña.
  • Hacer push no desmonta la pantalla anterior, y volver no la re-monta. Ese único hecho explica los datos viejos, la memoria que crece, los timers fantasma y la batería que se va.
  • useEffect para setup de por vida; useFocusEffect + useCallback para todo lo que deba apagarse cuando la pantalla no se ve; AppState además, porque minimizar la app no dispara blur.
  • Expo Router es el default razonable para apps nuevas con Expo en 2026: deep links casi gratis y URLs reales. React Navigation puro sigue ganando en árboles dinámicos, brownfield y rutas que no deberían ser URLs.
  • Por params viajan ids, nunca objetos: los params se serializan para persistir el estado, y un objeto además queda congelado. El estado de un flujo va en un provider del layout de esa pila.
  • Los universal links necesitan dominio verificado; el custom scheme lo puede secuestrar cualquier app, así que por ahí no viajan tokens. Todo path externo se valida contra una allowlist.
  • La sesión tiene tres estados —cargando, autenticado, anónimo— y el árbol condicional le gana a redirigir con navigate en los cinco problemas de la tabla de RNS5.6.
  • Un process kill borra todo el contexto de JS. Lo que quieras recuperar, escribilo a disco; versioná el estado persistido; y nunca restaures flujos de pago o verificación.
  • Para que se sienta instantáneo: native-stack, prefetch de datos en onPressIn, y recién después preload de pantallas — que cuesta memoria real.
  • Accesibilidad de navegación: mover el foco al cambiar de pantalla, BackHandler siempre dentro de useFocusEffect, interceptar el gesto de salida con datos sin guardar, y respetar "reducir movimiento".
  • Estructura por feature; app/ → features/ → shared/ y nunca al revés; rutas por constante, no por import de la pantalla; la regla escrita en el linter, no en el README.

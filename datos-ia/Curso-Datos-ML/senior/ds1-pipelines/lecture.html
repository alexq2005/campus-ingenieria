DS1 — Pipelines de datos: reproducibilidad y escala

DS1.0 Por qué este módulo

En el curso base aprendiste a entrenar modelos: NumPy, pandas, scikit-learn, PyTorch. En un notebook, todo anda. Cargás un CSV, hacés unas transformaciones, entrenás, y el número de validación sale hermoso. El problema es que ese notebook no es el sistema que va a producción, y el 80% del trabajo real de ML no está en el modelo: está en los datos que le llegan, cómo se calculan, de dónde vienen y si se pueden reproducir.

💡 La tesis del módulo. Un modelo en producción casi nunca falla con un stack trace. Falla en silencio: una métrica que baja de a poco, una predicción sesgada que nadie mira por dos semanas, un 94% en validación que se convierte en 71% con datos reales. Y la causa, nueve de cada diez veces, no es el modelo — es el dato. Este módulo es sobre construir la infraestructura de datos que hace que esos fallos silenciosos no ocurran, o que cuando ocurran, se vean.

La diferencia entre un análisis que corrió una vez y un pipeline que corre todos los días es la misma que hay entre un experimento y un producto. Un experimento se justifica solo: lo mirás, entendés el resultado, lo tirás. Un producto de datos tiene que ser reproducible (mismo input, mismo output), versionado (sabés qué datos y qué código produjeron cada resultado) y observable (te enterás cuando algo cambia). Nada de eso viene gratis con un .ipynb.

Stack 2026. Damos por sentado Python 3.11+ y PyTorch 2.5+. Para datos a escala el panorama cambió: Polars (Rust, más rápido que pandas), DuckDB para analítica local sobre archivos, Arrow como formato columnar en memoria y Parquet en disco. Para versionar datos, DVC o lakeFS; para orquestar, Dagster o Airflow. No vas a necesitar todo esto en cada proyecto — de hecho, la última sección es sobre cuándo no usarlo.

DS1.1 El notebook no es un pipeline

El notebook es la mejor herramienta que existe para explorar y la peor para producir. La razón es el estado oculto: las celdas se ejecutan en el orden que vos querés, no en el que están escritas, y el kernel guarda variables que ya no aparecen en ninguna celda. Es facilísimo tener un resultado que solo se reproduce si ejecutás las celdas 1, 5, 3, 8, 12 en ese orden exacto — y nadie, ni vos en dos meses, sabe cuál era ese orden.

El caso clásico. La celda 5 define df. La celda 12 hace df = df.dropna() mutando la variable. Volvés a correr la celda 8, que asume el df original con nulos. Ahora tu resultado depende de cuántas veces corriste la celda 12. Reiniciás el kernel para "limpiar" y descubrís que la mitad del análisis ya no corre porque dependía de una variable que definiste en una celda que borraste. El notebook parecía reproducible; nunca lo fue.

Un pipeline resuelve esto con tres propiedades que el notebook no tiene:

1. Determinismo. Mismo input y mismo código producen exactamente el mismo output. Eso implica fijar todas las semillas (random, NumPy, PyTorch, y el orden de los datos), evitar dependencias del reloj o del sistema de archivos, y no depender del orden de un dict o de un set que pueda variar entre corridas.
2. Versionado. Cada corrida está identificada por la tripleta datos + código + entorno. Si no podés decir "este resultado salió del commit a3f9, con el dataset v3 y el lockfile x", el resultado no es reproducible: es una anécdota.
3. Separación de etapas. Ingesta, validación, limpieza, feature engineering, entrenamiento y evaluación son etapas distintas, cada una con un contrato de entrada y de salida. Así cada una se testea sola, se cachea (si el input no cambió, no la re-ejecutás) y se reemplaza sin tocar las demás.

📌 La regla que separa el juguete del sistema. Un análisis es un pipeline cuando lo podés correr de cero, sin un humano tocando celdas, y da el mismo resultado dos veces. Si para reproducirlo hace falta que vos estés ahí ejecutando cosas en cierto orden, todavía es un experimento — y está bien que lo sea, mientras no lo confundas con producción.

Esto no significa "prohibido el notebook". Significa que el notebook es donde descubrís la transformación, y el pipeline es donde la consolidás. La transición —sacar la lógica del notebook a funciones testeadas con contratos claros— es el trabajo, y es el que más gente saltea.

DS1.2 Versionar datos, no solo código

Tu código está en git. ¿Y tus datos? Si la respuesta es "en un CSV que se llama train_final_v2_DEFINITIVO.csv en una carpeta", tenés un problema de reproducibilidad que ninguna cantidad de tests va a arreglar. Porque el mismo código sobre datos distintos da modelos distintos, y sin versionar el dato no podés decir con qué se entrenó cada modelo.

Por qué git no sirve para datasets

git fue diseñado para versionar texto: guarda diffs línea por línea y comprime bien lo que es legible. Un Parquet de 2 GB es binario y opaco; git no puede hacer un diff útil, así que en cada cambio guarda una copia entera. Diez versiones de un dataset de 2 GB son 20 GB en tu .git, y clonar el repo se vuelve inviable. git-lfs mitiga el tamaño (guarda punteros y sube los binarios aparte) pero no resuelve la semántica: seguís sin poder ramificar datos, comparar dos versiones o hacer rollback de un dataset sin arrastrar todo el repo.

La analogía. Meter datasets en git es como guardar los videos crudos de una película en el repositorio del guión. El guión (código) cambia con diffs chiquitos y legibles; los videos (datos) son enormes, binarios y no se benefician de nada de lo que git hace bien. Lo que querés es versionar un puntero al video —su hash y dónde vive— y dejar el archivo pesado en un almacenamiento hecho para eso.

DVC: git para los punteros, object storage para los datos

DVC (Data Version Control) hace exactamente eso. Calcula el hash del dataset, guarda un archivo chiquito de texto (.dvc) en git con ese hash y el tamaño, y sube el archivo real a un remote (S3, GCS, Azure, un disco de red). git versiona el puntero; DVC sincroniza el contenido.

# Registrar un dataset: DVC lo hashea y crea el puntero
dvc add data/train.parquet
# genera data/train.parquet.dvc  (un YAML con el md5 y el size)
# y agrega data/train.parquet al .gitignore automáticamente

git add data/train.parquet.dvc data/.gitignore
git commit -m "datos: snapshot v3 del set de entrenamiento"

dvc push        # sube el Parquet real al remote configurado
# ...en otra máquina, o dentro de seis meses:
git checkout a3f9 && dvc pull   # recuperás EXACTAMENTE ese dataset

Ahora el commit de git ancla las tres cosas: el código (los .py), el puntero al dato (.dvc) y, si versionás también el lockfile, el entorno. git checkout de un commit viejo + dvc pull te devuelve el mundo exacto que produjo un modelo.

lakeFS: ramas y merges sobre el data lake entero

DVC brilla cuando versionás archivos concretos dentro de un repo. Cuando lo que querés versionar es un lake completo —miles de tablas Parquet sobre object storage, compartido por varios equipos— la herramienta es lakeFS: te da operaciones tipo git (branch, commit, merge, revert) sobre el storage, sin copiar los datos. Podés abrir una rama experimento-x del lake, correr un pipeline que reescribe tablas, validar el resultado y hacer merge a main solo si pasó — o revert si rompiste algo, atómicamente, sobre petabytes.

📌 Reproducibilidad real = cuatro cosas pineadas. Código (git sha) + datos (dvc hash o lakeFS commit) + entorno (lockfile de dependencias) + artefacto del modelo (hash del .pt/.pkl). Si falta cualquiera de las cuatro, "reproducible" es una ilusión. El día que un modelo se comporta raro en prod, esta tripleta-más-uno es la diferencia entre "reproduzco el bug en diez minutos" y "no tengo idea con qué se entrenó esto".

DS1.3 pandas vs Polars vs DuckDB

pandas es la herramienta con la que aprendiste, y sigue siendo la correcta para muchísimas cosas. Pero tiene límites arquitectónicos que a escala duelen: es mayormente de un solo hilo, es eager (ejecuta cada operación en el acto, sin ver la consulta completa) y carga todo en RAM. Cuando el dataset se acerca al tamaño de tu memoria, o cuando el pipeline tarda minutos donde debería tardar segundos, aparecen dos alternativas que nacieron pensando en esto.

Polars: lazy, multihilo y con optimizador de consultas

Polars está escrito en Rust, usa Arrow por debajo y es multihilo de fábrica. Su superpoder es la API lazy: cuando escribís una cadena de transformaciones con scan_*, Polars no ejecuta nada — construye un plan de consulta. Recién con .collect() el optimizador reordena el plan y lo ejecuta de la forma más barata.

import polars as pl

# scan_parquet NO lee el archivo: arma un plan
plan = (
    pl.scan_parquet("ventas/*.parquet")
      .filter(pl.col("pais") == "AR")        # se empuja HACIA la lectura
      .group_by("producto")
      .agg(pl.col("monto").sum().alias("total"))
      .sort("total", descending=True)
)

print(plan.explain())   # mirá el plan optimizado ANTES de ejecutar
df = plan.collect()     # recién acá se lee — y se lee lo mínimo

El optimizador aplica predicate pushdown (empuja el filter hasta la lectura, así solo lee las filas de AR), projection pushdown (lee solo las columnas pais, producto, monto y descarta las otras 40) y elimina subexpresiones repetidas. En un notebook eager, vos leés todo y filtrás después; en Polars lazy, el motor lee menos desde el principio. Para datasets más grandes que la RAM, el modo streaming procesa por bloques sin materializar todo.

DuckDB: SQL analítico embebido sobre tus archivos

DuckDB es "el SQLite de la analítica": una base OLAP que corre dentro de tu proceso, sin servidor, con ejecución vectorizada. Lee Parquet y CSV directo desde el disco sin cargarlos a un DataFrame, y te deja escribir SQL sobre ellos.

-- DuckDB consulta el Parquet directo, sin materializar nada en RAM
SELECT producto, sum(monto) AS total
FROM 'ventas/*.parquet'
WHERE pais = 'AR'
GROUP BY producto
ORDER BY total DESC
LIMIT 10;

Para agregaciones y joins sobre archivos columnares, DuckDB suele ser lo más rápido y lo más simple: no cargás nada, no hay servidor, y aprovecha el mismo predicate pushdown que Parquet permite. Además interopera con Arrow a costo cero, así que podés pasar de DuckDB a Polars a pandas sin copiar memoria.

La conclusión que sí es robusta: para analítica columnar a escala, Polars y DuckDB juegan en otra liga que pandas eager, y la diferencia es más de memoria que de tiempo.

Cuándo pandas todavía gana

No todo es escala. pandas sigue siendo la mejor opción cuando el dataset es chico (el overhead de armar un plan no se amortiza), cuando una librería del ecosistema espera un DataFrame de pandas y no querés convertir, cuando necesitás un método específico que Polars no tiene, o —lo más honesto— cuando tu equipo lo conoce y el proyecto no tiene un problema de performance real. Cambiar de herramienta por moda, sin un cuello de botella medido, es sobre-ingeniería. La regla es la de siempre: primero medí, después optimizá.

DS1.4 Formatos columnares: Arrow y Parquet

Detrás de Polars y DuckDB hay una idea que vale la pena entender por separado, porque explica por qué son rápidos: el almacenamiento columnar.

Un CSV o un JSON son orientados a fila: los valores de una fila están juntos en el disco. Para leer una sola columna de un archivo de 50 columnas, igual tenés que recorrer todas las filas y descartar 49 valores de cada una. Perfecto para escribir registros de a uno (un log, una transacción); pésimo para analítica, que casi siempre toca pocas columnas de muchas filas.

💡 Columnar: los valores de una misma columna están contiguos. Una consulta que usa 3 de 50 columnas lee solo esas 3. Y como los valores de una columna son del mismo tipo y suelen parecerse, comprimen muchísimo mejor (encoding por diccionario para categorías, run-length para repeticiones). Menos bytes leídos del disco y menos bytes en memoria: por eso el columnar gana en analítica por un margen enorme.

Hay dos formatos que conviene no confundir, porque resuelven cosas distintas:

  • Arrow es el formato en memoria. Define cómo se ven los datos columnares en la RAM, de forma estándar entre lenguajes. Su gracia es el zero-copy: Polars, DuckDB, pandas 2.0 y muchos otros comparten buffers Arrow sin serializar ni copiar. Pasás una tabla de DuckDB a Polars y no se mueve un byte.
  • Parquet es el formato en disco. Columnar, comprimido, y —clave— con metadata por bloque: cada row group guarda el mínimo y el máximo de cada columna. Es un archivo pensado para que un motor lea lo menos posible.

Particionado y predicate pushdown

Dos técnicas explotan la metadata de Parquet para saltear datos sin leerlos:

Particionado: organizás los archivos en carpetas según una columna, por ejemplo ventas/anio=2024/mes=01/parte-0.parquet. Una consulta que filtra anio = 2024 ni siquiera abre las carpetas de los otros años. Esto es partition pruning: descarte a nivel de directorio, gratis.

Predicate pushdown: dentro de un archivo, el motor mira el min/max de cada row group. Si tu consulta pide monto > 1000 y un row group tiene max(monto) = 800, lo saltea entero sin leerlo. Combinado con projection pushdown (leer solo las columnas necesarias), una consulta bien escrita sobre Parquet particionado puede tocar el 1% del dato físico.

Elegí la columna de particionado por cómo vas a consultar, no por cómo se ven los datos. Particioná por lo que aparece en tus WHERE (fecha, región, tipo). Y cuidado con el over-partitioning: partir por una columna de alta cardinalidad (un user_id) genera millones de archivos chiquitos y el costo de abrir cada uno se come toda la ganancia. La regla práctica: apuntá a archivos de entre 128 MB y 1 GB por partición.

DS1.5 Data quality como código

Acá va la afirmación más importante del módulo, y la que más cuesta interiorizar: un dato malo que entra al entrenamiento es peor que un bug de código. El bug de código, casi siempre, tira una excepción: lo ves, hay un stack trace, lo arreglás. El dato malo no tira nada. Entrena un modelo que da métricas plausibles, pasa a producción, y sesga decisiones durante semanas hasta que alguien nota que algo raro pasa con cierto segmento de usuarios. No hay error. Hay un modelo que aprendió basura con total tranquilidad.

⚠️ El silencio es el peligro. Un NaN que tu pipeline rellena con 0 "por las dudas", una columna que cambió de unidad (de pesos a miles de pesos) en la fuente, un encoding que convierte tildes en símbolos raros, una fila duplicada que infla una categoría: nada de esto rompe el fit(). Todo esto envenena el modelo. Los datos que cruzan un boundary —file I/O, una API, una tabla de otro equipo— son la fuente número uno de bugs silenciosos, y por eso el boundary es exactamente donde tenés que validar.

La solución es tratar la calidad de datos como se trata la calidad de código: con tests, que corren solos y fallan ruidosamente. Dos herramientas del ecosistema:

  • Pandera: definís un schema declarativo para tu DataFrame (tipos, rangos, unicidad, nulabilidad) y lo validás como una función. Liviano, se integra en el código, ideal para poner un contrato en el borde de cada etapa.
  • Great Expectations: más pesado y más completo. Definís "expectativas" sobre los datos, genera documentación de calidad navegable y reportes de validación. Vale la pena cuando la calidad de datos es un artefacto que varios equipos consumen.
import pandera as pa
from pandera import Column, Check, DataFrameSchema

schema = DataFrameSchema({
    "id":     Column(int,   unique=True),
    "edad":   Column(int,   Check.in_range(0, 120)),
    "monto":  Column(float, Check.ge(0), nullable=False),
    "pais":   Column(str,   Check.isin(["AR", "BR", "CL", "UY"])),
    "email":  Column(str,   Check.str_matches(r"^[^@]+@[^@]+\.[^@]+$")),
})

# lazy=True junta TODOS los errores en vez de cortar en el primero
datos_ok = schema.validate(df, lazy=True)
# si algo no cumple, LEVANTA una excepción con el detalle:
# qué columna, qué check, cuántas filas y ejemplos concretos

Un buen contrato de datos va más allá de los tipos. Los checks que de verdad atrapan problemas son los semánticos: rangos con sentido de negocio (una edad de 300 es un dato roto, no un tipo incorrecto), unicidad de claves, tasa de nulos por debajo de un umbral, cardinalidad esperada de una categórica, y —el más avanzado— estabilidad de distribución: la media de monto de hoy comparada con la histórica. Un drift silencioso de la distribución es la señal más temprana de que algo cambió en la fuente.

📌 Fail fast, y en el boundary. Validá al ingerir (que entre solo dato sano) y otra vez antes de entrenar (que el dato transformado siga sano). Y cuando falle, que el pipeline aborte, no que rellene y siga. Es infinitamente más barato frenar una corrida por datos malos que entrenar, desplegar y descubrir el problema en producción tres semanas después.

DS1.6 Feature engineering reproducible

Llegamos a la causa número uno de modelos que andan perfecto en el test y fracasan en producción, y casi nadie la nombra en los cursos: el train/serve skew, o sesgo entre entrenamiento y servicio.

💡 Train/serve skew. Es cuando una misma feature se calcula de forma distinta en entrenamiento y en producción. En training la computás en batch, con pandas, sobre un histórico completo. En serving la computa otro código —a veces en otro lenguaje, otro equipo, otra definición— sobre un único request en tiempo real. Aunque las dos versiones tengan la misma intención, difieren en los bordes. El modelo aprendió con una distribución y en prod ve otra. Nunca lo va a decir; simplemente rinde peor.

El ejemplo canónico: la feature "monto promedio de compras de los últimos 30 días". En el notebook de training la calculás con un groupby elegante sobre toda la tabla histórica. En producción, un microservicio en otro lenguaje la recalcula por request, y define "30 días" como 30 días calendario incluyendo el día actual todavía incompleto, mientras que tu training usaba 30 días cerrados. Dos definiciones sutilmente distintas, dos distribuciones, y un modelo que degrada sin que ningún test unitario se queje.

La solución estructural: computar la feature una sola vez

El fix táctico es obvio: una sola definición de la feature, en una función compartida que importan tanto el training como el serving. Si hay un solo código que calcula "promedio de 30 días", no puede haber dos definiciones.

# feature_defs.py — importado por el pipeline de train Y por el de serving
def monto_promedio_30d(historial, momento):
    """Promedio de 'monto' en la ventana de 30 días ANTERIOR a 'momento'.
    'momento' es el instante de la predicción; la ventana es cerrada."""
    desde = momento - pd.Timedelta(days=30)
    ventana = historial[(historial["ts"] >= desde) & (historial["ts"] < momento)]
    return ventana["monto"].mean()

El fix estructural, cuando la organización escala, es un feature store: un sistema que computa cada feature una vez y la sirve tanto al training (modo offline, sobre el histórico) como al serving (modo online, baja latencia) desde la misma definición. Resuelve el skew por construcción, y además centraliza y reutiliza features entre modelos.

Point-in-time correctness. Al armar el set de entrenamiento, cada feature de cada fila tiene que reflejar lo que se sabía en el momento de esa fila, no lo que se sabe hoy. Es facilísimo, con un join descuidado, pegarle a una fila de enero un valor que recién existió en marzo. Eso ya no es skew: es leakage temporal, el tema de la próxima sección. Un feature store serio garantiza point-in-time correctness en el join offline; a mano, es la trampa más fácil de pisar.

DS1.7 Data leakage a nivel senior

El curso base te mostró el leakage obvio: escalar antes de partir en train/test. Acá vamos por las formas sutiles, las que pasan revisión de código y solo se detectan si sabés qué buscar. Leakage es cualquier información sobre el target o sobre el futuro que se filtra a las features de entrenamiento y que el modelo no va a tener disponible en producción. El síntoma es siempre el mismo: un modelo demasiado bueno para ser verdad.

Las cuatro formas que importan

1. Leakage temporal. Usar información del futuro para predecir el pasado. Aparece de dos maneras: un split aleatorio sobre una serie temporal (mezclás enero con diciembre, el modelo "ve" el futuro en el train), o una feature computada con datos posteriores al momento de predicción (un promedio que incluye el propio evento que querés predecir). Es el más común y el más caro.
2. Leakage por preprocesamiento. Hacer fit del scaler, del imputador o del encoder sobre todo el dataset antes de partir. La media y la varianza que usás para normalizar el train ya "vieron" el test. Se arregla metiendo el preprocesamiento dentro de un Pipeline de scikit-learn, que hace fit solo con el train de cada fold de la validación cruzada.
3. Target leakage. Una feature que es consecuencia del target, no causa. El ejemplo clásico: predecir el default de un crédito usando la feature "tiene seguro de impago activado" — pero ese seguro se contrata después de que se sabe que la persona va a defaultear. La feature es casi el target disfrazado. En producción no la vas a tener a tiempo, o va a significar otra cosa.
4. Leakage de grupo. El mismo sujeto (paciente, usuario, cliente) aparece en train y en test. El modelo memoriza al individuo en vez de aprender el patrón. La métrica de test miente porque el test no es realmente "datos nuevos". Se arregla con un split por grupo (GroupKFold), que garantiza que cada sujeto está de un solo lado.

Las señales de que hay leakage. Un AUC sospechosamente cercano a 1.0. Una sola feature que domina toda la importancia del modelo. Una correlación de una feature con el target por encima de 0.95. Un salto de performance enorme al agregar una feature "nueva". Cuando veas cualquiera de estas, no festejes: sospechá. En ML, un resultado demasiado bueno casi siempre es un bug de datos, no un golpe de suerte.

DS1.8 Orquestación: el pipeline es software

Cuando el pipeline tiene varias etapas con dependencias, necesitás algo que las corra en orden, reintente las que fallan, y las dispare en la cadencia correcta. Eso es un orquestador, y modela el pipeline como un DAG (grafo acíclico dirigido): los nodos son etapas, las aristas son dependencias. Airflow es el estándar veterano; Dagster y Prefect son la generación moderna, con mejor manejo de datos y de testing local.

Tasks vs. assets. Airflow piensa en tareas ("corré este script"). Dagster piensa en assets ("producí esta tabla"), lo que se llama data-aware orchestration: el orquestador sabe qué dato produce cada etapa, puede materializar solo lo que quedó desactualizado y razonar sobre el linaje. Para pipelines de datos y ML, pensar en assets suele encajar mejor con cómo funciona el trabajo.

Idempotencia y backfill: las dos propiedades no negociables

Idempotencia significa que correr la misma etapa dos veces, con el mismo input, da el mismo resultado y no rompe nada. Es lo que hace que reintentar sea seguro. El patrón: escribí a una partición determinista (por fecha, por ejemplo) y sobreescribila, en vez de hacer un append ciego que duplica datos cada vez que reintentás.

# Idempotente: la salida es una partición determinista por fecha.
# Re-correr el mismo día PISA esa partición; no acumula duplicados.
def transformar(fecha: str):
    entrada = f"raw/fecha={fecha}/"
    salida  = f"clean/fecha={fecha}/"
    (pl.scan_parquet(entrada)
       .pipe(limpiar)
       .sink_parquet(salida))   # overwrite atómico de ESA partición

Backfill es recomputar el histórico cuando cambiás la lógica. Si arreglaste un bug en una feature, necesitás re-correr los últimos seis meses. Un DAG bien diseñado está parametrizado por fecha: podés dispararlo para cualquier ventana del pasado y, como cada etapa es idempotente, el resultado es correcto sin importar cuántas veces la corras.

📌 Un pipeline de datos es software, con las mismas necesidades. Tests (de la lógica y de los datos, DS1.5), CI (correr el DAG en staging con una muestra antes de mergear), observabilidad (métricas de frescura, volumen y tasa de nulos en cada corrida) y alertas cuando algo se sale de rango. Si tu pipeline no tiene nada de esto, no es un sistema de producción: es un cron con suerte, y la suerte se acaba.

DS1.9 Escala: cuándo salís de una sola máquina

Hay una creencia instalada de que "datos a escala" significa "cluster de Spark". En 2026 esa creencia está, la mayoría de las veces, equivocada — y sale carísima.

💡 Un solo nodo moderno aguanta terabytes. Una VM en la nube con 128–512 GB de RAM y discos NVMe cuesta poco y es trivial de conseguir por horas. Con Polars en modo streaming o con DuckDB, procesás cientos de GB —y hasta algunos TB— en esa única máquina, sin cluster, sin shuffle de red, sin serialización distribuida, sin debuggear un job que falló en el ejecutor 47. La enorme mayoría de lo que la gente llama "big data" entra cómodo en un nodo grande.

Spark (y el procesamiento distribuido en general) casi nunca hace falta antes de lo que la gente cree. Un cluster tiene un costo que no se ve en el benchmark: setup y mantenimiento, el shuffle de datos por la red entre nodos, la serialización, y sobre todo la dificultad de debuggear algo que corre en cincuenta máquinas a la vez. Ese costo solo se justifica cuando de verdad tenés decenas de TB, o un throughput que un nodo no da. Por debajo de ese umbral —donde vive el 90% de los proyectos— un solo nodo es más rápido (no paga red), más barato y muchísimo más simple de operar.

La herramienta de escala que sí usás casi siempre es el particionado: en vez de cargar todo, procesás partición por partición, en paralelo dentro del nodo, sin que nada entre entero en memoria. Combinado con formatos columnares y pushdown, te lleva sorprendentemente lejos.

La regla operativa: medí el tamaño real de tu dato antes de elegir arquitectura. Si entra en un nodo grande —y hoy "grande" es una tarjeta de crédito y diez minutos— quedate en un nodo. Subís a distribuido cuando el nodo más grande razonable ya no alcanza, con números en la mano, no cuando lo imaginás. El costo de operar Spark de más es real; el costo de un nodo grande de más es unos dólares la hora.

DS1.10 Cuándo NO complicar

Todo este módulo describe herramientas potentes, y la tentación senior es usarlas todas. No lo hagas. La sobre-ingeniería de datos es tan cara como la sub-ingeniería, y bastante más común en equipos que acaban de aprender estas cosas.

⚠️ El pipeline de 3 pasos no necesita Airflow. Si tu proceso es "extraé de una tabla, transformá, guardá un Parquet" y corre una vez por día, un script de Python con cron, un lockfile para no pisarse, logging y una validación de Pandera al final es todo lo que necesitás. Montar Airflow, un feature store y un data lake para eso no te hace más senior: te hace responsable de operar tres sistemas complejos para resolver un problema que cabía en cuarenta líneas.

Los síntomas de sobre-ingeniería de datos, para que los reconozcas en tus propios proyectos:

  • Un feature store para cinco features que usa un solo modelo.
  • Spark para procesar 2 GB que entran en la RAM de tu laptop.
  • Un data lake con catálogo y capas medallion para diez tablas.
  • DVC sobre un CSV de referencia que no cambia nunca.
  • Un DAG de orquestación con reintentos y sensores para un job que no tiene dependencias.
📌 La complejidad se justifica con escala real, no con aspiración. Volumen de datos, tamaño del equipo, SLAs concretos: esos justifican infraestructura. "Por si algún día crecemos" no. Empezá con lo más simple que funcione y verificalo de punta a punta; agregá cada pieza de infraestructura cuando el dolor que resuelve sea real y medible. Es infinitamente más fácil agregar Airflow el día que lo necesitás que sacarlo el día que descubrís que nunca lo necesitaste.

🧑‍🎓 Worked Example — 94% en validación, 71% en producción

Un equipo entrena un modelo de churn (predecir qué clientes se van a dar de baja). En validación da 94% de accuracy — festejan y despliegan. La primera semana en producción, la métrica real es 71%. El modelo es casi inútil. ¿Qué pasó?

Paso 1 — Descartar el diagnóstico fácil. "Es overfitting" es lo primero que dicen todos, y está mal. El overfitting clásico se ve dentro del mismo dataset: train altísimo, test bajo. Acá el problema es distinto: validación y producción son mundos distintos. Una brecha val↔prod tan grande no es memorización — es que el dato de validación no representaba al dato de producción. Eso apunta a dos sospechosos: leakage o train/serve skew. Casi siempre, cuando la brecha es brutal, están los dos.

Paso 2 — Auditar las features por importancia. Se mira qué features pesan más en el modelo. Una domina todo: dias_desde_ultima_actividad. Al revisar cómo se computó en el training set, aparece el bug:

# CÓMO SE COMPUTÓ EN TRAINING (con leakage temporal)
df["dias_desde_ultima_actividad"] = (
    df["fecha_actividad"].max() - df["fecha_actividad"]   # ¡max() del dataset!
).dt.days
# 'max()' es la fecha en que se ARMÓ el dataset — información del futuro.
# La feature "sabe" hasta dónde llega el histórico completo.

En training, max() es el borde derecho del dataset: un punto en el futuro respecto de casi todas las filas. En producción, esa feature se computa contra la fecha del request (el "ahora"). Son dos definiciones distintas de "última actividad": leakage temporal. El modelo aprendió a apoyarse en una señal que en prod significa otra cosa.

Paso 3 — Encontrar el segundo problema. La otra feature importante es monto_promedio_30d. En training la calculó un groupby de pandas sobre el histórico. En producción la calcula un microservicio que define la ventana de 30 días incluyendo el día actual todavía incompleto. Misma intención, bordes distintos: train/serve skew. Dos distribuciones sutilmente corridas para la misma columna.

Paso 4 — Arreglar de raíz, no parchar. Tres cambios:

(a) Split temporal correcto. Nunca más split aleatorio en datos con tiempo. El train usa datos hasta T; la validación usa datos posteriores a T. Así la validación simula de verdad lo que es predecir el futuro.
# MAL: mezcla pasado y futuro, la validación miente
train, val = train_test_split(df, test_size=0.2, random_state=42)

# BIEN: la validación es SIEMPRE posterior al train
corte = df["fecha"].quantile(0.8)
train = df[df["fecha"] <= corte]
val   = df[df["fecha"] >  corte]
(b) Feature point-in-time. dias_desde_ultima_actividad se recomputa para que cada fila use solo lo conocido a su timestamp, nunca el max() global. La feature de training pasa a significar exactamente lo mismo que la de serving.
(c) Una sola definición de cada feature. monto_promedio_30d se saca a una función compartida (o a un feature store) que importan el training y el serving. Si hay un solo código, no puede haber dos definiciones de "30 días".

El resultado. La validación baja a 79%, y eso es una buena noticia: el 94% era mentira, inflado por el leakage. La producción sube a 77%. La brecha se cerró de 23 puntos a 2. Terminaron con un modelo que en el papel parece peor y en la realidad es muchísimo mejor.

📌 La lección del ejercicio. Cuando un modelo brilla en validación y se apaga en producción, el bug casi nunca está en el modelo: está en el dato. Un split temporal honesto y una feature computada una sola vez arreglan más problemas de "el modelo no anda en prod" que cualquier arquitectura de red o cualquier búsqueda de hiperparámetros. Un número de validación demasiado bueno no es un logro: es un síntoma.

Checkpoint — ¿lo tenés claro?

¿Por qué git no sirve para versionar un dataset, y qué hace DVC distinto?

git versiona contenido de texto con diffs línea por línea. Un Parquet es binario y opaco: git no puede diffear, así que guarda una copia completa en cada cambio, y el repositorio se infla hasta volverse inmanejable. DVC versiona un puntero: calcula el hash del dataset, guarda un archivo .dvc chiquito en git con ese hash, y sube el archivo real a un remote (S3/GCS). El commit de git ancla código y puntero al dato juntos; git checkout + dvc pull reconstruye el estado exacto. La reproducibilidad completa necesita cuatro cosas pineadas: código, datos, entorno y artefacto del modelo.

Tu modelo da 94% en validación y 71% en producción. ¿Qué descartás primero y qué sospechás?

Descartás overfitting clásico: eso se ve dentro del mismo dataset (train alto, test bajo), no como una brecha entre validación y producción. Una brecha val↔prod tan grande significa que la validación no representaba a producción, y eso apunta a leakage (una feature que usa info del futuro o del target, que en prod no está) o a train/serve skew (la misma feature computada distinto en train y en serving). Se audita empezando por las features de mayor importancia: la que domina suele ser la culpable. El arreglo típico es split temporal correcto más una única definición point-in-time de cada feature.

¿Por qué Polars lazy y el Parquet particionado leen menos datos que pandas eager?

pandas es eager: ejecuta cada operación al toque, sin ver la consulta completa, así que primero carga todo el archivo y recién después filtra y selecciona columnas. Polars lazy construye un plan con scan_* y lo optimiza antes de ejecutar: aplica predicate pushdown (empuja el filtro hasta la lectura, lee solo las filas que pasan) y projection pushdown (lee solo las columnas usadas). El Parquet ayuda por su estructura columnar y su metadata: min/max por row group permite saltear bloques enteros, y el particionado por carpeta descarta directorios sin abrirlos. Resultado: una consulta bien escrita puede tocar el 1% del dato físico.

Resumen ejecutivo

  • El notebook no es un pipeline: le falta determinismo, versionado y separación de etapas. Un análisis es pipeline cuando corre de cero, sin humano, y da el mismo resultado dos veces.
  • Versioná los datos, no solo el código. git no sirve para binarios grandes; DVC versiona un hash y guarda el dato en un remote; lakeFS da git sobre el lake entero. Reproducibilidad = código + datos + entorno + artefacto, los cuatro pineados.
  • pandas / Polars / DuckDB: pandas para explorar y para el ecosistema; Polars (lazy, multihilo, pushdown) para ETL a escala; DuckDB para agregaciones SQL sobre Parquet. La ventaja a escala es más de memoria que de tiempo — medí lo tuyo.
  • El columnar (Arrow en memoria, Parquet en disco) gana en analítica: lee solo las columnas necesarias, comprime mejor, y con particionado + predicate pushdown saltea el grueso del dato sin leerlo.
  • Data quality como código: un dato malo es peor que un bug, porque falla en silencio. Validá schemas (Pandera/Great Expectations) en el boundary, con checks semánticos, y abortá al fallar.
  • Train/serve skew y data leakage son la causa #1 de modelos que andan en test y fallan en prod. Una sola definición de cada feature, point-in-time correctness, y split temporal en vez de aleatorio.
  • El pipeline es software: DAGs idempotentes, backfill parametrizado por fecha, tests, CI y observabilidad. Y no compliques: un solo nodo aguanta terabytes, Spark casi nunca hace falta, y el proceso de 3 pasos no necesita Airflow.

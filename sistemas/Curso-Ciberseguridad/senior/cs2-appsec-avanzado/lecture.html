CS2 — AppSec avanzado: la clase de bug, no el bug

CS2.0 Por qué este módulo: de bugs a clases de bug

El curso base te enseñó el OWASP Top 10 de a uno: acá la inyección SQL, allá el XSS reflejado, más adelante el CSRF y el SSRF. Es la forma correcta de empezar, porque le pone nombre y cara a cada bug. Pero tiene un techo: cada vez que sale una técnica nueva —una "X injection" que ayer no existía— quedás un paso atrás, esperando que alguien la bautice, escriba la regla del scanner y la agregue al checklist.

Este módulo apunta más abajo. No a los diez bugs con nombre, sino a la clase de bug: el mecanismo común que los genera a todos. Si entendés la raíz, no necesitás haber visto el bug antes para reconocerlo. Podés razonar sobre uno que todavía no tiene nombre.

💡 La tesis del módulo. Casi todo bug de aplicación web es una instancia de una de dos confusiones: (1) confundir datos con código —dejar que la entrada del usuario cruce a un intérprete y se ejecute como estructura—, o (2) confundir canales de confianza —creerle a un canal (el navegador, la red interna, el otro proxy, el cliente) una autoridad que ese canal no tiene—. Inyección, XSS, deserialización, SSTI son la primera. CSRF, SSRF, smuggling, IDOR, secretos en el cliente son la segunda. Aprendé las dos confusiones y el Top 10 deja de ser una lista para memorizar: se vuelve deducible.

Damos por sabido lo del M04 (inyección, XSS, CSRF, SSRF a nivel introductorio), el M03 (autorización) y el M08 (secure coding). Desde acá subimos: variantes que el scanner no ve, defensas estructurales, y el criterio para distinguir una protección real de una que solo parece proteger.

CS2.1 La raíz de casi todo: datos vs código, y canales de confianza

Antes de las variantes, fijemos el marco, porque es lo único que vas a poder aplicar a un bug que no viste nunca.

Confusión 1 — datos que se vuelven código

Todo intérprete recibe una cadena y la parte en dos: lo que es estructura (comandos, operadores, delimitadores) y lo que es contenido (los valores). La vulnerabilidad aparece cuando el atacante logra que parte de sus datos crucen la frontera y se lean como estructura. El intérprete cambia —motor SQL, motor de plantillas, shell, deserializador, parser de XML, DSL de consultas— pero la confusión es idéntica.

📌 La corrección es siempre la misma forma. Mantené los datos como datos: parametrización (consultas preparadas), APIs estructuradas en vez de armar strings, codificación consciente del contexto en la salida. Nunca construyas código —una query, una plantilla, un comando— concatenando texto con entrada no confiable. Si escribiste "..." + entrada + "..." y el resultado lo interpreta algo, ya perdiste; la pregunta es solo cuándo.

Confusión 2 — canales que reciben confianza que no merecen

El otro medio bug del mundo no es meter código: es explotar que el sistema le cree a un canal. El CSRF abusa de que el servidor confía en la autoridad ambiental del navegador (manda la cookie sola). El SSRF abusa de que un backend confía en su propia posición de red. El request smuggling abusa de que dos proxies confían en que el otro parsea igual. El IDOR abusa de que el endpoint confía en que el cliente solo pide lo suyo. Los secretos en el cliente abusan de que alguien confió en que el browser podía guardar algo.

📌 La corrección también rima. Hacé la confianza explícita y verificada en cada frontera. No infieras autoridad del canal: no porque venga con cookie es el usuario correcto para ese recurso; no porque lo pida el backend es una URL segura; no porque el cliente lo mande el precio es real. Cada boundary revalida.

Todo lo que sigue en este módulo es una aplicación de estas dos ideas. Cuando veas una técnica nueva, la primera pregunta es ¿cuál de las dos confusiones explota? — y de ahí sale la defensa antes de que exista el parche.

CS2.2 Inyección más allá de SQL

El M04 te mostró la inyección con el ejemplo canónico: SQL. Acá vas a ver cuatro intérpretes distintos donde se repite exactamente el mismo patrón, para que la próxima variante no te tome por sorpresa.

Server-Side Template Injection (SSTI)

Los motores de plantillas (Jinja, Twig, Freemarker, Handlebars) toman una plantilla y la evalúan. El bug aparece cuando la entrada del usuario se vuelve parte del texto de la plantilla en lugar de ser un dato que la plantilla consume:

# VULNERABLE: el input del usuario se vuelve PARTE de la plantilla
from flask import render_template_string, request

@app.route("/saludo")
def saludo():
    nombre = request.args.get("nombre", "")
    # se concatena input en el TEXTO de la plantilla: el motor lo va a evaluar
    return render_template_string("<h1>Hola " + nombre + "</h1>")
# CORRECTO: la plantilla es estatica; el nombre es SOLO un dato
from flask import render_template, request

@app.route("/saludo")
def saludo():
    nombre = request.args.get("nombre", "")
    return render_template("saludo.html", nombre=nombre)
    # en saludo.html:  {{ nombre }}  queda auto-escapado por el motor
⚠️ Por qué SSTI escala a RCE. Se confirma la vulnerabilidad con una expresión aritmética que el motor evalúa y devuelve resuelta. A partir de ahí —y esto es lo que lo hace tan grave— como el motor expone objetos del lenguaje anfitrión, el atacante navega el grafo de objetos desde lo que la plantilla dejó accesible hasta una primitiva que ejecuta comandos del sistema. No necesito mostrar la cadena para que quede la lección: el input jamás debe ser parte del texto de la plantilla. Si tu framework tiene render_template_string con concatenación, es un hallazgo, no un estilo.

Inyección en NoSQL y GraphQL

"Cambié Mongo por Postgres para no tener inyección" es un malentendido: la inyección no era de SQL, era de concatenar. En NoSQL la variante clásica es la inyección de operadores: el cuerpo JSON del cliente entra crudo como filtro, y un objeto con un operador ($ne, $gt) reemplaza al valor escalar que esperabas.

// VULNERABLE: el cuerpo JSON del cliente entra crudo como filtro
app.post("/login", async (req, res) => {
  const user = await db.collection("users").findOne({
    usuario: req.body.usuario,
    clave:   req.body.clave        // si clave = { "$ne": null }, matchea a cualquiera
  });
});
// CORRECTO: forzar tipos; un operador no puede colarse como valor
const usuario = String(req.body.usuario);
const user = await db.collection("users").findOne({ usuario });
// la clave NUNCA va en el filtro: se compara aparte contra un hash guardado
// (ver M01/M02). Y el input se valida con un esquema antes de tocar la query.

En GraphQL conviven dos superficies. Una es la de siempre: si un resolver arma una query SQL o Mongo con un argumento, es inyección clásica y se arregla parametrizando. La otra es propia del protocolo: la introspección filtra todo el esquema, las consultas anidadas profundas son una negación de servicio (una query que pide amigos de amigos de amigos… explota el backend), y el batching por alias convierte un endpoint en una máquina de fuerza bruta que evade el rate-limit por request.

Defensa GraphQL (capas, no bala de plata): límites de profundidad y complejidad de query, persisted queries (solo se aceptan consultas conocidas de antemano), rate-limit por costo y no por request, e introspección apagada en producción —con matiz: apagarla es ofuscación, no seguridad; el esquema se puede inferir. La seguridad real está en autorizar por campo y por objeto dentro de cada resolver, nunca solo en la puerta.

Inyección por argumentos (aunque no haya shell)

El consejo "no uses shell=True" es correcto pero incompleto. Aun sin shell —pasando una lista de argumentos, sin metacaracteres— hay inyección si la entrada del usuario se convierte en un token de argv que el programa lee como una opción. Un nombre de archivo que empieza con guion deja de ser un dato y pasa a ser un flag que cambia lo que hace la herramienta.

# VULNERABLE POR ARGUMENTOS: sin shell, pero el input decide un flag
import subprocess

def exportar(nombre):
    # si nombre empieza con "-", curl lo interpreta como opcion, no como dato
    subprocess.run(["curl", "https://api.interna/subir", "-F", nombre])
# CORRECTO: validar con allowlist + separador de fin-de-opciones
import subprocess, re

def exportar(nombre):
    if not re.fullmatch(r"[a-zA-Z0-9_.-]{1,64}", nombre):
        raise ValueError("nombre invalido")
    # "--" le dice a la herramienta: lo que sigue NO son opciones
    subprocess.run(["curl", "https://api.interna/subir",
                    "-F", "archivo=@" + nombre, "--"])

Deserialización insegura, a fondo

El caso más elegante —y más peligroso— de "datos que se vuelven código". Formatos como pickle (Python), ObjectInputStream (Java), unserialize (PHP), BinaryFormatter (.NET) o Marshal (Ruby) no transportan solo valores: transportan qué tipo reconstruir y cómo. Deserializar bytes no confiables es dejar que el atacante decida qué objetos instanciás y qué callbacks se disparan al hacerlo.

# VULNERABLE: pickle reconstruye CUALQUIER objeto y dispara sus callbacks
import pickle
datos = pickle.loads(cuerpo_no_confiable)   # RCE si el atacante controla los bytes
# CORRECTO: formato SOLO-DATOS, sin capacidad de instanciar tipos arbitrarios
import json
datos = json.loads(cuerpo_no_confiable)     # a lo sumo, un JSON invalido
# si necesitas tipos, validalos con un esquema (pydantic / jsonschema),
# nunca dejando que el payload elija la clase a construir.
Qué es una gadget chain (conceptual). El atacante casi nunca "sube código". Reutiliza clases que ya están en tu aplicación y sus dependencias. Un gadget es una clase cuyo método de deserialización (un __reduce__, un readObject, un método mágico) hace algo aprovechable. Una cadena encadena varios gadgets para que el efecto acumulado —lectura de archivo, llamada a un método, ejecución— sea lo que el atacante quiere, todo con piezas que vos ya trajiste al classpath. Por eso "no tengo código peligroso" es falsa tranquilidad: el peligro es la suma de piezas benignas. La única defensa robusta es no deserializar datos no confiables con estos formatos; si es inevitable, allowlist estricta de tipos y firma criptográfica del payload.
El patrón se repite en los cuatro casos. Plantilla, filtro NoSQL, argv, flujo de objetos: intérpretes distintos, misma confusión. Una vez que ves eso, "una nueva X injection" deja de ser algo nuevo que aprender —es lo mismo en un intérprete distinto—, y la defensa la deducís antes de leer el aviso.

CS2.3 XSS avanzado: cuando el sanitizado casero no alcanza

El M04 cubrió el XSS reflejado y almacenado, y la defensa de siempre: escapar en la salida según el contexto. Acá van las variantes que rompen las defensas ingenuas —y por qué el approach "yo sanitizo el string" es una batalla perdida contra el parser del navegador.

Mutation XSS (mXSS)

El sanitizador ve un DOM; el navegador construye otro. Cuando asignás una cadena a innerHTML, el parser del browser aplica décadas de reglas de recuperación de errores, contenido "foráneo" (SVG, MathML), y re-serializaciones que mutan el markup en el momento de insertarlo. El resultado es un nodo ejecutable que el sanitizador nunca vio, porque la cadena que sanitizaste no es el árbol que el navegador termina armando.

⚠️ Consecuencia dura: sanitizar un string y después pasarlo por innerHTML puede fallar aunque el string se vea limpio. La mutación ocurre al parsear, un paso posterior a tu limpieza. Por eso el sanitizado tiene que operar sobre el DOM ya parseado, con conocimiento del parser —no sobre texto plano con expresiones regulares.

DOM clobbering

Un ataque sin una sola etiqueta <script>. El HTML puede definir elementos con id y name que sombrean variables globales y propiedades del DOM. Si tu código consulta un global que un atacante puede plantar como elemento, termina usando una referencia que él controla.

<!-- Markup del atacante, sin script: dos anclas forman una coleccion -->
<a id="config"></a>
<a id="config" name="apiBase" href="https://sitio-del-atacante.example"></a>
// El codigo confia en un global que el HTML acaba de "clobberear"
if (window.config) {
  cargarDesde(window.config.apiBase);   // ahora resuelve al valor del atacante
}
// CORRECTO: no confiar en lookups que el DOM puede sombrear
const CONFIG = Object.freeze({ apiBase: "https://api.propia" });
if (typeof CONFIG.apiBase === "string") {
  cargarDesde(CONFIG.apiBase);          // referencia explicita + chequeo de tipo
}

Por qué el sanitizado casero siempre pierde

El parser HTML del navegador es una de las piezas de software más complejas y llenas de casos borde que existen: estados de parsing, contenido foráneo, reglas de encoding, recuperación de errores. Una expresión regular o un allowlist a mano no puede modelar eso, y cada versión del navegador cambia algún detalle. Escribir tu propio sanitizador es firmar un contrato de mantenimiento contra un blanco móvil que siempre te va a ganar.

// FRAGIL: sanitizado casero + innerHTML = mXSS tarde o temprano
el.innerHTML = limpiarConRegex(entradaUsuario);   // el parser del browser gana

// MEJOR: libreria mantenida, consciente del parser y del contexto
import DOMPurify from "dompurify";
el.innerHTML = DOMPurify.sanitize(entradaUsuario);

// MEJOR AUN: si no necesitas HTML, ni lo parsees
el.textContent = entradaUsuario;                  // imposible ejecutar nada

Trusted Types: la defensa estructural

El problema real del XSS de DOM no es un sink: son los miles de sinks (innerHTML, outerHTML, document.write, eval, src de scripts) repartidos por todo el código, y la esperanza de que alguien se acordó de sanitizar en cada uno. Trusted Types invierte el problema: con la directiva CSP require-trusted-types-for 'script', esos sinks rechazan cadenas crudas y solo aceptan valores producidos por una política registrada. Pasás de "¿sanitizamos en los mil lugares?" a "¿este valor trae la prueba de que pasó por la única política?".

// UN unico cuello de botella auditable para todo el HTML dinamico
const politica = trustedTypes.createPolicy("app-html", {
  createHTML: (s) => DOMPurify.sanitize(s)
});

el.innerHTML = politica.createHTML(entradaUsuario);  // OK: valor "probado"
el.innerHTML = entradaUsuario;                        // ERROR: string crudo, rechazado
Esto es exactamente el principio de secure by design (CS2.9) aplicado al DOM: en vez de depender de que el dev se acuerde en cada sink, el sink falla-cerrado por construcción. Cambiás disciplina humana por una garantía del runtime, y la superficie auditable pasa de miles de líneas a una sola política.

Los límites reales de CSP

La Content-Security-Policy es una mitigación valiosa, pero no cura el XSS: limita el radio de la explosión. Y se la sobreestima constantemente.

<!-- Mitiga, no cura: nonce estricto + strict-dynamic, sin unsafe-inline -->
<meta http-equiv="Content-Security-Policy"
      content="script-src 'nonce-r4nd0m' 'strict-dynamic'; object-src 'none'; base-uri 'none'">
Dónde una CSP se cae: unsafe-inline la anula; un allowlist amplio con un endpoint JSONP o un host de scripts abierto adentro es un bypass servido; sin base-uri 'none', el DOM clobbering de <base> reescribe rutas; un nonce que se refleja o se reusa deja de proteger. Una CSP estricta con nonce/hash y strict-dynamic sube muchísimo la vara —pero el bug de XSS sigue ahí. Tratarla como "ya estamos a salvo del XSS" es el error.

CS2.4 Request smuggling: dos servidores, un desacuerdo

El HTTP request smuggling (o HTTP desync) es la confusión de canal de confianza en su forma más pura, llevada a la capa de "¿dónde termina un request y empieza el siguiente?".

El escenario: hay un front-end (CDN, balanceador, proxy) y un back-end, y ambos leen el mismo flujo de bytes. Si el request es ambiguo respecto de cuánto mide el cuerpo —porque trae dos formas de indicarlo a la vez, o una malformada que uno honra y el otro ignora— los dos servidores pueden discrepar sobre dónde corta el mensaje. Lo que el front cree que es el cuerpo, el back lo interpreta como el comienzo de otro request, y ese request "de contrabando" se cuela adelante del pedido del próximo usuario.

# La ambiguedad (defensivo): dos formas de indicar el largo, a la vez.
# Un servidor obedece Content-Length; el otro, Transfer-Encoding.
# La DEFENSA es rechazar el request ambiguo en el borde, NO interpretarlo.
Content-Length: 6
Transfer-Encoding: chunked
⚠️ Por qué es tan potente. No requiere credenciales. Es una discrepancia entre dos componentes de confianza, así que puede saltear controles de acceso que vivían en el front-end, envenenar cachés compartidas (un usuario recibe la respuesta destinada a otro) y capturar requests ajenos. Es el análogo, a nivel de protocolo, de la confusión datos/código: dos parsers que no se ponen de acuerdo sobre la estructura del mensaje.
📌 Defensa arquitectónica (conceptual, sin payload).
  • Normalizar o rechazar en el borde todo request con Content-Length y Transfer-Encoding a la vez, o con framing malformado.
  • Front y back con el mismo parser y la misma configuración HTTP: la desincronización nace de dos criterios distintos.
  • HTTP/2 extremo a extremo: su framing lleva la longitud explícita y no admite esta ambigüedad; el riesgo reaparece si el back "baja" a HTTP/1.1.
  • Evitar reutilizar la conexión con el upstream cuando no aporta, para que un request no pueda contaminar al siguiente.

CS2.5 Lógica de negocio: los bugs que ninguna herramienta encuentra

Los scanners buscan firmas: un payload conocido, una respuesta característica. Las vulnerabilidades de lógica de negocio no tienen firma porque el request está perfectamente bien formado: lo que se rompe no es la sintaxis, es la intención. La secuencia o los valores violan una invariante del negocio que ninguna herramienta conoce, porque esa invariante vive en la cabeza de quien diseñó la feature.

Race conditions y TOCTOU en pagos

El patrón TOCTOU (Time-Of-Check to Time-Of-Use): entre el momento en que verificás una condición y el momento en que actuás, hay una ventana. Si llegan varios requests concurrentes, todos pasan el chequeo antes de que ninguno haya escrito el resultado. Se confía en que el estado no cambió entre el check y el use —la confusión de canal, otra vez, ahora contra el reloj—. Es el corazón del Worked Example de abajo.

Abuso de flujos

Un flujo multi-paso (carrito → pago → confirmación; o los pasos de un reset de contraseña) es seguro solo si el servidor obliga el orden. Si cada endpoint confía en que el paso anterior corrió, el atacante saltea: golpea "confirmar pedido" sin pasar por "pagar", o repite el paso de un reset. La defensa es una máquina de estados del lado servidor, no un flujo que maneja el cliente con botones.

Manipulación de precios del lado cliente

El clásico eterno: confiar en un precio, una cantidad o un descuento que vino del cliente —un campo oculto, un JSON con precio: 0—. El cliente puede mandar cualquier cosa.

// El atacante manda directamente esto; no hay "validacion de UI" que lo pare
POST /api/checkout
{ "item": "notebook", "precio": 1, "cantidad": 1 }
📌 Regla sin excepciones: ningún valor con consecuencia económica se toma del cliente. El servidor recalcula precio, descuento e impuestos a partir de datos que él controla (catálogo, reglas de cupón), usando del request solo los identificadores (qué ítem), nunca los montos.

IDOR encadenados

Un IDOR aislado puede parecer de severidad baja: "filtra el nombre de otro usuario, y qué". Pero la severidad está en la cadena. Un IDOR que expone un user_id alimenta a otro endpoint que, con ese id, expone un token de recuperación, que alimenta la toma de la cuenta. Tres bugs "menores" componen un account takeover.

💡 Cómo se piensan estos bugs. No se buscan con un payload: se buscan enumerando invariantes y atacando cada una. "Un cupón se aplica a lo sumo una vez por usuario." "Un usuario solo ve sus propios pedidos." "El precio es autoridad del servidor." "Los pasos ocurren en orden." Para cada invariante, la pregunta es ¿qué request o qué secuencia la viola? Es threat modeling (CS1) a nivel de feature, y es la parte del trabajo que no se automatiza.

CS2.6 Autorización a escala: el bug más común y peor detectado

La autorización (M03) es fácil de explicar en un endpoint y brutalmente difícil de sostener en doscientos. Porque authz no es un control: es N controles dispersos, uno por endpoint, y el problema es la consistencia. Cualquier handler que se olvidó el check, o que verificó autenticación pero no autorización, o que chequeó el recurso equivocado, es un agujero.

# FRAGIL: la regla vive esparcida en cada handler (y alguno se la olvida)
@app.get("/factura/{id}")
def ver_factura(id, user):
    factura = repo.get(id)
    if factura.owner_id != user.id and user.role != "admin":
        abort(403)
    return factura
# multiplicalo por 200 endpoints: basta UNO sin el 'if' para tener un IDOR
⚠️ Por qué es el peor detectado. La inyección y el XSS tienen payload: mandás algo raro y pasa algo raro. Un check de authz faltante no tiene payload —el "exploit" es un request perfectamente normal, hecho por el usuario equivocado—. No hay error, no hay crash, el happy path funciona impecable. El código que falta se ve idéntico al código correcto. Ni un scanner ni un test genérico conocen tu política, así que el bug pasa la revisión, pasa el pipeline, y vive en producción hasta que alguien lo prueba a mano.

La respuesta a escala es sacar la decisión de cada handler y centralizarla en una política testeable y auditable —un motor como OPA/Rego o AWS Cedar, o una capa interna bien estructurada—. El handler hace una pregunta uniforme; la regla vive en un solo lugar.

# MEJOR: la decision se delega a UNA politica central + enforcement que falla-cerrado
@app.get("/factura/{id}")
@requiere_permiso                     # middleware default-deny: sin decision explicita, 403
def ver_factura(id, user):
    factura = repo.get(id)
    autz.exigir(user, accion="factura:leer", recurso=factura)  # pregunta a la politica
    return factura
📌 Dos condiciones, no una. Centralizar la política resuelve la consistencia de la regla, pero no sirve si un handler se olvida de invocarla. Combinalo con enforcement a nivel framework que falle-cerrado: default-deny (sin decisión explícita, se rechaza), y autorización por objeto, no solo por ruta —el bug clásico es autorizar el endpoint pero no verificar que este recurso sea del usuario—.

CS2.7 La cadena de dependencias del front

Tu aplicación no es solo tu código: es tu código más cientos de dependencias transitivas que corren en tu build y en el browser de tus usuarios. Cada una es una delegación de confianza.

Ataques a paquetes npm

El vector no es una vulnerabilidad en tu código, sino un paquete comprometido: una cuenta de mantenedor tomada que publica una actualización maliciosa, un typosquat (un nombre parecido al que quisiste instalar), o dependency confusion (el nombre de un paquete interno resuelve al registro público, donde el atacante subió uno homónimo). El código malicioso corre en el postinstall durante el build, o se envía al bundle que llega al usuario.

# Reproducible y verificado por hash: no "la ultima version" en cada build
npm ci                  # instala EXACTO lo del lockfile, con chequeo de integridad
npm audit --production  # deuda conocida en el arbol de dependencias
npm ci --ignore-scripts # si no necesitas postinstall, no lo ejecutes
Higiene de supply chain del front: lockfile con hashes de integridad y npm ci (no npm install) en CI; minimizar dependencias (cada una es superficie); revisar los diffs de actualización en vez de saltar de versión a ciegas; SBOM y análisis de composición (SCA); y para paquetes internos, un registro con scope propio para cerrar la puerta a dependency confusion.

Integridad de subrecursos (SRI)

Si cargás un script de un CDN, Subresource Integrity hace que el browser rechace ejecutarlo si los bytes no coinciden con el hash que declaraste: defensa directa contra un CDN comprometido que sirve un JavaScript alterado.

<!-- El browser NO ejecuta el script si los bytes no coinciden con el hash -->
<script src="https://cdn.example/lib.min.js"
        integrity="sha384-oqVuAfXR9GqQ8Kux1kPzQho1wx4JwY8wCq7fdgcCY5uykM6R9rx7HNQlGYl"
        crossorigin="anonymous"></script>
SRI protege integridad, no confidencialidad, y tiene un límite: sirve para recursos versionados y estables —hay que actualizar el hash en cada cambio legítimo—, y no aplica a recursos generados dinámicamente. No reemplaza a la CSP; se combinan.

El DOM como superficie

Todo script de tercero —analítica, tag manager, chat, A/B testing— corre con acceso total al DOM y privilegios de tu mismo origen. Puede leer formularios, cookies sin HttpOnly, inyectar nodos. Cada tercero que embebés es confianza que le prestás a un dominio que no controlás. Minimizá, aislá lo que puedas en iframes con sandbox, y usá la CSP para acotar qué pueden cargar.

CS2.8 Secretos en el cliente: todo lo que llega al browser es público

La afirmación más simple y más ignorada del AppSec de front:

💡 Todo lo que llega al navegador es público. El JavaScript minificado y ofuscado, las claves de API "escondidas", los feature flags, cualquier clave de "cifrado del lado cliente": el devtools del usuario —y el de un atacante— lo ve todo. La ofuscación no es secreto; es un cartel que dice "mirá acá" con letra chica. 
// TEATRO: "ofuscar" no es "ocultar". Apenas llega al browser, ya es publico.
const API_KEY = "sk_live_9f8b...";   // cualquiera lo lee en el bundle
// DISENO CORRECTO: el secreto vive en el backend; el browser llama a TU API
const r = await fetch("/api/precio", {
  method: "POST",
  body: JSON.stringify({ items })
});
// el precio lo calcula y firma el servidor, con datos que el cliente no controla
📌 Qué significa para el diseño. El cliente es un entorno de ejecución no confiable que no controlás. Todo secreto que deba seguir siendo secreto vive en el servidor. Una API key que tiene que estar en el cliente debe ser pública por diseño: con scope reducido, rate-limit, restricción por referrer/origen y revocable —o proxeada por tu backend—. La validación del lado cliente es UX, nunca seguridad. Y el corolario que ata todo el módulo: autorización, cálculo de precios y reglas de negocio no se pueden hacer cumplir en el cliente. El cliente puede esconder un botón; no puede impedir el request.

CS2.9 Secure by design: la defensa que no depende de la memoria

Recorrimos muchas defensas. Si tuvieras que quedarte con un solo principio para elegir cómo construir, es este: la mejor defensa es la que no depende de que el dev se acuerde. La disciplina humana no escala a mil call-sites ni a cinco años de rotación de equipo. Los tipos y los defaults, sí.

Elegí herramientas cuyo camino por defecto sea seguro y cuyo camino inseguro sea ruidoso y visible:

ORM/query builder que parametriza por defecto. El SQL crudo es el opt-in, y salta a la vista en el code review. El default no inyecta.
Plantillas con auto-escaping prendido. El marcador raw/safe es el opt-out visible; olvidarse produce salida escapada de más, no un XSS.
Tipos que fuerzan validación en la frontera. Parse, don't validate: un tipo que solo se construye validando hace que "input sin validar" sea irrepresentable aguas abajo.
# El tipo hace imposible representar "input sin validar" mas adelante
import re
from dataclasses import dataclass

@dataclass(frozen=True)
class Email:
    valor: str
    def __post_init__(self):
        if not re.fullmatch(r"[^@\s]+@[^@\s]+\.[^@\s]+", self.valor):
            raise ValueError("email invalido")

# Si una funcion pide un Email, no puede recibir un string crudo sin validar:
# el error se detecta al CONSTRUIR, no vaya-a-saber-donde al usarlo.
📌 El principio en una frase. Mové la seguridad de "acordate de hacer X en cada uno de los 1000 lugares" a "el único lugar que puede hacer X-inseguro es visible, y todo el resto es seguro por construcción". Trusted Types (CS2.3), el default-deny de authz (CS2.6) y el tipo Email de arriba son la misma jugada: empujar la corrección hacia los tipos y los defaults, no hacia la memoria del que codea.

CS2.10 Cuándo una defensa es teatro

Cerramos con el criterio para no engañarte a vos mismo. Una defensa es teatro de seguridad cuando se puede evadir sin tocar el código vulnerable, o cuando depende de que el atacante use exactamente el vector que anticipaste.

TeatroPor qué fallaDefensa real
WAF como única capaFiltra firmas en el borde: se evade con encoding o con un bug de lógica que no tiene firma; el agujero sigue ahíWAF más código corregido (defensa en profundidad), nunca en lugar de
"Sanitizamos el input" (sin contexto)Escapar para HTML lo que va a un shell, una URL o un string JS es el encoding equivocadoEncoding por contexto en la salida, en el sink; la validación de entrada complementa, no sustituye
Validación solo en el clienteEl atacante manda el request directo a la API y saltea toda la UIValidar en el servidor; el cliente es UX
Ofuscar secretos en el bundleTodo lo que llega al browser es público (CS2.8)El secreto en el backend; keys de cliente scoped y revocables
El test decisivo: preguntate "¿esta defensa se puede evadir sin arreglar el bug de fondo?". Si la respuesta es sí, es una capa —tal vez útil para ganar tiempo—, pero no es la solución. La solución vive en el código que causa la vulnerabilidad, y todo lo demás es contención alrededor.

🧑‍🎓 Worked Example — el cupón que se aplica N veces

Una tienda tiene un endpoint "aplicar cupón". El cupón WELCOME10 es un crédito válido una vez por usuario. En producción aparece un usuario que lo aplicó cinco veces y quedó con saldo a favor. El código se ve correcto y no tiene errores. ¿Qué pasó y cómo se blinda?

Paso 1 — El código "correcto" que sangra. Valida "no usado" y después marca "usado". Impecable en el happy path.

# VULNERABLE: TOCTOU entre validar y consumir
def aplicar_cupon(user_id, codigo):
    ya_usado = db.query(
        "SELECT 1 FROM cupones_usados WHERE user_id = ? AND codigo = ?",
        user_id, codigo)
    if ya_usado:                       # TIME-OF-CHECK
        raise Error("cupon ya usado")
    descuento = tabla_cupones[codigo]
    aplicar_descuento(user_id, descuento)
    db.execute(                        # TIME-OF-USE (una eternidad despues, en CPU)
        "INSERT INTO cupones_usados (user_id, codigo) VALUES (?, ?)",
        user_id, codigo)

Paso 2 — El diagnóstico. Es TOCTOU. Entre el SELECT (check) y el INSERT (use) hay una ventana. Si el atacante dispara cinco requests casi simultáneos, los cinco corren el SELECT y ven "no usado" antes de que cualquiera llegue al INSERT. Los cinco pasan, los cinco aplican. El request está bien formado, el código no tiene bug de sintaxis: es un bug de concurrencia que ningún linter marca. Confiamos en que el estado no cambió entre el check y el use, y esa confianza es la vulnerabilidad.

Paso 3 — Tres capas de defensa, cada una contra un ataque distinto.

Capa 1 — Bloqueo optimista (escritura condicional). La base decide el ganador: el INSERT solo ocurre si nadie se adelantó. Los perdedores afectan 0 filas y se rechazan.

# Capa 1 — escritura condicional: la carrera la resuelve la BD, no la app
filas = db.execute(
    "INSERT INTO cupones_usados (user_id, codigo) "
    "SELECT ?, ? WHERE NOT EXISTS ("
    "  SELECT 1 FROM cupones_usados WHERE user_id = ? AND codigo = ?)",
    user_id, codigo, user_id, codigo)
if filas == 0:
    raise Error("cupon ya usado")      # otro request gano la carrera

Capa 2 — Idempotencia. El cliente manda una clave única por intención; los reintentos y duplicados devuelven el mismo resultado sin volver a aplicar.

# Capa 2 — idempotencia: la misma intencion produce el mismo resultado
def aplicar_cupon(user_id, codigo, idempotency_key):
    previo = store.get(idempotency_key)
    if previo is not None:
        return previo                  # reintento/duplicado: devolvemos lo guardado
    resultado = _aplicar_una_vez(user_id, codigo)
    store.put(idempotency_key, resultado, ttl=86400)
    return resultado

Capa 3 — Límite atómico en la base. La invariante vive en el esquema, no en el código. Aunque haya varias instancias de la app, el almacén compartido es el único árbitro.

-- Capa 3 — la invariante vive en el esquema: la BD la enforcea siempre
CREATE TABLE cupones_usados (
    user_id  BIGINT      NOT NULL,
    codigo   TEXT        NOT NULL,
    usado_en TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_cupon_por_usuario UNIQUE (user_id, codigo)
);

-- El segundo INSERT concurrente viola UNIQUE y la BD lo rechaza en forma atomica
INSERT INTO cupones_usados (user_id, codigo)
VALUES ($1, $2)
ON CONFLICT (user_id, codigo) DO NOTHING;   -- filas afectadas = 0 : ya estaba usado

Paso 4 — Qué capa para qué ataque. No son redundantes: cada una tapa un hueco que las otras dejan.

Escenario de ataqueCapa que lo detienePor qué
Doble click / reintento de red del mismo intentoIdempotenciaLa segunda vez devuelve el resultado guardado; no re-aplica
Dos requests en el mismo instante, mismo procesoBloqueo optimistaSolo uno cumple la condición; el resto afecta 0 filas
Requests repartidos entre varias instancias detrás del balanceadorRestricción atómica en la BDLos locks de app no cruzan procesos; la BD es el único árbitro compartido
100 requests en paralelo scripteadosBD atómica + bloqueo optimistaLa invariante la enforcea el almacén; las capas de app fallan-rápido antes
📌 La lección del ejercicio no es "usá una restricción UNIQUE". Es que la invariante —"un cupón se aplica a lo sumo una vez por usuario"— es el artefacto de diseño, y se hace cumplir en la capa más baja y autoritativa (la base), con las capas de app como optimizaciones que fallan rápido. Un lock en memoria del proceso te habría dado una falsa sensación de seguridad: no cruza instancias. Esto es secure by design (CS2.9): la BD no depende de que ningún dev se acuerde de nada.

Checkpoint — ¿lo tenés claro?

Sale una técnica de inyección nueva, con otro nombre, contra un intérprete que no conocías. ¿Cómo la encarás sin esperar el parche?

Preguntándote cuál de las dos confusiones explota. Si es "datos que se vuelven código" (casi siempre, en una inyección), la defensa de la clase ya la sabés: que los datos no crucen a estructura —parametrizar, usar una API estructurada, no concatenar entrada no confiable en aquello que el intérprete va a evaluar—. No importa si el intérprete es SQL, un motor de plantillas, argv o un deserializador: el antídoto es el mismo. Bloquear el payload de ejemplo con una regla es perseguir firmas; corregir la frontera datos/código mata toda la clase.

¿Por qué un check de autorización faltante es el bug peor detectado, más que un XSS o una inyección?

Porque no tiene payload ni firma. El XSS y la inyección se disparan con una entrada anómala que produce una respuesta anómala; una herramienta puede buscar eso. Un check de authz que falta se explota con un request perfectamente normal hecho por el usuario equivocado: no hay error, no hay crash, el happy path anda. El código ausente se ve idéntico al código correcto, y ningún scanner conoce tu política de permisos. Por eso pasa la revisión y el pipeline, y por eso la defensa es estructural: política central testeable más enforcement default-deny por objeto, no un if repetido a mano en 200 lugares.

Tu SPA trae una API key en el bundle, minificado y ofuscado. Un revisor dice que está protegida. ¿Tiene razón?

No. Todo lo que llega al browser es público: el devtools del usuario —y de un atacante— lee el bundle entero, ofuscado o no. La ofuscación no es confidencialidad. Una clave que debe seguir secreta vive en el backend, y el browser llama a tu API. Si una key sí o sí tiene que estar en el cliente, tiene que ser pública por diseño: scope reducido, rate-limit, restricción por origen y revocable. SRI no ayuda acá —protege la integridad del script, no la confidencialidad de un secreto adentro—.

Resumen ejecutivo

  • Casi todo bug web es una de dos confusiones: datos que se vuelven código, o un canal que recibe confianza que no merece. Aprendé las dos y deducís los bugs que todavía no tienen nombre.
  • Inyección es la misma confusión en distintos intérpretes: SSTI, NoSQL/GraphQL, argumentos de argv, deserialización con gadget chains. La corrección siempre es mantener los datos como datos.
  • El XSS de DOM no se gana con sanitizado casero: el parser del navegador muta el markup (mXSS) y el HTML puede sombrear globales (DOM clobbering). La defensa estructural es Trusted Types; la CSP mitiga, no cura.
  • El request smuggling nace de que front y back parsean distinto el mismo request. Se defiende rechazando la ambigüedad en el borde y con HTTP/2 extremo a extremo.
  • Los bugs de lógica de negocio (TOCTOU, abuso de flujos, precios del cliente, IDOR encadenados) no tienen firma: se cazan enumerando invariantes y preguntando qué las viola.
  • La autorización a escala es el bug más común y peor detectado —sin payload, sin firma—. Se ataca con política central (OPA/Cedar) más enforcement default-deny por objeto.
  • La cadena de dependencias del front y los secretos en el cliente son confianza mal puesta: todo lo que llega al browser es público, y cada dependencia corre en tu build y en tus usuarios.
  • Secure by design: la mejor defensa no depende de que el dev se acuerde —defaults seguros, tipos que fuerzan validación, sinks que fallan-cerrado—. Y una defensa que se evade sin tocar el bug de fondo es teatro.

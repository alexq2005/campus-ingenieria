Módulo 03 — Autorización y control de acceso

En el M02 resolviste quién sos. Este módulo es sobre qué podés hacer, y ahí es donde se rompen las aplicaciones reales: un id en la URL que nadie verificó, un endpoint que nació sin control, un admin que se dio "por hoy" hace dos años. El control de acceso roto lidera el OWASP Top 10 desde 2021.

Autenticación ≠ autorización

💡 Dos preguntas distintas, en ese orden. Autenticación (AuthN) responde "¿quién sos?" y se resuelve una vez, al entrar. Autorización (AuthZ) responde "¿podés hacer esta acción sobre este objeto?" y va en cada request. Estar logueado no es un permiso: es el prerrequisito para evaluarlos.
🏨 La analogía del hotel. El mostrador te identifica con el DNI: autenticación, una sola vez. La tarjeta abre tu habitación y el gimnasio, pero no el depósito: autorización, y se evalúa en cada puerta. Un hotel que pide el DNI en la entrada y deja todas las puertas sin cerradura autentica perfecto y autoriza cero.

Por qué la autorización se rompe mucho más que la autenticación:

  • No hay librería que la resuelva. El login lo hace un framework probado; "esta factura es del usuario X" es lógica de tu dominio, y la escribís vos endpoint por endpoint.
  • No falla ruidosamente. Un login roto lo reporta el primer usuario; una autorización rota funciona perfecto: solo permite de más, en silencio.
  • Los tests miran el camino feliz: se prueba que el dueño vea su recurso, casi nunca que otro no lo vea.

Modelos de control de acceso

Cuatro formas de responder "¿puede S hacer A sobre O?". No son excluyentes: los sistemas reales combinan dos.

ModeloCómo decideCuándo usarloSu límite
ACL
listas		Una lista por objeto: "este archivo lo leen Ana y Beto"Pocos objetos y permisos puntuales. Los archivos de UnixNo escala: miles de objetos × miles de usuarios
RBAC
roles		El usuario tiene roles; el rol tiene permisos: "los editores publican"El más común: puestos claros y establesExplosión de roles: aparece editor_sur_sin_borrado
ABAC
atributos		Reglas sobre sujeto, objeto y contexto: "el médico ve la historia si está de guardia en ese servicio"Cuando decide el contexto: horario, país, montoHay que simular para saber quién accede a qué
ReBAC
relaciones		Un grafo: "sos editor de la carpeta y el documento está dentro"Compartición entre usuarios, jerarquías, herencia. DriveNecesita servicio dedicado y consultas de grafo rápidas
El artículo Zanzibar de Google (2019) describe el ReBAC que autoriza Drive, YouTube y Calendar: todo son tuplas objeto#relación@sujeto y "¿puede X leer Y?" se resuelve recorriendo el grafo. De ahí salieron OpenFGA y SpiceDB.
Empezá con RBAC y agregá lo mínimo. Una regla que no entra en un rol —"solo en horario laboral", "solo montos menores a X"— va como atributo (RBAC + ABAC), no como rol nuevo. Y "un usuario comparte el objeto con otro" pide relaciones.

Los tres principios que sostienen todo

1. Mínimo privilegio. Cada sujeto —persona, servicio, token, contenedor— recibe los permisos que necesita y ni uno más. El usuario de base de datos que arma reportes no necesita UPDATE; el cron de facturación no borra usuarios.
2. Denegar por defecto. Lo que no está explícitamente permitido está prohibido: un endpoint nuevo nace cerrado y se abre a propósito. Lista blanca de rutas públicas, no lista negra de rutas protegidas.
3. Separación de deberes. Nadie completa solo un proceso sensible: quien crea un pago no lo aprueba, quien escribe el código no aprueba su deploy. No es desconfianza: es que una cuenta comprometida no alcance para el daño completo.
Privilege creep: el permiso que nadie saca. Ana entra a soporte y recibe el panel de tickets. Pasa a ventas y le suman el CRM, pero nadie le quita soporte. Cubre dos semanas en facturación y le dan admin "temporal". A los tres años puede hacer todo, sin que nadie lo decidiera. El antídoto es aburrido: permisos con vencimiento y recertificación periódica.

Escalada de privilegios: horizontal y vertical

Cuando la autorización falla, el atacante gana permisos que no le tocaban. Hay dos direcciones, y conviene separarlas porque se testean distinto:

                 ▲  VERTICAL — usuario común ──► admin
   HORIZONTAL    │     "cambio mi rol", "entro al panel /admin"
   ◄─────────────┼─────────────►   mismo nivel, otra identidad
   la factura    │   el perfil     "leo los datos de otro usuario"
   del user B    │   del user C
  • Horizontal: seguís siendo un usuario común pero accedés a datos de otro usuario común. La más frecuente y la más subestimada: en los logs no aparece ningún "admin", solo un usuario legítimo pidiendo recursos. Filtrar la base de clientes entera se hace iterando IDs.
  • Vertical: pasás a un nivel superior. Suele venir de un endpoint administrativo sin control o de un campo rol que el cliente manda en un PUT /perfil.

IDOR / BOLA: el bug número uno

⚠️ Broken Object Level Authorization es el puesto #1 del OWASP API Security Top 10, y su primo IDOR el clásico de las apps web. La receta es siempre la misma: el servidor recibe un identificador desde el cliente, lo usa para buscar el dato y nunca comprueba si el usuario autenticado tiene derecho sobre ese objeto. Cambiar /facturas/1042 por /facturas/1043 devuelve la factura de otro: es apretar una tecla.

Es tan común porque el chequeo que falta no se ve: el código "funciona" y devuelve una factura bien formada. El QA prueba con su usuario y ve la suya; el bug solo existe desde la perspectiva de un segundo usuario.

El malentendido más caro: "lo arreglo usando UUIDs". Un UUID evita que el ID sea adivinable, pero no es la solución: el problema nunca fue que fuera predecible sino que no se verifica el dueño. Los identificadores se filtran solos —URLs compartidas, logs, referers, exports— y ahí el acceso vuelve a abrirse. El UUID es defensa en profundidad; la propiedad es el control.

Nivel de función vs nivel de objeto

Son dos chequeos distintos y necesitás los dos: confundirlos deja media aplicación abierta.

ChequeoPreguntaSi falta…Ejemplo de falla
Nivel de función¿Este rol puede ejecutar esta operación?Escalada verticalUn usuario común llama DELETE /api/usuarios/9 y funciona
Nivel de objeto¿Este usuario puede tocar este registro?Escalada horizontal (IDOR/BOLA)Un usuario legítimo lee GET /api/facturas/1043, que es de otro
📌 Esconder el botón no es autorización. Si la UI oculta "Eliminar" para los no-admin pero el endpoint DELETE no verifica nada, la protección dura hasta que alguien abra las devtools. El front decide qué mostrar; el back, qué permitir.

Confused deputy: cuando el permiso lo pone otro

El diputado confundido es un servicio con permisos altos que ejecuta acciones a pedido de terceros con permisos bajos: actúa de buena fe, pero usa su autoridad para hacer lo que le pidió alguien que no la tenía.

Usuario común  ──pide──►  Servicio de reportes  ──lee con su credencial──►  RRHH
(sin acceso a RRHH)       (acceso total a la base)

El servicio pregunta "¿el dato existe?" en vez de "¿este usuario puede verlo?"

Aparece en integraciones todo el tiempo: el microservicio que consulta con una credencial de servicio "porque es interno", el proxy que reenvía requests sin propagar quién los originó. La regla que lo evita es una sola: el servicio decide en nombre del solicitante, no en el suyo.

Path traversal: el mismo bug, sobre archivos

Cuando el objeto es un archivo, la referencia insegura toma la forma de una ruta: si el nombre lo elige el usuario y se concatena a un directorio base, ../ permite salir de ahí y leer lo que el proceso puede leer.

# ❌ La ruta la arma el usuario
ruta = "/var/app/uploads/" + request.args["archivo"]
# archivo = "../../../etc/passwd"  →  se escapa del directorio base

# ✅ Resolvé la ruta real y comprobá que sigue adentro
import os
BASE = os.path.realpath("/var/app/uploads")
ruta = os.path.realpath(os.path.join(BASE, request.args["archivo"]))
if not ruta.startswith(BASE + os.sep):
    abort(403)

# ✅✅ Mejor: que mande un ID; el nombre real lo buscás en la base,
#     y ahí mismo verificás el dueño.

¿Dónde vive la decisión?

EstrategiaCómo esVentajaRiesgo
En cada endpointUn if al principio de cada handlerExplícito, sin infraestructuraFrágil: el endpoint nuevo se olvida y nadie lo nota
En middlewareUna capa que intercepta antes del handlerDenegar por defecto real: lo nuevo nace cerradoCubre el nivel de función; el de objeto sigue en el handler
Política centralizadaLas reglas viven aparte (OPA/Rego, Cedar, Casbin) y el código preguntaAuditable y versionable sin tocar la app; una sola verdad para todos los serviciosUn componente más que operar; latencia si se consulta por red

Centralizar convierte el control de acceso en algo que se puede leer y revisar: con reglas dispersas en 200 handlers, "¿quién puede aprobar pagos?" se responde con un grep y un rezo; con política declarativa, leyendo un archivo que además se testea solo.

APIs y microservicios: propagá identidad, no permisos

📌 Entre servicios viaja quién pide, no qué puede. Si A le manda a B un header X-Es-Admin: true, la decisión ya la tomó A y B obedece: cualquiera que pueda hablarle a B es admin. Propagá la identidad en un token firmado y de vida corta, y que cada servicio evalúe los permisos por su cuenta. La red interna no es un perímetro.

🔧 En tu código: la autorización que no se rompe

1. En el servidor y en cada request. Sin excepciones para "esta pantalla ya la validamos" ni para peticiones internas.
2. Nunca uses un identificador del cliente sin comprobar el dueño, y comprobalo dentro de la consulta, no en un if posterior que se pierde en el próximo refactor. 
# ❌ IDOR: el ID viene del cliente y no se verifica de quién es
@app.get("/facturas/<int:factura_id>")
def ver_factura(factura_id):
    f = db.query_one("SELECT * FROM facturas WHERE id = ?", factura_id)
    return render(f)

# ✅ El dueño es parte de la consulta, y sale de la sesión
@app.get("/facturas/<int:factura_id>")
def ver_factura(factura_id):
    f = db.query_one(
        "SELECT * FROM facturas WHERE id = ? AND owner_id = ?",
        factura_id, sesion.usuario_id)      # ← de la sesión, jamás del request
    if f is None:
        abort(404)          # 404 y no 403: no confirmes que el objeto existe
    return render(f)
3. Deny by default en el router. Lista blanca de rutas públicas, no lista negra de rutas protegidas: así el endpoint que agregás mañana nace cerrado. 
# ❌ Lista negra: cada ruta nueva nace pública
RUTAS_PROTEGIDAS = {"/admin", "/facturas"}
def middleware(req):
    if req.path in RUTAS_PROTEGIDAS:
        exigir_sesion(req)

# ✅ Lista blanca: todo cerrado salvo lo explícitamente abierto
RUTAS_PUBLICAS = {"/", "/login", "/health"}
def middleware(req):
    if req.path not in RUTAS_PUBLICAS:
        usuario = exigir_sesion(req)
        exigir_permiso(usuario, req)   # ¿puede ejecutar ESTA operación?
4. El caso "A pide el recurso de B" es un test, no una revisión manual. Uno por tipo de recurso, corriendo en CI: la única forma de que el chequeo no desaparezca en un refactor futuro. 
def test_usuario_a_no_accede_a_la_factura_de_b(client):
    factura_b = crear_factura(owner=usuario_b)
    client.login(usuario_a)

    r = client.get(f"/facturas/{factura_b.id}")
    assert r.status_code in (403, 404)
    assert b"total" not in r.data        # ni siquiera una fuga parcial

def test_usuario_comun_no_borra_usuarios(client):
    client.login(usuario_a)              # rol: "cliente"
    assert client.delete("/api/usuarios/9").status_code == 403
5. No uses el rol del token sin validarlo. Verificá firma, emisor, audiencia y expiración; en operaciones sensibles consultá el estado vivo: un token de hace 50 minutos puede decir admin de alguien a quien despidieron hace 20. 
# ❌ El cliente elige su propio rol
if request.headers.get("X-User-Role") == "admin":
    borrar_todo()

# ✅ Identidad verificada + permisos consultados al sistema, no al token
claims = jwt.decode(token, CLAVE_PUBLICA, algorithms=["RS256"],
                    audience="api-facturas", issuer="https://idp.interno")
if not politica.permite(claims["sub"], "facturas:borrar", factura_id):
    abort(403)

Errores típicos

1. Confiar en que el ID es difícil de adivinar.
❌ "Usamos UUIDs, nadie va a acertar un identificador."
✅ El ID puede ser público: lo que protege el recurso es verificar el dueño en cada acceso.
2. Comprobar permisos solo al armar el menú.
❌ El front oculta "Eliminar" si el rol no es admin, y el endpoint DELETE confía en eso.
✅ La UI decide qué mostrar; el servidor decide qué permitir. Solo uno es un control de seguridad.
3. Usar el user_id que viene en el cuerpo del request.
❌ transferir(desde=body["user_id"], monto=body["monto"]) — el cliente elige de qué cuenta sale la plata.
✅ La identidad sale siempre de la sesión o del token verificado.
4. Dar permisos de admin "temporalmente".
❌ "Dale admin a Ana para que resuelva esto hoy" — y ahí queda, sin registro ni fecha.
✅ Accesos elevados con vencimiento automático y motivo registrado. Sin soporte de expiración, el alta se abre con la baja ya agendada.

Checkpoint

¿Por qué conviene devolver 404 en vez de 403 cuando alguien pide un objeto que no le pertenece?

Porque un 403 confirma que el objeto existe, y esa confirmación ya es información: iterando IDs con respuestas distinguibles, un atacante mapea cuántos registros hay y en qué rango están los identificadores válidos, sin leer un dato. Un 404 uniforme hace que "no existe" y "no es tuyo" se vean idénticos desde afuera. La excepción es cuando el usuario debería saber que el recurso existe y solo le falta un permiso.

Tenés RBAC funcionando y aparece el requisito "cada usuario comparte sus documentos con quien quiera". ¿Por qué RBAC solo no alcanza?

Porque RBAC asigna permisos a categorías de usuarios que define la organización, y acá el permiso lo define un usuario final sobre un objeto puntual, en tiempo real. Con roles habría que crear uno por documento compartido —editor_doc_8842—, la explosión de roles que vuelve inauditable un sistema. Es una relación entre sujeto y objeto: pide ReBAC, con herencia por carpeta. RBAC sigue sirviendo para lo organizacional.

Un microservicio interno acepta un header X-User-Role que le manda el API gateway. ¿Qué está mal y cómo se arregla?

Está delegando la autorización en quien lo llama, lo cual solo es seguro si nadie más puede hablarle — suposición que se cae con una VPN mal configurada, un SSRF o un contenedor comprometido: es el confused deputy. El arreglo tiene dos partes: propagar la identidad del usuario original en un token firmado y de vida corta (no un permiso ya resuelto), y que el servicio verifique la firma y evalúe los permisos por sí mismo.

Ejercicios

  1. Tomá un endpoint tuyo que reciba un ID en la URL y rastreá el camino hasta la base: ¿dónde se verifica el dueño? Si es "en ningún lado", arreglalo con WHERE id = ? AND owner_id = ?.
  2. Escribí el test "el usuario A no puede acceder al recurso de B". Verificá que falla antes del arreglo y pasa después.
  3. Listá las rutas de tu aplicación y marcá cuáles exigen sesión y cuáles verifican permisos de función. ¿El router deniega por defecto?
  4. Diseñá el modelo de autorización de una app de proyectos con dueño, miembros, invitados de solo lectura y comentarios privados. Elegí entre RBAC, ABAC y ReBAC, y justificá.
  5. Revisá los permisos de tu cuenta en algún sistema que uses: ¿cuántos usaste el último mes? Los que sobran son tu privilege creep.
  6. Buscá un servicio tuyo que actúe con su propia credencial a pedido de un usuario, y escribí cómo lo convertirías para que decida en nombre del solicitante.

🧠 Autoevaluación

1. Cambiando /pedidos/501 por /pedidos/502 se ve el pedido de otro cliente. ¿Cuál es el arreglo correcto?

Es un IDOR/BOLA: el problema no es que el ID sea predecible sino que no se verifica la propiedad. UUIDs y mover el ID al body son ofuscación — en cuanto el identificador se filtra, el acceso vuelve a estar abierto. El control real es WHERE id = ? AND owner_id = ?.

2. Un microservicio interno recibe del gateway el header X-Es-Admin: true y actúa en consecuencia. ¿Qué antipatrón es?

El servicio delega la decisión en quien lo llama y ejecuta con sus permisos altos: alcanza con que algo de la red interna pueda hablarle —un SSRF, un contenedor comprometido— para ser admin. Lo correcto es propagar la identidad en un token firmado y que cada servicio evalúe los permisos por su cuenta.

3. El front oculta "Eliminar usuario" para los no-admin, y el endpoint DELETE /api/usuarios/{id} no verifica el rol. ¿Qué falta y qué escalada habilita?

Esconder un control en la UI no es seguridad: el endpoint se llama igual con curl. Lo que falta es "¿este rol puede ejecutar esta operación?" —nivel de función—, y permite que un usuario común ejecute una acción de administrador: escalada vertical. La de nivel de objeto sería tocar el registro de otro usuario del mismo nivel.

Módulo 10 — systemd

¿Qué es systemd?

systemd es el sistema de inicio (init) y manager de servicios moderno en Linux. Reemplazó a SysVinit/Upstart en casi todas las distros mayores.

Responsable de:

  • Arrancar el sistema (PID 1)
  • Lanzar y supervisar servicios (daemons)
  • Gestionar logs (journald)
  • Tareas programadas (timers, alternativa a cron)
  • Mountpoints, sockets, devices, etc.

systemctl — comando principal

Estado y control de servicios

systemctl status nginx                     # estado actual
sudo systemctl start nginx                 # iniciar
sudo systemctl stop nginx                  # detener
sudo systemctl restart nginx               # reiniciar
sudo systemctl reload nginx                # recargar config sin reiniciar
sudo systemctl reload-or-restart nginx     # reload si soporta, si no restart

sudo systemctl enable nginx                # habilitar al arranque
sudo systemctl disable nginx               # deshabilitar
sudo systemctl enable --now nginx          # habilitar y arrancar a la vez
sudo systemctl mask nginx                  # bloquea (no se puede arrancar)
sudo systemctl unmask nginx                # desbloquea

systemctl is-active nginx
systemctl is-enabled nginx
systemctl is-failed nginx

Listar

systemctl                                  # todas las units cargadas
systemctl list-units --type=service        # solo servicios
systemctl list-units --state=failed        # los que fallaron
systemctl list-unit-files                  # todas (instaladas)
systemctl list-unit-files --state=enabled

Anatomía de un .service

[Unit]
Description=Mi App
After=network.target
Requires=postgresql.service

[Service]
Type=simple
User=appuser
Group=appgroup
WorkingDirectory=/opt/miapp
Environment="ENV=production"
EnvironmentFile=/etc/miapp/env
ExecStart=/usr/bin/python3 /opt/miapp/main.py
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
RestartSec=5s
StandardOutput=journal
StandardError=journal

# Hardening
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
ReadWritePaths=/var/lib/miapp

[Install]
WantedBy=multi-user.target

Crear un servicio

sudo nano /etc/systemd/system/miapp.service
sudo systemctl daemon-reload                # leer cambios
sudo systemctl enable --now miapp
sudo systemctl status miapp

Para servicios de usuario (sin sudo):

mkdir -p ~/.config/systemd/user/
nano ~/.config/systemd/user/miapp.service
systemctl --user daemon-reload
systemctl --user enable --now miapp

journald — el log del sistema

journalctl consulta los logs centralizados:

journalctl                                 # todos los logs

journalctl --vacuum-time=2weeks            # limpiar viejos

Timers — alternativa moderna a cron

Definición

# /etc/systemd/system/backup.timer
[Unit]
Description=Backup diario

[Timer]
OnCalendar=daily
OnCalendar=*-*-* 02:30:00      # alternativa: cron-style
Persistent=true                 # ejecuta si se perdió la última corrida
RandomizedDelaySec=10min

[Install]
WantedBy=timers.target
# /etc/systemd/system/backup.service
[Unit]
Description=Backup ejecutable

[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh
sudo systemctl enable --now backup.timer
systemctl list-timers                      # ver próximas ejecuciones

Errores típicos que se ven recién al reiniciar

Editar la unit y no correr daemon-reload. systemd tiene las units cacheadas en memoria: tu restart vuelve a levantar la versión vieja y te volvés loco buscando por qué el cambio no hace nada. 
sudo nano /etc/systemd/system/miapp.service
sudo systemctl restart miapp           # ❌ arranca con la config anterior
# ✅
sudo systemctl daemon-reload
sudo systemctl restart miapp
systemctl cat miapp                    # 🔎 confirmá qué está leyendo de verdad
start sin enable. El servicio queda andando y todo parece bien... hasta que el server se reinicia a las 3 AM y no vuelve, porque nunca se creó el enlace en el target de arranque. 
sudo systemctl start miapp             # ❌ solo ahora; no sobrevive al reboot
sudo systemctl enable --now miapp      # ✅ arranca ahora Y en cada arranque
systemctl is-enabled miapp             # 🔎 tiene que responder: enabled
Editar el .service que instaló el paquete. Los archivos de /usr/lib/systemd/system/ son del paquete: la próxima actualización los pisa y tu cambio desaparece sin aviso. 
sudo nano /usr/lib/systemd/system/nginx.service   # ❌ lo pisa el próximo upgrade
sudo systemctl edit nginx                        # ✅ drop-in en /etc, que siempre gana
systemctl cat nginx                              # 🔎 muestra el original + los overrides
Restart=always tapando un bug de arranque. Si el servicio muere apenas arranca (falta una variable, la base todavía no está lista), systemd lo relanza para siempre: el journal se llena, el CPU sube y el estado nunca queda en failed, así que ninguna alerta salta. 
Restart=always                         # ❌ loop infinito silencioso
# ✅ en [Service]:
Restart=on-failure
RestartSec=5s
# ✅ y en [Unit], para que se rinda y quede en failed:
StartLimitIntervalSec=300
StartLimitBurst=5

Checkpoint — ¿lo tenés claro?

¿Por qué conviene systemctl edit en vez de abrir el .service original con el editor?

Porque systemctl edit no toca el archivo del paquete: crea un drop-in en /etc/systemd/system/miapp.service.d/override.conf con solo las líneas que querés cambiar, y lo que está en /etc siempre le gana a lo que está en /usr/lib. La ventaja es doble: la actualización del paquete no te pisa nada, y tu cambio queda aislado y fácil de revertir (borrás el drop-in y listo). Para ver el resultado final combinado está systemctl cat miapp.

¿Qué diferencia hay entre Type=simple y Type=forking, y qué pasa si elegís mal?

Con simple, systemd da el servicio por arrancado apenas lanza el proceso de ExecStart, y ese proceso tiene que quedarse en primer plano. Con forking, systemd espera que el proceso inicial se duplique y termine, y después sigue al hijo. Si declarás simple un daemon que se demoniza, systemd ve morir al padre y cree que el servicio se cayó (lo reinicia en loop o lo marca failed); al revés, un forking mal puesto deja a systemd esperando un fork que nunca ocurre, hasta el timeout. Regla práctica: si el programa tiene una opción tipo --foreground, usala y quedate con simple.

¿Cuándo usás reload y cuándo restart, y por qué importa en un server con tráfico?

reload le manda una señal al proceso que ya está corriendo para que relea su configuración: no se cae, no pierde las conexiones abiertas y no hay ventana de downtime. restart mata el proceso y levanta uno nuevo: se cortan las conexiones en curso y hay unos segundos sin servicio. El detalle importante es que no todos los servicios saben recargarse (depende de que la unit tenga ExecReload=); para esos casos existe reload-or-restart, que usa el método suave si puede y el bruto si no.

Respondé sin mirar arriba. Cada pregunta te explica el porqué.

1. ¿Qué diferencia hay entre systemctl start nginx y systemctl enable nginx?

Son cosas distintas: un servicio puede estar corriendo sin estar habilitado (y al revés). Para hacer las dos de una: systemctl enable --now nginx. Recargar la config sin reiniciar es reload.

2. Editaste /etc/systemd/system/miapp.service. ¿Qué hacés antes de reiniciar el servicio?

systemd tiene las units cacheadas: daemon-reload las relee del disco. mask justamente bloquea el servicio para que no pueda arrancar, e isolate cambia el target del sistema al vuelo.

3. En un .timer, ¿para qué sirve Persistent=true?

Recupera la ejecución que se salteó, igual que anacron. Guardar los logs entre reinicios es otra cosa: Storage=persistent en journald.conf.

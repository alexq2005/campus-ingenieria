Módulo 11 — Seguridad

Modelo de amenazas

Un servidor Linux típico enfrenta:

  • Acceso no autorizado (SSH brute force, exploits)
  • Escalación de privilegios (de usuario común a root)
  • Persistencia (rootkits, cron jobs maliciosos)
  • Exfiltración (robar datos)
  • Disrupción (DDoS, fork bombs, llenar disco)

El principio de mínimo privilegio es la guía central: cada componente solo debe tener los permisos estrictamente necesarios.

Hardening de SSH

/etc/ssh/sshd_config:

Port 22                                    # cambiar a uno alto reduce ruido (no es seguridad real)
PermitRootLogin no                         # ⭐ obligatorio
PasswordAuthentication no                  # ⭐ solo llaves
PubkeyAuthentication yes
PermitEmptyPasswords no
MaxAuthTries 3
LoginGraceTime 30
ClientAliveInterval 300
ClientAliveCountMax 2
AllowUsers ana luis                        # whitelist de usuarios
AllowGroups ssh-users                      # o por grupo
X11Forwarding no

Aplicar:

sudo sshd -t                               # validar sintaxis
sudo systemctl reload sshd
Nunca cierres tu sesión actual hasta haber probado que la config funciona desde otra terminal.

Llaves modernas

ssh-keygen -t ed25519                      # ⭐ recomendado 2025
ssh-keygen -t rsa -b 4096                  # alternativa

Firewall

ufw (Uncomplicated Firewall, Debian/Ubuntu)

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow ssh
sudo ufw allow 80/tcp
sudo ufw allow from 192.168.1.0/24
sudo ufw limit ssh                         # limita conexiones repetidas
sudo ufw enable
sudo ufw status verbose

firewalld (RHEL/Fedora)

sudo firewall-cmd --state
sudo firewall-cmd --get-zones
sudo firewall-cmd --zone=public --add-service=https --permanent
sudo firewall-cmd --zone=public --add-port=8080/tcp --permanent
sudo firewall-cmd --reload
sudo firewall-cmd --list-all

nftables (bajo nivel, reemplazo de iptables)

sudo nft list ruleset
sudo nft -f /etc/nftables.conf

fail2ban — protección contra brute force

Lee logs de SSH/web/etc. y banea IPs que fallan demasiado.

sudo apt install fail2ban
sudo systemctl enable --now fail2ban
sudo fail2ban-client status
sudo fail2ban-client status sshd
sudo fail2ban-client unban 1.2.3.4

Config: /etc/fail2ban/jail.local:

[DEFAULT]
bantime = 1h
findtime = 10m
maxretry = 5

[sshd]
enabled = true
port = 22

SELinux — Mandatory Access Control (RHEL/Fedora)

Va más allá de los permisos UGO: el kernel impone reglas adicionales por contexto (tipo, rol, dominio).

getenforce                                 # Enforcing / Permissive / Disabled
sudo setenforce 0                          # cambiar a permisivo (temporal)
sudo setenforce 1                          # enforcing
sestatus

Alternativa a SELinux, perfiles por aplicación.

Buenas prácticas — checklist

  • ☐ No login de root vía SSH
  • ☐ Solo llaves SSH (no contraseñas)
  • ☐ Firewall denegando todo lo no necesario
  • ☐ fail2ban activo en sshd
  • ☐ Actualizaciones automáticas habilitadas
  • ☐ umask >= 027
  • ☐ Llaves SSH con permisos 600
  • ☐ sudo en lugar de su -
  • ☐ Logs persistentes y monitoreados
  • ☐ Backups regulares y verificados
  • ☐ HTTPS en todos los servicios web
  • ☐ Sin servicios escuchando 0.0.0.0 si no hace falta
  • ☐ Usuarios sin shell para servicios (/usr/sbin/nologin)

Errores típicos que te dejan sin acceso (o sin seguridad)

Recargar sshd sin validar la config. Un typo en sshd_config y el daemon no vuelve a levantar. Si ya cerraste la sesión y no tenés consola física ni panel del proveedor, el servidor queda inaccesible. 
sudo systemctl restart sshd            # ❌ a ciegas y con una sola sesión abierta
# ✅ el ritual completo:
sudo sshd -t                           # 1. validar la sintaxis
sudo systemctl reload sshd             # 2. recargar (reload, no restart)
ssh user@host                          # 3. probar desde OTRA terminal
# 4. recién ahí cerrás la sesión original
Apagar la contraseña antes de subir la llave. Con PasswordAuthentication no y sin tu pública en authorized_keys, no queda ninguna forma de entrar al servidor. 
# ✅ el orden importa:
ssh-copy-id user@host                  # 1. subir la llave pública
ssh user@host                          # 2. confirmar que entrás SIN contraseña
# 3. recién ahí poner PasswordAuthentication no en sshd_config
sudo sshd -t && sudo systemctl reload sshd
chmod 777 como "solución" a un permiso denegado. Le das escritura a cualquier usuario o proceso de la máquina: si el server web tiene una vulnerabilidad, ahora puede reescribir tu sitio. Y encima, en RHEL/Fedora muchas veces el bloqueo no era de permisos sino de contexto SELinux, así que el 777 ni siquiera arregla el problema. 
sudo chmod -R 777 /var/www/html        # ❌ el sistema entero con permiso de escritura
# ✅ dueño correcto + permisos mínimos:
sudo chown -R root:www-data /var/www/html
sudo find /var/www/html -type d -exec chmod 750 {} +
sudo find /var/www/html -type f -exec chmod 640 {} +
sudo ausearch -m avc -ts recent        # 🔎 si es RHEL, fijate si el que bloqueó fue SELinux
sudo restorecon -Rv /var/www/html
Desactivar SELinux o el firewall "para probar" y dejarlo así. Es la forma más rápida de que algo funcione y la más rápida de quedar expuesto: nadie vuelve a prenderlo, y el problema real sigue ahí sin diagnosticar. 
sudo setenforce 0                      # ❌ queda permissive y nadie lo revierte
sudo systemctl stop firewalld          # ❌ ídem
# ✅ averiguá qué bloqueó y arreglá eso:
sudo ausearch -m avc -ts recent
sudo setsebool -P httpd_can_network_connect 1
sudo setenforce 1 && getenforce        # volvé a Enforcing y verificalo

Checkpoint — ¿lo tenés claro?

Mover SSH del puerto 22 al 2222, ¿es seguridad? ¿Qué sí lo es?

No es seguridad, es reducción de ruido. Los bots que escanean internet golpean el 22 en masa; correrlo a otro puerto te limpia el auth.log, pero cualquier escaneo con nmap lo encuentra en segundos, así que no frena a nadie que te apunte a vos en particular. Lo que protege de verdad es lo que no depende de que el puerto sea un secreto: solo llaves (PasswordAuthentication no), PermitRootLogin no, AllowUsers o AllowGroups, MaxAuthTries, el firewall filtrando por red de origen y fail2ban. El puerto alto es una comodidad, no una defensa.

Si los permisos UGO ya están bien puestos, ¿qué agregan SELinux o AppArmor?

Los permisos clásicos son discrecionales (DAC): el dueño de un archivo puede aflojarlos cuando quiera, y un proceso que corre como root los ignora a todos. SELinux y AppArmor son obligatorios (MAC): las reglas las impone el kernel según el contexto o el perfil del proceso, y ni el dueño ni root las relajan sobre la marcha. El valor real se ve cuando algo se compromete: aunque el atacante logre ejecutar código dentro de nginx, el perfil solo le permite tocar lo que nginx necesita, no /etc/shadow ni el directorio de tu base de datos.

¿Por qué el checklist dice usar sudo en lugar de su -?

Por tres razones. Trazabilidad: cada comando con sudo queda registrado junto al usuario que lo ejecutó en /var/log/auth.log o en el journal, mientras que con su - todo lo hizo "root" y en un incidente no sabés quién fue. Granularidad: en sudoers podés autorizar comandos puntuales a una persona en vez de entregarle el sistema entero. Y secretos: con sudo cada uno usa su propia contraseña, así que no hay una password de root compartida por el equipo que haya que rotar cada vez que alguien se va. Como bonus, el privilegio dura un comando y no toda la terminal.

🧠 Autoevaluación rápida

Respondé sin mirar arriba. Cada pregunta te explica el porqué.

1. ¿Con qué comando validás la sintaxis de sshd_config antes de recargar el servicio?

sshd -t prueba la config sin aplicarla. Y la regla de oro: nunca cierres tu sesión actual hasta confirmar, desde otra terminal, que todavía podés entrar.

2. sudo setenforce 0 en un sistema con SELinux…

Es temporal — al reiniciar vuelve a lo que diga la config, y lo verificás con getenforce o sestatus. Restaurar contextos es otra cosa: restorecon -Rv.

3. En jail.local de fail2ban tenés maxretry = 5 y findtime = 10m. ¿Qué significa?

findtime es la ventana donde se cuentan los fallos, maxretry cuántos se toleran y bantime (1h en el ejemplo) cuánto dura el ban. Se desbanea a mano con fail2ban-client unban IP.

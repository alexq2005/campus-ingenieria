Módulo 13 — Proyectos Integradores

Tres proyectos prácticos que combinan los módulos anteriores. Cada uno simula un escenario real de sysadmin/devops.

Proyecto 1 — Servidor Web seguro con Nginx

Objetivo: levantar un servidor Nginx en una VM Ubuntu, con HTTPS, firewall, fail2ban y backups automatizados.

Pasos

  1. Preparar el sistema 
    sudo apt update && sudo apt upgrade -y
sudo apt install -y nginx ufw fail2ban certbot python3-certbot-nginx
  2. Crear usuario de servicio sin shell 
    sudo useradd --system --no-create-home --shell /usr/sbin/nologin webadmin
  3. Configurar firewall 
    sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow ssh
sudo ufw allow 'Nginx Full'
sudo ufw enable
  4. Hardening de SSH (/etc/ssh/sshd_config): 
    PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
  5. Sitio web básico (/etc/nginx/sites-available/midominio): 
    server {
    listen 80;
    server_name midominio.com www.midominio.com;
    root /var/www/midominio;
    index index.html;
    location / { try_files $uri $uri/ =404; }
}
    sudo ln -s /etc/nginx/sites-available/midominio /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
  6. HTTPS con Let's Encrypt 
    sudo certbot --nginx -d midominio.com -d www.midominio.com
  7. fail2ban para SSH y Nginx 
    sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local
# Habilitar [sshd] y [nginx-http-auth]
sudo systemctl enable --now fail2ban
  8. Backups con timer systemd
    • /usr/local/bin/backup-www.sh (script de tar)
    • /etc/systemd/system/backup-www.service y .timer

Conceptos aplicados

  • Módulos 04 (permisos), 06 (usuarios), 08 (redes/SSH)
  • Módulo 10 (systemd timers)
  • Módulo 11 (seguridad, TLS, firewall, fail2ban)
  • Módulo 12 (backup, logrotate)

Proyecto 2 — Herramienta CLI de administración

Objetivo: script bash que reúne información del sistema en un reporte: usuarios, servicios, disco, red, top procesos.

Requisitos

  • Output legible (con headers de sección)
  • Opciones --all, --quick, --save FILE
  • Salida también disponible como JSON con --json
  • Códigos de exit correctos
  • Compatible con bash 4+ y set -euo pipefail

Esqueleto

Ver scripts/sys-report.sh por una implementación de referencia.

Conceptos aplicados

  • Módulo 05 (procesos: ps, top)
  • Módulo 09 (bash scripting completo)
  • Módulo 12 (df, dmesg, journalctl)

Proyecto 3 — Despliegue de una app Python

Objetivo: tomar una app Python (Flask/FastAPI) y desplegarla como un servicio systemd con reverse proxy Nginx, logs centralizados, y restart automático.

Pasos

  1. Crear usuario dedicado 
    sudo useradd --system --create-home --home-dir /opt/miapp --shell /usr/sbin/nologin miapp
  2. Estructura de la app 
    /opt/miapp/
├── .venv/
├── app.py
└── requirements.txt
  3. Instalar deps en venv 
    sudo -u miapp python3 -m venv /opt/miapp/.venv
sudo -u miapp /opt/miapp/.venv/bin/pip install fastapi uvicorn
  4. Service unit (/etc/systemd/system/miapp.service): 
    [Unit]
Description=Mi App FastAPI
After=network.target

[Service]
Type=simple
User=miapp
Group=miapp
WorkingDirectory=/opt/miapp
ExecStart=/opt/miapp/.venv/bin/uvicorn app:app --host 127.0.0.1 --port 8000
Restart=on-failure
RestartSec=5s
StandardOutput=journal
StandardError=journal
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
ReadWritePaths=/opt/miapp/data

[Install]
WantedBy=multi-user.target
  5. Habilitar y verificar 
    sudo systemctl daemon-reload
sudo systemctl enable --now miapp
sudo systemctl status miapp
journalctl -u miapp -f
  6. Reverse proxy con Nginx (/etc/nginx/sites-available/miapp): 
    server {
    listen 80;
    server_name miapp.example.com;
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
  7. HTTPS 
    sudo certbot --nginx -d miapp.example.com
  8. Verificación
    • Tirar el proceso a propósito (sudo systemctl kill miapp) y confirmar que Restart=on-failure lo levanta
    • Ver logs: journalctl -u miapp --since "5 min ago"
    • ss -tlnp | grep 8000 para verificar que escucha en localhost

Filosofía final

"Sé conservador en lo que hacés, liberal en lo que aceptás de los demás." — Postel's Law
"La administración de sistemas es 90% prevenir desastres y 10% recuperarse de los que ocurrieron igual."

Tres principios para llevarte:

  1. Backups: si no probaste restaurarlo, no tenés backup
  2. Reproducibilidad: si no podés re-armarlo en una hora desde cero, sos rehén de tu servidor
  3. Documentación: tu yo del futuro va a olvidar todo. Escribí runbooks para cada cosa rara

Errores típicos al desplegar

Correr certbot con el puerto 80 cerrado o el DNS sin propagar. El desafío HTTP-01 necesita que Let's Encrypt llegue desde internet a tu server por el puerto 80, con el dominio ya apuntando a esa IP. Si no, falla por timeout y encima gastás intentos del rate limit. 
sudo certbot --nginx -d midominio.com   # ❌ si ufw bloquea el 80 o el DNS no resuelve
# ✅ verificá primero:
dig +short midominio.com                # ¿apunta a la IP de esta VM?
sudo ufw allow 'Nginx Full'             # 80 y 443 abiertos
curl -I http://midominio.com            # ¿responde desde afuera?
sudo certbot --nginx -d midominio.com --dry-run   # ensayo sin consumir el límite
Symlink relativo en sites-enabled. ln -s guarda el destino tal cual se lo escribís: con una ruta relativa hecha desde otro directorio, el enlace queda roto, nginx ignora el sitio y el ls a secas no te lo muestra. 
sudo ln -s ../sites-available/midominio /etc/nginx/sites-enabled/          # ❌ frágil
sudo ln -s /etc/nginx/sites-available/midominio /etc/nginx/sites-enabled/ # ✅ ruta absoluta
ls -l /etc/nginx/sites-enabled/         # 🔎 un enlace roto apunta a la nada
sudo nginx -t
ExecStart con activate o rutas relativas. systemd no ejecuta un shell: no hay source, ni ~, ni el PATH de tu usuario, ni encadenado con &&. Si el arranque depende de activar el venv, el servicio ni levanta. 
ExecStart=source .venv/bin/activate && uvicorn app:app    # ❌ no existe para systemd
# ✅ binario absoluto del venv:
ExecStart=/opt/miapp/.venv/bin/uvicorn app:app --host 127.0.0.1 --port 8000
WorkingDirectory=/opt/miapp
Secretos legibles por todo el sistema. Un .env con la contraseña de la base creado con los permisos por defecto queda en 644: lo lee cualquier usuario de la máquina, incluido el proceso comprometido de al lado. 
echo "DB_PASSWORD=..." > /opt/miapp/.env   # ❌ queda 644: lo lee todo el mundo
# ✅ dueño root, grupo del servicio, 640:
sudo install -o root -g miapp -m 640 /dev/null /etc/miapp/env
sudo nano /etc/miapp/env
# y en la unit: EnvironmentFile=/etc/miapp/env
# nunca la clave en ExecStart: los argumentos se ven en ps y en systemctl show

Checkpoint — ¿lo tenés claro?

¿Por qué el reverse proxy y la app son dos procesos separados y no uno solo?

Porque hacen cosas distintas y conviene poder cambiar una sin tocar la otra. Nginx se ocupa de lo caro y delicado de hacer bien: terminar TLS, servir estáticos, timeouts, límites de tamaño, buffering de clientes lentos, rate limiting y repartir tráfico. La app se ocupa solo de la lógica y escucha en el loopback. La ganancia práctica: renovás el certificado o cambiás la config del proxy sin tocar la app, reiniciás la app sin que quede expuesta a internet mientras arranca, y el día que necesites escalar levantás tres instancias detrás del mismo server block.

El server se reinicia solo a las 3 AM. ¿Qué tiene que estar configurado para que a las 3:01 esté todo funcionando?

Todo lo que hiciste "a mano" tiene que estar declarado en algún lado persistente: los servicios con systemctl enable y no solo start (nginx, miapp, fail2ban); los timers de backup y de renovación del certificado, también con enable; los discos de datos en /etc/fstab con nofail y no montados a mano; las reglas de firewall persistidas (ufw enable las guarda, iptables a secas no); y el orden de arranque resuelto con After= o Requires= si la app necesita la red o la base listas. La única prueba que vale es hacerlo: reiniciá vos a propósito y verificá con systemctl --failed y un curl al sitio.

¿Qué te dice ss -tlnp que systemctl status no puede decirte?

systemctl status te dice qué opina systemd del proceso: que lo lanzó y que sigue vivo. Eso no prueba que el servicio esté escuchando: un proceso puede quedar active (running) sin haber bindeado ningún socket (se colgó antes de llegar ahí), o haberlo bindeado en el puerto o la interfaz equivocados — que es justo el bug que te deja la app expuesta en 0.0.0.0 o inalcanzable para el proxy. ss -tlnp te muestra el estado real del kernel: qué puerto, en qué dirección y de qué PID. Es la diferencia entre "quedó configurado así" y "está haciendo eso".

🧠 Autoevaluación rápida

Respondé sin mirar arriba. Cada pregunta te explica el porqué.

1. En el proyecto 1, ¿qué corrés siempre antes de systemctl reload nginx?

nginx -t valida la config: con un typo en el server block, el reload te deja el sitio caído. Mismo espíritu que sshd -t del módulo 11.

2. El usuario de servicio se crea con useradd --system --shell /usr/sbin/nologin webadmin. ¿Por qué ese shell?

Mínimo privilegio: la cuenta existe para correr el servicio, no para loguearse. Es uno de los ítems del checklist de seguridad del módulo 11.

3. En el proyecto 3, uvicorn escucha en --host 127.0.0.1 --port 8000. ¿Por qué no en 0.0.0.0?

El proxy_pass de Nginx la alcanza por localhost; el firewall, el TLS y el mundo exterior los maneja el reverse proxy. Lo verificás con ss -tlnp | grep 8000.

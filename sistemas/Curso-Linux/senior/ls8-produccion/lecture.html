LS8 — Producción: automatización, HA y runbooks

LS8.0 Por qué este módulo

Los siete módulos anteriores te dieron el mapa interno de Linux: procesos y scheduler (LS1), memoria y presión (LS2), namespaces y cgroups (LS3), almacenamiento (LS4), red (LS5), eBPF (LS6) y systemd (LS7). Sabés diagnosticar. Este módulo es sobre lo otro: operar. Y operar bien tiene una definición incómodamente simple.

💡 La tesis del módulo. La diferencia entre un sysadmin y un SRE no es cuánto sabe de Linux: es que el segundo no toca servidores a mano. Cada cambio manual es un dato que existe en un solo lugar —la memoria de quien lo hizo— y que nadie puede revisar, revertir ni reproducir. La automatización no es comodidad: es la única forma conocida de que un sistema sea auditable y recreable.

Esto no es ideología. Es una consecuencia aritmética: administrar 3 servidores a mano es viable, 30 es doloroso y 300 es imposible. Pero el punto importante es que el umbral real es 1, porque el problema no aparece cuando tenés muchos servidores: aparece el día que tenés que volver a construir uno y nadie se acuerda de qué le hicieron durante tres años.

LS8.1 Mascotas y ganado: el servidor que nadie se anima a tocar

La metáfora es vieja y sigue siendo la mejor que hay:

🐕 Una mascota tiene nombre propio (zeus, atenea), es única, la cuidás cuando se enferma y si se muere es un drama. 🐄 El ganado tiene número (web-07), es intercambiable, y si uno falla lo reemplazás sin ceremonia. La pregunta de diagnóstico es: si este servidor se prende fuego ahora, ¿cuánto tardás en tener otro idéntico? Si la respuesta es "no sé" o "días", tenés una mascota.

El servidor mascota se construye solo, sin que nadie lo decida. Alguien instala un paquete "para probar" y queda. Alguien edita un /etc/ a las tres de la mañana durante un incidente y no lo documenta. Alguien agrega una entrada al cron. Tres años después el servidor funciona por razones que nadie puede enumerar completas, y eso convierte cualquier cambio en un acto de fe.

⚠️ El costo real no es el desorden: es la parálisis. Un servidor cuyo estado nadie puede reproducir se vuelve intocable. No se actualiza (¿y si se rompe?), no se migra, no se clona para hacer staging. Y como no se actualiza, acumula CVEs. La deuda técnica de infraestructura se paga siempre, y casi siempre se paga en el peor momento: durante una caída, o durante una auditoría de seguridad.

Infraestructura inmutable

La respuesta moderna es dejar de modificar servidores y pasar a reemplazarlos. En un esquema inmutable, un servidor se construye una vez desde una definición versionada y después nadie le hace SSH para cambiarle nada: si hay que cambiar algo, se cambia la definición, se construye una máquina nueva y se descarta la vieja.

ModeloCómo se cambia algoQué garantiza
Mutable manualSSH + editarNada. El estado real es desconocido
Mutable declarativo (Ansible, Puppet)Cambiar el código, re-aplicarConvergencia: el servidor tiende al estado declarado
Inmutable (imagen, contenedor)Construir imagen nueva, reemplazarIdentidad: dos servidores de la misma imagen son iguales
Inmutable no significa "sin estado". Los datos siguen viviendo en algún lado —una base, un volumen, un bucket— y ese lado sí es mutable y sí necesita backups. Lo que se vuelve inmutable es el sistema operativo y la aplicación: la parte que se puede reconstruir desde código.

LS8.2 Infraestructura como código: Ansible y la idempotencia

Ansible corre por SSH, no necesita agente en el destino y se escribe en YAML. Esa combinación explica su adopción: el primer playbook útil sale en una tarde. Pero lo que hay que entender no es la sintaxis, es el cambio de mentalidad de imperativo a declarativo.

El playbook: qué es cada grupo

    app_user: appsvc

- name: Base de datos
  hosts: db

    - base

El rol: la unidad reutilizable

Un rol es un directorio con una estructura fija. Ansible sabe dónde buscar cada cosa, así que no hay que configurar nada:

roles/nginx/
├── tasks/main.yml        # qué hacer
├── handlers/main.yml     # qué correr SOLO si algo cambió
├── templates/            # archivos Jinja2 (.j2)
├── files/                # archivos que se copian tal cual
├── defaults/main.yml     # variables con la prioridad más BAJA (las sobreescribís fácil)
├── vars/main.yml         # variables con prioridad ALTA (constantes del rol)
└── meta/main.yml         # dependencias con otros roles
# roles/nginx/tasks/main.yml
- name: Paquete nginx instalado
  ansible.builtin.apt:
    name: nginx
    state: present            # ESTADO deseado, no acción: "que esté", no "instalalo"
    update_cache: true
    cache_valid_time: 3600

- name: Usuario de servicio existe
  ansible.builtin.user:
    name: "{{ app_user }}"
    system: true
    shell: /usr/sbin/nologin
    create_home: false

- name: Configuración de nginx desplegada
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
    owner: root
    group: root
    mode: "0644"
    validate: "nginx -t -c %s"   # si el template genera basura, NO se escribe el archivo
  notify: recargar nginx         # dispara el handler SOLO si este task cambió algo

- name: Sitio por defecto ausente
  ansible.builtin.file:
    path: /etc/nginx/sites-enabled/default
    state: absent
  notify: recargar nginx

- name: Servicio nginx activo y habilitado al boot
  ansible.builtin.systemd:
    name: nginx
    state: started
    enabled: true
# roles/nginx/handlers/main.yml
- name: recargar nginx
  ansible.builtin.systemd:
    name: nginx
    state: reloaded      # reload, NO restart: no corta las conexiones vivas

Idempotencia: el concepto que separa todo lo demás

📌 Una operación es idempotente si aplicarla N veces deja el sistema igual que aplicarla una vez. No significa "no hace nada la segunda vez": significa que el resultado es el mismo. Es la propiedad que te permite correr el playbook completo un martes cualquiera, sin miedo, y usarlo como verificación además de como despliegue.

Un script bash no la tiene, y el ejemplo es brutalmente concreto:

#!/usr/bin/env bash
# setup.sh — NO es idempotente. Corré esto dos veces y mirá qué pasa.
apt-get install -y nginx
echo "worker_processes 4;" >> /etc/nginx/nginx.conf   # se AGREGA otra vez en cada corrida
useradd appsvc                                          # falla la 2da vez: "user already exists"
sed -i 's/80/8080/' /etc/nginx/nginx.conf               # ya no hay 80 que cambiar... ¿o cambió otro 80?
systemctl restart nginx                                 # corta conexiones aunque NADA haya cambiado

Se puede escribir bash idempotente. El punto es cuánto cuesta, y que ese costo se paga en cada línea:

# La versión idempotente del mismo script: el triple de código y todavía frágil
dpkg -s nginx >/dev/null 2>&1 || apt-get install -y nginx

grep -q '^worker_processes' /etc/nginx/nginx.conf \
  || echo "worker_processes 4;" >> /etc/nginx/nginx.conf

id -u appsvc >/dev/null 2>&1 || useradd -r -s /usr/sbin/nologin appsvc

# ¿Y el restart? Habría que detectar si el archivo cambió realmente:
cksum_antes=$(cksum /etc/nginx/nginx.conf)
# ... escribir config ...
[ "$cksum_antes" != "$(cksum /etc/nginx/nginx.conf)" ] && systemctl reload nginx
El error conceptual más común: pensar que Ansible es "bash con YAML". Los módulos de Ansible ya vienen escritos con toda esa lógica adentro: el módulo apt chequea si el paquete está, el módulo template compara el contenido antes de escribir, el módulo user compara UID, shell y grupos. Por eso cada task reporta ok (ya estaba) o changed (lo modifiqué). Si usás el módulo command o shell para todo, perdiste la idempotencia y estás escribiendo bash con más pasos. 
# Cuando NO queda otra que usar command, se le agrega la condición a mano:
- name: Inicializar el cluster de la base
  ansible.builtin.command: /usr/lib/postgresql/16/bin/initdb -D /var/lib/postgresql/16/main
  args:
    creates: /var/lib/postgresql/16/main/PG_VERSION   # si ese archivo existe, no corre

- name: Regenerar el índice solo si el catálogo cambió
  ansible.builtin.command: /opt/app/bin/reindex
  register: reindex
  changed_when: "'reindexed' in reindex.stdout"       # vos definís qué significa "cambió"
  failed_when: reindex.rc not in [0, 2]               # y qué significa "falló"

Ansible no compite con los contenedores — sigue siendo lo que configura el host que los aloja, el bastión, el servidor de base de datos y todo lo que no se puede tirar y rehacer cada quince minutos.

LS8.4 La infraestructura también se testea

Escribir el playbook no es la parte difícil. La difícil es tener confianza para aplicarlo en producción un viernes. Esa confianza se construye con tres niveles de prueba, exactamente como con el código.

Nivel 1 — Dry run: --check --diff

# --check: no cambia nada, reporta qué HARÍA. --diff: muestra el diff de cada archivo.
ansible-playbook -i inventory/prod.ini site.yml --check --diff --limit web-01.prod.internal

# Salida esperada en un servidor ya convergido:
# web-01.prod.internal : ok=24  changed=0  unreachable=0  failed=0  skipped=3
--check no es infalible y hay que saber por qué. Los tasks que usan command/shell se saltean (Ansible no puede saber qué harían), y cualquier task que dependa del resultado de otro que no corrió va a reportar mal. Un --check limpio es evidencia fuerte, no una demostración. Para eso está el nivel 2.

Nivel 2 — Molecule: probar el rol en un entorno descartable

pip install "molecule[docker]" molecule-plugins ansible-lint
cd roles/nginx
molecule init scenario -d docker

# El ciclo completo, en una VM/contenedor limpio:
molecule test
#  1. create      -> levanta el contenedor/VM
#  2. converge    -> aplica el rol
#  3. idempotence -> lo aplica OTRA VEZ y FALLA si algún task reporta "changed"
#  4. verify      -> corre los tests de estado
#  5. destroy     -> limpia todo

molecule converge   # aplicar sin destruir, para iterar rápido
molecule login      # entrar al contenedor a mirar qué quedó mal
📌 El paso idempotence es el que vale oro. Corre el rol dos veces y falla si la segunda corrida reporta cualquier changed. Es una prueba automática de la propiedad de LS8.2, y detecta al instante los shell: sin creates:, los lineinfile mal anclados y los templates con timestamps adentro.

Nivel 3 — testinfra: aserciones sobre el estado final

# molecule/default/tests/test_nginx.py — se ejecuta DENTRO del host de prueba
def test_paquete_instalado(host):
    assert host.package("nginx").is_installed

def test_servicio_corriendo_y_habilitado(host):
    svc = host.service("nginx")
    assert svc.is_running
    assert svc.is_enabled

def test_escucha_en_el_puerto(host):
    assert host.socket("tcp://0.0.0.0:8080").is_listening

def test_config_es_valida(host):
    assert host.run("nginx -t").rc == 0

def test_permisos_de_la_config(host):
    f = host.file("/etc/nginx/nginx.conf")
    assert f.user == "root" and f.mode == 0o644

def test_no_corre_como_root(host):
    # regresión: en 2024 un cambio de template hizo que el worker corriera como root
    assert "appsvc" in host.check_output("ps -o user= -C nginx | sort -u")
Fijate en el último test: es un test de regresión de infraestructura. Cada incidente que resolvés debería dejar uno igual. Es la misma disciplina que en software — el bug que ya pasó una vez es exactamente el que más barato sale prevenir.

LS8.5 Drift: cuando el servidor deja de parecerse al código

El drift de configuración es la divergencia entre lo que el código declara y lo que el servidor realmente tiene. Aparece siempre, porque siempre hay una madrugada en la que alguien arregla algo a mano y se olvida de subirlo al repo.

La buena noticia: si tus playbooks son idempotentes, ya tenés el detector de drift escrito. Es --check --diff corriendo solo, todos los días:

#!/usr/bin/env bash
# /usr/local/bin/drift-check.sh — lo dispara un systemd timer (ver LS7)
set -euo pipefail
SALIDA=$(mktemp)

ansible-playbook -i /opt/iac/inventory/prod.ini /opt/iac/site.yml \
  --check --diff > "$SALIDA" 2>&1 || true

# Cualquier "changed=" distinto de 0 es un servidor que se desvió
if grep -qE 'changed=[1-9]' "$SALIDA"; then
    grep -E 'changed=[1-9]' "$SALIDA" | logger -t drift -p daemon.warning
    /usr/local/bin/notificar-sre "DRIFT detectado" < "$SALIDA"
    exit 1
fi
logger -t drift -p daemon.info "flota convergida: 0 desvíos"

Complementalo con las herramientas del propio gestor de paquetes, que te dicen qué archivos del sistema fueron modificados respecto de lo que instaló el paquete:

# Debian/Ubuntu: qué archivos NO coinciden con el checksum del paquete
apt-get install -y debsums
debsums -ac          # -a incluye configs, -c solo lista los que cambiaron

# RHEL/Rocky/Fedora: lo mismo, nativo
rpm -Va --nomtime | grep '^..5'     # la columna 5 es "checksum distinto"

# Qué unidades habilitó alguien fuera del playbook (ver LS7)
systemctl list-unit-files --state=enabled --no-pager

# Qué se agregó al cron o a los timers
ls -la /etc/cron.d/ /etc/systemd/system/*.timer 2>/dev/null
El anti-patrón: detectar drift y corregirlo automáticamente pisando el servidor sin mirar. Ese cambio manual puede ser el fix de un incidente en curso, y revertirlo a ciegas a las 4 AM convierte un problema en dos. Lo correcto es alertar, mirar el diff y decidir: o el cambio sube al código (era legítimo), o se revierte (era un descuido). El drift es información, no un enemigo.

LS8.6 Alta disponibilidad de verdad

"Alta disponibilidad" se usa como sinónimo de "tenemos dos servidores". No es eso. HA es la propiedad de seguir dando servicio cuando un componente falla, y se diseña componente por componente preguntando lo mismo: si esto muere ahora, ¿qué pasa?

El mito de los nueves

DisponibilidadDowntime al añoDowntime al mesQué implica de verdad
99%3 d 15 h7 h 18 mUn servidor bien cuidado
99,9% ("tres nueves")8 h 45 m43 mRedundancia + guardias
99,95%4 h 22 m21 mFailover automático probado
99,99% ("cuatro nueves")52 m 35 s4 m 23 sMulti-zona, despliegues sin downtime, on-call 24/7
99,999%5 m 15 s26 sMuy poca gente lo necesita y menos gente lo logra
⚠️ Leé la fila de 99,99% otra vez: 52 minutos al año, para TODO. Ahí adentro entran los reinicios por kernel, los despliegues fallidos, los errores de configuración y la caída del proveedor de nube. Un solo incidente mal manejado te consume el presupuesto anual entero. Por eso prometer cuatro nueves sin haber medido nunca los tres es la forma más rápida de firmar un SLA que no vas a cumplir. Primero medí lo que tenés, después prometé.

Puntos únicos de falla (SPOF)

El ejercicio es aburrido y por eso casi nadie lo hace: listar cada componente y tacharlo mentalmente. La lista típica de SPOFs que sobreviven en sistemas "redundantes":

El balanceador. Dos servidores web detrás de un solo nginx. Si cae el nginx, cayó todo. Se resuelve con VRRP (keepalived) o un balanceador gestionado.
La base de datos. Casi siempre. Una réplica que nunca se promovió no es HA: es un backup caliente. HA de verdad exige failover probado.
El DNS y los certificados. Un certificado vencido tira abajo un sistema perfectamente redundante. Es la causa de caída más ridícula y una de las más frecuentes.
La zona de disponibilidad. Tres servidores en el mismo rack, el mismo switch o el mismo datacenter comparten destino.
La persona. Si una sola persona sabe cómo hacer el failover, esa persona es el SPOF. Por eso existen los runbooks (LS8.10).

Health checks: el detalle que decide si el failover funciona

# /etc/nginx/conf.d/upstream.conf
upstream app {
    least_conn;                       # al menos-conexiones, mejor que round-robin si las requests duran distinto
    server web-01:8080 max_fails=3 fail_timeout=10s;
    server web-02:8080 max_fails=3 fail_timeout=10s;
    server web-03:8080 max_fails=3 fail_timeout=10s backup;   # solo entra si los otros caen
    keepalive 32;
}

server {
    location /healthz { proxy_pass http://app; proxy_next_upstream error timeout http_502 http_503; }
}
📌 Un health check que solo devuelve 200 OK desde el proceso web no sirve. El proceso puede estar vivo y la app completamente rota porque perdió la conexión a la base. Distinguí dos endpoints: liveness ("el proceso responde, no lo mates") y readiness ("puedo atender tráfico: la base contesta, la cola contesta, la caché contesta"). El balanceador consulta readiness; el supervisor consulta liveness. Confundirlos produce el peor de los mundos: un nodo roto que sigue recibiendo tráfico, o un nodo sano que se reinicia en loop porque la base tardó dos segundos de más.
Split brain. Si dos nodos pierden contacto entre sí pero ambos siguen vivos, los dos pueden creerse el primario y aceptar escrituras. El resultado son dos bases divergentes, y reconciliarlas a mano es una de las peores tardes que existen. La defensa es el quórum: se necesita mayoría estricta para actuar, por eso los clusters se arman con número impar de nodos (3, 5), y por eso un cluster de 2 nodos no puede tener quórum sin un tercer testigo.
HA sin backups probados es una ilusión. La replicación copia todo, incluido el DROP TABLE y el ransomware — en milisegundos, a todos los nodos. La redundancia te protege de fallas de hardware; los backups te protegen de fallas de software y de personas, que son la mayoría. Son defensas contra amenazas distintas y una nunca reemplaza a la otra.

LS8.7 Backups: la única métrica que importa es el tiempo de restauración

💡 La regla 3-2-1. 3 copias de los datos, en 2 medios o tecnologías distintas, con 1 fuera del sitio. La variante moderna es 3-2-1-1-0: una copia inmutable o air-gapped (contra ransomware, que ahora borra los backups primero) y 0 errores en la última verificación de restauración.

Los dos números que definen tu política

MétricaQué mideLa determina
RPO (Recovery Point Objective)Cuántos datos podés perderLa frecuencia del backup. Backup diario ⇒ RPO de 24 h
RTO (Recovery Time Objective)Cuánto podés estar caídoLa velocidad de restauración, medida — no estimada
 
# restic: deduplicado, cifrado y con snapshots. borg es el equivalente clásico.
export RESTIC_REPOSITORY="s3:https://s3.amazonaws.com/backups-prod"
export RESTIC_PASSWORD_FILE=/etc/restic/pass

# Backup incremental: solo sube los bloques nuevos, pero cada snapshot es COMPLETO al restaurar
restic backup /srv/data /etc --tag nightly --exclude-file=/etc/restic/excludes

# Retención: sin esto el repo crece para siempre
restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 12 --keep-yearly 3 --prune

# Verificar la INTEGRIDAD del repo (metadatos + una muestra de datos reales)
restic check --read-data-subset=5%
📌 Un backup que nunca se restauró no es un backup: es una carpeta grande con esperanza adentro. El número que hay que publicar en el dashboard no es "último backup: hace 2 h" — eso solo prueba que el script corrió. Es "última restauración exitosa: hace 6 días, tardó 41 minutos, checksum OK". Ese sí es un dato sobre tu capacidad de recuperarte. 
#!/usr/bin/env bash
# restore-drill.sh — simulacro automático de restauración. Semanal, en hardware de prueba.
set -euo pipefail
INICIO=$(date +%s)
DESTINO=/restore-test/$(date +%F)

restic restore latest --target "$DESTINO" --path /srv/data

# Verificación funcional: que los bytes estén NO alcanza, la app tiene que arrancar
sudo -u postgres pg_restore -d verificacion "$DESTINO/srv/data/dump.pgc"
psql -d verificacion -c 'SELECT count(*) FROM pedidos;' | tee /tmp/filas.txt

RTO=$(( $(date +%s) - INICIO ))
echo "restore_test_duration_seconds $RTO" > /var/lib/node_exporter/textfile/restore.prom
echo "restore_test_success 1"           >> /var/lib/node_exporter/textfile/restore.prom
echo "✅ RTO medido: ${RTO}s"
Ese textfile del final es el truco: el resultado del simulacro entra como métrica de Prometheus vía el textfile collector del node_exporter (LS8.9). Así podés alertar por "hace más de 10 días que no se prueba una restauración" — que es el único tipo de alerta de backup que previene desastres reales.
La detección y respuesta ante el incidente que te obliga a restaurar —incluido el caso de ransomware, donde el orden de las operaciones es crítico— está desarrollada en M10 del curso de Ciberseguridad: detección y respuesta. Los backups son la última línea de esa cadena, y el M10 explica qué hacer antes de tocarlos: preservar evidencia, identificar el punto de compromiso y no restaurar sobre un sistema todavía comprometido.

LS8.8 Actualizar sin cortar el servicio

Rolling update: de a uno, con verificación

# rolling.yml — actualiza la flota sin ventana de mantenimiento
- name: Rolling update de los web
  hosts: web
  become: true
  serial: 1                    # de a un host; "25%" o [1, 2, 4] para tandas crecientes
  max_fail_percentage: 0       # si UNO falla, se frena todo el rollout

  pre_tasks:
    - name: Sacar el nodo del balanceador (drenar)
      ansible.builtin.uri:
        url: "http://lb-01.prod.internal/api/drain/{{ inventory_hostname }}"
        method: POST
      delegate_to: localhost

    - name: Esperar a que terminen las requests en vuelo
      ansible.builtin.wait_for:
        timeout: 30            # más que el timeout más largo de la app

  roles:
    - app

  post_tasks:
    - name: Health check propio ANTES de reponerlo
      ansible.builtin.uri:
        url: "http://{{ inventory_hostname }}:8080/readyz"
        status_code: 200
      retries: 10
      delay: 3
      register: salud
      until: salud.status == 200

    - name: Devolver el nodo al balanceador
      ansible.builtin.uri:
        url: "http://lb-01.prod.internal/api/enable/{{ inventory_hostname }}"
        method: POST
      delegate_to: localhost
📌 Drenar no es apagar. Sacar el nodo del balanceador y matar el proceso en el mismo segundo corta las requests que estaban a mitad de camino. El orden correcto es: (1) dejar de recibir tráfico nuevo, (2) esperar a que terminen las que están en vuelo, (3) recién ahí systemctl stop. En systemd eso se configura con KillSignal=SIGTERM y un TimeoutStopSec mayor a la request más lenta (LS7), y en la app con un handler de SIGTERM que cierre el listener y espere.

Actualizar la librería no reinicia lo que la usaba. 💡 PSI es la señal temprana. Las métricas de utilización mienten: una CPU al 100% puede estar perfecta (batch) y una al 60% puede estar ahogando a todos (contención). Pressure Stall Information (LS2) mide otra cosa: cuánto tiempo hubo tareas totalmente frenadas esperando un recurso. Eso correlaciona con la latencia que sufre el usuario mucho mejor que cualquier porcentaje de uso, y sube antes de que el sistema colapse. 
# PSI crudo en el host (LS2), y expuesto por node_exporter
cat /proc/pressure/io

# full avg10=9.11  avg60=5.44  avg300=2.10 total=41230011
#  some = al menos una tarea frenada · full = TODAS frenadas (el sistema no avanza)

curl -s localhost:9100/metrics | grep '^node_pressure'
# alerts.yml — alertas basadas en saturación, no en porcentajes de uso
groups:
  - name: host
    rules:
      - alert: SaturacionIO
        expr: rate(node_pressure_io_stalled_seconds_total[5m]) > 0.20
        for: 10m
        labels: {severity: warning}
        annotations:
          summary: "20% del tiempo hay tareas frenadas por I/O en {{ $labels.instance }}"
          runbook_url: "https://runbooks.internal/saturacion-io"

      - alert: DiscoSeLlenaEn4Dias
        expr: predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 4*24*3600) < 0
        for: 1h
        labels: {severity: warning}
        annotations:
          summary: "A este ritmo, / se llena en menos de 4 días en {{ $labels.instance }}"
          runbook_url: "https://runbooks.internal/disco-lleno"

      - alert: RestauracionNoProbada
        expr: time() - restore_test_last_success_timestamp_seconds > 10 * 86400
        labels: {severity: critical}
        annotations:
          summary: "Hace más de 10 días que no se verifica una restauración"
Alertar sobre causas en vez de síntomas. "CPU al 90%" despierta gente a las 3 AM por un batch nocturno perfectamente sano. "La latencia p99 del checkout superó 2 s durante 5 minutos" describe algo que le está pasando a un usuario real. Regla práctica: si una alerta no requiere que un humano actúe ahora, no es una alerta — es un gráfico. Cada alerta ruidosa que dejás viva entrena al equipo a ignorar las alertas.

LS8.10 Runbooks y post-mortems sin culpa

Un runbook es el procedimiento escrito para una situación específica. Su público objetivo no sos vos hoy: es la persona con menos contexto del equipo, a las tres de la mañana, con adrenalina y medio dormida. Todo lo que un runbook debe optimizar sale de ahí.

Un runbook maloUn runbook bueno
"Reiniciar el servicio si hace falta"El comando exacto, copiable, con el host y las flags
Explica la arquitectura completaUn párrafo de contexto y va directo a los pasos
Asume que sabés dónde están los logsDa la ruta y el comando de consulta ya armado
No dice cómo verificarCada paso dice qué salida esperar y qué hacer si no aparece
No tiene salida de emergenciaDice cuándo abandonar y a quién escalar, con el criterio explícito
Se escribió una vezSe actualiza en cada uso; el link está en la alerta (runbook_url)
📌 El test del runbook: dáselo a alguien que no construyó el sistema y pedile que lo ejecute en staging sin preguntar nada. Cada vez que tenga que preguntar algo, ahí hay un agujero. Si nadie puede seguirlo sin vos, el runbook no existe: vos sos el runbook, y sos un SPOF (LS8.6).

Post-mortem sin culpa

Después de cada incidente serio se escribe un post-mortem. Sin culpa (blameless) no significa que no se analicen los errores humanos: significa que se parte de la premisa de que toda persona actuó razonablemente con la información que tenía en ese momento, y que si una acción individual pudo tirar abajo el sistema, el problema es del sistema.

Línea de tiempo con horarios y evidencia. Qué pasó, cuándo se detectó, cuándo se mitigó, cuándo se resolvió. Con links a los gráficos y los logs, no de memoria.
Impacto medido. Cuántos usuarios, cuánto tiempo, qué operaciones fallaron, cuánto presupuesto de error consumió. Números, no adjetivos.
Causa raíz, en plural. Casi nunca hay una sola. Preguntá "¿por qué?" hasta llegar a algo estructural, y frená antes de llegar a "porque Juan se equivocó" — eso no es una causa raíz, es dónde se detuvo el análisis.
Qué funcionó. No solo lo que falló: la alerta que sí disparó, el runbook que sí sirvió. Eso es lo que hay que replicar.
Acciones con dueño y fecha. Cada una en el backlog, priorizada. Un post-mortem sin acciones cerradas es un documento de terapia, no de ingeniería.
⚠️ Por qué "sin culpa" no es amabilidad, es estrategia. Si señalás a la persona, la próxima vez la gente esconde los errores, tarda en avisar y no cuenta lo que hizo. Perdés exactamente la información que necesitás para arreglar el sistema. El equipo que puede decir "borré la tabla equivocada" sin miedo se recupera en minutos; el que no puede decirlo se recupera en horas y vuelve a fallar igual.

LS8.11 Capacity planning: saber antes de quedarte corto

Capacity planning es responder "¿cuándo me quedo sin recurso?" con una fecha, no con una sensación. Con métricas históricas la versión básica alcanza para el 90% de los casos:

# Extrapolación lineal directa en PromQL
predict_linear(node_filesystem_avail_bytes{mountpoint="/var"}[7d], 30*86400)
#  -> bytes libres previstos en 30 días. Si da negativo, ya tenés la fecha.

# Cuánto creció el uso de disco en el último mes, en %
100 * (1 - node_filesystem_avail_bytes offset 30d / node_filesystem_avail_bytes)

# Headroom real: qué margen te queda si perdés un nodo de N
(sum(node_memory_MemTotal_bytes) - max(node_memory_MemTotal_bytes))
  > sum(container_memory_working_set_bytes)
📌 Planificá para N+1, no para N. Si tres nodos aguantan el pico justo, dos no aguantan nada — y algún día vas a tener dos, porque uno se va a caer o vas a tener que actualizarlo (LS8.8). La capacidad se dimensiona con un nodo menos que los que tenés, en el pico, no en el promedio. El promedio no te tira el sistema abajo; el pico sí.
El crecimiento rara vez es lineal, y los saltos no se ven venir. Una campaña de marketing, un cliente grande que entra, un feature viral. La extrapolación lineal sirve para lo previsible (logs, base de datos, archivos); para lo demás la defensa no es predecir mejor, es poder escalar rápido — que es, otra vez, el mismo argumento de LS8.1: si construir un servidor nuevo lleva 20 minutos y no dos días, la predicción importa mucho menos.

🧑‍🎓 Worked Example — de servidor mascota a playbook reproducible

web-07 lleva cuatro años en producción. Lo instaló alguien que ya no está en la empresa. Funciona. Nadie sabe exactamente qué tiene adentro, nadie lo reinició desde 2023 y ya hay dos CVEs de kernel sin parchear. Hay que convertirlo en algo reproducible sin cortar el servicio.

Paso 1 — Inventario forense: qué tiene este servidor que no tiene una instalación limpia. No se trata de leer todo /etc: se trata de encontrar el delta contra la imagen base.

# En una VM LIMPIA de la misma versión, sacar la línea de base:
dpkg-query -W -f='${Package}\n' | sort > /tmp/base-packages.txt

# En web-07, el delta de paquetes: lo que alguien instaló a mano
dpkg-query -W -f='${Package}\n' | sort > /tmp/web07-packages.txt
comm -13 /tmp/base-packages.txt /tmp/web07-packages.txt

# Qué archivos de configuración fueron modificados respecto del paquete original
debsums -ac 2>/dev/null        # cada línea es una decisión que hay que declarar

# Qué unidades habilitó alguien (LS7)
systemctl list-unit-files --state=enabled --no-pager | sort

# Qué escucha, con qué proceso y qué usuario (LS5)
ss -lntup

# Qué corre por cron o timer
ls -la /etc/cron.d/ /etc/cron.daily/ /etc/systemd/system/*.timer 2>/dev/null
crontab -l -u root; crontab -l -u appsvc

# Qué se tocó a mano recientemente en /etc (pista, no prueba)
find /etc -type f -newer /etc/hostname -printf '%T+ %p\n' 2>/dev/null | sort -r | head -40

# Usuarios y claves SSH que no deberían estar
awk -F: '$3 >= 1000 {print $1, $6, $7}' /etc/passwd
find /home /root -name authorized_keys -exec ls -la {} +
Guardá toda esa salida en un archivo del repo, con fecha. Es la evidencia de que el playbook cubre lo que había, y en seis meses va a ser la única forma de responder "¿esto lo declaramos porque hacía falta o porque estaba?".

Paso 2 — Escribir el playbook a partir del delta, no a partir de la imaginación. Cada línea del inventario forense se convierte en un task declarativo. Nada más: si no apareció en el delta, no va.

Paso 3 — Usar --check --diff contra el servidor real como oráculo. Este es el paso que hace que todo el ejercicio sea seguro: el diff te dice exactamente qué te falta declarar, sin tocar nada.

ansible-playbook -i inventory/prod.ini site.yml --limit web-07 --check --diff

# Primera corrida: changed=31  -> 31 diferencias entre tu código y la realidad.
# Por cada una hay que decidir:
#   (a) el servidor tiene algo legítimo que el playbook no declara -> agregarlo al playbook
#   (b) el playbook declara algo que el servidor no tiene          -> ¿es una mejora o un error tuyo?
# Iterar hasta:
# web-07 : ok=58  changed=0  unreachable=0  failed=0
📌 Llegar a changed=0 en --check es el momento en que el servidor deja de ser una mascota. A partir de ahí, el código y la máquina dicen lo mismo, y ese código es la respuesta a "¿qué tiene este servidor?". Todavía no probaste que podés recrearlo — eso es el paso 4 — pero ya podés auditarlo y revisarlo en un pull request.

Paso 4 — Probarlo sin arriesgar producción: construir el gemelo. El --check prueba convergencia sobre lo que ya existe. La prueba de verdad es construir web-08 desde cero con el mismo playbook y comparar el estado observable de los dos:

# 1) Rol probado aisladamente antes de tocar nada
cd roles/app && molecule test        # incluye el paso de idempotencia (LS8.4)

# 2) Construir el gemelo desde cero
ansible-playbook -i inventory/prod.ini site.yml --limit web-08

# 3) Comparar el estado OBSERVABLE de los dos servidores
for h in web-07 web-08; do
  ssh "$h" 'dpkg-query -W -f="${Package} ${Version}\n" | sort'          > "/tmp/pkgs.$h"
  ssh "$h" 'systemctl list-unit-files --state=enabled --no-pager|sort'  > "/tmp/units.$h"
  ssh "$h" 'ss -lntup | sort'                                          > "/tmp/ports.$h"
  ssh "$h" 'sysctl -a 2>/dev/null | sort'                              > "/tmp/sysctl.$h"
done
diff -u /tmp/pkgs.web-07  /tmp/pkgs.web-08
diff -u /tmp/units.web-07 /tmp/units.web-08
diff -u /tmp/ports.web-07 /tmp/ports.web-08

# 4) Prueba funcional real: mandarle tráfico de verdad antes de confiar
ab -n 5000 -c 50 http://web-08:8080/healthz
curl -fsS http://web-08:8080/readyz
Vas a encontrar diferencias que no hay que replicar: versiones de paquetes que avanzaron, un log rotado, un módulo cargado por hardware distinto. El criterio es: ¿esta diferencia afecta el comportamiento del servicio? Si no, se documenta y se ignora. Si sí, o va al playbook o hay que entender por qué el gemelo la necesita y el original no.

Paso 5 — El corte. Con web-08 validado, se drena web-07 del balanceador (LS8.8), se lo saca del inventario activo y se lo deja apagado pero sin destruir durante una semana. Es el rollback más barato que existe.

Paso 6 — El runbook resultante, que es el verdadero entregable del ejercicio. Sin esto, el playbook es un archivo que solo vos sabés cuándo y cómo correr:

# Runbook: recrear un servidor web desde cero

**Cuándo usar este runbook:** web-NN no responde y no se recupera con reinicio, o hay que
reemplazarlo por hardware/actualización mayor.
**Duración esperada:** 25 minutos.  **Requiere:** acceso a Vault + rol `deploy`.
**Impacto durante el procedimiento:** ninguno si quedan ≥ 2 nodos sanos (verificar en el paso 0).

## 0. Antes de empezar (2 min)
    curl -s http://lb-01.prod.internal/api/status | jq '.nodes[] | select(.healthy)'
Esperado: al menos 2 nodos healthy. Si hay 1 o 0 -> NO recrear, ESCALAR (ver "Escalamiento").

## 1. Sacar el nodo dañado del balanceador (1 min)
    curl -X POST http://lb-01.prod.internal/api/drain/web-NN
Esperado: `{"status":"draining"}`. Verificar que el tráfico cayó a 0 en el dashboard
"Fleet / per-node RPS" antes de seguir.

## 2. Aprovisionar la máquina nueva (10 min)
    cd /opt/iac && terraform apply -target=module.web["web-NN"]
Esperado: la IP aparece en la salida. Anotarla.

## 3. Configurarla (8 min)
    ansible-playbook -i inventory/prod.ini site.yml --limit web-NN --diff
Esperado: `failed=0`. Si algún task falla -> NO continuar, ver "Fallas conocidas".

## 4. Verificar ANTES de darle tráfico (3 min)
    ansible-playbook -i inventory/prod.ini site.yml --limit web-NN --check   # -> changed=0
    curl -fsS http://web-NN:8080/readyz                                      # -> 200
    ssh web-NN 'systemctl is-system-running'                                 # -> running

## 5. Reponerlo en el balanceador (1 min)
    curl -X POST http://lb-01.prod.internal/api/enable/web-NN
Esperado: RPS del nodo sube en 60 s. Si no sube -> revisar readyz otra vez.

## Fallas conocidas
- `apt: 404 Not Found` -> el mirror interno está caído. Fallback: `-e apt_mirror=deb.debian.org`.
- El playbook queda colgado en "Esperar a la base" -> el firewall de la VM nueva no tiene la
  regla de salida al puerto 5432. Ver ticket INF-2214.

## Escalamiento
Si a los 30 min el nodo no está sirviendo tráfico: avisar en #sre-oncall y llamar al
on-call secundario. NO seguir intentando solo.

## Última revisión
2026-09-03 — se ejecutó en el incidente INC-4471, funcionó, se corrigió el paso 4
(faltaba el chequeo de `is-system-running`).
📌 La lección del ejercicio no es "usá Ansible". Es que la reproducibilidad se construye desde la realidad hacia el código —midiendo lo que hay, no imaginándolo— y que solo se puede afirmar que un servidor es reproducible el día que lo reprodujiste y comparaste. Igual que un backup no existe hasta que lo restauraste. Todo lo demás es documentación optimista.

Checkpoint — ¿lo tenés claro?

¿Por qué un script bash "que funciona" no reemplaza a un playbook de Ansible?

Porque no es idempotente por defecto. El script describe acciones ("instalá", "agregá esta línea") y por eso su resultado depende del estado en el que encuentre la máquina: corrido dos veces duplica líneas de configuración, falla al crear un usuario que ya existe y reinicia servicios aunque nada haya cambiado. Un playbook describe estado deseado ("que el paquete esté", "que el archivo tenga este contenido"), y los módulos ya traen adentro la lógica de comparar antes de actuar. Esa propiedad es la que te habilita a correrlo cuando quieras — y por lo tanto a usarlo como detector de drift y como documentación ejecutable, no solo como instalador.

Tenés tres réplicas de la base con failover automático. ¿Estás protegido contra la pérdida de datos?

No, y confundir esas dos cosas es uno de los errores más caros que existen. La replicación te protege contra fallas de hardware: si un nodo muere, otro sigue. No te protege contra fallas de software o de personas, que son la mayoría de los incidentes: un DELETE sin WHERE, una migración con bug o un ransomware se replican a los tres nodos en milisegundos, porque el sistema de replicación no tiene forma de saber que esa escritura era indeseada. Para eso hacen falta backups con retención (poder volver a ayer), copias inmutables (que el atacante no pueda borrar) y —sobre todo— una restauración probada con su tiempo medido. HA y backups defienden contra amenazas distintas y ninguna reemplaza a la otra.

¿Por qué la métrica que importa de un backup es el tiempo de restauración y no el de backup?

Porque el tiempo de backup solo prueba que el script corrió; no prueba que los datos sean legibles, que estén completos ni que la aplicación pueda arrancar con ellos. Durante un incidente, la pregunta real es "¿en cuánto vuelvo a estar en línea?", y eso es el RTO: descargar decenas de gigabytes, descomprimir, restaurar la base, reconstruir índices y verificar consistencia. Es habitual descubrir que ese número es diez veces peor de lo que todos suponían — y descubrirlo durante la caída es lo peor que puede pasar. Por eso el simulacro de restauración se automatiza, se mide y su resultado se expone como métrica: para poder alertar cuando hace demasiado tiempo que no se verifica.

Resumen ejecutivo

  • Mascota vs ganado: el umbral no es la cantidad de servidores, es si podés recrear uno. Un servidor con historia manual es deuda impagable e intocable.
  • Idempotencia es la propiedad central: aplicar N veces = aplicar una vez. Los módulos de Ansible la traen; bash no, y escribirla a mano cuesta el triple de código en cada línea.
  • Bash para lo puntual; Ansible para servidores de larga vida; imágenes y contenedores cuando podés reemplazar en vez de modificar. Se combinan por capas.
  • La infraestructura se testea: --check --diff (dry run), Molecule (incluye el test de idempotencia) y testinfra (aserciones sobre el estado final).
  • El drift se detecta con el mismo playbook corriendo en --check todos los días. Se alerta, no se corrige a ciegas: el cambio manual puede ser el fix de un incidente en curso.
  • HA es sobrevivir a la falla de un componente, no tener dos servidores. 99,99% son 52 minutos al año para todo. Distinguí liveness de readiness, cuidá el quórum y buscá los SPOF — incluida la persona que es la única que sabe hacer el failover.
  • 3-2-1 (y 3-2-1-1-0). El número que se publica no es "último backup", es "última restauración exitosa y cuánto tardó". Un backup sin restaurar no es un backup.
  • Actualizar sin downtime: serial, drenar antes de apagar, unattended-upgrades solo de seguridad y sin reboot automático, needrestart porque el parche no reinicia lo que usaba la librería, y livepatch para posponer —no eliminar— el reboot.
  • Observabilidad: método USE, y PSI como señal temprana porque mide tiempo frenado, no porcentaje de uso. Alertá sobre síntomas del usuario, no sobre causas.
  • Runbooks escritos para las 3 AM: comandos exactos, salida esperada y criterio de escalamiento. Post-mortems sin culpa, porque señalar personas hace que la próxima vez te escondan la información que necesitás.
  • Capacity planning: extrapolá con datos, dimensioná N+1 sobre el pico, y recordá que poder escalar rápido vale más que predecir bien.

🎓 Cierre del track — qué estudiar después

Terminaste Linux Senior. Desde LS1 hasta acá recorriste el sistema desde el scheduler hasta el runbook, y en el camino quedó claro el patrón: casi todo lo que parece magia en Linux es un mecanismo simple que podés inspeccionar. Esa es la habilidad que se lleva a cualquier stack. Lo que sigue, en orden de rendimiento por hora invertida:

1. Kubernetes. Es la continuación natural de LS3 (namespaces y cgroups) y LS7 (systemd): los mismos mecanismos del kernel, orquestados en cluster. Aprendelo después de esto y no antes, porque entender qué hace un contenedor por dentro convierte a K8s en algo comprensible en vez de un oráculo de YAML.
2. Terraform / OpenTofu. Ansible configura lo que ya existe; Terraform crea la infraestructura (redes, VMs, DNS, buckets). Juntos cierran el ciclo completo del paso 2 del worked example.
3. La disciplina SRE. SLI, SLO y presupuesto de error; eliminación de toil; ingeniería del caos. Los libros de SRE de Google son gratis y son el material canónico de este módulo llevado a escala.
4. Certificaciones, si te sirven para el CV. LFCS y RHCSA validan administración práctica (RHCSA es examen 100% práctico y tiene buen peso en el mercado); CKA es la de Kubernetes. Ninguna te enseña lo que ya aprendiste acá, pero abren puertas donde el filtro es automático.
5. Profundizar en lo que más te sirvió. Si te enganchó LS6, seguí con eBPF y observabilidad continua (bpftrace, Cilium, Pixie). Si te enganchó LS5, seguí con redes y service mesh. Si te enganchó LS4, seguí con sistemas de archivos distribuidos y bases de datos.
💡 Lo único que no se aprende leyendo. Armate un laboratorio propio —tres VMs alcanzan— y practicá romper y recuperar: llenale el disco, matale la red, corrompé un backup a propósito, apagá el primario y hacé el failover con cronómetro. La confianza en producción no viene de saber la teoría: viene de haber estado ahí antes, cuando no importaba.

🧠 Autoevaluación

1. Corrés tu playbook por segunda vez sobre un servidor que no cambió y Ansible reporta changed=7. ¿Qué significa?

Sobre un servidor sin cambios, una segunda corrida debe dar changed=0: eso es la idempotencia. Un changed persistente indica tasks que actúan sin comparar — típicamente command/shell sin creates: o changed_when:, lineinfile con regex que no matchea lo que escribió, o un template con un timestamp adentro. El daño no es cosmético: te rompe la detección de drift (todo parece desviado) y dispara handlers que reinician servicios sin motivo.

2. Tenés replicación síncrona a tres nodos y failover automático probado. Un desarrollador corre un DELETE sin WHERE en producción. ¿Qué te salva?

La replicación no distingue escrituras deseadas de indeseadas: propaga el DELETE a todos los nodos en milisegundos, y con replicación síncrona lo hace antes de confirmar la transacción. HA protege contra fallas de hardware; contra errores de software y humanos solo protege un backup que te permita volver a un punto anterior en el tiempo — y que hayas restaurado alguna vez, para saber cuánto tarda.

3. Tu dashboard dice "último backup exitoso: hace 2 horas". ¿Qué te garantiza eso sobre tu capacidad de recuperación?

Ese indicador solo dice que el script terminó con código 0. No dice si el archivo se puede descifrar, si la base es consistente, si la app arranca con esos datos, ni cuánto lleva bajarlos y restaurarlos. El RTO es una medición empírica: se obtiene restaurando de verdad y cronometrando. Por eso el simulacro se automatiza y su resultado se expone como métrica —con el timestamp de la última restauración exitosa— para poder alertar cuando hace demasiado que nadie verifica.

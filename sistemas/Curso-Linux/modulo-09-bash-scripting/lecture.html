El shebang

La primera línea (#!) le dice al kernel qué intérprete usar:

#!/bin/bash
#!/usr/bin/env bash      # más portable
#!/usr/bin/env python3

Modo estricto recomendado

set -e          # salir si algún comando falla
set -u          # error si se usa variable no definida
set -o pipefail # falla si cualquier comando del pipe falla
set -x          # debug: imprime cada comando antes de ejecutarlo

# Forma compacta
set -euo pipefail

[ ] vs [[ ]]

  • [ ] es POSIX, funciona en sh; sintaxis estricta
  • [[ ]] es de bash, más features (regex, sin word splitting)
[[ $nombre == "Ana" ]]                     # bash, recomendado
[[ $archivo == *.txt ]]                    # glob match
[[ $email =~ ^[a-z]+@[a-z]+\.[a-z]+$ ]]   # regex con =~

Funciones

saludar() {
    local nombre="$1"           # local: scope a la función
    echo "Hola, $nombre"
    return 0                    # exit code (no valor)
}

saludar "Ana"

# Capturar "valor de retorno" (vía echo)
mensaje=$(saludar "Luis")
echo "Capturado: $mensaje"
En bash, return es solo el exit code (0-255). Para devolver datos, usá echo y captura con $(...).

Errores típicos que borran datos

Variable sin comillas en un rm -rf. Si $DIR está vacía o tiene un typo en el nombre, rm -rf $DIR/ se expande literalmente a rm -rf /. Es el clásico que borró producción en más de una empresa. 
rm -rf $DIR/                           # ❌ con DIR vacía, esto es: rm -rf /
rm -rf "${DIR:?falta definir DIR}"/    # ✅ aborta el script si DIR está vacía o no existe
cd sin comprobar que funcionó. Si el directorio no existe, el cd falla, el script sigue parado donde estaba y el comando siguiente se ejecuta donde no debía. 
cd /opt/deploy/build; rm -rf *         # ❌ si el cd falla, vaciás el directorio actual
cd /opt/deploy/build || exit 1         # ✅ cortá si no pudiste entrar
rm -rf ./*
Paths sin comillas. Sin comillas, bash hace word splitting: un archivo llamado informe final.pdf llega al comando como dos argumentos. Con mv o rm, el resultado va de un "no such file" inofensivo a tocar el archivo equivocado. 
cp $archivo /backup                    # ❌ "informe final.pdf" se parte en 2 argumentos
cp -- "$archivo" /backup/              # ✅ un solo argumento, y -- corta el parseo de flags
Iterar la salida de ls. for f in $(ls) parte los nombres por espacios y saltos de línea, y encima vuelve a expandir los * que haya dentro de un nombre. Nunca parsees ls en un script. 
for f in $(ls *.txt); do rm "$f"; done                        # ❌ se rompe con espacios
for f in *.txt; do [ -e "$f" ] || continue; rm -- "$f"; done  # ✅ glob directo
find . -name '*.txt' -print0 | xargs -0 rm --                 # ✅ para árboles grandes

Checkpoint — ¿lo tenés claro?

¿Por qué "$@" y "$*" no son lo mismo al reenviar los argumentos a otro comando?

"$@" se expande a una palabra por argumento, respetando los que tienen espacios: si te pasaron mi archivo.txt entre comillas, sigue siendo un solo argumento del otro lado. "$*" junta todo en un único string separado por el primer carácter de IFS, así que el comando destino recibe un solo parámetro gigante. Para reenviar argumentos, siempre "$@" con comillas; "$*" sirve para mostrar o loguear.

¿Qué hace set -u y por qué te salva justo de un rm -rf?

Hace que el script aborte cuando usás una variable que no está definida, en vez de expandirla en silencio a la cadena vacía. Ese vacío silencioso es exactamente lo que convierte rm -rf $DIR/ en rm -rf / cuando escribiste mal el nombre de la variable o el export nunca corrió. Con set -u (o con la forma ${DIR:?}) el script muere antes de tocar el disco. Es la u de set -euo pipefail.

Con una variable vacía y sin comillas, ¿por qué [ $x = "y" ] revienta y [[ $x == "y" ]] no?

Porque son cosas distintas. [ ] es un comando que recibe argumentos ya expandidos por el shell: con $x vacía le llegan solo = e y, y protesta por sintaxis. [[ ]] es sintaxis del propio bash: no hace word splitting ni expansión de globs sobre sus operandos, por eso tolera la variable vacía y además te habilita =~ y los patrones. Igual, la conclusión práctica es la misma: poné las comillas siempre, y usá [[ ]] cuando ya sabés que el script corre en bash.

Respondé sin mirar arriba. Cada pregunta te explica el porqué.

1. ¿Qué agrega set -o pipefail al modo estricto?

Por defecto el exit code de un pipe es el del último comando, así que un error a mitad de camino pasa desapercibido. Imprimir cada línea es set -x, y salir ante un fallo es set -e.

2. Dentro de una función de bash, ¿qué devuelve return?

return es únicamente el estado de salida. Para devolver datos hacés echo y lo capturás con mensaje=$(saludar "Luis").

3. ¿Qué guarda $# en un script?

$$ es el PID, $? el exit code del último comando y $@ la lista completa de argumentos. $# es solo cuántos son — por eso sirve en while [ $# -gt 0 ]; do ... shift; done.

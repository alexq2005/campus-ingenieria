Módulo 01 — Sistema de Archivos

Filosofía Unix: "todo es un archivo"

En Linux, todo se representa como archivo: dispositivos, procesos, sockets, configuración del kernel. Esto unifica las APIs.

Por ejemplo:

  • /dev/sda — disco duro
  • /proc/cpuinfo — info del CPU
  • /dev/null — agujero negro (descarta lo que escribas)
  • /dev/random — generador de números aleatorios

Todas las distros siguen un layout estándar a partir de / (raíz):

Rutas absolutas vs relativas

/home/ana/docs/notas.txt    # absoluta (empieza con /)
docs/notas.txt              # relativa al directorio actual
./docs/notas.txt            # idem (. = directorio actual)
../otro/archivo             # sube un nivel (.. = padre)
~/docs/notas.txt            # ~ = home del usuario actual (~/ = $HOME/)
~ana/docs                   # home de usuario "ana"

Inodos

Cada archivo tiene un inodo: estructura que guarda metadatos (permisos, dueño, timestamps, ubicación de bloques). El nombre del archivo es solo una entrada en un directorio que apunta a un inodo.

ls -i archivo.txt          # muestra el número de inodo
stat archivo.txt           # info detallada del inodo

Hard links vs symbolic links

Hard link

Otra entrada en un directorio apuntando al mismo inodo:

ln origen.txt hardlink.txt
  • Mismo contenido, mismo inodo
  • Si borrás el original, el hard link sigue funcionando
  • No funcionan entre sistemas de archivos distintos
  • No se pueden hacer a directorios

Symbolic link (symlink, soft link)

"Acceso directo" — un archivo especial que apunta a otra ruta:

ln -s /ruta/original.txt symlink.txt
  • Si borrás el original, el symlink queda roto
  • Funcionan entre sistemas de archivos
  • Se pueden hacer a directorios
  • Se ven con ls -l: lrwxrwxrwx ... symlink.txt -> /ruta/original.txt

Errores típicos con enlaces y montajes

1. Borrar un symlink a directorio con la barra final. rm -rf enlace/ no borra el enlace: entra por él y borra el contenido del directorio real al que apunta. Un carácter de diferencia.
# ❌ mal — vacía el directorio destino
rm -rf backups/

# ✅ bien — borra solo el enlace; el destino queda intacto
rm backups

# Antes de borrar, mirá siempre a dónde apunta:
ls -l backups        # backups -> /mnt/discos/backups-2026
2. Montar sobre un directorio que ya tenía archivos. El montaje no borra nada, pero tapa lo que había: parece que se perdió, y todo lo que escribas ahí va al disco nuevo. Al desmontar, los viejos "reaparecen" y los nuevos desaparecen.
# ❌ mal — /mnt/datos ya tenía cosas adentro
sudo mount /dev/sdb1 /mnt/datos

# ✅ bien — verificá que el punto de montaje esté vacío
ls -A /mnt/datos            # sin salida = vacío
sudo mount /dev/sdb1 /mnt/datos
findmnt /mnt/datos          # confirmá qué quedó montado
3. Tocar /etc/fstab y reiniciar sin probar. Una línea mal escrita ahí deja el sistema sin bootear (arranca en modo emergencia). Y ojo: /dev/sdb1 puede cambiar de nombre entre arranques según el orden en que aparezcan los discos — usá el UUID, que no cambia.
# ❌ mal — editar fstab con /dev/sdb1 y reiniciar a ciegas

# ✅ bien
sudo cp /etc/fstab /etc/fstab.bak     # backup primero
blkid /dev/sdb1                       # de acá sacás el UUID
sudo nano /etc/fstab                  # UUID=xxxx-xxxx /mnt/datos ext4 defaults,nofail 0 2
sudo mount -a                         # PROBÁ acá: si no tira error, recién ahí reiniciás
4. Sacar el pendrive sin desmontar. Linux cachea las escrituras: el archivo puede figurar como copiado y todavía no estar físicamente en el disco. Si tirás del USB en ese momento, lo perdés.
# ❌ mal — copiar y sacar el pendrive
cp -r ~/tesis /mnt/usb/

# ✅ bien
cp -r ~/tesis /mnt/usb/
sync                        # fuerza el volcado de la caché a disco
sudo umount /mnt/usb

# Si dice "target is busy", averiguá quién lo está usando (no lo fuerces a ciegas):
lsof +f -- /mnt/usb

Checkpoint — ¿lo tenés claro?

¿Por qué un hard link no puede cruzar de partición ni apuntar a un directorio, y un symlink sí?

Porque son cosas distintas. El hard link es otra entrada de directorio que apunta a un número de inodo, y los inodos se numeran dentro de cada sistema de archivos: el inodo 1234 de una partición no tiene nada que ver con el 1234 de otra. Además, permitir hard links a directorios habilitaría ciclos que dejarían dando vueltas a find o a rm -r. El symlink no guarda un inodo sino una ruta de texto, y una ruta se puede escribir apuntando a cualquier lado — por eso cruza filesystems y apunta a directorios, al precio de quedar roto si el destino desaparece.

¿Por qué du y df pueden darte números distintos del mismo disco?

Porque miden cosas distintas. du recorre el árbol de directorios y suma lo que encuentra; df le pregunta al filesystem cuántos bloques le quedan libres. Se separan cuando algo ocupa bloques pero no aparece en el árbol: archivos borrados que un proceso todavía tiene abiertos, archivos tapados por un montaje encima, o el ~5% de bloques que ext4 reserva para root. Si df dice "lleno" y du no encuentra a quién culpar, casi siempre es el primer caso.

¿Qué pasa si borrás un archivo que un proceso está usando?

rm saca el nombre del directorio, no el contenido. Mientras haya un proceso con ese archivo abierto, el inodo sigue vivo y el espacio no se libera: el archivo ya no aparece en ls, pero el disco sigue igual de lleno. Se libera recién cuando ese proceso cierra el descriptor o termina. Es el caso típico de "borré los logs y el disco sigue al 100%": faltaba reiniciar el servicio que los tenía abiertos.

1. Borrás el archivo original. ¿Qué pasa con un hard link que apuntaba a él?

El hard link es otra entrada de directorio hacia el mismo inodo, así que el contenido sobrevive. El que queda roto al borrar el original es el symlink (ln -s).

2. Según el FHS, ¿en qué directorio viven los logs del sistema?

/var guarda datos variables: logs, mail y caches. /etc es configuración del sistema y /boot tiene el kernel más el bootloader.

3. En ls -l, una l en el primer carácter indica…

El primer carácter es el tipo: - regular, d directorio, l symlink, b/c dispositivos, p named pipe y s socket.

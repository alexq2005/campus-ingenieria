Módulo 08 — Traits

Los traits son el corazón del polimorfismo en Rust. Si venís de otros lenguajes, pensalos como interfaces: un contrato de comportamiento que distintos tipos pueden cumplir. Pero los traits van más allá — son la herramienta con la que Rust escribe código genérico, reutilizable y seguro sin herencia de clases. En este módulo aprendés a definirlos, implementarlos, usarlos como parámetros y entender cómo Rust elige entre despacho estático y dinámico.

¿Qué es un trait?

💡 Un trait define comportamiento compartido. Es un conjunto de métodos que un tipo se compromete a tener. Funciona como las interfaces de Java o C#, o los protocols de Swift. La declaración más simple solo lista las firmas de los métodos, sin cuerpo: 
trait Resumir {
    fn resumir(&self) -> String;
}
Cualquier tipo que implemente Resumir garantiza tener un método resumir que devuelve un String.

Fijate en los detalles: el método recibe &self (una referencia prestada al propio valor, sin tomar ownership) y devuelve String con la flecha ->. La firma termina en ; porque acá solo declaramos el contrato: cada tipo pondrá su propia implementación.

Implementar un trait

Para que un tipo cumpla el contrato, usás un bloque impl NombreTrait for Tipo:

struct Articulo {
    titulo: String,
    autor: String,
}

impl Resumir for Articulo {
    fn resumir(&self) -> String {
        format!("{}, por {}", self.titulo, self.autor)
    }
}

Ahora cualquier Articulo tiene el método resumir(). Y lo importante: un tipo puede implementar muchos traits distintos, cada uno en su propio bloque impl. No hay límite ni jerarquía rígida — vas componiendo capacidades.

Regla del huérfano (orphan rule): solo podés implementar un trait para un tipo si al menos uno de los dos (el trait o el tipo) es tuyo, definido en tu crate. No podés implementar un trait ajeno para un tipo ajeno — eso evita conflictos entre librerías.

#[derive(...)]: traits gratis

Muchos traits comunes tienen una implementación tan mecánica que el compilador la genera por vos. Solo tenés que pedirlo con el atributo #[derive(...)] arriba del tipo:

#[derive(Debug, Clone, PartialEq)]
struct Punto {
    x: i32,
    y: i32,
}

Con esa sola línea, Punto ahora se puede imprimir con {:?} (gracias a Debug), copiar con .clone() (gracias a Clone) y comparar con == (gracias a PartialEq).

TraitQué te da al derivarlo
DebugImprimir con {:?} para depurar
CloneCopia explícita y profunda con .clone()
CopyCopia implícita barata (solo tipos simples)
PartialEqComparar con == y !=
PartialOrdComparar con <, >, <=, >=
DefaultCrear un valor por defecto con ::default()
HashUsar el tipo como clave en un HashMap

Traits como parámetros

Acá está la verdadera potencia: una función puede aceptar cualquier tipo que implemente un trait, sin saber cuál es. La sintaxis corta usa &impl Trait:

fn notificar(item: &impl Resumir) {
    println!("¡Novedad! {}", item.resumir());
}

Esa función acepta una referencia a cualquier cosa que sepa resumir() — un Articulo, un Tweet, lo que sea. Es polimorfismo sin herencia.

La forma equivalente y más explícita son los trait bounds con un parámetro genérico <T>:

fn procesar<T: Resumir>(x: T) {
    println!("{}", x.resumir());
}
&impl Trait vs <T: Trait>: son casi lo mismo. fn f(x: &impl Resumir) es azúcar sintáctico de fn f<T: Resumir>(x: &T). Usá impl Trait cuando hay un solo parámetro simple; usá <T> cuando necesitás nombrar el tipo (por ejemplo, para forzar que dos parámetros sean del mismo tipo: fn g<T: Resumir>(a: T, b: T)).

Podés exigir varios traits a la vez con +:

fn mostrar<T: Resumir + Clone>(x: T) {
    let copia = x.clone();
    println!("{}", copia.resumir());
}

Métodos por defecto

Un trait no tiene por qué dejar todos los métodos sin cuerpo. Puede ofrecer una implementación por defecto que los tipos heredan automáticamente si no la sobreescriben:

trait Resumir {
    fn resumir(&self) -> String;

    // Método con cuerpo por defecto:
    fn vista_previa(&self) -> String {
        format!("(Leer más) {}", self.resumir())
    }
}

Cualquier tipo que implemente Resumir obtiene vista_previa() gratis. Si un tipo concreto quiere algo distinto, simplemente la redefine en su bloque impl. Fijate que el método por defecto puede llamar a otros métodos del mismo trait (acá usa self.resumir()), aunque esos todavía no tengan implementación — Rust sabe que cada tipo la proveerá.

Traits estándar que vas a usar siempre

TraitPara qué sirve
DisplayFormato "para humanos" con {}. Lo implementás a mano (no se deriva).
DebugFormato "para programadores" con {:?}. Casi siempre derivado.
CloneDuplicar un valor explícitamente con .clone().
IteratorConvertir un tipo en algo iterable con for, .map(), etc.

Implementar Display a mano se ve así (no se puede derivar porque solo vos sabés cómo querés que se vea):

use std::fmt;

impl fmt::Display for Punto {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "({}, {})", self.x, self.y)
    }
}
Regla de oro: derivá Debug en casi todos tus tipos — es gratis y te salva en cada sesión de depuración. Implementá Display solo en los tipos que el usuario final va a ver impresos.

Dispatch estático vs dinámico

Cuando una función trabaja con "cualquier tipo que implemente un trait", Rust tiene dos estrategias para resolverlo:

🔧 Una analogía: el dispatch estático (genéricos) es como pedirle al compilador que te haga una versión a medida de la función para cada tipo concreto — más herramientas en la caja, pero cada una afilada y rapidísima. El dispatch dinámico (dyn) es como tener una sola llave ajustable que decide en tiempo de ejecución a qué tornillo aplicarse — una sola herramienta flexible, con un pequeño costo al usarla.
AspectoEstático: <T: Trait> / impl TraitDinámico: Box<dyn Trait>
Cuándo se resuelveEn compilación (monomorfización)En ejecución (vtable)
VelocidadMáxima (cero costo)Mínima indirección
Tamaño del binarioMayor (una copia por tipo)Menor (una sola versión)
Tipos mezcladosNo: un solo tipo por llamadaSí: distintos tipos en la misma colección

El caso típico de dyn: guardar tipos distintos en la misma colección, algo que los genéricos no permiten:

// Un Vec con elementos de tipos diferentes, unidos por su trait:
let items: Vec<Box<dyn Resumir>> = vec![
    Box::new(articulo),
    Box::new(tweet),
];

for item in &items {
    println!("{}", item.resumir());
}
📌 Regla práctica: usá genéricos (dispatch estático) por defecto — son más rápidos y es el camino idiomático. Recurrí a Box<dyn Trait> solo cuando necesitás mezclar tipos distintos en runtime (por ejemplo, una lista heterogénea de "cosas dibujables").

Ejemplo completo: un trait, dos tipos, una función

Juntemos todo. Definimos el trait Resumir, lo implementamos para dos tipos distintos, y escribimos una función que acepta &impl Resumir:

// 1. El contrato
trait Resumir {
    fn resumir(&self) -> String;
}

// 2. Dos tipos distintos
struct Articulo {
    titulo: String,
    autor: String,
}

struct Tweet {
    usuario: String,
    texto: String,
}

// 3. Cada uno implementa el trait a su manera
impl Resumir for Articulo {
    fn resumir(&self) -> String {
        format!("{} — por {}", self.titulo, self.autor)
    }
}

impl Resumir for Tweet {
    fn resumir(&self) -> String {
        format!("@{}: {}", self.usuario, self.texto)
    }
}

// 4. Una función polimórfica: acepta CUALQUIER cosa que sepa resumir
fn notificar(item: &impl Resumir) {
    println!("¡Novedad! {}", item.resumir());
}

fn main() {
    let a = Articulo {
        titulo: String::from("Rust 2.0"),
        autor: String::from("Ada"),
    };
    let t = Tweet {
        usuario: String::from("rustlang"),
        texto: String::from("¡traits everywhere!"),
    };

    notificar(&a);   // ¡Novedad! Rust 2.0 — por Ada
    notificar(&t);   // ¡Novedad! @rustlang: ¡traits everywhere!
}

La misma función notificar funciona con Articulo y con Tweet sin cambiar una línea. Eso es el polimorfismo de Rust: contratos de comportamiento, no jerarquías de clases.

Errores típicos al empezar

Buscar "herencia" tipo OOP. Rust no tiene herencia de clases (no podés hacer que Tweet "extienda" a Articulo y herede sus campos). El modelo de Rust es composición + traits: compartís comportamiento con traits, no estructura con clases padre. Si venís de Java/C++, este es el cambio mental más grande del módulo.
Olvidar importar el trait con use. Para llamar un método de un trait, el trait tiene que estar en alcance. Si el método vive en otro módulo o crate y no hiciste use ruta::DelTrait;, el compilador te dirá que el método "no existe" — aunque el impl esté bien. El método está; lo que falta es traer el trait al alcance.
Confundir Display con Debug. {} requiere Display (lo escribís vos); {:?} requiere Debug (lo derivás). Si imprimís un struct con {} sin haber implementado Display, no compila — usá {:?} o implementá Display.

Checkpoint — ¿lo tenés claro?

¿En qué se parece un trait a una interfaz de Java, y en qué se diferencia de la herencia?

Se parece en que define un contrato de comportamiento (un conjunto de métodos) que distintos tipos pueden cumplir. Se diferencia de la herencia en que no transmite estructura ni campos: Rust no tiene clases padre. Compartís comportamiento mediante traits (composición), no estructura mediante herencia.

Implementaste un trait para un tipo y al llamar su método el compilador dice que "no existe". El impl está bien. ¿Qué pasa?

Casi seguro te falta traer el trait al alcance con use ruta::DelTrait;. Para usar los métodos de un trait, el trait tiene que estar importado en el archivo donde lo llamás, aunque la implementación esté en otro lado.

¿Cuándo usarías Box<dyn Trait> en vez de un genérico <T: Trait>?

Cuando necesitás guardar valores de tipos distintos en la misma colección o estructura, unidos solo por el trait que comparten (una lista heterogénea). Los genéricos se resuelven en compilación y exigen un único tipo por instancia; dyn resuelve en runtime con una vtable y permite mezclar tipos, a cambio de una pequeña indirección.

Ejercicios

  1. Definí un trait Animal con un método sonido(&self) -> String. Implementalo para dos structs, Perro y Gato, devolviendo "Guau" y "Miau".
  2. Agregale al trait Animal un método por defecto describir(&self) -> String que use self.sonido() y devuelva algo como "Hago: Guau". Verificá que ambos tipos lo heredan sin reimplementarlo.
  3. Escribí una función hacer_ruido(a: &impl Animal) que imprima el sonido. Probala con un Perro y un Gato. Después reescribila usando un trait bound explícito <T: Animal>.
  4. Derivá #[derive(Debug, Clone, PartialEq)] en el struct Perro. Imprimí un Perro con {:?}, clonalo con .clone() y compará dos perros con ==.
  5. Creá un Vec<Box<dyn Animal>> que contenga un Perro y un Gato mezclados, y recorrelo con un for imprimiendo el sonido de cada uno. Notá que con un genérico común esto no sería posible.

🧠 Autoevaluación

1. ¿Qué define un trait en Rust?

Un trait es como una interfaz: declara métodos que un tipo se compromete a tener. No transmite estructura ni campos — Rust usa composición, no herencia de clases.

2. ¿Para qué sirve #[derive(Debug, Clone)] arriba de un struct?

#[derive(...)] genera implementaciones mecánicas de traits comunes (Debug, Clone, PartialEq, etc.) sin que tengas que escribirlas a mano.

3. ¿Cuándo conviene Box<dyn Trait> en lugar de un genérico <T: Trait>?

dyn usa dispatch dinámico (vtable en runtime) y permite tipos heterogéneos en una colección. Los genéricos se resuelven en compilación, son más rápidos, pero exigen un único tipo por instancia.

Módulo 11 — Cargo, Crates & Testing

Hasta ahora escribiste Rust en un solo archivo. Pero los proyectos reales crecen: necesitás organizar el código, reusar librerías de otra gente y verificar que todo funciona. Esas tres tareas tienen un mismo protagonista: Cargo, el toolchain de Rust. En este módulo vas a dominar Cargo a fondo, entender el ecosistema de crates, organizar tu código en módulos y escribir tests que corren con un solo comando.

Cargo a fondo: Cargo.toml y Cargo.lock

💡 Cargo es a Rust lo que npm es a Node o pip a Python. Crea proyectos, los compila, descarga dependencias, corre tests y genera documentación. El centro de todo es un archivo de manifiesto: Cargo.toml.

Cuando hacés cargo new mi_proyecto, Cargo genera un Cargo.toml como este:

[package]
name = "mi_proyecto"
version = "0.1.0"
edition = "2021"

[dependencies]
serde = "1.0"
rand = "0.8.5"

Hay dos secciones clave: [package] tiene la metadata de tu proyecto (nombre, versión, edición del lenguaje), y [dependencies] lista las librerías externas que usás, cada una con su versión.

Cargo.toml vs Cargo.lock. Vos editás Cargo.toml (decís qué querés, ej: serde = "1.0"). Cargo genera Cargo.lock automáticamente, anotando las versiones exactas que resolvió (ej: serde 1.0.197). El .lock garantiza que vos y tus compañeros compilen con las mismas versiones — no lo edites a mano.

Agregar dependencias

Tenés dos formas de agregar una dependencia. La rápida, con el subcomando cargo add:

cargo add serde
cargo add rand@0.8.5      # versión específica

O editando Cargo.toml a mano y dejando que Cargo resuelva en el próximo build:

[dependencies]
serde = "1.0"

crates.io: el registro de paquetes

¿De dónde salen serde, rand y compañía? De crates.io, el registro oficial de paquetes de Rust. Un crate es una unidad de compilación/distribución: tu propio proyecto es un crate, y cada librería que importás también lo es.

Módulos: organizar el código

Un archivo enorme es ingobernable. Rust te deja partir el código en módulos con tres palabras clave: mod, pub y use.

📌 Las tres palabras del sistema de módulos: mod declara un módulo, pub hace algo visible desde afuera (por defecto todo es privado), y use trae un nombre al alcance para no escribir la ruta completa cada vez.

Podés declarar un módulo inline dentro del mismo archivo:

mod matematica {
    // privado por defecto: NO accesible desde afuera
    fn interno() -> i32 { 42 }

    // pub: visible desde fuera del módulo
    pub fn sumar(a: i32, b: i32) -> i32 {
        a + b
    }
}

fn main() {
    // ruta completa con :: para llegar a la función
    let r = matematica::sumar(2, 3);
    println!("{}", r); // 5
}

O moverlo a su propio archivo. Si en main.rs escribís mod matematica; (con punto y coma, sin bloque), Cargo busca el código en src/matematica.rs.

El árbol de módulos y use

Los módulos forman un árbol que arranca en la raíz del crate: crate. Para no repetir rutas largas, use trae un nombre al alcance:

mod matematica {
    pub fn sumar(a: i32, b: i32) -> i32 { a + b }
}

use crate::matematica::sumar;   // lo traigo al alcance

fn main() {
    let r = sumar(10, 5);        // ya no hace falta matematica::
    println!("{}", r);           // 15
}
🔭 El árbol de módulos es como carpetas y archivos. crate:: es la raíz (como / en el filesystem), cada mod es una subcarpeta, y :: separa niveles como / separa carpetas. use es como crear un atajo (symlink) a algo que está hondo en el árbol.

Testing built-in

Rust trae testing de fábrica — no necesitás instalar nada. Marcás una función con el atributo #[test] y dentro usás macros de aserción para verificar resultados.

MacroVerifica que…
assert!(cond)la condición es true
assert_eq!(a, b)a es igual a b
assert_ne!(a, b)a es distinto de b

La convención es agrupar los tests en un módulo marcado con #[cfg(test)], que le dice al compilador: "compilá esto solo cuando corras los tests, no en el build normal".

pub fn duplicar(x: i32) -> i32 {
    x * 2
}

#[cfg(test)]
mod tests {
    use super::*;   // trae duplicar() al alcance del módulo de tests

    #[test]
    fn duplica_positivo() {
        assert_eq!(duplicar(21), 42);
    }

    #[test]
    fn duplica_cero() {
        assert_eq!(duplicar(0), 0);
    }

    #[test]
    fn no_es_lo_mismo() {
        assert_ne!(duplicar(5), 5);
    }
}

Y corrés todo con un comando:

cargo test

Cargo compila los tests, los ejecuta y te muestra cuántos pasaron y cuántos fallaron.

Tests de integración

Unit tests vs tests de integración. Los #[cfg(test)] mod tests que viven dentro de tu código fuente son unit tests (prueban funciones internas, incluso privadas). Los tests de integración van en una carpeta tests/ en la raíz del proyecto, en archivos separados, y prueban tu crate desde afuera, como lo usaría otro usuario — solo ven la API pub.

Documentación con cargo doc

Rust convierte tus comentarios en documentación HTML navegable. Los doc comments usan /// (tres barras) en vez de //, y van arriba de lo que documentan:

/// Duplica un número entero.
///
/// # Ejemplo
/// ```
/// let r = duplicar(21);
/// assert_eq!(r, 42);
/// ```
pub fn duplicar(x: i32) -> i32 {
    x * 2
}

Y generás el sitio HTML con:

cargo doc --open
💡 Los ejemplos de los doc comments también se testean. Cuando corrés cargo test, Rust compila y ejecuta el código dentro de los bloques ``` de tu documentación. Así tu doc nunca queda desactualizada: si el ejemplo deja de compilar, el test falla.

Errores comunes

Olvidar pub. Si declarás un módulo o función sin pub, NO es accesible desde afuera. El compilador te dirá algo como "function is private". Recordá: todo es privado por defecto en Rust.
Un test sin aserción. Una función #[test] que no tiene ningún assert! y no hace panic! siempre pasa, aunque no verifique nada. Un test que no afirma nada da una falsa sensación de seguridad.
No fijar versiones de dependencias. Dejar dependencias sin versión clara (o borrar el Cargo.lock de un binario) lleva a que builds distintos usen versiones distintas — el clásico "en mi máquina funciona". Fijá versiones y versioná el Cargo.lock.
⚠️ cargo test corre todo en paralelo por defecto. Si tus tests comparten estado global (un archivo, una variable estática), pueden pisarse. Mantené cada test independiente; si hace falta, usá cargo test -- --test-threads=1 para correrlos en serie.

Checkpoint — ¿lo tenés claro?

¿Cuál es la diferencia entre Cargo.toml y Cargo.lock?

Cargo.toml lo escribís vos y declara qué dependencias querés (ej: serde = "1.0"). Cargo.lock lo genera Cargo y anota las versiones exactas resueltas (ej: serde 1.0.197), para que todos compilen igual. No edites el .lock a mano.

¿Por qué una función dentro de un mod no se ve desde afuera?

Porque en Rust todo es privado por defecto. Hay que marcarla con pub para que sea accesible fuera del módulo. Lo mismo aplica al propio mod.

¿Qué hace #[cfg(test)] sobre el módulo de tests?

Le dice al compilador que ese módulo se compile solo cuando corrés cargo test, no en el build normal. Así los tests no pesan en el binario final de producción.

Ejercicios

  1. Creá un proyecto con cargo new y agregá la dependencia rand con cargo add rand. Mirá cómo cambió tu Cargo.toml y qué apareció en Cargo.lock.
  2. Definí un módulo mod geometria con una función pub fn area_rectangulo(ancho: f64, alto: f64) -> f64 y llamala desde main con la ruta completa.
  3. Agregá un use crate::geometria::area_rectangulo; y volvé a llamar la función sin el prefijo del módulo.
  4. Escribí un bloque #[cfg(test)] mod tests con dos funciones #[test] que verifiquen area_rectangulo usando assert_eq!. Corré cargo test.
  5. Agregá un doc comment con /// a area_rectangulo, incluí un ejemplo en un bloque ``` y generá la documentación con cargo doc --open.

🧠 Autoevaluación

1. ¿Cuál archivo declarás vos para pedir una dependencia y cuál genera Cargo con las versiones exactas?

Vos declarás en Cargo.toml qué querés; Cargo resuelve y fija las versiones exactas en Cargo.lock, que no se edita a mano.

2. Tenés mod util { fn ayuda() {} } y querés llamar ayuda() desde main. ¿Por qué falla?

Todo es privado por defecto en Rust. Para verla desde afuera del módulo hay que declararla pub fn ayuda().

3. ¿Qué macro usás dentro de un #[test] para verificar que dos valores son iguales?

assert_eq!(a, b) falla el test si a y b no son iguales. Para "distinto" se usa assert_ne!.

Módulo 06 — Manejo de Errores

En la mayoría de los lenguajes, cuando algo falla, se "lanza" una excepción que vuela hacia arriba hasta que alguien la atrapa. Rust hace algo distinto y, una vez que lo entendés, mucho más honesto: los errores son valores comunes que devolvés y manejás como cualquier otro dato. Nada de saltos invisibles en el flujo del programa.

Rust no tiene excepciones

💡 Dos categorías de error, dos herramientas. Rust divide los problemas en dos: los recuperables (un archivo que no existe, una conexión que cae, una entrada inválida) que se modelan con el tipo Result<T, E>; y los irrecuperables (un bug genuino: un índice fuera de rango, una invariante rota) que disparan panic! y abortan. No hay try/catch: el manejo de errores es parte del tipo de retorno de cada función.

La consecuencia es enorme: mirando la firma de una función ya sabés si puede fallar. Si devuelve Result, fallar es una posibilidad explícita que tenés que manejar. El compilador no te deja ignorarla por accidente.

El tipo Result<T, E>

Result es un enum (lo viste en M05) con dos variantes: Ok(valor) cuando todo salió bien, y Err(error) cuando algo falló. En la práctica es así de simple:

enum Result<T, E> {
    Ok(T),   // éxito, contiene el valor
    Err(E),  // fallo, contiene el error
}

Las funciones que pueden fallar declaran Result en su retorno. Por ejemplo, una función que parsea texto a número:

fn parsear(texto: &str) -> Result<i32, String> {
    match texto.trim().parse::<i32>() {
        Ok(n) => Ok(n),
        Err(_) => Err(format!("'{}' no es un número", texto)),
    }
}
El genérico se lee fácil: en Result<i32, String>, el i32 es el tipo del valor de éxito y el String es el tipo del error. La T y la E de Result<T, E> son solo placeholders que cada función rellena.

Manejar un Result

Hay tres formas principales de lidiar con un Result, de la más explícita a la más concisa.

1. Con match (lo más explícito)

Desarmás las dos variantes a mano. Es verboso pero clarísimo, y el compilador te obliga a cubrir ambos casos:

match parsear("42") {
    Ok(n) => println!("Número: {}", n),
    Err(e) => println!("Error: {}", e),
}

2. Con .unwrap() / .expect() (atajos peligrosos)

.unwrap() devuelve el valor si es Ok, pero hace panic si es Err. .expect("mensaje") es igual pero te deja personalizar el mensaje del panic:

let n = parsear("42").unwrap();              // 42, o panic si falla
let m = parsear("42").expect("debía parsear"); // igual, con mensaje propio
⚠️ Solo para prototipos y tests. .unwrap() y .expect() convierten un error recuperable en un panic que tumba el programa. Están bien para un script rápido o un test donde un fallo debe abortar, pero en código de producción son una bomba de tiempo.

3. Con el operador ? (el idiom)

El operador ? es la joya del manejo de errores en Rust. Puesto detrás de una expresión que da Result: si es Ok(v), extrae la v y sigue; si es Err(e), retorna ese error inmediatamente desde la función actual. Propaga el error hacia arriba, sin escribir el match a mano:

fn doble(texto: &str) -> Result<i32, String> {
    let n = parsear(texto)?;  // si Err, retorna el Err acá mismo
    Ok(n * 2)                 // si Ok, sigue con el valor
}
🔗 El ? es como un peaje con barrera. Si el valor que pasa es Ok, la barrera se abre y el valor sigue su camino. Si es Err, la barrera baja: el error da media vuelta y sale por donde entró (lo retorna la función). Vos no tenés que vigilar la barrera en cada línea — el ? lo hace por vos.

Solo podés usar ? dentro de una función que devuelva Result (o Option), porque necesita "tener a dónde" retornar el error.

Errores irrecuperables: panic!

Cuando el programa llega a un estado que no debería ser posible — un bug genuino, una invariante rota — la respuesta correcta es abortar con panic!. El programa imprime un mensaje, desenrolla la pila y termina:

fn dividir(a: i32, b: i32) -> i32 {
    if b == 0 {
        panic!("división por cero: esto es un bug del llamador");
    }
    a / b
}

Acceder a un índice fuera de rango (v[99] en un vector de 3 elementos) también hace panic automáticamente: es un bug, no un error esperable.

📌 La regla de oro. Usá Result para lo esperable (puede fallar y querés que el llamador decida qué hacer). Usá panic! solo para bugs (estados imposibles que indican que el programa está roto). Y para propagar errores hacia arriba sin ruido, usá el operador ?.

De Option a Result: .ok_or()

A veces tenés un Option (M04) pero necesitás un Result — por ejemplo, para poder usar el operador ?. El método .ok_or() convierte un None en Err y un Some(v) en Ok(v):

fn primero(v: &[i32]) -> Result<i32, String> {
    let x = v.first().ok_or("la lista está vacía".to_string())?;
    Ok(*x)
}
🧰 Box<dyn Error> para no casarte con un tipo de error. Cuando una función puede fallar de varias maneras distintas, escribir el tipo exacto de error se vuelve incómodo. El tipo Box<dyn Error> es un "error genérico" que acepta cualquier error: fn cargar() -> Result<Datos, Box<dyn Error>>. Es muy común en main y en código de aplicación; lo verás más a fondo cuando manejes errores reales de librerías.

Errores comunes que vas a cometer

.unwrap() por todos lados en producción. Funciona en tu máquina con datos perfectos, pero el día que el input es inesperado, el programa hace panic y se cae en runtime. Reservá unwrap para prototipos y tests.
Usar panic! como manejo normal de errores. Panic es para bugs irrecuperables, no para "el usuario escribió mal el email". Si es algo que esperás que pase a veces, devolvé Result y dejá que el llamador decida.
Ignorar un Result que te devuelven. Rust marca Result con #[must_use]: si lo tirás sin usar, el compilador te avisa con un warning. No lo silencies — manejá el resultado o propagalo con ?.
🚫 El panic no es gratis. Un panic! en producción tumba el hilo (o el programa entero). En un servidor web mal armado, un solo .unwrap() sobre datos del usuario puede tirar abajo el servicio para todos. Por eso el idiom es Result + ?: el error se maneja, no explota.

Checkpoint — ¿lo tenés claro?

¿Cuál es la diferencia entre un error recuperable y uno irrecuperable en Rust?

Un error recuperable es algo esperable que puede fallar (archivo inexistente, input inválido) y se modela con Result<T, E> para que el llamador decida qué hacer. Uno irrecuperable es un bug genuino (índice fuera de rango, invariante rota) y se maneja con panic!, que aborta el programa.

¿Qué hace exactamente el operador ??

Puesto detrás de una expresión Result: si es Ok(v), extrae v y el programa sigue; si es Err(e), retorna ese Err inmediatamente desde la función actual, propagándolo hacia arriba. Solo se puede usar dentro de funciones que devuelven Result u Option.

¿Por qué .unwrap() es peligroso en producción?

Porque hace panic! (tumba el programa) en cuanto el Result es Err. Convierte un error recuperable en un crash. Está bien para prototipos y tests, pero en producción deberías manejar el error con match o propagarlo con ?.

Ejercicios

  1. Escribí una función fn parsear(texto: &str) -> Result<i32, String> que devuelva Ok con el número o Err con un mensaje. Probala con un match sobre el resultado.
  2. Agregá una función fn doble(texto: &str) -> Result<i32, String> que use el operador ? para parsear y devuelva el número multiplicado por 2.
  3. Tomá un Option<i32> y convertilo en Result<i32, String> usando .ok_or(); después usá ? para extraer el valor.
  4. Escribí una función que haga panic! ante una entrada imposible (por ejemplo, una edad negativa) y explicá por qué acá panic es lo correcto y no un Result.
  5. Reemplazá un .unwrap() por un match que maneje el caso Err imprimiendo un mensaje, y comprobá que el programa ya no hace panic con input inválido.

🧠 Autoevaluación

1. ¿Qué tipo usás para un error recuperable que el llamador debería manejar?

Rust no tiene excepciones. Los errores recuperables se modelan con Result<T, E>: Ok(valor) en éxito, Err(error) en fallo.

2. ¿Qué hace el operador ? cuando la expresión da Err?

El ? propaga: si es Ok(v) extrae v y sigue; si es Err(e) retorna ese error inmediatamente desde la función (que debe devolver Result u Option).

3. ¿Cuándo es correcto usar panic!?

panic! es para bugs verdaderamente irrecuperables (índice fuera de rango, invariante rota). Para lo esperable usá Result y dejá que el llamador decida.

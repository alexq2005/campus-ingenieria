Módulo 02 — Ownership

Llegamos al concepto que define a Rust y lo separa de todo lo demás. Ownership (propiedad) es el mecanismo por el cual Rust logra lo imposible: gestionar memoria de forma totalmente segura, sin garbage collector y sin que vos tengas que liberarla a mano. Si entendés ownership, entendés Rust. Si no, vas a pelearte con el compilador sin saber por qué.

La idea central: cada valor tiene UN dueño

💡 Una sola regla lo gobierna todo. Cada valor en Rust tiene exactamente una variable que es su dueña. Cuando esa variable sale de scope (termina el bloque { } donde vive), el valor se libera automáticamente. A eso se le llama drop. No hay free() manual como en C, ni un GC corriendo en segundo plano como en Java o Python: el compilador inserta la liberación exacta donde corresponde.

Mirá este ejemplo. La variable s es la dueña de un String. Cuando el bloque termina, Rust llama a drop y libera la memoria sin que vos hagas nada:

fn main() {
    {
        let s = String::from("hola"); // s es la dueña del String
        println!("{}", s);            // se usa normalmente
    } // <- aquí termina el scope: s sale de alcance y el String se libera (drop)

    // println!("{}", s); // ERROR: s ya no existe acá
}
¿Por qué importa el scope? En Rust el scope es la región del código donde una variable es válida. El momento exacto en que una variable sale de scope es el momento exacto en que su valor se libera. No antes (sería use-after-free), no después (sería un leak). El compilador lo calcula por vos.

Move: transferir el ownership

Acá viene lo que confunde a todos los que llegan de otros lenguajes. ¿Qué pasa cuando asignás un valor a otra variable?

fn main() {
    let s1 = String::from("hola");
    let s2 = s1; // el ownership se MUEVE de s1 a s2

    println!("{}", s1); // ERROR: value used after move
}
📌 Esto NO copia el String. Un String guarda en el stack un puntero al texto que vive en el heap. Si Rust copiara solo el puntero, dos variables apuntarían al mismo dato del heap, y al salir de scope ambas intentarían liberarlo → double-free. Para evitarlo, Rust mueve el ownership: tras let s2 = s1;, s1 queda invalidada. Solo s2 es dueña, solo s2 liberará el dato. Usar s1 después es error de compilación.

El compilador te lo dice claramente:

error[E0382]: borrow of moved value: `s1`
  --> src/main.rs:5:20
   |
3  |     let s1 = String::from("hola");
   |         -- move occurs because `s1` has type `String`,
   |            which does not implement the `Copy` trait
4  |     let s2 = s1;
   |              -- value moved here
5  |     println!("{}", s1);
   |                    ^^ value borrowed here after move

Copy: los tipos simples se copian, no se mueven

Si todo se moviera, trabajar con números sería un infierno. Por eso los tipos simples que viven enteramente en el stack implementan el trait Copy: al asignarlos se hace una copia barata y la variable original sigue siendo válida.

fn main() {
    let x = 5;
    let y = x; // x se COPIA en y (i32 es Copy)

    println!("x = {}, y = {}", x, y); // OK: ambas valen 5
}

🔗 Pensalo así: un valor Copy es como pasarle a alguien una fotocopia de un papel — los dos se quedan con el suyo. Un valor que se mueve es como pasarle el papel original — vos te quedás sin él. Por eso un i32 se fotocopia (es chiquito y barato) pero un String se entrega (clonar el heap sería caro y silencioso).

Clone: copia profunda explícita

¿Y si sí querés conservar las dos? Pedís una copia profunda explícita con .clone(). Esto duplica también los datos del heap, así que cada variable es dueña de su propio dato:

fn main() {
    let s1 = String::from("hola");
    let s2 = s1.clone(); // copia PROFUNDA: duplica el dato del heap

    println!("s1 = {}, s2 = {}", s1, s2); // OK: ambas válidas e independientes
}
📌 clone() es explícito a propósito. Rust nunca copia el heap "por las tuyas" — eso sería un costo oculto. Si ves .clone() en el código, sabés que ahí hay una asignación de memoria real. La claridad sobre el costo es una decisión de diseño del lenguaje.

Ownership y funciones

Pasar un valor a una función funciona igual que asignarlo a otra variable: si el tipo no es Copy, el ownership se mueve adentro de la función. Cuando la función termina, ese valor sale de scope y se libera — salvo que lo devuelvas.

fn main() {
    let s = String::from("hola");
    consumir(s);          // el ownership de s se mueve a la función

    // println!("{}", s); // ERROR: s ya fue movida adentro de consumir()

    let n = 5;
    copiar(n);            // n es i32 (Copy): se copia
    println!("{}", n);    // OK: n sigue válida
}

fn consumir(texto: String) {
    println!("recibí: {}", texto);
} // <- texto sale de scope acá y el String se libera

fn copiar(numero: i32) {
    println!("recibí: {}", numero);
}
Adelanto del M03: mover el valor cada vez que llamás una función es incómodo (¿y si la función solo quiere mirar el dato sin quedárselo?). La solución idiomática son las referencias (&s): le "prestás" el valor a la función sin transferir el ownership. Lo vemos en detalle en el próximo módulo.

Lo que esto elimina — en compilación

📌 El modelo de ownership erradica tres clases enteras de bugs ANTES de ejecutar:
  • use-after-free — usar memoria ya liberada: imposible, porque la variable invalidada no compila.
  • double-free — liberar dos veces el mismo dato: imposible, porque solo hay un dueño que libera.
  • memory leaks — memoria que nunca se libera: el drop automático al salir de scope la previene.
Otros lenguajes atrapan algunos de estos en runtime (con crashes) o nunca (con corrupción silenciosa). Rust los atrapa en compile time: si compila, esos bugs no están.

Errores típicos al empezar

Usar una variable después de moverla. El error más común. let s2 = s1; y después tocar s1 → value used after move. Recordá: tras un move, la variable original deja de existir.
Clonar todo para "callar" al compilador. Cuando el borrow checker se queja, es tentador resolverlo metiendo .clone() en todos lados. Funciona, pero clonás memoria que no hacía falta clonar. Casi siempre la respuesta correcta es una referencia (M03), no un clone. clone() es para cuando de verdad querés dos copias independientes.

Ejemplo completo: el move que falla y cómo arreglarlo

Este código no compila porque usa s1 después de moverla a s2:

fn main() {
    let s1 = String::from("Rust");
    let s2 = s1;                       // ownership movido a s2
    println!("{} y {}", s1, s2);       // ERROR: s1 ya no es válida
}

Fix con clone() (cuando realmente necesitás dos Strings independientes):

fn main() {
    let s1 = String::from("Rust");
    let s2 = s1.clone();               // copia profunda: dos dueños, dos datos
    println!("{} y {}", s1, s2);       // OK
}

Mejor opción (adelanto del M03): referencia. Si solo querés leer ambas sin duplicar memoria, prestás el valor con &:

fn main() {
    let s1 = String::from("Rust");
    let s2 = &s1;                      // s2 es una referencia: NO mueve ni copia
    println!("{} y {}", s1, s2);       // OK: s1 sigue siendo la dueña
}

Checkpoint — ¿lo tenés claro?

¿Qué le pasa a un valor cuando su variable dueña sale de scope?

Se libera automáticamente: Rust llama a drop en ese punto exacto. No hay que liberar a mano (como en C) ni esperar a un garbage collector (como en Java/Python). El compilador inserta la liberación donde corresponde.

¿Por qué let s2 = s1; invalida a s1 si s1 es un String?

Porque el ownership se mueve. El String apunta a datos en el heap; si s1 y s2 quedaran ambas válidas, las dos intentarían liberar el mismo dato al salir de scope (double-free). Rust lo evita dejando un solo dueño: s2. Por eso s1 deja de ser usable.

¿Por qué let y = x; con un i32 NO invalida a x?

Porque i32 implementa el trait Copy: vive enteramente en el stack y copiarlo es barato. Al asignarlo se hace una copia y x sigue válida. Solo los tipos con datos en el heap (como String o Vec) se mueven en vez de copiarse.

Ejercicios

  1. Escribí un bloque { } con un String adentro y, fuera del bloque, intentá usar esa variable. Leé el error y explicá con tus palabras por qué falla.
  2. Reproducí el clásico: let s1 = String::from("hola"); let s2 = s1; y después println!("{}", s1);. Mirá el mensaje value used after move.
  3. Arreglá el ejercicio anterior de DOS formas distintas: una con .clone() y otra con una referencia (&s1). Compará cuál duplica memoria y cuál no.
  4. Probá lo mismo pero con let x = 5; let y = x; println!("{} {}", x, y);. ¿Compila? Explicá por qué un i32 se comporta distinto a un String.
  5. Escribí una función fn longitud(s: String) -> usize que reciba un String y devuelva su largo. Después de llamarla, intentá usar el String original en main y observá el error de move. (Spoiler: en el M03 lo vas a resolver con referencias.)

🧠 Autoevaluación

1. Tras let s2 = s1; donde s1 es un String, ¿qué pasa con s1?

String no es Copy, así que la asignación mueve el ownership a s2. Usar s1 después es error de compilación (value used after move).

2. ¿Cuándo se libera la memoria de un valor en Rust?

No hay GC ni free() manual: el valor se libera (drop) exactamente cuando su dueño sale de scope. El compilador inserta la liberación por vos.

3. Querés conservar DOS String independientes a partir de uno. ¿Qué usás?

.clone() duplica también los datos del heap, dando dos dueños independientes. La asignación simple movería (no copiaría), y un mismo dato puede tener un único dueño a la vez — pero podés crear copias con clone().

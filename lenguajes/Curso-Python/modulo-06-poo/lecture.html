Módulo 06 — Programación Orientada a Objetos

Clases y objetos

Una clase es un molde; un objeto (instancia) es un caso concreto.

class Persona:
    def __init__(self, nombre: str, edad: int):
        self.nombre = nombre
        self.edad = edad

    def saludar(self) -> str:
        return f"Hola, soy {self.nombre}"

ana = Persona("Ana", 30)   # crea instancia (llama __init__)
print(ana.saludar())       # 'Hola, soy Ana'

self

Es la convención: el primer parámetro de los métodos representa la instancia. No es palabra reservada, podrías llamarlo distinto, pero no lo hagas.

__init__

El constructor. Se ejecuta al crear la instancia. No devuelve nada.

Atributos de clase vs instancia

class Perro:
    especie = "Canis lupus familiaris"   # de clase (compartido)

    def __init__(self, nombre):
        self.nombre = nombre              # de instancia (único)

a = Perro("Rex")
b = Perro("Lupita")
a.especie    # mismo valor compartido
a.nombre     # 'Rex'
b.nombre     # 'Lupita'

Métodos

De instancia (regular)

def metodo(self, ...):
    ...

De clase (@classmethod)

Recibe la clase, no la instancia. Útil para constructores alternativos:

class Fecha:
    def __init__(self, dia, mes, año):
        self.dia, self.mes, self.año = dia, mes, año

    @classmethod
    def desde_string(cls, texto):
        d, m, a = map(int, texto.split("/"))
        return cls(d, m, a)

f = Fecha.desde_string("15/03/2024")

Estáticos (@staticmethod)

No reciben self ni cls. Función "pegada" a la clase por organización:

class Matematica:
    @staticmethod
    def es_par(n):
        return n % 2 == 0

Matematica.es_par(4)   # True

Encapsulación

Python no tiene private real. Convenciones:

  • _atributo — "interno" (no toques desde afuera, pero técnicamente accesible)
  • __atributo — name mangling (se renombra a _ClaseNombre__atributo)
class Cuenta:
    def __init__(self):
        self._saldo = 0          # privado por convención
        self.__pin = "1234"      # privado fuerte (name mangling)

Properties (getters/setters pythónicos)

class Temperatura:
    def __init__(self, celsius):
        self._celsius = celsius

    @property
    def celsius(self):
        return self._celsius

    @celsius.setter
    def celsius(self, valor):
        if valor < -273.15:
            raise ValueError("Bajo el cero absoluto")
        self._celsius = valor

    @property
    def fahrenheit(self):
        return self._celsius * 9/5 + 32

t = Temperatura(25)
t.celsius           # 25 (sin paréntesis — es property)
t.celsius = 30      # llama al setter
t.fahrenheit        # 86.0

Herencia

class Animal:
    def __init__(self, nombre):
        self.nombre = nombre

    def hablar(self):
        return "..."

class Perro(Animal):                    # hereda de Animal
    def hablar(self):                   # override
        return "Guau"

class Gato(Animal):
    def hablar(self):
        return "Miau"

for animal in [Perro("Rex"), Gato("Mishi")]:
    print(f"{animal.nombre}: {animal.hablar()}")

super() para llamar al padre

class Empleado(Persona):
    def __init__(self, nombre, edad, salario):
        super().__init__(nombre, edad)   # llama Persona.__init__
        self.salario = salario

Herencia múltiple (con cuidado)

class A: pass
class B: pass
class C(A, B): pass

# MRO (Method Resolution Order)
C.__mro__   # (C, A, B, object)

Polimorfismo

Mismo método, distinto comportamiento según el tipo. Python usa duck typing:

"Si camina como un pato y grazna como un pato, es un pato."

No requiere herencia explícita: si un objeto tiene los métodos esperados, sirve.

def hacer_hablar(animal):
    return animal.hablar()      # funciona con cualquier objeto que tenga .hablar()

Métodos especiales (dunders)

Permiten que tus objetos se comporten como built-ins:

class Vector:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __repr__(self):                # representación oficial
        return f"Vector({self.x}, {self.y})"

    def __str__(self):                 # para print() y str()
        return f"({self.x}, {self.y})"

    def __add__(self, other):          # v1 + v2
        return Vector(self.x + other.x, self.y + other.y)

    def __eq__(self, other):           # v1 == v2
        return self.x == other.x and self.y == other.y

    def __len__(self):                 # len(v)
        return int((self.x**2 + self.y**2) ** 0.5)

    def __getitem__(self, i):          # v[0], v[1]
        return (self.x, self.y)[i]

v1 = Vector(1, 2)
v2 = Vector(3, 4)
print(v1 + v2)        # (4, 6)
print(v1 == Vector(1, 2))  # True

Dataclasses (Python 3.7+)

Boilerplate-free para clases que principalmente almacenan datos:

from dataclasses import dataclass, field

@dataclass
class Producto:
    nombre: str
    precio: float
    stock: int = 0
    tags: list[str] = field(default_factory=list)

p = Producto("Café", 1500, 10)
print(p)   # Producto(nombre='Café', precio=1500, stock=10, tags=[])

Genera automáticamente __init__, __repr__, __eq__.

Variantes

@dataclass(frozen=True)   # inmutable
@dataclass(slots=True)    # más eficiente en memoria (Python 3.10+)

Clases abstractas (abc)

from abc import ABC, abstractmethod

class Forma(ABC):
    @abstractmethod
    def area(self):
        pass

class Circulo(Forma):
    def __init__(self, r):
        self.r = r

    def area(self):
        return 3.14159 * self.r ** 2

# Forma()  # TypeError: no se puede instanciar abstracta
Circulo(5).area()

Errores típicos con clases

1. Olvidar self en la firma del método — Python le pasa la instancia como primer argumento igual, la hayas declarado o no. 
class Persona:
    def saludar():            # ❌ falta self
        return "Hola"

Persona().saludar()
# TypeError: saludar() takes 0 positional arguments but 1 was given

class Persona:
    def saludar(self):        # ✅ self es la instancia y va siempre primero
        return "Hola"
2. Usar un atributo de clase mutable como si fuera de instancia — lo estás compartiendo entre todos los objetos. 
class Perro:
    amigos = []              # ❌ una sola lista para toda la especie

a, b = Perro(), Perro()
a.amigos.append("Lupita")
b.amigos                     # ['Lupita'] — ¡pero no era amiga de b!

class Perro:
    def __init__(self):
        self.amigos = []     # ✅ una lista nueva por instancia
3. Poner un default mutable en una @dataclass — acá Python te frena antes: ni siquiera te deja definir la clase. 
@dataclass
class Producto:
    tags: list[str] = []                            # ❌ ValueError: mutable default

@dataclass
class Producto:
    tags: list[str] = field(default_factory=list)   # ✅ una lista por instancia
4. Definir solo __str__ y no entender por qué la lista muestra basura — print(obj) usa __str__, pero al imprimir una colección Python le pide __repr__ a cada elemento. 
print(v1)      # (1, 2)                                ← usa __str__
print([v1])    # [<__main__.Vector object at 0x7f...>]  ← ❌ usa __repr__
Definí siempre __repr__ (es el que te salva en el debugging) y agregá __str__ solo si querés una versión distinta para el usuario final.

Checkpoint — ¿lo tenés claro?

Si Python tiene duck typing, ¿para qué sirve entonces la herencia?

Para el polimorfismo puro no hace falta: hacer_hablar(animal) funciona con cualquier objeto que tenga .hablar(), herede de Animal o no. Lo que aporta la herencia es reutilizar implementación (el __init__ de Animal, sus métodos comunes) y declarar una intención de diseño, que después se puede verificar con isinstance o directamente forzar con ABC. Con duck typing ganás flexibilidad, porque no atás tu función a una jerarquía; perdés la red de seguridad, porque el error recién aparece en runtime, cuando llega un objeto sin el método esperado.

¿Por qué @classmethod recibe cls y @staticmethod no recibe nada?

Porque resuelven problemas distintos. Un classmethod necesita saber sobre qué clase lo llamaron: por eso Fecha.desde_string puede terminar en return cls(d, m, a) y seguir funcionando en una subclase, construyendo objetos de la subclase y no de Fecha. Un staticmethod no toca ni la instancia ni la clase: es una función suelta que vive ahí por organización y que podría estar fuera de la clase sin que nada cambie.

Si _saldo y __pin se pueden leer igual desde afuera, ¿para qué se usan?

Porque en Python la encapsulación es un contrato, no una cerradura. El _ es un mensaje al resto del equipo: "esto es interno, puede cambiar sin aviso, no dependas de ello", y las herramientas lo respetan (no aparece en el autocompletado ni se exporta con import *). El doble __ agrega name mangling: el atributo pasa a llamarse _Clase__pin, lo que no impide el acceso deliberado pero sí evita colisiones accidentales cuando una subclase define un atributo con el mismo nombre. La filosofía de fondo es la del Zen: acá somos todos adultos.

🧠 Autoevaluación rápida

Respondé sin mirar arriba. Cada pregunta te explica el porqué.

1. ¿Qué te genera automáticamente el decorador @dataclass?

@dataclass te ahorra el boilerplate de las clases que sobre todo guardan datos: arma el constructor, un __repr__ legible y la comparación por valor. Los defaults mutables van con field(default_factory=list).

2. Con @property def fahrenheit(self), ¿cómo leés el valor desde t = Temperatura(25)?

Una property se accede como atributo y Python llama al método por detrás. Esa es la forma pythónica de los getters/setters: podés validar en el @celsius.setter sin cambiarle la interfaz a quien usa la clase.

3. En Empleado(Persona), ¿qué hace super().__init__(nombre, edad)?

Si definís tu propio __init__ en la subclase, el del padre no se ejecuta solo: hay que invocarlo con super(). Si no lo hacés, self.nombre y self.edad nunca se setean.

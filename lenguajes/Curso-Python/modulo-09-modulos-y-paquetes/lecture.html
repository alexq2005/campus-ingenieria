Módulo 09 — Módulos y Paquetes

Módulo

Cualquier archivo .py es un módulo. Lo importás en otro código:

# math_utils.py
PI = 3.14159

def area_circulo(r):
    return PI * r ** 2
# main.py
import math_utils

print(math_utils.PI)
print(math_utils.area_circulo(5))

Formas de importar

import math                           # módulo completo
import math as m                      # con alias
from math import pi, sqrt             # nombres específicos
from math import sqrt as raiz         # con alias
from math import *                    # ⚠️ ANTI-PATRÓN: contamina namespace
No usar from x import * excepto en __init__.py con __all__ explícito.

El módulo principal — __name__

Cada módulo tiene __name__. Cuando se ejecuta directamente, vale "__main__". Cuando se importa, vale el nombre del módulo:

# script.py
def main():
    print("Ejecutando")

if __name__ == "__main__":
    main()

Esto permite que un archivo sea importable y ejecutable sin efectos colaterales.

Búsqueda de módulos

Python busca módulos en sys.path, en este orden:

  1. Directorio del script actual
  2. PYTHONPATH (variable de entorno)
  3. Directorios de la instalación
  4. site-packages (donde pip instala paquetes)
import sys
print(sys.path)

Paquetes

Un paquete es un directorio con un __init__.py que agrupa varios módulos:

mi_paquete/
├── __init__.py
├── modulo_a.py
├── modulo_b.py
└── subpaquete/
    ├── __init__.py
    └── modulo_c.py
from mi_paquete import modulo_a
from mi_paquete.subpaquete import modulo_c

__init__.py

Se ejecuta al importar el paquete. Útil para:

  • Exponer una API pública con __all__
  • Re-exportar símbolos importantes
# mi_paquete/__init__.py
from .modulo_a import funcion_publica
from .modulo_b import ClasePrincipal

__all__ = ["funcion_publica", "ClasePrincipal"]
__version__ = "1.0.0"

Imports relativos

Dentro de un paquete:

from . import modulo_b           # mismo paquete
from .modulo_b import x
from ..otro import y             # paquete padre

Entornos virtuales

Cada proyecto debe tener su virtualenv para aislar dependencias:

# Crear
python -m venv .venv

# Activar
# Linux/macOS:
source .venv/bin/activate
# Windows (cmd):
.venv\Scripts\activate.bat
# Windows (PowerShell):
.venv\Scripts\Activate.ps1

# Verificar
which python      # debería apuntar al venv

# Desactivar
deactivate

pip — gestor de paquetes

pip install requests                  # última versión
pip install "requests>=2.28,<3"       # rango
pip install -r requirements.txt       # desde archivo
pip install -e .                      # paquete local en modo editable
pip uninstall requests
pip list                              # paquetes instalados
pip show requests                     # info detallada
pip freeze > requirements.txt         # exporta versiones exactas

requirements.txt

requests==2.31.0
pandas>=2.0,<3.0
fastapi
Recomendado: usar pip-compile (de pip-tools) o uv para lockfiles deterministas.

Errores típicos con imports y entornos

Imports circulares. a.py importa b y b importa a. Cuando Python está a mitad de ejecutar a, el módulo ya existe en sys.modules pero todavía está vacío, así que el import de la vuelta falla. Casi siempre es señal de que hay una tercera pieza común esperando salir. 
# ❌ mal
# usuarios.py
from pedidos import calcular_total

# pedidos.py
from usuarios import Usuario
# ImportError: cannot import name 'Usuario' from partially initialized
# module 'usuarios' (most likely due to a circular import)

# ✅ bien — extraé lo compartido a un tercer módulo
# modelos.py   -> define Usuario y Pedido
# usuarios.py  -> from modelos import Usuario
# pedidos.py   -> from modelos import Usuario, Pedido
Llamar a tu archivo igual que un módulo del stdlib. El directorio del script va primero en sys.path, así que tu random.py le gana al de Python — y no solo para vos: también para cualquier librería que por adentro haga import random. Los clásicos que rompen todo: json.py, email.py, types.py, test.py, logging.py. 
# ❌ mal — tenés un archivo random.py al lado del script
import random
random.randint(1, 6)
# AttributeError: module 'random' has no attribute 'randint'

# ✅ bien — nombrá desde tu dominio
# sorteo.py, dados.py, utils_random.py ...
Correr con python archivo.py un módulo que usa imports relativos. Ejecutado así, el archivo pasa a ser __main__ y no tiene paquete padre: el . del import no apunta a ningún lado. 
# ❌ mal
python mi_paquete/cli.py
# ImportError: attempted relative import with no known parent package

# ✅ bien — corré el paquete, no el archivo suelto
python -m mi_paquete.cli
Instalar con el venv desactivado. El paquete cae en el Python global y después, ya con el entorno activo, aparece el clásico ModuleNotFoundError de algo que "ya instalaste". Confirmá siempre en qué Python estás parado antes de instalar. 
# ❌ mal
pip install requests          # ¿en qué intérprete? nadie sabe

# ✅ bien — activar, instalar con python -m pip, verificar
source .venv/bin/activate     # Windows: .venv\Scripts\Activate.ps1
python -m pip install requests
python -c "import sys; print(sys.prefix)"   # debe apuntar al .venv

Checkpoint — ¿lo tenés claro?

Tres archivos distintos hacen import config. ¿Cuántas veces se ejecuta el código de nivel superior de config.py?

Una sola. La primera vez Python ejecuta el módulo y guarda el objeto resultante en sys.modules; los imports siguientes solo devuelven esa misma instancia ya construida. Por eso un módulo funciona de hecho como un singleton (una constante definida ahí arriba es la misma para todos), y también por eso un print() suelto en un módulo solo aparece una vez por más que lo importes veinte veces.

¿Por qué un __init__.py que re-exporta medio paquete puede volverse un problema?

Porque convierte al __init__.py en una dependencia invisible: alguien escribe from mi_paquete import Cosa sin saber de qué archivo sale Cosa. El día que borrás o renombrás ese archivo, un grep por from mi_paquete.modulo_x import no encuentra nada y parece que no lo usa nadie... hasta que rompés a todos los que importaban desde el paquete. Además, todo lo que el __init__.py importa se ejecuta apenas tocás cualquier parte del paquete, lo que encarece el arranque y multiplica las chances de import circular.

¿Por qué cada proyecto necesita su propio venv en vez de instalar todo en el Python del sistema?

Porque las dependencias entran en conflicto: el proyecto A necesita pandas 1.5 y el B pandas 2.1, y en un único entorno global solo puede ganar uno. El venv le da a cada proyecto su propio site-packages, con lo cual además podés congelar versiones exactas con pip freeze y que otra persona reproduzca tu entorno, no una mezcla imposible de repetir. Beneficio extra: si algo se pudre, borrás la carpeta .venv y volvés a empezar sin tocar el Python del sistema.

🧠 Autoevaluación rápida

Respondé sin mirar arriba. Cada pregunta te explica el porqué.

1. ¿Qué vale __name__ en un archivo que corrés directamente con python script.py?

Por eso el idiom if __name__ == "__main__": ejecuta main() solo al correrlo, y no cuando otro módulo lo importa. Al importarlo, __name__ pasa a ser el nombre del módulo.

2. ¿Qué convierte a un directorio en un paquete importable?

El __init__.py marca el directorio como paquete y se ejecuta al importarlo: ahí se re-exportan símbolos y se define __all__.

3. ¿Qué hace pip freeze > requirements.txt?

freeze vuelca el estado actual del entorno usando ==. Para instalar desde el archivo el comando es pip install -r requirements.txt.

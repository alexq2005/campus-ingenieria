PS4 — El modelo de datos: descriptors y metaclases

PS4.0 Por qué este módulo

En PS1 viste que todo valor es un PyObject con un puntero a su tipo. Este módulo es la continuación natural: qué le pregunta el intérprete a ese tipo cuando escribís len(x), x[3], a == b, with x: o simplemente x.campo.

💡 La tesis del módulo. Python no tiene "tipos privilegiados". list, dict y str no reciben trato especial del intérprete: solo implementan bien un conjunto de métodos con nombres acordados. Ese conjunto de nombres es el modelo de datos, y es un contrato público. Si tu objeto lo implementa, funciona con for, con in, con sorted(), con with y con cualquier librería de terceros que nunca oyó hablar de tu clase.

La consecuencia práctica es doble. La primera es de diseño: escribir un objeto que se siente nativo es cuestión de elegir qué protocolos implementar, no de heredar de nada. La segunda es de supervivencia: cuando abrís un framework serio —Django, SQLAlchemy, Pydantic, dataclasses— y ves clases que "mágicamente" saben cosas de sí mismas, lo que estás viendo son descriptors y metaclases. Sin este módulo, ese código es magia. Con este módulo, es mecánica.

Advertencia de tono. Esta es la caja de herramientas más peligrosa del lenguaje. Todo lo que ves acá se puede usar para escribir código elegantísimo que nadie de tu equipo va a poder debuggear un martes a las 3 de la mañana. La sección PS4.10 no es un apéndice: es la mitad del módulo.

PS4.1 Los protocolos: el catálogo

Un protocolo del modelo de datos es un grupo de métodos especiales (los dunder, __x__) que habilitan una sintaxis. No se declaran, no se registran: se implementan y listo.

Contexto__enter__, __exit__with x: — adquirir y liberar de forma garantizada

La demostración canónica de por qué esto importa: dos métodos y el objeto ya se comporta como una secuencia de la biblioteca estándar.

import random
from collections import namedtuple

Carta = namedtuple("Carta", "valor palo")

class Baraja:
    palos = "espadas bastos oros copas".split()
    valores = [str(n) for n in range(1, 8)] + ["sota", "caballo", "rey"]

    def __init__(self):
        self._cartas = [Carta(v, p) for p in self.palos for v in self.valores]

    def __len__(self):
        return len(self._cartas)

    def __getitem__(self, pos):
        return self._cartas[pos]     # delegar en la lista: el slicing viene gratis

b = Baraja()
len(b)                  # 40
b[0]                    # Carta(valor='1', palo='espadas')
b[:3]                   # slicing: list.__getitem__ ya lo resuelve
random.choice(b)        # funciona: random usa len() + indexación
Carta("rey", "oros") in b   # True — __contains__ cae de vuelta al escaneo secuencial
for carta in b: ...     # itera: sin __iter__, Python usa el protocolo VIEJO de secuencia
sorted(b, key=lambda c: c.palo)
Ese último punto es un detalle que casi nadie sabe: si una clase no define __iter__ pero sí __getitem__, iter() fabrica un iterador legacy que llama obj[0], obj[1], … hasta que salte IndexError. Es compatibilidad hacia atrás con Python 1.x que sigue viva. Funciona, pero no la uses a propósito: es más lenta, no soporta índices no enteros y confunde a quien lea el código.

Los métodos especiales se buscan en el TIPO, no en la instancia

Esta es la regla que explica el 90% de las sorpresas del modelo de datos, y es una optimización deliberada de CPython: las invocaciones implícitas de dunders saltean __getattribute__ y el __dict__ de la instancia, y van directo a la ranura (slot) del tipo.

class Raro:
    def __init__(self):
        self.__len__ = lambda: 42        # asignado en la INSTANCIA

r = Raro()
r.__len__()      # 42  — llamada explícita: sí encuentra el atributo de instancia
len(r)           # TypeError: object of type 'Raro' has no len()

# La versión que sí funciona: el método vive en el TIPO
Raro.__len__ = lambda self: 42
len(r)           # 42  — y afecta a todas las instancias, incluso las ya creadas
📌 Corolario que se cobra caro: un objeto proxy que implemente __getattr__ para reenviar todo a otro objeto no reenvía los dunders. Tu proxy va a fallar en len(), in, with, == y repr() aunque el __getattr__ esté perfecto. Por eso los proxies serios declaran explícitamente cada dunder que quieren delegar.

PS4.2 __eq__ y __hash__: la regla de oro

El error clásico. Definís igualdad por valor, todo anda bien, y el día que metés el objeto en un set explota:

class Punto:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __eq__(self, otro):
        if not isinstance(otro, Punto):
            return NotImplemented          # que Python pruebe la operación reflejada
        return (self.x, self.y) == (otro.x, otro.y)

Punto(1, 2) == Punto(1, 2)     # True
{Punto(1, 2)}                  # TypeError: unhashable type: 'Punto'
{Punto(1, 2): "origen"}        # TypeError: idem

Punto.__hash__                 # None   ← acá está la explicación
💡 Por qué pasa. Todo objeto hereda de object un __hash__ basado en su identidad. Ese hash es consistente con la igualdad por defecto (que también es identidad). Cuando redefinís __eq__, esa consistencia se rompería en silencio: dos puntos iguales tendrían hashes distintos y el set guardaría duplicados. Python prefiere romper ruidosamente, así que al definir __eq__ pone __hash__ = None automáticamente.
📌 El invariante, que no es opcional: si a == b, entonces hash(a) == hash(b). La recíproca no hace falta (dos objetos distintos pueden colisionar). Y ambos deben calcularse sobre los mismos campos, que además tienen que ser inmutables mientras el objeto viva en un set o dict. 
# Opción 1 — a mano, sobre los MISMOS campos que usa __eq__
class Punto:
    __slots__ = ("x", "y")

    def __init__(self, x, y):
        self.x, self.y = x, y

    def __eq__(self, otro):
        if not isinstance(otro, Punto):
            return NotImplemented
        return (self.x, self.y) == (otro.x, otro.y)

    def __hash__(self):
        return hash((self.x, self.y))      # misma tupla que en __eq__

    def __repr__(self):
        return f"Punto({self.x}, {self.y})"

# Opción 2 — la que deberías usar el 95% de las veces
from dataclasses import dataclass

@dataclass(frozen=True, slots=True)
class Punto:
    x: float
    y: float
    # eq=True por defecto; frozen=True hace que se genere __hash__ coherente
Configuración de @dataclass__hash__ resultanteCuándo
eq=True (por defecto), frozen=FalseNone — no hasheableEntidad mutable: un registro que vas a editar
eq=True, frozen=TrueGenerado a partir de los camposValue object: coordenada, dinero, ID compuesto

La trampa mortal: hashear sobre campos mutables. Si metés un objeto en un set y después mutás un campo que participa del hash, el objeto queda huérfano: sigue adentro de la tabla, ocupando memoria, pero en el bucket equivocado. obj in mi_set devuelve False aunque el objeto esté ahí, y mi_set.remove(obj) tira KeyError. No hay excepción, no hay warning: es corrupción silenciosa de una estructura de datos. 
@dataclass(unsafe_hash=True)     # mutable + hasheable = bomba de tiempo
class Etiqueta:
    nombre: str

e = Etiqueta("urgente")
s = {e}
e.nombre = "normal"      # mutamos un campo que participa del hash
e in s                   # False  (!!) — el objeto está adentro, pero en otro bucket
s.remove(e)              # KeyError: Etiqueta(nombre='normal')
list(s)                  # [Etiqueta(nombre='normal')] — ahí está, inalcanzable

PS4.3 El acceso a atributos, paso a paso

Antes de los descriptors hay que ver el algoritmo que los usa. Cuando escribís obj.x, esto es lo que pasa realmente:

obj.x
  │
  ▼
type(obj).__getattribute__(obj, "x")     ← TODO acceso con punto entra por acá
  │
  ├─ 1. Buscar "x" recorriendo type(obj).__mro__  →  lo llamamos attr_cls
  │
  ├─ 2. ¿attr_cls define __set__ o __delete__?
  │        SÍ → DESCRIPTOR DE DATOS
  │             return attr_cls.__get__(obj, type(obj))        ★ GANA SIEMPRE
  │
  ├─ 3. ¿"x" está en obj.__dict__?
  │        SÍ → return obj.__dict__["x"]                        ← el caso común
  │
  ├─ 4. ¿attr_cls define solo __get__?
  │        SÍ → descriptor de NO-DATOS (funciones, classmethod…)
  │             return attr_cls.__get__(obj, type(obj))
  │
  ├─ 5. ¿attr_cls existe y es un valor común?
  │        SÍ → return attr_cls                                 ← atributo de clase
  │
  └─ 6. AttributeError
           │
           └→ ¿type(obj) define __getattr__?
                    SÍ → type(obj).__getattr__(obj, "x")        ← último recurso
                    NO → propagar el AttributeError

Tres consecuencias que hay que tener grabadas:

1. Descriptor de datos > instancia > descriptor de no-datos. Ese orden es todo. Un descriptor con __set__ no puede ser tapado por un atributo de instancia; uno que solo tiene __get__, sí.
2. __getattr__ ≠ __getattribute__. El primero es un fallback: se llama solo cuando la búsqueda normal fracasó. El segundo intercepta todos los accesos, incluso los que existen — es potentísimo y es la forma más fácil de escribir una recursión infinita.
3. Los dunders implícitos no pasan por acá (PS4.1). len(obj) mira la ranura del tipo directamente, sin tocar __getattribute__.
class Log:
    def __getattribute__(self, nombre):
        print(f"acceso a {nombre}")
        # ⛔ return self.__dict__[nombre]  →  self.__dict__ vuelve a entrar acá: RecursionError
        return object.__getattribute__(self, nombre)      # ✅ la salida correcta

class Perezoso:
    """__getattr__ solo se dispara si el atributo NO existe: costo cero en el caso normal."""
    def __getattr__(self, nombre):
        if nombre == "conexion":
            print("abriendo conexión (una sola vez)")
            self.conexion = "conn-abierta"   # queda en __dict__ → nunca más pasa por acá
            return self.conexion
        raise AttributeError(nombre)         # ¡obligatorio! si no, todo objeto tiene todo
Un __getattr__ que no levanta AttributeError para los nombres desconocidos rompe hasattr(), copy, pickle, unittest.mock y los autocompletados del IDE — todos ellos preguntan por atributos como __deepcopy__, __getstate__ o __wrapped__ y esperan que fallen.

PS4.4 Descriptors: el mecanismo debajo de todo

Un descriptor es, simplemente, un objeto que define __get__, __set__ o __delete__ y vive como atributo de una clase. No hereda de nada ni se registra en ningún lado.

MétodoFirmaCuándo lo llama Python
__get__(self, obj, objtype=None)Al leer. obj es None si se accede desde la clase
__set__(self, obj, value)Al asignar. Su sola presencia lo convierte en descriptor de datos
__delete__(self, obj)En del obj.attr. También lo hace de datos
__set_name__(self, owner, name)Una vez, al crear la clase: le avisa cómo se llama. PEP 487
Pensalo como un middleware para un atributo. Sin descriptor, obj.edad es una consulta a un diccionario. Con descriptor, es una llamada a función que vos controlás: podés validar, cachear, loguear, convertir tipos o traer el dato de una base — sin que quien escribe obj.edad se entere de nada.

property es un descriptor, y podés escribirlo vos

La mejor forma de convencerse es reimplementarlo. Son 25 líneas y no hay nada mágico adentro:

class Propiedad:
    """Un clon funcional de property(). Sí: property es solo esto, escrito en C."""

    def __init__(self, fget=None, fset=None, fdel=None, doc=None):
        self.fget, self.fset, self.fdel = fget, fset, fdel
        self.__doc__ = doc or getattr(fget, "__doc__", None)
        self._nombre = ""

    def __set_name__(self, owner, name):
        self._nombre = name

    def __get__(self, obj, objtype=None):
        if obj is None:
            return self                     # Clase.prop → el descriptor mismo
        if self.fget is None:
            raise AttributeError(f"la propiedad {self._nombre!r} no tiene getter")
        return self.fget(obj)

    def __set__(self, obj, value):          # ← definirlo (aunque fset sea None) lo hace de DATOS
        if self.fset is None:
            raise AttributeError(f"la propiedad {self._nombre!r} es de solo lectura")
        self.fset(obj, value)

    def __delete__(self, obj):
        if self.fdel is None:
            raise AttributeError(f"la propiedad {self._nombre!r} no se puede borrar")
        self.fdel(obj)

    # los decoradores encadenados devuelven un descriptor NUEVO, no mutan el actual
    def getter(self, fget):  return type(self)(fget, self.fset, self.fdel, self.__doc__)
    def setter(self, fset):  return type(self)(self.fget, fset, self.fdel, self.__doc__)
    def deleter(self, fdel): return type(self)(self.fget, self.fset, fdel, self.__doc__)
class Rectangulo:
    def __init__(self, ancho, alto):
        self.ancho, self.alto = ancho, alto

    @Propiedad                       # exactamente la misma sintaxis que @property
    def area(self):
        """Calculada, nunca almacenada."""
        return self.ancho * self.alto

r = Rectangulo(3, 4)
r.area              # 12
r.area = 99         # AttributeError: la propiedad 'area' es de solo lectura
r.__dict__          # {'ancho': 3, 'alto': 4}  — 'area' NO está: no es un dato guardado
📌 Acá se ve por qué el orden de PS4.3 importa. Propiedad define __set__ aunque no tenga setter, así que es un descriptor de datos y gana sobre obj.__dict__. Por eso una propiedad de solo lectura es realmente de solo lectura: ni siquiera r.__dict__["area"] = 99 logra taparla. Si Propiedad solo tuviera __get__, cualquier asignación la sepultaría para siempre en esa instancia.

El caso real: un validador reutilizable

Las property no escalan cuando tenés doce campos con la misma validación: terminás copiando doce getters y doce setters idénticos. El descriptor te deja escribir la regla una vez.

from abc import ABC, abstractmethod

class Validado(ABC):
    """Descriptor de datos: valida en cada asignación y guarda en el __dict__ del objeto."""

    def __set_name__(self, owner, name):
        self.nombre = name                       # 'edad', 'apellido', …

    def __get__(self, obj, objtype=None):
        if obj is None:
            return self
        try:
            return obj.__dict__[self.nombre]
        except KeyError:
            raise AttributeError(
                f"{type(obj).__name__}.{self.nombre} no fue asignado todavía"
            ) from None

    def __set__(self, obj, value):
        obj.__dict__[self.nombre] = self.validar(value)   # guardar el valor YA validado

    @abstractmethod
    def validar(self, value):
        """Devuelve el valor normalizado o levanta ValueError/TypeError."""


class Entero(Validado):
    def __init__(self, *, minimo=None, maximo=None):
        self.minimo, self.maximo = minimo, maximo

    def validar(self, value):
        if not isinstance(value, int) or isinstance(value, bool):
            raise TypeError(f"{self.nombre} debe ser int, llegó {type(value).__name__}")
        if self.minimo is not None and value < self.minimo:
            raise ValueError(f"{self.nombre} debe ser >= {self.minimo}, llegó {value}")
        if self.maximo is not None and value > self.maximo:
            raise ValueError(f"{self.nombre} debe ser <= {self.maximo}, llegó {value}")
        return value


class Texto(Validado):
    def __init__(self, *, largo_max=None, opciones=None):
        self.largo_max, self.opciones = largo_max, opciones

    def validar(self, value):
        if not isinstance(value, str):
            raise TypeError(f"{self.nombre} debe ser str")
        value = value.strip()
        if self.largo_max is not None and len(value) > self.largo_max:
            raise ValueError(f"{self.nombre}: máximo {self.largo_max} caracteres")
        if self.opciones is not None and value not in self.opciones:
            raise ValueError(f"{self.nombre} debe ser uno de {sorted(self.opciones)}")
        return value
class Empleado:
    nombre  = Texto(largo_max=60)
    edad    = Entero(minimo=18, maximo=99)
    turno   = Texto(opciones={"mañana", "tarde", "noche"})

    def __init__(self, nombre, edad, turno):
        self.nombre, self.edad, self.turno = nombre, edad, turno

e = Empleado("  Ana  ", 34, "tarde")
e.nombre            # 'Ana'  — el validador normalizó (strip) al asignar
e.__dict__          # {'nombre': 'Ana', 'edad': 34, 'turno': 'tarde'}

Empleado("Ana", 12, "tarde")    # ValueError: edad debe ser >= 18, llegó 12
e.edad = True                   # TypeError: edad debe ser int, llegó bool
e.turno = "madrugada"           # ValueError: turno debe ser uno de ['mañana',…]
Dos detalles que separan un descriptor correcto de uno roto. (1) Guardar en obj.__dict__[self.nombre] con el mismo nombre no genera recursión, justamente porque el descriptor de datos tiene prioridad sobre el __dict__: las lecturas nunca lo encuentran solas. (2) El estado va en obj, nunca en self: el descriptor es uno solo compartido por todas las instancias de la clase. Un self.valor = value ahí adentro hace que las mil instancias de Empleado compartan la misma edad — y es un bug que en tests con una sola instancia no aparece.

PS4.5 Los métodos también son descriptors

Nunca te preguntaste de dónde sale el self. La respuesta es que las funciones son descriptors de no-datos: definen __get__ y nada más.

def saludar(self):
    return f"hola desde {self}"

saludar.__get__                 # <method-wrapper '__get__' of function object>

class C:
    metodo = saludar

c = C()
C.metodo                        # la función pelada (Python 3)
c.metodo                        # <bound method saludar of <C object…>>
c.metodo.__self__ is c          # True — el binding es literalmente esto:
saludar.__get__(c, C)           # el mismo bound method, hecho a mano

# Y como las funciones son descriptors de NO-datos, la instancia les gana:
c.metodo = lambda: "yo mando"
c.metodo()                      # 'yo mando'  — el __dict__ tapó al método (paso 3 > paso 4)
💡 Todo el sistema de métodos de Python es una aplicación del protocolo de descriptors. Un bound method es un objeto creado al vuelo por function.__get__, que guarda __func__ y __self__ y al llamarse inserta el self como primer argumento. staticmethod y classmethod son descriptors también: el primero devuelve la función sin tocar, el segundo la liga a la clase en vez de a la instancia. No hay una regla especial del intérprete: hay tres descriptors. 
class D:
    @staticmethod
    def estatico(): return "sin self ni cls"

    @classmethod
    def declase(cls): return f"cls={cls.__name__}"

vars(D)["estatico"]     # <staticmethod object>  — el descriptor crudo
vars(D)["declase"]      # <classmethod object>
D.estatico              # la función pelada: staticmethod.__get__ la devuelve tal cual
D().declase()           # 'cls=D' — classmethod.__get__ liga cls, venga de instancia o de clase
Desde 3.10 los objetos staticmethod son invocables directamente (antes había que sacarlos del __dict__ con .__func__). Y ojo con un cambio que rompe código viejo: encadenar @classmethod sobre @property —un truco popular en 3.9–3.10 para hacer "propiedades de clase"— quedó deprecado en 3.11 y eliminado en 3.13. En 3.14 no funciona: si necesitás una propiedad de clase, escribí un descriptor propio cuyo __get__ use el parámetro objtype.

PS4.6 __slots__, dataclasses y su choque con los descriptors

__slots__ no es una anotación de tipos ni una optimización opaca: le pide al constructor de clases que genere un descriptor de datos por cada nombre y que no cree __dict__. Es, otra vez, el mismo mecanismo.

class Punto:
    __slots__ = ("x", "y")
    def __init__(self, x, y): self.x, self.y = x, y

type(vars(Punto)["x"])      # <class 'member_descriptor'>  ← un descriptor de datos en C
vars(Punto)["x"].__get__    # tiene __get__ y __set__: por eso las asignaciones funcionan

p = Punto(1, 2)
p.__dict__                  # AttributeError: 'Punto' object has no attribute '__dict__'
p.z = 3                     # AttributeError: 'Punto' object has no attribute 'z'
Qué ganásQué perdés
Memoria: sin __dict__, típicamente 40–50% menos por instanciaNo podés agregar atributos dinámicos (a veces eso es lo que querés)
Acceso algo más rápido: offset fijo en vez de hash de diccionario__weakref__ hay que pedirlo explícitamente en __slots__
Detecta typos: p.nomrbe = "x" falla en vez de crear un campo fantasmaHerencia frágil: si cualquier base no tiene __slots__, vuelve el __dict__

La interacción con descriptors: el conflicto de nombres

class Roto:
    __slots__ = ("edad",)
    edad = Entero(minimo=0)      # ValueError al CREAR la clase:
                                 # 'edad' in __slots__ conflicts with class variable

Es coherente: el slot y el descriptor quieren ocupar el mismo casillero del __dict__ de la clase. Y hay un segundo problema, más callado: nuestro Validado guarda en obj.__dict__, que con __slots__ no existe. La solución estándar es que el descriptor use un slot privado con otro nombre:

class ValidadoSlots(Validado):
    def __set_name__(self, owner, name):
        self.nombre = name
        self.privado = "_slot_" + name        # el casillero real

    def __get__(self, obj, objtype=None):
        if obj is None: return self
        return getattr(obj, self.privado)     # lee el slot, no el __dict__

    def __set__(self, obj, value):
        setattr(obj, self.privado, self.validar(value))

class Persona:
    __slots__ = ("_slot_edad",)               # el slot se llama distinto del atributo
    edad = Entero.__new__(Entero)             # (en la práctica: class Edad(ValidadoSlots))

@dataclass(slots=True): la letra chica

from dataclasses import dataclass, field

@dataclass(slots=True, frozen=True)
class Medicion:
    sensor: str
    valor: float
    etiquetas: tuple[str, ...] = ()
⚠️ slots=True no agrega slots: construye una CLASE NUEVA. __slots__ tiene que estar presente antes de que el tipo se cree, y un decorador corre después. Entonces dataclasses arma un segundo objeto-clase y lo devuelve en lugar del original. Todo lo que haya capturado una referencia a la clase original antes del decorador —un registro global poblado en __init_subclass__, otro decorador aplicado más abajo, un weakref, un isinstance contra la referencia vieja— sigue apuntando a una clase que ya no es la que usa nadie. El super() sin argumentos sí fue arreglado (CPython repara la celda __class__ desde 3.12), pero el problema de identidad no tiene arreglo posible.
Dataclasses y descriptors sí se llevan bien. Si el default de un campo es un descriptor, dataclasses lo respeta: se le llama __set_name__ como a cualquier atributo de clase, y el valor por defecto que usa el __init__ generado se obtiene invocando descriptor.__get__(None, cls). Es la vía oficial para combinar validación con dataclasses sin escribir un __post_init__ gigante. Con slots=True, recordá que la clase se crea dos veces: __set_name__ corre dos veces, así que ese método debe ser idempotente y no tocar estado global.

PS4.7 Metaclases: la clase de una clase

Si las instancias son creadas por su clase, ¿quién crea a las clases? Otra clase. Esa es toda la idea.

class C: pass

type(C())          # <class '__main__.C'>   — la clase de la instancia
type(C)            # <class 'type'>         — la clase de la clase = su METACLASE
type(type)         # <class 'type'>         — el punto fijo: type se crea a sí mismo

# Una sentencia class es azúcar sobre una llamada a type con tres argumentos:
D = type("D", (object,), {"saludar": lambda self: "hola", "version": 3})
D().saludar()      # 'hola'

El protocolo completo que ejecuta __build_class__ cuando ve una sentencia class:

class Usuario(Modelo, tabla="usuarios"):
    nombre = Campo(str)

 1. Determinar la metaclase (la de las bases, o el keyword metaclass=)
 2. ns = metacls.__prepare__("Usuario", bases, tabla="usuarios")   → un mapeo vacío
 3. Ejecutar el CUERPO de la clase dentro de ns  → ns["nombre"] = Campo(str)
 4. cls = metacls.__new__(metacls, "Usuario", bases, ns, tabla="usuarios")
        └─ type.__new__ hace además, en este orden:
              a) llamar __set_name__(cls, nombre) en cada objeto de ns que lo tenga
              b) llamar Modelo.__init_subclass__(cls, tabla="usuarios")
 5. metacls.__init__(cls, ...)
 6. Ligar el nombre "Usuario" en el módulo
class RegistroMeta(type):
    """Lleva un registro de todas las subclases y prohíbe métodos duplicados."""
    registro: dict[str, type] = {}

    @classmethod
    def __prepare__(mcls, nombre, bases, **kw):
        return DetectorDeDuplicados()          # ← lo único que SOLO una metaclase puede hacer

    def __new__(mcls, nombre, bases, ns, *, abstracta=False, **kw):
        cls = super().__new__(mcls, nombre, bases, dict(ns), **kw)
        if not abstracta:
            mcls.registro[nombre.lower()] = cls
        return cls

    def __repr__(cls):                          # 'self' acá es la CLASE, no la instancia
        return f"<modelo {cls.__name__}>"

class DetectorDeDuplicados(dict):
    def __setitem__(self, k, v):
        if k in self:
            raise TypeError(f"'{k}' está definido dos veces en el cuerpo de la clase")
        super().__setitem__(k, v)
📌 Lo único que solo una metaclase puede hacer: (1) __prepare__, o sea controlar el mapeo donde se ejecuta el cuerpo de la clase — así enum detecta miembros duplicados y así se preservaba el orden antes de 3.7; (2) cambiar las bases o devolver algo que no es la clase pedida; (3) personalizar isinstance/issubclass con __instancecheck__ (es lo que hace abc.ABCMeta); (4) definir comportamiento de la clase como objeto: su __repr__, su __call__, su __getattr__, su iteración (for miembro in MiEnum). Todo lo demás que se hace con metaclases se puede hacer más simple.
⚠️ El conflicto de metaclases: el costo que nadie calcula. Una clase solo puede tener una metaclase, y tiene que ser subclase de las metaclases de todas sus bases. En cuanto tu RegistroMeta existe, nadie puede escribir class X(TuModelo, abc.ABC), ni combinarlo con Protocol, ni con un modelo de Django, ni con Generic en según qué versiones. El error es TypeError: metaclass conflict: the metaclass of a derived class must be a (non-strict) subclass of the metaclasses of all its bases, aparece meses después, en el código de otro, y la única salida es fabricar una metaclase combinada. Una metaclase no es una decisión local: es un impuesto sobre todo el árbol de herencia, para siempre. 
import abc

class MiMeta(type): pass
class Base(metaclass=MiMeta): pass

class Hijo(Base, abc.ABC): ...     # TypeError: metaclass conflict

class MetaCombinada(MiMeta, abc.ABCMeta): pass    # el "arreglo": más metaclases
class Hijo(Base, abc.ABC, metaclass=MetaCombinada): ...   # ahora sí, y así crece la bola

PS4.8 __init_subclass__: el 90% de las metaclases, sin metaclase

PEP 487 —el mismo que trajo __set_name__— agregó un gancho que cubre el caso de uso dominante: "quiero que pase algo cada vez que alguien hereda de mi clase". Es un classmethod implícito que recibe la subclase recién creada.

class Plugin:
    registro: dict[str, type] = {}

    def __init_subclass__(cls, /, nombre=None, abstracto=False, **kw):
        super().__init_subclass__(**kw)          # ← obligatorio: cooperación en el MRO
        if abstracto:
            return
        cls.nombre = nombre or cls.__name__.lower()
        if cls.nombre in Plugin.registro:
            raise TypeError(f"plugin duplicado: {cls.nombre!r}")
        Plugin.registro[cls.nombre] = cls

class ExportadorCSV(Plugin, nombre="csv"):       # los kwargs de la sentencia class llegan acá
    def exportar(self, filas): ...

class ExportadorJSON(Plugin):                     # sin nombre → 'exportadorjson'
    def exportar(self, filas): ...

Plugin.registro          # {'csv': ExportadorCSV, 'exportadorjson': ExportadorJSON}
type(ExportadorCSV)      # <class 'type'>  ← metaclase normal: se combina con TODO
Dos detalles operativos. (1) __init_subclass__ no corre para la clase que lo define, solo para sus descendientes — por eso Plugin.registro se inicializa a mano. (2) Cuando corre, los __set_name__ de todos los descriptors del cuerpo ya se ejecutaron (paso 4a de PS4.7), así que podés inspeccionar los descriptors sabiendo que ya conocen su nombre. Ese orden es lo que hace viable el mini-ORM del worked example.

PS4.9 contextlib: el protocolo de contexto sin escribir clases

El protocolo __enter__/__exit__ es el que más veces vas a implementar, y casi nunca hace falta una clase para eso.

from contextlib import contextmanager
import time, logging

@contextmanager
def cronometrar(etiqueta):
    t0 = time.perf_counter()
    try:                                   # ⚠️ el try/finally NO es opcional
        yield                              # todo lo de antes = __enter__; lo de después = __exit__
    finally:
        logging.info("%s tardó %.3fs", etiqueta, time.perf_counter() - t0)

with cronometrar("consulta pesada"):
    hacer_la_consulta()                    # aunque esto explote, el log se escribe
El bug del @contextmanager sin try/finally. Si el bloque with levanta una excepción, Python la inyecta dentro del generador en el punto del yield. Sin try/finally, el generador muere ahí y el código de limpieza posterior al yield nunca corre: la conexión queda abierta, el lock tomado, el archivo temporal en disco. Y como el camino feliz sí funciona, los tests pasan. 
from contextlib import ExitStack, suppress, closing, nullcontext

# 1. ExitStack — N contextos decididos en runtime, cerrados en orden inverso
def procesar(rutas):
    with ExitStack() as stack:
        archivos = [stack.enter_context(open(r, encoding="utf-8")) for r in rutas]
        # si el archivo 7 de 10 falla al abrir, los 6 anteriores se cierran igual
        return combinar(archivos)

# 2. ExitStack como "rollback": registrar deshacer a medida que se avanza
def desplegar(servicios):
    with ExitStack() as stack:
        for s in servicios:
            s.arrancar()
            stack.callback(s.parar)        # si algo falla más adelante, se para todo
        verificar_salud(servicios)
        stack.pop_all()                    # ✅ todo OK: renunciamos al rollback

# 3. suppress — reemplaza el try/except/pass, y dice explícitamente qué ignora
with suppress(FileNotFoundError):
    Path("cache.tmp").unlink()

# 4. nullcontext — un with condicional sin duplicar el bloque
ctx = abrir_transaccion() if usar_tx else nullcontext()
with ctx:
    guardar(datos)

# 5. closing — para objetos con .close() que no implementan el protocolo
with closing(urlopen(url)) as respuesta:
    cuerpo = respuesta.read()
Un context manager hecho con @contextmanager es de un solo uso: el generador se agota. Si necesitás reentrancia o reutilización, heredá de contextlib.ContextDecorator o escribí la clase. Y para el mundo async de PS3 existen los espejos exactos: @asynccontextmanager y AsyncExitStack, con la misma semántica.

PS4.10 Cuándo NO usar nada de esto

Todo lo anterior comparte una propiedad incómoda: hace que el comportamiento del código no esté donde se lo lee. Quien lee usuario.edad = -5 ve una asignación. Que en realidad sea una llamada a un validador definido en otro archivo, en una clase base, es información que no está en la pantalla.

💡 El criterio. Estas herramientas cambian dónde vive la complejidad, no cuánta hay. Se justifican cuando la magia se escribe una vez y se consume muchas veces: cien clases con validación declarativa contra un descriptor de treinta líneas es un negocio excelente. Un descriptor de treinta líneas para dos atributos de una clase es una deuda que va a pagar otro.

🧑‍🎓 Worked Example — un mini-ORM declarativo

Objetivo: que el usuario de nuestra librería escriba class Usuario(Modelo): nombre = Campo(str) y obtenga gratis __init__ con validación de tipos, __repr__, el nombre de la tabla y un INSERT. Es el caso de uso histórico de las metaclases. Vamos a construirlo dos veces y a elegir.

Paso 1 — La pieza que no cambia: el descriptor Campo. Independientemente de cómo construyamos la clase, cada atributo necesita saber su nombre, su tipo y cómo validarse. Eso es un descriptor de datos, tal cual PS4.4:

class Campo:
    """Descriptor de datos: un atributo tipado, validado y con nombre de columna."""

    def __init__(self, tipo, *, requerido=True, default=None, columna=None):
        self.tipo, self.requerido, self.default = tipo, requerido, default
        self.columna = columna

    def __set_name__(self, owner, name):        # lo llama type.__new__, gratis
        self.nombre = name
        self.columna = self.columna or name

    def __get__(self, obj, objtype=None):
        if obj is None:
            return self                          # Usuario.nombre → el Campo (lo usa el SQL)
        return obj.__dict__.get(self.nombre, self.default)

    def __set__(self, obj, value):
        if value is None:
            if self.requerido:
                raise ValueError(f"{self.nombre} es obligatorio")
        elif not isinstance(value, self.tipo):
            raise TypeError(
                f"{self.nombre} debe ser {self.tipo.__name__}, "
                f"llegó {type(value).__name__}"
            )
        obj.__dict__[self.nombre] = value

    def __repr__(self):
        return f"Campo({self.tipo.__name__}, columna={self.columna!r})"

Paso 2 — Versión A: con metaclase. Es como está escrito Django y como estaba escrito SQLAlchemy clásico.

class ModeloMeta(type):
    def __new__(mcls, nombre, bases, ns, *, tabla=None, **kw):
        cls = super().__new__(mcls, nombre, bases, ns, **kw)
        # recorrer el MRO al revés para que las subclases pisen a las bases
        cls._campos = {
            k: v
            for klass in reversed(cls.__mro__)
            for k, v in vars(klass).items()
            if isinstance(v, Campo)
        }
        cls._tabla = tabla or nombre.lower()
        return cls

    def __repr__(cls):
        return f"<Modelo {cls.__name__}({', '.join(cls._campos)})>"

class Modelo(metaclass=ModeloMeta):
    def __init__(self, **kw):
        faltantes = set(kw) - set(self._campos)
        if faltantes:
            raise TypeError(f"campos desconocidos: {sorted(faltantes)}")
        for nombre, campo in self._campos.items():
            setattr(self, nombre, kw.get(nombre, campo.default))   # pasa por Campo.__set__
Dos bugs que aparecen solos si escribís esto rápido. (1) Juntar los campos con ns en vez del __mro__ hace que las subclases pierdan los campos heredados — clásico, y se descubre en producción. (2) Si __set_name__ no corriera antes, campo.nombre no existiría todavía; funciona porque super().__new__ (o sea type.__new__) lo dispara durante la creación. Ese orden hay que conocerlo, no deducirlo.

Paso 3 — Versión B: __init_subclass__ + descriptors. Misma API pública, sin metaclase:

class Modelo:
    _campos: dict[str, Campo] = {}
    _tabla: str = ""

    def __init_subclass__(cls, /, tabla=None, **kw):
        super().__init_subclass__(**kw)
        cls._tabla = tabla or cls.__name__.lower()
        cls._campos = {
            k: v
            for klass in reversed(cls.__mro__)
            for k, v in vars(klass).items()
            if isinstance(v, Campo)
        }

    def __init__(self, **kw):
        faltantes = set(kw) - set(self._campos)
        if faltantes:
            raise TypeError(f"campos desconocidos: {sorted(faltantes)}")
        for nombre, campo in self._campos.items():
            setattr(self, nombre, kw.get(nombre, campo.default))

    def __repr__(self):
        args = ", ".join(f"{k}={getattr(self, k)!r}" for k in self._campos)
        return f"{type(self).__name__}({args})"

    def insert(self):
        cols = ", ".join(c.columna for c in self._campos.values())
        marks = ", ".join("?" for _ in self._campos)
        valores = tuple(getattr(self, k) for k in self._campos)
        return f"INSERT INTO {self._tabla} ({cols}) VALUES ({marks})", valores
class Usuario(Modelo, tabla="usuarios"):
    nombre = Campo(str)
    edad   = Campo(int, requerido=False, default=0)
    email  = Campo(str, columna="correo_electronico")

class UsuarioPremium(Usuario, tabla="usuarios_premium"):
    descuento = Campo(float, requerido=False, default=0.0)

u                       # Usuario(nombre='Ana', edad=0, email='ana@ejemplo.com')

Checkpoint — ¿lo tenés claro?

Tenés un descriptor con __get__ y __set__, y en el __init__ hacés self.edad = 30. ¿Dónde termina el 30, y qué pasa si en vez de obj.__dict__ el descriptor guardara en self?

El 30 termina donde vos decidas dentro de __set__, porque la asignación no escribe en obj.__dict__ por su cuenta: al ser un descriptor de datos, __setattr__ se lo delega. El idioma correcto es obj.__dict__[self.nombre] = value, que funciona sin recursión precisamente porque los descriptors de datos tienen prioridad sobre el __dict__ en la lectura (paso 2 antes que paso 3 en PS4.3). Si en cambio guardaras en self.valor, estarías escribiendo en el descriptor, que es un único objeto compartido por todas las instancias de la clase: la última instancia creada le pisaría la edad a todas las demás. Es un bug que no aparece en tests con un solo objeto y se manifiesta bajo concurrencia o en un bucle.

Tu framework define una metaclase. Un usuario te reporta TypeError: metaclass conflict. ¿Qué le pasó y qué opciones tiene?

Intentó heredar de tu clase y de otra que también tiene metaclase propia —típicamente abc.ABC, un Protocol, un modelo de Django o de SQLAlchemy—. Python exige que la metaclase de la clase derivada sea subclase de las metaclases de todas sus bases, y ninguna de las dos lo es de la otra. Las opciones son: crear una metaclase combinada (class Combinada(TuMeta, ABCMeta): pass) y pasarla con metaclass=, lo cual funciona pero multiplica el problema; evitar la herencia múltiple usando composición; o —la solución de fondo— que el framework no use metaclase y resuelva lo mismo con __init_subclass__. Esta es exactamente la razón por la que en el worked example elegimos la versión B.

¿Por qué len(obj) puede fallar aunque obj.__len__() funcione perfecto?

Porque las invocaciones implícitas de métodos especiales se resuelven en el tipo, no en la instancia: len(obj) mira la ranura correspondiente de type(obj) y saltea __getattribute__ y el __dict__ de la instancia. Si el __len__ lo asignaste a la instancia (self.__len__ = ...), la llamada explícita obj.__len__() lo encuentra por la vía normal de atributos, pero len(obj) no. Es una optimización deliberada de CPython, y su consecuencia práctica más importante es que un proxy basado en __getattr__ no delega ningún dunder: hay que declararlos uno por uno.

Resumen ejecutivo

  • El modelo de datos es el contrato entre tus objetos y el intérprete: implementá los dunders del protocolo y tu clase se comporta como una nativa, sin heredar de nada.
  • Los dunders implícitos se buscan en el tipo, no en la instancia. Por eso los proxies con __getattr__ no delegan len(), with ni ==.
  • __eq__ pone __hash__ = None. Van juntos, sobre los mismos campos, y esos campos tienen que ser inmutables mientras el objeto viva en un set o dict. En la práctica: @dataclass(frozen=True).
  • El acceso a atributos tiene un orden fijo: descriptor de datos > __dict__ de la instancia > descriptor de no-datos > atributo de clase > __getattr__. Todo lo demás del módulo se deduce de ahí.
  • Un descriptor convierte un atributo en una llamada a función que vos controlás. property, los métodos, classmethod, staticmethod y __slots__ son todos aplicaciones del mismo protocolo.
  • El estado de un descriptor va en obj, nunca en self: el descriptor es único y compartido por todas las instancias.
  • @dataclass(slots=True) construye una clase nueva: cuidado con toda referencia capturada antes del decorador.
  • Una metaclase solo se justifica por __prepare__, __instancecheck__ o por customizar la clase como objeto. Todo lo demás lo hace __init_subclass__ sin el impuesto permanente del metaclass conflict.
  • contextlib te da el protocolo de contexto sin clases: @contextmanager (siempre con try/finally), ExitStack para N recursos y rollback, suppress para decir qué ignorás.
  • La magia se paga en debugging ajeno. Se justifica cuando se escribe una vez y se consume muchas; nunca para ahorrar diez líneas.

🧠 Autoevaluación

1. Una clase define x como descriptor con __get__ y __set__. Alguien hace obj.__dict__["x"] = 99 y después lee obj.x. ¿Qué obtiene?

El orden de __getattribute__ es: descriptor de datos, después obj.__dict__, después descriptor de no-datos. Como x define __set__, es de datos y se resuelve en el paso 2, antes de que el diccionario de la instancia entre en juego. Esa entrada del __dict__ queda inaccesible por atributo — y es exactamente el mecanismo que hace que una property de solo lectura sea realmente de solo lectura. Si el descriptor tuviera únicamente __get__, el resultado sería 99.

2. Agregás __eq__ a una clase que funcionaba bien y de golpe explota al meterla en un set. ¿Por qué?

El __hash__ heredado de object se basa en la identidad, y sería incoherente con una igualdad por valor: dos objetos iguales caerían en buckets distintos y el set guardaría duplicados. Python prefiere fallar ruidosamente y anula el hash. La corrección es definir __hash__ sobre los mismos campos que usa __eq__ —y asegurarse de que sean inmutables— o directamente usar @dataclass(frozen=True), que genera ambos de forma coherente.

3. Querés que todas las subclases de tu clase base se registren solas en un diccionario. ¿Cuál es la primera herramienta que probás?

El registro automático de subclases es el caso de uso número uno de las metaclases, y es justo el que PEP 487 resolvió sin ellas. __init_subclass__ recibe cada subclase recién creada (con los kwargs de la sentencia class, y con los __set_name__ ya ejecutados) y deja type(MiClase) is type, así que sigue componiendo con ABC, Protocol y cualquier framework de terceros. El decorador funciona pero no se hereda: cada subclase tendría que acordarse de decorarse. La metaclase se reserva para __prepare__, __instancecheck__ o customizar la clase como objeto.

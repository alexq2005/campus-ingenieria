PS3 — asyncio a fondo

PS3.0 Por qué: async no es "más rápido", es "más eficiente esperando"

La frase que arruina más código async del que arregla es "lo pasamos a async para que sea más rápido". No es lo que hace. Una función async ejecuta exactamente el mismo bytecode que su versión síncrona, y encima paga el costo del intérprete al suspender y reanudar. Si tu programa calcula números, pasarlo a asyncio lo hace más lento.

💡 La tesis del módulo. asyncio no acelera el trabajo: elimina el tiempo muerto. En un programa bloqueante, mientras esperás una respuesta HTTP de 200 ms, tu hilo está detenido sin hacer nada útil. asyncio te deja usar esos 200 ms para atender otras 500 conexiones. La ganancia no es de CPU, es de concurrencia por unidad de memoria: un hilo del sistema operativo cuesta megabytes de stack, una tarea de asyncio cuesta kilobytes.

De ahí se deduce todo lo demás. Si la ganancia viene de aprovechar la espera, cualquier cosa que no ceda el control mientras espera destruye el modelo entero. Y esa es, casi sin excepciones, la causa raíz de todos los bugs de asyncio que vas a ver en producción.

🍳 Un cocinero, muchas hornallas. Un cocinero bloqueante pone la olla al fuego y se queda mirándola veinte minutos. Un cocinero async pone la olla, pone un temporizador, y mientras tanto pica cebolla, atiende la puerta y arma tres platos más. No cocina más rápido: no se queda parado. Ahora imaginá que ese mismo cocinero decide pelar cien papas a mano en el medio del servicio: todos los temporizadores siguen sonando y nadie los atiende. Eso es bloquear el event loop.

PS3.1 El event loop por dentro

El event loop es un solo hilo que hace una sola cosa a la vez. No hay paralelismo, no hay preemción, no hay nada que te interrumpa: tu código corre hasta que vos decidís ceder el control. Esa propiedad es la que hace que asyncio sea razonable de auditar — y la que lo vuelve frágil ante una sola línea bloqueante.

El corazón está en BaseEventLoop._run_once(), en asyncio/base_events.py. Simplificado, cada vuelta hace esto:

                        ┌────────────────────────────────────┐
     ┌─────────────────►│ 1. ¿Hay callbacks pendientes        │
     │                  │    en la cola _ready?               │
     │                  └────────────────┬───────────────────┘
     │              sí │                 │ no
     │  timeout = 0    │                 │ timeout = próximo timer (o infinito)
     │                 ▼                 ▼
     │                  ┌────────────────────────────────────┐
     │                  │ 2. selector.select(timeout)        │  ← epoll / kqueue / IOCP
     │                  │    ***EL PROCESO DUERME ACÁ***     │     el SO despierta al
     │                  └────────────────┬───────────────────┘     llegar un byte
     │                                   ▼
     │                  ┌────────────────────────────────────┐
     │                  │ 3. los fds listos empujan sus       │
     │                  │    callbacks a la cola _ready       │
     │                  └────────────────┬───────────────────┘
     │                                   ▼
     │                  ┌────────────────────────────────────┐
     │                  │ 4. los timers vencidos (heap)       │
     │                  │    también van a _ready             │
     │                  └────────────────┬───────────────────┘
     │                                   ▼
     │                  ┌────────────────────────────────────┐
     │                  │ 5. ejecutar TODOS los callbacks     │
     │                  │    que había al empezar el paso 5   │
     │                  │  ──── acá corre TU código ────      │
     └──────────────────┴────────────────────────────────────┘

   Cada callback es, típicamente, Task.__step():
   llamar coro.send(None) y correr la corrutina hasta el próximo await
   que realmente suspenda. Si tu callback tarda 3 segundos,
   el paso 2 no vuelve a ejecutarse en 3 segundos. Nada.
📌 Todo el modelo se resume en el paso 5. El loop no puede atender I/O mientras corre tu callback, porque es el mismo hilo. La latencia de cada conexión de tu servidor es, literalmente, la suma de lo que tardan los callbacks de todas las demás. Por eso en asyncio la métrica que importa no es el throughput promedio: es la duración del callback más largo.

El paso 5 tiene un detalle fino que explica muchas cosas: el loop toma la longitud de _ready antes de empezar y solo corre esa cantidad. Los callbacks que se agreguen durante esa pasada esperan a la siguiente vuelta. Eso evita que una tarea que se re-programa a sí misma con call_soon mate de hambre al I/O — pero no te salva de un while True sin await.

PS3.2 Corrutinas: generadores con mejor ropa

Una corrutina no es magia ni un hilo liviano. Es un objeto con estado suspendible, exactamente igual que un generador. Compartir la maquinaria es literal: async def produce un objeto con send(), throw() y close().

async def sumar(a, b):
    return a + b

c = sumar(2, 3)
type(c)            # <class 'coroutine'>  — NO se ejecutó nada todavía
c.cr_frame         # tiene un frame, como un generador
c.cr_await         # None: no está esperando nada

# Lo corremos "a mano", sin event loop, como un generador:
try:
    c.send(None)   # arranca la corrutina
except StopIteration as fin:
    fin.value      # 5  <- el return de una corrutina viaja en StopIteration
Una corrutina que nunca se ejecuta emite RuntimeWarning: coroutine 'x' was never awaited. Es el warning más ignorado de Python y casi siempre significa que te olvidaste un await o un create_task. Tratalo como error: python -W error::RuntimeWarning, o filterwarnings = ["error::RuntimeWarning"] en tu configuración de pytest.

Qué hace realmente await

Acá está el malentendido más caro del módulo. await no lanza un hilo, no crea concurrencia y muchas veces ni siquiera cede el control. await significa: "delegá en este awaitable, y si él suspende, suspendo yo también". Es la versión con esteroides de yield from.

Se puede demostrar sin librerías. Un objeto es awaitable si define __await__ devolviendo un iterador — y lo que ese iterador hace es… yield:

class CedoElControl:
    """Lo que sale del yield sube hasta la Task, que se lo pasa al loop."""
    def __await__(self):
        valor_devuelto = yield "estoy suspendida, despertame vos"
        return valor_devuelto

async def tarea():
    print("antes")
    r = await CedoElControl()     # <-- acá el frame se congela
    print("después, recibí:", r)

c = tarea()
print(c.send(None))    # antes / 'estoy suspendida, despertame vos'
try:
    c.send("listo")    # después, recibí: listo
except StopIteration:
    pass
💡 La regla mecánica. await sobre un Future no terminado suspende y devuelve el control al loop. await sobre otra corrutina es una llamada de función común y corriente: entra, ejecuta y vuelve, sin pasar por el loop. Si esa corrutina interna nunca toca un Future, el loop jamás tuvo la oportunidad de correr otra cosa. 
import asyncio, time

async def no_cede_nunca():
    total = 0
    for i in range(50_000_000):     # es "async" pero no suspende jamás
        total += i
    return total

async def latido():
    while True:
        print("vivo", time.strftime("%H:%M:%S"))
        await asyncio.sleep(1)      # esto SÍ suspende: crea un timer

async def main():
    asyncio.create_task(latido())
    await no_cede_nunca()           # el latido se calla ~4 segundos

asyncio.run(main())
La palabra async no hace nada por sí sola. Marcar una función como async def no la vuelve concurrente, no la manda a otro hilo y no la hace cooperativa. Solo la vuelve suspendible. Si adentro no hay ningún await que llegue a un Future, es código bloqueante con sintaxis moderna.

PS3.3 Tasks vs corrutinas: quién corre y quién solo existe

Una corrutina, sola, no corre. Es un objeto inerte. Lo que el loop programa y ejecuta es una Task: un envoltorio que es a la vez un Future y un callback (Task.__step) que sabe hacerle send() a la corrutina cada vez que le toca.

import asyncio, time

async def trabajo(n):
    await asyncio.sleep(1)
    return n

async def secuencial():          # 3 segundos: cada await espera al anterior
    return [await trabajo(i) for i in range(3)]

async def concurrente():         # 1 segundo: las tres arrancaron juntas
    tareas = [asyncio.create_task(trabajo(i)) for i in range(3)]
    return [await t for t in tareas]
Regla de lectura rápida de código ajeno: si en el archivo no hay ni un create_task, ni un TaskGroup, ni un gather, no hay concurrencia. Hay un programa secuencial escrito con sintaxis async, que probablemente sea más lento que la versión síncrona. Es muchísimo más común de lo que parece.

PS3.4 TaskGroup: por qué reemplaza a gather en código nuevo

asyncio.gather tiene un problema de diseño que se paga siempre en producción: cuando una tarea falla, las demás quedan corriendo. gather te propaga la primera excepción y se desentiende del resto. Esas tareas siguen consumiendo conexiones, escribiendo archivos a medio terminar y, cuando finalmente fallan, te dejan un Task exception was never retrieved en los logs a las tres de la mañana.

import asyncio

async def rapida_y_rota():
    await asyncio.sleep(0.1)
    raise ValueError("me rompí")

async def lenta_e_ignorada():
    try:
        await asyncio.sleep(5)
        print("¡seguí corriendo 5 segundos después del error!")
    finally:
        print("nadie me esperó, nadie me limpió")

async def main_mala():
    await asyncio.gather(rapida_y_rota(), lenta_e_ignorada())
    # ValueError sale a los 0.1s... y lenta_e_ignorada queda huérfana

TaskGroup (Python 3.11+) implementa concurrencia estructurada: el bloque async with no termina hasta que todas sus tareas terminaron, y si una falla, cancela a las demás y espera a que se limpien. Nada sobrevive al bloque. Nunca.

import asyncio

async def main_buena():
    async with asyncio.TaskGroup() as tg:
        t1 = tg.create_task(rapida_y_rota())
        t2 = tg.create_task(lenta_e_ignorada())
    # Al salir del bloque: t1 falló -> t2 fue cancelada y esperada.
    # Se levanta un ExceptionGroup con TODO lo que falló de verdad.

# Y se manejan con except* (PEP 654), que filtra por tipo dentro del grupo:
async def con_manejo():
    try:
        async with asyncio.TaskGroup() as tg:
            for url in urls:
                tg.create_task(bajar(url))
    except* TimeoutError as eg:
        log.warning("%d timeouts", len(eg.exceptions))
    except* PermissionError as eg:
        log.error("credenciales rotas: %r", eg.exceptions[0])
        raise

📌 Código nuevo: TaskGroup. gather queda para el caso puntual de "quiero los N resultados en orden, y los errores como valores" (return_exceptions=True). Todo lo que sea "lanzá estas cosas y que no quede nada colgado" es TaskGroup. La diferencia no es estética: es la diferencia entre un apagado limpio y un proceso que hay que matar con -9.

PS3.5 Timeouts: asyncio.timeout vs wait_for, y shield

asyncio.wait_for(coro, t) envuelve un solo awaitable. asyncio.timeout(t) (3.11+) es un context manager que le pone plazo a un bloque entero, incluyendo lo que armaste antes y después del await principal:

import asyncio

# wait_for: solo cubre la llamada. Si el parseo tarda, no lo cubre nadie.
datos = await asyncio.wait_for(cliente.get(url), timeout=5)
parseado = parsear(datos)                      # fuera del plazo

# timeout: cubre TODO el bloque, con el mismo presupuesto de tiempo.
async with asyncio.timeout(5):
    datos = await cliente.get(url)
    parseado = await procesar(datos)           # dentro del plazo
    await guardar(parseado)

# Plazo absoluto (útil para un deadline de request end-to-end):
async with asyncio.timeout_at(loop.time() + presupuesto_restante):
    ...

El mecanismo es el mismo en los dos casos y conviene tenerlo claro: el timeout no "corta" nada, cancela. Programa un timer que llama a task.cancel(), y cuando el CancelledError vuelve, lo traduce a TimeoutError.

Acá aparece un detalle fino de 3.11 que resuelve un bug histórico: Task.cancelling() y Task.uncancel(). asyncio.timeout los usa para distinguir "te cancelé yo por mi plazo" de "llegó una cancelación de afuera mientras tanto". Sin eso, un timeout interno se comía la cancelación del padre y la tarea seguía viva. Si escribís tus propios helpers que cancelan, es la API que tenés que respetar. 
import asyncio

async def con_reintentos(coro_factory, intentos=3, plazo=2.0):
    for n in range(intentos):
        try:
            async with asyncio.timeout(plazo):
                return await coro_factory()
        except TimeoutError:                 # desde 3.11 es el builtin
            if n == intentos - 1:
                raise
            await asyncio.sleep(2 ** n)      # backoff exponencial

shield: la excepción, no la regla

asyncio.shield(aw) protege un awaitable de una cancelación que venga de afuera. Se justifica en un solo escenario: una operación que no se puede repetir ni dejar a medias — confirmar un pago, commitear una transacción, mandar un ACK.

import asyncio

async def manejar_pedido(pago):
    # Si el cliente corta la conexión, NO queremos abortar el cobro a medias.
    tarea = asyncio.create_task(confirmar_cobro(pago))
    try:
        return await asyncio.shield(tarea)
    except asyncio.CancelledError:
        # A NOSOTROS nos cancelaron; el cobro sigue. Hay que esperarlo igual.
        await tarea            # si no, queda huérfano y el proceso muere antes
        raise
⚠️ La trampa de shield. El escudo protege a la tarea interna, no a vos. Si te cancelan, vos recibís CancelledError igual y la tarea protegida sigue corriendo sin dueño. Si no la esperás explícitamente, el apagado del proceso la va a matar en el peor momento posible. shield sin un await tarea en el except es casi siempre un bug disfrazado de precaución.

PS3.6 Cancelación: CancelledError no es un error común

Cancelar en asyncio no mata nada: inyecta una excepción en el punto donde la corrutina está suspendida. Tu código la ve como cualquier otra excepción, corre sus finally, y debe dejarla salir.

import asyncio

# Desde Python 3.8, CancelledError hereda de BaseException, NO de Exception.
issubclass(asyncio.CancelledError, Exception)       # False
issubclass(asyncio.CancelledError, BaseException)   # True
📌 Ese cambio de jerarquía es intencional y es tu red de contención. Un except Exception: genérico —el que todos escribimos alrededor de un handler— no se traga la cancelación. Lo que sí se la traga es un except BaseException:, un except: pelado o un except asyncio.CancelledError: que no re-lanza. Esos tres son bugs. 
import asyncio, logging

# ❌ MAL: se come la cancelación. La tarea "se niega" a morir y el
#         apagado se cuelga hasta que alguien la mate a la fuerza.
async def worker_malo(q):
    while True:
        try:
            item = await q.get()
            await procesar(item)
        except Exception:
            logging.exception("error procesando")
        except asyncio.CancelledError:
            logging.info("me cancelaron")     # ...y sigue el while True

# ✅ BIEN: limpiar en finally, dejar salir la cancelación.
async def worker_bueno(q, conexion):
    try:
        while True:
            item = await q.get()
            try:
                await procesar(item)
            except Exception:
                logging.exception("item %r falló, sigo", item)
    except asyncio.CancelledError:
        logging.info("cancelado: cerrando prolijo")
        raise                                  # ← IMPRESCINDIBLE
    finally:
        await conexion.close()                 # ver el aviso de abajo
Cuidado con los await dentro de finally durante una cancelación. Si tardan, retrasan todo el apagado; y si vuelven a ser cancelados (segunda señal, o el timeout del orquestador), tu limpieza queda a medias. Para limpiezas que tienen que completarse, envolvelas: async with asyncio.timeout(2): await conexion.close(), y si hace falta protegerlas de la cancelación en curso, await asyncio.shield(...) con el cuidado de PS3.5. Lo ideal es que el cierre sea rápido y no dependa de la red.

PS3.7 Los cuatro errores clásicos

1. Bloquear el loop con código síncrono

El error número uno, por lejos. Una llamada bloqueante en un handler y toda la aplicación se congela para todos los usuarios, no solo para el que la disparó.

import asyncio, requests, hashlib, json

# ❌ Cada uno de estos congela el loop entero mientras dura:
async def handler_malo(path, url):
    r = requests.get(url)                       # cliente HTTP síncrono
    with open(path) as f:                       # I/O de archivo síncrona
        datos = json.load(f)
    clave = hashlib.pbkdf2_hmac("sha256", pw, salt, 600_000)   # CPU pesada
    return r.text

# ✅ Cada cosa a su lugar:
async def handler_bueno(path, url, cliente):
    r = await cliente.get(url)                                  # httpx/aiohttp
    datos = json.loads(await asyncio.to_thread(leer_texto, path))
    clave = await asyncio.to_thread(
        hashlib.pbkdf2_hmac, "sha256", pw, salt, 600_000)       # 3.9+
    return r.text
La biblioteca estándar es casi toda bloqueante. open(), socket, subprocess.run, time.sleep, sqlite3, requests, boto3, casi todo driver de base de datos "clásico", PIL, json.loads sobre un archivo de 200 MB. Que estén dentro de un async def no cambia absolutamente nada. La pregunta correcta al revisar código no es "¿es async?" sino "¿esta línea puede tardar sin ceder?".

2. Crear una task y no guardar la referencia

Este es de los que aparecen solo bajo carga, en producción, y una de cada mil veces. asyncio.create_task devuelve una Task, pero el loop la guarda en un WeakSet. Si vos no guardás una referencia fuerte, el recolector puede llevársela en medio de la ejecución.

import asyncio

# ❌ La task puede desaparecer sin terminar, sin error, sin log.
async def handler_malo(evento):
    asyncio.create_task(auditar(evento))    # "fire and forget"
    return "ok"

# ✅ Referencia fuerte hasta que termine, y errores que se ven.
_en_vuelo: set[asyncio.Task] = set()

def lanzar_en_fondo(coro, *, nombre=None) -> asyncio.Task:
    tarea = asyncio.create_task(coro, name=nombre)
    _en_vuelo.add(tarea)
    tarea.add_done_callback(_en_vuelo.discard)
    tarea.add_done_callback(_reportar_si_falla)
    return tarea

def _reportar_si_falla(t: asyncio.Task) -> None:
    if t.cancelled():
        return
    if (exc := t.exception()) is not None:
        logging.error("tarea de fondo %s falló", t.get_name(), exc_info=exc)
El add_done_callback que reporta errores es tan importante como el que mantiene la referencia. Sin él, una task de fondo que explota no rompe nada visible: el Task exception was never retrieved aparece cuando el GC la recoge, con un stack sin contexto y a veces mucho después. En una aplicación con TaskGroup de largo aliento, todo esto te lo da el grupo gratis — es otra razón para preferirlo.

3. await adentro de un lock, mal usado

Hay dos versiones de este error y conviene distinguirlas, porque una es un deadlock y la otra es una pérdida silenciosa de concurrencia.

import asyncio, threading

# ❌ (a) DEADLOCK: threading.Lock en código async.
#        La tarea A adquiere y hace await -> se suspende SIN soltar.
#        La tarea B intenta adquirir -> .acquire() BLOQUEA EL HILO.
#        Ese hilo es el event loop, así que A nunca se reanuda. Cuelgue total.
candado_malo = threading.Lock()
async def a():
    with candado_malo:
        await asyncio.sleep(1)

# ❌ (b) SERIALIZACIÓN: asyncio.Lock correcto, pero sostenido de más.
#        Las 500 tareas hacen la llamada HTTP de a una. Chau concurrencia.
candado = asyncio.Lock()
async def b(cliente, url, cache):
    async with candado:
        r = await cliente.get(url)          # 200 ms sosteniendo el candado
        cache[url] = r.text

# ✅ El candado protege SOLO la sección crítica (que no hace I/O).
async def b_bien(cliente, url, cache):
    r = await cliente.get(url)              # sin candado: concurrente
    async with candado:
        cache[url] = r.text                 # microsegundos
asyncio.Lock no es reentrante. Si una función que ya tiene el candado llama a un helper que también lo pide, se cuelga para siempre — y no hay detección de deadlock que te avise. Además, en un loop de un solo hilo muchas veces no necesitás candado: entre dos await consecutivos nadie más corre, así que un contador += 1 es atómico. El candado hace falta cuando la sección crítica tiene un await en el medio y el estado quedaría inconsistente.

4. time.sleep en vez de asyncio.sleep

import asyncio, time

async def reintentar_mal():
    time.sleep(1)          # congela el loop 1 segundo: TODAS las conexiones
    ...

async def reintentar_bien():
    await asyncio.sleep(1) # programa un timer y cede el control
await asyncio.sleep(0) es un caso especial y útil: no espera nada, pero cede el control una vuelta del loop. Sirve para meter un punto de suspensión en un cálculo largo que no podés mover a un hilo, y en tests para forzar que una task recién creada llegue a arrancar. No lo uses como parche crónico: si necesitás salpicar sleep(0) por todo un algoritmo, ese algoritmo va a un to_thread.

PS3.8 Detectar que el loop está bloqueado

El síntoma de un loop bloqueado es engañoso: no hay errores, no hay excepciones, la CPU está al 100% en un solo núcleo y las latencias p99 se van a la luna. Hay tres herramientas y conviene usarlas en este orden.

import asyncio, logging

async def main():
    ...

# 1) Modo debug: avisa qué callback tardó de más y desde dónde se creó.
logging.basicConfig(level=logging.DEBUG)
asyncio.run(main(), debug=True)

# Equivalente sin tocar el código: PYTHONASYNCIODEBUG=1 python app.py
# Salida típica:
#   Executing <Task pending name='Task-7' coro=<handler() at api.py:42>
#   created at api.py:88> took 1.831 seconds

# 2) Bajar el umbral (por defecto 0.1 s) para cazar bloqueos más chicos:
loop = asyncio.get_running_loop()
loop.slow_callback_duration = 0.02      # avisame si un callback pasa 20 ms
⚠️ El modo debug no va a producción. Activa el rastreo del origen de cada corrutina, chequeos extra y logging denso: te cuesta rendimiento y ruido. Es una herramienta de diagnóstico en staging o en local con carga sintética. En producción, lo que dejás puesto es un watchdog de latencia del loop, que cuesta prácticamente nada. 
import asyncio, time, logging

async def watchdog_del_loop(intervalo=0.25, umbral=0.15):
    """Si dormir 0.25 s tardó 3 segundos, el loop estuvo bloqueado 2.75 s."""
    while True:
        t0 = time.perf_counter()
        await asyncio.sleep(intervalo)
        retraso = time.perf_counter() - t0 - intervalo
        if retraso > umbral:
            logging.warning("event loop bloqueado %.0f ms", retraso * 1000)
            metricas.observe("loop_lag_ms", retraso * 1000)

La tercera herramienta es la más nueva. Python 3.14 incorporó introspección de asyncio: podés imprimir el árbol de llamadas de las corrutinas vivas, incluso desde afuera, contra un proceso que ya está corriendo y colgado.

# Desde adentro del proceso
python -c "import asyncio; asyncio.print_call_graph()"

# Desde afuera, contra un PID en producción (3.14+)
python -m asyncio ps 12345        # tabla de tasks vivas
python -m asyncio pstree 12345    # árbol de quién espera a quién

Sacar el trabajo del loop

import asyncio
from concurrent.futures import ProcessPoolExecutor

# I/O bloqueante o CPU moderada -> un hilo. El GIL se libera en I/O (PS1).
texto = await asyncio.to_thread(pathlib.Path("informe.csv").read_text)

# CPU pesada en Python puro -> un proceso. El GIL NO se libera acá.
loop = asyncio.get_running_loop()
with ProcessPoolExecutor(max_workers=4) as pool:
    resultado = await loop.run_in_executor(pool, calcular_pesado, datos)
📌 to_thread no es gratis y tiene techo. Usa un ThreadPoolExecutor compartido con un límite por defecto de min(32, cpu_count + 4). Si mandás mil llamadas bloqueantes ahí, se encolan: convertiste un cuello de botella en otro, y encima invisible. Para carga sostenida, creá tu propio executor con un tamaño pensado y medí su cola.

PS3.9 Tabla de decisión: asyncio, hilos, procesos o free-threading

En PS1 vimos por qué el GIL limita solo al CPU-bound en Python puro, y que el PEP 779 volvió oficial el build free-threaded en 3.14. Con eso, la decisión ya no es binaria:

Cuándo NO usar asyncio. (1) Cuando la concurrencia que necesitás cabe en un ThreadPoolExecutor de 20 hilos: es menos código y menos formas de romperlo. (2) Cuando tu dependencia crítica —el ORM, el driver, el SDK del proveedor— solo existe en versión bloqueante: vas a terminar con to_thread en todos lados y la peor parte de los dos mundos. (3) Cuando el equipo no tiene experiencia y el sistema toca dinero: los bugs de asyncio son de concurrencia, y los bugs de concurrencia no se reproducen en el debugger. (4) Cuando el cuello de botella es CPU. Free-threading (PS1) hoy resuelve más problemas reales de rendimiento que reescribir a async.

PS3.10 Backpressure: por qué 10.000 tasks es un bug

La operación más fácil de escribir en asyncio es también la más peligrosa: crear una task por cada ítem de una lista. Con 50 ítems anda perfecto. Con 50.000 tenés un incidente.

import asyncio

# ❌ 10.000 tasks vivas al mismo tiempo
async def bajar_todo(urls, cliente):
    async with asyncio.TaskGroup() as tg:
        for u in urls:                       # 10.000 iteraciones
            tg.create_task(bajar(cliente, u))

Qué se rompe exactamente, en orden de aparición:

1. Memoria. Cada task es un objeto Python + un frame de corrutina + su Future + lo que la corrutina tenga capturado. Multiplicá por diez mil y sumale las respuestas que se van acumulando en RAM porque nadie las consumió todavía.
2. El pool de conexiones. Tu cliente HTTP tiene un límite (httpx: 100 conexiones por defecto). Las 9.900 tasks restantes quedan encoladas esperando una conexión. Ese límite es real, pero ahora es invisible: pagaste diez mil tasks para tener cien en vuelo.
3. Los timeouts, todos juntos. Cada task arrancó su plazo de 10 s al crearse, no al conseguir conexión. Las últimas de la fila se vencen sin haber mandado un solo byte. Vas a ver una avalancha de TimeoutError que no tienen nada que ver con el servidor.
4. El otro lado. Si por casualidad sí conseguís mandar diez mil requests, le hiciste una denegación de servicio a tu proveedor. Te va a devolver 429, o te va a bloquear la IP, o —peor— va a andar y vas a repetirlo con cien mil.
📌 La cantidad de trabajo en vuelo es un parámetro de diseño, no una consecuencia del tamaño de la entrada. Si tu concurrencia depende de len(entrada), no tenés un sistema: tenés una bomba con temporizador esperando el día que la entrada crezca 100×.

Las dos formas de acotar

import asyncio

# A) Semáforo: simple, sirve cuando la lista de entrada entra en memoria.
async def bajar_acotado(urls, cliente, limite=50):
    sem = asyncio.Semaphore(limite)
    resultados = {}

    async def uno(u):
        async with sem:                      # nunca más de 50 adentro
            resultados[u] = await bajar(cliente, u)

    async with asyncio.TaskGroup() as tg:
        for u in urls:
            tg.create_task(uno(u))
    return resultados
import asyncio

# B) Cola acotada + N workers: memoria constante aunque la entrada sea infinita
#    (un stream, una tabla de 50 millones de filas, una cola de mensajes).
async def pipeline(fuente, cliente, workers=50, cola_max=200):
    cola: asyncio.Queue[str] = asyncio.Queue(maxsize=cola_max)

    async def worker():
        while True:
            url = await cola.get()
            try:
                await bajar(cliente, url)
            finally:
                cola.task_done()

    async with asyncio.TaskGroup() as tg:
        consumidores = [tg.create_task(worker()) for _ in range(workers)]
        async for url in fuente:
            await cola.put(url)      # ← si la cola está llena, ACÁ frena
        await cola.join()            #   eso es backpressure de verdad
        for c in consumidores:
            c.cancel()
💡 La diferencia clave está en el await cola.put(...). Con el semáforo, las 10.000 tasks existen igual — solo que 9.950 están dormidas. Con la cola acotada, el productor se frena cuando el consumidor no da abasto, y la memoria del proceso no depende del tamaño de la entrada. Eso es backpressure: la presión viaja hacia atrás hasta la fuente. El semáforo limita concurrencia; la cola limita concurrencia y memoria.
Un semáforo limita concurrencia (cuántas a la vez), no tasa (cuántas por segundo). Si el proveedor te pide "máximo 20 req/s", con 50 en paralelo y respuestas de 100 ms vas a 500 req/s y te bloquea igual. Para tasa necesitás un token bucket, o respetar el header Retry-After de los 429. Son dos límites distintos y casi siempre hacen falta los dos.

PS3.11 Testear código async

pytest no ejecuta corrutinas por su cuenta: sin un plugin, un test async def se salta con un warning y te queda una suite verde que no probó nada. Las dos opciones son pytest-asyncio y anyio.

# pyproject.toml — con pytest-asyncio, el modo auto evita decorar cada test
[tool.pytest.ini_options]
asyncio_mode = "auto"
filterwarnings = ["error::RuntimeWarning"]   # caza las corrutinas sin await
import asyncio, pytest

# --- Testear la CANCELACIÓN: que limpie y que re-lance ---
async def test_worker_limpia_al_cancelar(conexion_falsa):
    tarea = asyncio.create_task(worker_bueno(asyncio.Queue(), conexion_falsa))
    await asyncio.sleep(0)              # dejar que arranque de verdad

    tarea.cancel()
    with pytest.raises(asyncio.CancelledError):
        await tarea                     # debe PROPAGAR, no tragarse

    assert conexion_falsa.cerrada       # y debe haber limpiado en finally

# --- Testear TIMEOUTS sin dormir de verdad ---
async def test_timeout_dispara():
    nunca = asyncio.Event()             # un Event que nadie setea
    with pytest.raises(TimeoutError):
        async with asyncio.timeout(0.01):
            await nunca.wait()

# --- Testear el LÍMITE de concurrencia, que es lo que la gente no testea ---
async def test_nunca_mas_de_50_en_vuelo(monkeypatch):
    en_vuelo = 0
    pico = 0

    async def bajar_espia(_cliente, _url):
        nonlocal en_vuelo, pico
        en_vuelo += 1
        pico = max(pico, en_vuelo)
        await asyncio.sleep(0)          # punto de suspensión
        en_vuelo -= 1

anyio es la alternativa cuando querés que tu librería corra también sobre Trio, o cuando preferís su modelo de cancel scopes. Se testea con @pytest.mark.anyio y una fixture anyio_backend. Para una aplicación que solo va a usar asyncio, pytest-asyncio en modo auto alcanza y sobra.
No pongas await asyncio.sleep(0.5) en los tests para "esperar a que pase algo". Es la receta de una suite lenta y con fallos intermitentes en CI (que siempre es más lenta que tu máquina). Sincronizá con lo que realmente representa el evento: un asyncio.Event, un await cola.join(), o await tarea. sleep(0) para ceder una vuelta es legítimo; sleep(0.5) como sincronización es deuda.

PS3.12 Producción: apagar sin romper nada

asyncio.run() hace más de lo que parece al terminar: cancela todas las tasks pendientes, las espera, cierra los generadores asíncronos y apaga el executor por defecto. El problema es que hace todo eso de golpe y sin plazo de gracia. Un servicio serio necesita controlar esa secuencia.

import asyncio, contextlib, logging, signal

async def main():
    apagar = asyncio.Event()
    loop = asyncio.get_running_loop()

    # En Unix, la forma correcta: el handler corre EN el loop, sin race conditions.
    # (En Windows add_signal_handler no existe: usar signal.signal + call_soon_threadsafe)
    for s in (signal.SIGTERM, signal.SIGINT):
        with contextlib.suppress(NotImplementedError):
            loop.add_signal_handler(s, apagar.set)

    async with asyncio.TaskGroup() as tg:        # supervisor de por vida
        tg.create_task(watchdog_del_loop())
        tg.create_task(consumidor_de_cola())
        servidor = await arrancar_http()

        await apagar.wait()                      # bloquea hasta SIGTERM

        logging.info("apagando: dejo de aceptar conexiones")
        await servidor.dejar_de_aceptar()        # 1. cerrar la puerta
        await drenar_en_vuelo(plazo=25)          # 2. terminar lo empezado
        raise asyncio.CancelledError             # 3. cancelar lo de fondo

asyncio.run(main())
📌 El orden del apagado no es negociable. Primero dejás de aceptar trabajo nuevo, después drenás lo que ya está en vuelo con un plazo, y recién al final cancelás las tareas de fondo. Al revés —cancelar primero— matás pedidos que el cliente ya considera aceptados. Ese plazo tiene que ser menor que el terminationGracePeriodSeconds de tu orquestador, o el SIGKILL llega antes de que termines y todo el trabajo prolijo fue decorativo.
Las tareas de fondo son el punto débil de todo servicio async. Al apagar, cualquiera que no esté supervisada por un TaskGroup o por tu conjunto de referencias fuertes (PS3.7) simplemente desaparece con el proceso: a mitad de una escritura, con una transacción abierta, sin haber mandado el ACK. La regla es que toda task tenga un dueño identificable. Si no sabés quién espera a una task, esa task no existe en el apagado.

🧑‍🎓 Worked Example — el scraper de 5.000 URLs

Hay que bajar 5.000 páginas de producto de un proveedor, extraer tres campos y guardarlos. La primera versión "funcionaba en las pruebas" con 40 URLs. Con las 5.000 reales revienta a los 38 segundos y no deja nada usable.

Paso 1 — La versión ingenua. Es exactamente lo que escribiría cualquiera que aprendió asyncio en un tutorial:

import asyncio, httpx

async def bajar(cliente, url):
    r = await cliente.get(url)
    r.raise_for_status()
    return extraer(r.text)

async def main(urls):
    async with httpx.AsyncClient() as cliente:
        return await asyncio.gather(*(bajar(cliente, u) for u in urls))

asyncio.run(main(urls_5000))

Paso 2 — Qué pasó, con números. No "se rompió": se rompió de cuatro maneras distintas y cada una tiene una causa distinta.

httpx.PoolTimeout en 1.240 URLsEl pool tiene 100 conexiones; 4.900 tasks esperando turno agotaron el plazo del pool sin mandar un byte

Paso 3 — Diagnóstico. El error de fondo es uno solo: la concurrencia quedó atada al tamaño de la entrada. Todo lo demás es consecuencia. El límite real del sistema (100 conexiones, ~40 req/s del proveedor) ya existía; lo único que logramos con 5.000 tasks fue hacerlo invisible y pagarlo en memoria y en timeouts falsos.

Paso 4 — La versión que va a producción. Cada pieza corrige un síntoma concreto de la tabla de arriba:

import asyncio, random, httpx, logging
from dataclasses import dataclass

CONCURRENCIA = 40          # ≤ pool de conexiones y ≤ tasa que tolera el proveedor
PLAZO_POR_URL = 10.0
INTENTOS = 3

@dataclass(slots=True)
class Resultado:
    url: str
    datos: dict | None = None
    error: str | None = None

async def bajar_con_reintentos(cliente, url, sem) -> Resultado:
    for intento in range(INTENTOS):
        try:
            async with sem:                             # ← límite de concurrencia
                async with asyncio.timeout(PLAZO_POR_URL):   # ← plazo por ítem
                    r = await cliente.get(url)
                    if r.status_code == 429:
                        raise httpx.HTTPStatusError("429", request=r.request,
                                                    response=r)
                    r.raise_for_status()
                    return Resultado(url, extraer(r.text))

        except asyncio.CancelledError:
            raise                                       # ← NUNCA la atrapamos
        except (httpx.HTTPError, TimeoutError) as e:
            if intento == INTENTOS - 1:
                return Resultado(url, error=repr(e))    # ← el fallo es un DATO
            espera = min(2 ** intento, 8) + random.random()   # backoff + jitter
            logging.info("reintento %d de %s en %.1fs", intento + 1, url, espera)
            await asyncio.sleep(espera)

async def main(urls) -> list[Resultado]:
    sem = asyncio.Semaphore(CONCURRENCIA)
    limites = httpx.Limits(max_connections=CONCURRENCIA + 10)
    resultados: list[Resultado] = []

    async with httpx.AsyncClient(limits=limites, timeout=None) as cliente:
        async with asyncio.TaskGroup() as tg:           # ← nada queda huérfano
            tareas = [tg.create_task(bajar_con_reintentos(cliente, u, sem))
                      for u in urls]
        resultados = [t.result() for t in tareas]

    ok = sum(r.error is None for r in resultados)
    logging.info("%d/%d OK, %d con error", ok, len(urls), len(urls) - ok)
    return resultados

Paso 5 — Qué mejoró cada cambio. Esta tabla es el entregable real del ejercicio: cada línea es una decisión defendible, no una receta copiada.

📌 La decisión más importante del ejercicio es la que menos parece código. Es Resultado(url, error=...): convertir el fallo de un ítem en un dato en vez de una excepción. El fail-fast de TaskGroup es exactamente lo que querés cuando las tareas son partes de una operación indivisible (armar una respuesta, escribir una transacción) — si una falla, las demás no sirven. Pero en un lote de 5.000 ítems independientes, abortar todo porque el ítem 3.412 dio 404 es la política equivocada. Por eso el TaskGroup queda reservado para lo que sí es fatal: se cayó la autenticación, se llenó el disco. Elegir dónde poner esa frontera es el trabajo senior; el resto es sintaxis.
Con 5 millones de URLs, esta versión también se cae: la lista de tareas y la de resultados no entran en memoria. Ahí el patrón correcto es el de la cola acotada de PS3.10 —N workers consumiendo un stream, escribiendo cada resultado a disco o a una base a medida que llega— y la memoria deja de depender de la entrada. Vale la pena notar que ese cambio no es una optimización: es un cambio de arquitectura, y conviene saber de antemano en qué orden de magnitud te toca hacerlo.

Checkpoint — ¿lo tenés claro?

Tenés await procesar(x) dentro de un handler y el servidor igual se cuelga. ¿Cómo puede ser, si hay un await?

Porque await sobre otra corrutina no cede el control: es una llamada de función que entra, ejecuta y vuelve. El control vuelve al loop solo cuando se llega a un await sobre un Future que todavía no terminó — un socket, un timer, un Event. Si procesar es async def pero adentro solo hace cálculo, o llama a requests.get, o abre un archivo con open, el loop no corrió nada más en todo ese tiempo. Se confirma en un minuto con asyncio.run(main(), debug=True), que te va a decir qué callback tardó y en qué línea se creó.

¿Por qué TaskGroup es mejor que gather aunque tu código "no falle nunca"?

Porque la diferencia aparece justo cuando sí falla, que es cuando menos margen tenés. Con gather, la primera excepción sale y las demás tareas siguen corriendo sin dueño: mantienen conexiones abiertas, escriben archivos a medias y sus errores aparecen después como Task exception was never retrieved sin contexto. Con TaskGroup, al salir del bloque tenés la garantía estructural de que no quedó nada vivo, y si fallaron tres tareas ves las tres en un ExceptionGroup, no solo la primera. Además el grupo mantiene las referencias fuertes por vos, así que desaparece el bug del GC comiéndose una task.

Tu scraper con Semaphore(50) igual recibe 429. ¿Qué te falta?

Un semáforo limita concurrencia, no tasa. Con 50 en vuelo y respuestas de 100 ms estás emitiendo ~500 req/s; si el proveedor tolera 40 req/s, te bloquea igual. Son dos límites distintos: para la tasa necesitás un token bucket (o simplemente respetar el header Retry-After que viene en el 429 y hacer backoff con jitter). Y conviene medir cuál de los dos te está mordiendo antes de bajar el semáforo a ciegas, porque bajarlo mucho te deja el pool de conexiones ocioso y multiplicás el tiempo total sin ganar nada.

Resumen ejecutivo

  • asyncio no acelera el trabajo: elimina el tiempo muerto de espera y consigue miles de operaciones concurrentes con la memoria de un hilo. Si el cuello de botella es CPU, empeora las cosas.
  • El event loop es un hilo, un callback a la vez: duerme en select() y despierta a correr callbacks. La latencia de todos depende del callback más largo.
  • Las corrutinas son generadores mejorados y await es yield disfrazado. await sobre otra corrutina no cede el control; solo lo cede un Future pendiente.
  • Una corrutina no corre sola: la que el loop programa es la Task. Sin create_task, TaskGroup o gather, no hay concurrencia.
  • TaskGroup (3.11+) reemplaza a gather en código nuevo: cancelación estructurada, ExceptionGroup con except*, y la garantía de que nada queda huérfano.
  • asyncio.timeout le pone plazo a un bloque, no a una llamada. shield solo para operaciones no repetibles — y siempre esperando la tarea protegida.
  • CancelledError hereda de BaseException: se limpia en finally y se re-lanza. Atraparla sin re-lanzar es un servicio que no se apaga.
  • Los cuatro errores clásicos: bloquear el loop, no guardar la referencia de una task, sostener un lock a través de un await, y time.sleep.
  • Diagnóstico: debug=True y slow_callback_duration en staging, watchdog de latencia en producción, y python -m asyncio pstree PID desde 3.14. El trabajo pesado sale con to_thread o run_in_executor.
  • La concurrencia es un parámetro de diseño, no len(entrada). Semáforo para acotar concurrencia; cola acotada para acotar además la memoria.

🧠 Autoevaluación

1. Un handler hace await calcular(x), donde calcular es async def y adentro suma diez millones de números. ¿Qué pasa con el resto de las conexiones?

await sobre otra corrutina es delegación —entra, ejecuta, vuelve— igual que yield from. El control vuelve al loop únicamente cuando se llega a un await sobre un Future que todavía no terminó (un socket, un timer, un Event). Como calcular nunca toca uno, el loop no ejecuta ningún otro callback durante todo ese tiempo. La palabra async vuelve una función suspendible, no concurrente. La solución es await asyncio.to_thread(...), o un ProcessPoolExecutor si es CPU pesada en Python puro (PS1).

2. En un worker de larga vida escribís except asyncio.CancelledError: log.info("chau") y seguís con el while True. ¿Cuál es la consecuencia?

Cancelar es inyectar una excepción, no matar la tarea: si la atrapás y no la re-lanzás, la tarea sigue viva. Ahí TaskGroup, asyncio.timeout y el apagado de asyncio.run quedan esperando a alguien que nunca termina, y el proceso se cuelga hasta que llegue el SIGKILL del orquestador — con transacciones abiertas y escrituras a medias. El patrón correcto es limpiar en finally (con plazo, si la limpieza toca la red) y hacer raise al final del except. Que CancelledError herede de BaseException desde 3.8 es justamente para que tu except Exception genérico no la atrape sin querer.

3. Tenés 5.000 URLs y las lanzás con gather, una task por URL. El pool del cliente HTTP tiene 100 conexiones. ¿Cuál es el problema de fondo?

El límite real (100 conexiones, más la tasa que tolere el proveedor) ya existía; las 5.000 tasks solo lo volvieron invisible y caro. Pagás RAM por 4.900 tasks dormidas, sus plazos empiezan a correr al crearse y no al conseguir conexión —así aparece una avalancha de TimeoutError falsos—, y encima gather deja huérfanas a las 4.999 restantes cuando una falla, perdiendo el trabajo ya completado. La corrección es un Semaphore del tamaño del pool más TaskGroup y un timeout por ítem dentro del semáforo; y si la entrada puede crecer sin techo, una cola acotada con N workers para que la memoria deje de depender de ella.

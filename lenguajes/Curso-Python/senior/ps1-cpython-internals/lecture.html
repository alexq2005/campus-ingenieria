PS1 — CPython por dentro: objetos, GIL y free-threading

PS1.0 Por qué este módulo

Hasta acá usaste Python. Desde acá vas a entender por qué se comporta como se comporta. Esa diferencia aparece el día que tenés que explicar por qué un for en Python es 50 veces más lento que en C, por qué agregar hilos no aceleró nada, o por qué una lista de un millón de enteros come 40 MB en vez de 8.

💡 La tesis del módulo. Casi todas las rarezas de rendimiento de Python se explican con tres hechos: (1) todo valor es un objeto con header en el heap, (2) la memoria se administra con conteo de referencias, y (3) ese conteo tenía que ser seguro entre hilos, y la forma barata de lograrlo fue un candado global. Entendé esos tres y el resto se deduce.

Y hay una razón de coyuntura para estudiarlo ahora: el punto (3) dejó de ser una verdad absoluta. Desde Python 3.14, gracias al PEP 779, el build sin GIL pasó de experimental a oficialmente soportado. Lo que aprendiste sobre concurrencia en Python está cambiando debajo de tus pies, y conviene saber exactamente qué cambia y qué no.

PS1.1 Todo es un objeto: el header que pagás siempre

En C, un int son 4 bytes en el stack. En CPython, un entero es una estructura en el heap con un encabezado. Todo objeto arranca con, como mínimo, un contador de referencias y un puntero a su tipo:

// Objects/object.h, simplificado
typedef struct _object {
    Py_ssize_t ob_refcnt;      // cuántos apuntan a esto
    PyTypeObject *ob_type;     // de qué tipo es
} PyObject;

Podés verlo desde Python:

import sys

sys.getsizeof(0)          # 28  bytes — un cero "vacío" ya pesa 28
sys.getsizeof(2**30)      # 32
sys.getsizeof(2**300)     # 68  — los enteros son de precisión arbitraria
sys.getsizeof([])         # 56  — una lista vacía
sys.getsizeof([0] * 1000) # 8056 — 8 bytes por puntero, más el header
📌 Una lista de enteros no guarda enteros: guarda punteros a objetos entero. [0]*1000 ocupa ~8 KB de punteros, y además existe en algún lado el objeto 0. Por eso un array.array o un numpy.ndarray —que guardan los valores crudos, contiguos— usan una fracción de la memoria y permiten que la CPU aproveche la caché. 
import array, sys
lista = [i for i in range(1000)]
arr   = array.array("q", range(1000))   # enteros de 64 bits, contiguos

sys.getsizeof(lista)   # 8856  + 1000 objetos int aparte
sys.getsizeof(arr)     # 8064  y nada más: los valores están adentro
CPython internea (cachea) los enteros chicos, de −5 a 256, y muchos strings que parecen identificadores. Por eso a = 256; b = 256; a is b da True pero con 257 da False. Es un detalle de implementación, no del lenguaje: nunca escribas lógica que dependa de eso.

PS1.2 Reference counting y el recolector de ciclos

CPython libera memoria en el instante en que el contador llega a cero. Es determinista y de baja latencia — a diferencia de la JVM o Go, que tienen un GC que corre cuando quiere.

import sys

x = object()
sys.getrefcount(x)   # 2: la variable x, y el argumento temporal de la llamada
y = x
sys.getrefcount(x)   # 3
del y
sys.getrefcount(x)   # 2

El problema del refcounting puro son los ciclos: dos objetos que se apuntan entre sí nunca bajan a cero, aunque nadie más los referencie. Para eso existe el módulo gc, un recolector generacional que solo busca ciclos:

import gc

class Nodo:
    def __init__(self): self.otro = None

a, b = Nodo(), Nodo()
a.otro = b
b.otro = a          # ciclo: refcount de ambos nunca llega a 0
del a, b            # inalcanzables, pero NO liberados todavía

gc.collect()        # devuelve la cantidad de objetos liberados
Consecuencia práctica: si tu clase tiene __del__ y participa de un ciclo, el orden de finalización queda en manos del GC y puede tardar. Por eso los recursos se liberan con context managers (with), no con __del__. Un __del__ nunca es una garantía de cuándo.

Cuándo apagar el GC (y por qué casi nunca)

En procesos de vida corta que crean muchos objetos y terminan —un script de ETL, un job por lote— apagar el recolector de ciclos puede dar unos puntos de rendimiento. Es una optimización real y medible, y también una forma fácil de crear una fuga si el proceso pasa a ser de vida larga:

import gc, time

def medir(fn):
    t0 = time.perf_counter(); fn(); return time.perf_counter() - t0

def carga():
    for _ in range(200_000):
        {"a": [1, 2, 3], "b": {"c": 4}}

con_gc = medir(carga)
gc.disable()
sin_gc = medir(carga)
gc.enable()
print(f"con GC {con_gc:.3f}s · sin GC {sin_gc:.3f}s · {con_gc/sin_gc:.2f}x")
Medí en TU carga antes de creer cualquier número. La ganancia depende por completo de cuántos objetos con ciclos generás. En muchos programas la diferencia es ruido, y el riesgo de olvidarte el gc.disable() puesto es permanente.

PS1.3 Del código al bytecode

Python compila a bytecode y lo ejecuta en una máquina virtual de pila. dis te deja verlo, y es la herramienta que convierte discusiones de rendimiento en hechos:

import dis

def suma_lenta(xs):
    total = 0
    for x in xs:
        total = total + x
    return total

dis.dis(suma_lenta)

Comparando dos formas de escribir lo mismo, el bytecode te muestra el costo real:

import dis

def con_punto(s):     # busca el atributo en CADA iteración
    r = []
    for x in s:
        r.append(x)
    return r

def sin_punto(s):     # resuelve el método UNA vez
    r = []
    add = r.append
    for x in s:
        add(x)
    return r

dis.dis(con_punto)    # vas a ver LOAD_METHOD dentro del loop
dis.dis(sin_punto)    # el LOAD_METHOD salió del loop
Ese truco (method hoisting) era un clásico de optimización. Los intérpretes modernos lo mitigan bastante, así que hoy se usa más para leer bytecode que para optimizar. La lección que sí sirve: en Python, cada punto es una búsqueda en un diccionario, y los loops calientes pagan esa búsqueda por iteración.

PS1.4 El GIL: qué protege realmente

El Global Interpreter Lock es un mutex único por intérprete que garantiza que un solo hilo ejecuta bytecode a la vez. No existe para hacerte la vida difícil: existe porque el refcounting de PS1.2 no es atómico, y ponerle un candado a cada objeto sería más lento que un candado global.

Escenario¿Los hilos ayudan?Por qué
CPU-bound (cálculo puro)❌ No, y a veces empeoraSolo uno corre bytecode; se suma el costo de cambiar de contexto
I/O-bound (red, disco)✅ Sí, muchoEl GIL se libera durante la espera de I/O
NumPy / C extensions✅ SíLa extensión libera el GIL mientras hace su trabajo en C

Se comprueba en treinta segundos:

import time, threading
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

def cpu(n=8_000_000):
    x = 0
    for i in range(n): x += i
    return x

def cronometrar(nombre, fn):
    t0 = time.perf_counter(); fn(); print(f"{nombre}: {time.perf_counter()-t0:.2f}s")

cronometrar("secuencial x4", lambda: [cpu() for _ in range(4)])
cronometrar("4 hilos     ", lambda: list(ThreadPoolExecutor(4).map(lambda _: cpu(), range(4))))
cronometrar("4 procesos  ", lambda: list(ProcessPoolExecutor(4).map(cpu, [8_000_000]*4)))
📌 La regla clásica: CPU-bound → procesos (ProcessPoolExecutor). I/O-bound → hilos o asyncio (PS3). Esa regla fue verdad durante 30 años. En 3.14 dejó de ser toda la verdad.

PS1.5 Free-threading: el GIL dejó de ser obligatorio

💡 Lo que cambió. Desde Python 3.13 existe un build alternativo con el GIL desactivado. Con el PEP 779, en Python 3.14 ese build pasó de experimental a oficialmente soportado. No es el build por defecto todavía, pero ya no es un juguete: es una configuración con la que se puede ir a producción.

Se instala y se usa como un intérprete aparte — la t es de threaded:

# Con uv (ver PS6), el free-threaded se pide explícitamente
uv python install 3.14t
uv run --python 3.14t python -c "import sys; print(sys._is_gil_enabled())"
# False  -> estás corriendo sin GIL

python3.14t -VV        # el build lo dice en la versión
import sys, sysconfig

# ¿Este intérprete puede correr sin GIL?
sysconfig.get_config_var("Py_GIL_DISABLED")   # 1 en el build free-threaded
sys._is_gil_enabled()                          # False si está realmente apagado

Qué ganás y qué pagás

AspectoEstado en 3.14
Paralelismo real con hilos✅ Sí: el código CPU-bound escala con los núcleos
Penalidad en un solo hilo~5–10% más lento que el build normal
Código Python puroCorre sin cambios en la enorme mayoría de los casos
Extensiones en C⚠️ Deben declararse compatibles; si no, el intérprete vuelve a activar el GIL
Biblioteca estándarSoporte prácticamente completo
Ecosistema de tercerosMixto: hay librerías listas y otras atrasadas
⚠️ El error que te va a morder. Correr con el build free-threaded no garantiza que estés sin GIL. Si importás una extensión C que no se declaró compatible, CPython vuelve a habilitar el GIL en caliente y tu paralelismo desaparece — sin error, sin warning visible. Por eso el sys._is_gil_enabled() del ejemplo no es curiosidad: es una verificación que va en el arranque de tu app, o en un test. 
# Verificación defensiva al iniciar un servicio que DEPENDE del paralelismo real
import sys, logging

def exigir_free_threading():
    if not hasattr(sys, "_is_gil_enabled"):
        raise RuntimeError("Se requiere Python 3.13+ para free-threading")
    if sys._is_gil_enabled():
        raise RuntimeError(
            "El GIL está activo. Alguna extensión C lo reactivó: "
            "revisá las dependencias nativas antes de asumir paralelismo."
        )
    logging.info("free-threading activo: %d núcleos disponibles", __import__("os").cpu_count())
Sin GIL, tu código Python deja de ser accidentalmente seguro. Muchas operaciones que parecían atómicas lo eran por efecto lateral del GIL. Un contador += 1 desde varios hilos siempre estuvo mal, pero muchas veces "funcionaba". Sin GIL, la carrera aparece de verdad. La corrección es la de siempre: threading.Lock, estructuras inmutables, o no compartir estado.

PS1.6 El JIT experimental

La otra pieza que llegó con 3.13–3.14 es un compilador JIT (copy-and-patch) que traduce bytecode caliente a código máquina. Sigue siendo experimental y hay que habilitarlo explícitamente al compilar el intérprete.

Hoy las ganancias del JIT son modestas y muy dependientes de la carga. Su valor real es estructural: por primera vez CPython tiene la infraestructura para optimizar en tiempo de ejecución, y eso es lo que va a mover la aguja en las próximas versiones. No diseñes nada asumiendo que el JIT te va a salvar — todavía no.

PS1.7 Cuándo esto te importa de verdad

Saber internals no sirve para escribir código más raro. Sirve para tomar tres o cuatro decisiones que después no se pueden revertir barato:

1. Elegir el modelo de concurrencia. I/O masivo → asyncio. CPU con librerías nativas (NumPy, Polars) → hilos, que ya escalan. CPU en Python puro → procesos, o free-threading si tus dependencias lo soportan y lo verificaste.
2. Elegir la estructura de datos. Millones de números homogéneos nunca van en una list: van en array, NumPy o Polars. La diferencia no es 20%, son órdenes de magnitud en memoria y en caché.
3. Saber cuándo salir de Python. Si el perfil dice que el 80% del tiempo está en un loop numérico tuyo, ninguna micro-optimización de Python lo va a arreglar. Ahí se vectoriza, o se baja a una extensión nativa (PS8).
4. Saber cuándo NO optimizar. Si el 95% del tiempo lo pasás esperando a la base de datos, el intérprete es irrelevante. Esto es lo más frecuente, y lo que más se ignora.

🧑‍🎓 Worked Example — "el servicio no escala con más hilos"

Un servicio procesa documentos: los baja de S3, extrae texto y calcula un hash de contenido. Con 1 hilo tarda 40 s por lote. Alguien sube a 8 hilos y ahora tarda 38 s. Pregunta: ¿qué pasó?

Paso 1 — No adivinar: medir dónde se va el tiempo.

# py-spy perfila un proceso EN PRODUCCIÓN sin reiniciarlo ni instrumentarlo
uv tool install py-spy
py-spy top --pid 12345
py-spy record --pid 12345 --duration 30 --output perfil.svg

Paso 2 — Leer el resultado. El flamegraph muestra 15% en socket.recv (I/O, libera el GIL) y 78% en la función de extracción de texto, que es Python puro. Ahí está la respuesta: la carga es CPU-bound, no I/O-bound. Los 8 hilos se pelean por el mismo GIL y encima pagan cambios de contexto.

Paso 3 — Las opciones, con su costo.

OpciónGanancia esperadaCosto
ProcessPoolExecutor~N núcleosSerializar datos entre procesos; memoria × N
Free-threading (3.14t)~N núcleos, sin serializarVerificar TODAS las dependencias nativas
Reemplazar la extracción por una librería nativaPuede ser 10×Cambiar dependencia; revalidar resultados
Vectorizar el hash con hashlib sobre buffersMarginal acáBajo

Paso 4 — Decidir y verificar. Se elige procesos porque una dependencia nativa todavía no es compatible con free-threading. Y —esto es lo que separa el trabajo senior— se deja el chequeo escrito para que la decisión no se degrade sola:

import sys, pytest

@pytest.mark.skipif(sys._is_gil_enabled(), reason="build con GIL: paralelismo por procesos")
def test_free_threading_disponible():
    """Cuando la dependencia nativa se actualice, este test empieza a correr
    y nos avisa que ya podemos volver a hilos y ahorrar la serialización."""
    assert not sys._is_gil_enabled()
📌 La lección del ejercicio no es "usá procesos". Es que hilos vs procesos vs async no se decide por costumbre: se decide mirando un perfil. Y que cada decisión así merece dejar una prueba o una nota que explique por qué, porque dentro de seis meses el motivo ya no va a ser obvio.

Checkpoint — ¿lo tenés claro?

¿Por qué el GIL existe si "solo trae problemas"?

Porque la administración de memoria de CPython es por conteo de referencias, y ese contador se toca en cada asignación, cada paso de un loop y cada llamada. Hacerlo seguro entre hilos requiere sincronización: un candado por objeto significaría millones de operaciones atómicas por segundo, y el resultado medido es que el intérprete de un solo hilo se vuelve más lento. El GIL fue el intercambio pragmático: se penaliza el caso multi-hilo CPU-bound (raro en 1992) para no penalizar el caso de un hilo (el 99%). Free-threading finalmente paga ese costo —5–10% en un hilo— porque los núcleos de hoy hacen que valga la pena.

Estás en el build free-threaded y tu código sigue sin escalar. ¿Qué revisás primero?

sys._is_gil_enabled(). Si devuelve True, alguna extensión C que importaste no se declaró compatible y CPython reactivó el GIL en caliente, sin error visible. Recién si el GIL está realmente apagado tiene sentido buscar la causa en otro lado: contención de un Lock propio, trabajo que en realidad es I/O, o falso compartido de caché.

¿Por qué una lista de un millón de enteros usa mucha más memoria que un array del mismo tamaño?

Porque la lista guarda punteros (8 bytes cada uno) a objetos int que viven aparte en el heap, y cada uno de esos objetos tiene su propio header con refcount y tipo — 28 bytes o más. El array.array y NumPy guardan los valores crudos y contiguos: 8 bytes por número y nada más. Además de la memoria, la diferencia grande es la localidad: recorrer memoria contigua aprovecha la caché de la CPU, mientras que seguir punteros dispersos la desperdicia.

Resumen ejecutivo

  • Todo valor es un objeto en el heap con header: por eso Python pesa y por eso los tipos nativos contiguos ganan por órdenes de magnitud.
  • La memoria se libera por refcounting (determinista) más un GC de ciclos. Los recursos se cierran con with, nunca con __del__.
  • El GIL existe para proteger ese refcounting. Limita solo el CPU-bound en Python puro; el I/O y las extensiones nativas ya escalaban.
  • PEP 779: free-threading es oficialmente soportado en 3.14. Cuesta 5–10% en un hilo y exige que las extensiones C sean compatibles — verificalo con sys._is_gil_enabled(), porque el fallback es silencioso.
  • Sin GIL, las carreras que "funcionaban de casualidad" dejan de funcionar. Lo que siempre estuvo mal, ahora se rompe.
  • El JIT es experimental: importante por lo que habilita a futuro, no por lo que rinde hoy.

🧠 Autoevaluación

1. Corrés tu servicio con python3.14t y el trabajo CPU-bound sigue sin escalar con hilos. ¿Cuál es la primera hipótesis?

Es el fallback silencioso: si una extensión nativa no se declara compatible con free-threading, el intérprete vuelve a activar el GIL sin emitir un error visible. Se confirma en un segundo con sys._is_gil_enabled() — por eso conviene dejar esa verificación en el arranque del servicio, no descubrirlo perfilando.

2. ¿Por qué se recomienda cerrar recursos con with y no con __del__?

El refcounting libera en el acto solo cuando no hay ciclos. Dentro de un ciclo, el objeto lo recoge el GC generacional cuando le toca, así que un __del__ que cierra un archivo o una conexión puede ejecutarse mucho después — o competir con el apagado del intérprete. El with hace el cierre determinista y explícito.

3. El 95% del tiempo de tu servicio se va esperando respuestas de la base de datos. ¿Qué esperás ganar pasándolo al build free-threaded?

El GIL nunca fue el problema en cargas de I/O: se libera mientras el hilo espera, así que los hilos ya escalaban ahí. Free-threading resuelve el caso CPU-bound en Python puro. Encima pagarías la penalidad de 5–10% en un solo hilo a cambio de nada. Es el ejemplo de manual de optimizar donde no está el tiempo.

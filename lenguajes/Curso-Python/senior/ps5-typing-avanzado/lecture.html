PS5 — Typing avanzado

PS5.0 Por qué: los tipos no documentan, cambian el diseño

La forma más común de vender el tipado en Python es la peor: "sirve para documentar". Si eso fuera todo, un docstring alcanzaría. El valor real es otro, y es más incómodo: escribir el tipo te obliga a decir con precisión qué hace tu función, y cuando esa precisión es difícil de expresar, casi siempre es porque la función hace algo mal pensado.

💡 La tesis del módulo. Un tipo que no se puede escribir sin Any, sin diez overload o sin una unión de siete miembros no es un problema del verificador: es una abstracción mal elegida. El sistema de tipos es el detector de humo del diseño. La reacción correcta ante un tipo horrible no es silenciarlo — es preguntarse por qué la función se comporta de tantas maneras distintas.

Un ejemplo mínimo. Alguien escribe esto y no se le ocurre cómo anotarlo:

def procesar(entrada, modo="auto", devolver_todo=False):
    """Si entrada es str, la parsea. Si es dict, la valida.
    Si modo == 'batch', espera una lista. Si devolver_todo, devuelve
    una tupla (resultado, errores, metadata); si no, solo resultado."""

La firma honesta sería algo como str | dict | list[dict] a la entrada y Resultado | tuple[Resultado, list[Error], Meta] a la salida. Ese tipo es feo porque la función es fea: son tres funciones disfrazadas de una. El tipado no inventó el problema, lo hizo visible.

📌 Regla operativa. Cuando pelear con el verificador te lleva más de diez minutos, parás de pelear con el verificador y empezás a mirar el diseño. En el 80% de los casos el Any que estabas por escribir se disuelve si partís la función en dos, o si el dato entra ya validado desde el borde del sistema.

PS5.1 Recordatorio: nadie verifica esto en runtime

Antes de todo lo demás, el hecho que más se olvida: Python ignora las anotaciones al ejecutar. No son casts, no son validaciones, no cuestan nada en tiempo de ejecución.

def duplicar(x: int) -> int:
    return x * 2

duplicar("hola")   # devuelve 'holahola'. Ni un warning. Es Python válido.
duplicar([1, 2])   # devuelve [1, 2, 1, 2]. Tampoco pasa nada.

Quién los verifica, entonces:

QuiénCuándoQué hace
El intérpreteNuncaGuarda las anotaciones y sigue de largo
Verificador estático (mypy, pyright, ty)Antes de ejecutar, en tu editor y en CIAnaliza el código y reporta inconsistencias
Validador de runtime (pydantic, attrs, msgspec)Al construir el objetoVerifica datos reales y convierte o falla

En Python 3.14 cambió cómo se guardan: el PEP 649 hizo que las anotaciones se evalúen de forma diferida, por defecto. Ya no hace falta from __future__ import annotations para poder referenciar una clase que todavía no existe, y desapareció la mayoría de los problemas de referencias circulares en anotaciones.

from annotationlib import get_annotations, Format   # nuevo en 3.14

def enviar(destino: "Servidor", reintentos: int = 3) -> None: ...

get_annotations(enviar)                        # se evalúan recién acá
get_annotations(enviar, format=Format.STRING)  # {'destino': 'Servidor', ...}
                                               # sin evaluar nada
Consecuencia práctica: una anotación que antes rompía el import ahora solo rompe si alguien la lee. Las librerías que introspeccionan tipos (pydantic, FastAPI, ORMs) usan annotationlib; tu código de aplicación, en general, no toca esto nunca.

PS5.2 Protocol: interfaces sin herencia

Python siempre fue duck typing: importa lo que el objeto sabe hacer, no de quién hereda. Protocol es exactamente eso, pero verificable. Se llama tipado estructural: un tipo encaja si tiene la forma correcta, sin declarar nada.

from typing import Protocol

class Cerrable(Protocol):
    def close(self) -> None: ...

def usar_y_cerrar(recurso: Cerrable) -> None:
    try:
        ...
    finally:
        recurso.close()

class MiSocket:            # NO hereda de Cerrable. No la conoce.
    def close(self) -> None:
        print("cerrado")

usar_y_cerrar(MiSocket())  # ✅ encaja por forma
usar_y_cerrar(open("x"))   # ✅ los archivos también tienen close()

Lo poderoso es que funciona con clases que no controlás: la de una librería de terceros, la del stdlib, un mock de tus tests. No hace falta registrarlas ni modificarlas.

from collections.abc import Iterator
from typing import Protocol

class RepositorioUsuarios(Protocol):
    def obtener(self, user_id: int) -> "Usuario | None": ...
    def listar(self, *, activos: bool = True) -> Iterator["Usuario"]: ...

# El servicio depende del PROTOCOLO, no de la implementación concreta.
class ServicioAltas:
    def __init__(self, repo: RepositorioUsuarios) -> None:
        self._repo = repo

# En tests, un fake común y silvestre encaja sin heredar de nada:
class RepoFalso:
    def __init__(self, datos: dict[int, "Usuario"]) -> None:
        self._datos = datos
    def obtener(self, user_id: int) -> "Usuario | None":
        return self._datos.get(user_id)
    def listar(self, *, activos: bool = True) -> Iterator["Usuario"]:
        yield from self._datos.values()
Si al fake le falta un método o le sobra un parámetro, el verificador te lo dice antes de correr el test. Eso resuelve el problema clásico de los mocks: el test pasa en verde mientras producción explota porque el mock quedó desactualizado respecto de la interfaz real.

El error con @runtime_checkable. Habilita isinstance(), pero la verificación es superficial: comprueba que existan los nombres de los métodos, no sus firmas ni sus tipos. Una clase con def close(self, forzar, timeout, modo) pasa el isinstance(x, Cerrable) y después explota en la llamada. Usalo para ramificar, nunca como si fuera una validación real.
📌 Heurística. ¿Querés compartir implementación entre clases tuyas? → ABC. ¿Querés describir lo que necesitás de un colaborador que puede venir de cualquier lado? → Protocol. En arquitecturas hexagonales / puertos y adaptadores, los puertos son Protocol casi siempre.

PS5.3 TypeVar, bound, constraints y la sintaxis nueva

Un genérico es una función o clase que preserva la relación entre sus tipos. La diferencia con Any es todo:

from typing import Any

def primero_malo(xs: list[Any]) -> Any: ...
def primero_bien[T](xs: list[T]) -> T: ...      # sintaxis 3.12+

n = primero_malo([1, 2, 3])   # n: Any  → a partir de acá el chequeo MUERE
m = primero_bien([1, 2, 3])   # m: int  → sigue el chequeo
⚠️ Any es contagioso. No es "un tipo desconocido": es apagá el verificador desde acá para abajo. Un Any devuelto por una función central se propaga por todo el flujo de datos y silencia errores a diez archivos de distancia, sin que nadie se entere. Los verificadores tienen una opción específica para cazarlo (--disallow-any-expr, reportAny), y es de las más útiles.

La sintaxis vieja y la nueva

# Antes de 3.12 — el TypeVar vive fuera y hay que importarlo
from typing import TypeVar
T = TypeVar("T")

def primero(xs: list[T]) -> T:
    return xs[0]

# Desde 3.12 (PEP 695) — el parámetro es parte de la firma
def primero[T](xs: list[T]) -> T:
    return xs[0]

class Pila[T]:                          # clase genérica, sin heredar de Generic
    def __init__(self) -> None:
        self._items: list[T] = []
    def push(self, item: T) -> None:
        self._items.append(item)
    def pop(self) -> T:
        return self._items.pop()

type Json = str | int | float | bool | None | list["Json"] | dict[str, "Json"]
type Pagina[T] = tuple[list[T], str | None]      # alias genérico
type Alias = ... no es un simple =: crea un TypeAliasType con evaluación diferida. Por eso el alias Json de arriba puede referirse a sí mismo — algo que con la forma vieja requería comillas y a veces ni así funcionaba.

bound vs constraints: no son lo mismo

from decimal import Decimal

# BOUND: "cualquier subtipo de X". T puede ser X o cualquier descendiente.
def maximo[T: (int | float | Decimal)](xs: list[T]) -> T: ...

class Entidad:
    id: int

def guardar[E: Entidad](obj: E) -> E:      # E es Entidad o subclase
    print(obj.id)                          # ✅ el bound garantiza .id
    return obj                             # devuelve el subtipo EXACTO

u = guardar(Usuario(...))   # u: Usuario, no Entidad

# CONSTRAINTS: "exactamente uno de estos, elegí". Sin subtipos intermedios.
def unir[S: (str, bytes)](a: S, b: S) -> S:
    return a + b

unir("a", "b")     # ✅ S = str
unir(b"a", b"b")   # ✅ S = bytes
unir("a", b"b")    # ❌ no puede ser str y bytes a la vez

PS5.4 ParamSpec y Concatenate: el caso donde typing gana de verdad

Este es el problema que hizo falta resolver. Un decorador envuelve una función y devuelve otra. Sin ParamSpec, no había forma de decir "la de salida tiene exactamente los mismos parámetros que la de entrada", así que todo decorador anulaba el chequeo de todo lo que decoraba.

from collections.abc import Callable

# ❌ Lo que se escribía antes: la firma se pierde
def loguear(fn: Callable[..., object]) -> Callable[..., object]:
    def envoltura(*args: object, **kwargs: object) -> object:
        print("llamando", fn.__name__)
        return fn(*args, **kwargs)
    return envoltura

@loguear
def transferir(origen: str, destino: str, monto: float) -> bool: ...

transferir("a")                     # 😱 nadie se queja
transferir(1, 2, "mucha plata")     # 😱 tampoco
resultado: int = transferir("a", "b", 10.0)   # 😱 devuelve object/Any

ParamSpec captura la lista completa de parámetros —posicionales, keyword, defaults— como una sola variable:

import functools
from collections.abc import Callable

def loguear[**P, R](fn: Callable[P, R]) -> Callable[P, R]:
    @functools.wraps(fn)
    def envoltura(*args: P.args, **kwargs: P.kwargs) -> R:
        print("llamando", fn.__name__)
        return fn(*args, **kwargs)
    return envoltura

@loguear
def transferir(origen: str, destino: str, monto: float) -> bool: ...

transferir("a")                  # ❌ error: falta 'destino' y 'monto'
transferir(1, 2, "mucha plata")  # ❌ error: int no es str
ok: bool = transferir("a", "b", 10.0)   # ✅ bool, no Any
📌 P.args y P.kwargs van siempre juntos y siempre así. No son tipos que puedas usar en otro lado: son la forma canónica de reenviar los argumentos. Si escribís *args: P.args sin el **kwargs: P.kwargs, el verificador lo rechaza.

Concatenate: cuando el decorador agrega o consume un parámetro

ParamSpec solo sirve si la firma queda idéntica. Si tu decorador inyecta un argumento (una conexión, un usuario autenticado, un span de tracing), la firma de salida es la de entrada menos ese primer parámetro. Eso es Concatenate:

import functools
from collections.abc import Awaitable, Callable
from typing import Concatenate

def con_conexion[**P, R](
    fn: Callable[Concatenate[Conexion, P], Awaitable[R]],
) -> Callable[P, Awaitable[R]]:
    """Toma una función cuyo PRIMER parámetro es una Conexion
    y devuelve otra sin ese parámetro: lo inyecta el decorador."""
    @functools.wraps(fn)
    async def envoltura(*args: P.args, **kwargs: P.kwargs) -> R:
        async with pool.acquire() as conn:
            return await fn(conn, *args, **kwargs)
    return envoltura

@con_conexion
async def buscar_usuario(conn: Conexion, user_id: int) -> Usuario: ...

await buscar_usuario(42)      # ✅ la conexión NO se pasa: la pone el decorador
await buscar_usuario("42")    # ❌ error: str no es int
await buscar_usuario(conn, 42)  # ❌ error: sobra un argumento
💡 Por qué esto importa tanto. Los decoradores están en el camino crítico de casi toda app real: rutas HTTP, tareas de background, reintentos, caché, permisos, transacciones. Si cada uno de ellos devuelve Any, tu proyecto puede tener 100% de anotaciones y cero chequeo efectivo en las funciones que más importan. ParamSpec es la diferencia entre typing decorativo y typing que atrapa bugs.

PS5.5 Self, Never, LiteralString, Final, ClassVar

Cinco piezas chicas que resuelven cinco problemas concretos.

from typing import ClassVar, Final, LiteralString, Never, Self

# ── Self: métodos encadenables que respetan la subclase ──────────────
class Query:
    def where(self, cond: str) -> Self:      # NO "-> Query"
        self._conds.append(cond)
        return self

class QueryPostgres(Query):
    def returning(self, col: str) -> Self: ...

q = QueryPostgres().where("id = 1").returning("id")   # ✅ sigue siendo Postgres
# Con "-> Query", el .where() degradaba el tipo y .returning() era un error.

# ── Never: esta función no vuelve nunca ──────────────────────────────
def abortar(msg: str) -> Never:
    raise RuntimeError(msg)

def clasificar(x: int | str) -> str:
    if isinstance(x, int):
        return "número"
    elif isinstance(x, str):
        return "texto"
    abortar("imposible")   # ✅ el verificador acepta que no falta un return

# ── LiteralString: defensa de tipos contra inyección SQL ─────────────
def ejecutar(sql: LiteralString) -> None: ...

ejecutar("SELECT * FROM usuarios")           # ✅ literal del código
tabla: LiteralString = "usuarios"
ejecutar(f"SELECT * FROM {tabla}")           # ✅ compuesto de literales
ejecutar(f"SELECT * FROM {entrada_web}")     # ❌ error: str común

# ── Final y ClassVar ────────────────────────────────────────────────
class Reintentos:
    MAXIMO: Final = 5                # no se puede reasignar ni sobrescribir
    activos: ClassVar[int] = 0       # atributo de CLASE, no de instancia

    def __init__(self, tope: int) -> None:
        self.tope = tope

Reintentos.MAXIMO = 10               # ❌ error: es Final
ClassVar además es obligatorio en dataclasses: un atributo anotado sin ClassVar se convierte en campo de instancia. Con ClassVar, la dataclass lo ignora y queda como estado de la clase — que es lo que casi siempre querías con ese contador o ese registro.

PS5.6 overload: cuando el retorno depende del argumento

Hay funciones cuyo tipo de salida cambia según lo que les pasás. Devolver str | bytes es correcto pero inútil: obliga a quien llama a hacer isinstance aunque sepa perfectamente qué pidió. @overload declara las combinaciones válidas una por una:

from typing import Literal, overload

@overload
def leer(ruta: str, *, binario: Literal[True]) -> bytes: ...
@overload
def leer(ruta: str, *, binario: Literal[False] = False) -> str: ...

def leer(ruta: str, *, binario: bool = False) -> str | bytes:
    """La implementación real: no se anota con overload y NO la ve quien llama."""
    modo = "rb" if binario else "r"
    with open(ruta, modo) as f:
        return f.read()

texto = leer("a.txt")                   # texto: str
datos = leer("a.bin", binario=True)     # datos: bytes
texto.upper()                           # ✅ sin isinstance, sin cast

El otro uso clásico es None como default distinguible:

@overload
def buscar(uid: int) -> Usuario | None: ...
@overload
def buscar(uid: int, *, default: Usuario) -> Usuario: ...

def buscar(uid: int, *, default: Usuario | None = None) -> Usuario | None:
    return _tabla.get(uid, default)

buscar(1).nombre                       # ❌ error: puede ser None
buscar(1, default=ANONIMO).nombre      # ✅ nunca es None
Los overload son un olor cuando se multiplican. Dos o tres describen un comportamiento genuinamente polimórfico. Siete significan que la función tiene siete modos y debería ser siete funciones (o una función más un par de helpers). Volvé a PS5.0: el tipo difícil está señalando el diseño.

PS5.7 TypedDict, NamedTuple, dataclass: cuál usar

TypedDict le pone forma a un diccionario. En runtime es un dict común: no hay clase, no hay validación, no hay costo.

from typing import NotRequired, Required, TypedDict

class Evento(TypedDict):

e2: Evento = {"tipo": "click"}                 # ❌ falta 'ts'
e3: Evento = {"tipo": "click", "ts": 1.0, "x": 5}   # ❌ clave desconocida

# Al revés: todo opcional salvo lo marcado
class Filtros(TypedDict, total=False):

PS5.8 Narrowing: TypeGuard vs TypeIs

Narrowing (afinado) es cuando el verificador reduce un tipo dentro de una rama. Lo hace solo, con las construcciones de siempre:

def procesar(x: int | str | None) -> str:
    if x is None:
        return "vacío"          # acá x es None
    if isinstance(x, int):
        return str(x * 2)       # acá x es int
    return x.upper()            # acá x es str, y el verificador lo sabe

def obtener(config: dict[str, str]) -> str:
    valor = config.get("host")          # str | None
    assert valor is not None, "falta host"
    return valor.upper()                # ✅ afinado a str por el assert

# Walrus: asignar y afinar en la misma línea
if (m := patron.match(texto)) is not None:
    print(m.group(1))                   # m es Match, no Match | None

El problema aparece cuando la comprobación está dentro de una función tuya: el verificador no puede mirar adentro, así que no afina nada. Para eso están los dos predicados de tipo. Y no son intercambiables.

from typing import TypeGuard, TypeIs

def es_str_guard(x: object) -> TypeGuard[str]:
    return isinstance(x, str)

def es_str_is(x: object) -> TypeIs[str]:
    return isinstance(x, str)

def con_guard(x: int | str) -> None:
    if es_str_guard(x):
        reveal_type(x)    # str
    else:
        reveal_type(x)    # int | str   ← ❗ NO se afinó el else

def con_is(x: int | str) -> None:
    if es_str_is(x):
        reveal_type(x)    # str
    else:
        reveal_type(x)    # int        ← ✅ el else también se afina

# El caso donde TypeGuard sigue siendo necesario:
# list[str] NO es subtipo de list[object] (list es invariante — ver PS5.9),
# así que TypeIs lo rechazaría.
def son_todos_str(xs: list[object]) -> TypeGuard[list[str]]:
    return all(isinstance(x, str) for x in xs)

def unir(xs: list[object]) -> str:
    if son_todos_str(xs):
        return ", ".join(xs)     # ✅ xs es list[str]
    raise TypeError("se esperaban strings")
⚠️ Ninguno de los dos verifica nada. TypeIs y TypeGuard le prometen al verificador que tu función devuelve True exactamente cuando el valor es de ese tipo. Si tu implementación miente —revisa mal, se olvida un caso, chequea el largo en vez del contenido— el verificador te va a creer y el error va a aparecer en producción, con el tipo "confirmado". Estas dos anotaciones son de las poquísimas donde el chequeo estático depende de que vos tengas razón.

PS5.9 Varianza: por qué list[int] no es un list[float]

La pregunta es: si int es compatible con float, ¿list[int] es compatible con list[float]? La respuesta de Python es no, y el error confunde a todo el mundo la primera vez.

def promedio(xs: list[float]) -> float:
    return sum(xs) / len(xs)

enteros: list[int] = [1, 2, 3]
promedio(enteros)
# error: Argument 1 has incompatible type "list[int]"; expected "list[float]"

No es un capricho. Si se permitiera, esto sería legal y rompería en runtime:

def sabotear(xs: list[float]) -> None:
    xs.append(3.14)          # perfectamente válido para una list[float]

enteros: list[int] = [1, 2, 3]
sabotear(enteros)            # si list fuera covariante, esto pasaría
enteros[3] << 2              # 💥 TypeError: 3.14 no soporta shift
💡 La regla de una línea. Un contenedor donde podés escribir tiene que ser invariante, porque escribir permite meter algo que rompa al que lo lee. Un contenedor de solo lectura puede ser covariante sin peligro. Por eso list es invariante y Sequence es covariante. 
from collections.abc import Sequence

def promedio(xs: Sequence[float]) -> float:   # ✅ el arreglo correcto
    return sum(xs) / len(xs)

promedio([1, 2, 3])              # ✅ list[int] encaja
promedio((1.5, 2.5))             # ✅ una tupla también
promedio(range(10))              # ✅ un range también

Manejador = Callable[[ValueError], None]

def manejar_cualquiera(e: Exception) -> None: ...   # acepta MÁS
def manejar_especifico(e: UnicodeError) -> None: ...# acepta MENOS

h1: Manejador = manejar_cualquiera    # ✅ contravarianza en el argumento
h2: Manejador = manejar_especifico    # ❌ le podrían pasar un ValueError común
Con la sintaxis de 3.12+ (class Caja[T]) no declarás la varianza: el verificador la infiere de cómo usás T en la clase. Si solo aparece en retornos, sale covariante; si aparece en parámetros de métodos, invariante. Es una razón más para migrar a PEP 695.
📌 Regla de oro para firmas públicas. Pedí Sequence, Iterable o Mapping en los parámetros; devolvé list o dict concretos en el retorno. Sé flexible en lo que aceptás y específico en lo que entregás. La mayoría de los errores de varianza que vas a ver desaparecen con solo aplicar esto.

PS5.11 Adoptar strict sin frenar al equipo

El error clásico: prender strict = true en un proyecto de 60.000 líneas, ver 4.000 errores y desactivar el tipado para siempre. La estrategia que funciona es estricto por default, con islas explícitas que se van borrando.

# pyproject.toml
[tool.mypy]
python_version = "3.14"
strict = true                      # el default del proyecto es estricto
warn_unused_ignores = true         # avisa cuando un ignore ya no hace falta
warn_unreachable = true

# Isla 1: código viejo que todavía no se tipó. Se va achicando.
[[tool.mypy.overrides]]
module = ["miapp.legacy.*", "miapp.reportes.batch"]
disallow_untyped_defs = false
disallow_incomplete_defs = false

# Isla 2: dependencias sin stubs. No es deuda nuestra.
[[tool.mypy.overrides]]
module = ["libreria_vieja.*", "sdk_del_proveedor.*"]
ignore_missing_imports = true
1. Empezá por el módulo nuevo, no por el viejo. Todo archivo creado desde hoy nace en strict. Eso frena el crecimiento de la deuda sin tocar una línea existente.
2. Listá las islas, no las escondas. Los overrides por módulo son visibles en el pyproject.toml y se pueden contar. Un # type: ignore disperso, no.
3. Poné un trinquete en CI. El número de errores solo puede bajar. Cualquiera puede mejorarlo; nadie puede empeorarlo. Es la mecánica que hace que la migración avance sin un proyecto dedicado.
#!/usr/bin/env bash
# scripts/trinquete_tipos.sh — falla si la deuda de tipos aumentó
set -euo pipefail
TOPE=$(cat .mypy_tope)
ACTUAL=$(uv run mypy miapp 2>/dev/null | grep -c "^.*error:" || true)

if [ "$ACTUAL" -gt "$TOPE" ]; then
  echo "❌ Los errores de tipos subieron: $TOPE -> $ACTUAL"; exit 1
fi
if [ "$ACTUAL" -lt "$TOPE" ]; then
  echo "$ACTUAL" > .mypy_tope
  echo "✅ Bajó a $ACTUAL. Commiteá .mypy_tope."
fi
4. Tipá primero las fronteras internas. Los módulos que todos importan —modelos de dominio, clientes de servicios, utilidades compartidas— rinden mucho más que las hojas del árbol: un tipo bueno ahí se propaga a todos sus consumidores.
5. Cuando pongas un type: ignore, ponele código y motivo. # type: ignore[arg-type] # el SDK miente en el stub, ver #4821. Con warn_unused_ignores, el día que el stub se arregle mypy te avisa que ese ignore sobra y lo borrás.

PS5.12 Runtime vs estático: dónde SÍ hace falta validar

Esta es la confusión más cara del tipado en Python. Las anotaciones te protegen de tus propios errores al escribir código. No te protegen de nada de lo que entra al proceso desde afuera.

# ❌ Una mentira con forma de tipo
import json

def cargar_config(ruta: str) -> dict[str, int]:
    return json.load(open(ruta))     # json.load devuelve Any

cfg = cargar_config("app.json")
cfg["puerto"] + 1                    # 💥 TypeError si el JSON traía "8080"
⚠️ El tipo dice dict[str, int] y el verificador está conforme. Pero nadie miró el archivo. json.load devuelve Any, y Any se acomoda a lo que le pidas. Anotar un borde no valida el borde: solo lo documenta y silencia al verificador, que es lo peor de los dos mundos.

En los bordes va validación de verdad, con datos reales:

from pydantic import BaseModel, Field, ValidationError

class ConfigApp(BaseModel):
    host: str
    puerto: int = Field(ge=1, le=65535)
    workers: int = Field(default=4, ge=1)
    debug: bool = False

    model_config = {"extra": "forbid"}   # clave desconocida = error, no silencio

def cargar_config(ruta: str) -> ConfigApp:
    try:
        return ConfigApp.model_validate_json(Path(ruta).read_text())
    except ValidationError as e:
        raise SystemExit(f"Config inválida en {ruta}:\n{e}") from e

cfg = cargar_config("app.json")
cfg.puerto + 1     # ✅ ahora sí: es int de verdad, verificado con el archivo

📌 El patrón se llama "validar en el borde". Se valida una vez, al entrar el dato al proceso, y desde ahí para adentro se confía en los tipos. Validar en cada capa es lento, redundante y hace que nadie sepa dónde está la verdad. Validar en ninguna es cómo llegan a producción los None inesperados.

PS5.13 Cuándo el tipado es contraproducente

1. Scripts de una sola vez. Un análisis exploratorio, un notebook, un script que corre hoy y se borra mañana. El costo de anotar no se amortiza porque no hay mantenimiento futuro.
2. Código genuinamente dinámico. Metaprogramación, plugins descubiertos en runtime, decoradores que reescriben clases (PS4). A veces el tipo honesto es Any, y encerrarlo en un Any explícito y comentado es mejor que quince líneas de gimnasia con cast.
3. Cuando estás tipando para el verificador y no para el lector. Si una firma tiene tres TypeVar, un ParamSpec, dos overload y nadie del equipo puede explicarla, esa firma ya no ayuda a nadie. Simplificá el diseño o aceptá un tipo más flojo y honesto.
4. Anotar todo con Any para llegar al 100%. Es peor que no anotar: instala confianza falsa. Un archivo sin anotaciones se ve sin anotaciones; uno lleno de Any se ve tipado y no verifica nada.
5. Con librerías sin stubs decentes. Si el 40% de tu código toca un SDK que no tiene tipos, vas a escribir más type: ignore que lógica. Ahí conviene envolver el SDK en una capa fina, tipada a mano, y tener un solo lugar sucio en vez de cincuenta.
El contraejemplo importante: nada de esto aplica a librerías. Si publicás un paquete, tus tipos son parte de tu API pública y le ahorran horas a cada persona que lo usa. Ahí el tipado estricto no se discute — y acordate del py.typed, sin ese archivo tus anotaciones son invisibles para quien te instala.

🧑‍🎓 Worked Example — tipar un decorador async con parámetros

Necesitás un decorador @reintentar(veces=3, espera=0.5) que envuelva funciones async y reintente ante fallos de red con backoff exponencial. Tiene que preservar la firma exacta de lo que decora. Es el caso de uso más común de ParamSpec y también el que más gente escribe mal.

Paso 1 — La versión que escribe todo el mundo.

import asyncio, functools

def reintentar(veces: int = 3, espera: float = 0.5):
    def decorador(fn):
        @functools.wraps(fn)
        async def envoltura(*args, **kwargs):
            for intento in range(veces):
                try:
                    return await fn(*args, **kwargs)
                except (TimeoutError, ConnectionError):
                    if intento == veces - 1:
                        raise
                    await asyncio.sleep(espera * 2 ** intento)
        return envoltura
    return decorador

Funciona perfecto en runtime. Y desde el punto de vista de los tipos es una catástrofe silenciosa:

@reintentar(veces=5)
async def cobrar(cliente_id: int, monto: float, moneda: str = "ARS") -> Recibo:
    ...

# TODO esto pasa el verificador sin una queja:
await cobrar()                             # 😱 faltan dos argumentos
await cobrar("42", "mucha plata")          # 😱 los tipos están al revés
await cobrar(1, 100.0, moneda=b"USD")      # 😱 bytes donde va str
recibo: int = await cobrar(1, 100.0)       # 😱 Recibo asignado a un int
⚠️ El daño no termina en la función decorada. cobrar(...) ahora devuelve Any, así que recibo es Any, y todo lo que hagas con recibo —pasarlo a otra función, guardarlo, leerle atributos que no existen— también deja de verificarse. Un decorador mal tipado apaga el chequeo de una rama entera del programa, y como no genera ningún error, nadie lo nota nunca.

Paso 2 — Confirmarlo, no suponerlo.

reveal_type(cobrar)

# basedpyright  (reportAny está prendido por default)

Paso 3 — La versión correcta, con ParamSpec.

import asyncio, functools
from collections.abc import Awaitable, Callable

def reintentar[**P, R](
    veces: int = 3,
    espera: float = 0.5,
    excepciones: tuple[type[Exception], ...] = (TimeoutError, ConnectionError),
) -> Callable[[Callable[P, Awaitable[R]]], Callable[P, Awaitable[R]]]:
    """Devuelve un decorador que toma una async (P) -> R
    y devuelve otra async (P) -> R: los MISMOS parámetros, el MISMO retorno."""
    def decorador(fn: Callable[P, Awaitable[R]]) -> Callable[P, Awaitable[R]]:
        @functools.wraps(fn)
        async def envoltura(*args: P.args, **kwargs: P.kwargs) -> R:
            ultimo: Exception | None = None
            for intento in range(veces):
                try:
                    return await fn(*args, **kwargs)
                except excepciones as exc:
                    ultimo = exc
                    if intento < veces - 1:
                        await asyncio.sleep(espera * 2 ** intento)
            assert ultimo is not None      # el bucle corrió al menos una vez
            raise ultimo
        return envoltura
    return decorador

Leído de afuera hacia adentro, el tipo de retorno de reintentar se lee literalmente: "una cosa que recibe una función async de parámetros P que devuelve R, y entrega otra función async de los mismos parámetros P que devuelve el mismo R". Ese es todo el contrato.

Paso 4 — Ahora sí, los errores aparecen.

reveal_type(cobrar)

await cobrar(1, 100.0, moneda=b"USD") # ❌ error: bytes no es str
recibo: int = await cobrar(1, 100.0)  # ❌ error: Recibo no es int
recibo2: Recibo = await cobrar(1, 100.0)   # ✅

Paso 5 — La variante con Concatenate. Si además querés que el decorador inyecte algo —el intento actual, un span, una conexión— la firma de salida ya no es igual a la de entrada, y ParamSpec solo no alcanza:

from typing import Concatenate

def con_intento[**P, R](
    fn: Callable[Concatenate[int, P], Awaitable[R]],   # 1er param: nro de intento
) -> Callable[P, Awaitable[R]]:
    @functools.wraps(fn)
    async def envoltura(*args: P.args, **kwargs: P.kwargs) -> R:
        for intento in range(3):
            try:
                return await fn(intento, *args, **kwargs)
            except ConnectionError:
                if intento == 2:
                    raise
        raise AssertionError("inalcanzable")
    return envoltura

@con_intento
async def descargar(intento: int, url: str, *, timeout: float = 5.0) -> bytes:
    print(f"intento {intento} de {url}")
    ...

await descargar("https://x.com")               # ✅ 'intento' lo pone el decorador
await descargar("https://x.com", timeout=1.0)  # ✅ el kwarg sobrevive
await descargar(0, "https://x.com")            # ❌ error: sobra un argumento
📌 Qué detecta la buena que la mala no detectaba. Cantidad de argumentos, tipo de cada argumento posicional, tipo de cada keyword, nombres de los keywords, presencia de los defaults, y el tipo de retorno — más todo lo que se hace con ese retorno aguas abajo. La versión ingenua no detectaba ninguna de esas cosas, y como no fallaba nunca, parecía estar bien. El costo de arreglarla fueron dos líneas de anotación.
Y no te olvides de functools.wraps. Sin él, la función pierde __name__, __doc__, __wrapped__ y __annotations__. Los tipos estáticos quedan bien igual, pero se rompe todo lo que introspecciona en runtime: los logs muestran envoltura, pytest no encuentra los fixtures, FastAPI no arma el esquema y inspect.signature miente. Estático y runtime son dos problemas distintos: ParamSpec arregla uno, wraps el otro.

Checkpoint — ¿lo tenés claro?

¿Por qué un decorador sin ParamSpec es peor que no tener tipos en esa función?

Porque una función sin anotar se nota: el verificador puede reportarla con disallow_untyped_defs, y quien la lee ve que no hay contrato. Un decorador que devuelve Callable[..., Any] se ve tipado, no dispara ninguna regla, y además convierte en Any el resultado de cada llamada. Ese Any se propaga: todo lo que reciba ese valor deja de verificarse, en archivos que ni saben que existe el decorador. Es una fuga silenciosa de chequeo, y como los decoradores se aplican justo a las funciones más importantes (rutas, tareas, transacciones), la fuga suele estar exactamente donde más duele.

Tenés def es_error(x: object) -> bool y el else de tu if no se afina. ¿Qué cambiás y por qué no TypeGuard?

Cambiás el retorno a TypeIs[Error]. TypeGuard solo afina la rama positiva: en el else el tipo queda tal como estaba, porque su semántica es "si devuelve True, tratalo como T" y no dice nada sobre el caso False. TypeIs tiene semántica de predicado real —"esto es un T, o no lo es"— y por eso el verificador puede restar Error del tipo en el else. El precio es una restricción: el tipo afinado tiene que ser subtipo del parámetro. TypeGuard queda para los casos donde esa relación no existe, como pasar de list[object] a list[str], que por invarianza de list no es una relación de subtipo.

Tu función recibe list[float] y alguien te pasa list[int]. ¿Está mal el verificador?

No, y el arreglo no es un cast. list es invariante porque se puede escribir en ella: si list[int] fuera aceptable donde se pide list[float], tu función podría hacer xs.append(3.14) y corromper la lista del que llamó, que sigue creyendo que tiene enteros. La solución correcta es pedir menos: Sequence[float], que es de solo lectura y por eso puede ser covariante. Como bonus, ahora también aceptás tuplas, range y cualquier otra secuencia. La regla general: parámetros con tipos abstractos y de lectura, retornos con tipos concretos.

Resumen ejecutivo

  • Los tipos cambian el diseño: un tipo difícil de escribir es un síntoma, no un obstáculo. Antes de meter un Any, revisá la abstracción.
  • Python ignora las anotaciones en runtime (y desde 3.14, con PEP 649, ni siquiera las evalúa hasta que alguien las pide). Verifican los checkers estáticos; validan pydantic y compañía.
  • Protocol = tipado estructural, sin herencia, funciona con clases ajenas. ABC = jerarquía nominal con implementación compartida. Puertos y dependencias → Protocol.
  • Sintaxis moderna: def f[T](x: T) -> T, class Pila[T], type Alias = .... Con PEP 695 la varianza se infiere sola.
  • ParamSpec es el caso donde typing gana de verdad: sin él, cada decorador devuelve Any y apaga el chequeo de las funciones más importantes del sistema. Concatenate cubre los decoradores que inyectan o consumen parámetros.
  • Self para APIs encadenables, Never para funciones que no vuelven, LiteralString como defensa contra inyección, Final y ClassVar para constantes y estado de clase.
  • TypeIs afina las dos ramas y es el default; TypeGuard solo la positiva, y queda para conversiones que no son relaciones de subtipo.
  • Varianza: pedí Sequence/Iterable/Mapping, devolvé list/dict. Los contenedores mutables son invariantes por una razón real.
  • 2026: pyright/basedpyright en el editor, mypy en CI, ty observado de cerca pero todavía sin bloquear merges. Nunca dos verificadores bloqueantes a la vez.
  • strict se adopta con islas explícitas en pyproject.toml y un trinquete en CI que solo permite bajar la deuda.
  • Las anotaciones no validan datos. En los bordes —HTTP, archivos, DB, colas, CLI— va pydantic. Adentro del proceso, solo anotaciones.

🧠 Autoevaluación

1. Tu proyecto tiene 100% de funciones anotadas y mypy pasa en verde, pero siguen llegando bugs de tipos a producción en las rutas HTTP. ¿Cuál es la causa más probable?

Es el patrón clásico. Un decorador tipado como Callable[..., Any] hace que la función decorada —y el resultado de cada llamada— sea Any, así que el verificador deja de mirar exactamente las funciones más críticas. Se confirma en un segundo con reveal_type(mi_ruta), y se arregla con ParamSpec (o Concatenate si el decorador inyecta parámetros). Encima nunca genera un error, así que el problema es invisible hasta que lo buscás.

2. Necesitás una función que confirme si un valor es Error, y que el else del if también quede afinado. ¿Qué anotás como retorno?

TypeIs tiene semántica de predicado real: el verificador afina a Error en el if y resta Error del tipo en el else. TypeGuard solo promete algo sobre la rama positiva, así que el else queda con el tipo original. El precio de TypeIs es que el tipo afinado debe ser subtipo del parámetro; cuando esa relación no existe —por ejemplo list[object] a list[str], que la invarianza de list impide— ahí sí hace falta TypeGuard.

3. Una función anotada -> dict[str, int] hace return json.load(f) y explota en runtime porque el JSON traía strings. ¿Cuál es el diagnóstico correcto?

El verificador no puede saber qué hay adentro de un archivo: json.load devuelve Any, y Any se acomoda a cualquier anotación sin protestar. La anotación ahí no describe la realidad, la declara — y encima silencia la sospecha. La regla es "validar en el borde": todo lo que entra al proceso (HTTP, archivos, DB, colas, CLI) pasa por un validador de runtime una sola vez, y de ahí para adentro se confía en los tipos estáticos.

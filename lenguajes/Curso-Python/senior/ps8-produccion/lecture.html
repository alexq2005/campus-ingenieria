PS8 — Python en producción

PS8.0 Por qué este módulo

El código que funciona en tu máquina y el código que aguanta producción se parecen mucho menos de lo que uno cree. En tu máquina el disco es rápido, la red no falla, hay un solo usuario, el proceso vive mientras vos mirás la terminal y, si algo se rompe, lo ves en el momento. En producción nada de eso es cierto: la red se corta a la mitad de una respuesta, el orquestador te manda un SIGTERM con 30 segundos de aviso, hay 400 requests concurrentes de los cuales tres son patológicos, y cuando algo se rompe te enterás por un gráfico media hora después.

💡 La tesis del módulo. Producción no es un lugar: es un conjunto de propiedades que tu proceso tiene que cumplir. Arranca de forma reproducible, falla ruidosamente al configurarse mal, cuenta lo que hace en un formato que una máquina puede leer, sobrevive a que sus dependencias se porten mal, y termina de forma ordenada cuando le avisan. Ninguna de esas cinco propiedades aparece sola: se escriben a mano, y casi todas se escriben antes del primer incidente o se escriben con el sitio caído.

Este módulo cierra el track. PS1–PS5 fueron sobre entender el lenguaje; PS6 y PS7 sobre construir con él; PS8 es sobre entregarlo y sostenerlo. Es también donde Python deja de ser el protagonista: buena parte del trabajo senior consiste en decidir dónde Python es la herramienta correcta, dónde conviene bajar a código nativo, y dónde directamente conviene otra cosa.

PS8.1 Empaquetado: del wheel al contenedor

Hay dos formatos de entrega y sirven para cosas distintas. El wheel (.whl) es un artefacto de librería: código ya construido, sin paso de compilación en destino, instalable con uv pip install o pip. El contenedor es un artefacto de servicio: incluye el intérprete, las dependencias nativas del sistema y el entrypoint.

# Wheel: para lo que otros van a importar (una librería, un SDK interno)
uv build                      # deja dist/paquete-1.4.2-py3-none-any.whl y el sdist
uv publish --index interno    # a tu índice privado

# Contenedor: para lo que se despliega y corre
docker build -t servicio:1.4.2 .
📌 Nunca instales en producción desde el repositorio. Ni git clone, ni uv sync contra un pyproject.toml sin lock. El artefacto que probaste en CI tiene que ser bit a bit el que corre en producción. Todo lo demás es una apuesta a que nadie publicó una versión nueva de una transitiva entre el test y el deploy.

El Dockerfile multi-stage con uv

La idea del multi-stage es simple: una etapa construye (con compiladores, headers, herramientas) y otra etapa corre (solo el runtime). Lo que quedó en la primera no viaja a la imagen final.

# ── Etapa 1: build ────────────────────────────────────────────────
FROM python:3.13-slim-bookworm AS builder

# uv como binario estático, versionado. Nada de "curl | sh" sin pin.
COPY --from=ghcr.io/astral-sh/uv:0.9.2 /uv /uvx /bin/

ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy \
    UV_PYTHON_DOWNLOADS=never

WORKDIR /app

# Primero SOLO los manifiestos: si no cambian, esta capa sale de caché
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-install-project --no-dev

# Recién ahora el código, que cambia en cada commit
COPY src/ ./src/
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev

# ── Etapa 2: runtime ──────────────────────────────────────────────
FROM python:3.13-slim-bookworm

RUN groupadd --gid 10001 app \
 && useradd --uid 10001 --gid app --no-create-home --shell /usr/sbin/nologin app

WORKDIR /app
COPY --from=builder --chown=app:app /app/.venv /app/.venv
COPY --from=builder --chown=app:app /app/src   /app/src

ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

USER app
EXPOSE 8000
CMD ["uvicorn", "app.main:api", "--host", "0.0.0.0", "--port", "8000", \
     "--timeout-graceful-shutdown", "25"]
El orden de los COPY es la optimización más rentable del archivo. Copiar pyproject.toml + uv.lock antes que el código hace que la capa de dependencias —la cara, la de 300 MB— solo se reconstruya cuando cambian las dependencias. Un cambio de una línea en tu código pasa de un build de 90 segundos a uno de 8. Y --mount=type=cache le da a uv su caché entre builds sin meterla en la imagen.

# Variante distroless del runtime: sin shell, sin gestor de paquetes, sin root
FROM gcr.io/distroless/python3-debian12:nonroot

WORKDIR /app
COPY --from=builder /app/.venv/lib/python3.13/site-packages /app/deps
COPY --from=builder /app/src /app/src

ENV PYTHONPATH="/app/deps:/app/src" PYTHONUNBUFFERED=1
# distroless no tiene shell: el ENTRYPOINT es exec form obligatorio

Distroless no es gratis. Sin shell no podés hacer kubectl exec y mirar. El precio se paga el día del incidente. La contrapartida moderna son los ephemeral debug containers (kubectl debug), que te adjuntan un contenedor con herramientas al pod sin modificar la imagen. Si no tenés eso disponible en tu plataforma, quedate en slim.
Por qué importa el tamaño, más allá del ego. No es el disco: es el pull. Una imagen de 1 GB en un escalado de emergencia a 40 pods son 40 GB de tráfico y minutos de latencia antes de servir la primera request — justo cuando estás escalando porque te estás cayendo. Y cada paquete de más es una CVE potencial que alguien te va a reportar. Un .dockerignore con .git, .venv, tests/ y __pycache__ suele sacar más peso que cualquier truco elaborado.

PS8.2 Configuración: fallar al arrancar, no en la primera request

La configuración viene del entorno (12-factor), no de un archivo versionado. Pero leer os.environ["DB_URL"] desperdigado por el código tiene tres problemas: no sabés qué variables necesita el servicio hasta que explota, todo es str, y el error aparece en la request 1 en vez de en el arranque.

# app/settings.py
from functools import lru_cache
from typing import Literal

from pydantic import Field, PostgresDsn, field_validator
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",            # solo para desarrollo local
        env_prefix="APP_",
        extra="forbid",             # una variable APP_* desconocida es un error
        frozen=True,                # inmutable: nadie la muta en caliente
    )

    entorno: Literal["dev", "staging", "prod"] = "dev"
    db_url: PostgresDsn                                   # sin default: OBLIGATORIA
    api_key_pagos: str = Field(min_length=32, repr=False) # repr=False: no se imprime
    timeout_http_s: float = Field(default=5.0, gt=0, le=30)
    max_reintentos: int = Field(default=3, ge=0, le=5)
    drenaje_s: float = Field(default=5.0, ge=0)
    log_level: Literal["DEBUG", "INFO", "WARNING", "ERROR"] = "INFO"

    @field_validator("log_level")
    @classmethod
    def prod_no_debuguea(cls, v: str, info) -> str:
        if info.data.get("entorno") == "prod" and v == "DEBUG":
            raise ValueError("DEBUG en prod filtra payloads enteros a los logs")
        return v


@lru_cache
def get_settings() -> Settings:
    return Settings()          # type: ignore[call-arg]

Lo importante no es pydantic: es dónde se llama. Si get_settings() se invoca en el módulo de arranque, un typo en una variable de entorno mata el proceso en el segundo cero y el orquestador nunca lo pone en rotación. Si se invoca perezosamente dentro de un handler, el pod arranca "sano", recibe tráfico y devuelve 500 a usuarios reales.

# app/main.py — la validación ocurre ANTES de abrir el puerto
import sys
from pydantic import ValidationError

try:
    settings = get_settings()
except ValidationError as e:
    # A stderr y en texto legible: esto lo lee un humano mirando `kubectl logs`
    print("Configuración inválida — el servicio NO arranca:", file=sys.stderr)
    print(e, file=sys.stderr)
    raise SystemExit(78)        # EX_CONFIG de sysexits.h
El antipatrón clásico: os.getenv("TIMEOUT", "5") repartido por diez archivos. Cada default silencioso es un bug que no vas a ver: el día que alguien escribe TIMEOOUT=30 en el manifiesto, el servicio sigue usando 5 y nadie se entera hasta que se cae por timeouts. Por eso extra="forbid": una variable con prefijo APP_ que el modelo no conoce es un error de arranque, no un silencio.
⚠️ Secretos: no van acá. Una variable de entorno es visible en /proc/<pid>/environ, en un docker inspect, en un core dump y en el manifiesto que alguien pegó en un chat. Para credenciales reales lo que corresponde es un gestor (Vault, AWS Secrets Manager, SOPS, External Secrets) montado como archivo con rotación, y nunca un secreto en la imagen ni en el repo. El tema completo —incluida la firma de artefactos y el riesgo de supply chain de tus propias dependencias— está en M07 · Secretos y supply chain del Curso de Ciberseguridad. Leelo antes de tu primer deploy real.

PS8.3 Logging estructurado

Un log en texto libre es cómodo para vos y un problema para todos los demás. "usuario 4821 falló al pagar: timeout" obliga a que la herramienta de observabilidad adivine con expresiones regulares. Un log estructurado emite un objeto JSON por evento, y todo campo se vuelve consultable, agregable y alertable.

# app/logging_setup.py
import logging
import structlog
from opentelemetry import trace


def agregar_traza(_, __, evento: dict) -> dict:
    """Cose cada log a la traza distribuida que lo originó (PS8.4)."""
    ctx = trace.get_current_span().get_span_context()
    if ctx.is_valid:
        evento["trace_id"] = format(ctx.trace_id, "032x")
        evento["span_id"] = format(ctx.span_id, "016x")
    return evento


def configurar(nivel: str, json: bool) -> None:
    procesadores = [
        structlog.contextvars.merge_contextvars,   # contexto por request
        structlog.processors.add_log_level,
        structlog.processors.TimeStamper(fmt="iso", utc=True),
        agregar_traza,
        structlog.processors.StackInfoRenderer(),
        structlog.processors.format_exc_info,
    ]
    procesadores.append(
        structlog.processors.JSONRenderer() if json
        else structlog.dev.ConsoleRenderer()      # coloreado, para tu terminal
    )
    structlog.configure(
        processors=procesadores,
        wrapper_class=structlog.make_filtering_bound_logger(
            logging.getLevelName(nivel)
        ),
        cache_logger_on_first_use=True,
    )

El id de correlación es lo que convierte cien líneas sueltas en la historia de una request. Se genera (o se hereda de un header) una vez, se guarda en un contextvar y aparece solo en todos los logs de esa request, incluidos los de las corrutinas hijas:

import uuid
import structlog
from starlette.middleware.base import BaseHTTPMiddleware

log = structlog.get_logger()


class ContextoRequest(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        structlog.contextvars.clear_contextvars()
        rid = request.headers.get("x-request-id") or str(uuid.uuid4())
        structlog.contextvars.bind_contextvars(
            request_id=rid,
            ruta=request.url.path,
            metodo=request.method,
        )
        respuesta = await call_next(request)
        respuesta.headers["x-request-id"] = rid   # se lo devolvemos al cliente
        return respuesta

📌 Qué NO loguear, nunca. Contraseñas, tokens, cookies de sesión, headers Authorization, números de tarjeta, el cuerpo completo de un request de autenticación. Y —esto se olvida— datos personales: nombre, mail, teléfono, dirección. Un log es un almacén de datos con retención larga, acceso amplio y respaldos: todo lo que entra ahí queda bajo el mismo régimen legal que tu base de datos. Loguéa identificadores (usuario_id=4821), no identidades.
Reforzalo con código, no con disciplina: un procesador de structlog que recorra el evento y reemplace por "***" cualquier clave que matchee password|token|secret|authorization|card. Cuesta quince líneas y te cubre del día que alguien loguee un dict entero "para depurar rápido".

PS8.4 OpenTelemetry: un estándar para las tres señales

Durante años cada señal tuvo su herramienta y su formato: métricas en un lado, trazas en otro, logs en un tercero, y ninguna forma de cruzarlas. OpenTelemetry (OTel) es el estándar que unifica trazas, métricas y logs bajo un mismo modelo de datos, un mismo protocolo (OTLP) y una misma noción de contexto — de modo que un log, una métrica y un span de la misma operación comparten trace_id.

La analogía útil. Las métricas son el tablero del auto: te dicen que algo anda mal (temperatura alta) y son baratas de guardar por años. Las trazas son abrir el capó de un viaje concreto: te muestran exactamente dónde se fue el tiempo. Los logs son lo que el conductor anotó en ese momento. Vas de la métrica a la traza a los logs, en ese orden. Empezar por los logs es abrir el capó de un auto al azar.

La instrumentación automática no requiere tocar tu código: envuelve las librerías conocidas (FastAPI, httpx, SQLAlchemy, redis, psycopg) y produce spans para cada request entrante, cada query y cada llamada saliente.

uv add opentelemetry-distro opentelemetry-exporter-otlp
uv run opentelemetry-bootstrap -a install     # detecta tus libs e instala sus instrumentaciones

# Se activa envolviendo el comando; el código no cambia
OTEL_SERVICE_NAME=checkout \
OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4318 \
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf \
OTEL_RESOURCE_ATTRIBUTES="service.version=1.4.2,deployment.environment=prod" \
OTEL_TRACES_SAMPLER=parentbased_traceidratio \
OTEL_TRACES_SAMPLER_ARG=0.1 \
  uv run opentelemetry-instrument uvicorn app.main:api --host 0.0.0.0

La manual es para lo que solo vos sabés que existe: una etapa de negocio, un cálculo caro, una decisión. La regla es instrumentar las fronteras semánticas, no cada función.

from opentelemetry import trace

tracer = trace.get_tracer("app.checkout")


async def cobrar(orden_id: str, monto_centavos: int) -> Resultado:
    with tracer.start_as_current_span("checkout.cobrar") as span:
        span.set_attribute("orden.id", orden_id)
        span.set_attribute("orden.monto_centavos", monto_centavos)
        try:
            resultado = await proveedor.cargar(orden_id, monto_centavos)
        except TimeoutError as e:
            span.record_exception(e)
            span.set_status(trace.StatusCode.ERROR, "timeout del proveedor")
            raise
        span.set_attribute("pago.proveedor_id", resultado.id)
        return resultado
Cardinalidad: el error caro. Un atributo de span puede ser único por request (orden.id) sin problema. Una etiqueta de métrica no: cada combinación distinta de etiquetas crea una serie temporal nueva. Poner usuario_id como label de un contador es la forma canónica de multiplicar por diez la factura del backend de métricas y tumbarlo. Alta cardinalidad va en trazas y logs; en métricas van solo dimensiones acotadas (ruta, metodo, status).
Qué mirar primero cuando algo va lento. (1) El gráfico de latencia por percentil: ¿subió el p50 —todo está lento— o solo el p99 —una minoría sufre—? (2) Una traza lenta de ese período, no una cualquiera: la mayoría de los backends te dejan filtrar por duración. (3) En esa traza, el span más ancho: ahí está el tiempo. (4) Los logs de ese trace_id. Cuatro pasos, cinco minutos. Sin trazas, el mismo diagnóstico son dos horas de leer logs.

PS8.5 Las métricas que importan

Se pueden medir mil cosas. Tres explican casi todos los incidentes, y son las del método RED: Rate (requests por segundo), Errors (proporción de fallos) y Duration (latencia, en percentiles).

from opentelemetry import metrics

meter = metrics.get_meter("app.http")

duracion = meter.create_histogram(
    "http.server.request.duration",     # nombre de la convención semántica de OTel
    unit="s",
    description="Latencia de las requests atendidas",
)

async def middleware_metricas(request, call_next):
    t0 = time.perf_counter()
    status = 500
    try:
        respuesta = await call_next(request)
        status = respuesta.status_code
        return respuesta
    finally:
        duracion.record(
            time.perf_counter() - t0,
            # baja cardinalidad: la PLANTILLA de ruta, no la ruta con el id adentro
            {"http.route": request.scope.get("route_path", "desconocida"),
             "http.request.method": request.method,
             "http.response.status_code": status},
        )

Por qué el promedio miente

Supongamos mil requests: 990 tardan 50 ms y 10 tardan 5 segundos. El promedio da 99 ms y parece excelente. La realidad es que uno de cada cien usuarios espera cinco segundos.

MedidaValorQué te dice de verdad
Promedio99 msCasi nada: un solo outlier lo mueve, y esconde la cola entera.
p50 (mediana)50 msLa experiencia típica. Si sube, todo está lento.
p9550 msSigue sano: el problema afecta a menos del 5%.
p995 sAhí está. 1 de cada 100 requests es inaceptable.
p99.95 sLo que sufre tu usuario más activo, que hace 1000 requests por sesión.
💡 La cola es la experiencia real. Si una pantalla dispara 20 llamadas al backend, la probabilidad de que al menos una caiga en el p99 es 1 − 0.99²⁰ ≈ 18%. Es decir: el "1% de requests lentas" se convierte en "casi 1 de cada 5 cargas de pantalla lentas". Por eso los SLO se escriben sobre percentiles altos y no sobre promedios.

La tercera señal es la saturación: qué tan cerca del límite está el recurso más escaso. En un servicio Python asíncrono los sospechosos habituales son el pool de conexiones a la base (¿cuántas esperando?), la profundidad de la cola del event loop, la memoria RSS contra el límite del contenedor, y —si usás procesos— cuántos workers están ocupados. La saturación es la única de las tres que te avisa antes del incidente: la latencia y los errores llegan cuando ya está pasando.

No promedies percentiles. Sacar el promedio del p99 de diez pods no da el p99 del sistema — matemáticamente no significa nada. Los percentiles se calculan agregando los histogramas, que es exactamente lo que hacen Prometheus y OTel. Si tu tablero hace avg(p99), está mintiendo con precisión decimal.

PS8.6 Profiling en producción con py-spy

El perfilador que aprendiste en PS2 sirve mientras podés reproducir el problema. Cuando la lentitud solo ocurre con tráfico real, a las 3 de la tarde, en un pod específico, necesitás otra cosa: py-spy lee la memoria de un proceso vivo desde afuera, sin reiniciarlo, sin instrumentarlo y sin que el proceso sepa que existe.

# Qué está ejecutando AHORA, actualizado como `top`
py-spy top --pid 1

# Volcado instantáneo del stack de cada hilo: ideal para un cuelgue o un deadlock
py-spy dump --pid 1

# 60 segundos de muestreo -> flamegraph interactivo
py-spy record --pid 1 --duration 60 --format speedscope --output perfil.json

# Corrutinas de asyncio: sin --idle solo ves el event loop esperando
py-spy dump --pid 1 --locals
py-spy top  --pid 1 --idle
Para que funcione dentro de un contenedor hace falta SYS_PTRACE. En Docker es --cap-add=SYS_PTRACE; en Kubernetes, o bien la capability en el securityContext, o bien —lo preferible— un contenedor efímero de debug: kubectl debug -it pod/checkout-7f9 --image=ghcr.io/benfred/py-spy --target=app --profile=general. Así no aflojás los permisos del pod de producción de forma permanente.
📌 El overhead de py-spy sobre el proceso observado es prácticamente nulo porque muestrea desde otro proceso: no instala tracing hooks en el intérprete. Esa es la diferencia con cProfile, que puede duplicar el tiempo de ejecución y por eso jamás va a producción. Regla: cProfile para reproducir en tu máquina, py-spy para diagnosticar en la de verdad.

PS8.7 Salud del proceso: probes y apagado ordenado

El orquestador necesita responder dos preguntas distintas, y confundirlas causa incidentes propios.

ProbePreguntaSi falla…Qué debe chequear
liveness¿El proceso está vivo o colgado?Lo matan y reinicianCasi nada: que el event loop responda. Nada de dependencias.
readiness¿Puede atender tráfico ahora?Lo sacan de rotación (sigue vivo)Pool de DB abierto, caché caliente, migraciones aplicadas.
startup¿Terminó de arrancar?Se posterga livenessLo mismo que readiness, con más paciencia.
⚠️ El error que tira toda la flota. Poner el chequeo de la base de datos en el liveness. Si la base tiene un hipo de 40 segundos, todos los pods fallan liveness al mismo tiempo, Kubernetes los mata a todos, todos reintentan conectarse a la vez contra una base ya sufriente y el hipo se convierte en una caída total con efecto rebaño. Liveness responde "estoy vivo"; readiness responde "puedo trabajar". Nunca al revés. 
from fastapi import FastAPI, Response

api = FastAPI(lifespan=ciclo_de_vida)


@api.get("/livez", include_in_schema=False)
async def livez() -> Response:
    # Si el event loop está bloqueado esto ni siquiera se ejecuta: eso ya es la señal
    return Response(status_code=200)


@api.get("/readyz", include_in_schema=False)
async def readyz(response: Response) -> dict:
    if not api.state.listo:
        response.status_code = 503
        return {"listo": False, "motivo": "drenando o arrancando"}
    try:
        await asyncio.wait_for(pool.execute("SELECT 1"), timeout=1.0)
    except Exception:
        response.status_code = 503
        return {"listo": False, "motivo": "base inalcanzable"}
    return {"listo": True}
livenessProbe:
  httpGet: { path: /livez, port: 8000 }
  periodSeconds: 10
  failureThreshold: 3          # 30 s de gracia antes de matar
readinessProbe:
  httpGet: { path: /readyz, port: 8000 }
  periodSeconds: 5
  failureThreshold: 2
startupProbe:
  httpGet: { path: /readyz, port: 8000 }
  periodSeconds: 5
  failureThreshold: 30         # hasta 150 s para arrancar sin que lo maten

terminationGracePeriodSeconds: 40
lifecycle:
  preStop:
    exec: { command: ["sleep", "5"] }   # deja que el LB se entere antes del SIGTERM

Shutdown ordenado ante SIGTERM

Cuando Kubernetes quiere terminar un pod manda SIGTERM y arranca un cronómetro; al vencer terminationGracePeriodSeconds manda SIGKILL, que no se puede atrapar. Todo lo que estuvieras haciendo se corta a la mitad. El detalle incómodo: el SIGTERM y la baja del endpoint del balanceador ocurren en paralelo, no en orden, así que durante uno o dos segundos te siguen llegando requests nuevas después de que te avisaron que te vas.

import asyncio
from contextlib import asynccontextmanager

import httpx


@asynccontextmanager
async def ciclo_de_vida(app: FastAPI):
    # ── arranque ──
    app.state.http = httpx.AsyncClient(timeout=TIMEOUTS, limits=LIMITES)
    app.state.pool = await crear_pool(settings.db_url)
    app.state.listo = True
    log.info("servicio_listo", version=settings.version)

    yield                       # acá el servicio atiende tráfico

    # ── apagado (llega con SIGTERM) ──
    app.state.listo = False     # 1. /readyz empieza a devolver 503
    log.info("drenando", segundos=settings.drenaje_s)
    await asyncio.sleep(settings.drenaje_s)   # 2. el LB nos saca de rotación

    # 3. uvicorn ya dejó de aceptar conexiones y espera a las en vuelo
    #    (--timeout-graceful-shutdown 25, menor que los 40 s de gracia del pod)
    await app.state.http.aclose()             # 4. cerrar salientes
    await app.state.pool.close()              # 5. devolver conexiones a la base
    log.info("apagado_limpio")
📌 La aritmética del apagado. drenaje (5 s) + graceful shutdown de uvicorn (25 s) < terminationGracePeriodSeconds (40 s). Si el interior tarda más que el exterior, llega el SIGKILL y perdés justo las requests que estabas intentando terminar bien. Y ojo con el PID 1: si tu CMD arranca a través de un shell (CMD python app.py en shell form), la señal se la come el shell y tu proceso nunca la ve. Usá siempre la forma exec: CMD ["python", "app.py"].

PS8.8 Errores y resiliencia

En producción tus dependencias no fallan: se ponen lentas. Y una dependencia lenta es peor que una caída, porque una caída libera recursos y una lentitud los retiene hasta que se agotan. De ahí la regla que ordena todo este apartado.

📌 Toda llamada de red lleva timeout. Toda. Sin excepción. Un cliente HTTP sin timeout explícito puede esperar indefinidamente. Cien requests esperando indefinidamente es tu pool de conexiones agotado, tu event loop lleno de tareas zombis y tu servicio caído por culpa de otro servicio. El timeout no es una optimización: es el mecanismo que evita que la falla ajena se vuelva tuya. 
import httpx

TIMEOUTS = httpx.Timeout(
    connect=2.0,    # abrir el socket: si tarda más, el destino no está sano
    read=5.0,       # esperar cada chunk de respuesta
    write=5.0,
    pool=1.0,       # esperar un slot libre del pool: ESTE es el que se olvida
)
LIMITES = httpx.Limits(max_connections=100, max_keepalive_connections=20)

# Un cliente por proceso, reutilizado. Crear uno por request tira el keep-alive
# a la basura y te hace pagar el handshake TLS en cada llamada.
cliente = httpx.AsyncClient(timeout=TIMEOUTS, limits=LIMITES)

Reintentos: backoff exponencial y jitter

Reintentar sin pensar es una forma elegante de tirarte el sistema. Si mil clientes fallan al mismo tiempo y todos reintentan a los 100 ms, generás un pico sincronizado que garantiza que el segundo intento también falle — el thundering herd. La solución tiene dos partes: esperar cada vez más (exponencial) y desordenar esas esperas (jitter).

from tenacity import (
    retry, retry_if_exception_type, stop_after_attempt,
    wait_exponential_jitter, before_sleep_log,
)

TRANSITORIOS = (httpx.ConnectError, httpx.ReadTimeout, httpx.PoolTimeout)


@retry(
    retry=retry_if_exception_type(TRANSITORIOS),
    wait=wait_exponential_jitter(initial=0.2, max=4.0, jitter=0.3),
    stop=stop_after_attempt(3),          # 3 intentos, no "hasta que salga"
    before_sleep=before_sleep_log(logger, logging.WARNING),
    reraise=True,
)
async def consultar_inventario(sku: str) -> int:
    r = await cliente.get(f"/inventario/{sku}")
    r.raise_for_status()
    return r.json()["disponible"]
Qué NO reintentar. Un 400, un 401, un 404, un 422: el pedido está mal, repetirlo lo va a seguir estando. Reintentar solo errores transitorios (fallo de conexión, timeout, 429, 503 con Retry-After). Y jamás reintentar una operación no idempotente sin protección: un POST /pagos que sufrió timeout puede haberse ejecutado del otro lado, y el reintento cobra dos veces. 
# Idempotencia: la clave la genera el CLIENTE y viaja con el pedido.
# El servidor la guarda con la respuesta; si la vuelve a ver, devuelve la misma.
async def cobrar_idempotente(orden_id: str, monto: int, clave: str) -> Resultado:
    if (previa := await cache.get(f"idem:{clave}")) is not None:
        log.info("idempotencia_hit", clave=clave)
        return Resultado.model_validate_json(previa)

    resultado = await cliente.post(
        "/cargos",
        json={"orden": orden_id, "monto": monto},
        headers={"Idempotency-Key": clave},   # el proveedor serio también la respeta
    )
    await cache.set(f"idem:{clave}", resultado.text, ex=86_400)
    return Resultado.model_validate_json(resultado.text)

Circuit breaker

El reintento asume que la falla es puntual. Cuando la dependencia está realmente caída, reintentar solo agrega carga a algo que ya no puede responder y consume tus propios recursos esperando. El circuit breaker corta: después de N fallos consecutivos abre el circuito y falla de inmediato, sin siquiera intentar, durante un período; después deja pasar una request de prueba.

import time
from enum import Enum


class Estado(Enum):
    CERRADO = "cerrado"        # todo normal, las llamadas pasan
    ABIERTO = "abierto"        # falla rápido, no se llama a nadie
    SEMIABIERTO = "semi"       # deja pasar UNA para ver si se recuperó


class CircuitBreaker:
    def __init__(self, umbral: int = 5, reposo_s: float = 30.0):
        self.umbral, self.reposo_s = umbral, reposo_s
        self.fallos = 0
        self.estado = Estado.CERRADO
        self.abierto_desde = 0.0

    async def llamar(self, fn, *args):
        if self.estado is Estado.ABIERTO:
            if time.monotonic() - self.abierto_desde < self.reposo_s:
                raise CircuitoAbierto("proveedor marcado como caído")
            self.estado = Estado.SEMIABIERTO       # una sonda

        try:
            resultado = await fn(*args)
        except TRANSITORIOS:
            self.fallos += 1
            if self.fallos >= self.umbral or self.estado is Estado.SEMIABIERTO:
                self.estado, self.abierto_desde = Estado.ABIERTO, time.monotonic()
                log.error("circuito_abierto", fallos=self.fallos)
            raise
        else:
            self.fallos, self.estado = 0, Estado.CERRADO
            return resultado
Fallar rápido es una feature. Un CircuitoAbierto en 0 ms que devuelve un resultado degradado —el precio cacheado, una lista vacía con un aviso— es infinitamente mejor para el usuario que un spinner de 30 segundos que termina en error. El diseño de la degradación es tan parte del servicio como el camino feliz, y casi nunca se especifica.

PS8.9 Cuándo bajar a código nativo: PyO3 + maturin

Llega un punto en que el perfil dice, sin ambigüedad, que el 80% del tiempo está en una función tuya de Python puro y que ya la vectorizaste todo lo que se podía. Ahí la respuesta es sacar esa función del intérprete. PyO3 permite escribir una extensión en Rust que Python importa como un módulo cualquiera, y maturin se encarga de compilarla y empaquetarla en un wheel.

// src/lib.rs
use pyo3::prelude::*;
use rayon::prelude::*;

fn levenshtein(a: &str, b: &str) -> usize {
    let (a, b): (Vec<char>, Vec<char>) = (a.chars().collect(), b.chars().collect());
    let mut fila: Vec<usize> = (0..=b.len()).collect();
    for (i, ca) in a.iter().enumerate() {
        let mut previo = fila[0];
        fila[0] = i + 1;
        for (j, cb) in b.iter().enumerate() {
            let coste = if ca == cb { 0 } else { 1 };
            let nuevo = (fila[j + 1] + 1).min(fila[j] + 1).min(previo + coste);
            previo = fila[j + 1];
            fila[j + 1] = nuevo;
        }
    }
    fila[b.len()]
}

/// Distancia de edición entre dos cadenas.
#[pyfunction]
fn distancia(a: &str, b: &str) -> usize {
    levenshtein(a, b)
}

/// Lote completo, en paralelo real: `allow_threads` SUELTA el GIL,
/// así que rayon usa todos los núcleos mientras Python espera.
#[pyfunction]
fn distancia_lote(py: Python<'_>, pares: Vec<(String, String)>) -> Vec<usize> {
    py.allow_threads(|| {
        pares.par_iter().map(|(a, b)| levenshtein(a, b)).collect()
    })
}

#[pymodule]
fn distancias(m: &Bound<'_, PyModule>) -> PyResult<()> {
    m.add_function(wrap_pyfunction!(distancia, m)?)?;
    m.add_function(wrap_pyfunction!(distancia_lote, m)?)?;
    Ok(())
}
# Desde Python es un módulo más — y ahí está toda la gracia
import distancias

distancias.distancia("kitten", "sitting")            # 3
distancias.distancia_lote([("abc", "abd"), ("x", "y")])   # [1, 1]
Dos detalles que hacen la diferencia. abi3-py311 compila contra la ABI estable: un solo wheel sirve para 3.11, 3.12, 3.13 y las que vengan, en vez de uno por versión. Y py.allow_threads libera el GIL mientras corre Rust — es exactamente el mecanismo que hace que NumPy escale con hilos (PS1.4). Sin esa línea, tu extensión es rápida pero sigue serializando a todos los hilos de Python.

PS8.10 Cuándo Python NO es la respuesta

Parte de la madurez técnica es reconocer los límites de tu herramienta favorita sin defenderla por costumbre. Hay escenarios donde Python es la elección incorrecta y ninguna optimización lo arregla:

📌 Y qué hacer cuando pasa: casi nunca es "reescribir todo". El movimiento correcto es identificar el componente que tiene el requisito duro y sacarlo — como servicio aparte, como extensión nativa, como worker en otro lenguaje detrás de una cola. El resto del sistema (la API, la lógica de negocio, el pegamento, el análisis) se queda en Python, donde la velocidad de desarrollo y el ecosistema siguen siendo imbatibles. Un rewrite completo por un cuello de botella del 5% del código es el error de arquitectura más caro y más frecuente de esta categoría.

Heredás checkout: un servicio FastAPI de 600 líneas que llama a un proveedor de pagos y escribe en Postgres. Corre con uvicorn app.main:api --reload, la configuración está en un config.py con la API key adentro, loguea con print(), y se despliega copiando el repo a una VM. Funciona. Tenés que ponerlo en Kubernetes el viernes.

Paso 1 — Congelar el artefacto. Antes que nada, reproducibilidad: uv lock genera el lockfile, el Dockerfile multi-stage de PS8.1 construye la imagen, y CI la etiqueta con el SHA del commit. Desde ahora "la versión que está en prod" es una respuesta exacta, no una arqueología de git log en la VM.

Paso 2 — Sacar la configuración del código. El config.py se convierte en el Settings de PS8.2. La API key sale del repo (y se rota, porque estuvo en el historial de git: asumila comprometida). Las variables se inyectan por entorno; el secreto, montado desde el gestor. Se agrega el try/except ValidationError con SystemExit(78) del arranque.

Paso 3 — Logs que una máquina pueda leer. Los print() se reemplazan por structlog en JSON, con el middleware de request_id. En el mismo commit se agrega el procesador que redacta claves sensibles: el servicio maneja pagos, y un payload de tarjeta en los logs es un incidente de cumplimiento, no un bug.

Paso 4 — Ver adentro. opentelemetry-instrument envuelve el arranque: sin tocar el código aparecen spans de FastAPI, httpx y la base. Se agrega a mano el span checkout.cobrar con orden.id y el resultado del proveedor, y el procesador que inyecta trace_id en cada log. Muestreo al 10% con parentbased_traceidratio: suficiente para diagnosticar, barato de guardar.

Paso 5 — Sobrevivir a las dependencias. Aparece el hallazgo del día: el cliente HTTP del proveedor se creaba dentro de cada handler y sin timeout. Se pasa a un AsyncClient único en el lifespan, con el httpx.Timeout de cuatro campos. La consulta de inventario —idempotente— recibe tenacity con jitter; el cobro —no idempotente— recibe la clave de idempotencia en vez de reintentos ciegos.

Paso 6 — Decirle la verdad al orquestador. /livez devuelve 200 y nada más. /readyz chequea el pool contra la base con un timeout de 1 s. Las probes del manifiesto usan el endpoint correcto en cada caso, y el startupProbe le da 150 s al arranque para que la migración inicial no dispare reinicios.

Paso 7 — Apagarse bien. El lifespan hace el drenaje: baja listo, espera 5 s, deja que uvicorn cierre las requests en vuelo (25 s), y recién ahí cierra cliente y pool. El manifiesto le da 40 s de gracia y un preStop de 5 s. El CMD se escribe en forma exec para que el SIGTERM llegue al proceso y no a un shell.

Paso 8 — Verificar cada punto, no confiar en cada punto. Esta es la parte que separa un deploy de una esperanza:

Checkpoint — ¿lo tenés claro?

¿Por qué es un error grave chequear la base de datos en el liveness probe?

Porque las dos probes disparan acciones distintas: readiness te saca de rotación, liveness te mata. Si la base tiene una degradación transitoria, un liveness que la consulta hace que todos los pods fallen simultáneamente y sean reiniciados a la vez. Al volver, todos intentan reconectarse al mismo tiempo contra una base que todavía está sufriendo, con las cachés vacías y sin conexiones tibias: un hipo de 40 segundos se convierte en una caída total con efecto rebaño. Liveness solo debe responder "mi proceso no está colgado"; cualquier dependencia externa va en readiness, donde el peor caso es dejar de recibir tráfico un rato.

Tu p50 está en 40 ms y tu p99 en 3 s. ¿Dónde buscás y por qué el promedio no te sirvió?

El p50 sano dice que el camino normal está bien: no es un problema global de CPU, de código ni de una query que empeoró para todos. La cola alta apunta a algo que afecta a una minoría de requests: contención por un lock o por el pool de conexiones (busca saturación), un caso de datos particular —un usuario con 10.000 ítems—, un reintento que agrega segundos, o un garbage collect/una recarga de caché que golpea de a ratos. El promedio no sirvió porque mezcla las dos poblaciones en un número que no describe a ninguna: con 99% en 40 ms y 1% en 3 s el promedio da ~70 ms y parece excelente. El diagnóstico concreto sale de filtrar trazas por duración >1 s y comparar sus spans contra los de una traza rápida.

Vas a reintentar una llamada que falló por timeout. ¿Qué tenés que preguntarte antes?

Si la operación es idempotente. Un timeout significa "no sé qué pasó", no "no pasó": el pedido pudo haber llegado y ejecutado, y perderse solo la respuesta. Reintentar un GET o un PUT es seguro; reintentar un POST /cobros puede cobrarle dos veces al usuario. Si no es idempotente, hay tres caminos: mandar una clave de idempotencia que el servidor respete y deduplique, consultar el estado antes de reintentar, o no reintentar y devolver un error accionable. Y en todos los casos el reintento lleva backoff exponencial con jitter y un tope de intentos, porque sin jitter mil clientes fallando juntos reintentan juntos y garantizan el segundo fallo.

Resumen ejecutivo

  • Empaquetá el artefacto, no el repo. Multi-stage con uv, lock congelado, usuario no root, base slim por defecto y distroless solo si tenés cómo depurar sin shell. El orden de los COPY es lo que hace rápido al build.
  • La configuración se valida al arrancar. Settings tipadas con extra="forbid" y salida con código de error si falta algo. Nada de defaults silenciosos. Los secretos van en un gestor, nunca en la imagen ni en el repo.
  • Logs en JSON con contexto e id de correlación, cosidos al trace_id. Nunca secretos ni PII: identificadores, no identidades — y hacelo cumplir con un procesador, no con disciplina.
  • OpenTelemetry unifica trazas, métricas y logs. Instrumentación automática para las librerías, manual para las fronteras de negocio. Cuidado con la cardinalidad en métricas.
  • Percentiles, no promedios. p50 para la experiencia típica, p99 para la real. Con 20 llamadas por pantalla, un p99 del 1% se vuelve 18% de pantallas lentas. Y la saturación es la única señal que avisa antes.
  • py-spy perfila un proceso vivo en producción sin reiniciarlo y con overhead nulo. Probá el procedimiento antes de necesitarlo.
  • Liveness ≠ readiness. Liveness no toca dependencias. El apagado es: bajar readiness → drenar → cerrar en vuelo → cerrar recursos, y todo eso más rápido que el terminationGracePeriodSeconds.
  • Timeout en toda llamada de red. Reintentos exponenciales con jitter, solo sobre errores transitorios y operaciones idempotentes. Circuit breaker para fallar rápido y degradar con gracia.
  • PyO3 + maturin cuando el perfil —no la intuición— señala un hot spot acotado; abi3 para un wheel por plataforma y allow_threads para soltar el GIL. Si ya existe una librería nativa que lo hace, usala.
  • Reconocé cuándo Python no es la herramienta y sacá solo el componente con el requisito duro. Un rewrite completo por un cuello de botella del 5% es el error más caro de esta lista.

Cierre del track — qué estudiar después

Ocho módulos atrás Python era un lenguaje que usabas. Ahora sabés cómo representa sus objetos, cómo administra memoria, cómo concurre, cómo se tipa, cómo se prueba y cómo se opera. Eso es la base de un perfil senior: no un catálogo de trucos, sino un modelo mental que te deja predecir el comportamiento del sistema y explicar por qué elegiste lo que elegiste.

1. Sistemas distribuidos. Todo lo de PS8.8 —timeouts, reintentos, idempotencia, degradación— es la punta del iceberg. Consistencia eventual, particiones, colas, exactly-once (y por qué no existe). Es el techo real de la mayoría de las carreras backend.
2. Bases de datos por dentro. Índices, planes de ejecución, niveles de aislamiento, locks. Nueve de cada diez servicios Python son lentos por la base, no por Python — y ese diagnóstico no aparece en ningún perfilador del intérprete.
3. Rust, en serio. No para reescribir todo: para tener la opción de PS8.9 disponible de verdad, y porque su modelo de ownership te va a hacer escribir mejor Python concurrente aunque nunca despliegues una línea de Rust.
4. Seguridad más allá de los secretos. Modelado de amenazas, dependencias y supply chain, autenticación y autorización bien hechas. En producción la seguridad no es una feature: es una propiedad del sistema, igual que las cinco de PS8.0.
5. Y lo más importante: operá algo real. Poné un servicio tuyo en producción, aunque no lo use nadie más que vos. La primera vez que te despierte una alerta a las 3 AM vas a aprender más sobre observabilidad que en cualquier módulo — incluido este.

🧠 Autoevaluación

1. Tu servicio arranca sano y recién en la primera request devuelve 500 porque falta una variable de entorno. ¿Cuál es el arreglo estructural?

Si la config se valida antes de abrir el puerto, el proceso muere en el segundo cero, el orquestador nunca lo pone en rotación y ningún usuario ve el error: el deploy simplemente no avanza. El try/except en el handler convierte un error de deploy en un error del usuario, y el default silencioso es peor todavía — enmascara el problema hasta que alguien lo descubre semanas después investigando otra cosa. Por eso además extra="forbid": un APP_TIMEOOUT mal tipeado tiene que ser un error de arranque, no un silencio.

2. Un proveedor externo empieza a tardar 30 segundos en responder en vez de fallar. ¿Cuál es el riesgo mayor para tu servicio?

Una dependencia lenta es peor que una caída: una caída libera recursos rápido, la lentitud los retiene. Cada request colgada ocupa una conexión del pool, una tarea del event loop y memoria; cuando se agotan, tu servicio deja de atender también todo lo que no dependía del proveedor. Por eso el timeout no es una optimización sino el mecanismo que impide que la falla ajena se vuelva propia — y por eso el paso siguiente es el circuit breaker, que deja de intentar y degrada con gracia en vez de esperar.

3. El perfil de py-spy muestra que el 85% del tiempo se va esperando respuestas de la base de datos. ¿Qué esperás ganar reescribiendo el hot spot con PyO3 + maturin?

Bajar a código nativo acelera cómputo, no espera. Si el 85% del tiempo el proceso está bloqueado esperando a la base, la ganancia máxima teórica de optimizar todo el resto es un 15% — y a cambio sumás un toolchain de Rust, CI multiplataforma, wheels por arquitectura y un bus factor nuevo. Es el mismo error de PS1.7 con otro disfraz: optimizar donde no está el tiempo. Acá lo que corresponde es mirar índices, plan de ejecución, N+1 queries y pool de conexiones.

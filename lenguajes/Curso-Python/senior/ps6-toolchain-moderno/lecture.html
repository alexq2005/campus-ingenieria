PS6 — Toolchain moderno: uv, ruff y ty

PS6.0 Por qué este módulo

Entre 2024 y 2026 el toolchain de Python cambió más que en los quince años anteriores. Durante casi dos décadas la respuesta a "¿cómo armo un proyecto Python?" fue una lista de seis o siete herramientas que había que aprender por separado, que no se hablaban entre sí y que cada una resolvía una porción del problema. Hoy la respuesta cabe en dos binarios.

💡 La tesis del módulo. El toolchain no es una cuestión de gusto personal. Define cuánto tarda tu CI, si tu build es reproducible y cuánto tarda una persona nueva en tener el proyecto corriendo. Esos tres números son medibles, y las herramientas de 2026 los mejoran por un factor grande — no por un 10%.

Los números que motivaron el cambio no son de marketing. uv, la herramienta de Astral escrita en Rust, pasó a 126 millones de descargas mensuales en PyPI contra unos 75 millones de Poetry: en dos años se convirtió en el instalador más usado después de pip. OpenAI migró la infraestructura de Codex de pip a uv y reportó un ahorro de alrededor de un millón de minutos de cómputo por semana. Ese es el orden de magnitud del que hablamos cuando decimos "10 a 100 veces más rápido".

Este módulo no es un tour de features. Es cómo se arma, se bloquea, se verifica, se publica y se integra a CI un proyecto Python serio hoy — y, al final, cuándo no conviene migrar.

PS6.1 De dónde venimos: un problema, siete herramientas

El stack clásico no era malo por incompetencia: creció por acumulación. Cada herramienta resolvió un agujero que la anterior dejaba, y ninguna podía absorber a las otras porque todas estaban escritas en Python y arrancaban dentro del mismo intérprete que intentaban administrar. Ese era el techo.

📌 Lo que realmente cambió no es la velocidad: es la cantidad de estados posibles. Con el stack viejo, "el proyecto está bien instalado" era una afirmación sobre siete herramientas independientes, cada una con su archivo de configuración y su noción de "entorno activo". Con uv, hay un pyproject.toml, un uv.lock y un comando que garantiza que el entorno coincide con el lock antes de ejecutar nada. La velocidad es lo que se nota primero; la reducción de estados es lo que te ahorra las tardes perdidas.

PS6.2 uv a fondo

uv es un binario único, sin dependencias, escrito en Rust. No necesita un Python instalado para funcionar — de hecho, instala Pythons.

# macOS / Linux
curl -LsSf https://astral.sh/uv/install.sh | sh

# Windows (PowerShell)
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"

# o, si ya tenés pipx o un pip a mano
pipx install uv

uv --version
uv self update

Arrancar un proyecto

uv init mi-proyecto
cd mi-proyecto

# lo que quedó:
# .python-version    versión de Python fijada para el proyecto
# pyproject.toml     metadata + dependencias
# README.md
# main.py
# (el .venv y el uv.lock aparecen en el primer uv add / uv run)

uv init --lib mi-libreria     # layout src/ + build backend, para publicar
uv init --app mi-servicio     # layout de aplicación (por defecto)

Agregar y quitar dependencias

uv add "httpx>=0.27"
uv add "fastapi[standard]"
uv add --dev pytest pytest-cov ruff
uv add --group docs mkdocs-material          # grupo propio (PEP 735)
uv add "polars@git+https://github.com/pola-rs/polars"   # desde git
uv add ./libs/interno                        # path local

uv remove requests
💡 uv add hace cuatro cosas en un comando: escribe la dependencia en pyproject.toml, re-resuelve el grafo completo, actualiza uv.lock y sincroniza el .venv. Con pip, esas cuatro cosas eran cuatro pasos manuales, y olvidarte del segundo era el origen clásico del "en mi máquina anda".

Ejecutar cosas

uv run python -m mi_proyecto
uv run pytest
uv run ruff check .

# probar una librería sin instalarla en el proyecto
uv run --with rich python -c "from rich import print; print('[bold]hola[/bold]')"

# forzar otro intérprete para esta corrida
uv run --python 3.14t python -c "import sys; print(sys._is_gil_enabled())"
📌 uv run sincroniza antes de ejecutar. Verifica que el .venv coincida con el uv.lock y, si no, lo arregla — en milisegundos. Consecuencia práctica: desaparece el source .venv/bin/activate y desaparece la clase entera de bugs de "estaba en el venv equivocado". Es probablemente el cambio de hábito más grande del módulo.

Sincronizar y bloquear

uv sync                    # el entorno pasa a ser EXACTAMENTE el lockfile
uv sync --frozen           # falla si el lock no está al día — esto va en CI
uv sync --no-dev           # solo dependencias de runtime (imagen de producción)
uv sync --all-extras --all-groups

uv lock                    # resolver y escribir uv.lock, sin tocar el .venv
uv lock --check            # ¿el lock está sincronizado con el pyproject?
uv lock --upgrade          # subir todo lo que se pueda
uv lock --upgrade-package httpx   # subir SOLO httpx y lo que arrastre

Gestionar versiones de Python

uv python list                 # lo instalado y lo disponible para bajar
uv python install 3.13 3.14
uv python install 3.14t        # build free-threaded (PEP 779, ver PS1)
uv python pin 3.14             # escribe .python-version
uv python find                 # qué intérprete usaría acá

uv venv                        # .venv con el Python fijado
uv venv --python 3.14t .venv-ft
El 3.14t es el build sin GIL oficialmente soportado desde Python 3.14 gracias al PEP 779 (lo vimos en PS1). Que uv lo instale con un comando es parte de por qué el free-threading dejó de ser un experimento de laboratorio: probarlo cuesta treinta segundos, no una tarde de compilar CPython.

Herramientas CLI: uv tool y uvx

uv tool install ruff           # instalada global, en su propio entorno aislado
uv tool install py-spy
uv tool list
uv tool upgrade --all

uvx ruff check .               # efímero: baja, corre y se olvida
uvx --from httpie http GET https://example.com

La interfaz compatible con pip

uv también expone una capa uv pip deliberadamente compatible, pensada para meterlo en proyectos viejos sin cambiarles nada:

uv pip install -r requirements.txt      # mismo comando, 10-100x más rápido
uv pip compile requirements.in -o requirements.txt
uv pip sync requirements.txt            # el entorno pasa a ser EXACTAMENTE el archivo
uv pip list
uv pip freeze
Esa capa es la puerta de entrada barata: si tu equipo no quiere migrar el proyecto entero, cambiar pip install por uv pip install en el Dockerfile y en el CI ya te da la mayor parte de la ganancia de tiempo, con un diff de dos líneas y cero riesgo de resolución distinta si usás uv pip sync.

El uv.lock es universal

📌 Un solo lockfile para todas las plataformas. uv.lock no es una foto de tu máquina: contiene la resolución para Linux, macOS y Windows, para las arquitecturas relevantes y para todo el rango de requires-python que declaraste. Un pip freeze hecho en tu portátil con macOS y Python 3.12 no describe lo que se va a instalar en el contenedor Linux con 3.13. Ese desajuste silencioso es la causa raíz de una fracción enorme de los "anda en local, falla en prod".

PS6.3 Scripts con dependencias embebidas (PEP 723)

Esta es, de lejos, la funcionalidad más útil y menos conocida del stack moderno. El PEP 723 define un bloque de metadata en un comentario dentro de un .py: el script declara sus propias dependencias y su versión mínima de Python.

# /// script
# requires-python = ">=3.12"
# dependencies = [
#     "httpx>=0.27",
#     "rich>=13",
# ]
# ///
"""Chequea el estado de una lista de endpoints y lo muestra en una tabla."""
import asyncio
import httpx
from rich.console import Console
from rich.table import Table

ENDPOINTS = [
    "https://example.com",
    "https://httpbin.org/status/503",
]

async def revisar(cliente: httpx.AsyncClient, url: str) -> tuple[str, int | str]:
    try:
        r = await cliente.get(url, timeout=5)
        return url, r.status_code
    except httpx.HTTPError as e:
        return url, type(e).__name__

async def main() -> None:
    async with httpx.AsyncClient() as c:
        filas = await asyncio.gather(*(revisar(c, u) for u in ENDPOINTS))
    tabla = Table("endpoint", "estado")
    for url, estado in filas:
        tabla.add_row(url, str(estado))
    Console().print(tabla)

asyncio.run(main())
uv run chequeo.py          # uv lee el bloque, arma un entorno efímero y ejecuta

# y podés editar el bloque con comandos, sin tocarlo a mano:
uv add --script chequeo.py "pandas>=2.2"
uv remove --script chequeo.py rich

# hasta se le puede dar su propio lockfile
uv lock --script chequeo.py
💡 Por qué importa más de lo que parece. Elimina la carpeta scripts/ con su requirements-scripts.txt que nadie mantiene. Un script de operaciones queda como un solo archivo: se manda por Slack, se pega en un ticket, se guarda en un gist, y quien lo reciba lo corre con uv run sin leer un README ni crear un venv. Los scripts internos dejan de pudrirse porque el archivo lleva su contexto adentro.
En Linux/macOS podés hacerlo ejecutable con un shebang: #!/usr/bin/env -S uv run --script como primera línea, antes del bloque /// script. Después es ./chequeo.py y listo.

PS6.4 Workspaces: un monorepo, un lockfile

Cuando un repositorio tiene varios paquetes que se importan entre sí —un core, una api, un worker— el problema clásico es que cada uno resuelve sus dependencias por su cuenta y terminan con versiones incompatibles de la misma librería. Los workspaces de uv resuelven todo el conjunto de una vez.

# pyproject.toml de la raíz
[project]
name = "plataforma"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["core", "api"]

[tool.uv.workspace]
members = ["packages/*"]
exclude = ["packages/legacy-*"]

[tool.uv.sources]
core = { workspace = true }
api  = { workspace = true }

[dependency-groups]
dev = ["pytest>=8", "ruff>=0.8"]
uv sync                                  # resuelve TODOS los miembros juntos
uv run --package api uvicorn api.main:app --reload
uv add --package api "httpx>=0.27"       # agrega la dep AL paquete api
uv run --package worker pytest
📌 Un solo uv.lock en la raíz para todo el monorepo. Eso hace estructuralmente imposible que api y worker corran con versiones distintas de pydantic: la resolución es única. Es la misma idea que Cargo en Rust o los workspaces de pnpm.
Un workspace no es gratis. Fuerza una resolución compartida: si api necesita numpy 2.x y worker está clavado en numpy 1.x, el workspace no puede satisfacer a los dos y vas a tener que arreglar el conflicto de verdad. Eso suele ser bueno, pero si tus paquetes necesitan versionado y ciclos de release independientes, la respuesta correcta puede ser repositorios separados, no un workspace.

PS6.5 ruff: un binario en lugar de veinte

ruff es el linter y formateador de Astral, también en Rust. Reemplaza a black, flake8 (y su ecosistema de plugins), isort, pyupgrade, autoflake, pydocstyle, bandit y una decena más — reimplementando más de 800 reglas de esas herramientas en un solo ejecutable. En 2026 es el linter por defecto del ecosistema.

uv add --dev ruff          # o: uv tool install ruff

ruff check .               # lintear
ruff check --fix .         # arreglar lo que se puede arreglar sin riesgo
ruff check --fix --unsafe-fixes .   # incluir arreglos que PUEDEN cambiar semántica
ruff check --statistics .  # ¿cuántas violaciones de cada regla? empezá siempre por acá
ruff check --watch .       # loop mientras editás

ruff format .              # formatear (compatible con el estilo de black)
ruff format --check .      # ¿está formateado? no toca nada — esto va en CI
ruff format --diff .       # mostrar qué cambiaría

ruff rule F401             # documentación de una regla, sin abrir el navegador

Configuración en pyproject.toml

[tool.ruff]
line-length = 100
target-version = "py313"
extend-exclude = ["migrations", "_generated", "vendor"]

[tool.ruff.lint]
select = [
    "E", "W",    # pycodestyle: errores y warnings
    "F",         # pyflakes: imports/variables sin usar, nombres indefinidos
    "I",         # isort: orden de imports
    "N",         # pep8-naming
    "UP",        # pyupgrade: modernizar sintaxis al target-version
    "B",         # flake8-bugbear: trampas reales (mutable default args, etc.)
    "C4",        # comprehensions innecesarias
    "SIM",       # simplificaciones
    "ASYNC",     # errores típicos de asyncio (ver PS3)
    "S",         # bandit: seguridad
    "RUF",       # reglas propias de ruff
]
ignore = [
    "E501",      # largo de línea: lo maneja el formateador
    "S101",      # assert: lo permitimos, ver per-file-ignores
]

[tool.ruff.lint.per-file-ignores]
"tests/**" = ["S101", "ARG", "PLR2004"]   # asserts y magic numbers en tests: OK
"__init__.py" = ["F401"]                   # re-exports intencionales

[tool.ruff.lint.isort]
known-first-party = ["mi_proyecto"]

[tool.ruff.lint.pydocstyle]
convention = "google"

[tool.ruff.format]
quote-style = "double"
docstring-code-format = true   # también formatea el código dentro de los docstrings
PrefijoReemplaza a¿Vale la pena prenderlo?
F, E, Wpyflakes + pycodestyle✅ Siempre. Es el piso.
Iisort✅ Siempre. Elimina discusiones de imports.
Bflake8-bugbear✅ Sí: encuentra bugs reales, no estilo.
UPpyupgrade✅ Sí, junto con target-version bien puesto.
Sbandit⚠️ Sí, con per-file-ignores para tests.
ANNflake8-annotations⚠️ Solo si ya tenés typing serio (PS5).
Dpydocstyle⚠️ Solo en librerías públicas. En apps es ruido.
ALL—❌ Nunca de entrada: son 800+ reglas contradictorias entre sí.
El error clásico al adoptar ruff: poner select = ["ALL"] el primer día, recibir 4.000 errores, apagarlo y no volver nunca. El camino que funciona es al revés: arrancá con el equivalente exacto a lo que ya tenías, verificá que el diff sea vacío, mergeá, y recién después prendé un prefijo por sprint con su commit de arreglos aparte.

Migrar sin destruir el historial de git

Formatear un repo entero produce un commit que toca todos los archivos y arruina git blame. Hay una solución estándar y es de dos líneas:

ruff format .
git commit -am "style: formatear todo el repo con ruff format"

# registrar ESE commit como ignorable por blame
git rev-parse HEAD >> .git-blame-ignore-revs
git add .git-blame-ignore-revs
git commit -m "chore: ignorar el commit de formateo en git blame"

# que git lo use localmente (cada persona lo corre una vez)
git config blame.ignoreRevsFile .git-blame-ignore-revs
GitHub y GitLab leen .git-blame-ignore-revs automáticamente en su vista de blame. Con eso, el commit de formateo se vuelve invisible: el blame sigue apuntando a quien escribió cada línea de verdad. Lo mismo aplica al commit de ruff check --fix masivo, si lo hacés aparte.

PS6.6 ty y el estado del type-checking

ty es el type-checker de Astral, también en Rust. Sigue la misma jugada que ruff: reimplementar en un lenguaje compilado algo que tardaba minutos en Python puro. Los órdenes de magnitud son parecidos — donde mypy tarda 40 segundos en un repo grande, ty tarda menos de uno.

uvx ty check                   # probarlo sin instalar nada
uv add --dev ty
uv run ty check src/
uv run ty check --error-on-warning src/
CheckerEstado 2026Fuerte enDébil en
mypyMaduro, referencia de factoEcosistema de plugins (Django, SQLAlchemy, Pydantic), semántica muy discutida y estableLento en repos grandes; incremental frágil
pyright / basedpyrightMaduro, motor de PylanceRápido, inferencia potente, es lo que ya corre en el editor de la mayoríaNode como dependencia; sin sistema de plugins
tyJoven, en previewVelocidad; integración natural con uv/ruffCobertura de casos raros y de stubs de terceros todavía en construcción
📌 Recomendación honesta para un proyecto serio hoy. El gate de CI —el que bloquea el merge— ponelo en mypy o en pyright, que es lo que ya corre en el editor de tu equipo. Agregá ty como un job no bloqueante en paralelo, y mirá el reporte cada tanto. El día que ty deje de reportar falsos positivos en tu código y su versión se declare estable, invertís los roles y ganás el tiempo de CI. Adoptar un checker en preview como gate de merge es apostar la velocidad del equipo a un roadmap ajeno.
⚠️ No confundas linter con type-checker. ruff no reemplaza a mypy ni a ty: ruff hace análisis por archivo, sin resolver tipos entre módulos. Que ruff check pase en verde no dice absolutamente nada sobre si tus tipos cierran. Son dos herramientas con dos trabajos distintos, y las dos van en CI.

PS6.7 pyproject.toml a fondo

Un solo archivo declara metadata, dependencias, build backend y la configuración de casi todas las herramientas. Este es un ejemplo completo y comentado:

[project]                                  # PEP 621: metadata estándar
name = "reporte-ventas"
version = "1.4.0"
description = "Genera reportes de ventas desde el data warehouse."
readme = "README.md"
requires-python = ">=3.12"
license = "MIT"
authors = [{ name = "Alex Quiñones", email = "alex@ejemplo.com" }]
keywords = ["reporting", "etl"]
classifiers = [
    "Programming Language :: Python :: 3.13",
    "Typing :: Typed",
]

dependencies = [                           # lo que necesita en RUNTIME
    "httpx>=0.27,<1.0",
    "pydantic>=2.7",
    "polars>=1.0",
]

[project.optional-dependencies]            # extras PÚBLICOS: pip install reporte-ventas[pdf]
pdf = ["weasyprint>=62"]
excel = ["xlsxwriter>=3.2"]

[dependency-groups]                        # PEP 735: grupos PRIVADOS de desarrollo
dev = ["pytest>=8", "pytest-cov>=5", "ruff>=0.8", "mypy>=1.11"]
docs = ["mkdocs-material>=9"]

[project.scripts]                          # entry points de CLI
reporte = "reporte_ventas.cli:main"

[project.urls]
Repository = "https://github.com/ejemplo/reporte-ventas"
Changelog = "https://github.com/ejemplo/reporte-ventas/blob/main/CHANGELOG.md"

[build-system]                             # cómo se construye el paquete
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.uv]
default-groups = ["dev"]                   # qué grupos instala uv sync por defecto

[tool.pytest.ini_options]
addopts = "-q --strict-markers"
testpaths = ["tests"]

[tool.mypy]
strict = true
warn_unreachable = true
💡 optional-dependencies vs dependency-groups — la distinción que casi todos confunden. Los extras ([project.optional-dependencies]) son públicos: viajan en el paquete publicado y tus usuarios los instalan con pip install paquete[pdf]. Los grupos ([dependency-groups], PEP 735) son privados del desarrollo: no se publican y no existen para quien instala tu librería. Poner pytest como extra es un error clásico que le mete tus dependencias de test a todos tus usuarios.
Build backendCuándo
hatchlingPor defecto para casi todo. Rápido, buena configuración de archivos incluidos.
uv_buildEl backend propio de uv: mínimo y muy rápido, para paquetes Python puros.
setuptoolsProyectos viejos con setup.py hecho a medida que todavía funciona.
maturinExtensiones en Rust (PyO3).
scikit-build-coreExtensiones en C/C++ con CMake (ver PS8).

📌 Publicá los dos, y no publiques tokens. En CI usá Trusted Publishing: PyPI acepta el token OIDC efímero que emite GitHub Actions para tu repositorio, y no necesitás guardar ningún secreto de larga vida. Un token de PyPI filtrado en un log de CI es una toma de control de tu paquete, y por lo tanto de todos los entornos que lo instalan.
Una versión publicada en PyPI es inmutable y para siempre. Podés yankear una release (marcarla como no elegible para resoluciones nuevas) pero no borrarla ni reemplazarla. Por eso el paso de TestPyPI no es burocracia: es la única oportunidad de descubrir que el wheel se armó sin el paquete de datos, o que el entry point apunta a un módulo que no existe.

PS6.9 Reproducibilidad: el lockfile es el contrato

Esta sección existe por una afirmación que se repite mucho y es falsa: "mi requirements.txt tiene todas las versiones pineadas, o sea que es reproducible".

Por qué pip install -r requirements.txt no es reproducible
No cubre lo transitivo. Pinear fastapi==0.115.0 no pinea starlette, anyio ni typing-extensions, que se resuelven de nuevo en cada instalación.
Es una foto de una plataforma. Un pip freeze desde macOS/3.12 no describe lo que instala un contenedor Linux/3.13: los marcadores de entorno cambian el conjunto de paquetes.
Sin hashes, no hay integridad. Sin --require-hashes, nada garantiza que el artefacto que bajás hoy sea byte a byte el de ayer.
Resuelve otra vez, cada vez. Un paquete nuevo publicado a las 3 AM puede cambiar tu build de las 9 sin que vos hayas tocado una línea.
 
# En desarrollo: si cambiaste pyproject, el lock se actualiza solo
uv add "polars>=1.10"

# En CI: NUNCA re-resolver. Fallar si el lock no coincide con el pyproject.
uv sync --frozen --all-groups
uv lock --check

# Puente hacia sistemas que todavía piden requirements.txt (Docker viejo, un cliente)
uv export --format requirements-txt --no-dev --no-emit-project -o requirements.txt
📌 Commiteá el uv.lock. Siempre. En aplicaciones es obvio: es la definición de qué se despliega. En librerías también, aunque suene contradictorio — el lock no se publica ni le impone nada a tus usuarios (ellos resuelven contra los rangos de tu pyproject.toml), pero le da a tu CI un entorno estable, así un fallo de tests significa "rompí algo" y no "alguien publicó algo".
El anti-patrón que anula todo lo anterior: correr uv sync a secas en CI en vez de uv sync --frozen. Sin --frozen, si alguien tocó pyproject.toml y no actualizó el lock, uv lo actualiza en silencio y tu pipeline testea un conjunto de paquetes que no está commiteado en ningún lado. Ese pipeline pasa en verde y no prueba lo que vas a desplegar.

PS6.10 CI: el workflow completo

name: ci
on:
  push: { branches: [main] }
  pull_request:

jobs:
  calidad:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        python: ["3.12", "3.13", "3.14"]
    steps:
      - uses: actions/checkout@v4

      - name: Instalar uv
        uses: astral-sh/setup-uv@v5
        with:
          enable-cache: true
          cache-dependency-glob: "uv.lock"

      - name: Instalar Python ${{ matrix.python }}
        run: uv python install ${{ matrix.python }}

      - name: Sincronizar (sin re-resolver)
        run: uv sync --frozen --all-extras --all-groups

      - name: El lock está al día
        run: uv lock --check

      - name: Lint
        run: uv run ruff check --output-format=github .

      - name: Formato
        run: uv run ruff format --check .

      - name: Tipos (gate)
        run: uv run mypy src/

      - name: Tipos (ty, informativo)
        run: uv run ty check src/
        continue-on-error: true

      - name: Tests
        run: uv run pytest -q --cov=src --cov-report=xml

  free-threading:
    runs-on: ubuntu-latest
    continue-on-error: true      # informativo hasta que el ecosistema esté listo
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
        with: { enable-cache: true }
      - run: uv python install 3.14t
      - run: uv sync --frozen --python 3.14t
      - run: uv run --python 3.14t pytest -q
El --output-format=github de ruff hace que las violaciones aparezcan como anotaciones sobre las líneas del diff en el pull request, en vez de esconderse en el log. Es una línea de configuración que cambia por completo cuánta gente lee el resultado del linter.
💡 Dónde se va el tiempo de un CI Python. En el stack viejo, un pipeline típico repartía sus 4–5 minutos así: instalar dependencias 2:30, tests 1:00, black+flake8+isort 0:40, mypy 0:40. Con uv la instalación cae a segundos (y con caché, a menos aún) y ruff colapsa esos 0:40 en menos de un segundo. El pipeline queda dominado por los tests — que es exactamente donde debería irse el tiempo.

Ahora la parte que la mayoría de los artículos se saltea: cuándo cada uno sigue siendo la respuesta correcta.

pip + venv todavía tiene sentido en un script de veinte líneas con dos dependencias; en una imagen Docker donde ya tenés un requirements.txt con hashes que funciona y agregar otra herramienta solo agrega superficie; y en entornos corporativos donde el mirror interno o el proceso de aprobación de binarios no contempla uv todavía. "Es la herramienta que ya está aprobada" es una razón técnica legítima.
poetry todavía tiene sentido en un proyecto grande, estable y con poca actividad, donde ya funciona y donde el equipo tiene plugins propios de poetry. Migrar cuesta días de trabajo humano; si tu CI tarda 90 segundos y a nadie le molesta, el retorno de esa migración es cero. Poetry sigue mantenido y adoptó PEP 621 en su versión 2.
uv es la respuesta en cualquier proyecto nuevo; cuando el CI tarda minutos y ese tiempo se paga en cada PR; en monorepos; cuando el equipo pelea con versiones de Python; y cuando el "en mi máquina anda" ya costó un incidente. Cuanto más grande el proyecto y más gente lo toca, más grande el retorno.
El riesgo real de uv, dicho sin adornos: es joven, y tanto uv como ruff y ty vienen de una sola empresa con capital de riesgo. Depender de un proveedor único es un riesgo de verdad, no un detalle. La mitigación es concreta y conviene verificarla antes de adoptar, no después: uv no inventa formatos propietarios — se apoya en pyproject.toml estándar (PEP 621, 723, 735) y uv export te devuelve un requirements.txt en un comando. Probá la salida de emergencia una vez, comprobá que el proyecto sigue instalándose con pip, y ahí sí adoptá tranquilo.

🧑‍🎓 Worked Example — migrar una API real a uv + ruff sin romper el CI

Una API Flask de tres años: requirements.txt con 41 dependencias directas pineadas, requirements-dev.txt con 12 más, entorno con venv, formateo con black, lint con flake8 + flake8-bugbear + isort, CI en GitHub Actions que tarda 4 min 20 s. Hay que migrarla sin que producción se entere.

Paso 0 — La línea de base. Este paso no es opcional. Antes de tocar nada hay que capturar exactamente qué se instala hoy, porque ese es el conjunto de paquetes que está corriendo en producción ahora mismo:

python -m venv .venv-baseline
.venv-baseline/bin/pip install -r requirements.txt -r requirements-dev.txt
.venv-baseline/bin/pip freeze | sort > baseline.txt
.venv-baseline/bin/pytest -q         # anotar: 312 passed en 48 s

wc -l baseline.txt                   # 118 paquetes, contando transitivos

Paso 1 — Crear el pyproject.toml importando lo que ya existe. uv sabe leer un requirements y volcarlo:

uv init --app --no-readme .          # no pisa archivos existentes
uv add -r requirements.txt
uv add --dev -r requirements-dev.txt
uv sync --all-groups

Paso 2 — Verificar equivalencia ANTES de mergear. Acá está el corazón del ejercicio. Los tests pasando no alcanzan: hay que comparar el conjunto resuelto contra la línea de base, paquete por paquete:

uv export --format requirements-txt --all-groups --no-hashes --no-emit-project \
  | grep -v '^#' | grep -v '^$' | sort > resuelto.txt

# comparar solo nombre==versión, ignorando los marcadores de entorno
diff <(cut -d';' -f1 baseline.txt | tr -d ' ') \
     <(cut -d';' -f1 resuelto.txt | tr -d ' ')

El diff dio 9 líneas. Cada una entra en una de tres categorías, y cada categoría tiene una acción distinta:

Tipo de diferenciaPor qué pasaQué hacer
Versión más nueva de un transitivo (6 casos)requirements.txt solo pineaba las directas; los transitivos se re-resolvían igual en cada deployEs un upgrade real, aunque estuviera pasando sin que nadie lo viera. Decidí: o lo aceptás y lo anotás en el PR, o lo pineás para que el diff quede vacío y lo subís en un PR aparte.
Paquete que estaba y ya no está (2 casos)Transitivos que dejaron de ser necesarios, o un extra que se perdió al importarInvestigar uno por uno. Si desapareció un extra (por ejemplo psycopg[binary] importado como psycopg), producción arranca y falla al abrir la conexión. Los tests con SQLite no lo detectan.
Paquete nuevo (1 caso)uv resolvió un backport distinto para el rango de requires-python declaradoNormal. Verificá que el requires-python del pyproject.toml coincida con lo que realmente soportás.
📌 La migración se mergea con el diff vacío, o con el diff explicado línea por línea en el PR. "Los tests pasan" no es evidencia suficiente: los tests no cubren el import opcional que solo se ejecuta con la variable de entorno de producción puesta. Este paso es lo que separa una migración de una ruleta.

Paso 3 — Reemplazar black + flake8 + isort por ruff, con configuración conservadora. El objetivo del primer commit es que el diff de formateo sea casi nulo:

uv remove --dev black flake8 flake8-bugbear isort
uv add --dev ruff

ruff check --statistics .     # qué se rompería con esta config: leer ANTES de arreglar
ruff format --diff . | wc -l  # cuántas líneas cambia respecto de black
[tool.ruff]
line-length = 88              # el default de black: hace que el diff sea mínimo
target-version = "py312"
extend-exclude = ["migrations"]

[tool.ruff.lint]
# equivalente aproximado a lo que ya corría: flake8 + bugbear + isort
select = ["E4", "E7", "E9", "F", "I", "B"]

[tool.ruff.lint.isort]
known-first-party = ["api"]   # replicar lo que decía el setup.cfg de isort

Paso 4 — El commit de formateo, aislado y neutralizado en el blame:

ruff format .
git commit -am "style: formateo con ruff format (equivalente a black)"
git rev-parse HEAD >> .git-blame-ignore-revs
git add .git-blame-ignore-revs
git commit -m "chore: ignorar el commit de formateo en git blame"

Paso 5 — CI en dos fases, nunca de golpe. Primero se agrega el job de uv en paralelo al de pip, marcado como no bloqueante. Durante una semana los dos corren sobre los mismos PRs y se comparan resultados. Si en esa semana el job de uv nunca difiere del de pip, se invierten: el de uv pasa a ser requerido y el de pip se borra. Si difieren aunque sea una vez, ahí está el bug que te habrías comido en producción.

Paso 6 — Limpieza, con una excepción.

git rm requirements.txt requirements-dev.txt setup.cfg .flake8
git add pyproject.toml uv.lock .python-version
Si el Dockerfile de producción todavía hace pip install -r requirements.txt, no borres el archivo: generalo. Un paso de uv export --no-dev -o requirements.txt en el build mantiene el contrato viejo con el lockfile nuevo como fuente de verdad. Cambiar el gestor de paquetes y el Dockerfile en el mismo PR es duplicar la superficie de fallo justo en el punto donde no querés ambigüedad sobre qué rompió.

📌 La lección del ejercicio no es "usá uv". Es que una migración de toolchain se valida comparando el conjunto resuelto contra la línea de base, no confiando en que los tests pasen. Y que se despliega por fases con los dos sistemas corriendo en paralelo, porque el objetivo no es migrar rápido: es poder afirmar, con evidencia, que no cambió nada más que lo que querías cambiar.

Checkpoint — ¿lo tenés claro?

Mi requirements.txt tiene todas las versiones con ==. ¿Por qué no es reproducible?

Porque pinea solo las dependencias directas. Las transitivas —lo que traen tus dependencias— se vuelven a resolver en cada instalación, así que un release nuevo de starlette o de typing-extensions puede cambiar tu build sin que vos hayas tocado una línea. Además, un pip freeze es una foto de una plataforma y una versión de Python: los marcadores de entorno hacen que el conjunto instalado difiera entre tu macOS y el contenedor Linux. Y sin --require-hashes tampoco hay garantía de integridad del artefacto. El uv.lock resuelve las tres cosas: incluye transitivos, cubre todas las plataformas dentro de tu requires-python, y trae hashes.

Migraste a uv, los 312 tests pasan, pero el diff de uv export contra el pip freeze viejo tiene 9 líneas. ¿Mergeás?

No, todavía no: primero clasificás las 9. Las que son un transitivo más nuevo son un upgrade real y hay que declararlo en el PR (o pinear para dejar el diff vacío y subir el upgrade aparte). Las peligrosas son las que desaparecieron: si al importar el requirements se perdió un extra —típico psycopg[binary] importado como psycopg— la app arranca perfecto y explota al abrir la primera conexión real. Los tests con SQLite o con mocks nunca lo tocan. Mergeás con diff vacío, o con cada línea explicada.

Si ruff reemplaza a flake8, black, isort y pyupgrade, ¿también reemplaza a mypy?

No, y confundir eso es peligroso. ruff hace análisis estático por archivo: detecta imports sin usar, sintaxis vieja, orden de imports, patrones riesgosos. No construye un modelo de tipos que atraviese módulos, así que no puede decirte que le estás pasando un str a una función que espera Path definida tres paquetes más allá. Ese trabajo lo hacen mypy, pyright o ty. Un CI serio corre las dos cosas: ruff check como lint y un type-checker como gate aparte.

Resumen ejecutivo

  • uv (Astral, en Rust) absorbió pip, venv, pyenv, virtualenv, pipx y poetry en un binario, 10–100× más rápido. Con ~126 M de descargas mensuales contra ~75 M de Poetry, es el default de facto en 2026; OpenAI ahorra ~1 millón de minutos de cómputo por semana desde que migró Codex.
  • uv run sincroniza antes de ejecutar: se termina el activate y se termina la clase de bugs del venv equivocado.
  • El uv.lock es universal — cubre plataformas y versiones de Python. Un requirements.txt con == no es reproducible: no pinea transitivos y es una foto de una sola máquina.
  • PEP 723 deja que un .py declare sus dependencias adentro. uv run script.py resuelve solo: un archivo autocontenido, sin README ni venv.
  • ruff reemplaza a black + flake8 + isort + pyupgrade y 15 herramientas más. Adoptalo conservador (equivalente a lo que ya tenías), y aislá el commit de formateo con .git-blame-ignore-revs.
  • ty es rapidísimo pero joven: hoy va como job informativo, con mypy o pyright como gate real. Y ruff no reemplaza al type-checker.
  • En CI: uv sync --frozen + uv lock --check. Sin --frozen, uv re-resuelve en silencio y tu pipeline testea algo que no está commiteado.
  • Sé honesto sobre cuándo no migrar: pip sigue bien para scripts chicos y entornos corporativos cerrados; poetry sigue bien en proyectos estables donde la migración no paga. Y verificá la salida de emergencia (uv export) antes de adoptar.

🧠 Autoevaluación

1. Tu CI corre uv sync a secas. Alguien abre un PR que agrega una dependencia al pyproject.toml pero se olvida de commitear el uv.lock actualizado. ¿Qué pasa?

Este es el anti-patrón que anula toda la reproducibilidad. Sin --frozen, uv sync actualiza el lock sobre la marcha y el CI valida algo que después nadie va a poder reconstruir — el lock que se despliega es distinto del que se testeó. La forma correcta en CI es uv sync --frozen (falla si el lock no está al día) y, si querés el mensaje explícito, además uv lock --check.

2. Estás migrando de requirements.txt a uv. Los 312 tests pasan y el diff entre el pip freeze viejo y el uv export nuevo muestra que dos paquetes desaparecieron. ¿Cuál es la lectura correcta?

Un paquete que estaba y ya no está es la categoría peligrosa del diff. El caso típico es un extra perdido —psycopg[binary] importado como psycopg— que hace que la app arranque perfecto y explote al abrir la primera conexión real. Los tests con SQLite o con mocks nunca ejercitan ese camino. La regla es mergear con diff vacío, o con cada línea clasificada y explicada en el PR.

3. Tu proyecto tiene ruff check y ruff format --check en verde en CI, con select = ["ALL"]. ¿Qué garantía te da eso sobre los tipos?

ruff es un linter, no un type-checker: encuentra imports sin usar, sintaxis vieja y patrones riesgosos dentro de un archivo, pero no resuelve tipos a través de módulos y por eso no puede detectar que le pasás un str a una función que espera un Path definida en otro paquete. Las reglas ANN solo verifican que las anotaciones existan, no que sean correctas. Un CI serio corre ruff y un type-checker como gate aparte.

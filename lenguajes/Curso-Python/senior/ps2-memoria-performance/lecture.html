PS2 — Memoria y performance

PS2.0 Por qué este módulo: optimizar sin medir es superstición

En PS1 viste por qué Python pesa: cada valor es un objeto en el heap con header, refcount y puntero a tipo. Este módulo es la contraparte práctica: cómo se mide eso, cómo se encuentra qué lo está causando, y qué se hace al respecto.

La razón por la que el tema merece un módulo entero es que casi todo el mundo lo hace al revés. El patrón típico es: alguien lee que las list comprehensions son más rápidas que append, reescribe media aplicación, y el servicio sigue tardando lo mismo — porque el 90% del tiempo se iba en una consulta sin índice.

💡 La tesis del módulo. Rendimiento no es un conjunto de trucos, es un método: (1) definir la métrica que importa —latencia p99, RSS pico, throughput—, (2) medirla con la herramienta adecuada, (3) atacar el término dominante, (4) volver a medir, (5) dejar una guardia automática para que la mejora no se pierda sola en tres sprints. Los pasos 1 y 5 son los que separan trabajo senior de anécdotas.
📌 Ley de Amdahl, en criollo. Si una parte se lleva el 20% del tiempo y la volvés infinitamente rápida, ganás como mucho un 20%. Optimizar lo que no domina el perfil tiene techo matemático — y ese techo casi siempre es más bajo que el costo de mantener el código raro que escribiste para lograrlo.

PS2.1 El layout de un objeto y qué ahorra __slots__

Una instancia común de una clase Python son dos asignaciones de memoria: el objeto en sí (header + un puntero a __dict__ + un puntero a __weakref__) y, aparte, el diccionario donde viven los atributos. __slots__ elimina la segunda: los atributos pasan a ser posiciones fijas dentro del propio objeto, como los campos de un struct de C.

import sys

class PuntoDict:
    def __init__(self, x, y, z):
        self.x, self.y, self.z = x, y, z

class PuntoSlots:
    __slots__ = ("x", "y", "z")
    def __init__(self, x, y, z):
        self.x, self.y, self.z = x, y, z

d = PuntoDict(1, 2, 3)
s = PuntoSlots(1, 2, 3)

# getsizeof es SUPERFICIAL: hay que sumar el __dict__ a mano
print(sys.getsizeof(d), sys.getsizeof(d.__dict__))   # p.ej. 48 + 104
print(sys.getsizeof(s), hasattr(s, "__dict__"))      # p.ej. 56  False
Los números exactos cambian entre versiones y builds: no memorices "104", memorizá la forma de medirlo. Desde 3.11 CPython usa key-sharing dictionaries: varias instancias de la misma clase comparten la tabla de claves, así que el ahorro de __slots__ es menor que en Python 3.6, pero sigue siendo real y crece con la cantidad de instancias.

La medición honesta no es sobre una instancia: es sobre un millón. Y no se hace con getsizeof, se hace midiendo la memoria del proceso o con tracemalloc:

import tracemalloc

def medir_pico(fabrica, n=1_000_000):
    tracemalloc.start()
    objetos = [fabrica(i, i, i) for i in range(n)]
    actual, pico = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    del objetos
    return pico / 1e6   # MB

print(f"dict  : {medir_pico(PuntoDict):.1f} MB")
print(f"slots : {medir_pico(PuntoSlots):.1f} MB")
# Orden de magnitud típico: ~150 MB vs ~90 MB. Medilo en TU build.
📌 Cuándo __slots__ paga. Cuando tenés muchas instancias de la misma clase chica: nodos de un grafo, puntos, filas de un dataset, eventos en un buffer. El ahorro es 30–50% de memoria y, de yapa, el acceso a atributos es un poco más rápido porque es un offset fijo en vez de una búsqueda en un dict. Para diez instancias de un servicio, no cambia absolutamente nada y solo agrega fricción.

Qué rompe __slots__

Esto es lo que hay que saber antes de esparcirlo por el codebase, porque son limitaciones estructurales, no detalles:

Lo que se pierdeDetalle
Atributos dinámicosobj.nuevo = 1 lanza AttributeError. Es una feature, no un bug: te agarra los typos.
__dict__No existe. Cualquier código que haga vars(obj) o obj.__dict__.update(...) se rompe — incluye algunos serializadores.
Herencia múltipleDos bases con __slots__ no vacíos son incompatibles: TypeError: multiple bases have instance lay-out conflict.
Subclases descuidadasUna subclase que no declara __slots__ reintroduce el __dict__ y el ahorro se evapora en silencio.
weakrefNo se puede hacer weakref al objeto salvo que agregues "__weakref__" a los slots.
functools.cached_propertyNecesita __dict__ para guardar el valor: no funciona con slots.
 
class Base:
    __slots__ = ("a",)

class HijaOK(Base):
    __slots__ = ()          # mantiene el ahorro

class HijaFuga(Base):
    pass                    # ¡vuelve a tener __dict__! silenciosamente

print(hasattr(HijaOK(),   "__dict__"))   # False
print(hasattr(HijaFuga(), "__dict__"))   # True  <- el ahorro se perdió
Si usás @dataclass, no hace falta escribir los slots a mano: @dataclass(slots=True) los genera. Y si el objeto es realmente inmutable y chico, @dataclass(frozen=True, slots=True) o directamente un NamedTuple suelen ser aún más baratos.

PS2.2 sys.getsizeof miente: medir de verdad con tracemalloc

sys.getsizeof devuelve el tamaño del objeto y nada de lo que referencia. Para cualquier contenedor, eso lo vuelve casi inútil como medida de "cuánta memoria estoy usando":

import sys

textos = ["x" * 1000 for _ in range(10_000)]

sys.getsizeof(textos)          # ~80_056  -> "80 KB", dice la lista
sum(sys.getsizeof(t) for t in textos) + sys.getsizeof(textos)
                               # ~10_500_000 -> 10 MB de verdad
El error clásico: reportar getsizeof(mi_cache) en un dashboard y concluir que el caché "ocupa 300 KB". Lo que ocupa 300 KB es la tabla hash. Los valores adentro pueden ser gigabytes. Y sumar recursivamente tampoco es correcto, porque un objeto referenciado desde dos lugares se contaría dos veces.

tracemalloc, en la biblioteca estándar, resuelve el problema desde el otro lado: en vez de preguntarle a un objeto cuánto pesa, registra cada asignación del intérprete y la atribuye a la línea de código que la hizo.

import tracemalloc

tracemalloc.start(10)          # guardar 10 frames de stack por asignación

datos = {i: [0] * 100 for i in range(5_000)}
otros = ["y" * 500 for _ in range(20_000)]

snap = tracemalloc.take_snapshot()
for stat in snap.statistics("lineno")[:5]:
    print(stat)                # archivo:línea  tamaño  cantidad de bloques

actual, pico = tracemalloc.get_traced_memory()
print(f"actual {actual/1e6:.1f} MB · pico {pico/1e6:.1f} MB")
tracemalloc.stop()
tracemalloc tiene overhead real: entre 1,5× y 3× más lento, y la memoria del propio rastreo crece con la cantidad de frames que le pidas. Se enciende para diagnosticar, no se deja prendido en producción — para eso está memray o un muestreo periódico con pocos frames.
📌 Tres números distintos que no hay que confundir. (a) Memoria que Python cree que asignó (tracemalloc). (b) RSS del proceso, lo que ve el sistema operativo (psutil.Process().memory_info().rss) — es el número por el que te mata el OOM killer. (c) Memoria pico, no la final. Un job puede terminar en 200 MB y haber tocado 6 GB en el medio: el que te mata es el pico. 
import os, psutil, tracemalloc

proc = psutil.Process(os.getpid())

def snapshot_completo(etiqueta):
    py_actual, py_pico = tracemalloc.get_traced_memory()
    rss = proc.memory_info().rss
    print(f"{etiqueta:<12} python={py_actual/1e6:7.1f} MB "
          f"pico={py_pico/1e6:7.1f} MB  rss={rss/1e6:7.1f} MB")

tracemalloc.start()
snapshot_completo("inicio")
buffer = bytearray(300_000_000)
snapshot_completo("post-alloc")
del buffer
snapshot_completo("post-free")   # el RSS puede NO bajar: el allocator retiene arenas
Que el RSS no baje después de liberar objetos no es una fuga. CPython administra bloques chicos con su propio allocator (pymalloc) y devuelve arenas al sistema operativo solo cuando quedan completamente vacías; la fragmentación hace que muchas veces no pase. Fuga es cuando el RSS crece monótonamente ciclo tras ciclo, no cuando se queda en una meseta.

PS2.3 Cazar una fuga real: snapshots y compare_to

Una fuga en Python casi nunca es memoria "perdida" al estilo C: es memoria que todavía es alcanzable porque alguien guardó una referencia y se olvidó. Un caché sin límite, una lista de handlers a la que se le suscriben objetos que nunca se dan de baja, un logger que acumula registros, un decorador que retiene los argumentos.

La técnica es siempre la misma: dos snapshots separados por N ciclos de trabajo, y comparar. Lo que crece entre ambos es lo que se acumula.

import tracemalloc

# --- el sospechoso: un "caché" que nunca borra nada ---
_REGISTRO = []

def procesar(evento):
    resultado = {"id": evento, "payload": "z" * 2_000}
    _REGISTRO.append(resultado)          # <- acá está la fuga
    return resultado["id"]

def ciclo(n=5_000):
    for i in range(n):
        procesar(i)

tracemalloc.start(25)

ciclo()                                   # calentar: descartamos el arranque
antes = tracemalloc.take_snapshot()

ciclo()                                   # el trabajo que sospechamos que fuga
despues = tracemalloc.take_snapshot()

diferencias = despues.compare_to(antes, "lineno")
for stat in diferencias[:5]:
    print(f"{stat.size_diff/1e6:+7.2f} MB  {stat.count_diff:+7d} bloques  {stat}")

La salida señala la línea exacta que acumula. Cuando la línea no alcanza —porque el culpable es list.append llamado desde veinte lugares— se cambia el criterio a "traceback" y se pide el stack completo:

top = despues.statistics("traceback")[0]
print(f"{top.size/1e6:.1f} MB en {top.count} bloques, asignados desde:")
for linea in top.traceback.format():
    print("   ", linea)
Protocolo de caza de fugas, en orden. (1) Confirmar que hay fuga: el RSS crece ciclo tras ciclo y no se estabiliza. (2) Aislar el ciclo más chico que la reproduce. (3) compare_to entre dos snapshots para ubicar la línea. (4) Preguntarse quién retiene: gc.get_referrers(obj) te dice quién apunta al objeto. (5) Cortar la referencia o hacerla débil. (6) Test de regresión que falle si vuelve.
import gc

sospechoso = _REGISTRO[0]
for quien in gc.get_referrers(sospechoso):
    print(type(quien), repr(quien)[:80])   # ¿quién no lo suelta?
gc.get_referrers es una herramienta de diagnóstico interactivo, no de producción: es lenta, devuelve también frames temporales del propio intérprete, y puede resucitar objetos. Usala en un REPL o en un endpoint de debug protegido, nunca en el camino caliente.

PS2.4 Ciclos, weakref y cachés que no retienen

Del refcounting de PS1 se deduce una regla directa: mientras alguien tenga una referencia fuerte, el objeto vive. Un caché es, por definición, alguien que tiene una referencia fuerte a todo lo que cacheó. Por eso el caché es la fuente número uno de fugas en Python.

weakref ofrece la referencia que no cuenta: permite observar un objeto sin impedir que muera.

import weakref, gc

class Sesion:
    def __init__(self, uid): self.uid = uid

s = Sesion("u-1")
ref = weakref.ref(s)

print(ref())        # <Sesion object ...>  el objeto sigue vivo
del s
gc.collect()
print(ref())        # None  -> murió, y la referencia débil lo sabe

La forma útil de eso es un caché que no retiene: WeakValueDictionary. Sirve para lo que en inglés llaman identity map — garantizar que si dos partes del programa piden el mismo id obtengan el mismo objeto, sin que ese mapa mantenga vivo nada por su cuenta.

import weakref

class Documento:
    def __init__(self, doc_id, contenido):
        self.doc_id, self.contenido = doc_id, contenido

_VIVOS = weakref.WeakValueDictionary()

def obtener(doc_id):
    doc = _VIVOS.get(doc_id)
    if doc is None:
        doc = Documento(doc_id, cargar_de_disco(doc_id))
        _VIVOS[doc_id] = doc          # NO impide que se libere
    return doc

a = obtener("d1")
b = obtener("d1")
assert a is b                          # misma instancia mientras alguien la use
del a, b                               # cuando nadie la usa, sale del mapa sola
⚠️ No todo se puede referenciar débilmente. int, str, tuple, list y dict no soportan weakref (y las clases con __slots__ tampoco, salvo que incluyan "__weakref__"). Un WeakValueDictionary de strings tira TypeError. Si necesitás cachear valores primitivos con límite, lo correcto es un caché LRU acotado, no weakrefs.

El otro uso serio de weakref es romper ciclos. El caso canónico es padre ↔ hijo: si ambos lados son fuertes, el par entero depende del GC generacional para morir. Si la referencia al padre es débil, el refcounting los libera al instante:

import weakref

class Nodo:
    __slots__ = ("valor", "hijos", "_padre", "__weakref__")

    def __init__(self, valor):
        self.valor, self.hijos, self._padre = valor, [], None

    @property
    def padre(self):
        return self._padre() if self._padre is not None else None

    def agregar(self, hijo):
        self.hijos.append(hijo)             # fuerte hacia abajo
        hijo._padre = weakref.ref(self)     # DÉBIL hacia arriba: no hay ciclo
Y para la limpieza determinista de recursos asociados a un objeto, weakref.finalize(obj, funcion, *args) es la alternativa correcta a __del__: se ejecuta cuando el objeto muere, no participa del ciclo, y se puede cancelar. Igual, si el recurso es un archivo o un socket, la respuesta sigue siendo with.

python -c "

El sesgo de cProfile que engaña a todo el mundo: cobra un costo fijo por llamada. Una función chiquita invocada diez millones de veces aparece inflada; un bloque monolítico que tarda lo mismo aparece barato. Resultado: te manda a optimizar getters triviales. Cuando el perfil determinista y el de sampling no coinciden, creele al de sampling.
tottime es el tiempo propio de la función; cumtime incluye todo lo que llamó. Si main encabeza por cumtime, no descubriste nada — ordená por tottime para encontrar dónde se quema CPU realmente.

scalene: cuando no sabés si el problema es Python o es C

uv tool install scalene
scalene --html --outfile perfil.html mi_script.py

💡 Lo que hace único a scalene. Separa, línea por línea, el tiempo gastado en el intérprete de Python del gastado en código nativo (NumPy, Pandas, tu extensión en Rust). Esa distinción es la que decide la estrategia: si la línea caliente ya es 95% nativa, reescribirla en Python no te va a dar nada y hay que cambiar de algoritmo o de librería. Si es 95% Python, vectorizar o bajar a C sí va a mover la aguja.

PS2.6 Cómo se lee un flamegraph

Es el formato en el que te van a llegar los perfiles y se malinterpreta sistemáticamente. Tres reglas alcanzan:

1. El ancho es todo. El ancho de una barra es la fracción de muestras en las que esa función estaba en el stack: su tiempo total (inclusivo). Una barra que ocupa media pantalla es donde se va la mitad del tiempo. Punto.
2. La altura no significa nada. El eje vertical es profundidad de la pila de llamadas, no tiempo ni importancia. Una torre altísima y flaca es irrelevante; una barra baja y ancha es tu problema.
3. El eje X no es la línea de tiempo. Los frames se ordenan alfabéticamente para que los hermanos se agrupen y las mesetas se vean. No leas "primero esto, después aquello": no hay cronología.
📌 Qué buscar, en la práctica. Mesetas anchas (una función que domina) y sobre todo hojas anchas: una barra ancha sin nada encima es tiempo propio, código que está quemando CPU él mismo. Ese es el candidato número uno. Un frame ancho con una torre encima solo está esperando a sus hijos: el culpable está más arriba.
Un icicle graph (crece hacia abajo, es lo que muestra memray) es el mismo gráfico dado vuelta. Y ojo con el eje semántico: en un flamegraph de CPU el ancho es tiempo; en uno de memoria el ancho es bytes asignados. Se leen igual, pero responden preguntas distintas.

PS2.7 Optimizaciones que mueven la aguja, en orden

Cuando el perfil ya te dijo dónde está el tiempo, se aplican en este orden. No es una lista de opciones: es una secuencia, y se baja un escalón solo cuando el anterior está agotado.

#PalancaGanancia típicaCosto
1Algoritmo — bajar la complejidad10×–1000×Pensar; a veces reescribir
2Estructura de datos — set en vez de list, deque, array, columnas10×–100×Bajo
3Evitar copias — streaming, memoryview, generadores2×–10×, y baja el pico de memoriaMedio
4Cachear — functools.cache, memoización, precómputoDepende del hit rateRiesgo de fuga e invalidación
5Vectorizar / salir de Python — NumPy, Polars, extensión nativa10×–100× en cargas numéricasDependencia nueva; revalidar resultados
—Micro-optimizar bytecode0–5%Código ilegible para siempre
 
import time

def lento(consultas, universo):          # O(n·m): busca en una lista
    return [q for q in consultas if q in universo]

def rapido(consultas, universo_set):     # O(n): busca en un hash
    return [q for q in consultas if q in universo_set]

universo   = list(range(200_000))
universo_s = set(universo)
consultas  = list(range(0, 200_000, 7))

for nombre, fn, u in (("list", lento, universo), ("set", rapido, universo_s)):
    t0 = time.perf_counter(); fn(consultas, u)
    print(f"{nombre}: {time.perf_counter()-t0:.3f}s")
# list: ~9 s   ·   set: ~0.003 s   -> tres órdenes de magnitud, un cambio de tipo

El escalón 3 —evitar copias— es el que más se ignora y el que más impacta en memoria. La diferencia entre materializar y transmitir:

import tracemalloc

def materializando(path):
    with open(path, encoding="utf-8") as f:
        lineas = f.readlines()                       # TODO el archivo en RAM
    return sum(len(l) for l in lineas if l.startswith("ERROR"))

def transmitiendo(path):
    with open(path, encoding="utf-8") as f:
        return sum(len(l) for l in f if l.startswith("ERROR"))   # una línea por vez

for fn in (materializando, transmitiendo):
    tracemalloc.start()
    fn("app.log")
    print(fn.__name__, f"pico {tracemalloc.get_traced_memory()[1]/1e6:.1f} MB")
    tracemalloc.stop()
# El resultado es idéntico; el pico de memoria, no.
Micro-optimizaciones que no valen la pena en 2026: sacar el punto del loop (method hoisting), reemplazar for por map "porque es en C", usar variables locales en lugar de globales por deporte, o elegir % sobre f-strings. Todo eso rinde entre 0 y 5% y lo mata cualquier decisión de los escalones 1 a 3. La excepción real y siempre válida: no concatenes strings en un loop — usá "".join(partes), porque ahí el problema no es micro, es cuadrático.

PS2.8 lru_cache: ganancia o fuga con buena prensa

functools.lru_cache es un decorador de una línea que puede darte 100× o comerte la RAM del servidor. Las dos cosas por el mismo motivo: mantiene referencias fuertes a los argumentos y a los resultados.

from functools import lru_cache, cache

@lru_cache(maxsize=1024)          # ACOTADO: descarta lo menos usado
def cotizacion(par: str, dia: str) -> float:
    return consultar_api(par, dia)

@cache                            # equivale a lru_cache(maxsize=None): SIN límite
def fib(n: int) -> int:
    return n if n < 2 else fib(n - 1) + fib(n - 2)

# Medir el caché no es opcional: es el único modo de saber si sirve
cotizacion("EURUSD", "2026-09-01")
cotizacion("EURUSD", "2026-09-01")
print(cotizacion.cache_info())
# CacheInfo(hits=1, misses=1, maxsize=1024, currsize=1)
Cachear conviene si…Es una fuga disfrazada si…
El dominio de argumentos es chico y acotadoLos argumentos son ids de usuario, timestamps o UUIDs: el dominio es infinito
La función es pura y deterministaLos datos subyacentes cambian y nadie invalida el caché
El hit rate medido es altoNunca miraste cache_info()
Los resultados son chicosDevolvés DataFrames, respuestas HTTP completas o listas grandes
Pusiste un maxsize deliberadoUsaste @cache "porque es más lindo"
⚠️ La trampa que más veces vi en producción: @lru_cache sobre un método. El primer argumento es self, así que el caché guarda una referencia fuerte a la instancia y no la suelta nunca. Todos los objetos que hayan pasado por ese método quedan vivos para siempre, con todo lo que arrastren. El caché es un atributo de la función, que vive en la clase: no muere con la instancia. 
from functools import lru_cache, cached_property

class Informe:
    def __init__(self, filas): self.filas = filas   # 200 MB, digamos

    @lru_cache(maxsize=None)        # ❌ retiene TODAS las instancias, para siempre
    def total_malo(self):
        return sum(self.filas)

    @cached_property                # ✅ el valor vive en la instancia y muere con ella
    def total(self):
        return sum(self.filas)
Reglas de bolsillo: (1) maxsize explícito siempre, salvo dominio demostrablemente finito. (2) Cachés por instancia → cached_property, no lru_cache. (3) Exponé cache_info() en tus métricas: un caché con hit rate del 12% es solo memoria desperdiciada, y con 0% es memoria desperdiciada y latencia agregada. (4) En un servidor con N workers, hay N cachés independientes: multiplicá la memoria por N antes de dimensionar.

PS2.9 Cuándo NO optimizar

La decisión más rentable de este módulo suele ser no hacer nada. Antes de tocar una línea, pasá estos filtros:

1. ¿El tiempo está en I/O? Si el 95% se va esperando la base de datos, una API o el disco, el intérprete es irrelevante — podrías reescribir todo en C y ganar 5%. La palanca ahí es un índice, menos round-trips, un JOIN en vez de N+1 consultas, o concurrencia de I/O (PS3). No es un problema de Python.
2. ¿Tenés una métrica y un objetivo? "Hacerlo más rápido" no es un objetivo. "p99 por debajo de 300 ms" o "el job entra en 2 GB" sí lo son, y además te dicen cuándo parar. Sin número, la optimización no termina nunca.
3. ¿Cuánto cuesta el problema realmente? Un job nocturno que tarda 40 minutos en vez de 10 y a nadie le molesta no es un problema de rendimiento: es una molestia estética. Dos días de trabajo ahí son dos días que no dedicaste a algo que sí importa.
4. ¿La optimización cabe en la cabeza del próximo? Código raro y 15% más rápido, en una ruta que no domina el perfil, es deuda pura. Si lo hacés igual, dejá el benchmark que lo justifica al lado del código: sin esa evidencia, en seis meses alguien lo va a "limpiar" — y va a tener razón.
📌 El orden que casi nunca falla. Corrección → claridad → medición → optimización del término dominante → guardia de regresión. Saltarse la medición es la definición operativa de superstición.

🧑‍🎓 Worked Example — "el job come 6 GB y lo mata el OOM killer"

Un ETL nocturno lee 40 millones de filas, calcula un score por fila y escribe un resumen. Andaba bien. Desde que el dataset creció, el contenedor (límite: 4 GB) lo mata a mitad de camino con Killed — sin traceback, sin log, sin nada. La primera propuesta del equipo es subir el límite a 8 GB.

Paso 1 — Confirmar el síntoma con un número, no con una impresión. "Killed" sin traceback es la firma del OOM killer del kernel. Lo primero es medir el pico real y ver si crece con el input:

/usr/bin/time -v python job.py 2>&1 | grep "Maximum resident"
# Maximum resident set size (kbytes): 6120448   -> 6,1 GB de pico

dmesg | tail -5
# Out of memory: Killed process 4711 (python) total-vm:7.9G, anon-rss:6.0G

Paso 2 — Perfilar la memoria, no la CPU. El problema es espacio, así que la herramienta es memray, con un subconjunto del input que quepa en la máquina de desarrollo:

memray run --native -o job.bin job.py --limite 2000000
memray flamegraph job.bin        # -> memray-flamegraph-job.html
memray summary  job.bin

Paso 3 — Leer el flamegraph. Una sola meseta ocupa el 88% del ancho, y su hoja es una línea:

# job.py  (versión original)
def procesar(path):
    resultados = []                                   # <- 5,4 GB acá
    for fila in leer_csv(path):
        resultados.append({
            "id":    fila["id"],
            "score": calcular_score(fila),
            "crudo": fila,                            # se guarda la fila ENTERA
        })
    return resumir(resultados)

El diagnóstico es completo: se acumulan 40 millones de diccionarios que además retienen la fila original, cuando lo único que resumir necesita es un agregado. La memoria crece linealmente con el input: subir el límite a 8 GB compra tres meses, no una solución.

Paso 4 — Las opciones, con su costo. Esta tabla es el entregable real del análisis; sin ella, la decisión es una opinión:

OpciónPico esperadoCosto / riesgo
Subir el límite del contenedor a 8 GB6,1 GB (igual)No arregla nada: vuelve a romperse cuando el dataset crezca. Y cuesta plata todos los meses.
Generador: yield en vez de append, y agregación incremental~40 MBBajo. resumir debe aceptar un iterable y no indexar ni recorrer dos veces.
Chunking: procesar de a 50.000 filas y escribir parciales~150 MBMedio. Requiere reducción parcial + merge final; permite reanudar si falla.

Paso 5 — Decidir. Gana el generador: resuelve el problema entero, no agrega dependencias y el diff es de veinte líneas. El chunking queda anotado como paso siguiente si más adelante hace falta reanudar tras un fallo; Polars queda para cuando el cuello pase de ser memoria a ser tiempo.

# job.py  (versión corregida)
from collections import Counter
from typing import Iterator

def procesar(path) -> Iterator[tuple[str, float]]:
    """Perezoso a propósito: NO materializa. Ver test_no_materializa."""
    for fila in leer_csv(path):
        yield fila["id"], calcular_score(fila)      # solo lo que se necesita

def resumir(pares) -> dict:
    total, n, por_bucket = 0.0, 0, Counter()
    for _id, score in pares:                        # una pasada, estado O(1)
        total += score
        n += 1
        por_bucket[round(score, 1)] += 1
    return {"promedio": total / n, "n": n, "buckets": dict(por_bucket)}

Paso 6 — La guardia, que es lo que hace que esto sea trabajo senior. Un arreglo sin test se deshace la primera vez que alguien "solo necesita la lista completa un momentito". Van dos guardias complementarias: una sobre el contrato (es perezoso) y otra sobre el presupuesto (no supera X MB).

# tests/test_job_memoria.py
import inspect, tracemalloc, pytest
from job import procesar, resumir

def test_no_materializa():
    """Contrato: procesar() devuelve un generador. Si alguien mete un
    list(...) adentro, este test falla ANTES de que lo haga el OOM killer."""
    assert inspect.isgeneratorfunction(procesar)
    salida = procesar("tests/datos/muestra.csv")
    assert inspect.isgenerator(salida)

@pytest.mark.limit_memory("150 MB")        # requiere pytest-memray
def test_presupuesto_de_memoria():
    """El job entero sobre 1M de filas debe entrar en 150 MB."""
    assert resumir(procesar("tests/datos/1M.csv"))["n"] == 1_000_000

def test_pico_no_escala_con_el_input():
    """La marca del streaming: duplicar el input NO duplica el pico."""
    picos = []
    for archivo in ("tests/datos/100k.csv", "tests/datos/200k.csv"):
        tracemalloc.start()
        resumir(procesar(archivo))
        picos.append(tracemalloc.get_traced_memory()[1])
        tracemalloc.stop()
    assert picos[1] < picos[0] * 1.3       # constante, no lineal
📌 La lección del ejercicio no es "usá generadores". Es la secuencia: reproducir con un número (6,1 GB, no "mucha memoria") → elegir la herramienta según la métrica (memoria ⇒ memray, no cProfile) → tabular las opciones con su costo antes de elegir → dejar una guardia ejecutable. El tercer test es el más valioso de los tres: no verifica un valor, verifica una propiedad —que el pico no escala con el input— y esa propiedad es justamente la que se rompió.

Checkpoint — ¿lo tenés claro?

Tu servicio libera un montón de objetos y el RSS no baja. ¿Es una fuga?

Probablemente no. CPython administra los objetos chicos con pymalloc, que agrupa las asignaciones en arenas y solo las devuelve al sistema operativo cuando quedan completamente vacías; con fragmentación, eso casi nunca pasa. Que la memoria se quede en una meseta después de un pico es comportamiento normal y esperado. La firma de una fuga es distinta: el RSS crece monótonamente ciclo tras ciclo, sin estabilizarse. La forma de distinguirlas es correr N ciclos idénticos y comparar tracemalloc entre el ciclo 2 y el ciclo 10: si el delta es plano, es fragmentación; si crece proporcional a los ciclos, alguien está guardando referencias.

El perfil de cProfile dice que el 40% del tiempo está en un getter de dos líneas. ¿Qué hacés?

Desconfiar y confirmar con un profiler de sampling. cProfile es determinista y cobra un costo fijo por llamada, así que infla sistemáticamente las funciones chicas y muy llamadas — un getter invocado diez millones de veces es el caso de manual. Corré py-spy record o scalene sobre la misma carga: si el getter desaparece del top, era artefacto del instrumento. Y si igual resulta ser real, la solución no es "optimizar el getter": es llamarlo menos veces —sacarlo de un loop, cachear el valor, o cambiar la estructura de datos— porque en Python el costo dominante es la llamada en sí, no el cuerpo.

¿Por qué @lru_cache sobre un método es peligroso, y qué usás en su lugar?

Porque el caché es un atributo de la función, que vive en la clase, no en la instancia — y el primer argumento cacheado es self. Eso significa que el diccionario del caché mantiene una referencia fuerte a cada instancia que haya pasado por el método, y esas instancias no se liberan nunca, con todo lo que arrastren (DataFrames, conexiones, buffers). Es una fuga que crece con el tráfico y no se ve en el código. Para un valor derivado por instancia, la herramienta correcta es functools.cached_property: guarda el resultado en el __dict__ de la instancia y muere con ella. Si además necesitás invalidarlo, un del obj.propiedad lo limpia. Y si de verdad querés un caché compartido entre instancias, cacheá una función libre que reciba solo los datos primitivos que importan, nunca self.

Resumen ejecutivo

  • Rendimiento es método, no trucos: métrica → medición → término dominante → guardia de regresión. Sin métrica no hay optimización, hay superstición.
  • __slots__ elimina el __dict__ por instancia: 30–50% menos memoria cuando hay muchas instancias chicas. Rompe atributos dinámicos, vars(), herencia múltiple, cached_property, y una subclase sin __slots__ anula el ahorro en silencio.
  • sys.getsizeof es superficial y no sirve para contenedores. Los números reales salen de tracemalloc (por línea de Python) y del RSS (lo que mira el OOM killer). El que te mata es el pico, no el final.
  • Fugas: dos snapshots + compare_to ubican la línea; gc.get_referrers dice quién retiene. En Python la fuga casi siempre es una referencia olvidada, y casi siempre es un caché.
  • weakref observa sin retener: WeakValueDictionary para identity maps, referencias débiles hacia arriba para romper ciclos padre↔hijo. Ojo: int, str, tuple, list y dict no admiten weakref.
  • Herramienta según la pregunta: cProfile para el mapa inicial (con su sesgo por llamada), py-spy para producción sin instrumentar y para procesos colgados, memray para memoria, scalene para separar tiempo de Python del de C.
  • En un flamegraph: el ancho es el tiempo, la altura no significa nada, y el eje X no es cronológico. Buscá hojas anchas.
  • Orden de las palancas: algoritmo → estructura de datos → evitar copias → cachear → vectorizar. Las micro-optimizaciones de bytecode rinden 0–5% y cuestan legibilidad para siempre.
  • lru_cache retiene referencias fuertes: con maxsize=None y dominio infinito es una fuga; sobre un método retiene self eternamente. Medí siempre cache_info().
  • Si el tiempo está en I/O, el intérprete es irrelevante. Es el caso más frecuente y el más ignorado.

🧠 Autoevaluación

1. Un job se muere por OOM y querés saber qué línea acumula la memoria. ¿Qué herramienta usás?

La pregunta es de memoria, así que la herramienta tiene que medir memoria. cProfile y timeit miden tiempo y no van a ver nada; getsizeof es superficial y no dice quién asignó qué. memray registra cada asignación y te da un flamegraph donde el ancho son bytes; tracemalloc con dos snapshots y compare_to llega al mismo lugar sin instalar nada, a cambio de más overhead.

2. Agregaste @lru_cache(maxsize=None) a un método de una clase que carga 200 MB de datos. Con el tiempo el servicio consume cada vez más RAM. ¿Por qué?

El caché es un atributo de la función, y la función vive en la clase — no en la instancia. Como el primer argumento cacheado es self, cada instancia que pasa por el método queda referenciada fuertemente por el diccionario del caché y no se libera jamás, arrastrando sus 200 MB. Para un valor derivado por instancia va functools.cached_property, que guarda el resultado en la instancia y muere con ella.

3. En un flamegraph de CPU ves una torre muy alta y angosta, y al lado una barra baja que ocupa el 60% del ancho. ¿Dónde está el problema?

El ancho de una barra es la fracción de muestras en las que esa función estaba en el stack, o sea su tiempo total: el 60% del tiempo se va ahí. La altura es solo profundidad de llamadas y no dice nada sobre el costo. Y el eje X está ordenado alfabéticamente para agrupar hermanos y hacer visibles las mesetas — no es una línea de tiempo, así que "cuál aparece primero" no significa nada.

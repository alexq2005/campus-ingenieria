PS7 — Testing serio

PS7.0 Por qué este módulo

Casi todos los proyectos empiezan con tests. Muy pocos los conservan. El patrón de muerte es siempre el mismo: la suite tarda ocho minutos, alguien la saca del hook de pre-commit "por ahora", después dos tests empiezan a fallar de a ratos, se marcan como skip "hasta que los arreglemos", y seis meses más tarde nadie confía en lo que dice el CI. Un test suite lento o frágil se termina desactivando, y a partir de ese día tenés todo el costo de mantener tests y ninguno de sus beneficios.

💡 La tesis del módulo. El objetivo de testear no es la cobertura. Es confianza para cambiar código. Un test sirve si, cuando lo rompés, te enteraste de algo que te importaba; y si, cuando pasa, podés hacer deploy sin revisar a mano. Todo lo que sigue —hypothesis, mutation testing, testcontainers— son formas de responder una sola pregunta: ¿mis tests se romperían si el código estuviera mal?

Esa pregunta es más incómoda de lo que parece, porque la métrica que todo el mundo mira —la cobertura— no la responde. Se puede tener 100% de líneas cubiertas y una suite que no detecta absolutamente nada. En PS7.6 vamos a construir exactamente ese caso y romperlo.

Todo lo de esta lección se instala con el toolchain de PS6:

uv add --dev pytest pytest-cov pytest-xdist pytest-asyncio anyio hypothesis mutmut testcontainers
uv run pytest -q

PS7.1 Fixtures: el modelo mental correcto

Una fixture no es "código que corre antes del test". Es una dependencia declarada por nombre: el test pide db y pytest se encarga de construirla, cachearla según su scope y destruirla. Es inyección de dependencias, no setUp().

import pytest

@pytest.fixture
def carrito():
    return Carrito(usuario="ana")

def test_carrito_arranca_vacio(carrito):     # pide "carrito" por nombre
    assert carrito.total() == 0

def test_agregar_suma(carrito):              # recibe uno NUEVO, no el de arriba
    carrito.agregar("libro", 1000)
    assert carrito.total() == 1000

Setup y teardown con yield

Si la fixture usa yield en vez de return, todo lo que va después del yield es el teardown, y corre aunque el test falle:

import pytest, tempfile, shutil
from pathlib import Path

@pytest.fixture
def dir_temporal():
    ruta = Path(tempfile.mkdtemp())
    yield ruta                     # el test corre acá
    shutil.rmtree(ruta)            # se limpia SIEMPRE, pase o falle
Para archivos temporales no escribas eso: pytest ya trae tmp_path (un Path por test), tmp_path_factory (compartido), monkeypatch, capsys y caplog. Antes de escribir una fixture, revisá si ya existe — vale la regla de Verify Before Creating.

Scopes: dónde se paga el tiempo

ScopeSe construyeUsalo paraRiesgo
function (default)Una vez por testDatos, objetos baratosNinguno; es el correcto por defecto
classUna vez por clase de testsAgrupar tests que comparten un estado caroOrden implícito entre tests
moduleUna vez por archivoUn cliente HTTP, un parser costosoUn test puede ensuciar al siguiente
sessionUna vez por corridaLevantar Postgres, compilar, entrenar un modelo chicoAlto: estado global; y con xdist se crea una por worker
📌 La regla: el scope más caro para el recurso, el más barato para los datos. Levantá el contenedor de Postgres en session, pero abrí una transacción por test que se revierte al final. Así pagás el arranque una vez y conservás el aislamiento. 
@pytest.fixture(scope="session")
def motor():                       # caro: una sola vez en toda la corrida
    return crear_engine(URL_TEST)

@pytest.fixture                    # barato: uno por test, y se deshace
def sesion(motor):
    conn = motor.connect()
    trx = conn.begin()
    yield Sesion(bind=conn)
    trx.rollback()                 # el test no deja rastro en la base
    conn.close()

Fixtures como factories

El error más común de fixtures es que devuelvan un objeto fijo. En cuanto necesitás dos usuarios distintos, la fixture no sirve. La solución es que la fixture devuelva una función:

@pytest.fixture
def hacer_usuario(sesion):
    creados = []

    def _hacer(nombre="ana", saldo=0, activo=True):
        u = Usuario(nombre=nombre, saldo=saldo, activo=activo)
        sesion.add(u)
        creados.append(u)
        return u

    yield _hacer                          # el test recibe la FÁBRICA
    for u in creados:                     # y el teardown sabe qué limpiar
        sesion.delete(u)

def test_transferencia(hacer_usuario):
    origen  = hacer_usuario("ana", saldo=1000)
    destino = hacer_usuario("beto", saldo=0)
    transferir(origen, destino, 400)
    assert (origen.saldo, destino.saldo) == (600, 400)

conftest.py y su jerarquía

conftest.py es el archivo donde viven las fixtures compartidas. No se importa: pytest lo descubre solo, y lo hace por directorio. Las fixtures de un conftest.py están disponibles para ese directorio y todos sus hijos, y un hijo puede redefinir el nombre de una fixture del padre.

tests/
├─ conftest.py            # fixtures globales: config, factories, marks
├─ unit/
│  └─ test_precios.py     # ve las de tests/
└─ integracion/
   ├─ conftest.py         # fixtures de infra: postgres, redis
   └─ test_ordenes.py     # ve las de tests/ Y las de integracion/
El conftest.py gigante es una señal de alarma. Cuando el de la raíz pasa de 300 líneas y empieza a importar la mitad de la app, dejó de ser configuración y se volvió un módulo de producción sin tests. Partilo por directorio: la fixture de Postgres no tiene por qué existir cuando corrés solo los unitarios.

request: la fixture que describe al test

@pytest.fixture

Fixtures parametrizadas

Con params=, cada test que use la fixture se multiplica. Es la forma de correr toda una carpeta contra dos backends sin tocar ni un test:

@pytest.fixture(params=["sqlite", "postgres"], ids=["sqlite", "pg"])
def repo(request):
    if request.param == "sqlite":
        yield RepoSQLite(":memory:")
    else:
        yield RepoPostgres(os.environ["PG_URL"])

# este único test corre DOS veces: test_guardar[sqlite] y test_guardar[pg]
def test_guardar(repo):
    repo.guardar(Orden(id=1))
    assert repo.buscar(1) is not None
Ojo con el efecto multiplicativo: una fixture con 3 params usada por otra con 4 params genera 12 combinaciones por test. Es la causa número uno de suites que pasan de 40 segundos a 9 minutos sin que nadie se dé cuenta.

PS7.2 parametrize, y el ids= que casi nadie usa

Un for adentro de un test es un antipatrón: si falla la tercera iteración, el test se corta y no sabés nada de las otras. parametrize genera N tests independientes.

import pytest
from tienda import precio_final

@pytest.mark.parametrize(
    ("monto", "esperado"),
    [
        (0,        0.0),
        (999.99,   999.99),
        (1_000,    950.0),
        (9_999,    9_499.05),
        (10_000,   8_500.0),
    ],
)
def test_precio_por_escalon(monto, esperado):
    assert precio_final(monto) == pytest.approx(esperado)

Sin ids, el fallo dice test_precio_por_escalon[3]. Con ids, dice lo que rompiste:

@pytest.mark.parametrize(
    ("monto", "esperado"),
    [
        pytest.param(999.99, 999.99,   id="justo-abajo-del-primer-escalon"),
        pytest.param(1_000,  950.0,    id="borde-exacto-primer-escalon"),
        pytest.param(9_999,  9_499.05, id="justo-abajo-del-segundo"),
        pytest.param(10_000, 8_500.0,  id="borde-exacto-segundo-escalon"),
        pytest.param(-1,     None,     id="monto-negativo",
                     marks=pytest.mark.xfail(raises=ValueError, strict=True)),
    ],
)
def test_precio_por_escalon(monto, esperado):
    assert precio_final(monto) == pytest.approx(esperado)
📌 El id no es cosmética. Es lo único que vas a ver en el log de CI a las 2 AM. FAILED test_precio[borde-exacto-segundo-escalon] te dice qué invariante se rompió; FAILED test_precio[3] te obliga a abrir el archivo y contar. Y como bonus: pytest -k "borde-exacto" corre justo esos.

PS7.3 pytest en el día a día

La diferencia entre alguien que "tiene tests" y alguien que usa tests está casi entera en estos flags:

ComandoQué haceCuándo
pytest -xPara en el primer falloCuando rompiste algo grande y no querés 400 líneas de traceback
pytest --lfCorre solo los que fallaron la vez pasadaEl loop de arreglar un bug. Es el flag más rentable de todos
pytest --ffCorre todos, pero los que fallaron primeroVerificación final del fix
pytest -k "orden and not lento"Filtra por subcadena del nombreIterar sobre un área sin conocer los marks
pytest -m integracionFiltra por markSeparar unitarios de integración en CI

Los marks se declaran en la config para que un typo sea un error y no un test que silenciosamente no corre nunca:

# pyproject.toml
[tool.pytest.ini_options]
addopts = "-q --strict-markers --strict-config"
testpaths = ["tests"]
markers = [
  "lento: tarda mas de 1s",
  "integracion: necesita infra real (docker)",
]
filterwarnings = ["error"]        # un DeprecationWarning nuevo rompe el build
--strict-markers es obligatorio. Sin él, @pytest.mark.integracon (con el typo) es un mark válido que no matchea nada: el test queda excluido de -m integracion y de -m "not integracion" a la vez. Nadie lo nota durante meses.

PS7.4 Property-based testing con hypothesis

Los tests por ejemplo verifican los casos que se te ocurrieron. El problema es que los bugs viven, casi por definición, en los casos que no se te ocurrieron. El property-based testing invierte el planteo: en vez de escribir 20 ejemplos, describís una propiedad que siempre debe valer y la librería busca un contraejemplo.

La analogía. Un test por ejemplo es un control de calidad que revisa cinco piezas elegidas a mano. Una propiedad es la especificación de la pieza, y hypothesis es un inspector que genera piezas raras a propósito —el string vacío, el NaN, el entero de 400 dígitos, la lista con dos elementos iguales— buscando una que viole la spec. 
from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_ordenar_es_idempotente(xs):
    assert sorted(sorted(xs)) == sorted(xs)

@given(st.text())
def test_json_roundtrip(s):
    assert json.loads(json.dumps(s)) == s

@given(st.lists(st.integers(), min_size=1))
def test_el_maximo_esta_en_la_lista(xs):
    assert max(xs) in xs

Las propiedades que sirven

PatrónFormaEjemplo típico
Round-tripdecode(encode(x)) == xSerializadores, parsers, compresión, ORM
InvarianteAlgo que siempre vale del resultadoUn saldo nunca es negativo; el total = suma de ítems
Oráculorapido(x) == lento_obvio(x)Comparar tu versión optimizada con la ingenua
Monotoníaa <= b implica f(a) <= f(b)Precios, rankings, scores, escalones
Idempotenciaf(f(x)) == f(x)Normalizar, deduplicar, migraciones, PUT
Nunca explotaLa función no lanza excepciones inesperadasParsers de entrada del usuario

assume: descartar entradas sin sentido

from hypothesis import given, assume, strategies as st

@given(st.integers(), st.integers())
def test_division(a, b):
    assume(b != 0)                # descarta el caso, no lo falla
    assert (a // b) * b + (a % b) == a
assume tira entradas a la basura. Si descartás demasiadas, hypothesis aborta con FailedHealthCheck: filter_too_much, y tiene razón: si el 95% de lo que genera no sirve, el problema es la estrategia, no el filtro. Construí la estrategia correcta con .map(), .filter() liviano o st.builds() en vez de generar basura y descartarla. 
# mal: genera cualquier cosa y descarta casi todo
@given(st.text())
def test_email(s):
    assume("@" in s and "." in s.split("@")[-1])   # descarta el 99.9%
    ...

# bien: la estrategia solo produce cosas válidas
emails = st.builds(
    "{}@{}.com".format,
    st.text(st.characters(whitelist_categories=("Ll", "Nd")), min_size=1, max_size=20),
    st.sampled_from(["ejemplo", "test", "correo"]),
)

@given(emails)
def test_email(e):
    assert parsear_email(e).dominio.endswith(".com")

Shrinking: por qué el contraejemplo es tan chiquito

Esto es lo que separa a hypothesis de un simple generador aleatorio. Cuando encuentra un fallo, no te lo reporta: primero lo reduce. Prueba versiones sistemáticamente más simples del contraejemplo (listas más cortas, números más cercanos a cero, strings más cortos) mientras el test siga fallando.

Falsifying example: test_promedio(
    xs=[0, 0],
)

El fallo original quizá fue xs=[-914, 22, 0, 8871, -3, 0, 5]. Después de decenas de intentos, hypothesis descubre que ninguno de esos números importa: lo único necesario es que la suma dé cero. El contraejemplo mínimo es el diagnóstico. No te dice solo "falla", te dice qué hace fallar.

Hypothesis guarda los contraejemplos que encontró en .hypothesis/examples/ y los vuelve a probar primero en cada corrida. Un bug que encontró una vez no vuelve a colarse. Ese directorio va en .gitignore; el caso que valga la pena se congela a mano con @example(...). 
from hypothesis import given, example, strategies as st

@given(st.floats(allow_nan=False, allow_infinity=False))
@example(0.0)              # casos que ya nos mordieron: siempre se prueban
@example(-0.0)
def test_formato_moneda(x):
    assert formatear(x).startswith("$")

📌 No se elige: se combinan. Ejemplos para los casos de negocio que un humano tiene que poder leer ("un socio con cupón paga 14.000"). Propiedades para las leyes que el sistema no puede violar nunca ("el precio nunca es negativo", "gastar más nunca sale más barato"). Cada uno cubre exactamente el punto ciego del otro.

PS7.6 La cobertura es una métrica engañosa

La cobertura mide qué líneas se ejecutaron. No mide si alguien verificó el resultado. Este test da 100%:

def test_no_explota():
    for m in (500, 2_000, 20_000):
        precio_final(m)        # 100% de lineas. CERO asserts. CERO valor.

Y hay una segunda trampa, más sutil: la cobertura de líneas no es la de ramas.

def envio(monto, urgente=False):
    costo = 500
    if monto > 5_000:
        costo = 0
    if urgente:
        costo += 800
    return costo

# Con dos tests -- envio(10_000) y envio(1_000, urgente=True) -- todas las
# lineas se ejecutan: cobertura de lineas 100%.
# Pero la combinacion (monto alto + urgente) nunca se probo.
uv run pytest --cov=tienda --cov-branch --cov-report=term-missing
# la columna "Missing" con --cov-branch muestra "12->15", o sea:
# la rama que va de la linea 12 a la 15 nunca se tomo
MétricaQué garantizaQué NO garantiza
Cobertura de líneasLa línea se ejecutóQue alguien haya verificado nada
Cobertura de ramasCada if se tomó por los dos ladosLas combinaciones de condiciones
Mutation scoreQue romper el código rompe un testQue hayas escrito los tests que faltan
El antipatrón del 100% obligatorio. Poner fail_under = 100 no produce mejores tests: produce tests escritos para tocar líneas. La gente empieza a testear __repr__ y getters porque son baratos, y sigue sin testear el cálculo de facturación porque es difícil. Un piso razonable (70–80%) más 100% en los módulos que tocan plata, seguridad o datos del usuario refleja mucho mejor el riesgo real.

PS7.7 Mutation testing: la única forma de saber si tus tests sirven

💡 La idea. La herramienta introduce un bug artificial en tu código (cambia un >= por >, un + por -, un True por False), corre tu suite y observa. Si algún test falla, el mutante fue matado: tus tests detectan ese error. Si todos pasan, el mutante sobrevive: acabás de descubrir un cambio que podés hacer en producción sin que nadie se entere. 
uv add --dev mutmut
uv run mutmut run
uv run mutmut results          # lista de mutantes sobrevivientes
uv run mutmut show 7           # el diff exacto del mutante 7
--- tienda/precios.py
+++ tienda/precios.py
@@ -8,7 +8,7 @@
-    if monto >= 10_000:
+    if monto > 10_000:

Mutante 7: SOBREVIVIO
Ningun test cambia de resultado con este diff.

Ese diff es una acusación concreta: nadie probó el valor exacto 10.000. No es un consejo de estilo, es una línea de código que podés cambiar sin consecuencias.

Estado del mutanteSignificaQué hacer
🟢 MatadoUn test lo detectóNada. Así se ve un test que sirve
🔴 SobrevivióNingún test nota la diferenciaEscribir el test que falta, o borrar el código si nadie lo necesita
⏱ TimeoutEl mutante hizo un loop infinitoCuenta como matado
⚠️ EquivalenteEl mutante es funcionalmente idéntico al originalIgnorarlo. Es ruido inevitable, no un test faltante
Cuándo NO hacer mutation testing. Es carísimo: corre tu suite entera una vez por mutante, así que un proyecto mediano puede tardar horas. No va en el CI de cada PR. Corrélo (1) sobre los módulos críticos, no sobre todo el repo — mutmut run --paths-to-mutate tienda/precios.py; (2) en un job nocturno o semanal; (3) una vez, a mano, cuando querés saber si la suite que heredaste vale algo. Y no persigas el 100% de mutation score: los mutantes equivalentes hacen que sea inalcanzable.

DobleQué haceEjemploCuándo

# FAKE: una implementacion completa y honesta, en 8 lineas
class RepoEnMemoria:
    def __init__(self):
        self._datos: dict[int, Orden] = {}

    def guardar(self, orden):
        self._datos[orden.id] = orden

    def buscar(self, id_):
        return self._datos.get(id_)

def test_confirmar_orden():
    repo = RepoEnMemoria()                  # sin mocks, sin magia
    repo.guardar(Orden(id=1, estado="nueva"))
    confirmar(repo, 1)
    assert repo.buscar(1).estado == "confirmada"
# MOCK: correcto cuando el efecto ES el requisito
from unittest.mock import Mock

def test_se_notifica_al_confirmar():
    notificador = Mock()
    confirmar(RepoEnMemoria(), 1, notificador=notificador)
    notificador.enviar.assert_called_once_with(orden_id=1, plantilla="confirmada")

Cuándo mockear es el bug

⚠️ No mockees lo que no es tuyo. Si mockeás el SDK de Stripe, de boto3 o el driver de Postgres, tu test no verifica que tu código funcione contra esa librería: verifica que funcione contra tu idea de esa librería. El día que la API real devuelve un campo distinto, hace paginación, o lanza una excepción que no previste, tu suite sigue en verde y producción se cae. Es el modo de fallo más caro del testing: cobertura alta, confianza alta, protección cero. 
# ❌ Este test pasa para siempre, incluso si la API cambia por completo
def test_cobro(monkeypatch):
    fake = Mock()
    fake.Charge.create.return_value = {"status": "succeeded"}   # ¿seguro?
    monkeypatch.setattr("mi_app.pagos.stripe", fake)
    assert cobrar(1000) is True
En vez de mockear...Usá
Un SDK de nube (AWS)moto / localstack: el fake oficial que sigue la API real
Un cliente HTTP de tercerosrespx / vcrpy: respuestas HTTP grabadas de la API real
La base de datosTestcontainers (PS7.9): el motor de verdad
Redisfakeredis, o un contenedor
El reloj (datetime.now)time-machine / freezegun, o mejor: inyectar el reloj como dependencia
📌 La regla operativa: mockeá en tu frontera, no en la del otro. Envolvé el SDK en una clase tuya (PasarelaDePagos), testeá esa clase contra el servicio real o su fake oficial, y en el resto de la app mockeá tu interfaz. Ese wrapper es el único lugar del código que tiene que saber cómo se llaman los campos de Stripe.

PS7.9 Testcontainers: la base de datos de verdad

El mock de base de datos miente por construcción: no valida constraints, no tiene transacciones reales, no falla por deadlock, no aplica tus migraciones y no conoce el dialecto SQL de tu motor. Testcontainers levanta el Postgres real en Docker, y lo apaga solo.

# tests/integracion/conftest.py
import pytest
from testcontainers.postgres import PostgresContainer

@pytest.fixture(scope="session")
def pg_url():
    with PostgresContainer("postgres:17-alpine") as pg:
        url = pg.get_connection_url()
        aplicar_migraciones(url)        # tus migraciones REALES, sobre el motor REAL
        yield url

@pytest.fixture
def sesion(pg_url):
    conn = crear_engine(pg_url).connect()
    trx = conn.begin()
    yield Sesion(bind=conn)
    trx.rollback()                      # aislamiento por test, sin recrear la base

@pytest.mark.integracion
def test_no_permite_email_duplicado(sesion):
    sesion.add(Usuario(email="a@b.com")); sesion.commit()
    with pytest.raises(IntegrityError):          # el UNIQUE de verdad
        sesion.add(Usuario(email="a@b.com")); sesion.commit()
Ese test es imposible con SQLite en memoria y con cualquier mock: el constraint UNIQUE lo aplica el motor, no tu código. Los bugs que aparecen solo en producción viven casi todos en esta categoría — tipos, zonas horarias, ON DELETE CASCADE, colaciones, NULL en índices únicos.
El costo. Necesitás Docker disponible (en tu máquina y en el CI), el primer arranque tarda unos segundos y descarga imágenes. Por eso van marcados: pytest -m "not integracion" para el loop rápido de desarrollo, y la suite completa en CI. La imagen se pinea por versión (postgres:17-alpine, nunca latest) o tus tests se rompen solos un martes cualquiera.

PS7.10 Velocidad: la suite que nadie apaga

Antes de paralelizar, medí. Casi siempre el 80% del tiempo está en el 3% de los tests:

# xdist: un proceso por nucleo
uv run pytest -n auto

# reparte por archivo: los tests de un mismo modulo caen en el mismo worker
uv run pytest -n auto --dist loadfile
SituaciónQué hacer

Paralelizar destapa tests que dependían del orden. Si al poner -n auto aparecen fallos "raros", no es culpa de xdist: esos tests siempre estuvieron acoplados por estado global —un singleton, una variable de módulo, un archivo en disco, la misma fila en la base— y el orden secuencial los tapaba. Verificalo antes con pytest -p no:randomly --tb=short o instalando pytest-randomly, que ordena los tests al azar a propósito.

PS7.11 Testear código async

Lo que aprendiste en PS3 hay que poder probarlo. La configuración mínima con pytest-asyncio en modo automático:

[tool.pytest.ini_options]
asyncio_mode = "auto"           # no hace falta marcar cada test
async def test_trae_usuario(cliente_http):
    u = await cliente_http.get_usuario(1)
    assert u.nombre == "ana"

Pero el camino feliz es la parte fácil. Lo que rompe en producción es la cancelación y los timeouts: recursos que quedan abiertos cuando una tarea se corta a la mitad.

import anyio, pytest

@pytest.fixture
def anyio_backend():
    return "asyncio"

@pytest.mark.anyio
async def test_libera_el_recurso_aunque_lo_cancelen():
    liberado = False

    async def trabajo():
        nonlocal liberado
        try:
            await anyio.sleep(10)          # simula una operacion lenta
        finally:
            liberado = True                # el cleanup DEBE correr igual

    with anyio.move_on_after(0.05) as scope:
        await trabajo()

    assert scope.cancelled_caught          # efectivamente se canceló
    assert liberado                        # y el finally corrió

@pytest.mark.anyio
async def test_el_timeout_se_respeta():
    with pytest.raises(TimeoutError):
        with anyio.fail_after(0.1):
            await operacion_lenta()
⚠️ El bug clásico del testing async: el falso verde. Si te olvidás el await, muchas suites mal configuradas no fallan — el test termina, la corrutina nunca se ejecuta y solo queda un RuntimeWarning: coroutine was never awaited perdido en el output. Por eso filterwarnings = ["error"] en el pyproject.toml de PS7.3 no es paranoia: convierte ese warning en un fallo.

PS7.12 Qué NO testear

Cada test que escribís es código que hay que mantener. Los que no aportan información igual cuestan tiempo de CI y frenan refactors.

🧑‍🎓 Worked Example — 100% de cobertura y un bug vivo

Un e-commerce cobra de menos. Contabilidad reporta que en algunos casos aumentar el monto del carrito baja el total a pagar. El módulo de precios tiene 100% de cobertura, cinco tests y ningún fallo en seis meses.

El código bajo sospecha:

# tienda/precios.py
TOPE = 0.30
CUPONES = {"BIENVENIDA": 0.10, "AMIGO": 0.05}

def precio_final(monto: float, cupon: str | None = None, socio: bool = False) -> float:
    if monto < 0:
        raise ValueError("monto negativo")

    desc = 0.0
    if monto >= 10_000:          # escalon 2
        desc = 0.15
    elif monto >= 1_000:         # escalon 1
        desc = 0.05

    desc += CUPONES.get(cupon, 0.0)
    if socio:
        desc += 0.10
    if desc > TOPE:
        desc = TOPE

    return round(monto * (1 - desc), 2)

Los tests que "cubren" todo:

# tests/test_precios.py

Tres acusaciones concretas. El mutante 12 y el 19 son ruido menor (equivalente y de formato). El mutante 7 es la pista: nadie probó nunca el valor exacto 10.000, ni sus vecinos. Los tests saltan de 2.000 a 20.000 y el borde queda a oscuras.

💡 Precisión importante. El mutation testing no encontró el bug: no sabe qué debería hacer tu función. Encontró que tus tests no miran ese borde. Y como los bugs viven en los bordes, te llevó exactamente a la puerta correcta.

Paso 2 — Escribir la propiedad, no más ejemplos. La regla de negocio que contabilidad describió es una propiedad de monotonía: gastar más nunca puede salir más barato.

# tests/test_precios_props.py
from hypothesis import given, strategies as st
from tienda.precios import precio_final

montos = st.floats(min_value=0, max_value=1_000_000,
                   allow_nan=False, allow_infinity=False)

@given(a=montos, b=montos)
def test_gastar_mas_nunca_paga_menos(a, b):
    a, b = min(a, b), max(a, b)
    assert precio_final(a) <= precio_final(b) + 0.01   # tolerancia de redondeo
Falsifying example: test_gastar_mas_nunca_paga_menos(
    a=9999.0,
    b=10000.0,
)
assert 9499.05 <= 8500.0 + 0.01

El bug, en una línea: con 9.999 pesos el cliente paga 9.499,05; agregando un peso al carrito paga 8.500. Hay un acantilado de 999 pesos en el escalón. Cualquier cliente que lo descubra —o cualquier script que optimice el carrito— cobra de menos, y el sistema jamás se queja.

Fijate el shrinking en acción. El primer contraejemplo que encontró hypothesis fue probablemente algo como a=7431.88…, b=42918.03…. Reduciendo, descubrió que ni los decimales ni la distancia importaban: lo mínimo necesario es un peso a cada lado de 10.000. El contraejemplo mínimo es el diagnóstico.

Paso 3 — El fix. El descuento por escalón es discontinuo por diseño. La corrección es hacerlo marginal, como los tramos del impuesto a las ganancias: cada peso recibe la tasa de su tramo, y la función se vuelve continua y monótona.

TRAMOS = [(10_000, 0.15), (1_000, 0.05), (0, 0.0)]   # (piso, tasa), de mayor a menor

def _ahorro_por_tramos(monto: float) -> float:
    ahorro, restante = 0.0, monto
    for piso, tasa in TRAMOS:
        if restante > piso:
            ahorro += (restante - piso) * tasa       # solo el EXCEDENTE del tramo
            restante = piso
    return ahorro

def precio_final(monto: float, cupon: str | None = None, socio: bool = False) -> float:
    if monto < 0:
        raise ValueError("monto negativo")

    extra = min(CUPONES.get(cupon, 0.0) + (0.10 if socio else 0.0), TOPE)
    ahorro = _ahorro_por_tramos(monto) + monto * extra
    return round(monto - min(ahorro, monto * TOPE), 2)

Ahora la propiedad pasa con 100 ejemplos, con 1.000 y con los contraejemplos guardados en .hypothesis/. Y —esto es lo importante— los tests por ejemplo también hay que actualizarlos: precio_final(20_000) ya no da 17.000. Ese cambio en los números es la conversación con negocio que el bug estaba tapando.

📌 La lección no es "usá hypothesis". Es la secuencia: mutation testing te dice dónde tus tests no miran (una vez, en frío, sobre el módulo crítico), y una propiedad convierte esa zona ciega en un test permanente que cuesta menos de un segundo por corrida. La cobertura no participó de nada de esto — estuvo en 100% desde el principio y durante todo el bug.

Checkpoint — ¿lo tenés claro?

Tenés 100% de cobertura de ramas. ¿Qué garantiza y qué no?

Garantiza que cada línea se ejecutó y que cada if se tomó por los dos lados durante la corrida. No garantiza nada sobre los asserts: un test que solo llama funciones sin verificar resultados da 100%. Tampoco cubre las combinaciones de condiciones ni los valores de borde dentro de una rama —que es justo donde estaba el bug del worked example: la rama monto >= 10_000 se ejecutaba con 20.000, así que figuraba cubierta, mientras el valor 10.000 nunca se probó. Para responder "¿mis tests detectarían un error acá?" la métrica correcta es el mutation score, no la cobertura.

¿Por qué el contraejemplo de hypothesis es tan chico, y por qué eso importa?

Por el shrinking. Cuando encuentra un fallo, hypothesis no te lo reporta: primero busca versiones sistemáticamente más simples de esa entrada —listas más cortas, números más cerca de cero, strings más chicos— que sigan fallando, y te devuelve la mínima. Importa porque cambia el trabajo que te queda: con xs=[-914, 22, 0, 8871, -3] tenés que investigar cuál de los cinco números es el culpable; con xs=[0, 0] el diagnóstico ya está hecho —el problema es la suma cero—. El contraejemplo mínimo no es un fallo prolijo: es la explicación de la causa.

¿Cuándo mockear es directamente el bug?

Cuando mockeás algo que no controlás: el SDK de Stripe, boto3, el driver de la base. Tu test deja de verificar que el código funciona contra la librería real y pasa a verificar que funciona contra tu idea de la librería — una idea escrita el día que leíste la doc y que nadie actualiza. Cuando la API real cambia un campo, agrega paginación o lanza una excepción nueva, la suite sigue verde y producción se cae. La alternativa: envolver el servicio externo en una interfaz propia, testear esa capa contra el servicio real (testcontainers), su fake oficial (moto) o respuestas grabadas (vcrpy), y mockear solo tu propia interfaz en el resto de la app.

Resumen ejecutivo

  • El objetivo no es la cobertura: es confianza para cambiar código. Una suite lenta o frágil se termina desactivando, y entonces cuesta todo y no protege nada.
  • Fixtures = inyección de dependencias. Scope caro para recursos (session + contenedor), scope barato para datos (function + transacción que se revierte). Si necesitás varios objetos, la fixture devuelve una factory.
  • parametrize con ids=: el nombre del caso es lo único que vas a leer en el log de CI. Y --strict-markers siempre, o un typo silencia un test para siempre.
  • Hypothesis testea propiedades (round-trip, invariante, oráculo, monotonía, idempotencia) y el shrinking te devuelve el contraejemplo mínimo, que ya es el diagnóstico. Ejemplos y propiedades se combinan: cubren puntos ciegos opuestos.
  • La cobertura mide ejecución, no verificación. Se puede tener 100% con cero asserts. Ramas > líneas, y el mutation score > ambas: es la única métrica que responde "¿mis tests fallarían si el código estuviera mal?".
  • Mutation testing es caro: módulos críticos, job nocturno, nunca en cada PR — y el 100% es inalcanzable por los mutantes equivalentes.
  • De los cinco test doubles, el fake suele ser el mejor. Mockear lo que no es tuyo produce el peor de los mundos: cobertura alta y protección cero. Mockeá en tu frontera.
  • Testcontainers para integración: constraints, tipos y transacciones reales. Imagen pineada, marcada, fuera del loop rápido.
  • Velocidad: primero --durations, después -n auto. Si paralelizar rompe tests, esos tests ya estaban acoplados por estado global.
  • En async, probá cancelación y timeouts, no solo el camino feliz — y poné filterwarnings = ["error"] para que un await olvidado no pase como verde.

🧠 Autoevaluación

1. Tu módulo de facturación tiene 100% de cobertura de ramas y ningún test falló en seis meses, pero seguís teniendo bugs de cálculo en producción. ¿Qué medís para saber si los tests sirven?

La cobertura mide ejecución, no verificación: un test sin un solo assert da 100%. El mutation testing hace la pregunta correcta —"si rompo esta línea, ¿alguien se entera?"— y cada mutante sobreviviente es un cambio que podés hacer en producción sin que la suite reaccione. En el worked example, el mutante >= → > señaló exactamente el borde donde vivía el bug, con la cobertura en 100% todo el tiempo.

2. Tenés una fixture session que levanta Postgres con testcontainers. Corrés pytest -n auto en una máquina de 8 núcleos y el CI se queda sin memoria. ¿Qué pasó?

"Session" significa una vez por corrida de pytest, y con xdist cada worker es su propia corrida en su propio proceso: no hay memoria compartida entre ellos. Es la trampa más común al paralelizar. Las salidas son limitar los workers (-n 4), agrupar los tests de infra en un worker con --dist loadgroup + @pytest.mark.xdist_group, o levantar un solo contenedor afuera de pytest y pasarle la URL por variable de entorno.

3. Vas a testear el módulo que cobra con Stripe. ¿Cuál es la estrategia que da confianza real?

Mockear el SDK verifica tu código contra tu idea de la API de Stripe, congelada el día que leíste la doc. Cuando la API real agrega un campo, pagina o lanza una excepción nueva, la suite sigue verde y el cobro se rompe. El wrapper concentra en un solo lugar el conocimiento de la API externa: esa capa se testea contra algo real (vcrpy, el sandbox, un fake oficial) y el resto de la app mockea una interfaz que sí controlás. La tercera opción es la peor: no testear el módulo que toca plata.

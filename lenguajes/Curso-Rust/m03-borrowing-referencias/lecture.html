Módulo 03 — Borrowing & Referencias

En el M02 viste el lado duro del ownership: pasar un valor a una función lo mueve, y después ya no lo podés usar. Eso es seguro pero incómodo: ¿cada vez que quiero que una función lea mi dato tengo que regalárselo? No. La respuesta de Rust es borrowing (tomar prestado): pasás una referencia al dato en vez del dato mismo. El dueño sigue siendo el dueño.

Qué es una referencia

💡 Una referencia es un préstamo, no una mudanza. &x crea una referencia a x: un puntero que te deja usar el valor sin tomar posesión de él. Cuando el préstamo termina, el dueño original (x) sigue siendo válido y podés seguir usándolo. Nada se movió, nada se liberó.

Para acceder al valor detrás de una referencia se usa el operador de desreferencia * (deref). En muchos casos Rust lo hace automáticamente, pero conceptualmente: r es "la referencia" y *r es "el valor al que apunta".

fn main() {
    let x = 5;
    let r = &x;          // r toma prestado x (referencia inmutable)

    println!("{}", x);    // x sigue siendo válido: NO se movió
    println!("{}", *r);   // *r = deref: accede al valor (5)
    println!("{}", r);    // println! desreferencia solo: también imprime 5
}
Lectura de los símbolos: & en una expresión significa "tomá una referencia a esto" (crear préstamo). & en un tipo significa "esto es una referencia" (ej: &i32). Y * es la operación inversa: "seguí la referencia hasta el valor".

Borrowing: la solución natural al move

Recordá el problema del M02: pasar un String a una función lo movía. Con una referencia, en cambio, la función toma el dato prestado y al volver el dueño lo conserva.

fn longitud(s: &String) -> usize {  // toma prestado, no mueve
    s.len()
}

fn main() {
    let texto = String::from("hola mundo");
    let n = longitud(&texto);          // le prestamos texto

    // texto SIGUE siendo válido: solo lo prestamos, no lo movimos
    println!("'{}' mide {}", texto, n);
}
🔗 Analogía: mover es regalar tu libro — ya no lo tenés. Tomar prestado es prestarlo: tu amigo lo lee y te lo devuelve. Mientras lo tiene prestado, vos no podés rayarlo (referencia inmutable) salvo que se lo prestes en exclusiva para que lo edite (referencia mutable).

Dos sabores de referencia: &T y &mut T

ReferenciaSintaxis¿Cuántas a la vez?¿Puede modificar?
Inmutable&TMuchas simultáneasNo, solo lee
Mutable&mut TUna solaSí, lee y escribe

Una referencia inmutable (&T) es de solo lectura: podés tener tantas como quieras al mismo tiempo, porque nadie va a cambiar el dato. Una referencia mutable (&mut T) permite modificar el dato, pero a cambio Rust exige exclusividad: solo una a la vez, y ninguna inmutable activa en paralelo.

fn agregar_signo(s: &mut String) {  // referencia mutable: puede modificar
    s.push_str("!");
}

fn main() {
    let mut saludo = String::from("hola");  // el dato debe ser mut
    agregar_signo(&mut saludo);              // le prestamos en exclusiva

    println!("{}", saludo);  // "hola!" — la modificación persiste
}
📌 Para mutar a través de una referencia hacen falta DOS mut: la variable original debe declararse let mut (si no, no es modificable), y la referencia debe crearse como &mut (si no, es de solo lectura). Faltando cualquiera de los dos, no compila.

La regla del borrow checker

💡 La regla de oro del borrowing. En cualquier momento dado, para un mismo dato podés tener una de estas dos cosas, nunca ambas:
  1. Cualquier cantidad de referencias inmutables (&T), o bien
  2. Exactamente una referencia mutable (&mut T).
"Muchos lectores o un único escritor — nunca lectores y escritor al mismo tiempo."

¿Por qué tanta rigidez? Porque esa es exactamente la condición que produce un data race: dos accesos al mismo dato, al menos uno escribiendo, sin sincronización. Al prohibir esa combinación, Rust elimina los data races en tiempo de compilación, no en runtime. El bug ni siquiera llega a existir.

fn main() {
    let mut v = String::from("dato");

    // OK: varias referencias inmutables a la vez
    let r1 = &v;
    let r2 = &v;
    println!("{} y {}", r1, r2);   // se usan acá; el préstamo termina

    // OK: ahora una mutable (los préstamos inmutables ya terminaron)
    let m = &mut v;
    m.push_str("!");
    println!("{}", m);
}
NLL (Non-Lexical Lifetimes): un préstamo dura hasta su último uso, no hasta el final del bloque {}. Por eso el ejemplo de arriba compila: r1 y r2 dejaron de usarse antes de que apareciera m. El borrow checker es más inteligente de lo que parece.

Errores típicos del borrow checker

Mezclar mutable con otra referencia. Tener una &mut v y simultáneamente otra referencia (mutable o inmutable) al mismo dato no compila: "cannot borrow `v` as mutable because it is also borrowed as immutable". Solución: que el préstamo anterior termine antes de pedir el mutable.
Modificar a través de una referencia inmutable. Si recibís &T (no &mut T) e intentás escribir, el compilador lo rechaza: "cannot borrow `*s` as mutable". Una referencia inmutable es de solo lectura, punto.
Dos &mut al mismo dato. let a = &mut v; let b = &mut v; y usar ambas → error. Solo puede existir una referencia mutable activa. Esto es justo lo que previene escrituras pisándose entre sí.

No dangling: una referencia nunca sobrevive a su dato

En C/C++ podés devolver un puntero a una variable local que ya se destruyó — un dangling pointer que apunta a basura. En Rust eso no compila: el compilador verifica que ninguna referencia viva más que el dato al que apunta.

// ❌ NO COMPILA: dangling reference
fn colgada() -> &String {
    let s = String::from("hola");
    &s    // devolvemos una referencia a s...
}        // ...pero s se libera AQUÍ: la referencia quedaría colgada

// ✅ Solución: devolver el valor (mover el ownership al que llama)
fn correcta() -> String {
    let s = String::from("hola");
    s     // movemos s afuera; el dueño pasa a ser quien llama
}
Devolver una referencia a una variable local. El error es "missing lifetime specifier" / "returns a reference to data owned by the current function". La variable muere al terminar la función, así que su referencia apuntaría a memoria liberada. La solución suele ser devolver el valor (mover), no una referencia.
¿Cómo sabe Rust cuánto vive cada referencia? Con lifetimes (tiempos de vida). Casi siempre los infiere solo, pero a veces hay que anotarlos explícitamente. Eso lo desarrollamos en el M09 — Lifetimes; por ahora alcanza con la intuición: una referencia no puede durar más que su dato.

Slices: ver una porción sin copiar

Un slice es una referencia a una parte contigua de una colección, en vez de a toda. No copia datos: es una vista (puntero + longitud) hacia un trozo del original. Como es una referencia, también respeta el borrow checker.

SliceEs porción de…Ejemplo
&strun String&texto[0..4]
&[T]un Vec<T> o array&numeros[1..3]
 
fn main() {
    let frase = String::from("hola mundo");
    let hola: &str  = &frase[0..4];   // slice de String: "hola"
    let mundo: &str = &frase[5..10];  // "mundo"
    println!("{} / {}", hola, mundo);

    let numeros = vec![10, 20, 30, 40, 50];
    let medio: &[i32] = &numeros[1..4]; // slice de Vec: [20, 30, 40]
    println!("{:?}", medio);

    // El slice es solo una VISTA: no copió nada, apunta al original
}
✅ Idioma común: escribí tus funciones para recibir &str en vez de &String. Así sirven tanto para un String como para un literal de texto ("hola", que ya es &str) — más flexible y sin copiar nada.

Checkpoint — ¿lo tenés claro?

¿Qué le pasa al dueño de un valor después de que se lo prestamos con &?

Nada: sigue siendo el dueño y el valor sigue siendo válido. Una referencia toma prestado el valor sin mover el ownership. Cuando el préstamo termina (en su último uso), el dueño puede seguir usando el dato normalmente.

¿Cuántas referencias mutables y cuántas inmutables podés tener al mismo dato a la vez?

O bien muchas referencias inmutables (&T), o bien una sola referencia mutable (&mut T) — nunca las dos cosas a la vez. Esa regla es la que elimina los data races en tiempo de compilación.

¿Por qué no se puede devolver una referencia a una variable local de la función?

Porque la variable local se libera al terminar la función, así que la referencia quedaría colgada (dangling), apuntando a memoria ya liberada. Rust lo detecta en compilación y no lo permite. La solución habitual es devolver el valor (mover el ownership a quien llama).

Ejercicios

  1. Escribí una función fn primera_letra(s: &String) -> char que tome un String prestado y devuelva su primer carácter. Verificá en main que el String original sigue usable después de la llamada.
  2. Escribí una función fn duplicar(s: &mut String) que concatene el contenido del String consigo mismo. Acordate de declarar la variable como let mut y pasarla con &mut.
  3. Intentá a propósito crear let r = &v; y let m = &mut v; usándolas al mismo tiempo (por ej. un println! que use ambas después). Leé el error del borrow checker y explicá con tus palabras qué te está diciendo.
  4. Escribí (a propósito) una función que devuelva &String a una variable local y observá el error de dangling reference. Después arreglala devolviendo String en vez de &String.
  5. Dado let v = vec![1, 2, 3, 4, 5];, creá un slice &[i32] con los tres del medio y otro con los dos primeros, e imprimílos con {:?}.

🧠 Autoevaluación

1. Pasás &texto (una referencia) a una función. ¿Qué le pasa a texto después de la llamada?

Una referencia toma el valor prestado sin mover el ownership. El dueño (texto) sigue siendo válido después de la llamada.

2. ¿Cuál combinación de referencias al MISMO dato permite el borrow checker?

La regla: muchos lectores (&T) o un único escritor (&mut T), nunca ambos. Eso previene data races en compilación.

3. ¿Por qué este código no compila?
fn f() -> &String { let s = String::from("hi"); &s }

La variable local s se destruye al terminar la función, así que la referencia quedaría colgada. Rust lo detecta y no compila; la solución es devolver String (mover).

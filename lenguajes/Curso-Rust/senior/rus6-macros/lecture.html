RuS6 — Macros: declarativas, procedurales y su costo

RuS6.0 Por qué las macros de Rust no son las de C

Si venís de C, la palabra macro te trae malos recuerdos: sustitución de texto ciega, paréntesis defensivos por todos lados, variables que se pisan, y errores de compilación que hablan de código que vos nunca escribiste. Las macros de Rust arreglan casi todo eso, y lo hacen por una razón estructural: operan sobre árboles de tokens y fragmentos del AST, no sobre caracteres.

El ejemplo canónico. En C, el preprocesador reemplaza texto antes de que el compilador vea nada:

#define CUADRADO(x) x * x

int main(void) {
    int r = CUADRADO(1 + 2);   // se expande a:  1 + 2 * 1 + 2
    return r;                  // r == 5, no 9
}

La solución en C es escribir ((x) * (x)) y no olvidarse nunca. En Rust el problema no existe, porque $x:expr no captura texto: captura una expresión completa como un solo nodo. Cuando la macro la vuelve a emitir, sigue siendo esa expresión, indivisible.

macro_rules! cuadrado {
    ($x:expr) => { $x * $x };
}

fn main() {
    let r = cuadrado!(1 + 2);   // (1 + 2) * (1 + 2)
    assert_eq!(r, 9);           // ✅ sin paréntesis defensivos
}
💡 La tesis del módulo. Una macro de Rust es una función que corre en tiempo de compilación y cuya entrada y salida son tokens de Rust. De ahí se deducen sus dos superpoderes y su gran limitación. Superpoderes: puede generar código que vos no podrías escribir a mano sin repetirte, y puede validar cosas antes de que el programa exista. Limitación: corre antes de la resolución de tipos, así que no sabe qué tipo tiene nada. Todo lo que sigue en este módulo es una consecuencia de esas tres frases.

Esa limitación no es un detalle menor: es la restricción. Una macro ve el token Option y no sabe si es el Option de la biblioteca estándar, un alias tuyo, o un enum propio que se llama igual. Ve Vec<T> y no sabe si T implementa Clone. Volvemos a esto varias veces, porque es el origen del 80% de las macros mal diseñadas.

Rust tiene dos familias, y conviene tenerlas separadas desde el arranque:

FamiliaCómo se defineQué veDónde vive
Declarativas (macro_rules!)Patrones y sustituciones, dentro de tu propio crateÁrboles de tokens que matchean un patrónCualquier módulo
ProceduralesCódigo Rust arbitrario que transforma un TokenStreamTodos los tokens del ítem, sin restriccionesUn crate aparte, marcado proc-macro = true

La regla de oro del módulo, adelantada: empezá siempre por lo más simple que funcione, y en el orden función → trait → macro_rules! → proc-macro. Cada escalón te cuesta legibilidad, herramientas y tiempo de compilación.

RuS6.1 macro_rules!: patrones, repetición y fragment specifiers

Una macro declarativa es una lista de reglas (patrón) => { expansión } separadas por punto y coma. Se prueban en orden, de arriba hacia abajo, y gana la primera que matchea:

macro_rules! saludar {
    // regla 1: sin argumentos
    () => {
        println!("hola")
    };
    // regla 2: un identificador
    ($quien:ident) => {
        println!("hola, {}", stringify!($quien))
    };
    // regla 3: una expresión que produce algo Display
    ($quien:expr) => {
        println!("hola, {}", $quien)
    };
}

fn main() {
    saludar!();              // hola
    saludar!(mundo);         // hola, mundo     (regla 2: 'mundo' es un ident)
    saludar!("Ada".trim());  // hola, Ada       (regla 3)
}

Fijate que la regla 2 y la 3 se pisan parcialmente: mundo también sería una expresión válida. Como la 2 va primero, gana la 2. Si las intercambiaras, la regla del ident quedaría muerta para siempre — y no habría warning que te avise.

Los fragment specifiers

El :algo después de la metavariable le dice al compilador con qué parser leer ese fragmento. Elegir mal es la primera fuente de macros frustrantes.

📌 Por qué existe la columna "qué puede seguirlo". No es capricho. Después de $e:expr el compilador solo acepta =>, , o ; porque son los únicos tokens que hoy y siempre van a ser imposibles de confundir con la continuación de una expresión. Si mañana Rust agrega sintaxis nueva de expresiones, tu macro tiene que seguir compilando igual. Es una garantía de compatibilidad hacia adelante pagada con una restricción hoy.
El error que te va a costar una tarde. Una vez que capturaste algo como $e:expr, ese fragmento se vuelve opaco: internamente es un solo token con delimitadores invisibles. Si se lo pasás a otra macro que espera $($t:tt)*, no se va a re-descomponer. Por eso las macros que hacen recursión sobre su entrada capturan tt y no expr: el tt es el único que conserva la estructura para el siguiente paso.

Repetición: $()*, $()+ y $()?

La sintaxis es $( ... ) sep rep, donde sep es un separador opcional y rep es * (cero o más), + (uno o más) o ? (cero o uno, sin separador). El mismo grupo se usa en el patrón para capturar y en la expansión para emitir:

macro_rules! mapa {
    // caso vacío: mapa!()
    () => {
        ::std::collections::HashMap::new()
    };
    // caso general: mapa!{ "a" => 1, "b" => 2, }   ← coma final opcional
    ($($clave:expr => $valor:expr),+ $(,)?) => {{
        let mut m = ::std::collections::HashMap::new();
        $( m.insert($clave, $valor); )+
        m
    }};
}

fn main() {
    let edades = mapa! {
        "ada"   => 36,
        "grace" => 45,     // la coma final compila gracias a $(,)?
    };
    assert_eq!(edades["ada"], 36);
}

Tres detalles de artesanía en esas ocho líneas:

1. Las llaves dobles {{ }}. Las externas delimitan la expansión; las internas crean un bloque, que es una expresión. Sin ellas, la macro emitiría tres sentencias sueltas y no podrías escribir let m = mapa!{...};.
2. $(,)? al final del patrón. Acepta la coma final que todo el mundo escribe. Omitirlo es la queja número uno de los usuarios de tu macro.
3. La ruta absoluta ::std::collections::HashMap. Los caminos no son higiénicos: se resuelven en el ámbito de quien llama. Si el usuario tiene un struct HashMap propio, tu macro se rompe. Con :: adelante, apuntás a la raíz y no hay ambigüedad posible.

Las repeticiones anidan. El patrón clásico de una matriz literal, donde el nivel externo son filas y el interno columnas:

macro_rules! matriz {
    ( $( [ $($celda:expr),* $(,)? ] ),* $(,)? ) => {
        vec![ $( vec![ $($celda),* ] ),* ]
    };
}

fn main() {
    let m: Vec<Vec<i32>> = matriz![
        [1, 2, 3],
        [4, 5, 6],
    ];
    assert_eq!(m[1][2], 6);
}
Regla de oro de las repeticiones anidadas: la estructura de $() en la expansión tiene que reflejar la del patrón. Si capturaste dos niveles, emitís dos niveles. Si intentás emitir $celda con un solo $()*, el compilador te dice "variable 'celda' is still repeating at this depth", que es raro la primera vez pero literal: te quedó un nivel sin desplegar.

Munching de tt y reglas internas

Para procesar entradas arbitrarias existe el patrón tt munching: consumir un token tree por vez y recurrir. También la convención de reglas internas marcadas con @, que no son parte de la API pública de la macro:

macro_rules! contar {
    // regla interna: cada tt vale 1
    (@uno $_x:tt) => { 1usize };
    // regla pública: suma un 1 por cada token tree
    ($($x:tt)*) => { 0usize $( + contar!(@uno $x) )* };
}

const N: usize = contar!(a b "c" 4 (5 + 6));
// N == 5, y se evalúa en tiempo de compilación
La recursión de macros tiene límite: 128 niveles por defecto. Se sube con #![recursion_limit = "256"] en la raíz del crate, pero si necesitás subirlo mucho es señal de que tu macro es cuadrática en tiempo de compilación y hay que rediseñarla. La versión de arriba es lineal justamente porque expande un + 1 por token en vez de re-invocarse sobre la cola.

Exportar la macro: #[macro_export] y $crate

Una macro declarativa solo es visible después de su definición en el orden textual del archivo, salvo que la exportes. #[macro_export] la publica en la raíz del crate. Y ahí aparece el problema de las rutas: dentro de tu macro no sabés cómo se llama tu crate en el proyecto del usuario.

// en tu crate `bitacora`
pub fn escribir(nivel: u8, msg: &str) { /* ... */ }

#[macro_export]
macro_rules! aviso {
    ($($arg:tt)*) => {
        // $crate se expande a ::bitacora — o al nombre real, si el usuario
        // hizo  bitacora = { package = "bitacora", version = "1" }  con alias
        $crate::escribir(2, &::std::format!($($arg)*))
    };
}
📌 $crate es obligatorio en toda macro exportada. Sin él, tu macro compila en tu crate y falla en el de tu usuario con "cannot find function escribir". Es el bug más frecuente de las macros publicadas en crates.io, y solo aparece cuando alguien más la usa — nunca en tus propios tests.

RuS6.2 Higiene: por qué tu variable no pisa la del llamador

Este es el punto donde Rust se separa de C de manera más visible. Mirá el clásico SWAP:

#define SWAP(a, b) { int tmp = (a); (a) = (b); (b) = tmp; }

int main(void) {
    int tmp = 1, x = 2;
    SWAP(tmp, x);      // se expande a: { int tmp = tmp; tmp = x; x = tmp; }
    // tmp y x quedan ambos en basura: la variable de la macro pisó la del llamador
}

La macro no tiene forma de saber que el usuario ya tenía un tmp. La convención histórica en C es llamar a las variables internas __tmp_swap_line_37 y rezar. En Rust el problema simplemente no ocurre:

macro_rules! con_temporal {
    ($e:expr) => {{
        let tmp = 40;
        $e + tmp
    }};
}

fn main() {
    let tmp = 2;
    // El `tmp` de adentro y el `tmp` de afuera son DOS bindings distintos.
    assert_eq!(con_temporal!(tmp), 42);   // 2 + 40, no 40 + 40
}
💡 Cómo funciona la higiene. Cada identificador que Rust ve lleva pegado un SyntaxContext: una marca invisible que dice "este nombre nació acá". El tmp escrito en el cuerpo de la macro y el tmp escrito en main son textualmente iguales pero tienen contextos distintos, así que la resolución de nombres los trata como variables diferentes. No hay renombre mágico ni prefijos: hay un sistema de identidad de identificadores.

Qué es higiénico y qué no

Acá está el matiz que separa a quien leyó el libro de quien escribió macros de verdad. La higiene de macro_rules! es parcial: cubre variables locales, labels y lifetimes. No cubre nada más.

Elemento¿Higiénico?Consecuencia práctica
Variables locales (let)✅ SíPodés usar cualquier nombre sin miedo.
Labels de loop ('salir:)✅ SíÍdem.
Lifetimes✅ SíÍdem.
Rutas y tipos (HashMap, Result)❌ NoSe resuelven en el sitio de llamada. Usá ::std::… y $crate::….
Nombres de ítems generados (fn, struct)❌ NoVan al ámbito del llamador y pueden colisionar.
Campos y métodos❌ NoSe resuelven por tipo, después de la expansión.
 
macro_rules! frágil {
    () => {{
        // ❌ 'Result' NO es higiénico: si el usuario tiene su propio Result
        //    (¡y muchos crates lo definen!), esto compila distinto o no compila.
        let r: Result<u8, ()> = Ok(1);
        r
    }};
}

macro_rules! robusta {
    () => {{
        // ✅ Ruta absoluta: no hay ambigüedad posible
        let r: ::core::result::Result<u8, ()> = ::core::result::Result::Ok(1);
        r
    }};
}
⚠️ En macros procedurales la higiene es una decisión tuya. quote! genera tokens con Span::call_site(), que es no higiénico: todo se resuelve como si lo hubiera escrito el usuario. Si tu proc-macro emite let tmp = ..., ese tmp sí puede colisionar. Para el comportamiento tipo macro_rules! existe Span::mixed_site(), disponible en quote::quote_spanned!. Es un tema del que casi nadie habla y que produce bugs muy difíciles de reproducir.

RuS6.3 Los límites de macro_rules!

Las macros declarativas cubren muchísimo terreno con muy poco costo. Pero se chocan contra cuatro paredes duras, y reconocerlas rápido te ahorra días.

Pared 1 — No puede fabricar identificadores nuevos. Dado Usuario, no hay forma en macro_rules! de producir UsuarioBuilder, USUARIO_ID o fn crear_usuario. concat_idents! existe pero es inestable y ni siquiera sirve para declarar cosas. La única salida en estable es el crate paste… que es una proc-macro. O sea: la pared ya te empujó al otro lado.
Pared 2 — No inspecciona tipos ni semántica. $t:ty te da tokens que parsean como un tipo. No sabés si es Copy, si es un enum, cuántas variantes tiene, ni si Option es el de std. Cualquier decisión que dependa de eso es imposible.
Pared 3 — No se puede enganchar a una definición real. Podés escribir mi_struct!{ Usuario { nombre: String } } con tu propia sintaxis, pero no podés poner #[derive(MiCosa)] arriba de un struct normal. Los derive son territorio exclusivo de las procedurales.
Pared 4 — Los errores son crípticos. Cuando ninguna regla matchea, el compilador dice "no rules expected this token in macro invocation" y señala un token cualquiera. No hay forma de explicar qué esperabas… salvo un truco.

Ese truco es una regla catch-all con compile_error!, y es lo mínimo que le debés a quien use tu macro:

macro_rules! configurar {
    (modo = debug)   => { Config::debug() };
    (modo = release) => { Config::release() };
    // 👇 catch-all: convierte un error incomprensible en una instrucción
    ($($otro:tt)*) => {
        ::core::compile_error!(
            "uso: configurar!(modo = debug) o configurar!(modo = release)"
        )
    };
}

// configurar!(modo = prod);
// error: uso: configurar!(modo = debug) o configurar!(modo = release)
📌 El test de "¿me tengo que ir a procedural?" Respondé estas cuatro: ¿necesito fabricar nombres? ¿necesito leer una definición existente (struct/enum/fn) sin cambiar cómo se escribe? ¿necesito leer atributos tipo #[builder(each = "arg")]? ¿necesito errores con span propio apuntando al campo culpable? Un solo "sí" y macro_rules! no alcanza. Cuatro "no" y una proc-macro es sobreingeniería.

RuS6.4 Macros procedurales: los tres tipos

Una macro procedural es una función Rust normal que corre dentro del compilador. Recibe tokens, hace lo que se le antoja —parsear, consultar una base de datos, leer un archivo— y devuelve tokens. Hay exactamente tres formas, distinguidas por dónde se invocan y qué reemplazan:

TipoFirmaSe invocaQué hace con el ítem original
derivefn(TokenStream) -> TokenStream#[derive(Builder)] sobre struct/enum/unionLo deja intacto y agrega ítems nuevos
atributofn(TokenStream, TokenStream) -> TokenStream#[medir(nivel = "info")] sobre casi cualquier ítemLo reemplaza por completo
function-likefn(TokenStream) -> TokenStreamsql!( SELECT … )Reemplaza la invocación
 
use proc_macro::TokenStream;

// 1. derive — solo agrega. El primer TokenStream es el struct completo.
#[proc_macro_derive(Builder, attributes(builder))]
pub fn derive_builder(entrada: TokenStream) -> TokenStream { /* … */ }

// 2. atributo — reemplaza. args = lo de adentro de los paréntesis del atributo,
//    item = el ítem entero al que está pegado.
#[proc_macro_attribute]
pub fn medir(args: TokenStream, item: TokenStream) -> TokenStream { /* … */ }

// 3. function-like — reemplaza la llamada.
#[proc_macro]
pub fn sql(entrada: TokenStream) -> TokenStream { /* … */ }
El attributes(builder) del derive declara helper attributes: le avisa al compilador que #[builder(...)] sobre los campos es legal y que se lo tiene que pasar a tu macro en vez de rechazarlo. Sin esa declaración, cualquier atributo desconocido es un error de compilación. Es exactamente el mecanismo por el que funciona #[serde(rename = "…")].

Por qué van en su propio crate

Un crate de proc-macros se declara así, y esa marca cambia todo:

# mi-crate-macros/Cargo.toml
[package]
name = "mi-crate-macros"
version = "0.1.0"
edition = "2024"

[lib]
proc-macro = true          # 👈 la línea que lo cambia todo

[dependencies]
syn = { version = "2", features = ["full"] }
quote = "1"
proc-macro2 = "1"

Con proc-macro = true, Cargo compila ese crate como una biblioteca dinámica para la máquina que compila, no para la máquina destino, y rustc la carga como un plugin mientras compila tu código. De ahí salen tres consecuencias que hay que tener presentes:

  • No podés mezclar. Un crate proc-macro solo puede exportar macros procedurales. Nada de structs, funciones o traits públicos.
  • Compila para el host. Si hacés cross-compilation a ARM, el crate de macros igual se compila para tu x86. Es correcto, pero explica por qué a veces aparece dos veces en el árbol de dependencias.
  • Necesita una fachada. Nadie quiere depender de dos crates. La convención es mi-crate (con los traits y tipos) que re-exporta la macro:
// mi-crate/src/lib.rs
pub use mi_crate_macros::Builder;   // el usuario solo escribe: mi-crate = "1"

pub trait Construible { /* … */ }
Dentro de una proc-macro no existe $crate. Es la trampa gemela de la de macro_rules!. Si tu derive genera ::mi_crate::Construible y el usuario renombró la dependencia en su Cargo.toml, no compila. Las dos salidas reales: el crate proc-macro-crate, que lee el Cargo.toml del consumidor y te dice el nombre efectivo; o la técnica de serde, que envuelve todo en un const _: () = { extern crate serde as _serde; … }; para tener un alias garantizado.

RuS6.5 El trío estándar: syn + quote + proc-macro2

El TokenStream que te da el compilador es una lista plana e incómoda. Nadie escribe proc-macros a mano sobre eso. El ecosistema convergió hace años en tres crates que hacen falta juntos:

CrateRolPor qué no se puede evitar
proc-macro2Un TokenStream que funciona fuera del compiladorLos tipos de proc_macro solo existen durante una expansión: sin esto no podés escribir un solo #[test] unitario de tu lógica.
synParsea tokens a un AST tipado (DeriveInput, ItemFn, Type, Expr…)Reimplementar el parser de Rust no es una opción razonable.
quoteGenera tokens con plantillas (quasi-quoting)Construir tokens a mano es ilegible y propenso a errores de span.

El flujo siempre es el mismo: parsear con syn → decidir en Rust normal → emitir con quote.

use proc_macro2::TokenStream as TokenStream2;
use quote::quote;
use syn::Ident;

fn ejemplo(nombre: &Ident, campos: &[Ident]) -> TokenStream2 {
    // #var  interpola cualquier cosa que implemente ToTokens
    // #(#xs),*  repite sobre un iterador, con separador
    quote! {
        impl #nombre {
            pub fn campos() -> &'static [&'static str] {
                &[ #( ::core::stringify!(#campos) ),* ]
            }
        }
    }
}
Las features de syn importan para tu tiempo de compilación. Por defecto trae derive (suficiente para parsear un struct). full agrega el parser de expresiones, sentencias y cuerpos de función — es lo que necesitás para macros de atributo tipo #[tokio::main], y es la parte cara. extra-traits agrega Debug a todo el AST: ponela solo mientras depurás y sacala antes de publicar.

Lo que separa una macro usable de una odiada: los errores

Acá está el 90% de la diferencia de calidad. Una proc-macro que hace unwrap() produce esto:

error: proc-macro derive panicked
 --> src/modelo.rs:8:10
  |
8 | #[derive(Builder)]
  |          ^^^^^^^
  |
  = help: message: called `Option::unwrap()` on a `None` value

El usuario no tiene la menor idea de qué hizo mal. La alternativa cuesta cinco líneas y cambia la experiencia por completo:

use syn::spanned::Spanned;

// ❌ mal: revienta el compilador, span inútil
let campos = match datos { Data::Struct(s) => s.fields, _ => panic!("solo structs") };

// ✅ bien: error de compilación normal, apuntando al token exacto
fn revisar(campo: &syn::Field) -> syn::Result<()> {
    if campo.ident.is_none() {
        return Err(syn::Error::new(
            campo.span(),                       // 👈 el span del CAMPO culpable
            "Builder no soporta structs de tupla; usá campos nombrados",
        ));
    }
    Ok(())
}

// Acumular todos los errores en vez de mostrar uno por build:
fn revisar_todos(campos: &[syn::Field]) -> syn::Result<()> {
    let mut acumulado: Option<syn::Error> = None;
    for c in campos {
        if let Err(e) = revisar(c) {
            match &mut acumulado {
                Some(previo) => previo.combine(e),   // 👈 combine, no return
                None => acumulado = Some(e),
            }
        }
    }
    match acumulado { Some(e) => Err(e), None => Ok(()) }
}
📌 El patrón de entrada canónico de todo derive. La función pública nunca hace trabajo: parsea, delega a una función que devuelve syn::Result, y convierte el error en compile_error!. Así nunca hay un panic y siempre hay un span. 
#[proc_macro_derive(Builder, attributes(builder))]
pub fn derive_builder(entrada: TokenStream) -> TokenStream {
    let ast = syn::parse_macro_input!(entrada as syn::DeriveInput);
    expandir(ast)
        .unwrap_or_else(syn::Error::into_compile_error)   // 👈 la línea clave
        .into()
}

Y el segundo truco de spans, el que casi nadie aplica: quote_spanned!. Cuando generás código que le pone un bound a un tipo del usuario, ese código debe llevar el span del tipo, no el de tu macro. Así, cuando falta el Clone, el error subraya el campo:

use quote::quote_spanned;
use syn::spanned::Spanned;

// El error "the trait `Clone` is not implemented" va a apuntar
// a la línea del CAMPO en el struct del usuario, no al #[derive(Builder)].
let asercion = quote_spanned! { campo.ty.span() =>
    const _: fn() = || {
        fn exige_clone<T: ::core::clone::Clone>() {}
        exige_clone::<#tipo>();
    };
};

RuS6.6 Un #[derive(Builder)] completo, de punta a punta

Vamos a escribir el derive entero. El objetivo: dado un struct del usuario, generar un builder que exija los campos obligatorios y deje opcionales los Option<T>.

// Lo que el usuario escribe:
use mi_crate::Builder;

#[derive(Builder)]
pub struct Conexion {
    host: String,
    puerto: u16,
    usuario: Option<String>,     // opcional: no hace falta setearlo
}

fn main() -> Result<(), String> {
    let c = Conexion::builder()
        .host("db.interno".into())
        .puerto(5432)
        .build()?;               // ← Err("falta el campo `host`") si te olvidás
    Ok(())
}

Paso 1 — El esqueleto y la validación de entrada

use proc_macro::TokenStream;
use proc_macro2::TokenStream as TokenStream2;
use quote::{format_ident, quote, quote_spanned};
use syn::{
    parse_macro_input, punctuated::Punctuated, spanned::Spanned, token::Comma,
    Data, DeriveInput, Field, Fields, GenericArgument, PathArguments, Type,
};

#[proc_macro_derive(Builder)]
pub fn derive_builder(entrada: TokenStream) -> TokenStream {
    let ast = parse_macro_input!(entrada as DeriveInput);
    expandir(&ast)
        .unwrap_or_else(syn::Error::into_compile_error)
        .into()
}

fn campos_nombrados(ast: &DeriveInput) -> syn::Result<&Punctuated<Field, Comma>> {
    match &ast.data {
        Data::Struct(s) => match &s.fields {
            Fields::Named(f) => Ok(&f.named),
            otros => Err(syn::Error::new(
                otros.span(),
                "Builder necesita campos nombrados: `struct X { a: T }`",
            )),
        },
        Data::Enum(e) => Err(syn::Error::new(
            e.enum_token.span(),
            "Builder no se puede derivar en enums",
        )),
        Data::Union(u) => Err(syn::Error::new(
            u.union_token.span(),
            "Builder no se puede derivar en unions",
        )),
    }
}

Paso 2 — Detectar Option<T> (y ver la limitación en vivo)

/// Si `ty` es `Option<T>`, devuelve `T`.
fn tipo_interno_de_option(ty: &Type) -> Option<&Type> {
    let Type::Path(tp) = ty else { return None };
    let seg = tp.path.segments.last()?;
    if seg.ident != "Option" {
        return None;
    }
    let PathArguments::AngleBracketed(args) = &seg.arguments else { return None };
    match args.args.first()? {
        GenericArgument::Type(t) => Some(t),
        _ => None,
    }
}
⚠️ Leé esa función otra vez: es puramente sintáctica. Acepta Option<T>, std::option::Option<T> y también el enum Option que definió el usuario en su propio módulo. Y rechaza un type Quizas = Option<String>;, porque ve el token Quizas y no sabe que es un alias. No hay forma de arreglarlo: la macro corre antes de que exista información de tipos. Todas las macros del ecosistema —serde incluido— tienen exactamente esta limitación. Documentala en tu README en vez de fingir que no existe.

Paso 3 — Generar las tres piezas

fn expandir(ast: &DeriveInput) -> syn::Result<TokenStream2> {
    let nombre = &ast.ident;
    let nombre_builder = format_ident!("{}Builder", nombre);   // 👈 fabricar un ident
    let campos = campos_nombrados(ast)?;

    // (a) los campos del builder: todo envuelto en Option
    let declaraciones = campos.iter().map(|c| {
        let id = &c.ident;
        let ty = &c.ty;
        if tipo_interno_de_option(ty).is_some() {
            quote! { #id: #ty }                                  // ya era Option
        } else {
            quote! { #id: ::core::option::Option<#ty> }
        }
    });

    // (b) un setter por campo, con el span del tipo original
    let setters = campos.iter().map(|c| {
        let id = &c.ident;
        let ty = tipo_interno_de_option(&c.ty).unwrap_or(&c.ty);
        quote_spanned! { c.ty.span() =>
            pub fn #id(&mut self, valor: #ty) -> &mut Self {
                self.#id = ::core::option::Option::Some(valor);
                self
            }
        }
    });

    // (c) el build(): los obligatorios fallan con un mensaje que nombra el campo
    let construccion = campos.iter().map(|c| {
        let id = &c.ident;
        if tipo_interno_de_option(&c.ty).is_some() {
            quote! { #id: self.#id.take() }
        } else {
            let msg = format!("falta el campo `{}`", id.as_ref().unwrap());
            quote_spanned! { c.span() =>
                #id: self.#id.take().ok_or_else(
                    || ::std::string::String::from(#msg)
                )?
            }
        }
    });

    let inicial = campos.iter().map(|c| {
        let id = &c.ident;
        quote! { #id: ::core::option::Option::None }
    });

    Ok(quote! {
        impl #nombre {
            pub fn builder() -> #nombre_builder {
                #nombre_builder { #(#inicial),* }
            }
        }

        pub struct #nombre_builder {
            #(#declaraciones),*
        }

        impl #nombre_builder {
            #(#setters)*

            pub fn build(&mut self)
                -> ::core::result::Result<#nombre, ::std::string::String>
            {
                ::core::result::Result::Ok(#nombre {
                    #(#construccion),*
                })
            }
        }
    })
}
Tres decisiones de diseño escondidas ahí. (1) format_ident! es lo que macro_rules! no puede hacer — fabricar ConexionBuilder a partir de Conexion; es la razón por la que este derive tiene que ser procedural. (2) Uso take() y no clone(): no le impongo Clone al usuario, a costa de que build() consuma los valores. (3) Todas las rutas son absolutas y con ::core:: cuando se puede, para que el derive funcione también en crates #![no_std].

RuS6.8 El costo, con datos

Las macros no son gratis, y el precio no se paga donde uno cree. Vamos por partes.

1. Las proc-macros se ejecutan en cada compilación

El crate de macros se compila una vez y queda cacheado. Pero la expansión corre cada vez que se compila el crate que la usa, incluso en cargo check. Con compilación incremental el resultado se cachea por ítem, pero cualquier cambio en el crate de macros invalida todo lo que está río abajo. Y hay un detalle de arquitectura que duele: rustc habla con la proc-macro por un canal serializado, de a un crate por vez, así que esa parte no se paraleliza como el resto de la compilación.

2. syn pesa, y está en el camino crítico

# ¿Quién me está trayendo syn, y con qué features?
cargo tree -e normal -i syn
cargo tree --duplicates              # ¿tengo syn 1 y syn 2 conviviendo?

# ¿Dónde se va el tiempo del build limpio?
cargo clean && cargo build --timings
# genera target/cargo-timings/cargo-timing.html — ordenalo por duración

# Medición honesta, con varias corridas
cargo install hyperfine
hyperfine --warmup 1 --prepare 'cargo clean' 'cargo build'
Órdenes de magnitud típicos en una máquina de escritorio de 2026, que tenés que reproducir en la tuya antes de citarlos: proc-macro2 + quote ≈ 1–2 s; syn con features por defecto ≈ 3–5 s; syn con full ≈ 8–15 s. Se paga una sola vez por build limpio, pero bloquea: nada que dependa de tu derive puede empezar hasta que el dylib de la macro esté linkeado. Por eso una macro chiquita puede empeorar el wall clock mucho más de lo que sugiere su tamaño.

Hay una optimización poco conocida y muy efectiva. Por defecto Cargo compila los build scripts y las proc-macros con el perfil de desarrollo, o sea sin optimizar — y después las ejecuta miles de veces:

# Cargo.toml — compila las proc-macros optimizadas aunque el resto sea debug
[profile.dev.build-override]
opt-level = 3

[profile.release.build-override]
opt-level = 3

Se paga un poco más al compilar syn una sola vez y se gana en cada expansión. En proyectos con muchos derives la diferencia es medible; en proyectos chicos es ruido. Es exactamente el tipo de cambio que hay que medir con hyperfine antes y después, no adoptar por fe.

3. Qué hace por dentro un #[derive(Serialize)]

La fama de serde como "el que hace lento el build" es merecida, pero la causa no es la que se dice. El Serialize de un struct de 20 campos genera algo así:

// cargo expand, muy recortado
const _: () = {
    extern crate serde as _serde;              // 👈 alias, por si renombraste el crate
    impl _serde::Serialize for Conexion {
        fn serialize<S>(&self, ser: S) -> _serde::__private::Result<S::Ok, S::Error>
        where S: _serde::Serializer {
            let mut st = _serde::Serializer::serialize_struct(ser, "Conexion", 3)?;
            _serde::ser::SerializeStruct::serialize_field(&mut st, "host", &self.host)?;
            _serde::ser::SerializeStruct::serialize_field(&mut st, "puerto", &self.puerto)?;
            _serde::ser::SerializeStruct::serialize_field(&mut st, "usuario", &self.usuario)?;
            _serde::ser::SerializeStruct::end(st)
        }
    }
};

Eso es barato. El caro es Deserialize: genera un enum __Field con una variante por campo, un __FieldVisitor con visit_str, visit_bytes y visit_u64, un __Visitor con visit_seq y visit_map, arrays de nombres constantes y el manejo de duplicados. Fácilmente 200–400 líneas por struct. Y todo eso es genérico sobre D: Deserializer, así que se monomorfiza por cada formato que uses.

💡 El costo real de los derives no está en expandir: está en lo que le dan de comer a LLVM. Generar 300 líneas de Rust tarda milisegundos. Monomorfizar y optimizar esas 300 líneas por cada uno de tus 80 structs y por cada formato es lo que hace que el build tarde minutos. La herramienta para verlo es cargo llvm-lines, no --timings. 
cargo install cargo-llvm-lines
cargo llvm-lines -p mi-crate | head -25
# Ordena las funciones por líneas de IR generadas. Si arriba de todo hay
# 'serde::de::…' o tu propio derive, ahí está tu tiempo de compilación.

# Nightly: cuánto expandió cada macro, en tokens y bytes
cargo +nightly rustc -- -Zmacro-stats

Mitigaciones reales, en orden de esfuerzo: apagar features que no usás (serde sin derive donde escribís el impl a mano), aplicar el derive solo a los tipos que cruzan un límite de serialización en vez de a todo el modelo de dominio, partir el crate para que un cambio no recompile todo, y —en el extremo— escribir el impl a mano para los cinco tipos más grandes. No hay bala de plata; hay medición.

RuS6.9 Cuándo NO escribir una macro

⚠️ Esta es la sección más importante del módulo. Todo lo anterior te enseñó a construir el martillo. Esto te enseña a no ver clavos por todos lados. La mayoría de las macros que se escriben en la industria no deberían existir: resuelven con metaprogramación algo que el sistema de tipos ya resolvía.

Lo que te cuesta una macro, en concreto

  • Tu IDE la entiende peor. rust-analyzer expande proc-macros, pero es más lento, a veces falla, y una macro que lee archivos o variables de entorno puede no funcionar dentro del editor. goto-definition sobre un método generado te lleva al cuerpo de la macro, no al método.
  • Tu equipo la debuggea peor. Un breakpoint en código generado es un ejercicio de paciencia. Los stack traces mencionan funciones que nadie escribió.
  • El code review pierde. El git diff muestra la macro, no lo que hace. Nadie revisa 300 líneas invisibles.
  • Los errores empeoran. Cualquier error de tipos dentro de la expansión sale en el sitio de llamada, con un mensaje sobre código que el usuario no ve — salvo que hayas hecho el trabajo de spans de RuS6.5.
  • El build tarda más. RuS6.8 completo.
  • El aparato de tests crece. trybuild, cargo expand, casos .stderr versionados.
📌 Cuándo sí, sin duda. Una macro es la respuesta correcta cuando el problema es genuinamente sintáctico y el sistema de tipos no puede expresarlo: enumerar los campos de un struct (serde), validar SQL contra una base real en tiempo de compilación (sqlx::query!), chequear un string de formato (format!), reescribir una async fn main (#[tokio::main]). Todas comparten una firma: hacen algo que ninguna feature del lenguaje puede hacer, no algo que da un poco de fiaca escribir.
El corolario incómodo: las macros deberían morirse. Una macro suele existir para tapar un agujero del lenguaje. Cuando el agujero se cierra, la macro sobra. lazy_static! fue reemplazado por OnceLock y LazyLock; #[async_trait] dejó de ser necesario en la mayoría de los casos cuando llegaron las async fn en traits; maplit sigue vivo porque el agujero sigue abierto. Si escribís una macro, dejá anotado en el README qué feature del lenguaje la volvería innecesaria. Es la mejor forma de que alguien la borre a tiempo.

RuS6.10 build.rs: generar código sin macros

Hay una tercera vía que se olvida seguido. Si tu entrada es un archivo —un .proto, un schema SQL, un CSV de códigos de país, una gramática— la herramienta no es una macro: es un build script que escribe Rust en OUT_DIR y después se incluye.

// build.rs — corre antes de compilar el crate
use std::{env, fmt::Write as _, fs, path::PathBuf};

fn main() {
    // Sintaxis moderna con `::` (Cargo 1.77+); la vieja `cargo:` sigue andando
    println!("cargo::rerun-if-changed=datos/paises.csv");

    let salida = PathBuf::from(env::var("OUT_DIR").unwrap());
    let csv = fs::read_to_string("datos/paises.csv").expect("falta datos/paises.csv");

    let mut codigo = String::from("pub static PAISES: &[(&str, &str)] = &[\n");
    for (n, linea) in csv.lines().skip(1).enumerate() {
        let (iso, nombre) = linea
            .split_once(',')
            .unwrap_or_else(|| panic!("linea {} mal formada: {linea:?}", n + 2));
        // {:?} escapa el string por nosotros — nada de concatenar comillas a mano
        writeln!(codigo, "    ({iso:?}, {nombre:?}),").unwrap();
    }
    codigo.push_str("];\n");

    fs::write(salida.join("paises.rs"), codigo).unwrap();
}
// src/paises.rs — el consumo
include!(concat!(env!("OUT_DIR"), "/paises.rs"));

pub fn nombre(iso: &str) -> Option<&'static str> {
    PAISES.iter().find(|(c, _)| *c == iso).map(|(_, n)| *n)
}

RuS6.11 Leer las macros del ecosistema

No vas a escribir muchas macros. Vas a diagnosticar las de otros todas las semanas. Estas cuatro cubren casi todo lo que te vas a encontrar.

#[tokio::main] — una macro de atributo que reescribe tu main

// Lo que escribís
#[tokio::main(flavor = "current_thread")]
async fn main() { trabajo().await; }

// Lo que existe realmente (cargo expand)
fn main() {
    let cuerpo = async { trabajo().await; };
    return tokio::runtime::Builder::new_current_thread()
        .enable_all()
        .build()
        .expect("Failed building the Runtime")
        .block_on(cuerpo);
}
Esto explica de un saque tres preguntas frecuentes: por qué #[tokio::main] necesita la feature macros y rt-multi-thread; por qué el error "there is no reactor running" aparece cuando alguien saca el atributo; y por qué #[tokio::test] crea un runtime por test — lo ves en la expansión, no en la documentación. Cada vez que dudes de qué runtime estás usando, cargo expand te lo dice literalmente.

thiserror — un derive puramente de compilación

use thiserror::Error;

#[derive(Debug, Error)]
pub enum ErrorCarga {
    #[error("no se pudo leer {ruta}")]
    Io { ruta: String, #[source] causa: std::io::Error },
    #[error("JSON invalido en la linea {0}")]
    Json(usize),
    #[error(transparent)]                    // delega Display al de adentro
    Otro(#[from] anyhow::Error),
}
// Genera: impl Display (con el formato de cada #[error]),
//         impl Error::source() (de los campos #[source]/#[from]),
//         impl From<anyhow::Error> (del #[from]).

Detalle que se pregunta en entrevistas: thiserror no deja dependencia en tiempo de ejecución — genera impls de traits de std y nada más. anyhow es al revés: es una biblioteca de runtime, y sus anyhow!/bail! son macro_rules! triviales. Por eso la regla habitual: thiserror en bibliotecas, anyhow en aplicaciones.

clap — un derive que es una fachada del builder

#[derive(Parser)] no inventa nada: traduce tu struct a llamadas de la API de builder que existía antes. Por eso cada atributo del derive tiene un equivalente en el builder, y por eso algunos errores hablan de conceptos ("arg", "command", "group") que no aparecen en tu código. Cuando un atributo de clap no hace lo que esperás, expandí y mirá a qué llamada se tradujo.

sqlx::query! — la macro que hace lo imposible

// Se conecta a la base EN TIEMPO DE COMPILACIÓN (o lee .sqlx/ en modo offline),
// valida el SQL contra el schema real e infiere los tipos de las columnas.
let fila = sqlx::query!("SELECT id, email FROM usuarios WHERE id = $1", id)
    .fetch_one(&pool)
    .await?;

// fila.email es String o Option<String> según la nullability REAL de la columna.
// Un typo en el nombre de la tabla es un error de compilación, no un panic a las 3 AM.
💡 Este es el argumento definitivo a favor de las macros procedurales. Ningún genérico, ningún trait, ninguna feature futura del lenguaje puede validar un string de SQL contra un schema en PostgreSQL. Requiere ejecutar código arbitrario durante la compilación, que es exactamente lo que una proc-macro es. Cuando alguien te diga "las macros son un antipatrón", sqlx::query! es la respuesta: cuando el problema justifica el costo, el costo se paga contento.

🧑‍🎓 Worked Example — el patrón que aparece 12 veces

Un servicio de facturación tiene 12 tipos de evento (CrearFactura, AnularFactura, RegistrarPago…). Los 12 necesitan lo mismo: convertirse en una FilaAuditoria con un nombre de evento en snake_case, un timestamp y el payload en JSON. Hoy están las 12 implementaciones copiadas a mano y ya hubo dos bugs por copiar y no cambiar el nombre. Alguien propone un #[derive(Auditable)]. ¿Es la respuesta?

Paso 0 — Escribir la restricción antes que la solución. El requisito real es: un solo lugar donde se define el mapeo, imposible de desincronizar, y el nombre del evento derivado del nombre del tipo. Los 12 tipos ya derivan Serialize. Con eso escrito, evaluamos las cuatro salidas en orden de simplicidad.

Salida 1 — Una función

fn a_fila(nombre: &str, payload: &impl Serialize) -> FilaAuditoria { /* … */ }

// En cada uno de los 12 lugares:
a_fila("crear_factura", &evento)

Veredicto: no alcanza. Resuelve la lógica, pero el string sigue escrito a mano 12 veces. Es literalmente el bug que queremos eliminar. Descartada — y descartada por la razón correcta, no por "es poco elegante".

Salida 2 — Trait con blanket impl

pub trait Evento: Serialize {
    /// Por defecto: el nombre del tipo, en snake_case, calculado una sola vez.
    fn nombre_evento() -> &'static str where Self: Sized {
        static CACHE: OnceLock<String> = OnceLock::new();
        CACHE.get_or_init(|| a_snake_case(::core::any::type_name::<Self>())).as_str()
    }
}

// Blanket impl: TODO lo que sea Evento es Auditable, gratis.
impl<T: Evento> Auditable for T {
    fn a_fila(&self) -> FilaAuditoria {
        FilaAuditoria {
            evento: T::nombre_evento(),
            momento: OffsetDateTime::now_utc(),
            payload: serde_json::to_value(self).unwrap_or(Value::Null),
        }
    }
}

// Y en cada tipo, una línea:
impl Evento for CrearFactura {}

Veredicto: funciona. 12 líneas de impl Evento for X {}, cero macros, el nombre se deriva solo. Dos objeciones legítimas: type_name no está garantizado por el estándar como estable entre versiones, y dos tipos necesitan un nombre distinto al del struct. La segunda se resuelve sin tocar nada, sobrescribiendo el método por defecto en esos dos casos. La primera se resuelve con un test:

// Un test barato clava el contrato y avisa si una versión futura lo cambia.
#[test]

    assert_eq!(CrearFactura::nombre_evento(), "crear_factura");
    assert_eq!(RegistrarPago::nombre_evento(), "registrar_pago");

Checkpoint — ¿lo tenés claro?

¿Por qué CUADRADO(1 + 2) da 5 en C y cuadrado!(1 + 2) da 9 en Rust?

Porque el preprocesador de C hace sustitución de texto antes de que el compilador parsee: x * x se convierte literalmente en 1 + 2 * 1 + 2, y ahí las reglas de precedencia se aplican sobre el texto ya mezclado. En Rust, $x:expr captura la expresión 1 + 2 como un nodo del árbol sintáctico, con delimitadores invisibles que la mantienen indivisible. Cuando la macro emite $x * $x, cada $x sigue siendo esa expresión completa, así que el resultado es (1 + 2) * (1 + 2). Esa diferencia —tokens estructurados versus caracteres— es la que también da higiene, mejores errores y la imposibilidad de generar código sintácticamente inválido.

Tu macro_rules! tiene que generar FooBuilder a partir de Foo. ¿Qué hacés?

No se puede, y hay que reconocerlo rápido en vez de pelearla: macro_rules! no puede fabricar identificadores nuevos (concat_idents! es inestable y ni siquiera sirve para declarar ítems). Hay tres salidas. (a) Pedirle el nombre al usuario: builder!(Foo, FooBuilder); — feo pero honesto, y cuesta cero. (b) El crate paste, que resuelve exactamente esto… pero es una proc-macro, así que ya pagaste el costo sin ganar el control. (c) Escribir una proc-macro de verdad y usar format_ident!("{}Builder", nombre). Si además necesitás leer atributos o dar errores con span propio, la (c) es la única que sirve; si es solo el nombre, la (a) suele ser la decisión sensata.

Tu derive funciona, pero cuando el usuario se equivoca el error apunta a #[derive(Builder)] y dice "proc-macro derive panicked". ¿Qué le falta?

Dos cosas, y las dos son baratas. Primero, sacar todos los panic! y unwrap(): la función pública tiene que parsear, delegar en una que devuelva syn::Result, y cerrar con .unwrap_or_else(syn::Error::into_compile_error). Eso convierte el pánico en un error de compilación normal. Segundo, darle un span útil: syn::Error::new(campo.span(), "…") o Error::new_spanned(&campo.ty, "…") para que el subrayado caiga sobre el campo culpable y no sobre el atributo. Si además el error es de trait bounds del código generado, se arregla emitiendo esa parte con quote_spanned! usando el span del tipo. Y para que no se degrade con el próximo refactor, se congela en un .stderr de trybuild: el test compara mensaje y ubicación.

Resumen ejecutivo

  • Las macros de Rust operan sobre tokens y fragmentos del AST, no sobre texto. De ahí salen la higiene, los buenos errores y la imposibilidad del bug clásico de CUADRADO(1+2).
  • Corren antes de la resolución de tipos. Una macro nunca sabe si algo implementa Clone, ni si Option es el de std. Toda decisión es sintáctica, siempre.
  • macro_rules! cuesta casi nada y cubre muchísimo: patrones, repetición $()*, $(,)? para la coma final, $crate obligatorio al exportar, y un catch-all con compile_error! como mínimo de cortesía.
  • La higiene es parcial: protege variables locales, labels y lifetimes. No protege rutas, tipos ni nombres de ítems — por eso ::std:: y $crate:: en todo lo que emitas.
  • Se sube a procedural por cuatro razones y solo esas: fabricar identificadores, engancharse a una definición real, leer atributos, o dar errores con span propio.
  • El trío es syn + quote + proc-macro2, en un crate con proc-macro = true. Nunca panic!: syn::Result, Error::new_spanned, combine y into_compile_error.
  • cargo expand para ver qué generaste (propio o ajeno) y trybuild para que los errores no se degraden. Sin las dos, es programar a ciegas.
  • El costo real no es expandir: es syn en el camino crítico del build limpio y la monomorfización del código generado. Se mide con --timings, cargo tree -i syn y cargo llvm-lines, no se estima.
  • Si un trait, un genérico o una función alcanzan, ganan. Una macro es código que tu IDE entiende peor, que tu equipo debuggea peor, que rompe goto-definition y que nadie revisa en el diff.
  • Si la entrada es un archivo, la herramienta es build.rs, no una macro. Y si una feature del lenguaje vuelve tu macro innecesaria, anotalo: lazy_static! y #[async_trait] ya murieron así.

🧠 Autoevaluación

1. Tu macro_rules! necesita generar, a partir de Pedido, un tipo llamado PedidoBuilder. ¿Qué te dice eso?

Es la Pared 1. Las macros declarativas pueden reordenar y repetir tokens que ya existen, pero no pueden construir un identificador nuevo a partir de otro. concat_idents! es inestable y ni siquiera sirve para declarar ítems. Las salidas reales son pedirle el nombre al usuario (builder!(Pedido, PedidoBuilder)), usar el crate paste —que ya es una proc-macro—, o escribir una proc-macro y usar format_ident!. Ni el recursion_limit ni el fragment specifier tienen nada que ver.

2. Tu #[derive(Config)] hace unwrap() cuando el usuario lo aplica a un enum, y el error dice "proc-macro derive panicked" apuntando al atributo. ¿Cuál es el arreglo correcto?

Un pánico en una proc-macro siempre produce el mismo error inútil, con el span del #[derive(...)] y el mensaje escondido en un = help:. Cambiar unwrap por expect mejora el texto pero sigue siendo un pánico con span equivocado. El patrón correcto es el canónico: la función pública parsea y delega, la lógica devuelve syn::Result, los errores se crean con syn::Error::new(span, msg) apuntando al token culpable, y el cierre convierte todo en un compile_error! normal. Y después se congela con un .stderr de trybuild, porque un buen mensaje sin test se degrada solo.

3. Tenés que implementar el mismo método en 12 tipos que ya comparten un trait. Un compañero propone un #[derive(...)] propio. ¿Qué evaluás primero?

El orden es función → trait → macro_rules! → proc-macro, y hay que frenar en el primer escalón que sirva. Un blanket impl cubre exactamente este caso —"todos los que ya son X también son Y"— sin agregar una línea de metaprogramación, sin traer syn al árbol de dependencias (que en un build limpio son varios segundos en el camino crítico) y sin romper goto-definition. El build.rs es la herramienta para cuando la entrada es un archivo, no código Rust. Y elegir versión de syn es optimizar una decisión que todavía no deberías haber tomado.

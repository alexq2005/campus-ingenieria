RuS8 — Embebido y producción: no_std, Embassy y deploy

RuS8.0 Por qué este módulo

Hay una propiedad de Rust que casi ningún otro lenguaje tiene, y que recién se aprecia cuando la usás en los dos extremos a la vez: el mismo lenguaje, con la misma semántica de ownership y los mismos traits, corre en un servidor con 128 GB de RAM y en un microcontrolador con 64 KB de flash. No es "Rust y además un dialecto embebido". Es el mismo compilador, el mismo cargo, los mismos Result y las mismas reglas de préstamos. Lo único que cambia es qué biblioteca estándar tenés disponible.

💡 La tesis del módulo. Este es el cierre del track, y cubre las dos puntas de lo que significa "poner Rust en producción". Del lado servidor, producción es una lista corta de decisiones que se toman una vez y se pagan durante años: cómo se representan los errores, cómo se observa el sistema, cómo se empaqueta y cómo se audita el árbol de dependencias. Del lado embebido, producción es entender qué desaparece cuando sacás std, qué queda, y cómo el modelo de async que estudiaste en RuS3 resulta ser —de manera bastante inesperada— la mejor herramienta que existe para escribir firmware que dure meses con una batería.

Y hay una razón para estudiar el lado embebido ahora y no dentro de tres años: dejó de ser un experimento. Espressif adoptó Rust como SDK oficial de primer nivel a través de esp-rs. Embassy se convirtió en el runtime async de facto en microcontroladores y los proyectos nuevos rara vez arrancan con el patrón clásico de super-loop más interrupciones. probe-rs reemplazó a OpenOCD en la práctica para flashear y debuggear. Lo que hace cinco años eran demos de conferencia hoy es el camino por defecto.

Este módulo tiene dos mitades que se pueden leer por separado. La Parte A (RuS8.1–RuS8.5) es sobre servicios: si trabajás en backend, es la que te toca mañana. La Parte B (RuS8.6–RuS8.12) es sobre firmware. Recomiendo leer las dos igual, porque la Parte B te obliga a ver con claridad cuánto trabajo hace std por vos —trabajo que en el servidor es invisible justamente porque siempre está ahí.

RuS8.1 Parte A — Errores en una app real: thiserror vs anyhow

En RuS2 viste que Result y el operador ? se apoyan en el trait From: ? propaga el error convirtiéndolo al tipo de error de la función que lo contiene. En un ejercicio eso es trivial porque hay un solo tipo de error. En una aplicación real vas a tener errores de I/O, de red, de parseo, de la base de datos y de tu propia lógica de dominio, y la pregunta se vuelve concreta: ¿qué tipo de error devuelve cada capa?

La respuesta del ecosistema es una regla con dos casos, y vale la pena entender por qué son dos casos distintos y no una preferencia de estilo.

📌 La regla. thiserror en librerías. anyhow en binarios. La diferencia real es quién va a consumir el error: si es otro código, el error tiene que ser un tipo cerrado que se pueda inspeccionar con match; si es un humano leyendo un log, lo que importa es el contexto acumulado, no la forma del tipo.

Una librería expone un enum de errores. El punto no es que sea "más prolijo": es que el que llama necesita poder decidir distinto según el caso. Si tu librería devuelve un error opaco, el que la usa no puede distinguir "el token expiró, reintentá" de "el JSON está roto, no reintentes nunca".

use thiserror::Error;

#[derive(Debug, Error)]
pub enum ClienteError {
    #[error("fallo de transporte hacia {url}")]
    Transporte {
        url: String,
        #[source] fuente: reqwest::Error,
    },

    #[error("la respuesta no es JSON válido")]
    Deserializacion(#[from] serde_json::Error),

    #[error("el servidor respondió {codigo}: {mensaje}")]
    Api { codigo: u16, mensaje: String },

    #[error("el token expiró hace {0} segundos")]
    TokenExpirado(u64),
}

thiserror es una macro derive —de las que estudiaste en RuS6— que genera el impl Display a partir de los atributos #[error(...)] y el impl std::error::Error con el método source() apuntando al campo marcado con #[source]. El #[from] genera además el impl From, que es lo que hace funcionar al ?:

pub fn parsear(cuerpo: &str) -> Result<Usuario, ClienteError> {
    // serde_json::Error se convierte solo, porque hay #[from]
    let u: Usuario = serde_json::from_str(cuerpo)?;
    Ok(u)
}
Error frecuente: poner #[from] en todas las variantes. #[from] exige que la conversión sea sin ambigüedad: no podés tener dos variantes que conviertan desde std::io::Error, porque el compilador no sabría cuál elegir. Además, la conversión automática tira contexto: si tenés tres llamadas de red distintas en una función y las tres se convierten a la misma variante, el mensaje no te dice cuál falló. Cuando querés contexto, construí la variante a mano con map_err. 
let resp = self.http.get(&url).send().await
    .map_err(|e| ClienteError::Transporte { url: url.clone(), fuente: e })?;

Del otro lado: el binario

En el main de un servicio, esa disciplina se vuelve contraproducente. Nadie va a hacer match sobre el error de tu main: el error se loguea y el proceso decide si sigue o se muere. Escribir un enum que una las quince fuentes de error de todo el programa es trabajo puro sin beneficio. Ahí entra anyhow, que da un tipo único —anyhow::Error— capaz de contener cualquier cosa que implemente std::error::Error, y que aporta lo que sí importa: contexto encadenado.

use anyhow::{Context, Result};

fn cargar_config(ruta: &Path) -> Result<Config> {
    let texto = std::fs::read_to_string(ruta)
        .with_context(|| format!("no pude leer la config en {}", ruta.display()))?;

    let cfg: Config = toml::from_str(&texto)
        .with_context(|| format!("la config en {} no es TOML válido", ruta.display()))?;

    cfg.validar().context("la config parsea pero es inconsistente")?;
    Ok(cfg)
}

Cuando eso falla, el error impreso no es No such file or directory (os error 2), que no le sirve a nadie. Es una cadena:

Error: no pude leer la config en /etc/svc/config.toml

Caused by:
    0: No such file or directory (os error 2)
with_context toma un closure y solo lo ejecuta si hay error, así que el format! no se paga en el camino feliz. context toma un valor ya construido: usalo con literales, no con format!.

Las dos bibliotecas conviven sin fricción, porque anyhow::Error implementa From<E> para todo E: std::error::Error + Send + Sync + 'static. Tus errores de thiserror entran solos:

// en el binario, mezclando errores de tres librerías distintas
async fn ciclo(&self) -> anyhow::Result<()> {
    let cfg = cargar_config(&self.ruta)?;              // anyhow
    let datos = self.cliente.traer().await             // ClienteError (thiserror)
        .context("fallo al traer datos del proveedor")?;
    self.db.guardar(&datos).await                       // sqlx::Error
        .context("fallo al persistir el lote")?;
    Ok(())
}

La regla se rompe en un caso, y es un caso que aparece: cuando el binario sí necesita decidir según el error. En un servidor HTTP tenés que mapear el error a un código de estado, y eso es lógica, no logging. Ahí querés un enum propio en la capa de handlers aunque el resto del programa use anyhow:

// axum: el error de la capa HTTP sí es un tipo cerrado
#[derive(Debug, Error)]
enum ApiError {
    #[error("no encontrado")]
    NoEncontrado,
    #[error("credenciales inválidas")]
    NoAutorizado,
    #[error(transparent)]
    Interno(#[from] anyhow::Error),   // el cajón de sastre
}

impl IntoResponse for ApiError {
    fn into_response(self) -> Response {
        let status = match self {
            ApiError::NoEncontrado => StatusCode::NOT_FOUND,
            ApiError::NoAutorizado => StatusCode::UNAUTHORIZED,
            ApiError::Interno(ref e) => {
                tracing::error!(error = ?e, "error interno");
                StatusCode::INTERNAL_SERVER_ERROR
            }
        };
        (status, self.to_string()).into_response()
    }
}
Fijate en el Interno: el mensaje del error interno se loguea con todo el detalle, pero al cliente le llega solo el status. Nunca devuelvas el Display de un error interno en una respuesta HTTP: los errores de base de datos filtran nombres de tablas, y los de I/O filtran rutas del filesystem. Eso es exactamente la clase de fuga de información que trata el M07 de Ciberseguridad.

RuS8.2 Observabilidad: tracing, no log

El crate log es la fachada clásica: info!, warn!, error!. Funciona, es minúsculo y para una CLI alcanza. Para un servicio async no alcanza, y la razón es estructural, no de gustos.

Un log es una línea con un instante. En un servidor sincrónico con un thread por request, eso es suficiente porque el thread es la unidad de trabajo: agrupás por thread ID y reconstruís la request. En un servidor async —lo que viste en RuS3 y RuS4— una tarea salta de thread en cada .await, y miles de tareas se intercalan sobre el mismo par de threads. El thread ID deja de significar nada. Si tenés diez requests concurrentes, tus líneas de log quedan entreveradas sin ninguna manera de separarlas.

La diferencia. log registra eventos: "pasó esto, a esta hora". tracing registra eventos y spans: períodos de tiempo con estructura, que se anidan y que viajan con la tarea. Un span es "estoy adentro del procesamiento del pedido 4471", y todo lo que se loguee mientras esa tarea está viva —aunque sea en otro thread, aunque pasen tres .await— queda etiquetado con ese pedido. Es la única forma de que un log async sea legible. 
use tracing::{info, warn, instrument};

#[instrument(skip(db), fields(pedido_id = %pedido.id))]
async fn procesar(pedido: Pedido, db: &Pool) -> anyhow::Result<Recibo> {
    info!("iniciando procesamiento");

    let stock = verificar_stock(&pedido, db).await?;   // hereda el span
    if stock.faltante > 0 {
        warn!(faltante = stock.faltante, "stock insuficiente, backorder");
    }

    let recibo = cobrar(&pedido).await?;               // hereda el span
    info!(monto = recibo.monto, "procesamiento completo");
    Ok(recibo)
}

El atributo #[instrument] —otra macro procedural— envuelve la función en un span que se abre al entrar y se cierra al salir, incluyendo la duración. skip(db) evita que intente formatear el pool de conexiones, que no tiene Debug útil y sería enorme. fields(...) agrega campos al span; el % pide Display y el ? pide Debug.

Lo importante es lo que no se ve: verificar_stock y cobrar no reciben el pedido_id por parámetro. Sus propios logs lo llevan igual, porque el span es contextual y se propaga por la tarea. Esto es lo que hace que tracing encaje con async: el contexto sigue a la tarea, no al thread.

El suscriptor: dónde se decide el formato

tracing solo emite. Quien decide qué hacer con eso es tracing-subscriber, y esa separación es lo que te deja cambiar de formato sin tocar una línea de código de negocio.

use tracing_subscriber::{layer::SubscriberExt, util::SubscriberInitExt, EnvFilter};

fn init_telemetria(json: bool) {
    let filtro = EnvFilter::try_from_default_env()
        .unwrap_or_else(|_| EnvFilter::new("info,sqlx=warn,hyper=warn"));

    let registro = tracing_subscriber::registry().with(filtro);

    if json {
        // producción: una línea JSON por evento, para ingestión automática
        registro.with(tracing_subscriber::fmt::layer().json()).init();
    } else {
        // desarrollo: legible por humanos, con colores
        registro.with(tracing_subscriber::fmt::layer().pretty()).init();
    }
}
# el filtro se controla por variable de entorno, sin recompilar
RUST_LOG=info cargo run
RUST_LOG=debug,mi_app::pagos=trace,sqlx=off cargo run

# en producción: subir el nivel de un módulo puntual sin tocar el resto
RUST_LOG="warn,mi_app::pagos=debug" ./servicio
📌 En producción, JSON siempre. Un log de texto plano obliga a que alguien escriba expresiones regulares del lado del agregador, y esas regex se rompen el día que alguien cambia un mensaje. Con .json(), cada campo del span es un campo del documento: filtrar por pedido_id es una query, no un grep. El costo es que deja de ser cómodo de leer a mano — por eso la función de arriba tiene las dos ramas.

OpenTelemetry: cuando el sistema es más de un proceso

Cuando la request atraviesa tres servicios, los spans locales dejan de alcanzar: necesitás que el span del servicio A sea el padre del span del servicio B. Ese es el estándar OpenTelemetry, y el puente se llama tracing-opentelemetry. Como es una capa más del registry, se agrega sin tocar nada de lo anterior:

use tracing_opentelemetry::OpenTelemetryLayer;

let tracer = opentelemetry_otlp::new_pipeline()
    .tracing()
    .with_exporter(opentelemetry_otlp::new_exporter().tonic())
    .install_batch(opentelemetry_sdk::runtime::Tokio)?;

tracing_subscriber::registry()
    .with(EnvFilter::from_default_env())
    .with(tracing_subscriber::fmt::layer().json())   // logs a stdout
    .with(OpenTelemetryLayer::new(tracer))           // trazas al colector
    .init();
El install_batch importa: exportar cada span de a uno por red agrega latencia a cada request. El exportador por lotes acumula en memoria y manda en tandas desde una tarea aparte. La contra es que si el proceso se muere de golpe, perdés el último lote — un intercambio razonable para telemetría, inaceptable para un log de auditoría.

RuS8.3 Configuración y secretos

La configuración de un servicio viene de tres lados que hay que combinar con precedencia clara: valores por defecto en el código, un archivo, y variables de entorno que pisan a los dos. En Rust eso se resuelve deserializando a un struct con serde, lo cual tiene una ventaja enorme sobre leer un diccionario: si falta un campo o tiene el tipo equivocado, el proceso no arranca, en lugar de explotar tres horas después cuando alguien toca ese código path.

use serde::Deserialize;
use secrecy::{ExposeSecret, SecretString};

#[derive(Debug, Deserialize)]
pub struct Config {
    #[serde(default = "puerto_default")]
    pub puerto: u16,
    pub base_datos_url: SecretString,     // ← nunca se imprime
    pub timeout_ms: u64,
    #[serde(default)]
    pub modo_debug: bool,
}

fn puerto_default() -> u16 { 8080 }

impl Config {
    pub fn cargar() -> anyhow::Result<Self> {
        // figment: capas con precedencia explícita, de menor a mayor
        figment::Figment::new()
            .merge(figment::providers::Toml::file("config.toml"))
            .merge(figment::providers::Env::prefixed("APP_"))
            .extract()
            .context("configuración inválida")
    }
}

El detalle que separa un servicio serio de uno que va a filtrar credenciales es SecretString, del crate secrecy. Es un wrapper cuyo Debug imprime Secret([REDACTED String]) en lugar del valor. Suena menor hasta que ves cómo se filtran los secretos en la vida real: casi nunca por un println! deliberado. Se filtran porque alguien puso #[derive(Debug)] en la config, y después alguien más escribió tracing::debug!(config = ?cfg, "arrancando"), y esa línea mandó la URL de la base con usuario y contraseña a un agregador de logs de terceros que la retiene 90 días.

let cfg = Config::cargar()?;

tracing::info!(config = ?cfg, "config cargada");
// -> Config { puerto: 8080, base_datos_url: Secret([REDACTED alloc::string::String]), .. }

// para usarlo hay que pedirlo explícitamente, y eso se ve en el code review
let pool = PgPool::connect(cfg.base_datos_url.expose_secret()).await?;
📌 El valor de secrecy no es criptográfico, es social. No cifra nada. Lo que hace es convertir "filtrar un secreto por accidente" en "filtrar un secreto escribiendo expose_secret()", que es una línea que salta en cualquier revisión y que podés buscar con grep en todo el repo. Mueve el error de invisible a visible.

El resto de la historia —de dónde salen esas variables de entorno, rotación de credenciales, por qué un secreto en el repo sigue estando en el repo aunque lo borres con un commit, y qué hace un gestor tipo Vault— está en el M07 del curso de Ciberseguridad. Es el complemento directo de esta sección y de la RuS8.5.

RuS8.4 Deploy: binario estático, imagen mínima y compilación cruzada

Un binario de Rust compilado con el target por defecto de Linux (x86_64-unknown-linux-gnu) enlaza dinámicamente contra glibc. Eso significa que el binario que compilaste en tu Ubuntu 24.04 puede no arrancar en una imagen basada en Debian 11: version GLIBC_2.38 not found. Es el clásico. La solución es enlazar contra musl, que produce un binario completamente estático, sin ninguna dependencia de bibliotecas del sistema:

rustup target add x86_64-unknown-linux-musl

# en Debian/Ubuntu hace falta el linker de musl
sudo apt install musl-tools

cargo build --release --target x86_64-unknown-linux-musl

# comprobalo: "statically linked" es la respuesta que querés
ldd target/x86_64-unknown-linux-musl/release/servicio
#   not a dynamic executable

Con un binario estático, la imagen de Docker deja de necesitar sistema operativo:

# Dockerfile — build multi-etapa hacia una imagen sin nada adentro
FROM rust:1.83-alpine AS build
RUN apk add --no-cache musl-dev
WORKDIR /src

# truco de caché: copiar solo los manifiestos y compilar dependencias primero
COPY Cargo.toml Cargo.lock ./
RUN mkdir src && echo "fn main(){}" > src/main.rs && cargo build --release
RUN rm -rf src

COPY src ./src
RUN touch src/main.rs && cargo build --release

FROM scratch
COPY --from=build /src/target/release/servicio /servicio
USER 10001:10001
ENTRYPOINT ["/servicio"]

FROM scratch es literalmente una imagen vacía. El resultado típico ronda los 8–20 MB: solo tu binario. La superficie de ataque es mínima porque no hay shell, no hay curl, no hay gestor de paquetes: un atacante que logre ejecución remota no tiene con qué moverse. Y el escáner de vulnerabilidades del registry no reporta nada, porque no hay paquetes del sistema que reportar.

scratch tiene tres trampas que muerden siempre. (1) No hay certificados raíz: cualquier request HTTPS saliente falla con un error de verificación de certificado. Hay que copiar /etc/ssl/certs/ca-certificates.crt desde la etapa de build, o usar rustls con la feature webpki-roots, que los embebe en el binario. (2) No hay /etc/passwd: el USER tiene que ser numérico. (3) No hay zoneinfo: las zonas horarias con nombre no resuelven. Si algo de eso te complica, distroless (gcr.io/distroless/static-debian12) trae certificados, usuarios y zonas, sigue sin shell, y pesa unos 2 MB más.

El tamaño del binario en sí se controla desde el perfil de release, y las opciones tienen un costo que conviene conocer:

[profile.release]
opt-level = 3
lto = "fat"          # optimización entre unidades: más rápido y más chico, compila lento
codegen-units = 1    # menos paralelismo al compilar, mejor código final
strip = "symbols"    # saca símbolos de debug: puede ser la mitad del tamaño
panic = "abort"      # sin unwinding: menos código, pero NO se puede recuperar de un panic

# perfil aparte para perfilar en producción: release + símbolos
[profile.profiling]
inherits = "release"
debug = 1
strip = "none"
Cuidado con panic = "abort" del lado servidor. Sin unwinding, std::panic::catch_unwind deja de funcionar y un panic en cualquier tarea mata el proceso entero. Tokio, por defecto, aísla el panic de una tarea: la tarea muere, el runtime sigue. Con abort perdés eso. En un servicio que atiende miles de requests, un panic en una sola por un input raro se convierte en una caída total. En embebido es al revés y abort es prácticamente obligatorio — lo vemos en RuS8.12.

Compilación cruzada

Compilar para otra arquitectura desde tu máquina —típicamente ARM64 para servidores Graviton o para una Raspberry Pi— es donde cargo solo se queda corto, porque necesita un linker de la arquitectura destino. La herramienta que resuelve eso es cross, que hace el build dentro de un contenedor con el toolchain ya armado:

cargo install cross --git https://github.com/cross-rs/cross

cross build --release --target aarch64-unknown-linux-musl
cross build --release --target armv7-unknown-linux-musleabihf   # Pi 32 bits

# y para el otro extremo de este módulo: un micro Cortex-M4
rustup target add thumbv7em-none-eabihf
cargo build --release --target thumbv7em-none-eabihf

Ese último comando es la bisagra del módulo. thumbv7em-none-eabihf: el none del medio es el sistema operativo, y dice que no hay ninguno. Ese target no tiene std disponible. Todo lo que sigue en la Parte B sale de ahí.

RuS8.5 Supply chain: el árbol de dependencias es tu superficie de ataque

Rust tiene una biblioteca estándar deliberadamente chica: no trae cliente HTTP, ni serialización, ni generación de números aleatorios criptográficos, ni fechas. Todo eso viene de crates.io. La consecuencia es directa y hay que decirla sin eufemismos: en Rust el árbol de dependencias crece muy rápido. Un servicio web con axum + tokio + sqlx + serde arranca cómodamente arriba de las 250 dependencias transitivas.

cargo install cargo-tree cargo-audit cargo-deny cargo-outdated

cargo tree --depth 1            # dependencias directas
cargo tree --duplicates         # el mismo crate en dos versiones mayores: peso muerto
cargo tree -i openssl-sys       # ¿QUIÉN metió openssl en mi build?

Ese último comando (-i, de invert) es el que más se usa en la práctica: te dice qué dependencia tuya arrastró a una que no querías. Es la forma de encontrar por qué tu build necesita OpenSSL del sistema cuando vos creías estar usando rustls.

Las dos herramientas que van en CI

cargo-audit compara tu Cargo.lock contra la RustSec Advisory Database y falla si alguna versión que estás usando tiene una vulnerabilidad publicada:

cargo audit

#    Crate:     time
#    Version:   0.1.44
#    Title:     Potential segfault in the time crate
#    ID:        RUSTSEC-2020-0071
#    Solution:  Upgrade to >=0.2.23
#    Dependency tree: time 0.1.44 -> chrono 0.4.19 -> mi-app 0.1.0

cargo-deny es más amplio y es el que realmente conviene tener: además de vulnerabilidades, revisa licencias, fuentes y duplicados, todo desde un archivo de política versionado en el repo:

# deny.toml
[advisories]
yanked = "deny"
ignore = []                       # cada excepción va acá, con comentario y fecha

[licenses]
allow = ["MIT", "Apache-2.0", "BSD-3-Clause", "ISC", "Unicode-3.0"]
confidence-threshold = 0.9

[bans]
multiple-versions = "warn"
deny = [
  { name = "openssl", reason = "usamos rustls en todo el stack" },
]

[sources]
unknown-registry = "deny"         # nada fuera de crates.io
allow-git = []                    # ninguna dependencia apuntando a un repo suelto
# en CI, esto tiene que fallar el pipeline
cargo deny check advisories
cargo deny check licenses
cargo deny check bans sources
📌 El Cargo.lock se commitea. Siempre. La regla vieja era "solo en binarios, no en librerías". Cambió: hoy se commitea también en librerías, porque el lockfile es lo que hace que el CI sea reproducible y lo que cargo audit necesita leer. El lockfile de una librería no afecta a quien la consume — cargo lo ignora al resolver dependencias de otro proyecto. No hay contra.
El riesgo que no se resuelve con herramientas. Un crate de crates.io ejecuta código tuyo en tres momentos: al compilar (build.rs), al expandir macros procedurales (RuS6) y en runtime. Los dos primeros corren con tus permisos, en tu máquina y en tu CI, antes de que ningún test se ejecute. cargo-audit encuentra vulnerabilidades conocidas; no encuentra un crate malicioso publicado hace dos horas con un nombre parecido al que quisiste escribir. Las defensas reales son aburridas: pocas dependencias directas, leer qué arrastra cada una, fijar versiones, y desconfiar de nombres casi iguales a los populares. cargo-vet y cargo-crev agregan revisión compartida entre organizaciones, pero eso ya es política de equipo, no una herramienta.

RuS8.6 Parte B — Qué desaparece sin std

Un microcontrolador típico no tiene sistema operativo, no tiene MMU, no tiene filesystem y no tiene red salvo que se la pongas vos. La biblioteca estándar de Rust asume que todas esas cosas existen. Sacarla es una línea:

#![no_std]
#![no_main]

Y a partir de esa línea, esto es lo que se va y lo que queda:

CapaQué te daRequiere
coreTipos primitivos, Option, Result, iteradores, traits, slices, fmt, aritmética, punteros, atómicos (si el target los tiene)Nada. Siempre está disponible
allocVec, String, Box, Rc, Arc, BTreeMap, VecDequeUn allocator global que le proporciones vos
stdTodo lo anterior más threads, File, TcpStream, std::time, HashMap, variables de entorno, println!, panic con unwindingUn sistema operativo
💡 Lo que no se pierde es lo importante. Ownership, borrowing, lifetimes, traits, genéricos, pattern matching, Result y el operador ?, iteradores con todas sus optimizaciones, macros declarativas y procedurales: todo eso vive en el compilador y en core, no en std. Escribir no_std no es escribir "Rust reducido". Es escribir Rust sin heap ni I/O — lo cual, en un micro, es exactamente lo que querés.

Sin heap: heapless

Perder Vec y String parece dramático hasta que ves el reemplazo. El crate heapless da las mismas estructuras con capacidad fija, definida en el tipo mediante un parámetro const genérico. Viven enteras en el stack o en un static:

use heapless::{Vec, String, spsc::Queue};

// un Vec de hasta 32 muestras, sin heap, tamaño conocido en tiempo de compilación
let mut muestras: Vec<u16, 32> = Vec::new();

match muestras.push(lectura) {
    Ok(()) => {}
    Err(_valor) => {
        // el buffer está lleno. En std esto reasignaba en silencio;
        // acá el compilador te OBLIGA a decidir qué hacer.
        muestras.remove(0);
        let _ = muestras.push(lectura);
    }
}

let mut linea: String<64> = String::new();
let _ = write!(linea, "t={}C h={}%", temp, hum);

// cola de un productor y un consumidor: la forma segura de pasarle datos a una ISR
static mut COLA: Queue<u16, 16> = Queue::new();
📌 Que push devuelva Result es la característica, no el inconveniente. En un sistema empotrado que tiene que correr meses sin reiniciarse, "el buffer se llenó" no es un caso excepcional: es un caso operativo que va a pasar, probablemente de noche, cuando el sensor se vuelva loco o la red se caiga. heapless te fuerza a escribir la política —descartar el más viejo, descartar el nuevo, encender un LED de error— en el momento en que escribís el código, en vez de descubrirla cuando el dispositivo se queda sin memoria en campo.

Si igual necesitás asignación dinámica —parsear JSON de tamaño variable, por ejemplo— podés usar alloc como término medio, aportando vos el allocator:

#![no_std]
extern crate alloc;

use alloc::vec::Vec;              // ahora sí, Vec dinámico
use embedded_alloc::LlffHeap as Heap;

#[global_allocator]
static HEAP: Heap = Heap::empty();

fn init_heap() {
    use core::mem::MaybeUninit;
    const TAM_HEAP: usize = 8 * 1024;                      // 8 KB, y ni uno más
    static mut MEMORIA: [MaybeUninit<u8>; TAM_HEAP] = [MaybeUninit::uninit(); TAM_HEAP];
    unsafe { HEAP.init(&raw mut MEMORIA as usize, TAM_HEAP) }
}
Usar alloc en un micro es una decisión con consecuencias, no una comodidad. Sin MMU no hay memoria virtual: la fragmentación es permanente y acumulativa, y un dispositivo que asigna y libera bloques de tamaños distintos durante semanas termina fallando una asignación aunque le sobre memoria total. Además, el tiempo de alloc no es determinista, lo cual rompe cualquier análisis de tiempo real. La regla del ecosistema: heapless por defecto, alloc solo donde el tamaño es genuinamente dinámico, y nunca dentro de una interrupción.

El ecosistema embebido de Rust está organizado en tres capas más un contrato transversal, y entender esa arquitectura es lo que te permite leer cualquier proyecto de firmware y saber dónde mirar.

Vale la pena ver la diferencia de niveles con el mismo objetivo —prender un LED— escrito en cada capa.

// ── PAC: registros crudos. Sabés exactamente qué bit tocás y por qué.
let dp = stm32f4::stm32f401::Peripherals::take().unwrap();
dp.RCC.ahb1enr.modify(|_, w| w.gpiocen().set_bit());     // clock del puerto C

// ── HAL: la misma operación, con el ownership haciendo de sistema de tipos
use stm32f4xx_hal::{pac, prelude::*};

💡 El truco de tipos que hace segura la capa HAL. gpioc.pc13.into_push_pull_output() consume el pin y devuelve un tipo distinto: PC13<Output<PushPull>>. El pin original ya no existe, así que es literalmente imposible configurar el mismo pin dos veces de dos formas distintas desde dos módulos, o llamar a set_high() sobre un pin que quedó como entrada. En C eso es un bug clásico de firmware que se manifiesta como un periférico que "a veces no anda". Acá es un error de compilación, y no se paga nada en runtime: todos esos tipos desaparecen en la compilación. Es el mismo typestate que viste en RuS2, aplicado a hardware.

embedded-hal: por qué un driver es portable

Acá está el aporte arquitectónico más importante del ecosistema. Si escribís el driver de un sensor contra los traits de embedded-hal en vez de contra un HAL concreto, ese driver funciona en cualquier micro que tenga un HAL —STM32, nRF, RP2040, ESP32— sin cambiar una línea:

use embedded_hal::i2c::I2c;
use embedded_hal::delay::DelayNs;

pub struct Sht31<I2C> {
    i2c: I2C,
    dir: u8,
}

impl<I2C: I2c> Sht31<I2C> {
    pub fn new(i2c: I2C) -> Self {
        Self { i2c, dir: 0x44 }
    }

    pub fn medir<D: DelayNs>(&mut self, delay: &mut D)
        -> Result<(f32, f32), I2C::Error>
    {
        self.i2c.write(self.dir, &[0x24, 0x00])?;   // medición de alta repetibilidad
        delay.delay_ms(15);                          // el sensor necesita este tiempo

        let mut buf = [0u8; 6];
        self.i2c.read(self.dir, &mut buf)?;

        let t_raw = u16::from_be_bytes([buf[0], buf[1]]);
        let h_raw = u16::from_be_bytes([buf[3], buf[4]]);

        let temp = -45.0 + 175.0 * (t_raw as f32) / 65535.0;
        let hum  = 100.0 * (h_raw as f32) / 65535.0;
        Ok((temp, hum))
    }
}

Ese impl<I2C: I2c> es todo. El driver no sabe en qué placa corre y no le importa. El usuario le pasa el bus I2C que le dio su HAL:

// en una placa STM32
let i2c = dp.I2C1.i2c((scl, sda), 100.kHz(), &clocks);
let mut sensor = Sht31::new(i2c);

// en un ESP32-C3, el MISMO driver
let i2c = esp_hal::i2c::master::I2c::new(peripherals.I2C0, config)?
    .with_sda(peripherals.GPIO4)
    .with_scl(peripherals.GPIO5);
let mut sensor = Sht31::new(i2c);
📌 Esto es lo que en C no existe. En C, un driver de sensor se escribe contra el SDK del fabricante, o contra punteros a función que vos tenés que cablear a mano en cada proyecto. Portarlo es reescribir la capa de acceso. En Rust, embedded-hal convirtió eso en genéricos con traits — y por eso hay cientos de drivers de sensores en crates.io que andan en cualquier micro sin tocarlos. Es la razón principal por la que el ecosistema embebido de Rust creció tan rápido.

RuS8.8 Sin sistema operativo: #[entry], panics e interrupciones

Sin std no hay fn main en el sentido habitual, porque no hay runtime de C que llame a main después de inicializar el proceso. El programa mínimo se ve así:

#![no_std]
#![no_main]

use cortex_m_rt::entry;
use panic_halt as _;              // define el manejador de panic (frena y listo)

#[entry]
fn main() -> ! {                  // ← nunca retorna: no hay a dónde volver
    let mut contador: u32 = 0;
    loop {
        contador = contador.wrapping_add(1);
        cortex_m::asm::nop();
    }
}

Tres cosas ahí valen una explicación. El tipo de retorno ! ("never") dice que la función no termina nunca, y el compilador lo verifica: si el loop tuviera un break, no compila. Es correcto, porque si el firmware "terminara" el procesador se quedaría ejecutando lo que hubiera en la memoria siguiente. El #[entry] de cortex-m-rt pone la dirección de esa función en la tabla de vectores, en la posición del reset handler, e inserta el código de arranque que inicializa .data y pone .bss en cero. Y el use panic_halt as _ —importado solo por su efecto— aporta el manejador de panic, que en no_std tenés que proveer vos:

// las alternativas más usadas, elegís UNA
use panic_halt as _;      // loop {} — el dispositivo se congela
use panic_reset as _;     // reinicia el micro: lo típico en producción
use panic_probe as _;     // imprime el panic por RTT al debugger: para desarrollo

// o el tuyo, si querés registrar la causa antes de reiniciar
#[panic_handler]
fn panic(info: &core::panic::PanicInfo) -> ! {
    guardar_en_flash(info);       // para poder leerlo en el próximo arranque
    cortex_m::peripheral::SCB::sys_reset()
}

El problema difícil: compartir estado con una interrupción

Acá es donde el modelo de Rust se cruza de frente con la realidad del hardware. Una interrupción (ISR) es una función que el hardware invoca en cualquier momento, interrumpiendo lo que sea que estuviera corriendo. Si la ISR y el main tocan el mismo dato, tenés una carrera. Rust no te deja escribir eso sin decir cómo lo estás resolviendo: no podés simplemente poner un static mut y tocarlo desde los dos lados.

use core::cell::RefCell;
use critical_section::Mutex;

// el dato compartido: Mutex de critical-section + RefCell adentro
static CONTADOR: Mutex<RefCell<u32>> = Mutex::new(RefCell::new(0));

#[interrupt]
fn TIM2() {
    critical_section::with(|cs| {
        let mut c = CONTADOR.borrow_ref_mut(cs);
        *c += 1;
    });
    limpiar_flag_timer();
}

#[entry]
fn main() -> ! {
    loop {
        let valor = critical_section::with(|cs| *CONTADOR.borrow_ref(cs));
        if valor % 100 == 0 {
            hacer_algo(valor);
        }
    }
}
💡 Por qué ese Mutex no es el de std. El Mutex de std duerme al thread si el candado está tomado. En un micro no hay threads y una ISR no puede dormir: si la ISR se bloquea esperando un candado que tiene el main, y el main no puede avanzar porque la ISR lo está interrumpiendo, el sistema se cuelga para siempre. Por eso critical_section::Mutex no bloquea: deshabilita las interrupciones mientras dura la sección. El token cs que recibe el closure es una prueba en el sistema de tipos de que las interrupciones están apagadas, y sin ese token no hay forma de acceder al dato. Es imposible olvidarse de tomar la sección crítica, porque el código no compilaría.
El costo de eso es real: mientras la sección crítica está abierta, ninguna interrupción se atiende. Una sección crítica larga aumenta la latencia máxima de todo el sistema y puede hacerte perder eventos. La regla es entrar, copiar o modificar el mínimo, y salir. Nada de I/O ni de cálculos adentro. Esta clase de razonamiento —quién puede interrumpir a quién, y por cuánto tiempo— es el trabajo intelectual central del firmware clásico, y es exactamente lo que Embassy viene a simplificar.

RuS8.9 Embassy: async sin sistema operativo ni allocator

Acá se cierra el círculo del track. En RuS3 viste que un async fn compila a una máquina de estados que implementa Future, y que .await es un punto donde esa máquina de estados se suspende y devuelve el control. En RuS4 viste un ejecutor (Tokio) que las agenda sobre un pool de threads. La pregunta que casi nadie se hace al estudiar eso es: ¿el modelo necesita threads?

No los necesita. Un Future es un struct con un poll. El ejecutor es un bucle que decide a cuál llamarle. Nada de eso requiere sistema operativo, ni threads, ni asignación dinámica de memoria. Y resulta que la semántica de "esperar sin bloquear" describe con una precisión asombrosa lo que hace un microcontrolador: esperar a que un periférico termine.

La coincidencia feliz. Un firmware pasa casi todo su tiempo esperando: que el ADC termine la conversión, que el UART termine de mandar el byte, que pasen 30 segundos, que el usuario apriete el botón. El patrón clásico es o bien un busy-wait (que quema batería) o bien una interrupción por cada evento más una máquina de estados a mano que reconstruya en qué punto del procedimiento estabas. Esa máquina de estados escrita a mano es exactamente lo que async genera automáticamente. Embassy hace que la ISR sea, simplemente, lo que despierta al future.

Embassy 0.6 es el runtime async para microcontroladores, y hoy es el punto de partida por defecto de casi cualquier proyecto nuevo. Sus tareas se asignan estáticamente en tiempo de compilación —cada #[embassy_executor::task] reserva su propio espacio, con tamaño conocido— así que no hay heap y no hay allocator.

#![no_std]
#![no_main]

use embassy_executor::Spawner;
use embassy_time::{Duration, Timer};
use embassy_stm32::gpio::{Level, Output, Speed, AnyPin};
use {defmt_rtt as _, panic_probe as _};

#[embassy_executor::task]
async fn parpadeo(pin: AnyPin, periodo: Duration) {
    let mut led = Output::new(pin, Level::Low, Speed::Low);
    loop {
        led.toggle();
        Timer::after(periodo).await;     // ← acá el micro se DUERME
    }
}

#[embassy_executor::task]
async fn leer_sensor(mut i2c: I2c<'static>) {
    let mut sensor = Sht31::new(i2c);
    loop {
        if let Ok((t, h)) = sensor.medir_async().await {
            defmt::info!("t={=f32} h={=f32}", t, h);
        }
        Timer::after(Duration::from_secs(30)).await;
    }
}

#[embassy_executor::main]
async fn main(spawner: Spawner) {
    let p = embassy_stm32::init(Default::default());

    spawner.spawn(parpadeo(p.PC13.degrade(), Duration::from_millis(500))).unwrap();
    spawner.spawn(leer_sensor(construir_i2c(p.I2C1))).unwrap();
}

Eso son dos actividades concurrentes, cada una escrita como un procedimiento lineal y legible, sin una sola máquina de estados a mano, sin una sola sección crítica escrita por vos, y sin heap. Comparalo con lo que hace falta para lo mismo en el modelo clásico: un timer configurado, dos contadores en static, una ISR que los decrementa, dos Mutex de critical-section, y un loop en main que revisa flags.

Lo que hace Timer::after(...).await

Esta es la parte que importa para el consumo, y conviene entenderla con precisión. Cuando ninguna tarea tiene trabajo, el ejecutor de Embassy no hace busy polling: ejecuta wfi (wait for interrupt), que deja al núcleo dormido hasta que llegue una interrupción. El driver de embassy-time programó de antemano un timer de hardware para que dispare en el instante del próximo Timer pendiente. El micro duerme, el timer dispara, la ISR marca el future como listo, el ejecutor lo vuelve a pollear.

// esto NO es lo mismo, aunque el efecto visible parezca igual:
delay.delay_ms(30_000);              // busy-wait: el núcleo ejecuta NOPs 30 s a full
Timer::after_secs(30).await;         // el núcleo duerme 30 s en wfi
📌 En un dispositivo a batería, esa línea es la diferencia entre un día y una semana. Un Cortex-M4 haciendo busy-wait consume del orden de 10–20 mA. En wfi, del orden de 1–2 mA. Y la belleza del asunto es que no tuviste que hacer nada para conseguirlo: el ahorro sale gratis de escribir .await en vez de delay. El modelo async, que en el servidor optimiza throughput, en un micro optimiza energía. Es el mismo mecanismo con otro beneficio.

Embassy además trae primitivas de sincronización pensadas para esto: Channel (una cola async con capacidad fija), Signal (el último valor, sin cola), Mutex async y select, que espera al primero de varios futures:

use embassy_sync::{blocking_mutex::raw::ThreadModeRawMutex, channel::Channel};
use embassy_futures::select::{select, Either};

static MUESTRAS: Channel<ThreadModeRawMutex, Muestra, 8> = Channel::new();

#[embassy_executor::task]
async fn productor(mut sensor: Sensor) {
    loop {
        let m = sensor.leer().await;
        MUESTRAS.send(m).await;                  // espera si la cola está llena
        Timer::after_secs(30).await;
    }
}

#[embassy_executor::task]
async fn transmisor(mut radio: Radio) {
    loop {
        let m = MUESTRAS.receive().await;

        // lo que sea que termine primero: el envío o el timeout
        match select(radio.enviar(&m), Timer::after_secs(5)).await {
            Either::First(Ok(())) => defmt::info!("enviado"),
            Either::First(Err(e)) => defmt::warn!("error de radio: {}", e),
            Either::Second(_)     => defmt::warn!("timeout de envío"),
        }
    }
}

Ese select con timeout es, en el modelo clásico, un timer extra, otro flag y otra rama en la máquina de estados. Acá son tres líneas.

RuS8.10 esp-rs y la elección de placa: RISC-V vs Xtensa

Espressif adoptó Rust como SDK oficial de primer nivel: esp-rs no es un port comunitario, es un equipo pago del fabricante manteniendo esp-hal, esp-wifi, esp-idf-hal y la integración con Embassy. Para un ecosistema donde durante años Rust fue tolerado en el mejor de los casos, es un cambio grande, y es la razón por la que hoy la placa más recomendable para empezar con Rust embebido es un ESP32 — con una advertencia que decide qué modelo comprás.

La decisión que hay que tomar ANTES de comprar la placa. Espressif fabrica chips con dos arquitecturas distintas, y en Rust no se tratan igual:
  • RISC-V (ESP32-C3, C6, H2, P4): compila con el Rust upstream. Un rustup target add y listo. El toolchain es el mismo que usás para todo lo demás, se actualiza con rustup update y funciona en CI sin trámite.
  • Xtensa (ESP32 original, ESP32-S2, S3): Xtensa no está en LLVM upstream, así que necesita un fork de LLVM y un toolchain aparte que se instala con espup. Funciona bien, pero es una cadena de herramientas paralela: se actualiza aparte, va atrás de las versiones de Rust, y complica el CI y los contenedores de build.
# ── RISC-V (ESP32-C3/C6/H2/P4): toolchain estándar, sin nada especial
rustup target add riscv32imc-unknown-none-elf      # C3
rustup target add riscv32imac-unknown-none-elf     # C6 / H2
cargo build --release --target riscv32imc-unknown-none-elf

# ── Xtensa (ESP32 / S2 / S3): toolchain forkeado
cargo install espup
espup install
. ~/export-esp.sh          # exporta el toolchain "esp" en cada shell
cargo +esp build --release --target xtensa-esp32s3-none-elf
📌 La recomendación práctica. Si estás empezando, o si vas a montar CI, comprá RISC-V. Un ESP32-C3 cuesta unos pocos dólares, trae WiFi y BLE, y compila con el toolchain que ya tenés. Un ESP32-C6 agrega Thread/Zigbee y WiFi 6. Elegí Xtensa solo si necesitás algo específico del S3 —dos núcleos, PSRAM grande, aceleración para inferencia— y sabé de antemano que estás firmando por un toolchain paralelo.

Si venís del mundo ESP-IDF y querés migrar de a poco, esp-idf-hal es el puente. Para un proyecto nuevo pensado para bajo consumo, esp-hal + Embassy es el camino.

RuS8.11 probe-rs y defmt: flashear, debuggear y loguear

Durante veinte años, debuggear un micro con herramientas libres significó OpenOCD: un archivo de configuración por placa, GDB por arriba, y una experiencia que espantaba a cualquiera que viniera de otro lado. probe-rs reemplazó eso en la práctica dentro del mundo Rust. Es una implementación nativa en Rust del protocolo de debug (CMSIS-DAP, J-Link, ST-Link), con soporte para cientos de chips y —esto es lo que cambia el día a día— integración directa con cargo run.

cargo install probe-rs-tools

probe-rs list                                  # ¿ve la sonda?
probe-rs info --chip esp32c3                   # ¿ve el chip?

probe-rs run --chip STM32F401RETx target/thumbv7em-none-eabihf/release/firmware
probe-rs attach --chip esp32c3 ...             # conectarse sin reflashear
# .cargo/config.toml — para que "cargo run" flashee y corra en la placa
[target.thumbv7em-none-eabihf]
runner = "probe-rs run --chip STM32F401RETx"

[build]
target = "thumbv7em-none-eabihf"

[target.'cfg(all())']
rustflags = [
  "-C", "link-arg=-Tlink.x",       # el linker script de cortex-m-rt
  "-C", "link-arg=-Tdefmt.x",      # las tablas de defmt
]

Con eso, cargo run --release compila, flashea, resetea el chip y te deja la salida de log en la terminal. El ciclo de desarrollo pasa a ser el mismo que en un proyecto de escritorio.

defmt: logging que casi no ocupa flash

Loguear en un micro tiene un problema que en el servidor no existe: el texto pesa. Cada cadena de formato de un println! es bytes de flash, y el código de formateo de core::fmt puede sumar varios KB. En un chip con 128 KB de flash, un logging generoso se come una fracción notable del presupuesto.

defmt (deferred formatting) resuelve eso con una idea elegante: las cadenas no van al dispositivo. Quedan en una tabla dentro del binario ELF, que se queda en tu máquina; el dispositivo transmite un índice más los argumentos en binario, y el host reconstruye el mensaje leyendo la tabla del mismo ELF que flasheó.

use defmt::{info, warn, error, Format};

#[derive(Format)]                       // como Debug, pero para defmt
struct Muestra { temp: f32, hum: f32, bateria_mv: u16 }

info!("arrancando, versión {=str}", env!("CARGO_PKG_VERSION"));
info!("muestra: {}", muestra);                       // usa el derive Format
warn!("batería baja: {=u16} mV", bateria_mv);
error!("i2c falló en 0x{=u8:x}", direccion);
# el nivel se decide EN COMPILACIÓN: lo que no pasa el filtro no ocupa un solo byte
DEFMT_LOG=info cargo run --release
DEFMT_LOG=trace cargo run                    # desarrollo
DEFMT_LOG=off   cargo build --release        # producción: cero costo, cero flash
La comparación típica: una línea de log con dos valores cuesta del orden de 4–8 bytes transmitidos con defmt, contra 30–60 bytes de texto y varios KB de código de formateo con println!. En un enlace RTT eso significa que podés loguear en un bucle rápido sin alterar el timing del sistema — que es la trampa clásica del debugging por printf en firmware: el log es tan lento que el bug desaparece cuando lo instrumentás.

RuS8.12 Restricciones reales del embebido

Todo lo anterior puede dar la impresión de que el embebido en Rust es cómodo. Lo es, comparado con lo que era. Pero hay restricciones que no desaparecen y que conviene tener presentes antes de empezar un proyecto.

Tamaño del binario

El flash es un presupuesto duro y fijo. Se mide y se vigila:

cargo install cargo-binutils cargo-bloat
rustup component add llvm-tools-preview

cargo size --release -- -A                 # secciones: .text, .rodata, .data, .bss
cargo bloat --release -n 20                # las 20 funciones más grandes
cargo bloat --release --crates             # qué crate ocupa cuánto
Los tres culpables habituales cuando un binario embebido se va de tamaño: (1) el código de formateo de core::fmt, que entra por un write! o un unwrap() con mensaje —por eso defmt—; (2) las monomorfizaciones de RuS7: una función genérica instanciada con quince tipos son quince copias en el flash; (3) matemática de punto flotante en un micro sin FPU, donde cada operación se convierte en una llamada a una rutina de software. opt-level = "s" o "z" optimizan por tamaño en lugar de por velocidad, y en embebido suele ser lo que querés.

panic = "abort" y qué significa un panic acá

En embebido, panic = "abort" no es una opción: es obligatorio, porque el unwinding necesita tablas de excepciones que no tienen sentido sin sistema operativo. La consecuencia de diseño es que un panic es una caída total del dispositivo, y eso cambia cómo escribís el código: unwrap() y expect() son aceptables durante la inicialización —si el hardware no está donde debe, no hay nada que hacer— y son inaceptables en el bucle principal.

[profile.release]
panic = "abort"
opt-level = "s"
lto = "fat"
codegen-units = 1
overflow-checks = true   # ojo: en release está APAGADO por defecto
Ese overflow-checks = true merece un párrafo. En release, Rust desactiva la verificación de desbordamiento por defecto, y un u8 que pasa de 255 vuelve a 0 en silencio. En un servidor eso es un bug feo; en un dispositivo que controla un motor o una válvula puede ser un problema de seguridad física. Si el costo de rendimiento te lo permite —y en un firmware que espera el 99% del tiempo, te lo permite—, dejalo prendido. Si no, usá checked_add, saturating_add o wrapping_add de forma explícita, para que quede escrito cuál de los tres comportamientos querías.

No hay std::time

Instant::now() y SystemTime no existen: no hay reloj de sistema, ni epoch, ni nadie que sincronice nada. El tiempo lo da un timer de hardware, y lo que tenés es tiempo transcurrido desde el arranque, no fecha y hora. Si necesitás una marca temporal real hay que traerla de afuera (NTP por red, o un RTC con su propia pila).

use embassy_time::{Instant, Duration, Timer};

let t0 = Instant::now();                       // desde el boot, no desde 1970
hacer_algo().await;
let transcurrido: Duration = t0.elapsed();
defmt::info!("tardó {=u64} ms", transcurrido.as_millis());
El resto de las cosas que no están: no hay HashMap (usá heapless::FnvIndexMap o BTreeMap con alloc), no hay std::error::Error (por eso thiserror tiene un modo no_std y anyhow directamente no aplica), no hay variables de entorno, no hay filesystem, no hay Box<dyn Trait> sin alloc, y la mayoría de los crates que usás a diario tampoco están. Buscá siempre el badge no_std en crates.io o la feature default-features = false.

Dónde sigue esto: el hardware

Este módulo cubre el software del embebido: no_std, la pila de crates, el runtime, el toolchain. Lo que deliberadamente no cubre es el otro 50% del oficio: cómo se lee un datasheet, qué es realmente un bus I2C o SPI en el osciloscopio, por qué necesitás una resistencia de pull-up, cómo se mide el consumo de verdad, y qué hace un regulador de tensión. Todo eso está en el curso de Computación Física, que es el complemento natural de esta parte. El firmware más elegante del mundo no arranca si el circuito está mal, y la mayoría de las horas perdidas en un proyecto embebido son de hardware, no de código.

🧑‍🎓 Worked Example — un sensor que tiene que durar meses con batería

Requisito: un sensor de temperatura y humedad reporta por WiFi cada 30 segundos a un servidor. Va adentro de una cámara frigorífica, alimentado con una batería de 2000 mAh, y no se puede abrir para cambiarla en al menos tres meses. Hardware: ESP32-C3 + SHT31 por I2C. ¿Super-loop o Embassy? ¿Alcanza con eso?

Paso 1 — Traducir el requisito a una cifra. Antes que cualquier decisión de arquitectura, la restricción hay que convertirla en un número, porque es el número el que decide:

# 3 meses = 2160 horas. Con 2000 mAh y un 20% de margen por temperatura y envejecimiento:
# corriente media máxima = (2000 mAh * 0.8) / 2160 h = 0.74 mA
#
# PRESUPUESTO: 0,74 mA de consumo MEDIO. Todo lo que sigue se mide contra eso.
📌 Este paso es el que más se saltea y el que más caro sale. "Que dure meses" no es un requisito: es un deseo. 0,74 mA promedio sí es un requisito, porque se puede medir con un instrumento y porque descarta arquitecturas enteras de un plumazo. Sin este número, la discusión "super-loop vs Embassy" es una cuestión de opinión.

Paso 2 — La versión ingenua, para tener la línea de base. Así se escribe casi siempre la primera vez, y es la que hay que descartar con datos:

// SUPER-LOOP: correcto, legible... y come batería como si estuviera enchufado
#[entry]
fn main() -> ! {
    let (mut i2c, mut wifi, mut delay) = init();
    wifi.conectar(SSID, PASS).unwrap();       // se conecta una vez y queda asociado

    loop {
        let (t, h) = sht31_leer(&mut i2c, &mut delay).unwrap();
        wifi.post("http://servidor/m", &formatear(t, h)).ok();
        delay.delay_ms(30_000);               // ← 30 segundos ejecutando NOPs
    }
}

Dos cosas están mal, y ninguna es evidente leyendo el código. La primera: ese delay_ms es un busy-wait — el núcleo ejecuta instrucciones a máxima frecuencia durante 30 segundos para no hacer nada. La segunda, más cara todavía: el WiFi queda asociado permanentemente, y una radio asociada consume decenas de miliamperes de forma continua, aunque no transmita.

Paso 3 — La versión con Embassy y deep sleep. La estructura importante es que el dispositivo no está vivo entre lecturas: se apaga casi por completo y el RTC lo despierta:

#![no_std]
#![no_main]

use embassy_executor::Spawner;
use embassy_time::{Duration, Timer};
use esp_hal::rtc_cntl::{Rtc, sleep::TimerWakeupSource};
use {esp_backtrace as _, defmt_rtt as _};

// sobrevive al deep sleep: esta RAM no se apaga
#[unsafe(link_section = ".rtc.data")]
static mut BUFFER: [Muestra; 10] = [Muestra::VACIA; 10];
#[unsafe(link_section = ".rtc.data")]
static mut CUANTAS: usize = 0;

#[esp_hal_embassy::main]
async fn main(_spawner: Spawner) -> ! {
    let p = esp_hal::init(esp_hal::Config::default());
    let mut rtc = Rtc::new(p.LPWR);

    // 1. despertar, leer el sensor: ~150 ms, sin radio
    let mut sensor = Sht31::new(construir_i2c(p.I2C0, p.GPIO4, p.GPIO5));
    let muestra = sensor.medir_async().await.unwrap_or(Muestra::VACIA);

    let n = unsafe {
        BUFFER[CUANTAS] = muestra;
        CUANTAS += 1;
        CUANTAS
    };

    // 2. transmitir solo cada 10 muestras (= cada 5 minutos)
    if n >= 10 {
        transmitir_lote(p.WIFI, unsafe { &BUFFER }).await.ok();
        unsafe { CUANTAS = 0 };
    }

    // 3. dormir hasta la próxima lectura. No es un await: el chip se APAGA.
    let despertador = TimerWakeupSource::new(core::time::Duration::from_secs(30));
    rtc.sleep_deep(&[&despertador]);
}

async fn transmitir_lote(wifi: WIFI, buf: &[Muestra; 10]) -> Result<(), Error> {
    let mut stack = conectar_wifi(wifi).await?;      // ~600 ms con IP estática

    // sin timeout, un AP caído deja la radio prendida hasta agotar la batería
    match select(enviar(&mut stack, buf), Timer::after_secs(3)).await {
        Either::First(r) => r,
        Either::Second(_) => Err(Error::Timeout),    // cortamos y a dormir igual
    }
}

Paso 4 — Los números, que son los que deciden. Con corrientes típicas de un ESP32-C3 (~10 µA en deep sleep, ~25 mA despierto sin radio, ~140 mA promedio con WiFi transmitiendo):

#EstrategiaCorriente mediaAutonomía (2000 mAh)¿Cumple 0,74 mA?

La cuenta de la fila E, para que se pueda auditar: cada 30 s el chip despierta 150 ms a 25 mA (3,75 mA·s); una de cada diez veces suma 0,8 s de radio a 140 mA (112 mA·s); el resto del tiempo duerme a 10 µA. Por ventana de 5 minutos: 10 × 3,75 + 112 + 3 ≈ 152 mA·s, dividido 300 s da 0,51 mA promedio.

💡 Leé la tabla dos veces, porque dice dos cosas distintas. La primera es la esperable: Embassy le gana al super-loop 4× de entrada (fila A a B) sin que hayas hecho ningún esfuerzo de optimización — solo por escribir .await en vez de delay, que pone al núcleo en wfi. La segunda es la incómoda: ese 4× no alcanza ni de cerca. Lo que realmente cierra el presupuesto es el duty cycling (dormir de verdad, no esperar) y el batching (desacoplar la frecuencia de medición de la de transmisión). El pico de consumo que importa no es el CPU: es la radio, y el gasto grande está en asociarse a la red, no en mandar los datos.

Paso 5 — Entonces, ¿por qué Embassy, si lo que salvó el proyecto fue el batching? Porque el batching y el deep sleep también se pueden hacer en un super-loop, pero mirá qué forma tiene la lógica en cada modelo:

📌 La conclusión del ejercicio, que es la del módulo entero. Embassy no gana porque sea "más moderno": gana porque convierte en tres líneas legibles la estructura que de verdad ahorra energía, y esa estructura —dormir agresivamente, medir y transmitir a ritmos distintos, cortar por timeout— es la que en el modelo clásico se escribe como una máquina de estados de doscientas líneas que nadie quiere tocar. El ahorro directo del wfi es un 4×. El ahorro real, el 100×, viene de una arquitectura que solo se sostiene en el tiempo si es fácil de leer. Y nada de esto reemplaza medirlo: conectá un medidor de corriente antes de creerle a esta tabla, incluida la mía.

Checkpoint — ¿lo tenés claro?

¿Por qué thiserror en librerías y anyhow en binarios, si los dos "manejan errores"?

Porque cambia quién consume el error. El código que usa tu librería necesita decidir distinto según el caso: reintentar si el token expiró, abortar si el JSON está roto. Eso exige un tipo cerrado que se pueda inspeccionar con match, y thiserror genera ese enum con sus Display y sus From. En cambio, en el main de un servicio el error termina en un log que lee una persona: no hace falta un tipo, hace falta contexto acumulado, y anyhow lo da con .context() a un costo de escritura casi nulo. La excepción es la capa de handlers HTTP, donde el binario sí necesita hacer match para elegir el status code — ahí volvés a un enum, con una variante Interno(#[from] anyhow::Error) de cajón de sastre.

Estás en no_std y necesitás juntar hasta 32 lecturas. ¿Qué usás y por qué no Vec?

heapless::Vec<u16, 32>. Vec vive en alloc, que necesita un allocator global que en un micro tenés que proveer vos — y hacerlo tiene un costo que no es solo de código: sin MMU, la fragmentación es permanente y un dispositivo que asigna y libera durante semanas puede terminar fallando una asignación aunque le sobre memoria; además el tiempo de asignación no es determinista. heapless::Vec tiene la capacidad en el tipo, vive en el stack o en un static, y su push devuelve Result, lo que te obliga a escribir ahora qué pasa cuando el buffer se llena. Eso no es una molestia: es la política de desbordamiento explícita, en lugar de descubrirla en campo a las tres de la mañana.

Un compañero dice: "Embassy es async, o sea que es más lento que un super-loop, que corre directo sobre el hardware". ¿Qué le contestás?

Que confunde async con "runtime pesado". Las tareas de Embassy se asignan estáticamente en tiempo de compilación: no hay heap, no hay allocator y no hay un stack por tarea como en un RTOS — cada tarea ocupa solo el tamaño de su máquina de estados, decenas de bytes. El ejecutor es un bucle que llama a poll; cuando ninguna tarea está lista ejecuta wfi y el núcleo duerme, mientras que un super-loop con delay_ms ejecuta NOPs a máxima frecuencia. O sea que en un dispositivo a batería, async no es que sea "casi tan bueno": es varias veces mejor, y sin que tengas que hacer nada. La limitación real de Embassy es otra y sí hay que decirla: el ejecutor es cooperativo, así que una tarea que calcula 200 ms sin ceder bloquea a todas las demás. Si tenés tiempo real duro sobre una tarea larga, eso va en una interrupción o Embassy no es la herramienta.

Resumen ejecutivo

  • Errores: thiserror en librerías (tipo cerrado, inspeccionable con match), anyhow en binarios (contexto encadenado con .context()). Se combinan sin fricción; en handlers HTTP volvés a un enum para mapear status codes, y nunca devolvés el Display de un error interno al cliente.
  • Observabilidad: tracing, no log. En async el thread ID no significa nada; los spans viajan con la tarea y sobreviven a los .await. #[instrument], salida JSON en producción, EnvFilter por RUST_LOG, y OpenTelemetry como una capa más del registry.
  • Secretos: SecretString de secrecy no cifra nada — convierte una fuga accidental por Debug en una llamada explícita a expose_secret() que se ve en el code review. El resto, en el M07 de Ciberseguridad.
  • Deploy: musl para binario estático, FROM scratch o distroless para imágenes de 8–20 MB sin shell. Ojo con los certificados raíz, el USER numérico y las zonas horarias. panic = "abort" es peligroso del lado servidor y obligatorio del lado embebido.
  • Supply chain: en Rust el árbol crece rápido (250+ deps es normal). cargo audit y cargo deny en CI, deny.toml versionado, Cargo.lock siempre commiteado. build.rs y las macros procedurales ejecutan código en tu CI antes de cualquier test: esa es la parte que ninguna herramienta te resuelve.
  • no_std: se van heap, Vec/String, threads, I/O, std::time y HashMap. Queda core con todo lo que hace a Rust: ownership, traits, genéricos, Result, iteradores. alloc es el término medio, con un allocator propio y el costo de la fragmentación.
  • Arquitectura: PAC → HAL → BSP, con embedded-hal como el contrato transversal. Un driver escrito contra esos traits corre sin cambios en STM32, nRF, RP2040 o ESP32 — eso es lo que en C no existe.
  • Embassy 0.6 es el runtime async de facto en microcontroladores: tareas asignadas estáticamente, sin heap, y wfi por defecto cuando nada está listo. Su límite es que el ejecutor es cooperativo.
  • Placa: esp-rs es SDK oficial de Espressif. RISC-V (C3, C6, H2, P4) compila con Rust upstream; Xtensa (ESP32, S2, S3) necesita un LLVM forkeado vía espup. Para empezar y para CI, RISC-V.
  • Herramientas: probe-rs reemplazó a OpenOCD y se integra con cargo run; defmt deja las cadenas en el host y transmite índices, así que loguear cuesta bytes en vez de kilobytes.
  • La lección del Worked Example: async da un 4× gratis, pero el 100× lo da la arquitectura (dormir de verdad + desacoplar medición de transmisión). Embassy gana porque hace que esa arquitectura sea fácil de escribir y de mantener. Y todo se mide antes de creerlo.

🧠 Autoevaluación

1. Vas a arrancar un proyecto de firmware en Rust y querés que el toolchain sea el estándar, sin instalaciones paralelas, para que ande en CI sin trámite. ¿Qué placa elegís?

La línea RISC-V (C3, C6, H2, P4) compila con el Rust de siempre: un rustup target add y listo. La línea Xtensa (ESP32 original, S2, S3) no está en LLVM upstream y necesita un fork de LLVM que se instala con espup: funciona bien, pero es una cadena de herramientas paralela que se actualiza aparte, va atrás de las versiones de Rust y complica CI y contenedores de build. Que esp-rs sea SDK oficial de Espressif no borra esa diferencia de arquitectura. Elegí Xtensa solo si necesitás algo específico del S3, sabiendo lo que estás firmando.

2. Tu dispositivo a batería duerme con Timer::after_secs(30).await en vez de delay.delay_ms(30_000), y ganaste ~4× de autonomía. Necesitás 100×. ¿Dónde está el resto?

El .await pone al núcleo en wfi y eso es el 4×, gratis. Pero el consumo dominante no es el CPU: es la radio, y el gasto grande está en asociarse a la red, no en mandar los bytes. Los dos cambios que mueven la aguja son deep sleep (apagar el chip entre lecturas, no solo dejarlo idle) y batching (leer cada 30 s pero transmitir cada 5 minutos, guardando en RTC RAM). Bajar el reloj y optimizar por tamaño ayudan en los márgenes; cambiar de runtime no toca el problema, porque el problema es de arquitectura, no de scheduler.

3. Publicás una librería que habla con una API HTTP. Un usuario se queja de que no puede distinguir un token expirado (que conviene reintentar) de un JSON malformado (que no). ¿Qué hiciste mal?

Esa es exactamente la línea que separa los dos crates. anyhow::Error es un contenedor opaco: sirve cuando el consumidor es un humano leyendo un log, y por eso va en binarios. Desde una librería, el consumidor es otro código que necesita decidir distinto según el caso, y eso requiere un tipo cerrado que se pueda inspeccionar con match — un enum de thiserror con variantes TokenExpirado y Deserializacion. Parsear el mensaje de Display es un contrato frágil que se rompe el día que alguien mejora la redacción del error, y agregar contexto no arregla nada porque el problema no es la falta de información: es que no hay nada sobre lo que ramificar.

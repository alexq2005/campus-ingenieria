RuS7 — Performance: medir el zero-cost

RuS7.0 Por qué este módulo

“Zero-cost abstractions” es la frase que más se repite sobre Rust y la que menos se verifica. La formulación original de Bjarne Stroustrup —que Rust heredó— dice dos cosas, y la segunda se olvida siempre: lo que no usás no lo pagás, y lo que sí usás no lo podrías haber escrito mejor a mano. Fijate que ninguna de las dos afirma “es gratis”. Afirman “no es peor que la versión manual”. Y eso es una hipótesis comprobable, no un axioma.

💡 La tesis del módulo. Un iterador de Rust normalmente compila al mismo código máquina que el bucle escrito a mano. Normalmente. Cuando no lo hace —y pasa— la única forma de enterarte es mirando. Este módulo es el equipamiento para mirar: perfiles de compilación, benchmarks estadísticos, flamegraphs, contadores de allocaciones y, cuando hace falta, el asm generado. Sin ese equipamiento, tus decisiones de rendimiento son folclore.

Y hay una razón práctica para tomarlo en serio: en Rust la mayoría de las discusiones de performance que ves en foros son falsas. No porque la gente mienta, sino porque midió mal. Midió en debug. Midió un for que el optimizador borró entero porque el resultado no se usaba. Midió con un cronómetro manual y una sola corrida. Comparó dos programas donde uno leía de la caché del sistema de archivos y el otro no. El 80% del trabajo de este módulo es no cometer esos errores; el 20% restante es saber qué hacer con un número honesto.

“Los programadores gastan enormes cantidades de tiempo pensando en la velocidad de partes no críticas de sus programas. Deberíamos olvidarnos de las pequeñas eficiencias el 97% del tiempo.” — Donald Knuth, 1974. La cita que todos truncan sigue: “...pero no deberíamos dejar pasar nuestras oportunidades en ese 3% crítico”. El módulo trata de encontrar ese 3%.

RuS7.1 Lo primero, y lo que más veces resuelve todo: --release

Antes que cualquier otra técnica de este módulo: si medís sin --release, tu número no significa nada. No es “un poco más lento”. Un build de desarrollo puede ser 10× a 100× más lento que uno optimizado, y el factor no es uniforme: castiga desproporcionadamente justo lo que Rust hace bien, porque las abstracciones (iteradores, Option, envoltorios de tipos, operadores de índice) son montones de funciones chiquitas que en debug no se inlinean.

# El error más común del planeta
cargo run                  # perfil dev:     opt-level = 0
cargo run --release        # perfil release: opt-level = 3

# Lo mismo para tests y benchmarks
cargo test --release
cargo bench                # bench ya usa el perfil `bench`, que hereda de release

El bug de medición clásico. Alguien escribe un micro-benchmark, lo corre con cargo run, ve que Rust “es más lento que Python” y publica. Cambiar a --release lo pone 60× más rápido. Antes de investigar cualquier anomalía de rendimiento, la primera pregunta —siempre— es: ¿esto está en release?

RuS7.2 Perfiles de compilación: qué gana cada opción y qué cuesta

release es un punto de partida razonable, no el techo. Los ajustes finos van en Cargo.toml y cada uno intercambia tiempo de build por tiempo de ejecución (o por tamaño del binario).

# Cargo.toml — perfil de release afinado para un binario de servidor
[profile.release]
opt-level     = 3          # 0,1,2,3 | "s" (size) | "z" (size, sin loop vectorization)
lto           = "fat"      # false | "thin" | "fat" (alias: true)
codegen-units = 1          # menos unidades = mejor optimización global
panic         = "abort"    # sin unwinding: binario más chico y algo más rápido
strip         = "symbols"  # saca símbolos del binario final
debug         = false

# Perfil derivado: release CON símbolos, exclusivo para perfilar
[profile.profiling]
inherits = "release"
debug    = true            # línea+función en el flamegraph
strip    = "none"

Ese [profile.profiling] es la pieza que más gente se pierde: perfilar el build de release sin símbolos te da un flamegraph lleno de direcciones hexadecimales. Un perfil heredado te da el mismo código máquina con nombres legibles.

[profile.dev.package."*"]

RuS7.3 Benchmarks: por qué el cronómetro a mano miente

El primer instinto es medir con Instant::now(). Ese instinto produce números que parecen datos y son ruido.

use std::time::Instant;

fn main() {
    let datos: Vec<u64> = (0..1_000_000).collect();
    let t0 = Instant::now();
    let suma: u64 = datos.iter().sum();
    println!("{:?} — {suma}", t0.elapsed());   // "42ns" 🤔
}

42 nanosegundos para sumar un millón de enteros son unos 200 terabytes por segundo. No pasó. Lo que pasó es que LLVM evaluó la suma en tiempo de compilación —los datos son una constante conocida— y dejó el resultado hardcodeado. Estás midiendo un println!.

Los cinco pecados del cronómetro manual:

1. El optimizador borra tu benchmark. Si el resultado no se usa, la operación se elimina; si la entrada es constante, se precalcula.
2. No hay warmup. La primera corrida paga fallos de caché de instrucciones, page faults del heap y, en CPUs modernas, frecuencias todavía bajas por gobernadores de energía.
3. Una sola muestra no tiene varianza. Sin distribución no sabés si la diferencia entre 1,20 ms y 1,25 ms es una mejora o el vecino de al lado moviendo el mouse.
4. La resolución del reloj. Medir algo de 40 ns con un reloj cuya llamada cuesta ~20 ns es medir el reloj.
5. No detectás regresiones. Un número suelto en la consola de hoy no se compara con el de hace tres semanas.

// benches/parseo.rs
use criterion::{criterion_group, criterion_main, Criterion, BenchmarkId};
use std::hint::black_box;

fn parsear(linea: &str) -> Option<u64> {
    linea.split(' ').nth(2)?.parse().ok()
}

fn bench_parseo(c: &mut Criterion) {
    let linea = "2026-09-03 INFO 4821 request completado";

    c.bench_function("parsear_linea", |b| {
        b.iter(|| parsear(black_box(linea)))
    });

    // Barrido de tamaños: ¿la función es O(n) o algo peor?
    let mut grupo = c.benchmark_group("parseo_lote");
    for n in [100usize, 1_000, 10_000, 100_000] {
        let lote: Vec<String> = (0..n).map(|i| format!("2026-09-03 INFO {i} ok")).collect();
        grupo.throughput(criterion::Throughput::Elements(n as u64));
        grupo.bench_with_input(BenchmarkId::from_parameter(n), &lote, |b, lote| {
            b.iter(|| {
                let mut acc = 0u64;
                for l in lote {
                    acc += parsear(black_box(l)).unwrap_or(0);
                }
                acc
            })
        });
    }
    grupo.finish();
}

black_box: la barrera que salva el experimento

std::hint::black_box (estable desde Rust 1.66; usalo en vez del re-export deprecado de criterion) es una función identidad que el compilador trata como opaca: no puede asumir nada sobre el valor que entra ni sobre el que sale, así que no puede constant-foldear ni eliminar el cálculo.

use std::hint::black_box;

// ❌ SIN black_box: el compilador ve que `n` es constante y que nadie usa el
//    resultado. La función entera se convierte en `ret`. Medís 0,4 ns.
fn mal(b: &mut criterion::Bencher) {
    b.iter(|| fibonacci(30));
}

// ✅ CON black_box en LOS DOS lados: la entrada es opaca (no se precalcula)
//    y el resultado se "consume" (no se elimina).
fn bien(b: &mut criterion::Bencher) {
    b.iter(|| black_box(fibonacci(black_box(30))));
}
El error de poner black_box solo afuera. black_box(fibonacci(30)) impide que se borre el resultado, pero no impide que LLVM calcule fibonacci(30) en tiempo de compilación y meta la constante. Necesitás la barrera en la entrada para que el argumento sea desconocido. Regla mnemotécnica: opaco lo que entra, opaco lo que sale.
black_box no es gratis ni preciso: es una pista, implementada con un bloque de ensamblador vacío que “toca” el valor. Puede forzar un valor a memoria que de otro modo viviría en un registro, lo que agrega unos nanosegundos. En funciones de microsegundos es irrelevante; en funciones de 2 ns, la barrera puede ser la mitad de lo que medís. Para esos casos, medí un lote (mil llamadas dentro del iter) y dividí.
💡 Alternativa moderna: divan es un harness de benchmarks más nuevo, con menos ceremonia (macros #[divan::bench] tipo #[test]) y medición de allocaciones incorporada. Criterion sigue siendo el estándar para regresiones en CI porque su análisis estadístico y sus baselines son más maduros. Los dos son mejores que Instant.

RuS7.4 Perfilado: encontrar el 3% que importa

El benchmark te dice cuánto tarda. El profiler te dice dónde. Nunca optimices sin haber mirado un perfil: la intuición sobre dónde se va el tiempo acierta, según cualquiera que haya hecho esto muchas veces, alrededor de un tercio de las veces.

samply — el más fácil, y multiplataforma

cargo install samply

# Compilá con símbolos (el perfil `profiling` de RuS7.2)
cargo build --profile profiling

# Grabá: abre el Firefox Profiler en el navegador con el resultado

# También podés adjuntarte a un proceso ya corriendo
samply record --pid 48213

Es un sampling profiler: interrumpe el proceso ~1000 veces por segundo y anota la pila de llamadas. No instrumenta nada, así que el overhead es de 1–3% y los números que ves son los del programa real, no los de una versión con sondas.

🔍 Cómo se lee un flamegraph. El ancho es tiempo: una caja que ocupa el 40% del ancho es el 40% de las muestras. La altura es profundidad de pila, no tiempo — una torre alta y finita es irrelevante. Los colores son aleatorios, no significan nada. Buscá mesetas anchas: una caja ancha cuyos hijos son angostos es una función que hace el trabajo ella misma; una caja ancha con un hijo igual de ancho es solo un intermediario. Y el eje X está ordenado alfabéticamente, no cronológicamente: no leas un flamegraph como una línea de tiempo.

RuS7.5 Allocaciones: el costo que casi nunca aparece en el código

En un programa de Rust bien escrito y bien perfilado, la causa número uno de lentitud no es el algoritmo: es que se pide memoria al sistema demasiadas veces. Una allocación cuesta entre 15 y 100 ns según el allocador y la fragmentación, no se vectoriza, no se paraleliza bien (el allocador global tiene sus propios locks) y ensucia la caché.

Vec::with_capacity: lo más barato que vas a hacer hoy

Un Vec que crece duplica su capacidad: para llegar a un millón de elementos hace ~20 reallocaciones y copia, en total, cerca de dos millones de elementos. Si sabés el tamaño, decilo.

// ❌ 20 reallocaciones + ~2M de elementos copiados
let mut v = Vec::new();
for i in 0..1_000_000 { v.push(i); }

// ✅ una allocación, cero copias
let mut v = Vec::with_capacity(1_000_000);
for i in 0..1_000_000 { v.push(i); }

// ✅✅ mejor todavía: el iterador conoce su tamaño (ExactSizeIterator)
//     y `collect` llama a with_capacity solo
let v: Vec<i32> = (0..1_000_000).collect();
Ese último caso es zero-cost real y verificable: collect consulta Iterator::size_hint, y para un Range el hint es exacto, así que reserva una vez. Con un filter en el medio el hint pasa a ser (0, Some(n)) y collect reserva el mínimo: ahí sí conviene Vec::with_capacity + extend si tenés una estimación mejor.

collect() intermedios: el desperdicio más común

// ❌ tres Vec completos en memoria, dos de ellos tirados enseguida
let r: Vec<String> = lineas
    .iter()
    .map(|l| l.trim().to_string())          // Vec<String> #1 — N allocaciones
    .collect::<Vec<_>>()
    .into_iter()
    .filter(|l| !l.is_empty())              // Vec<String> #2
    .collect::<Vec<_>>()
    .into_iter()
    .map(|l| l.to_uppercase())              // Vec<String> #3 — otras N allocaciones
    .collect();

// ✅ una sola pasada, una sola allocación de salida, cero intermedios
let r: Vec<String> = lineas
    .iter()
    .map(|l| l.trim())
    .filter(|l| !l.is_empty())
    .map(|l| l.to_uppercase())
    .collect();

Esta es la primera verificación empírica del zero-cost: la versión de abajo, con tres adaptadores encadenados, compila a un único bucle. Los adaptadores de iterador son structs sin estado extra cuyos next() se inlinean unos dentro de otros hasta desaparecer. La versión de arriba no puede fusionarse: cada collect es una barrera de materialización.

String vs &str es una decisión de rendimiento

Se enseña como una cuestión de ownership, y lo es, pero la consecuencia práctica es de allocaciones. String es dueño de un buffer en el heap: crearlo cuesta una allocación, clonarlo cuesta otra más una copia. &str es un puntero y un largo: 16 bytes en el stack, cero allocaciones.

// ❌ una allocación por línea, por campo: millones en un log grande
fn campos_lentos(linea: &str) -> Vec<String> {
    linea.split(' ').map(|s| s.to_string()).collect()
}

// ✅ cero allocaciones: los &str apuntan dentro de la línea original
fn campos_rapidos(linea: &str) -> Vec<&str> {
    linea.split(' ').collect()
}

// ✅✅ ni siquiera el Vec: si solo consumís, devolvé el iterador
fn campos_cero<'a>(linea: &'a str) -> impl Iterator<Item = &'a str> + 'a {
    linea.split(' ')
}

Cuando una función “a veces” necesita ser dueña, la respuesta no es String por las dudas: es Cow, que alloca solo en la rama que lo necesita.

use std::borrow::Cow;

/// Devuelve la línea sin comentario. Si no hay comentario (el caso frecuente),
/// no alloca nada: devuelve una vista de la entrada.
fn sin_comentario(l: &str) -> Cow<'_, str> {
    match l.find('#') {
        None    => Cow::Borrowed(l),
        Some(i) => Cow::Owned(l[..i].trim_end().to_owned()),
    }
}

Buffers reusados, SmallVec y arenas

use std::io::{self, BufRead, Write};

// Patrón "leer sin allocar por línea": un solo String reusado.
// `lines()` devuelve io::Result<String> y alloca UNA VEZ POR LÍNEA.
fn procesar<R: BufRead, W: Write>(mut e: R, mut s: W) -> io::Result<()> {
    let mut buf = String::with_capacity(256);
    loop {
        buf.clear();                       // conserva la capacidad, tira el contenido
        if e.read_line(&mut buf)? == 0 { break; }
        if let Some(campo) = buf.split(' ').nth(2) {
            writeln!(s, "{campo}")?;
        }
    }
    Ok(())
}
📌 clear() no libera: reusa. Vec::clear y String::clear dejan el largo en 0 pero mantienen la capacidad. Ese es el mecanismo del patrón de arriba: la allocación se paga una vez y las 20 millones de líneas siguientes escriben en el mismo buffer. Si querés devolver la memoria, shrink_to_fit.

}

RuS7.6 Verificar el zero-cost: mirar el asm

Acá está el corazón del módulo. La promesa dice que el iterador compila igual que el bucle a mano. Comprobémoslo en vez de creerlo.

Caso 2: donde el zero-cost NO se cumple

// El compilador NO puede vectorizar esto, aunque parezca idéntico al caso 1
#[inline(never)]
pub fn suma_f32(v: &[f32]) -> f32 {
    v.iter().sum()
}

La suma de f32 no es asociativa: (a+b)+c puede dar un resultado distinto de a+(b+c) por redondeo. Vectorizar implica reasociar (sumar en cuatro acumuladores paralelos y combinarlos al final), lo que cambiaría el resultado. Rust y LLVM se niegan a hacerlo sin permiso explícito, así que el bucle queda escalar y corre 4–8× más lento que el equivalente entero.

// Solución 1: reasociar VOS, explícitamente. Aceptás el cambio de redondeo.
pub fn suma_f32_rapida(v: &[f32]) -> f32 {
    let mut acc = [0.0f32; 8];
    let mut trozos = v.chunks_exact(8);
    for c in &mut trozos {
        for i in 0..8 { acc[i] += c[i]; }     // 8 acumuladores independientes
    }
    let resto: f32 = trozos.remainder().iter().sum();
    acc.iter().sum::<f32>() + resto
}
⚠️ Otros lugares donde la abstracción SÍ cuesta. collect::<Vec<_>>() alloca (es su trabajo, pero no es gratis). chars() decodifica UTF-8 y no puede saltar de a bytes: si buscás un byte ASCII, as_bytes() es varias veces más rápido. flat_map e iter().rev() sobre estructuras no contiguas rompen la vectorización. Los closures que capturan por move valores grandes se copian. Y impl Trait en posición de retorno se monomorfiza, pero un Box<dyn Fn> no (RuS7.8). El zero-cost es la norma, no una ley.

RuS7.7 Bounds checking: cuándo desaparece y cómo ayudarlo

Cada v[i] en Rust es, en principio, una comparación y un salto condicional a panic_bounds_check. En la práctica, LLVM elimina la mayoría de esos chequeos porque puede probar que el índice está en rango. La pregunta útil es cuándo no puede.

// ✅ Sin bounds check: el iterador es dueño del rango, no hay índice
pub fn dobla_iter(v: &mut [i32]) {
    for x in v.iter_mut() { *x *= 2; }
}

// ✅ Sin bounds check: LLVM prueba que i < v.len() por la condición del bucle
pub fn dobla_indice(v: &mut [i32]) {
    for i in 0..v.len() { v[i] *= 2; }
}

// ❌ CON bounds check en cada iteración: `n` es independiente del largo
pub fn dobla_n(v: &mut [i32], n: usize) {
    for i in 0..n { v[i] *= 2; }
}

// ✅ Arreglado sin unsafe: un solo chequeo al principio, y adentro nada
pub fn dobla_n_bien(v: &mut [i32], n: usize) {
    let v = &mut v[..n];                  // panic acá si n > len, UNA vez
    for x in v.iter_mut() { *x *= 2; }
}

El truco general se llama slicing defensivo: en vez de pelear con el optimizador dentro del bucle, recortá el slice antes y dejá que la prueba sea trivial.

// ❌ dos bounds checks por iteración: a[i] y b[i] con largos no relacionados
pub fn producto_mal(a: &[f64], b: &[f64], out: &mut [f64]) {
    for i in 0..out.len() { out[i] = a[i] * b[i]; }
}

// ✅ los tres largos se igualan una vez; adentro no queda ningún chequeo
//    y además esto SÍ se vectoriza
pub fn producto_bien(a: &[f64], b: &[f64], out: &mut [f64]) {
    let n = out.len().min(a.len()).min(b.len());
    let (a, b, out) = (&a[..n], &b[..n], &mut out[..n]);
    for i in 0..n { out[i] = a[i] * b[i]; }
}

// ✅✅ la versión idiomática, sin índices y sin chequeos: zip
pub fn producto_zip(a: &[f64], b: &[f64], out: &mut [f64]) {
    for (o, (x, y)) in out.iter_mut().zip(a.iter().zip(b)) { *o = x * y; }
}
📌 La regla operativa. En Rust, los iteradores son la optimización, no un lujo de estilo. iter(), zip, chunks_exact, windows y array_windows le dan al compilador información que la indexación manual esconde. Cuando alguien te diga “uso índices porque es más rápido”, pedile el asm.
⚠️ get_unchecked es la última opción, no la primera. Existe unsafe { *v.get_unchecked(i) } y sí, saca el chequeo. También convierte un panic determinista en corrupción de memoria silenciosa el día que alguien cambie un largo. Antes de llegar ahí: probá el slicing defensivo, medí si el bounds check aparece siquiera en el perfil (casi nunca aparece: el predictor de saltos acierta el 100% de las veces y el costo real ronda el 1–3%), y si igual necesitás unsafe, leé RuS5 y encapsulalo detrás de una API segura con un // SAFETY: que explique el invariante.

RuS7.8 Box<dyn Trait> vs genéricos: el costo real del dispatch

En RuS2 viste la diferencia semántica entre despacho estático (genéricos, monomorfización) y dinámico (objetos de trait, vtable). Acá va la parte medida, que suele sorprender.

pub trait Filtro { fn aplica(&self, x: f64) -> f64; }

pub struct Ganancia(pub f64);
impl Filtro for Ganancia {
    #[inline] fn aplica(&self, x: f64) -> f64 { x * self.0 }
}

// Estático: se genera una copia de `procesar` por cada tipo concreto.
// `aplica` se inlinea y desaparece; el bucle se vectoriza.
pub fn procesar_estatico<F: Filtro>(f: &F, v: &mut [f64]) {
    for x in v.iter_mut() { *x = f.aplica(*x); }
}

// Dinámico: una sola copia. Cada llamada es un salto indirecto por vtable.
// No se inlinea, no se vectoriza.
pub fn procesar_dinamico(f: &dyn Filtro, v: &mut [f64]) {
    for x in v.iter_mut() { *x = f.aplica(*x); }
}

📌 El costo del despacho dinámico es real y es chico. Un salto indirecto bien predicho cuesta 1–3 ciclos (~1 ns). Un fallo de caché L3 cuesta 200–300 ciclos (~100 ns). Si tu función hace cualquier trabajo sustancial, el dispatch se pierde en el ruido. Lo que sí duele no es el salto: es que dyn bloquea el inlining, y sin inlining se caen la vectorización, el constant folding y la eliminación de código muerto. Por eso la penalidad es enorme en funciones de una línea y despreciable en todo lo demás.
💡 La tercera vía que la gente olvida: despacho por enum. Si el conjunto de implementaciones es cerrado y conocido, un enum con un match te da despacho estático, una sola copia del código, sin allocación y sin vtable. Es el patrón que usan casi todos los intérpretes rápidos escritos en Rust. 
pub enum FiltroConcreto { Ganancia(f64), Offset(f64), Clip { lo: f64, hi: f64 } }

impl FiltroConcreto {
    #[inline]
    pub fn aplica(&self, x: f64) -> f64 {
        match self {
            FiltroConcreto::Ganancia(k)   => x * k,
            FiltroConcreto::Offset(k)     => x + k,
            FiltroConcreto::Clip { lo, hi } => x.clamp(*lo, *hi),
        }
    }
}

// predictor acierta siempre; y como no hay indirección, LLVM puede sacar el
// match FUERA del bucle (loop unswitching) y vectorizar cada rama.

RuS7.9 Layout de datos y caché: la optimización que le gana a todas

Una CPU moderna hace ~4 operaciones por ciclo y tarda ~300 ciclos en traer un dato de RAM. La aritmética es esencialmente gratis; la memoria es lo caro. Por eso el layout de los datos suele importar más que cualquier micro-optimización aritmética.

use std::mem::{size_of, align_of};

struct Malo  { a: u8, b: u64, c: u8, d: u32 }   // como lo escribiste
#[repr(C)]
struct MaloC { a: u8, b: u64, c: u8, d: u32 }   // orden garantizado, con padding

fn main() {
    // repr(Rust) REORDENA los campos para minimizar padding
    println!("{} {}", size_of::<Malo>(),  align_of::<Malo>());   // 16 8
    // repr(C) respeta tu orden y paga el padding: 1+7+8+1+3+4 = 24
    println!("{} {}", size_of::<MaloC>(), align_of::<MaloC>());  // 24 8
}
repr(Rust) es el default y es tu amigo: el compilador puede reordenar campos y lo hace para achicar el struct. #[repr(C)] desactiva ese reordenamiento y solo se usa cuando el layout tiene que ser estable: FFI, mapeo de estructuras binarias, o cuando lo exige un formato externo. Usarlo “por prolijidad” es una pesimización.
⚠️ #[repr(packed)] es peligroso, no solo lento. Elimina todo el padding, pero entonces tomar una referencia a un campo desalineado es comportamiento indefinido, y en algunas arquitecturas es directamente un fallo de hardware. En x86 “funciona” pero cada acceso desalineado cuesta ciclos extra. Si necesitás layout compacto para serializar, leé y escribé los campos con read_unaligned/to_le_bytes, o usá un crate de serialización.

AoS vs SoA: el cambio que multiplica

// Array of Structs (AoS) — lo natural de escribir
struct Particula { x: f32, y: f32, z: f32, vx: f32, vy: f32, vz: f32, masa: f32, id: u64 }
// 40 bytes por partícula. Para actualizar solo X, la CPU trae líneas de caché
// de 64 bytes de las cuales usás 4. Desperdiciás el 90% del ancho de banda.

fn avanzar_aos(ps: &mut [Particula], dt: f32) {
    for p in ps.iter_mut() { p.x += p.vx * dt; }
}

// Structure of Arrays (SoA) — lo que le gusta a la CPU
struct Particulas {
    x:  Vec<f32>, y:  Vec<f32>, z:  Vec<f32>,
    vx: Vec<f32>, vy: Vec<f32>, vz: Vec<f32>,
    masa: Vec<f32>, id: Vec<u64>,
}

fn avanzar_soa(ps: &mut Particulas, dt: f32) {
    // Dos slices contiguos: cada línea de caché se usa entera y LLVM vectoriza
    for (x, vx) in ps.x.iter_mut().zip(&ps.vx) { *x += vx * dt; }
}

📌 Casi 8× sin cambiar ni una operación aritmética. No hay ninguna micro-optimización de este módulo que dé eso. Por eso el orden correcto de trabajo es: primero algoritmo, después layout de datos, después allocaciones, y recién al final las opciones del compilador y SIMD. La contra de SoA es que la ergonomía empeora (perdés “la partícula” como entidad) y que si tu acceso típico usa todos los campos de un solo elemento, AoS gana. Medí tu patrón de acceso real.
💡 Otros efectos de caché que valen oro: ordenar los datos por la clave con la que los recorrés (transforma accesos aleatorios en secuenciales); usar índices u32 en vez de punteros de 64 bits para grafos grandes; poner los campos “calientes” juntos y los fríos en un struct aparte; y para estructuras compartidas entre hilos, separar los datos de cada hilo por al menos una línea de caché para evitar false sharing (el crate crossbeam-utils tiene CachePadded).

RuS7.10 Paralelismo con rayon: cuándo una línea alcanza

rayon es la mejor relación esfuerzo/resultado del ecosistema: convertís iter() en par_iter() y tu bucle usa todos los núcleos, con work-stealing y sin que puedas introducir data races —el sistema de tipos lo impide.

use rayon::prelude::*;

// Secuencial
let total: u64 = datos.iter().map(|d| costoso(d)).sum();

// Paralelo. Sí, es literalmente eso.
let total: u64 = datos.par_iter().map(|d| costoso(d)).sum();

// Con control del grano: si cada ítem es barato, agrupá para amortizar
let total: u64 = datos.par_chunks(4096)
    .map(|c| c.iter().map(|d| barato(d)).sum::<u64>())
    .sum();

El antipatrón del acumulador con lock. par_iter().for_each(|x| resultados.lock().unwrap().push(f(x))) paraleliza el f(x) y serializa todo lo demás, con el costo extra del lock. La forma correcta es map + collect, o fold/reduce, que acumulan por hilo y combinan al final sin ninguna sincronización explícita. 
use rayon::prelude::*;
use std::collections::HashMap;

// ✅ fold local por hilo, reduce al final: cero locks
let conteo: HashMap<&str, usize> = palabras
    .par_iter()
    .fold(HashMap::new, |mut acc, p| { *acc.entry(*p).or_insert(0) += 1; acc })
    .reduce(HashMap::new, |mut a, b| {
        for (k, v) in b { *a.entry(k).or_insert(0) += v; }
        a
    });

RuS7.11 SIMD: cuándo vale la pena escribirlo a mano

Primera regla del SIMD manual: lo más probable es que ya lo tengas. LLVM autovectoriza bucles simples sobre slices contiguos si no hay dependencias entre iteraciones ni operaciones no asociativas. Verificá con cargo asm antes de escribir intrinsics: si ves vpaddd, vmulps o vfmadd, ya estás vectorizado.

// Nightly: portable SIMD, la opción legible y multi-arquitectura
#![feature(portable_simd)]
use std::simd::{f32x8, num::SimdFloat};

pub fn suma_simd(v: &[f32]) -> f32 {
    let (pre, medio, post) = v.as_simd::<8>();   // alinea y parte el slice
    let acumulado: f32x8 = medio.iter().copied().sum();
    pre.iter().sum::<f32>() + acumulado.reduce_sum() + post.iter().sum::<f32>()
}
// Estable: intrinsics + detección en runtime.
// Desde Rust 1.86, `#[target_feature]` puede ir en funciones SEGURAS: solo se
// las puede llamar desde contextos que ya garantizan la feature.
#[cfg(target_arch = "x86_64")]
#[target_feature(enable = "avx2")]
fn suma_avx2(v: &[f32]) -> f32 {
    use std::arch::x86_64::*;
    unsafe {
        let mut acc = _mm256_setzero_ps();
        let trozos = v.chunks_exact(8);
        let resto  = trozos.remainder();
        for c in trozos { acc = _mm256_add_ps(acc, _mm256_loadu_ps(c.as_ptr())); }
        let mut buf = [0f32; 8];
        _mm256_storeu_ps(buf.as_mut_ptr(), acc);
        buf.iter().sum::<f32>() + resto.iter().sum::<f32>()
    }
}

pub fn suma(v: &[f32]) -> f32 {
    #[cfg(target_arch = "x86_64")]
    if is_x86_feature_detected!("avx2") { return suma_avx2(v); }
    v.iter().sum()                       // camino portable de respaldo
}
📌 Cuándo SÍ escribir SIMD a mano. (1) El perfil dice que un bucle numérico es > 20% del tiempo total. (2) Miraste el asm y no está vectorizado. (3) Sabés por qué no lo está (float no asociativo, control de flujo adentro, accesos no contiguos, posible aliasing). (4) La ganancia teórica justifica el código: 4–8× en el bucle, que sobre un 20% del total son 17% de mejora global — hacé la cuenta de Amdahl antes de escribir. Si alguna de las cuatro falla, no lo escribas: hay crates (wide, pulp, faster, o directamente ndarray/polars) que ya resolvieron tu caso mejor.

RuS7.13 Cuándo NO optimizar

La habilidad más cara de este módulo no es optimizar: es decidir que no hace falta. Cada optimización tiene un costo permanente en legibilidad, en superficie de bugs y en tiempo de la gente que va a mantener eso.

📌 No optimices si...
  • No medisté. Regla cero, sin excepciones.
  • Ya cumplís el objetivo. Si el requisito es p99 < 100 ms y estás en 40 ms, terminaste. “Más rápido” no es un requisito.
  • El componente no está en el camino crítico. Amdahl: acelerar 10× algo que es el 5% del tiempo total te da 4,5% global. Hacé la cuenta antes.
  • El cuello está afuera. Base de datos, red, disco, otro servicio. Optimizar tu CPU cuando esperás 200 ms a Postgres es teatro.
  • La ganancia es menor que la varianza de tu medición. Si el intervalo de confianza de criterion se solapa, no mejoraste nada demostrable.
  • El código se ejecuta una vez por día. Un job nocturno que tarda 8 minutos en vez de 3 no es un problema.
  • Vas a necesitar unsafe para ganar 3%. Ese intercambio casi nunca cierra.
💡 El orden que sí funciona. 1) Definí el objetivo en números. 2) Medí el estado actual con --release. 3) Perfilá. 4) Atacá la meseta más ancha, no la que más te intriga. 5) Medí de nuevo con criterion contra un baseline. 6) Si no mejoró, revertí —no dejes complejidad que no compró nada. 7) Escribí un benchmark de regresión para que la mejora no se pierda sola en tres meses.

Paso 1 — El código original

use std::collections::HashMap;
use std::fs::File;
use std::io::{BufRead, BufReader};

fn resumir(ruta: &str) -> std::io::Result<HashMap<String, (u64, u64)>> {
    let f = BufReader::new(File::open(ruta)?);
    let mut acc: HashMap<String, (u64, u64)> = HashMap::new();

    for linea in f.lines() {
        let linea = linea?;                                    // ① String por línea
        let campos: Vec<String> = linea.split(' ')
            .map(|s| s.to_string())                            // ② String por campo
            .collect();                                        // ③ Vec por línea
        if campos.len() < 9 { continue; }

        let endpoint = campos[6].to_lowercase();               // ④ otra String
        let estado: u64 = campos[8].parse().unwrap_or(0);
        let e = acc.entry(endpoint).or_insert((0, 0));         // ⑤ String clonada al insertar
        e.0 += 1;
        if estado >= 500 { e.1 += 1; }
    }
    Ok(acc)
}

Paso 3 — Los intentos, uno por uno y todos medidos

// Intento C — la reescritura principal: buffer reusado + &str en vez de String
fn resumir_v2(ruta: &str) -> std::io::Result<HashMap<Box<str>, (u64, u64)>> {
    let mut f = BufReader::with_capacity(1 << 20, File::open(ruta)?);   // buffer de 1 MB
    let mut acc: HashMap<Box<str>, (u64, u64)> = HashMap::new();
    let mut buf = String::with_capacity(512);

    loop {
        buf.clear();                                     // reusa la capacidad
        if f.read_line(&mut buf)? == 0 { break; }

        // SmallVec: hasta 12 campos sin tocar el heap. Cero Strings.
        let campos: smallvec::SmallVec<[&str; 12]> = buf.trim_end().split(' ').collect();
        if campos.len() < 9 { continue; }

        let endpoint = campos[6];
        let estado: u64 = campos[8].parse().unwrap_or(0);

        // Solo allocamos la clave la PRIMERA vez que vemos el endpoint
        match acc.get_mut(endpoint) {
            Some(e) => { e.0 += 1; if estado >= 500 { e.1 += 1; } }
            None => { acc.insert(endpoint.into(), (1, u64::from(estado >= 500))); }
        }
    }
    Ok(acc)
}
// Intento D — matar el to_lowercase(): comparar sin allocar
// (to_lowercase alloca SIEMPRE, incluso si el texto ya está en minúsculas)
// En vez de normalizar la clave, normalizamos solo al comparar:
use std::collections::HashMap;
fn clave_normalizada<'a>(acc: &'a HashMap<Box<str>, (u64, u64)>, s: &str) -> Option<&'a str> {
    acc.keys().find(|k| k.eq_ignore_ascii_case(s)).map(|k| &**k)
}
// ⚠️ ojo: esto es O(claves) por línea. Solo sirve porque hay ~40 endpoints.
// Con 100.000 claves sería catastrófico: ahí conviene un hash case-insensitive.
// Intento F — hash más barato. SipHash resiste ataques de colisión (correcto
// para claves que vienen de la red), pero acá las claves son internas.
// FxHash es ~4× más rápido y no criptográfico.
use rustc_hash::FxHashMap;
let mut acc: FxHashMap<Box<str>, (u64, u64)> = FxHashMap::default();
// Intento G — el que propuso el equipo: rayon
use rayon::prelude::*;
use rayon::iter::ParallelBridge;

fn resumir_par(ruta: &str) -> std::io::Result<FxHashMap<Box<str>, (u64, u64)>> {
    let f = BufReader::with_capacity(1 << 20, File::open(ruta)?);
    Ok(f.lines()
        .par_bridge()                                  // ⚠️ vuelve a allocar String/línea
        .filter_map(|l| l.ok())
        .fold(FxHashMap::default, |mut acc, linea| { acumular(&mut acc, &linea); acc })
        .reduce(FxHashMap::default, fusionar))
}

📌 El cuello se mudó. Al principio el 61% era CPU gastada en allocaciones — paralelizable en teoría. Después de arreglarla, el 79% es esperar al disco, que es un recurso único: ocho hilos leen el mismo archivo por el mismo controlador. Peor todavía, par_bridge tiene que producir un String por línea para poder mandarla a otro hilo, así que reintrodujo las 24 millones de allocaciones que acabábamos de eliminar, y encima le sumó el costo del scheduler. Por eso G empeora un 4%: no es que “rayon sea malo”, es que se aplicó a la etapa equivocada del problema.
La trampa a la que le ganamos. Si el equipo hubiera implementado rayon primero (sobre el código base A), habría medido 8,10 s → 3,4 s y declarado victoria: una mejora de 2,4× real y visible. Y se habría quedado con un programa que sigue haciendo 24 millones de allocaciones, con 8 hilos, tres veces más complejo, y tres veces más lento que la solución de un hilo bien escrita. Paralelizar código ineficiente esconde la ineficiencia detrás de núcleos: la primera regla es hacer menos trabajo, no repartir el mismo trabajo.

Checkpoint — ¿lo tenés claro?

Tu benchmark de una función que suma un millón de elementos reporta 3 nanosegundos. ¿Qué pasó y cómo lo arreglás?

El optimizador borró el trabajo. Con datos conocidos en tiempo de compilación y un resultado que nadie usa, LLVM constant-foldea la suma o elimina el bucle entero por dead code elimination; lo que medís es el overhead del harness. Se arregla con std::hint::black_box en los dos lados: black_box(f(black_box(entrada))). La barrera de entrada hace que el argumento sea opaco (no se puede precalcular) y la de salida hace que el resultado se considere usado (no se puede eliminar). Verificación adicional: si duplicás el tamaño de la entrada y el tiempo no cambia, seguís midiendo nada.

El perfil dice que el 40% del tiempo está en __rust_alloc. Enumerá, en orden, qué revisás.

(1) Vec/String que crecen sin with_capacity cuando el tamaño es conocido o estimable. (2) to_string()/to_owned()/clone() dentro de bucles calientes: ¿se puede trabajar con &str/&[T], o con Cow si a veces hace falta ser dueño? (3) collect::<Vec<_>>() intermedios que se descartan enseguida: encadenar los adaptadores en una sola pasada. (4) Buffers que se recrean por iteración en vez de reusarse con clear(). (5) Colecciones chicas y frecuentes → SmallVec; muchas allocaciones con la misma vida → arena (bumpalo). (6) Recién ahí, cambiar el allocador global a mimalloc. Y todo el tiempo, medir con dhat: el contador de bloques totales te dice si bajaste de “una por ítem” a “constante”, que es el salto que importa.

¿Cómo demostrarías que un filter().map().sum() compila al mismo código que un bucle manual — y en qué caso concreto sabés de antemano que no lo va a hacer?

Se demuestra con cargo asm --release --lib crate::funcion sobre las dos versiones (marcadas #[inline(never)] para que no desaparezcan dentro del llamador) y comparando el asm; o en godbolt.org para una exploración rápida. Deberías ver un único bucle, sin llamadas a next() y sin allocaciones. El caso donde no se cumple, y se sabe de antemano, es con punto flotante: v.iter().sum::<f32>() no se vectoriza porque la suma de floats no es asociativa, y reasociar cambiaría el resultado por redondeo. LLVM no toma esa libertad sin permiso. Si querés la vectorización, tenés que reasociar vos —acumuladores múltiples con chunks_exact— y aceptar explícitamente la diferencia numérica. Otros casos previsibles: cualquier collect intermedio (alloca por definición), chars() sobre UTF-8 cuando alcanzaba con bytes, e iteración sobre estructuras no contiguas.

Resumen ejecutivo

  • Zero-cost es una hipótesis verificable, no un axioma. Se verifica leyendo el asm con cargo asm o Compiler Explorer. Se cumple casi siempre con iteradores sobre slices; se rompe de forma predecible con floats no asociativos, collect intermedios y dyn en funciones triviales.
  • --release primero. Un número medido en debug no significa nada. Ojo con overflow-checks: es una diferencia de comportamiento, no solo de velocidad.
  • Perfiles: lto = "thin" casi siempre; fat + codegen-units = 1 solo en el build de producción; panic = "abort" en binarios; target-cpu=native solo si compilás donde corre; y un [profile.profiling] heredado de release con debug = true para poder perfilar.
  • Benchmarks con criterion, no con Instant: warmup, cientos de muestras, intervalos de confianza y baselines para detectar regresiones. Si los intervalos se solapan, no hubo mejora.
  • std::hint::black_box en los dos lados o el compilador borra tu benchmark.
  • Perfilá antes de tocar nada: samply (fácil, multiplataforma) o perf + flamegraph. El ancho es tiempo, la altura no; buscá mesetas anchas con hijos angostos.
  • Las allocaciones son el sospechoso número uno. with_capacity, buffers reusados con clear(), &str en vez de String, Cow para el caso mixto, SmallVec para colecciones chicas, arenas para vidas de fase. Medí con dhat: mirá bloques totales, no solo bytes.
  • Los iteradores eliminan bounds checks que los índices no. Cuando necesites índices, recortá los slices antes del bucle. get_unchecked es la última opción, no la primera.
  • dyn cuesta poco por el salto y mucho por el inlining perdido: 7× en funciones de una línea, invisible en cualquier cosa que toque memoria. El despacho por enum es la tercera vía cuando el conjunto es cerrado.
  • El layout le gana a la micro-optimización: AoS → SoA dio 8× sin cambiar una sola operación aritmética. repr(Rust) por defecto; repr(C) solo para FFI; repr(packed) casi nunca.
  • rayon es una línea, y a veces esa línea empeora todo: trabajo por ítem chico, colecciones chicas, cuello de I/O o de ancho de banda, o locks compartidos. Paralelizar código ineficiente esconde la ineficiencia.
  • SIMD manual solo con las cuatro condiciones: es > 20% del perfil, no está autovectorizado, sabés por qué, y Amdahl justifica el código.
  • El tiempo de compilación es performance del equipo: medilo con cargo build --timings y cargo llvm-lines; atacá monomorfización (thin wrappers), proc-macros, linker y perfil dev.
  • Saber no optimizar es la habilidad cara: si ya cumplís el objetivo, si no está en el camino crítico, si el cuello está afuera, o si la ganancia cabe dentro de tu barra de error — no toques nada.

🧠 Autoevaluación

1. Un benchmark de fibonacci(30) reporta 0,4 ns. Escribís b.iter(|| black_box(fibonacci(30))) y sigue dando lo mismo. ¿Qué falta?

La barrera de salida impide que se elimine el resultado, pero con el argumento constante LLVM evalúa fibonacci(30) en tiempo de compilación y mete la constante. Hay que hacer opaca la entrada también. Regla: opaco lo que entra, opaco lo que sale.

2. Tu perfil muestra 61% en __rust_alloc y 8% en I/O. Alguien propone par_iter(). ¿Cuál es la objeción técnica correcta?

Paralelizar código que allocá de más esconde la ineficiencia detrás de núcleos: seguís haciendo millones de allocaciones, ahora peleándose por el allocador global. Primero se elimina el trabajo innecesario (buffers reusados, &str, sin collect intermedios); recién después se evalúa si queda algo que valga la pena paralelizar — y muchas veces, como en el Worked Example, ya no queda.

3. v.iter().sum::<i64>() se vectoriza pero v.iter().sum::<f32>() no, sobre datos del mismo tamaño. ¿Por qué?

Vectorizar una suma significa usar varios acumuladores en paralelo y combinarlos al final, es decir, reasociar. Con enteros el resultado es idéntico; con floats puede diferir por redondeo, así que el compilador se niega salvo que uses -ffast-math (que Rust no expone) o reasocies vos mismo con chunks_exact y acumuladores múltiples, aceptando explícitamente la diferencia numérica.

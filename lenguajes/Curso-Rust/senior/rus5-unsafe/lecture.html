RuS5 — Unsafe correcto: invariantes, UB y FFI

RuS5.0 Por qué este módulo

Hay una frase que circula en foros, en respuestas de Stack Overflow y en más de un code review: "metelo en un unsafe y listo". Esa frase describe mal lo que pasa. unsafe no es un interruptor que apaga las reglas. No desactiva el borrow checker, no relaja los lifetimes, no permite mutar detrás de una referencia compartida, no convierte el código en C.

💡 La tesis del módulo. unsafe no te da permisos: te transfiere obligaciones. Es una anotación que dice, literalmente: "acá hay invariantes que el compilador ya no puede verificar, y yo, el autor, me hago cargo de mantenerlos". El conjunto de reglas que hay que respetar es exactamente el mismo con y sin unsafe. Lo único que cambia es quién las chequea.

La consecuencia práctica de entenderlo así es enorme. Si unsafe fuera un permiso, la pregunta de diseño sería "¿me alcanza con este permiso?". Como es una obligación, la pregunta correcta es otra: "¿puedo enunciar por escrito el invariante del que me estoy haciendo cargo, y puedo garantizar que ningún uso de esta API lo rompa?". Si no podés escribir esa frase, no estás listo para escribir el bloque.

Empecemos por desarmar el mito más común. Este código no compila, y el unsafe no ayuda en nada:

fn main() {
    let mut v = vec![1, 2, 3];
    unsafe {
        let primero = &v[0];   // préstamo compartido, vive hasta el println
        v.push(4);             // ERROR: cannot borrow `v` as mutable
        println!("{primero}");
    }
}
error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable
 --> src/main.rs:5:9
  |
4 |         let primero = &v[0];
  |                        - immutable borrow occurs here
5 |         v.push(4);
  |         ^^^^^^^^^ mutable borrow occurs here
6 |         println!("{primero}");
  |                    ------- immutable borrow later used here
📌 Dentro de un bloque unsafe, el 95% de Rust sigue siendo exactamente igual. Ownership, borrowing, lifetimes, Drop, chequeo de tipos, exhaustividad de match: todo intacto. unsafe agrega cinco capacidades puntuales y nada más. Esa lista es corta y hay que sabérsela de memoria.

RuS5.1 Qué habilita exactamente unsafe

La lista completa, sin excepciones, es esta:

  1. Desreferenciar un puntero crudo (*const T o *mut T).
  2. Llamar a una función o método marcado unsafe — incluidas las funciones de un bloque extern.
  3. Implementar un trait unsafe (Send, Sync, GlobalAlloc, Allocator, ...).
  4. Acceder o modificar un static mut.
  5. Leer un campo de una union.

Nada más. Ni un ítem más. Es útil verlo escrito en código, porque muestra lo acotado que es el permiso:

static mut CONTADOR: u32 = 0;

union Bits {
    entero: u32,
    flotante: f32,
}

unsafe fn peligrosa() -> u8 { 42 }

unsafe trait DeclaroAlgoQueNoSePuedeVerificar {}
struct Marcador;
unsafe impl DeclaroAlgoQueNoSePuedeVerificar for Marcador {}

fn main() {
    let x = 10i32;
    let p: *const i32 = &x;

    unsafe {
        let _1 = *p;                              // (1) desreferenciar
        let _2 = peligrosa();                     // (2) llamar unsafe fn
        // (3) el `unsafe impl` de arriba
        CONTADOR += 1;                            // (4) static mut (ver más abajo)
        let b = Bits { entero: 0x4048_F5C3 };
        let _3 = b.flotante;                      // (5) leer campo de union
    }
}
Fijate en el punto (3): unsafe trait y unsafe impl no tienen nada que ver con punteros. Un trait es unsafe cuando otro código va a confiar ciegamente en una promesa que el compilador no puede comprobar. Send promete "es seguro mover esto a otro hilo". Sync promete "es seguro compartir &T entre hilos". Quien implementa, promete; quien usa, confía.

La edición 2024 endureció el terreno

Si venís de código escrito para la edición 2018 o 2021, hay cuatro cambios de la edición 2024 (estable desde Rust 1.85, y el default de cargo new en Rust 1.95) que afectan directo a este módulo.

Primero: el cuerpo de una unsafe fn ya no es un bloque unsafe implícito. El lint unsafe_op_in_unsafe_fn pasó a warn por defecto:

// Edición 2021: compilaba sin decir nada.
// Edición 2024: warning `unsafe_op_in_unsafe_fn`.
pub unsafe fn leer(p: *const u8) -> u8 {
    *p                    // ⚠️ operación unsafe sin bloque explícito
}

// Forma correcta en edición 2024:
pub unsafe fn leer_ok(p: *const u8) -> u8 {
    // SAFETY: el contrato de esta función exige que `p` sea válido para
    // lectura de 1 byte y esté correctamente alineado. Lo delegamos al llamador.
    unsafe { *p }
}

El cambio parece burocrático y no lo es. Antes, una unsafe fn de 80 líneas era un bloque unsafe gigante donde cualquier línea podía ser la peligrosa. Ahora las operaciones riesgosas están marcadas una por una y cada una puede tener su justificación al lado. Auditar deja de ser leer 80 líneas y pasa a ser leer tres.

Segundo: los bloques extern ahora se declaran unsafe extern, y se puede marcar como safe a los ítems que realmente lo son:

unsafe extern "C" {
    // Llamarla puede violar invariantes: el llamador se hace cargo.
    fn strlen(s: *const core::ffi::c_char) -> usize;

    // Esta no toca punteros ni estado global: es segura de llamar.
    safe fn abs(x: core::ffi::c_int) -> core::ffi::c_int;
}

fn main() {
    let n = abs(-7);              // sin bloque unsafe: está marcada `safe`
    println!("{n}");
}

Tercero: ciertos atributos que afectan el enlazado pasaron a exigir el envoltorio unsafe(...), porque un símbolo con nombre fijo puede colisionar con otro y romper el programa entero:

// Edición 2021: #[no_mangle]
// Edición 2024:
#[unsafe(no_mangle)]
pub extern "C" fn sumar(a: i32, b: i32) -> i32 {
    a + b
}

// Ídem para #[unsafe(export_name = "...")] y #[unsafe(link_section = "...")]

Cuarto, y es el que más código viejo rompe: tomar una referencia a un static mut es un error en la edición 2024 (el lint static_mut_refs pasó a deny). El motivo es que es prácticamente imposible garantizar que no exista otra referencia viva al mismo static, y dos &mut simultáneos son UB inmediato:

static mut BUFFER: [u8; 16] = [0; 16];

fn mal() {
    unsafe {
        let r = &mut BUFFER;      // ❌ error en edición 2024: static_mut_refs
        r[0] = 1;
    }
}

// Alternativas reales, en orden de preferencia:
use std::sync::atomic::{AtomicU32, Ordering};
use std::sync::Mutex;

static CONTADOR: AtomicU32 = AtomicU32::new(0);          // 1. atómico
static ESTADO: Mutex<Vec<u8>> = Mutex::new(Vec::new());   // 2. Mutex

fn bien() {
    CONTADOR.fetch_add(1, Ordering::Relaxed);
    ESTADO.lock().unwrap().push(7);
}
Error clásico de principiante avanzado: "necesito un contador global, uso static mut con unsafe". Casi nunca hace falta. Un AtomicU32 es más rápido que un contador con candado, es safe, y no tiene ningún invariante que mantener a mano. El static mut quedó como un artefacto histórico casi sin usos legítimos fuera del arranque de un binario no_std.

RuS5.2 La safety boundary: la idea central del diseño

Acá está el concepto que separa el unsafe de un profesional del unsafe de alguien que está peleando con el compilador. Se llama safety boundary (frontera de seguridad) y se enuncia así:

📌 El unsafe se encapsula adentro de una API safe cuyo contrato sea imposible de violar desde afuera. Si existe alguna secuencia de llamadas —por más rebuscada que sea— que use solo funciones públicas safe y provoque UB, tu API está rota. No "es responsabilidad del usuario": está rota.

Ese es el criterio que usa la librería estándar. Vec está lleno de punteros crudos, aritmética de punteros y memoria no inicializada, y sin embargo Vec es una API safe: no hay forma de causar UB usando push, pop, indexado y iter(). Todo el peso de mantener el invariante "los primeros len elementos del buffer están inicializados y len <= capacity" vive adentro del tipo.

El ejemplo canónico de por qué esto es un ejercicio de diseño y no de sintaxis es split_at_mut. Queremos partir un slice en dos mitades mutables. El borrow checker no puede aceptarlo porque no sabe razonar sobre índices disjuntos:

// Esto NO compila: dos préstamos mutables del mismo slice.
fn partir(s: &mut [i32], medio: usize) -> (&mut [i32], &mut [i32]) {
    (&mut s[..medio], &mut s[medio..])
}

La implementación real usa unsafe, pero el punto es dónde lo pone y qué chequea antes:

use std::slice;

pub fn partir(s: &mut [i32], medio: usize) -> (&mut [i32], &mut [i32]) {
    let largo = s.len();
    let ptr = s.as_mut_ptr();

    // El chequeo que hace que el unsafe de abajo sea correcto SIEMPRE.
    assert!(medio <= largo, "medio ({medio}) fuera de rango ({largo})");

    // SAFETY: `medio <= largo` por el assert de arriba, así que ambos rangos
    // caen dentro de la asignación de `s`. Los rangos [0, medio) y
    // [medio, largo) son DISJUNTOS, por lo que los dos `&mut` resultantes
    // nunca aliasan el mismo elemento. Los lifetimes salientes están atados
    // al de `s` por la firma, así que no pueden sobrevivirlo.
    unsafe {
        (
            slice::from_raw_parts_mut(ptr, medio),
            slice::from_raw_parts_mut(ptr.add(medio), largo - medio),
        )
    }
}

Mirá la estructura, porque es una plantilla que vas a repetir siempre:

1. Se valida en runtime lo que el compilador no puede validar en tiempo de compilación (el assert!).
2. Se escribe un comentario // SAFETY: que enuncia, punto por punto, por qué se cumple cada requisito de la operación unsafe.
3. El bloque unsafe es lo más chico posible: solo las dos llamadas peligrosas.
4. La firma pública es safe y sus lifetimes atan el resultado al input, de modo que el compilador impide el uso-después-de-liberar aunque el interior sea crudo.

El comentario // SAFETY: no es decorativo

Es la convención universal del ecosistema — la librería estándar la exige en cada bloque, y clippy::undocumented_unsafe_blocks la puede volver obligatoria en tu crate. Un buen // SAFETY: responde tres preguntas: ¿qué requiere la operación?, ¿por qué se cumple acá?, ¿qué código de este archivo podría romperlo si cambia?.

# Cargo.toml — hacer que el comentario sea obligatorio en todo el crate
[lints.clippy]
undocumented_unsafe_blocks = "deny"
multiple_unsafe_ops_per_block = "deny"
Un // SAFETY: que dice "es seguro porque funciona" no es un comentario de safety: es una confesión. Si al escribirlo no podés nombrar el invariante concreto, es señal de que todavía no entendés por qué tu código anda, y estás a un refactor de distancia de que deje de andar.

Cuándo la frontera no puede cerrarse

A veces el contrato depende de algo que la función no puede verificar. En ese caso la API se expone como unsafe fn — y eso es correcto, no un fracaso. Lo que no es aceptable es exponer una función safe cuyo mal uso cause UB:

pub struct BufferCrudo {
    datos: Vec<u8>,
    inicializados: usize,
}

impl BufferCrudo {
    /// # Safety
    /// El llamador debe garantizar que los primeros `n` bytes del buffer
    /// fueron efectivamente escritos (por ejemplo, por una syscall de lectura).
    /// Pasar un `n` mayor a lo escrito expone memoria no inicializada: UB.
    pub unsafe fn declarar_inicializados(&mut self, n: usize) {
        debug_assert!(n <= self.datos.capacity());
        self.inicializados = n;
    }

    // Esta sí es safe: no hay forma de usarla mal.
    pub fn leidos(&self) -> &[u8] {
        &self.datos[..self.inicializados]
    }
}
Regla de oro para la documentación: toda unsafe fn pública lleva una sección /// # Safety en su docstring listando las precondiciones. Es tan estándar que clippy::missing_safety_doc te lo reclama solo.

RuS5.3 Undefined Behavior: por qué no es "un bug"

Acá está la parte que a mucha gente le cuesta, y es la más importante de todo el módulo. Undefined Behavior no es un error de programa. Es un error de razonamiento sobre el programa.

Un bug común —un índice mal calculado, un off-by-one— produce un resultado incorrecto pero determinado: si lo ejecutás mil veces con la misma entrada, obtenés la misma respuesta equivocada mil veces. Podés depurarlo con println!, podés reproducirlo, podés escribir un test que falle.

UB es otra cosa. El compilador optimiza asumiendo que el UB nunca ocurre. Cuando ocurre, las conclusiones que sacó el optimizador pasan a ser falsas, y el código generado puede hacer literalmente cualquier cosa: borrar la rama que "no podía pasar", reordenar escrituras, o convertir un bucle en un salto incondicional. El síntoma aparece a 400 líneas del origen, cambia según el nivel de optimización, y desaparece cuando agregás un println! para investigarlo.

⚠️ UB no es "va a crashear". UB es "el compilador tenía permiso de asumir que esto no pasaba, y construyó el binario sobre esa suposición". Un programa con UB que hoy funciona perfecto puede romperse mañana por subir una versión menor del compilador, por activar LTO, o por que alguien agregó una función en otro archivo y cambió las decisiones de inlining. No es un bug latente: es un binario cuyo significado nunca estuvo definido.

La demostración clásica en Rust, adaptada del ejemplo que usa el propio Rustonomicon:

fn cuantos(x: bool) -> u32 {
    // El compilador SABE que un `bool` solo puede valer 0 o 1.
    // Por eso este match es exhaustivo con dos brazos y elimina todo lo demás.
    match x {
        true => 1,
        false => 0,
    }
}

fn main() {
    let byte: u8 = 3;                       // NO es 0 ni 1
    // SAFETY: mentira. Esto es UB: creamos un `bool` con un valor inválido.
    let b: bool = unsafe { std::mem::transmute(byte) };
    println!("{}", cuantos(b));             // ¿1? ¿0? ¿3? ¿basura? Indefinido.
}

Con -C opt-level=0 ese programa suele imprimir 1. Con -C opt-level=3 puede imprimir cualquier cosa, incluida una lectura fuera de rango si el match se compiló como una tabla de saltos indexada por el valor del booleano. Ninguno de los dos resultados es "el correcto": el programa no tiene comportamiento definido.

RuS5.4 El catálogo de UB en Rust

La lista oficial vive en el Reference, pero en la práctica seis casos explican casi todo lo que vas a encontrar. Vale la pena tenerlos como checklist mental cada vez que escribís un bloque.

1. Referencia colgante (dangling)

fn colgante() -> &'static i32 {
    let x = 42;
    let p: *const i32 = &x;
    // SAFETY: falsa. `x` muere al terminar la función; el puntero queda colgado.
    unsafe { &*p }        // UB: referencia a memoria liberada
}                          // ← `x` se destruye acá

El caso hostil de verdad no es este —es demasiado obvio— sino el que aparece cuando guardás un puntero a un elemento de un Vec y después el Vec crece: la reasignación mueve todo el buffer y tu puntero apunta a memoria liberada.

2. Aliasing de &mut

Una referencia &mut T promete ser única. No "es la única que se usa": es la única que existe. Violarlo es UB aunque nunca escribas por las dos:

fn aliasing_mutable() {
    let mut x = 10i32;
    let p = &mut x as *mut i32;

    unsafe {
        let a = &mut *p;
        let b = &mut *p;   // ❌ UB: dos &mut vivos a la misma dirección
        *a += 1;
        *b += 1;           // el optimizador puede fusionar, reordenar o borrar
        println!("{x}");
    }
}
Este es el UB que más se cuela sin darse cuenta, porque no rompe nada visible en debug. Es también el que Miri detecta mejor, gracias al modelo experimental de Stacked Borrows (y su sucesor Tree Borrows) que discutimos en RuS5.7.

3. Leer memoria no inicializada

use std::mem::MaybeUninit;

fn no_inicializado() {
    // ❌ UB instantáneo: `assume_init` afirma que ya se escribió, y es mentira.
    let x: i32 = unsafe { MaybeUninit::uninit().assume_init() };
    println!("{x}");
}

"Leer basura" suena inofensivo si venís de C. En Rust no lo es: un valor no inicializado no es "un número al azar", es un valor sin ningún valor, y compararlo consigo mismo puede dar false porque el optimizador está autorizado a materializarlo dos veces distinto.

4. Desalineación

fn desalineado() {
    let bytes: [u8; 8] = [1, 2, 3, 4, 5, 6, 7, 8];
    let p = bytes.as_ptr();

    unsafe {
        // `u32` requiere alineación de 4. `p.add(1)` casi seguro no la cumple.
        let malo = *(p.add(1) as *const u32);      // ❌ UB
        println!("{malo}");

        // Forma correcta si de verdad necesitás leer sin alineación:
        let bueno = (p.add(1) as *const u32).read_unaligned();
        println!("{bueno}");
    }
}

5. Invariantes de tipo rotas

Cada tipo tiene un conjunto de bit-patterns válidos, y salirse de él es UB aunque nunca uses el valor:

use std::num::NonZeroU32;

unsafe fn invariantes_rotas() {
    let _a: bool = std::mem::transmute(2u8);          // bool ∉ {0, 1}
    let _b: char = std::mem::transmute(0xD800u32);    // surrogate UTF-16
    let _c: NonZeroU32 = std::mem::transmute(0u32);   // cero en un NonZero
    let _d: &i32 = std::mem::transmute(0usize);       // referencia nula
    // Los cuatro son UB en el instante de la creación, sin leer nada.
}
📌 El UB de valores inválidos ocurre al construir el valor, no al usarlo. Es una diferencia crucial: no alcanza con "no lo toco". Si creaste un bool que vale 2, el programa ya está indefinido, aunque la variable se descarte en la línea siguiente.

6. Data race

// Con `unsafe impl Sync` sobre un tipo que NO lo es, podés reintroducir
// exactamente la clase de bug que Rust elimina de fábrica.
struct MiCelda(std::cell::UnsafeCell<u64>);
unsafe impl Sync for MiCelda {}          // ⚠️ promesa falsa: sin sincronización

// Dos hilos escribiendo el mismo u64 sin atómicos ni candado = data race = UB.
// No es "resultado impredecible": es indefinido, y el optimizador lo aprovecha.

Hay dos casos que la gente cree que son UB y no lo son, y conviene tenerlos claros para no perder tiempo: el overflow de enteros (es un pánico en debug y aritmética envolvente en release — un bug, no UB) y las fugas de memoria (mem::forget es una función safe: filtrar memoria es feo, no indefinido).

RuS5.5 Punteros crudos, provenance y NonNull

Un puntero crudo (*const T, *mut T) es la herramienta base. Crearlo y hacer aritmética con él es safe; desreferenciarlo no:

fn punteros() {
    let mut x = 5i32;

    let p_lectura: *const i32 = &x;         // safe
    let p_escritura: *mut i32 = &mut x;     // safe
    let p_invalido = 0xdead_beef_usize as *mut i32;   // safe crearlo (!)

    unsafe {
        println!("{}", *p_lectura);         // unsafe: desreferenciar
        *p_escritura = 6;
        // *p_invalido = 7;                 // esto sí sería UB
    }

    // Métodos útiles que evitan escribir el `*` a mano:
    unsafe {
        let v = p_lectura.read();           // copia el valor
        p_escritura.write(v * 2);           // escribe sin correr el Drop viejo
        assert!(!p_lectura.is_null());
        if let Some(r) = p_lectura.as_ref() { println!("{r}"); }
    }
}

Provenance: por qué un puntero no es un número

Este es el punto donde Rust se separa fuerte de la intuición de C. En Rust —y en el modelo de memoria que usa LLVM— un puntero no es solo una dirección: lleva asociada una provenance, que es el permiso de acceder a un rango específico de memoria, derivado de la asignación de la que salió. Dos punteros con la misma dirección numérica pueden tener provenance distinta, y usar el equivocado es UB aunque el número coincida.

fn provenance() {
    let mut a = [0u8; 4];
    let mut b = [0u8; 4];

    let pa = a.as_mut_ptr();
    let pb = b.as_mut_ptr();

    // Aunque por casualidad `pa.add(4) == pb`, escribir a través de
    // `pa.add(4)` es UB: la provenance de `pa` cubre solo los 4 bytes de `a`.
    unsafe {
        // *pa.add(4) = 1;   // ❌ fuera del rango que `pa` tiene permitido
        *pb = 1;             // ✅ el puntero correcto para tocar `b`
    }
    println!("{a:?} {b:?}");
}

Desde Rust 1.84 hay una API estable para trabajar con esto explícitamente, la strict provenance. La regla es: si necesitás la dirección como número, pedila con addr(); si necesitás reconstruir un puntero a partir de un número, tenés que declarar de dónde sale la provenance:

fn strict_provenance() {
    let x = 42u64;
    let p: *const u64 = &x;

    // Dirección como entero, SIN perder ni robar provenance: safe.
    let direccion: usize = p.addr();
    println!("alineado a 8: {}", direccion % 8 == 0);

    // Manipular los bits bajos manteniendo la provenance del original (tagged pointers):
    let etiquetado = p.map_addr(|a| a | 0b1);
    let limpio = etiquetado.map_addr(|a| a & !0b1);
    // SAFETY: `limpio` conserva la provenance de `p`, que apunta a `x` vivo.
    unsafe { assert_eq!(*limpio, 42); }

    // Si de verdad necesitás ida y vuelta por entero (FFI, hardware):
    let expuesta = p.expose_provenance();
    let recuperado: *const u64 = std::ptr::with_exposed_provenance(expuesta);
    unsafe { assert_eq!(*recuperado, 42); }
}
Por eso "castear punteros" no es lo mismo que en C. En C, (int*)(uintptr_t)p es idiomático y funciona. En Rust, p as usize as *const i32 compila pero borra la información que Miri y el optimizador necesitan; con -Zmiri-strict-provenance te lo marca como error. Usá addr(), map_addr() y with_exposed_provenance() según qué querés expresar.

NonNull: el puntero crudo que se comporta

NonNull<T> es un *mut T con dos ventajas: garantiza que no es nulo (lo que permite la optimización de nicho — Option<NonNull<T>> ocupa lo mismo que un puntero) y es covariante en T, que es lo que querés casi siempre al construir estructuras de datos:

use std::ptr::NonNull;
use std::marker::PhantomData;

pub struct MiCaja<T> {
    ptr: NonNull<T>,
    _marca: PhantomData<T>,   // le dice al compilador que "poseemos" un T
}

impl<T> MiCaja<T> {
    pub fn new(valor: T) -> Self {
        let bruto = Box::into_raw(Box::new(valor));
        // SAFETY: `Box::into_raw` nunca devuelve null.
        let ptr = unsafe { NonNull::new_unchecked(bruto) };
        Self { ptr, _marca: PhantomData }
    }

    pub fn get(&self) -> &T {
        // SAFETY: el puntero salió de un Box vivo que solo libera nuestro Drop,
        // y el lifetime del &T resultante está atado al de &self.
        unsafe { self.ptr.as_ref() }
    }
}

impl<T> Drop for MiCaja<T> {
    fn drop(&mut self) {
        // SAFETY: reconstruimos exactamente el Box que creamos en `new`,
        // y esto corre una sola vez porque Drop corre una sola vez.
        unsafe { drop(Box::from_raw(self.ptr.as_ptr())); }
    }
}
El PhantomData<T> no es adorno. Sin él, el compilador no sabe que MiCaja<T> es dueña de un T, y el drop check puede permitir órdenes de destrucción que dejen referencias colgadas. Es el ejemplo perfecto de cómo el unsafe te obliga a re-declarar a mano cosas que en código safe el compilador deduce solo.

RuS5.6 MaybeUninit: memoria que todavía no es un valor

Cuando escribís una estructura de datos que reserva memoria antes de llenarla —un Vec, un buffer circular, un arena allocator— necesitás una forma de decir "acá hay espacio para un T, pero todavía no hay un T". Ese tipo es MaybeUninit<T>.

Antes existía mem::uninitialized::<T>(), y está deprecado desde Rust 1.39 por una razón que vale la pena entender: su firma era una mentira de tipos. Devolvía un T, así que el compilador creía que tenía un valor válido, y si T tenía invariantes (un bool, una referencia, un NonZeroU32) el UB ocurría en el instante de la llamada. Además, si algo entre la creación y la inicialización hacía pánico, se corría el Drop de un valor que nunca existió:

use std::mem::MaybeUninit;

// ❌ La API vieja: `mem::uninitialized()` era UB para casi todo T.
// let mut v: Vec<u8> = unsafe { std::mem::uninitialized() };

// ✅ La API correcta: el tipo dice la verdad.
fn inicializar() -> String {
    let mut espacio: MaybeUninit<String> = MaybeUninit::uninit();

    // `write` inicializa SIN correr el Drop del contenido anterior
    // (correcto: no hay contenido anterior).
    espacio.write(String::from("hola"));

    // SAFETY: acabamos de escribir un String válido en `espacio` y no hubo
    // ningún camino de salida entre la escritura y esta línea.
    unsafe { espacio.assume_init() }
}

El patrón que más vas a usar es el de un arreglo o buffer parcialmente inicializado. La sutileza está en el drop en caso de pánico:

use std::mem::MaybeUninit;

fn construir_arreglo<F>(mut f: F) -> [String; 4]
where
    F: FnMut(usize) -> String,
{
    // SAFETY: un arreglo de MaybeUninit no requiere inicialización;
    // `MaybeUninit<T>` es válido con cualquier patrón de bits.
    let mut arr: [MaybeUninit<String>; 4] = unsafe { MaybeUninit::uninit().assume_init() };

    for (i, hueco) in arr.iter_mut().enumerate() {
        hueco.write(f(i));
        // ⚠️ Si `f` hace pánico en i == 2, los strings 0 y 1 quedan sin
        // liberarse. Es una FUGA, no UB. En código de producción esto se
        // resuelve con un guard que lleve la cuenta y los libere en su Drop.
    }

    // SAFETY: el loop escribió las 4 posiciones y terminó sin salir por pánico.
    unsafe { std::mem::transmute::<_, [String; 4]>(arr) }
}
Para leer un slice parcialmente inicializado sin transmutar a mano, mirá MaybeUninit::slice_assume_init_ref y Vec::spare_capacity_mut, que te da directamente un &mut [MaybeUninit<T>] de la capacidad libre. Es lo que usa el propio Read::read_buf para llenar buffers sin pagar el costo de ponerlos en cero primero.

RuS5.7 Miri: el detector de UB

Hasta acá el módulo te pidió razonar. Miri te deja verificar. Es un intérprete del MIR (la representación intermedia de Rust) que ejecuta tu programa manteniendo, para cada puntero, su provenance, su rango válido y una pila de permisos. Cuando una operación viola las reglas, para y te dice exactamente cuál.

El caso didáctico perfecto es un test que pasa en verde y esconde UB. Este código se ve razonable: se saca un puntero de lectura del buffer y se escribe a través de él.

pub struct Celda {
    datos: Vec<u64>,
}

impl Celda {
    pub fn set(&mut self, i: usize, v: u64) {
        // El bug: `as_ptr()` produce un puntero de SOLO LECTURA.

        let p = self.datos.as_ptr() as *mut u64;

        unsafe { p.add(i).write(v); }

}

    c.set(2, 99);
    assert_eq!(c.datos[2], 99);          // ✅ pasa: `cargo test` da verde
}

⚠️ La limitación que define cómo usás Miri: solo ve lo que ejecutás. Miri no es análisis estático, es un intérprete. Un UB en una rama que ningún test recorre es invisible para Miri. Y corre entre 50 y 400 veces más lento que el binario nativo, así que la suite completa puede tardar minutos u horas. La consecuencia práctica es la contraria a la intuitiva: la calidad de tu cobertura de tests determina la calidad de tu verificación de UB. Miri no reemplaza escribir tests: los vuelve mucho más valiosos.

Las otras limitaciones a tener presentes: Miri no puede ejecutar la mayoría del código FFI (llamar a una función de C compilada queda fuera de su alcance, salvo el soporte experimental de -Zmiri-native-lib); no modela el comportamiento exacto de instrucciones SIMD específicas de la plataforma; y su modelo de aliasing —Stacked Borrows / Tree Borrows— es experimental: en casos muy raros puede marcar como error un patrón que el equipo de opsem termine declarando legal. En la práctica, cuando Miri se queja, el 99% de las veces tenés un bug real.

Poné Miri en CI, pero no en el pipeline que bloquea cada push. El patrón usual es un job nocturno sobre los tests de los módulos que tienen unsafe, más una corrida obligatoria en cualquier PR que toque un archivo con bloques unsafe. Así pagás el costo de tiempo solo donde importa.

RuS5.8 unsafe impl Send y unsafe impl Sync

Send y Sync son auto traits: el compilador los implementa solo si todos los campos del tipo los tienen. Escribir unsafe impl a mano significa que estás pasando por encima de esa deducción, y lo que prometés es muy concreto:

  • Send: es seguro mover un valor de este tipo a otro hilo. Se rompe cuando el tipo depende de estado atado al hilo actual (un MutexGuard de pthread, un handle de GUI, un TLS).
  • Sync: es seguro que dos hilos tengan &T al mismo tiempo. Equivale a decir que &T es Send. Se rompe cuando hay mutabilidad interior sin sincronización.

El caso legítimo típico es un tipo que guarda un puntero crudo —que por definición no es Send ni Sync— pero cuya lógica sí garantiza la seguridad:

use std::ptr::NonNull;

/// Puntero a un bloque asignado por nosotros, del que somos dueños únicos.
pub struct BloquePropio {
    ptr: NonNull<u8>,
    largo: usize,
}

// SAFETY: `BloquePropio` es el dueño EXCLUSIVO de la asignación a la que
// apunta `ptr`: no existe otro alias en el proceso, y la memoria no está
// atada a ningún hilo (viene del allocator global). Mover el valor a otro
// hilo mueve también la propiedad de la asignación, así que es seguro.
unsafe impl Send for BloquePropio {}

// SAFETY: la API pública solo expone `&[u8]` a través de `&self` y no
// ofrece NINGUNA vía de mutación mediante referencia compartida. Por lo
// tanto dos hilos con `&BloquePropio` solo pueden leer, y leer en paralelo
// memoria inmutable no es una carrera.
unsafe impl Sync for BloquePropio {}

impl BloquePropio {
    pub fn como_slice(&self) -> &[u8] {
        // SAFETY: `ptr` es válido para `largo` bytes inicializados mientras
        // viva `self`, y el lifetime del slice está atado a `&self`.
        unsafe { std::slice::from_raw_parts(self.ptr.as_ptr(), self.largo) }
    }
}
El anti-patrón que hay que saber reconocer en un review: alguien pelea con "*mut T cannot be sent between threads safely", encuentra en un blog que unsafe impl Send lo calla, lo pega, compila, y sigue. Acaba de firmar una garantía sobre un tipo cuya lógica no analizó. Si en el unsafe impl no hay un // SAFETY: que explique qué hace que el acceso concurrente sea seguro, en el review se rechaza. Sin excepciones.
Existe la operación inversa y es safe: quitar Send/Sync agregando un campo PhantomData<*const ()> o PhantomData<std::rc::Rc<()>>. Se usa cuando tu tipo parece thread-safe por sus campos pero no lo es por su lógica. Restringir nunca requiere unsafe; ampliar, siempre.

RuS5.9 FFI: hablar con C

La interoperabilidad con C es, por lejos, el motivo más común y más legítimo para escribir unsafe. El compilador no puede saber nada sobre lo que hace una función compilada en otro lenguaje, así que toda llamada es un salto al vacío que vos tenés que respaldar.

Declarar y llamar

Supongamos esta librería C:

// suma.c
#include <stddef.h>

int sumar(int a, int b) {
    return a + b;
}

size_t contar_no_cero(const int *datos, size_t n) {
    size_t total = 0;
    for (size_t i = 0; i < n; i++) {
        if (datos[i] != 0) total++;
    }
    return total;
}

Del lado de Rust, en edición 2024:

use core::ffi::{c_int, c_void};

#[link(name = "suma")]
unsafe extern "C" {
    safe fn sumar(a: c_int, b: c_int) -> c_int;
    fn contar_no_cero(datos: *const c_int, n: usize) -> usize;
}

/// Wrapper safe: acá está la safety boundary.
pub fn contar(datos: &[c_int]) -> usize {
    // SAFETY: `datos.as_ptr()` es válido para `datos.len()` elementos
    // inicializados y correctamente alineados, y la función de C solo LEE
    // ese rango (verificado en su implementación). No retiene el puntero
    // después de retornar, así que no hay riesgo de dangling.
    unsafe { contar_no_cero(datos.as_ptr(), datos.len()) }
}

#[repr(C)]: el layout no es negociable

Rust no garantiza el orden de los campos de un struct: el compilador puede reordenarlos para minimizar el padding, y puede cambiar de criterio entre versiones. Si un struct cruza la frontera FFI, necesita un layout definido:

#[repr(C)]                       // layout idéntico al de C
pub struct Punto {
    pub x: f64,
    pub y: f64,
}

#[repr(C)]                       // enums con discriminante de tamaño C
pub enum Estado {
    Ok = 0,
    ErrorIo = 1,
    ErrorParseo = 2,
}

#[repr(transparent)]             // mismo layout que su único campo
pub struct Handle(*mut core::ffi::c_void);

// ❌ Sin repr(C), pasar esto a C es UB: el layout es "lo que decida rustc".
pub struct PuntoRust { pub x: f64, pub y: f64 }

La otra mitad del problema son los tipos que no tienen equivalente en C. Un &str es un fat pointer (dirección + largo), un Vec<T> son tres palabras, un Option<T> genérico no tiene layout garantizado, y un trait object es un puntero doble. Ninguno de esos cruza la frontera tal cual:

Strings: CStr, CString y el puntero colgado

Un String de Rust es UTF-8 con largo explícito y puede contener bytes NUL. Un string de C es una secuencia terminada en NUL sin largo. La conversión nunca es gratis, y el error clásico es este:

use std::ffi::{CStr, CString};
use core::ffi::c_char;

unsafe extern "C" {
    fn imprimir(s: *const c_char);
}

fn mal() {
    // ❌ EL ERROR CLÁSICO. El CString temporal se destruye al terminar
    // ESTA sentencia, así que `p` queda colgado antes de usarse.
    let p = CString::new("hola").unwrap().as_ptr();
    unsafe { imprimir(p); }        // UB: use-after-free
}

fn bien() {
    // ✅ El CString vive en una variable con nombre, así que sobrevive
    // hasta el final del scope.
    let c = CString::new("hola").unwrap();
    // SAFETY: `c` sigue viva en este scope, así que `c.as_ptr()` apunta a
    // una cadena terminada en NUL válida durante toda la llamada.
    unsafe { imprimir(c.as_ptr()); }
}
⚠️ Este bug compila sin un solo warning y anda "bien" en la mayoría de las corridas, porque la memoria recién liberada casi siempre todavía contiene los bytes viejos. Falla en producción, bajo carga, cuando el allocator reutiliza el bloque. Miri lo detecta al instante. Es el ejemplo número uno de por qué correr FFI bajo tests con Miri —cuando es posible— o al menos con ASan, no es opcional.

En la dirección de lectura, convertir un char * que viene de C exige asumir cosas que solo vos podés saber:

use std::ffi::CStr;
use core::ffi::c_char;

/// # Safety
/// `p` debe ser no nulo, apuntar a una secuencia de bytes terminada en NUL,
/// y esa memoria debe permanecer válida e inmutable durante toda la llamada.
pub unsafe fn leer_c_string(p: *const c_char) -> Result<String, std::str::Utf8Error> {
    // SAFETY: precondiciones delegadas al llamador por el contrato de arriba.
    let cstr = unsafe { CStr::from_ptr(p) };
    cstr.to_str().map(|s| s.to_owned())    // copia: no retenemos el puntero
}

¿Quién libera la memoria?

Es la pregunta que hay que responder antes de escribir una línea de FFI, y la respuesta correcta es siempre la misma: libera quien asignó, con el allocator que usó. El allocator de Rust y el malloc de C son distintos; pasarle a free() un puntero salido de un Box es UB, y liberar con Box::from_raw algo que asignó malloc también.

use std::ffi::CString;
use core::ffi::c_char;

/// Entrega a C una cadena asignada por Rust. C debe devolverla
/// a `cadena_liberar` — NUNCA a free().
#[unsafe(no_mangle)]
pub extern "C" fn cadena_crear(n: u32) -> *mut c_char {
    let s = format!("valor = {n}");
    match CString::new(s) {
        Ok(c) => c.into_raw(),          // cede la propiedad al llamador
        Err(_) => std::ptr::null_mut(),
    }
}

/// # Safety
/// `p` debe ser exactamente un puntero devuelto por `cadena_crear` que no
/// haya sido liberado todavía. Pasar cualquier otra cosa es UB.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn cadena_liberar(p: *mut c_char) {
    if p.is_null() { return; }
    // SAFETY: por el contrato, `p` salió de `CString::into_raw`.
    unsafe { drop(CString::from_raw(p)); }
}

Pánicos y ABI

Desde Rust 1.81, si un pánico intenta desenrollarse fuera de una función extern "C", el proceso aborta en vez de caer en UB. Es una mejora enorme, pero abortar sigue siendo un mal resultado para una librería: lo correcto es atrapar el pánico y traducirlo a un código de error.

use std::panic::{catch_unwind, AssertUnwindSafe};
use core::ffi::c_int;

#[unsafe(no_mangle)]
pub extern "C" fn procesar(datos: *const u8, n: usize) -> c_int {
    let resultado = catch_unwind(AssertUnwindSafe(|| {
        if datos.is_null() { return -1; }
        // SAFETY: el contrato documentado exige `datos` válido para `n` bytes.
        let slice = unsafe { std::slice::from_raw_parts(datos, n) };
        slice.iter().filter(|b| **b != 0).count() as c_int
    }));

    match resultado {
        Ok(v) => v,
        Err(_) => -2,        // el pánico se convierte en código de error
    }
}
Si necesitás que las excepciones de C++ o los pánicos de Rust sí crucen la frontera (por ejemplo, entre dos crates de Rust enlazados dinámicamente), existe la ABI extern "C-unwind", estabilizada en Rust 1.71. Es un caso especializado: la opción por defecto sigue siendo atrapar y traducir.

RuS5.10 Exponer Rust a otros lenguajes

La dirección inversa —Rust como el motor rápido dentro de una app escrita en otro lenguaje— es hoy uno de los usos más frecuentes del lenguaje, y la razón por la que muchos equipos lo adoptan sin migrar nada.

El caso más maduro es Python. Ya lo viste desde el otro lado en el track de Python Senior: PS8 — Producción cubre el empaquetado y despliegue de extensiones nativas. Desde Rust, la herramienta es PyO3, y lo interesante para este módulo es que vos no escribís el unsafe: la macro lo genera y lo audita por vos.

use pyo3::prelude::*;

/// Calcula la distancia de Levenshtein. Desde Python se ve como una
/// función normal; el marshalling de tipos lo genera la macro.
#[pyfunction]
fn distancia(a: &str, b: &str) -> PyResult<usize> {
    let (n, m) = (a.chars().count(), b.chars().count());
    let mut fila: Vec<usize> = (0..=m).collect();

    for (i, ca) in a.chars().enumerate() {
        let mut previo = fila[0];
        fila[0] = i + 1;
        for (j, cb) in b.chars().enumerate() {
            let costo = usize::from(ca != cb);
            let nuevo = (fila[j + 1] + 1)
                .min(fila[j] + 1)
                .min(previo + costo);
            previo = fila[j + 1];
            fila[j + 1] = nuevo;
        }
    }
    let _ = n;
    Ok(fila[m])
}

#[pymodule]
fn textotools(m: &Bound<'_, PyModule>) -> PyResult<()> {
    m.add_function(wrap_pyfunction!(distancia, m)?)?;
    Ok(())
}

RuS5.11 Cuándo NO usar unsafe (la sección más importante)

Si te quedás con una sola idea de todo el módulo, que sea esta: la enorme mayoría de los unsafe que se escriben no hacían falta. Hay una alternativa segura, y suele ser tan rápida que la diferencia no se mide.

Estas son las cuatro excusas que aparecen en los code reviews, con su reemplazo:

"Necesito unsafe porque..."Alternativa segura
...tengo que evitar el chequeo de límitesIteradores, chunks_exact, zip: el compilador elimina el chequeo solo
...necesito dos referencias mutables al mismo Vecsplit_at_mut, iter_mut, get_disjoint_mut
...necesito mutabilidad interiorCell, RefCell, Mutex, RwLock, atómicos
...tengo una estructura cíclica / grafoÍndices en un Vec (arena), o Rc/Weak
...necesito un global mutableOnceLock, LazyLock, atómicos, Mutex estático

El primer caso merece una demostración, porque es el que se repite más. La creencia es que indexar cuesta caro por el chequeo de límites y que get_unchecked lo arregla:

// ❌ La versión "optimizada" con unsafe
pub fn sumar_unsafe(a: &[f32], b: &[f32]) -> f32 {
    let mut total = 0.0;
    for i in 0..a.len() {
        // SAFETY: dudosa — depende de que b.len() >= a.len(), que NO se chequea.
        total += unsafe { *a.get_unchecked(i) * *b.get_unchecked(i) };
    }
    total
}

// ✅ La versión segura: `zip` le prueba al compilador que los índices son
// válidos, así que genera el MISMO código máquina y encima vectoriza mejor.
pub fn sumar_safe(a: &[f32], b: &[f32]) -> f32 {
    a.iter().zip(b).map(|(x, y)| x * y).sum()
}

La versión safe no solo iguala a la unsafe: en muchos casos la supera, porque un iterador le da a LLVM garantías estructurales sobre el recorrido que un bucle con índices no le da. Y de paso, la versión unsafe tiene un bug de seguridad real: si b es más corto que a, lee fuera de rango.

La performance hay que medirla, no suponerla

📌 Un unsafe justificado por rendimiento y sin benchmark adjunto es un unsafe injustificado. El orden es siempre: escribir la versión segura, medirla con un benchmark reproducible, perfilar para saber dónde se va el tiempo, y recién ahí —si el hotspot está confirmado y la mejora es sustancial— evaluar unsafe. Si hiciste los pasos en otro orden, no estás optimizando: estás adivinando con riesgo.

El costo que nadie contabiliza

Supongamos que medís y el unsafe te da un 30% real en un hotspot real. Sigue faltando la otra mitad de la ecuación, la que no aparece en el benchmark:

  • Cada PR que toca ese archivo necesita un revisor que entienda el modelo de memoria. En un equipo de ocho personas, eso puede ser una o dos. Se convierte en un cuello de botella permanente.
  • El invariante es global al módulo, no local al bloque. Un unsafe correcto se puede romper por un cambio en un campo privado, hecho seis meses después por alguien que no sabía que existía la dependencia. Esa es la razón por la que el "unsafe superblock" del módulo es la unidad real de auditoría.
  • Los bugs que produce son de la clase más cara de diagnosticar. No se reproducen, dependen del nivel de optimización y desaparecen bajo el debugger.
  • La suite necesita correr bajo Miri, con el costo de CI y de mantenimiento que eso implica.

Frente a eso, un 30% en un hotspot que representa el 5% del tiempo total del programa es una mejora del 1,5% end-to-end. Vale la pena preguntarse si no había un algoritmo mejor, o si el tiempo del equipo no rendía más en otro lado.

Cuando te toca leer un bloque de unsafe ajeno, esta es la checklist:

  1. ¿Hay un // SAFETY:, y enuncia un invariante concreto? Si dice "es seguro", empezá a desconfiar.
  2. ¿Existe alguna secuencia de llamadas safe públicas que rompa el invariante? Esta es la pregunta central: probá mentalmente el caso vacío, el caso lleno, el índice del borde y el reentrante.
  3. ¿Qué pasa si algo hace pánico a mitad del bloque? ¿Queda el tipo en un estado inconsistente que después alguien va a leer? (exception safety: el error más sutil de todos.)
  4. ¿El bloque abarca más operaciones de las necesarias? Un unsafe { } de veinte líneas casi siempre esconde dos operaciones peligrosas y dieciocho inocentes.
  5. ¿La suite del proyecto corre bajo Miri? Mirá el CI. Si el crate tiene mucho unsafe y no corre Miri, es una señal fuerte.
  6. ¿Los tests cubren los caminos que ejecutan el unsafe? Recordá: Miri solo ve lo que se ejecuta.

[lints.rust]
unsafe_code = "forbid"

# Si un módulo lo necesita, se usa "deny" (que un módulo puede permitir
# explícitamente con #[allow]) en vez de "forbid" (que no se puede levantar).

RuS5.13 Worked example: buffer circular "por rendimiento"

Vamos a hacer el recorrido completo, tal como pasa en un proyecto real: escribir una versión segura, escribir una versión unsafe "porque va a ser más rápida", ver que los tests pasan, correr Miri, encontrar UB, arreglarlo, y medir. El final es la lección.

Paso 1 — La versión segura

// src/ring_safe.rs
pub struct RingSafe<T> {
    buf: Vec<Option<T>>,
    cabeza: usize,
    cola: usize,
    largo: usize,
}

impl<T> RingSafe<T> {
    pub fn nuevo(cap: usize) -> Self {
        assert!(cap > 0, "la capacidad debe ser positiva");
        let mut buf = Vec::with_capacity(cap);
        buf.resize_with(cap, || None);
        Self { buf, cabeza: 0, cola: 0, largo: 0 }
    }

    pub fn push(&mut self, v: T) -> Result<(), T> {
        if self.largo == self.buf.len() { return Err(v); }
        self.buf[self.cola] = Some(v);
        self.cola = (self.cola + 1) % self.buf.len();
        self.largo += 1;
        Ok(())
    }

    pub fn pop(&mut self) -> Option<T> {
        if self.largo == 0 { return None; }
        let v = self.buf[self.cabeza].take();
        self.cabeza = (self.cabeza + 1) % self.buf.len();
        self.largo -= 1;
        v
    }

    pub fn len(&self) -> usize { self.largo }
    pub fn is_empty(&self) -> bool { self.largo == 0 }
}

Funciona, es imposible de romper y no tiene un solo unsafe. Sus dos costos reales: cada elemento paga el espacio del discriminante de Option<T>, y cada push/pop paga un chequeo de límites más una operación de módulo.

Paso 2 — La versión unsafe (con el bug adentro)

// src/ring_unsafe.rs
use std::mem::MaybeUninit;

pub struct RingRaw<T> {
    buf: Box<[MaybeUninit<T>]>,
    mascara: usize,        // cap - 1, con cap potencia de dos → módulo por AND
    cabeza: usize,
    cola: usize,
    largo: usize,
}

impl<T> RingRaw<T> {
    pub fn nuevo(cap: usize) -> Self {
        assert!(cap.is_power_of_two(), "la capacidad debe ser potencia de dos");
        let mut v = Vec::with_capacity(cap);
        v.resize_with(cap, MaybeUninit::uninit);
        Self {
            buf: v.into_boxed_slice(),
            mascara: cap - 1,
            cabeza: 0, cola: 0, largo: 0,
        }
    }

    pub fn push(&mut self, v: T) -> Result<(), T> {
        if self.largo == self.buf.len() { return Err(v); }
        let i = self.cola;
        // 🐛 EL BUG: `as_ptr()` devuelve un puntero de SOLO LECTURA derivado
        // de un préstamo compartido. Castearlo a *mut no le suma permisos.
        let p = self.buf.as_ptr() as *mut MaybeUninit<T>;
        // SAFETY: creemos que basta con que el índice esté en rango. No basta.
        unsafe { (*p.add(i)).write(v); }
        self.cola = (self.cola + 1) & self.mascara;
        self.largo += 1;
        Ok(())
    }

    pub fn pop(&mut self) -> Option<T> {
        if self.largo == 0 { return None; }
        let i = self.cabeza;
        // SAFETY: la posición `i` está inicializada porque largo > 0 y solo
        // se leen posiciones escritas por `push`. `assume_init_read` mueve
        // el valor afuera y deja el hueco lógicamente vacío.
        let v = unsafe { self.buf[i].assume_init_read() };
        self.cabeza = (self.cabeza + 1) & self.mascara;
        self.largo -= 1;
        Some(v)
    }

    pub fn len(&self) -> usize { self.largo }
}

impl<T> Drop for RingRaw<T> {
    fn drop(&mut self) {
        // Hay que destruir SOLO los elementos vivos: los demás nunca existieron.
        while self.pop().is_some() {}
    }
}

Con esa información, el optimizador puede cachear una lectura en un registro, hoistear una carga fuera del bucle, o reordenar accesos. Hoy el binario sale bien; con -C lto=fat y ese push inlineado dentro de un bucle caliente, puede dejar de estarlo — sin que ningún test cambie.

Paso 5 — El arreglo

pub fn push(&mut self, v: T) -> Result<(), T> {
    if self.largo == self.buf.len() { return Err(v); }
    let i = self.cola;
    // ✅ `as_mut_ptr` deriva de `&mut self`: el puntero SÍ tiene permiso
    // de escritura sobre toda la asignación.
    let p = self.buf.as_mut_ptr();
    // SAFETY: `i < buf.len()` porque `largo < buf.len()` y `cola` siempre
    // se mantiene enmascarado con `mascara == len - 1`. El puntero viene de
    // `&mut self`, así que tiene permiso de escritura, y no hay otro alias
    // vivo de esta asignación mientras dure la llamada.
    unsafe { (*p.add(i)).write(v); }
    self.cola = (self.cola + 1) & self.mascara;
    self.largo += 1;
    Ok(())
}

¿Por qué la ganancia fue tan chica? Porque LLVM ya estaba haciendo casi todo el trabajo: el chequeo de límites de self.buf[i] se elimina cuando el optimizador puede probar que el índice está en rango, y el módulo por una potencia de dos se compila al mismo AND que escribimos a mano. Ninguna de esas condiciones aparece por defecto: hay que ir a buscarlas con un profiler antes de escribir la primera línea de unsafe.

Checkpoint — ¿lo tenés claro?

Si unsafe no desactiva el borrow checker, ¿qué desactiva exactamente?

Nada: habilita cinco operaciones que fuera de un bloque unsafe son un error de compilación — desreferenciar punteros crudos, llamar funciones unsafe, implementar traits unsafe, acceder a static mut y leer campos de union. Todo lo demás sigue chequeado igual: ownership, borrowing, lifetimes, tipos, Drop. Lo que sí cambia es de quién es la responsabilidad de mantener los invariantes de esas cinco operaciones: pasa del compilador a vos, y por eso todo bloque lleva un // SAFETY: que enuncia el invariante concreto del que te hacés cargo.

Tus tests pasan y tenés 90% de cobertura. ¿Alcanza para afirmar que tu código unsafe no tiene UB?

No, por dos razones distintas. Primero, un test verde no dice nada sobre UB: el ejemplo de as_ptr() as *mut del worked example pasó tres tests, incluido el del wrap-around, y era UB en cada llamada — el síntoma aparece recién cuando el optimizador aprovecha la suposición que rompiste. Segundo, aun corriendo Miri, Miri solo ve lo que ejecutás: un UB en una rama que ningún test recorre es invisible. La afirmación defendible es "no encontré UB en los caminos que mis tests cubren bajo Miri, con estos flags", que es bastante más modesta y bastante más honesta.

Un compañero justifica un unsafe diciendo "es 30% más rápido". ¿Qué preguntás?

Cuatro cosas, en orden. (1) ¿Dónde está el benchmark? — sin número reproducible, el 30% es una suposición. (2) ¿El 30% de qué fracción del tiempo total? — un 30% sobre un hotspot que pesa el 3% end-to-end es un 0,9%. (3) ¿Cuál es el invariante y puede romperse desde la API pública? — si existe alguna secuencia de llamadas safe que cause UB, la API está rota sin importar la velocidad. (4) ¿Corre bajo Miri, y los tests cubren los caminos que ejecutan el bloque? Y aunque las cuatro respuestas sean buenas, queda el costo permanente: cada PR sobre ese módulo va a necesitar un revisor que entienda el modelo de memoria.

Resumen ejecutivo

  • unsafe no da permisos, transfiere obligaciones: las reglas son las mismas, cambia quién las verifica.
  • Habilita exactamente cinco cosas: desreferenciar punteros crudos, llamar unsafe fn, hacer unsafe impl, tocar static mut y leer campos de union. El resto de Rust sigue chequeado.
  • El diseño correcto es la safety boundary: encapsular el unsafe en una API safe que sea imposible de romper desde afuera, y documentar cada bloque con // SAFETY:.
  • UB no es un bug: el compilador optimiza asumiendo que no ocurre, así que el síntoma aparece lejos, cambia con el nivel de optimización y desaparece bajo el debugger.
  • Los seis UB frecuentes: dangling, aliasing de &mut, memoria no inicializada, desalineación, valores inválidos y data races. Overflow y fugas no son UB.
  • Un puntero lleva provenance, no solo una dirección. Usá addr(), map_addr() y with_exposed_provenance() en vez de castear a usize.
  • MaybeUninit<T> es el tipo honesto para memoria sin inicializar; mem::uninitialized() está deprecado desde 1.39 porque su firma mentía.
  • Miri detecta UB en runtime y es la herramienta central del módulo — con una limitación que define cómo se usa: solo ve lo que ejecutás, así que tu cobertura de tests es tu cobertura de verificación.
  • La edición 2024 endureció el terreno: unsafe_op_in_unsafe_fn, unsafe extern, #[unsafe(no_mangle)] y static_mut_refs como error.
  • En FFI, respondé quién libera antes de escribir código; el error clásico es el CString temporal cuyo as_ptr() queda colgado en la misma línea.
  • Casi siempre hay una alternativa segura, y suele ser igual de rápida. La performance se mide antes, no se supone: el worked example ganó 4,2% a cambio de tres bloques unsafe, un UB y Miri en CI.

🧠 Autoevaluación

1. Metés un préstamo conflictivo adentro de un bloque unsafe y el compilador lo sigue rechazando. ¿Por qué?

unsafe habilita desreferenciar punteros crudos, llamar funciones unsafe, hacer unsafe impl, tocar static mut y leer campos de union. Nada más. Ownership, borrowing y lifetimes se siguen chequeando idénticamente adentro y afuera del bloque. Si necesitás eludir el borrow checker, la vía es pasar por punteros crudos —y ahí sos vos quien tiene que garantizar el aliasing, que es exactamente la obligación que unsafe te transfiere.

2. Tu suite de tests pasa bajo cargo +nightly miri test sin errores. ¿Qué podés afirmar?

Miri es un intérprete, no un análisis estático: solo observa el código que efectivamente se ejecuta. Un bloque unsafe en una rama que ningún test recorre le es invisible, y su modelo de aliasing depende de los flags (-Zmiri-strict-provenance, -Zmiri-tree-borrows). Además Miri no puede ejecutar la mayoría del código FFI, así que sobre la frontera con C no dice casi nada. La conclusión práctica: tu cobertura de tests es tu cobertura de verificación de UB.

3. Reescribiste un hotspot con unsafe y el benchmark da 4% de mejora. ¿Cuál es la lectura correcta?

El 4% es solo un lado de la balanza. Del otro lado hay costos que no aparecen en el benchmark: cada PR sobre ese módulo necesita un revisor que entienda el modelo de memoria, el invariante es global al módulo y se puede romper meses después desde un cambio aparentemente inocente, los bugs que produce dependen del nivel de optimización y no se reproducen, y la suite pasa a necesitar Miri en CI. Además, un 4% sobre un hotspot que pesa el 5% del tiempo total es un 0,2% end-to-end. El unsafe se justifica cuando un profiler muestra un cuello de botella dominante y la ganancia medida es sustancial — no antes.

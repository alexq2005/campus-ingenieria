RuS4 — Tokio en producción

RuS4.0 Por qué este módulo

En RuS3 desarmaste el Future: viste que async fn compila a una máquina de estados, que poll devuelve Pending o Ready, que el Waker es el mecanismo que avisa cuándo volver a intentar, y que Pin existe porque esas máquinas de estados se autoreferencian. Sabés cómo funciona un future. Lo que todavía no sabés es lo que separa un prototipo de un servicio: quién llama a poll, sobre qué hilos, con qué política, y qué pasa cuando eso se hace mal.

💡 La tesis del módulo. En Rust el lenguaje te da el Future, pero no te da el ejecutor. Esa decisión de diseño —única entre los lenguajes con async— significa que el comportamiento en producción de tu servicio no está definido por el compilador sino por una librería que elegís vos. Casi todos los incidentes serios de un servicio async en Rust no son bugs del lenguaje ni de tu lógica: son desencuentros entre lo que tu código asume del runtime y lo que el runtime realmente hace. Bloquear un worker, sostener un lock a través de un await, perder datos en un select!, spawnear sin límite. Nada de eso lo detecta el borrow checker.

Y hay una razón de coyuntura para estudiarlo ahora. El ecosistema async de Rust pasó cinco años fragmentado, y en 2026 terminó de consolidarse: hay un ganador claro, hay un perdedor que fue oficialmente discontinuado con aviso de seguridad, y hay un cambio de arquitectura en el horizonte (io_uring) que va a mover los números de I/O de forma importante. Todo eso cambia qué recomendás, qué leés y qué escribís. Este módulo asume Rust 1.95 y edición 2024.

RuS4.1 El estado del ecosistema en 2026

Durante mucho tiempo la respuesta honesta a "qué runtime uso" era "depende". Ya no lo es. Tokio ganó, y ganó por goleada: alrededor de 150 millones de descargas por mes en crates.io, y —lo que importa más— es la dependencia de facto de casi todo el stack de red: hyper, axum, tonic, reqwest, sqlx, aws-sdk-rust, rdkafka, lapin. Si tu servicio habla HTTP, gRPC o con una base de datos, ya estás corriendo sobre Tokio aunque no lo hayas escrito.

📌 La regla práctica de 2026: usá Tokio salvo que tengas un motivo escrito para no hacerlo. "Es más liviano" no es un motivo si igual vas a depender de reqwest. RuS4.2 El runtime: dos formas, dos contratos

Tokio no es "un" runtime: son dos schedulers distintos con propiedades muy distintas, y elegir el equivocado es una de las decisiones que después cuesta caro revertir.

tokio-util = { version = "0.7", features = ["rt"] }   # CancellationToken, codecs
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }

Multi-thread: el default

use tokio::runtime::Builder;

fn main() -> anyhow::Result<()> {
    let rt = Builder::new_multi_thread()
        .worker_threads(8)               // default: núcleos disponibles
        .max_blocking_threads(512)       // default: 512 (pool aparte)
        .thread_name("api-worker")
        .enable_all()                    // timers + I/O reactor
        .build()?;

    rt.block_on(async {
        servir().await
    })
}

// Equivalente declarativo, que es lo que vas a ver el 95% de las veces:
// #[tokio::main]
// async fn main() -> anyhow::Result<()> { servir().await }

El scheduler multi-thread usa work stealing. Cada worker tiene una cola local de capacidad fija (256 tareas). Cuando spawneás, la tarea va a la cola local del worker que la creó; si esa cola está llena, la mitad se vuelca a una cola global (injector). Cuando un worker se queda sin trabajo, primero mira su cola local, después la global, y si sigue vacío le roba la mitad de la cola a otro worker elegido al azar. Hay además una ranura LIFO especial: la última tarea despertada por el worker actual se ejecuta primero, lo cual es una optimización enorme para el patrón "mandar un mensaje y que el otro lado responda", porque los datos siguen calientes en la caché de ese núcleo.

Este diseño explica dos cosas que confunden. Primero: una tarea puede migrar de hilo entre dos await, por eso tokio::spawn exige Send. Segundo: el trabajo no se reparte equitativamente por diseño, se reparte por robo reactivo, así que un worker atascado no libera sus tareas ya encoladas — nadie le puede robar mientras él no vuelva al bucle del scheduler. Guardá esa frase, es la raíz de la mitad de los incidentes de este módulo.

Current-thread: un solo hilo, cero sincronización

use std::rc::Rc;
use tokio::task::LocalSet;

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let local = LocalSet::new();

    local.run_until(async {
        // Rc NO es Send: en el runtime multi-thread esto ni compila.
        let compartido = Rc::new(vec![1_u32, 2, 3]);
        let copia = Rc::clone(&compartido);

        tokio::task::spawn_local(async move {
            println!("suma = {}", copia.iter().sum::<u32>());
        })
        .await
        .unwrap();
    })
    .await;
}

El runtime current_thread corre todas las tareas en el hilo que llamó a block_on. No hay robo, no hay migración, no hay atómicos en el camino caliente del scheduler. Eso lo hace más rápido por operación y más predecible, y habilita futures !Send vía spawn_local y LocalSet.

El patrón "un runtime por núcleo" (thread-per-core). Algunos servicios de latencia extrema —bases de datos, proxies, sistemas de trading— arrancan N runtimes current_thread, uno pineado a cada núcleo, con SO_REUSEPORT para que el kernel reparta las conexiones. Ganás: cero robo, cero migración, estructuras !Send por shard, colas de latencia mucho más chatas. Perdés: si un shard se desbalancea, nadie lo ayuda. Es una arquitectura, no un flag; no la adoptes sin medir que el work stealing te esté costando de verdad.
Error clásico en tests. #[tokio::test] usa current_thread por defecto. Un test que "pasa siempre" ahí puede fallar en producción porque nunca ejercitó la migración entre hilos ni la contención real. Si tu código va a correr en multi-thread, al menos algunos tests deberían usar #[tokio::test(flavor = "multi_thread", worker_threads = 4)].

RuS4.3 Tareas: qué es realmente un spawn

Una tarea de Tokio no es un hilo. Es una máquina de estados en el heap más un puntero al scheduler. Confundir las dos cosas lleva a diseños equivocados en ambas direcciones: gente que evita spawnear "porque es caro" y gente que spawnea un millón de tareas sin pensar en la memoria.

use tokio::task::JoinHandle;

async fn procesar(id: u64) -> anyhow::Result<usize> {
    let cuerpo = reqwest::get(format!("https://api.local/items/{id}"))
        .await?
        .bytes()
        .await?;
    Ok(cuerpo.len())
}

#[tokio::main]
async fn main() {
    // spawn exige: Future + Send + 'static, y Output: Send + 'static
    let h: JoinHandle<anyhow::Result<usize>> = tokio::spawn(procesar(42));

    // JoinHandle ES un Future. Resuelve a Result<T, JoinError>.
    match h.await {
        Ok(Ok(n))    => println!("ok, {n} bytes"),
        Ok(Err(e))   => eprintln!("la tarea corrió y falló: {e}"),
        Err(je) if je.is_panic()     => eprintln!("la tarea entró en pánico"),
        Err(je) if je.is_cancelled() => eprintln!("la tarea fue abortada"),
        Err(e)       => eprintln!("otro JoinError: {e}"),
    }
}
📌 Hay dos niveles de Result y confundirlos es un bug real. El Result de afuera es del join: dice si la tarea terminó normalmente, si entró en pánico o si fue abortada. El de adentro es el valor que devolvió tu función. Un h.await.unwrap() convierte un pánico de una tarea en un pánico de otra tarea, y ahí es donde los stack traces dejan de servir. Manejá los dos niveles por separado y logueá el JoinError con su causa.

El tamaño de la máquina de estados es tuyo, no de Tokio. Si tu async fn tiene un [u8; 65536] vivo a través de un await, ese buffer viaja dentro de la tarea y cada instancia pesa 64 KiB. Con 10.000 tareas son 640 MB. La solución no es dejar de spawnear: es sacar el buffer del estado (asignarlo dentro del scope corto, o usar un pool). cargo +nightly rustc -- -Zprint-type-sizes te muestra el tamaño real de cada future.

El detalle que muerde: soltar el JoinHandle no cancela

// Esto NO cancela nada: la tarea queda corriendo, huérfana.
tokio::spawn(async {
    limpieza_larga().await;   // sigue viva aunque nadie la espere
});

// Y si entra en pánico, el pánico se queda adentro del JoinError
// que nadie lee: el servicio pierde una función y no se entera.
Tokio no tiene concurrencia estructurada. Soltar el JoinHandle desvincula (detach) la tarea: sigue corriendo hasta que termina sola o hasta que se cae el runtime. Esto es distinto de lo que hacen Swift o Kotlin, donde el scope padre cancela a los hijos. Consecuencia práctica: si spawneás y tirás el handle, aceptaste que esa tarea puede seguir viva después de que su "dueño" murió, y que un pánico adentro va a ser invisible. Las dos herramientas para evitarlo son JoinSet (RuS4.9) y CancellationToken (RuS4.5).

RuS4.4 spawn_blocking: el pecado original del async

Este es, con distancia, el error número uno en servicios async de Rust. Y es traicionero porque el código compila, los tests pasan, y el problema aparece solo bajo carga.

// 🔴 MAL: una operación sincrónica larga adentro de una tarea async.
async fn manejar(req: Peticion) -> Respuesta {
    let datos = leer_de_red(&req).await;          // ok, cede el worker

    // Estas tres NO ceden. Mientras corren, el worker está secuestrado:
    let comprimido = zstd::encode_all(&datos[..], 19).unwrap();  // ~18 ms de CPU
    let hash       = argon2_hash(&req.password);                 // ~120 ms
    let cfg        = std::fs::read_to_string("/etc/app.toml");    // syscall bloqueante

    Respuesta::nueva(comprimido, hash, cfg)
}
🚨 Por qué esto congela otras tareas. El scheduler de Tokio es cooperativo: solo puede cambiar de tarea en un punto await que devuelve Pending. Mientras tu función corre CPU sin ceder, el worker está adentro de un único poll y no vuelve al bucle del scheduler. No puede atender su cola local, no puede sacar de la global, y —clave— nadie le puede robar el trabajo que ya tiene encolado, porque el robo también lo ejecutan workers y este está ocupado. Con worker_threads = 8, ocho peticiones simultáneas con Argon2 de 120 ms dejan el runtime entero muerto durante 120 ms: no se aceptan conexiones nuevas, no corren los timers, el /health da timeout y el balanceador te saca del pool. 
// Demostración mínima: 4 workers, 4 tareas que bloquean, y un "latido"

#[tokio::main(flavor = "multi_thread", worker_threads = 4)]

La corrección

// 🟢 BIEN: el trabajo bloqueante va al pool de bloqueo.
async fn manejar(req: Peticion) -> anyhow::Result<Respuesta> {
    let datos = leer_de_red(&req).await;

    let comprimido = tokio::task::spawn_blocking(move || {
        zstd::encode_all(&datos[..], 3)
    })
    .await??;    // primer ? = JoinError, segundo ? = el error de zstd

    let pass = req.password.clone();
    let hash = tokio::task::spawn_blocking(move || argon2_hash(&pass)).await?;

    // Para archivos, mejor la API async nativa que ya usa el pool por dentro:
    let cfg = tokio::fs::read_to_string("/etc/app.toml").await?;

    Ok(Respuesta::nueva(comprimido, hash, cfg))
}

spawn_blocking manda la clausura a un pool de hilos separado, que por defecto crece hasta max_blocking_threads = 512 y recicla hilos ociosos a los 10 segundos. Los workers del runtime quedan libres para seguir haciendo I/O. Es el pool que usan por dentro tokio::fs y las resoluciones DNS.

📌 spawn_blocking no crea CPU de la nada. Es la trampa del arreglo a medias: mover la compresión al pool de bloqueo hace que el runtime siga respondiendo, pero si la operación es CPU-bound seguís teniendo el mismo número de núcleos. Con 8 cores y 18 ms de CPU por request, el techo es ~444 req/s, esté donde esté el trabajo. spawn_blocking arregla la starvation; el throughput lo arreglás bajando el costo, limitando la concurrencia o agregando máquinas. block_in_place es la excepción, no la regla. tokio::task::block_in_place convierte al worker actual en hilo de bloqueo y avisa al scheduler que mueva el resto de sus tareas a otros workers. Sirve cuando no podés mover el trabajo por un problema de tipos (datos !Send ya en la tarea). Tiene tres letras chicas: solo existe en el runtime multi-thread (en current_thread hace panic!), no ayuda si todos los workers lo hacen a la vez, y sigue costando la redistribución. El presupuesto cooperativo

// Un bucle "async" puede igual monopolizar el worker si nunca devuelve Pending.
async fn drenar(mut rx: tokio::sync::mpsc::Receiver<Msg>) {
    while let Some(m) = rx.recv().await {
        procesar_rapido(&m);      // 5 µs, pero el canal siempre tiene datos
    }
    // Sin el "coop budget" esto no cedería nunca.
}

// Si escribís un bucle CPU largo y querés portarte bien, cedé a mano:
async fn sumar_mucho(v: &[u64]) -> u64 {
    let mut acc = 0;
    for (i, x) in v.iter().enumerate() {
        acc += *x;
        if i % 8192 == 0 { tokio::task::yield_now().await; }
    }
    acc
}

Tokio le da a cada tarea un presupuesto de ~128 operaciones de recurso por poll. Cuando se agota, las operaciones de Tokio (canales, sockets, mutex) empiezan a devolver Pending aunque tengan datos listos, forzando a la tarea a ceder. Eso evita que un consumidor rápido con una cola siempre llena mate a sus vecinos. Pero el presupuesto solo cuenta operaciones de Tokio: un bucle de puro cómputo no lo toca, y ahí tenés que llamar a yield_now vos.

RuS4.5 Cancelación: abortar, expirar, y no corromper nada

En RuS3 viste el mecanismo: cancelar un future en Rust es simplemente dejar de llamar a poll y dropearlo. Es barato y es instantáneo. También es la fuente de una clase de bugs que no existe en otros lenguajes, porque el punto de cancelación es cualquier await, y el estado a medio construir se va con el Drop.

Tres herramientas, tres alcances

use std::time::Duration;
use tokio::time::{timeout, error::Elapsed};

// 1) abort(): matar una tarea concreta desde afuera.
let h = tokio::spawn(async { trabajo_largo().await });
h.abort();                       // se cancela en su próximo punto de await
match h.await {
    Err(e) if e.is_cancelled() => println!("abortada, como pedimos"),
    otro => println!("terminó antes de que llegara el abort: {otro:?}"),
}

// 2) timeout(): ponerle un límite a una operación.
let r: Result<Vec<u8>, Elapsed> =
    timeout(Duration::from_millis(300), bajar_archivo()).await;

match r {
    Ok(bytes) => println!("{} bytes", bytes.len()),
    Err(_)    => println!("expiró: el future ya fue dropeado"),
}
abort() sobre un spawn_blocking casi no hace nada. Si la tarea bloqueante todavía no arrancó, se descarta de la cola. Si ya está corriendo, no hay forma de interrumpirla: no hay puntos de await donde soltarla, y Tokio no va a matar el hilo. Por eso las operaciones bloqueantes largas necesitan su propio mecanismo de cancelación cooperativa: un AtomicBool que la clausura chequee cada tanto, o la API de cancelación de la librería subyacente. 
use tokio_util::sync::CancellationToken;

// 3) CancellationToken: cancelación jerárquica y explícita.
#[tokio::main]
async fn main() {
    let raiz = CancellationToken::new();

    for id in 0..4 {
        let hijo = raiz.child_token();     // cancelar la raíz cancela a todos
        tokio::spawn(async move {
            loop {
                tokio::select! {
                    // Rama de cancelación SIEMPRE primero: se lee mejor
                    // y con `biased` tendría prioridad estricta.
                    _ = hijo.cancelled() => {
                        tracing::info!(id, "cierre pedido, liberando");
                        break;
                    }
                    trabajo = siguiente_item(id) => {
                        procesar(trabajo).await;
                    }
                }
            }
        });
    }

    tokio::signal::ctrl_c().await.unwrap();
    raiz.cancel();                          // avisa a todo el árbol de una
}

Cancel safety: la trampa que corrompe estado en silencio

Acá está el tema más difícil de todo el módulo, y el que más caro sale. tokio::select! poliea varios futures y, cuando uno termina, dropea todos los demás a mitad de camino. Si alguno de esos futures tenía estado adentro suyo, ese estado se va a la basura.

use tokio::io::AsyncReadExt;

// 🔴 INCORRECTO: read_exact NO es cancel-safe.
async fn servir(mut sock: tokio::net::TcpStream, tok: CancellationToken) {
    let mut cabecera = [0u8; 8];
    loop {
        tokio::select! {
            _ = tok.cancelled() => break,

            r = sock.read_exact(&mut cabecera) => {
                // Si `tok.cancelled()` gana mientras read_exact ya leyó 5 de 8
                // bytes, el future se dropea. Esos 5 bytes YA salieron del socket
                // y viven en el estado del future que acabamos de tirar.
                // Se perdieron. En la próxima vuelta el protocolo queda desfasado
                // y vas a parsear basura, sin ningún error visible.
                if r.is_err() { break; }
                manejar(&cabecera).await;
            }
        }
    }
}
use futures::StreamExt;
use tokio_util::codec::{Framed, LengthDelimitedCodec};

// 🟢 CORRECTO (opción A): que el estado viva FUERA del future.
// Framed guarda el buffer parcial en el codec, no en el future de `next()`.
// Por eso `StreamExt::next` sí es cancel-safe acá.
async fn servir(sock: tokio::net::TcpStream, tok: CancellationToken) {
    let mut frames = Framed::new(sock, LengthDelimitedCodec::new());
    loop {
        tokio::select! {
            _ = tok.cancelled() => break,

            Some(marco) = frames.next() => {
                match marco {
                    Ok(bytes) => manejar(&bytes).await,
                    Err(e)    => { tracing::warn!(%e, "marco inválido"); break; }
                }
            }
            else => break,   // el stream se terminó
        }
    }
}
// 🟢 CORRECTO (opción B): pinear el future AFUERA del loop, para que
// sobreviva entre iteraciones y se siga poleando desde donde iba.
async fn con_pin(mut sock: tokio::net::TcpStream, tok: CancellationToken) {
    let mut buf = [0u8; 8];
    let lectura = sock.read_exact(&mut buf);
    tokio::pin!(lectura);        // ahora es un &mut a un future estable

    loop {
        tokio::select! {
            _ = tok.cancelled() => break,
            r = &mut lectura => {
                // Al polear `&mut lectura`, si el select pierde esta rama
                // el future NO se dropea: sigue vivo con sus 5 bytes adentro.
                if r.is_ok() { manejar(&buf).await; }
                break;
            }
        }
    }
}

Antes de meter cualquier future en un select!, buscá la frase "Cancel safety" en su documentación de Tokio — está literalmente documentado método por método. Y si escribís una async fn propia que va a vivir en un select!, documentá vos si es cancel-safe o no. Esa línea de doc vale más que un test.

RuS4.6 Sincronización: tokio::sync no reemplaza a std::sync

Es muy común ver código que importa tokio::sync::Mutex en todos lados "porque estamos en async". Está mal, y cuesta rendimiento medible.

use std::sync::{Arc, Mutex};

// 🟢 Lo normal: el Mutex de std, tomado y soltado sin cruzar un await.
#[derive(Clone)]
struct Metricas(Arc<Mutex<Contadores>>);

impl Metricas {
    fn sumar(&self, ruta: &str) {
        let mut g = self.0.lock().unwrap();
        *g.por_ruta.entry(ruta.to_string()).or_insert(0) += 1;
    }   // el guard muere acá: la sección crítica son nanosegundos
}

    m.sumar(&req.ruta);                    // sin await adentro del lock
    let cuerpo = consultar_db(req).await;  // el lock ya se soltó
    Respuesta::nueva(cuerpo)
}
// 🔴 Esto NO COMPILA, y está bien que no compile.
async fn roto(m: Arc<Mutex<Estado>>) {
    let g = m.lock().unwrap();
    guardar_en_db(&*g).await;    // el guard sigue vivo cruzando el await
    drop(g);
}

//   within this `async fn`, the trait `Send` is not implemented for

    g.escribir(msg).await?;          // el protocolo exige exclusión durante el await
    g.leer_ack().await?;
    Ok(())
}

RuS4.7 Los canales, y cuál usar

tokio::sync trae cuatro canales que se parecen y sirven para cosas distintas. Elegir mal el canal es una fuente silenciosa de pérdida de mensajes o de crecimiento de memoria.

use tokio::sync::mpsc;

// mpsc: muchos productores, UN consumidor. El caballito de batalla.
#[tokio::main]
async fn main() {
    let (tx, mut rx) = mpsc::channel::<Trabajo>(128);   // ACOTADO: 128 en vuelo

    for id in 0..4 {
        let tx = tx.clone();
        tokio::spawn(async move {
            for t in generar(id) {
                // send().await espera si el canal está lleno: eso ES backpressure.
                if tx.send(t).await.is_err() { break; }  // el receptor se fue
            }
        });
    }
    drop(tx);   // 🔑 soltar el emisor original, si no recv() nunca da None

    while let Some(t) = rx.recv().await {   // recv es cancel-safe
        procesar(t).await;
    }
    println!("todos los emisores cerraron, salimos limpio");
}
use tokio::sync::oneshot;

// oneshot: exactamente un valor. El patrón request/response de los actores.
enum Comando {
    Leer  { clave: String, resp: oneshot::Sender<Option<String>> },
    Escribir { clave: String, valor: String, resp: oneshot::Sender<()> },
}

async fn actor(mut rx: mpsc::Receiver<Comando>) {
    let mut mapa = std::collections::HashMap::new();   // sin Mutex: hay un solo dueño
    while let Some(cmd) = rx.recv().await {
        match cmd {
            Comando::Leer { clave, resp } => {
                let _ = resp.send(mapa.get(&clave).cloned());
            }
            Comando::Escribir { clave, valor, resp } => {
                mapa.insert(clave, valor);
                let _ = resp.send(());
            }
        }
    }
}

    tx.send(Comando::Leer { clave: clave.into(), resp: resp_tx }).await?;
    Ok(resp_rx.await?)
}

RuS4.8 Backpressure: por qué "una tarea por request" es un bug

El patrón más natural del mundo async es también uno de los más peligrosos:

// 🔴 Sin límite: cada conexión spawnea, y nada dice cuántas caben.
loop {
    let (sock, _) = listener.accept().await?;
    tokio::spawn(async move { manejar(sock).await });   // ¿cuántas? las que vengan
}

Bajo carga normal esto anda perfecto. Bajo un pico —o un cliente hostil, o una base de datos que se puso lenta y hace que cada request dure 20× más— el número de tareas vivas crece sin techo. Cada una tiene su buffer, su conexión a la DB, su estado. La memoria sube, el pool de la base se agota, las latencias se disparan, y el sistema no se degrada: colapsa. Un servidor con backpressure atiende 500 req/s y rechaza el resto con un 503 rápido; uno sin backpressure intenta atender 5.000 y no atiende ninguna.

use std::sync::Arc;
use tokio::sync::Semaphore;

// 🟢 Con límite duro de concurrencia.
#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let listener = tokio::net::TcpListener::bind("0.0.0.0:8080").await?;
    let cupos = Arc::new(Semaphore::new(1_000));       // techo explícito

    loop {
        let (sock, _) = listener.accept().await?;

        // acquire_owned da un permiso 'static que viaja a la tarea.
        // El permiso se devuelve solo cuando se dropea al final del scope.
        let permiso = match Arc::clone(&cupos).try_acquire_owned() {
            Ok(p)  => p,
            Err(_) => {                                 // saturado: shed load
                tracing::warn!("capacidad llena, rechazando");
                responder_503(sock).await;
                continue;
            }
        };

        tokio::spawn(async move {
            let _permiso = permiso;                     // vive lo que vive la tarea
            manejar(sock).await;
        });
    }
}
📌 try_acquire vs acquire: es una decisión de producto, no de código. acquire().await encola al cliente: la petición espera su turno. try_acquire() rechaza al toque. Encolar sirve para trabajo interno donde nadie está mirando un reloj. Rechazar sirve para tráfico de usuarios, porque una petición encolada 8 segundos ya fue abandonada del otro lado y atenderla es trabajo tirado. La combinación correcta suele ser: timeout(300ms, sem.acquire()) — esperás un poquito, y si no hay lugar devolvés 503 con Retry-After. 
// Backpressure en una cadena de procesamiento, con canales acotados.
// Cada etapa frena a la anterior cuando se llena: la presión viaja hacia atrás.
async fn pipeline() {
    let (tx_crudo, mut rx_crudo)   = tokio::sync::mpsc::channel::<Crudo>(256);
    let (tx_listo, mut rx_listo)   = tokio::sync::mpsc::channel::<Listo>(64);

    // Etapa 2: si escribir en la DB va lento, rx_listo se llena,
    // la etapa 1 se frena en su send().await, y el productor original también.
    tokio::spawn(async move {
        while let Some(item) = rx_crudo.recv().await {
            let listo = transformar(item).await;
            if tx_listo.send(listo).await.is_err() { break; }
        }
    });

    tokio::spawn(async move {
        while let Some(item) = rx_listo.recv().await {
            escribir_db(item).await;
        }
    });

    let _ = tx_crudo;   // el productor real usa este extremo
}
Limitá también hacia afuera. El backpressure no es solo defensivo. Un Semaphore alrededor de las llamadas a un servicio externo evita que vos seas el que lo tira abajo, y es la mitad de un circuit breaker. La otra mitad es el timeout. Los dos juntos convierten "un servicio lento me arrastra" en "un servicio lento me devuelve errores rápidos que puedo manejar".

RuS4.9 JoinSet: manejar N tareas sin perder ninguna

Cuando spawneás un grupo de tareas relacionadas, guardar los handles en un Vec y hacer await uno por uno tiene tres problemas: procesás en orden de creación y no de finalización, un pánico en la tarea 7 lo descubrís recién cuando llegás a ella, y no hay forma limpia de cancelar el grupo entero.

use tokio::task::JoinSet;

async fn bajar_todo(urls: Vec<String>) -> Vec<(String, usize)> {
    let mut set = JoinSet::new();
    let cupos = std::sync::Arc::new(tokio::sync::Semaphore::new(16));

    for u in urls {
        let permiso = std::sync::Arc::clone(&cupos).acquire_owned().await.unwrap();
        set.spawn(async move {
            let _p = permiso;
            let bytes = reqwest::get(&u).await?.bytes().await?;
            Ok::<_, anyhow::Error>((u, bytes.len()))
        });
    }

    let mut salida = Vec::new();
    // join_next devuelve las tareas EN ORDEN DE FINALIZACIÓN, no de creación.
    while let Some(res) = set.join_next().await {
        match res {
            Ok(Ok(par))  => salida.push(par),
            Ok(Err(e))   => tracing::warn!(%e, "una descarga falló"),
            Err(je) if je.is_panic() => tracing::error!("una tarea entró en pánico"),
            Err(je)      => tracing::error!(%je, "join falló"),
        }
    }
    salida
}
// Patrón "el primero que termine gana, cancelo el resto".
async fn el_mas_rapido(replicas: Vec<String>) -> anyhow::Result<Datos> {
    let mut set = JoinSet::new();
    for r in replicas { set.spawn(consultar(r)); }

    while let Some(res) = set.join_next().await {
        if let Ok(Ok(d)) = res {
            set.shutdown().await;   // aborta las que quedan y ESPERA a que mueran
            return Ok(d);
        }
    }
    anyhow::bail!("todas las réplicas fallaron")
}
Dropear un JoinSet aborta todas sus tareas. Esa es la diferencia grande con un Vec<JoinHandle>, donde soltar los handles deja las tareas huérfanas corriendo. Por eso el JoinSet es la forma más cercana que tiene Tokio a la concurrencia estructurada, y por eso conviene que sea tu default para cualquier grupo de tareas. Cuidado con una letra chica: el drop pide el abort pero no espera; si necesitás la garantía de que terminaron, usá shutdown().await.
Cuándo NO usar JoinSet. Si las tareas son homogéneas, ligeras y no necesitás resultados individuales, futures::stream::iter(items).for_each_concurrent(16, |i| async move { ... }) es más barato: no spawnea nada, corre todo en la misma tarea con concurrencia acotada. La contra es que no hay paralelismo entre ellas (un solo worker) y un pánico se lleva puesta toda la operación. Usá JoinSet cuando querés paralelismo real y aislamiento de fallas.

RuS4.10 Shutdown ordenado

Un servicio que muere de golpe con SIGTERM deja peticiones a medias, transacciones sin cerrar y buffers sin volcar. En Kubernetes esto se nota como errores 502 en cada despliegue. El shutdown ordenado tiene cinco pasos y ninguno es opcional.

1. Escuchar la señal. SIGTERM en Linux, Ctrl+C en desarrollo. Los dos, siempre.
2. Dejar de aceptar trabajo nuevo. Cerrar el listener y marcar /health como no-listo, para que el balanceador te saque del pool antes de que empieces a cerrar.
3. Avisarle a todo el árbol. Un CancellationToken raíz cancela y cada tarea decide cómo cerrar.
4. Drenar. Esperar a que terminen las peticiones en vuelo, con un límite de tiempo.
5. Cerrar recursos y salir. Volcar buffers, cerrar el pool de la DB, y darle al runtime un shutdown_timeout para el pool de bloqueo.
use std::time::Duration;
use tokio_util::sync::CancellationToken;
use tokio::task::JoinSet;

async fn senal_de_cierre() {
    let ctrl_c = async { tokio::signal::ctrl_c().await.expect("ctrl_c") };

    #[cfg(unix)]
    let term = async {
        use tokio::signal::unix::{signal, SignalKind};
        signal(SignalKind::terminate()).expect("SIGTERM").recv().await;
    };
    #[cfg(not(unix))]
    let term = std::future::pending::<()>();

    tokio::select! { _ = ctrl_c => {}, _ = term => {} }
    tracing::info!("señal de cierre recibida");
}

fn main() -> anyhow::Result<()> {
    let rt = tokio::runtime::Runtime::new()?;

    rt.block_on(async {
        let token = CancellationToken::new();
        let mut tareas = JoinSet::new();

        // Trabajadores de fondo, cada uno con su hijo del token raíz.
        for id in 0..4 {
            let t = token.child_token();
            tareas.spawn(async move { trabajador(id, t).await });
        }

        // Servidor HTTP con shutdown integrado (axum / hyper).
        let t_http = token.child_token();
        let listener = tokio::net::TcpListener::bind("0.0.0.0:8080").await?;
        tareas.spawn(async move {
            axum::serve(listener, rutas())
                .with_graceful_shutdown(async move { t_http.cancelled().await })
                .await
                .map_err(anyhow::Error::from)
        });

        senal_de_cierre().await;
        marcar_no_listo();          // paso 2: el balanceador nos saca
        tokio::time::sleep(Duration::from_secs(2)).await;   // que se entere
        token.cancel();             // paso 3

        // Paso 4: drenar con techo. Si alguien se cuelga, no nos colgamos con él.
        match tokio::time::timeout(Duration::from_secs(25), async {
            while let Some(r) = tareas.join_next().await {
                if let Err(e) = r { tracing::error!(%e, "tarea terminó mal"); }
            }
        }).await {
            Ok(())  => tracing::info!("todas las tareas drenaron"),
            Err(_)  => { tracing::warn!("timeout de drenaje, abortando"); tareas.abort_all(); }
        }

        cerrar_pool_db().await;     // paso 5
        anyhow::Ok(())
    })?;

    // Le damos 10 s al pool de bloqueo antes de matar el proceso.
    rt.shutdown_timeout(Duration::from_secs(10));
    Ok(())
}
El drenaje sin timeout es peor que no drenar. Si una tarea tiene un bug y nunca termina, un join_next() sin límite deja el proceso colgado hasta que el orquestador lo mata con SIGKILL: perdiste el shutdown ordenado y además tardaste 30 segundos en morir. Regla: el timeout de drenaje siempre menor al terminationGracePeriodSeconds del pod, con margen.
🚨 No dropees un Runtime desde adentro de un contexto async. Hacerlo produce Cannot drop a runtime in a context where blocking is not allowed. Pasa cuando alguien crea un runtime dentro de una async fn, o cuando un Drop de una struct que contiene un Runtime se ejecuta dentro de block_on. Un runtime se crea y se dropea en el main sincrónico, punto.

RuS4.13 io_uring y Tokio 2.x

El modelo de I/O de Tokio 1.x es readiness-based: epoll avisa "este socket tiene datos" y después vos hacés un read(). Son dos viajes al kernel por operación. io_uring es completion-based: le enviás la operación al kernel por una cola compartida en memoria y él te avisa cuando ya la completó, sin syscall por operación. Para servicios con muchas operaciones chicas, la diferencia es grande.

El plan del proyecto para Tokio 2.x es estabilizar el soporte de io_uring en Linux, con ganancias importantes de throughput de I/O. Es el cambio de arquitectura más grande del runtime desde su 1.0.

📌 Por qué esto no es un flag y sí un cambio de API. Con epoll, read(&mut buf) funciona porque el kernel copia mientras vos esperás. Con io_uring, el kernel escribe en tu buffer después, de forma asíncrona: si cancelás la operación y liberás el buffer, el kernel escribe en memoria liberada. Por eso las APIs de io_uring pasan buffers por valor y te los devuelven al completar, en vez de tomarlos prestados. Los traits AsyncRead y AsyncWrite, que se basan en &mut [u8], no mapean directo. Ese es el problema de diseño que hay que resolver, y por eso tardó. 
// Así se ve hoy el estilo "ownership-passing" en tokio-uring (experimental).
// Fijate que el buffer VIAJA hacia adentro y VUELVE con el resultado.
fn ejemplo() -> std::io::Result<()> {
    tokio_uring::start(async {
        let archivo = tokio_uring::fs::File::open("datos.bin").await?;
        let buf = vec![0u8; 4096];

        // read_at consume el buffer y devuelve (resultado, buffer).
        let (res, buf) = archivo.read_at(buf, 0).await;
        let n = res?;
        println!("{n} bytes: {:?}", &buf[..n.min(16)]);
        Ok(())
    })
}
Qué hacer hoy: nada especial, y eso es lo correcto. No reescribas tu servicio para io_uring. Tres razones concretas. (1) Es solo Linux, y con kernel razonablemente nuevo: si desplegás en macOS o Windows necesitás igual el camino epoll. (2) Muchos entornos —contenedores con seccomp restrictivo, varios proveedores gestionados— bloquean las syscalls de io_uring por su historial de CVEs, así que la ganancia puede no estar disponible donde corrés. (3) La ganancia es en el syscall overhead de I/O; si tu p99 lo domina la base de datos o la CPU de tu propio código, no vas a ver nada. Lo que sí conviene hacer ahora: aislar tu I/O detrás de traits propios, para que el día que llegue el cambio toques una capa y no doscientos archivos.

Paso 3 — Hacer la cuenta antes de tocar código. Este es el paso que casi nadie hace y el que decide todo. 8 núcleos × 1 s ÷ 18 ms = 444 compresiones por segundo. Es el techo físico. A 500 req/s ofrecidas, el servicio está estructuralmente por encima de su capacidad: ninguna reorganización del código async lo arregla. Y sumar réplicas tampoco, porque cada réplica nueva tiene el mismo techo y el tráfico se reparte — sí ayudaría, pero cuesta plata y no era el problema principal.

Paso 4 — Arreglar por capas, midiendo cada una.

use std::sync::Arc;
use tokio::sync::Semaphore;

#[derive(Clone)]
struct App { s3: Arc<S3>, cupos_cpu: Arc<Semaphore>, nivel: i32 }

// cupos_cpu: Semaphore::new(16) — dos veces los núcleos, para tapar
// los huecos sin permitir una cola infinita.
// nivel: 3 en vez de 19.

async fn manejar(State(app): State<App>, cuerpo: Bytes) -> Result<StatusCode, Error> {
    let doc = serde_json::from_slice::<Documento>(&cuerpo)?;

    // (a) Backpressure: esperamos poquito y, si no hay lugar, 503 rápido.
    //     Rechazar en 300 ms es infinitamente mejor que responder en 2,3 s.
    let permiso = tokio::time::timeout(
        std::time::Duration::from_millis(300),
        Arc::clone(&app.cupos_cpu).acquire_owned(),
    )
    .await
    .map_err(|_| Error::Saturado)?      // 503 + Retry-After
    .expect("el semáforo no se cierra");

    // (b) El trabajo de CPU sale del runtime: los workers quedan libres
    //     para aceptar conexiones, correr timers y responder /health.
    let nivel = app.nivel;
    let comprimido = tokio::task::spawn_blocking(move || {
        let _p = permiso;                          // el permiso muere con la tarea
        zstd::encode_all(&cuerpo[..], nivel)       // (c) nivel 3: ~2,4 ms
    })
    .await
    .map_err(|_| Error::Interno)??;

    app.s3.put(&doc.clave, comprimido).await?;
    Ok(StatusCode::ACCEPTED)
}

Checkpoint — ¿lo tenés claro?

¿Por qué una sola operación bloqueante puede tumbar un runtime multi-thread de 8 workers, si son 8 hilos independientes?

Porque el scheduler es cooperativo y el work stealing es reactivo. Un worker que está adentro de un poll largo no vuelve al bucle del scheduler, así que no atiende su cola local ni la global — y, lo más importante, nadie le puede robar las tareas que ya tiene encoladas, porque el robo también lo ejecutan workers ocupados. Una sola operación de 120 ms degrada 1/8 del runtime; ocho peticiones concurrentes lo congelan entero: no se aceptan conexiones, no corren los timers, el /health da timeout y el balanceador te saca. En un runtime current_thread alcanza con una.

¿Qué significa exactamente que un future sea "cancel-safe", y cómo hago segura una lectura de socket dentro de un select!?

Un future es cancel-safe si dropearlo a medio camino no pierde información observable. read_exact no lo es: si leyó 5 de 8 bytes, esos 5 bytes ya salieron del socket y viven dentro del future; al dropearlo se pierden y el protocolo queda desfasado, sin error visible. Hay dos arreglos. El primero es mover el estado afuera del future: un Framed con un codec guarda el buffer parcial en el codec, así que next() sí es cancel-safe. El segundo es crear el future una sola vez fuera del bucle y pinearlo con tokio::pin!, poleando &mut future adentro del select!: si esa rama pierde, el future no se dropea y sigue desde donde iba. Y cuando escribas async fn propias que vayan a un select!, documentá si son cancel-safe.

Tenés un HashMap compartido por 200 tareas. ¿std::sync::Mutex o tokio::sync::Mutex?

El de std, salvo que haya un await adentro de la sección crítica. Un get o un insert son nanosegundos: tomar el lock, operar y soltarlo antes de cualquier await no bloquea a nadie de forma apreciable, y el Mutex de std es varias veces más barato que el de Tokio, que es un semáforo con cola FIFO donde cada lock() es un punto de suspensión. El de Tokio se justifica solo cuando el await tiene que pasar dentro del lock —por ejemplo un protocolo sobre una conexión que exige exclusión durante el intercambio—. Y si el MutexGuard de std se te cuela a través de un await, el compilador te frena: el guard es !Send, el future deja de ser Send y tokio::spawn lo rechaza. Antes de decidir entre los dos, preguntate si no conviene directamente que una tarea sea dueña del mapa y las demás le hablen por un mpsc.

Resumen ejecutivo

  • El ecosistema se consolidó en Tokio (~150 M descargas/mes). smol es la alternativa liviana viva, Embassy es para embebido, y async-std está discontinuado con aviso de seguridad RUSTSEC-2025-0052: no lo uses y sacalo si aparece en cargo tree.
  • El runtime multi-thread usa work stealing y exige Send; el current-thread no sincroniza nada, permite futures !Send y da latencias más predecibles, pero un bloqueo lo congela entero.
  • Una tarea no es un hilo: cuesta cientos de nanosegundos y una asignación. Soltar el JoinHandle no cancela: desvincula, y el pánico que ocurra adentro se pierde.
  • Meter trabajo bloqueante en una tarea async congela workers enteros, porque el scheduler solo cambia de tarea en un await. Se arregla con spawn_blocking — que cura la starvation pero no crea CPU.
  • Cancel safety: select! dropea los futures perdedores a medio camino. read_exact y write_all pierden datos ahí; Framed::next y un future pineado afuera del bucle, no. Buscá "Cancel safety" en la doc de cada método.
  • tokio::sync::Mutex no reemplaza al de std: usá el de std salvo que necesites sostener el lock a través de un await. Mejor todavía: mensajes por canal a una tarea dueña.
  • Los cuatro canales resuelven cosas distintas: mpsc (cola con backpressure), oneshot (respuesta), broadcast (todos ven todo, con Lagged), watch (solo el último valor).
  • Spawnear una tarea por request sin límite es un bug. Canales acotados y Semaphore convierten un colapso en una degradación medible con 503 honestos.
  • JoinSet es lo más cerca que está Tokio de la concurrencia estructurada: resultados por orden de finalización, y dropearlo aborta el grupo.
  • El shutdown ordenado son cinco pasos —señal, dejar de aceptar, cancelar el árbol, drenar con timeout, cerrar recursos— y el timeout de drenaje no es opcional.
  • tracing + tokio-console son el diagnóstico correcto: un perfilador de CPU te va a mostrar epoll_wait y no las 4.000 tareas hambrientas.
  • io_uring llega con Tokio 2.x en Linux y promete ganancias grandes de throughput de I/O, pero cambia la forma de las APIs (buffers por valor). Hoy: no reescribas nada, aislá tu I/O detrás de traits propios.

3. Dentro de un select! tenés una rama con sock.read_exact(&mut buf) y otra con token.cancelled(). El token se cancela cuando read_exact ya leyó 5 de los 8 bytes. ¿Qué pasa?

Ese es el caso de manual de un future no cancel-safe. read_exact acumula lo leído en el estado del propio future; al dropearlo, esos bytes desaparecen y el kernel no los "devuelve" a ningún lado. Como no hay error, el bug se manifiesta más tarde como datos corruptos o un parseo imposible.

RuS1 — Ownership por dentro: borrow checker, lifetimes y varianza

RuS1.0 Por qué este módulo

El curso base te enseñó a pelear con el borrow checker. Aprendiste el repertorio de golpes: cloná esto, poné un & allá, sacá la variable del for, envolvelo en Rc. Funciona. Y a la vez es agotador, porque cada error se siente como una regla arbitraria nueva en vez de una consecuencia de algo que ya sabías.

Este módulo es para que dejes de pelear. No agregando trucos, sino al revés: mostrándote que casi todo el borrow checker se deduce de un solo invariante. Cuando lo tenés internalizado, los errores dejan de ser sorpresas y pasan a ser confirmaciones — «claro, si permitiera esto, se rompería aquello».

💡 La tesis del módulo. El compilador de Rust hace cumplir una regla: en cualquier instante, un dato puede tener muchos lectores o un escritor, nunca las dos cosas. Aliasing XOR mutabilidad. Los lifetimes son la contabilidad de cuándo está vigente cada préstamo. La varianza es la regla de cómo se pueden convertir esos lifetimes entre sí sin romper el invariante. Todo lo demás —NLL, RefCell, Rc, Pin— son consecuencias o escapes explícitos de esa regla.

Trabajamos con Rust 1.95 y la edición 2024, que ya es la que vas a encontrar en cualquier proyecto nuevo. La edición importa acá más que en otros temas: cambió cuándo se liberan ciertos préstamos temporales y cambió qué lifetimes captura un impl Trait. Lo vemos en RuS1.13.

RuS1.1 El modelo: ownership, move, Copy y Drop

Arrancamos por lo que ya sabés, pero mirándolo desde la implementación. Un valor tiene exactamente un dueño. Cuando el dueño sale de scope, el valor se destruye. Asignar o pasar por valor mueve la propiedad.

fn main() {
    let a = String::from("hola");   // a es dueño del buffer del heap
    let b = a;                      // MOVE: b pasa a ser dueño, a queda inválido
    // println!("{a}");             // error[E0382]: borrow of moved value: `a`
    println!("{b}");
}                                   // se libera una sola vez, cuando muere b
📌 Un move en Rust es un memcpy de los bits del valor y nada más. No hay constructor de movimiento como en C++, no hay hook que puedas interceptar. Lo único que agrega Rust es que, estáticamente, marca el origen como inutilizable para que nadie libere dos veces. Guardate esta frase: en RuS1.12 explica por qué los structs auto-referenciales son imposibles.

Copy vs Clone: no son dos niveles de lo mismo

Mucha gente los aprende como «Copy es la versión barata de Clone». Es más preciso decir que Copy es un permiso y Clone es una operación.

CopyClone
Qué esMarker trait, sin métodos propiosTrait con método clone()
Cuándo actúaImplícito: en cada asignación o paso por valorExplícito: solo si lo escribís
Qué haceDuplicar los bits, y el original sigue válidoLo que vos programes (puede alocar, abrir recursos, etc.)
CostoObligatoriamente trivialArbitrario
Convive con DropNuncaSí, sin problema
 
#[derive(Clone, Copy, Debug)]
struct Punto { x: f64, y: f64 }

#[derive(Clone, Debug)]              // Clone sí, Copy no: hay heap adentro
struct Etiqueta { texto: String }

fn main() {
    let p = Punto { x: 1.0, y: 2.0 };
    let q = p;                       // COPY: p sigue usable
    println!("{p:?} {q:?}");         // ambos válidos

    let e = Etiqueta { texto: "hola".into() };
    let f = e.clone();               // explícito: aloca otro String
    println!("{e:?} {f:?}");
}

Por qué Drop y Copy son mutuamente excluyentes

Esta pregunta cae en entrevistas y separa a quien memorizó de quien entendió. El compilador te frena de entrada:

#[derive(Clone, Copy)]
struct Handle(u32);

impl Drop for Handle {
    fn drop(&mut self) {
        println!("cerrando fd {}", self.0);
    }
}
// error[E0184]: the trait `Copy` cannot be implemented for this type;
//               the type has a destructor
💡 El razonamiento. Copy significa: «duplicar los bits produce un valor independiente y válido, y el original no se invalida». Drop significa: «este valor es responsable de liberar un recurso exactamente una vez». Si un tipo tuviera los dos, cada asignación crearía un dueño extra del mismo recurso, y cada copia correría drop al morir. Un fd cerrado tres veces, un free() doble. Rust no puede permitirlo, así que lo prohíbe en la definición del tipo, no en el uso.

Y hay una consecuencia práctica que sí te va a morder: agregar un impl Drop a un tipo que hoy es Copy es un cambio incompatible para todos tus usuarios, porque de golpe sus asignaciones pasan a ser moves.

El orden de destrucción

Las variables locales se destruyen en orden inverso de declaración; los campos de un struct, en orden de declaración. Es determinista y sin recolector: por eso Rust puede tener RAII sin sorpresas de latencia.

struct Ruidoso(&'static str);
impl Drop for Ruidoso {
    fn drop(&mut self) { println!("drop {}", self.0); }
}

struct Par { primero: Ruidoso, segundo: Ruidoso }

fn main() {
    let _a = Ruidoso("a");
    let _b = Ruidoso("b");
    let _p = Par { primero: Ruidoso("p.1"), segundo: Ruidoso("p.2") };
}
// drop p.1      <- campos: orden de declaración
// drop p.2
// drop b        <- locales: orden INVERSO
// drop a
Truco de diagnóstico. Cuando no entendés por qué algo «sigue prestado», metele un tipo con Drop ruidoso y mirá el orden real de destrucción. Los errores de borrow casi siempre son errores de cuándo muere algo, y esta técnica los hace visibles sin leer una línea de MIR.

RuS1.2 El invariante: aliasing XOR mutabilidad

Acá está el corazón. Las dos reglas que memorizaste en M03 —«muchas &T o una sola &mut T»— no son dos reglas: son una sola formulación de la misma cosa.

📌 El invariante único. Mientras exista una referencia mutable a un valor, esa referencia es el único camino de acceso a ese valor en todo el programa. Mientras existan referencias compartidas, nadie puede escribir a través de ninguna de ellas. Traducido: aliasing (varios caminos al mismo dato) y mutabilidad son mutuamente excluyentes. 
fn main() {
    let mut v = vec![1, 2, 3];
    let r = &v[0];        // préstamo compartido
    v.push(4);            // error[E0502]: cannot borrow `v` as mutable
    println!("{r}");      // porque también está prestado como inmutable
}

El ejemplo se ve pedante hasta que pensás qué hace push: si el Vec se queda sin capacidad, realoca el buffer y libera el viejo. Tu r quedaría apuntando a memoria liberada. En C++ eso es iterator invalidation, la fuente clásica de use-after-free silencioso. En Rust es un error de compilación, y sale del mismo invariante.

De un invariante salen tres garantías

Clase de bugPor qué el invariante lo mata
Use-after-freeLiberar exige propiedad exclusiva; si alguien tiene un préstamo vivo, no podés ser exclusivo
Iterator invalidationMutar la colección exige &mut; el iterador ya sostiene un &
Data raceUna carrera necesita dos hilos, uno escribiendo, sobre el mismo dato. Escribir exige exclusividad: no hay dos
🔗 Analogía. Es una pizarra en una sala de reuniones. Pueden entrar diez personas a leer al mismo tiempo. Pero si alguien va a borrar y reescribir, la sala se cierra: entra solo esa persona. No porque escribir sea peligroso, sino porque leer mientras alguien reescribe te deja con media frase vieja y media nueva. La regla no protege al que escribe: protege a los que leen.

El invariante también es una optimización

Esto casi nadie lo cuenta: aliasing XOR mutabilidad no es solo seguridad, es información que el optimizador de C no tiene. Rust emite el atributo noalias de LLVM en sus referencias, que en C es el opt-in manual llamado restrict.

pub fn acumular(destino: &mut i32, sumando: &i32) {
    *destino += *sumando;
    *destino += *sumando;
}
// LLVM sabe que `destino` y `sumando` NO pueden apuntar al mismo i32
// (uno es &mut, el otro &: el invariante lo prohíbe).
// Entonces puede leer *sumando UNA sola vez y hacer *destino += 2 * s.
// El equivalente en C: el compilador DEBE releer *sumando la segunda vez,
// porque nada le prohíbe que destino == sumando.
void acumular(int *destino, const int *sumando) {
    *destino += *sumando;
    *destino += *sumando;   // recarga obligatoria
}
// Para conseguir lo mismo hay que jurarlo a mano — y si mentís, es UB:
void acumular_rapido(int *restrict destino, const int *restrict sumando);
Esta es la respuesta corta a «¿por qué Rust puede ser tan rápido como C si hace más chequeos?». Los chequeos son en compilación y cuestan cero en runtime; la información que producen habilita optimizaciones que en C hay que pedir a mano y con riesgo. El invariante es simultáneamente la restricción más molesta y el activo más valioso del lenguaje.

RuS1.3 NLL: por qué el préstamo termina en el último uso

Hasta Rust 2015 el borrow checker era léxico: un préstamo vivía desde donde se creaba hasta que se cerraba la llave del bloque. Simple de implementar, y rechazaba montañas de código correcto. Desde la edición 2018 rige NLL (Non-Lexical Lifetimes): un préstamo vive hasta su último uso, calculado sobre el grafo de flujo de control del MIR.

fn main() {
    let mut v = vec![1, 2, 3];

    let primero = &v[0];       // el préstamo NACE acá
    println!("{primero}");     // ...y MUERE acá: último uso de `primero`

    v.push(4);                 // OK desde NLL. Con el checker léxico: E0502
    println!("{v:?}");
}
💡 El cambio mental que importa. Un lifetime no es un scope. Es un conjunto de puntos del grafo de control donde el préstamo tiene que seguir siendo válido — lo que el compilador llama una región. Por eso dos préstamos «del mismo bloque» pueden no solaparse, y por eso un return temprano puede alargar un préstamo mucho más de lo que sugiere la indentación.

NLL también resuelve el caso clásico del match que devolvía por dos ramas:

fn primero_o_default(v: &mut Vec<String>) -> &str {
    if v.is_empty() {
        v.push(String::from("vacío"));   // muta: necesita &mut
    }
    &v[0]                                // presta: y acá el &mut ya murió
}

Dónde NLL todavía dice que no (y no es tu culpa)

Hay un caso famoso que sigue sin compilar en la edición 2024, conocido como NLL problem case #3: cuando un préstamo se devuelve condicionalmente, el compilador lo considera vivo en toda la función, incluso en la rama donde no se devolvió.

use std::collections::HashMap;

fn obtener_o_crear<'m>(m: &'m mut HashMap<String, String>, k: &str) -> &'m String {
    if let Some(v) = m.get(k) {
        return v;              // este préstamo se ata a 'm ...
    }
    m.insert(k.to_string(), String::from("default"));  // error[E0499]
    m.get(k).unwrap()          // ... y por eso `m` sigue prestado acá
}

El compilador no se equivoca en la seguridad — el programa es correcto, pero el análisis actual no puede probarlo. Las dos salidas prácticas:

use std::collections::HashMap;

// Opción A — la idiomática: la API `entry` fue diseñada exactamente para esto.
fn obtener_o_crear_a<'m>(m: &'m mut HashMap<String, String>, k: &str) -> &'m String {
    m.entry(k.to_string()).or_insert_with(|| String::from("default"))
}

// Opción B — cuando no hay `entry`: chequear sin quedarte con el préstamo.
fn obtener_o_crear_b<'m>(m: &'m mut HashMap<String, String>, k: &str) -> &'m String {
    if !m.contains_key(k) {                      // contains_key no retiene nada
        m.insert(k.to_string(), String::from("default"));
    }
    m.get(k).unwrap()                            // un único préstamo, al final
}
El sucesor de NLL se llama Polonius: reformula el análisis en términos de «qué préstamos están vivos en cada punto» en vez de «qué regiones contienen qué puntos», y acepta este caso. Al momento de escribir esto sigue en nightly (-Z polonius=next) y no cambia nada de lo que aprendés acá — los mismos programas seguros seguirán siendo seguros; solo se van a aceptar más programas que ya eran correctos.

RuS1.4 Lifetimes de verdad: no son «cuánto vive el dato»

La definición de manual —«un lifetime es cuánto vive una referencia»— sirve para el M09 y se rompe en cuanto llegás a firmas genéricas. La definición útil es otra.

📌 Un lifetime es una restricción de relación entre referencias, no una duración. Escribir &'a str no dice «esto vive 40 milisegundos». Dice: «existe una región 'a, y esta referencia es válida en toda ella». Y las anotaciones que ponés en una firma no crean duraciones: relacionan las de los parámetros con las del resultado. 
// Esto NO dice "a y b viven lo mismo".
// Dice: "existe una región 'a en la que AMBOS son válidos, y el resultado
//        también lo es". El compilador elige la MÁS CHICA que funcione.
fn mas_larga<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let larga = String::from("una cadena larga");
    let elegida;
    {
        let corta = String::from("corta");
        elegida = mas_larga(&larga, &corta);   // 'a se achica al scope de `corta`
        println!("{elegida}");                 // OK: acá 'a todavía vale
    }
    // println!("{elegida}");                  // error: 'a terminó con `corta`
}

Los lifetimes tienen subtipado

Un lifetime más largo puede usarse donde se espera uno más corto. Se escribe 'largo: 'corto y se lee «'largo sobrevive a 'corto» (outlives). Esto es subtipado: &'static str es un subtipo de &'a str para cualquier 'a.

fn usar<'corto>(s: &'corto str) -> usize { s.len() }

fn main() {
    let estatica: &'static str = "vivo todo el programa";
    let local = String::from("vivo poquito");

    usar(estatica);      // 'static se "achica" a 'corto: coerción implícita
    usar(&local);        // el lifetime de `local` también sirve
}

// Y podés exigir la relación explícitamente:
fn guardar<'largo, 'corto>(destino: &mut Vec<&'corto str>, s: &'largo str)
where
    'largo: 'corto,      // "'largo dura al menos lo que 'corto"
{
    destino.push(s);     // meter algo más longevo en un contenedor más efímero: OK
}
El error mental más común: creer que si anotás 'a en una firma le estás diciendo al compilador cuánto tiene que vivir el dato. No. Las anotaciones son promesas que el llamador tiene que poder cumplir. Si prometés algo imposible, el error no aparece en tu función: aparece en cada lugar que la llama, y por eso se siente lejano e inexplicable. Cuando un error de lifetime te apunta a una llamada, leé la firma, no el cuerpo.

RuS1.5 Elisión: las tres reglas que evitan que escribas 'a

El 95% de las funciones con referencias no llevan anotaciones porque el compilador aplica tres reglas mecánicas. No son inteligencia artificial ni inferencia: son tres pasos, en orden, y si después de los tres queda algún lifetime de salida sin asignar, es error.

Regla 1. A cada parámetro que sea una referencia se le asigna su propio lifetime fresco. Dos parámetros por referencia dan 'a y 'b, distintos.
Regla 2. Si hay exactamente un lifetime de entrada, ese se le asigna a todos los lifetimes de salida.
Regla 3. Si hay varios lifetimes de entrada pero uno de los parámetros es &self o &mut self, el lifetime de self se le asigna a todos los de salida.
// Escribís esto:
fn primera_palabra(s: &str) -> &str { s.split(' ').next().unwrap_or("") }

// El compilador lee esto (regla 1 + regla 2):
fn primera_palabra<'a>(s: &'a str) -> &'a str { /* ... */ }
// Acá la elisión FALLA y por eso te pide la anotación:
fn mas_larga(a: &str, b: &str) -> &str { if a.len() >= b.len() { a } else { b } }
// error[E0106]: missing lifetime specifier
//   regla 1 -> 'a y 'b;  regla 2 -> no aplica (hay dos);  regla 3 -> no hay self.
//   El compilador NO adivina: si eligiera mal, te dejaría una referencia colgada.
struct Parser<'texto> { fuente: &'texto str, pos: usize }

impl<'texto> Parser<'texto> {
    // Regla 3: la salida se ata a &self, NO a `patron`.
    fn resto(&self, patron: &str) -> &str {
        &self.fuente[self.pos..]
    }
}
// Y ojo, es una regla, no una adivinanza correcta: si de verdad quisieras
// devolver una tajada de `patron`, la regla 3 te da la firma EQUIVOCADA
// y tenés que anotar a mano:
//   fn tajada<'p>(&self, patron: &'p str) -> &'p str { &patron[1..] }
Bonus poco conocido: el lifetime del parser de arriba se llama 'texto, no 'a. Los nombres de lifetime son identificadores comunes y ponerles nombres con significado ('buf, 'conn, 'arena) mejora los mensajes de error muchísimo. Cuando un struct tiene dos lifetimes, 'a y 'b son una crueldad para tu yo del futuro.

RuS1.6 'static: casi nunca significa lo que la gente cree

'static tiene dos significados distintos según dónde aparezca, y confundirlos es el origen de la mitad de las peleas con thread::spawn, Box<dyn Error> y los runtimes async.

FormaQué diceEjemplos que la cumplen
&'static TEsta referencia apunta a datos que viven todo el programaLiterales de string, static, Box::leak
T: 'staticEste tipo no contiene ninguna referencia que pueda expirarString, Vec<u8>, i32, &'static str
⚠️ T: 'static NO significa «vive para siempre». Significa «es dueño de todo lo que contiene, así que podría vivir para siempre si quisieras». Un String cumple T: 'static y se destruye tres líneas después. Esta confusión es la número uno de todo el tema. 
fn exige_static<T: 'static>(_t: T) {}

fn main() {
    // 1) &'static T — el dato está en el binario
    let literal: &'static str = "esto vive todo el programa";
    exige_static(literal);

    // 2) T: 'static — el TIPO no tiene préstamos adentro
    let efimera = String::from("me muero en dos líneas");
    exige_static(efimera);     // compila: String no contiene referencias
                               // y se destruye acá nomás, no "para siempre"

    // Lo que NO cumple T: 'static es esto:
    let local = String::from("local");
    let prestada: &str = &local;
    // exige_static(prestada);  // error: `local` no vive lo suficiente
}

Dónde te lo vas a cruzar

use std::thread;

fn main() {
    let datos = vec![1, 2, 3];

    // thread::spawn exige F: 'static porque el hilo puede sobrevivir
    // a esta función. Por eso hay que MOVER, no prestar.
    let h = thread::spawn(move || println!("{datos:?}"));
    h.join().unwrap();
}
fn main() {
    let datos = vec![1, 2, 3];

    // La salida moderna: scoped threads (estable desde 1.63).
    // El scope GARANTIZA que los hilos terminan antes de salir,
    // así que NO hace falta 'static y podés prestar.
    std::thread::scope(|s| {
        s.spawn(|| println!("leo prestado: {:?}", &datos));
        s.spawn(|| println!("y yo también: {}", datos.len()));
    });

    println!("sigo siendo dueño: {datos:?}");   // datos nunca se movió
}
El antipatrón: Box::leak para «arreglar» un error de lifetime. Convierte cualquier valor en &'static… filtrando la memoria a propósito. Es legítimo una vez, al arrancar, para una config que va a vivir todo el proceso. Es una fuga si lo hacés por request, por conexión o dentro de un loop. Si tu solución a un error de lifetime fue Box::leak, casi seguro la respuesta correcta era Arc, un scope, o replantear quién es el dueño. 
// Aceptable: UNA vez, al arranque, config que vive todo el proceso.
fn cargar_config() -> &'static Config {
    let c = Box::new(Config::leer_de_disco());
    Box::leak(c)
}

// Fuga garantizada: se llama por request y nunca se libera nada.
fn nombre_de_usuario(id: u64) -> &'static str {
    Box::leak(consultar_nombre(id).into_boxed_str())   // NO HAGAS ESTO
}

RuS1.7 HRTB: for<'a>, o «para todo lifetime»

Un Higher-Ranked Trait Bound aparece cuando necesitás que algo funcione para cualquier lifetime, elegido por el llamado, no por el llamador. Es la diferencia entre «yo elijo un 'a y vos cumplís» y «vos tenés que cumplir para todos los 'a posibles».

// Lo que querés decir: "f funciona con CUALQUIER lifetime que yo le pase"
fn aplicar<F>(f: F) -> String
where
    F: for<'a> Fn(&'a str) -> &'a str,
{
    let temporal = String::from("hola mundo");
    f(&temporal).to_string()          // el 'a acá es local: nadie afuera lo conoce
}

fn main() {
    println!("{}", aplicar(|s| s.split(' ').next().unwrap()));
}

Compará con la versión sin HRTB, que parece lo mismo y no sirve:

// Acá 'a lo elige el LLAMADOR, antes de entrar a la función.
fn aplicar_mal<'a, F>(f: F) -> String
where
    F: Fn(&'a str) -> &'a str,
{
    let temporal = String::from("hola mundo");
    f(&temporal).to_string()
    // error[E0597]: `temporal` does not live long enough
    // Claro: 'a ya estaba fijado desde afuera y `temporal` no llega.
}
Casi nunca vas a escribir for<'a> a mano, porque los bounds de closures lo aplican solos por elisión. Se vuelve visible en tres lugares: (1) cuando guardás un closure en un campo, tipo Box<dyn for<'a> Fn(&'a str)>; (2) en los mensajes de error de serde, donde DeserializeOwned es literalmente for<'de> Deserialize<'de>; (3) cuando escribís un trait genérico sobre préstamos. Si te aparece en un error, ahora sabés leerlo: «para todo lifetime».

RuS1.8 Varianza: la sección que casi nadie enseña

Ya vimos que &'static str se puede usar donde se pide &'a str: hay subtipado entre lifetimes. La varianza responde la pregunta siguiente, que es la que de verdad importa: si Largo es subtipo de Corto, ¿es Contenedor<Largo> subtipo de Contenedor<Corto>?

ContravarianteF<C> es subtipo de F<L>Va «al revés». Parámetros de función

Por qué &'a T es covariante en 'a

Porque solo podés leer. Si tengo una referencia válida por mucho tiempo y me la pedís por poco tiempo, no puede pasar nada malo: durante ese ratito el dato existe seguro. Achicar el lifetime siempre es seguro.

Por qué &'a mut T es invariante en T

Acá está el ejemplo que justifica toda la sección. Una referencia mutable no solo lee: escribe. Y escribir con el tipo aflojado te deja meter un dato efímero en un lugar donde alguien prometió que había un dato longevo.

// Supongamos, POR ABSURDO, que &mut T fuera covariante en T.
// Entonces &mut &'static str podría usarse como &mut &'corto str.

fn asignar<'corto>(destino: &mut &'corto str, origen: &'corto str) {
    *destino = origen;
}

fn main() {
    let mut r: &'static str = "vivo para siempre";

    {
        let efimera = String::from("me muero en la llave");
        asignar(&mut r, &efimera);   // error[E0597] — y MENOS MAL
        //      ^^^^^^ acá haría falta la covarianza que Rust prohíbe
    }                                 // `efimera` se libera acá

    println!("{r}");   // si hubiera compilado: LECTURA DE MEMORIA LIBERADA
}
⚠️ Ese es el agujero exacto que la invarianza previene. Si &mut T fuera covariante en T, el compilador aceptaría degradar &mut &'static str a &mut &'corto str, escribir por ahí una referencia corta, y devolverte una variable que declara ser &'static apuntando a un String ya destruido. Java tiene exactamente este agujero con los arrays (covariantes) y lo tapa con un chequeo en runtime, ArrayStoreException. Rust lo tapa en el sistema de tipos y no paga nada en runtime.

Contravarianza: los parámetros van al revés

fn ejecutar(f: fn(&'static str)) { f("literal en el binario") }

fn imprime_cualquiera<'a>(s: &'a str) { println!("{s}"); }

fn main() {
    // `imprime_cualquiera` acepta CUALQUIER lifetime -> es MÁS general
    // que lo pedido (que solo tiene que aceptar 'static). Sirve.
    ejecutar(imprime_cualquiera);
}

// Al revés NO funciona, y es la definición de contravarianza:
fn ejecutar_corto<'a>(f: fn(&'a str), s: &'a str) { f(s) }
fn solo_static(s: &'static str) { println!("{s}"); }
// ejecutar_corto(solo_static, &local);   // error: solo_static exige 'static
🔗 Analogía para no olvidarla. Un contrato de trabajo dice «te doy un ingrediente y me devolvés un plato». Podés reemplazar al cocinero por uno que acepte más ingredientes (contravarianza en la entrada: más general está bien) y que devuelva un plato más específico (covarianza en la salida). Lo que no podés es contratar a uno que exija ingredientes más raros que los del contrato.

PhantomData: elegir la varianza a mano

Cuando escribís tipos con punteros crudos o FFI, el compilador no puede deducir la varianza correcta porque el parámetro no aparece en ningún campo real. PhantomData es cómo se lo decís.

use std::marker::PhantomData;

// Un slice propio sobre memoria cruda. Sin PhantomData, T no aparece en
// ningún campo "de verdad" y el compilador no sabe qué varianza darle
// ni que este tipo es "dueño" de valores T (importante para drop check).
struct MiSlice<'a, T> {
    ptr: *const T,
    largo: usize,
    _marca: PhantomData<&'a T>,   // covariante en 'a y en T, y sin Send/Sync gratis
}

// Recetario de varianza con PhantomData:
//   PhantomData<T>            -> covariante en T
//   PhantomData<&'a T>        -> covariante en 'a y en T
//   PhantomData<&'a mut T>    -> covariante en 'a, INVARIANTE en T
//   PhantomData<fn(T)>        -> contravariante en T
//   PhantomData<fn(T) -> T>   -> invariante en T
//   PhantomData<*const T>     -> covariante, y quita Send/Sync automáticos
Cuándo NO tocar varianza. Si estás escribiendo código seguro normal —structs con campos comunes, genéricos sobre Vec y HashMap— la varianza que infiere el compilador es la correcta y no tenés que pensar en esto jamás. La sección existe para dos momentos: cuando un error de lifetime «imposible» no cede con ningún 'a que pruebes (casi siempre hay un tipo invariante en el medio, típicamente un &mut o una Cell), y cuando escribís estructuras de datos con unsafe (RuS5).

RuS1.9 Interior mutability: mutar a través de &T

El invariante dice que no podés escribir a través de una referencia compartida. Y sin embargo RefCell, Mutex y los atómicos lo hacen todo el tiempo. No es una excepción mágica: es que el chequeo se corre de compilación a runtime, y la puerta por la que se hace es una sola.

// core/src/cell.rs, simplificado. Este es el ÚNICO tipo del lenguaje
// por el que es legal obtener un *mut T a partir de un &T.
#[repr(transparent)]
pub struct UnsafeCell<T: ?Sized> { value: T }

impl<T: ?Sized> UnsafeCell<T> {
    pub const fn get(&self) -> *mut T { self as *const Self as *mut T }
}
// El compilador lo trata especial: NO emite `noalias` para lo que hay
// adentro. Por eso las optimizaciones de RuS1.2 no rompen a RefCell.

Todo lo demás está construido encima. Una Cell mínima entra en seis líneas:

use std::cell::UnsafeCell;

pub struct MiCell<T> { valor: UnsafeCell<T> }

impl<T: Copy> MiCell<T> {
    pub fn nueva(v: T) -> Self { MiCell { valor: UnsafeCell::new(v) } }
    pub fn get(&self) -> T { unsafe { *self.valor.get() } }
    pub fn set(&self, v: T) { unsafe { *self.valor.get() = v } }
}
// Es seguro porque NUNCA entrega una referencia al interior: solo copias.
// Sin referencias al interior, no hay aliasing que romper.
// Y es !Sync automáticamente, porque UnsafeCell<T> es !Sync.

// Patrón defensivo: préstamo mínimo + manejo explícito del conflicto
match cache.try_borrow_mut() {

        // No paniquear: registrar y seguir, o reencolar el trabajo.

    }
}

// Si el callback vuelve a tocar la cache -> panic garantizado.

RuS1.10 Rc, Arc y sí, Rust también filtra memoria

Rc<T> es propiedad compartida por conteo de referencias, sin sincronización. Arc<T> es lo mismo con contadores atómicos, para cruzar hilos. Por dentro son casi triviales:

// alloc/src/rc.rs, simplificado
struct RcInner<T: ?Sized> {
    strong: Cell<usize>,   // cuántos Rc apuntan acá; a 0 se destruye el valor
    weak: Cell<usize>,     // cuántos Weak (+1 mientras quede algún strong)
    value: T,              // el dato, en el MISMO bloque del heap
}
// Rc<T> es un puntero a esto. Por eso Rc::clone() es incrementar un usize:
// NO copia el dato. Y por eso Rc<T> te da &T, nunca &mut T
// (hay varios dueños: la exclusividad es imposible por construcción).
📌 Rc te da propiedad compartida, no mutabilidad compartida. Para mutar necesitás combinarlo con interior mutability: Rc<RefCell<T>> en un hilo, Arc<Mutex<T>> entre hilos. Esa combinación es la que hace que Rust «se parezca a un lenguaje con GC», y también la que trae los dos problemas de esta sección: el panic de RefCell y los ciclos.

El ciclo que filtra

El conteo de referencias no tiene forma de descubrir que dos objetos se sostienen mutuamente. Si a apunta a b y b apunta a a, sus contadores nunca llegan a cero, aunque nadie más los alcance. Es una fuga real, en Rust seguro, sin un solo unsafe:

use std::cell::RefCell;
use std::rc::Rc;

struct Nodo { nombre: &'static str, vecino: RefCell<Option<Rc<Nodo>>> }

impl Drop for Nodo {
    fn drop(&mut self) { println!("drop {}", self.nombre); }
}

fn main() {
    let a = Rc::new(Nodo { nombre: "a", vecino: RefCell::new(None) });
    let b = Rc::new(Nodo { nombre: "b", vecino: RefCell::new(None) });

    *a.vecino.borrow_mut() = Some(Rc::clone(&b));
    *b.vecino.borrow_mut() = Some(Rc::clone(&a));   // ← el ciclo se cierra

    println!("strong(a) = {}", Rc::strong_count(&a));   // 2
    println!("strong(b) = {}", Rc::strong_count(&b));   // 2
}
// No se imprime NINGÚN "drop". Los dos nodos quedaron en el heap
// hasta que el proceso termine. Memory leak, en safe Rust.
Esto no es un bug de Rust: es una decisión de diseño explícita. Filtrar memoria no es unsafe — no causa comportamiento indefinido, no corrompe nada, no es un agujero de seguridad de memoria. Por eso std::mem::forget es una función segura. Rust promete memory safety, no ausencia de fugas. Confundir las dos cosas es el error de marketing más común sobre el lenguaje.

Weak: la solución

Un Weak<T> apunta al mismo bloque pero no cuenta como dueño. Para usarlo hay que hacer upgrade(), que devuelve Option<Rc<T>>: None si el valor ya se destruyó.

use std::cell::RefCell;
use std::rc::{Rc, Weak};

struct Nodo {
    nombre: &'static str,
    padre: RefCell<Weak<Nodo>>,        // hacia ARRIBA: débil, no es dueño
    hijos: RefCell<Vec<Rc<Nodo>>>,     // hacia ABAJO: fuerte, sí es dueño
}

impl Drop for Nodo {
    fn drop(&mut self) { println!("drop {}", self.nombre); }
}

fn main() {
    let raiz = Rc::new(Nodo {
        nombre: "raiz",
        padre: RefCell::new(Weak::new()),
        hijos: RefCell::new(vec![]),
    });
    let hijo = Rc::new(Nodo {
        nombre: "hijo",
        padre: RefCell::new(Rc::downgrade(&raiz)),   // Weak
        hijos: RefCell::new(vec![]),
    });
    raiz.hijos.borrow_mut().push(Rc::clone(&hijo));  // Rc

    // Subir al padre: siempre puede fallar, y el tipo te obliga a decidir.
    if let Some(p) = hijo.padre.borrow().upgrade() {
        println!("el padre de {} es {}", hijo.nombre, p.nombre);
    }
}
// drop raiz
// drop hijo      ← los dos se liberan. Sin ciclo.
📌 La regla mecánica para cualquier estructura enlazada: las aristas que van hacia abajo en la jerarquía (padre → hijo, dueño → poseído, observado → nada) son Rc/Arc. Las que van hacia arriba o hacia el costado (hijo → padre, observador → sujeto, caché → entrada) son Weak. Si alguna vez podés recorrer un ciclo siguiendo solo Rc, tenés una fuga.

RuS1.11 Patrones para salir de las peleas más comunes

Pelea 1 — «no puedo llamar a un método de self dentro de un loop sobre self»

struct Servidor { conexiones: Vec<String>, atendidas: usize }

impl Servidor {
    fn registrar(&mut self, _c: &str) { self.atendidas += 1; }

    fn tick(&mut self) {
        for c in &self.conexiones {   // presta self.conexiones (compartido)
            self.registrar(c);        // error[E0502]: registrar pide &mut *self
        }                             //   ENTERO, no solo el campo `atendidas`
    }
}

La causa exacta: el borrow checker sí distingue campos distintos dentro de un cuerpo de función, pero una llamada a método presta self completo. Tres salidas, en orden de preferencia:

// Salida A — no llamar al método: tocar el campo directo.
// Los préstamos a campos DISJUNTOS del mismo struct sí conviven.
fn tick_a(&mut self) {
    for _c in &self.conexiones {
        self.atendidas += 1;          // compila: campos distintos
    }
}
// Salida B — dividir el struct según lo que se presta junto.
// Es la que casi siempre indica un diseño mejor.
struct Metricas { atendidas: usize }
impl Metricas {
    fn registrar(&mut self, _c: &str) { self.atendidas += 1; }
}

struct Servidor { conexiones: Vec<String>, metricas: Metricas }

impl Servidor {
    fn tick(&mut self) {
        for c in &self.conexiones {       // &self.conexiones
            self.metricas.registrar(c);   // &mut self.metricas -> disjuntos: OK
        }
    }
}
// Salida C — mem::take: sacar el dato, trabajar libre, devolverlo.
// Útil cuando de verdad necesitás &mut self adentro del loop.
impl Servidor {
    fn tick_c(&mut self) {
        let conexiones = std::mem::take(&mut self.conexiones);  // deja un Vec vacío
        for c in &conexiones {
            self.registrar(c);        // self ya no está prestado por el loop
        }
        self.conexiones = conexiones; // devolver (ojo si hay early return)
    }
}
Cuándo NO usar mem::take: si adentro del loop podés hacer return o ?, el campo se queda vacío para siempre y acabás de crear un bug de estado silencioso. Si hay caminos de salida tempranos, usá la salida B (dividir el struct) o un guard con Drop que restaure. mem::take es una herramienta afilada, no un comodín.

Pelea 2 — «tengo que devolver a veces prestado y a veces propio»

use std::borrow::Cow;

// Cow = Clone On Write: presta si puede, aloca solo si tuvo que cambiar algo.
fn normalizar(s: &str) -> Cow<'_, str> {
    if s.contains(' ') {
        Cow::Owned(s.replace(' ', "_"))   // hubo cambio: alocamos
    } else {
        Cow::Borrowed(s)                  // sin cambios: CERO alocaciones
    }
}

fn main() {
    let a = normalizar("ya_estaba_bien");   // Borrowed: no alocó nada
    let b = normalizar("con espacios");     // Owned: alocó una vez
    println!("{a} {b}");
}
Cow brilla en el caso «el 95% de las entradas ya están bien». Un parser de configuración, un sanitizador de rutas, un normalizador de headers HTTP: alocás solo en el 5% raro. En cambio, si casi siempre transformás, Cow agrega un enum y una rama a cambio de nada — ahí devolvé String y listo.

Pelea 3 — cuándo clonar es la respuesta correcta

💡 Clonar no es una derrota. Es una decisión de ingeniería con un costo medible. La pregunta correcta no es «¿puedo evitar este clone?» sino «¿este clone está en un camino caliente?». Un String de 30 bytes clonado una vez por request, en un servicio que hace una consulta a Postgres por request, es literalmente inmedible al lado de la latencia de red.
SituaciónClonar es…
Configuración, al arrancar✅ Correcto. Simplifica y corre una vez
Clave para un HashMap que se guarda✅ Correcto. Igual necesitás propiedad
Prototipo hasta que el diseño se estabilice✅ Correcto. Refactorizás después, con perfil en mano
Adentro de un loop de millones de iteraciones❌ Ahí sí importa: medí y sacalo
Un Vec grande, por request❌ Usá Arc y compartilo
Para «hacer callar» un error que no entendés⚠️ Peligroso: suele tapar un problema de diseño de propiedad

Pelea 4 — índices en vez de referencias

El patrón que resuelve el 90% de las estructuras enlazadas, y el que desarrollamos en el Worked Example: si guardar referencias es imposible, guardá índices a un Vec. Las «referencias» pasan a ser datos comunes (usize), el borrow checker deja de tener opinión, y de yapa los datos quedan contiguos en memoria.

RuS1.12 Cuándo el borrow checker tiene razón y vos no

Hay una familia de errores donde no hay truco, ni anotación, ni Cow que valga: los structs auto-referenciales, esos donde un campo apunta a otro campo del mismo struct.

struct Parser {
    texto: String,
    actual: &str,     // quisiera apuntar DENTRO de self.texto
}
// error[E0106]: missing lifetime specifier
// Y si le ponés un lifetime... ¿cuál? No existe un 'a que signifique
// "el lifetime de mi propio campo de al lado".

Podrías pensar que es una limitación de la sintaxis. No lo es. El problema es más profundo, y lo anticipamos en RuS1.1:

⚠️ Un move en Rust es un memcpy, y no hay forma de interceptarlo. Aunque el compilador te dejara construir el struct, en cuanto lo devolvieras de una función, lo metieras en un Vec o lo mandaras a otro hilo, los bits se copiarían a otra dirección — y el puntero interno seguiría apuntando a la dirección vieja. C++ tapa esto con constructores de movimiento; Rust no los tiene por diseño, porque son justamente lo que hace que mover sea caro e impredecible. 
// El experimento mental, si compilara:
let p = armar_parser();   // los bits del struct se copian del stack de la
                          // función al del llamador...
                          // ...y `p.actual` sigue apuntando a la vieja dirección.
// No hay lifetime que arregle esto: el problema no es CUÁNTO vive, es DÓNDE está.

La respuesta del lenguaje se llama Pin: un envoltorio que promete a nivel de tipos que el valor no se va a mover de su dirección. Es la pieza que hace posibles los async fn, porque un bloque async compilado es exactamente esto — una máquina de estados donde una variable local viva a través de un .await es un campo que apunta a otro campo.

Lo desarrollamos en RuS3 — Async por dentro. Por ahora quedate con el diagnóstico: si tu error de lifetime describe un struct que se apunta a sí mismo, dejá de buscar la anotación mágica. Las salidas reales son tres, en orden de preferencia: (1) guardar índices/offsets en vez de referencias (un usize no se invalida al mover), (2) separar el dueño del prestatario en dos tipos, o (3) Pin con Box::pin, o crates como ouroboros/self_cell que encapsulan el unsafe. 
// Salida (1), la que casi siempre alcanza: offsets en vez de punteros.
struct Parser {
    texto: String,
    pos: usize,        // un índice NO se invalida cuando el struct se mueve
}

impl Parser {
    fn actual(&self) -> &str { &self.texto[self.pos..] }   // se calcula al pedir
}

RuS1.13 Lo que cambió en la edición 2024

La edición 2024 tocó tres cosas que caen justo en este módulo. Si venís de código 2021, conviene tenerlas presentes porque explican errores que aparecen (o desaparecen) al migrar.

1. Los temporales del if let mueren antes del else

use std::cell::RefCell;
use std::collections::HashMap;

fn main() {
    let cache: RefCell<HashMap<u32, u32>> = RefCell::new(HashMap::new());
    let k = 7;

    if let Some(v) = cache.borrow().get(&k).copied() {
        println!("hit: {v}");
    } else {
        // Edición 2021: el `Ref` de borrow() vivía hasta el final del if/else
        //               -> esta línea PANIQUEA en runtime.
        // Edición 2024: el temporal se libera antes de entrar acá -> funciona.
        cache.borrow_mut().insert(k, 42);
    }
}

2. impl Trait captura todos los lifetimes en scope

// Edición 2024: el impl Trait de retorno captura TODOS los lifetimes
// en scope por defecto. Antes había que repetir + 'a a mano.
fn nombres<'a>(v: &'a [String]) -> impl Iterator<Item = &'a str> {
    v.iter().map(|s| s.as_str())
}

// Y si NO querés capturar nada (para poder devolverlo más allá del préstamo),
// lo decís explícito con la sintaxis `use<>`:
fn longitudes(v: &[String]) -> impl Iterator<Item = usize> + use<> {
    v.iter().map(|s| s.len()).collect::<Vec<_>>().into_iter()
}

3. Referencias a static mut son error duro

fn main() {

        // Edición 2021: warning. Edición 2024: error[E0796].
        // let r = &mut CONTADOR;

    }

🧑‍🎓 Worked Example — el grafo que no compila de ninguna forma

Necesitás representar un grafo no dirigido: nodos con nombre, y cada nodo conoce a sus vecinos. La primera idea es obvia y no compila. Vamos a recorrer las tres soluciones reales, medir qué cuesta cada una, y terminar con una recomendación por caso.

Paso 1 — El intento natural, y por qué está muerto.

struct Nodo<'a> {
    nombre: String,
    vecinos: Vec<&'a Nodo<'a>>,
}

fn main() {
    let mut a = Nodo { nombre: "a".into(), vecinos: vec![] };
    let mut b = Nodo { nombre: "b".into(), vecinos: vec![] };

    a.vecinos.push(&b);      // a toma prestado b (compartido)
    b.vecinos.push(&a);      // error[E0502]: b ya está prestado por a,
                             // y para mutar b hace falta &mut b
}
📌 No es un problema de sintaxis: es el invariante de RuS1.2 aplicado. Un grafo con ciclos exige que dos caminos lleguen al mismo nodo mientras ese nodo todavía se puede modificar. Aliasing + mutabilidad. No hay lifetime que lo permita, y no debería haberlo: si b se realocara o se destruyera, el vecino de a quedaría colgado.

Paso 2 — Solución 1: Rc<RefCell<Nodo>>. Mover ambos chequeos a runtime.

use std::cell::RefCell;
use std::rc::{Rc, Weak};

struct Nodo {
    nombre: String,
    vecinos: Vec<Weak<RefCell<Nodo>>>,   // Weak: si fueran Rc, TODO ciclo filtra
}

type Ref = Rc<RefCell<Nodo>>;

fn nuevo(nombre: &str) -> Ref {
    Rc::new(RefCell::new(Nodo { nombre: nombre.into(), vecinos: vec![] }))
}

fn conectar(a: &Ref, b: &Ref) {
    a.borrow_mut().vecinos.push(Rc::downgrade(b));
    b.borrow_mut().vecinos.push(Rc::downgrade(a));
}

fn vecinos_de(n: &Ref) -> Vec<String> {
    n.borrow()
        .vecinos
        .iter()
        .filter_map(|w| w.upgrade())               // el vecino puede haber muerto
        .map(|v| v.borrow().nombre.clone())
        .collect()
}

fn main() {
    let a = nuevo("a");
    let b = nuevo("b");
    let c = nuevo("c");
    conectar(&a, &b);
    conectar(&b, &c);
    println!("{:?}", vecinos_de(&b));   // ["a", "c"]
}
Lo que estás pagando. Cada nodo es una alocación separada del heap, con dos contadores de encabezado, y recorrer una arista es seguir un puntero a una dirección arbitraria — pésima localidad de caché. Cada acceso hace un chequeo de préstamo con una rama. Y hay dos formas de romperlo en producción: un borrow() vivo mientras alguien hace borrow_mut() (panic), y —si te olvidás del Weak— un ciclo que filtra. Nota que vecinos_de tuvo que clonar los nombres: devolver &str desde adentro de un RefCell es imposible, porque el Ref muere al salir.

Paso 3 — Solución 2: índices en un Vec (arena a mano). El grafo es dueño de todo; las aristas son números.

type NodoId = usize;

struct Nodo { nombre: String, vecinos: Vec<NodoId> }

#[derive(Default)]
struct Grafo { nodos: Vec<Nodo> }

impl Grafo {
    fn agregar(&mut self, nombre: &str) -> NodoId {
        self.nodos.push(Nodo { nombre: nombre.into(), vecinos: vec![] });
        self.nodos.len() - 1
    }

    fn conectar(&mut self, a: NodoId, b: NodoId) {
        self.nodos[a].vecinos.push(b);
        self.nodos[b].vecinos.push(a);     // ningún problema: son usize
    }

    fn bfs(&self, desde: NodoId) -> Vec<&str> {
        let mut visto = vec![false; self.nodos.len()];
        let mut cola = std::collections::VecDeque::from([desde]);
        let mut orden = Vec::new();
        visto[desde] = true;

        while let Some(id) = cola.pop_front() {
            orden.push(self.nodos[id].nombre.as_str());   // devolver &str: gratis
            for &v in &self.nodos[id].vecinos {
                if !visto[v] { visto[v] = true; cola.push_back(v); }
            }
        }
        orden
    }
}

fn main() {
    let mut g = Grafo::default();
    let (a, b, c) = (g.agregar("a"), g.agregar("b"), g.agregar("c"));
    g.conectar(a, b);
    g.conectar(b, c);
    println!("{:?}", g.bfs(a));   // ["a", "b", "c"]
}
Por qué esta suele ser la correcta. Cero contadores, cero chequeos en runtime, todos los nodos contiguos en memoria (el BFS recorre caché amigable), y bfs puede devolver &str prestado del grafo sin clonar nada. Además, serializar y testear se vuelve trivial: es un Vec. Es exactamente lo que hacen por dentro rustc, los motores de juego con ECS y casi cualquier compilador.
El costo escondido de los índices: un NodoId es un puntero sin chequeo de tipo. Nada te impide usar un id del grafo A para indexar el grafo B, ni conservar un id de un nodo borrado y leer el nodo que ocupó su lugar. El compilador te ayudaba con las referencias y acá renunciaste a esa ayuda. Mitigación barata: un newtype (struct NodoId(usize);) para que al menos no se mezcle con otros índices. Mitigación completa: la solución 3.

Paso 4 — Solución 3: una crate de arena. Alguien ya resolvió esto mejor que vos.

// slotmap: índices con GENERACIÓN. Un id de un nodo borrado no vuelve
// a indexar nada, aunque el slot se recicle.
use slotmap::{DefaultKey, SlotMap};

let mut sm: SlotMap<DefaultKey, String> = SlotMap::new();
let k = sm.insert("a".to_string());
sm.remove(k);
assert!(sm.get(k).is_none());        // el id caducó: no leyó basura ajena
// petgraph: si además querés algoritmos, no reimplementes Dijkstra.
use petgraph::graph::UnGraph;
use petgraph::algo::dijkstra;

let mut g: UnGraph<&str, u32> = UnGraph::new_undirected();
let a = g.add_node("a");
let b = g.add_node("b");
let c = g.add_node("c");
g.add_edge(a, b, 1);
g.add_edge(b, c, 4);

let distancias = dijkstra(&g, a, None, |e| *e.weight());
println!("{:?}", distancias[&c]);    // 5
// typed-arena / bumpalo: TODO muere junto. Con esto SÍ podés usar
// referencias de verdad entre nodos, porque la arena garantiza que
// nada se libera antes que el resto.
use typed_arena::Arena;

struct Nodo<'a> { nombre: &'a str, vecinos: std::cell::RefCell<Vec<&'a Nodo<'a>>> }

let arena: Arena<Nodo> = Arena::new();
let a = arena.alloc(Nodo { nombre: "a", vecinos: Default::default() });
let b = arena.alloc(Nodo { nombre: "b", vecinos: Default::default() });
a.vecinos.borrow_mut().push(b);
b.vecinos.borrow_mut().push(a);      // ciclo permitido: nadie se libera solo

Y la lección real del ejercicio no es «usá índices». Es que cuando el borrow checker rechaza toda variante de tu diseño, no está pidiéndote una anotación: te está diciendo que tu modelo de propiedad no existe. Un nodo no puede ser dueño de sus vecinos si los vecinos también son dueños de él. Alguien tiene que ser el dueño único —el grafo— y el resto tiene que ser una referencia débil, un índice, o una arena. Ese replanteo es el trabajo; la sintaxis es la consecuencia.

Checkpoint — ¿lo tenés claro?

¿Por qué &'a mut T es covariante en 'a pero invariante en T?

Son dos posiciones distintas. Sobre 'a solo podés acortar el préstamo, y acortarlo siempre es seguro: si la referencia era válida por diez segundos, usarla durante dos no rompe nada. Sobre T, en cambio, la referencia mutable lee y escribe. Si fuera covariante podrías tratar un &mut &'static str como un &mut &'corto str, escribirle adentro una referencia efímera, y quedarte con una variable declarada &'static str que apunta a memoria ya liberada. Si fuera contravariante pasaría el problema espejo del lado de la lectura. Cuando podés leer y escribir con el mismo tipo, la única opción segura es que el tipo no se pueda aflojar en ningún sentido: invariante. Ese es también el motivo de que Cell<T> y *mut T sean invariantes.

Tu programa Rust consume memoria sin parar. ¿Es un bug de memory safety?

No, y la distinción importa. Rust garantiza memory safety —nada de use-after-free, doble liberación, data races ni lecturas fuera de rango— pero no garantiza ausencia de fugas. Filtrar es seguro: por eso std::mem::forget y Box::leak son funciones normales, sin unsafe. La causa típica en safe Rust es un ciclo de Rc o Arc: dos objetos que se sostienen mutuamente nunca llegan a contador cero. Se diagnostica con Rc::strong_count en los puntos sospechosos, o con un impl Drop ruidoso que nunca se imprime, y se arregla convirtiendo en Weak las aristas que van «hacia arriba» en la jerarquía. Las otras causas frecuentes son cachés sin política de expiración y colas que crecen más rápido de lo que se consumen — ninguna es un problema del lenguaje.

Escribís fn f<T: 'static>(t: T). ¿Qué le estás exigiendo realmente a T?

Que el tipo no contenga ninguna referencia con un lifetime más corto que 'static. Es decir: que sea dueño de todo lo que lleva adentro, o que lo que preste viva todo el programa. No le estás exigiendo que el valor viva para siempre: un String cumple T: 'static y se destruye al salir del scope. Un Vec<u8>, un i32 y un &'static str también cumplen. Lo que no cumple es un &'a str con 'a corto, o un struct que contenga uno. Este bound aparece en thread::spawn (el hilo puede sobrevivir al que lo creó), en Box<dyn Error> —que en realidad es Box<dyn Error + 'static>— y en Any, que necesita que el tipo sea estable para poder hacer downcast. Si te choca con spawn, la salida moderna casi nunca es Box::leak: es mover los datos con move, compartirlos con Arc, o usar thread::scope, que garantiza el join y por eso te deja prestar.

Resumen ejecutivo

  • El borrow checker hace cumplir un invariante: aliasing XOR mutabilidad. Use-after-free, invalidación de iteradores y data races son tres consecuencias de la misma regla — y de yapa habilita el noalias que en C hay que jurar a mano.
  • Un move es un memcpy sin hooks. De ahí sale que Copy y Drop sean incompatibles (cada copia correría el destructor) y que los structs auto-referenciales sean imposibles sin Pin.
  • NLL: el préstamo muere en su último uso, no al cerrar la llave. Todavía falla en el retorno condicional de un préstamo (problem case #3); la salida idiomática es entry o un contains_key previo.
  • Un lifetime no es una duración: es una restricción de relación entre referencias. Las anotaciones no crean vida, imponen promesas que el llamador debe poder cumplir. Tres reglas de elisión te ahorran escribirlas casi siempre.
  • &'static T (el dato vive todo el programa) y T: 'static (el tipo no contiene préstamos que expiren) son cosas distintas. Box::leak casi nunca es la solución; thread::scope y Arc casi siempre sí.
  • Varianza: &'a T es covariante en todo; &'a mut T es covariante en 'a pero invariante en T, y eso tapa un agujero real de use-after-free. Cell, RefCell y *mut T también son invariantes; PhantomData es cómo se elige a mano.
  • Interior mutability mueve el chequeo a runtime. UnsafeCell es la raíz de todo; Cell no puede fallar, RefCell paniquea, Mutex bloquea. Un panic de RefCell es un error de compilación que se te escapó a producción.
  • Rust filtra memoria y eso es seguro por diseño: un ciclo de Rc nunca llega a cero. Regla mecánica: aristas hacia abajo con Rc, hacia arriba con Weak.
  • Para estructuras enlazadas, el default profesional son índices en un Vec (o slotmap si borrás nodos). Rc<RefCell<>> se reserva para topologías chicas e impredecibles.
  • Cuando el checker rechaza todas las variantes de tu diseño, el problema no es la sintaxis: tu modelo de propiedad no existe. Definí quién es el dueño único y todo lo demás se ordena.

🧠 Autoevaluación

1. ¿Por qué &'a mut T es invariante en T?

Una referencia mutable lee y escribe. Si fuera covariante en T, un &mut &'static str podría pasarse donde se pide &mut &'corto str; ahí adentro se le escribe una referencia corta, y al salir del scope quedás con una variable declarada &'static str apuntando a memoria liberada. Es exactamente el agujero que Java tiene con los arrays covariantes y tapa en runtime con ArrayStoreException. Ojo con la tercera opción: &'a mut T sí es covariante en 'a — la invarianza es solo en T.

2. Tu servicio en Rust seguro consume memoria sin parar. Usa Rc en varias estructuras y no hay un solo bloque unsafe. ¿Cuál es la primera hipótesis?

Rust garantiza memory safety, no ausencia de fugas — filtrar no es UB, por eso mem::forget y Box::leak son funciones seguras. El conteo de referencias no detecta ciclos por construcción. Se diagnostica con Rc::strong_count o con un impl Drop ruidoso que nunca se imprime, y se arregla convirtiendo a Weak las aristas que van «hacia arriba» en la jerarquía. Las otras causas típicas son cachés sin expiración y colas que crecen más rápido de lo que se drenan.

3. thread::spawn te rechaza el closure pidiendo 'static, pero los datos que querés leer son un Vec local y el hilo termina antes que la función. ¿Cuál es la salida correcta?

spawn exige F: 'static porque el hilo podría sobrevivir al que lo creó — el compilador no tiene forma de saber que vos vas a hacer el join. thread::scope (estable desde 1.63) sí lo garantiza estructuralmente, y por eso levanta el requisito: prestás el Vec y seguís siendo dueño después. Box::leak «funciona» filtrando la memoria a propósito, algo aceptable una vez al arrancar y desastroso por request. Y el for<'a> no aplica: no es un problema de cuantificación sobre lifetimes, es un requisito de propiedad.

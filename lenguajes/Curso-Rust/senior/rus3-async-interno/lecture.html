RuS3 — Async por dentro: Future, Pin y wakers

RuS3.0 Por qué este módulo

Si venís de JavaScript, Python, C# o Go, ya usaste async. Y probablemente llegaste a Rust, escribiste tu primer async fn, y el compilador te tiró tres errores que en ningún otro lenguaje existen: «future cannot be sent between threads safely», «the trait bound ...: Unpin is not satisfied», y un warning que dice que tu función no hizo nada.

Esos errores no son arbitrarios ni son mala calidad de diagnóstico. Son la superficie visible de un diseño distinto, y hasta que no entendés el diseño, cada error es una lotería: probás Box::pin, probás Arc<Mutex<_>>, probás .clone(), y algo compila. Ese es exactamente el nivel del que este módulo te saca.

💡 La tesis del módulo. Todo async en Rust se deduce de una sola decisión de diseño: el lenguaje no trae runtime. Una Future es un valor común y corriente que no hace nada hasta que alguien la poletea. De ahí salen, en cadena: el must_use, la máquina de estados generada, la necesidad de Pin, el Waker, la cancelación por drop, y el requisito de Send. Entendé la decisión y los seis errores se vuelven predecibles.
Estado del ecosistema, 2026. Trabajamos con Rust 1.95 y edición 2024. Tokio es el runtime de facto (~150M de descargas por mes) y smol la alternativa liviana y embebible. No uses async-std: fue discontinuado oficialmente y tiene aviso de seguridad por falta de mantenimiento (RUSTSEC-2025-0052). Si heredás un proyecto con async-std, migrarlo es trabajo de mantenimiento urgente, no una preferencia estética. El detalle práctico de Tokio —schedulers, JoinSet, tracing, tuning— va en RuS4. Acá vemos el mecanismo, que es lo que no cambia cuando cambiás de runtime.

RuS3.1 La diferencia fundamental: no hay runtime incluido

En JavaScript, cuando llamás una función async, el cuerpo empieza a ejecutarse ya, sincrónicamente, hasta el primer await; te devuelve una Promise que ya está en vuelo, y el event loop del navegador o de Node se encarga del resto. En Python, asyncio viene en la biblioteca estándar. En Go, el runtime con su scheduler está compilado dentro de cada binario, quieras o no.

Rust apunta a firmware, kernels y binarios sin sistema operativo. Meter un scheduler y un reactor de I/O dentro de core hubiera sido inaceptable. Entonces la biblioteca estándar define solo el contrato —los traits Future, Poll, Waker, Context— y deja la implementación afuera, en crates como Tokio o smol.

async fn guardar_en_disco(datos: Vec<u8>) -> std::io::Result<()> {
    tokio::fs::write("salida.bin", datos).await
}

fn main() {
    let datos = vec![1, 2, 3];
    guardar_en_disco(datos);   // ← ¿qué pasó acá?
    println!("listo");
}

La respuesta: no pasó absolutamente nada. No se abrió ningún archivo, no se escribió un byte, no hubo tarea en segundo plano. Se construyó un valor —un struct anónimo, en el stack— y se lo tiró al final de la sentencia. El compilador avisa:

warning: unused implementer of `Future` that must be used
 --> src/main.rs:8:5
  |
8 |     guardar_en_disco(datos);
  |     ^^^^^^^^^^^^^^^^^^^^^^^
  |
  = note: futures do nothing unless you `.await` or poll them
📌 Una async fn no es una función que corre en segundo plano: es un constructor de máquinas de estado. Llamarla te devuelve el objeto apagado. El objeto arranca cuando alguien lo .await-ea (lo que delega el trabajo de poletearlo a quien te esté poleteando a vos) o cuando se lo entregás a un ejecutor con spawn o block_on.

Compará el mismo error en los dos lenguajes. En JS, olvidarte el await es un bug de orden: la operación igual ocurre, solo que no la esperaste y las excepciones se pierden. En Rust es un bug de omisión: la operación nunca ocurre.

// Las tres formas de que una future efectivamente corra:

// 1) Esperarla dentro de otro contexto async (la más común)
async fn tarea() -> std::io::Result<()> {
    guardar_en_disco(vec![1, 2, 3]).await?;   // ahora sí
    Ok(())
}

// 2) Dársela al ejecutor como tarea independiente (concurrencia real)
let handle = tokio::spawn(guardar_en_disco(vec![1, 2, 3]));
// ... el handle es un JoinHandle; si lo dropeás, la tarea sigue viva

// 3) Bloquear un hilo sincrónico hasta que termine (el borde del mundo async)
let rt = tokio::runtime::Runtime::new()?;
rt.block_on(guardar_en_disco(vec![1, 2, 3]))?;
Confusión clásica: .await no es concurrencia. a().await; b().await; corre a y después b, secuencialmente, igual que sin async. Lo único que ganaste es que mientras a espera I/O, el ejecutor puede correr otras tareas. Para que a y b avancen a la vez necesitás tokio::join!(a(), b()) (concurrencia en la misma tarea) o dos spawn (paralelismo posible en distintos hilos).

RuS3.2 El trait Future: el contrato completo

Todo el edificio se apoya en veinte líneas de core::future:

pub trait Future {
    type Output;

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> {
    Ready(T),
    Pending,
}

Leelo palabra por palabra, porque cada pieza va a explicar un error futuro:

  • type Output — lo que produce cuando termina. Si escribiste async fn f() -> u32, el Output es u32.
  • self: Pin<&mut Self> — no es &mut self. Es una promesa de que este valor no se va a mover de dirección de memoria. Toda la sección RuS3.4 existe para explicar por qué.
  • cx: &mut Context — el canal de vuelta hacia el ejecutor. Hoy contiene esencialmente un Waker: «cuando tengas novedades, tocá este timbre».
  • Poll<Self::Output> — Ready(v) si terminó, Pending si no. No hay una tercera opción, y no hay bloqueo permitido en el medio.

Una future trivial, escrita a mano, para fijar la forma:

use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

struct YaEsta(u32);

impl Future for YaEsta {
    type Output = u32;

    fn poll(self: Pin<&mut Self>, _cx: &mut Context<'_>) -> Poll<u32> {
        Poll::Ready(self.0)      // nunca devuelve Pending: termina en el primer poll
    }
}

// Uso: `YaEsta(7).await` dentro de cualquier contexto async devuelve 7.

El contrato que firmás al implementar poll tiene cuatro cláusulas, y violarlas produce bugs que no se manifiestan como errores de compilación sino como tareas que se cuelgan para siempre:

1. poll no puede bloquear. Devolvés Ready o Pending, rápido. Un thread::sleep, un File::read sincrónico o un cálculo de 200 ms adentro de poll congelan al ejecutor y a todas las demás tareas del mismo hilo.
2. Antes de devolver Pending, tenés que garantizar que alguien va a llamar a cx.waker().wake(). Si devolvés Pending y nadie registra el waker, tu tarea nunca se vuelve a poletear. No hay timeout, no hay reintento automático: se cuelga en silencio.
3. Después de devolver Ready, no se te puede volver a poletear. Hacerlo es un bug del ejecutor y el comportamiento es libre: las futures generadas por async fn paniquean con async fn resumed after completion.
4. Te pueden poletear de más, en cualquier momento y desde cualquier hilo. Un wake espurio es legal. Tu poll tiene que ser idempotente respecto a «me preguntaron y todavía no estoy listo»: volver a chequear el estado y volver a registrar el waker.
La cláusula 2 es la que más se rompe al escribir futures a mano, y su síntoma —una tarea que se queda esperando eternamente sin consumir CPU— es indistinguible de un deadlock. Cuando algo async «se cuelga sin usar CPU», la primera hipótesis siempre es waker perdido.

RuS3.3 async fn es azúcar: la máquina de estados a mano

Acá está el corazón del módulo. El compilador toma tu async fn y la transforma en un struct anónimo que implementa Future, con un campo por cada variable local que sobreviva a un .await, y un enum de estados con un estado por cada punto de suspensión. Es exactamente la transformación que harías vos a mano si no existiera async.

Tomemos algo mínimo:

async fn total() -> u64 {
    let a = pedir(1).await;
    let b = pedir(2).await;
    a + b
}

Dos .await significan tres estados posibles: recién creada, esperando la primera, esperando la segunda (más el estado terminal). Y la variable a tiene que sobrevivir al segundo .await, así que va a vivir dentro del struct. El equivalente escrito a mano:

use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

// Fut es el tipo (anónimo, en el original) que devuelve `pedir`.
enum TotalFut<Fut: Future<Output = u64>> {
    Inicio,                          // todavía no se poleteó nunca
    EsperandoA { f1: Fut },          // suspendida en el primer .await
    EsperandoB { a: u64, f2: Fut },  // suspendida en el segundo; `a` viaja adentro
    Terminada,                       // ya devolvió Ready
}

Y el poll, que es un bucle sobre el estado. Fijate que cada .await se convierte en «poleteo a la sub-future; si me da Pending, propago Pending hacia arriba». Esa propagación es la clave: el Pending sube por toda la cadena de .await hasta el ejecutor.

impl<Fut: Future<Output = u64> + Unpin> Future for TotalFut<Fut> {
    type Output = u64;

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<u64> {
        loop {
            match &mut *self {
                TotalFut::Inicio => {
                    *self = TotalFut::EsperandoA { f1: pedir(1) };
                    // seguimos el loop: hay que poletearla al menos una vez
                }
                TotalFut::EsperandoA { f1 } => {
                    match Pin::new(f1).poll(cx) {
                        Poll::Pending => return Poll::Pending,   // ← el .await
                        Poll::Ready(a) => {
                            *self = TotalFut::EsperandoB { a, f2: pedir(2) };
                        }
                    }
                }
                TotalFut::EsperandoB { a, f2 } => {
                    let a = *a;
                    match Pin::new(f2).poll(cx) {
                        Poll::Pending => return Poll::Pending,   // ← el otro .await
                        Poll::Ready(b) => {
                            *self = TotalFut::Terminada;
                            return Poll::Ready(a + b);
                        }
                    }
                }
                TotalFut::Terminada => panic!("future poleteada después de terminar"),
            }
        }
    }
}
💡 Leé de nuevo el match y anotá cinco cosas que acabás de deducir:
· Una future no tiene stack propio. Su estado vive en un struct; por eso una tarea cuesta cientos de bytes y no dos megas.
· Reanudar es barato: saltar a una rama de un match. No hay cambio de contexto ni de stack.
· Pending se propaga hacia arriba hasta el ejecutor. Todo el árbol de .await se «desarma» y se «rearma» en cada poll.
· La cláusula 3 del contrato es literal: ese panic! del estado Terminada es el mismo mensaje que ves en producción.
· El tipo es anónimo. No podés escribir «el tipo que devuelve total()»; por eso las firmas dicen impl Future<Output = u64> o Pin<Box<dyn Future<Output = u64>>>.

El tamaño de una future, y por qué te importa

Como el struct tiene que albergar el estado más grande de todos (más las sub-futures anidadas, recursivamente), una async fn con muchos .await y buffers locales puede ser sorprendentemente pesada. Y ese tamaño se paga en cada spawn y en cada move:

async fn chica() -> u8 { 0 }

async fn gorda() -> u8 {
    let buffer = [0u8; 8192];                 // vive a través del await
    tokio::task::yield_now().await;
    buffer[0]
}

fn main() {
    println!("{}", std::mem::size_of_val(&chica()));   // unos pocos bytes
    println!("{}", std::mem::size_of_val(&gorda()));   // > 8 KB
}
Truco de producción: si tokio::spawn aparece caro en el perfil o la memoria crece con la cantidad de tareas más de lo esperado, medí size_of_val de la future antes de spawnearla. La cura típica es sacar buffers grandes fuera del cuerpo async (pasarlos por Arc, o usar BytesMut) o meter las ramas raras en un Box::pin para que no inflen el caso común.

El corolario que muerde es la recursión: una async fn que se llama a sí misma tendría tamaño infinito, porque su struct contendría una copia de sí mismo. El compilador lo detecta y te obliga a poner una indirección:

use std::future::Future;
use std::pin::Pin;

// ❌ error[E0733]: recursion in an `async fn` requires boxing
// async fn cuenta(n: u32) { if n > 0 { cuenta(n - 1).await } }

// ✅ el Box rompe la recursión de tipos: el struct guarda un puntero, no otro struct
fn cuenta(n: u32) -> Pin<Box<dyn Future<Output = ()> + Send>> {
    Box::pin(async move {
        if n > 0 {
            cuenta(n - 1).await;
        }
    })
}

RuS3.4 Pin y Unpin: por qué la máquina no se puede mover

Ahora la pregunta que todo el mundo posterga: ¿por qué poll recibe Pin<&mut Self> y no &mut self?

Porque la máquina de estados que genera el compilador puede ser auto-referencial. Mirá este código, que es perfectamente normal:

async fn procesar() {
    let datos = [0u8; 128];
    let vista = &datos[..];        // referencia a una variable local...
    enviar(vista).await;           // ...que sobrevive a un punto de suspensión
    println!("{}", vista.len());   // ...y se sigue usando después
}

El struct generado tiene que guardar las dos cosas: el arreglo datos y el puntero vista, que apunta adentro de datos. Algo con esta forma:

// Pseudocódigo de lo que genera el compilador. NO compila en Rust seguro:
struct ProcesarFut {
    datos: [u8; 128],
    vista: *const [u8],   // ← apunta a `self.datos`. AUTO-REFERENCIAL.
    estado: u8,
}
⚠️ Y acá está el problema. En Rust, mover un valor es un memcpy de sus bytes a otra dirección, y es una operación que el lenguaje considera siempre segura: nadie tiene que enterarse. Pero si movés ProcesarFut, los 128 bytes de datos viajan a otra dirección y el puntero vista sigue apuntando a la dirección vieja, que ahora es basura. Cualquier uso posterior es undefined behavior — lectura de memoria liberada, en el peor de los casos silenciosa.

El lenguaje necesitaba una forma de decir «este valor, a partir de acá, no se mueve más». Esa forma es Pin.

// Pin<P> es un wrapper sobre un puntero P que promete:
//   "el valor apuntado no se va a mover de dirección hasta que se dropee"
//
// El wrapper NO tiene runtime: es un newtype de coste cero.
// La garantía es de tipos: no existe una API segura para sacar
// un &mut T desde un Pin<&mut T> ... salvo que T sea Unpin.

pub auto trait Unpin {}   // ← "a mí moverme no me hace nada"

Unpin es un auto-trait: lo implementan automáticamente casi todos los tipos —u32, String, Vec<T>, tus structs—, porque casi ningún tipo es auto-referencial. Las excepciones importantes son exactamente dos: los tipos que contienen PhantomPinned, y las máquinas de estado generadas por async. Por eso la restricción no molesta en el 99% del código y aparece justo cuando manipulás futures a mano.

use std::pin::{pin, Pin};

let fut = procesar();          // vive en el stack, todavía movible

// Opción A — pinnear en el stack, sin asignar memoria (macro `pin!`, estable)
let mut fut = pin!(fut);       // ahora es Pin<&mut ProcesarFut>: no se puede mover
// fut.as_mut().poll(&mut cx);

// Opción B — pinnear en el heap (una asignación, pero el valor es "portátil")
let mut boxed: Pin<Box<dyn Future<Output = ()>>> = Box::pin(procesar());
// boxed.as_mut().poll(&mut cx);
📌 En la práctica casi nunca escribís Pin: lo leés en los errores. Cuando tenés una future por valor y necesitás poletearla o pasarla a algo que espera Pin, la respuesta es Box::pin (heap, funciona siempre, permite dyn) o std::pin::pin! / tokio::pin! (stack, sin asignar, pero el valor queda anclado a ese scope). Elegí pin! por default en un select! o un loop; Box::pin cuando necesites guardarla en una estructura o borrar el tipo.

Los dos errores que vas a ver, con su traducción:

error[E0277]: `dyn Future<Output = ()>` cannot be unpinned
  = note: consider using the `pin!` macro
          consider using `Box::pin` if you need to access the pinned value outside of the current scope

# Traducción: tenés una future sin pinnear y algo pide Pin. Envolvela.

error[E0596]: cannot borrow data in a dereference of `Pin<&mut Estado>` as mutable
  = help: trait `DerefMut` is required to modify through a dereference,
          but it is not implemented for `Pin<&mut Estado>`

# Traducción: estás dentro de un poll y querés &mut a un campo.
# Si tu tipo es Unpin: `self.get_mut().campo`.
# Si tiene futures adentro: usá pin-project-lite, no unsafe a mano.

Ese último caso —un struct tuyo que contiene futures y necesita poletearlas— se llama pinning estructural, y hacerlo a mano requiere unsafe y razonar sobre invariantes sutiles. La solución idiomática es la macro de pin-project-lite, que genera los accesores correctos sin que escribas unsafe:

pin_project_lite::pin_project! {
    pub struct ConLog<F> {
        #[pin] interna: F,        // se proyecta como Pin<&mut F>
        etiqueta: &'static str,   // se proyecta como &mut &'static str
    }
}

impl<F: std::future::Future> std::future::Future for ConLog<F> {
    type Output = F::Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<F::Output> {
        let this = self.project();
        match this.interna.poll(cx) {          // ya viene pinneada
            Poll::Pending => Poll::Pending,
            Poll::Ready(v) => {
                eprintln!("{} terminó", this.etiqueta);
                Poll::Ready(v)
            }
        }
    }
}
Pin tiene fama de ser la parte más incómoda del diseño, y con razón: es un parche de tipos sobre una garantía que el lenguaje no tenía. Hay trabajo en curso sobre ergonomía de pinning para hacerlo más transparente, pero a la fecha lo estable es lo que viste acá: pin!, Box::pin y pin-project-lite. No adoptes sintaxis de RFCs abiertos en código de producción.

RuS3.5 Waker y Context: cómo el ejecutor sabe cuándo reintentar

Ya sabemos que poll devuelve Pending cuando no puede avanzar. La pregunta obvia es: ¿quién le avisa al ejecutor que vuelva a intentar? Porque la alternativa ingenua —poletear todo en un bucle infinito— quemaría un núcleo al 100% para no hacer nada. Eso se llama busy polling y es exactamente lo que el diseño evita.

La respuesta es el Waker: un handle clonable, thread-safe, con un solo método útil, que la future guarda y alguien externo dispara.

pub struct Context<'a> { /* ... */ }

impl<'a> Context<'a> {
    pub fn from_waker(waker: &'a Waker) -> Context<'a>;
    pub fn waker(&self) -> &'a Waker;
}

impl Waker {
    pub fn wake(self);              // "reencolá la tarea" (consume el waker)
    pub fn wake_by_ref(&self);      // idem, sin consumirlo
    pub fn will_wake(&self, otro: &Waker) -> bool;   // ¿son el mismo?
    pub const fn noop() -> &'static Waker;           // waker que no hace nada (tests)
}

El ciclo completo, que conviene tener grabado:

   EJECUTOR                    FUTURE                   MUNDO EXTERNO
   (bucle)                     (tu código)              (epoll, timer, canal)

  saca tarea de la cola
        │
        │  poll(Pin<&mut F>, cx)
        ├──────────────────────────►
        │                      ¿hay dato listo?
        │                            │ no
        │                       guarda cx.waker().clone()
        │                            ├──────────────────────────►  registra interés
        │       Poll::Pending        │                              (fd en epoll,
        │◄───────────────────────────┤                               timer wheel...)
        │
   la tarea NO vuelve a la cola.
   el hilo duerme en epoll_wait
   (0% de CPU)                                                     ⏰ llega el evento
        │                                                                │
        │                            waker.wake()  ◄─────────────────────┘
        │◄───────────────────────────┤
   la tarea vuelve a la cola
        │
        │  poll(Pin<&mut F>, cx)     ← puede ser OTRO hilo y OTRO waker
        ├──────────────────────────►
        │       Poll::Ready(v)       │
        │◄───────────────────────────┤
   tarea completada
💡 Todo el diseño es un sistema de notificación, no de espera. Nadie «espera» a nadie: se registra interés y se devuelve el control. El hilo que corre el ejecutor termina bloqueado en una sola llamada al sistema (epoll_wait, kqueue, IOCP) que despierta cuando cualquiera de los diez mil descriptores tiene novedades. Esa es toda la ventaja de async sobre hilos: diez mil esperas se colapsan en una.

Construir un Waker desde cero exige RawWaker y una vtable con cuatro punteros de función unsafe. Casi nunca hace falta, porque desde hace años existe el trait Wake en std, que hace exactamente lo mismo con Arc y sin una línea de unsafe:

use std::sync::{Arc, mpsc::SyncSender};
use std::task::{Wake, Waker};

struct Tarea {
    cola: SyncSender<Arc<Tarea>>,
    // ... más campos en el ejemplo real
}

impl Wake for Tarea {
    fn wake(self: Arc<Self>) {
        // "despertarse" es, literalmente, volver a la cola de listos
        let _ = self.cola.clone().send(self);
    }
}

// Y la conversión es directa:
// let waker: Waker = Waker::from(arc_tarea.clone());

El bug del waker perdido

Este es el bug al implementar futures a mano, y merece su propia sección porque es sutil y su síntoma es un cuelgue silencioso. La versión rota:

// ❌ MAL: hay una ventana de carrera entre chequear y registrar
fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<()> {
    if self.estado.lock().unwrap().listo {          // (1) tomo y suelto el lock
        return Poll::Ready(());
    }
    //  ⚠️ acá, entre (1) y (2), el hilo productor puede poner listo = true
    //     y llamar a wake() sobre un waker que TODAVÍA NO GUARDAMOS.
    //     Ese wake se pierde. Nadie nos vuelve a poletear. Cuelgue eterno.
    self.estado.lock().unwrap().waker = Some(cx.waker().clone());   // (2)
    Poll::Pending
}
// ✅ BIEN: un solo lock cubre chequeo y registro; la carrera desaparece
fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<()> {
    let mut e = self.estado.lock().unwrap();
    if e.listo {
        Poll::Ready(())
    } else {
        e.waker = Some(cx.waker().clone());   // SIEMPRE sobrescribir, ver abajo
        Poll::Pending
    }
}
Segundo error, igual de común: guardar el waker solo la primera vez (if e.waker.is_none() { ... }). Está mal. Una future puede migrar entre tareas —te movieron dentro de un select!, te reubicaron en otro worker— y en cada poll te pueden entregar un waker distinto. Si guardaste el viejo, vas a despertar a una tarea que ya no es la tuya, y la tuya queda colgada. La regla es: guardá siempre el waker del poll más reciente. Si querés evitar el clone() cuando es el mismo, la comparación barata es if !viejo.will_wake(cx.waker()).

RuS3.6 Send y Sync en futures: el error más frustrante

Este es el error que más tiempo hace perder en Rust async, y su causa es siempre la misma. Empecemos por el porqué: los runtimes multi-hilo con work stealing pueden poletear tu tarea desde un hilo distinto cada vez. Por eso tokio::spawn exige:

pub fn spawn<F>(future: F) -> JoinHandle<F::Output>
where
    F: Future + Send + 'static,
    F::Output: Send + 'static;

Y acá está la parte no obvia: una future generada por async es Send si y solo si todo lo que vive a través de un .await es Send. No importa lo que uses; importa lo que sostenés mientras esperás, porque eso es lo que queda guardado en el struct que puede viajar de hilo.

use std::sync::Mutex;
use std::collections::HashMap;

// ❌ NO compila al hacer tokio::spawn de esto
async fn actualizar(cache: &Mutex<HashMap<String, u64>>, clave: String) {
    let mut guard = cache.lock().unwrap();     // MutexGuard: !Send
    let valor = consultar_api(&clave).await;   // ⚠️ el guard vive a través del await
    guard.insert(clave, valor);
}
error: future cannot be sent between threads safely
   |
   = help: within `impl Future<Output = ()>`, the trait `Send` is not implemented
           for `std::sync::MutexGuard<'_, HashMap<String, u64>>`
note: future is not `Send` as this value is used across an await
   |
   |     let mut guard = cache.lock().unwrap();

El diagnóstico es excelente si sabés leerlo: te dice el tipo culpable y el .await exacto. Los tres arreglos, en orden de preferencia:

// ✅ ARREGLO 1 (el mejor): no sostener el lock a través del await.
//    Un bloque explícito garantiza el drop antes de la espera.
async fn actualizar(cache: &Mutex<HashMap<String, u64>>, clave: String) {
    let valor = consultar_api(&clave).await;   // primero la parte lenta
    {
        let mut guard = cache.lock().unwrap(); // después, el lock, cortito
        guard.insert(clave, valor);
    }                                          // el guard muere acá
}
// ✅ ARREGLO 2: si REALMENTE necesitás sostener el lock a través del await,
//    usá el mutex async del runtime: su guard sí es Send.
use tokio::sync::Mutex;

async fn actualizar(cache: &Mutex<HashMap<String, u64>>, clave: String) {
    let mut guard = cache.lock().await;        // MutexGuard de Tokio: Send
    let valor = consultar_api(&clave).await;   // el guard sobrevive, y está bien
    guard.insert(clave, valor);
}

// ✅ ARREGLO 3: si el dato es intrínsecamente de un solo hilo (Rc, RefCell,
//    un cliente no-Send), no lo hagas Send: corré la tarea anclada a un hilo.
//    tokio::task::spawn_local dentro de un LocalSet, o LocalRuntime.
El arreglo 2 no es gratis y se abusa. tokio::sync::Mutex es varias veces más caro que std::sync::Mutex (hay una cola de wakers detrás) y, peor, invita a mantener secciones críticas largas que serializan todo tu servicio. La guía real: si la sección crítica no tiene .await adentro, usá std::sync::Mutex — es más rápido y el compilador te va a avisar si te equivocás. El mutex async es para el caso genuino de «tengo que sostener el recurso mientras espero I/O».

RuS3.7 Cancelación: cancelar es dropear la future

En casi todos los lenguajes cancelar una operación async es una ceremonia: un CancellationToken, una excepción especial, un canal de señal. En Rust la cancelación es brutalmente simple, y esa simplicidad es a la vez su virtud y su trampa:

📌 Cancelar una future es drop-earla. Se ejecuta el Drop de las variables locales que estaban vivas en el struct de estado, y nada más. El código que estaba después del .await simplemente no corre nunca. No hay excepción, no hay unwinding, no hay finally, no hay Drop asíncrono. 
async fn transferir(db: &Pool, de: Id, a: Id, monto: i64) -> anyhow::Result<()> {
    let mut tx = db.begin().await?;
    debitar(&mut tx, de, monto).await?;
    // ⚠️ si nos cancelan JUSTO acá, `acreditar` no corre nunca.
    //    Se dropea `tx` (rollback implícito si el driver lo hace en Drop),
    //    pero NADIE ejecutó un rollback async ni logueó nada.
    acreditar(&mut tx, a, monto).await?;
    tx.commit().await?;
    Ok(())
}

¿Y quién te cancela? Cuatro cosas, todas cotidianas:

  • tokio::time::timeout(dur, fut) — si vence, dropea fut.
  • tokio::select! — cuando una rama gana, dropea todas las demás.
  • JoinHandle::abort(), o dropear un JoinSet.
  • Un servidor HTTP que detecta que el cliente cerró la conexión y baja la tarea del handler.

Cancel safety: la propiedad que nadie te enseñó

Una future es cancel-safe si dropearla en cualquier punto de suspensión no pierde ni corrompe información. Es una propiedad del contrato de cada API, no algo que el compilador verifique, y por eso la documentación de Tokio la declara explícitamente método por método. Ejemplos:

API¿Cancel-safe?Por qué
mpsc::Receiver::recv✅ SíO te lleva el mensaje o no lo saca de la cola
AsyncReadExt::read✅ SíO leyó bytes al buffer y devolvió, o no consumió nada
time::sleep, Mutex::lock✅ SíNo hay estado parcial que perder
AsyncReadExt::read_exact❌ NoPuede haber leído N bytes al buffer y perderlos al cancelar
AsyncBufReadExt::read_line❌ NoLo mismo: datos ya consumidos del socket, línea incompleta
AsyncWriteExt::write_all❌ NoPuede haber escrito la mitad; el par recibe un mensaje truncado
 
// ❌ BUG DE CORRUPCIÓN SILENCIOSA
// `read_exact` no es cancel-safe: cuando el ticker gana, se dropea
// un read_exact que ya había copiado bytes al buffer. Esos bytes se
// perdieron del socket y el próximo frame arranca desalineado.
loop {
    tokio::select! {
        r = socket.read_exact(&mut cabecera) => { procesar(r?)?; }
        _ = ticker.tick() => { enviar_heartbeat().await?; }
    }
}
// ✅ ARREGLO A: sacar la operación no-cancel-safe del select.
//    La tarea de lectura vive en su propia tarea; el select solo mira canales,
//    que sí son cancel-safe.
let (tx, mut rx) = tokio::sync::mpsc::channel(64);
tokio::spawn(async move { leer_frames(socket, tx).await });

loop {
    tokio::select! {
        Some(frame) = rx.recv() => { procesar(frame)?; }
        _ = ticker.tick()       => { enviar_heartbeat().await?; }
    }
}
// ✅ ARREGLO B: pinnear la future FUERA del loop, para que sobreviva
//    a las vueltas y se retome donde iba (`&mut fut` no la dropea).
let lectura = socket.read_exact(&mut cabecera);
tokio::pin!(lectura);

loop {
    tokio::select! {
        r = &mut lectura => { procesar(r?)?; break; }
        _ = ticker.tick() => { enviar_heartbeat().await?; }
    }
}
⚠️ select! es la fuente número uno de bugs sutiles en Rust async. Se lee como un switch inocente y es, en realidad, un cancelador implícito que corre en cada vuelta del loop. La regla defensiva: en un select! dentro de un loop, cada rama debe ser cancel-safe o estar pinneada afuera. Si no podés garantizarlo, mové el trabajo a otra tarea y comunicá con canales.

Limpiar cuando te cancelan

Como no existe AsyncDrop estable, no podés hacer await en un destructor. Las tres estrategias reales:

// 1) Guard con limpieza SÍNCRONA en Drop (métricas, contadores, flags)
struct EnVuelo(std::sync::Arc<std::sync::atomic::AtomicUsize>);
impl Drop for EnVuelo {
    fn drop(&mut self) {
        self.0.fetch_sub(1, std::sync::atomic::Ordering::Relaxed);
    }
}

// 2) Limpieza asíncrona: el guard NO espera, delega en una tarea aparte
struct RollbackAlDropear(Option<Transaccion>);
impl Drop for RollbackAlDropear {
    fn drop(&mut self) {
        if let Some(tx) = self.0.take() {
            tokio::spawn(async move { let _ = tx.rollback().await; });
        }
    }
}

// 3) Cancelación cooperativa explícita: tokio_util::sync::CancellationToken.
//    En vez de que te dropeen, te enterás y salís por la puerta.
async fn worker(token: tokio_util::sync::CancellationToken) {
    loop {
        tokio::select! {
            _ = token.cancelled() => { cerrar_prolijo().await; return; }
            trabajo = proximo_trabajo() => { hacer(trabajo).await; }
        }
    }
}

RuS3.8 Streams y async en traits

Si Future es «un valor, eventualmente», Stream es «cero o más valores, eventualmente»: el equivalente async de Iterator. Su forma sale sola de combinar los dos traits:

// Iterator:  fn next(&mut self)                          -> Option<Self::Item>
// Future:    fn poll(Pin<&mut Self>, &mut Context)       -> Poll<Self::Output>
//
// Stream = la combinación de ambos:
pub trait Stream {
    type Item;
    fn poll_next(
        self: Pin<&mut Self>,
        cx: &mut Context<'_>,
    ) -> Poll<Option<Self::Item>>;
}
//   Poll::Pending          → todavía no hay ítem
//   Poll::Ready(Some(x))   → tomá este ítem, seguí pidiendo
//   Poll::Ready(None)      → se terminó el stream
Stream todavía no está en std estable (el nombre reservado es AsyncIterator). En la práctica viene de futures_core / futures, y Tokio expone tokio_stream. Tampoco hay for await: se itera a mano. 
use tokio_stream::StreamExt;

async fn consumir(mut s: impl tokio_stream::Stream<Item = u64> + Unpin) -> u64 {
    let mut total = 0;
    while let Some(x) = s.next().await {       // el equivalente de `for x in s`
        total += x;
    }
    total
}

// Los combinadores se parecen a los de Iterator, pero son perezosos y asincrónicos:
// s.map(f).filter(p).take(10).chunks_timeout(100, Duration::from_millis(50))

Sobre async fn en traits (AFIT), que ya viste en RuS2 junto con RPITIT: es estable y funciona, pero arrastra dos limitaciones que en async duelen especialmente.

trait Repositorio {
    async fn buscar(&self, id: u64) -> Option<Registro>;   // estable
}

// Limitación 1: no podés expresar "la future que devuelve es Send",
// así que `tokio::spawn` sobre un genérico con este trait falla.
//   → salida: escribir la firma a mano...
trait RepositorioSend {
    fn buscar(&self, id: u64) -> impl std::future::Future<Output = Option<Registro>> + Send;
}
//   → ...o usar el macro `trait_variant::make` para generar la variante Send.

// Limitación 2: un trait con AFIT no es dyn-compatible: no hay dyn Repositorio.
//   → salida: `async_trait` (boxea la future, cuesta una asignación por llamada)
//     o un enum que despache entre las implementaciones concretas.
Regla práctica: AFIT nativo para código genérico (sin borrado de tipo, sin coste), y #[async_trait] solo cuando necesitás dyn de verdad — un registro de plugins, inyección de dependencias en tests. La asignación por llamada es irrelevante frente a un round-trip de red, y catastrófica en un loop caliente.

RuS3.9 Bloquear el ejecutor: el pecado capital

Un runtime multi-hilo de Tokio arranca, por defecto, con tantos workers como núcleos. Cada worker corre un bucle que saca tareas de una cola y las poletea. Si un poll tarda 500 ms sin devolver, ese worker está muerto durante 500 ms: todas las tareas de su cola —que pueden ser miles de conexiones— esperan.

// ❌ Cada una de estas líneas mata un worker completo mientras dura
async fn handler(datos: Vec<u8>) -> String {
    std::thread::sleep(Duration::from_millis(200));   // sleep bloqueante
    let cfg = std::fs::read_to_string("config.toml"); // I/O sincrónica
    let hash = argon2_hash(&datos);                   // 300 ms de CPU pura
    let r = reqwest::blocking::get("https://api...");  // cliente HTTP bloqueante
    hash
}
⚠️ El síntoma en producción es traicionero: la latencia media se ve bien y la p99 explota, porque solo sufren las tareas que quedaron detrás de la que bloqueó. Si además usás std::thread::sleep dentro de un runtime current_thread, bloqueás el runtime entero. Y el caso más venenoso: llamar block_on dentro de una tarea async ya en ejecución — Tokio lo detecta y paniquea con Cannot start a runtime from within a runtime, que al menos es un error visible.

Las salidas, según qué es lo que bloquea:

// 1) I/O bloqueante o librería sincrónica sin versión async
//    → spawn_blocking: la manda a un pool de hilos SEPARADO (hasta 512 por defecto)
let cfg = tokio::task::spawn_blocking(|| {
    std::fs::read_to_string("config.toml")
}).await??;

// 2) CPU pesada y paralelizable
//    → rayon (o un pool propio) + un canal para devolver el resultado
let (tx, rx) = tokio::sync::oneshot::channel();
rayon::spawn(move || { let _ = tx.send(argon2_hash(&datos)); });
let hash = rx.await?;

// 3) CPU larga pero divisible en pedacitos dentro de la misma tarea
//    → cedé el control cada N iteraciones
for (i, item) in items.iter().enumerate() {
    procesar(item);
    if i % 1000 == 0 {
        tokio::task::yield_now().await;   // devuelve el worker a la cola
    }
}
Por qué yield_now alcanza a veces: Tokio tiene scheduling cooperativo con un presupuesto de operaciones por tarea. Muchos .await de Tokio consumen presupuesto y, al agotarse, devuelven Pending aunque el dato esté listo, para forzar que otras tareas corran. Eso protege contra tareas hambronas que siempre tienen datos, pero no protege contra un bloque de CPU sin ningún .await adentro: ahí el runtime no tiene dónde intervenir. Si tu loop no tiene puntos de suspensión, el yield_now lo ponés vos.

RuS3.10 Cuándo NO usar async

Async en Rust tiene un costo que se paga en compilación, en legibilidad, en dificultad de debugging y en errores de tipos que no existirían con hilos. Ese costo se justifica en un caso concreto: muchísimas esperas concurrentes de I/O. Fuera de ese caso, los hilos siguen siendo excelentes en Rust, y elegirlos no es un atraso.

Un CLI, un compilador, un procesador de archivos por lotes, un job de ETL, un scraper de 50 URLs con un pool de hilos: nada de eso mejora con async, y todo empeora en legibilidad. 
// Async innecesario: 50 URLs, un runtime completo, tipos async por todos lados.
// Con hilos es más corto, se debuggea con backtraces reales, compila más rápido
// y no arrastra Tokio como dependencia:
use std::thread;

let resultados: Vec<_> = thread::scope(|s| {
    urls.iter()
        .map(|u| s.spawn(move || ureq::get(u).call()))
        .collect::<Vec<_>>()
        .into_iter()
        .map(|h| h.join().unwrap())
        .collect()
});
El otro error simétrico: usar async pero con una sola tarea. Un programa que hace #[tokio::main] y después ejecuta veinte .await secuenciales no gana nada: pagaste todo el costo del modelo y no hay concurrencia que aprovechar. Si no hay al menos dos cosas que puedan avanzar a la vez, async es puro overhead conceptual.

🧑‍🎓 Worked Example — un Timer a mano y un ejecutor de 50 líneas

Objetivo: escribir una Future desde cero que se complete después de un tiempo, con su waker y un hilo que notifica; correrla en un ejecutor propio; y después reemplazar las dos piezas por Tokio para comprobar que el runtime no es magia — es este bucle.

Paso 1 — La future. El estado compartido entre el hilo que espera y el poll es un Arc<Mutex<...>> con dos campos: si ya terminó, y a quién avisarle.

use std::future::Future;
use std::pin::Pin;
use std::sync::{Arc, Mutex};
use std::task::{Context, Poll, Waker};
use std::time::Duration;

struct Estado {
    listo: bool,
    waker: Option<Waker>,
}

pub struct Timer {
    estado: Arc<Mutex<Estado>>,
}

impl Timer {
    pub fn nuevo(d: Duration) -> Self {
        let estado = Arc::new(Mutex::new(Estado { listo: false, waker: None }));
        let compartido = Arc::clone(&estado);

        // Un hilo por timer es un juguete didáctico: Tokio usa UNA rueda de
        // temporizadores para millones de timers. Ver el paso 5.
        std::thread::spawn(move || {
            std::thread::sleep(d);
            let mut e = compartido.lock().unwrap();
            e.listo = true;
            if let Some(w) = e.waker.take() {
                w.wake();          // "che, ejecutor: volvé a poletearme"
            }
        });

        Timer { estado }
    }
}

impl Future for Timer {
    type Output = ();

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<()> {
        // Un solo lock cubre chequeo + registro: no hay wakeup perdido (RuS3.5).
        let mut e = self.estado.lock().unwrap();
        if e.listo {
            Poll::Ready(())
        } else {
            e.waker = Some(cx.waker().clone());   // siempre el más reciente
            Poll::Pending
        }
    }
}
Detalle de Pin que conviene notar: dentro del poll escribimos self.estado sin ninguna ceremonia. Eso funciona porque Pin<P> siempre implementa Deref: el acceso compartido (&) nunca estuvo restringido, lo que Pin impide es sacar un &mut con el que podrías hacer mem::swap y mover el valor. Como acá solo necesitamos &Arc, no hace falta ni Unpin ni unsafe.

Paso 2 — La tarea y su waker. Una tarea es la future boxeada y pinneada, más el remitente de la cola de listos. «Despertar» es literalmente «volver a la cola».

use std::sync::mpsc::{sync_channel, Receiver, SyncSender};
use std::task::Wake;

struct Tarea {
    // Option: cuando la future termina, la sacamos y no la devolvemos.
    future: Mutex<Option<Pin<Box<dyn Future<Output = ()> + Send>>>>,
    cola: SyncSender<Arc<Tarea>>,
}

impl Wake for Tarea {
    fn wake(self: Arc<Self>) {
        let cola = self.cola.clone();
        let _ = cola.send(self);   // reencolarse ES despertarse
    }
}
Usamos SyncSender y no Sender por una razón concreta: Waker::from(Arc<W>) exige W: Wake + Send + Sync + 'static, y SyncSender<T> es Sync. Es un ejemplo perfecto de cómo los bounds de un trait de std te empujan a la estructura correcta.

Paso 3 — El ejecutor. Acá está todo el «misterio» de async: un canal, un bucle, y un poll.

pub struct Ejecutor {
    tx: SyncSender<Arc<Tarea>>,
    rx: Receiver<Arc<Tarea>>,
}

impl Ejecutor {
    pub fn nuevo() -> Self {
        let (tx, rx) = sync_channel(1024);
        Ejecutor { tx, rx }
    }

    pub fn spawn(&self, fut: impl Future<Output = ()> + Send + 'static) {
        let tarea = Arc::new(Tarea {
            future: Mutex::new(Some(Box::pin(fut))),
            cola: self.tx.clone(),
        });
        self.tx.send(tarea).expect("cola llena");
    }

    pub fn correr(self) {
        let Ejecutor { tx, rx } = self;
        drop(tx);   // cuando no queden tareas vivas, el canal cierra y salimos

        while let Ok(tarea) = rx.recv() {
            let mut slot = tarea.future.lock().unwrap();
            if let Some(mut fut) = slot.take() {
                let waker = Waker::from(Arc::clone(&tarea));
                let mut cx = Context::from_waker(&waker);

                if fut.as_mut().poll(&mut cx).is_pending() {
                    *slot = Some(fut);   // sigue viva: la guardamos para el próximo wake
                }
                // si dio Ready, `fut` se dropea acá y la tarea muere
            }
        }
    }
}

Paso 4 — Correrlo.

fn main() {
    let ex = Ejecutor::nuevo();
    let t0 = std::time::Instant::now();

    ex.spawn(async move {
        println!("[a] arranco   {:?}", t0.elapsed());
        Timer::nuevo(Duration::from_millis(300)).await;
        println!("[a] termino   {:?}", t0.elapsed());
    });

    ex.spawn(async move {
        println!("[b] arranco   {:?}", t0.elapsed());
        Timer::nuevo(Duration::from_millis(100)).await;
        println!("[b] mitad     {:?}", t0.elapsed());
        Timer::nuevo(Duration::from_millis(100)).await;
        println!("[b] termino   {:?}", t0.elapsed());
    });

    ex.correr();
}

💡 Leé la salida y date cuenta de lo que acabás de construir. Un solo hilo ejecutó dos tareas concurrentes: a arrancó primero, se suspendió, b avanzó dos veces mientras a dormía, y el total fueron ~300 ms, no 500. No hay hilos por tarea, no hay callbacks, no hay busy-wait: entre los tres puntos de suspensión el ejecutor estuvo bloqueado en rx.recv(), con 0% de CPU. Eso es exactamente lo que hace Tokio; lo único que le falta a tu ejecutor es escala, robustez y un reactor de I/O real.

Paso 5 — Lo mismo, con Tokio. Cambian dos líneas conceptuales, y ninguna idea:

#[tokio::main]
async fn main() {
    let t0 = std::time::Instant::now();

    let a = tokio::spawn(async move {                 // ← nuestro Ejecutor::spawn
        tokio::time::sleep(Duration::from_millis(300)).await;   // ← nuestro Timer
        println!("[a] termino   {:?}", t0.elapsed());
    });

    let b = tokio::spawn(async move {
        tokio::time::sleep(Duration::from_millis(100)).await;
        tokio::time::sleep(Duration::from_millis(100)).await;

Todo lo que Tokio agrega es ingeniería sobre esas tres piezas. Cuando en producción una tarea «no avanza», ahora tenés un modelo mental para preguntarte lo correcto: ¿alguien la reencoló? ¿quién tiene su waker? ¿qué worker la estaba poleteando y qué lo bloqueó?

Checkpoint — ¿lo tenés claro?

¿Por qué Future::poll recibe Pin<&mut Self> y no &mut self?

Porque la máquina de estados que genera el compilador para una async fn puede ser auto-referencial: si una referencia a una variable local sobrevive a un .await, el struct guarda el dato y un puntero a ese mismo dato. Mover el struct (un memcpy a otra dirección, algo que en Rust siempre se consideró seguro) dejaría ese puntero apuntando a basura: undefined behavior. Pin es la garantía a nivel de tipos de que el valor no se va a mover antes de dropearse; no cuesta nada en runtime y no molesta a los tipos Unpin, que son casi todos. En tu código lo resolvés con Box::pin, pin! o pin-project-lite.

Tu servicio quedó colgado: una tarea no avanza y el proceso usa 0% de CPU. ¿Qué revisás primero?

Un waker perdido: alguien devolvió Pending sin dejar registrado el waker del poll actual, o lo registró afuera del mismo lock con el que chequeó el estado (carrera clásica: el productor marca «listo» y llama a wake() justo en la ventana en que todavía no guardaste el waker). Otro sospechoso con la misma firma es haber guardado el waker solo la primera vez: si la future migró de tarea, estás despertando a otro. Si el 0% de CPU en cambio es 100%, la hipótesis se invierte: alguien está bloqueando un worker con trabajo sincrónico y hay que sacarlo a spawn_blocking o a rayon.

¿Por qué «future is not Send» aparece aunque el MutexGuard lo uses una sola vez y lo dropees enseguida?

Porque el criterio no es «lo usaste», es «está vivo en el punto de suspensión». Todo lo que sigue vivo cuando la función se suspende queda guardado dentro del struct de estado, y ese struct es el que Tokio puede mandar a otro hilo. Si en tu código el guard sigue siendo alcanzable después del .await, contamina toda la future. El arreglo confiable no es drop(guard) sino un bloque explícito { ... } que cierre el alcance antes de la espera; así el análisis del compilador ve sin ambigüedad que el guard no sobrevive. Si genuinamente necesitás sostenerlo mientras esperás I/O, ahí sí corresponde tokio::sync::Mutex, sabiendo que es más caro.

Resumen ejecutivo

  • Rust no trae runtime. std define el contrato (Future, Poll, Waker, Context) y el runtime lo pone una crate: Tokio o smol. async-std está discontinuado (RUSTSEC-2025-0052): no lo empieces y migrá lo que quede.
  • Una future es un valor inerte. Llamar una async fn no ejecuta nada; por eso el trait es #[must_use]. Corre cuando la .await-eás, la spawn-eás o la pasás por block_on.
  • async fn compila a una máquina de estados: un enum con un estado por punto de suspensión y un campo por cada local que sobreviva a un .await. De ahí salen el tamaño de la future, el panic de «resumed after completion» y la necesidad de Box::pin para recursión.
  • Pin existe porque esa máquina puede ser auto-referencial y moverla sería UB. Casi nunca lo escribís: lo leés en los errores y lo resolvés con Box::pin, pin! o pin-project-lite.
  • El ciclo es poll → Pending + registro del waker → notificación externa → re-poll. Devolver Pending sin registrar el waker cuelga la tarea para siempre; guardá siempre el waker más reciente, bajo el mismo lock con el que chequeás el estado.
  • «future is not Send» casi siempre significa que sostenés un MutexGuard de std, un Rc o un RefCell a través de un .await. El arreglo por default es un bloque que lo cierre antes de esperar, no cambiar de mutex.
  • Cancelar es dropear. El código después del .await no corre, no hay AsyncDrop, y select! dentro de un loop cancela sus ramas perdedoras en cada vuelta: cada rama debe ser cancel-safe o estar pinneada afuera.
  • Bloquear un worker mata la p99, no el promedio. I/O sincrónica y FFI van a spawn_blocking; CPU pesada a rayon; loops largos sin .await necesitan yield_now puesto a mano.
  • Async no es superior a hilos: es para muchas esperas concurrentes. Un CLI, un compilador, un job por lotes o 50 requests con un pool de hilos son mejores con std::thread, y elegir eso es criterio, no atraso.

🧠 Autoevaluación

1. Llamás guardar_en_disco(datos) —una async fn— sin .await. Compila con un warning. ¿Qué ocurrió en runtime?

En Rust no hay runtime implícito: la llamada solo construye la máquina de estados y la devuelve apagada. Nadie la poletea, así que ni siquiera se abre el archivo. La tercera opción es el comportamiento de JavaScript, donde el cuerpo de una función async corre sincrónicamente hasta el primer await — confundir los dos modelos es la fuente del bug. Por eso el trait Future es #[must_use]: futures do nothing unless you .await or poll them.

2. tokio::spawn te rechaza una tarea con «future cannot be sent between threads safely». ¿Cuál es la causa típica y el arreglo por default?

Un runtime con work stealing puede poletear la misma tarea desde hilos distintos, así que todo lo que quede vivo en un punto de suspensión —y por lo tanto guardado dentro del struct de estado— tiene que ser Send. El error incluso te señala el tipo culpable y el .await exacto. El arreglo confiable es un bloque { ... } que cierre el guard antes de la espera; recién si necesitás sostenerlo mientras esperás I/O corresponde tokio::sync::Mutex, que es más caro y tienta a alargar secciones críticas.

3. Tenés un loop con tokio::select! entre socket.read_exact(&mut buf) y un ticker de heartbeat. Los frames llegan corruptos. ¿Por qué?

En Rust cancelar es dropear, y select! dropea todas las ramas que no ganaron — en cada vuelta del loop. read_exact no es cancel-safe: puede haber consumido bytes del socket y copiado parte al buffer, y al dropearse esos bytes ya no están en el socket ni completaron un frame, así que el próximo frame arranca desalineado. No hay error ni panic: es corrupción silenciosa. Las dos salidas son mover la lectura a su propia tarea y comunicar por un canal (que sí es cancel-safe), o pinnear la future afuera del loop con tokio::pin! y esperarla por &mut para que sobreviva a las vueltas.

RuS2 — Traits avanzados: GATs, coherencia y dispatch

RuS2.0 Por qué este módulo

En la mayoría de los lenguajes orientados a objetos, cuando tenés que decidir cómo se organiza un sistema, la herramienta es la herencia: una clase base, subclases que la especializan, métodos virtuales que se sobrescriben. Rust no tiene nada de eso. No hay herencia de implementación, no hay clases abstractas, no hay super.metodo(). Lo único que hay son traits.

Eso convierte al sistema de traits en algo mucho más grande que "las interfaces de Rust". Es el lenguaje de diseño completo: el polimorfismo, la reutilización, las conversiones, las garantías de concurrencia, la sobrecarga de operadores, el manejo de errores con ? y hasta la seguridad de memoria entre hilos se expresan como traits. Si el diseño de traits está mal, no hay refactor cosmético que lo salve: la firma equivocada de un tipo asociado se propaga por cincuenta archivos.

💡 La tesis del módulo. Casi todas las decisiones difíciles de arquitectura en Rust se reducen a cuatro preguntas, y las cuatro se contestan en este módulo: (1) ¿este tipo va como parámetro genérico o como tipo asociado? (2) ¿este trait se resuelve en compilación o en runtime? (3) ¿este trait tiene que ser usable como dyn? (4) ¿esto necesita ser un trait, o alcanzaba con una función? Las tres primeras son técnicas y tienen respuestas casi mecánicas. La cuarta es de criterio y es la que más código de más genera.

Escribimos esto con Rust 1.95 y la edición 2024 como línea de base. Dos fechas importan mucho para lo que sigue: los GATs son estables desde 1.65 (noviembre 2022) y async fn en traits es estable desde 1.75 (diciembre 2023) — con una letra chica que vamos a leer entera, porque es la principal fuente de sorpresas en código async de producción.

Nota de vocabulario. Lo que durante una década se llamó object safety ("¿este trait puede usarse como dyn Trait?") se renombró oficialmente a dyn compatibility a partir de Rust 1.83. El concepto es idéntico; cambió el nombre porque "safety" en Rust ya significa otra cosa (unsafe) y confundía. Vas a ver los dos términos: en el compilador moderno leés "the trait is not dyn compatible", en el 90% de los blogs y libros vas a leer "not object safe". Son lo mismo.

RuS2.1 Tipos asociados vs parámetros de tipo: la decisión que define tu API

Un trait puede recibir tipos de dos maneras completamente distintas. La diferencia parece cosmética la primera vez que la ves y es, de lejos, la decisión de diseño más costosa de revertir.

// (A) Tipo asociado — el tipo es una SALIDA del trait.
//     Dado Self, el tipo queda determinado. Hay UNA sola respuesta.
trait Iterator {
    type Item;
    fn next(&mut self) -> Option<Self::Item>;
}

// (B) Parámetro de tipo — el tipo es una ENTRADA del trait.
//     El que llama elige. Puede haber MUCHAS respuestas para el mismo Self.
trait From<T> {
    fn from(valor: T) -> Self;
}

La formulación precisa es esta: un parámetro genérico hace que el trait sea, en realidad, una familia de traits — From<u8> y From<String> son traits distintos y un mismo tipo puede implementar los dos. Un tipo asociado, en cambio, es una función del tipo que implementa: dado Self, existe exactamente un Self::Item.

📌 El test de una línea. Preguntate: «¿tiene sentido que un mismo tipo implemente este trait más de una vez, con tipos distintos?» Si la respuesta es sí, va como parámetro genérico. Si es no, va como tipo asociado. No hay un tercer caso, y contestar mal esta pregunta se paga durante todo el ciclo de vida del código.

Por qué Iterator::Item es asociado y no parámetro

Iterator es el caso testigo perfecto porque en las primeras versiones de Rust se debatió exactamente esto. Supongamos que fuera Iterator<Item>, con parámetro:

// HIPOTÉTICO: si Iterator tuviera parámetro en vez de tipo asociado
trait Iterator<Item> {
    fn next(&mut self) -> Option<Item>;
}

struct Bytes { /* ... */ }

impl Iterator<u8>   for Bytes { /* ... */ }   // legal
impl Iterator<char> for Bytes { /* ... */ }   // TAMBIÉN legal

// Y ahora esto es irresoluble:
let b = Bytes::new();
for x in b { }              // ¿x es u8 o char? El compilador no tiene forma de saberlo.
let total: u32 = b.sum();   // ídem: ¿qué impl?

Con parámetro, cada uso de un iterador necesitaría anotación explícita. El for, que es la razón de existir del trait, dejaría de funcionar sin ayuda del programador. Con tipo asociado, en cambio, la inferencia tiene un camino único y todo el ecosistema de adaptadores (map, filter, collect) se escribe sin arrastrar parámetros.

La contracara ergonómica se ve al escribir límites (bounds). Compará las dos firmas de la misma función:

// Con tipo asociado: el tipo se restringe donde hace falta, sin agregar parámetros.
fn sumar<I>(it: I) -> u64
where
    I: Iterator<Item = u64>,
{
    it.sum()
}

// Con parámetro habría que arrastrarlo por TODA la cadena de llamadas:
fn sumar_hipotetico<T, I>(it: I) -> T
where
    I: Iterator<T>,
    T: std::iter::Sum<T>,
{
    it.sum()
}

Ese T extra no se queda quieto: cualquier función que llame a sumar_hipotetico y sea genérica también tiene que declararlo, y así hacia arriba hasta el main. Es la clase de deuda que no se ve en el primer archivo y se vuelve insoportable en el décimo.

El caso híbrido: Add tiene los dos

El operador + es el mejor ejemplo de que la decisión no es "asociado bueno, parámetro malo", sino que cada tipo cumple un rol distinto:

// std::ops::Add — simplificado
trait Add<Rhs = Self> {
    type Output;
    fn add(self, rhs: Rhs) -> Self::Output;
}
  • Rhs es parámetro (con valor por defecto Self) porque un mismo tipo tiene que poder sumarse con varios: Instant + Duration, Duration + Duration, String + &str. Son impls distintas y todas legítimas.
  • Output es asociado porque una vez fijados Self y Rhs, el tipo del resultado ya está decidido. Si Output fuera parámetro, a + b sería ambiguo y necesitarías anotar el tipo de cada suma.
use std::ops::Add;

#[derive(Debug, Clone, Copy)]
struct Metros(f64);
#[derive(Debug, Clone, Copy)]
struct Pies(f64);

// Mismo Self, dos impls: eso solo es posible porque Rhs es parámetro.
impl Add<Metros> for Metros {
    type Output = Metros;
    fn add(self, o: Metros) -> Metros { Metros(self.0 + o.0) }
}

impl Add<Pies> for Metros {
    type Output = Metros;                       // Output determinado: no hay ambigüedad
    fn add(self, o: Pies) -> Metros { Metros(self.0 + o.0 * 0.3048) }
}

let d = Metros(10.0) + Pies(3.0);   // el compilador elige el impl por el tipo del Rhs

RuS2.2 Dispatch estático vs dinámico: qué pagás en cada caso

Rust ofrece las dos formas de polimorfismo y —a diferencia de casi cualquier otro lenguaje— te hace elegir explícitamente. No hay un default oculto.

trait Dibujable {
    fn dibujar(&self) -> String;
}

// (A) Dispatch ESTÁTICO: monomorfización.
//     El compilador genera una copia de esta función POR CADA T concreto que uses.
fn render_estatico<T: Dibujable>(items: &[T]) -> String {
    items.iter().map(|i| i.dibujar()).collect()
}

// (B) Dispatch DINÁMICO: una sola copia, la decisión se toma en runtime.
fn render_dinamico(items: &[Box<dyn Dibujable>]) -> String {
    items.iter().map(|i| i.dibujar()).collect()
}

Qué hace exactamente la monomorfización

Si llamás render_estatico con Circulo, Cuadrado y Texto, el compilador emite tres funciones distintas en el binario, cada una con la llamada a dibujar resuelta y, muy probablemente, inlineada. Eso es lo que hace que los genéricos de Rust sean de costo cero en tiempo de ejecución: no queda ninguna indirección. Y también es lo que hace que el binario y el tiempo de compilación crezcan de manera lineal en la cantidad de instanciaciones.

// Lo que "ve" el backend después de monomorfizar (pseudo-código):
fn render_estatico__Circulo(items: &[Circulo]) -> String { /* dibujar de Circulo, inlineado */ }
fn render_estatico__Cuadrado(items: &[Cuadrado]) -> String { /* ... */ }
fn render_estatico__Texto(items: &[Texto]) -> String { /* ... */ }

Qué es exactamente una vtable

dyn Trait es un tipo unsized: no tiene tamaño conocido en compilación, así que siempre se usa detrás de un puntero (&dyn, Box<dyn>, Arc<dyn>). Ese puntero es gordo: son dos palabras, una al dato y otra a la vtable, una tabla estática —una por cada par (tipo, trait)— con el destructor, el tamaño, la alineación y los punteros a cada método.

use std::mem::size_of;

fn main() {
    println!("{}", size_of::<&u32>());               // 8   — puntero fino
    println!("{}", size_of::<&dyn Dibujable>());     // 16  — datos + vtable
    println!("{}", size_of::<Box<dyn Dibujable>>()); // 16
    println!("{}", size_of::<Option<Box<dyn Dibujable>>>()); // 16 — niche optimization
}

RuS2.3 Object safety: por qué no todo trait puede ser dyn

Cuando escribís Box<dyn Trait>, el compilador tiene que poder construir una vtable. Si alguna parte del trait hace eso imposible, el trait no es dyn-compatible y el error es E0038. Las reglas no son arbitrarias: cada una tapa un agujero concreto.

El receptor debe ser self, &self, &mut self, Box<Self>, Rc<Self>, Arc<Self> o Pin<P>Solo esos receptores saben llegar al dato desde un puntero gordo
Self no puede aparecer por valor en el retorno ni como tipo de un parámetroDetrás de dyn, Self es unsized: no se puede devolver ni pasar por valor

    fn nombre(&self) -> &str;
    fn escribir<W: Write>(&self, w: W);     // ✗ método genérico

// error[E0038]: the trait `Serializador` is not dyn compatible
// note: for this to be dyn compatible, the method `escribir` cannot have generic type parameters
let s: Box<dyn Serializador> = todo!();

Los tres rediseños que resuelven el 95% de los casos

1. Reemplazar el genérico por un dyn en el parámetro. Casi siempre es la solución correcta y el costo es una indirección más en un lugar donde ya estabas haciendo I/O:

trait Serializador {
    fn nombre(&self) -> &str;
    fn escribir(&self, w: &mut dyn Write) -> std::io::Result<()>;   // ✓ dyn-compatible
}

let s: Box<dyn Serializador> = Box::new(Json);
let mut buf = Vec::new();
s.escribir(&mut buf)?;

2. Excluir el método problemático de la vtable con where Self: Sized. El método sigue existiendo para los tipos concretos, pero no se puede llamar a través de dyn. Es el truco que usa Iterator para que dyn Iterator exista pese a tener sesenta métodos con genéricos:

trait Serializador {
    fn escribir(&self, w: &mut dyn Write) -> std::io::Result<()>;

    // Azúcar cómoda, pero fuera de la vtable:
    fn a_string(&self) -> String
    where
        Self: Sized,
    {
        let mut b = Vec::new();
        self.escribir(&mut b).unwrap();
        String::from_utf8(b).unwrap()
    }
}

3. Partir el trait en dos: núcleo dyn-compatible + trait de extensión con blanket impl. Es el patrón más limpio cuando querés las dos cosas: los métodos cómodos y la posibilidad de guardar Box<dyn>.

// Núcleo mínimo, dyn-compatible. Es lo que se guarda e inyecta.
trait Serializador {
    fn escribir(&self, w: &mut dyn Write) -> std::io::Result<()>;
}

// Extensión ergonómica: métodos genéricos, disponible para TODO Serializador,
// incluido `dyn Serializador` (porque el blanket cubre `T: ?Sized`).
trait SerializadorExt: Serializador {
    fn a_vec(&self) -> std::io::Result<Vec<u8>> {
        let mut b = Vec::new();
        self.escribir(&mut b)?;
        Ok(b)
    }
}

impl<T: Serializador + ?Sized> SerializadorExt for T {}
💡 Ese ?Sized del blanket impl es lo que hace que el patrón funcione. Sin él, dyn Serializador —que es unsized— no obtendría los métodos de extensión y tendrías que desreferenciar a mano en cada uso. Es exactamente lo que hacen tokio::io::AsyncReadExt, futures::StreamExt e itertools::Itertools.

El caso Clone: el que te va a morder seguro

Clone no es dyn-compatible, porque fn clone(&self) -> Self devuelve Self por valor. Entonces Box<dyn MiTrait> nunca se puede clonar si MiTrait: Clone... y peor: ni siquiera podés declarar trait MiTrait: Clone y usar dyn. La salida estándar es devolver el Box ya construido:

trait Politica {
    fn evaluar(&self, x: u32) -> bool;
    fn clonar(&self) -> Box<dyn Politica>;    // ✓ el retorno es Sized
}

impl<T> Politica for T
where
    T: 'static + Clone + PoliticaBase,
{
    fn evaluar(&self, x: u32) -> bool { self.evaluar_base(x) }
    fn clonar(&self) -> Box<dyn Politica> { Box::new(self.clone()) }
}

// Y así Box<dyn Politica> sí puede implementar Clone:
impl Clone for Box<dyn Politica> {
    fn clone(&self) -> Self { self.clonar() }
}
La crate dyn-clone hace exactamente esto con dos líneas (dyn_clone::clone_trait_object!(Politica);). Vale la pena conocer el mecanismo igual: el día que el patrón aparezca con PartialEq o con Hash —que tampoco son dyn-compatibles— vas a tener que escribirlo a mano.

RuS2.4 GATs: el tipo asociado que necesitaba un lifetime

Hay una limitación de Iterator que es fácil de no notar hasta que te choca de frente: el ítem que devuelve next no puede tomar prestado del iterador. Y no es un capricho, es una consecuencia directa de que Item sea un tipo asociado sin parámetros.

trait Iterator {
    type Item;                                    // fijo, no depende de nada
    fn next(&mut self) -> Option<Self::Item>;     // el préstamo de self es local a la llamada
}

Self::Item se elige una vez, en el impl, sin acceso al lifetime del &mut self de cada llamada. Por lo tanto el ítem no puede contener una referencia a los datos del iterador. Eso explica varias cosas que quizá viviste como rarezas:

  • No existe slice::windows_mut — cada ventana tomaría prestado el slice mutablemente.
  • BufRead::lines() devuelve io::Result<String>: asigna un String por línea. Por eso, para leer un archivo grande, la versión rápida es read_line reusando un buffer, que no es un Iterator.
  • Un parser zero-copy que devuelva tokens apuntando a su propio buffer interno no puede exponerse como Iterator.

La solución: un tipo asociado que sí toma parámetros

Los GATs (Generic Associated Types), estables desde Rust 1.65, permiten que un tipo asociado tenga sus propios parámetros de lifetime o de tipo:

trait LendingIterator {
    type Item<'a>
    where
        Self: 'a;

    fn next(&mut self) -> Option<Self::Item<'_>>;
}

Ahora Item es una función de tipos: dado un lifetime 'a, produce un tipo. Y next puede instanciarlo con el lifetime del préstamo de self. Eso es lo que era literalmente imposible de expresar antes de 1.65 — se intentaba con traits auxiliares y bounds for<'a>, y el resultado eran firmas que nadie podía leer.

struct VentanasMut<'t, T> {
    datos: &'t mut [T],
    tam: usize,
    pos: usize,
}

impl<'t, T> LendingIterator for VentanasMut<'t, T> {
    type Item<'a> = &'a mut [T]
    where
        Self: 'a;

    fn next(&mut self) -> Option<Self::Item<'_>> {
        let inicio = self.pos;
        if inicio + self.tam > self.datos.len() {
            return None;
        }
        self.pos += 1;                                   // mutamos ANTES de prestar
        Some(&mut self.datos[inicio..inicio + self.tam])
    }
}

// Y el uso: cada ventana toma prestado el iterador, así que solo puede haber una viva.
let mut v = [1, 2, 3, 4, 5];
let mut it = VentanasMut { datos: &mut v, tam: 3, pos: 0 };
while let Some(w) = it.next() {
    w.sort_unstable();          // ✓ mutamos la ventana en el lugar, sin copiar
}
📌 El where Self: 'a no es decorativo. Sin él, el compilador no puede saber que Self::Item<'a> —que puede contener referencias a datos de Self— sigue siendo válido durante 'a. Es tan universalmente necesario que rustc directamente te sugiere agregarlo en el mensaje de error. Ponelo siempre en la declaración del trait; si algún impl no lo necesita, no molesta.

El otro uso de GATs: familias de tipos

El caso de lifetime es el más famoso, pero el patrón general es "quiero que el trait devuelva un constructor de tipos, no un tipo". Ejemplo típico: un trait que devuelve un iterador que toma prestado de self.

trait Coleccion {
    type Item;
    type Iter<'a>: Iterator<Item = &'a Self::Item>
    where
        Self: 'a,
        Self::Item: 'a;

    fn iterar(&self) -> Self::Iter<'_>;
}

impl<T> Coleccion for Vec<T> {
    type Item = T;
    type Iter<'a> = std::slice::Iter<'a, T>
    where
        T: 'a;

    fn iterar(&self) -> Self::Iter<'_> { self.iter() }
}
Para este caso concreto, desde Rust 1.75 hay una alternativa mucho más corta: fn iterar(&self) -> impl Iterator<Item = &Self::Item>; con RPITIT (RuS2.5). Los GATs siguen haciendo falta cuando necesitás nombrar el tipo desde afuera, ponerle bounds adicionales, o cuando el parámetro no es un lifetime sino un tipo.

Honestidad sobre los límites

Los GATs son potentes y también incómodos. Vale la pena saberlo antes de basar una arquitectura en ellos:

  • Un trait con GATs no es dyn-compatible. Adiós Box<dyn LendingIterator>.
  • LendingIterator no está en std y probablemente tarde. No compone con los adaptadores existentes (map, filter, collect asumen que el ítem no toma prestado), no funciona con for, y varias operaciones simplemente no tienen sentido (no podés hacer collect de ítems que se invalidan en el próximo next).
  • Los mensajes de error son de los peores de Rust. Un bound de lifetime mal puesto produce errores de varias pantallas.
  • Hay límites conocidos alrededor de HRTBs (for<'a>) e implicaciones de lifetime que se van resolviendo de a poco.
Criterio práctico: usá GATs cuando el préstamo es el punto del diseño — parsers zero-copy, arenas, filas de base de datos que reusan un buffer, wrappers de FFI que prestan memoria ajena. Si estás llegando a GATs para evitar un clone() de un String chico en un camino frío, medí primero: casi seguro el clone es más barato que la complejidad que estás por agregar.

RuS2.5 impl Trait: en argumento, en retorno y dentro de traits

impl Trait significa cosas distintas según dónde aparezca. Confundirlas es una fuente clásica de errores raros.

En posición de argumento (APIT)

fn mostrar(x: impl std::fmt::Display) { println!("{x}"); }

// Es casi azúcar de:
fn mostrar_gen<T: std::fmt::Display>(x: T) { println!("{x}"); }

Casi. La diferencia es real y es de API: con impl Trait en argumento el que llama no puede usar turbofish. mostrar::<u32>(1) no compila; mostrar_gen::<u32>(1) sí. Por eso, cambiar de una forma a la otra en una función pública es un cambio incompatible aunque el código se vea equivalente.

En posición de retorno (RPIT)

fn pares(v: Vec<u32>) -> impl Iterator<Item = u32> {
    v.into_iter().filter(|x| x % 2 == 0)
}

Acá impl Trait es un tipo opaco: existe un tipo concreto real (una Filter<IntoIter<u32>, [closure]> impronunciable), el compilador lo conoce y lo optimiza, pero el que llama solo ve los bounds que declaraste. Es la única forma de devolver closures e iteradores encadenados sin Box.

Dos trampas de RPIT. (1) Solo puede haber un tipo concreto por función: si dos ramas de un if devuelven iteradores distintos, no compila — ahí necesitás Box<dyn Iterator>, Either, o un enum. (2) Los auto traits se filtran: si el tipo concreto resulta ser Send, el que llama puede usarlo como Send aunque vos no lo declaraste. Eso significa que un cambio interno tuyo que rompe Send le rompe la compilación a tus usuarios sin que la firma haya cambiado. 
// ✗ No compila: dos tipos concretos distintos para el mismo impl Trait
fn elegir(cond: bool, v: Vec<u32>) -> impl Iterator<Item = u32> {
    if cond { v.into_iter().filter(|x| x > &0) }
    else    { v.into_iter().map(|x| x * 2) }        // error[E0308]
}

// ✓ Con dyn: una sola firma, dos tipos posibles, a costa de una asignación
fn elegir_ok(cond: bool, v: Vec<u32>) -> Box<dyn Iterator<Item = u32>> {
    if cond { Box::new(v.into_iter().filter(|x| x > &0)) }
    else    { Box::new(v.into_iter().map(|x| x * 2)) }
}

Captura precisa de lifetimes y el cambio de la edición 2024

Un tipo opaco puede "capturar" lifetimes de los parámetros. En la edición 2021, un RPIT capturaba solo los lifetimes que aparecían explícitamente en los bounds, y había que escribir + '_ a mano todo el tiempo. En la edición 2024 el default se invirtió: captura todos los lifetimes en alcance, que es lo que casi siempre querés. Para el caso raro en que no lo querés, existe la sintaxis de captura precisa + use<...>, estable desde 1.82:

// Edición 2024: captura 'a y T por defecto — no hace falta el `+ 'a`
fn nombres<'a, T: Nombrable>(v: &'a [T]) -> impl Iterator<Item = &'a str> {
    v.iter().map(|x| x.nombre())
}

// Captura precisa: "este opaco NO depende de 'a", y así el que llama
// puede soltar el préstamo antes de consumir el resultado.
fn conteo<'a, T>(v: &'a [T]) -> impl Iterator<Item = usize> + use<> {
    (0..v.len()).collect::<Vec<_>>().into_iter()
}

RPITIT: impl Trait en retorno dentro de un trait

Estable desde Rust 1.75. Antes de eso, un trait que quisiera devolver un iterador tenía que declarar un tipo asociado y cada impl tenía que nombrar un tipo concreto — lo cual, con closures de por medio, era directamente imposible sin Box:

// ANTES de 1.75 — el impl tenía que nombrar el tipo, y una closure no tiene nombre
trait Almacen {
    type Iter: Iterator<Item = u32>;
    fn valores(&self) -> Self::Iter;
}

impl Almacen for MiAlmacen {
    // ✗ imposible de escribir sin Box: el tipo de un `.filter(|x| ...)` no se puede nombrar
    type Iter = std::vec::IntoIter<u32>;
    fn valores(&self) -> Self::Iter { self.datos.clone().into_iter() }  // clone forzado
}
// DESDE 1.75 — RPITIT
trait Almacen {
    fn valores(&self) -> impl Iterator<Item = u32>;
}

impl Almacen for MiAlmacen {
    fn valores(&self) -> impl Iterator<Item = u32> {
        self.datos.iter().copied().filter(|x| *x > 0)   // ✓ sin clone, sin Box
    }
}
⚠️ RPITIT tiene un precio y hay que saberlo antes de usarlo: un trait con impl Trait en retorno deja de ser dyn-compatible. No hay Box<dyn Almacen>. Además el tipo de retorno es un tipo asociado anónimo: no lo podés nombrar, no le podés agregar bounds desde afuera (por ejemplo, exigir que sea Send) ni guardarlo en un campo de struct. Ese último límite es el que vuelve venenoso el próximo tema.

RuS2.6 async fn en traits: estable, con letra chica

Desde Rust 1.75 podés escribir esto y compila:

trait Repositorio {
    async fn buscar(&self, id: u64) -> Option<Usuario>;
    async fn guardar(&self, u: &Usuario) -> Result<(), RepoError>;
}
💡 La clave para entender todo lo que sigue: async fn en un trait no es una feature aparte. Es RPITIT con azúcar. La declaración de arriba desazucara exactamente a esto: 
trait Repositorio {
    fn buscar(&self, id: u64) -> impl Future<Output = Option<Usuario>> + '_;
    fn guardar<'a>(&'a self, u: &'a Usuario)
        -> impl Future<Output = Result<(), RepoError>> + 'a;
}
Por lo tanto hereda las tres limitaciones de RPITIT: no es dyn-compatible, el futuro no se puede nombrar, y no le podés poner bounds desde afuera.

Límite 1 — no hay Box<dyn Repositorio>

// error[E0038]: the trait `Repositorio` is not dyn compatible
// note: method `buscar` returns an `impl Trait`
let repos: Vec<Box<dyn Repositorio>> = vec![];

Y esto no es un detalle académico: es exactamente lo que necesitás para tener una colección heterogénea de backends, o para inyectar un doble en un test sin volver genérico todo el árbol de tipos.

Límite 2 — el problema de los bounds Send

Este es el que más tiempo hace perder. tokio::spawn exige que el futuro sea Send. Con un trait genérico, no tenés forma de exigirlo:

async fn procesar<R: Repositorio>(repo: R) {
    tokio::spawn(async move {
        repo.buscar(1).await;     // error: el futuro devuelto puede no ser Send
    });
}

// Querrías escribir algo así, pero el tipo de retorno es anónimo:
// async fn procesar<R>(repo: R) where R: Repositorio, R::buscar(..): Send  ← no es un bound común

Es un agujero real del lenguaje, no un error tuyo. La solución portátil y madura hoy es la crate trait-variant, que genera automáticamente una variante del trait con los bounds Send puestos en cada futuro:

// Genera `RepositorioLocal` (sin Send) y `Repositorio: RepositorioLocal` con futuros Send.
#[trait_variant::make(Repositorio: Send)]
pub trait RepositorioLocal {
    async fn buscar(&self, id: u64) -> Option<Usuario>;
}

// Ahora sí:
async fn procesar<R: Repositorio + Send + 'static>(repo: R) {
    tokio::spawn(async move { repo.buscar(1).await; });
}
A nivel lenguaje, la respuesta definitiva a este problema es RTN (Return Type Notation): poder escribir where R::buscar(..): Send y hablar del tipo de retorno de un método sin nombrarlo. Es un área que se movió mucho entre 2024 y 2026; antes de apoyar una arquitectura en ella, verificá el estado exacto en la release que estés usando (rustup doc --reference o el changelog de tu versión). Mientras tanto, trait-variant funciona hoy y en toolchains viejos.

Límite 3 — el futuro no tiene nombre

No podés guardarlo en un campo de struct, ni ponerlo en un Vec, ni escribir type MiFut = <R as Repositorio>::buscar::Future;. Si tu diseño necesita almacenar futuros en vuelo —un pool, un scheduler propio, una máquina de estados— async fn nativo en trait no te alcanza.

Por qué async-trait sigue vivo en 2026

La macro #[async_trait] reescribe cada async fn como una función que devuelve un futuro boxeado:

#[async_trait::async_trait]
trait Repositorio: Send + Sync {
    async fn buscar(&self, id: u64) -> Option<Usuario>;
}

// Genera, aproximadamente:
// trait Repositorio: Send + Sync {
//     fn buscar<'a>(&'a self, id: u64)
//         -> Pin<Box<dyn Future<Output = Option<Usuario>> + Send + 'a>>;
// }

Un tipo de retorno concreto y Sized, con Send ya puesto. Eso resuelve los tres límites de un saque: el trait vuelve a ser dyn-compatible, el futuro es nombrable (BoxFuture) y los bounds Send están declarados. El costo es explícito: una asignación en el heap por cada llamada y dispatch dinámico del futuro.

📌 No es una derrota, es un trade-off explícito. Se lee mucho "usá async fn nativo, async-trait quedó obsoleto". Es falso a medias: quedó obsoleto para el caso genérico, que era el 60% de los usos. Para el 40% restante —todo lo que necesita dyn— sigue siendo la herramienta. Una asignación por llamada al lado de un round-trip a Postgres es ruido estadístico; en un loop que corre un millón de veces por segundo, no.

RuS2.7 Coherencia y la orphan rule

Coherencia es la garantía de que, para un par (trait, tipo) dado, existe como máximo una implementación en todo el programa. No en tu crate: en todo el binario final, sumando todas las dependencias transitivas.

Es una garantía más fuerte de lo que parece. Significa que HashMap<MiClave, V> hashea igual en tu código y adentro de una librería que ni sabés que existe. Significa que a == b no depende de qué módulo hizo la comparación. En lenguajes con clases de tipos "abiertas" (Scala con implicits, por ejemplo), estas garantías se pierden y aparecen bugs de los feos.

La orphan rule es el mecanismo que hace cumplir la coherencia sin necesidad de un chequeo global. Simplificando: impl Trait for Tipo es legal si el trait es local a tu crate o el tipo es local a tu crate. Si los dos son ajenos, no.

use std::fmt;

// ✓ Trait ajeno, tipo propio
struct MiTipo;
impl fmt::Display for MiTipo { /* ... */ }

// ✓ Trait propio, tipo ajeno
trait Mediana { fn mediana(&self) -> Option<f64>; }
impl Mediana for Vec<f64> { /* ... */ }

// ✗ Los dos ajenos — error[E0117]
impl fmt::Display for Vec<String> { /* ... */ }
// error: only traits defined in the current crate can be implemented for types
//        defined outside of the crate
💡 Por qué la regla es tan estricta. Sin ella, la crate ana podría implementar Display for Vec<String> y la crate beto también. Cada una compila perfecto por separado. El día que alguien dependa de las dos, el programa no linkea — y el que rompe no es ninguna de las dos, es el usuario. Peor todavía: cualquier dependencia tuya podría romperte el build agregando un impl en una versión de parche. La orphan rule convierte ese desastre distribuido en un error local y temprano.

Tipos fundamentales

Hay una excepción calculada: &T, &mut T, Box<T> y Pin<P> están marcados #[fundamental], lo que significa que son "transparentes" para la orphan rule. Si MiTipo es local, &MiTipo y Box<MiTipo> cuentan como locales:

// ✓ legal: Box es fundamental, MiTipo es local
impl fmt::Display for Box<MiTipo> { /* ... */ }

// ✗ ilegal: Vec NO es fundamental
impl fmt::Display for Vec<MiTipo> { /* ... */ }

El newtype: la salida estándar

Cuando necesitás implementar un trait ajeno para un tipo ajeno, se envuelve el tipo en una struct propia de un solo campo:

use std::fmt;

#[repr(transparent)]                       // garantiza el mismo layout que el interno
pub struct Csv(pub Vec<String>);

impl fmt::Display for Csv {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "{}", self.0.join(","))
    }
}

let filas = Csv(vec!["a".into(), "b".into()]);
println!("{filas}");     // "a,b"
📌 El newtype es gratis en runtime y caro en ergonomía. Con #[repr(transparent)], Csv ocupa exactamente lo mismo que Vec<String> y el compilador lo trata igual: cero overhead. Lo que perdés son los métodos del tipo interno — hay que delegarlos, exponer into_inner()/as_slice(), o (con mucho cuidado, ver RuS2.10) implementar Deref.

El newtype no es solo un workaround de coherencia: es una de las mejores herramientas de diseño de Rust. struct UserId(u64) y struct OrderId(u64) son tipos distintos, y el compilador te impide pasarlos cambiados — un bug que en un lenguaje con int descubrís en producción.

El patrón alternativo: extension trait

Cuando lo que querés es agregar métodos a un tipo ajeno (y no cumplir un trait ajeno), no hace falta newtype: definí un trait local y hacele blanket impl.

pub trait SliceExt<T> {
    fn mediana(&self) -> Option<f64>;
}

impl<T: Into<f64> + Copy> SliceExt<T> for [T] {
    fn mediana(&self) -> Option<f64> {
        if self.is_empty() { return None; }
        let mut v: Vec<f64> = self.iter().map(|x| (*x).into()).collect();
        v.sort_by(|a, b| a.partial_cmp(b).unwrap());
        let n = v.len();
        Some(if n % 2 == 1 { v[n / 2] } else { (v[n / 2 - 1] + v[n / 2]) / 2.0 })
    }
}

// Con `use mi_crate::SliceExt;` en alcance:
let m = [1u8, 3, 5, 7].mediana();

RuS2.8 Blanket impls y los conflictos que traen

Un blanket impl implementa un trait para todos los tipos que cumplan cierta condición. El caso canónico está en std:

// std, simplificado: todo lo que se puede mostrar se puede convertir a String
impl<T: fmt::Display + ?Sized> ToString for T {
    fn to_string(&self) -> String { /* ... */ }
}

// Y el que hace que nunca implementes Into a mano:
impl<T, U: From<T>> Into<U> for T {
    fn into(self) -> U { U::from(self) }
}

Es una herramienta potentísima —definís una vez, aplica a todo el universo de tipos que cumplan el bound— y también es la que produce los conflictos de coherencia más frustrantes.

use std::fmt::Display;

trait Serializar { fn ser(&self) -> String; }

impl<T: Display> Serializar for T {
    fn ser(&self) -> String { self.to_string() }
}

struct MiStruct { a: u32 }

impl Serializar for MiStruct {              // error[E0119]
    fn ser(&self) -> String { format!("{{\"a\":{}}}", self.a) }
}
// error[E0119]: conflicting implementations of trait `Serializar` for type `MiStruct`
Lo que sorprende: MiStruct no implementa Display. El conflicto igual existe, porque el chequeo de solapamiento no razona en negativo: no puede concluir "este impl no aplica porque el bound no se cumple", ya que ese bound podría cumplirse mañana (vos mismo agregando un impl Display, o una dependencia agregando uno). El resultado sería que un cambio aparentemente aditivo rompiera el programa. Rust prefiere rechazarlo hoy.

Las tres salidas

1. Blanket sobre un marcador propio (opt-in). En vez de aplicar a todo lo que sea Display, aplicá a todo lo que vos marcaste:

trait SerializarPorDisplay: Display {}      // marcador local, sin métodos

impl<T: SerializarPorDisplay> Serializar for T {
    fn ser(&self) -> String { self.to_string() }
}

impl SerializarPorDisplay for u32 {}        // opt-in explícito, una línea por tipo
impl SerializarPorDisplay for String {}

impl Serializar for MiStruct {              // ✓ ya no hay conflicto
    fn ser(&self) -> String { format!("{{\"a\":{}}}", self.a) }
}

2. Wrapper explícito. Si querés el comportamiento por Display solo en algunos lugares, envolvé: struct PorDisplay<T>(T); con impl<T: Display> Serializar for PorDisplay<T>. Cero conflictos, el uso queda explícito.

3. No usar blanket impl. A menudo la respuesta correcta. Un derive macro que genere el impl por tipo te da lo mismo sin comprometer la coherencia: es literalmente lo que hace serde.

⚠️ Semver: agregar un blanket impl a un trait público es un cambio incompatible. Cualquier usuario de tu crate que tenga impl TuTrait for SuTipo deja de compilar si SuTipo cumple tu nuevo bound. No aparece en ningún diff de firmas y no lo detecta cargo semver-checks en todos los casos. Si publicás una librería: definí los blanket impls en la 1.0 o no los definas nunca.
La feature que resolvería esto es specialization ("si hay un impl más específico, gana"). Lleva años en nightly con problemas de soundness abiertos, y min_specialization se usa dentro de std pero no está expuesto. No diseñes nada asumiendo que va a estabilizarse.

RuS2.9 Traits marcadores: Send, Sync, Sized, ?Sized

Algunos traits no tienen métodos: solo marcan una propiedad del tipo. Son la base de las garantías más fuertes de Rust y, por eso mismo, el compilador los maneja distinto.

Send y Sync

  • Send: es seguro mover el valor a otro hilo.
  • Sync: es seguro compartir &T entre hilos. Formalmente: T: Sync ⟺ &T: Send.

Son auto traits: el compilador los deriva estructuralmente. Una struct es Send si todos sus campos lo son. Nunca escribís impl Send for X; simplemente lo es o no lo es según de qué esté hecha.

TipoSendSyncPor qué

Arc<T>✅ si T: Send + Sync✅ si T: Send + SyncContador atómico, pero el contenido se comparte
Cell<T>, RefCell<T>✅ si T: Send❌Mutabilidad interior sin sincronización

💡 Acá está la belleza del diseño. Arc<RefCell<T>> no compila entre hilos, y no porque exista una regla que diga "no uses RefCell con hilos": simplemente RefCell no es Sync, entonces Arc<RefCell<T>> no es Send, entonces thread::spawn lo rechaza. La regla de concurrencia emerge del sistema de tipos. Todo el "fearless concurrency" de Rust son estos dos traits vacíos. 
use std::marker::PhantomData;

// Forzar !Send y !Sync sin usar features inestables: un puntero crudo fantasma.
pub struct HandleDeGrafico {
    raw: u64,
    _no_thread: PhantomData<*const ()>,   // los punteros crudos son !Send + !Sync
}

// El caso inverso: SÍ es seguro, pero el compilador no puede probarlo.
// Prometerlo requiere `unsafe` — y la prueba va en el comentario, no de adorno.
pub struct HandleFfi(*mut std::ffi::c_void);

// SAFETY: la librería C garantiza que el handle es válido desde cualquier hilo
// y que todas sus funciones son thread-safe (ver docs vX.Y, sección "Threading").
unsafe impl Send for HandleFfi {}

Sized y ?Sized

Sized significa "el tamaño se conoce en tiempo de compilación". Lo especial es que es un bound implícito: cada parámetro genérico lo lleva puesto sin que lo escribas.

fn f<T>(x: T) {}
// El compilador lee, en realidad:
fn f<T: Sized>(x: T) {}

Los tipos unsized son str, [T], dyn Trait y cualquier struct cuyo último campo lo sea. Solo se pueden usar detrás de un puntero. Para aceptarlos en genéricos hay que relajar el bound con ?Sized:

use std::fmt::Display;

fn imprimir<T: Display>(x: &T) { println!("{x}"); }
// imprimir("hola");            // ✗ str no es Sized
// imprimir(&d as &dyn Display) // ✗ dyn Display no es Sized

fn imprimir_ok<T: Display + ?Sized>(x: &T) { println!("{x}"); }
imprimir_ok("hola");             // ✓
imprimir_ok(&42 as &dyn Display); // ✓
📌 En una definición de trait, Self es ?Sized por defecto — al revés que en funciones y structs. Es justamente lo que permite que dyn Trait implemente Trait. Si escribís trait Foo: Sized, estás cerrando la puerta a dyn Foo para siempre. Hacelo solo a propósito.
Regla de oro para librerías: si una función genérica solo toca T a través de una referencia, poné ?Sized. Es gratis, no rompe a nadie, y hace que tu API acepte &str, &[T] y &dyn Trait. Al revés —quitar ?Sized después— sí es un cambio incompatible.

El resto de la familia

  • Unpin: auto trait, casi todo lo es. Marca que mover el valor después de haberlo "fijado" es seguro. Se vuelve central en async (RuS3).
  • Copy: no es auto trait. Es opt-in con derive y cambia la semántica de movimiento a copia bit a bit. Requiere Clone como supertrait.
  • 'static: no es un trait, es un bound de lifetime, pero se comporta como marcador. T: 'static significa "no contiene referencias prestadas de nada" — no significa "vive para siempre". Es la confusión más frecuente del lenguaje.

RuS2.10 Deref y coerción: la herramienta que más se abusa

Deref tiene dos efectos: el operador *, y la coerción por deref, que el compilador aplica automáticamente en los sitios de coerción y durante la resolución de métodos.

fn saludar(nombre: &str) { println!("hola {nombre}"); }

let s: String = String::from("ana");
saludar(&s);          // &String -> &str automáticamente, vía Deref<Target = str>

let v: Vec<u32> = vec![3, 1, 2];
let primero = v.first();      // `first` es de [T], no de Vec: autoderef lo encuentra

let b: Box<String> = Box::new("x".into());
let n = b.len();              // Box<String> -> String -> str: dos derefs encadenados

Es una de las razones por las que Rust se siente ergonómico pese a distinguir tantos tipos de referencia. Los usos correctos de Deref son todos del mismo tipo: punteros inteligentes — Box, Rc, Arc, String→str, Vec<T>→[T], MutexGuard<T>→T, Cow.

El abuso: Deref para simular herencia

use std::ops::Deref;

struct Usuario { id: u64, nombre: String }
struct Admin { usuario: Usuario, permisos: Vec<String> }

// ✗ ANTIPATRÓN: "Admin hereda de Usuario"
impl Deref for Admin {
    type Target = Usuario;
    fn deref(&self) -> &Usuario { &self.usuario }
}

let a = Admin { /* ... */ };
println!("{}", a.nombre);      // "funciona": parece herencia

Parece que funciona. Falla en cuanto salís de la sintaxis de punto:

trait Identificable { fn id(&self) -> u64; }
impl Identificable for Usuario { fn id(&self) -> u64 { self.id } }

fn registrar<T: Identificable>(x: &T) { /* ... */ }

registrar(&a);        // ✗ error: Admin no implementa Identificable.
                      //   La coerción por deref NO aplica a la resolución de bounds.
registrar(&*a);       // ✓ pero hay que deshacer la ilusión a mano, en cada llamada
Los cuatro problemas de Deref-como-herencia. (1) No hay subtipado: Admin no satisface T: Identificable, y ningún bound genérico lo va a aceptar. (2) Sombreado silencioso: el día que agregues Admin::nombre(), todas las llamadas a.nombre() pasan a resolver al método nuevo sin ningún aviso, porque los métodos inherentes ganan antes que los del Target. (3) Los mensajes de error empeoran mucho: el compilador habla de tipos que el lector nunca escribió. (4) Rompe el contrato: las Rust API Guidelines (C-DEREF) dicen que Deref es solo para punteros inteligentes, y todo el ecosistema lee tu código con esa expectativa.
📌 Cuándo SÍ implementar Deref: el tipo es un puntero/contenedor transparente, la conversión es infalible, barata (idealmente un campo) y no cambia el significado del valor. Cuándo NO: para reutilizar métodos de un campo. Para eso: delegación explícita (aburrida y clarísima), o exponer as_inner(), o —si lo que querés es la conversión genérica— AsRef, que es exactamente el trait para eso y no dispara magia en la resolución de métodos. 
// ✓ La versión honesta del mismo diseño: composición + delegación explícita
impl Admin {
    pub fn usuario(&self) -> &Usuario { &self.usuario }
    pub fn nombre(&self) -> &str { &self.usuario.nombre }
}

impl Identificable for Admin {
    fn id(&self) -> u64 { self.usuario.id }     // tres líneas, cero sorpresas
}

impl AsRef<Usuario> for Admin {
    fn as_ref(&self) -> &Usuario { &self.usuario }
}

RuS2.11 Conversiones: From, Into, TryFrom, AsRef y Borrow

From e Into: implementá uno, obtené el otro

Por el blanket impl impl<T, U: From<T>> Into<U> for T, implementar From te da Into gratis. Nunca implementes Into a mano.

struct Celsius(f64);
struct Fahrenheit(f64);

impl From<Celsius> for Fahrenheit {
    fn from(c: Celsius) -> Self { Fahrenheit(c.0 * 9.0 / 5.0 + 32.0) }
}

let f: Fahrenheit = Celsius(100.0).into();      // gratis
let f2 = Fahrenheit::from(Celsius(0.0));        // ídem

Dónde usar cada uno en una firma:

// Ergonómico: acepta &str, String, Cow<str>, ...
pub fn nuevo(nombre: impl Into<String>) -> Config {
    Config { nombre: nombre.into() }
}

// En camino caliente: NO forzar la asignación si el que llama no la necesita
pub fn buscar(&self, clave: &str) -> Option<&Valor> { /* ... */ }
impl Into<String> es cómodo y tiene un costo real: obliga a materializar un String aunque el que llama ya tuviera uno prestado que le alcanzaba. En un constructor que corre una vez al arranque es perfecto; en una función llamada un millón de veces por segundo es una asignación por llamada. Elegí según la posición en el perfil, no por costumbre.

? es From disfrazado

Este es el punto donde el sistema de traits se vuelve invisible y omnipresente. El operador ? desazucara, aproximadamente, a:

// expr?  ==>
match expr {
    Ok(v)  => v,
    Err(e) => return Err(From::from(e)),       // ← acá está todo
}

Es decir: ? convierte automáticamente el error al tipo de error de la función, siempre que exista el From. Por eso una función puede propagar errores de tres orígenes distintos sin una sola línea de conversión explícita:

use std::{fs, num::ParseIntError, path::Path};

#[derive(Debug)]
pub enum AppError {
    Io(std::io::Error),
    Numero(ParseIntError),
    Vacio,
}

impl From<std::io::Error> for AppError {
    fn from(e: std::io::Error) -> Self { AppError::Io(e) }
}
impl From<ParseIntError> for AppError {
    fn from(e: ParseIntError) -> Self { AppError::Numero(e) }
}

pub fn leer_puerto(p: &Path) -> Result<u16, AppError> {
    let texto = fs::read_to_string(p)?;        // io::Error   -> AppError
    let linea = texto.lines().next().ok_or(AppError::Vacio)?;
    let puerto = linea.trim().parse::<u16>()?; // ParseIntError -> AppError
    Ok(puerto)
}
thiserror genera esos From con un atributo #[from] y además el Display. No es magia nueva: es exactamente el código de arriba, escrito por una macro. Saber qué genera es lo que te permite depurar cuando ? "no encuentra la conversión" — el error siempre es que falta un From.

RuS2.12 Cuándo NO hacer un trait

Todo lo anterior fue "cómo hacerlo bien". Esta sección es la que más código de más evita.

💡 La abstracción con una sola implementación no es una abstracción: es una indirección. Un trait con un solo impl no te da flexibilidad — te da un salto extra al leer, bounds genéricos que se propagan hacia arriba por todas las firmas, errores del compilador más largos, y un "punto de extensión" que en la práctica nadie va a extender porque fue diseñado mirando un solo caso.

El argumento que casi siempre aparece es "lo necesito para testear". A veces es cierto. Muy seguido hay opciones más baratas:

SituaciónAlternativa antes del trait
Quiero sustituir una función (el reloj, un generador de IDs)Un campo con una closure: ahora: Box<dyn Fn() -> Instant>
Conjunto cerrado de comportamientos que controloenum + match: exhaustivo, sin heap, sin vtable
Quiero probar el código sin tocar la base de datosUn test de integración con testcontainers o wiremock: prueba lo que realmente corre
Un único punto de variación entre dev y prod#[cfg(test)] o una feature flag en la construcción del objeto
Reutilizar lógica entre dos structs parecidasUna función libre que reciba los datos que necesita

Señales de que el trait sí se justifica

  • Existen dos o más implementaciones reales hoy, no hipotéticas (regla de tres: extraé después del tercer uso, no antes del primero).
  • Es un borde de plugin: código de terceros va a implementarlo.
  • Publicás una librería y el usuario aporta la implementación (un trait Backend, un Formatter).
  • Necesitás una colección heterogénea genuina.
  • El trait expresa una capacidad transversal que aplica a tipos sin relación entre sí (Serialize, Display, Hash) — este es el uso más valioso de todos.

Señales de que no

  • La segunda implementación la inventaste vos para justificar el trait, y es un Fake que solo se usa en tests.
  • El trait tiene exactamente los métodos de una struct, con los mismos nombres, y el impl es una línea por método.
  • El nombre del trait es el nombre de la struct con una I adelante, o con Trait/able pegado atrás por falta de mejor idea.
  • Para llamarlo hay que agregar un parámetro genérico a cinco funciones que no les importa.
Costo oculto que casi nadie cuenta: los bounds genéricos son virales. fn servicio<R: Repositorio>(...) obliga a que quien lo llame también sea genérico, o fije el tipo. En una capa de aplicación, un trait mal ubicado convierte cincuenta firmas concretas en cincuenta firmas genéricas — y ese refactor no se revierte con un git revert tranquilo seis meses después.

Paso 1 — La primera versión, y por qué no anda

Paso 2 — Rediseño dyn-compatible

Cuatro cambios, uno por problema:

use futures::future::BoxFuture;

pub trait Repositorio: Send + Sync {
    /// (a) La constante pasa a método: entra en la vtable sin problema.
    fn tabla(&self) -> &'static str;

    /// (b) El genérico se va: el tipo de entidad es un TIPO ASOCIADO.
    ///     Es la elección correcta también por RuS2.1: un repositorio
    ///     concreto maneja exactamente una entidad.
    type Entidad: Send + Sync + 'static;

    /// (c) El futuro se boxea explícitamente: tipo concreto, Sized, Send.
    fn buscar(&self, id: u64)
        -> BoxFuture<'_, Result<Option<Self::Entidad>, RepoError>>;

    fn guardar<'a>(&'a self, e: &'a Self::Entidad)
        -> BoxFuture<'a, Result<(), RepoError>>;

    /// (d) Devolvemos el Box ya construido, no Self.
    fn clonar(&self) -> Box<dyn Repositorio<Entidad = Self::Entidad>>;
}
// El impl real. `Box::pin` es la única asignación agregada por llamada.
pub struct RepoPg { pool: sqlx::PgPool }

Checkpoint — ¿lo tenés claro?

¿Cómo decidís entre un tipo asociado y un parámetro de tipo genérico?

Con una sola pregunta: ¿tiene sentido que un mismo tipo implemente el trait más de una vez, con tipos distintos? Si sí, va como parámetro (From<T>: un tipo se construye desde muchos otros; Add<Rhs>: se suma con varios). Si no, va como asociado (Iterator::Item: un iterador itera sobre una sola cosa; TryFrom::Error: una conversión falla de una sola manera). El marco mental es entrada/salida: el parámetro lo elige quien llama, el tipo asociado lo decide quien implementa. Equivocarse hacia el parámetro cuesta anotaciones y errores de inferencia en cada uso, y contamina las firmas de toda la cadena de llamadas con un genérico extra; equivocarse hacia el asociado cuesta romper la API el día que necesitás la segunda implementación.

Agregaste un async fn a un trait que funcionaba y ahora Box<dyn Trait> dejó de compilar. ¿Qué pasó y qué opciones tenés?

async fn en un trait es azúcar de RPITIT: desazucara a fn f(&self) -> impl Future<Output = T> + '_. Y impl Trait en posición de retorno hace que el trait deje de ser dyn-compatible, porque cada impl devuelve un tipo opaco distinto y de tamaño distinto — no hay una firma única que poner en la vtable. Tres salidas: (1) #[async_trait], que reescribe el retorno como Pin<Box<dyn Future + Send + 'a>> — tipo concreto, Sized, dyn-compatible, a costa de una asignación por llamada; (2) escribir esa firma a mano con BoxFuture, mismo costo pero sin macro y con la firma visible en el código; (3) si en realidad no necesitabas dyn, quedarte con async fn nativo y agregar #[trait_variant::make(.. : Send)] para poder hacer spawn. La decisión es si el trait vive en un borde (necesita dyn) o en el núcleo genérico (no lo necesita).

Querés implementar Display para Vec<String> y el compilador te lo prohíbe. ¿Por qué, y cuál es la salida?

Es la orphan rule: Display es de std y Vec también, así que ninguno de los dos es local a tu crate (error E0117). Existe para garantizar coherencia: como máximo un impl de un trait para un tipo en todo el binario. Sin la regla, dos crates podrían implementar Display for Vec<String>, cada una compilaría bien por separado, y el programa que dependa de ambas no linkearía — rompiendo a un tercero que no hizo nada. Peor: cualquier dependencia podría romperte el build agregando un impl en una versión de parche. La salida estándar es el newtype: #[repr(transparent)] struct Csv(Vec<String>); e implementar Display for Csv. Es gratis en runtime (mismo layout, cero overhead) y cuesta ergonomía: perdés los métodos del tipo interno y hay que delegarlos o exponer into_inner(). Si lo que querías no era cumplir Display sino agregar métodos, ni siquiera hace falta el newtype: definí un trait local y hacele impl para Vec<String> (extension trait), que es legal porque el trait es tuyo.

Resumen ejecutivo

  • Tipo asociado vs parámetro genérico se decide con una pregunta: ¿puede un tipo implementar el trait más de una vez? Sí → parámetro. No → asociado. El parámetro es entrada (lo elige quien llama), el asociado es salida (lo decide quien implementa).
  • Monomorfización da costo cero en runtime y cobra en tiempo de compilación y tamaño de binario, escalando con instanciaciones × tamaño del código genérico. dyn Trait cobra una indirección (y, sobre todo, la pérdida de inlining) y no escala con la cantidad de tipos. Un enum es la tercera opción cuando el conjunto es cerrado.
  • Dyn compatibility (antes "object safety", renombrada en 1.83) prohíbe métodos genéricos, Self por valor, constantes asociadas, GATs y impl Trait en retorno. Se rediseña con &mut dyn en parámetros, where Self: Sized, o partiendo el trait en núcleo + extensión con blanket impl ?Sized.
  • GATs (estables desde 1.65) permiten un tipo asociado parametrizado por lifetime — el LendingIterator que devuelve ítems que toman prestado del iterador, imposible de expresar antes. Precio: el trait deja de ser dyn-compatible y no compone con los adaptadores de Iterator.
  • RPITIT (1.75) permite -> impl Trait dentro de traits y elimina el tipo asociado ceremonial. Precio: mata la dyn compatibility.
  • async fn en traits (1.75) es RPITIT: hereda sus tres límites — sin dyn, sin bounds Send desde afuera, futuro no nombrable. trait-variant resuelve el Send; async-trait resuelve los tres a cambio de una asignación por llamada, y por eso sigue siendo la herramienta correcta cuando necesitás dyn.
  • Coherencia garantiza un solo impl por (trait, tipo) en todo el binario. La orphan rule la hace cumplir; el newtype (gratis en runtime, caro en ergonomía) es la salida estándar, y el extension trait lo es cuando solo querés agregar métodos.
  • Blanket impls son potentes y bloquean impls específicos, porque la coherencia no razona en negativo. Agregar uno a un trait público es un cambio incompatible. La salida limpia es blanquear sobre un marcador propio con opt-in explícito.
  • Send/Sync son auto traits derivados estructuralmente: de ahí sale toda la seguridad de concurrencia sin una sola regla especial. Sized es un bound implícito en genéricos y, al revés, Self en un trait es ?Sized por defecto.
  • Deref es para punteros inteligentes, no para simular herencia: no da subtipado, sombrea métodos en silencio y empeora los errores. Para reutilizar un campo, delegá o usá AsRef.
  • From/Into (implementá solo From) y TryFrom son la base de ?, que literalmente llama a From::from sobre el error. AsRef es ergonomía; Borrow tiene un contrato semántico fuerte (Hash/Eq/Ord equivalentes) y romperlo produce búsquedas fallidas silenciosas.
  • Un trait con una sola implementación es una indirección, no una abstracción. Antes de crearlo, evaluá una closure, un enum, un test de integración o #[cfg(test)].

1. Tenés trait Politica { fn clonar(&self) -> Self; } y el compilador rechaza Box<dyn Politica> con E0038. ¿Cuál es la causa exacta?

Detrás de dyn Politica, el tipo concreto se borró: Self pasa a ser unsized y no se puede devolver por valor ni pasar por valor. Por eso Clone —cuya firma es fn clone(&self) -> Self— nunca es dyn-compatible. La salida estándar es devolver el puntero ya construido: fn clonar(&self) -> Box<dyn Politica>, que sí es Sized, y después impl Clone for Box<dyn Politica> delegando en él. Ojo con la opción 1: agregar Self: Sized al trait hace exactamente lo contrario — prohíbe dyn para siempre.

2. Tenés impl<T: Display> MiTrait for T y agregás impl MiTrait for MiStruct. MiStruct no implementa Display. ¿Qué pasa?

La coherencia no puede apoyarse en la ausencia de un impl. Si lo hiciera, agregar un impl Display for MiStruct —un cambio aparentemente aditivo, y que hasta podría venir de una dependencia— rompería el programa retroactivamente. Rust prefiere el error temprano. Las salidas son: blanquear sobre un marcador propio con opt-in explícito (trait MiMarcador: Display {}), usar un wrapper (struct PorDisplay<T>(T)), o directamente no usar blanket impl y generar los impls con un derive. Y recordá el corolario de semver: agregar un blanket impl a un trait público es un cambio incompatible.

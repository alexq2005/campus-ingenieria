Módulo 09 — Lifetimes

Bienvenido a la parte más temida de Rust. Respirá: vamos despacio. Los lifetimes tienen mala fama porque la sintaxis se ve rara (&'a str) y porque suelen aparecer en mensajes de error largos. Pero la idea es simple, y lo más importante: casi nunca vas a escribirlos a mano. Al terminar este módulo vas a entender qué son, por qué existen, y cuándo (en las pocas ocasiones) hay que anotarlos.

¿Qué es un lifetime?

💡 Un lifetime es CUÁNTO VIVE una referencia. No es un tipo de dato ni un valor en memoria: es información que el compilador usa para garantizar que ninguna referencia sobreviva al dato que apunta. Ese es el objetivo único: cero dangling references (referencias colgadas que apuntan a memoria liberada). Los lifetimes no cambian el runtime — el programa compilado corre exactamente igual. Solo le informan al compilador para que pueda chequear tu código.

Vení de M03 (borrowing): cuando hacés &x tomás prestada una referencia a x. El borrow checker ya te asegura que no usás esa referencia después de que x se libere. Los lifetimes son simplemente las etiquetas que ese chequeo usa por debajo. La mayoría del tiempo el compilador las pone solo.

La buena noticia: casi nunca los escribís

Lifetime elision (elisión de lifetimes): el compilador deduce los lifetimes solo en la enorme mayoría de los casos siguiendo unas reglas fijas. Por eso podés llevar módulos enteros de Rust sin escribir una sola 'a. Si venís asustado por capturas de pantalla de código lleno de &'a, tranquilo: ese código es la excepción, no la regla del día a día.

Por ejemplo, esta función toma una referencia y devuelve otra, y no necesita ninguna anotación — el compilador la infiere:

// El compilador deduce los lifetimes: no escribís nada.
fn primera_palabra(s: &str) -> &str {
    let bytes = s.as_bytes();
    for (i, &b) in bytes.iter().enumerate() {
        if b == b' ' {
            return &s[0..i];
        }
    }
    &s[..]
}

Funciona porque hay una sola referencia de entrada: el compilador asume que la salida está atada a esa entrada. No hay ambigüedad, así que no hace falta anotar.

¿Cuándo SÍ hay que anotarlos?

📌 La regla práctica: tenés que anotar lifetimes cuando una función devuelve una referencia y el compilador no puede deducir a cuál de los inputs está atada. Si hay dos (o más) referencias de entrada y devolvés una referencia, el compilador no sabe cuál de las dos sobrevive en la salida — ahí tenés que decírselo vos.

Ese es prácticamente el único escenario común. Si tu función no devuelve referencias, o solo recibe una, el elision te cubre.

La sintaxis: el parámetro 'a

Un lifetime se escribe con una comilla simple seguida de un nombre corto, casi siempre 'a. Se declara entre <> después del nombre de la función, igual que un parámetro genérico de tipo (M07). Mirá la función clásica, "el más largo de dos strings":

fn mas_largo<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() {
        x
    } else {
        y
    }
}

Leamos esa firma de izquierda a derecha, con calma:

💡 Qué promete esa firma: como x, y y el retorno comparten 'a, le estás diciendo al compilador que el retorno vive tanto como el MENOR de los dos inputs. Es decir: la referencia devuelta es válida solo mientras AMBOS, x e y, sigan vivos. En cuanto el primero de los dos muere, la salida deja de ser válida. El compilador usa esa promesa para rechazar cualquier uso peligroso.

¿Por qué hace falta acá y no en primera_palabra?

Porque mas_largo recibe dos referencias y devuelve una. El compilador no puede adivinar si el retorno está atado a x o a y — depende de cuál sea más largo, algo que solo se sabe en runtime. Sin la anotación, no sabría cuánto tiempo es seguro usar el resultado. La 'a resuelve la ambigüedad: "el resultado dura lo que dure el menor de los dos".

🔗 Analogía: pensá los lifetimes como etiquetas adhesivas con fecha de vencimiento que le pegás a cada referencia. La etiqueta le dice al compilador: "esta referencia es válida durante este tramo, no más". No hacen nada cuando el programa corre — son una promesa verificada en compilación, no código que se ejecuta. Como el cartel "consumir antes de…": no cambia la comida, solo informa hasta cuándo es segura.

Lifetimes en structs que guardan referencias

Hasta ahora tus structs (M04) guardaban datos que poseían (String, i32). Pero un struct también puede guardar una referencia a un dato que vive afuera. Cuando lo hace, Rust te obliga a anotar el lifetime, porque el struct no puede sobrevivir al dato que referencia:

struct Extracto<'a> {
    parte: &'a str,
}

fn main() {
    let novela = String::from("Llamame Ismael. Hace algunos años...");
    let primera = novela.split('.').next().unwrap();
    let e = Extracto { parte: primera };
    println!("{}", e.parte);
}

El <'a> después de Extracto dice: "una instancia de Extracto no puede vivir más que la referencia parte que guarda adentro". Si novela se liberara mientras e todavía existe, sería una dangling reference — y el compilador no lo permite.

✅ Truco mental: si un struct tiene un campo que es & (referencia), va a necesitar un lifetime. Si todos sus campos son dueños de sus datos (String, Vec, números), no necesita ninguno.

El lifetime especial 'static

Hay un lifetime con nombre propio: 'static. Significa que la referencia vive durante todo el programa, de principio a fin. El caso más común son los literales de string, que están incrustados en el binario:

// Todo literal de string tiene tipo &'static str.
let saludo: &'static str = "Hola, mundo";
⚠️ No abuses de 'static: a veces, al pelear con el compilador, uno cae en la tentación de marcar todo como 'static para "callar el error". Casi siempre es la solución equivocada — fuerza datos a vivir más de lo necesario o esconde el problema real. Usalo solo cuando el dato genuinamente vive todo el programa.

El error más común (y cómo NO sufrirlo)

Devolver una referencia a una variable LOCAL de la función. Esto es el clásico que no compila. La variable local se libera al terminar la función, así que la referencia quedaría colgada: 
// ❌ NO compila: `s` muere al salir de la función.
fn roto() -> &str {
    let s = String::from("hola");
    &s   // referencia a algo que está por desaparecer
}

El compilador rechaza esto y te dice que s "no vive lo suficiente". Ninguna anotación de lifetime lo arregla, porque el problema es real: el dato desaparece. La solución no es pelear con 'a, es devolver un valor que sea dueño de sí mismo:

// ✅ Compila: devolvés un String owned, sin referencias colgadas.
fn arreglado() -> String {
    String::from("hola")
}
🚫 La trampa más grande con lifetimes: ponerte a pelear con anotaciones <'a> cada vez más complicadas cuando devolver un valor owned (un String, o un .clone()) sería más simple y más claro. Antes de meter lifetimes en una firma, preguntate: ¿necesito de verdad devolver una referencia, o me conviene devolver el dato en propiedad? Muchas veces la respuesta es lo segundo, y el código queda mucho más legible.

Checkpoint — ¿lo tenés claro?

¿Qué representa un lifetime y afecta el rendimiento del programa?

Representa cuánto vive una referencia. Es solo información para el compilador, que la usa para garantizar que ninguna referencia sobreviva al dato que apunta. No afecta el runtime: el programa compilado corre igual con o sin las anotaciones.

¿Por qué mas_largo<'a>(x: &'a str, y: &'a str) -> &'a str necesita la anotación pero primera_palabra(s: &str) -> &str no?

Porque primera_palabra tiene una sola referencia de entrada: el compilador deduce (elision) que la salida está atada a ella. mas_largo tiene dos referencias de entrada y devuelve una; el compilador no puede saber a cuál está atada la salida, así que vos se lo decís con 'a: el retorno vive tanto como el menor de los dos inputs.

Tu función crea un String local y querés devolverlo por referencia, pero no compila. ¿Qué hacés?

No intentes arreglarlo con lifetimes: el problema es real, la variable local muere al salir de la función. Devolvé el valor owned (el String directamente, no &String). Es más simple y correcto.

Ejercicios

  1. Escribí fn mas_largo<'a>(x: &'a str, y: &'a str) -> &'a str y llamala con dos strings de distinto largo. Comprobá que devuelve el más largo.
  2. Sacá la anotación 'a de mas_largo y mirá el mensaje de error del compilador. Leelo entero: te dice exactamente qué lifetime falta.
  3. Definí struct Extracto<'a> { parte: &'a str } y construí una instancia tomando la primera oración de un String. Imprimí e.parte.
  4. Escribí una función rota que devuelva &str a una variable String local. Confirmá que no compila; después arreglala devolviendo String (owned) en vez de la referencia.
  5. Declará let s: &'static str = "campus"; y explicá en un comentario por qué los literales de string son 'static.

🧠 Autoevaluación

1. ¿Qué representa un lifetime en Rust?

Un lifetime es información sobre cuánto vive una referencia. El compilador la usa para evitar dangling references. No afecta el runtime y Rust no tiene garbage collector.

2. ¿Cuándo tenés que anotar lifetimes a mano?

La mayoría se infieren por elision. Solo hace falta anotar cuando devolvés una referencia y hay ambigüedad sobre a cuál input pertenece (típicamente, dos o más referencias de entrada).

3. Tu función arma un String local y querés devolver &str apuntando a él, pero no compila. ¿La mejor solución?

El problema es real: la variable local muere al salir. Ningún lifetime lo arregla. Devolver el valor owned (String) es más simple y correcto; 'static solo escondería el problema.

Módulo 10 — Concurrencia sin Miedo

La concurrencia es famosa por sus bugs: programas que funcionan mil veces y fallan la vez 1001, errores que solo aparecen en producción bajo carga, condiciones de carrera imposibles de reproducir. Rust acuñó un término para su enfoque: fearless concurrency — concurrencia sin miedo. La promesa no es que la concurrencia sea fácil, sino que el bug más temido simplemente no compila.

El data race que no puede existir

💡 El borrow checker hace imposible un data race EN COMPILACIÓN. Un data race ocurre cuando dos hilos acceden al mismo dato al mismo tiempo, al menos uno escribe, y no hay sincronización. Es el bug clásico de la concurrencia. En Rust, las mismas reglas de ownership que ya conocés (un solo &mut a la vez, o muchos & compartidos pero ninguno mutable) se aplican también entre hilos. Compartir un dato mutable sin sincronizar simplemente no compila. Eso es fearless concurrency: el compilador te salva del bug antes de ejecutar.

En otros lenguajes la concurrencia segura depende de tu disciplina: acordate de tomar el candado, acordate de no compartir ese buffer. En Rust el compilador verifica esa disciplina. Si el código podría tener un data race, no llega ni a correr.

Threads: ejecutar en paralelo

Un thread (hilo) es una línea de ejecución independiente. Rust te deja lanzarlos con thread::spawn, que recibe una closure (función anónima) con el trabajo a hacer:

use std::thread;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..5 {
            println!("hilo secundario: {i}");
        }
    });

    for i in 1..3 {
        println!("hilo principal: {i}");
    }

    handle.join().unwrap(); // esperar a que el hilo termine
}
📌 .join() espera al hilo. thread::spawn devuelve un JoinHandle. Llamar handle.join() bloquea hasta que ese hilo termina. Sin el join(), el hilo principal podría terminar primero y matar a los secundarios a mitad de camino.

Closures move: transferir ownership al hilo

Un hilo puede vivir más que la función que lo lanzó. Por eso, si la closure usa datos de afuera, Rust necesita garantizar que esos datos sigan vivos. La solución es move: le decís a la closure que tome ownership de los datos que captura.

use std::thread;

fn main() {
    let datos = vec![1, 2, 3];

    // move || transfiere ownership de `datos` al hilo
    let handle = thread::spawn(move || {
        println!("el hilo es dueño de: {datos:?}");
    });

    handle.join().unwrap();
    // acá ya NO podés usar `datos`: su ownership se movió al hilo
}
¿Por qué move? Sin move, la closure pediría prestado (&datos) y el compilador no podría probar que datos vive lo suficiente — el hilo podría seguir corriendo cuando main ya liberó el vector. Con move ||, el dato viaja dentro del hilo y el problema desaparece.

Compartir estado: Arc<Mutex<T>>

¿Y si varios hilos necesitan el mismo dato y modificarlo? move no alcanza: solo un hilo puede ser dueño. Necesitás dos piezas que se combinan:

TipoQué resuelve
Arc<T>Atomically Reference Counted: permite que varios dueños compartan el mismo dato entre hilos de forma segura. Cuenta referencias de manera atómica.
Mutex<T>Mutual Exclusion: un candado. Solo un hilo a la vez puede acceder al dato; los demás esperan su turno.
Arc<Mutex<T>>El combo idiomático: compartir (Arc) un dato protegido (Mutex) entre varios hilos.

El ejemplo canónico: varios hilos incrementando un contador compartido.

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // Arc para compartir; Mutex para proteger el i32
    let contador = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let contador = Arc::clone(&contador); // nueva referencia compartida
        let handle = thread::spawn(move || {
            // lock() devuelve un guard; se libera solo al salir de scope
            let mut n = contador.lock().unwrap();
            *n += 1;
        });
        handles.push(handle);
    }

    for h in handles {
        h.join().unwrap();
    }

    println!("Resultado: {}", *contador.lock().unwrap()); // 10
}
📌 Arc::clone NO copia el dato. Solo incrementa el contador de referencias y devuelve otro puntero al mismo valor. Es barato. Cada hilo recibe su propia Arc (su propio dueño compartido) gracias al move.
🔗 Una analogía: el Mutex es el baño de una oficina con una sola llave. Arc reparte copias de la dirección del baño a todos. Para entrar, cada uno toma la llave (lock()); mientras la tiene, nadie más entra; al salir devuelve la llave automáticamente (cuando el guard sale de scope). Nadie se pisa porque el candado serializa el acceso.

Channels: comunicar en vez de compartir

Compartir memoria con candados funciona, pero hay otra filosofía (popularizada por Go): "no comuniques compartiendo memoria; comparte memoria comunicando". Rust trae channels en std::sync::mpsc — multiple producer, single consumer (múltiples productores, un consumidor).

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel(); // tx = transmisor, rx = receptor

    thread::spawn(move || {
        let mensajes = vec!["hola", "desde", "el", "hilo"];
        for m in mensajes {
            tx.send(m).unwrap(); // enviar al canal
        }
    });

    // rx es iterable: recibe hasta que el canal se cierra
    for recibido in rx {
        println!("Recibí: {recibido}");
    }
}
tx.send / rx.recv: tx.send(v) manda un valor; rx.recv() bloquea hasta recibir uno (o devuelve error si el canal se cerró). Podés clonar tx para tener varios productores. Cuando todos los transmisores se sueltan, el receptor sabe que no llegan más mensajes y el for termina solo.

Send y Sync: los traits que vigilan los hilos

¿Cómo sabe el compilador qué es seguro mover o compartir entre hilos? Con dos marker traits (marcas) que se implementan casi siempre solos:

TraitSignificado
SendEl tipo se puede mover a otro hilo de forma segura. Casi todos lo son. Rc<T> NO (por eso existe Arc).
SyncEl tipo se puede compartir por referencia (&T) entre hilos de forma segura.

No los implementás a mano casi nunca: el compilador los deriva automáticamente. Pero te sirve entender el mensaje de error cuando aparezca "the trait Send is not implemented": significa "este tipo no es seguro de mover entre hilos, y por eso no te dejo".

💡 Acá está el truco completo. Send y Sync son parte del sistema de tipos. Cuando intentás mover algo inseguro a un hilo, falla la verificación de traits — en compilación. La seguridad de concurrencia no es una librería ni una convención: está tejida en el lenguaje mismo.

Los errores clásicos (que Rust te perdona o te detecta)

Querer compartir un &mut entre hilos. No compila — y eso te SALVA. Es exactamente el data race que destruiría tu programa en otro lenguaje. El compilador te empuja hacia Arc<Mutex<T>> o un channel, que son seguros.
Deadlock con Mutex. El borrow checker NO te salva de esto. Si un hilo toma el lock A y espera el B, mientras otro toma el B y espera el A, se traban para siempre. También pasa con lock anidado (tomar el mismo Mutex dos veces sin soltarlo). Regla: tomá los locks siempre en el mismo orden y por el menor tiempo posible.
Olvidar .join(). Si main termina antes que los hilos, el programa se cierra y los hilos secundarios mueren a mitad de trabajo — sin error, sin aviso. Siempre hacé join() de los handles que te importan.
⚠️ "No compila" ≠ "no hay bugs". Rust elimina los data races, no todos los bugs de concurrencia. Deadlocks, livelocks y lógica de orden incorrecta siguen siendo tu responsabilidad. La diferencia es que el bug más sutil y catastrófico — el acceso simultáneo no sincronizado — queda descartado de raíz.

Checkpoint — ¿lo tenés claro?

¿Por qué se dice que Rust ofrece "fearless concurrency"?

Porque las reglas de ownership y el borrow checker hacen imposible un data race en tiempo de compilación. El bug más temido de la concurrencia (acceso simultáneo no sincronizado a datos mutables) simplemente no compila, así que no llega a producción.

¿Para qué sirve cada pieza de Arc<Mutex<T>>?

Arc (referencia atómica contada) permite que varios hilos sean dueños compartidos del mismo dato. Mutex (exclusión mutua) es el candado que garantiza que solo un hilo a la vez accede al dato. Juntos: compartir un dato mutable de forma segura entre hilos.

¿Qué diferencia hay entre usar un Mutex y usar un channel mpsc?

Con Mutex los hilos comparten memoria y se sincronizan con un candado. Con un channel mpsc los hilos comunican: un hilo envía valores con tx.send y otro los recibe con rx.recv, sin compartir el dato directamente. Es el estilo "comparte memoria comunicando".

Ejercicios

  1. Lanzá 3 hilos con thread::spawn que impriman su número del 0 al 2. Hacé join() de todos y verificá que el programa espera a que terminen.
  2. Creá un vec![1, 2, 3] y movélo a un hilo con move ||. Intentá usarlo en main después del spawn y leé el error del compilador sobre el ownership movido.
  3. Replicá el contador con Arc<Mutex<i32>>: 10 hilos que suman 1 cada uno. Verificá que el resultado final sea exactamente 10.
  4. Armá un channel mpsc donde un hilo envíe los números del 1 al 5 con tx.send y el hilo principal los reciba iterando sobre rx.
  5. Cloná el tx de un channel y pasalo a dos hilos distintos (dos productores). Comprobá que el receptor recibe los mensajes de ambos.

🧠 Autoevaluación

1. ¿Qué bug de concurrencia hace Rust imposible en tiempo de compilación?

El borrow checker aplica las reglas de ownership entre hilos, así que un data race no compila. Los deadlocks y la lógica incorrecta siguen siendo posibles.

2. ¿Cuál es el combo idiomático para compartir un dato mutable entre varios hilos?

Arc permite varios dueños entre hilos (referencia atómica) y Mutex protege el acceso con un candado. Rc no es Send, así que no sirve entre hilos.

3. ¿Para qué sirve una closure move || al lanzar un hilo?

Con move la closure toma ownership de lo que captura, así el dato viaja dentro del hilo y el compilador no necesita probar que el préstamo vive lo suficiente.

Módulo 12 — Proyectos Integradores

Llegaste al final. Ya tenés todo Rust en la cabeza: ownership y borrowing, structs y enums, Option y Result con el operador ?, genéricos, traits, iteradores, concurrencia, y Cargo con tests. Lo que falta no es más teoría — es integrarlo en proyectos reales, donde las piezas dejan de estar aisladas y empiezan a trabajar juntas.

Esta guía es distinta a los módulos anteriores. Menos explicación, más estructura. Te presento 4 proyectos, cada uno con su objetivo, los módulos del curso que aplica, las fases para construirlo, y un criterio claro de "✅ terminado cuando…". No te doy el código resuelto — esa es justamente la parte que tenés que escribir vos.
💡 Por qué proyectos y no más lecciones. Saber cada concepto por separado no es lo mismo que combinarlos. Un proyecto real te obliga a decidir: ¿esto es un struct o un enum? ¿devuelvo Result o hago panic!? ¿clono o presto una referencia? Ahí es donde Rust deja de ser teoría y se vuelve tuyo.

🛠️ Proyecto 1 — Una CLI rápida

Objetivo: construir una herramienta de terminal que reciba argumentos y procese texto. Una buena primera elección es un contador de palabras (estilo wc) o un mini-grep que busque un patrón en un archivo. Es el proyecto perfecto para entrar: poco vistoso, pero te hace tocar argumentos, archivos y manejo de errores de una.

Módulo del cursoCómo lo aplicás acá
M04 — Structs & EnumsModelar la configuración (patrón a buscar, ruta del archivo) en un struct
M06 — Manejo de erroresResult + el operador ? para propagar fallos de lectura del archivo
M07 — Iteradoreslines(), filter(), split_whitespace(), count() sobre el contenido
std / crate clapLeer argumentos con std::env::args (a mano) o con el crate clap (declarativo)

La forma mínima, sin dependencias, arranca leyendo argumentos del entorno:

use std::env;
use std::fs;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let args: Vec<String> = env::args().collect();
    let patron = &args[1];
    let ruta = &args[2];

    let contenido = fs::read_to_string(ruta)?;   // el ? propaga el error de I/O

    for linea in contenido.lines() {
        if linea.contains(patron) {
            println!("{}", linea);
        }
    }
    Ok(())
}
Subí el nivel con clap. Cuando quieras flags reales (--ignore-case, --count), agregá el crate clap con cargo add clap --features derive y describí los argumentos con un struct anotado. Es la forma idiomática de las CLIs serias en Rust.

Fases para construirlo:

  1. Crear el proyecto con cargo new mi-grep y correrlo vacío.
  2. Leer los argumentos con std::env::args e imprimirlos para ver que llegan bien.
  3. Leer el archivo con fs::read_to_string y devolver Result con ?.
  4. Iterar las líneas y filtrar las que contienen el patrón.
  5. Manejar los errores feos: ¿qué pasa si faltan argumentos? ¿si el archivo no existe?
  6. (Opcional) Migrar a clap y agregar un flag --count que muestre cuántas coincidencias hubo.
✅ Terminado cuando…
  • Corre con cargo run -- patron archivo.txt y muestra las líneas que coinciden.
  • Si el archivo no existe, falla con un mensaje claro (no con un panic críptico).
  • Si faltan argumentos, avisa cómo usar el programa.
  • No hay ningún .unwrap() en el camino feliz: usás ? y Result.

📚 Proyecto 2 — Mini librería con tests

Objetivo: escribir un crate (una librería) con una API limpia y bien testeada. La mejor elección es una estructura de datos pequeña: una pila (stack, LIFO) o una cola (queue, FIFO). Es chico, pero te obliga a pensar en la interfaz pública y en los casos borde (¿qué pasa al sacar de una pila vacía?).

Módulo del cursoCómo lo aplicás acá
M07 — GenéricosUna Pila<T> que funcione para cualquier tipo, no solo enteros
M08 — TraitsImplementar Default, o derivar Debug y Clone para la API
M04 — Optionpop() devuelve Option<T>: Some si hay, None si está vacía
M11 — Tests#[test] para cubrir push, pop, vacía, y el orden LIFO

El esqueleto de una pila genérica se ve así:

pub struct Pila<T> {
    elementos: Vec<T>,
}

impl<T> Pila<T> {
    pub fn nueva() -> Self {
        Pila { elementos: Vec::new() }
    }

    pub fn push(&mut self, item: T) {
        self.elementos.push(item);
    }

    pub fn pop(&mut self) -> Option<T> {
        self.elementos.pop()      // devuelve None si está vacía
    }

    pub fn esta_vacia(&self) -> bool {
        self.elementos.is_empty()
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn pop_respeta_lifo() {
        let mut p = Pila::nueva();
        p.push(1);
        p.push(2);
        assert_eq!(p.pop(), Some(2));   // el último que entró, sale primero
        assert_eq!(p.pop(), Some(1));
        assert_eq!(p.pop(), None);      // vacía → None
    }
}
Una pila es una pila de platos. Apilás platos arriba (push) y solo podés sacar el de más arriba (pop) — el último que pusiste. LIFO: Last In, First Out. Una cola, en cambio, es la fila del banco: el primero que llega es el primero que se atiende (FIFO).

Fases para construirlo:

  1. cargo new mi-pila --lib (el flag --lib crea una librería, no un binario).
  2. Definir Pila<T> con un Vec<T> adentro.
  3. Implementar nueva, push y pop (que devuelve Option<T>).
  4. Agregar esta_vacia y len.
  5. Escribir tests con #[test]: el orden LIFO, sacar de vacía, push/pop alternados.
  6. Correr cargo test y que todo pase en verde.
✅ Terminado cuando…
  • La pila es genérica: Pila<i32> y Pila<String> compilan sin tocar el código.
  • pop() sobre una pila vacía devuelve None, nunca hace panic.
  • Tenés al menos 3 tests con #[test] y cargo test pasa todo.
  • La API pública (pub) es mínima y clara — nada interno expuesto de más.

⚡ Proyecto 3 — Procesador concurrente

Objetivo: usar varios threads para procesar trabajo en paralelo y juntar los resultados de forma segura. Una idea concreta: contar palabras en muchos archivos a la vez, un thread por archivo, sumando todo a un total compartido. Acá Rust brilla: el compilador te garantiza que no hay data races.

Módulo del cursoCómo lo aplicás acá
M10 — Concurrenciathread::spawn para lanzar trabajo en paralelo
M10 — Arc + MutexArc<Mutex<T>> para compartir un total entre threads de forma segura
M10 — ChannelsAlternativa: mpsc para que cada thread envíe su resultado al hilo principal
M06 — ErroresManejar archivos que no existen sin que se caiga todo el programa

El patrón Arc<Mutex<T>> — un contador compartido entre threads:

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let total = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for n in 0..4 {
        let total = Arc::clone(&total);   // cada thread comparte el mismo contador
        let h = thread::spawn(move || {
            let palabras = n * 10;        // acá iría: leer archivo y contar
            let mut suma = total.lock().unwrap();
            *suma += palabras;            // sección crítica, protegida por el Mutex
        });
        handles.push(h);
    }

    for h in handles {
        h.join().unwrap();                // esperar a que todos terminen
    }

    println!("Total: {}", *total.lock().unwrap());
}

La alternativa con channels (mpsc = multiple producer, single consumer) evita el lock: cada thread manda su número por el canal y el principal los suma a medida que llegan.

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    for n in 0..4 {
        let tx = tx.clone();
        thread::spawn(move || {
            tx.send(n * 10).unwrap();     // cada thread envía su resultado
        });
    }
    drop(tx);                             // cerrar el emisor original

    let total: i32 = rx.iter().sum();     // el principal recibe y suma
    println!("Total: {}", total);
}
Cuidado con olvidar join. Si el hilo principal termina antes que los threads que lanzaste, esos threads se matan a la mitad. Siempre guardá los handles y hacé join() sobre todos, o usá un channel que mantenga vivo el flujo hasta que todos envíen.

Fases para construirlo:

  1. Primero la versión secuencial: contar palabras de una lista de archivos en un bucle normal. Que funcione.
  2. Decidir el modelo: ¿Arc<Mutex> compartido o channel mpsc? Empezá con el que te resulte más claro.
  3. Lanzar un thread::spawn por archivo, moviendo lo necesario con move.
  4. Juntar resultados: lock + suma, o recibir por el canal.
  5. Hacer join() de todos los handles antes de imprimir el total.
  6. Comparar: ¿el total concurrente coincide con el secuencial? Tiene que dar igual.
✅ Terminado cuando…
  • El total concurrente es idéntico al de la versión secuencial (si no, hay un bug de sincronización).
  • No hay data races: el código compila — en Rust, si compila con threads, no hay carrera de datos.
  • Todos los threads se esperan con join(); nada queda colgado.
  • Un archivo inexistente no tira abajo el programa entero.

🦀 Proyecto 4 — Rust embebido en el ESP32

Objetivo: el puente con Computación Física. Hacer que Rust corra directo sobre el microcontrolador — sin sistema operativo debajo — para parpadear un LED o leer un sensor en el ESP32. Es Rust en su hábitat original: programación de sistemas, cerca del metal.

💡 ¿Qué es no_std? Hasta ahora todos tus programas usaban la standard library de Rust (std): Vec, String, archivos, threads… Todo eso asume que hay un sistema operativo que da memoria dinámica, archivos y demás. Un microcontrolador no tiene OS. Por eso se compila con #![no_std]: Rust sin la librería estándar, usando solo el core del lenguaje. Tenés tipos, control de flujo y Option/Result, pero no hay Vec ni String "gratis" — la memoria es un recurso que administrás vos.
Concepto del cursoCómo cambia en embebido
M00 — CargoSeguís usando Cargo, pero compilás para otra arquitectura (cross-compile) y flasheás al chip
std completaReemplazada por #![no_std] + el crate esp-hal (la capa que habla con el hardware del ESP32)
M06 — ErroresResult y Option siguen — son del core, no de std
Computación FísicaAplicás GPIO, PWM y sensores que viste en ese curso, pero con la seguridad de Rust

Un "blink" mínimo con esp-hal tiene esta forma (el detalle exacto depende de la versión del crate):

#![no_std]
#![no_main]

use esp_hal::delay::Delay;
use esp_hal::gpio::{Level, Output};
use esp_backtrace as _;

#[esp_hal::main]
fn main() -> ! {
    let p = esp_hal::init(Default::default());

    let mut led = Output::new(p.GPIO2, Level::Low);
    let delay = Delay::new();

    loop {
        led.toggle();        // prende / apaga
        delay.delay_millis(500);
    }
}
📌 Lo que delata que es embebido: #![no_std] (sin librería estándar), #![no_main] (el arranque lo maneja el chip, no el main normal), el tipo de retorno -> ! (el programa nunca termina — corre para siempre en el micro), y el loop {} infinito. No hay return ni "fin del programa": un microcontrolador siempre está haciendo algo.

Fases para construirlo:

  1. Instalar el toolchain del ESP32 (espup instala el target de Rust para Espressif).
  2. Generar el proyecto base con la plantilla oficial (esp-generate / cargo generate).
  3. Identificar a qué pin GPIO está conectado el LED de tu placa (suele ser el GPIO2).
  4. Escribir el loop con toggle() + delay para parpadear.
  5. Flashear con cargo run (que usa espflash por detrás) y ver el LED parpadear.
  6. (Siguiente paso) Leer un sensor por una entrada analógica (ADC) e imprimir el valor por el puerto serie.
🔌 El puente con Computación Física. Todo lo que aprendiste sobre electrónica — GPIO, PWM, ADC, pull-ups, el ESP32 — aplica acá, pero ahora con la red de seguridad de Rust en vez de C. Repasá los fundamentos de hardware en el ⚡ Curso de Computación Física y volvé a implementarlos en Rust.
Embebido es el proyecto más difícil — y está bien. Necesitás hardware real (un ESP32), drivers y un toolchain de cross-compilación. Si todavía no tenés la placa, leé y entendé el concepto de no_std igual: es el "para qué existe Rust" en estado puro. Cuando consigas el chip, este es el proyecto que te va a hacer sentir que sos programador de sistemas.

Checkpoint — repaso del curso

¿Por qué pop() de una pila debería devolver Option<T> y no T?

Porque la pila puede estar vacía. Si devolviera T, no habría forma de representar "no hay nada que sacar" sin hacer panic. Option<T> obliga a quien llama a manejar el caso None — es la forma segura, sin null, que Rust impone (M04).

¿Qué garantiza Rust cuando un programa con threads compila?

Que no hay data races: nunca dos threads acceden a la misma memoria de forma conflictiva sin sincronización. El compilador lo verifica con ownership y los traits Send/Sync. Por eso compartís estado con Arc<Mutex<T>> o channels mpsc (M10): el tipo te fuerza a hacerlo bien.

¿Qué significa #![no_std] y por qué hace falta en el ESP32?

Significa compilar sin la librería estándar de Rust, usando solo el core del lenguaje. Hace falta en un microcontrolador porque std asume un sistema operativo (memoria dinámica, archivos, threads del OS) que el ESP32 no tiene. Seguís teniendo tipos, control de flujo y Option/Result, pero administrás la memoria vos.

🧠 Autoevaluación — repaso del curso

1. En la CLI, ¿qué te permite el operador ? al leer un archivo con fs::read_to_string(ruta)??

El ? desempaca el Ok si todo salió bien, o retorna temprano el Err hacia quien llamó (M06). Por eso la función devuelve Result.

2. En el procesador concurrente, ¿qué usás para compartir un contador entre varios threads de forma segura?

Arc permite múltiples dueños del dato y Mutex serializa el acceso; alternativamente, los channels mpsc envían resultados sin estado compartido (M10). El compilador rechaza lo inseguro.

3. ¿Por qué un programa para el ESP32 usa #![no_std]?

La librería estándar (std) depende de un OS (memoria dinámica, archivos, threads). En un microcontrolador sin OS se compila con #![no_std] y se usa el core del lenguaje más un crate como esp-hal.

Módulo 08 — Goroutines & Channels

Llegamos a la feature que define a Go. Mientras otros lenguajes pegan la concurrencia con cinta (threads pesados, callbacks, async/await), Go la trae en el corazón del idioma: una palabra clave (go) lanza tareas concurrentes, y los channels las comunican de forma segura. En este módulo entendés cómo lanzar miles de tareas, cómo sincronizarlas y por qué el lema de Go es "compartí memoria comunicando".

Goroutines: concurrencia con una palabra

💡 Una goroutine es una función que corre concurrentemente con el resto del programa. La lanzás poniendo go delante de la llamada. No es un thread del sistema operativo: es una unidad ligerísima que administra el runtime de Go. Podés tener decenas de miles sin transpirar.

Así se lanza una:

package main

import (
    "fmt"
    "time"
)

func hacerAlgo(nombre string) {
    fmt.Println("trabajando:", nombre)
}

func main() {
    go hacerAlgo("tarea A")   // corre concurrentemente
    go hacerAlgo("tarea B")   // y esta también
    time.Sleep(time.Second)   // hack temporal: esperar que terminen
}
🔗 Pensalo como un restaurante. Un thread del SO es contratar un cocinero completo (caro, lento de incorporar). Una goroutine es delegarle una orden a un mozo que ya está: el chef de cocina (el runtime) reparte miles de órdenes entre unos pocos cocineros reales (los threads). Vos pensás en "órdenes", no en "cocineros".

El problema: main no espera

En el ejemplo de arriba usamos time.Sleep, y eso es una trampa. La función main es ella misma una goroutine (la principal). Si main termina, el programa entero termina y se llevan puestas todas las goroutines que aún estaban corriendo, las hayan completado o no.

⚠️ Sin sincronización, no hay garantías. Si lanzás go hacerAlgo() y main sigue de largo hasta el final, puede que la goroutine nunca llegue a ejecutarse. time.Sleep "parece" arreglarlo pero es frágil: adiviná cuánto tarda la tarea y rezá. Necesitás una forma real de sincronizar — y la mejor es un channel.

Channels: tuberías tipadas

💡 Un channel es una tubería tipada para comunicar goroutines. Una goroutine mete un valor por un extremo y otra lo saca por el otro. El channel se encarga de la sincronización: no hay locks manuales, no hay condiciones de carrera al pasar el dato.

Se crea con make y tiene un tipo: un chan int solo transporta int. Las dos operaciones usan el operador <- (una flecha que apunta hacia dónde va el dato):

ch := make(chan int)   // channel de enteros

ch <- 5                // ENVIAR: el 5 entra al channel (la flecha apunta AL channel)
v := <-ch              // RECIBIR: sacar un valor del channel (la flecha sale DEL channel)
✅ Regla mnemotécnica de la flecha. El dato "viaja" en la dirección de <-. En ch <- 5 el 5 va hacia ch (envío). En v := <-ch el valor sale de ch hacia v (recepción). El channel siempre está del lado de la punta de flecha cuando recibís, y del lado contrario cuando enviás.

Unbuffered vs buffered

Hay dos sabores de channel, y la diferencia es crucial:

TipoCreaciónComportamiento
Unbufferedmake(chan int)El envío se bloquea hasta que alguien reciba. Sincroniza: emisor y receptor se "dan la mano".
Bufferedmake(chan int, 3)Tiene capacidad (3). El envío solo se bloquea si el buffer está lleno; recibir solo se bloquea si está vacío.
Un channel unbuffered es un punto de encuentro: ch <- v queda esperando ahí parado hasta que otra goroutine haga <-ch. Justo por eso sirve para sincronizar. Un channel buffered es más como una cola con casilleros: podés dejar hasta N valores sin que nadie los retire todavía. 
// Unbuffered: este envío ESPERA a un receptor
sync := make(chan int)

// Buffered con capacidad 2: estos dos NO bloquean
buf := make(chan string, 2)
buf <- "hola"
buf <- "mundo"
// buf <- "tercero"   // ESTO bloquearía: buffer lleno

close y recibir con range

Cuando una goroutine termina de mandar valores, puede cerrar el channel con close(ch). Eso le avisa al receptor que no vienen más datos. El receptor puede recorrer todos los valores cómodamente con for ... range:

func main() {
    ch := make(chan int, 3)

    ch <- 10
    ch <- 20
    ch <- 30
    close(ch)              // no se envían más valores

    // range termina solo cuando el channel está cerrado y vacío
    for v := range ch {
        fmt.Println("recibí:", v)
    }
}
📌 Reglas de close. Cierra el que envía, nunca el que recibe. Enviar a un channel cerrado provoca un panic. Recibir de un channel cerrado devuelve el valor cero del tipo (y un segundo valor booleano false: v, ok := <-ch). Y for range sobre el channel se corta solo al cerrarse.

Ejemplo completo: varias goroutines reportando por un channel

Acá está el patrón que vas a usar mil veces: lanzás varias goroutines que calculan algo y mandan el resultado por un channel; main los recibe a medida que llegan.

package main

import "fmt"

// cada worker calcula el cuadrado y lo manda por el channel
func worker(id int, resultados chan<- int) {
    resultados <- id * id
}

func main() {
    resultados := make(chan int)

    // lanzamos 3 goroutines
    go worker(2, resultados)
    go worker(3, resultados)
    go worker(4, resultados)

    // main recibe los 3 valores (el orden NO está garantizado)
    for i := 0; i < 3; i++ {
        v := <-resultados
        fmt.Println("resultado:", v)
    }
}
Fijate en el tipo del parámetro: chan<- int es un channel solo de envío (la flecha pegada a chan indica la dirección permitida). Es una restricción que te da el compilador: dentro de worker no podés recibir por error. Su simétrico, <-chan int, sería solo de recepción.

select: esperar en varios channels a la vez

💡 select es como un switch, pero para channels. Espera hasta que una de varias operaciones de channel esté lista y ejecuta ese caso. Si varias están listas a la vez, elige una al azar. Es la herramienta para coordinar múltiples fuentes de datos. 
func main() {
    a := make(chan string)
    b := make(chan string)

    go func() { a <- "desde A" }()
    go func() { b <- "desde B" }()

    // esperamos 2 mensajes, vengan del channel que vengan
    for i := 0; i < 2; i++ {
        select {
        case msg := <-a:
            fmt.Println("recibí", msg)
        case msg := <-b:
            fmt.Println("recibí", msg)
        }
    }
}

Un select con un caso default no se bloquea: si ningún channel está listo, ejecuta el default y sigue. Combinado con time.After, select también sirve para implementar timeouts.

El modelo CSP de Go

💡 El lema de Go: "No comuniques compartiendo memoria; compartí memoria comunicando." En vez de que dos goroutines toquen la misma variable protegida por locks (el modelo clásico, propenso a errores), una goroutine posee el dato y se lo pasa a otra por un channel. Quien tiene el dato es el único que lo toca. Este modelo se llama CSP (Communicating Sequential Processes).

La idea es invertir el problema: en vez de pelearte con cerrojos para que dos hilos no pisen la misma memoria, hacés que el dato fluya de una goroutine a otra. El channel es el único punto de contacto, y Go garantiza que ese pasaje es seguro.

Tres errores clásicos

Deadlock. Si enviás a un channel unbuffered y no hay nadie que reciba (ni lo habrá), tu goroutine queda bloqueada para siempre. Si todas las goroutines quedan bloqueadas, Go lo detecta y aborta: fatal error: all goroutines are asleep - deadlock!. Causa típica: hacer ch <- v en main sin haber lanzado antes el receptor.
Goroutine leak. Lanzás una goroutine que se queda esperando en un channel del que nadie va a enviar/recibir nunca. No crashea, pero esa goroutine nunca termina y va acumulando memoria. Las fugas de goroutines son el "memory leak" de Go.
Race condition. Si varias goroutines tocan la misma variable sin sincronizar (sin channel ni Mutex), el resultado es impredecible y dependiente del scheduler. Justamente lo que CSP busca evitar. Lo vemos a fondo en M09 (y conocés go run -race, el detector de carreras).
🔥 Probá el detector de carreras. Go trae un detector incorporado: corré tu programa con go run -race main.go o testeá con go test -race. Te marca en runtime cualquier acceso concurrente sin sincronizar a la misma memoria. Es la primera herramienta a la que recurrís cuando un programa concurrente "a veces falla".

Checkpoint — ¿lo tenés claro?

¿Por qué time.Sleep es una mala forma de esperar a las goroutines?

Porque es adivinar cuánto van a tardar: si tardan más, main termina antes y las mata; si tardan menos, desperdiciás tiempo. No hay garantía real. Un channel (o un sync.WaitGroup) sincroniza de verdad: main espera exactamente hasta que la goroutine reportó.

¿Cuál es la diferencia entre un channel unbuffered y uno buffered?

El unbuffered (make(chan int)) sincroniza: el envío se bloquea hasta que alguien reciba — emisor y receptor se "dan la mano". El buffered (make(chan int, 3)) tiene capacidad: el envío solo se bloquea si el buffer está lleno, y recibir solo se bloquea si está vacío.

¿Qué hace select y para qué sirve?

Espera en varios channels a la vez y ejecuta el caso del primero que esté listo (si hay varios listos, elige al azar). Es como un switch para operaciones de channel. Con un caso default no se bloquea, y combinado con time.After implementa timeouts.

Ejercicios

  1. Lanzá una goroutine con go que imprima un mensaje, y comprobá que sin time.Sleep (o sin un channel) el mensaje a veces no aparece. Después arreglalo con un channel.
  2. Creá un channel chan int, lanzá 3 goroutines que envíen su número al cuadrado, y recibilos en main con un bucle for i := 0; i < 3; i++.
  3. Llená un channel buffered de capacidad 4 con valores, hacé close(ch), y recorré todo con for v := range ch imprimiendo cada valor.
  4. Provocá un deadlock a propósito: hacé ch <- 1 en main sobre un channel unbuffered sin ningún receptor, y mirá el mensaje fatal error: ... deadlock!.
  5. Escribí un select que reciba de dos channels distintos (cada uno alimentado por su propia goroutine) e imprima de cuál llegó cada mensaje.

🧠 Autoevaluación

1. ¿Qué hace la palabra clave go delante de una llamada a función?

Poner go f() arranca f en una goroutine: una unidad de ejecución ligerísima que corre concurrentemente con el resto. Podés tener miles.

2. En un channel unbuffered, ¿qué pasa al hacer ch <- v si nadie está recibiendo?

Un channel unbuffered sincroniza: el envío espera a un receptor. Si en main enviás sin haber lanzado un receptor, Go aborta con fatal error: ... deadlock!.

3. ¿Qué resume mejor el modelo de concurrencia (CSP) de Go?

El lema de Go invierte el modelo clásico de locks: en vez de compartir una variable protegida, una goroutine posee el dato y lo pasa por un channel. El channel es el único punto de contacto seguro.

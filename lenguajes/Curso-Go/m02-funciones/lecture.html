Módulo 02 — Funciones

Las funciones son el corazón de cualquier programa en Go. Pero la forma en que Go las trata tiene varias sorpresas si venís de C, Java, Python o JavaScript: el tipo va después del nombre, una función puede devolver varios valores a la vez, y existe defer para diferir limpieza. En este módulo dejás de pelearte con la sintaxis y empezás a escribir Go idiomático.

Sintaxis básica

Una función en Go se declara con la palabra clave func, el nombre, los parámetros (con su tipo), y el tipo de retorno:

func saludar(nombre string) string {
    return "Hola, " + nombre
}

func sumar(a int, b int) int {
    return a + b
}
💡 El tipo va DESPUÉS del nombre. En C/Java escribís int sumar(int a, int b). En Go es al revés: func sumar(a int, b int) int. La regla es "nombre, después tipo" — se lee de izquierda a derecha como en una oración. Si varios parámetros comparten tipo, podés agruparlos: func sumar(a, b int) int.

Si una función no devuelve nada, simplemente no ponés tipo de retorno: func saludar(nombre string) { ... }. Y recordá de M00: una función o variable declarada y no usada es error de compilación, no un warning.

Múltiples valores de retorno — el idiom estrella

Esta es la característica que más distingue a Go. Una función puede devolver varios valores a la vez, sin tener que armar una tupla, una lista o un objeto:

func divmod(a, b int) (int, int) {
    return a / b, a % b   // devuelve cociente Y resto
}

func main() {
    coc, resto := divmod(17, 5)
    fmt.Println(coc, resto)   // 3 2
}

Fijate que el tipo de retorno ahora va entre paréntesis: (int, int). Y del lado de quien llama, recibís ambos valores con := en una sola línea.

💡 El patrón (resultado, error). El uso MÁS común de los múltiples retornos en Go es devolver un resultado y un error. En lugar de excepciones (try/except), Go devuelve el error como un valor normal que vos chequeás: 
import (
    "fmt"
    "strconv"
)

func main() {
    n, err := strconv.Atoi("42")   // string a int: devuelve (int, error)
    if err != nil {
        fmt.Println("no se pudo convertir:", err)
        return
    }
    fmt.Println("el número es", n)   // el número es 42
}
📌 La convención sagrada de Go: el error siempre es el último valor de retorno, y siempre se chequea con if err != nil. Si err es nil, todo salió bien. Vas a escribir este patrón miles de veces — es el reemplazo de las excepciones.

Retornos nombrados (named returns)

Go te deja ponerle nombre a los valores de retorno en la firma. Esos nombres se comportan como variables ya declaradas dentro de la función, y un return sin argumentos (return "desnudo") devuelve sus valores actuales:

func divmod(a, b int) (cociente, resto int) {
    cociente = a / b
    resto = a % b
    return            // return DESNUDO: devuelve cociente y resto
}
El return desnudo (return sin valores) es cómodo en funciones cortas porque autodocumenta qué devolvés. En funciones largas conviene evitarlo: es fácil perderle el rastro a qué valores van a salir. Usalo con criterio.

Parámetros variadic (cantidad variable)

Si querés que una función acepte una cantidad indefinida de argumentos del mismo tipo, usás ... antes del tipo. Adentro, ese parámetro es un slice (lo viste en M01):

func suma(nums ...int) int {
    total := 0
    for _, n := range nums {
        total += n
    }
    return total
}

func main() {
    fmt.Println(suma(1, 2, 3))        // 6
    fmt.Println(suma(10, 20, 30, 40)) // 100
    fmt.Println(suma())               // 0 (cero argumentos también vale)
}
Si ya tenés un slice y querés pasarlo a una función variadic, lo "desparramás" con ... al llamarla: suma(misNumeros...). Es la operación inversa.

Funciones como valores (first-class) y closures

En Go las funciones son valores de primera clase: las podés guardar en una variable, pasarlas como argumento y devolverlas desde otra función — igual que un int o un string.

func main() {
    // una función guardada en una variable
    doble := func(x int) int {
        return x * 2
    }
    fmt.Println(doble(21))   // 42
}

Un closure es una función que captura variables del entorno donde fue creada. Esas variables siguen vivas mientras el closure exista, aunque la función que las creó ya haya terminado:

func contador() func() int {
    n := 0
    return func() int {   // este closure "recuerda" n
        n++
        return n
    }
}

func main() {
    siguiente := contador()
    fmt.Println(siguiente())  // 1
    fmt.Println(siguiente())  // 2
    fmt.Println(siguiente())  // 3 — n se conserva entre llamadas
}
🧩 Pensá en un closure como una mochila. La función se lleva en su mochila las variables que necesita del lugar donde nació. Aunque salga de ese lugar (la función externa retornó), sigue cargando la mochila y puede leer y modificar lo que hay adentro.

defer: limpieza garantizada

defer difiere la ejecución de una llamada hasta que la función que la rodea esté por retornar. Es la herramienta ideal para limpieza: cerrar un archivo, soltar un lock, cerrar una conexión. Escribís la apertura y el cierre juntos, y Go se encarga de ejecutar el cierre al final pase lo que pase.

func main() {
    fmt.Println("inicio")
    defer fmt.Println("esto se ejecuta AL FINAL")
    fmt.Println("medio")
}
// Imprime:
// inicio
// medio
// esto se ejecuta AL FINAL
💡 Varios defer se ejecutan en orden LIFO (Last In, First Out): el último defer que escribiste es el primero en ejecutarse, como una pila de platos. Tiene sentido para limpieza: lo último que abriste es lo primero que cerrás. 
func main() {
    defer fmt.Println("1")
    defer fmt.Println("2")
    defer fmt.Println("3")
}
// Imprime: 3, luego 2, luego 1 (LIFO)

Ejemplo completo: retorno (resultado, error) + defer

Juntemos todo. Una función que "abre un recurso", lo usa, y garantiza el cierre con defer — y que reporta errores con el patrón (resultado, error):

import (
    "errors"
    "fmt"
)

// dividir devuelve el resultado Y un error si el divisor es 0
func dividir(a, b int) (int, error) {
    if b == 0 {
        return 0, errors.New("división por cero")
    }
    return a / b, nil
}

func usarRecurso() {
    fmt.Println("abriendo recurso...")
    defer fmt.Println("cerrando recurso (siempre se ejecuta)")

    r, err := dividir(10, 0)
    if err != nil {
        fmt.Println("error:", err)   // error: división por cero
        return   // aunque retornemos acá, el defer igual cierra el recurso
    }
    fmt.Println("resultado:", r)
}

func main() {
    usarRecurso()
}
// Imprime:
// abriendo recurso...
// error: división por cero
// cerrando recurso (siempre se ejecuta)
📌 Por qué defer es tan poderoso: aunque la función retorne temprano por un error (o incluso entre en pánico), el defer igual se ejecuta. Por eso jamás te olvidás de cerrar un archivo o soltar un recurso: lo declarás justo después de abrirlo y te despreocupás.

Errores comunes

Ignorar el segundo valor de retorno (el error). Hacer n, _ := strconv.Atoi(texto) descarta el error con _. Si la conversión falla, n queda en 0 y nunca te enterás. Chequeá err salvo que tengas una razón MUY clara para ignorarlo.
Confundir el orden LIFO de varios defer. Si escribís defer A() y luego defer B(), se ejecuta B primero, después A. No es el orden en que los escribiste — es el inverso.
Capturar la variable de loop en un closure. Clásico: lanzar closures dentro de un for que usan la variable del loop. En versiones viejas de Go todos terminaban viendo el ÚLTIMO valor. Desde Go 1.22 cada iteración tiene su propia variable, pero si dependés de una versión vieja, copiá la variable adentro del loop: n := n antes de usarla en el closure.

Checkpoint — ¿lo tenés claro?

¿En qué orden van el nombre y el tipo de un parámetro en Go?

Primero el nombre, después el tipo: func sumar(a, b int) int. Es al revés que C/Java. Si varios parámetros comparten tipo, lo escribís una sola vez al final del grupo.

¿Cuál es la convención de Go para reportar errores?

Devolver el error como el último valor de retorno y chequearlo con if err != nil. Si err == nil, todo salió bien. Reemplaza a las excepciones (try/except).

Si escribís defer A() y luego defer B(), ¿en qué orden se ejecutan al retornar?

Primero B() y después A() — orden LIFO (Last In, First Out), como una pila. El último defer declarado es el primero en correr.

Ejercicios

  1. Escribí una función minMax(nums ...int) (int, int) variadic que devuelva el menor y el mayor de los números recibidos.
  2. Implementá dividir(a, b float64) (float64, error) que devuelva un error si b es 0, y usala chequeando err con if err != nil.
  3. Reescribí divmod usando retornos nombrados y un return desnudo.
  4. Creá un closure acumulador() que devuelva una función; cada llamada le suma su argumento a un total interno y lo devuelve. Verificá que el total se conserva entre llamadas.
  5. Escribí una función con tres defer que impriman "uno", "dos" y "tres", y predecí en qué orden se imprimen antes de ejecutarla. Confirmá que es LIFO.

🧠 Autoevaluación

1. ¿Cómo se declara correctamente en Go una función que recibe dos enteros y devuelve un entero?

En Go el tipo va después del nombre, y si los parámetros comparten tipo se escribe una sola vez: func sumar(a, b int) int.

2. En el patrón idiomático de Go, ¿cómo se reporta y maneja un error?

Go no tiene excepciones para errores normales: la función devuelve (resultado, error) y vos chequeás if err != nil. Es la convención sagrada del lenguaje.

3. Si una función tiene defer A() seguido de defer B(), ¿en qué orden se ejecutan cuando la función retorna?

Los defer se apilan y se ejecutan en orden LIFO (Last In, First Out): el último declarado es el primero en correr. Por eso B() va antes que A().

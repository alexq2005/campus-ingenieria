GS2 — Memoria, escape analysis y el GC Green Tea

GS2.0 Por qué este módulo

En GS1 desarmaste el scheduler: viste que el runtime multiplexa goroutines sobre hilos del sistema y que casi nada de lo que parece "concurrencia gratis" es realmente gratis. Este módulo hace lo mismo con la otra mitad del runtime: la memoria.

Go no tiene malloc ni free. Tampoco tiene ownership como Rust ni destructores deterministas como C++. La lectura ingenua de eso es "en Go la memoria no es mi problema". La lectura correcta es otra: la decisión sigue existiendo, solo que la toma el compilador — y la toma leyendo cómo escribiste vos. Cambiar una firma de func f() Usuario a func f() *Usuario puede mover un millón de asignaciones por segundo del stack al heap sin que aparezca ni una línea nueva de código.

💡 La tesis del módulo. El rendimiento de memoria en Go se explica con tres capas encadenadas: (1) el compilador decide, con escape analysis, si un valor vive en el stack (gratis) o en el heap (caro); (2) todo lo que va al heap se convierte en trabajo futuro para el recolector; (3) el recolector está diseñado para no pausarte, no para ser barato. Entendé el orden: primero reducís lo que llega al heap, después tuneás el GC. Al revés casi nunca funciona.

Y hay una razón muy concreta para estudiarlo ahora: el recolector de Go acaba de cambiar. El GC Green Tea, que durante dos versiones fue experimental, es el recolector por defecto desde Go 1.26 (febrero de 2026). En programas reales con uso intensivo de memoria reduce el overhead del GC entre un 10% y un 40%, con menos pausas y más throughput. El recolector viejo todavía se puede pedir como escape hatch, pero solo hasta Go 1.27, que elimina la opción. Es decir: si tenés servicios cuyos números de GC conocés de memoria, esos números ya no valen.

📌 En Go, new y & no significan "heap". A diferencia de C++ o Java, tomar la dirección de una variable local no obliga a asignarla en el heap. Si el compilador puede probar que ese puntero no sobrevive a la función, el valor se queda en el stack aunque hayas escrito &. Y al revés: un valor sin ningún & puede terminar en el heap si su tamaño no se conoce en compilación. La sintaxis no te dice nada; el compilador sí. 
package main

type Punto struct{ X, Y float64 }

// El puntero NO sale de la función: Punto se queda en el stack.
func distanciaAlOrigen() float64 {
    p := &Punto{X: 3, Y: 4}
    return p.X*p.X + p.Y*p.Y
}

// El puntero SÍ sale: Punto se mueve al heap.
func nuevoPunto(x, y float64) *Punto {
    p := &Punto{X: x, Y: y}
    return p
}

El stack de goroutine que crece

El stack de una goroutine no es un bloque fijo como el de un hilo del sistema operativo. Arranca chiquito — 2 KB — y crece cuando hace falta. Ese detalle es lo que permite tener cientos de miles de goroutines vivas: si cada una reservara 1 MB como un pthread, 100.000 goroutines pedirían 100 GB de direcciones.

El mecanismo se llama stack growth y funciona así: el compilador inserta un chequeo al principio de cada función que pueda necesitar más espacio (el prólogo). Si el stack no alcanza, el runtime llama a morestack, reserva un stack del doble de tamaño, copia el viejo adentro y ajusta todos los punteros que apuntaban a él. Por eso en Go no podés guardar la dirección de una variable de stack fuera del alcance del runtime: el runtime necesita poder mover ese stack.

package main

import (
    "fmt"
    "runtime"
)

// Recursión profunda: fuerza al runtime a agrandar el stack varias veces.
func profundo(n int, marca *byte) uintptr {
    var local [64]byte
    if n == 0 {
        // Distancia aproximada entre el frame actual y el inicial.
        return uintptr(len(local)) // solo para que 'local' no se optimice
    }
    return profundo(n-1, &local[0])
}

func main() {
    var m runtime.MemStats
    runtime.ReadMemStats(&m)
    fmt.Println("stack en uso antes:", m.StackInuse)

    var b byte
    profundo(20_000, &b)

    runtime.ReadMemStats(&m)
    fmt.Println("stack en uso después:", m.StackInuse)
}
El stack de una goroutine también se encoge: el recolector, durante el escaneo, puede reducir a la mitad un stack que quedó sobredimensionado. El límite superior por goroutine es de 1 GB en 64 bits, y es ajustable con runtime/debug.SetMaxStack. Cuando lo cruzás, el runtime aborta con goroutine stack exceeds limit — que en la práctica casi siempre significa recursión infinita, no un stack legítimamente grande.
El costo escondido del stack growth. Copiar un stack no es gratis: es un memmove más el ajuste de punteros. Una función caliente que queda justo en el borde y hace crecer/encoger el stack en cada llamada puede costarte más que la asignación en heap que estabas tratando de evitar. Es raro, pero cuando aparece en un perfil se ve clarísimo: runtime.morestack arriba de todo.

GS2.2 Escape analysis: la decisión más importante que no escribiste

El escape analysis es una fase del compilador que, para cada valor, se pregunta: ¿alguna referencia a esto sobrevive al frame que lo creó? Si la respuesta demostrable es "no", el valor va al stack. Si es "sí", o si el compilador no puede probar que no, el valor escapa al heap.

📌 El análisis es conservador, y eso es correcto. Ante la duda, el compilador manda al heap. Un falso negativo (mandar al heap algo que podía ir al stack) cuesta rendimiento; un falso positivo (dejar en el stack algo que sobrevive) sería memoria corrupta. Por eso muchas veces la pregunta útil no es "¿por qué escapa?" sino "¿qué le impide al compilador probar que no escapa?".

Cómo verlo

# Un -m: las decisiones. Dos -m: además el razonamiento (por qué).
go build -gcflags='-m' ./...
go build -gcflags='-m -m' ./...

# Solo un paquete, sin ruido de inlining:
go build -gcflags='-m' ./internal/procesador 2>&1 | grep -v inline

# También funciona en tests y benchmarks:
go test -gcflags='-m' -run xxx -bench=Handler ./internal/procesador
Ojo con las comillas en Windows. En PowerShell, -gcflags='-m' con comillas simples puede llegar literal al compilador. Usá go build "-gcflags=-m" ./... o corré el comando desde Git Bash. Si ves el error flag provided but not defined, es esto.

La salida real, leída línea por línea

// archivo: escape.go
package escape

type Usuario struct {
    ID     int
    Nombre string
    Tags   []string
}

func porValor(id int) Usuario {
    u := Usuario{ID: id, Nombre: "ana"}
    return u
}

func porPuntero(id int) *Usuario {
    u := Usuario{ID: id, Nombre: "ana"}
    return &u
}

func soloLectura(u *Usuario) int {
    return u.ID
}

func usar() int {
    a := porValor(1)
    return soloLectura(&a)
}

Traducido: porValor devuelve una copia y no genera nada en el heap. porPuntero devuelve la dirección de una local, y el compilador la mueve al heap (moved to heap: u). En soloLectura el parámetro u "does not escape": el compilador probó que la función no guarda ese puntero en ningún lado, así que quien la llame puede pasarle la dirección de una variable de stack sin pagar nada.

Con -m -m el compilador te muestra el camino por el que el valor se escapa. Esto es lo que realmente sirve cuando el escape no es obvio:

$ go build -gcflags='-m -m' ./escape.go
./escape.go:15:5: &u escapes to heap:
./escape.go:15:5:   flow: ~r0 = &{storage for &u}:
./escape.go:15:5:     from &u (spill) at ./escape.go:15:9
./escape.go:15:5:     from return &u (return) at ./escape.go:15:2
./escape.go:15:5: moved to heap: u
Ese bloque flow: es la herramienta. Se lee de abajo hacia arriba: "vuelve por el return → se guarda en el registro de retorno → por lo tanto escapa". Cuando el escape viene de tres funciones más abajo por una interfaz, el flow es la única forma de encontrar el eslabón real sin adivinar.

Los cuatro patrones que fuerzan un escape

1. Devolver un puntero a una local. El caso canónico. El valor tiene que sobrevivir al frame, punto. No hay análisis que lo evite.
2. Guardar el valor en una interfaz. Meter un valor concreto en un any, en un error, en un io.Reader: casi siempre implica una asignación en heap. Es la causa más frecuente y la menos visible. Sección GS2.3.
3. Capturarlo en un closure que sobrevive. Una goroutine, un callback guardado en una estructura, un defer en un loop: si el closure se va, las variables capturadas se van con él.
4. Tamaño desconocido en compilación. Históricamente, make([]byte, n) con n variable iba siempre al heap, porque el compilador no sabía cuánto stack reservar. Esto cambió: el compilador de las versiones recientes puede asignar el backing store de un slice en el stack en bastantes más situaciones que antes. Sigue habiendo un límite de tamaño, y sigue exigiendo que el slice no escape por otra vía.
package escape

import "sync"

var global *int
var mu sync.Mutex

// (1) return de puntero a local -> heap
func uno() *int {
    x := 42
    return &x
}

// (2) interfaz -> heap
func dos() any {
    x := 42
    return x // el valor se "empaqueta" dentro de la interfaz
}

// (3) closure que sobrevive -> heap
func tres() func() int {
    contador := 0
    return func() int { contador++; return contador }
}

// (3b) goroutine que captura -> heap
func tresB(datos []byte) {
    go func() {
        mu.Lock()
        _ = len(datos) // 'datos' vive más que tresB
        mu.Unlock()
    }()
}

// (4) tamaño variable: puede o no quedar en stack según el caso
func cuatro(n int) int {
    buf := make([]byte, n)
    s := 0
    for i := 0; i < len(buf); i++ {
        s += int(buf[i])
    }
    return s
}

// (5) escribir en un puntero global -> heap seguro
func cinco() {
    x := 7
    global = &x
}
⚠️ El escape se propaga hacia arriba, no hacia abajo. Una función tuya, chiquita y perfecta, puede empezar a asignar en heap porque alguien allá arriba la pasó a través de una interfaz. Por eso los resultados de -gcflags='-m' se leen por call path, no por función suelta, y por eso un benchmark microscópico que da 0 allocs/op puede dar 3 cuando lo integrás al servicio real.

El truco de los benchmarks: //go:noinline

Si medís una función chica, el compilador la va a inlinear y el escape analysis va a ver todo el contexto junto. Eso puede darte 0 asignaciones en el benchmark y 2 en producción. Para medir la función aislada, se desactiva el inlining:

package escape

//go:noinline
func crearAislado(id int) *Usuario {
    return &Usuario{ID: id}
}
Usá //go:noinline solo para experimentos. Dejarlo en código de producción es una pesimización silenciosa: el inlining es una de las optimizaciones que más rinde en Go, y además habilita el escape analysis que te ahorra las asignaciones.

GS2.3 Interfaces y boxing: la asignación que no ves

Una interfaz en Go es un par de palabras: un puntero al descriptor de tipo y un puntero al dato. La consecuencia es directa: para meter un valor concreto en una interfaz, ese valor tiene que estar en algún lado al que se pueda apuntar. Si el valor vivía en el stack y la interfaz lo sobrevive, hay que copiarlo al heap. A eso se le dice boxing.

package boxing

import "fmt"

type Contador struct{ N int64 }

func imprimir() {
    c := Contador{N: 5}
    fmt.Println(c) // c escapa: los ...any de Println son "leaking param"
}

func sinEscape() int64 {
    c := Contador{N: 5}
    return c.N    // no hay interfaz de por medio: stack
}
$ go build -gcflags='-m' ./boxing.go
./boxing.go:10:14: ... argument does not escape
./boxing.go:10:14: c escapes to heap
📌 fmt.Println hace escapar sus argumentos. Siempre. La firma es func Println(a ...any) (int, error), y la implementación usa reflexión, así que el compilador no puede probar que el valor no se guarda. Por eso un fmt.Println de debug dentro de un loop caliente no solo cuesta el I/O: convierte en asignaciones en heap valores que antes vivían en el stack, y ese costo persiste aunque el output vaya a /dev/null.

El compilador tiene algunos atajos. Los valores de tamaño cero (struct{}{}) no asignan nunca, y los enteros chicos se resuelven contra una tabla estática del runtime en vez de asignar. Pero no armes tu diseño sobre esos atajos: son detalles de implementación.

package boxing

// Sumidero para que el compilador no borre el trabajo del benchmark.
var sumidero any

func BoxingChico()  { sumidero = 42 }      // suele NO asignar (valor cacheado)
func BoxingGrande() { sumidero = 1 << 40 } // asigna: 8 bytes en heap
func BoxingCero()   { sumidero = struct{}{} } // nunca asigna

El anti-patrón de la abstracción prematura. Definir type Store interface { Get(id int) (*Registro, error) } cuando hay una sola implementación no te da flexibilidad: te da un dynamic dispatch que impide inlinear, impide el escape analysis a través del borde, y convierte cada retorno en una asignación. La interfaz se agrega cuando aparece la segunda implementación o el test la necesita — no "por si acaso".

GS2.4 El recolector de Go: concurrente, tricolor, con write barrier

El GC de Go es un mark-and-sweep concurrente, no generacional, no compactante. Cada una de esas cuatro palabras es una decisión de diseño con consecuencias que vas a ver en tus perfiles.

El algoritmo tricolor, en cuatro frases

La metáfora de los tres baldes. Todos los objetos empiezan blancos (candidatos a morir). El recolector pinta de gris lo que es alcanzable desde las raíces (stacks de goroutines, globales, registros). Después toma cada objeto gris, pinta de gris a todo lo que ese objeto apunta, y se pinta a sí mismo de negro (vivo y ya escaneado). Cuando no quedan grises, todo lo blanco es basura y se libera de una.

Lo interesante no es el algoritmo: es que corre al mismo tiempo que tu programa. Y eso rompe el invariante. Si mientras el recolector trabaja tu código toma un puntero de un objeto blanco y lo guarda en un objeto ya negro, el recolector nunca va a volver a mirar ese negro — y liberaría memoria viva.

La solución es el write barrier: durante la fase de marcado, el compilador inserta un chequeo en cada escritura de puntero del programa, que le avisa al recolector "che, este objeto cambió". Es el costo estructural del GC de Go y es la razón de que el marcado tenga un impacto en throughput incluso cuando no hay ninguna pausa visible.

// Lo que escribís:
nodo.siguiente = otro

// Lo que corre durante la fase de marcado (conceptual):
// if writeBarrier.enabled {
//     gcWriteBarrier(&nodo.siguiente, otro)
// }
// nodo.siguiente = otro

Las pausas: qué se para y por cuánto

Go tiene dos stop-the-world por ciclo, y ambos son cortos porque solo hacen preparación y cierre, nunca el trabajo pesado:

Fase¿Para el mundo?Qué hace
Sweep terminationSí, microsegundosCierra el barrido anterior, activa el write barrier
MarkingNoEl grueso del trabajo. Corre en paralelo con tu código, usando ~25% del CPU
Mark terminationSí, microsegundosVerifica que no quedan grises, apaga el write barrier
SweepingNoLibera lo blanco, perezosamente, a medida que se pide memoria
💡 Go optimizó latencia, no throughput — y eso es una decisión, no una virtud absoluta. El objetivo declarado del GC de Go son pausas por debajo del milisegundo, y hoy típicamente están en decenas o cientos de microsegundos. El precio está en dos lados: el write barrier le cuesta a tu código incluso cuando no hay pausa, y el marcado se lleva alrededor de un cuarto del CPU mientras corre. Un GC generacional como el de la JVM puede tener más throughput bruto en cargas batch; el de Go gana cuando lo que te importa es el p99 de una API.
Por qué Go no es generacional. La hipótesis generacional ("casi todos los objetos mueren jóvenes") vale menos en Go que en Java, porque en Go los objetos de vida corta muchas veces ni llegan al heap: el escape analysis los deja en el stack. Y no compacta porque compactar exige mover objetos, y mover objetos exige poder actualizar todos los punteros — algo que se pelea con unsafe.Pointer, con cgo y con la simplicidad del modelo. En vez de compactar, Go usa un asignador por size classes que mantiene la fragmentación acotada.

Cuándo arranca un ciclo

El GC de Go es proporcional. No corre cada N segundos: corre cuando el heap creció un porcentaje sobre el tamaño que tenía vivo al final del ciclo anterior. Ese porcentaje es GOGC, y su default es 100.

# Con GOGC=100 (default):
#   heap vivo al final del ciclo anterior = 100 MB
#   objetivo del próximo ciclo            = 100 + 100% de 100 = 200 MB
#
# Con GOGC=200:  objetivo = 100 + 200% = 300 MB  -> menos ciclos, más RAM
# Con GOGC=50:   objetivo = 100 +  50% = 150 MB  -> más ciclos, menos RAM
# Con GOGC=off:  nunca corre por crecimiento (peligroso sin GOMEMLIMIT)
📌 De acá sale la intuición más útil del módulo: el trabajo total del GC no depende de cuánto asignás, sino de cuánto queda vivo multiplicado por cuántas veces corre. Un programa que asigna 10 GB por segundo pero mantiene 5 MB vivos casi no le da trabajo al recolector. Un programa que asigna poquito pero mantiene un caché de 8 GB vivos le da muchísimo, porque cada ciclo tiene que recorrer ese grafo entero.

GS2.5 Green Tea: qué cambió y por qué mejora

💡 Lo que cambió. Green Tea es un rediseño del algoritmo de marcado. El recolector clásico marcaba objeto por objeto: sacaba un puntero de la cola de grises, iba a ese objeto, lo escaneaba, encolaba sus hijos. Green Tea marca por spans: agrupa el trabajo por bloques contiguos de memoria y escanea el bloque entero de una, aprovechando que esos objetos ya están en la misma línea de caché.

Puesto en términos de hardware: el marcado clásico es pointer chasing, el peor patrón posible para una CPU moderna. Cada salto es un fallo de caché potencial, el prefetcher no puede anticipar nada, y el procesador pasa la mayor parte del tiempo esperando a la RAM. Green Tea reordena el mismo trabajo para que sea mayormente secuencial, que es exactamente lo que el hardware sabe hacer rápido — y además abre la puerta a usar instrucciones vectoriales para escanear varios objetos por operación.

# El escape hatch, SOLO mientras exista (desaparece en 1.27):
GODEBUG=greenteagc=0 ./mi-servicio

# Comparar los dos en la misma carga, antes de decidir nada:
go test -bench=. -benchtime=10s ./... > nuevo.txt

📌 La ganancia medida es de 10% a 40% menos overhead de GC en programas reales con uso intensivo de memoria, con menos pausas y más throughput. Leé bien qué significa ese número: es una reducción del costo del recolector, no del tiempo total de tu programa. Si tu servicio gastaba 8% de CPU en GC, el mejor caso te devuelve unos 3 puntos de CPU. Es excelente y es gratis, pero no es una bala de plata: si tu problema es que asignás de más, Green Tea no te lo arregla, solo lo hace más barato de limpiar.
Qué revisar cuando actualices a 1.26. El cambio es transparente para el código, pero tus umbrales de alerta pueden dejar de tener sentido: si tenías una alarma sobre "ciclos de GC por minuto" o sobre el CPU de GC, los valores base se mueven. Y si algún dashboard parsea las líneas de gctrace, verificá el formato después de actualizar. El plan sano es: medir con 1.26 antes de tocar nada, guardar los números nuevos como línea de base, y recién ahí re-calibrar las alertas.
Dos mejoras del compilador que acompañan a esta versión y que juegan a favor del mismo objetivo: el backing store de los slices se puede asignar en el stack en más situaciones que antes (menos objetos llegando al heap), y el builtin new ahora acepta una expresión — p := new(calcular()) te da un puntero a una variable nueva ya inicializada, sin la danza de tmp := calcular(); p := &tmp.

GS2.6 Tuning honesto: GOGC y GOMEMLIMIT

Go te da exactamente dos perillas. Dos. No hay veinte flags como en la JVM, y eso es a propósito.

PerillaQué controlaDefaultNaturaleza
GOGCCuánto puede crecer el heap antes del próximo ciclo, en % del heap vivo100Relativa
GOMEMLIMITTecho blando de memoria total del runtime (heap + stacks + metadatos)ilimitadoAbsoluta
💡 GOMEMLIMIT es la herramienta más útil de las dos, y la que menos se usa. GOGC es relativa: no sabe cuánta RAM tenés. Si tu heap vivo salta de 100 MB a 900 MB por una ráfaga de tráfico, GOGC=100 va a apuntar tranquilamente a 1,8 GB — y si el contenedor tiene un límite de 1 GB, el kernel te mata antes de que el GC decida correr. GOMEMLIMIT le da al runtime la única información que le falta: cuánto techo hay. Cuando el total se acerca a ese techo, el GC corre más seguido aunque GOGC no lo pida, y además le devuelve memoria al sistema operativo más agresivamente. 
# Se puede fijar por variable de entorno...
GOMEMLIMIT=900MiB ./mi-servicio
GOMEMLIMIT=1GiB GOGC=off ./mi-servicio    # solo por límite, sin ciclos por crecimiento

# ...o desde el código, que es lo correcto en un contenedor,
# porque el límite se puede leer del propio cgroup.
package main

import (
    "os"
    "runtime/debug"
    "strconv"
)

// Fija GOMEMLIMIT al 90% del límite del contenedor, dejando el 10%
// para lo que el runtime de Go no contabiliza (cgo, mmap de terceros, el binario).
func configurarLimite(limiteContenedorBytes int64) {
    limite := limiteContenedorBytes * 90 / 100
    debug.SetMemoryLimit(limite)
}

func main() {
    // En Kubernetes, la Downward API puede inyectar el límite del contenedor:
    //   valueFrom: { resourceFieldRef: { resource: limits.memory } }
    if v := os.Getenv("MEMORY_LIMIT_BYTES"); v != "" {
        if n, err := strconv.ParseInt(v, 10, 64); err == nil {
            configurarLimite(n)
        }
    }
    // ...
}

El caso clásico: OOMKilled en Kubernetes

El servicio corre estable con 300 MB durante semanas. Un martes a las 11, el tráfico se duplica, y el pod muere con OOMKilled, exit code 137. Los dashboards de memoria muestran una rampa limpia hasta el límite y corte. El GC "no llegó a correr".

Lo que pasó: con GOGC=100 y un heap vivo que subió a 550 MB por la ráfaga, el runtime se fijó como objetivo del próximo ciclo 1,1 GB. El pod tenía limits.memory: 1Gi. El GC estaba haciendo exactamente lo que le pediste — el problema es que nunca le dijiste que existía un techo.

# El fix mínimo, en el manifiesto:
resources:
  limits:
    memory: 1Gi
  requests:
    memory: 1Gi
env:
  # 90% de 1Gi. El 10% restante cubre lo que el runtime de Go NO contabiliza.
  - name: GOMEMLIMIT
    value: "900MiB"
  # Bonus: GOMAXPROCS coherente con el límite de CPU (ver GS1).
  - name: GOMAXPROCS
    valueFrom:
      resourceFieldRef:
        resource: limits.cpu
⚠️ GOMEMLIMIT es un límite BLANDO, y esa palabra importa. Si tu memoria realmente viva supera el límite, el runtime no te va a matar el programa ni va a liberar memoria alcanzable: va a correr el GC una y otra vez, sin recuperar nada, quemando CPU. Es la death spiral. Go la mitiga limitando el GC al 50% del CPU, así que el proceso sigue avanzando, pero degradado y lentísimo. Por eso GOMEMLIMIT nunca reemplaza al límite del contenedor: se ponen los dos, con el del contenedor un poco más arriba, para que si hay una fuga real el pod muera rápido y se reinicie en vez de agonizar.
Fijar GOMEMLIMIT igual al límite del contenedor. El runtime de Go contabiliza su heap, sus stacks y sus metadatos — pero no el binario mapeado en memoria, ni lo que reserve una librería vía cgo, ni buffers del kernel. Si ponés los dos números iguales, el kernel te mata igual, solo que ahora también estás quemando CPU en GC mientras te matan. El 90% es un punto de partida razonable; si usás cgo pesado, bajá más.

2. runtime/metrics — ¿cómo lo exporto?

📌 Preferí runtime/metrics sobre runtime.MemStats. ReadMemStats hace un stop-the-world para tomar una foto consistente: llamarlo cada segundo desde un scraper de métricas es meterle pausas a tu propio servicio para medir pausas. runtime/metrics es la API moderna, no para el mundo, expone muchísimo más (histogramas de pausas, desglose de CPU, límites efectivos) y es estable ante cambios internos del runtime — precisamente porque el runtime cambia, como acaba de pasar con Green Tea. 
package observabilidad

import "runtime/metrics"

// Fracción del CPU total que se está yendo en el recolector.
// Este número es el que decide si tiene sentido optimizar memoria.
func FraccionGC() float64 {
    m := []metrics.Sample{
        {Name: "/cpu/classes/gc/total:cpu-seconds"},
        {Name: "/cpu/classes/total:cpu-seconds"},
    }
    metrics.Read(m)
    total := m[1].Value.Float64()
    if total == 0 {
        return 0
    }
    return m[0].Value.Float64() / total
}

        }

}

func percentil(h *metrics.Float64Histogram, p float64) float64 {
    var total uint64
    for _, c := range h.Counts {
        total += c
    }
    objetivo, acum := uint64(float64(total)*p), uint64(0)
    for i, c := range h.Counts {
        acum += c
        if acum >= objetivo {
            return h.Buckets[i]
        }
    }
    return 0
}

Pedir una métrica inexistente no explota: te devuelve KindBad. Si no lo chequeás, vas a exportar ceros silenciosos y a construir alertas sobre nada. GS2.8 Reducir la presión: las tres técnicas que rinden

1. Prealocar con la capacidad conocida

La técnica de mejor relación esfuerzo/beneficio del lenguaje, y la que más se olvida. Un append sobre un slice sin capacidad reasigna y copia cada vez que se llena — con crecimiento geométrico, así que para n elementos hacés del orden de log(n) asignaciones y copiás O(n) bytes de más.

package prealoc

type Registro struct {
    ID     int64
    Nombre string
}

// ❌ Sin capacidad: reasigna y copia varias veces.
func TransformarMal(entrada []Registro) []string {
    var out []string
    for _, r := range entrada {
        out = append(out, r.Nombre)
    }
    return out
}

// ✅ Con capacidad: UNA asignación, cero copias.
func TransformarBien(entrada []Registro) []string {
    out := make([]string, 0, len(entrada))
    for _, r := range entrada {
        out = append(out, r.Nombre)
    }
    return out
}
package prealoc

import "testing"

var datos = make([]Registro, 10_000)

func BenchmarkMal(b *testing.B) {
    b.ReportAllocs()
    for i := 0; i < b.N; i++ {
        _ = TransformarMal(datos)
    }
}

func BenchmarkBien(b *testing.B) {
    b.ReportAllocs()
    for i := 0; i < b.N; i++ {
        _ = TransformarBien(datos)
    }
}

Lo mismo vale para mapas: make(map[string]int, n) evita los rehash sucesivos. Y para armar strings: strings.Builder con Grow(n) en vez de s += x en un loop, que asigna un string nuevo en cada iteración porque los strings en Go son inmutables.

2. Evitar conversiones string ↔ []byte innecesarias

Convertir entre string y []byte copia, porque los strings son inmutables y los slices no. En un parser o un handler HTTP eso puede ser el grueso de tus asignaciones.

La buena noticia es que el compilador conoce varios patrones y los optimiza sin copiar. Vale la pena tenerlos memorizados, porque escribir el patrón "correcto" es gratis:

package conv

import "strings"

var m = map[string]int{"a": 1}

func patronesSinCopia(b []byte) {
    _ = m[string(b)]                 // ✅ lookup: no copia
    _ = string(b) == "esperado"      // ✅ comparación: no copia
    for range string(b) {            // ✅ range: no copia
    }
    _ = strings.Contains(string(b), "x") // ⚠️ ACÁ SÍ copia
}

func siempreCopia(b []byte) string {
    return string(b) // ✅ correcto: querés una copia inmutable e independiente
}
package conv

import "unsafe"

// Conversiones sin copia. Go 1.20+ ofrece unsafe.String / unsafe.Slice.
// USALAS SOLO si podés garantizar el invariante que dice el comentario.

// El []byte NO se puede modificar mientras el string exista.
func bytesAString(b []byte) string {
    if len(b) == 0 {
        return ""
    }
    return unsafe.String(&b[0], len(b))
}

// El string resultante NO se puede escribir. Escribirlo es UB.
func stringABytes(s string) []byte {
    return unsafe.Slice(unsafe.StringData(s), len(s))
}
⚠️ unsafe.String convierte un problema de rendimiento en un problema de corrupción de memoria. Si el []byte de origen se reutiliza —y en un handler HTTP con sync.Pool se reutiliza—, el string que devolviste cambia de contenido debajo de tus pies. Peor: si ese string quedó como clave de un mapa, el mapa queda inconsistente para siempre y el bug aparece a los tres días, en otro endpoint. Regla práctica: usá unsafe solo si el perfil lo justifica, solo en una función chica con un comentario que declare el invariante, y solo si el resultado no sobrevive al llamador.

3. sync.Pool: reusar buffers, con las trampas puestas sobre la mesa

sync.Pool es un caché de objetos temporales por procesador lógico. Su lugar natural es el buffer por request de un servidor de alto tráfico: algo que se pide muchísimas veces por segundo, se usa dentro de un scope corto y se devuelve.

package handler

import (
    "bytes"
    "net/http"
    "sync"
)

var bufPool = sync.Pool{
    // Ojo: puntero, no valor. Ver la trampa 2 más abajo.
    New: func() any { return new(bytes.Buffer) },
}

const capMaxRetenida = 64 << 10 // 64 KiB

func Manejar(w http.ResponseWriter, r *http.Request) {
    buf := bufPool.Get().(*bytes.Buffer)
    buf.Reset() // trampa 1: SIEMPRE resetear al sacarlo

    defer func() {
        // trampa 3: no devolver monstruos a la pool
        if buf.Cap() <= capMaxRetenida {
            bufPool.Put(buf)
        }
    }()

    serializar(buf, r)
    _, _ = w.Write(buf.Bytes()) // trampa 4: escribir ANTES de devolver
}

func serializar(dst *bytes.Buffer, r *http.Request) {
    dst.WriteString(r.URL.Path)
}
#TrampaConsecuenciaAntídoto
1No resetear el objetoFiltración de datos entre requests. Es un bug de seguridad, no de rendimientoReset() al hacer Get, no al hacer Put
2Guardar un valor en vez de un punteroEl any del Put boxea: asignás justo donde querías ahorrarNew devuelve siempre *T
3Devolver buffers gigantesUn request con un payload de 200 MB deja ese buffer retenido para siempre, por cada PChequear Cap() antes del Put
4Usar el objeto después del PutOtra goroutine ya lo tiene: corrupción intermitente e irreproducibledefer Put y no tocar nada después
5Poolear objetos chicosEmpeora: el Get/Put cuesta más que la asignaciónSolo poolear lo que es caro de crear o grande
6Tráfico bajoLa pool se vacía en cada GC: casi todos los Get son miss y pagás el overhead a cambio de nadaMedir. Sin volumen sostenido, sync.Pool no rinde
Cómo interactúa con el GC. La pool se vacía en cada ciclo de recolección — con un matiz importante: existe una victim cache, así que los objetos sobreviven un ciclo antes de desaparecer. Por eso sync.Pool es un caché de objetos efímeros, no un free list permanente: si necesitás que algo viva garantizadamente, sync.Pool es la herramienta equivocada.

GS2.9 Cuándo NO optimizar memoria

📌 La pregunta de una sola línea. Antes de tocar nada, mirá el porcentaje de la línea de gctrace o el resultado de FraccionGC(). Si el GC ocupa el 2% de tu CPU, el techo absoluto de toda tu optimización de memoria es 2%. No hay sync.Pool, prealocación ni unsafe que te dé más que eso — y cada uno de ellos suma complejidad y superficie de bugs para siempre.
GC en % de CPUVeredicto
< 3%No optimices memoria. Tu tiempo está en otro lado: I/O, base de datos, serialización, un algoritmo cuadrático
3–10%Zona gris. Mirá -alloc_objects: si hay dos o tres culpables claros, arreglalos. Si está repartido parejo, dejalo
> 10%Hay algo estructural: asignás por elemento en un loop caliente, o boxeás en una interfaz por request. Vale la pena entrar
> 25% sostenidoCasi seguro no es tuning: es un diseño que asigna por ítem donde debería asignar por lote, o una fuga
Los tres errores de prioridad que se repiten. (a) Meter sync.Pool en un servicio que hace 40 requests por minuto. (b) Bajar GOGC "para usar menos memoria" en una máquina con 60 GB libres, y duplicar el CPU de GC a cambio de nada. (c) Pelear tres días contra el escape analysis en un handler que pasa el 92% del tiempo esperando a PostgreSQL. Los tres tienen la misma raíz: optimizar lo que se entiende en vez de lo que se midió.

Ninguna prealocación arregla eso: mientras la función devuelva el buffer, ese buffer tiene que sobrevivir al frame. La única salida es cambiar el contrato: en vez de devolver un buffer nuevo, recibir uno prestado y devolverlo cuando termina el request.

Paso 4 — El cambio, en dos movimientos. Primero prealocar con el tamaño real (el header Content-Length lo dice), después reusar con una pool:

package servicio

import (
    "bytes"
    "io"
    "net/http"
    "sync"
)

var cuerpoPool = sync.Pool{
    New: func() any {
        b := new(bytes.Buffer)
        b.Grow(8 << 10) // 8 KiB: el p90 medido de los payloads
        return b
    },
}

const capMaxRetenida = 256 << 10

// Ahora el buffer es PRESTADO: el llamador lo devuelve cuando terminó.
func (p *Procesador) leerCuerpo(r *http.Request) (*bytes.Buffer, error) {
    buf := cuerpoPool.Get().(*bytes.Buffer)
    buf.Reset()

    // Si el cliente mandó Content-Length, reservamos exacto y evitamos regrowth.
    if n := r.ContentLength; n > 0 && n < int64(capMaxRetenida) {
        buf.Grow(int(n))
    }
    if _, err := io.Copy(buf, r.Body); err != nil {
        devolverCuerpo(buf)
        return nil, err
    }
    return buf, nil
}

func devolverCuerpo(buf *bytes.Buffer) {
    if buf.Cap() <= capMaxRetenida {
        cuerpoPool.Put(buf)
    }
}

func (p *Procesador) Manejar(w http.ResponseWriter, r *http.Request) {
    buf, err := p.leerCuerpo(r)
    if err != nil {
        http.Error(w, "cuerpo inválido", http.StatusBadRequest)
        return
    }
    defer devolverCuerpo(buf) // una sola salida, siempre

    p.procesar(buf.Bytes()) // válido SOLO hasta el defer
}

18% más lento y una asignación más que antes de "optimizar". Tres causas, todas instructivas:

1. El objeto era chico. Evento son ~40 bytes: una asignación en el heap de Go para un tamaño así es una operación en el mcache local del P, sin locks. Un Get/Put de sync.Pool cuesta más que eso.
2. La pool derrotó al escape analysis. Antes del cambio, en varios call paths el compilador probaba que el Evento no escapaba y lo dejaba en el stack — costo cero. Al pasarlo por Get() any, el compilador pierde toda la información de tipo y flujo: ahora el objeto tiene que estar en el heap, sí o sí. La pool convirtió asignaciones de stack en asignaciones de heap.
3. El any del Put agregó su propio boxing en los caminos donde el compilador no pudo eliminarlo. De ahí sale la asignación extra que se ve en el benchstat.
📌 La lección del contraejemplo no es "sync.Pool es malo". Es que sync.Pool resuelve un problema muy específico: objetos grandes o caros de construir, en un servicio con volumen sostenido, con un ciclo de vida claramente delimitado. Aplicada fuera de ese caso, no es neutral: es una pesimización que además te agrega la obligación de acordarte de devolver el objeto — la misma carga mental del free() manual, sin la ayuda del compilador. Y notá que la diferencia entre el caso bueno (el buffer, 8 KiB, prestado dentro de un handler) y el malo (el evento, 40 bytes, devuelto al llamador) no se descubre razonando: se descubre con benchstat.

Checkpoint — ¿lo tenés claro?

¿Por qué un programa que asigna 10 GB/s puede darle menos trabajo al GC que uno que asigna 100 MB/s?

Porque el costo del recolector no lo manda cuánto asignás, sino cuánto queda vivo. El marcado tiene que recorrer el grafo de objetos alcanzables: si de esos 10 GB/s sobreviven 5 MB, cada ciclo escanea 5 MB y termina enseguida. Si el otro programa asigna 100 MB/s pero mantiene un caché de 8 GB vivos, cada ciclo tiene que recorrer ese grafo entero. Además, con GOGC=100 el objetivo del próximo ciclo se calcula sobre el heap vivo, así que el segundo programa además dispara ciclos más caros. El corolario práctico: para bajar el costo del GC hay dos palancas distintas —reducir la basura (escape analysis, prealocar, reusar) y reducir lo vivo (cachés más chicos, TTL, estructuras compactas)— y sirven para problemas diferentes.

Tu pod muere con OOMKilled pero gctrace muestra que el GC corría normal y el heap vivo era estable. ¿Qué pasó y cómo se arregla?

El GC estaba haciendo justo lo que le pediste. Con GOGC=100, el runtime apunta a un heap del doble del vivo: si el vivo saltó a 550 MB por una ráfaga, el objetivo pasó a 1,1 GB, y el kernel mató el proceso al cruzar el limits.memory de 1 GiB antes de que el ciclo se disparara. El runtime no sabía que existía un techo. El arreglo es GOMEMLIMIT al ~90% del límite del contenedor (dejando margen para lo que Go no contabiliza: el binario, cgo, buffers del kernel), y dejar el límite del contenedor puesto igual, porque GOMEMLIMIT es blando: si la memoria realmente viva supera el techo, el runtime entra en death spiral —GC continuo sin recuperar nada, acotado al 50% del CPU— y ahí querés que el pod muera y se reinicie en vez de agonizar.

Green Tea es default desde Go 1.26 y baja el overhead de GC 10–40%. ¿Qué hacés con tu servicio que gasta 15% de CPU en GC?

Actualizás, medís, y después seguís trabajando — porque Green Tea abarata el marcado, no reduce lo que asignás. En el mejor caso, ese 15% baja a ~9%: sigue estando muy por encima del umbral donde vale la pena entrar a mirar -alloc_objects. El orden correcto es siempre el mismo: primero medir con la versión nueva y guardar esos números como línea de base (los viejos ya no valen, y las alertas calibradas sobre ellos hay que rehacerlas), después atacar la causa —que casi siempre es asignar por ítem en un loop caliente o boxear en una interfaz por request—, y recién al final tocar GOGC. Sumale que el opt-out GODEBUG=greenteagc=0 desaparece en 1.27: sirve para comparar durante la migración, no como configuración permanente.

Resumen ejecutivo

  • El compilador decide stack o heap con escape analysis, y la sintaxis no te lo anticipa: & no significa heap. Lo mirás con go build -gcflags='-m -m' y leés el bloque flow: para encontrar el eslabón real.
  • Cuatro patrones fuerzan el escape: devolver un puntero a una local, guardar en una interfaz, capturar en un closure que sobrevive, y tamaño desconocido (esto último, cada vez menos: el compilador ya puede poner el backing store de slices en el stack en más casos).
  • Meter un valor en any/error/io.Reader casi siempre lo manda al heap. fmt.Println en un hot path no cuesta solo I/O: convierte valores de stack en asignaciones de heap.
  • El GC es concurrente, tricolor, con write barrier, y está optimizado para latencia, no throughput: pausas de microsegundos a cambio del costo del barrier y ~25% del CPU durante el marcado.
  • Green Tea es el recolector por defecto desde Go 1.26: marca por spans contiguos en vez de saltar de objeto en objeto, y reduce el overhead de GC entre 10% y 40%. El opt-out GODEBUG=greenteagc=0 desaparece en Go 1.27.
  • Todo servicio Go en un contenedor debería fijar GOMEMLIMIT al ~90% del límite, y mantener también el límite del contenedor: el techo de Go es blando y, si la memoria viva lo supera, degrada en vez de morir.
  • Medí con tres herramientas y tres preguntas: gctrace=1 (¿qué está pasando?), runtime/metrics (¿cómo lo exporto sin un STW por scrape?), pprof -alloc_objects (¿quién asigna?). El recolector sufre por cantidad de objetos, no por bytes.
  • Las técnicas que rinden, en orden: prealocar con capacidad conocida, evitar conversiones string↔[]byte, y sync.Pool solo para objetos grandes o caros con volumen sostenido — mal aplicada, derrota al escape analysis y empeora las cosas.
  • Si el GC ocupa menos del 3% de tu CPU, no hay nada que ganar acá. Medí antes de optimizar y volvé a medir después; si no medís, no optimizaste: cambiaste código.

🧠 Autoevaluación

1. Tu servicio corre en un pod con limits.memory: 2Gi y muere con OOMKilled durante los picos, aunque el heap vivo es estable en 400 MB. ¿Cuál es el arreglo correcto?

Con GOGC=100 el runtime apunta al doble del heap vivo, y no tiene forma de saber que existe un techo de 2 GiB: en un pico el objetivo se le va por arriba del límite y el kernel mata el proceso. GOMEMLIMIT le da esa información y convierte un OOM duro en presión de GC gradual. Bajar GOGC a 20 es una perilla relativa que quema CPU permanentemente sin garantizar el techo, y runtime.GC() por request es un stop-the-world autoinfligido que además no libera memoria alcanzable. El límite del contenedor se mantiene: GOMEMLIMIT es blando, y ante una fuga real preferís que el pod muera y se reinicie antes que agonizar en death spiral.

2. Metiste un sync.Pool para un struct de 40 bytes en tu hot path y benchstat dice que quedó 18% más lento y con una asignación más por operación. ¿Cuál es la explicación más probable?

Es el contraejemplo del worked example. Para un struct chico, asignar en el heap de Go es una operación en el mcache local del P, sin locks, más barata que el Get/Put de la pool. Y lo más importante: sync.Pool trabaja con any, así que el compilador pierde el tipo y el flujo, y objetos que el escape analysis dejaba en el stack pasan obligatoriamente al heap. La pool no ahorró asignaciones — creó unas nuevas. sync.Pool rinde con objetos grandes o caros de construir, en servicios con volumen sostenido y un ciclo de vida bien delimitado.

3. Actualizaste a Go 1.26 y el GC Green Tea es ahora el default. Tu perfil muestra que el recolector consume el 2% del CPU. ¿Qué esperás ganar dedicándole una semana a optimizar asignaciones?

Si el recolector ocupa el 2% del CPU, eliminar todas tus asignaciones te devuelve, en el límite teórico, 2 puntos. Con ese número, el tiempo rinde muchísimo más en el I/O, la base de datos o el algoritmo que se está comiendo el otro 98%. Y ojo con el 10–40% de Green Tea: es una reducción del overhead del recolector, no del tiempo total del programa — sobre un 2%, son décimas. La regla del módulo es esta: medí el porcentaje primero, y dejá que ese número decida si vale la pena entrar.

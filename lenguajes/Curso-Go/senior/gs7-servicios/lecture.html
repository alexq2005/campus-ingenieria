GS7 — Servicios en producción: HTTP, gRPC y resiliencia

GS7.0 Por qué este módulo

Go es el lenguaje de la nube por una razón poco romántica: levantar un servidor HTTP son cinco líneas, no lleva dependencias, compila a un binario estático y arranca en milisegundos. Docker, Kubernetes, Prometheus, etcd, Terraform y Traefik están escritos en Go, y todos empezaron con un http.ListenAndServe.

El problema es que esa facilidad crea una ilusión peligrosa. Hacer un servidor es trivial. Hacer uno que aguante —que sobreviva a que su base de datos se ponga lenta, a que un cliente abra 10.000 conexiones y no mande nada, a un deploy en el medio de un pico, a que un servicio de abajo devuelva 503 durante cuarenta minutos— no lo es. Y la distancia entre las dos cosas casi nunca es un problema de Go: es un puñado de decisiones de configuración que nadie tomó porque el valor por defecto parecía razonable.

💡 La tesis del módulo. Un servicio no se cae porque su código sea lento. Se cae porque no tiene límites. Sin límite de tiempo, sin límite de concurrencia, sin límite de reintentos, cualquier degradación de una dependencia se convierte en consumo de recursos ilimitado en tu proceso. Todo lo que sigue —timeouts, semáforos, circuit breakers, rate limits— es la misma idea repetida en distintas capas: poné una cota, y decidí vos qué pasa cuando se toca.

Vamos a trabajar sobre Go 1.26. Buena parte de lo que antes justificaba traer un framework hoy está en la biblioteca estándar: el router con patrones de método y comodines llegó en 1.22, http.ResponseController en 1.20, context.WithoutCancel y WithTimeoutCause en 1.21, math/rand/v2 —sin semilla y sin candado global— en 1.22. Si tu mapa mental de net/http es el de 2019, está desactualizado en las partes que importan.

GS7.1 El router de la stdlib: qué cambió en 1.22

Hasta Go 1.21, http.ServeMux hacía una sola cosa: matchear prefijos de path. No entendía métodos, no extraía parámetros y no tenía noción de especificidad. Por eso todo el mundo instalaba gorilla/mux o chi: no por las features exóticas, sino para poder escribir GET /users/{id}.

Desde 1.22 el mux de la stdlib entiende patrones con método y comodines:

mux := http.NewServeMux()

// Método + comodín. El valor se lee con r.PathValue.
mux.HandleFunc("GET /items/{id}", getItem)
mux.HandleFunc("PUT /items/{id}", putItem)
mux.HandleFunc("DELETE /items/{id}", deleteItem)
mux.HandleFunc("POST /items", createItem)

// Comodín "hasta el final": captura el resto del path, barras incluidas.
mux.HandleFunc("GET /files/{path...}", serveFile)

// {$} = coincidencia EXACTA con "/", no con todo lo que empiece en "/".
mux.HandleFunc("GET /{$}", home)

// Sin método: matchea cualquiera.
mux.Handle("/metrics", promhttp.Handler())
func getItem(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("id")       // string, siempre; validá vos el formato
    if id == "" {
        http.Error(w, "id requerido", http.StatusBadRequest)
        return
    }
    // ...
}

Hay tres reglas que conviene tener presentes porque cambian el comportamiento respecto del mux viejo:

  • Gana el patrón más específico, no el que registraste primero. /items/{id} le gana a /items/, y /items/especial le gana a /items/{id}. Si dos patrones son ambiguos —ninguno es más específico que el otro— el mux panickea al registrarlos, no en runtime. Es un error de arranque, que es exactamente donde querés que aparezca.
  • Registrar GET también registra HEAD automáticamente.
  • Si un path matchea un patrón pero con otro método, el mux responde 405 Method Not Allowed con el header Allow correcto. Antes daba 404.
El error que se hereda del mux viejo. mux.HandleFunc("/admin/", h) —con barra final— sigue significando "todo lo que empiece con /admin/", y mux.HandleFunc("/", h) sigue siendo un catch-all de todo el sitio. Si querés la raíz y solo la raíz, es "GET /{$}". Más de un endpoint de debug quedó expuesto por confiar en que "/" significaba "la home".

GS7.3 Timeouts del servidor: la sección que salva servicios

Si de este módulo te llevás una sola cosa, que sea esta. http.ListenAndServe(":8080", mux) crea un http.Server con todos los timeouts en cero, y cero significa "sin límite". Un cliente puede abrir una conexión, mandar GET / HTTP y quedarse ahí para siempre. Tu proceso mantiene la conexión, el file descriptor y la goroutine, indefinidamente.

// ❌ Lo que sale en todos los tutoriales.
log.Fatal(http.ListenAndServe(":8080", mux))
// Sin ReadHeaderTimeout: mil conexiones lentas te consumen mil FDs
// y mil goroutines. Eso es Slowloris, un ataque de 2009 que sigue
// funcionando contra servicios Go escritos con el ejemplo de la doc.

La versión que va a producción define el server explícitamente:

srv := &http.Server{
    Addr:    ":8080",
    Handler: root,                       // el mux con todos los middlewares

    // Tiempo máximo para recibir los headers. Es el que corta Slowloris.
    // Debe ser corto: nadie tarda 5 s en mandar 400 bytes de headers.
    ReadHeaderTimeout: 5 * time.Second,

    // Headers + body completo. Subilo solo en endpoints de upload,
    // y mejor por request (ver más abajo) que globalmente.
    ReadTimeout: 15 * time.Second,

    // Desde que se terminan de leer los headers hasta que se termina
    // de escribir la respuesta. Acota el handler entero.
    WriteTimeout: 30 * time.Second,

    // Cuánto vive una conexión keep-alive ociosa esperando otro request.
    IdleTimeout: 120 * time.Second,

    // Cota dura al tamaño de headers (default 1 MB).
    MaxHeaderBytes: 1 << 20,

    // Que los logs internos del server vayan a tu logger, no a stderr pelado.
    ErrorLog: log.New(logWriter{}, "", 0),
}

if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
    log.Fatalf("servidor caído: %v", err)
}

El caso incómodo: streaming, SSE y WebSockets

WriteTimeout es global y por lo tanto choca con cualquier respuesta larga: un Server-Sent Events que dura una hora se corta a los 30 segundos. La solución vieja era poner WriteTimeout: 0 y quedarse sin protección en todo el servicio. Desde Go 1.20 hay una respuesta mejor: ajustar el deadline por request.

func streamEvents(w http.ResponseWriter, r *http.Request) {
    rc := http.NewResponseController(w)

    // Este request en particular no tiene deadline de escritura.
    if err := rc.SetWriteDeadline(time.Time{}); err != nil {
        http.Error(w, "streaming no soportado", http.StatusInternalServerError)
        return
    }

    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")

    for {
        select {
        case <-r.Context().Done():   // el cliente cerró: salimos
            return
        case ev := <-events:
            fmt.Fprintf(w, "data: %s\n\n", ev)
            if err := rc.Flush(); err != nil {
                return               // conexión rota
            }
        }
    }
}
http.ResponseController también resuelve el otro problema histórico: si un middleware envuelve el ResponseWriter para capturar el status code, la envoltura suele perder las interfaces Flusher y Hijacker, y el streaming deja de andar. El controller busca un método Unwrap() http.ResponseWriter en tu envoltura y llega al writer real. Implementalo siempre que envuelvas.

Cota al body: la que casi nadie pone

GS7.4 El cliente: http.DefaultClient no tiene timeout

Este es el bug que tumbó producción en todas las empresas que usan Go, sin excepción. Mirá la definición:

// net/http/client.go
var DefaultClient = &Client{}   // Timeout: 0  →  SIN LÍMITE

Y ahora mirá el código que todos escribimos alguna vez:

// ❌ Todas estas llamadas usan DefaultClient. Ninguna tiene timeout.
resp, err := http.Get("http://inventario/stock/42")
resp, err := http.Post(url, "application/json", body)
resp, err := http.DefaultClient.Do(req)

Si inventario acepta la conexión TCP pero nunca responde —está vivo, pero trabado en un lock de base de datos, o el kernel aceptó el backlog mientras el proceso agoniza— tu goroutine se queda ahí. Para siempre. No hay error, no hay log, no hay métrica que se dispare sola. Simplemente cada request que entra suma una goroutine que nunca sale.

⚠️ La aritmética de la caída. Por la Ley de Little, la cantidad de requests en vuelo es L = λ × W: tasa de llegada por tiempo de servicio. A 500 req/s con una latencia normal de 20 ms tenés 10 requests en vuelo. Si la dependencia pasa a tardar 8 segundos, son 4.000. Si nunca responde, W es infinito y L crece sin techo: 30.000 goroutines al minuto, cada una con su stack, sus buffers de request y respuesta y su conexión. La memoria sube, el GC trabaja más, todo se pone más lento, el health check empieza a fallar, el orquestador te mata el pod y su tráfico se reparte entre los que quedan. Eso es una cascada, y empezó por un campo sin setear.

GS7.5 http.Client bien configurado

Un cliente de producción se define una vez, a nivel de paquete, con transport propio:

var inventarioClient = &http.Client{
    // Cota TOTAL: DNS + conexión + TLS + envío + espera + lectura del body.
    // Es la red de seguridad, no el mecanismo principal (ver abajo).
    Timeout: 5 * time.Second,

    Transport: &http.Transport{
        Proxy: http.ProxyFromEnvironment,
        DialContext: (&net.Dialer{
            Timeout:   2 * time.Second,     // establecer TCP
            KeepAlive: 30 * time.Second,
        }).DialContext,

        // Pool de conexiones: lo que evita un handshake por request.
        MaxIdleConns:        200,
        MaxIdleConnsPerHost: 100,   // ⚠️ el default es 2
        MaxConnsPerHost:     200,   // cota dura de conexiones simultáneas
        IdleConnTimeout:     90 * time.Second,

        TLSHandshakeTimeout:   3 * time.Second,
        ExpectContinueTimeout: 1 * time.Second,
        ResponseHeaderTimeout: 3 * time.Second,  // esperar el primer byte
        ForceAttemptHTTP2:     true,
    },
}
El default que arruina el rendimiento: http.DefaultTransport tiene MaxIdleConnsPerHost = 2. Con 200 requests concurrentes al mismo host, 198 conexiones se crean y se cierran en cada ciclo. El resultado es handshake TLS por request, decenas de miles de sockets en TIME_WAIT y, en cargas altas, agotamiento de puertos efímeros: el sistema deja de poder abrir conexiones salientes y todo falla con cannot assign requested address. Si tu servicio le pega fuerte a un host, subí MaxIdleConnsPerHost.
El otro error clásico: crear un &http.Client{} nuevo dentro de cada request. Cada cliente nuevo trae su propio Transport, y el Transport es el que tiene el pool. Un cliente por request significa cero reuso de conexiones y, además, una fuga: los transports viejos retienen sus conexiones ociosas hasta que el GC los junte. El cliente es un objeto de larga vida, seguro para uso concurrente. Uno por dependencia, a nivel de paquete o inyectado.

El body que hay que cerrar y drenar

resp, err := inventarioClient.Do(req)
if err != nil {
    return err          // ⚠️ con err != nil, resp es nil: NO hagas defer antes
}
defer func() {
    // Drenar antes de cerrar: si quedan bytes sin leer, la conexión NO
    // vuelve al pool, se cierra. Con CopyN acotamos por si el server
    // mandó 2 GB que no nos interesan.
    io.CopyN(io.Discard, resp.Body, 64<<10)
    resp.Body.Close()
}()

if resp.StatusCode != http.StatusOK {
    return fmt.Errorf("inventario devolvió %d", resp.StatusCode)
}
return json.NewDecoder(resp.Body).Decode(out)
La fuga clásica es el return temprano por status code: cerrás el body pero nunca lo leíste, así que la conexión se descarta en vez de reutilizarse. En un servicio que chequea status en cada llamada, eso convierte el pool en decorativo. Y la variante peor es no cerrar nada: la conexión queda tomada hasta que el GC corra el finalizador, lo cual puede no pasar nunca en un proceso que no presiona memoria.

Timeout global vs contexto por request

Client.Timeout es una red de seguridad, no el mecanismo fino. Cubre todo el intercambio incluida la lectura del body, así que si vence a mitad de una descarga te da un error parcial raro. Lo que querés en un servicio es que el contexto del request entrante gobierne la llamada saliente:

func (s *Service) Stock(ctx context.Context, id string) (int, error) {
    // Presupuesto propio para esta dependencia, siempre menor que el
    // del request entrante. Si el contexto padre ya venció, esto falla ya.
    ctx, cancel := context.WithTimeout(ctx, 800*time.Millisecond)
    defer cancel()

    req, err := http.NewRequestWithContext(ctx, http.MethodGet, s.url+"/stock/"+id, nil)
    if err != nil {
        return 0, err
    }
    // ... Do, drenar, decodificar
}

GS7.6 Middlewares: la firma y el límite

Go no necesita un tipo Middleware: la firma idiomática es una función que recibe un handler y devuelve otro. Eso es todo, y por eso los middlewares de chi funcionan con la stdlib y viceversa.

type Middleware func(http.Handler) http.Handler

// Chain aplica en orden de lectura: el primero es el más externo.
func Chain(h http.Handler, ms ...Middleware) http.Handler {
    for i := len(ms) - 1; i >= 0; i-- {
        h = ms[i](h)
    }
    return h
}
func RequestID(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        id := r.Header.Get("X-Request-ID")
        if id == "" {
            id = uuid.NewString()
        }
        w.Header().Set("X-Request-ID", id)
        ctx := context.WithValue(r.Context(), ctxKeyReqID{}, id)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

func Recover(logger *slog.Logger) Middleware {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            defer func() {
                if rec := recover(); rec != nil {
                    // http.ErrAbortHandler es intencional: no es un bug.
                    if rec == http.ErrAbortHandler {
                        panic(rec)
                    }
                    logger.Error("panic en handler",
                        "err", rec,
                        "stack", string(debug.Stack()),
                        "req_id", reqIDFrom(r.Context()),
                        "path", r.URL.Path)
                    http.Error(w, "error interno", http.StatusInternalServerError)
                }
            }()
            next.ServeHTTP(w, r)
        })
    }
}
// El orden importa: lo de afuera envuelve a lo de adentro.
root := Chain(mux,
    RequestID,              // 1º: todo lo demás quiere el id
    Recover(logger),        // 2º: atrapa panics de auth y del handler
    Logging(logger),        // 3º: mide lo que realmente se ejecuta
    Metrics(reg),
    MaxBody(1<<20),
    Auth(verifier),         // último: ya hay id, logs y recovery
)
📌 Qué va en un middleware y qué no. Va lo transversal y agnóstico del dominio: request id, recovery, logging, métricas, tracing, CORS, límite de body, autenticación (¿quién sos?), rate limiting, compresión. No va la autorización fina (¿podés tocar este recurso?, que depende de datos que el middleware no tiene), la validación específica de un endpoint, ni nada que necesite tipos del dominio. La señal de que te pasaste es cuando el middleware empieza a leer y re-serializar el body, o a hacer un switch por path: eso es un handler mal ubicado.

GS7.7 Graceful shutdown (y por qué en Kubernetes no alcanza)

Cuando el orquestador te manda SIGTERM, el default de Go es morir en el acto: los requests en vuelo se cortan a la mitad, sus transacciones quedan colgando y el cliente ve una conexión rota. Shutdown resuelve la parte del proceso:

func run(ctx context.Context) error {
    ctx, stop := signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)
    defer stop()

    srv := newServer(...)

    errCh := make(chan error, 1)
    go func() {
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            errCh <- err
        }
    }()

    select {
    case err := <-errCh:
        return err                     // no pudo ni arrancar
    case <-ctx.Done():
        logger.Info("señal recibida, drenando")
    }

    // 1. Dejar de decir que estamos listos. El balanceador tarda en enterarse.
    health.SetReady(false)
    time.Sleep(5 * time.Second)

    // 2. Ahora sí: dejar de aceptar, esperar a los que están en vuelo.
    shCtx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
    defer cancel()
    if err := srv.Shutdown(shCtx); err != nil {
        logger.Warn("shutdown forzado", "err", err)
        srv.Close()
    }

    // 3. Recién ahora cerrar lo de abajo: DB, colas, flush de trazas.
    return closeDeps(shCtx)
}

El time.Sleep del paso 1 parece un hack y es, en realidad, la parte más importante. En Kubernetes, cuando un pod entra en Terminating pasan dos cosas en paralelo, sin coordinación: el kubelet manda SIGTERM al contenedor, y el controlador de endpoints le avisa a kube-proxy, al Ingress y a los service meshes que ese pod ya no recibe tráfico. La segunda es una propagación distribuida que tarda segundos. Si vos cerrás el listener apenas llega SIGTERM, durante esos segundos el balanceador sigue mandándote requests y el cliente recibe connection refused: errores 502 en cada deploy, achacados eternamente a "la red".

Números que tienen que cerrar. terminationGracePeriodSeconds (default 30 s) debe ser mayor que sleep + timeout de Shutdown. Con 5 + 20 = 25 s vas justo; poné 40. Si se vence, el kubelet manda SIGKILL y perdés todo lo que estabas drenando. Y ojo: Shutdown no espera a conexiones hijacked —WebSockets, streams de larga vida—; esas las tenés que rastrear vos y avisarles con srv.RegisterOnShutdown.

GS7.8 Contexto por request: cancelación hasta la base de datos

En GS3 vimos context como mecanismo de cancelación. En un servicio es, además, la única forma de que un cliente que se fue deje de costarte plata. r.Context() se cancela solo cuando el cliente cierra la conexión, y esa cancelación tiene que viajar hacia abajo:

func (r *Repo) Buscar(ctx context.Context, q string) ([]Item, error) {
    // QueryContext manda un cancel al servidor de la base cuando ctx muere:
    // Postgres aborta la query. Con Query() a secas, la query sigue corriendo
    // en el servidor aunque nadie vaya a leer el resultado.
    rows, err := r.db.QueryContext(ctx, `SELECT id, nombre FROM items WHERE nombre ILIKE $1`, q)
    if err != nil {
        return nil, err
    }
    defer rows.Close()
    // ...
}
Por qué esto es un vector de caída y no una prolijidad. Un usuario impaciente recarga cinco veces una búsqueda pesada. Sin propagación de contexto, esas cinco queries siguen ocupando conexiones del pool y CPU de la base aunque nadie espere la respuesta. El pool se agota, el resto de los endpoints —que no tienen nada que ver— empiezan a fallar por context deadline exceeded pidiendo una conexión, y a los treinta segundos tenés un incidente completo originado en un botón de refresh.

El caso inverso también existe: trabajo que debe sobrevivir al request. Un evento de auditoría no se puede perder porque el cliente cerró el navegador. Desde Go 1.21:

func handler(w http.ResponseWriter, r *http.Request) {
    // ... responder rápido ...

    // Conserva los valores (request id, trazas) pero NO la cancelación.
    bg := context.WithoutCancel(r.Context())
    bg, cancel := context.WithTimeout(bg, 10*time.Second)
    go func() {
        defer cancel()
        if err := auditor.Registrar(bg, ev); err != nil {
            logger.Error("auditoría perdida", "err", err)
        }
    }()
}
Al depurar, context.Cause(ctx) (1.20+) te dice por qué murió el contexto, no solo que murió. Con context.WithTimeoutCause(ctx, d, errors.New("presupuesto de inventario agotado")) el log deja de decir "context deadline exceeded" —el error más inútil de Go en producción— y pasa a nombrar la etapa exacta que se pasó de tiempo.

GS7.9 Reintentos: exponencial, con jitter, y con presupuesto

Reintentar es lo primero que se le ocurre a todo el mundo y también la forma más rápida de convertir una degradación en una caída. Un reintento inmediato duplica la carga sobre un servicio que ya no da abasto. Tres reintentos la cuadruplican.

func conBackoff(ctx context.Context, intentos int, fn func(context.Context) error) error {
    const base = 100 * time.Millisecond
    const techo = 5 * time.Second

    var err error
    for i := 0; i < intentos; i++ {
        if err = fn(ctx); err == nil {
            return nil
        }
        if !esReintentable(err) || i == intentos-1 {
            return err
        }

        // Exponencial acotado...
        espera := min(base<<i, techo)
        // ...y "full jitter": un valor aleatorio ENTRE 0 y la espera.
        espera = time.Duration(rand.Int64N(int64(espera)))

        select {
        case <-ctx.Done():
            return context.Cause(ctx)   // el presupuesto manda sobre el retry
        case <-time.After(espera):
        }
    }
    return err
}
💡 Por qué el jitter no es un detalle. Imaginate 2.000 clientes cuyas llamadas fallan todas en el mismo segundo porque el servicio se reinició. Con backoff exponencial puro, los 2.000 esperan exactamente 100 ms y vuelven a pegar en el mismo milisegundo. El servicio que estaba levantándose recibe 2.000 requests simultáneos y se cae de nuevo. Repetís a los 200 ms, a los 400 ms: una onda periódica que impide la recuperación para siempre. El jitter reparte esos 2.000 reintentos de forma uniforme en la ventana y el pico se aplana. Sin jitter, tu política de reintentos es un ataque de denegación de servicio coordinado contra tu propia infraestructura. 
func esReintentable(err error) bool {
    if errors.Is(err, context.Canceled) || errors.Is(err, context.DeadlineExceeded) {
        return false                 // el presupuesto ya se acabó

    var he *HTTPError
    if errors.As(err, &he) {
        switch he.Status {
        case 429, 502, 503, 504:
            return true              // sobrecarga o falla transitoria
        }
        return false                 // 4xx: reintentar no cambia nada
    }
    var ne net.Error
    return errors.As(err, &ne)       // errores de red: sí
}

GS7.10 Circuit breaker: dejar de golpear al que está caído

El reintento asume que la falla es transitoria. Cuando no lo es —la dependencia está caída hace diez minutos— cada request tuyo gasta un timeout completo, ocupa una goroutine durante todo ese tiempo y le suma carga a un servicio que está tratando de levantarse. El circuit breaker corta ese ciclo con tres estados:

  • Cerrado — todo pasa. Se cuentan fallas en una ventana móvil.
  • Abierto — se superó el umbral: todo falla al instante, sin tocar la red. Cero latencia, cero goroutines retenidas, cero carga sobre la dependencia.
  • Semiabierto — pasado el tiempo de espera, dejamos pasar unas pocas pruebas. Si andan, cierra; si no, vuelve a abrir.
var cb = gobreaker.NewCircuitBreaker[[]byte](gobreaker.Settings{
    Name:        "inventario",
    MaxRequests: 3,                 // pruebas permitidas en semiabierto
    Interval:    30 * time.Second,  // ventana de conteo
    Timeout:     10 * time.Second,  // cuánto queda abierto antes de probar
    ReadyToTrip: func(c gobreaker.Counts) bool {
        ratio := float64(c.TotalFailures) / float64(c.Requests)
        return c.Requests >= 20 && ratio >= 0.6   // mínimo de muestras + %
    },
    OnStateChange: func(name string, from, to gobreaker.State) {
        logger.Warn("breaker cambió", "dep", name, "de", from, "a", to)
        breakerState.WithLabelValues(name).Set(float64(to))
    },
})

body, err := cb.Execute(func() ([]byte, error) {
    return llamarInventario(ctx, id)
})
if errors.Is(err, gobreaker.ErrOpenState) {
    return cacheODegradado(id)      // plan B, no un 500
}
El breaker sin timeout no sirve para nada. Un breaker cuenta fallas. Si la dependencia no falla sino que tarda —acepta la conexión y no responde— nunca hay una falla que contar, el breaker se queda cerrado y las goroutines se siguen apilando exactamente igual. El timeout es lo que convierte lentitud en falla, que es lo único que un breaker sabe medir. Por eso el orden de instalación es siempre: primero timeout, después breaker.
Umbral por ratio, nunca por conteo absoluto, y siempre con mínimo de muestras. "Abrir tras 5 fallas" en un servicio de 10.000 rps abre el breaker con una tasa de error del 0,05%. Y un ratio sin mínimo abre con 1 falla de 1 request en un endpoint de bajo tráfico. Necesitás las dos condiciones.

GS7.11 Límite de concurrencia y rate limiting

El timeout acota cuánto dura cada request. El límite de concurrencia acota cuántos hay a la vez, que es la otra mitad de la Ley de Little. Es el patrón bulkhead: si el mamparo aguanta, la inundación de un compartimento no hunde el barco.

type Limitada struct {
    sem chan struct{}       // buffer = concurrencia máxima
    cli *http.Client
}

func NewLimitada(max int) *Limitada {
    return &Limitada{sem: make(chan struct{}, max), cli: inventarioClient}
}

func (l *Limitada) Do(ctx context.Context, req *http.Request) (*http.Response, error) {
    // El presupuesto se chequea primero: un select con `default` nunca
    // bloquea, así que mezclar ahí el caso ctx.Done() elige al azar.
    if ctx.Err() != nil {
        return nil, context.Cause(ctx)
    }
    select {
    case l.sem <- struct{}{}:
        defer func() { <-l.sem }()
    default:
        // Sin cupo: fallar YA es mejor que encolar. Una cola sin límite
        // es una fuga de memoria con pasos extra.
        return nil, ErrSaturado
    }
    return l.cli.Do(req)
}

Del lado de entrada, golang.org/x/time/rate implementa token bucket: una tasa sostenida más un colchón de ráfaga.

// 100 req/s sostenidos, tolerando ráfagas de 200.
var global = rate.NewLimiter(rate.Limit(100), 200)

func RateLimit(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if !global.Allow() {                  // no bloquea: acepta o rechaza
            w.Header().Set("Retry-After", "1")
            http.Error(w, "demasiadas solicitudes", http.StatusTooManyRequests)
            return
        }
        next.ServeHTTP(w, r)
    })
}
// Por cliente, con expiración: sin la limpieza, el mapa crece para siempre.
type PorCliente struct {
    mu    sync.Mutex
    lims  map[string]*entrada
    r     rate.Limit
    burst int
}
type entrada struct {
    lim   *rate.Limiter
    visto time.Time
}

func (p *PorCliente) Get(key string) *rate.Limiter {
    p.mu.Lock()
    defer p.mu.Unlock()
    e, ok := p.lims[key]
    if !ok {
        e = &entrada{lim: rate.NewLimiter(p.r, p.burst)}
        p.lims[key] = e
    }
    e.visto = time.Now()
    return e.lim
}

func (p *PorCliente) Limpiar(maxEdad time.Duration) {
    p.mu.Lock()
    defer p.mu.Unlock()
    for k, e := range p.lims {
        if time.Since(e.visto) > maxEdad {
            delete(p.lims, k)
        }
    }
}
Allow() rechaza al instante — es lo que querés en el borde HTTP. Wait(ctx) bloquea hasta que haya token o el contexto muera — sirve para salida, cuando vos controlás el ritmo con el que le pegás a una API de terceros y preferís esperar antes que fallar. Elegir mal el método es transformar un rate limit en una cola invisible.

GS7.12 Idempotencia: el requisito que los reintentos imponen

Un reintento no distingue "la operación falló" de "la operación funcionó pero la respuesta se perdió". Desde el cliente ambas cosas son el mismo timeout. Por eso, en cuanto habilitás reintentos estás obligando a que la operación sea idempotente: repetirla N veces tiene que dar el mismo resultado que ejecutarla una. Si no, el segundo intento de POST /pagos cobra de nuevo.

func (s *Pagos) Crear(ctx context.Context, key string, p Pago) (Recibo, error) {
    tx, err := s.db.BeginTx(ctx, nil)
    if err != nil {
        return Recibo{}, err
    }
    defer tx.Rollback()

    // La clave se inserta en la MISMA transacción que el efecto.
    // El índice único es lo que hace atómica la garantía; un "chequear
    // y después insertar" tiene una ventana de carrera entre las dos.
    _, err = tx.ExecContext(ctx,
        `INSERT INTO idempotencia (clave, creado) VALUES ($1, now())`, key)
    if isUniqueViolation(err) {
        tx.Rollback()
        return s.reciboGuardado(ctx, key)   // ya se procesó: devolvemos lo mismo
    }
    if err != nil {
        return Recibo{}, err
    }

    rec, err := s.cobrar(ctx, tx, p)
    if err != nil {
        return Recibo{}, err
    }
    if err := s.guardarRecibo(ctx, tx, key, rec); err != nil {
        return Recibo{}, err
    }
    return rec, tx.Commit()
}
📌 La clave la genera el cliente, no el servidor, y la mantiene a través de los reintentos del mismo intento lógico. Si el cliente genera una clave nueva en cada retry, no sirvió de nada. Guardá también la respuesta asociada a la clave, con un TTL (24–72 h): el reintento tardío tiene que recibir el mismo recibo, no un 409 que el cliente no sabe interpretar.

GS7.13 gRPC: cuándo conviene y cuánto cuesta

gRPC es RPC sobre HTTP/2 con contratos en Protocol Buffers y código generado. La ganancia técnica es real: serialización binaria (3–10× más chica que JSON), multiplexación de muchas llamadas sobre una conexión, streaming bidireccional de primera clase, y —lo más subestimado— los deadlines viajan en el protocolo. Si el cliente pone 200 ms, ese presupuesto llega al servidor como header grpc-timeout y se propaga a las llamadas que ese servidor haga a su vez. En REST eso lo tenés que cablear a mano en cada salto.

// inventario/v1/inventario.proto

📌 Regla práctica. gRPC para servicio a servicio interno con alto volumen, muchos lenguajes y contratos que cambian seguido. REST para APIs públicas, navegadores y cualquier consumidor que no controlás. Muchos equipos terminan con las dos cosas: gRPC adentro, un gateway REST en el borde. Si querés el contrato tipado sin el costo operativo de HTTP/2, mirá Connect-RPC: mismos .proto, pero habla HTTP/1.1 y se puede curlear.
La trampa del balanceo. gRPC abre una conexión HTTP/2 y multiplexa todo ahí. Un balanceador L4 la asigna a un backend y ahí se queda: si escalás de 3 a 30 réplicas, los clientes existentes le siguen pegando a las 3 originales. Se resuelve con balanceo del lado del cliente (round_robin + resolver DNS), con un proxy L7 o con MaxConnectionAge para forzar reconexiones periódicas. Es el problema número uno de gRPC en Kubernetes y no da ningún error: solo ves réplicas nuevas que no reciben tráfico.

GS7.14 Errores en el borde: no filtrar internals

El patrón más común de la primera versión de cualquier API Go es también una fuga de información:

// ❌ Le manda al cliente el mensaje crudo del driver.
if err != nil {
    http.Error(w, err.Error(), http.StatusInternalServerError)
    return
}
// El cliente recibe algo así:
// pq: relation "usuarios_internos" does not exist  (host db-prod-3.interno:5432)

Ahí acabás de regalar el motor de base de datos, nombres de tablas, hostnames internos y, con un poco de suerte para el atacante, un fragmento de la query. Es exactamente el Security Misconfiguration del M04 del curso de Ciberseguridad: el mensaje de error como herramienta de reconocimiento. La regla es simple y no tiene excepciones: el detalle va al log con un identificador; al cliente le va una categoría más ese identificador.

var (
    ErrNoEncontrado = errors.New("no encontrado")
    ErrConflicto    = errors.New("conflicto de versión")
    ErrNoAutorizado = errors.New("no autorizado")
)

type APIError struct {
    Code    string `json:"code"`
    Message string `json:"message"`
    ReqID   string `json:"request_id"`
}

func responderError(w http.ResponseWriter, r *http.Request, err error) {
    reqID := reqIDFrom(r.Context())

    status, code, msg := http.StatusInternalServerError, "internal", "error interno"
    switch {
    case errors.Is(err, ErrNoEncontrado):
        status, code, msg = http.StatusNotFound, "not_found", "recurso inexistente"
    case errors.Is(err, ErrConflicto):
        status, code, msg = http.StatusConflict, "conflict", "el recurso cambió"
    case errors.Is(err, ErrNoAutorizado):
        status, code, msg = http.StatusForbidden, "forbidden", "sin permisos"
    case errors.Is(err, context.DeadlineExceeded):
        status, code, msg = http.StatusGatewayTimeout, "timeout", "tiempo agotado"
    }

    // El detalle completo va acá, nunca al cliente.
    logger.Error("request fallido", "err", err, "req_id", reqID,
        "path", r.URL.Path, "status", status)

    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(status)
    json.NewEncoder(w).Encode(APIError{Code: code, Message: msg, ReqID: reqID})
}

GS7.15 Configuración: fallar al arrancar, no en la primera request

El anti-patrón que más incidentes silenciosos genera es leer configuración desde adentro del código de negocio:

// ❌ Este error aparece a las tres de la mañana, en el único endpoint
// que nadie probó después del deploy.
func (s *Service) enviar(ctx context.Context, m Mensaje) error {
    url := os.Getenv("NOTIFY_URL")   // vacío en producción, nadie se enteró
    ...
}

La configuración se lee, se valida y se congela una vez, en el arranque. Si falta algo, el proceso no arranca. Un pod que no levanta se ve en el primer minuto del deploy; un endpoint roto puede tardar semanas en descubrirse.

type Config struct {
    Addr            string
    DatabaseURL     string
    NotifyURL       string
    InventarioURL   string
    ShutdownTimeout time.Duration
    MaxInflight     int
    LogLevel        slog.Level
}

func Load() (Config, error) {
    c := Config{
        Addr:            getenv("ADDR", ":8080"),
        DatabaseURL:     os.Getenv("DATABASE_URL"),
        NotifyURL:       os.Getenv("NOTIFY_URL"),
        InventarioURL:   os.Getenv("INVENTARIO_URL"),
        ShutdownTimeout: getdur("SHUTDOWN_TIMEOUT", 20*time.Second),
        MaxInflight:     getint("MAX_INFLIGHT", 100),
    }

    var faltan []string
    for k, v := range map[string]string{
        "DATABASE_URL":   c.DatabaseURL,
        "NOTIFY_URL":     c.NotifyURL,
        "INVENTARIO_URL": c.InventarioURL,
    } {
        if v == "" {
            faltan = append(faltan, k)
        }
    }
    if len(faltan) > 0 {
        sort.Strings(faltan)
        // Todas las que faltan de una: no de a una por deploy.
        return c, fmt.Errorf("faltan variables de entorno: %s", strings.Join(faltan, ", "))
    }
    if _, err := url.Parse(c.InventarioURL); err != nil {
        return c, fmt.Errorf("INVENTARIO_URL inválida: %w", err)
    }
    if c.MaxInflight < 1 {
        return c, errors.New("MAX_INFLIGHT debe ser >= 1")
    }
    return c, nil
}
Logueá la config resuelta al arrancar, con los secretos redactados. La mitad de los incidentes de "está usando la config equivocada" se resuelven en diez segundos con esa línea de log. Y validá también lo alcanzable: un ping a la base y un chequeo de resolución DNS de cada dependencia, con timeout, antes de decir "ready". Es la diferencia entre un pod que falla el arranque y uno que arranca sano para fallar en el primer request real.

func main() {

func run(ctx context.Context) error {
    cfg, err := config.Load()

    repo := postgres.NewItems(db)

}

GS7.17 Worked Example: la caída en cascada

El sistema. checkout (12 réplicas, 500 req/s en total, 2 vCPU y 512 MB por pod) llama a inventario en cada request. En operación normal inventario responde en 20 ms y el p99 de checkout es 40 ms.

El incidente. Un martes a las 14:07, inventario pierde un índice tras una migración. Sus queries pasan de 15 ms a 8 segundos. No devuelve errores: acepta la conexión y contesta, tarde. A las 14:09, checkout empieza a devolver 502 en todos sus endpoints, incluidos los que no tocan inventario. A las 14:11 los pods entran en CrashLoopBackOff. Inventario, mientras tanto, sigue vivo y respondiendo.

El código. Lo que había en el cliente era esto:

func stock(id string) (int, error) {
    resp, err := http.Get("http://inventario/stock/" + id)   // DefaultClient
    if err != nil {
        return 0, err
    }
    defer resp.Body.Close()
    var out struct{ Cantidad int }
    return out.Cantidad, json.NewDecoder(resp.Body).Decode(&out)
}

El diagnóstico. Tres señales, en este orden:

$ curl -s localhost:6060/debug/pprof/goroutine?debug=1 | head -5

28901 @ 0x43e5c5 0x4a1f0d 0x4a3b21 ...

#       net/http.(*Transport).RoundTrip
#       checkout/internal/inventario.stock

28.901 goroutines bloqueadas en roundTrip. La cuenta cierra con la Ley de Little: 500 req/s × ~58 s acumulados = ~29.000 en vuelo. Cada una retiene stack, buffers y una conexión. El heap crece hasta el límite del contenedor y el kernel mata el proceso. Cuando checkout-abc muere, sus 500 req/s se reparten entre los 11 pods restantes, que llegan al límite más rápido. Eso es la cascada: no la causó inventario, la causó la ausencia de un límite en checkout.

Solución por capas, midiendo cada una

Capa 1 — Timeout en el cliente. Un cambio de tres líneas:

var invClient = &http.Client{
    Timeout:   800 * time.Millisecond,
    Transport: transportProduccion(),   // con MaxIdleConnsPerHost decente
}

func stock(ctx context.Context, id string) (int, error) {
    req, _ := http.NewRequestWithContext(ctx, http.MethodGet, "http://inventario/stock/"+id, nil)
    resp, err := invClient.Do(req)
    ...
}

Ahora W está acotado en 0,8 s, así que L = 500 × 0,8 = 400 goroutines como máximo, sin importar cuánto empeore inventario. El endpoint de checkout sigue fallando —inventario no responde, no hay magia— pero el proceso sobrevive: la memoria se estabiliza, los health checks pasan, los otros endpoints atienden normal y el pod no se reinicia. El incidente pasa de "checkout caído" a "checkout con una funcionalidad degradada", que es una página de guardia distinta.

Capa 2 — Límite de concurrencia (bulkhead). Un semáforo de 100 sobre las llamadas a inventario. Con cupo lleno se responde al instante con un error de saturación. Las goroutines quedan en 100 en vez de 400, y —lo más importante— las conexiones del pool de Postgres que esos handlers tenían tomadas quedan libres: los endpoints que sí funcionan dejan de competir por recursos con los que están muriendo.

Capa 3 — Circuit breaker. Con el timeout convirtiendo lentitud en falla, el breaker por fin tiene algo que contar: tras 20 fallas con ratio ≥ 0,6, abre. La latencia del camino roto cae de 800 ms a microsegundos, así que el request de checkout responde rápido con su plan B (último stock cacheado) en vez de gastar el presupuesto entero del usuario. E inventario deja de recibir 500 req/s y pasa a recibir 3 pruebas cada 10 segundos, lo cual le da margen real para recuperarse.

📌 La moraleja tiene dos partes. Primera: el timeout solo resuelve el 80%. Es tres líneas, no tiene dependencias, no requiere una biblioteca ni una decisión de arquitectura, y es la diferencia entre un incidente y una caída. Las capas 2 y 3 mejoran la calidad de la degradación; la capa 1 es la que evita que te mueras. Segunda: el orden no es negociable. Un breaker sin timeout no cuenta nada porque no hay fallas, solo lentitud. Un límite de concurrencia sin timeout retrasa el OOM pero no lo evita, porque los slots nunca se liberan. Checkpoint — ¿lo tenés claro?

¿Por qué un circuit breaker no habría evitado la caída de checkout si no se agregaba antes el timeout?

Porque un breaker cuenta fallas, y en ese incidente no había fallas: inventario aceptaba las conexiones y respondía, solo que tarde. Sin timeout, cada llamada quedaba pendiente indefinidamente, nunca devolvía un error, y el contador del breaker se quedaba en cero mientras las goroutines se apilaban exactamente igual. El timeout es lo que traduce "lento" a "falló", que es el único lenguaje que un breaker entiende. Por eso el orden de instalación es timeout primero, después límite de concurrencia, después breaker: cada capa depende de que la anterior exista.

En Kubernetes, ¿por qué llamar a srv.Shutdown() apenas llega SIGTERM produce 502 en cada deploy?

Porque el SIGTERM y la baja del pod de los endpoints del Service ocurren en paralelo y sin coordinación. El kubelet te manda la señal en el instante en que el controlador de endpoints empieza a propagar la novedad a kube-proxy, al Ingress y al service mesh, y esa propagación tarda segundos. Si cerrás el listener en el milisegundo cero, durante esa ventana el balanceador sigue enviándote tráfico y cada request nuevo rebota con connection refused. La secuencia correcta es: marcar el readiness como no-listo, esperar unos 5 segundos a que el balanceador se entere, y recién ahí llamar a Shutdown — asegurándote de que terminationGracePeriodSeconds sea mayor que la espera más el timeout de drenado.

Habilitás reintentos con backoff en el cliente de pagos. ¿Qué cambió del lado del servidor?

Que el servidor ahora debe ser idempotente para esa operación, porque un timeout del cliente no distingue "no se procesó" de "se procesó y se perdió la respuesta". El segundo intento de un POST /pagos sin protección cobra dos veces. La solución es una Idempotency-Key generada por el cliente y estable a lo largo de los reintentos del mismo intento lógico, insertada con un índice único dentro de la misma transacción que produce el efecto: si la inserción viola la restricción, la operación ya ocurrió y se devuelve el recibo guardado en vez de volver a cobrar. Chequear-y-después-insertar en dos pasos no sirve: tiene una ventana de carrera justo en el medio.

Resumen ejecutivo

  • Desde 1.22 el ServeMux de la stdlib entiende GET /items/{id}, {path...} y {$}, gana el patrón más específico y los conflictos panickean al registrar. Para la mayoría de los servicios, ya no hace falta un framework.
  • http.ListenAndServe deja todos los timeouts en cero. Un server de producción setea ReadHeaderTimeout, ReadTimeout, WriteTimeout e IdleTimeout; para streaming se ajusta el deadline por request con http.ResponseController.
  • http.DefaultClient no tiene timeout. Es la causa raíz más común de caídas por cascada en Go. Cliente propio, timeout, MaxIdleConnsPerHost por encima del default de 2, y NewRequestWithContext para que mande el presupuesto del request.
  • El resp.Body se drena y se cierra. Cerrar sin leer descarta la conexión en vez de devolverla al pool.
  • Middleware es func(http.Handler) http.Handler. Ahí va lo transversal; la lógica de dominio va en el handler o en el servicio.
  • Graceful shutdown = readiness en falso → esperar a que el balanceador se entere → Shutdown(ctx) → cerrar dependencias. Con terminationGracePeriodSeconds más grande que la suma.
  • El contexto del request viaja hasta la base con QueryContext. Un request abandonado que sigue quemando CPU y conexiones es un vector de caída, no una prolijidad.
  • Reintentos: exponencial con jitter (sin jitter creás una estampida sincronizada contra el servicio que se está recuperando), solo en errores reintentables, solo en operaciones idempotentes, con presupuesto y en una sola capa.
  • El breaker necesita el timeout para tener fallas que contar. Umbral por ratio con mínimo de muestras, nunca por conteo absoluto.
  • Reintentos ⇒ idempotencia: Idempotency-Key del cliente + índice único en la misma transacción que el efecto.
  • gRPC adentro (contratos, streaming, deadlines propagados); REST en el borde. El costo real es tooling, depuración y balanceo de HTTP/2.
  • Nunca http.Error(w, err.Error(), 500): detalle al log con request id, categoría al cliente, código de estado correcto.
  • La config se valida al arrancar y el proceso no levanta si falta algo. cmd/ cablea, internal/ es una garantía del compilador, no una convención.

🧠 Autoevaluación

1. Tu servicio recibe 400 req/s y le pega a una dependencia que dejó de responder (acepta la conexión, no contesta nunca). Usás http.Get. ¿Qué pasa y por qué?

DefaultClient es &Client{}, con Timeout: 0, que significa "sin límite". Por la Ley de Little, con el tiempo de servicio tendiendo a infinito la cantidad de requests en vuelo crece sin techo: 400/s × 60 s = 24.000 goroutines al minuto, cada una con su stack, sus buffers y su conexión. La memoria sube hasta el límite del contenedor, el runtime no cancela nada por su cuenta, y el kernel mata el proceso. El arreglo son tres líneas: un http.Client propio con Timeout.

2. Agregás reintentos con backoff exponencial sin jitter. Tu dependencia se reinicia y 2.000 clientes fallan en el mismo segundo. ¿Cuál es la consecuencia?

El backoff exponencial separa intentos sucesivos de un mismo cliente, pero no separa a los clientes entre sí: si todos fallaron en t0 y todos esperan exactamente 100 ms, todos vuelven en t0+100 ms. El servicio que estaba arrancando recibe el pico completo y se cae otra vez, y el ciclo se repite a los 200 ms, a los 400 ms. El full jitter —esperar un valor aleatorio entre 0 y la ventana calculada— reparte esos reintentos de forma uniforme y aplana el pico. Sin jitter, tu política de reintentos es una denegación de servicio coordinada contra tu propia infraestructura.

3. Tu handler devuelve http.Error(w, err.Error(), 500) y el error viene del driver de Postgres. ¿Cuál es el problema principal?

El mensaje crudo del driver puede incluir el motor, el nombre de la tabla, el host interno y hasta un pedazo de la query: es exactamente el Security Misconfiguration del M04 de Ciberseguridad, el error como herramienta de reconocimiento. El patrón correcto es mapear errores de dominio a códigos con errors.Is/errors.As, loguear el detalle completo junto al request id, y devolverle al cliente una categoría estable más ese id para que soporte pueda correlacionar. Y sí, el código importa —504 si venció una dependencia, 503 si estás sobrecargado— pero es secundario frente a la filtración.

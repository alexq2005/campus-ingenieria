GS4 — Interfaces, genéricos y diseño de API

GS4.0 Por qué este módulo

Go te sacó casi todas las herramientas con las que otros lenguajes expresan abstracciones. No hay herencia. No hay sobrecarga de funciones ni de operadores. No hay excepciones. No hay parámetros por defecto. No hay tipos suma como valores. Lo que te queda es una lista corta: structs, interfaces, funciones y —desde 1.18— parámetros de tipo. Con eso tenés que decir todo.

La consecuencia es incómoda y liberadora al mismo tiempo: en Go el diseño de tipos es el diseño de la API. No hay una capa de patrones sobre la cual esconder una mala decisión de tipos. Si elegiste mal la firma de una función, se nota en cada llamada. Si publicaste una interfaz de doce métodos, se nota en cada test de cada usuario de tu librería.

💡 La tesis del módulo. Las decisiones de tipos que más duelen a los seis meses son las que parecían inocentes el día que las tomaste: devolver un tipo concreto de error en vez de error, publicar una interfaz "por si acaso", agregar un parámetro más al constructor, exponer un campo que después no podés cambiar. Ninguna de esas se siente como una decisión de arquitectura cuando la escribís. Todas lo son.

Y hay una razón de coyuntura para estudiarlo ahora. Go 1.26 movió tres piezas de este tablero: los tipos genéricos ya pueden referirse a sí mismos en su propia lista de parámetros de tipo (lo que destraba estructuras recursivas y constraints del estilo "el tipo se restringe a sí mismo"), new pasó a aceptar una expresión (matando de un plumazo el helper genérico más copiado de la historia de Go), y errors.AsType[T]() llegó a la biblioteca estándar. Nada de eso cambia el lenguaje de raíz, pero sí cambia cuál es el código idiomático a escribir hoy.

GS4.1 Una interfaz por dentro: dos punteros

Antes de discutir cuándo usar una interfaz, hay que saber qué es. Un valor de tipo interfaz en Go no es un puntero a un objeto: son dos palabras del tamaño de un puntero, siempre.

// runtime/runtime2.go — simplificado

// Interfaz CON métodos (io.Reader, error, tu propia interfaz)
type iface struct {
    tab  *itab          // tipo dinámico + tabla de métodos
    data unsafe.Pointer // puntero al valor concreto
}

// Interfaz VACÍA: any / interface{}
type eface struct {
    _type *_type        // solo el tipo dinámico: no hay métodos que resolver
    data  unsafe.Pointer
}

// La itab es lo que hace posible el despacho dinámico
type itab struct {
    inter *interfacetype // qué interfaz
    _type *_type         // qué tipo concreto la satisface
    hash  uint32
    _     [4]byte
    fun   [1]uintptr     // punteros a los métodos (arreglo de largo variable)
}

Podés verlo sin creerme:

package main

import (
    "fmt"
    "unsafe"
)

type Forma interface{ Area() float64 }

type Cuadrado struct{ Lado float64 }

func (c Cuadrado) Area() float64 { return c.Lado * c.Lado }

func main() {
    var f Forma = Cuadrado{Lado: 3}

    fmt.Println(unsafe.Sizeof(f))   // 16 en 64 bits: DOS palabras, siempre

    // Leemos esas dos palabras crudas (solo para entender; nunca en producción)
    palabras := *(*[2]uintptr)(unsafe.Pointer(&f))
    fmt.Printf("itab=%#x  data=%#x\n", palabras[0], palabras[1])

    var vacia Forma
    fmt.Println(vacia == nil)       // true: LAS DOS palabras están en cero
}

De esa representación salen tres consecuencias que vas a ver el resto del módulo:

1. Una interfaz siempre pesa 16 bytes (en 64 bits), guarde lo que guarde. Un []any de un millón de elementos son 16 MB solo de cabeceras, más los valores apuntados.
2. Meter un valor que no es puntero en una interfaz suele mandarlo al heap. El campo data es un puntero: si guardás un Cuadrado, el compilador tiene que darle una dirección. Eso se llama boxing y lo detectás con el análisis de escape.
3. Llamar a un método por interfaz es una llamada indirecta. El destino sale de tab.fun[i] en tiempo de ejecución, así que el compilador normalmente no puede inlinear ni optimizar a través de esa llamada. A veces sí, cuando puede devirtualizar porque probó que el tipo dinámico es único.
# El análisis de escape te dice exactamente qué se fue al heap y por qué
go build -gcflags='-m -m' ./... 2>&1 | grep -i 'escapes to heap'

# Ejemplo de salida típica:
#   ./main.go:14:16: Cuadrado{...} escapes to heap:
#   ./main.go:14:16:   flow: {storage for ... } = &{storage for Cuadrado{...}}
#   ./main.go:14:16:   from Forma(Cuadrado{...}) (interface-converted)
El compilador tiene una optimización para el caso más común: si el valor que metés en la interfaz es una constante conocida en compilación o un entero chico, usa una copia de solo lectura ya existente en vez de asignar. Por eso fmt.Println(1) no asigna pero fmt.Println(x) con x variable sí. No confíes en la regla: medí con -benchmem.

GS4.2 La trampa: una interfaz con un puntero nil NO es nil

Esta es la trampa más famosa de Go, la que aparece en toda entrevista senior, y la razón por la que hay servicios en producción devolviendo error 500 cuando todo salió bien. Y sale directo de GS4.1.

📌 La regla exacta. Un valor de interfaz es nil si y solo si sus dos palabras están en cero: sin tipo dinámico y sin dato. Si le asignás un puntero nil de un tipo concreto, la palabra del tipo queda escrita. La interfaz tiene tipo. Y por lo tanto no es nil. 
package main

import "fmt"

type ErrorValidacion struct{ Campo string }

func (e *ErrorValidacion) Error() string {
    return "campo inválido: " + e.Campo
}

// ⚠️ El pecado original: devolver el TIPO CONCRETO en vez de error
func validar(entrada string) *ErrorValidacion {
    if entrada == "" {
        return &ErrorValidacion{Campo: "entrada"}
    }
    return nil // esto es un *ErrorValidacion nil
}

func procesar(entrada string) error {
    return validar(entrada) // ← acá se convierte a interfaz: tipo=*ErrorValidacion, dato=nil
}

func main() {
    err := procesar("todo bien")

    fmt.Println(err == nil) // false   ← el bug
    fmt.Println(err)        // <nil>    ← y encima IMPRIME como si fuera nil
    fmt.Printf("%T\n", err) // *main.ErrorValidacion

    if err != nil {
        fmt.Println("devolvemos 500 al usuario aunque no pasó nada malo")
    }
}
Por qué muerde específicamente en error. Porque if err != nil es el idiom más repetido del lenguaje: está en cada línea de cada archivo. Cuando ese chequeo miente, miente en todos lados a la vez. Y el síntoma es cruel: fmt.Println(err) imprime <nil>, porque fmt ve un puntero nil y lo formatea como tal. Vas a leer el log, ver "<nil>", y concluir que el error es nil. No lo es.

Si necesitás diagnosticar un caso así en código ajeno, la única forma es preguntar por reflexión:

import "reflect"

// Herramienta de DIAGNÓSTICO, no de producción.
func esNilDeVerdad(err error) bool {
    if err == nil {
        return true // interfaz nil de verdad: dos palabras en cero
    }
    v := reflect.ValueOf(err)
    switch v.Kind() {
    case reflect.Pointer, reflect.Map, reflect.Slice,
        reflect.Chan, reflect.Func, reflect.Interface:
        return v.IsNil() // tiene tipo, pero el dato adentro es nil
    }
    return false
}
No metas esa función en producción. Es una curita sobre un diseño roto, es lenta, y esconde el problema real en vez de arreglarlo. Si la ves en un code review, el hallazgo no es "esta función es fea": es "hay una función en algún lado devolviendo un tipo concreto de error".

El arreglo estructural es de una línea, y es la regla que tenés que internalizar:

// ✅ Devolvé SIEMPRE la interfaz error, nunca el tipo concreto
func validar(entrada string) error {
    if entrada == "" {
        return &ErrorValidacion{Campo: "entrada"}
    }
    return nil // nil de la INTERFAZ: las dos palabras en cero
}

Hay una variante más sutil, con retornos nombrados y defer, que engaña incluso a gente con años de Go:

// ⚠️ Mismo bug, disfrazado
func abrirYProcesar(ruta string) (err error) {
    var perr *ErrorValidacion // ← declarado como tipo concreto

    defer func() {
        err = perr // si perr es nil, err queda como interfaz NO nil
    }()

    // ... trabajo que puede o no asignar perr ...
    return nil
}

// ✅ La corrección: la variable local también es de tipo error
func abrirYProcesar2(ruta string) (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("pánico recuperado: %v", r)
        }
    }()
    return nil
}
Ponelo en el CI, no en tu memoria. staticcheck detecta varios de estos casos (comparaciones imposibles contra nil, retornos de tipo concreto que solo se usan como error). Un linter que corre en cada PR vale más que una regla que vos tenés que recordar a las siete de la tarde de un viernes.

GS4.3 Interfaces implícitas: definilas donde se consumen

En Java o C# un tipo declara qué interfaces implementa. En Go no: si tenés los métodos, satisfacés la interfaz, aunque no sepas que existe, aunque se haya escrito después que vos, aunque esté en un módulo que no importás. Eso no es una curiosidad sintáctica: cambia por completo quién debería declarar la interfaz.

La forma que traés de otros lenguajes es esta, y es la incorrecta:

// ❌ paquete storage: define la interfaz JUNTO a su implementación
package storage

type Store interface {
    Get(ctx context.Context, id string) ([]byte, error)
    Put(ctx context.Context, id string, b []byte) error
    Delete(ctx context.Context, id string) error
    List(ctx context.Context, prefijo string) ([]string, error)
    Stat(ctx context.Context, id string) (Info, error)
}

type S3Store struct{ /* ... */ }

func NuevoS3(bucket string) Store { /* ... */ } // devuelve la interfaz: peor todavía

¿Qué pasa cuando el paquete report solo necesita leer? Tiene que importar storage para nombrar el tipo del parámetro. Y su test tiene que implementar los cinco métodos, aunque use uno. Y el día que storage agregue un sexto método, el test de report deja de compilar sin que nadie haya tocado report.

// ✅ paquete report: declara la interfaz MÁS CHICA que necesita, donde la necesita
package report

import "context"

// Sin exportar. No hace falta que sea pública para ser útil.
type lector interface {
    Get(ctx context.Context, id string) ([]byte, error)
}

func Generar(ctx context.Context, l lector, ids []string) ([]byte, error) {
    var salida []byte
    for _, id := range ids {
        b, err := l.Get(ctx, id)
        if err != nil {
            return nil, fmt.Errorf("report: leyendo %q: %w", id, err)
        }
        salida = append(salida, b...)
    }
    return salida, nil
}

Ahora storage puede exportar el struct concreto y no declarar ninguna interfaz. report no importa storage para nada: recibe cualquier cosa que sepa hacer Get. Y el fake del test es esto:

type lectorFalso map[string][]byte

func (l lectorFalso) Get(_ context.Context, id string) ([]byte, error) {
    b, ok := l[id]
    if !ok {
        return nil, fmt.Errorf("no encontrado: %s", id)
    }
    return b, nil
}

func TestGenerar(t *testing.T) {
    l := lectorFalso{"a": []byte("hola "), "b": []byte("mundo")}

    got, err := report.Generar(context.Background(), l, []string{"a", "b"})
    if err != nil {
        t.Fatal(err)
    }
    if string(got) != "hola mundo" {
        t.Fatalf("got %q", got)
    }
}
📌 Aceptá interfaces, devolvé structs. El productor exporta el tipo concreto (func NuevoS3(bucket string) *S3Store). El consumidor declara la interfaz que necesita. Así el productor puede agregar métodos sin romper a nadie —agregarle un método a un struct nunca es breaking— y el consumidor puede pedir exactamente lo que usa. Si el productor exporta la interfaz, agregarle un método rompe a todos los que la implementaron.
La analogía del enchufe. El fabricante de la lámpara no define qué es un tomacorriente; define un enchufe que encaja. La forma la define la pared —el que consume—. Si cada fabricante definiera su propio estándar de pared, tendrías que importar la lámpara para poder enchufarla.

GS4.4 Interfaces chicas: por qué io.Reader ganó

Las dos interfaces más exitosas de la historia de Go tienen un método cada una:

package io

type Reader interface {
    Read(p []byte) (n int, err error)
}

type Writer interface {
    Write(p []byte) (n int, err error)
}

Un método. Con eso se conectan cosas que no se conocen entre sí: un archivo, una conexión TCP, un buffer en memoria, un descompresor gzip, un lector limitado, un hash, el cuerpo de una respuesta HTTP, el stdout de un proceso hijo. Todo eso es intercambiable porque el contrato es diminuto.

// Todo esto compone porque el contrato es de UN método
r := io.LimitReader(resp.Body, 10<<20)     // máximo 10 MB
gz, _ := gzip.NewReader(r)                 // descomprimir al vuelo
h := sha256.New()                          // hash.Hash es un io.Writer
tee := io.TeeReader(gz, h)                 // leer y hashear en un solo paso

n, err := io.Copy(destino, tee)            // y todo esto sin buffers intermedios

Ahora imaginá esa misma cadena si io.Reader tuviera doce métodos. Cada eslabón tendría que implementar los doce. LimitReader no existiría: nadie escribe un adaptador de doce métodos para limitar bytes.

Cuando necesitás más de un método, la forma idiomática no es declarar una interfaz gorda: es componer las chicas.

package io

type ReadWriter interface {
    Reader
    Writer
}

type ReadWriteCloser interface {
    Reader
    Writer
    Closer
}
Agregarle un método a una interfaz publicada rompe a TODOS los que la implementaron, incluso a gente que no conocés, en repos que no podés ver. Por eso io.Reader no cambió en quince años. Comparalo con agregar un campo a un struct: eso no es breaking (salvo que alguien use literales sin nombres de campo, y ya vamos a ver cómo prevenirlo). Los structs se pueden extender; las interfaces publicadas, prácticamente no.

Si querés publicar una interfaz y además conservar la libertad de agregarle métodos, existe el truco de la interfaz sellada: un método sin exportar que nadie fuera de tu paquete puede implementar.

package ast

// Nadie fuera de este paquete puede implementar Nodo, porque no puede
// declarar el método nodo(). Así podemos agregarle métodos a Nodo
// sin romper a ningún usuario externo.
type Nodo interface {
    Pos() int
    Fin() int
    nodo() // no exportado: sella la interfaz
}

type Literal struct{ inicio, fin int }

func (l *Literal) Pos() int { return l.inicio }
func (l *Literal) Fin() int { return l.fin }
func (l *Literal) nodo()    {}
Además de proteger la evolución, sellar una interfaz te da lo más parecido a un tipo suma que hay en Go: el conjunto de implementaciones es cerrado y conocido, así que un switch de tipos sobre Nodo es exhaustivo por construcción. El compilador no te lo verifica —eso Go no lo tiene— pero al menos nadie puede agregar un caso desde afuera.

GS4.5 Cuándo NO usar una interfaz

Este patrón está en el 80% de los repos de Go que vas a tocar en tu vida profesional:

// ❌ La abstracción prematura, en su forma más pura
package usuario

type Servicio interface {
    Crear(ctx context.Context, u Usuario) (string, error)
    Obtener(ctx context.Context, id string) (Usuario, error)
    Actualizar(ctx context.Context, u Usuario) error
    Borrar(ctx context.Context, id string) error
}

type servicio struct{ db *sql.DB } // ← única implementación, para siempre

func NuevoServicio(db *sql.DB) Servicio { return &servicio{db: db} }

Los síntomas son inconfundibles: la interfaz y la implementación viven en el mismo archivo, tienen el mismo nombre (uno con mayúscula, otro sin), son 1 a 1, y el constructor devuelve la interfaz. Se hizo "para poder testear" y "por si mañana cambiamos de base".

Qué se paga por eso, concretamente:

1. Se pierde la documentación. godoc del método muestra la firma de la interfaz, sin cuerpo, sin comportamiento. Para entender qué hace Crear tenés que buscar a mano quién la implementa.
2. Se pierde el "ir a la definición". Tu IDE te lleva a la interfaz, no al código. En una cadena de tres capas hechas así, leer un flujo se vuelve un juego de saltos.
3. Se pierde despacho estático e inlining. Cada llamada pasa por la itab. En el 99% de los casos no importa; en el 1% que importa, ya está enterrado bajo diez capas.
4. Hay que mantener dos cosas sincronizadas. Cada método nuevo se escribe dos veces. Cada firma que cambia, dos veces.
5. El test termina probando el mock. Se genera un mock desde la interfaz, se programa "cuando te llamen con X devolvé Y", y se verifica que se llamó con X. Eso no prueba el sistema: prueba que escribiste dos veces la misma expectativa.
Un mock no cuenta como segunda implementación. "Tiene dos implementaciones: la real y la de tests" es el argumento circular más común de Go. Si la única razón para que exista la interfaz es el test, primero preguntate si no hay una costura más barata: una función como campo del struct, un httptest.NewServer, un t.TempDir(), una base real en un contenedor.

Cuándo una interfaz sí se justifica, sin discusión:

  • Ya existen dos o más implementaciones reales —no una real y un mock—: S3 y disco local, Postgres y SQLite, un transporte HTTP y uno gRPC.
  • Es un borde real del sistema que en tests reemplazás por necesidad: el reloj, la red, el generador de aleatorios, el filesystem.
  • Es un punto de extensión publicado: querés que los usuarios de tu librería enchufen su propia implementación (http.RoundTripper, slog.Handler, sort.Interface).
  • Necesitás romper un ciclo de importación entre dos paquetes que se necesitan mutuamente.
📌 La regla operativa. Escribí el struct concreto. Usalo. Cuando aparezca la segunda implementación real, extraé la interfaz —y extraela en el paquete que la consume, con los métodos que ese paquete usa—. Refactorizar un tipo concreto a una interfaz es un cambio mecánico de quince minutos. Desarmar tres capas de interfaces de una sola implementación es un proyecto de dos semanas.

GS4.6 Genéricos: qué problema resolvieron de verdad

Antes de 1.18 tenías tres formas de escribir código reutilizable sobre tipos: copiar y pegar, interface{} con asserts, o generar código con go generate. Los genéricos mataron la segunda y la tercera para estructuras de datos y utilidades. Eso es todo lo que resolvieron, y es muchísimo.

// La versión pre-1.18: dinámica, verbosa, y rota en runtime
func Min(a, b interface{}) interface{} {
    switch x := a.(type) {
    case int:
        y, ok := b.(int)
        if !ok {
            panic("tipos distintos")
        }
        if x < y {
            return x
        }
        return y
    case float64:
        y, ok := b.(float64)
        if !ok {
            panic("tipos distintos")
        }
        if x < y {
            return x
        }
        return y
    }
    panic("tipo no soportado") // el error llega a las 3 AM, no en compilación
}

// Y en cada uso, el assert de vuelta:
m := Min(3, 7).(int)
// La versión 1.18+: una línea de firma, cero asserts, error en compilación
import "cmp"

func Min[T cmp.Ordered](a, b T) T {
    if a < b {
        return a
    }
    return b
}

m := Min(3, 7)        // int, inferido
s := Min("ada", "go") // string, inferido
// Min(3, "go")       // ← no compila: "default type string does not match int"

Ahora la parte que casi nadie te cuenta: qué NO resolvieron.

La primera es la que más duele en la práctica, y conviene verla escrita:

type Conjunto[T comparable] struct{ m map[T]struct{} }

// ❌ NO COMPILA: "method must have no type parameters"
func (s *Conjunto[T]) Mapear[U comparable](f func(T) U) *Conjunto[U] { /* ... */ }

// ✅ La salida obligada: una función a nivel de paquete
func Mapear[T, U comparable](s *Conjunto[T], f func(T) U) *Conjunto[U] {
    salida := NuevoConjunto[U]()
    for v := range s.m {
        salida.Agregar(f(v))
    }
    return salida
}

// Y por eso se escribe así, y no encadenado:
nombres := Mapear(usuarios, func(u Usuario) string { return u.Nombre })
Esta restricción no es un olvido: permitir parámetros de tipo en métodos rompería la implementación actual de interfaces, porque la itab tendría que contener un número infinito de instanciaciones posibles del método. Por eso slices.Map no existe como método y toda la stdlib genérica —slices, maps, cmp— son funciones de paquete.

GS4.7 Constraints, comparable y el sombrerito ~

Un constraint es una interfaz usada de otra manera: en vez de describir un conjunto de métodos, describe un conjunto de tipos.

// Un conjunto de tipos, expresado con una unión
type Numero interface {
    ~int | ~int8 | ~int16 | ~int32 | ~int64 |
        ~uint | ~uint8 | ~uint16 | ~uint32 | ~uint64 |
        ~float32 | ~float64
}

func Sumar[T Numero](xs []T) T {
    var total T // el valor cero del parámetro de tipo
    for _, x := range xs {
        total += x
    }
    return total
}

Ese ~ es el detalle que separa a quien copió un constraint de Internet de quien entendió el modelo. int significa "exactamente el tipo int". ~int significa "cualquier tipo cuyo tipo subyacente sea int".

type Celsius float64      // tipo propio, subyacente float64
type IDUsuario int64      // tipo propio, subyacente int64

func main() {
    temps := []Celsius{20.5, 22.0, 19.5}
    fmt.Println(Sumar(temps)) // 62 — funciona SOLO gracias a ~float64

    // Si el constraint dijera "float64" sin ~, el compilador tiraría:
    //   Celsius does not satisfy Numero (possibly missing ~ for float64)
}
📌 Si tu constraint enumera tipos, casi siempre querés ~. Sin el sombrerito, tu función genérica deja afuera a todos los tipos con nombre propio: time.Duration, os.FileMode, y cada type MiID int que tenga tu dominio. Y esos son justamente los tipos que más querés que funcionen.

La biblioteca estándar ya te da los constraints que necesitás el 90% del tiempo:

import "cmp"

// cmp.Ordered — todo lo que soporta < <= > >= (enteros, floats, strings)
func Maximo[T cmp.Ordered](xs []T) (T, bool) {
    if len(xs) == 0 {
        var cero T
        return cero, false
    }
    m := xs[0]
    for _, x := range xs[1:] {
        if x > m {
            m = x
        }
    }
    return m, true
}

// comparable — todo lo que soporta == y != (o sea, todo lo que puede ser clave de map)
func Indice[T comparable](xs []T, buscado T) int {
    for i, x := range xs {
        if x == buscado {
            return i
        }
    }
    return -1
}
Ojo con comparable. Desde Go 1.20 lo satisfacen también los tipos que son comparables "en sentido amplio", como any. Eso significa que Indice[any] compila, pero si adentro de esos any hay un slice o un map, el == entra en pánico en runtime. El constraint te garantiza que el operador existe, no que sea seguro con el contenido que le metas.

Un constraint también puede mezclar métodos con el conjunto de tipos, y ahí aparece la regla que confunde a todos:

// ✅ Constraint con método: perfectamente usable, y además usable como tipo
type Nombrable interface {
    Nombre() string
}

// ✅ Constraint mezclando conjunto de tipos y método
type ClaveTexto interface {
    ~string
    // (los tipos del conjunto deben tener también los métodos declarados)
}

// ⚠️ Una interfaz con UNIÓN de tipos solo sirve como constraint
type Numero interface{ ~int | ~float64 }

var n Numero // ❌ no compila:
             // "cannot use type Numero outside a type constraint:
             //  interface contains type constraints"

Inferencia: hasta dónde llega

Go infiere los argumentos de tipo a partir de los argumentos de la función. Nunca a partir del tipo de retorno esperado.

// ✅ Inferido: T sale de xs
total := Sumar([]int{1, 2, 3})

// ✅ Inferido en cadena: T sale de xs, U sale del tipo de retorno de f
nombres := Mapear(usuarios, func(u Usuario) string { return u.Nombre })

// ❌ NO se puede inferir: no hay ningún argumento del que sacar T
// c := NuevoConjunto()
// ✅ Hay que decirlo
c := NuevoConjunto[string]()

// ❌ Tampoco desde la variable de destino: Go no infiere "hacia atrás"
// var s Conjunto[int] = NuevoConjunto()

// ⚠️ Caso clásico que sorprende: T se infiere del PRIMER argumento
Min(3, 7)      // T = int
Min(3, 7.5)    // T = float64 (3 es constante sin tipo, se adapta)
// Min(x, 7.5) con x int declarado → error: no hay un T que sirva
Cuando una función genérica no te infiere, no pelees: escribí el argumento de tipo. NuevoConjunto[string]() es más legible que tres capas de trucos para que la inferencia funcione. Y si tu API obliga al usuario a escribir los tipos siempre, es señal de que hay un parámetro de tipo que sobra.

GS4.8 Genéricos vs interfaces: la regla práctica

Los dos mecanismos parametrizan código. Pero parametrizan cosas distintas, y confundirlos es la fuente principal de código genérico malo.

💡 Los genéricos parametrizan DATOS. Las interfaces parametrizan COMPORTAMIENTO. Un genérico dice "esta estructura funciona con cualquier tipo de elemento, y lo resuelvo en compilación". Una interfaz dice "este agujero lo llena cualquiera que sepa hacer estas cosas, y lo resuelvo en ejecución". Si tu pregunta es "¿qué guarda?", es un genérico. Si es "¿quién lo hace?", es una interfaz.

GS4.9 Genéricos auto-referenciales — la novedad de Go 1.26

Hay un patrón que en otros lenguajes tiene nombre propio —CRTP en C++, self type en Scala— y que en Go venía chocando contra una restricción del compilador: un tipo genérico no podía nombrarse a sí mismo dentro de su propia lista de parámetros de tipo. Go 1.26 levantó esa restricción.

El caso de uso es el de "un tipo que se restringe a sí mismo": quiero exigir que un método devuelva el tipo concreto, no la interfaz.

// ✅ Go 1.26: Combinable aparece en SU PROPIA lista de parámetros de tipo
type Combinable[T Combinable[T]] interface {
    Combinar(T) T
    Cero() T
}

// Ahora un tipo concreto se ata a sí mismo, y el compilador lo verifica
type Total float64

func (t Total) Combinar(o Total) Total { return t + o }
func (t Total) Cero() Total            { return 0 }

func Plegar[T Combinable[T]](xs []T) T {
    var acc T
    if len(xs) == 0 {
        return acc
    }
    acc = xs[0].Cero()
    for _, x := range xs {
        acc = acc.Combinar(x)
    }
    return acc
}

Lo que gana es preciso: Combinar devuelve Total, no Combinable. No hay conversión, no hay assert, no hay interfaz en el medio, y el compilador te impide que Total.Combinar devuelva otra cosa por error.

Hasta 1.25 el rodeo era alguno de estos tres, todos peores:

// Rodeo A — parámetro de tipo extra, y el usuario se repite
type Combinable2[T any] interface {
    Combinar(T) T
}
// El llamador tiene que escribir el tipo dos veces y nada garantiza que
// coincidan con el receptor:
func Plegar2[T Combinable2[T]](xs []T) T { /* ... */ }

// Rodeo B — devolver la interfaz y perder el tipo concreto
type Combinable3 interface {
    Combinar(Combinable3) Combinable3 // ← cada uso necesita un type assert
}

// Rodeo C — any y verificar en runtime
func Plegar3(xs []any) any { /* asserts y pánicos */ }

Y la misma relajación aplica a structs recursivos que antes había que partir en dos declaraciones:

// ✅ Go 1.26: un nodo que exige que sus hijos sean del mismo tipo que él
type Nodo[T Nodo[T]] struct {
    Hijos []T
}
Verificá la versión antes de escribir esto. En Go 1.25 y anteriores, estas declaraciones son un error de compilación (invalid recursive type / ciclo de instanciación), no una advertencia. Si tu módulo declara go 1.24 en el go.mod, no vas a poder usarlo aunque tengas el toolchain nuevo instalado: la versión del lenguaje la fija el go.mod, no el compilador que tenés en la máquina.

Y de paso: new con expresión

La otra novedad de 1.26 que toca directamente el diseño de API: new ahora acepta una expresión, no solo un tipo.

// Antes: el helper genérico más copiado de la historia de Go

    Timeout: ptr(5 * time.Second),
    Reintentos: ptr(3),

    Reintentos: new(3),               // *int

Esto importa más de lo que parece para el diseño de structs de configuración. La única forma de distinguir "el usuario no configuró este campo" de "el usuario lo puso en cero" es usar un puntero, y hasta ahora eso te obligaba a arrastrar un helper en cada paquete. Ahora un Opciones con campos *int y *time.Duration es cómodo de construir, y el valor cero (nil) significa inequívocamente "usá el default".

GS4.10 El costo de los genéricos: GC shape stenciling

Go no implementó los genéricos como C++ o Rust (monomorfización total: una copia de código por cada tipo) ni como Java (borrado total: todo se convierte en Object). Eligió un punto intermedio llamado GC shape stenciling, y todos sus costos y beneficios salen de ahí.

💡 Cómo funciona. El compilador genera una copia del código por cada "GC shape" distinta, no por cada tipo. La shape es cómo ve el recolector de basura la memoria de ese tipo. Todos los tipos puntero comparten una sola shape, así que Primero[*Usuario] y Primero[*Pedido] ejecutan el mismo código máquina. Para saber el tipo real y encontrar los métodos, ese código recibe un argumento oculto: un diccionario. 
func Primero[T any](xs []T) T { return xs[0] }

// UNA sola copia de código, compartida (shape = puntero):
//   Primero[*Usuario]  Primero[*Pedido]  Primero[*os.File]  Primero[error]
//   → cada instanciación pasa su propio diccionario

// UNA copia de código CADA UNA (shapes distintas):
//   Primero[int]         → shape: 8 bytes sin punteros
//   Primero[float64]     → shape: 8 bytes sin punteros (comparte con int)
//   Primero[string]      → shape: puntero + largo
//   Primero[struct{a, b int}] → shape propia
//   Primero[[3]byte]     → shape propia

De ahí salen tres efectos medibles:

1. El binario crece —pero menos de lo que temerías—, porque las instanciaciones sobre punteros no duplican código. Crece con la variedad de formas de memoria, no con la cantidad de tipos.
2. Llamar a un método de un parámetro de tipo va por el diccionario. Es una llamada indirecta, muy parecida en costo a una llamada por interfaz, y no se inlinea. Acá está el mito que hay que enterrar: los genéricos no hacen que llamar métodos sea más rápido.
3. Donde sí ganás velocidad es eliminando el boxing. Un []int genérico guarda enteros contiguos; un []interface{} guarda cabeceras de 16 bytes apuntando a enteros en el heap. La diferencia no es el despacho: es la memoria y la caché.
// El costo REAL de interface{}: una asignación por valor
var xs []interface{}
for i := 0; i < 1_000_000; i++ {
    xs = append(xs, i) // cada int se copia al heap (salvo los chiquitos cacheados)
}
// ~16 MB de cabeceras + un objeto por entero, disperso en el heap

// La versión genérica (o simplemente tipada): cero asignaciones extra
var ys []int
for i := 0; i < 1_000_000; i++ {
    ys = append(ys, i)
}
// 8 MB contiguos, amigables con la caché de la CPU

🧑‍🎓 Worked Example — una librería de caché reutilizable

Necesitás un caché en memoria con TTL y límite de entradas. Lo van a usar tres servicios distintos con tipos distintos. Y el vencimiento tiene que poder testearse sin dormir el test.

Paso 1 — La versión con interface{}

package cache

import (
    "sync"
    "time"
)

type entrada struct {
    valor interface{}
    vence time.Time
}

type Cache struct {
    mu    sync.Mutex
    datos map[string]entrada
    ttl   time.Duration
}

func Nueva(ttl time.Duration) *Cache {
    return &Cache{datos: make(map[string]entrada), ttl: ttl}
}

func (c *Cache) Set(k string, v interface{}) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.datos[k] = entrada{valor: v, vence: time.Now().Add(c.ttl)}
}

func (c *Cache) Get(k string) (interface{}, bool) {
    c.mu.Lock()
    defer c.mu.Unlock()
    e, ok := c.datos[k]
    if !ok || time.Now().After(e.vence) {
        return nil, false
    }
    return e.valor, true
}

Funciona. Y en cada lugar donde se usa, aparece esto:

c := cache.Nueva(time.Minute)
c.Set("u:1", Usuario{Nombre: "Ada"})

v, ok := c.Get("u:1")
if !ok {
    // buscar en la base
}
u, ok := v.(Usuario) // ← el assert, en CADA uso, para siempre
if !ok {
    // ¿y ahora qué? Esto no es un error de negocio: es un bug.
    // Y no hay nada que impida que alguien haya guardado un Pedido acá.
}
Los cuatro problemas, ordenados por qué tan tarde te enterás: (1) el assert se repite en cada llamada; (2) nada impide guardar un Pedido bajo una clave de usuario; (3) cada Set con un valor no-puntero hace boxing y asigna en el heap; (4) si alguien escribe v.(Usuario) sin el , ok, el pánico llega en producción, un martes.

Paso 3 — La costura para el reloj

El TTL depende del tiempo, y un test que hace time.Sleep(2 * time.Minute) no es un test: es un castigo. Necesitás poder mover el reloj. La pregunta de diseño es: ¿interfaz o función?

// Opción A — una interfaz de UN método (punto de extensión público)
type Reloj interface {
    Ahora() time.Time
}

// Opción B — un campo de tipo función (costura privada, sin interfaz)
type Cache[K comparable, V any] struct {
    // ...
    ahora func() time.Time // por defecto: time.Now
}
📌 El criterio. ¿Querés que los usuarios de la librería enchufen su propio reloj —por ejemplo, uno sincronizado con NTP o uno de un simulador—? Interfaz pública. ¿Solo lo necesitás para tus tests? Campo de función, sin exportar, configurable por opción. Acá es lo segundo: una interfaz de un método que solo usás vos es una interfaz que sobra. 
// El "reloj falso" del test: doce líneas, sin mocks generados, sin librerías
type relojFalso struct{ t time.Time }

func (r *relojFalso) Ahora() time.Time       { return r.t }
func (r *relojFalso) Avanzar(d time.Duration) { r.t = r.t.Add(d) }
func TestVencimiento(t *testing.T) {
    reloj := &relojFalso{t: time.Unix(0, 0)}
    c := cache.Nueva[string, int](
        cache.ConTTL(time.Minute),
        cache.ConReloj(reloj.Ahora), // pasamos el MÉTODO como func() time.Time
    )

    c.Set("a", 1)
    if _, ok := c.Get("a"); !ok {
        t.Fatal("debería estar presente recién puesto")
    }

    reloj.Avanzar(59 * time.Second)
    if _, ok := c.Get("a"); !ok {
        t.Fatal("no debería vencer antes del TTL")
    }

    reloj.Avanzar(2 * time.Second)
    if _, ok := c.Get("a"); ok {
        t.Fatal("debería haber vencido")
    }
}
// Corre en microsegundos. Sin sleeps. Sin flakiness. Y prueba los BORDES,
// que con time.Sleep serían imposibles de testear con precisión.

Paso 4 — Opciones funcionales, y la fricción con los genéricos

Ya son tres parámetros (TTL, reloj, máximo) y van a ser cinco. Opciones funcionales. Pero acá aparece un problema real que casi nadie menciona:

// ⚠️ El intento ingenuo: opciones genéricas
type Opcion[K comparable, V any] func(*Cache[K, V])

func ConTTL[K comparable, V any](d time.Duration) Opcion[K, V] {
    return func(c *Cache[K, V]) { c.ttl = d }
}

// El uso queda insoportable: la inferencia NO ayuda, porque K y V solo
// aparecen en el tipo de RETORNO de la opción.
c := cache.Nueva[string, Usuario](
    cache.ConTTL[string, Usuario](time.Minute),   // ← repetir los tipos
    cache.ConMaximo[string, Usuario](500),        // ← otra vez
)
// ✅ La salida: la config NO es genérica, porque no depende de K ni de V
type config struct {
    ttl   time.Duration
    max   int
    ahora func() time.Time
}

type Opcion func(*config) // ← sin parámetros de tipo

func ConTTL(d time.Duration) Opcion      { return func(c *config) { c.ttl = d } }
func ConMaximo(n int) Opcion             { return func(c *config) { c.max = n } }
func ConReloj(f func() time.Time) Opcion { return func(c *config) { c.ahora = f } }

func Nueva[K comparable, V any](opts ...Opcion) *Cache[K, V] {
    cfg := config{ttl: 5 * time.Minute, max: 1024, ahora: time.Now}
    for _, o := range opts {
        o(&cfg)
    }
    return &Cache[K, V]{
        datos: make(map[K]entrada[V], cfg.max),
        ttl:   cfg.ttl,
        max:   cfg.max,
        ahora: cfg.ahora,
    }
}

// Y ahora el uso vuelve a ser humano:
c := cache.Nueva[string, Usuario](cache.ConTTL(time.Minute), cache.ConMaximo(500))
📌 Si tus opciones no dependen de los parámetros de tipo, no las hagas genéricas. Separá la configuración (no genérica) del contenedor (genérico). Esto es lo que hacen las librerías reales, y es la lección más transferible de todo el ejemplo: los parámetros de tipo se propagan como un virus si los dejás. Cortalos en el borde más chico posible.

Checkpoint — ¿lo tenés claro?

Tu función devuelve error, el log dice <nil>, y sin embargo err != nil es true. ¿Qué pasó y cómo lo arreglás?

Un valor de interfaz son dos palabras: tipo dinámico y dato. Es nil solo si las dos están en cero. En algún lado hay una función declarada como func f() *MiError —tipo concreto— cuyo return nil se convierte a error: la palabra del tipo queda escrita con *MiError y la del dato en cero. La interfaz tiene tipo, así que no es nil. Y fmt imprime <nil> porque formatea el puntero, que sí es nil — de ahí la confusión. El arreglo no es comparar con reflexión: es cambiar la firma a func f() error, así el return nil produce una interfaz genuinamente vacía. La misma trampa aparece con retornos nombrados asignados desde una variable de tipo concreto dentro de un defer.

Tenés que escribir código reutilizable. ¿Cómo decidís entre un genérico y una interfaz?

Preguntate qué estás parametrizando. Si es el dato —"esta estructura guarda cualquier tipo de elemento"— es un genérico: contenedores, utilidades de colecciones, funciones tipo Map/Filter/Min. Se resuelve en compilación, no hay boxing, y el tipo se preserva de punta a punta. Si es el comportamiento —"esto lo puede hacer cualquiera que sepa hacer X"— es una interfaz: storage, transporte, reloj, puntos de extensión para usuarios. Se resuelve en ejecución, que es justamente lo que necesitás cuando la implementación depende de la config o del entorno. La señal de alarma: un parámetro de tipo que aparece una sola vez, en la posición de un parámetro, y nunca en el retorno ni en el cuerpo — ese quería ser una interfaz, y hacerlo genérico solo agrega instanciaciones al binario. Y ojo con el mito: los genéricos no aceleran las llamadas a métodos —el diccionario del GC shape stenciling las deja tan indirectas como una interfaz—; aceleran cuando eliminan el boxing de interface{}.

¿Por qué agregar un método a una interfaz publicada rompe a tus usuarios, pero agregar un campo a un struct casi nunca?

Porque las interfaces en Go se satisfacen implícitamente: cualquiera pudo haber escrito un tipo que la implementa sin importar tu paquete ni avisarte. Al agregarle un método, todos esos tipos dejan de satisfacerla y su código deja de compilar. Con un struct pasa lo contrario: nadie "implementa" tu struct, solo lo usa; agregarle un campo o un método no invalida nada que ya funcionaba. La única excepción son los literales sin nombres de campo (T{1, 2}), que dependen del orden y la cantidad exacta — y eso se previene poniéndole al struct un campo sin exportar, como _ struct{}, que obliga a construirlo con nombres. De ahí sale la regla "aceptá interfaces, devolvé structs": el struct te deja crecer, la interfaz publicada te congela. Y si necesitás publicar una interfaz conservando el derecho a extenderla, sellala con un método sin exportar.

Resumen ejecutivo

  • Una interfaz son dos palabras: tipo dinámico y dato. Es nil solo si ambas están en cero — de ahí sale la trampa del puntero nil que no es nil, y por eso nunca declares una función que devuelva un tipo concreto de error.
  • Las interfaces son implícitas: declaralas donde se consumen, con los métodos que ese consumidor usa. Aceptá interfaces, devolvé structs.
  • Interfaces chicas: io.Reader ganó con un método. Doce métodos es una clase abstracta disfrazada. Componé con embedding, y sellá con un método sin exportar si necesitás poder extenderla.
  • La interfaz de una sola implementación, creada "para testear", cuesta documentación, navegabilidad, despacho estático y mantenimiento. Un mock no es una segunda implementación. Extraé la interfaz cuando aparezca la segunda implementación real.
  • Los genéricos parametrizan datos; las interfaces parametrizan comportamiento. No hay parámetros de tipo en métodos, ni covarianza, ni sobrecarga de operadores.
  • En los constraints, ~ significa "tipo subyacente" y casi siempre lo querés. comparable garantiza que == existe, no que no vaya a entrar en pánico con un any adentro. La inferencia sale de los argumentos, nunca del retorno.
  • Go 1.26: un tipo genérico puede nombrarse a sí mismo en su lista de parámetros de tipo (destraba el patrón self type y los recursivos); new acepta una expresión (new(42)); y errors.AsType[T]() reemplaza a errors.As con verificación en compilación.
  • GC shape stenciling: una copia de código por forma de memoria, no por tipo, más un diccionario. Los genéricos dan seguridad de tipos, no velocidad de despacho; la velocidad viene de eliminar el boxing.
  • %w hace público el error que envolvés; %v no. Centinela para "qué pasó", error tipado para "con qué datos". Nunca compares err.Error() como string.
  • Agregar un método a una interfaz publicada rompe; agregar un campo a un struct no (poné _ struct{} y deja de romper del todo). Verificá con gorelease en el CI, no de memoria.
  • any + reflexión: solo en el borde dinámico real (serialización, filas de base, plugins). Si tenés que reflexionar, hacelo una vez al inicializar y cacheá el resultado.

🧠 Autoevaluación

1. Una función devuelve error, el log imprime <nil> y sin embargo err != nil da true. ¿Cuál es la causa?

Un valor de interfaz son dos palabras (tipo dinámico + dato) y es nil solo si ambas están en cero. Devolver *MiError y convertirlo a error escribe la palabra del tipo, así que la interfaz no es nil aunque el puntero sí lo sea. fmt imprime <nil> porque formatea el puntero. El arreglo es declarar la firma como error, no comparar con reflexión.

2. Sobre el costo de los genéricos en Go, ¿cuál afirmación es correcta?

Go eligió un punto intermedio. Las instanciaciones sobre tipos puntero comparten una sola copia de código y reciben un diccionario oculto con el tipo real y los métodos; los tipos con forma de memoria propia (int, structs de escalares) generan copias separadas. Por eso llamar a un método de un parámetro de tipo va por el diccionario y cuesta parecido a una llamada por interfaz: los genéricos dan seguridad de tipos, y velocidad solo cuando eliminan asignaciones de interface{}.

3. Estás diseñando la API pública de un módulo. ¿Cuál de estos cambios NO rompe a tus usuarios?

Nadie "implementa" tu struct: solo lo usa, así que agregarle métodos (o campos, si el struct tiene un campo sin exportar que impide literales posicionales) no invalida nada. En cambio, las interfaces se satisfacen implícitamente: al agregar un método, todos los tipos externos que la implementaban dejan de compilar — por eso io.Reader no cambió nunca. Y agregar un parámetro de tipo rompe cada instanciación existente. De ahí la regla: aceptá interfaces, devolvé structs.

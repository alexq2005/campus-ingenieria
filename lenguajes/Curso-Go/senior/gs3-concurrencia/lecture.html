GS3 — Concurrencia avanzada: patrones y el memory model

GS3.0 Por qué este módulo

El curso base te enseñó a lanzar una goroutine, a pasar valores por un canal y a esperar con un WaitGroup. Con eso escribís programas concurrentes que funcionan. Este módulo es sobre la otra categoría: los programas concurrentes que funcionan 999 veces y fallan la número mil, en producción, un martes a las 3 de la mañana, y que cuando los corrés localmente para reproducir el problema andan perfecto.

💡 La tesis del módulo. En código concurrente, “lo probé y anda” no es evidencia de nada. Un programa con una carrera de datos puede dar el resultado correcto durante meses porque el planificador nunca eligió el orden malo. La única forma de tener confianza es razonar sobre qué le garantiza el lenguaje (el memory model), instrumentar lo que la máquina sí puede verificar (-race, goleak, timeouts en los tests) y usar patrones donde el caso patológico sea imposible por construcción, no improbable.

Vamos a usar Go 1.26 como referencia. Es una versión importante para este tema porque varias cosas que durante años se enseñaron como “trampas eternas” dejaron de serlo: la captura de la variable del loop se arregló en 1.22, los timers dejaron de filtrar memoria en 1.23, y WaitGroup ganó un método Go en 1.25 que elimina de raíz dos de los errores más comunes. Vas a tener que saber igual por qué existían: te vas a encontrar con repos cuyo go.mod declara una versión vieja y compilan con la semántica vieja aunque los compiles con el toolchain nuevo.

Este módulo asume GS1 (runtime y scheduler): que sabés qué es un M, un P y una G, y por qué una goroutine bloqueada no consume CPU pero sí memoria. Si necesitás el modelo mental de cómo el scheduler decide qué corre, volvé un momento a GS1.

GS3.1 El memory model: qué te garantiza Go y qué no

El memory model de Go es un documento corto y aburrido que define exactamente una cosa: bajo qué condiciones una lectura en una goroutine tiene garantizado ver el valor escrito por otra goroutine. Fuera de esas condiciones, el compilador y la CPU tienen permiso para reordenar, cachear en un registro, o directamente eliminar tu código.

Empecemos con el programa que parece correcto y no lo es. Este es el error de concurrencia más común del mundo, en todos los lenguajes:

package main

import "fmt"

var mensaje string
var listo bool

func main() {
	go func() {
		mensaje = "hola"   // (1)
		listo = true       // (2)
	}()

	for !listo {           // (3) espera activa
	}
	fmt.Println(mensaje)   // (4) ¿imprime "hola"?
}

Las tres cosas que pueden salir mal, y ninguna es un bug del runtime:

  1. El loop puede no terminar nunca. Nada en (3) sincroniza con nada. El compilador tiene permiso para leer listo una sola vez, guardarlo en un registro y compilar el for como un bucle infinito. Es una optimización legal: dentro de esa goroutine, nadie escribe listo.
  2. Puede imprimir la cadena vacía. Aunque (3) observe listo == true, no hay ninguna garantía de que la escritura de mensaje sea visible. El compilador puede reordenar (1) y (2) porque son independientes entre sí, y la CPU también.
  3. Puede funcionar perfecto un millón de veces. En x86, con go build sin optimizaciones agresivas, es muy probable que ande. Y ahí es donde te clava: en el servidor ARM de producción, con otra versión del compilador, deja de andar.
El error de razonamiento fatal es este: “lo corrí mil veces y siempre dio bien, entonces no hay carrera”. En concurrencia, la ausencia de síntoma no es ausencia de bug. El único argumento válido es “existe una relación happens-before entre la escritura y la lectura”. Si no la podés nombrar, no existe.

Happens-before, en criollo

La relación happens-before es un orden parcial entre eventos. Si el evento A happens-before el evento B, entonces todo lo que A escribió en memoria es visible para B. La palabra clave es parcial: dos eventos en goroutines distintas, sin una operación de sincronización entre medio, no están ordenados, y el lenguaje no promete nada sobre ellos.

Go define un puñado de operaciones que crean esas aristas. Esta tabla es, literalmente, el conjunto completo de herramientas que tenés:

OperaciónGarantía
Dentro de una goroutineEl orden del programa se respeta desde el punto de vista de esa goroutine. El compilador puede reordenar mientras nadie más mire.
go f()Todo lo que hiciste antes del go es visible dentro de f.
Envío por canalEl envío happens-before que la recepción correspondiente termine.
Canal sin bufferAdemás: la recepción happens-before que el envío retorne. Es un encuentro, sincroniza en los dos sentidos.
close(ch)El cierre happens-before una recepción que devuelva el valor cero por canal cerrado.
mu.Unlock()Happens-before el siguiente mu.Lock() que tenga éxito.
wg.Done()Todos los Done happen-before que wg.Wait() retorne.
once.Do(f)El retorno de f happens-before que cualquier otro Do retorne.
sync/atomicSecuencialmente consistente: un Store happens-before el Load que observa ese valor.

Con esa tabla en la mano, arreglar el programa de arriba es elegir una arista. La versión con canal es la más idiomática y la que mejor documenta la intención:

var mensaje string
listo := make(chan struct{})

go func() {
	mensaje = "hola"
	close(listo)        // el cierre sincroniza
}()

<-listo                 // recibir del canal cerrado crea el happens-before
fmt.Println(mensaje)    // garantizado: "hola"

La versión con atomic también es correcta —los atómicos de Go son secuencialmente consistentes— pero la espera activa sigue siendo una mala idea: te quema un core entero:

import "sync/atomic"

var listo atomic.Bool
var mensaje string

go func() {
	mensaje = "hola"
	listo.Store(true)      // Store con semántica de release
}()

for !listo.Load() {        // Load con semántica de acquire
}
fmt.Println(mensaje)       // correcto, pero el for te come un núcleo
📌 Regla de bolsillo. Antes de dar por buena cualquier lectura de una variable compartida, contestá en voz alta: “¿qué operación de la tabla ordena esta lectura respecto de la escritura?”. Si la respuesta es “ninguna, pero en la práctica la goroutine escribe primero”, tenés un bug. Puede tardar dos años en manifestarse.

El caso que engaña a todos: el doble chequeo

Este patrón aparece en cachés e inicializaciones perezosas escritas por gente con experiencia. Y está roto:

var mu sync.Mutex
var cliente *Cliente

func Obtener() *Cliente {
	if cliente != nil {        // lectura SIN candado ← carrera
		return cliente
	}
	mu.Lock()
	defer mu.Unlock()
	if cliente == nil {
		cliente = nuevoCliente()   // el puntero puede publicarse
	}                              // antes de que el objeto esté completo
	return cliente
}

El problema no es solamente la carrera sobre el puntero: es que otra goroutine puede ver un puntero no nulo a un objeto a medio construir, porque nada ordena la escritura de los campos internos respecto de la escritura del puntero. La solución no es agregar más chequeos, es usar la primitiva que existe exactamente para esto:

// Go 1.21+: OnceValue devuelve una función que ejecuta el init una sola vez
var Obtener = sync.OnceValue(func() *Cliente {
	return nuevoCliente()
})

// equivalente clásico, si necesitás manejar un error:
var (
	once    sync.Once
	cliente *Cliente
	errIni  error
)

func ObtenerConError() (*Cliente, error) {
	once.Do(func() { cliente, errIni = nuevoClienteConError() })
	return cliente, errIni
}

GS3.2 El race detector: tu único testigo, y lo que no ve

El detector de carreras de Go está construido sobre ThreadSanitizer y hace algo conceptualmente simple: mientras el programa corre, mantiene metadatos sobre cada acceso a memoria y sobre las aristas happens-before que se van creando, y grita cuando encuentra dos accesos al mismo byte, al menos uno de escritura, sin arista entre ellos. No adivina, no hace análisis estático, no tiene falsos positivos: si te reporta una carrera, la carrera está.

# las tres formas de activarlo
go run -race ./cmd/servidor
go test -race ./...
go build -race -o bin/servidor ./cmd/servidor   # binario instrumentado, para staging

Una salida real se lee de arriba hacia abajo: qué acceso, en qué goroutine, en qué línea, y dónde nació esa goroutine.

==================
WARNING: DATA RACE
Write at 0x00c000126010 by goroutine 7:
  main.main.func1()
      /app/main.go:14 +0x38

Previous read at 0x00c000126010 by main goroutine:
  main.main()
      /app/main.go:18 +0x8c

Goroutine 7 (running) created at:
  main.main()
      /app/main.go:12 +0x7a
==================
Found 1 data race(s)
exit status 66
Configuralo con GORACE. GORACE="halt_on_error=1" aborta en la primera carrera (útil en CI para que el log no tenga 400 reportes del mismo bug). history_size=7 agranda el buffer de historia por goroutine cuando los stacks salen incompletos, a costa de bastante memoria.

Lo que el race detector NO detecta

Acá está la parte que separa a quien usa la herramienta de quien confía ciegamente en ella. Son cuatro limitaciones y las cuatro te van a morder:

1. Solo ve lo que se ejecutó. No analiza el código: instrumenta accesos reales. Si tu test no ejerce la rama donde está la carrera, o si el planificador nunca hizo correr las dos goroutines cerca, no hay reporte. Un -race verde significa “en esta ejecución no hubo carreras”, no “el programa no tiene carreras”.
2. Solo detecta data races, no race conditions. Son cosas distintas. Una carrera de datos es un acceso concurrente sin sincronizar. Una condición de carrera es un bug de lógica por el orden de las operaciones. El código de abajo no tiene ni una sola carrera de datos —todos los accesos están protegidos— y pierde incrementos alegremente: 
// Cada método toma el candado. -race no dice absolutamente nada.
func (c *Contador) Incr(k string) {
	v := c.Get(k)      // Lock ... Unlock
	c.Set(k, v+1)      // Lock ... Unlock   ← entre medio, otro pudo incrementar
}

// correcto: una sola sección crítica, la operación completa es atómica
func (c *Contador) IncrOK(k string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.m[k]++
}
3. No detecta deadlocks ni fugas de goroutines. Un pool que se cuelga porque nadie drena un canal es, para el detector, un programa perfectamente sincronizado. De hecho lo es: está bloqueado, y bloquearse es sincronización. Para eso están el dump de goroutines (GS3.9) y goleak (GS3.10).
4. Cuesta caro. El binario instrumentado usa del orden de 2× a 20× más CPU y unas 5× a 10× más memoria, y hay un techo de goroutines simultáneas que puede rastrear. No es para producción a escala completa, aunque un canario instrumentado sea una idea excelente.

Por qué va en CI sí o sí

Como el detector solo ve el schedule que ocurrió, la única forma de aumentar la probabilidad de encontrar la carrera es correr muchas veces, en máquinas distintas, con paralelismo distinto. Eso es exactamente lo que te da CI y no te da tu notebook:

# en el pipeline de PRs: rápido, con timeout para que un cuelgue falle en vez de colgar
go test -race -timeout 120s ./...

# nocturno: repeticiones y variación del paralelismo, que es lo que cambia el schedule
go test -race -count=20 -timeout 30m ./internal/pool/...
GOMAXPROCS=1 go test -race -count=20 ./internal/pool/...   # schedules distintos
GOMAXPROCS=32 go test -race -count=20 ./internal/pool/...
📌 Sin -race en CI, tu suite de tests concurrentes no está probando concurrencia: está probando que el código no explota en el único orden que tu máquina eligió hoy. Y agregá siempre -timeout: un test que se cuelga sin timeout deja el runner colgado media hora; con timeout, Go mata el test e imprime el dump completo de goroutines, que es justo el diagnóstico que necesitás.

GS3.3 Canales, a fondo

Un canal es tres cosas a la vez: un mecanismo de transferencia de datos, un mecanismo de sincronización, y un mecanismo de control de flujo. La mayoría de los bugs de canales vienen de olvidarse de las últimas dos.

Sin buffer vs con buffer: es una decisión de acoplamiento

a := make(chan int)      // sin buffer: encuentro. El envío espera al receptor.
b := make(chan int, 100) // con buffer: el envío retorna mientras haya lugar.

La diferencia práctica no es de rendimiento, es de acoplamiento temporal y de backpressure:

Sin bufferCon buffer N
AcoplamientoTotal: el productor avanza al ritmo del consumidorParcial: se desacoplan hasta N elementos
BackpressureInmediata y perfectaDiferida: recién cuando se llena
SincronizaciónEn los dos sentidos (el envío sabe que se recibió)Solo en un sentido
Si el consumidor muereEl productor se bloquea al toque: te enterásEl productor sigue N mensajes más y después se bloquea
Costo de un pico de cargaLatenciaMemoria (N mensajes vivos)
💡 Cómo elegir el tamaño del buffer. No hay un número mágico y “por las dudas 1000” es la peor respuesta. Solo tres justificaciones válidas: (a) 0, cuando querés backpressure exacta y saber que el otro lado recibió; (b) 1, para desacoplar un paso sin acumular nada —el caso típico del canal de errores, para que el envío nunca bloquee al que reporta; (c) N medido, cuando conocés el tamaño del lote o la ráfaga que querés absorber. Un buffer grande no arregla un consumidor lento: convierte una caída en un problema de memoria y te retrasa el momento en que te enterás.

Quién cierra: nunca el receptor

Las reglas de cierre son inflexibles porque violarlas es un panic, no un error:

  • Enviar a un canal cerrado: panic.
  • Cerrar un canal ya cerrado: panic.
  • Cerrar un canal nil: panic.
  • Recibir de un canal cerrado: devuelve el valor cero al instante, todas las veces que quieras. Sin panic.

De ahí sale la única regla que hace falta recordar: cierra el que envía, y solo si es el único que envía. El receptor jamás cierra, porque no puede saber si alguien está por enviar. Con varios productores, ninguno puede cerrar por su cuenta: hace falta un coordinador.

// N productores, un canal. El cierre lo hace una goroutine que espera a todos.
func productores(n int) <-chan int {
	out := make(chan int)
	var wg sync.WaitGroup

	for id := range n {
		wg.Go(func() {              // Go 1.25: Add(1) + defer Done() implícitos
			for i := range 100 {
				out <- id*100 + i
			}
		})
	}

	go func() {
		wg.Wait()      // cuando el último productor terminó...
		close(out)     // ...recién ahí se puede cerrar
	}()

	return out
}
Fijate que el close vive en su propia goroutine. Si escribieras wg.Wait(); close(out) en línea antes del return, la función se bloquearía para siempre: los productores no pueden avanzar hasta que alguien reciba, y nadie va a recibir hasta que la función retorne el canal.

Y prestá atención al tipo de retorno: <-chan int, un canal de solo recepción. Es la forma de que el compilador te garantice que el que consume no puede ni enviar ni cerrar. Los tipos direccionales (chan<- T para solo envío, <-chan T para solo recepción) son documentación ejecutable: usalos siempre en las firmas.

El canal nil: apagar una rama del select

Un canal nil bloquea para siempre, tanto al enviar como al recibir. Suena a bug y es, en realidad, una herramienta preciosa: dentro de un select, una rama sobre un canal nil nunca se elige. Es decir, asignarle nil a una variable de canal desactiva esa rama. El caso de uso canónico es multiplexar dos fuentes hasta que ambas se agoten:

func merge(a, b <-chan int) <-chan int {
	out := make(chan int)

	go func() {
		defer close(out)
		for a != nil || b != nil {     // seguimos mientras quede alguna viva
			select {
			case v, ok := <-a:
				if !ok {
					a = nil            // se agotó: apagamos esta rama
					continue           // sin nil, este case se elegiría infinitas veces
				}
				out <- v
			case v, ok := <-b:
				if !ok {
					b = nil
					continue
				}
				out <- v
			}
		}
	}()

	return out
}
Sin el truco del nil, este código es un bucle caliente. Un canal cerrado está siempre listo para recibir: si a se cierra y dejás la rama activa, el select la elige constantemente devolviendo ceros, y te comés un núcleo al 100% sin producir nada. Es una de las formas más comunes de que un servicio Go pase de 2% a 100% de CPU sin ningún cambio de tráfico.

GS3.4 select: default, timeouts y multiplexado

El select bloquea hasta que una de sus ramas pueda avanzar. Si hay varias listas, elige una al azar — no en orden, no la primera: al azar, deliberadamente, para evitar que una rama muy activa mate de hambre a las demás. De ahí salen tres patrones.

Uno: default convierte el select en no bloqueante. Si ninguna rama está lista, se ejecuta el default y se sigue de largo:

// enviar sin bloquear nunca: si el buffer está lleno, descartamos
select {
case metricas <- m:
default:
	descartadas.Add(1)   // preferimos perder una métrica antes que frenar el request
}

// recibir sin bloquear: "¿hay algo?"
select {
case v := <-ch:
	usar(v)
default:
	// no había nada, seguimos
}
Un select con default adentro de un for sin espera es una espera activa. Si escribís for { select { case ...: default: } } vas a girar a máxima velocidad quemando CPU. Si necesitás sondear, sondeá con un time.Ticker; si necesitás esperar, sacá el default y dejá que el select bloquee, que es gratis.

Dos: timeouts. El clásico es time.After, pero en código nuevo el timeout casi siempre debería venir del context, porque así se propaga:

select {
case r := <-resultados:
	return r, nil
case <-time.After(2 * time.Second):
	return Resultado{}, errors.New("timeout esperando resultado")
}

// mejor: el deadline viene de arriba y se propaga a todo lo que llames
select {
case r := <-resultados:
	return r, nil
case <-ctx.Done():
	return Resultado{}, ctx.Err()
}
Dato 2026: hasta Go 1.22, un time.After adentro de un loop mantenía vivo el timer hasta que se disparaba, y era una fuente real de consumo de memoria en bucles calientes; la receta era usar time.NewTimer y llamar a Stop. Desde Go 1.23 los timers que nadie referencia se pueden recolectar antes de dispararse, así que esa fuga desapareció. Reusar un Timer con Reset sigue siendo útil por costo de asignación en loops muy calientes, pero ya no es obligatorio por memoria.

Tres: prioridad. Como la elección es al azar, no podés decir “atendé la cancelación antes que el trabajo”. Se emula con dos select anidados: uno no bloqueante que solo mira la rama prioritaria, y después el bloqueante:

for {
	// prioridad absoluta: si ya nos cancelaron, ni miramos el trabajo
	select {
	case <-ctx.Done():
		return ctx.Err()
	default:
	}

	select {
	case t, ok := <-tareas:
		if !ok {
			return nil
		}
		procesar(t)
	case <-ctx.Done():
		return ctx.Err()
	}
}

GS3.5 context: cancelación en árbol

Un context.Context es un nodo de un árbol que propaga cancelación hacia abajo. Cancelar un padre cancela a todos sus descendientes; cancelar un hijo no toca al padre. Eso es el 90% de lo que hace, y el resto —los valores— es la parte que más se usa mal.

ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()                    // SIEMPRE, aunque haya timeout

// hijo con un deadline más corto: se cancela antes que el padre
ctxDB, cancelDB := context.WithTimeout(ctx, 800*time.Millisecond)
defer cancelDB()

filas, err := db.QueryContext(ctxDB, "SELECT ...")
📌 El defer cancel() no es opcional ni siquiera con WithTimeout. El nodo hijo queda registrado en el padre hasta que se cancela o vence; si el padre vive mucho (por ejemplo, el contexto de un servidor de larga vida) y vos creás hijos sin cancelarlos, acumulás nodos y timers. go vet tiene un chequeo (lostcancel) que detecta el caso obvio; corrélo.

Propagar bien: el contexto tiene que llegar hasta el syscall

Un contexto que no se consulta es decoración. Cancelar solo funciona si cada operación bloqueante del camino lo mira: los select, los loops largos, y las llamadas de red y de base de datos en su variante ...Context.

func Sincronizar(ctx context.Context, ids []int) error {
	for i, id := range ids {
		// un loop de CPU largo también tiene que rendirse: chequeamos cada tanto
		if i%256 == 0 {
			select {
			case <-ctx.Done():
				return ctx.Err()
			default:
			}
		}

		req, err := http.NewRequestWithContext(ctx, "GET", urlDe(id), nil)
		if err != nil {
			return err
		}
		resp, err := http.DefaultClient.Do(req)   // se aborta si cancelan el ctx
		if err != nil {
			return fmt.Errorf("id %d: %w", id, err)
		}
		resp.Body.Close()
	}
	return nil
}

Herramientas modernas que casi nadie usa

// 1.20: cancelar con una causa, y recuperarla después
ctx, cancel := context.WithCancelCause(context.Background())
cancel(fmt.Errorf("el usuario cerró la pestaña"))
// ctx.Err()          -> context.Canceled  (genérico, poco útil en logs)
// context.Cause(ctx) -> "el usuario cerró la pestaña"

// 1.21: correr algo cuando el contexto se cancela, sin dejar una goroutine esperando
stop := context.AfterFunc(ctx, func() { conn.Close() })
defer stop()

// 1.21: trabajo de limpieza que NO debe morir con el request
go auditar(context.WithoutCancel(ctx), evento)   // conserva los valores, pierde el deadline

Los antipatrones

1. Guardar el contexto en un struct. type Servicio struct { ctx context.Context } mezcla el ciclo de vida de un request con el de un objeto que vive para siempre. El resultado son bugs donde un request cancelado mata trabajo de otro, o donde el timeout del primer request queda pegado a todos. El contexto se pasa como primer parámetro, se llama ctx, y no se guarda. La excepción reconocida son los structs que representan un request (como http.Request, que lo lleva adentro y expone WithContext).
2. Usar WithValue para pasar dependencias. El logger, el pool de conexiones y el cliente HTTP son dependencias: van por el constructor o por parámetro, con tipos verificados en compilación. WithValue es para datos de alcance del request —trace ID, usuario autenticado, locale— y siempre con una clave de un tipo propio no exportado, nunca un string: 
type claveUsuario struct{}   // tipo privado: nadie puede colisionar con tu clave

func ConUsuario(ctx context.Context, u *Usuario) context.Context {
	return context.WithValue(ctx, claveUsuario{}, u)
}

func UsuarioDe(ctx context.Context) (*Usuario, bool) {
	u, ok := ctx.Value(claveUsuario{}).(*Usuario)
	return u, ok
}
3. Aceptar un contexto y no usarlo nunca. Es peor que no aceptarlo: le miente al que llama, que cree que puede cancelar. Si tu función no puede cancelarse, no recibas ctx.
4. Pasar context.TODO() o Background() desde adentro. Corta el árbol: a partir de ahí, la cancelación de arriba no llega. TODO() es un marcador temporal para migraciones, no un valor por defecto.

GS3.6 Las primitivas de sync: cuándo cada una

// WaitGroup — esperar a que N goroutines terminen.
// Go 1.25 agregó el método Go, que hace Add(1) y defer Done() por vos.
var wg sync.WaitGroup
for _, u := range urls {
	wg.Go(func() { descargar(u) })
}
wg.Wait()

// Forma clásica, la que vas a ver en todo el código existente:
for _, u := range urls {
	wg.Add(1)                      // Add SIEMPRE fuera de la goroutine
	go func() {
		defer wg.Done()            // Done SIEMPRE con defer
		descargar(u)
	}()
}
wg.Wait()
// Mutex — sección crítica corta. Ponele defer al Unlock siempre.
type Cache struct {
	mu sync.Mutex
	m  map[string]int
}

func (c *Cache) Incr(k string) {
	c.mu.Lock()
	defer c.mu.Unlock()      // sobrevive a un return temprano y a un panic
	c.m[k]++
}

// atomic — contadores y flags. Tipos genéricos desde 1.19: nada de int64 sueltos.
type Metricas struct {
	pedidos atomic.Int64
	config  atomic.Pointer[Config]   // swap de configuración sin candado
}

func (m *Metricas) Contar() { m.pedidos.Add(1) }
func (m *Metricas) Recargar(c *Config) { m.config.Store(c) }

Por qué RWMutex a veces es más lento que Mutex

La intuición dice que si mil goroutines solo leen, dejarlas entrar a todas a la vez tiene que ser más rápido. En la práctica, con secciones críticas cortas, suele ser al revés. La razón es de hardware: RLock y RUnlock escriben —incrementan y decrementan un contador de lectores— y ese contador vive en una línea de caché compartida. Cada lector que entra invalida esa línea en el caché de todos los demás núcleos. Con una sección crítica de 20 nanosegundos, el costo del ping-pong de caché supera al beneficio de dejar entrar a varios a la vez.

func BenchmarkMutex(b *testing.B) {
	var mu sync.Mutex
	m := map[string]int{"k": 1}
	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			mu.Lock()
			_ = m["k"]        // lectura cortita: nanosegundos
			mu.Unlock()
		}
	})
}

func BenchmarkRWMutex(b *testing.B) {
	var mu sync.RWMutex
	m := map[string]int{"k": 1}
	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			mu.RLock()
			_ = m["k"]
			mu.RUnlock()
		}
	})
}
go test -bench=Mutex -cpu=1,4,16 -benchtime=2s ./...
# con -cpu=1 son casi iguales; con -cpu=16 y sección corta, el RWMutex
# se queda atrás por contención de la línea de caché del contador de lectores
📌 Elegí RWMutex solo si podés justificar dos cosas a la vez: que los lectores son muchos y que la sección de lectura dura microsegundos o más (parsear, recorrer una estructura grande, serializar). Para leer un campo o mirar un mapa, Mutex. Y ante la duda, corré el benchmark con -cpu variable: es de las pocas decisiones de concurrencia que se responden en dos minutos con datos.
Trampa del RWMutex: no es reentrante ni siquiera para lectores. Si una goroutine tiene RLock y adentro llama a una función que hace otro RLock, y entre las dos llega un escritor, se traba: el escritor espera a que salgan los lectores, y el segundo RLock espera al escritor (para que los escritores no mueran de hambre). Deadlock, y aparece solo bajo carga.

GS3.7 Cuándo un mutex le gana a un canal

El proverbio de Go es famoso: “Don't communicate by sharing memory; share memory by communicating.” (Rob Pike). Es un buen consejo de diseño y una pésima regla absoluta. La documentación del propio paquete sync es explícita en que hay casos donde el candado es lo correcto — y el caso más claro es el más simple: proteger un dato.

Comparemos las dos implementaciones de un contador compartido. Con canal, necesitás una goroutine servidora viva y un protocolo de pedidos:

// Contador "idiomático CSP": correcto, y una mala idea.
type ContadorCSP struct {
	incr   chan struct{}
	leer   chan chan int
	cerrar chan struct{}
}

func NuevoCSP() *ContadorCSP {
	c := &ContadorCSP{
		incr:   make(chan struct{}),
		leer:   make(chan chan int),
		cerrar: make(chan struct{}),
	}
	go func() {                        // una goroutine viva para siempre
		n := 0
		for {
			select {
			case <-c.incr:
				n++
			case resp := <-c.leer:
				resp <- n
			case <-c.cerrar:
				return                 // y si te olvidás de cerrar: fuga
			}
		}
	}()
	return c
}

func (c *ContadorCSP) Incr() { c.incr <- struct{}{} }
func (c *ContadorCSP) Leer() int {
	resp := make(chan int)             // una asignación por lectura
	c.leer <- resp
	return <-resp
}
// La versión que vas a querer mantener dentro de un año.
type Contador struct {
	n atomic.Int64
}

func (c *Contador) Incr() { c.n.Add(1) }
func (c *Contador) Leer() int64 { return c.n.Load() }

La segunda versión es unas dos décimas de nanosegundo contra unos cientos, no tiene goroutine que se pueda filtrar, no tiene ciclo de vida que administrar, y entra en cuatro líneas. La primera existe únicamente porque alguien tomó “compartí memoria comunicando” como mandamiento.

💡 El criterio que sí funciona. Preguntate qué estás moviendo. Canal cuando transferís propiedad de un dato de una goroutine a otra, cuando coordinás etapas de un pipeline, cuando necesitás backpressure, o cuando la señal es “terminé” / “cancelá”. Mutex o atomic cuando protegés estado que varias goroutines leen y escriben en el lugar: contadores, cachés, mapas de sesiones, configuración. El canal orquesta; el candado custodia.

GS3.8 Patrones, con código completo

Worker pool con límite

// N workers consumen del mismo canal. Es el patrón más usado y el que
// más se rompe: mirá GS3.12 para ver cómo se cuelga esta forma ingenua.
func Pool(tareas []Tarea, workers int) []Resultado {
	in := make(chan Tarea)
	out := make(chan Resultado, len(tareas))
	var wg sync.WaitGroup

	for range workers {
		wg.Go(func() {
			for t := range in {        // termina solo cuando in se cierra
				out <- hacer(t)
			}
		})
	}

	go func() {
		defer close(in)
		for _, t := range tareas {
			in <- t
		}
	}()

	wg.Wait()
	close(out)

	res := make([]Resultado, 0, len(tareas))
	for r := range out {
		res = append(res, r)
	}
	return res
}

Fan-out / fan-in

// Fan-out: una fuente, K consumidores en paralelo.
// Fan-in: K canales de salida, uno solo de entrada al siguiente paso.
func fanIn(canales ...<-chan Resultado) <-chan Resultado {
	out := make(chan Resultado)
	var wg sync.WaitGroup

	for _, c := range canales {
		wg.Go(func() {
			for v := range c {
				out <- v
			}
		})
	}

	go func() {
		wg.Wait()
		close(out)
	}()

	return out
}

Pipeline con cancelación

// Regla del pipeline: TODA etapa que envía tiene que poder rendirse.
// Un "out <- v" pelado es una fuga de goroutine esperando a pasar.
func generar(ctx context.Context, ns ...int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for _, n := range ns {
			select {
			case out <- n:
			case <-ctx.Done():
				return           // el consumidor se fue: nos vamos también
			}
		}
	}()
	return out
}

func cuadrado(ctx context.Context, in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for n := range in {
			select {
			case out <- n * n:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}

func usar() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()                       // al salir, todas las etapas se desarman

	for v := range cuadrado(ctx, generar(ctx, 1, 2, 3, 4, 5)) {
		fmt.Println(v)
		if v > 9 {
			break                        // salida temprana: el defer cancel limpia
		}
	}
}

Semáforo con canal buffered

// Limitar concurrencia sin pool: N fichas en un canal.
// Sirve cuando las tareas ya están lanzadas y solo querés poner un techo.
func DescargarTodo(ctx context.Context, urls []string, max int) error {
	sem := make(chan struct{}, max)
	var wg sync.WaitGroup

	for _, u := range urls {
		select {
		case sem <- struct{}{}:          // tomar ficha (bloquea si hay max en vuelo)
		case <-ctx.Done():
			wg.Wait()
			return ctx.Err()
		}

		wg.Go(func() {
			defer func() { <-sem }()     // devolver la ficha SIEMPRE
			descargar(ctx, u)
		})
	}

	wg.Wait()
	return nil
}

errgroup con contexto: el que vas a usar el 80% de las veces

import "golang.org/x/sync/errgroup"

func Recolectar(ctx context.Context, urls []string) ([]Doc, error) {
	g, ctx := errgroup.WithContext(ctx)   // ojo: sombrea ctx a propósito
	g.SetLimit(16)                        // techo de concurrencia, sin semáforo a mano

	docs := make([]Doc, len(urls))        // cada goroutine escribe SU índice:
	for i, u := range urls {              // no hace falta candado
		g.Go(func() error {
			d, err := bajar(ctx, u)
			if err != nil {
				return fmt.Errorf("%s: %w", u, err)
			}
			docs[i] = d
			return nil
		})
	}

	if err := g.Wait(); err != nil {
		return nil, err                   // devuelve el PRIMER error no nulo
	}
	return docs, nil
}
Tres detalles de errgroup que valen oro. (1) WithContext devuelve un contexto que se cancela apenas la primera goroutine devuelve error: el resto se entera y abandona. (2) Wait guarda solo el primer error; si necesitás todos, acumulá vos con errors.Join. (3) SetLimit(n) hace que g.Go bloquee cuando hay n en vuelo, así que reemplaza al semáforo — pero cuidado con llamar a g.Go desde adentro de otra goroutine del mismo grupo, porque podés trabarte contra tu propio límite.
Escribir docs[i] = d desde varias goroutines no es una carrera: cada una toca un índice distinto de un slice ya dimensionado, y son posiciones de memoria diferentes. Sí lo sería docs = append(docs, d), porque append lee y escribe la cabecera del slice. Es una distinción que -race confirma en el acto.

GS3.9 Deadlocks, livelocks y cómo se ven en un dump

Go tiene un detector de deadlocks en el runtime, pero con una limitación enorme: solo dispara si absolutamente todas las goroutines están bloqueadas. En un programa de juguete lo ves:

func main() {
	ch := make(chan int)   // sin buffer
	ch <- 1                // nadie recibe
	fmt.Println(<-ch)
}
// fatal error: all goroutines are asleep - deadlock!
En un servicio real ese mensaje no aparece nunca. Alcanza con que exista un http.Server escuchando, un Ticker de métricas o una goroutine del recolector de basura para que el runtime concluya que “algo puede avanzar”. Tu handler queda colgado, las goroutines se acumulan, la memoria sube... y el proceso sigue vivo y reportando healthy. Un deadlock parcial no se ve: se diagnostica.

Sacar y leer el dump de goroutines

curl -s 'http://localhost:6060/debug/pprof/goroutine?debug=2' > dump.txt

# 3) Contar por estado: la foto que te dice dónde está todo el mundo trabado

Las cinco causas que cubren casi todo

  1. Orden de candados invertido. La goroutine A toma mu1 y pide mu2; la B toma mu2 y pide mu1. Se arregla definiendo un orden total de adquisición (por ejemplo, siempre por ID ascendente) y respetándolo en todo el paquete.
  2. Enviar a un canal que ya nadie lee. El worked example de GS3.12 es exactamente esto.
  3. Unlock salteado. Un return de error entre el Lock y el Unlock. Por eso defer mu.Unlock() va inmediatamente después del Lock, siempre.
  4. WaitGroup con cuentas rotas. Un Add de más, o un Done que se saltea por un return temprano: Wait no vuelve nunca.
  5. RLock recursivo con un escritor esperando, como vimos en GS3.6.

Livelock: peor que un deadlock

Un livelock es un sistema donde todo el mundo está ocupadísimo y nadie progresa. Con un deadlock el proceso al menos se queda quieto y se nota; con un livelock la CPU está al 100%, las métricas parecen sanas y el throughput es cero. El patrón clásico son dos goroutines que se ceden el paso educadamente:

// LIVELOCK: los dos sueltan y reintentan al mismo ritmo, para siempre.
for {
	mu1.Lock()
	if !mu2.TryLock() {          // TryLock existe desde Go 1.18
		mu1.Unlock()
		continue                 // reintento inmediato, en sincronía con el otro
	}
	break
}
📌 Todo reintento necesita backoff con jitter. Si dos actores reintentan con el mismo período, se sincronizan y no salen nunca. Un time.Sleep de unos microsegundos aleatorios rompe la simetría. Y si podés evitar el reintento con un orden total de candados, mejor todavía: el livelock deja de ser posible en vez de ser improbable.

GS3.10 Fugas de goroutines y cómo testearlas

En GS1 vimos el costo: cada goroutine arranca con un stack chico pero crece, y mantiene vivo todo lo que su closure referencia. Una fuga de goroutines es, en la práctica, una fuga de memoria con un multiplicador. Y la causa número uno es siempre la misma: una goroutine bloqueada en un canal que nadie va a tocar.

// FUGA. El clásico absoluto.
func Consultar(url string) <-chan string {
	ch := make(chan string)          // SIN buffer
	go func() {
		ch <- pedidoLento(url)       // si nadie recibe, esta goroutine vive para siempre
	}()
	return ch
}

func Llamador() (string, error) {
	select {
	case r := <-Consultar("https://api.ejemplo.com"):
		return r, nil
	case <-time.After(100 * time.Millisecond):
		return "", errors.New("timeout")   // ← nos vamos y abandonamos el canal
	}
}

Cada timeout deja una goroutine bloqueada eternamente, reteniendo la respuesta HTTP, el buffer y todo el closure. Con 50 requests por segundo y un 2% de timeouts, son 86.400 goroutines fugadas por día. Hay dos arreglos, y conviene aplicar los dos:

// Arreglo 1: buffer de 1. El envío nunca bloquea, aunque nadie reciba.
func Consultar(url string) <-chan string {
	ch := make(chan string, 1)       // ← el único cambio
	go func() {
		ch <- pedidoLento(url)       // retorna siempre; el canal lo recoge el GC
	}()
	return ch
}

// Arreglo 2, el correcto de verdad: que el trabajo mismo se pueda cancelar.
func Consultar(ctx context.Context, url string) (string, error) {
	req, err := http.NewRequestWithContext(ctx, "GET", url, nil)
	if err != nil {
		return "", err
	}
	// ... el deadline del ctx aborta el pedido de red; no queda nada colgado
}

Un test que detecta la fuga: goleak

go.uber.org/goleak compara el conjunto de goroutines antes y después de tus tests y falla si quedaron de más. Es una línea de código y encuentra una clase entera de bugs:

package pool_test

import (
	"testing"

	"go.uber.org/goleak"
)

// Opción A: verificar al final de TODO el paquete de tests.
func TestMain(m *testing.M) {
	goleak.VerifyTestMain(m,
		// las goroutines de fondo legítimas se ignoran explícitamente
		goleak.IgnoreTopFunction("database/sql.(*DB).connectionOpener"),
	)
}

// Opción B: verificar test por test, que da mejor localización del culpable.
func TestConsultar_TimeoutNoDejaGoroutines(t *testing.T) {
	defer goleak.VerifyNone(t)

	_, err := Llamador()
	if err == nil {
		t.Fatal("esperaba timeout")
	}
	// con el código con fuga, acá falla: "found unexpected goroutines"
}
Sin dependencias, la versión pobre funciona bastante bien: guardá runtime.NumGoroutine() al empezar, dale al final unos milisegundos de gracia (las goroutines tardan un instante en morir) y compará. Es menos preciso que goleak, no te dice quién quedó viva, pero atrapa la fuga masiva.
Dato 2026: desde Go 1.25 existe testing/synctest en la biblioteca estándar (fue experimental en 1.24). Corre tu test en una “burbuja” con tiempo falso: los Sleep y los timers avanzan instantáneamente cuando todas las goroutines de la burbuja están bloqueadas, y synctest.Wait espera a que se aquieten. Un test de timeouts que tardaba 30 segundos reales pasa a tardar microsegundos y deja de ser flaky. Para código con context.WithTimeout y reintentos, cambia la vida.

GS3.11 Errores clásicos que sobreviven a la revisión de código

La variable del loop (arreglado en 1.22, pero tenés que entenderlo)

// Hasta Go 1.21, esto imprimía tres veces el último elemento (o basura).
for _, v := range []string{"a", "b", "c"} {
	go func() {
		fmt.Println(v)      // todas las goroutines capturan LA MISMA variable
	}()
}

La causa era la semántica del for: la variable v se declaraba una sola vez para todo el loop y se le reasignaba el valor en cada iteración. Las closures capturan variables, no valores, así que las tres goroutines miraban la misma casilla de memoria — y encima con una carrera de datos, porque el loop escribía mientras ellas leían. La receta era pasarla como argumento (go func(v string){...}(v)) o hacer un v := v al principio del cuerpo.

Go 1.22 cambió la semántica: ahora las variables del for son por iteración, y el código de arriba imprime a, b, c. Dos razones para que igual lo sepas:

  1. El cambio está condicionado por la versión declarada en go.mod. Un módulo que dice go 1.21 compila con la semántica vieja incluso con el toolchain 1.26. Vas a mantener repos así.
  2. La clase de bug no desapareció. Solo se arregló la variable del loop; cualquier otra variable compartida por closures sigue rota:
// SIGUE MAL en Go 1.26: la variable no es del loop, es de afuera.
buf := make([]byte, 0, 1024)
for i := range 3 {
	buf = append(buf, byte(i))
	go func() {
		procesar(buf)        // carrera: todas ven el mismo slice, que muta
	}()
}

wg.Add adentro de la goroutine

// MAL: hay una carrera entre Add y Wait.
var wg sync.WaitGroup
for _, t := range tareas {
	go func() {
		wg.Add(1)            // puede ejecutarse DESPUÉS de que Wait ya volvió
		defer wg.Done()
		hacer(t)
	}()
}
wg.Wait()                    // puede retornar con el contador en 0: no espera nada

// BIEN (clásico):            // MEJOR (Go 1.25):
for _, t := range tareas {    for _, t := range tareas {
	wg.Add(1)                     wg.Go(func() { hacer(t) })
	go func() {               }
		defer wg.Done()       wg.Wait()
		hacer(t)
	}()
}
wg.Wait()

El bug es sutil porque casi siempre anda: si lanzar la goroutine es más rápido que llegar al Wait, el contador sube a tiempo. Bajo carga, o con GOMAXPROCS=1, o en una máquina más lenta, Wait vuelve enseguida y el programa sigue de largo con trabajo a medio hacer. Es de los bugs que producen datos incompletos en vez de errores.

Los otros tres del podio

// 1. Olvidarse el defer en Done: si hacer() hace panic o hay un return
//    temprano, el contador nunca baja y Wait se cuelga para siempre.
go func() {
	hacer(t)
	wg.Done()        // ← MAL. Va como: defer wg.Done()
}()

// 2. Pasar el WaitGroup por valor: se copia el struct y el Done es sobre
//    la copia. go vet lo detecta (copylocks); corré go vet en CI.
func trabajar(wg sync.WaitGroup) { defer wg.Done() }   // MAL
func trabajar(wg *sync.WaitGroup) { defer wg.Done() }  // BIEN

// 3. Unlock sin defer, con un return de error en el medio.
func (c *Cache) Set(k string, v int) error {
	c.mu.Lock()
	if k == "" {
		return errors.New("clave vacía")   // ← el candado queda tomado PARA SIEMPRE
	}
	c.m[k] = v
	c.mu.Unlock()
	return nil
}

GS3.12 Worked example: el pool que se cuelga una vez cada mil

Este es el caso completo, tal como se vive. Un servicio de ingesta procesa lotes de 10.000 tareas con un pool de 8 workers. Funciona hace meses. Desde hace unos días, un lote cada tanto no termina nunca: la métrica de lotes completados se queda quieta, la de memoria sube despacio, y el health check sigue en verde porque el HTTP server responde perfecto.

Paso 1 — El código

func Procesar(tareas []Tarea, workers int) error {
	in := make(chan Tarea)
	errc := make(chan error, 1)
	var wg sync.WaitGroup

	for range workers {
		wg.Go(func() {
			for t := range in {
				if err := hacer(t); err != nil {
					select {
					case errc <- err:      // reportamos el primero
					default:               // los demás se descartan
					}
					return                 // ← acá está el bug
				}
			}
		})
	}

	for _, t := range tareas {
		in <- t                            // ← acá se manifiesta
	}
	close(in)
	wg.Wait()

	select {
	case err := <-errc:
		return err
	default:
		return nil
	}
}

Leelo con los ojos de la revisión de código: cada worker consume del canal, reporta el primer error sin bloquear, y sale. El productor envía todo y cierra. El WaitGroup está bien usado. El canal de errores tiene buffer 1 y un default para no trabarse. Todo parece correcto, y por eso pasó la revisión.

Paso 2 — -race, y sale limpio

$ go test -race -count=50 ./internal/ingesta/
ok  	ejemplo/internal/ingesta	18.442s

$ go test -race -count=50 -cpu=1,4,16 ./internal/ingesta/
ok  	ejemplo/internal/ingesta	52.907s

Cincuenta corridas, tres configuraciones de paralelismo, cero reportes. Y tiene todo el sentido del mundo: no hay ninguna carrera de datos. No hay una sola variable compartida sin sincronizar; toda la comunicación pasa por canales y por el WaitGroup. El race detector está haciendo su trabajo bien. El bug es de otra especie.

📌 Momento de aprendizaje. Un -race limpio sobre un programa que se cuelga es información, no un callejón sin salida: te descarta toda una familia de causas y te dice dónde mirar. Un programa bloqueado está, por definición, perfectamente sincronizado. Lo que sigue es el dump.

$ grep -A3 'chan send' dump.txt | head -6
goroutine 118 [chan send, 27 minutes]:
ejemplo/internal/ingesta.Procesar({0xc0004a2000, 0x2710, 0x2710}, 0x8)
	/app/internal/ingesta/pool.go:24 +0x1f4

Ahí está todo: cero workers vivos y el productor llevando 27 minutos parado en la línea 24, que es el in <- t. La secuencia real fue:

1. La tarea 40 falló (un timeout del servicio de abajo). Ese worker mandó el error a errc y ejecutó su return.
2. Como el error era sistémico —el servicio de abajo estaba caído— las siguientes tareas también fallaron. Uno por uno, los 8 workers hicieron return.
3. El productor iba por la tarea 51 de 10.000. El canal in no tiene buffer y ya no queda nadie que reciba: in <- t se bloquea para siempre.
4. close(in) y wg.Wait() nunca se ejecutan. La función no retorna. El lote queda a medias, sin error, sin log, sin nada.
5. El runtime no grita “deadlock” porque el http.Server del pprof y el ticker de métricas están vivos y sanos.
La causa raíz en una frase: el consumidor tiene derecho a rendirse, pero el productor no tiene forma de enterarse. Cualquier pipeline donde una punta puede irse y la otra no puede abandonar tiene este bug latente. Y como solo se dispara cuando hay un error temprano y quedan muchas tareas por enviar, en desarrollo con 20 tareas de prueba no aparece jamás.

Paso 4 — La reescritura

El arreglo no es agregarle buffer al canal (eso solo corre el problema 100 tareas más adelante). Es darle al productor una forma de rendirse, y hacerlo con la herramienta que ya trae esa semántica adentro:

import "golang.org/x/sync/errgroup"

func Procesar(ctx context.Context, tareas []Tarea, workers int) error {
	g, ctx := errgroup.WithContext(ctx)
	in := make(chan Tarea)

	// Productor: ahora puede abandonar.
	g.Go(func() error {
		defer close(in)                 // pase lo que pase, el canal se cierra
		for _, t := range tareas {
			select {
			case in <- t:
			case <-ctx.Done():
				return nil              // alguien falló: nos retiramos en silencio
			}
		}
		return nil
	})

	// Consumidores: al devolver error, errgroup cancela ctx por nosotros.
	for range workers {
		g.Go(func() error {
			for t := range in {
				if err := hacer(ctx, t); err != nil {
					return fmt.Errorf("tarea %d: %w", t.ID, err)
				}
			}
			return nil
		})
	}

	return g.Wait()                     // devuelve el primer error real
}

Por qué esto ya no se puede colgar, punto por punto:

  • Cuando un worker devuelve error, errgroup cancela el contexto automáticamente.
  • El productor está en un select con ctx.Done(): sale, y su defer close(in) cierra el canal.
  • Los workers que seguían vivos terminan su range in de forma natural cuando el canal se cierra. Nadie queda bloqueado.
  • g.Wait() devuelve el primer error registrado, que es el del worker —la causa real— y no el context.Canceled que vino después. Por eso el productor devuelve nil al cancelarse: para no ensuciar el diagnóstico si por casualidad llega primero.
  • Como hacer ahora recibe ctx, las tareas en vuelo también abortan en vez de terminar trabajo que ya no le importa a nadie.

Paso 5 — El test que impide que vuelva

Un arreglo sin test es una anécdota. Este test falla con el código viejo y pasa con el nuevo, y encima protege contra la fuga de goroutines:

package ingesta

import (
	"context"
	"errors"
	"testing"

	"go.uber.org/goleak"
)

func TestMain(m *testing.M) { goleak.VerifyTestMain(m) }

func TestProcesar_ErrorTempranoNoSeCuelga(t *testing.T) {
	defer goleak.VerifyNone(t)

	// La clave: MUCHAS tareas y el error MUY al principio.
	// Es la única combinación que reproduce el bug.
	tareas := make([]Tarea, 10_000)
	for i := range tareas {
		tareas[i] = Tarea{ID: i}
	}
	hacer = func(ctx context.Context, t Tarea) error {
		if t.ID == 40 {
			return errors.New("falla inyectada")
		}
		return nil
	}

	err := Procesar(context.Background(), tareas, 8)
	if err == nil {
		t.Fatal("esperaba el error de la tarea 40")
	}
}
# Con el código viejo: el test no falla, se CUELGA. El timeout lo convierte
# en una falla legible, con el dump completo de goroutines de regalo.
$ go test -race -timeout 30s ./internal/ingesta/
panic: test timed out after 30s

goroutine 22 [chan send, 1 minutes]:
ejemplo/internal/ingesta.Procesar(...)
	/app/internal/ingesta/pool.go:24
FAIL	ejemplo/internal/ingesta	30.019s

# Con el código nuevo:
$ go test -race -count=10 -timeout 30s ./internal/ingesta/
ok  	ejemplo/internal/ingesta	2.884s
📌 Las tres lecciones del ejercicio. (1) -race limpio no es luz verde: cubre carreras de datos, no bloqueos ni fugas. (2) Todo test de concurrencia necesita -timeout, porque convierte un cuelgue silencioso en una falla con diagnóstico incluido. (3) El test tiene que reproducir la forma del problema de producción —muchas tareas, error temprano—, no una versión chiquita y cómoda: con 20 tareas, este bug no existe.

Checkpoint — ¿lo tenés claro?

Corrés go test -race cincuenta veces sobre un pool que en producción se cuelga, y siempre pasa. ¿Qué concluís?

Que el bug no es una carrera de datos, y eso descarta media investigación. El detector solo reporta accesos concurrentes sin sincronizar sobre la misma memoria; un programa bloqueado está sincronizado por definición. El paso siguiente es el dump de goroutines (SIGQUIT, /debug/pprof/goroutine?debug=2, o el que imprime go test -timeout), buscando estados chan send, chan receive o semacquire con muchos minutos encima. Ojo con el otro lado de la moneda: cincuenta corridas limpias tampoco prueban que no haya carreras — solo que en esos cincuenta schedules no aparecieron.

Tenés cuatro goroutines enviando al mismo canal. ¿Quién lo cierra?

Ninguna de las cuatro por su cuenta: cerrar un canal ya cerrado es panic, y enviar a un canal cerrado también. La solución estándar es un WaitGroup al que cada productor le hace Done al terminar, más una goroutine aparte que hace wg.Wait() y recién ahí close(ch). Esa goroutine cerradora tiene que vivir en su propia goroutine, no en línea antes de devolver el canal, o la función se bloquea a sí misma. Y el receptor nunca cierra: no tiene forma de saber si alguien está por enviar.

Un compañero cambió un Mutex por un RWMutex "porque hay muchos más lectores que escritores" y el servicio empeoró. ¿Por qué?

Porque RLock y RUnlock también escriben: modifican un contador de lectores compartido que vive en una línea de caché. Cada lector que entra o sale invalida esa línea en todos los demás núcleos, y con secciones críticas de decenas de nanosegundos ese ping-pong cuesta más que la exclusión mutua que estás evitando. RWMutex rinde cuando la sección de lectura es larga (microsegundos o más), no cuando es "leer un campo del mapa". La respuesta correcta es medirlo: un b.RunParallel con -cpu=1,4,16 resuelve la discusión en dos minutos.

Resumen ejecutivo

  • El memory model es la única fuente de verdad: si no podés nombrar la operación (canal, mutex, WaitGroup, Once, atomic) que ordena una escritura respecto de una lectura, tenés un bug aunque el programa ande.
  • -race va en CI, con -count y GOMAXPROCS variados. Detecta carreras de datos reales, sin falsos positivos, pero solo en el schedule que se ejecutó, y no ve condiciones de carrera lógicas, deadlocks ni fugas.
  • Sin buffer es acoplamiento total y backpressure perfecta; con buffer cambia latencia por memoria. Elegí 0, 1 o un N que puedas justificar.
  • Cierra el que envía, y solo si es el único. Con varios productores, WaitGroup más una goroutine cerradora. Un canal nil desactiva su rama del select: es la forma correcta de drenar dos fuentes sin quemar un núcleo.
  • context se pasa como primer parámetro, se consulta en todo lugar que bloquee y se cancela con defer cancel(). Nunca se guarda en un struct ni se usa para inyectar dependencias.
  • El canal orquesta, el candado custodia. Para proteger un contador o un mapa, Mutex o atomic; RWMutex solo con secciones de lectura largas, y midiendo.
  • Toda goroutine necesita una salida garantizada. Si envía, que sea con select sobre ctx.Done() o con buffer suficiente; si recibe, que el canal se cierre siempre. goleak convierte eso en un test.
  • Go 1.26: la variable del loop se arregló en 1.22 (pero el go.mod viejo mantiene la semántica vieja), los timers dejaron de filtrar en 1.23, wg.Go llegó en 1.25 y testing/synctest hace deterministas los tests con tiempo.
  • Un test concurrente sin -timeout no es un test: es una forma de colgar el pipeline.

🧠 Autoevaluación

1. Tu worker pool se cuelga en producción, pero go test -race -count=50 pasa limpio. ¿Qué conclusión es la correcta?

El race detector reporta accesos concurrentes sin sincronizar sobre la misma memoria. Un programa bloqueado en un canal está, por definición, perfectamente sincronizado: no hay nada que reportar. Deadlocks, fugas de goroutines y condiciones de carrera lógicas (como un Get seguido de un Set, cada uno con su candado) le son invisibles. El diagnóstico correcto es el dump —SIGQUIT, /debug/pprof/goroutine?debug=2, o el que imprime go test -timeout— leyendo el estado y los minutos de cada goroutine.

2. Cambiás un sync.Mutex por un sync.RWMutex en una caché con 95% de lecturas de un solo campo, y el throughput baja. ¿Por qué?

Tomar el candado de lectura no es gratis: incrementa y decrementa un contador de lectores que vive en una línea de caché compartida, y cada operación la invalida en el resto de los núcleos. Si la sección crítica dura decenas de nanosegundos, ese ping-pong domina el costo. RWMutex rinde cuando las lecturas son largas —microsegundos o más— y numerosas. Se resuelve midiendo con b.RunParallel y -cpu=1,4,16, no discutiendo.

3. Un pipeline tiene una etapa que hace out <- v dentro de un for, sin select. El consumidor de aguas abajo corta con un break al encontrar lo que buscaba. ¿Qué pasa?

Es la fuga clásica de pipeline. Nadie va a recibir nunca más, así que el out <- v se bloquea eternamente, y esa goroutine mantiene vivo todo lo que su closure referencia. El runtime no grita "deadlock" porque hay otras goroutines corriendo, y el GC no puede recolectar una goroutine bloqueada. Por eso la regla del pipeline es que toda etapa que envía tiene que poder rendirse: select con ctx.Done() en cada envío, y defer cancel() del lado del consumidor. goleak convierte esa regla en un test.

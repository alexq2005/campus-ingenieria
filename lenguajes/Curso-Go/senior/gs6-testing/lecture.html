GS6 — Testing serio: fuzzing, integración y tests que sirven

GS6.0 Por qué este módulo

Go trae testing en la biblioteca estándar. No hay que elegir framework, no hay que configurar nada, no hay describe ni beforeEach: escribís una función que empieza con Test, corrés go test y listo. Esa decisión de diseño es una de las mejores del lenguaje y también su trampa más común, porque como la barrera de entrada es cero, la mayoría de los equipos se queda para siempre en el primer escalón: if got != want { t.Errorf(...) }, tablas de casos y un número de coverage que se mira una vez por trimestre.

Este módulo es el resto del camino. No vamos a repetir lo que ya viste en M10 —qué es un archivo _test.go, cómo se arma una tabla— sino a responder las preguntas que aparecen cuando el código pasa a producción y empieza a romperse de maneras que tus tests no anticiparon: ¿por qué el 95% de coverage no me salvó del panic?, ¿por qué este test falla uno de cada treinta corridas en CI?, ¿este mock está probando algo o está probando al mock?, ¿cómo pruebo la query de verdad sin montar una base entera a mano?

💡 La tesis del módulo. Un test tiene valor solo si puede fallar por una razón que te importe. Las tablas prueban los casos que ya se te ocurrieron; el fuzzing prueba los que no. Los mocks prueban que tu código llama a lo que vos creés que llama; los contenedores prueban que el sistema real acepta eso. El coverage mide líneas ejecutadas, no afirmaciones hechas. Todo lo que sigue es aplicar esa distinción, herramienta por herramienta.

Trabajamos con Go 1.26. Varias de las herramientas centrales acá son relativamente recientes: el fuzzing nativo llegó en 1.18, el coverage de binarios con GOCOVERDIR en 1.20, la semántica por iteración de la variable de for en 1.22, t.Context() y t.Chdir() en 1.24 y testing/synctest se estabilizó en 1.25. Si venís de tutoriales viejos, buena parte de los workarounds que aprendiste ya no hacen falta —y alguno directamente empeora el test.

GS6.1 Table-driven a nivel senior

La tabla básica ya la conocés. Lo que separa una tabla de juguete de una tabla de producción son cuatro cosas: cómo se nombra cada caso, cómo se paraleliza, cómo se limpia y qué se compara.

Nombres que dicen algo cuando fallan

El nombre del subtest no es decoración: es lo único que vas a ver en el log de CI a las tres de la mañana. caso 3 no sirve. El nombre tiene que describir la regla de negocio que se rompió, no la entrada.

func TestNormalizarTelefono(t *testing.T) {
    casos := []struct {
        nombre  string
        entrada string
        quiero  string
        errWant bool
    }{
        {"prefijo internacional se conserva", "+54 9 11 5555-1234", "+5491155551234", false},
        {"cero y quince locales se descartan", "011 15 5555-1234", "+5491155551234", false},
        {"menos de diez digitos es invalido", "1234", "", true},
        {"letras en el medio es invalido", "11 5555 ABCD", "", true},
    }

    for _, c := range casos {
        t.Run(c.nombre, func(t *testing.T) {
            got, err := NormalizarTelefono(c.entrada)
            if (err != nil) != c.errWant {
                t.Fatalf("error = %v, esperaba error = %v", err, c.errWant)
            }
            if got != c.quiero {
                t.Errorf("NormalizarTelefono(%q) = %q, quiero %q", c.entrada, got, c.quiero)
            }
        })
    }
}
📌 t.Run no es cosmética: crea un espacio de nombres direccionable. Los espacios pasan a guiones bajos y las barras arman jerarquía, así que podés correr un caso solo: go test -run 'TestNormalizarTelefono/cero_y_quince_locales_se_descartan'. Sin t.Run, si el caso 17 falla no tenés forma de correr solo el 17, y una tabla sin subtests corta en el primer t.Fatal: perdés la información de los 23 casos que venían después.

t.Parallel() y la trampa que ya no es la que creías

Durante años, el consejo repetido fue «acordate del tc := tc», porque la variable del for se compartía entre iteraciones y todos los subtests paralelos terminaban viendo el último caso. Desde Go 1.22, si tu go.mod declara go 1.22 o superior, la variable del for es nueva en cada iteración y ese shadow sobra.

// go.mod dice: go 1.26
for _, c := range casos {
    // c := c  ← ya NO hace falta desde Go 1.22
    t.Run(c.nombre, func(t *testing.T) {
        t.Parallel()          // este subtest se suspende y sigue cuando el padre retorne
        got := Normalizar(c.entrada)
        if got != c.quiero {
            t.Errorf("got %q, quiero %q", got, c.quiero)
        }
    })
}
Cuidado con los módulos viejos. La semántica nueva está atada a la versión declarada en go.mod, no a la versión del compilador. Un repo que todavía dice go 1.21 compilado con Go 1.26 sigue con la semántica vieja y necesita el c := c. Por eso go vet mantiene el chequeo loopclosure: no lo apagues.

La trampa que sí sigue viva es otra, y es más sutil: t.Parallel() pausa el subtest hasta que la función padre retorna. Todo lo que el padre difiera con defer se ejecuta antes de que los subtests paralelos siquiera arranquen.

func TestConBaseTemporal(t *testing.T) {
    db := abrirDB(t)
    defer db.Close()          // 💣 corre ANTES que los subtests paralelos

    for _, c := range casos {
        t.Run(c.nombre, func(t *testing.T) {
            t.Parallel()
            usar(db)          // db ya está cerrada: "sql: database is closed"
        })
    }
}
func TestConBaseTemporal(t *testing.T) {
    db := abrirDB(t)
    t.Cleanup(func() { db.Close() })   // ✅ corre cuando terminan TODOS los subtests

    for _, c := range casos {
        t.Run(c.nombre, func(t *testing.T) {
            t.Parallel()
            usar(db)
        })
    }
}
El error clásico: agregar t.Parallel() a una suite que funcionaba y ver fallas erráticas de «recurso cerrado» o «archivo no existe». No es una carrera de datos en tu código: es que los defer del padre se dispararon antes de tiempo. La regla es simple y no admite excepciones: en un test que tiene subtests paralelos, la limpieza va en t.Cleanup, nunca en defer.

Slice o map: elegí a conciencia

Una tabla como map[string]caso tiene una propiedad interesante: Go aleatoriza el orden de iteración de los mapas a propósito, así que si tus casos dependen del orden entre sí, el mapa lo va a delatar. El costo es que la reproducción de una falla ya no es determinista en cuanto al orden. Para tablas puras (sin estado compartido) da lo mismo; para tablas que tocan estado, el mapa es un detector de dependencias ocultas gratis.

GS6.2 Helpers: que el error apunte a la línea correcta

Apenas la suite crece aparecen los helpers, y con ellos el problema: cuando un assert falla dentro de compararUsuario(), el reporte dice helpers_test.go:42 para los 60 casos que lo usan. Inútil. La solución es una línea:

func requiereSinError(t *testing.T, err error) {
    t.Helper()                 // ← primera línea, siempre
    if err != nil {
        t.Fatalf("error inesperado: %v", err)
    }
}

func compararUsuario(t *testing.T, got, want Usuario) {
    t.Helper()
    if got.ID != want.ID {
        t.Errorf("ID = %d, quiero %d", got.ID, want.ID)
    }
    if got.Email != want.Email {
        t.Errorf("Email = %q, quiero %q", got.Email, want.Email)
    }
}

t.Helper() marca el frame como «de infraestructura» y hace que el reporte de fallas suba en el stack hasta el primer frame que no sea helper. Funciona de forma transitiva: si un helper llama a otro y ambos declaran t.Helper(), el archivo y la línea reportados son los del test real.

Lo que t.Helper() NO arregla: llamar a t.Fatal desde otra goroutine. t.Fatalf internamente hace FailNow(), y FailNow termina la goroutine con runtime.Goexit(). Si lo llamás desde una goroutine que vos lanzaste, matás esa goroutine y el test principal sigue corriendo como si nada, muchas veces hasta pasar. Desde una goroutine solo podés usar t.Errorf (que marca la falla sin cortar) o —mejor— mandar el error por un canal y hacer el t.Fatal en la goroutine del test. 
func TestServidorAceptaConexion(t *testing.T) {
    errc := make(chan error, 1)

    go func() {
        conn, err := net.Dial("tcp", addr)
        if err != nil {
            errc <- fmt.Errorf("dial: %w", err)   // NO t.Fatal acá adentro
            return
        }
        conn.Close()
        errc <- nil
    }()

    select {
    case err := <-errc:
        if err != nil {
            t.Fatal(err)          // ✅ en la goroutine del test
        }
    case <-t.Context().Done():    // Go 1.24+: contexto cancelado antes del Cleanup
        t.Fatal("timeout esperando la conexión")
    }
}

El helper que se limpia solo

El mejor uso de t.Cleanup es dentro del helper de setup. El que crea el recurso es el que sabe cómo destruirlo, y el test que lo usa escribe una sola línea:

func nuevoRepo(t *testing.T) *Repo {
    t.Helper()
    dir := t.TempDir()                     // se borra solo al terminar el test
    r, err := AbrirRepo(filepath.Join(dir, "datos.db"))
    if err != nil {
        t.Fatalf("abrir repo: %v", err)
    }
    t.Cleanup(func() {
        if err := r.Close(); err != nil {
            t.Errorf("cerrar repo: %v", err)   // un cierre que falla ES un bug
        }
    })
    return r
}

func TestGuardarYLeer(t *testing.T) {
    r := nuevoRepo(t)                      // una línea, cero teardown a la vista
    // ...
}
Los t.Cleanup se ejecutan en orden LIFO, como los defer, y se disparan también si el test falló con t.Fatal. Un helper puede registrar varios. Y t.TempDir() ya trae su propia limpieza: nunca escribas os.MkdirTemp a mano en un test.

GS6.3 Fuzzing nativo: la sección estrella

Las tablas prueban los casos que se te ocurrieron. El problema es que los bugs que llegan a producción son, casi por definición, los que no se te ocurrieron. El fuzzing ataca exactamente ese hueco: en vez de que vos escribas las entradas, el motor las genera, las muta y usa la cobertura del código como brújula para encontrar caminos que ninguna de tus entradas alcanzó.

Anatomía de un fuzz target

func FuzzNormalizarTelefono(f *testing.F) {
    // 1. Corpus semilla: entradas conocidas, buenas y malas
    f.Add("+54 9 11 5555-1234")
    f.Add("011 15 5555-1234")
    f.Add("")
    f.Add("+")

    // 2. La propiedad que tiene que valer SIEMPRE
    f.Fuzz(func(t *testing.T, entrada string) {
        got, err := NormalizarTelefono(entrada)
        if err != nil {
            return                 // rechazar entradas inválidas es correcto
        }
        // Si dijo que sí, el resultado tiene que cumplir el contrato:
        if !strings.HasPrefix(got, "+") {
            t.Fatalf("normalizó %q a %q, sin prefijo +", entrada, got)
        }
        // Y tiene que ser idempotente:
        otra, err := NormalizarTelefono(got)
        if err != nil || otra != got {
            t.Fatalf("no es idempotente: %q → %q → (%q, %v)", entrada, got, otra, err)
        }
    })
}

Fijate el cambio de mentalidad. Una tabla afirma «esta entrada da esta salida». Un fuzz target afirma «pase lo que pase, esta propiedad se cumple». No sabés qué te va a mandar el motor, así que no podés predecir la salida: solo podés declarar invariantes. Los tres invariantes más productivos en la práctica son:

  • No panic. Ni siquiera hace falta escribir un assert: si la función explota, el test falla. Es el invariante más barato y el que más bugs encuentra.
  • Round-trip. Parse(Render(x)) == x, Decode(Encode(x)) == x, Descomprimir(Comprimir(b)) == b. Cualquier par codificador/decodificador tiene esta propiedad y es donde el fuzzing brilla.
  • Diferencial. Tu implementación nueva y rápida tiene que dar exactamente lo mismo que la vieja y lenta, para toda entrada.

Cómo se corre (y por qué el comando importa)

# Sin -fuzz: el target corre como test normal, solo contra el corpus semilla
# y contra testdata/. Esto es lo que corre en CI en cada commit.
go test ./...

# Con -fuzz: arranca el motor de mutación. Corre hasta que encuentra algo
# o hasta que se acaba el tiempo. NUNCA lo pongas así en CI.
go test -fuzz=FuzzNormalizarTelefono -fuzztime=60s ./telefono

# Combinado con el detector de carreras (más lento, encuentra más)
go test -fuzz=FuzzParse -fuzztime=5m -race ./parser
📌 Un fuzz target tiene dos vidas. Sin -fuzz es un test determinista que corre el corpus semilla y todo lo que haya en testdata/fuzz/<Target>/: rapidísimo, apto para CI en cada push. Con -fuzz es una sesión de búsqueda que puede durar minutos u horas. La forma correcta de usarlo en un equipo es: CI corre la primera vida siempre, y un job nocturno (o una corrida manual antes de un release) corre la segunda.

El corpus: semilla, caché y testdata

Hay dos corpus y confundirlos es la causa número uno de «me funcionó local y en CI no».

CorpusDónde viveVa al repoPara qué
Semillaf.Add(...) + testdata/fuzz/<Target>/SíPunto de partida del motor y suite de regresión determinista
Generado$GOCACHE/fuzz (caché de build)NoEntradas interesantes que el motor descubrió; se pierde al limpiar la caché

Cuando el motor encuentra una entrada que rompe algo, hace dos cosas valiosas: la minimiza (recorta bytes mientras siga fallando, así te queda el caso mínimo y no un blob de 4 KB) y la escribe en testdata/. Ese archivo es texto plano y se commitea:

$ cat testdata/fuzz/FuzzParse/8f2a1c7d3b9e04f1
go test fuzz v1
string("clave=valor\\")
💡 Acá está el círculo virtuoso. El bug encontrado por fuzzing se convierte, automáticamente y sin que escribas una línea, en un test de regresión determinista que va a correr en cada go test para siempre. No tenés que acordarte de agregar el caso a la tabla: el motor ya lo hizo. Un repo maduro tiene testdata/fuzz/ lleno de archivitos crípticos, y cada uno es un bug real que ya no puede volver.

Qué encuentra el fuzzing que las tablas no

Esta es la pregunta importante, y la respuesta no es «entradas raras» sino tres clases concretas de bug que las tablas sistemáticamente se pierden:

1. Índices fuera de rango en máquinas de estado sobre bytes. Cualquier parser que haga i++ adentro de un loop y después lea s[i] tiene un agujero en el borde derecho de la entrada. Vos escribís casos «con escape» y «sin escape»; nunca escribís el caso «la entrada termina justo en el medio de un escape», porque no es un caso de negocio: es un caso de implementación. El motor lo encuentra en segundos porque es la mutación más obvia (truncar).

2. Round-trips que no cierran. Tu Render escribe un valor con espacios sin comillar, tu Parse lo lee y devuelve otra cosa. Con casos elegidos a mano el round-trip siempre cierra, porque elegís valores prolijos. El motor prueba con "a=b=c", con "\n" adentro de un valor, con una clave vacía, con UTF-8 inválido.

3. Diferencias de unicode y bytes. Recorrer un string con for i := 0; i < len(s); i++ te da bytes; recorrerlo con for _, r := range s te da runas. Mezclar los dos en la misma función es un bug garantizado con entrada no-ASCII, y el motor genera basura no-ASCII todo el tiempo.

Límites: qué tipos acepta f.Fuzz

El primer parámetro es siempre *testing.T. Los siguientes solo pueden ser: []byte, string, cualquier entero con y sin signo, float32/float64, bool, rune y byte. No hay structs, ni slices de structs, ni maps, ni interfaces.

// ✅ válido
f.Fuzz(func(t *testing.T, datos []byte, limite int, activo bool) { ... })

// ❌ no compila: "fuzzing arguments can only have the following types: ..."
f.Fuzz(func(t *testing.T, u Usuario) { ... })
Los tipos del f.Add tienen que coincidir exactamente con la firma del f.Fuzz. Si la función toma []byte y hacés f.Add("hola"), el test hace panic al arrancar. Escribí f.Add([]byte("hola")). Y si el target toma tres parámetros, cada f.Add tiene que pasar los tres.

GS6.4 Property-based testing en Go

El fuzzing nativo es property-based testing, pero de un sabor particular: guiado por cobertura, con minimización, con corpus persistente… y sin generadores de tipos estructurados. Esa es exactamente la línea que divide lo que podés hacer con la stdlib y lo que necesita librería.

Truco: derivar la estructura de los bytes

Si querés fuzzear una función que toma un struct, la salida idiomática es tomar []byte y construir el struct de forma determinista a partir de esos bytes. Es lo mismo que hacen las librerías por debajo:

func FuzzAplicarDescuento(f *testing.F) {
    f.Add([]byte{10, 0, 3})

    f.Fuzz(func(t *testing.T, datos []byte) {
        if len(datos) < 3 {
            t.Skip()          // entrada demasiado corta: no es un fallo
        }
        p := Pedido{
            Items:     int(datos[0]),
            Cupon:     string(datos[1:2]),
            Categoria: Categoria(datos[2] % 4),
        }

        total := AplicarDescuento(p, 1000)

        // Propiedad de negocio: el descuento nunca puede dar negativo
        // ni superar el total original.
        if total < 0 || total > 1000 {
            t.Fatalf("descuento fuera de rango: pedido=%+v total=%d", p, total)
        }
    })
}
Usá t.Skip() —no return a secas y nunca t.Fatal— para descartar entradas que no cumplen la precondición. El motor entiende el skip como «esta entrada no aporta» y no la guarda en el corpus, con lo cual no ensucia la búsqueda.

Cuándo necesitás una librería

Cuando la propiedad involucra estructuras generadas con forma —un árbol balanceado, un slice de longitud entre 3 y 10 con elementos únicos, una secuencia de comandos válidos contra una máquina de estados— derivar de bytes se vuelve tan feo que oscurece la propiedad. Ahí entra pgregory.net/rapid, que sí tiene generadores composables y shrinking sobre los valores generados, no sobre los bytes:

import "pgregory.net/rapid"

func TestColaMantieneOrdenFIFO(t *testing.T) {
    rapid.Check(t, func(t *rapid.T) {
        n := rapid.IntRange(1, 100).Draw(t, "n")
        vals := rapid.SliceOfN(rapid.Int(), n, n).Draw(t, "vals")

        q := NuevaCola[int]()
        for _, v := range vals {
            q.Push(v)
        }
        for i, quiero := range vals {
            got, ok := q.Pop()
            if !ok || got != quiero {
                t.Fatalf("Pop #%d = (%v, %v), quiero %v", i, got, ok, quiero)
            }
        }
    })
}
Y no uses testing/quick. Está en la stdlib, tiene la forma de una librería property-based y está congelado: no recibe features nuevas, no minimiza y su generador es aleatorio puro, sin guía de cobertura. Si buscás en internet «property based testing golang» vas a encontrarlo en tutoriales viejos. Para casos sobre bytes/strings usá testing.F; para estructuras, rapid.

GS6.5 Interfaces para testear: definilas en el consumidor

En GS4 vimos la regla estructural: en Go las interfaces se satisfacen implícitamente, así que quien define la interfaz no tiene que ser quien la implementa. La consecuencia para el testing es enorme y casi nadie la aprovecha.

// ❌ El patrón que viene de Java: interfaz gigante junto a la implementación
package almacen

type Almacen interface {
    Guardar(context.Context, Usuario) error
    Buscar(context.Context, int64) (Usuario, error)
    Listar(context.Context, Filtro) ([]Usuario, error)
    Borrar(context.Context, int64) error
    Contar(context.Context) (int, error)
    Migrar(context.Context) error
    // ...11 métodos más
}

Si tu servicio de notificaciones solo necesita buscar, con esa interfaz estás obligado a implementar dieciséis métodos para poder testear uno. De ahí nace la industria de los generadores de mocks: la interfaz es tan grande que a mano es inviable.

// ✅ El patrón Go: la interfaz la declara quien la consume, con lo mínimo
package notificaciones

type buscadorUsuarios interface {
    Buscar(ctx context.Context, id int64) (Usuario, error)
}

type Servicio struct {
    usuarios buscadorUsuarios          // acepta interfaces...
}

func NuevoServicio(u buscadorUsuarios) *Servicio {   // ...devuelve structs
    return &Servicio{usuarios: u}
}

Ahora el doble de prueba es esto, completo:

type buscadorStub struct {
    fn func(context.Context, int64) (Usuario, error)
}

func (b buscadorStub) Buscar(ctx context.Context, id int64) (Usuario, error) {
    return b.fn(ctx, id)
}

func TestNotificaSoloAVerificados(t *testing.T) {
    s := NuevoServicio(buscadorStub{
        fn: func(_ context.Context, id int64) (Usuario, error) {
            return Usuario{ID: id, Verificado: false}, nil
        },
    })
    // ...
}
📌 Interfaz chica en el consumidor = el 80% de los mocks se vuelve innecesario. La interfaz de un método se implementa a mano en cuatro líneas, con un campo función que cada test define como quiera. No hay go:generate, no hay archivo generado de 400 líneas que hay que regenerar cuando cambia una firma, no hay dependencia nueva. Y como bonus: la interfaz chica documenta exactamente qué necesita ese paquete del mundo exterior.

GS6.6 Fakes contra mocks

Los términos se usan mal todo el tiempo, así que fijemos vocabulario porque la diferencia decide la calidad de la suite:

DobleQué haceContra qué verifica
StubDevuelve valores fijosEl resultado de tu código
FakeImplementación real pero simplificada (un map en vez de Postgres)El resultado de tu código, con estado coherente
MockRegistra llamadas y afirma sobre ellasCómo tu código usó la dependencia

Go, culturalmente, prefiere el fake escrito a mano, y hay una razón técnica además de la cultural: un mock verifica interacción, y la interacción es un detalle de implementación. El día que refactorizás Guardar para que haga un upsert en vez de Buscar + Insertar, el comportamiento observable no cambió pero doscientos tests con mocks se ponen rojos. Eso no es una red de seguridad: es un impuesto.

// Fake con estado: se comporta como el almacén real, en memoria.
type almacenFake struct {
    mu     sync.Mutex
    datos  map[int64]Usuario
    fallar error            // para forzar el camino de error cuando hace falta
}

func nuevoAlmacenFake() *almacenFake {
    return &almacenFake{datos: make(map[int64]Usuario)}
}

func (a *almacenFake) Guardar(_ context.Context, u Usuario) error {
    a.mu.Lock()
    defer a.mu.Unlock()
    if a.fallar != nil {
        return a.fallar
    }
    if _, existe := a.datos[u.ID]; existe {
        return ErrDuplicado          // el fake respeta las MISMAS reglas
    }
    a.datos[u.ID] = u
    return nil
}

func (a *almacenFake) Buscar(_ context.Context, id int64) (Usuario, error) {
    a.mu.Lock()
    defer a.mu.Unlock()
    u, ok := a.datos[id]
    if !ok {
        return Usuario{}, ErrNoEncontrado
    }
    return u, nil
}
El mutex del fake no es paranoia. Si tus tests corren con t.Parallel() o si el código bajo prueba usa goroutines, un fake con un map desnudo dispara un fallo del detector de carreras y vas a perder media hora creyendo que el bug está en tu código. Poné el mutex desde el principio.

Cuándo sí vale generar mocks

  • Interfaces que no controlás y son enormes: el SDK de AWS, un cliente gRPC generado con 40 métodos. Escribir eso a mano no es disciplina, es masoquismo — mockery o moq ahí ganan.
  • Cuando la interacción ES el requisito: «no se puede llamar al gateway de pagos dos veces con el mismo idempotency key» es una afirmación sobre llamadas, y verificarla necesita un espía.
  • Contratos que hay que auditar: en sistemas regulados, demostrar que se emitió exactamente un evento de auditoría por operación es parte del requisito.

Fuera de esos tres casos, el fake gana casi siempre. Y hay una prueba de olfato infalible: si borrás el código de producción y todos tus tests siguen pasando porque solo hablan con mocks, tus tests no prueban nada.

GS6.7 httptest: los dos modos y cuándo usar cada uno

El paquete net/http/httptest resuelve dos problemas distintos y la mayoría usa uno solo.

Modo 1 — ResponseRecorder: probar tu handler sin red

func TestHandlerUsuario(t *testing.T) {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /usuarios/{id}", handlerUsuario)   // Go 1.22+: patrón con método

    req := httptest.NewRequest(http.MethodGet, "/usuarios/42", nil)
    rec := httptest.NewRecorder()

    mux.ServeHTTP(rec, req)          // ← por el MUX, no el handler directo

    res := rec.Result()
    defer res.Body.Close()

    if res.StatusCode != http.StatusOK {
        t.Fatalf("status = %d, quiero 200", res.StatusCode)
    }
    var u Usuario
    if err := json.NewDecoder(res.Body).Decode(&u); err != nil {
        t.Fatalf("decodificar respuesta: %v", err)
    }
    if u.ID != 42 {
        t.Errorf("ID = %d, quiero 42", u.ID)
    }
}
La trampa de r.PathValue. Los wildcards del router de Go 1.22 ({id}) los completa el ServeMux, no el request. Si llamás handlerUsuario(rec, req) directo, r.PathValue("id") devuelve "" y el test o falla misteriosamente o —peor— pasa por un camino de error que no querías probar. O pasás por el mux, o usás req.SetPathValue("id", "42") explícitamente.

Modo 2 — NewServer: probar tu cliente contra HTTP real

El recorder es un objeto en memoria: no hay TCP, no hay serialización de headers, no hay timeouts, no hay redirecciones, no hay compresión. Para probar el otro lado —tu cliente HTTP, el que consume una API ajena— necesitás un servidor de verdad:

func TestClienteReintentaEn503(t *testing.T) {
    var intentos atomic.Int32

    srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if intentos.Add(1) < 3 {
            w.WriteHeader(http.StatusServiceUnavailable)
            return
        }
        w.Header().Set("Content-Type", "application/json")
        fmt.Fprint(w, `{"estado":"ok"}`)
    }))
    t.Cleanup(srv.Close)

    c := NuevoCliente(srv.URL, ConMaxReintentos(5))

    estado, err := c.Estado(t.Context())
    if err != nil {
        t.Fatalf("Estado(): %v", err)
    }
    if estado != "ok" {
        t.Errorf("estado = %q, quiero \"ok\"", estado)
    }
    if n := intentos.Load(); n != 3 {
        t.Errorf("intentos = %d, quiero 3", n)
    }
}
Para HTTPS usá httptest.NewTLSServer y —clave— srv.Client(), que devuelve un *http.Client ya configurado para confiar en el certificado autofirmado del server de prueba. Es infinitamente mejor que la solución que aparece en Stack Overflow, que es poner InsecureSkipVerify: true y arriesgarse a que ese flag se filtre al código de producción por copiar y pegar.

GS6.8 Testcontainers: dejar de mentirle a la base de datos

Un fake en memoria del repositorio prueba tu lógica. Lo que no prueba es el SQL: ni que la query compile, ni que el índice único exista, ni que el ON CONFLICT haga lo que creés, ni cómo se comporta el driver con un NULL en una columna time.Time, ni si esa transacción entra en deadlock bajo concurrencia. Esos son, casualmente, la mayoría de los bugs reales de la capa de datos.

testcontainers-go levanta el Postgres, el Redis o el Kafka de verdad en un contenedor descartable, desde el propio test:

//go:build integration

package repo_test

import (
    "context"
    "database/sql"
    "testing"

    "github.com/testcontainers/testcontainers-go"
    "github.com/testcontainers/testcontainers-go/modules/postgres"
    "github.com/testcontainers/testcontainers-go/wait"
)

func nuevaDBReal(t *testing.T) *sql.DB {
    t.Helper()
    ctx := context.Background()

    ctr, err := postgres.Run(ctx, "postgres:17-alpine",
        postgres.WithDatabase("app"),
        postgres.WithUsername("test"),
        postgres.WithPassword("test"),
        testcontainers.WithWaitStrategy(
            wait.ForLog("database system is ready to accept connections").
                WithOccurrence(2),
        ),
    )
    if err != nil {
        t.Fatalf("levantar postgres: %v", err)
    }
    testcontainers.CleanupContainer(t, ctr)   // registra el Terminate en t.Cleanup

    dsn, err := ctr.ConnectionString(ctx, "sslmode=disable")
    if err != nil {
        t.Fatalf("connection string: %v", err)
    }
    db, err := sql.Open("pgx", dsn)
    if err != nil {
        t.Fatalf("abrir db: %v", err)
    }
    t.Cleanup(func() { db.Close() })

    if err := Migrar(ctx, db); err != nil {   // las MISMAS migraciones de producción
        t.Fatalf("migrar: %v", err)
    }
    return db
}
El WithOccurrence(2) no es un detalle. La imagen oficial de Postgres arranca, corre los scripts de inicialización, se apaga y vuelve a arrancar. El log «ready to accept connections» aparece dos veces. Si esperás la primera, te conectás justo antes del reinicio y tenés un test flaky que falla el 5% de las veces con «connection refused». Este error específico es el rito de iniciación de todo el que usa testcontainers.

var dbCompartida *sql.DB

func TestMain(m *testing.M) {
    // Setup una sola vez para todo el paquete.
    ctr, db, limpiar := levantarPostgres()
    dbCompartida = db

    codigo := m.Run()      // corre todos los tests del paquete

    limpiar()              // ojo: os.Exit NO corre defers, por eso la llamada explícita
    _ = ctr
    os.Exit(codigo)
}

// Cada test corre adentro de una transacción que nunca se commitea.
func conTx(t *testing.T) *sql.Tx {
    t.Helper()
    tx, err := dbCompartida.BeginTx(t.Context(), nil)
    if err != nil {
        t.Fatalf("begin: %v", err)
    }
    t.Cleanup(func() { tx.Rollback() })   // aislamiento perfecto y gratis
    return tx
}
El costo de CI es real y hay que decidirlo, no descubrirlo. Testcontainers necesita un demonio Docker disponible en el runner, tira imágenes de la red (cacheálas o el CI paga 30 s por corrida) y levanta además un contenedor reaper (Ryuk) que limpia lo que quede huérfano. En runners sin Docker-in-Docker no funciona. Nada de esto lo hace mala idea: lo hace una decisión de infraestructura que tenés que tomar antes de escribir 80 tests que dependen de eso.

GS6.9 Build tags: separar la suite rápida de la lenta

Si los tests de integración corren con go test ./..., en dos meses nadie corre go test antes de commitear porque tarda cuatro minutos. Y una suite que no se corre no existe. La separación es obligatoria.

//go:build integration

package repo_test
# Suite rápida: por defecto los archivos con el tag ni se compilan
go test ./...                       # ~3 s

# Suite de integración: explícita
go test -tags=integration ./...     # ~90 s

# En CI: la rápida en cada push, la lenta en el merge a main
El defecto del build tag: el código etiquetado se pudre en silencio. Como el compilador ni lo mira sin el tag, podés renombrar un método y romper 40 tests de integración sin que nada te avise: go build ./... pasa, go vet ./... pasa, el editor a veces ni resalta el archivo. La contramedida es obligatoria en CI: go vet -tags=integration ./... en cada push, aunque los tests en sí solo corran en el merge. Compilar es barato; ejecutar es lo caro.

La alternativa: testing.Short()

func TestGuardarUsuarioContraPostgres(t *testing.T) {
    if testing.Short() {
        t.Skip("requiere Docker; correr sin -short")
    }
    db := nuevaDBReal(t)
    // ...
}
go test -short ./...    # saltea los pesados, pero los COMPILA todos

📌 Regla práctica: testing.Short() cuando la diferencia es solo de tiempo (un test que tarda 8 segundos); build tag cuando el archivo arrastra dependencias que no querés en el módulo principal (testcontainers se lleva puesto medio Docker SDK). Y si usás tags, el vet -tags en CI no es opcional.

GS6.10 Fugas de goroutines y -race: los dos chequeos innegociables

En GS1 y GS3 vimos que una goroutine bloqueada para siempre en un canal sin receptor no la limpia nadie: no hay GC de goroutines. En producción eso es una fuga que se ve recién a las seis horas, cuando la memoria del pod se dispara. En un test es invisible… salvo que lo mires.

import "go.uber.org/goleak"

// Verifica el paquete entero: si al terminar TODOS los tests quedan
// goroutines vivas que no estaban al inicio, falla.
func TestMain(m *testing.M) {
    goleak.VerifyTestMain(m)
}
// O por test, cuando querés precisión sobre quién filtra.
func TestWorkerCierraAlCancelar(t *testing.T) {
    defer goleak.VerifyNone(t)

    ctx, cancel := context.WithCancel(t.Context())
    w := NuevoWorker(ctx)
    w.Encolar("tarea")
    cancel()
    w.Esperar()          // si Esperar() no espera de verdad, goleak lo delata
}
Librerías legítimas dejan goroutines de fondo (el Transport de net/http, clientes de base con pool, exportadores de métricas). Para eso están goleak.IgnoreTopFunction("...") y goleak.IgnoreCurrent() —esta última tomada después del setup, para ignorar lo que ya existía. Lo que no hay que hacer es borrar goleak porque «tira falsos positivos»: cada ignore es una decisión documentada.

-race: siempre, sin excepciones

# Lo que corre CI, siempre:
go test -race -shuffle=on ./...

# Para cazar un flaky: repetir sin caché
go test -race -count=20 -run TestSospechoso ./paquete
El detector de carreras no encuentra carreras: encuentra carreras que ocurrieron. Es un análisis dinámico, no estático. Si el test nunca ejecuta las dos goroutines conflictivas al mismo tiempo, no reporta nada. Por eso -race tiene que combinarse con t.Parallel(), con -count=N y con fuzzing: hay que generar el concurrente para que el detector tenga qué observar. El costo es 2–20× en tiempo y 5–10× en memoria, y aun así vale cada centavo.

GS6.11 Coverage: por qué el porcentaje engaña

Go mide cobertura de sentencias: qué porcentaje de las líneas ejecutables corrió durante el test. Nada más. Concretamente, esto da 100%:

func TestCalcular(t *testing.T) {
    Calcular(10, 3)     // se ejecutó todo el cuerpo. Cero afirmaciones.
}

Y esto también, aunque la función tenga un bug obvio en una de las ramas de una condición compuesta:

func Permitir(u Usuario, r Recurso) bool {
    // El test cubre la línea con un caso donde ambas son true.
    // La rama "activo pero sin permiso" nunca se evaluó, y la línea
    // figura como cubierta al 100%.
    return u.Activo && u.TienePermiso(r)
}
💡 Lo que el número mide y lo que vos querés saber son cosas distintas. El coverage responde «¿esta línea se ejecutó?». Vos querés responder «si rompo esta línea, ¿algún test se pone rojo?». La distancia entre esas dos preguntas es donde viven los bugs de producción de código con 95% de cobertura. Un 40% con asserts serios vale más que un 95% de tests que solo llaman funciones.

Los comandos que sí sirven

# El número global no dice nada. El reporte por función, sí.
go test -coverprofile=cover.out ./...
go tool cover -func=cover.out | sort -k3 -n | head -20   # lo MENOS cubierto primero

# Visual: ver exactamente qué líneas quedaron rojas
go tool cover -html=cover.out

# Por defecto solo mide el paquete bajo test. Para medir lo que un test
# de integración toca en OTROS paquetes:
go test -coverpkg=./... -coverprofile=cover.out ./tests/integracion

# Con -race o subtests paralelos hace falta modo atómico
go test -race -covermode=atomic -coverprofile=cover.out ./...

Coverage de integración con GOCOVERDIR

Desde Go 1.20 podés instrumentar el binario, no el test. Eso te deja medir qué código toca realmente un test end-to-end que arranca tu servidor como proceso, o incluso una sesión de QA manual:

# 1. Compilar el binario instrumentado
go build -cover -o bin/api ./cmd/api

# 2. Correrlo con un directorio donde volcar los datos
mkdir -p /tmp/cov
GOCOVERDIR=/tmp/cov ./bin/api &
#    ...correr la suite end-to-end, el k6, lo que sea...
kill -INT $!          # el volcado se escribe al terminar limpiamente

# 3. Leer los resultados
go tool covdata percent -i=/tmp/cov
go tool covdata textfmt -i=/tmp/cov -o=cover-e2e.out
go tool cover -html=cover-e2e.out
Este es el uso honesto del coverage: no como métrica de vanidad, sino como detector de código muerto. Si después de correr toda la suite end-to-end y una semana de staging hay un paquete entero en 0%, la pregunta correcta no es «¿le escribo tests?» sino «¿para qué existe?».

GS6.12 Golden files: cuándo son la herramienta correcta

Un golden file es una salida esperada guardada en disco: el test genera la salida real y la compara byte a byte contra el archivo. El patrón canónico incluye un flag para regenerarlos:

var actualizar = flag.Bool("update", false, "regenerar los golden files")

func TestRenderizarFactura(t *testing.T) {
    casos := []string{"minima", "con_descuento", "multi_moneda"}

    for _, nombre := range casos {
        t.Run(nombre, func(t *testing.T) {
            entrada := cargarFixture(t, nombre+".json")
            got := Renderizar(entrada)

            golden := filepath.Join("testdata", nombre+".golden")
            if *actualizar {
                if err := os.WriteFile(golden, got, 0o644); err != nil {
                    t.Fatalf("escribir golden: %v", err)
                }
            }
            want, err := os.ReadFile(golden)
            if err != nil {
                t.Fatalf("leer golden: %v", err)
            }
            if diff := cmp.Diff(string(want), string(got)); diff != "" {
                t.Errorf("salida distinta (-quiero +tengo):\n%s", diff)
            }
        })
    }
}
go test ./render -update    # regenerar. Después: git diff, y REVISAR el diff.
✅ Son la herramienta correcta cuando…❌ Se vuelven un lastre cuando…
La salida es grande y estructurada (HTML, SQL generado, código generado, un plan de query)La salida tiene timestamps, UUIDs, orden de map o rutas absolutas: el test es flaky por diseño
Escribir el want a mano sería ilegibleEl diff es tan grande que nadie lo lee y -update se vuelve un reflejo
Lo que importa es «esto no cambió sin querer»Lo que importa es «esto cumple tal regla»: ahí querés un assert específico, no un diff
El diff es la mejor explicación posible del falloUn cambio cosmético legítimo rompe 200 goldens y todos se aprueban a ciegas
Si usás golden files, normalizá la salida antes de comparar. Reemplazá timestamps por <TS>, IDs generados por <ID>, ordená las claves del JSON. Un golden no determinista no es un test: es un generador de merge conflicts. Y regla de oro: el diff de un -update se revisa en el PR con la misma atención que el código, porque es literalmente la definición del comportamiento correcto.

GS6.13 Qué NO testear

La suite tiene un costo de mantenimiento permanente. Cada test que no puede fallar por una razón interesante es peso muerto que frena cada refactor futuro.

  • La biblioteca estándar. json.Marshal funciona. time.Parse funciona. Testear que strings.Split parte por comas no es un test: es un homenaje.
  • Getters, setters y constructores triviales. Si func (u Usuario) Nombre() string { return u.nombre } tiene un test propio, el test es una copia de la implementación. Se cubren solos cuando los usa un test real.
  • El framework. No pruebes que ServeMux rutea, que el ORM genera SQL o que el driver se conecta. Probá tu handler, tu query, tu mapeo.
  • El mock. Si un test configura un mock para que devuelva X y después verifica que el código recibió X, probaste el mock. Ese test pasa aunque borres la lógica del medio.
  • Los detalles privados que cambian en cada refactor. Testeá contra la superficie exportada del paquete. La pista está en el nombre del archivo: preferí package foo_test (test externo) sobre package foo; te obliga a probar lo que ven los demás.
  • El 100% de coverage. El tramo del 85% al 100% se paga casi entero en tests de ramas de error irreproducibles, y esos tests son los que más se rompen.

GS6.14 Flaky tests: causas típicas en Go y cómo se arreglan de raíz

Un test que falla una de cada treinta veces es peor que no tener test, porque entrena al equipo a ignorar el rojo. La reacción de reintentar (--retries 3) no arregla nada: esconde un bug que casi siempre también existe en producción. Estas son las cinco causas y su cura real.

1. Tiempo real

// ❌ Flaky garantizado: en un CI cargado, 100ms no alcanzan.
func TestCacheExpira(t *testing.T) {
    c := NuevoCache(50 * time.Millisecond)
    c.Set("k", "v")
    time.Sleep(100 * time.Millisecond)
    if _, ok := c.Get("k"); ok {
        t.Error("debería haber expirado")
    }
}

La cura moderna es testing/synctest, estable desde Go 1.25: corre el código en una «burbuja» con reloj falso, donde time.Sleep es instantáneo y el tiempo solo avanza cuando todas las goroutines de la burbuja están bloqueadas.

import "testing/synctest"

func TestCacheExpira(t *testing.T) {
    synctest.Test(t, func(t *testing.T) {
        c := NuevoCache(50 * time.Millisecond)
        c.Set("k", "v")

        time.Sleep(100 * time.Millisecond)   // instantáneo: reloj virtual
        synctest.Wait()                      // esperar a que todo se estabilice

        if _, ok := c.Get("k"); ok {
            t.Error("debería haber expirado")
        }
    })
}
📌 synctest cambia el cálculo por completo. Un test de timeouts, reintentos con backoff exponencial o expiración de sesiones que antes tardaba 30 segundos reales (y era flaky) ahora tarda milisegundos y es determinista. Si tu suite tiene time.Sleep desparramados, esta es la única sección del módulo que te va a devolver el tiempo invertido esta misma semana.

2. Orden de iteración de los maps

// ❌ El orden de un map es aleatorio POR DISEÑO en Go.
got := clavesDe(m)
if !reflect.DeepEqual(got, []string{"a", "b", "c"}) { ... }

// ✅ Ordenar antes de comparar...
slices.Sort(got)

// ✅ ...o comparar sin importar el orden
if diff := cmp.Diff(want, got, cmpopts.SortSlices(func(a, b string) bool {
    return a < b
})); diff != "" {
    t.Errorf("claves (-quiero +tengo):\n%s", diff)
}

3. Puertos y recursos fijos

// ❌ Dos tests en paralelo (o un CI con otro job) chocan: "address already in use"
ln, _ := net.Listen("tcp", "127.0.0.1:8080")

// ✅ Puerto 0 = "dame cualquiera libre", y preguntás cuál te tocó
ln, err := net.Listen("tcp", "127.0.0.1:0")
if err != nil {
    t.Fatalf("listen: %v", err)
}
t.Cleanup(func() { ln.Close() })
addr := ln.Addr().String()      // ej: 127.0.0.1:54312

Lo mismo con archivos: t.TempDir() siempre, nunca /tmp/test.db. Y con variables de entorno: t.Setenv(), que restaura el valor al terminar —y que, ojo, hace panic a propósito si el test llamó a t.Parallel(), porque el entorno es global al proceso y no se puede aislar por test.

4. Estado global compartido entre tests

Un var registroGlobal = map[string]Handler{} a nivel de paquete, un singleton con sync.Once, una conexión reutilizada: el test A deja algo escrito y el test B pasa solo si corre después. La cura tiene dos partes. La primera es de diagnóstico:

go test -shuffle=on ./...        # aleatoriza el orden y muestra la semilla
go test -shuffle=1730000000 ./...  # reproducir exactamente esa corrida

La segunda es de diseño: si el orden importa, el problema no es el test sino el estado global. Pasá la dependencia por parámetro en vez de leerla de un var de paquete.

5. Paralelismo mal declarado

Ya lo vimos con los defer, pero hay una variante más: t.Parallel() en un subtest que escribe en una variable capturada del padre. El detector de carreras lo agarra, pero solo si corrés con -race. Sin él, el síntoma es un valor incorrecto una vez cada tanto.

Protocolo para un flaky, en orden. (1) Reproducilo: go test -race -count=50 -run TestX ./pkg. (2) Si no reproduce, agregá -shuffle=on y corré el paquete entero: es dependencia de orden. (3) Si aparece solo en CI, es tiempo o recursos: buscá time.Sleep y puertos fijos. (4) Arreglá la causa. Nunca pongas un t.Skip «temporal» ni subas el sleep de 100 ms a 500 ms: eso no elimina el flaky, lo vuelve más raro y por lo tanto más caro de encontrar.

GS6.15 Worked Example: 95% de coverage, 40 casos en tabla, y un panic en producción

Tenemos un paquete kvconf que parsea un formato de configuración propio. Es viejo, es central, y tiene una tabla de 40 casos y 95,2% de coverage. El equipo lo considera sólido. La semana pasada tiró un panic en producción.

Paso 1 — El código

package kvconf

type Entrada struct {
    Seccion string
    Clave   string
    Valor   string
}

func Parse(src string) ([]Entrada, error) {
    var out []Entrada
    seccion := ""
    for n, linea := range strings.Split(src, "\n") {
        linea = strings.TrimSpace(linea)
        if linea == "" || strings.HasPrefix(linea, "#") {
            continue
        }
        if strings.HasPrefix(linea, "[") && strings.HasSuffix(linea, "]") {
            seccion = linea[1 : len(linea)-1]
            continue
        }
        clave, valor, ok := strings.Cut(linea, "=")
        if !ok {
            return nil, fmt.Errorf("línea %d: falta '='", n+1)
        }
        out = append(out, Entrada{
            Seccion: seccion,
            Clave:   strings.TrimSpace(clave),
            Valor:   desescapar(strings.TrimSpace(valor)),
        })
    }
    return out, nil
}

func desescapar(s string) string {
    var b strings.Builder
    for i := 0; i < len(s); i++ {
        if s[i] == '\\' {
            i++                    // avanzar al carácter escapado
            switch s[i] {          // 💣 si '\' era el último byte: index out of range
            case 'n':
                b.WriteByte('\n')
            case 't':
                b.WriteByte('\t')
            default:
                b.WriteByte(s[i])
            }
            continue
        }
        b.WriteByte(s[i])
    }
    return b.String()
}

El bug está a la vista una vez que sabés dónde mirar: i++ seguido de s[i] sin comprobar que i siga dentro del slice. Los 40 casos de la tabla incluyen "a=b\\nc", "a=b\\tc", "a=b\\\\c"… todos con algo después de la barra, porque escribir un escape colgando al final no es algo que a nadie se le ocurra a mano. Y como la línea switch s[i] sí se ejecuta en los 40 casos, figura como cubierta. El 95,2% es real y es inútil.

Paso 2 — El fuzz target (9 líneas)

func FuzzParse(f *testing.F) {
    // Semillas: reusamos algunos casos de la tabla que ya existía.
    f.Add("clave=valor")
    f.Add("[seccion]\nclave=valor")
    f.Add("# comentario\na=b\\nc")
    f.Add("")

    f.Fuzz(func(t *testing.T, src string) {
        entradas, err := Parse(src)     // invariante 1: NO PANIC
        if err != nil {
            return
        }
        // invariante 2: round-trip
        vuelta, err := Parse(Render(entradas))
        if err != nil {
            t.Fatalf("Render produjo algo que Parse rechaza: %v\nentrada: %q", err, src)
        }
        if !slices.Equal(entradas, vuelta) {
            t.Fatalf("round-trip roto\nsrc:    %q\nprimera: %+v\nsegunda: %+v",
                src, entradas, vuelta)
        }

func desescapar(s string) string {
    var b strings.Builder
    for i := 0; i < len(s); i++ {
        if s[i] == '\\' {
            if i+1 >= len(s) {
                b.WriteByte('\\')   // barra final literal: decisión explícita
                break
            }
            i++
            switch s[i] {
            case 'n':
                b.WriteByte('\n')
            case 't':
                b.WriteByte('\t')
            default:
                b.WriteByte(s[i])
            }
            continue
        }
        b.WriteByte(s[i])
    }
    return b.String()
}

Checkpoint — ¿lo tenés claro?

Tenés 95% de coverage y aun así te entró un panic a producción. ¿Qué te está midiendo ese número y qué no?

Mide cobertura de sentencias: qué porcentaje de las líneas ejecutables se ejecutó alguna vez durante la suite. No mide si hubo asserts, no mide cobertura de ramas dentro de una condición compuesta (a && b cuenta como cubierta con solo evaluar un caso), y no mide si un test se pondría rojo al romper esa línea. En el ejemplo de desescapar, la línea switch s[i] se ejecutaba en los 40 casos de la tabla y figuraba cubierta al 100%; lo que ningún caso ejercitaba era el valor del índice en el borde, y eso el coverage de sentencias no lo puede ver. La pregunta útil no es «¿cuánto cubro?» sino «si rompo esta línea a propósito, ¿algo se pone rojo?».

Tu tabla usa t.Parallel() en cada subtest y desde ayer falla con «database is closed». No tocaste el código de producción. ¿Qué pasó?

Casi con seguridad alguien agregó un recurso compartido en el test padre y lo liberó con defer. t.Parallel() suspende el subtest hasta que la función padre retorna, y los defer del padre corren exactamente en ese momento: la conexión se cierra antes de que el primer subtest paralelo arranque. La cura es t.Cleanup(func(){ db.Close() }), que se ejecuta recién cuando terminaron todos los subtests, incluidos los paralelos. Como pista adicional: si el mensaje fuera de carrera de datos y no de recurso cerrado, la sospecha sería otra —una variable capturada del padre que se escribe desde varios subtests—, y ahí lo confirmás con -race.

¿Por qué un fake escrito a mano suele envejecer mejor que un mock generado, y en qué tres casos el mock igual gana?

Porque el mock verifica interacción (qué métodos se llamaron, con qué argumentos, en qué orden) y la interacción es un detalle de implementación: el día que reemplazás Buscar+Insertar por un upsert, el comportamiento observable es idéntico pero doscientos tests se ponen rojos sin que haya ningún bug. El fake verifica resultado contra un estado coherente, así que sobrevive al refactor. Los tres casos donde el mock gana: interfaces enormes que no controlás (un SDK de nube, un cliente gRPC generado), requisitos que son sobre la interacción («no llamar dos veces al gateway de pagos con el mismo idempotency key»), y contratos auditables donde hay que demostrar que se emitió exactamente un evento por operación.

Resumen ejecutivo

  • Table-driven: nombres que describen la regla rota, t.Run siempre (te da -run por caso), y desde Go 1.22 el c := c sobra. La trampa viva es que defer del padre corre antes que los subtests paralelos: usá t.Cleanup.
  • t.Helper() hace que la falla apunte al test y no al helper. No arregla el t.Fatal desde otra goroutine, que mata esa goroutine y deja el test pasando: desde goroutines, t.Errorf o canal de errores.
  • Fuzzing nativo: escribís invariantes (no panic, round-trip, diferencial), el motor genera y muta guiado por cobertura. El caso que falla se minimiza y se guarda solo en testdata/, y pasa a ser regresión determinista. Sin -fuzz corre en CI en milisegundos; con -fuzz va a un job nocturno.
  • Property-based: testing.F cubre bytes, strings y números; para estructuras generadas con forma y shrinking real hace falta rapid. testing/quick está congelado, no lo uses.
  • Interfaces en el consumidor (GS4): una interfaz de un método se implementa a mano en cuatro líneas y hace innecesarios la mayoría de los mocks generados.
  • Fake > mock por defecto, porque el fake verifica resultado y el mock verifica implementación. El mock gana con SDKs enormes, con requisitos de interacción y con contratos auditables.
  • httptest: ResponseRecorder para la lógica del handler (pasando por el mux, si usás {wildcards}), NewServer para probar tu cliente contra HTTP de verdad —reintentos, timeouts, TLS con srv.Client().
  • Testcontainers valida lo que ningún fake puede: el SQL, los índices, el driver, los deadlocks. Un contenedor por paquete en TestMain, aislamiento por transacción con rollback, y WithOccurrence(2) en el wait de Postgres.
  • Build tags separan la suite rápida de la lenta, pero esconden el código del compilador: go vet -tags=integration ./... en CI es obligatorio. testing.Short() cuando solo molesta el tiempo.
  • -race y goleak: siempre. El detector es dinámico, así que hay que generar concurrencia (t.Parallel, -count) para que tenga qué observar.
  • Coverage: usalo por función para encontrar lo menos cubierto y con GOCOVERDIR para detectar código muerto en end-to-end. Como objetivo numérico, es una métrica de vanidad.
  • Flaky: tiempo real → testing/synctest (Go 1.25+); orden de map → ordenar o cmpopts.SortSlices; puertos → :0; estado global → -shuffle=on para detectarlo y parámetros para curarlo. Reintentar nunca es el arreglo.

🧠 Autoevaluación

1. Cuando el motor de fuzzing encuentra una entrada que rompe tu código, ¿qué pasa con esa entrada?

Ese es el círculo virtuoso del fuzzing nativo: recorta la entrada al caso mínimo que sigue fallando y la deja como archivo de texto en testdata/. Ese archivo va al repo y a partir de ahí el target —sin -fuzz, en milisegundos— lo corre siempre. El corpus generado sí vive en $GOCACHE/fuzz, pero ese no se commitea y se pierde al limpiar la caché.

2. En un test cuyos subtests llaman a t.Parallel(), ¿por qué defer db.Close() en la función padre rompe todo?

Ese es el orden real: el subtest paralelo se pausa, el cuerpo del padre termina, corren sus defer y recién ahí se liberan los subtests. La solución es t.Cleanup, que se ejecuta cuando terminaron el test y todos sus subtests. Y ojo: lo del c := c es otro tema distinto, y ese sí dejó de hacer falta en Go 1.22.

3. Tu paquete tiene 95% de coverage de sentencias. ¿Qué NO te garantiza ese número?

Go mide sentencias ejecutadas, no afirmaciones ni ramas. Un test que solo llama a la función da 100% sin verificar nada, y una línea con a && b figura cubierta aunque nunca se haya evaluado el caso «a verdadero, b falso». Por eso el ejemplo de desescapar tenía 95,2% y aun así un panic: la línea corría en los 40 casos, pero ninguno la ejercitaba en el borde del índice.

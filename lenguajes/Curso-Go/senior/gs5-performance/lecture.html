GS5 — Performance: pprof, benchmarks y optimización real

GS5.0 Por qué este módulo

Go trae, de fábrica y sin instalar nada, el mejor tooling de profiling de cualquier lenguaje mainstream. Un perfil de CPU, uno de heap, uno de contención de candados, un trace del scheduler con resolución de microsegundos, y una herramienta para diffear dos perfiles y ver exactamente qué empeoró entre dos commits. Todo eso viene en el binario que ya tenés instalado.

Y casi nadie lo usa más allá de tirar un -cpuprofile, mirar el top, ver que el 30% está en runtime.mallocgc, y sacar la conclusión equivocada.

💡 La tesis del módulo. Optimizar no es escribir código más rápido: es medir dónde se va el tiempo, cambiar una sola cosa, y volver a medir con suficiente rigor estadístico como para saber si el cambio hizo algo. El 80% del trabajo es instrumentación y método; el 20% es el truco de Go que aplicás al final. La gente hace esos porcentajes al revés y por eso pasa semanas optimizando funciones que representan el 2% del tiempo total.

Hay tres errores que se repiten en todos los equipos, y este módulo existe para vacunarte contra los tres:

1. Benchmarks que el compilador borró. Escribís un BenchmarkX, te da 0.31 ns/op, celebrás. Ese número es físicamente imposible: a 3 GHz un ciclo de reloj dura 0.33 ns. Lo que medís es un bucle vacío, porque el compilador probó que el resultado no se usa y eliminó la llamada entera.
2. Una sola corrida como evidencia. Corrés el benchmark antes y después, ves 412 µs contra 398 µs, declarás una mejora del 3,4%. En esa misma máquina, corriendo el mismo binario diez veces, la varianza es del 5%. No mediste una mejora: mediste ruido térmico.
3. Optimizar donde no está el tiempo. El perfil de CPU dice que encoding/json es el 40%. Lo optimizás y el endpoint baja de 180 ms a 156 ms, porque el resto del tiempo el proceso estaba bloqueado esperando a la base de datos, y un perfil de CPU no muestra tiempo bloqueado. Ese es el momento de dejar de tocar Go.
Contexto 2026. Este módulo asume Go 1.26. Lo relevante para performance en esta versión: llegó SIMD experimental vía simd/archsimd, io.ReadAll es más rápido (menos recrecimientos del buffer), reflect ganó iteradores al estilo range-over-func, y el compilador asigna los backing stores de slices en el stack en bastantes más casos que antes — o sea que allocaciones que ayer contabas hoy pueden no existir. El GC Green Tea ya es el default; lo vimos en GS2 y acá vamos a ver cómo aparece en los perfiles.

GS5.1 Benchmarks que no mienten

Un benchmark en Go es una función BenchmarkXxx(b *testing.B) en un archivo _test.go. El framework la llama con un b.N creciente hasta que el tiempo total es estadísticamente utilizable, y divide.

package parser

import "testing"

func BenchmarkParsear(b *testing.B) {
    entrada := []byte(`{"id":42,"nombre":"pedido"}`)
    b.ReportAllocs()                 // agrega B/op y allocs/op a la salida
    b.ResetTimer()                   // descarta el costo del setup de arriba
    for i := 0; i < b.N; i++ {
        Parsear(entrada)
    }
}
# -run=^$ evita correr los tests normales; solo queremos los benchmarks
go test -run=^$ -bench=BenchmarkParsear -benchmem ./parser/
goos: linux
goarch: amd64
pkg: api/parser
cpu: AMD EPYC 7763 64-Core Processor
BenchmarkParsear-8    3412108    351.4 ns/op    248 B/op    5 allocs/op
PASS

Se lee así: se ejecutó 3.412.108 veces, cada iteración tardó 351,4 nanosegundos, asignó 248 bytes en 5 allocaciones distintas. Las dos últimas columnas son las que más te van a servir, porque las allocaciones son el insumo del GC y suelen ser el único número que podés bajar de forma predecible.

El compilador puede borrar tu benchmark entero

Este es el error número uno, y es silencioso: no falla, te devuelve un número precioso.

func fib(n int) int {
    if n < 2 { return n }
    return fib(n-1) + fib(n-2)
}

// ❌ MAL: el resultado se descarta. fib no tiene efectos laterales,
// el compilador lo prueba y elimina la llamada.
func BenchmarkFibMalo(b *testing.B) {
    for i := 0; i < b.N; i++ {
        fib(20)
    }
}
BenchmarkFibMalo-8    1000000000    0.2913 ns/op    0 B/op    0 allocs/op
La regla del nanosegundo. Si un benchmark que hace trabajo real te da menos de ~1 ns/op, o exactamente 1000000000 iteraciones (el tope que impone testing), el compilador borró el cuerpo. A 3 GHz un ciclo dura 0,33 ns; fib(20) son unas 20.000 llamadas recursivas. No hay universo en el que eso salga en 0,29 ns.

La solución clásica es la variable sumidero (sink) a nivel de paquete. El compilador no puede probar que nadie fuera del paquete lee una variable exportable ni que el linker no la referencia, así que está obligado a ejecutar el trabajo que la produce:

// Sumidero a nivel de paquete: obliga al compilador a mantener el cálculo.
var sinkInt int

func BenchmarkFibBien(b *testing.B) {
    var r int
    for i := 0; i < b.N; i++ {
        r = fib(20)          // escribimos en una local...
    }
    sinkInt = r              // ...y la publicamos UNA vez, fuera del bucle
}
BenchmarkFibBien-8    41982    28437 ns/op    0 B/op    0 allocs/op

28,4 µs. Eso sí es fib(20). Fijate el detalle de asignar a la local r dentro del bucle y publicar en sinkInt una sola vez afuera: si escribieras directo en la global en cada iteración, estarías midiendo también un store a memoria global por vuelta, que en un benchmark de nanosegundos no es despreciable.

b.Loop: la forma moderna (Go 1.24+)

Desde Go 1.24 existe b.Loop(), que resuelve el problema de raíz sin sumideros:

func BenchmarkFibLoop(b *testing.B) {
    datos := cargarFixture()      // el setup NO se cronometra: va antes del Loop

    for b.Loop() {
        fib(20)                   // el compilador NO puede eliminar esto
    }

    verificar(datos)              // el teardown TAMPOCO se cronometra
}

b.Loop hace tres cosas que for i := 0; i < b.N; i++ no hace:

ComportamientoPor qué importa
Mantiene vivos parámetros y resultados de las llamadas del cuerpoYa no necesitás la variable sumidero: el compilador tiene prohibido borrar el trabajo
El cronómetro arranca en la primera llamada a b.Loop()b.ResetTimer() desaparece: el setup previo queda fuera automáticamente
El cuerpo se ejecuta en una sola pasada de mediciónEl setup costoso corre una vez, no una vez por cada tanteo de b.N
Usá b.Loop en todo lo nuevo. El patrón viejo con b.N sigue funcionando y lo vas a seguir viendo en código existente y en la stdlib, así que tenés que saber leerlo. Pero para escribir, b.Loop elimina de un saque las dos fuentes de benchmarks mentirosos: la eliminación de código muerto y el setup contabilizado.

Los otros controles de testing.B

func BenchmarkComprimir(b *testing.B) {
    entrada := hacerPayload(1 << 20)   // 1 MiB

    b.SetBytes(int64(len(entrada)))    // habilita la columna MB/s
    b.ReportAllocs()

    for b.Loop() {
        Comprimir(entrada)
    }
}

func BenchmarkHandlerParalelo(b *testing.B) {
    h := nuevoHandler()
    b.RunParallel(func(pb *testing.PB) {
        // cada goroutine tiene su propio estado: nada compartido acá
        req := nuevaRequest()
        for pb.Next() {
            h.Servir(req)
        }
    })
}

func BenchmarkConMetricaPropia(b *testing.B) {
    var fallos int
    for b.Loop() {
        if err := Procesar(); err != nil { fallos++ }
    }
    // métricas arbitrarias en la salida y en benchstat
    b.ReportMetric(float64(fallos)/float64(b.N), "fallos/op")
}
b.StopTimer() dentro del bucle es una trampa cara. Parar y arrancar el cronómetro cuesta del orden de cientos de nanosegundos. Si tu operación tarda 300 ns y frenás el reloj en cada iteración para hacer un setup, estás midiendo mayormente el costo de frenar el reloj. Si necesitás setup por iteración, o lo hacés barato, o generás todos los casos por adelantado y los indexás.

GS5.2 benchstat: una corrida no es un resultado

Una máquina de desarrollo no es un instrumento de medición. Tiene turbo boost que sube y baja según la temperatura, otros procesos, el scheduler del sistema operativo, y —en la nube— vecinos ruidosos en el mismo host físico. La varianza entre corridas idénticas del mismo binario suele estar entre el 2% y el 10%.

📌 Si tu "mejora" es menor que la varianza de tu máquina, no medís una mejora: medís tu máquina. Por eso la unidad mínima de evidencia no es una corrida, son diez, y la conclusión no la sacás vos: la saca una prueba estadística. 
go install golang.org/x/perf/cmd/benchstat@latest

# 1. Medí el estado actual, 10 repeticiones
git stash
go test -run=^$ -bench=Decodificar -benchmem -count=10 ./api/ > base.txt

# 2. Aplicá UN cambio y volvé a medir
git stash pop
go test -run=^$ -bench=Decodificar -benchmem -count=10 ./api/ > nuevo.txt

# 3. Que decida la estadística
benchstat base.txt nuevo.txt

Cómo se lee, campo por campo:

ElementoQué significa
412.4µLa mediana de las 10 corridas, no el promedio. Es robusta ante un outlier.
± 2%Dispersión de esas 10 muestras. Si ves ± 15%, tu entorno de medición está roto: cerrá el navegador, desactivá el turbo, no midas en un runner de CI compartido.
-12.42%El cambio de la mediana. Solo se muestra si es estadísticamente significativo.

El error de interpretación más común es tratar ~ como "no cambió nada". Un ~ con ± 9% y n=10 es compatible con una mejora real del 4% que no pudiste detectar con ese ruido. Si el cambio te importa, bajá el ruido (máquina dedicada, -benchtime=3s, más repeticiones) antes de concluir. La estadística no te dice la verdad: te dice cuánta confianza merece tu medición.
Higiene de medición, en orden de impacto: (1) nada más corriendo en la máquina; (2) -count=10 como mínimo; (3) si el resultado se acerca al umbral que te importa, subí a -count=20; (4) en Linux, fijar el governor en performance elimina una fuente enorme de varianza; (5) nunca compares números medidos en máquinas distintas, ni siquiera del mismo modelo.

GS5.3 pprof: los cinco perfiles y qué pregunta contesta cada uno

Acá es donde la mayoría se queda corta: usan el perfil de CPU para todo. Pero un perfil de CPU responde una pregunta, y si tu problema es de otra clase, va a mostrarte un plano perfectamente nítido del lugar equivocado.

PerfilCómo se obtienePregunta que contesta
CPU-cpuprofile cpu.out · /debug/pprof/profile?seconds=30¿En qué funciones se quema tiempo de CPU? Muestreo a 100 Hz.
Heap-memprofile mem.out · /debug/pprof/heapDos preguntas distintas: ¿quién asignó (alloc_space) y quién retiene ahora (inuse_space)?
goroutine/debug/pprof/goroutine¿Cuántas goroutines hay y en qué línea están paradas? Es el detector de fugas.
blockruntime.SetBlockProfileRate(n) + /debug/pprof/block¿Dónde se pasa el tiempo bloqueado en canales, WaitGroup o mutex?
mutexruntime.SetMutexProfileFraction(n) + /debug/pprof/mutex¿Qué candado concreto tiene contención y quién lo retuvo?

alloc_space vs inuse_space: la distinción que confunde a todos

El perfil de heap tiene cuatro vistas y elegir mal es el error clásico de la primera investigación de memoria:

VistaQué mideCuándo la querés
inuse_spaceBytes vivos en el instante del snapshotBuscás una fuga o por qué el RSS del pod no baja
inuse_objectsCantidad de objetos vivosEl GC tarda mucho marcando: importa el conteo, no los bytes
alloc_spaceBytes asignados acumulados desde que arrancó el proceso, liberados incluidosBuscás presión de GC: quién genera basura en el camino caliente
alloc_objectsCantidad total de objetos asignadosCorrelato exacto de la columna allocs/op de tus benchmarks
⚠️ El malentendido que hace perder tardes enteras. Abrís un perfil de heap buscando una fuga, ves alloc_space con bytes.Buffer.grow en 14 GB y creés que encontraste el culpable. No encontraste nada: alloc_space es histórico. Un servicio que lleva tres días arriba asignó y liberó terabytes sin tener ni una fuga. Para fugas se mira inuse_space, y siempre comparando dos snapshots separados en el tiempo, no uno solo. 
# Fuga: dos snapshots separados, y el diff entre ambos
curl -s http://127.0.0.1:6060/debug/pprof/heap > h1.pb.gz
sleep 600
curl -s http://127.0.0.1:6060/debug/pprof/heap > h2.pb.gz

# -diff_base: mostrá SOLO lo que creció en esos 10 minutos
go tool pprof -sample_index=inuse_space -diff_base=h1.pb.gz h2.pb.gz
El perfil de heap es muestreado: por defecto toma una muestra cada 512 KiB asignados (runtime.MemProfileRate). Eso lo hace casi gratis pero estadístico. Si estás cazando algo chico y esquivo, podés poner runtime.MemProfileRate = 1 al arrancar para registrar cada allocación — con un costo de rendimiento enorme, así que es una herramienta de laboratorio, no de producción.

block y mutex: los que hay que encender a mano

Estos dos vienen apagados porque cuestan. Se habilitan con una fracción de muestreo:

import "runtime"

func init() {
    // 1 de cada 10.000 eventos de bloqueo. Costo despreciable.
    runtime.SetMutexProfileFraction(10000)
    // Muestrear bloqueos que duren más de 1 ms (el valor es en nanosegundos).
    runtime.SetBlockProfileRate(1_000_000)
}
Un perfil de CPU no ve el tiempo bloqueado. Si tus goroutines esperan en un canal, en un sync.Mutex o en una syscall de red, el perfil de CPU simplemente no las muestra: no están consumiendo CPU. Un servicio con latencia p99 pésima y perfil de CPU plano es exactamente el caso de block y mutex, o del trace de la sección GS5.6.

La interfaz web y el flamegraph

Cómo leer un flamegraph. El eje X no es tiempo: es proporción, y los hijos están ordenados alfabéticamente. Cada barra es una función, y su ancho es el porcentaje de muestras en las que apareció en la pila. Las barras anchas y planas en la parte de arriba son donde se quema la CPU. Un pico angosto y altísimo es una recursión profunda que no cuesta nada. Buscás mesetas anchas, no torres altas.

GS5.5 net/http/pprof en producción sin abrir un agujero

Perfilar un servicio vivo, en producción, bajo carga real, es la diferencia entre optimizar el sistema y optimizar tu idea del sistema. El paquete net/http/pprof lo hace con una línea. Y con esa misma línea se publican en internet las pilas internas de tu proceso.

import _ "net/http/pprof"   // ⚠️ el import con guion bajo REGISTRA handlers
⚠️ Lo que ese import hace de verdad. Su init() registra /debug/pprof/ y sus rutas hijas en http.DefaultServeMux. Si tu servidor usa el mux por defecto —directamente, o porque una librería lo hace— acabás de exponer al público: los stacks completos de todas tus goroutines (que revelan rutas de archivos, nombres internos y arquitectura), /debug/pprof/cmdline con los flags del proceso (donde suele haber DSNs y tokens), y /debug/pprof/profile, que es un vector de denegación de servicio: cualquiera puede pedir un perfil de 30 segundos, y varios simultáneos degradan el proceso.

La forma correcta es un listener separado, atado a loopback, al que se llega por un túnel:

package main

import (
    "net/http"
    "net/http/pprof"
    "time"
)

// muxDebug arma un mux PROPIO: nada toca DefaultServeMux.
func muxDebug() *http.ServeMux {
    m := http.NewServeMux()
    m.HandleFunc("/debug/pprof/", pprof.Index)
    m.HandleFunc("/debug/pprof/cmdline", pprof.Cmdline)
    m.HandleFunc("/debug/pprof/profile", pprof.Profile)
    m.HandleFunc("/debug/pprof/symbol", pprof.Symbol)
    m.HandleFunc("/debug/pprof/trace", pprof.Trace)
    return m
}

func main() {
    // 127.0.0.1 explícito: NO ":6060", que escucha en todas las interfaces.
    depuracion := &http.Server{
        Addr:              "127.0.0.1:6060",
        Handler:           muxDebug(),
        ReadHeaderTimeout: 5 * time.Second,
    }
    go depuracion.ListenAndServe()

    // El servidor público, con su propio mux, sin rastro de pprof.
    publico := &http.Server{Addr: ":8080", Handler: rutasDeNegocio()}
    publico.ListenAndServe()
}
# Desde tu máquina: túnel SSH contra el loopback del pod/host
ssh -N -L 6060:127.0.0.1:6060 usuario@servidor-produccion

# En Kubernetes, el equivalente
kubectl port-forward pod/api-7d9f 6060:6060

# Y ahora perfilás como si fuera local
go tool pprof -http=:8080 http://127.0.0.1:6060/debug/pprof/profile?seconds=30
📌 Si por política de la organización el endpoint tiene que ser accesible por red, entonces necesita autenticación y autorización reales — no un "está en la VPN" ni un header secreto. Perfilar es una capacidad privilegiada de operaciones y merece el mismo control que cualquier otra: quién sos, y si ese quién tiene permiso para esta acción sobre este recurso. Los modelos concretos (RBAC, ABAC, deny por defecto, el problema de los controles del lado del cliente) están en M03 — Autorización del curso de Ciberseguridad. La regla corta para acá: loopback + túnel por defecto; cualquier otra cosa es una decisión de seguridad que hay que diseñar.
Costo real de perfilar en producción. El perfil de CPU es muestreo a 100 Hz: overhead típico por debajo del 1–2%, seguro de correr en un pod que sirve tráfico. El de heap es prácticamente gratis. Los de block y mutex dependen de la fracción que configures. El trace es el más caro: úsalo en ventanas de 3 a 10 segundos, nunca continuo.

GS5.6 El trace de ejecución: lo que pprof no ve

pprof te dice en qué funciones se gastó CPU. No te dice por qué una request tardó 400 ms si solo usó 12 ms de CPU. Para eso está go tool trace, que registra eventos del runtime con marca temporal: cada goroutine que arranca, se bloquea, se despierta, cada pausa de GC, cada syscall.

import (
    "os"
    "runtime/trace"
)

func main() {
    f, _ := os.Create("trace.out")
    defer f.Close()
    trace.Start(f)
    defer trace.Stop()

    trabajoDeVerdad()
}
# Desde un benchmark
go test -run=^$ -bench=Handler -trace=trace.out ./api/

# De un proceso vivo, ventana corta
curl -o trace.out 'http://127.0.0.1:6060/debug/pprof/trace?seconds=5'

go tool trace trace.out    # abre la UI en el navegador

Las vistas que resuelven problemas reales:

VistaDiagnostica
Goroutine analysisPor goroutine: cuánto estuvo ejecutando, cuánto esperando al scheduler, bloqueada en red, en sync, en GC. Es la descomposición de la latencia.
Network blocking profileDónde se bloquea esperando I/O. Acá aparece la base de datos que el perfil de CPU no mostraba.
Synchronization blockingCanales y mutex, con la pila de quien esperó
Scheduler latency profileGoroutines listas para correr pero sin P disponible. Si esto es grande, tenés más paralelismo del que la máquina soporta.
Timeline por PLas pausas stop-the-world del GC dibujadas en la línea de tiempo, con su duración exacta
💡 El caso donde el trace es la única herramienta. Latencia p99 de 800 ms, p50 de 40 ms, perfil de CPU plano y aburrido. El trace muestra la respuesta en dos minutos: las requests lentas son las que caen dentro de una pausa STW del GC, o las que quedaron encoladas en scheduler latency porque un puñado de goroutines monopolizó los P. Ninguno de esos dos hechos aparece en un perfil de CPU, porque en ambos casos tu código no estaba consumiendo CPU: estaba esperando. 
// Regiones y tareas: anotan el trace con TUS nombres de negocio
import "runtime/trace"

func (h *Handler) ServirPedidos(w http.ResponseWriter, r *http.Request) {
    ctx, tarea := trace.NewTask(r.Context(), "ServirPedidos")
    defer tarea.End()

    var p Pedido
    trace.WithRegion(ctx, "decodificar", func() {
        json.NewDecoder(r.Body).Decode(&p)
    })

    var filas []Fila
    trace.WithRegion(ctx, "consulta-db", func() {
        filas, _ = h.db.Query(ctx, consulta, p.ID)
    })

    trace.WithRegion(ctx, "responder", func() {
        json.NewEncoder(w).Encode(filas)
    })
}

Con eso, la vista User-defined tasks te da la distribución de latencia de ServirPedidos desglosada por región. Ya no adivinás qué parte tarda: lo leés.

Versiones recientes de Go incluyen además un flight recorder en runtime/trace: un buffer circular que mantiene siempre los últimos segundos de trace en memoria, con overhead bajo, y que volcás a disco cuando detectás el problema. Es la respuesta al viejo dilema de "el bug aparece una vez por día y no puedo dejar el trace prendido": lo dejás grabando siempre y guardás solo la ventana que rodea al evento raro.

GS5.7 Optimizaciones que sirven, en orden

Este orden no es una preferencia estética. Está ordenado por relación entre ganancia esperada y riesgo introducido, y saltearse los primeros escalones para ir directo a los últimos es la definición operativa de optimización prematura.

#PalancaGanancia típicaRiesgo / costo
1Algoritmo y trabajo evitado — mejor complejidad, caché, batching, menos round-trips10×–1000×Medio: cambia semántica, requiere tests
2Menos allocaciones — preasignar capacidad, reusar buffers, evitar escapes1,2×–3×Bajo si medís; alto si usás sync.Pool mal
3Menos indirección — sacar interfaces del camino caliente, valores en vez de punteros1,05×–1,4×Medio: suele empeorar el diseño
4Evitar copias grandes — pasar slices, no arrays; io.Copy con buffer reusado1,1×–5×Bajo, pero cuidado con el aliasing
5Paralelizar — worker pool, errgroupHasta N núcleosAlto: carreras, ordenamiento, backpressure
❌Micro-tuning de bucles — desenrollar a mano, evitar range, reordenar condiciones~0% (a veces negativo)Alto en legibilidad, nulo en beneficio
📌 Paralelizar está último por una razón. Los cuatro primeros escalones reducen el trabajo. Paralelizar no reduce nada: reparte el mismo trabajo entre más núcleos, y encima suma coordinación, no-determinismo y una clase entera de bugs nuevos. Si el trabajo por request es innecesario, paralelizarlo significa desperdiciar en ocho núcleos lo que antes desperdiciabas en uno.

Escalón 1, con números

// ❌ O(n·m): por cada pedido, recorre todos los usuarios
func EnriquecerLento(pedidos []Pedido, usuarios []Usuario) {
    for i := range pedidos {
        for _, u := range usuarios {
            if u.ID == pedidos[i].UsuarioID {
                pedidos[i].Email = u.Email
                break
            }
        }
    }
}

// ✅ O(n+m): un índice, y después una búsqueda constante
func EnriquecerRapido(pedidos []Pedido, usuarios []Usuario) {
    porID := make(map[int64]string, len(usuarios))   // capacidad exacta: cero rehash
    for _, u := range usuarios {
        porID[u.ID] = u.Email
    }
    for i := range pedidos {
        pedidos[i].Email = porID[pedidos[i].UsuarioID]
    }
}
EnriquecerLento-8      184.2m ± 2%
EnriquecerRapido-8       1.9m ± 1%   -98.97% (p=0.000 n=10)

97× con diez líneas. Ninguna cantidad de sync.Pool, de evitar interfaces ni de SIMD sobre la versión lenta se acerca a eso. Por eso el algoritmo va primero, siempre.

Escalón 2: menos allocaciones

// ❌ Cada append que supera la capacidad copia todo el slice a memoria nueva
func IDsLento(pedidos []Pedido) []int64 {
    var out []int64                      // capacidad 0: ~log2(n) recrecimientos
    for _, p := range pedidos {
        out = append(out, p.ID)
    }
    return out
}

// ✅ Una sola allocación, del tamaño exacto
func IDsRapido(pedidos []Pedido) []int64 {
    out := make([]int64, 0, len(pedidos))
    for _, p := range pedidos {
        out = append(out, p.ID)
    }
    return out
}
IDsLento-8     41.8µ ± 2%   357Ki ± 0%   19 allocs/op
IDsRapido-8    12.1µ ± 1%    80Ki ± 0%    1 allocs/op   -71.05% (p=0.000 n=10)
Sobre sync.Pool: es una herramienta afilada, no un acelerador genérico. Sirve cuando los objetos son grandes, de vida corta y de tamaño parecido — buffers de I/O es el caso de manual. Para objetos chicos suele ser más lento que dejar que el allocator haga su trabajo, porque el pool tiene su propio costo por operación. Y si guardás en el pool un objeto que todavía referencia datos de la request anterior, tenés una fuga de memoria y potencialmente una fuga de datos entre usuarios. Medí siempre antes y después con benchstat.

Escalón 3: menos indirección

// Una llamada a través de interfaz es indirecta: el compilador no sabe
// qué implementación es, así que NO puede inlinear ni especializar.
type Transformador interface{ Transformar(int) int }

func AplicarIface(t Transformador, xs []int) {   // llamada indirecta por elemento
    for i := range xs { xs[i] = t.Transformar(xs[i]) }
}

func AplicarFunc(f func(int) int, xs []int) {    // el compilador suele devirtualizar
    for i := range xs { xs[i] = f(xs[i]) }
}

func AplicarConcreto(xs []int) {                 // inlineable, sin indirección
    for i := range xs { xs[i] = xs[i]*2 + 1 }
}
Este escalón es el que más daño hace mal aplicado. "Las interfaces son lentas" se convierte en un rediseño que borra la capacidad de testear con dobles y de intercambiar implementaciones, a cambio de un 8% en una función que era el 3% del tiempo total — o sea, 0,24% del sistema. Sacá interfaces del camino caliente solo cuando el perfil te muestra esa llamada indirecta como un costo medible y ya agotaste los escalones 1 y 2.

GS5.8 Inlining y bounds check elimination

Estas dos son las optimizaciones del compilador que más se notan en código numérico y de parsing, y las dos se pueden inspeccionar. Eso las vuelve accionables en vez de folclore.

Inlining: ver qué decide el compilador

# -m imprime las decisiones de inlining y de escape analysis
go build -gcflags='-m' ./api/ 2>&1 | head -40

# Doble -m: explica POR QUÉ no pudo
go build -gcflags='-m -m' ./api/ 2>&1 | grep 'cannot inline'
./pedido.go:14:6: can inline (*Pedido).Total with cost 42 as: ...
./pedido.go:31:6: cannot inline (*Handler).Servir: function too complex: cost 271 exceeds budget 80
./pedido.go:44:22: &buf escapes to heap
./pedido.go:47:12: make([]byte, n) does not escape

Lo que hay que saber para leer esa salida:

  • El compilador tiene un presupuesto de complejidad (unos 80 "nodos"). Una función que lo excede no se inlinea, punto.
  • Una llamada a través de una interfaz no se puede inlinear salvo que el compilador logre devirtualizarla, es decir, probar cuál es el tipo concreto.
  • Inlinear no es solo ahorrarse el CALL: es lo que habilita todo lo demás. Con el cuerpo expandido en el sitio de llamada, el compilador puede propagar constantes, eliminar ramas muertas y, sobre todo, probar que un valor no escapa — y entonces asignarlo en el stack en vez del heap.
  • does not escape es la línea que más te interesa de todo -m: significa cero trabajo para el GC.
Go 1.26 mueve esta frontera a tu favor. El compilador ahora asigna el backing store de slices en el stack en bastantes más casos que antes. Consecuencia práctica: benchmarks que tenías con 3 o 4 allocs/op pueden bajar a 1 o 0 sin que hayas tocado el código. Corolario incómodo: si tu proyecto tiene tests que afirman una cantidad exacta de allocaciones, van a romperse al actualizar. Eso es una buena noticia disfrazada de falla.

Bounds check elimination (BCE)

Go verifica cada indexado de slice. Es lo que hace que un índice fuera de rango sea un panic y no una vulnerabilidad de corrupción de memoria — no es negociable. Lo que sí podés hacer es escribir de forma tal que el compilador pruebe que el índice es válido y elimine la verificación.

go build -gcflags='-d=ssa/check_bce/debug=1' ./codec/
./codec.go:22:14: Found IsInBounds
./codec.go:23:14: Found IsInBounds
./codec.go:24:14: Found IsInBounds
./codec.go:25:14: Found IsInBounds
La salida es al revés de lo que parece. Found IsInBounds señala las verificaciones que quedaron, o sea las que el compilador no pudo eliminar. Menos líneas en esa salida es mejor. La ausencia de mensajes es el resultado ideal. 
// ❌ 4 verificaciones: el compilador no sabe nada sobre len(b)
func LeerU32Lento(b []byte) uint32 {
    return uint32(b[0]) | uint32(b[1])<<8 | uint32(b[2])<<16 | uint32(b[3])<<24
}

// ✅ Una sola pista al principio y las 4 desaparecen
func LeerU32Rapido(b []byte) uint32 {
    _ = b[3]   // si esto no paniquea, b[0..3] son válidos y el compilador lo sabe
    return uint32(b[0]) | uint32(b[1])<<8 | uint32(b[2])<<16 | uint32(b[3])<<24
}

// ✅✅ Mejor todavía: la stdlib ya lo hace, con endianness explícita
func LeerU32Idiomatico(b []byte) uint32 {
    return binary.LittleEndian.Uint32(b)
}

Los tres patrones que ayudan al compilador, en orden de utilidad:

1. for i := range s. El compilador sabe por construcción que i está en rango, así que s[i] no lleva verificación. Es la razón más importante para preferir range sobre un contador manual — el opuesto exacto del mito de que range es más lento.
2. Reslicear una vez arriba. s = s[:n] al inicio de la función establece un hecho sobre la longitud que el compilador propaga a todos los indexados posteriores.
3. La pista _ = s[k]. Fuerza una única verificación al principio y elimina las k siguientes. Es una técnica de último recurso: úsala en un codec o un parser medido, con un comentario que explique qué está haciendo esa línea aparentemente inútil, y nunca en código de negocio.
BCE es un martillo de precisión, no de uso general. En un handler HTTP que hace una consulta a base de datos, eliminar cuatro bounds checks te ahorra unos nanosegundos sobre una operación de milisegundos: cero por ciento, con costo real en legibilidad. Esto vale la pena en codecs, parsers, criptografía y bucles numéricos apretados. En cualquier otro lugar, es ruido.

GS5.9 SIMD experimental: simd/archsimd (Go 1.26)

SIMD —Single Instruction, Multiple Data— es la capacidad del procesador de aplicar una operación a un vector entero de valores en una sola instrucción: sumar dieciséis enteros de 32 bits de un golpe en vez de dieciséis sumas. Hasta ahora, en Go, la única forma de acceder a eso era escribir ensamblador a mano en archivos .s, que es exactamente como la stdlib implementa bytes.IndexByte, los hashes de crypto y varios paths calientes más.

Go 1.26 introduce simd/archsimd: tipos vectoriales e intrínsecos expuestos como API de Go, detrás de un GOEXPERIMENT, inicialmente para amd64 (AVX2 / AVX-512).

# Está detrás de una bandera experimental: no se compila por defecto
GOEXPERIMENT=simd go build ./vectorial/
⚠️ Esto NO va a producción, y la advertencia es literal. Es material explícitamente experimental: la API puede cambiar o desaparecer sin pasar por la promesa de compatibilidad de Go 1.x; el código queda atado a una arquitectura, con lo cual perdés la compilación cruzada trivial que es media gracia de Go; requiere detección de features de CPU en runtime, porque no todo amd64 tiene AVX-512; y es trivialmente fácil escribir SIMD más lento que el bucle normal, porque el costo de cargar y descargar los registros vectoriales se come la ganancia si el arreglo es chico. Estudiálo, mirálo, no lo despliegues.
📌 Antes de pensar en SIMD, ya deberías haber agotado esto: ¿está el algoritmo correcto? ¿estás en cero allocaciones en el camino caliente? ¿verificaste con -m que las funciones críticas se inlinean? ¿confirmaste con check_bce que no quedan verificaciones en el bucle? ¿probaste si la stdlib ya trae una versión con ensamblador SIMD de lo que estás por escribir a mano? Si alguna respuesta es "no", ahí está tu próximo commit — y va a rendir más que el SIMD.

El valor real de esta novedad no es que la uses mañana: es estructural. Que exista una superficie en Go para SIMD significa que la stdlib y las librerías de terceros van a poder acelerar sus caminos calientes sin mantener ensamblador a mano por arquitectura. Vos te vas a beneficiar de eso sin escribir una sola línea de archsimd — que es exactamente como debería ser.

GS5.10 Cuándo NO optimizar

La habilidad senior en performance no es saber optimizar: es saber decir que no con evidencia en la mano. Estos son los cinco casos en los que la respuesta correcta es dejar el código como está.

1. El tiempo está en I/O. Si el trace dice que el 85% de la latencia es espera de base de datos o de un servicio externo, el código Go es irrelevante. Podés hacerlo infinitamente rápido y la mejora total sería del 15%. Lo que hay que atacar es la consulta, el índice, la cantidad de round-trips o la caché.
2. No hay un objetivo numérico. "Hacerlo más rápido" no es un requisito: es una sensación. "p99 por debajo de 200 ms con 500 rps" sí lo es, y además te dice cuándo parar. Sin número no hay criterio de terminado, y la optimización se vuelve infinita.
3. El costo está en el tiempo del equipo, no en la máquina. Un endpoint interno que corre 40 veces por día y tarda 900 ms no tiene un problema de performance. Un endpoint público con 4.000 rps y 90 ms sí. La misma latencia, decisiones opuestas.
4. La ganancia es menor que la varianza de tu medición. Si benchstat dice ~, no ganaste nada demostrable. Mergear ese cambio agrega complejidad a cambio de una creencia.
5. Va a expirar sola. Cada versión de Go trae mejoras en compilador y runtime. El caso de Go 1.26 con las slices en el stack es literal: código que alguien complicó a mano para evitar una allocación puede haber quedado obsoleto y ahora ser solo más difícil de leer, sin ser más rápido.
Ley de Amdahl, en criollo. Si una parte representa el 40% del tiempo total y la hacés infinitamente rápida, el sistema mejora un 40% — nunca más. Si representa el 5%, tu techo absoluto es 5%. Antes de invertir una semana en optimizar algo, mirá qué fracción del total es y calculá tu techo. Muchas veces el cálculo termina la discusión antes de empezar.

Paso 4 — Tres alternativas, medidas contra la misma base

// A — Streaming: decodificar directo del io.Reader, sin materializar el []byte
func decodificarStreaming(r io.Reader) (Resumen, error) {
    var p Resumen
    err := json.NewDecoder(r).Decode(&p)
    return p, err
}

// B — Reusar el buffer de lectura con sync.Pool, y seguir usando Unmarshal
var poolBuf = sync.Pool{New: func() any { return new(bytes.Buffer) }}

func decodificarConPool(r io.Reader) (Resumen, error) {
    buf := poolBuf.Get().(*bytes.Buffer)
    defer func() { buf.Reset(); poolBuf.Put(buf) }()

    if _, err := buf.ReadFrom(r); err != nil {
        return Resumen{}, err
    }
    var p Resumen
    err := json.Unmarshal(buf.Bytes(), &p)
    return p, err
}

// C — Otra librería, compatible en API con encoding/json
//     import gojson "github.com/goccy/go-json"
func decodificarOtraLib(datos []byte) (Resumen, error) {
    var p Resumen
    err := gojson.Unmarshal(datos, &p)
    return p, err
}

Checkpoint — ¿lo tenés claro?

Tu benchmark de una función de hashing te da 0,42 ns/op. ¿Qué pasó y cómo lo arreglás?

El compilador eliminó el cuerpo del bucle. Como el resultado de la función se descarta y la función no tiene efectos laterales observables, probó que la llamada es código muerto y la borró; lo que medís es un bucle vacío. A 3 GHz un ciclo de reloj dura 0,33 ns, así que cualquier trabajo real es imposible en 0,42 ns — esa es la señal. Las dos soluciones: escribir el resultado en una variable local dentro del bucle y publicarla en una variable sumidero a nivel de paquete una sola vez después del bucle, o —mejor, en Go 1.24+— usar for b.Loop(), que mantiene vivos parámetros y resultados de las llamadas del cuerpo y le prohíbe al compilador esa eliminación.

El pod usa 3 GB de RAM y sospechás una fuga. Abrís el perfil de heap y ves bytes.Buffer.grow con 42 GB. ¿Encontraste la fuga?

No, y probablemente estás mirando alloc_space, que es acumulado histórico desde que arrancó el proceso e incluye todo lo que ya se liberó. 42 GB en un servicio que lleva días arriba puede ser perfectamente sano: dice que ese buffer es un camino caliente que genera basura, lo cual es un dato de presión de GC, no de fuga. Para una fuga se usa inuse_space, que son los bytes vivos en el instante del snapshot, y no se mira un snapshot solo: se toman dos separados en el tiempo y se comparan con -diff_base, porque lo que define una fuga es crecer y no bajar, no ser grande.

Latencia p99 de 800 ms, p50 de 40 ms, y el perfil de CPU está plano y sin picos. ¿Qué herramienta usás y qué esperás encontrar?

go tool trace, porque un perfil de CPU solo muestra tiempo consumiendo CPU y este problema es de tiempo esperando — que es invisible ahí. Las tres causas típicas de esa firma: (1) requests que caen dentro de una pausa stop-the-world del GC, visible en la timeline por P; (2) scheduler latency, goroutines listas para correr sin un P libre, señal de que hay más paralelismo del que la máquina sostiene; (3) contención en un mutex compartido, que el synchronization blocking profile muestra con la pila de quien esperó. Complementariamente, habilitar los perfiles de block y mutex —que vienen apagados— confirma cuál de las tres es.

Resumen ejecutivo

  • Un benchmark cuyo resultado se descarta puede ser eliminado entero por el compilador. La señal es un número por debajo de 1 ns/op. Se arregla con una variable sumidero, o mejor con for b.Loop() (Go 1.24+), que además saca el setup del cronómetro.
  • Una corrida no es evidencia. -count=10 más benchstat, y un ~ significa "sin evidencia suficiente", no "sin diferencia".
  • Cinco perfiles, cinco preguntas distintas: CPU (dónde se quema), heap (quién asigna y quién retiene), goroutine (fugas), block y mutex (dónde se espera). Los dos últimos vienen apagados.
  • alloc_space es acumulado histórico → presión de GC. inuse_space es lo vivo ahora → fugas, y siempre comparando dos snapshots con -diff_base.
  • top -cum para encontrar el embudo, list para bajar a la línea exacta, -http=:8080 para el flamegraph. runtime.mallocgc alto no es un problema del runtime: es tu código asignando.
  • net/http/pprof importado con _ registra en DefaultServeMux: mux propio, listener en 127.0.0.1, acceso por túnel. Si tiene que ir por red, necesita autorización real (Ciberseguridad M03).
  • go tool trace muestra lo único que pprof no puede: espera de red, contención, latencia del scheduler y pausas de GC. Es la herramienta cuando el perfil de CPU está plano y la latencia no.
  • Orden de las palancas: algoritmo → allocaciones → indirección → copias → paralelizar. Micro-tuning de bucles casi nunca. Paralelizar va último porque reparte trabajo, no lo elimina.
  • -gcflags='-m' para inlining y escapes; -gcflags='-d=ssa/check_bce/debug=1' para bounds checks (los mensajes son los que quedaron). Valen en codecs y bucles numéricos, no en handlers.
  • Go 1.26: simd/archsimd es experimental y no va a producción; io.ReadAll más rápido; iteradores en reflect; y el compilador pone más backing stores de slices en el stack, así que tus conteos de allocaciones pueden bajar solos.
  • Si el tiempo está en I/O, el código Go es irrelevante. Medí primero la partición CPU/espera: te da el techo de mejora antes de invertir una semana.

Ejercicios

  1. Escribí un benchmark de una función recursiva descartando el resultado y comprobá que da menos de 1 ns/op. Después arreglálo de las dos formas —variable sumidero y b.Loop— y compará los tres números en una tabla. Explicá por qué el primero era imposible.
  2. Corré el mismo benchmark, sin cambiar una línea de código, con -count=10 dos veces seguidas. Pasá ambas salidas por benchstat y reportá el ± y el p obtenidos: esa es la varianza base de tu máquina, y ninguna mejora menor a ese número es creíble para vos.
  3. Tomá una función tuya que arme un slice con append sin capacidad inicial. Benchmarkeala con -benchmem, agregá make([]T, 0, n) y medí de nuevo con benchstat. Reportá el delta en sec/op, B/op y allocs/op, y verificá con -gcflags='-m' si algo dejó de escapar al heap.
  4. Montá net/http/pprof en un servicio tuyo en un mux separado atado a 127.0.0.1. Confirmá desde otra máquina que /debug/pprof/ no responde en el puerto público, y desde un túnel que sí. Documentá en el README cómo se perfila el servicio.
  5. Instrumentá tu handler más lento con trace.NewTask y trace.WithRegion, generá un trace de 10 segundos bajo carga y reportá la partición execution / network wait / sync+GC. Calculá el techo máximo de mejora que tenés optimizando código Go.
  6. Elegí una función de parsing o codificación de tu proyecto y corré -gcflags='-d=ssa/check_bce/debug=1'. Contá cuántos Found IsInBounds quedan, aplicá uno de los tres patrones de GS5.8, volvé a contar y —esto es lo importante— medí con benchstat si la diferencia es estadísticamente significativa o pura estética.
  7. Tomá dos perfiles de heap de un servicio con 10 minutos de diferencia y corré go tool pprof -sample_index=inuse_space -diff_base=h1 h2. Escribí en tres líneas si hay fuga y en qué línea de código está el crecimiento, o justificá por qué el crecimiento observado es normal.

🧠 Autoevaluación

1. Sospechás una fuga de memoria: el RSS del pod sube y nunca baja. ¿Qué vista del perfil de heap mirás?

alloc_space y alloc_objects son acumulados históricos desde que arrancó el proceso e incluyen todo lo ya liberado: un servicio sano de varios días muestra decenas de GB ahí sin tener ninguna fuga. Sirven para diagnosticar presión de GC, no retención. Lo que define una fuga es memoria viva que crece y no baja, así que se mira inuse_space y nunca en un snapshot solo: dos capturas separadas y -diff_base para ver exactamente qué creció en esa ventana.

2. Tu servicio tiene p99 de 800 ms y p50 de 40 ms, pero el perfil de CPU está plano y sin funciones destacadas. ¿Cuál es la explicación más probable?

Un perfil de CPU muestra únicamente muestras tomadas mientras el proceso consume CPU. Tiempo bloqueado en un canal, esperando la respuesta de la base, encolado sin un P disponible o adentro de una pausa stop-the-world es tiempo real de latencia que ahí no aparece: por eso el perfil se ve plano mientras el p99 explota. go tool trace descompone la vida de cada goroutine en execution / network wait / sync block / GC, y los perfiles de block y mutex —que vienen apagados y hay que habilitar— confirman cuál de esas causas es.

3. Un trace muestra que el 85% de la latencia de tu endpoint es espera de la base de datos. El perfil de CPU dice que encoding/json es el 40% del tiempo de CPU restante. ¿Qué hacés?

Ley de Amdahl: si la base es el 85%, todo el código Go es el 15%, y el JSON es el 40% de ese 15% — es decir, 6% del total. Ese 6% es tu techo absoluto aunque hicieras la decodificación infinitamente rápida. La tercera opción tampoco ayuda: el decodificado tiene que terminar antes de poder consultar con esos datos, hay una dependencia real, y paralelizar no reduce trabajo — reparte. El movimiento correcto es salir de Go y mirar la consulta, el índice, la cantidad de round-trips o una caché. Saber cuándo el código Go dejó de ser el problema es parte del trabajo.

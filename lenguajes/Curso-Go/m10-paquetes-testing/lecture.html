Módulo 10 — Paquetes, Módulos & Testing

Hasta acá escribiste todo en un solo archivo main.go. Eso no escala: un proyecto real tiene decenas de archivos repartidos en carpetas, depende de librerías de terceros, y necesita una red de seguridad de tests que avise cuando algo se rompe. En este módulo armás esa estructura: paquetes para organizar, módulos para manejar dependencias, y el testing built-in de Go para validar tu código sin instalar ningún framework.

Paquetes: organizar el código en carpetas

En Go, cada carpeta es un paquete. Todos los archivos .go de una misma carpeta declaran el mismo package en su primera línea y comparten un espacio de nombres: pueden verse entre sí sin importarse. Una estructura típica:

miapp/
├── go.mod
├── main.go              # package main
├── calculadora/
│   ├── suma.go          # package calculadora
│   └── resta.go         # package calculadora
└── formato/
    └── moneda.go        # package formato

Para usar algo de otro paquete, lo importás por su ruta de import (el nombre del módulo + la carpeta):

package main

import (
    "fmt"

    "ejemplo.com/miapp/calculadora"
)

func main() {
    fmt.Println(calculadora.Suma(2, 3)) // calificás con el nombre del paquete
}

Visibilidad: la Mayúscula manda

💡 No hay public ni private en Go. La regla es una sola y se ve a simple vista: un identificador que empieza con Mayúscula es exportado (visible desde otros paquetes); uno que empieza con minúscula es privado al paquete que lo define. Esto aplica a funciones, tipos, structs, campos, métodos y constantes. 
package calculadora

// Suma es EXPORTADA: otros paquetes pueden llamar calculadora.Suma()
func Suma(a, b int) int {
    return sumarInterno(a, b)
}

// sumarInterno es privada: solo se usa DENTRO del paquete calculadora
func sumarInterno(a, b int) int {
    return a + b
}
La misma regla decide qué campos de un struct son visibles. type Usuario struct { Nombre string; clave string } expone Nombre hacia afuera pero clave queda invisible (y por eso no se serializa a JSON automáticamente). Es el mecanismo de encapsulamiento de Go: el nombre es el modificador de acceso.

Módulos: manejar dependencias

Un proyecto Go moderno es un módulo. Lo iniciás una sola vez en la raíz del proyecto:

go mod init ejemplo.com/miapp

Eso crea el archivo go.mod, que declara el nombre del módulo, la versión mínima de Go y las dependencias:

module ejemplo.com/miapp

go 1.23

require github.com/google/uuid v1.6.0
Archivo / comandoPara qué sirve
go.modNombre del módulo, versión de Go y lista de dependencias directas (require).
go.sumChecksums criptográficos de cada dependencia (y sus dependencias). Garantiza que bajás exactamente el mismo código siempre. Se versiona en git.
go get url@versionAgrega o actualiza una dependencia de terceros y la anota en go.mod/go.sum.
go mod tidySincroniza go.mod: agrega lo que importás y falta, elimina lo que ya no usás.
1. Agregás una librería de terceros:
go get github.com/google/uuid
2. La usás en tu código importándola por su ruta:
import "github.com/google/uuid"

func main() {
    id := uuid.New()
    fmt.Println(id.String())
}
3. Antes de commitear, dejás todo prolijo:
go mod tidy   # agrega lo que falta, borra lo que sobra
✅ Hábito sano: corré go mod tidy antes de cada commit. Mantiene go.mod reflejando exactamente lo que tu código importa, ni más ni menos. Un go.mod con dependencias fantasma es ruido que confunde a quien lea el proyecto.

Testing built-in: sin frameworks

Go trae el testing en la librería estándar y en la herramienta go test. No instalás Jest, ni pytest, ni JUnit: la convención es el framework. Las reglas:

  • Los tests viven en archivos que terminan en _test.go (ej: suma_test.go), en la misma carpeta que el código que prueban.
  • Cada test es una función func TestXxx(t *testing.T) — empieza con Test y mayúscula, recibe un *testing.T.
  • Importás el paquete "testing" de la stdlib.
  • Un test falla cuando llamás a un método de error de t; si no llamás a ninguno, pasa.
MétodoQué hace
t.Errorf(...)Marca el test como fallido y sigue ejecutando el resto del test.
t.Fatalf(...)Marca el test como fallido y corta ese test ahí mismo (útil si lo que sigue no tiene sentido sin lo anterior).
t.Run("nombre", fn)Crea un subtest con nombre propio (clave para los table-driven tests).

Para correrlos:

go test              # corre los tests del paquete actual
go test ./...        # corre TODOS los tests del módulo, recursivo
go test -v           # modo verbose: muestra cada test y su resultado
go test -cover       # muestra el % de cobertura del código

Table-driven tests: el patrón idiomático

💡 El patrón estrella de Go. En vez de copiar/pegar la misma lógica de aserción una vez por cada caso, definís un slice de structs con {entrada, esperado} y recorrés los casos con un for. Agregar un caso nuevo es agregar una línea a la tabla. Combinado con t.Run, cada caso aparece nombrado en la salida.

Primero, la función a probar (en calculadora/suma.go):

package calculadora

// Suma devuelve a + b.
func Suma(a, b int) int {
    return a + b
}

Ahora su test table-driven (en calculadora/suma_test.go):

package calculadora

import "testing"

func TestSuma(t *testing.T) {
    casos := []struct {
        nombre   string
        a, b     int
        esperado int
    }{
        {"positivos", 2, 3, 5},
        {"con cero", 7, 0, 7},
        {"negativos", -4, -6, -10},
        {"mixto", -5, 5, 0},
    }

    for _, c := range casos {
        t.Run(c.nombre, func(t *testing.T) {
            got := Suma(c.a, c.b)
            if got != c.esperado {
                t.Errorf("Suma(%d, %d) = %d; esperado %d",
                    c.a, c.b, got, c.esperado)
            }
        })
    }
}

Al correr go test -v verías cada subtest por separado:

=== RUN   TestSuma
=== RUN   TestSuma/positivos
=== RUN   TestSuma/con_cero
=== RUN   TestSuma/negativos
=== RUN   TestSuma/mixto
--- PASS: TestSuma (0.00s)
    --- PASS: TestSuma/positivos (0.00s)
    --- PASS: TestSuma/con_cero (0.00s)
    --- PASS: TestSuma/negativos (0.00s)
    --- PASS: TestSuma/mixto (0.00s)
PASS
🔗 Pensalo como una planilla. Cada fila de la tabla es un caso de prueba con sus columnas (entrada → salida esperada). El for es el "revisor" que recorre la planilla fila por fila y marca con rojo solo las que no cuadran. Para sumar un caso nuevo no tocás la lógica del revisor: agregás una fila.

Benchmarks (mención breve)

Además de tests, go test sabe medir rendimiento. Un benchmark es una función func BenchmarkXxx(b *testing.B) que repite el código b.N veces; Go ajusta b.N hasta tener una medición estable.

func BenchmarkSuma(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Suma(2, 3)
    }
}
go test -bench=.    # corre los benchmarks del paquete

Errores frecuentes

Esperar que un identificador en minúscula sea accesible desde otro paquete. Si tu función se llama suma (minúscula), calculadora.suma() NO compila desde afuera: es privada. Para exportarla, renombrala a Suma.
Poner los tests fuera de un archivo _test.go. Si tu función TestSuma vive en suma.go en lugar de suma_test.go, go test no la encuentra (y peor: terminaría compilada dentro de tu binario de producción).
Un test que nunca llama a t.Errorf / t.Fatalf. Si calculás el resultado pero no lo comparás contra lo esperado (o comparás y no marcás el error), el test siempre pasa: no prueba nada. La señal de fallo en Go es llamar a un método de error de t.
⚠️ Cuidado con la variable del loop en versiones viejas de Go. Antes de Go 1.22, la variable c del for se reutilizaba entre iteraciones y los subtests paralelos podían leer el caso equivocado. Desde Go 1.22 cada iteración tiene su propia copia, así que el patrón de arriba es seguro. Si trabajás con un módulo declarado en go 1.21 o menos, copiá c := c dentro del loop por las dudas.

Checkpoint — ¿lo tenés claro?

¿Cómo decidís en Go si una función es pública o privada?

Por la primera letra de su nombre. Mayúscula inicial = exportada (pública, visible desde otros paquetes). Minúscula inicial = privada al paquete. No hay palabras clave public/private: el nombre es el modificador de acceso.

¿Para qué sirven go.mod, go.sum y go mod tidy?

go.mod declara el nombre del módulo, la versión de Go y las dependencias directas. go.sum guarda los checksums para garantizar que bajás siempre el mismo código. go mod tidy sincroniza go.mod: agrega lo que importás y falta, y elimina lo que ya no usás.

¿Qué es un table-driven test y por qué es idiomático?

Es definir un slice de structs con los casos {entrada, esperado} y recorrerlos con un for, usando t.Run para nombrar cada subtest. Es idiomático porque evita duplicar la lógica de aserción: agregar un caso nuevo es agregar una fila a la tabla, no copiar/pegar un bloque entero.

  1. Creá un módulo con go mod init ejemplo.com/practica y mirá el go.mod generado.
  2. Movés una función a un paquete calculadora/ (carpeta propia, package calculadora) e importala desde main. Hacela exportada con mayúscula inicial.
  3. Probá renombrar esa función a minúscula y observá el error de compilación al usarla desde main (visibilidad en acción).
  4. Escribí un test table-driven para una función EsPar(n int) bool, con al menos 4 casos y t.Run por caso. Corrélo con go test -v.
  5. Agregá github.com/google/uuid con go get, generá un UUID, y después corré go mod tidy y mirá cómo quedan go.mod y go.sum.

🧠 Autoevaluación

1. En Go, ¿qué hace que Calcular sea accesible desde otro paquete pero calcular no?

Go no tiene public/private. La visibilidad la decide la primera letra: mayúscula = exportado, minúscula = privado al paquete. Aplica a funciones, tipos, campos y constantes.

2. ¿Dónde tienen que vivir las funciones de test para que go test las encuentre?

Los tests van en archivos *_test.go junto al código. Así go test los compila solo durante el testeo y no terminan dentro de tu binario de producción.

3. ¿Qué define a un table-driven test?

El patrón idiomático: definís la tabla de casos como slice de structs y la recorrés con un for, nombrando cada subtest con t.Run. Agregar un caso nuevo es agregar una fila, sin duplicar lógica.

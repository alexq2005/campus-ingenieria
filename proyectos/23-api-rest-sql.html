🗃️ API REST con SQL e Índices

🎯 Objetivo: construir una API REST que persiste datos en PostgreSQL, con un modelo de datos bien diseñado, queries eficientes e índices que hacen la diferencia entre 5 ms y 5 segundos. Es el backend que sostiene casi cualquier app — y donde una mala decisión de esquema se paga durante años.
🔗 Conexión con el campus: M19 Modelado y SQL (esquema, joins, normalización), M20 Tuning (índices, EXPLAIN), M33 Fullstack y Python POO (modelos).

Cómo funciona — el índice que cambia todo

Qué vas a aprender

  • Diseñar un esquema relacional: tablas, claves, relaciones, normalización (M19).
  • CRUD vía SQL parametrizado (sin inyección SQL — M31 seguridad).
  • Diseñar endpoints REST con verbos y códigos de estado correctos.
  • Índices: cuándo crearlos, qué cuesta, y leer EXPLAIN ANALYZE (M20).
  • Joins, paginación y evitar el problema N+1.
  • Migraciones de esquema versionadas.

Stack

API: FastAPI (Python) o Express (Node) · PostgreSQL · un cliente SQL/ORM (psycopg, Drizzle, SQLAlchemy) · EXPLAIN ANALYZE para medir. Levantá Postgres con Docker (P21).

Código clave (query parametrizada + índice)

-- Esquema (M19)
CREATE TABLE pedidos (
  id        SERIAL PRIMARY KEY,
  cliente_id INT NOT NULL REFERENCES clientes(id),
  estado    TEXT NOT NULL,
  creado    TIMESTAMPTZ DEFAULT now()
);

-- Esta consulta se hace MUCHO → merece índice (M20)
-- EXPLAIN ANALYZE SELECT * FROM pedidos WHERE cliente_id = 42 AND estado = 'abierto';
CREATE INDEX idx_pedidos_cliente_estado ON pedidos (cliente_id, estado);

# API — NUNCA concatenar strings en SQL (inyección, M31)
@app.get("/clientes/{cid}/pedidos")
def pedidos_de(cid: int, estado: str = "abierto"):
    return db.execute(
        "SELECT * FROM pedidos WHERE cliente_id = %s AND estado = %s",
        (cid, estado),          # parámetros: la base los escapa por vos
    ).fetchall()
🔗 Dos lecciones que se cruzan: el índice compuesto (cliente_id, estado) acelera justo esa query (M20), y los parámetros %s previenen inyección SQL (M31). Concatenar la entrada del usuario en el SQL es el bug de seguridad #1 de la historia web — no lo hagas nunca.

Fases

Fase 1: diseñá el esquema (3-4 tablas con relaciones). Justificá claves y tipos.
Fase 2: API con CRUD completo, SQL parametrizado, códigos de estado correctos (200/201/404/422).
Fase 3: cargá ~100k filas de prueba. Encontrá una query lenta con EXPLAIN ANALYZE.
Fase 4: creá el índice adecuado. Volvé a medir: documentá el antes/después (ms).
Fase 5: paginación, manejo de errores, y migraciones versionadas del esquema.
✅ Terminado cuando:
  • La API hace CRUD completo y devuelve códigos de estado correctos.
  • Toda query usa parámetros (cero concatenación de strings).
  • Mostrás con EXPLAIN ANALYZE un Seq Scan que convertís en Index Scan, con los ms.
  • La paginación funciona y no hay N+1 en las listas.
  • El esquema tiene migraciones versionadas, no cambios a mano.

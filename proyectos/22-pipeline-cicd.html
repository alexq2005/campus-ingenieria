🔁 Pipeline CI/CD

🎯 Objetivo: que cada vez que hagas git push, una máquina corra tus tests, construya la app y —si todo pasa— la publique automáticamente. Eso es CI/CD: integración continua (validar siempre) + entrega continua (desplegar sin intervención manual). Adiós al "deploy a mano los viernes".
🔗 Conexión con el campus: M27 DevOps y CI/CD (pipelines), M26 Testing (la base de CI), Bash (los pasos del pipeline) y Testing en React.

Cómo funciona — el pipeline gatillado por push

Qué vas a aprender

  • Qué es un runner y cómo se define un workflow (YAML declarativo).
  • Disparadores: on push / pull_request, jobs, steps, matrices.
  • Correr tests automáticos en cada cambio (M26) — el corazón de CI.
  • Construir artefactos: bundle, imagen Docker (conecta con P21).
  • Secrets del repo para credenciales de deploy (sin exponerlas).
  • Gates: solo desplegar desde main y si todo pasó.

Stack

GitHub Actions (gratis para repos públicos) · tu proyecto con tests (pytest / Vitest) · destino de deploy: GitHub Pages, un VPS por SSH, o un registry de imágenes. Aplicable también a GitLab CI con sintaxis similar.

Código clave (.github/workflows/ci.yml)

name: CI/CD
on:
  push:
    branches: [main]          # gatillo: push a main

jobs:
  test-build-deploy:
    runs-on: ubuntu-latest    # un runner Linux efímero
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }

      - run: npm ci            # instalar exacto (lockfile)
      - run: npm run lint
      - run: npm test          # 🧪 si falla, el job corta acá (M26)
      - run: npm run build

      - name: Deploy            # solo se llega si todo lo anterior pasó
        run: ./scripts/deploy.sh
        env:
          DEPLOY_KEY: ${{ secrets.DEPLOY_KEY }}   # secreto del repo
🔗 El pipeline es un script de bash glorificado (Linux M09) que corre en un servidor limpio cada vez — por eso atrapa el "en mi máquina funciona". Y npm test como gate es la razón por la que M26 Testing importa: sin tests, CI no valida nada. Los secrets evitan poner claves en el código (M31).

Fases

Fase 1: un workflow mínimo que corra en cada push e imprima "hola". Entendé el ciclo runner/job/step.
Fase 2: CI real: instalar deps + lint + tests. Hacé fallar un test a propósito y mirá el pipeline rojo.
Fase 3: build del artefacto (bundle o imagen Docker, P21).
Fase 4: CD: deploy automático a GitHub Pages o por SSH, usando secrets.
Fase 5: badge de estado en el README, matriz de versiones, y bloqueo de merge si CI falla.
✅ Terminado cuando:
  • Cada push corre tests automáticamente y muestra ✓/✗ en GitHub.
  • Un test que falla DETIENE el deploy (el gate funciona).
  • El deploy es 100% automático: no tocás nada a mano.
  • Las credenciales viven en secrets, no en el repo.
  • El README muestra el badge de estado del pipeline.

Variantes

  1. Matriz: testear en varias versiones de Node/Python a la vez.
  2. Entornos: deploy automático a staging, manual a producción (con aprobación).
  3. Construir y publicar la imagen Docker del stack de P21 en un registry.
  4. Caché de dependencias para acelerar el pipeline.
  5. Notificar a Slack/Discord cuando el deploy termina o falla.

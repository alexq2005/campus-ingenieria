⚡ Caché con Redis

🎯 Objetivo: tomar una API con una query costosa y ponerle Redis como caché en memoria con el patrón cache-aside. La primera vez consultás la base; las siguientes, respondés desde RAM en sub-milisegundo. Vas a entender el trade-off central de los sistemas: velocidad vs frescura de los datos.
🔗 Conexión con el campus: M21 NoSQL/NewSQL (key-value en memoria), M20 Tuning (cuándo cachear), M13 Arquitectura (jerarquía de memoria) y el Proyecto 23 (API+SQL).

Cómo funciona — cache-aside (hit vs miss)

Qué vas a aprender

  • El patrón cache-aside (lazy loading) y cuándo conviene.
  • Redis como key-value en memoria y por qué es tan rápido (M21, M13 jerarquía de memoria).
  • TTL y expiración: balancear frescura vs carga a la base.
  • Invalidación de caché — "uno de los dos problemas difíciles de CS".
  • Medir hit ratio y latencia p50/p99 antes y después.
  • Riesgos: datos rancios, stampede, qué NO cachear.

Stack

Redis (Docker, P21) · la API del Proyecto 23 (o cualquier endpoint con una query cara) · cliente Redis (redis-py / ioredis) · una herramienta de carga (ab, wrk, k6) para medir.

Código clave (cache-aside con TTL)

import json, redis
r = redis.Redis()

def get_pedidos(cliente_id):
    key = f"pedidos:{cliente_id}"

    cached = r.get(key)              # 1) ¿hit?
    if cached:
        return json.loads(cached)   # responde desde RAM (<1ms)

    datos = db_query(cliente_id)     # 2) miss → base (lento)
    r.setex(key, 60, json.dumps(datos))   # 3) guardar 60s (TTL)
    return datos

def crear_pedido(cliente_id, pedido):
    db_insert(pedido)
    r.delete(f"pedidos:{cliente_id}")     # invalidar: el dato cambió
🔗 El setex con TTL es el corazón del trade-off: 60s de caché = hasta 60s de datos potencialmente rancios, a cambio de muchísima menos carga en la base. Y el delete al escribir es la invalidación — si te la olvidás, servís datos viejos. Esto conecta con la jerarquía de memoria de M13: caché rápida y chica delante de almacenamiento lento y grande, la misma idea que L1/L2/RAM/disco.

Fases

Fase 1: levantá Redis (Docker) y jugá con SET/GET/EXPIRE desde el CLI. Entendé key-value.
Fase 2: medí la latencia de tu endpoint lento SIN caché (p50/p99). Anotá los números.
Fase 3: implementá cache-aside con TTL. Volvé a medir: el speedup debería ser dramático.
Fase 4: invalidación al escribir. Verificá que NO servís datos rancios tras un cambio.
Fase 5: medí el hit ratio bajo carga. Ajustá el TTL según frescura vs carga.
✅ Terminado cuando:
  • Mostrás con números el antes/después de latencia (p99) con y sin caché.
  • El hit ratio es alto bajo carga repetida.
  • Tras escribir, la siguiente lectura refleja el dato nuevo (invalidación correcta).
  • Definiste un TTL razonable y podés justificarlo.
  • Sabés explicar qué NO cachearías y por qué (datos sensibles, muy volátiles).

Variantes

  1. Rate limiting con Redis (contador con TTL) — protección de la API (M30).
  2. Redis como cola de trabajos (jobs en background).
  3. Pub/Sub de Redis para notificaciones en vivo (conecta con el Chat real-time, P08).
  4. Sesiones de usuario en Redis en vez de en la base.
  5. Estrategia write-through vs cache-aside: compará trade-offs.

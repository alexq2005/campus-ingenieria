Módulo 12 — Performance y Testing

Si tu app tarda 2 segundos en hacer un click, perdés usuarios. Si tu app no tiene tests, perdés tu sueño cada deploy. Estos dos temas separan apps "que funcionan" de apps "production-grade".

Parte 1 — Performance

1. La regla de oro: medí antes de optimizar

"Premature optimization is the root of all evil." — Knuth

No memoices, no codeés code splitting, no useCallback "por las dudas". Primero:
  1. Reproducí el problema (cuantificalo: "click tarda 2s").
  2. Medí con React Profiler.
  3. Identificá el componente lento.
  4. Aplicá la optimización específica.
  5. Re-medí: ¿el problema se fue?

2. React Profiler

En DevTools → tab "⚛️ Profiler" → record interacción → ver qué componentes renderizaron y cuánto tardaron.

  • Naranja/rojo = lento → candidato a optimizar.
  • Verde = rápido → ignorar.
  • Si ves componentes renderizando "por nada" (props no cambiaron) → candidato a memo.

3. React.memo — evitar re-renders innecesarios

// Sin memo: re-renderiza siempre que el padre re-renderiza
function Item({ texto }) {
  console.log('Render Item:', texto);
  return <li>{texto}</li>;
}

// Con memo: re-renderiza SOLO si las props cambian
const Item = React.memo(function Item({ texto }) {
  console.log('Render Item:', texto);
  return <li>{texto}</li>;
});
memo compara props con Object.is (shallow). Si pasás objeto/array/función inline, SIEMPRE es referencia nueva → memo no sirve. Combinar con useMemo/useCallback en el padre.

4. useMemo y useCallback (recap M07)

function Padre({ items }) {
  // Sin useMemo, filtrados es array nuevo cada render
  const filtrados = useMemo(() =>
    items.filter(i => i.activo),
    [items]
  );

  // Sin useCallback, handleClick es función nueva cada render
  const handleClick = useCallback((id) => {
    console.log(id);
  }, []);

  return <Lista items={filtrados} onClick={handleClick} />;
}

const Lista = React.memo(function Lista({ items, onClick }) {
  // Ahora SÍ se beneficia del memo
  return ...;
});

5. Code splitting con lazy y Suspense

Cargar componentes solo cuando se necesitan reduce el bundle inicial:

import { lazy, Suspense } from 'react';

const Dashboard = lazy(() => import('./Dashboard'));
const Settings = lazy(() => import('./Settings'));

function App() {
  return (
    <Suspense fallback={<Spinner />}>
      <Routes>
        <Route path="/dashboard" element={<Dashboard />} />
        <Route path="/settings" element={<Settings />} />
      </Routes>
    </Suspense>
  );
}
Code splitting por ruta es el "low-hanging fruit" más grande para reducir bundle inicial. Vite + React lo hacen automáticamente con lazy.

6. Virtualización para listas largas

Si renderizás 10000 items, el browser muere. Solución: virtualizar — renderizar solo los visibles en pantalla.

npm install @tanstack/react-virtual
import { useVirtualizer } from '@tanstack/react-virtual';

function HugeList({ items }) {
  const parentRef = useRef(null);

  const virtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 40,
  });

  return (
    <div ref={parentRef} style={{ height: 400, overflow: 'auto' }}>
      <div style={{ height: virtualizer.getTotalSize(), position: 'relative' }}>
        {virtualizer.getVirtualItems().map((virtualItem) => (
          <div
            key={virtualItem.key}
            style={{
              position: 'absolute',
              top: 0,
              transform: `translateY(${virtualItem.start}px)`,
              height: virtualItem.size,
            }}
          >
            {items[virtualItem.index].nombre}
          </div>
        ))}
      </div>
    </div>
  );
}

7. Otras optimizaciones

  • Imágenes: loading="lazy" + WebP/AVIF + tamaños responsive con srcset.
  • Web fonts: font-display: swap, preload de fuentes críticas.
  • Bundle analysis: vite-plugin-bundle-visualizer para ver qué pesa.
  • Tree-shaking: importar solo lo necesario: import { merge } from 'lodash-es', NO import _ from 'lodash'.
  • React Compiler (RC en 2026): memoiza automáticamente. Si está activo, useMemo/useCallback manuales se vuelven raros.

Parte 2 — Testing

8. ¿Por qué testear?

Tests automáticos te dan confianza para refactorizar, agregar features y deploy sin pánico. Sin tests, cada cambio puede romper algo no relacionado y no enterarte hasta producción.

11. Tu primer test

// src/components/Boton.jsx
function Boton({ onClick, children }) {
  return <button onClick={onClick}>{children}</button>;
}

// src/components/Boton.test.jsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { describe, it, expect, vi } from 'vitest';
import Boton from './Boton';

describe('Boton', () => {
  it('muestra el children', () => {
    render(<Boton>Hola</Boton>);
    expect(screen.getByText('Hola')).toBeInTheDocument();
  });

  it('llama onClick al click', async () => {
    const onClick = vi.fn();
    render(<Boton onClick={onClick}>Click</Boton>);

    await userEvent.click(screen.getByRole('button'));

    expect(onClick).toHaveBeenCalledTimes(1);
  });
});

12. Filosofía de Testing Library

"Test how users use the app, not how it's built." — Kent C. Dodds

Buscás elementos por lo que el usuario ve: text, role, label. NO por className o id interno (esos pueden cambiar al refactorizar).
PrioridadQuery
1getByRole — más accesible (button, link, heading)
2getByLabelText — form inputs
3getByText — texto visible
4getByPlaceholderText — fallback
5getByTestId — último recurso (con data-testid="...")

13. Test con estado y eventos

// Contador.jsx
function Contador() {
  const [count, setCount] = useState(0);
  return (
    <>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>+1</button>
    </>
  );
}

// Contador.test.jsx
it('incrementa al click', async () => {
  render(<Contador />);

  expect(screen.getByText('Count: 0')).toBeInTheDocument();

  await userEvent.click(screen.getByRole('button', { name: '+1' }));

  expect(screen.getByText('Count: 1')).toBeInTheDocument();
});

14. Testear async (fetch)

// Posts.test.jsx
import { render, screen } from '@testing-library/react';
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';

const queryClient = new QueryClient({
  defaultOptions: { queries: { retry: false } },
});

it('muestra posts cargados', async () => {
  // Mock global fetch
  global.fetch = vi.fn().mockResolvedValueOnce({
    ok: true,
    json: async () => [{ id: 1, title: 'Post 1' }],
  });

  render(
    <QueryClientProvider client={queryClient}>
      <Posts />
    </QueryClientProvider>
  );

  expect(screen.getByText(/cargando/i)).toBeInTheDocument();

  // Esperar a que aparezca el post
  expect(await screen.findByText('Post 1')).toBeInTheDocument();
});

16. Errores típicos

Memoizar todo "por performance": si el componente es rápido, memo agrega overhead sin beneficio. Medí primero.
memo sin useCallback en el padre: pasás onClick={() => ...} (nuevo cada render) → memo no sirve. Combinar.
Listas larguísimas sin virtualizar: 5000 DOM nodes = lag. Virtualizar a partir de ~100 items visibles.
Tests acoplados al markup: assert por className o estructura interna. Refactor del CSS rompe el test. Usar roles/text.
No mockear fetch en tests: tests dependen del backend → flaky, lentos. Mockear con MSW o vi.fn.
Solo unit tests: sin integration tests no detectás cuando componentes se combinan mal. Pyramid balanceada.

✅ Checkpoint

1. ¿Cuándo usar React.memo?

Cuando MEDISTE que un componente re-renderiza sin necesidad (props no cambiaron) Y el componente es costoso de renderizar. NO memoizes por las dudas — overhead de comparación de props se acumula.

2. ¿Por qué memo a veces "no funciona"?

Porque memo compara props con Object.is (shallow). Si el padre pasa objeto/array/función inline, son referencias nuevas cada render → memo siempre falla. Hay que combinar con useMemo/useCallback en el padre para preservar referencias.

3. ¿Qué es code splitting?

Dividir el bundle JS en chunks que se cargan bajo demanda. Con lazy(() => import('./X')) + Suspense, el chunk X solo se descarga cuando se renderiza por primera vez. Reduce drásticamente el bundle inicial.

4. ¿Cuándo virtualizar listas?

Cuando renderizás > ~100 items simultáneos. Por debajo, el DOM aguanta sin lag. Por arriba, virtualizar evita crear miles de nodos invisibles. Usar TanStack Virtual o react-window.

5. ¿Por qué buscar elementos por role en lugar de className?

Porque className es detalle de implementación; role refleja CÓMO usa el usuario (button, link, heading). Refactorizar CSS no rompe tests basados en roles. Además, escribir tests con roles te fuerza a hacer el HTML accesible.

6. ¿Qué es la pirámide de testing?

Muchos tests unit (rápidos, baratos), medio integration tests (componentes combinados), pocos E2E (lentos, caros pero realistas). Mantener proporción evita lentitud Y falta de cobertura realista.

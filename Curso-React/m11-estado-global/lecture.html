Módulo 11 — Estado Global

Cuando muchos componentes necesitan los mismos datos, levantar estado pierde sentido. Necesitás un "store global". En 2026 hay varias opciones — saber cuál usar es la clave.

1. Decisión jerárquica de estado

Antes de "estado global", probá en este orden:
  1. useState local: si solo lo usa 1 componente.
  2. Lifting state: si 2-3 hermanos lo comparten.
  3. Composición / children: si querés evitar pasarlo manualmente.
  4. useContext: si lo necesita un subárbol (theme, locale, user actual).
  5. Zustand / Redux: si MUCHAS partes lo necesitan y cambia con frecuencia.
  6. URL params: si es estado de navegación (filtro, página).
  7. TanStack Query: si es server state.

2. Context API — la solución built-in

// stores/AuthContext.jsx
import { createContext, useContext, useState } from 'react';

const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);

  const login = async (email, pwd) => { /* ... */ };
  const logout = () => setUser(null);

  return (
    <AuthContext.Provider value={{ user, login, logout }}>
      {children}
    </AuthContext.Provider>
  );
}

export function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth fuera de AuthProvider');
  return ctx;
}

// Uso
<AuthProvider>
  <App />
</AuthProvider>

function Header() {
  const { user, logout } = useAuth();
  // ...
}
Context API tiene un problema: TODO el subárbol bajo el Provider re-renderiza si cambia el value (objeto nuevo). Para apps grandes con updates frecuentes, prefiero Zustand.

3. Zustand — el estándar moderno 2026

npm install zustand
// stores/useCounterStore.js
import { create } from 'zustand';

export const useCounterStore = create((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
  decrement: () => set((state) => ({ count: state.count - 1 })),
  reset: () => set({ count: 0 }),
}));
// Uso desde cualquier componente — sin Provider, sin nada
function Counter() {
  const { count, increment } = useCounterStore();
  return (
    <>
      <p>{count}</p>
      <button onClick={increment}>+1</button>
    </>
  );
}

function CounterDisplay() {
  // Solo se suscribe a `count` — no re-renderiza si cambia OTRO field
  const count = useCounterStore((state) => state.count);
  return <h1>{count}</h1>;
}
Zustand brilla por su simplicidad: no necesita Provider, selectors granulares evitan re-renders innecesarios, API mínima. Para 2026 es la opción por defecto cuando context no alcanza.

4. Zustand con persistencia

import { create } from 'zustand';
import { persist } from 'zustand/middleware';

export const useThemeStore = create(
  persist(
    (set) => ({
      theme: 'light',
      toggle: () => set((s) => ({ theme: s.theme === 'light' ? 'dark' : 'light' })),
    }),
    { name: 'theme-storage' }  // guardado en localStorage
  )
);

5. Zustand "slices" — store grande dividido

// Cada slice maneja un dominio
const createAuthSlice = (set) => ({
  user: null,
  login: (u) => set({ user: u }),
  logout: () => set({ user: null }),
});

const createCartSlice = (set) => ({
  items: [],
  addItem: (item) => set((s) => ({ items: [...s.items, item] })),
});

// Combinar
export const useStore = create((set) => ({
  ...createAuthSlice(set),
  ...createCartSlice(set),
}));

6. Redux Toolkit — el "viejo confiable"

Redux sigue siendo común en proyectos enterprise. La librería moderna se llama Redux Toolkit (RTK):

npm install @reduxjs/toolkit react-redux
// store/counterSlice.js
import { createSlice } from '@reduxjs/toolkit';

const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    increment: (state) => { state.value++; },  // Immer permite mutar
    decrement: (state) => { state.value--; },
  },
});

export const { increment, decrement } = counterSlice.actions;
export default counterSlice.reducer;
// store/index.js
import { configureStore } from '@reduxjs/toolkit';
import counterReducer from './counterSlice';

export const store = configureStore({
  reducer: { counter: counterReducer },
});

// Uso
function Counter() {
  const count = useSelector((s) => s.counter.value);
  const dispatch = useDispatch();

  return (
    <>
      <p>{count}</p>
      <button onClick={() => dispatch(increment())}>+1</button>
    </>
  );
}
RTK incluye RTK Query (alternativa a TanStack Query) y maneja bien apps grandes. Tiene MÁS boilerplate que Zustand pero más patrones consolidados para equipos grandes.

7. Jotai — atomic state

import { atom, useAtom } from 'jotai';

const countAtom = atom(0);

function Counter() {
  const [count, setCount] = useAtom(countAtom);
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}

Jotai es "Recoil-like": estado en átomos pequeños, componibles. Bueno cuando tu estado es muy granular.

9. Cuándo necesitás estado global de verdad

  • Usuario logueado (auth) — accesible en todo el árbol.
  • Carrito de compras — visible en navbar + checkout + detalle.
  • Notificaciones / toasts — disparables desde cualquier lugar.
  • Tema / preferencias UI — afectan todo.
  • Filtros globales que afectan múltiples componentes.
Si solo lo usás en 1-2 componentes, NO es estado global. Mantenelo local. El estado global "por las dudas" agrega complejidad y dificulta razonar sobre la app.

10. Patrón: combinar Zustand + TanStack Query

Tipo de estadoDónde va
Server state (posts del backend)TanStack Query
UI state local (modal abierto)useState
UI state global (theme, sidebar abierto)Zustand
Estado de form mientras se escribeuseState o React Hook Form
Filtros que vienen de URLuseSearchParams
Esta separación es CRUCIAL. Mezclar server y client state en el mismo store es bug factory.

11. Mini-ejemplo: store de carrito con Zustand

// stores/useCartStore.js
import { create } from 'zustand';
import { persist } from 'zustand/middleware';

export const useCartStore = create(
  persist(
    (set, get) => ({
      items: [],

      addItem: (product) => set((state) => {
        const existing = state.items.find(i => i.id === product.id);
        if (existing) {
          return {
            items: state.items.map(i =>
              i.id === product.id ? { ...i, qty: i.qty + 1 } : i
            )
          };
        }
        return { items: [...state.items, { ...product, qty: 1 }] };
      }),

      removeItem: (id) => set((state) => ({
        items: state.items.filter(i => i.id !== id)
      })),

      clear: () => set({ items: [] }),

      total: () => get().items.reduce((sum, i) => sum + i.precio * i.qty, 0),
    }),
    { name: 'cart-storage' }
  )
);

// Uso
function NavBar() {
  const count = useCartStore((s) => s.items.length);
  return <span>🛒 {count}</span>;
}

function ProductCard({ product }) {
  const addItem = useCartStore((s) => s.addItem);
  return <button onClick={() => addItem(product)}>Agregar</button>;
}

12. Errores típicos

Empezar con Redux desde el día 1: la mayoría de apps no lo necesitan. Empezá local, escalá a Zustand si duele.
Server state en Zustand: set({ posts: await fetch(...) }). No tenés cache automático, ni refetch, ni dedup. Usá TanStack Query.
Context con value inline: <Ctx.Provider value={{ x, y }}>. Objeto nuevo cada render → todo el subárbol re-renderiza. Memoizar el value.
Zustand sin selectors: const store = useStore() trae todo el store → re-render cuando CUALQUIER campo cambia. Usar selectors: useStore(s => s.count).
Reescribir todo en Redux por "buen patrón": no es 2018. Apps modernas usan menos Redux. Zustand + TanStack Query cubre el 90%.

✅ Checkpoint

1. ¿Cuándo necesitás "estado global"?

Cuando múltiples componentes en distintas partes del árbol necesitan el mismo dato Y este cambia con cierta frecuencia. Ejemplos: auth, carrito, tema, notificaciones. Si solo 2-3 hermanos lo usan, lift state al padre — no es global.

2. ¿Diferencia entre Context y Zustand?

Context es built-in pero causa re-render de todo el subárbol cuando el value cambia. Zustand es externo (~3KB), permite selectors granulares, no requiere Provider y tiene mejor performance en stores grandes.

3. ¿Cuándo elegir Redux Toolkit sobre Zustand?

Equipos grandes con patrones rígidos consolidados, devtools de Redux que querés mantener, ya tenés código RTK en producción, o necesitás middleware complejo (saga, observables).

4. ¿Server state vs client state?

Server state = datos del backend (posts, users). Necesita cache, refetch, dedup → TanStack Query / SWR. Client state = UI local (modal abierto, tema) → useState o Zustand. MEZCLAR los dos en el mismo store es antipatrón.

5. ¿Qué problema resuelven los selectors de Zustand?

Permiten suscribirse SOLO a una parte del store. useStore(s => s.count) hace que el componente re-renderice solo si count cambia, ignorando cambios en otros fields del store.

6. ¿Qué es Jotai?

Librería de estado "atómico": cada pieza es un "atom" pequeño y componible. Bueno cuando tu estado es muy granular o necesitás derivar valores async. Inspirado en Recoil pero más simple.

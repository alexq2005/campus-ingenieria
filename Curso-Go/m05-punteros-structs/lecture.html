Módulo 05 — Punteros & Métodos

Hasta acá pasaste valores a funciones y trabajaste con structs como si fueran cajas. En este módulo abrís el capó: un puntero es simplemente la dirección donde vive un valor en memoria. Con eso podés mutar el original en lugar de una copia, y evitar copiar structs grandes. Después le colgás métodos a tus tipos, y ahí aparece la decisión clave del módulo: receiver por valor vs por puntero.

Punteros sin miedo

💡 Un puntero guarda la dirección de memoria de un valor, no el valor en sí. Dos operadores son todo lo que necesitás: &x te da la dirección de x, y *p te da el valor apuntado por p (a esto se le llama "dereferenciar").

Mirá los dos operadores en acción:

x := 42
p := &x        // p es un *int: guarda la dirección de x
fmt.Println(p)  // imprime algo como 0xc0000140a0 (la dirección)
fmt.Println(*p) // imprime 42  (dereferencio: voy a buscar el valor)

*p = 100        // escribo a través del puntero
fmt.Println(x)  // imprime 100  ¡cambié x sin tocar x directamente!

El tipo de p se escribe *int ("puntero a int"). Para string sería *string, para un struct Persona sería *Persona, y así.

🔗 Analogía: pensá en una variable como una casa y su valor como lo que hay adentro. El puntero es la dirección postal de esa casa. Tener la dirección (&x) te deja entrar y cambiar lo que hay adentro (*p = ...) sin necesidad de "ser" la casa. Si le pasás la dirección a otra persona, ella entra a la misma casa, no a una copia.
Go NO tiene aritmética de punteros. En C podés hacer p + 1 para "moverte" a la siguiente posición de memoria — fuente clásica de bugs y agujeros de seguridad. En Go un puntero solo apunta o no apunta; no lo podés sumar ni restar. Más simple y mucho más seguro.

¿Para qué sirven realmente?

Dos motivos prácticos, y los dos importan:

  • Mutar el original (pasar por referencia). En Go los argumentos se pasan siempre por copia. Si una función recibe un valor y lo modifica, modifica su copia local — el original queda intacto. Pasando un puntero, la función puede tocar el original.
  • Evitar copiar structs grandes. Pasar un struct de 50 campos por valor copia los 50 campos en cada llamada. Pasar un *Struct copia solo la dirección (8 bytes). Más rápido y menos memoria.

Comparemos copia vs puntero en una función:

func duplicarCopia(n int) {
    n = n * 2          // toco MI copia local
}

func duplicarPuntero(n *int) {
    *n = *n * 2        // toco el original a través del puntero
}

func main() {
    x := 10
    duplicarCopia(x)
    fmt.Println(x)     // 10  — no cambió nada

    duplicarPuntero(&x)
    fmt.Println(x)     // 20  — sí cambió
}

Métodos sobre tipos

Un método es una función con un parámetro especial — el receiver — que va antes del nombre de la función. Ese receiver dice "esta función pertenece a este tipo".

type Persona struct {
    Nombre string
    Edad   int
}

// (p Persona) es el receiver: Saludar es un método de Persona
func (p Persona) Saludar() string {
    return "Hola, soy " + p.Nombre
}

func main() {
    juana := Persona{Nombre: "Juana", Edad: 30}
    fmt.Println(juana.Saludar())   // Hola, soy Juana
}
📌 Forma del receiver: func (recibidor Tipo) NombreMetodo(args) retorno { ... }. El receiver es como el self de Python o el this de otros lenguajes, pero en Go lo nombrás vos (la convención es una o dos letras: p para Persona, c para Cuenta). Podés colgar métodos sobre cualquier tipo que definas vos, no solo structs.

Receiver por VALOR vs por PUNTERO

Esta es la decisión central del módulo. El receiver puede ser por valor (p Persona) o por puntero (p *Persona), y cambia todo:

AspectoReceiver por valor (p Persona)Receiver por puntero (p *Persona)
Trabaja sobreUna copia del structEl original
¿Puede mutar el original?No (los cambios se pierden)Sí
CostoCopia todo el structCopia solo la dirección (8 bytes)
Cuándo usarloMétodos de solo lectura sobre structs chicosCuando mutás, o el struct es grande
📌 Regla práctica: si el método modifica el struct o el struct es grande, usá receiver por puntero. Si solo lee y el struct es chico, valor está bien. Ante la duda, muchos equipos usan puntero por consistencia.

Ejemplo: mutar un campo (puntero) vs no mutarlo (valor)

Acá se ve con claridad la diferencia. Tenemos dos métodos: uno con receiver por puntero y otro por valor, ambos intentan cumplir años:

type Persona struct {
    Nombre string
    Edad   int
}

// Receiver por PUNTERO: muta el original
func (p *Persona) CumplirAniosReal() {
    p.Edad++          // Go dereferencia solo: equivale a (*p).Edad++
}

// Receiver por VALOR: trabaja sobre una copia, el cambio se pierde
func (p Persona) CumplirAniosFalso() {
    p.Edad++          // incrementa la copia local; el original NO cambia
}

func main() {
    juana := Persona{Nombre: "Juana", Edad: 30}

    juana.CumplirAniosFalso()
    fmt.Println(juana.Edad)   // 30  — la copia se descartó

    juana.CumplirAniosReal()
    fmt.Println(juana.Edad)   // 31  — mutó el original
}
Fijate que dentro de CumplirAniosReal escribimos p.Edad++ y no (*p).Edad++. Go dereferencia los punteros a struct automáticamente cuando accedés a sus campos. Las dos formas son válidas; p.Edad es el azúcar sintáctico que casi todos usan.

Crear: new(T) vs &T{}

Hay dos formas de obtener un puntero a un struct nuevo:

// Opción A: &T{} — la más común. Creás e inicializás campos a la vez.
p1 := &Persona{Nombre: "Ana", Edad: 25}   // p1 es *Persona

// Opción B: new(T) — reserva memoria con todos los campos en su valor cero.
p2 := new(Persona)                         // p2 es *Persona, {Nombre:"", Edad:0}
p2.Nombre = "Beto"
p2.Edad = 40
✅ En la práctica: usá &T{...} casi siempre — es más corto y podés inicializar campos en el acto. new(T) es útil cuando solo querés un puntero a un valor cero y vas a llenar los campos después. Las dos te devuelven un *T.

Llamar métodos de puntero sobre valores (azúcar sintáctico)

Acá hay un detalle que confunde al principio. Si CumplirAniosReal tiene receiver *Persona, ¿cómo es que lo llamamos sobre juana, que es un valor y no un puntero?

juana := Persona{Nombre: "Juana", Edad: 30}
juana.CumplirAniosReal()   // funciona, aunque el receiver es *Persona
💡 Go llama métodos de puntero sobre valores direccionables automáticamente. Como juana es una variable (tiene una dirección sacable con &), Go reescribe juana.CumplirAniosReal() como (&juana).CumplirAniosReal() por vos. Es azúcar sintáctico: te ahorra escribir el &.
⚠️ "Direccionable" es la clave. El truco funciona porque juana es una variable. Pero un valor que no tiene dirección — como un elemento de un map (m["k"].Metodo()) o el retorno directo de una función — no es direccionable, y ahí Go no puede aplicar el azúcar: tenés que guardar el valor en una variable primero.

Errores típicos

Usar receiver por valor cuando querés mutar. Escribís func (c Cuenta) Depositar(m int) { c.Saldo += m } y el saldo nunca cambia: estás incrementando una copia que se descarta al volver. Debería ser func (c *Cuenta) Depositar(...).
Dereferenciar un puntero nil → panic. Un *Persona sin inicializar vale nil. Hacer p.Edad (que dereferencia) revienta con panic: runtime error: invalid memory address or nil pointer dereference. Verificá if p != nil antes de tocarlo.
Mezclar receivers por valor y por puntero en el mismo tipo. Si algunos métodos de Persona usan (p Persona) y otros (p *Persona), el código se vuelve confuso y, peor, puede romper la implementación de interfaces (M06). La guía oficial de Go: elegí uno por tipo y sé consistente.

Checkpoint — ¿lo tenés claro?

¿Qué hacen &x y *p?

&x te da la dirección de x (un puntero). *p dereferencia: va a buscar el valor que vive en la dirección guardada en p. Con *p = 100 escribís ese valor a través del puntero.

¿Por qué un método con receiver por valor no muta el original?

Porque en Go todo se pasa por copia. El receiver por valor recibe una copia del struct; cualquier cambio que le hagas vive en esa copia y se descarta al volver del método. Para mutar el original necesitás receiver por puntero (p *Tipo).

Si un método tiene receiver *Persona, ¿puedo llamarlo sobre una variable Persona?

Sí, siempre que la variable sea direccionable (que es el caso normal de una variable local). Go reescribe juana.Metodo() como (&juana).Metodo() automáticamente. No funciona sobre valores no direccionables como un elemento de un map.

Ejercicios

  1. Declará x := 5, creá p := &x, imprimí *p, luego hacé *p = 99 e imprimí x. Confirmá que cambió.
  2. Escribí una función incrementar(n *int) que sume 1 al valor apuntado. Llamala con & sobre una variable y verificá el efecto.
  3. Definí un struct Cuenta{ Saldo int } con un método Depositar(m int) de receiver por puntero que sume al saldo. Probá que el saldo persiste entre llamadas.
  4. Agregá a Cuenta un método Resumen() string de receiver por valor (solo lectura) que devuelva el saldo formateado. Explicá por qué este sí puede ser por valor.
  5. Creá una Persona con new(Persona) y otra con &Persona{...}. Imprimí ambas y comprobá que las dos son *Persona con fmt.Printf("%T\n", p).

🧠 Autoevaluación

1. ¿Qué hace el operador & aplicado a una variable?

&x da la dirección de x, o sea un puntero a x. Dereferenciar (traer el valor) es *p. Y Go no tiene aritmética de punteros, así que sumar a una dirección no existe.

2. Un método con receiver por valor (p Persona) que hace p.Edad++...

El receiver por valor recibe una copia del struct. El ++ afecta a esa copia local, que se descarta al volver. Para mutar el original hace falta receiver por puntero (p *Persona).

3. Tenés juana := Persona{...} (una variable) y un método con receiver *Persona. ¿Podés escribir juana.Metodo()?

Go llama métodos de puntero sobre valores direccionables automáticamente: reescribe juana.Metodo() como (&juana).Metodo(). Esto solo aplica a valores direccionables (variables), no a cosas como elementos de un map.

Módulo 06 — Interfaces

Las interfaces son el corazón del diseño en Go. Si en M05 aprendiste a darle métodos a tus structs, acá das el salto: dejás de pensar en qué tipo concreto tenés y empezás a pensar en qué puede hacer. Una interface describe comportamiento, no datos. Y la forma en que Go las conecta con tus tipos —de manera implícita, sin que digas nada— es lo que hace que el código sea tan flexible y desacoplado.

¿Qué es una interface?

💡 Una interface define COMPORTAMIENTO: un conjunto de métodos. No dice qué datos guarda un tipo, ni cómo los guarda. Dice solamente qué sabe hacer. Cualquier tipo que tenga esos métodos puede usarse donde se espera la interface.

La declaración más simple posible:

type Escritor interface {
    Escribir(s string) error
}

Eso es todo: Escritor es cualquier cosa que tenga un método Escribir(string) error. No importa si es un archivo, una conexión de red, un buffer en memoria o una impresora — si tiene ese método, es un Escritor.

🔌 Pensalo como un enchufe. La interface es la forma del enchufe (la firma de los métodos). Cualquier aparato que tenga esa forma de patas encaja, sin que el enchufe sepa ni le importe qué aparato es. La pared no pregunta "¿sos una tele o un cargador?"; solo le importa que tengas las patas correctas.

Implementación IMPLÍCITA: la idea clave de Go

💡 En Go NO existe la palabra implements. Si un tipo tiene todos los métodos que la interface pide, la satisface automáticamente. No declarás la relación en ningún lado: Go la deduce. Es duck typing ("si camina como pato y hace cuac como pato, es un pato") pero verificado en tiempo de compilación, no en runtime.

Compará cómo se declara la relación tipo↔interface en distintos lenguajes:

Lenguaje¿Cómo se declara que un tipo cumple la interface?
Java / C#Explícito: class Archivo implements Escritor
PythonImplícito pero sin chequeo: el error aparece en runtime (duck typing puro)
GoImplícito y chequeado al compilar: si tiene los métodos, ya está

Esto cambia cómo diseñás. En Java definís la interface y después los tipos "se anotan" para cumplirla. En Go podés definir una interface después, sobre tipos que ya existen (incluso de otra librería), y van a satisfacerla sin tocar su código.

Esta inversión es poderosa: el consumidor define la interface que necesita, no el productor. Si tu función solo necesita algo que sepa Escribir, declarás una interface chica con ese único método. Cualquier tipo del ecosistema que ya tenga Escribir entra gratis.

Ejemplo completo: una interface, dos tipos, una función

Definimos una interface Figura (algo que sabe calcular su área). Después dos structs que la satisfacen sin declararlo, y una función que acepta la interface:

package main

import (
    "fmt"
    "math"
)

// 1) La interface: comportamiento, no datos.
type Figura interface {
    Area() float64
}

// 2) Primer tipo concreto.
type Rectangulo struct {
    Ancho, Alto float64
}

func (r Rectangulo) Area() float64 {
    return r.Ancho * r.Alto
}

// 3) Segundo tipo concreto. No dice "implements Figura" en ningún lado.
type Circulo struct {
    Radio float64
}

func (c Circulo) Area() float64 {
    return math.Pi * c.Radio * c.Radio
}

// 4) Una función que acepta la INTERFACE, no el tipo concreto.
//    Funciona con Rectangulo, Circulo, o cualquier cosa futura que tenga Area().
func describir(f Figura) {
    fmt.Printf("El área es %.2f\n", f.Area())
}

func main() {
    describir(Rectangulo{Ancho: 3, Alto: 4}) // El área es 12.00
    describir(Circulo{Radio: 5})             // El área es 78.54

    // También podés guardarlas mezcladas en un slice de la interface:
    figuras := []Figura{
        Rectangulo{Ancho: 2, Alto: 2},
        Circulo{Radio: 1},
    }
    for _, f := range figuras {
        describir(f)
    }
}

Ninguno de los dos structs sabe que existe Figura. Solo tienen un método Area() float64, y eso los convierte en Figura automáticamente.

Interfaces chicas son mejores

📌 Idiom de Go: "The bigger the interface, the weaker the abstraction". Cuanto más grande la interface, peor la abstracción. Las mejores interfaces de la stdlib tienen uno o dos métodos. Una interface chica es fácil de satisfacer, fácil de combinar y fácil de mockear en tests.

Las dos interfaces más usadas de toda la librería estándar tienen un solo método cada una:

// io.Writer: cualquier cosa donde puedas escribir bytes.
type Writer interface {
    Write(p []byte) (n int, err error)
}

// fmt.Stringer: cualquier cosa que sepa describirse como texto.
type Stringer interface {
    String() string
}

io.Writer es tan chica que la cumplen un archivo, una conexión TCP, un buffer en memoria, os.Stdout y hasta un http.ResponseWriter. Por eso podés escribir tu lógica una vez y mandarla a cualquiera de esos destinos.

Implementar fmt.Stringer

Si tu tipo tiene un método String() string, fmt.Println y fmt.Printf("%v") lo usan automáticamente para imprimirlo bonito:

type Temperatura float64

// Con esto, Temperatura satisface fmt.Stringer.
func (t Temperatura) String() string {
    return fmt.Sprintf("%.1f°C", float64(t))
}

func main() {
    t := Temperatura(21.5)
    fmt.Println(t) // imprime: 21.5°C  (no 21.5)
}
✅ Truco para chequear en compilación que cumplís una interface: agregá una línea var _ fmt.Stringer = Temperatura(0). Si el tipo no satisface la interface, el código no compila — y lo descubrís al toque, no cuando falla en producción.

La interface vacía: interface{} / any

💡 La interface vacía interface{} no pide ningún método, así que cualquier valor la satisface. Desde Go 1.18 existe el alias any, que es exactamente lo mismo pero se lee mejor. Es el "comodín" de Go: sirve para guardar valores de tipo desconocido. 
// Estas dos firmas son idénticas:
func imprimir(v interface{}) { /* ... */ }
func imprimir(v any)         { /* ... */ }

var caja any
caja = 42          // ok
caja = "hola"      // ok
caja = []int{1, 2} // ok — cualquier cosa entra
⚠️ Úsala con moderación. Cuando guardás algo en any perdés la información de tipo: el compilador ya no te protege. Para volver a operar con el valor tenés que recuperar su tipo concreto con una type assertion o un type switch (lo vemos ahora). Si podés usar una interface chica con métodos concretos, casi siempre es mejor que any.

Recuperar el tipo: type assertion

Cuando tenés un valor dentro de una interface y necesitás el tipo concreto de vuelta, usás una type assertion:

var x any = "hola mundo"

s := x.(string)      // forma de UN solo valor: peligrosa
fmt.Println(len(s))  // 10
🚨 La forma de un solo valor hace PANIC si el tipo no coincide. Si x guardara un int y hacés x.(string), el programa explota en runtime con panic: interface conversion. Casi nunca querés esto.
📌 Usá SIEMPRE la forma de dos valores: v, ok := x.(string). El segundo valor ok es un booleano que te dice si la conversión funcionó. Si no funcionó, ok es false y v queda en su valor cero — sin panic. 
var x any = 42

if s, ok := x.(string); ok {
    fmt.Println("era un string:", s)
} else {
    fmt.Println("no era un string, no pasa nada") // entra acá
}

Decidir según el tipo: type switch

Cuando tenés que ramificar según varios tipos posibles, el type switch es la herramienta. Es un switch especial sobre x.(type):

func describirTipo(x any) string {
    switch v := x.(type) {
    case string:
        return fmt.Sprintf("string de %d caracteres", len(v))
    case int:
        return fmt.Sprintf("entero, el doble es %d", v*2)
    case bool:
        return fmt.Sprintf("booleano: %t", v)
    case nil:
        return "es nil"
    default:
        return fmt.Sprintf("tipo desconocido: %T", v)
    }
}

func main() {
    fmt.Println(describirTipo("hola")) // string de 4 caracteres
    fmt.Println(describirTipo(21))     // entero, el doble es 42
    fmt.Println(describirTipo(true))   // booleano: true
}

Dentro de cada case, la variable v ya tiene el tipo concreto de ese case (es string en el primero, int en el segundo). No hace falta hacer la assertion a mano: el switch te la da hecha y segura.

El gran idiom: "acepta interfaces, devolvé structs"

📌 "Accept interfaces, return structs". Tus funciones deberían recibir interfaces (lo más chicas posible) para ser flexibles con quién las llama; pero devolver tipos concretos (structs) para que quien recibe el resultado tenga toda la información disponible. Recibir amplio, devolver específico.

¿Por qué? Si recibís una interface chica, cualquiera puede llamarte (máxima flexibilidad de entrada). Si devolvés un struct concreto, el que recibe no pierde capacidades por una abstracción prematura — y si más adelante necesita tratarlo como interface, lo puede hacer él.

Errores típicos con interfaces

Diseñar interfaces gigantes. Una interface con 8 métodos es casi imposible de satisfacer y de mockear. Partila en varias chicas. Recordá: cuanto más grande, peor la abstracción.
Type assertion sin el ok. Escribir s := x.(string) en vez de s, ok := x.(string) provoca un panic en runtime si el tipo no coincide. Salvo que estés 100% seguro del tipo, usá siempre la forma de dos valores.
Creer que tenés que "declarar" que implementás una interface. Venís de Java/C# y buscás dónde poner implements. No existe. Si tu tipo tiene los métodos, ya satisface la interface — y punto.
Abusar de any. Meter todo en interface{} "para que sea genérico" tira a la basura el tipado estático de Go. Si conocés el comportamiento que necesitás, definí una interface chica con métodos.

Checkpoint — ¿lo tenés claro?

En Go, ¿cómo declara un tipo que satisface una interface?

No lo declara. La implementación es implícita: si el tipo tiene todos los métodos que la interface pide, la satisface automáticamente. No existe ninguna palabra clave implements; Go lo verifica al compilar.

¿Por qué v, ok := x.(string) es mejor que v := x.(string)?

Porque la forma de dos valores nunca hace panic. Si el tipo no coincide, ok es false y v queda en su valor cero, así podés manejar el caso con un if. La forma de un solo valor explota en runtime si el tipo no es el esperado.

¿Qué significa "acepta interfaces, devolvé structs"?

Que tus funciones reciban interfaces (chicas) para aceptar la mayor variedad posible de tipos que las cumplan, pero devuelvan structs concretos para que el llamador tenga toda la información disponible sin perder capacidades por una abstracción prematura.

Ejercicios

  1. Definí una interface Animal con un único método Sonido() string. Creá dos structs (Perro y Gato) que la satisfagan implícitamente, y una función hacerSonar(a Animal) que imprima el sonido.
  2. Hacé que el struct Perro también satisfaga fmt.Stringer con un método String() string que devuelva algo como "Perro(Fido)". Imprimí un Perro con fmt.Println y comprobá que usa tu String().
  3. Escribí una función esString(x any) (string, bool) que use type assertion de dos valores y devuelva el string y el ok. Probala con un string y con un int.
  4. Escribí una función clasificar(x any) string con un type switch que distinga al menos int, float64, string y un caso default.
  5. Tomá la interface Figura del ejemplo, agregá un tercer tipo (Triangulo) con su Area(), metelos a los tres en un []Figura y sumá todas las áreas recorriéndolas en un for range.

🧠 Autoevaluación

1. En Go, ¿qué hace que un tipo satisfaga una interface?

Go usa implementación implícita: si el tipo tiene los métodos requeridos, satisface la interface automáticamente. No existe implements ni herencia de interfaces.

2. ¿Por qué conviene v, ok := x.(string) sobre v := x.(string)?

La forma de dos valores es segura: ante un tipo que no coincide devuelve ok == false y el valor cero, sin panic. La forma de un solo valor provoca un panic en runtime.

3. ¿Qué describe el idiom "the bigger the interface, the weaker the abstraction"?

Cuanto más grande la interface, más difícil de satisfacer y de mockear, y peor la abstracción. Las mejores de la stdlib (io.Writer, fmt.Stringer) tienen un solo método.

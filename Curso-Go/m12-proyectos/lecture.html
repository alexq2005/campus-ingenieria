Módulo 12 — Proyectos Integradores

Llegaste al final. Ya tenés todo Go: sintaxis, structs, punteros, interfaces, errores como valores, goroutines, channels, paquetes, tests y un servidor HTTP. Lo que falta no es aprender más teoría — es integrar esas piezas en proyectos reales que podrías mostrar en un portfolio o usar en producción.

💡 Esta guía es distinta a los módulos anteriores. Menos explicación, más estructura. Para cada proyecto te doy: el objetivo, qué módulos del curso aplica, las fases (en orden) y un criterio claro de "terminado". El código lo escribís vos — esa es la parte donde realmente se fija lo aprendido.
Elegí uno y terminalo de punta a punta antes de saltar al siguiente. Un proyecto chico y completo enseña más que cuatro a medio hacer. Si tenés que ordenar la dificultad: CLI → Acortador → Worker → Paquete.

🔗 Proyecto 1 — Acortador de URLs en Go

Objetivo: un servidor HTTP que recibe una URL larga, le asigna un código corto y lo guarda en memoria. Después, cuando alguien visita /{code}, lo redirige a la URL original. Es la versión backend del proyecto P06 del campus — ahí lo viste en el navegador; acá construís el servidor de verdad.

PiezaMódulo del curso
Servidor HTTP, handlers, JSONM11 — HTTP & API
Guardar pares código→URL en un mapM04 — Estructuras de datos
Proteger el map con sync.Mutex (varias requests a la vez)M09 — Concurrencia avanzada
Devolver errores como valores (if err != nil)M07 — Errores

Los dos endpoints:

// POST /shorten   body: {"url":"https://ejemplo.com/algo/muy/largo"}
//                 resp: {"code":"a3f9","short":"http://localhost:8080/a3f9"}
// GET  /{code}    -> HTTP 302 redirect a la URL original

El esqueleto del almacén protegido con Mutex (lo completás vos):

type Store struct {
    mu   sync.Mutex
    urls map[string]string // code -> url larga
}

func (s *Store) Save(code, url string) {
    s.mu.Lock()
    defer s.mu.Unlock()
    s.urls[code] = url
}

func (s *Store) Get(code string) (string, bool) {
    s.mu.Lock()
    defer s.mu.Unlock()
    url, ok := s.urls[code]
    return url, ok
}
Sin el Mutex tenés un bug silencioso. Un map de Go NO es seguro para acceso concurrente: si dos requests escriben a la vez, el programa puede crashear con fatal error: concurrent map writes. Corré go run -race . para detectarlo.
  1. Servidor base: levantá un http.ServeMux que responda "ok" en / (repaso de M11).
  2. POST /shorten: leé el JSON del body, generá un código corto (random o contador), guardalo en el Store y devolvé el JSON con el código.
  3. GET /{code}: buscá el código en el Store; si existe, http.Redirect(w, r, url, http.StatusFound); si no, 404.
  4. Concurrencia: protegé el map con sync.Mutex y verificá con -race.
  5. Errores: validá que la URL no esté vacía y devolvé un 400 con un mensaje claro si lo está.
✅ Terminado cuando:
  • POST /shorten con una URL devuelve un código y lo persiste.
  • GET /{code} redirige a la URL original; un código inexistente devuelve 404.
  • go run -race . no reporta data races con varias requests simultáneas.
  • Una URL vacía o body inválido devuelve 400, no un panic.

🛠️ Proyecto 2 — Herramienta de línea de comandos (CLI)

Objetivo: una herramienta de terminal que recibe argumentos y hace algo útil. Dos ideas concretas: un conversor de unidades (convertir 100 km millas) o un TODO por terminal (todo add "comprar pan", todo list). Las CLIs son donde Go brilla: un solo binario, sin runtime, lo copiás y corre.

PiezaMódulo del curso
Leer argumentos (os.Args o el paquete flag)M00 / M10 — toolchain y paquetes
Modelar el dato con un structM04 / M05 — structs y punteros
Manejo de errores (input inválido, archivo que no abre)M07 — Errores

Las dos formas de leer argumentos:

// 1) Crudo: os.Args[0] es el nombre del programa, [1:] son los argumentos
args := os.Args[1:]
if len(args) < 1 {
    fmt.Println("uso: convertir <valor> <de> <a>")
    os.Exit(1)
}

// 2) Con flags: --from km --to millas --valor 100
from := flag.String("from", "km", "unidad de origen")
to   := flag.String("to", "millas", "unidad de destino")
flag.Parse()
Para un TODO real, guardá las tareas en un archivo JSON (tasks.json) con encoding/json — así sobreviven entre ejecuciones. Repasá os.ReadFile / os.WriteFile y el marshaling de M11.
  1. Parseo: leé los argumentos y validá que estén completos; si no, mostrá el uso y os.Exit(1).
  2. Modelo: definí el struct que representa el dato (una Task con texto y estado, o un par valor+unidad).
  3. Lógica: hacé la conversión o el alta/listado de tareas.
  4. Errores: devolvé errores claros para unidades desconocidas o archivos que no se pueden leer.
  5. Compilá: go build y probá el binario directamente desde la terminal.
✅ Terminado cuando:
  • El binario corre desde la terminal y procesa los argumentos correctamente.
  • Un argumento faltante o inválido muestra un mensaje de uso útil y sale con código ≠ 0.
  • (TODO) las tareas persisten en tasks.json entre ejecuciones.
  • go build genera un único ejecutable que copiás y corre sin dependencias.

⚡ Proyecto 3 — Worker concurrente

Objetivo: procesar N tareas en paralelo con goroutines, repartirlas por un channel y esperar a que todas terminen con un WaitGroup. El ejemplo clásico: chequear el estado HTTP de muchas URLs a la vez. Hacerlo secuencial tarda N×latencia; en paralelo tarda casi lo que la más lenta.

PiezaMódulo del curso
Lanzar trabajo en paralelo con goM08 — Goroutines & channels
Repartir tareas y recoger resultados por channelsM08 — Goroutines & channels
Esperar a que todas terminen con sync.WaitGroupM09 — Concurrencia avanzada
El cliente HTTP (http.Get)M11 — HTTP & API

El patrón worker pool en miniatura (lo completás vos):

func main() {
    urls := []string{"https://go.dev", "https://example.com", "https://httpbin.org/status/200"}
    var wg sync.WaitGroup
    results := make(chan string)

    for _, u := range urls {
        wg.Add(1)
        go func(url string) {
            defer wg.Done()
            resp, err := http.Get(url)
            if err != nil {
                results <- url + " -> ERROR: " + err.Error()
                return
            }
            defer resp.Body.Close()
            results <- fmt.Sprintf("%s -> %d", url, resp.StatusCode)
        }(u)
    }

    // cerrar el channel cuando todas las goroutines terminen
    go func() { wg.Wait(); close(results) }()

    for r := range results {
        fmt.Println(r)
    }
}
Ojo con la variable del bucle. En Go anterior a 1.22, capturar u directamente en la goroutine daba un bug clásico (todas veían el último valor). Por eso lo pasamos como argumento: go func(url string){...}(u). En Go 1.22+ ya está arreglado, pero pasarlo explícito sigue siendo lo más claro.
El WaitGroup es como un contador de mochilas en una excursión. Sumás uno por cada persona que sale (Add), cada una avisa cuando vuelve (Done), y el guía no cierra el portón (Wait) hasta que el contador llega a cero. Sin él, cerrás el channel antes de que vuelvan todos.
  1. Secuencial primero: chequeá las URLs una por una en un for. Cronometralo con time.Since.
  2. Paralelizá: lanzá una goroutine por URL, sumando al WaitGroup.
  3. Recolectá: mandá cada resultado por un channel y leelos en el main.
  4. Cerrá bien: usá una goroutine con wg.Wait(); close(results) para terminar el range.
  5. Compará: medí el tiempo paralelo vs el secuencial y mirá la diferencia.
✅ Terminado cuando:
  • Las N URLs se chequean en paralelo y se imprime el status de cada una.
  • El programa termina limpio (no se cuelga esperando un channel que nunca cierra).
  • Una URL caída no rompe el programa: se reporta como error y las demás siguen.
  • El tiempo paralelo es notablemente menor que el secuencial.

📦 Proyecto 4 — Paquete reutilizable con tests

Objetivo: diseñar un paquete con una API limpia, basada en una interfaz, y cubrirlo con tests table-driven. Es el proyecto menos vistoso pero el más "senior": acá practicás diseño de software, no solo escribir código que corre. Ejemplos: un validador, una calculadora de impuestos, un cache simple, un formateador.

PiezaMódulo del curso
Definir el contrato con una interfaceM06 — Interfaces
Organizar el código en un paquete propioM10 — Paquetes & testing
Tests table-driven con testingM10 — Paquetes & testing
Errores como valores en la API públicaM07 — Errores

La API basada en interfaz (define qué hace, no cómo):

package validador

// Regla es el contrato: cualquier validación implementa esto.
type Regla interface {
    Validar(valor string) error
}

// Distintas implementaciones cumplen la misma interfaz.
type NoVacio struct{}

func (NoVacio) Validar(v string) error {
    if v == "" {
        return errors.New("el valor no puede estar vacío")
    }
    return nil
}

El test table-driven (un caso por fila, un solo bloque de lógica):

func TestNoVacio(t *testing.T) {
    casos := []struct {
        nombre  string
        entrada string
        quiereErr bool
    }{
        {"vacío da error", "", true},
        {"con texto ok", "hola", false},
    }
    for _, c := range casos {
        t.Run(c.nombre, func(t *testing.T) {
            err := NoVacio{}.Validar(c.entrada)
            if (err != nil) != c.quiereErr {
                t.Errorf("Validar(%q): err=%v, quiereErr=%v", c.entrada, err, c.quiereErr)
            }
        })
    }
}
El nombre del archivo de test debe terminar en _test.go y cada test ser func TestXxx(t *testing.T). Corrés todo con go test ./... y ves la cobertura con go test -cover.
  1. Diseñá la interfaz primero: ¿cuál es el contrato mínimo? Una o dos firmas, no más.
  2. Implementá: al menos dos tipos que cumplan esa interfaz.
  3. Tests table-driven: una tabla de casos (positivos y negativos) recorrida con t.Run.
  4. API pública limpia: exportá solo lo necesario (mayúscula inicial); el resto, privado.
  5. Documentá: un comentario arriba de cada función exportada (estilo godoc).
✅ Terminado cuando:
  • El paquete expone una API basada en interfaz, con al menos dos implementaciones.
  • go test ./... pasa con casos positivos y negativos.
  • Otro paquete (un main de ejemplo) puede importarlo y usarlo sin tocar internals.
  • Las funciones exportadas tienen comentario godoc.

🎓 Cierre del curso — ¿qué sigue?

Con estos cuatro proyectos cubriste el corazón de Go en producción: HTTP, concurrencia, diseño con interfaces y testing. Desde acá, el camino se abre en cuatro direcciones muy demandadas:

  • Frameworks web — Gin, Echo o Chi te dan routing, middleware y manejo de params encima del net/http que ya conocés. Tu acortador de URLs es el lugar ideal para migrar a uno de ellos.
  • Bases de datos — el paquete estándar database/sql (con un driver de Postgres o SQLite) reemplaza el map en memoria por persistencia real.
  • gRPC — para comunicación entre servicios con contratos fuertes (protobuf). Es donde Go domina en arquitecturas de microservicios.
  • Docker — el superpoder de Go: como compila a un único binario estático, podés meterlo en una imagen scratch o distroless de pocos MB. Tu CLI o tu API entran en un contenedor diminuto que arranca al instante.
💡 El binario único es la ventaja que se nota al deployar. Un Dockerfile multi-stage compila el binario y lo copia a una imagen FROM scratch: el resultado pesa megabytes, no gigabytes, no trae runtime ni sistema operativo de más, y arranca en milisegundos. Esa es la razón concreta por la que la nube eligió Go.

Checkpoint — repaso final

¿Por qué hay que proteger un map con Mutex en el acortador de URLs?

Porque un map de Go no es seguro para acceso concurrente. Un servidor HTTP atiende muchas requests en goroutines distintas a la vez; si dos escriben el map simultáneamente, el runtime aborta con fatal error: concurrent map writes. El sync.Mutex garantiza que solo una goroutine toque el map por vez. Se detecta con go run -race.

En el worker concurrente, ¿para qué sirve el WaitGroup y por qué se cierra el channel en una goroutine aparte?

El WaitGroup cuenta cuántas goroutines lanzaste (Add) y cuántas terminaron (Done), y Wait bloquea hasta que todas acaben. Cerramos el channel en go func(){ wg.Wait(); close(results) }() porque el range sobre el channel en el main necesita que el channel se cierre para terminar — y solo podemos cerrarlo cuando sabemos que ninguna goroutine va a escribir más, es decir, después del Wait.

¿Por qué diseñar el paquete alrededor de una interfaz en vez de funciones sueltas?

La interfaz define el contrato (qué hace) separado de la implementación (cómo). Eso permite tener varias implementaciones intercambiables, escribir tests con implementaciones falsas (mocks/stubs) sin tocar la real, y que quien usa el paquete dependa del contrato y no de los detalles internos. Es la base del código desacoplado y testeable.

🧠 Autoevaluación — repaso del curso

1. En el acortador de URLs, varias requests escriben el mismo map a la vez. ¿Qué necesitás para que no crashee?

Los maps de Go NO son concurrent-safe: dos escrituras simultáneas abortan con fatal error: concurrent map writes. El sync.Mutex serializa el acceso. Go ni siquiera tiene try/catch — los errores son valores (M07).

2. En el worker concurrente, ¿para qué se usa el sync.WaitGroup?

El WaitGroup cuenta goroutines con Add/Done, y Wait bloquea hasta que el contador llega a cero. Así sabés cuándo cerrar el channel de resultados sin perder ninguno.

3. ¿Por qué Go es tan cómodo para deployar en Docker (su "superpoder")?

Go compila a un binario nativo sin dependencias externas, así que una imagen FROM scratch con solo ese binario pesa megabytes y arranca al instante. No es interpretado (es compilado) ni trae un SO adentro.

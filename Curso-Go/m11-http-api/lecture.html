Módulo 11 — API REST con net/http

Una de las cosas más sorprendentes de Go es que no necesitás un framework para levantar un servidor web. La librería estándar trae net/http: un servidor HTTP completo, listo para producción, que potencia proyectos reales. En este módulo construís una API REST que recibe y devuelve JSON, leyendo el request y respondiendo con los status codes correctos.

El servidor está en la stdlib

💡 net/http no es un juguete didáctico. Es el mismo paquete que usan servicios en producción que atienden millones de requests. Frameworks como Gin o Echo le agregan azúcar (routing más cómodo, middleware), pero por debajo casi todos se apoyan en net/http. Entender la base te da independencia: arrancás sin instalar nada.

Un servidor HTTP en Go se reduce a dos ideas: handlers (funciones que responden a un request) y un router que decide qué handler atiende cada ruta. Eso es todo lo que necesitás para empezar.

El handler: la pieza central

Un handler es una función con esta firma exacta:

func(w http.ResponseWriter, r *http.Request)
📌 Los dos parámetros: w (un http.ResponseWriter) es por donde escribís la respuesta que recibe el cliente. r (un *http.Request) es el request entrante: de ahí leés método, URL, query params, headers y body. Regla mental: de r se lee, en w se escribe.

El handler más simple posible:

func saludar(w http.ResponseWriter, r *http.Request) {
    fmt.Fprintln(w, "¡Hola desde Go!")
}

fmt.Fprintln escribe en cualquier destino que sea un "writer" — y w lo es. Lo que escribas ahí viaja como cuerpo de la respuesta HTTP.

Registrar rutas y arrancar

Con el handler escrito, lo asociás a una ruta y prendés el servidor:

package main

import (
    "fmt"
    "net/http"
)

func saludar(w http.ResponseWriter, r *http.Request) {
    fmt.Fprintln(w, "¡Hola desde Go!")
}

func main() {
    http.HandleFunc("/saludo", saludar)
    fmt.Println("Servidor en http://localhost:8080")
    http.ListenAndServe(":8080", nil)
}
  • http.HandleFunc("/saludo", saludar) dice: "cuando llegue un request a /saludo, llamá a saludar".
  • http.ListenAndServe(":8080", nil) arranca el servidor en el puerto 8080 y se queda escuchando. El nil significa "usá el router por defecto" (donde HandleFunc registró las rutas).

Probalo desde otra terminal:

go run main.go
# en otra terminal:
curl http://localhost:8080/saludo
# → ¡Hola desde Go!
Tu propio router con http.ServeMux. En vez del router global podés crear uno explícito: mux := http.NewServeMux(), registrar con mux.HandleFunc(...) y pasarlo a http.ListenAndServe(":8080", mux). Es más prolijo en apps grandes (evita el estado global) y facilita los tests, pero la idea es idéntica.

Leer del request

El *http.Request trae todo lo que mandó el cliente. Lo que más vas a usar:

Qué querésCómo
Método HTTPr.Method → "GET", "POST", ...
Path de la URLr.URL.Path → "/usuarios"
Query param ?q=...r.URL.Query().Get("q")
Cuerpo del requestr.Body (un stream que leés/decodificás)
Un headerr.Header.Get("Authorization")

Por ejemplo, ramificar según el método y leer un query param:

func buscar(w http.ResponseWriter, r *http.Request) {
    if r.Method != http.MethodGet {
        http.Error(w, "solo GET", http.StatusMethodNotAllowed)
        return
    }
    termino := r.URL.Query().Get("q")   // de /buscar?q=go saca "go"
    fmt.Fprintf(w, "Buscando: %s\n", termino)
}

JSON con encoding/json

Las APIs REST hablan JSON. Go lo maneja con el paquete encoding/json y unos struct tags que mapean campos de Go a claves JSON.

📌 Los struct tags. Un campo de struct debe empezar con mayúscula para que encoding/json pueda verlo (la exportación de M07). El tag `json:"nombre"` entre comillas invertidas le dice qué clave usar en el JSON. Sin tag, la clave sería el nombre del campo tal cual (Nombre, con mayúscula). 
type Tarea struct {
    ID      int    `json:"id"`
    Titulo  string `json:"titulo"`
    Hecha   bool   `json:"hecha"`
}

Responder JSON (codificar un struct y escribirlo en w):

func obtenerTarea(w http.ResponseWriter, r *http.Request) {
    t := Tarea{ID: 1, Titulo: "Aprender net/http", Hecha: false}
    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(t)
}

Eso produce: {"id":1,"titulo":"Aprender net/http","hecha":false}

Leer JSON del body de un POST (decodificarlo dentro de un struct):

func crearTarea(w http.ResponseWriter, r *http.Request) {
    var t Tarea
    if err := json.NewDecoder(r.Body).Decode(&t); err != nil {
        http.Error(w, "JSON inválido", http.StatusBadRequest)
        return
    }
    // t ya tiene los datos que mandó el cliente
    fmt.Printf("Nueva tarea: %+v\n", t)
}
Decode(&t) recibe un puntero a t (el & de M06) porque tiene que modificar esa variable rellenando sus campos. NewEncoder(w).Encode(t) escribe directo en w — no arma un string intermedio, hace streaming.

Status codes

El código de estado HTTP le dice al cliente cómo salió todo. Por defecto Go responde 200 OK; para otro código lo seteás vos:

SituaciónCódigoCómo
Todo bien (GET)200 OK(por defecto)
Recurso creado (POST)201 Createdw.WriteHeader(http.StatusCreated)
Datos del cliente mal400 Bad Requesthttp.Error(w, msg, http.StatusBadRequest)
Método no permitido405http.Error(w, msg, http.StatusMethodNotAllowed)
No existe404 Not Foundhttp.Error(w, msg, http.StatusNotFound)
⚠️ Orden importa: w.WriteHeader(code) tiene que ir antes de escribir el body. Una vez que mandás bytes al cuerpo, el header ya salió y un WriteHeader posterior se ignora (con un warning). Y solo se puede llamar una vez.

Ejemplo completo: API con 2 endpoints

Un servidor con GET /tarea (devuelve JSON) y POST /tarea (recibe JSON y responde 201):

package main

import (
    "encoding/json"
    "fmt"
    "net/http"
)

type Tarea struct {
    ID     int    `json:"id"`
    Titulo string `json:"titulo"`
    Hecha  bool   `json:"hecha"`
}

func manejarTarea(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "application/json")

    switch r.Method {
    case http.MethodGet:
        t := Tarea{ID: 1, Titulo: "Aprender net/http", Hecha: false}
        json.NewEncoder(w).Encode(t)

    case http.MethodPost:
        var t Tarea
        if err := json.NewDecoder(r.Body).Decode(&t); err != nil {
            http.Error(w, "JSON inválido", http.StatusBadRequest)
            return
        }
        t.ID = 42 // simulamos que la "base de datos" asignó un ID
        w.WriteHeader(http.StatusCreated)
        json.NewEncoder(w).Encode(t)

    default:
        http.Error(w, "método no permitido", http.StatusMethodNotAllowed)
    }
}

func main() {
    http.HandleFunc("/tarea", manejarTarea)
    fmt.Println("Servidor en http://localhost:8080")
    http.ListenAndServe(":8080", nil)
}

Probalo con curl:

# GET → devuelve la tarea
curl http://localhost:8080/tarea

# POST → manda JSON y recibe 201 con el id asignado
curl -X POST http://localhost:8080/tarea \
  -H "Content-Type: application/json" \
  -d '{"titulo":"Comprar pan","hecha":false}'
💡 Esto es la base del proyecto P06 — Acortador de URLs. Ese proyecto es exactamente esta estructura: un POST /shorten que recibe una URL larga, genera un código corto y lo guarda; y un GET /{code} que busca el código y redirige al original con http.Redirect(w, r, urlLarga, http.StatusFound). Si entendés este módulo, el proyecto es ensamblar piezas que ya conocés.

Errores típicos al armar la API

Olvidar Content-Type: application/json. Si no seteás w.Header().Set("Content-Type", "application/json"), el cliente (o el navegador) puede interpretar tu respuesta como texto plano. Seteá el header antes de escribir el body.
No chequear r.Method. Si no filtrás el método, tu endpoint de "crear" responde igual a un GET que a un POST. Validá el método y devolvé 405 si no corresponde.
Ignorar el error de Decode. Si el cliente manda JSON roto y no chequeás if err != nil, seguís adelante con un struct vacío y bugs silenciosos. Siempre validá y respondé 400 ante un body inválido.

Checkpoint — ¿lo tenés claro?

¿Cuál es la firma de un handler HTTP en Go y qué hace cada parámetro?

func(w http.ResponseWriter, r *http.Request). En w escribís la respuesta (body, headers, status code); de r leés el request (método, URL, query, body, headers). De r se lee, en w se escribe.

¿Cómo leés un JSON del body y cómo respondés con JSON?

Para leer: json.NewDecoder(r.Body).Decode(&v), donde v es un struct con tags y pasás un puntero (&v). Para responder: seteás w.Header().Set("Content-Type", "application/json") y usás json.NewEncoder(w).Encode(v).

¿Por qué un campo de struct tiene que empezar con mayúscula para serializarse a JSON?

Porque encoding/json está en otro paquete y solo puede acceder a campos exportados (mayúscula inicial). Un campo en minúscula es privado y el encoder lo ignora. El tag `json:"..."` controla qué nombre usa la clave en el JSON.

Ejercicios

  1. Levantá el servidor del ejemplo y pegale con curl tanto el GET como el POST. Confirmá que el POST devuelve el status 201 (agregale -i a curl para ver los headers).
  2. Agregá un endpoint GET /ping que responda el texto "pong" (sin JSON). Registralo con otro http.HandleFunc.
  3. En el handler, leé un query param: hacé que GET /tarea?titulo=algo devuelva una tarea cuyo Titulo sea ese valor.
  4. Reemplazá el router global por un http.NewServeMux() explícito y pasáselo a ListenAndServe. Verificá que todo sigue funcionando igual.
  5. Probá mandar un body roto al POST (curl ... -d 'esto no es json') y confirmá que recibís 400 Bad Request en vez de que el server crashee.

🧠 Autoevaluación

1. En la firma func(w http.ResponseWriter, r *http.Request), ¿para qué sirve cada parámetro?

w (ResponseWriter) es por donde escribís la respuesta; r (*Request) es el request entrante del que leés método, URL y body. De r se lee, en w se escribe.

2. ¿Cómo decodificás el JSON del body de un POST dentro de un struct t?

Se usa json.NewDecoder(r.Body).Decode(&t), pasando un puntero (&t) porque el decoder tiene que modificar la variable rellenando sus campos. Siempre chequeá el error que devuelve.

3. Antes de escribir el body de la respuesta, ¿qué debés hacer para que el cliente reciba JSON con el status correcto al crear un recurso?

El Content-Type y el WriteHeader(201) van antes de escribir el cuerpo: una vez que mandás bytes al body el header ya salió y un WriteHeader posterior se ignora.

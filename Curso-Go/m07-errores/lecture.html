Módulo 07 — Errores como Valores

Veniendo de Python o JavaScript estás acostumbrado a try/except y try/catch: el error "vuela" hacia arriba hasta que alguien lo atrapa. Go hace algo radicalmente distinto y, al principio, incómodo: los errores son valores comunes que una función devuelve junto con su resultado, y vos los manejás ahí mismo, en la línea siguiente. No hay magia, no hay saltos invisibles en el flujo. En este módulo aprendés el idiom central de Go.

La gran idea: Go NO tiene excepciones

💡 En Go un error es un VALOR. No existe try/catch. Una función que puede fallar devuelve dos cosas: el resultado y un error. Vos chequeás ese error explícitamente. El tipo error es una interface con un solo método: Error() string. Si el valor del error es nil, todo salió bien; si no es nil, algo falló.

La interface error de la librería estándar es así de simple:

type error interface {
    Error() string
}

Cualquier tipo que tenga un método Error() string es un error (esto conecta directo con las interfaces de M06: cumplís el contrato, sos del tipo).

El idiom universal: if err != nil

Casi toda función que puede fallar tiene esta firma: devuelve (Resultado, error). El que la llama chequea el error antes de usar el resultado.

package main

import (
    "fmt"
    "strconv"
)

func main() {
    n, err := strconv.Atoi("123")   // convierte string a int
    if err != nil {
        fmt.Println("no se pudo convertir:", err)
        return
    }
    fmt.Println("el número es:", n)  // solo llegás acá si err == nil
}
📌 Regla de oro: el error es parte de la firma de la función. No es opcional ni invisible: está ahí, en el tipo de retorno. Manejalo, no lo ignores. El patrón if err != nil { return ..., err } es tan común en Go que lo vas a escribir cientos de veces — y eso es bueno: el manejo de errores es explícito y está a la vista.

Así se ve el idiom cuando vos sos quien define la función que puede fallar:

func dividir(a, b float64) (float64, error) {
    if b == 0 {
        return 0, errors.New("división por cero")
    }
    return a / b, nil   // sin error: devolvés nil
}

func main() {
    resultado, err := dividir(10, 0)
    if err != nil {
        fmt.Println("error:", err)
        return
    }
    fmt.Println("resultado:", resultado)
}
Cuando no hay error, devolvés nil en la posición del error. Cuando sí hay error, devolvés un valor "cero" sensato en la posición del resultado (acá 0). El que llama nunca debería usar el resultado sin haber chequeado el error primero.

Crear errores: errors.New y fmt.Errorf

Hay dos formas básicas de fabricar un error:

FormaPara quéEjemplo
errors.New(...)Mensaje fijo, sin formatoerrors.New("archivo no encontrado")
fmt.Errorf(...)Mensaje con valores interpoladosfmt.Errorf("usuario %d no existe", id)
 
import (
    "errors"
    "fmt"
)

err1 := errors.New("conexión rechazada")
err2 := fmt.Errorf("no se pudo abrir %q (intento %d)", nombre, intento)

Wrappear errores con %w: agregar contexto sin perder el original

💡 Wrappear = envolver un error en otro que le agrega contexto, sin perder el original. Con el verbo %w de fmt.Errorf, el error nuevo "contiene" al viejo. Esto te deja construir una cadena de errores que cuenta toda la historia: "falló guardar el pedido: falló la query: conexión cerrada". 
func cargarConfig(ruta string) error {
    datos, err := os.ReadFile(ruta)
    if err != nil {
        // %w envuelve el error original y le agrega contexto
        return fmt.Errorf("cargar config %q: %w", ruta, err)
    }
    _ = datos
    return nil
}

Si os.ReadFile falla con "no such file", el error que sube es: cargar config "app.yaml": open app.yaml: no such file or directory. Cada capa agregó su contexto, pero el error original sigue adentro y se puede inspeccionar.

🔗 Analogía: wrappear un error es como ponerle etiquetas a una encomienda que pasa por varias estaciones. La encomienda original (el error raíz) no cambia; cada estación le pega un sticker — "salió de depósito", "pasó por aduana". Al final leés todos los stickers y sabés exactamente por dónde pasó y dónde se trabó. La diferencia entre %w y %v: con %w podés abrir la caja después (con errors.Is/As); con %v solo te queda el texto.

Inspeccionar errores: errors.Is y errors.As

Como un error puede estar envuelto en varias capas, Go te da dos funciones para mirar adentro de la cadena:

FunciónPregunta que respondeCuándo usarla
errors.Is(err, objetivo)¿Esta cadena contiene este error específico?Comparar contra un error centinela (ej: os.ErrNotExist)
errors.As(err, &destino)¿Esta cadena contiene un error de este tipo?Extraer un error custom para leer sus campos
 
// errors.Is — ¿es (o envuelve) este error puntual?
var ErrNoEncontrado = errors.New("recurso no encontrado")

func buscar(id int) error {
    return fmt.Errorf("buscar id %d: %w", id, ErrNoEncontrado)
}

func main() {
    err := buscar(7)
    if errors.Is(err, ErrNoEncontrado) {   // mira adentro de la cadena
        fmt.Println("404: no existe")
    }
}
// errors.As — ¿hay un error de este TIPO en la cadena? extraelo
type ErrorHTTP struct {
    Codigo int
}

func (e *ErrorHTTP) Error() string {
    return fmt.Sprintf("HTTP %d", e.Codigo)
}

func main() {
    err := fmt.Errorf("request falló: %w", &ErrorHTTP{Codigo: 503})

    var httpErr *ErrorHTTP
    if errors.As(err, &httpErr) {       // si lo encuentra, lo guarda en httpErr
        fmt.Println("código:", httpErr.Codigo)   // 503 — ahora leés sus campos
    }
}
Regla práctica: errors.Is compara contra un valor conocido (un error centinela como ErrNoEncontrado). errors.As busca por tipo y te devuelve el error concreto para que accedas a sus campos (httpErr.Codigo). Ambas recorren toda la cadena de %w.

Errores custom: un struct que implementa Error()

Cuando querés que el error lleve datos estructurados (un código, un campo, un valor), creás un tipo propio. Como error es una interface (M06), basta con implementar el método Error() string:

type ErrorValidacion struct {
    Campo   string
    Mensaje string
}

// con este método, *ErrorValidacion ES un error
func (e *ErrorValidacion) Error() string {
    return fmt.Sprintf("campo %q inválido: %s", e.Campo, e.Mensaje)
}

func validarEdad(edad int) error {
    if edad < 0 {
        return &ErrorValidacion{Campo: "edad", Mensaje: "no puede ser negativa"}
    }
    return nil
}

func main() {
    err := validarEdad(-5)
    var ve *ErrorValidacion
    if errors.As(err, &ve) {
        fmt.Println("falló el campo:", ve.Campo)   // edad
    }
}
✅ Tip: el error custom + errors.As es el combo más potente del módulo. El struct transporta datos (qué campo, qué código), y errors.As te lo recupera de la cadena aunque haya pasado por tres capas de %w. Así una capa de arriba puede decidir qué hacer según el tipo de error, no según el texto.

panic y recover: solo para lo verdaderamente excepcional

💡 panic NO es el try/except de Go. Un panic detiene el flujo normal y empieza a "desenrollar" la pila; si nadie lo recupera, el programa crashea. Se reserva para bugs irrecuperables (un índice fuera de rango, un estado imposible que indica un error de programación) — no para errores esperables como "archivo no encontrado" o "input inválido".

recover() atrapa un panic, pero solo funciona dentro de un defer. Sirve, por ejemplo, para que un servidor web no se caiga entero porque un handler entró en panic:

func tareaSegura() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("recuperado de un panic:", r)
        }
    }()

    panic("algo se rompió feo")   // sin el recover, el programa moriría acá
}

func main() {
    tareaSegura()
    fmt.Println("el programa sigue vivo")   // sí se ejecuta
}
⚠️ Atención: usar recover para convertir cualquier panic en un error "porque sí" es un antipatrón. La regla general es: errores esperables → valores error; bugs imposibles → panic. recover se usa con moderación, típicamente en el borde de un servidor o una librería para no derribar todo el proceso.
🚨 Nunca uses panic como mecanismo de control de flujo normal (validar un formulario, manejar un 404, parsear input del usuario). Eso es traer la mentalidad de excepciones de otros lenguajes a Go, y rompe el contrato: quien llama a tu función espera un error en la firma, no que le explote el programa.

Errores comunes al venir de Python/JS

Ignorar el err con _. resultado, _ := hacer() tira el error a la basura. Si la función puede fallar, manejá el error. Descartarlo es esconder bugs que vas a sufrir más tarde.
Usar panic como manejo de errores normal. "Total, lo atrapo con recover" — no. Los errores esperables son valores; panic es para lo irrecuperable.
Propagar el error sin contexto. Hacer return err pelado a través de diez capas te deja con un mensaje suelto ("connection refused") y cero idea de qué operación lo causó. Agregá contexto con fmt.Errorf("...: %w", err) en cada capa relevante.

Checkpoint — ¿lo tenés claro?

¿Qué tipo es error en Go y qué método exige?

Es una interface con un único método: Error() string. Cualquier tipo que implemente ese método es un error. Por eso podés crear errores custom con un struct propio (conecta con interfaces de M06).

¿Cuál es la diferencia entre errors.Is y errors.As?

errors.Is(err, objetivo) pregunta si la cadena contiene ese error específico (un valor centinela) — devuelve true/false. errors.As(err, &destino) pregunta si hay un error de ese tipo en la cadena y, si lo encuentra, lo extrae en destino para que leas sus campos. Ambas recorren toda la cadena de %w.

¿Cuándo usar panic en vez de devolver un error?

Casi nunca para errores normales. panic es para situaciones verdaderamente excepcionales / irrecuperables: un bug de programación, un estado imposible. Los errores esperables (archivo no encontrado, input inválido, fallo de red) se devuelven como valores error y se manejan con if err != nil. panic no es el try/except de Go.

🧠 Autoevaluación

1. ¿Cómo maneja los errores Go?

Go no tiene excepciones. Un error es un valor que la función devuelve junto al resultado; lo manejás explícitamente con if err != nil. error es una interface con el método Error() string.

2. ¿Para qué sirve el verbo %w en fmt.Errorf?

%w envuelve el error original dentro de uno nuevo con más contexto. Así armás una cadena que cuenta toda la historia, y el error raíz sigue accesible con errors.Is y errors.As.

3. ¿Cuándo es apropiado usar panic?

panic es para lo irrecuperable (un bug, un estado imposible). Los errores esperables se devuelven como valores error. recover() (dentro de un defer) atrapa un panic, pero usar panic como control de flujo normal es un antipatrón.

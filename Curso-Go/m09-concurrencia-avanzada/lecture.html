Módulo 09 — Concurrencia Avanzada

En M08 lanzaste goroutines y las comunicaste con channels. Pero la concurrencia real trae problemas nuevos: ¿cómo esperás a que terminen varias goroutines?, ¿cómo evitás que dos de ellas corrompan la misma variable?, ¿cómo cancelás trabajo que ya no necesitás? Acá resolvés las tres con las herramientas del paquete sync y con context.Context, y armás los patrones que vas a ver en todo código de servidor en Go.

El problema: el main no espera

Una goroutine no bloquea al programa. Si main() termina, el proceso muere y se lleva puestas todas las goroutines que estaban corriendo. Por eso necesitás una forma de esperar.

💡 Dos problemas distintos, dos herramientas distintas. Esperar a que N goroutines terminen → sync.WaitGroup. Proteger una variable que varias goroutines tocan a la vez → sync.Mutex. No las confundas: una coordina el cuándo terminan, la otra protege el quién escribe.

sync.WaitGroup: esperar a N goroutines

Un WaitGroup es un contador. Sumás 1 por cada goroutine que lanzás, cada goroutine resta 1 cuando termina, y Wait() bloquea hasta que el contador llega a cero.

package main

import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup

    for i := 1; i <= 3; i++ {
        wg.Add(1) // sumamos 1 ANTES de lanzar la goroutine
        go func(id int) {
            defer wg.Done() // resta 1 al terminar, pase lo que pase
            fmt.Printf("worker %d trabajando\n", id)
        }(i)
    }

    wg.Wait() // bloquea hasta que las 3 hagan Done()
    fmt.Println("todos terminaron")
}
📌 Las tres reglas del WaitGroup: (1) wg.Add(n) antes de lanzar la goroutine, nunca dentro. (2) defer wg.Done() como primera línea del cuerpo, así se ejecuta aunque haya un return temprano o un panic recuperado. (3) wg.Wait() donde quieras juntar a todas.
Pasamos i como argumento a la goroutine (func(id int){...}(i)). En Go anterior a 1.22 esto era obligatorio para capturar el valor correcto; desde 1.22 la variable del for ya tiene su propia copia por iteración, pero pasarla como parámetro sigue siendo explícito y claro.

El otro problema: el estado compartido

Cuando varias goroutines escriben la misma variable, el resultado es impredecible. Esto se llama race condition (condición de carrera). Mirá este contador roto:

var contador int
var wg sync.WaitGroup

for i := 0; i < 1000; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        contador++ // ⚠️ varias goroutines tocan contador a la vez
    }()
}
wg.Wait()
fmt.Println(contador) // casi nunca da 1000
¿Por qué falla? contador++ no es atómico: son tres pasos (leer, sumar 1, escribir). Si dos goroutines leen 41 al mismo tiempo, ambas escriben 42, y una suma se pierde. Con 1000 iteraciones perdés varias.

sync.Mutex: proteger el estado compartido

Un Mutex (mutual exclusion) garantiza que solo una goroutine a la vez entre en la zona protegida. La que llega primero hace Lock(); las demás esperan en Lock() hasta que la primera haga Unlock().

var contador int
var mu sync.Mutex
var wg sync.WaitGroup

for i := 0; i < 1000; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        mu.Lock()
        defer mu.Unlock() // se libera al salir de la goroutine
        contador++ // ahora SOLO una goroutine entra a la vez
    }()
}
wg.Wait()
fmt.Println(contador) // siempre 1000 ✅
📌 Si compartís memoria entre goroutines, protegela (Mutex) o evitá compartirla (channels). Son las dos estrategias de Go. El lema de la comunidad: "no te comuniques compartiendo memoria; compartí memoria comunicándote". Cuando puedas pasar datos por un channel en vez de compartir una variable, hacelo: suele ser más simple.
Usá defer mu.Unlock() apenas hacés Lock(). Así no te olvidás de liberar el lock si hay un return en el medio. Un lock que nunca se libera deja a todas las demás goroutines esperando para siempre (deadlock).

Race detector: la herramienta clave

Los races son traicioneros: el código "anda" en tu máquina y falla en producción una de cada mil veces. Go trae un detector incorporado. Solo agregás el flag -race:

go run -race main.go     # ejecuta vigilando accesos concurrentes
go test -race ./...      # corre los tests con el detector activado
Si hay un acceso concurrente no sincronizado, -race imprime un reporte WARNING: DATA RACE con las dos goroutines que chocaron y las líneas exactas. Es la forma más confiable de cazar estos bugs. Corré tus tests con -race de rutina.

context.Context: cancelar y poner deadlines

Imaginá que lanzaste 5 goroutines a buscar datos, y a los 2 segundos ya no las necesitás (el usuario cerró la pestaña, o una falló). ¿Cómo les avisás que paren? Con context.Context: un objeto que viaja por toda la cadena de llamadas y que se puede cancelar, propagando la señal a todos los que lo escuchan.

package main

import (
    "context"
    "fmt"
    "time"
)

func trabajar(ctx context.Context) {
    for {
        select {
        case <-ctx.Done(): // alguien canceló o venció el timeout
            fmt.Println("cancelado:", ctx.Err())
            return
        default:
            fmt.Println("trabajando...")
            time.Sleep(300 * time.Millisecond)
        }
    }
}

func main() {
    // se cancela solo a los 1s
    ctx, cancel := context.WithTimeout(context.Background(), 1*time.Second)
    defer cancel() // SIEMPRE liberar el context, aunque venza el timeout

    trabajar(ctx)
    fmt.Println("listo")
}
💡 El canal ctx.Done() es la clave. Es un channel que se cierra cuando hay que parar (por timeout o por cancelación manual). Tu goroutine lo escucha en un select: cuando <-ctx.Done() se desbloquea, salís limpiamente. ctx.Err() te dice por qué (context.Canceled o context.DeadlineExceeded).
ConstructorPara qué sirve
context.Background()El context raíz, vacío. Punto de partida en main o tests.
context.WithCancel(padre)Devuelve un ctx + una función cancel(). Llamás cancel() a mano cuando querés cortar.
context.WithTimeout(padre, dur)Se cancela solo al pasar dur (o si llamás cancel()). Ideal para requests con límite de tiempo.
context.WithDeadline(padre, t)Como timeout pero contra un instante absoluto.
📌 Convención universal en Go: el ctx context.Context va siempre como primer parámetro de la función. Vas a ver func Buscar(ctx context.Context, id string) (...) en toda la biblioteca estándar (HTTP, base de datos, etc.). Y siempre hacé defer cancel() aunque uses timeout: libera recursos asociados al context.
🔗 Analogía: el context es como el botón de cancelar descarga del navegador. Lo apretás (o se vence el tiempo) y la señal llega a todas las piezas que estaban trabajando en esa descarga para que suelten lo que estén haciendo. Nadie sigue laburando para un resultado que ya nadie quiere.

Patrón: Worker Pool

En vez de lanzar una goroutine por tarea (pueden ser millones), lanzás un número fijo de "workers" que consumen tareas de un channel. Así controlás cuánta concurrencia hay a la vez.

func worker(id int, trabajos <-chan int, resultados chan<- int, wg *sync.WaitGroup) {
    defer wg.Done()
    for n := range trabajos { // consume hasta que cierren el channel
        resultados <- n * n   // procesa y manda el resultado
    }
}

func main() {
    trabajos := make(chan int, 100)
    resultados := make(chan int, 100)
    var wg sync.WaitGroup

    // 3 workers fijos, sin importar cuántas tareas haya
    for w := 1; w <= 3; w++ {
        wg.Add(1)
        go worker(w, trabajos, resultados, &wg)
    }

    // mandamos 9 trabajos y cerramos el channel
    for j := 1; j <= 9; j++ {
        trabajos <- j
    }
    close(trabajos) // avisa a los workers que no hay más

    wg.Wait()         // esperamos a los 3 workers
    close(resultados) // ahora sí nadie escribe más
    for r := range resultados {
        fmt.Println(r)
    }
}
Fijate en los tipos direccionales: <-chan int es "solo lectura" (el worker solo recibe trabajos) y chan<- int es "solo escritura" (solo manda resultados). Go te deja declarar la dirección del channel en la firma para que el compilador te frene si lo usás al revés.

Patrón: Fan-out / Fan-in

Es la idea detrás del worker pool, vista desde arriba. Fan-out: varias goroutines leen del mismo channel de entrada para repartirse el trabajo. Fan-in: esas goroutines escriben en un único channel de salida, juntando todos los resultados en un solo lugar.

1. Un productor mete tareas en un channel trabajos.
2. N workers leen de trabajos en paralelo (fan-out: el trabajo se "abre en abanico").
3. Todos escriben en un channel resultados (fan-in: se "juntan" en uno).
4. Un WaitGroup sabe cuándo terminaron todos para cerrar resultados.
Worker pool + fan-out/fan-in es el patrón de procesamiento en lote de Go: bajar 1000 URLs, procesar 1000 archivos, etc. Controlás la concurrencia (cuántos workers), no saturás el sistema, y juntás los resultados ordenadamente.

Errores típicos que se cuelgan o corrompen

Olvidar wg.Done(). Si una goroutine no resta su 1, el contador nunca llega a cero y wg.Wait() se cuelga para siempre. Por eso va defer wg.Done() en la primera línea.
No proteger estado compartido. Sin Mutex (o sin channels), dos goroutines pisándose la misma variable producen datos corruptos y resultados que cambian en cada corrida. Corré con -race.
Ignorar ctx.Done(). Si tu goroutine no escucha el context, sigue trabajando aunque ya nadie quiera el resultado: desperdicia CPU, mantiene conexiones abiertas y no respeta los timeouts. Siempre incluí el case <-ctx.Done(): en el select.
Deadlock garantizado: hacer Lock() dos veces seguidas sobre el mismo sync.Mutex sin Unlock() en el medio cuelga la goroutine para siempre. Si necesitás re-entrar, repensá el diseño: el Mutex de Go no es reentrante.

Checkpoint — ¿lo tenés claro?

¿Cuándo usás WaitGroup y cuándo Mutex?

WaitGroup para esperar a que un grupo de goroutines termine (coordina el cuándo). Mutex para proteger una variable que varias goroutines escriben a la vez (controla el quién entra). Resuelven problemas distintos y a menudo se usan juntos.

¿Qué hace go run -race y por qué importa?

Ejecuta el programa vigilando accesos concurrentes no sincronizados a memoria. Si dos goroutines tocan la misma variable sin lock/channel, imprime un reporte DATA RACE con las líneas exactas. Importa porque los races fallan de forma intermitente y son casi imposibles de cazar a mano.

¿Cómo le avisás a una goroutine que deje de trabajar?

Le pasás un context.Context (primer parámetro) y dentro de su loop escuchás <-ctx.Done() en un select. Cuando el context se cancela (por cancel() o por timeout vencido), ese case se desbloquea y la goroutine sale limpiamente con return.

Ejercicios

  1. Escribí un programa que lance 5 goroutines, cada una imprima su id, y usá un WaitGroup para que main espere a que las 5 terminen antes de imprimir "fin".
  2. Tomá el contador roto (sin Mutex), corrélo con go run -race y leé el reporte de DATA RACE. Después agregá el Mutex y verificá que ya no aparece.
  3. Hacé una función trabajar(ctx context.Context) con un loop que imprime cada 200ms y sale cuando ctx.Done() se dispara. Llamala con un context.WithTimeout de 1 segundo.
  4. Implementá un worker pool de 4 workers que reciban números del 1 al 20 por un channel trabajos y devuelvan el cubo (n*n*n) por un channel resultados. No te olvides de close(trabajos) y del WaitGroup.
  5. Combiná todo: un worker pool donde, además, le pasás un context.WithCancel a cada worker; si llamás cancel() a mitad del trabajo, los workers dejan de tomar tareas nuevas. Verificá con -race que no haya races.

🧠 Autoevaluación

1. ¿Qué pasa si lanzás 3 goroutines con wg.Add(3) pero una se olvida de llamar wg.Done()?

El contador queda en 1 y Wait() bloquea eternamente. Por eso se pone defer wg.Done() en la primera línea de la goroutine, así corre pase lo que pase.

2. Varias goroutines escriben la misma variable sin sincronización. ¿Qué herramienta de Go te lo detecta?

El compilador NO detecta races. El flag -race instrumenta el programa y reporta DATA RACE con las líneas exactas donde chocaron las goroutines.

3. ¿Cómo escucha una goroutine la señal de cancelación de un context.Context?

ctx.Done() devuelve un channel que se cierra al cancelar (manual o por timeout). La goroutine lo escucha en un select y sale con return cuando ese case se desbloquea.

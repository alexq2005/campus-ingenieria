Módulo 12 — Proyectos Integradores

Llegaste al final. A esta altura ya conocés cada pieza por separado: componentes nativos, listas, navegación, estado, formularios, persistencia, APIs del dispositivo, gestos. Lo que faltaba era juntarlas. Eso es lo que hace este módulo: cuatro proyectos completos donde ninguna pieza vive sola.

💡 Un proyecto integrador no enseña nada nuevo: te obliga a combinar lo que ya sabés. La dificultad real de una app no está en ningún módulo individual — está en las costuras: cómo la lista habla con el almacenamiento, cómo la navegación pasa datos a la pantalla de edición, cómo el estado global sobrevive a un cierre de la app. Acá practicás esas costuras.
Cómo usar este módulo. No es una lección para leer de corrido: es una guía de proyectos. Elegí uno (te sugerimos empezar por las Notas nativas), seguí sus fases en orden, y volvé al módulo del curso que corresponda cada vez que necesites refrescar una pieza. Terminás un proyecto, pasás al siguiente.
📁 Andamiaje común para los cuatro. Arrancá siempre igual: npx create-expo-app@latest, abrís el proyecto, y antes de codear definís las pantallas (qué se ve) y el modelo de datos (qué se guarda). Recién después escribís componentes. Pensar primero la estructura te ahorra rehacer la mitad.

📝 Proyecto 1 — Notas nativas

Objetivo: reconstruir las "Notas Markdown" del campus como una app móvil de verdad. Una lista de notas que persisten en el celular, con una pantalla aparte para crear y editar cada una. Es el proyecto ideal para empezar porque toca lo esencial sin pedir permisos del sistema ni redes.

Módulo del cursoQué aporta a este proyecto
M03 — Listas<FlatList> para mostrar las notas de forma performante
M04 — NavegaciónPasar de la pantalla Lista a la pantalla Editor (y volver)
M06 — Formularios<TextInput> para el título y el cuerpo de la nota
M07 — PersistenciaAsyncStorage para que las notas sobrevivan al cierre de la app

Fases

  1. Modelo de datos. Definí qué es una nota: un objeto { id, titulo, cuerpo, fecha }. Las notas son un array de esos objetos.
  2. Pantalla Lista (solo UI). Una <FlatList> con datos de prueba hardcodeados. Cada fila muestra título y un fragmento del cuerpo.
  3. Navegación. Al tocar una fila, navegás al Editor pasándole el id. Agregá un botón "+" que abre el Editor sin id (nota nueva).
  4. Pantalla Editor. Dos <TextInput> (título y cuerpo). Botón "Guardar".
  5. Estado + persistencia. Subí las notas a estado, conectá guardar/borrar, y volcá todo a AsyncStorage en cada cambio. Al abrir la app, leelo de vuelta.
  6. Pulido. Confirmación al borrar, estado vacío ("Todavía no tenés notas"), y orden por fecha descendente.
Pista clave de la fase 5: guardá el array completo bajo una sola clave (ej. "notas") serializándolo con JSON.stringify, y al leer usá JSON.parse. No guardes una clave por nota — complica el borrado.
✅ Terminado cuando…
  • Podés crear una nota, cerrarla y al reabrir la app sigue ahí.
  • Podés editar una nota existente y los cambios persisten.
  • Podés borrar una nota y desaparece de la lista y del almacenamiento.
  • La lista muestra un estado vacío claro cuando no hay notas.

🌦️ Proyecto 2 — Clima

Objetivo: una app que muestra el clima de tu ubicación actual. Pide permiso de GPS, obtiene tus coordenadas, consulta una API de clima y muestra el resultado — manejando bien los estados de carga y error, que en una app real son la mitad del trabajo.

Módulo del cursoQué aporta a este proyecto
M05 — Estado & HooksUI con estados loading / error / ok y useEffect para disparar el fetch
M07 — Datos & fetchfetch() a la API de clima y parseo de la respuesta JSON
M08 — APIs del dispositivoexpo-location para pedir permiso y leer las coordenadas del GPS

Fases

  1. UI estática. Diseñá la tarjeta de clima (temperatura, descripción, ícono) con datos falsos. Que se vea linda primero.
  2. Las tres caras del estado. Modelá cargando, error y datos. Renderizá un spinner, un mensaje de error con botón "Reintentar", o la tarjeta — según el caso.
  3. Ubicación. Con expo-location, pedí permiso y obtené latitude/longitude. Manejá el caso "el usuario rechazó el permiso".
  4. Fetch real. Llamá a una API gratuita (ej. open-meteo.com, que no pide API key) con esas coordenadas. Parseá la respuesta.
  5. Conectar todo. En useEffect: pedir ubicación → fetch → setear estado. Cubrí cada falla con su rama de error.
  6. Pulido. "Deslizá para refrescar", y mostrar la ciudad además de las coordenadas.
⚠️ El permiso de ubicación puede ser rechazado — y en iOS el usuario puede haberlo desactivado en Ajustes. Tu app no debe quedar colgada en "cargando": si no hay permiso, mostrá un mensaje claro con instrucciones, no una pantalla en blanco.
✅ Terminado cuando…
  • Al abrir, la app pide permiso de ubicación y muestra el clima real de donde estás.
  • Si rechazás el permiso o falla la red, ves un mensaje claro, no un crash ni un spinner infinito.
  • El botón "Reintentar" vuelve a ejecutar todo el flujo.

✅ Proyecto 3 — Lista de tareas

Objetivo: el clásico to-do, pero hecho como app móvil seria: CRUD completo con persistencia, y la interacción nativa por excelencia — deslizar una tarea para borrarla. Acá introducís estado global para que cualquier pantalla acceda a las tareas sin pasar props por todos lados.

Módulo del cursoQué aporta a este proyecto
M07 — PersistenciaCRUD con AsyncStorage: crear, leer, actualizar (marcar hecha) y borrar
M09 — GestosSwipe-para-borrar con react-native-gesture-handler + Swipeable
M10 — Estado globalContext (o Zustand) para que las tareas vivan en un solo lugar

Fases

  1. Modelo y store. Una tarea es { id, texto, hecha }. Montá el estado global con las acciones agregar, alternar y borrar.
  2. UI básica. <FlatList> de tareas + un <TextInput> con botón para agregar. Tocar una tarea la marca como hecha (tachado).
  3. Persistencia. Cada cambio en el store se vuelca a AsyncStorage; al iniciar, se rehidrata.
  4. Swipe-para-borrar. Envolvé cada fila en Swipeable: al deslizar a la izquierda aparece el botón rojo "Borrar".
  5. Pulido. Contador de pendientes, filtro "todas / activas / hechas", y un toque de animación al borrar.
Error típico: persistir solo al agregar y olvidarse de marcar-hecha o borrar. La persistencia tiene que reaccionar a cualquier mutación del store, no a una sola acción. Centralizá el "guardar" en el store mismo, no en cada componente.
El swipe necesita un envoltorio raíz. react-native-gesture-handler exige que la app esté dentro de un <GestureHandlerRootView style={{ flex: 1 }}>. Si los gestos "no hacen nada", casi siempre falta eso.
✅ Terminado cuando…
  • Podés agregar, marcar como hecha y borrar tareas, y todo persiste entre sesiones.
  • Deslizar una fila revela y ejecuta el borrado.
  • El estado se lee desde el store global, no por props encadenadas.
  • El filtro y el contador reflejan el estado real en todo momento.

💪 Proyecto 4 — Hábitos

Objetivo: un tracker de hábitos diarios que te recuerda con una notificación local y te muestra tu progreso en un gráfico simple. Es el proyecto más ambicioso: combina notificaciones programadas, persistencia y una pequeña visualización de datos.

Módulo del cursoQué aporta a este proyecto
M08 — APIs del dispositivoexpo-notifications para programar recordatorios locales diarios
M07 — PersistenciaGuardar hábitos y su historial de completados por día
M03 + M02Lista de hábitos y un gráfico de barras "casero" con <View> de altura variable

Fases

  1. Modelo. Un hábito es { id, nombre, historial }, donde historial es un set de fechas (YYYY-MM-DD) en las que se cumplió.
  2. CRUD de hábitos. Lista con <FlatList>; agregar/borrar hábitos; un botón por hábito para "marcar hoy". Persistí en AsyncStorage.
  3. Gráfico de progreso. Sin librerías: una fila de <View> donde la height de cada barra sale de cuántos días se cumplió por semana. Datos → altura.
  4. Notificaciones. Con expo-notifications, pedí permiso y programá un recordatorio diario por hábito (ej. "20:00 — ¿hiciste hoy: Leer?").
  5. Pulido. Racha actual ("🔥 5 días seguidos") calculada desde el historial.
🔍 El gráfico no necesita magia. Una barra es solo un <View> con backgroundColor y una height calculada: height = (dias_cumplidos / 7) * 100. Ponés siete de esas barras en un <View> con flexDirection: 'row' y ya tenés un gráfico semanal. La visualización de datos, en el fondo, es traducir números a tamaños.
⚠️ Las notificaciones no funcionan igual en todos lados. En Expo Go las notificaciones locales programadas tienen limitaciones, y en un emulador pueden no dispararse. Probalas en un dispositivo físico y, para recordatorios serios, en un development build (no Expo Go).
✅ Terminado cuando…
  • Podés crear hábitos y marcarlos como cumplidos cada día; todo persiste.
  • Cada hábito programa un recordatorio diario que efectivamente llega.
  • El gráfico refleja los días cumplidos de la semana.
  • La racha se calcula bien (incluido el caso de romperla un día).

Cierre del curso — ¿qué sigue?

Si terminaste aunque sea uno de estos proyectos de punta a punta, ya no sos alguien que "vio React Native": sos alguien que construyó apps con React Native. Eso es otra cosa. De acá, el camino se abre en varias direcciones según hacia dónde quieras crecer:

Próximo pasoPor qué importa
TypeScript en RNTipar props, estado y respuestas de API. Atrapa la mitad de los bugs antes de correr la app. Es el estándar en proyectos serios.
Testing (Jest + RNTL)React Native Testing Library para probar componentes como los usa el usuario. Te da confianza para refactorizar sin romper.
Expo RouterNavegación basada en archivos (como Next.js). Más declarativa y escalable que armar el stack a mano.
Deep linkingQue un link externo abra una pantalla específica de tu app. Imprescindible para notificaciones, compartir y marketing.
PerformanceListas grandes, memoización, evitar re-renders, imágenes optimizadas. Lo que separa una app fluida de una que tironea.
💡 El mejor próximo proyecto es el que te importa. Reescribí una app que uses todos los días, o resolvé un problema tuyo. Vas a aprender diez veces más manteniendo algo que te interesa que siguiendo un tutorial más.

Checkpoint — repaso conceptual

¿Por qué casi todos estos proyectos usan AsyncStorage?

Porque una app móvil sin persistencia es frustrante: el usuario espera que sus datos sigan ahí al reabrirla. AsyncStorage es el almacenamiento clave-valor más simple para guardar estado local (notas, tareas, hábitos). Para datos relacionales grandes existen alternativas (SQLite, WatermelonDB), pero para estos proyectos alcanza y sobra. La clave: serializar con JSON.stringify al guardar y JSON.parse al leer.

En la app de Clima, ¿por qué insistimos tanto en los estados loading/error?

Porque todo lo que dependa de la red o de permisos del sistema puede fallar o tardar, y eso está fuera de tu control. Si solo programás el "camino feliz", la app queda colgada o crashea cuando no hay señal o el usuario rechaza el GPS. Modelar explícitamente cargando, error y datos no es opcional: es la diferencia entre una demo y una app usable.

¿Cuándo conviene estado global (Context/Zustand) y cuándo alcanza con useState?

useState alcanza cuando el estado vive en una pantalla y como mucho lo pasás a un par de hijos. Necesitás estado global cuando varias pantallas distintas leen o modifican los mismos datos (como las tareas, que se ven en la lista, se editan en otra pantalla y se cuentan en el header). El síntoma de que lo necesitás: estás pasando las mismas props por tres o cuatro niveles solo para que lleguen al fondo (prop drilling).

🧠 Autoevaluación — repaso del curso

1. Querés mostrar una lista larga de notas que persisten en el celular. ¿Qué combinación es la correcta?

<FlatList> renderiza listas largas de forma performante (solo lo visible) y AsyncStorage es el almacenamiento clave-valor de RN. localStorage no existe en móvil y <ScrollView> + .map() no escala.

2. En la app de Clima, el usuario rechaza el permiso de ubicación. ¿Qué debería pasar?

Todo lo que depende de permisos o red puede fallar. Hay que modelar explícitamente el estado de error y darle al usuario una salida — nunca un spinner infinito ni un crash.

3. Las mismas tareas se ven en la lista, se editan en otra pantalla y se cuentan en el header. Estás pasando props por cuatro niveles. ¿Qué te conviene?

El prop drilling (pasar props por muchos niveles) es la señal clásica de que necesitás estado global. Con Context o Zustand, cualquier pantalla accede a las tareas sin encadenar props ni duplicar datos.

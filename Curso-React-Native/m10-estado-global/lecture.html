Módulo 10 — Estado Global & Arquitectura

Hasta ahora cada pantalla manejaba su propio estado con useState. Pero apenas la app crece, aparece la pregunta incómoda: ¿dónde vive el usuario logueado? ¿el carrito? ¿el tema oscuro? Esos datos los necesitan muchas pantallas a la vez. En este módulo vas a aprender a compartir estado entre toda la app sin volverte loco pasando props, y a organizar el proyecto como una app real.

El problema: prop-drilling

Imaginá que el usuario logueado vive en la pantalla raíz, pero quien lo muestra es un <Avatar> enterrado 4 niveles abajo. La única forma que conocés es pasar la prop por cada nivel intermedio:

<App usuario={usuario}>
  <Layout usuario={usuario}>          {/* no lo usa, solo lo reenvía */}
    <Header usuario={usuario}>        {/* tampoco lo usa */}
      <Nav usuario={usuario}>         {/* tampoco */}
        <Avatar usuario={usuario} />  {/* recién acá se usa */}
      </Nav>
    </Header>
  </Layout>
</App>
Esto es prop-drilling: pasar una prop a través de componentes que no la necesitan, solo para que llegue al fondo. Tres niveles ya cansa; en una app real son ocho. Si cambiás el nombre de la prop, tocás cinco archivos. Es frágil y ruidoso.
🔍 Pensalo así: prop-drilling es como pasar un vaso de agua mano en mano por toda una fila de gente para que llegue al del fondo. El estado global es poner un dispensador en el medio: cualquiera que tenga sed va y se sirve, sin molestar a los demás.

Context API (recap)

El Context API es la solución que trae React de fábrica. Lo viste en el Curso de React; acá funciona idéntico porque es el mismo React. Tiene tres piezas:

PiezaQué hace
createContext()Crea el "canal" por donde viaja el dato
<Provider value={...}>Pone el dato disponible para todo lo que esté adentro
useContext(Canal)Lee el dato desde cualquier componente, sin importar qué tan abajo esté
 
import { createContext, useContext, useState } from 'react';

const TemaContext = createContext();   // 1. el canal

export function TemaProvider({ children }) {
  const [oscuro, setOscuro] = useState(false);
  return (
    <TemaContext.Provider value={{ oscuro, setOscuro }}>  {/* 2. proveer */}
      {children}
    </TemaContext.Provider>
  );
}

export const useTema = () => useContext(TemaContext);   // 3. hook para leer

Y desde cualquier componente, sin recibir props:

import { Pressable, Text } from 'react-native';
import { useTema } from '../store/tema';

function BotonTema() {
  const { oscuro, setOscuro } = useTema();   // se sirve del dispensador
  return (
    <Pressable onPress={() => setOscuro(!oscuro)}>
      <Text>{oscuro ? '🌙 Oscuro' : '☀️ Claro'}</Text>
    </Pressable>
  );
}
Context brilla para datos que cambian poco: el tema, el idioma, el usuario logueado, la sesión. Cosas que se setean una vez y rara vez se tocan. Para eso es perfecto y no necesitás nada más.
El talón de Aquiles del Context: cuando el value cambia, TODOS los componentes que hacen useContext se vuelven a renderizar — aunque solo les importe una parte del valor. Si metés ahí estado que cambia muchas veces por segundo (la posición de un dedo arrastrando, un timer), vas a re-renderizar medio árbol y la app se pone lenta.

Zustand: el estándar simple

💡 Zustand es una librería de estado global minúscula y muy popular. Su gracia: cero boilerplate. No hay Provider que envolver, no hay reducers, no hay acciones ceremoniales. Creás un "store" (una cajita con datos y funciones) y lo usás como un hook desde cualquier lado.
1. Instalalo.
npx expo install zustand
2. Creá el store con create. Recibe una función que devuelve el estado y las funciones que lo modifican (usando set):
import { create } from 'zustand';

export const useContador = create((set) => ({
  cuenta: 0,
  sumar: () => set((estado) => ({ cuenta: estado.cuenta + 1 })),
  reiniciar: () => set({ cuenta: 0 }),
}));
3. Usalo en cualquier componente como un hook. Pasás un selector para elegir solo lo que te interesa:
import { Text, View, Pressable } from 'react-native';
import { useContador } from '../store/contador';

function Pantalla() {
  const cuenta = useContador((s) => s.cuenta);    // solo me suscribo a 'cuenta'
  const sumar  = useContador((s) => s.sumar);

  return (
    <View>
      <Text>{cuenta}</Text>
      <Pressable onPress={sumar}><Text>+1</Text></Pressable>
    </View>
  );
}
📌 El selector es la clave del rendimiento. Cuando hacés useContador((s) => s.cuenta), el componente solo se vuelve a renderizar si cuenta cambia — no si cambia otra parte del store. Esto es lo que Context no te da gratis, y por eso Zustand escala mejor para estado que cambia seguido.

¿Context o Zustand? ¿Y Redux?

No hay un ganador absoluto; hay una herramienta para cada caso:

HerramientaUsala para…Costo
Context APIEstado simple y estable: tema, idioma, usuario, sesiónCero (viene en React); re-renderiza todo el árbol al cambiar
ZustandEstado global que cambia seguido: carrito, filtros, datos de la appUna dependencia chica; selectores evitan re-renders
ReduxApps grandes con lógica de estado muy compleja y equipos grandesMucho boilerplate; potente pero pesado para apps chicas
💡 Regla práctica para empezar: usá useState mientras el estado sea de una sola pantalla. Pasalo a Context si es global pero cambia poco. Pasalo a Zustand si es global y cambia seguido. Redux solo si el equipo ya lo usa o la complejidad lo justifica de verdad — para la mayoría de las apps con Zustand sobra.

Arquitectura de una app real

Una app de tres pantallas vive bien en un solo archivo. Una app de verdad necesita orden. La idea central: separar la lógica de la UI. Una estructura de carpetas habitual en Expo:

src/
├── components/    # piezas de UI reusables (Boton, Tarjeta, Avatar)
├── screens/       # pantallas completas (Home, Perfil, Carrito)
├── navigation/    # configuración de navegación entre pantallas
├── hooks/         # custom hooks (useCarrito, useAuth)
├── store/         # estado global (Zustand stores, Contexts)
├── services/      # llamadas a APIs, fetch, cliente HTTP
├── constants/     # colores, tamaños, textos fijos
└── utils/         # funciones puras de ayuda (formatear precio, validar)
No es una ley sagrada, es un punto de partida sano. Lo que importa es la intención: cada cosa tiene un lugar predecible. Cuando volvés al proyecto en dos meses, sabés exactamente dónde buscar la lógica del carrito (store/), cómo se ve un botón (components/) o de dónde salen los datos (services/).
📌 La regla de oro: separá lógica de UI. Un componente debería ocuparse de cómo se ve algo. La lógica de qué hace (calcular totales, hablar con la API, manejar el carrito) va en el store, los hooks o los services. Un <Pressable> que dispara agregarAlCarrito() no debería saber cómo se calcula el total.

Ejemplo completo: carrito de compras con Zustand

Veamos un caso real. Un carrito necesita: una lista de items, agregar uno, quitarlo, y saber el total. Lo modelamos como un store de Zustand — toda la lógica vive acá, lejos de la UI:

// src/store/carrito.js
import { create } from 'zustand';

export const useCarrito = create((set, get) => ({
  items: [],   // cada item: { id, nombre, precio, cantidad }

  agregar: (producto) => set((estado) => {
    const existe = estado.items.find((i) => i.id === producto.id);
    if (existe) {
      // ya está: subimos la cantidad
      return {
        items: estado.items.map((i) =>
          i.id === producto.id ? { ...i, cantidad: i.cantidad + 1 } : i
        ),
      };
    }
    // nuevo: lo agregamos con cantidad 1
    return { items: [...estado.items, { ...producto, cantidad: 1 }] };
  }),

  quitar: (id) => set((estado) => ({
    items: estado.items.filter((i) => i.id !== id),
  })),

  vaciar: () => set({ items: [] }),

  // función derivada: lee el estado actual con get()
  total: () => get().items.reduce((suma, i) => suma + i.precio * i.cantidad, 0),
}));

Y la pantalla solo se ocupa de mostrar — toca el store, no implementa nada:

// src/screens/Carrito.js
import { View, Text, Pressable, FlatList } from 'react-native';
import { useCarrito } from '../store/carrito';

export default function Carrito() {
  const items  = useCarrito((s) => s.items);
  const quitar = useCarrito((s) => s.quitar);
  const total  = useCarrito((s) => s.total);

  return (
    <View>
      <FlatList
        data={items}
        keyExtractor={(i) => String(i.id)}
        renderItem={({ item }) => (
          <View>
            <Text>{item.nombre} ×{item.cantidad} — ${item.precio * item.cantidad}</Text>
            <Pressable onPress={() => quitar(item.id)}>
              <Text>Quitar</Text>
            </Pressable>
          </View>
        )}
      />
      <Text>Total: ${total()}</Text>
    </View>
  );
}
🔍 Fijate qué limpio quedó: la pantalla no sabe cómo se calcula el total ni qué pasa al agregar un item repetido. Solo pide total() y muestra. Mañana cambiás la lógica de descuentos en el store y ninguna pantalla se entera. Eso es separar lógica de UI.
⚠️ Cuidado con suscribirte a todo. Evitá const carrito = useCarrito() sin selector: así el componente se re-renderiza ante cualquier cambio del store. Pedí solo lo que usás con un selector (useCarrito((s) => s.items)). Es la diferencia entre una app fluida y una que tironea.

Errores típicos de arquitectura

Meter TODO en un Context gigante. Un único Context con usuario + carrito + tema + filtros hace que cualquier cambio re-renderice toda la app. Separá por dominio, o mejor, usá Zustand para lo que cambia seguido.
Lógica de negocio dentro del componente. Calcular totales, validar, transformar datos de la API dentro del JSX vuelve el componente imposible de testear y reusar. Esa lógica va en store/, hooks/ o utils/.
Un store gigante sin organizar. Tener un solo store con 40 propiedades de cosas no relacionadas es tan malo como el Context monstruo. Hacé un store por dominio: useCarrito, useAuth, useFiltros. Pequeños y enfocados.
🚨 No mutar el estado directamente. Nunca hagas estado.items.push(x) dentro de set. Zustand (como React) detecta cambios por referencia: si mutás el array existente, la referencia no cambia y la UI no se actualiza. Siempre devolvé objetos/arrays nuevos ([...estado.items, x]).

Checkpoint — ¿lo tenés claro?

¿Qué es prop-drilling y por qué es un problema?

Es pasar una prop a través de componentes intermedios que no la usan, solo para que llegue a uno profundo. Es frágil (cualquier cambio toca varios archivos), ruidoso y difícil de mantener cuando la app crece. El estado global (Context o Zustand) lo resuelve dejando que el componente lea el dato directamente.

¿Cuándo conviene Context y cuándo Zustand?

Context para estado simple y estable que cambia poco (tema, idioma, usuario logueado). Zustand para estado global que cambia seguido (carrito, filtros, datos), porque sus selectores evitan re-renderizar componentes que no usan la parte que cambió. Context, en cambio, re-renderiza todo lo suscrito ante cualquier cambio.

¿Por qué separar la lógica de la UI en carpetas como store/ y services/?

Para que cada cosa tenga un lugar predecible y para poder cambiar la lógica sin tocar las pantallas. Si la lógica del carrito vive en store/, podés cambiar cómo se calcula el total sin que ninguna pantalla se entere. Además hace el código testeable y reusable: una función pura en utils/ se prueba sola, sin montar componentes.

Ejercicios

  1. Tomá una app tuya con prop-drilling (una prop pasando por 3+ niveles) y reemplazala por un Context. Verificá que el componente del fondo la lee sin recibir props.
  2. Instalá Zustand y creá un store useContador con cuenta, sumar y reiniciar. Usalo desde dos pantallas distintas y confirmá que comparten el mismo número.
  3. Escribí el store de carrito del ejemplo. Agregá tres productos (uno repetido) y verificá que la cantidad sube en vez de duplicar el item.
  4. Agregá al store del carrito una función cantidadTotal() que devuelva la suma de las cantidades de todos los items (no el precio). Mostrala en un badge.
  5. Reorganizá un proyecto chico en las carpetas components/, screens/, store/ y utils/. Mové la función que formatea precios a utils/ y usala desde el carrito.

🧠 Autoevaluación

1. ¿Qué es el "prop-drilling"?

Prop-drilling es ese reenvío de props a través de capas que no las necesitan. Es frágil y ruidoso; el estado global lo resuelve.

2. ¿Cuál es la principal ventaja de Zustand frente a Context para estado que cambia seguido?

El selector (useStore((s) => s.x)) suscribe el componente solo a esa porción. Context, en cambio, re-renderiza todo lo suscrito ante cualquier cambio del value.

3. ¿Cuál es el principio central de una buena arquitectura de app?

La UI se ocupa de cómo se ve; la lógica de qué hace vive aparte. Así podés cambiar la lógica sin tocar pantallas y todo queda testeable y reusable.

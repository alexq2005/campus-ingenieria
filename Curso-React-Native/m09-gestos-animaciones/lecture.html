Módulo 09 — Gestos & Animaciones

Una app móvil que no se mueve con fluidez se siente rota, aunque funcione. En este módulo vas a entender por qué hay animaciones que tironean y otras que fluyen como manteca, y cómo construir las segundas: arrastrar una tarjeta, escalar al tocar, deslizar para borrar. El secreto está en quién hace el trabajo y qué propiedades animás.

Por qué 60fps importa: el hilo de JS vs el hilo de UI

💡 Una pantalla móvil se redibuja ~60 veces por segundo (60fps). Eso da un presupuesto de 16,6 ms por frame para calcular y pintar todo. Si te pasás de ese tiempo, el frame se "salta" y el ojo lo percibe como un tirón (jank). Animación fluida = no perder frames.

React Native corre con (al menos) dos hilos importantes:

  • Hilo de JS: ejecuta tu código React, el estado, los useEffect, las llamadas a APIs… toda tu lógica.
  • Hilo de UI (el "main thread" nativo): el que efectivamente dibuja los píxeles en la pantalla, frame a frame.
🔍 Pensalo como una cocina: el hilo de UI es el mozo que lleva los platos a la mesa (60 viajes por segundo, sin parar). El hilo de JS es el cocinero. Si para cada viaje el mozo tiene que esperar que el cocinero termine de pensar, los platos llegan tarde y la mesa lo nota. Lo ideal: que el mozo ya sepa qué llevar y no dependa del cocinero en cada viaje.

Acá está el problema central: si animás moviendo estado de React (setState en cada frame), cada cambio obliga al hilo de JS a re-renderizar el componente, y recién después el hilo de UI puede dibujar. Si el hilo de JS está ocupado (cargando datos, procesando una lista), la animación se cuelga. El truco moderno es animar directamente en el hilo de UI, sin molestar a JS en cada frame.

Animar con setState. Hacer setOpacidad(o + 0.05) 60 veces por segundo dispara 60 re-renders por segundo. Cada re-render compite con el resto de tu lógica → tironeo garantizado en cuanto la app tenga algo más que hacer.

La Animated API (built-in): para entender el concepto

React Native trae una API de animación incluida, sin instalar nada: Animated. No es la mejor opción hoy, pero es perfecta para entender las tres piezas que toda animación necesita: un valor que cambia, una instrucción de cómo cambiarlo, y un componente que lo escucha.

import { useRef } from 'react';
import { Animated, View, Pressable, Text, StyleSheet } from 'react-native';

export default function App() {
  // 1. Un valor animable que NO vive en el estado de React (por eso useRef).
  const opacidad = useRef(new Animated.Value(0)).current;

  const aparecer = () => {
    // 2. La instrucción: llevá "opacidad" a 1 en 500 ms.
    Animated.timing(opacidad, {
      toValue: 1,
      duration: 500,
      useNativeDriver: true, // ⬅️ clave: corre en el hilo de UI
    }).start();
  };

  return (
    <View style={styles.container}>
      {/* 3. Animated.View escucha el valor y se redibuja solo. */}
      <Animated.View style={[styles.caja, { opacity: opacidad }]} />
      <Pressable onPress={aparecer}>
        <Text>Mostrar</Text>
      </Pressable>
    </View>
  );
}

const styles = StyleSheet.create({
  container: { flex: 1, justifyContent: 'center', alignItems: 'center', gap: 24 },
  caja: { width: 120, height: 120, backgroundColor: '#a78bfa', borderRadius: 16 },
});
¿Por qué useRef y no useState? El valor animado cambia decenas de veces por segundo. Si fuera estado, cada cambio re-renderizaría el componente. Con useRef el valor persiste entre renders sin provocar re-renders, y Animated.View se encarga de actualizar el píxel.
📌 useNativeDriver: true es lo que manda la animación al hilo de UI. Funciona solo para opacity y transform (mover, rotar, escalar). NO funciona para width, height ni colores de fondo — esas obligan a volver al hilo de JS y a recalcular el layout.

El estándar moderno: Reanimated

Para apps reales, hoy se usa react-native-reanimated. Su gran idea: tu código de animación corre entero en el hilo de UI, así que sigue fluido aunque el hilo de JS esté trabado. La API es más declarativa y se siente como hooks de React.

npx expo install react-native-reanimated react-native-gesture-handler

Las tres piezas equivalentes a las de Animated, pero más limpias:

PiezaEn ReanimatedPara qué sirve
El valor que cambiauseSharedValue(inicial)Valor que vive en el hilo de UI, compartido entre JS y UI
Conectar valor → estilouseAnimatedStyle(() => ...)Devuelve un estilo que se recalcula en UI cuando el valor cambia
Cómo animar el cambiowithTiming / withSpringTransición por duración fija / por física de resorte

Mismo ejemplo del fade, ahora con Reanimated:

import Animated, {
  useSharedValue,
  useAnimatedStyle,
  withTiming,
} from 'react-native-reanimated';
import { View, Pressable, Text, StyleSheet } from 'react-native';

export default function App() {
  // 1. El valor compartido (vive en el hilo de UI).
  const opacidad = useSharedValue(0);

  // 2. El estilo derivado: se recalcula en UI cuando "opacidad" cambia.
  const estiloCaja = useAnimatedStyle(() => ({
    opacity: opacidad.value,
  }));

  return (
    <View style={styles.container}>
      <Animated.View style={[styles.caja, estiloCaja]} />
      {/* 3. Al tocar, animamos el valor con withTiming. */}
      <Pressable onPress={() => (opacidad.value = withTiming(1, { duration: 500 }))}>
        <Text>Mostrar</Text>
      </Pressable>
    </View>
  );
}

const styles = StyleSheet.create({
  container: { flex: 1, justifyContent: 'center', alignItems: 'center', gap: 24 },
  caja: { width: 120, height: 120, backgroundColor: '#a78bfa', borderRadius: 16 },
});
Fijate el detalle clave: a un shared value se lo lee y escribe con .value (opacidad.value = ...), no con un setter. Y como todo corre en el hilo de UI, la animación sigue fluida aunque tu app esté cargando una lista enorme al mismo tiempo.
💡 withTiming vs withSpring. withTiming(valor, { duration }) recorre el cambio en un tiempo exacto (lineal o con curva), bueno para fades y transiciones predecibles. withSpring(valor) usa una simulación de resorte: rebota un poquito y se asienta, dando esa sensación "viva" y natural típica de iOS. Para interacciones táctiles, casi siempre querés withSpring.

Gestos: react-native-gesture-handler

Animar está bueno, pero lo que hace que una app se sienta nativa es responder al dedo: arrastrar, tocar, deslizar. Para eso se usa react-native-gesture-handler, que detecta gestos también en el hilo de UI y se combina de maravilla con Reanimated.

1. Envolvé tu app con GestureHandlerRootView una sola vez, en la raíz.
2. Creá un gesto con Gesture.Pan() (arrastrar) o Gesture.Tap() (tocar).
3. Conectá el gesto a la vista con <GestureDetector>, y dentro un Animated.View.

Acá una caja que escala con resorte al tocarla y se puede arrastrar:

import { GestureHandlerRootView, Gesture, GestureDetector } from 'react-native-gesture-handler';
import Animated, {
  useSharedValue,
  useAnimatedStyle,
  withSpring,
} from 'react-native-reanimated';
import { StyleSheet } from 'react-native';

export default function App() {
  const x = useSharedValue(0);
  const y = useSharedValue(0);
  const escala = useSharedValue(1);

  // Tocar → escala con resorte y vuelve.
  const tap = Gesture.Tap().onBegin(() => {
    escala.value = withSpring(1.3);
  }).onFinalize(() => {
    escala.value = withSpring(1);
  });

  // Arrastrar → seguir el dedo en tiempo real.
  const pan = Gesture.Pan().onChange((e) => {
    x.value += e.changeX;
    y.value += e.changeY;
  });

  // Combinamos ambos gestos en uno solo.
  const gestos = Gesture.Simultaneous(tap, pan);

  const estilo = useAnimatedStyle(() => ({
    transform: [
      { translateX: x.value },
      { translateY: y.value },
      { scale: escala.value },
    ],
  }));

  return (
    <GestureHandlerRootView style={styles.container}>
      <GestureDetector gesture={gestos}>
        <Animated.View style={[styles.caja, estilo]} />
      </GestureDetector>
    </GestureHandlerRootView>
  );
}

const styles = StyleSheet.create({
  container: { flex: 1, justifyContent: 'center', alignItems: 'center' },
  caja: { width: 120, height: 120, backgroundColor: '#a78bfa', borderRadius: 16 },
});
🔍 El "swipe to delete" que ves en todos lados (deslizar un mail a la izquierda para borrarlo) es exactamente esto: un Gesture.Pan() que mueve la fila con translateX, y cuando el desplazamiento pasa un umbral, dispara la acción de borrado. Componentes como Swipeable de gesture-handler ya lo empaquetan, pero por dentro es Pan + shared value + un estilo animado.
📌 Gestos + Reanimated van de la mano. El gesto actualiza un useSharedValue en el hilo de UI, y useAnimatedStyle lo refleja en el píxel sin pasar por JS. Por eso arrastrar se siente pegado al dedo, sin lag.

Qué propiedades animar (y cuáles no)

Aunque animes en el hilo de UI, no todas las propiedades cuestan lo mismo. Animar transform y opacity es barato: la GPU las compone sin recalcular nada. Animar width, height, top o padding obliga al motor a recalcular el layout de todo lo que está alrededor, frame a frame.

Animar layout en vez de transform. Para "agrandar" una caja, NO animes width/height: animá scale. Para moverla, NO animes top/left: animá translateX/translateY. El resultado visual es casi igual, pero el costo en frames es muchísimo menor.

📌 Regla práctica: usá Animated para entender cómo funciona una animación y para un fade puntual sin dependencias. Para todo lo demás —y especialmente cualquier cosa que involucre el dedo del usuario— usá Reanimated + gesture-handler.
⚠️ No abuses de las animaciones. El movimiento debe guiar al usuario (de dónde vino algo, a dónde va), no marearlo. Animaciones cortas (200–400 ms) y con propósito. Si todo rebota y vuela, la app se siente caótica, no pulida.

Checkpoint — ¿lo tenés claro?

¿Por qué animar con setState produce tirones?

Porque cada cambio de estado dispara un re-render en el hilo de JS. A 60 frames por segundo son 60 re-renders, que compiten con el resto de tu lógica. Si el hilo de JS se traba, la animación se cuelga. Reanimated evita esto corriendo la animación en el hilo de UI, sin tocar el estado de React.

¿Qué hace useSharedValue y cómo se lee/escribe?

Crea un valor que vive en el hilo de UI y es compartido entre JS y UI. Se accede con .value (por ejemplo x.value = withSpring(100)). Cambiarlo no provoca re-renders: lo escucha useAnimatedStyle, que recalcula el estilo directamente en UI.

¿Por qué conviene animar transform/opacity y no width/height?

Porque transform y opacity las compone la GPU sin recalcular el layout, así que son baratas frame a frame. Animar width, height o posiciones de layout obliga a recalcular el acomodo de todo lo de alrededor en cada frame, lo que consume el presupuesto de 16,6 ms y causa jank.

Ejercicios

  1. Instalá react-native-reanimated y react-native-gesture-handler con npx expo install y envolvé tu app en GestureHandlerRootView.
  2. Hacé una caja que aparezca con un fade (opacity de 0 a 1) usando useSharedValue + withTiming al apretar un botón.
  3. Cambiá ese withTiming por withSpring en una caja que escale al tocarla, y sentí la diferencia del rebote.
  4. Implementá una caja arrastrable con Gesture.Pan() que siga el dedo usando translateX/translateY.
  5. Combiná Pan + Tap con Gesture.Simultaneous: que la caja se pueda arrastrar y, al tocarla, escale con resorte y vuelva a su tamaño al soltar.

🧠 Autoevaluación

1. ¿Por qué Reanimated produce animaciones más fluidas que animar con setState?

Animar con setState dispara un re-render por frame en el hilo de JS. Reanimated mueve la animación al hilo de UI, así sigue fluida aunque JS esté ocupado.

2. En Reanimated, ¿cómo se lee y escribe un useSharedValue?

A un shared value se accede siempre con .value. Cambiarlo no provoca re-renders; lo escucha useAnimatedStyle y actualiza el estilo en el hilo de UI.

3. Para mover y agrandar una caja de forma fluida, ¿qué propiedades conviene animar?

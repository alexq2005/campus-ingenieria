Módulo 11 — Build & Publicación

Hasta ahora tu app vivía dentro de Expo Go: la escaneabas con un QR y corría sobre una app prestada. Eso es perfecto para desarrollar, pero nadie instala "Expo Go + tu QR" desde la calle. En este módulo cerrás el círculo: convertís tu proyecto en una app instalable de verdad (un .apk/.aab en Android, un .ipa en iOS) y la subís a las tiendas.

De "corre en Expo Go" a una app publicada

💡 Hay tres "estados" de tu app, cada vez más cerca del usuario final:
  1. Expo Go — tu código corre dentro de la app oficial de Expo. Rápido, pero no instalable ni publicable.
  2. Build — un binario propio (.apk/.aab/.ipa) con tu ícono, tu nombre y tus permisos. Se instala como cualquier app.
  3. Publicada — ese binario subido a Google Play y/o la App Store, disponible para que cualquiera lo descargue.

El salto de (1) a (2) lo hace EAS Build. El salto de (2) a (3) lo hace EAS Submit. Vamos por partes.

Paso 0 — Configurar la identidad: app.json

Antes de compilar nada, tu app necesita una identidad: cómo se llama, qué ícono tiene, qué pantalla muestra al abrirse, qué permisos pide. Todo eso vive en app.json (o app.config.js si necesitás lógica/variables de entorno).

CampoQué define
nameNombre visible debajo del ícono en el celular.
slugIdentificador del proyecto dentro de Expo (sin espacios).
versionVersión visible para el usuario (ej. 1.0.0).
iconÍcono de la app (PNG cuadrado, normalmente 1024×1024).
splashPantalla que se muestra mientras la app carga (splash screen).
ios.bundleIdentifierID único de la app en iOS (ej. com.tuempresa.miapp).
android.packageID único de la app en Android (mismo formato).
android.permissionsPermisos que la app declara (cámara, ubicación, etc.).

Un app.json típico para un primer build:

{
  "expo": {
    "name": "Mi Primera App",
    "slug": "mi-primera-app",
    "version": "1.0.0",
    "icon": "./assets/icon.png",
    "splash": {
      "image": "./assets/splash.png",
      "resizeMode": "contain",
      "backgroundColor": "#0f172a"
    },
    "ios": {
      "bundleIdentifier": "com.tuempresa.miprimeraapp",
      "buildNumber": "1"
    },
    "android": {
      "package": "com.tuempresa.miprimeraapp",
      "versionCode": 1,
      "permissions": ["CAMERA", "ACCESS_FINE_LOCATION"]
    }
  }
}
📌 El bundleIdentifier (iOS) y el package (Android) son la identidad única de tu app. Una vez publicada, no se pueden cambiar: cambiarlos crea, a ojos de la store, una app totalmente distinta. Elegilos bien la primera vez (formato dominio invertido: com.tuempresa.miapp).
¿app.json o app.config.js? Usá app.json (JSON estático) mientras alcance. Pasá a app.config.js cuando necesites lógica: leer variables de entorno, cambiar el nombre según el perfil (ej. "Mi App (dev)" vs "Mi App"), o decidir el ícono según el entorno.

EAS — Expo Application Services

💡 EAS es el servicio en la nube de Expo que compila y publica tu app por vos. En lugar de instalar Android Studio y Xcode en tu máquina, EAS levanta máquinas en la nube, compila ahí, y te devuelve el binario listo. Tiene dos comandos estrella:
  • eas build — genera el binario (.apk/.aab para Android, .ipa para iOS).
  • eas submit — sube ese binario a Google Play / App Store.
🔍 Pensalo como una "fábrica remota". Vos mandás el plano (tu código + app.json + eas.json), la fábrica de Expo arma el producto (el binario) con sus propias máquinas, y te lo manda de vuelta por un link. No necesitás tener la maquinaria pesada en tu casa.
💎 El superpoder real: EAS compila para iOS sin que tengas una Mac. Normalmente generar un .ipa exige Xcode, que solo corre en macOS. Como EAS compila en la nube, podés sacar la app de iPhone desde una PC con Windows o Linux. Eso, antes, era imposible sin comprar una Mac.

Comandos para tu primer build

1. Iniciá sesión en tu cuenta de Expo. (Si no tenés cuenta, se crea gratis en expo.dev.)
npm install -g eas-cli   # instala la herramienta de línea de comandos
eas login
2. Configurá el proyecto para EAS. Esto crea el archivo eas.json con los perfiles de build.
eas build:configure
3. Generá un build de prueba para Android. El perfil preview produce un .apk fácil de instalar a mano:
eas build -p android --profile preview

El comando sube tu proyecto, compila en la nube (tardá unos minutos) y al final te da un link de descarga del .apk. Lo bajás al celular, lo instalás y ya tenés tu app, sin Expo Go de por medio.

Perfiles de build — eas.json

No todos los builds son iguales: uno es para que vos pruebes, otro para repartir entre testers, y otro es el que va a la store. Esos "sabores" se llaman perfiles y viven en eas.json.

PerfilPara qué sirveSalida típica (Android)
developmentBuild de desarrollo con herramientas de debug (dev client)..apk con dev tools
previewProbar la app "como la verá el usuario", repartir a testers..apk instalable
productionEl build final que se sube a las stores..aab (App Bundle)
 
{
  "build": {
    "development": {
      "developmentClient": true,
      "distribution": "internal"
    },
    "preview": {
      "distribution": "internal",
      "android": { "buildType": "apk" }
    },
    "production": {
      "android": { "buildType": "app-bundle" }
    }
  }
}
¿Por qué .apk vs .aab? El .apk es un instalable directo, ideal para probar a mano (le pasás el archivo a alguien y lo instala). El .aab (Android App Bundle) es el formato requerido por Google Play: la store lo procesa y genera el .apk óptimo para cada modelo de celular. Por eso preview usa .apk (probar) y production usa .aab (publicar).

Updates OTA — actualizar sin pasar por la store

💡 Un update OTA ("Over The Air") empuja una nueva versión del JavaScript y los assets directo al celular del usuario, sin que tenga que ir a la store a actualizar. La próxima vez que abre la app, descarga el cambio y listo. Es el mecanismo más rápido para corregir un bug o cambiar un texto: minutos, no días de revisión de la store.

Se publica con un solo comando:

eas update --branch production --message "Arreglo del texto del botón"
📌 OTA NO puede cambiar código nativo. Si agregás un módulo nativo nuevo (cámara, notificaciones push, un SDK que toca el sistema), cambiás permisos, o subís la versión nativa, OTA no alcanza: necesitás un build nuevo (eas build) y volver a subirlo a la store. OTA solo actualiza lo que es JS/assets, no el binario nativo que ya está instalado.
🔍 Pensalo como una página web vs el navegador. OTA es como recargar el contenido de la página: rápido, inmediato. Un build nuevo es como tener que reinstalar el navegador: solo hace falta cuando cambia algo de la base (el motor nativo), no el contenido.

Requisitos de las stores

Tener el binario no alcanza: cada tienda pide papeleo y materiales. Antes de apretar eas submit, asegurate de tener:

RequisitoGoogle Play (Android)App Store (iOS)
Cuenta de desarrolladorPago único (~US$25)Apple Developer: anual (~US$99/año)
Ícono de alta resoluciónSí (512×512)Sí (1024×1024)
ScreenshotsSí, varios tamañosSí, varios tamaños de dispositivo
Descripción + categoríaSíSí
Política de privacidadObligatoria (URL pública)Obligatoria + cuestionario de privacidad
Revisión humanaHoras a díasSuele ser más estricta

Una vez listo el material y la cuenta, el envío es un comando:

eas submit -p android --profile production
⚠️ La política de privacidad no es opcional. Ambas tiendas rechazan apps que piden permisos (cámara, ubicación, contactos) sin una política de privacidad publicada que explique qué datos se recogen y para qué. Tené una URL pública lista antes de enviar.
🚫 Un build roto en producción afecta a usuarios reales. Antes de subir a la store, probá el build de production en un dispositivo físico — no solo en Expo Go. Lo que corre en Expo Go puede comportarse distinto en un binario real (permisos, assets, configuración nativa). Verificá en el binario, no asumas.

Errores típicos al publicar

Compilar sin configurar ícono, splash ni permisos. Te queda una app con el ícono genérico de Expo y pantalla en blanco al abrir. Configurá icon, splash y permissions en app.json antes del primer build de verdad.
Creer que OTA actualiza código nativo. Publicás un eas update con un módulo nativo nuevo y los usuarios no ven el cambio (o la app crashea). El código nativo solo cambia con un build nuevo.
No incrementar la versión. Las stores rechazan un build si el versionCode (Android) o buildNumber (iOS) no es mayor que el ya publicado. Subí el número en cada envío.

Checkpoint — ¿lo tenés claro?

¿Qué diferencia hay entre eas build y eas submit?

eas build genera el binario en la nube (.apk/.aab para Android, .ipa para iOS). eas submit toma ese binario y lo sube a Google Play / App Store. Primero se construye, después se envía.

¿Puedo sacar la app de iPhone sin tener una Mac?

Sí. EAS compila en la nube, así que genera el .ipa de iOS sin que tengas Xcode ni macOS. Igual necesitás una cuenta de Apple Developer (paga, anual) para publicarla en la App Store.

Cambié un texto y un color. ¿Build nuevo o OTA?

OTA (eas update). Texto, colores y lógica JS son justo lo que OTA puede empujar al instante, sin pasar por la store. Solo necesitarías un build nuevo si tocaras código nativo, permisos o la versión nativa.

Ejercicios

  1. Editá tu app.json: poné un name propio, un slug, una version y un bundleIdentifier/package con formato com.tuempresa.miapp.
  2. Conseguí (o diseñá) un ícono PNG cuadrado y una imagen de splash, y enlazalos en icon y splash.
  3. Corré eas build:configure y abrí el eas.json generado. Identificá los perfiles development, preview y production.
  4. Generá un .apk con eas build -p android --profile preview, descargalo e instalalo en un celular Android real.
  5. Cambiá un texto de la app y publicá un update OTA con eas update. Reabrí la app instalada y verificá que el texto cambió sin reinstalar.

🧠 Autoevaluación

1. ¿Qué hace eas build?

eas build compila tu proyecto en la nube y te devuelve el binario. Subirlo a las stores es trabajo de eas submit; actualizar solo el JS es trabajo de eas update.

2. Agregaste un módulo nativo nuevo (notificaciones push). ¿Alcanza con un update OTA?

OTA empuja JavaScript y assets, no código nativo. Un módulo nativo nuevo (o cambiar permisos/versión nativa) requiere eas build y volver a subir a la store.

3. ¿Para qué sirve el perfil preview en eas.json?

preview produce un .apk fácil de instalar a mano para probar y repartir. El que va a la store es production (genera .aab); el debug del dev client es development.
